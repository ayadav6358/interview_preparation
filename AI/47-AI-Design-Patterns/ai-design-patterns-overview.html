1. What is this?

AI design patterns are the named, recurring architectural solutions for common LLM application problems: RAG, Router, ReAct, Planner/Executor, Supervisor, Reflection, Critic, Human-in-the-loop, Multi-agent, Event-driven agent, Agentic RAG, Memory pattern, and Tool-use pattern — each already covered in depth elsewhere in this knowledge base, consolidated here as a quick-reference catalog.

2. Why does it exist?

Having named patterns lets engineers communicate architecture quickly ("this is a Supervisor pattern with a Reflection step") instead of re-explaining from scratch every time — the same value proposition as the Gang of Four patterns in traditional software engineering, applied to LLM application architecture.

3. Why is it important?

Pattern fluency is directly tested in system design interviews ("which pattern would you use here and why") and speeds up real architecture discussions — this page is the single-page reference tying together agent/RAG patterns scattered across many earlier sections.

4. Where is it used?

Architecture discussions, system design interviews, any LLM application design decision.

5. Prerequisites

RAG, AI Agents, Agentic AI Architectures, Multi-Agent Systems.

6. The pattern catalog

PatternProblem → Solution
RAGLLM lacks fresh/private knowledge → retrieve relevant context and inject into prompt
RouterDifferent requests need different handling → classify and direct to the right handler
ReActComplex tasks need dynamic multi-step action → interleave reasoning and tool-calling, observing results
Planner/ExecutorComplex goals need upfront decomposition → separate planning from step-by-step execution
SupervisorDifferent sub-tasks need different expertise → coordinate specialist agents and integrate results
Reflection/CriticFirst-pass output may have errors → add a self-critique/revision pass
Human-in-the-loopSome actions are too risky for full autonomy → pause for explicit human approval
Multi-agentTask benefits from specialization/parallelism → decompose across multiple coordinated agents
Event-driven agentAgent must react to external events, not just user requests → trigger agent runs from event streams/webhooks
Agentic RAGSimple one-shot retrieval is insufficient → let an agent iteratively plan, retrieve, and refine
Memory patternContext window can't hold everything across sessions → externalize state to a persistent memory store
Tool-use patternLLM needs to take real-world actions → expose defined functions the model can request to call

7. Terminology

All terminology for these patterns is covered in depth in their dedicated sections: RAG, Advanced RAG (Agentic RAG), Tool Calling, AI Agents (ReAct), Agentic AI (Planner/Executor, Supervisor, Reflection), Agent Memory, Multi-Agent Systems, LangGraph (human-in-the-loop).

8. Architecture per pattern

RAG:               Query → Retrieve → Augment prompt → Generate
Router:            Query → Classify → Dispatch to handler A/B/C
ReAct:              Goal → [Reason → Act → Observe] loop → Answer
Planner/Executor:  Goal → Plan (steps) → Execute each step → (re-plan if needed)
Supervisor:        Task → Supervisor → [Specialist A | B | C] → Integrate
Reflection/Critic: Draft → Critique → Revise → (loop or finalize)
Human-in-the-loop: Propose action → Interrupt (await human) → Execute on approval
Event-driven:      External event → Trigger → Agent run → Action
Agentic RAG:       Query → Agent loop: [retrieve → evaluate → refine query → retrieve again] → Answer
Memory:            Session → Extract durable facts → Store → Retrieve in future sessions
Tool-use:          LLM decides tool → App executes → Result → LLM continues

9. How to choose a pattern

Start from the actual problem symptom: need external knowledge → RAG; need to route varied requests → Router; need dynamic multi-step tool use → ReAct/Tool-use; need upfront decomposition of a complex goal → Planner/Executor; need distinct specialized expertise → Supervisor/Multi-agent; need higher output reliability → Reflection/Critic; need safety on risky actions → Human-in-the-loop; need cross-session continuity → Memory pattern. Patterns compose — a real system often combines several (e.g., Agentic RAG + Reflection + Human-in-the-loop for a high-stakes research assistant).

10. Step-by-step: applying the catalog

  1. Identify the core problem symptom from the list above.
  2. Select the matching pattern(s) as a starting architecture.
  3. Check "when NOT to use" — confirm the added complexity is actually justified (see Agentic AI's "when not to use agents" guidance).
  4. Implement the simplest version first; add further patterns only if evaluation shows a measurable need.
  5. Document which patterns compose your final architecture for team communication.

11. Simple example

A customer-support bot combining Router (classify ticket type) + RAG (retrieve relevant docs per type) + Human-in-the-loop (escalate refunds over $100) — three patterns composed into one practical system.

12. Real-world example

A production research assistant combines Planner/Executor (decompose the research question), Agentic RAG (iterative retrieval per sub-question), Reflection (critique the draft synthesis), and Human-in-the-loop (require approval before publishing externally) — a four-pattern composition addressing complexity, knowledge-grounding, quality, and safety respectively.

13. Code example

# Router + RAG composition
def route_and_answer(query):
    category = classify(query)  # Router pattern
    if category == "policy_question":
        context = retrieve(query, index="policy_docs")  # RAG pattern
        return generate(query, context)
    elif category == "order_status":
        return lookup_order_tool(query)  # Tool-use pattern
    else:
        return escalate_to_human(query)  # Human-in-the-loop pattern

14. Advanced example (combining patterns)

# Agentic RAG + Reflection composed
def agentic_rag_with_reflection(query, max_refine=3):
    context = retrieve(query)
    for _ in range(max_refine):
        draft = generate(query, context)
        critique = critique_draft(draft, context)
        if "sufficient" in critique.lower():
            return draft
        query = refine_query(query, critique)  # iterate retrieval
        context = retrieve(query)
    return draft  # best effort after max refinements

15. Common mistakes

  • Applying a pattern because it's trendy ("let's make it agentic") rather than because the actual problem symptom calls for it.
  • Combining too many patterns without evaluating whether each addition earns its added complexity/cost.
  • Not recognizing that many "complex agent" problems are actually solved by a simpler pattern (e.g., Router) once properly diagnosed.

16. Best practices

  • Diagnose the actual problem symptom before selecting a pattern.
  • Start with the simplest adequate pattern; add complexity only with measured justification.
  • Use pattern names in team communication for faster, clearer architecture discussions.

17. Production considerations

Every pattern composition still needs the full production treatment covered elsewhere: evaluation, observability, security, cost monitoring — patterns describe structure, not operational readiness.

18. Security considerations

Tool-use and Human-in-the-loop patterns are your primary security control points — apply least-privilege scoping and approval gates consistently regardless of which other patterns surround them.

19. Performance considerations

Each additional pattern layer (Reflection, Multi-agent, Agentic RAG's iteration) adds latency — budget accordingly and use Adaptive-style routing to apply expensive patterns only when needed.

20. Cost considerations

Pattern composition directly multiplies LLM call count — estimate cost per composed pattern combination before committing to a complex multi-pattern architecture.

21. Debugging/troubleshooting

  • Unclear which pattern is causing a quality issue in a composed system: trace each pattern's contribution separately (see LLM Observability) to isolate the failing stage.
  • System feels over-engineered: revisit whether each composed pattern is still earning its complexity against a simpler baseline.

27. Interview Questions — Beginner

Q1. What problem does the Router pattern solve?
A. Different requests needing different handling — it classifies and directs each request to the right handler.
Q2. What problem does the Reflection/Critic pattern solve?
A. First-pass output may have errors — it adds a self-critique/revision pass to improve reliability.
Q3. What problem does the Memory pattern solve?
A. The context window can't hold everything across sessions — it externalizes state to a persistent memory store.
Q4. What's the difference between the RAG pattern and the Agentic RAG pattern?
A. RAG is a single retrieve-then-generate pass; Agentic RAG lets an agent iteratively plan, retrieve, and refine across multiple steps.
Q5. Why are named design patterns useful for team communication?
A. They let engineers quickly convey architecture ("this is a Supervisor pattern with Reflection") without re-explaining from scratch each time.
Q6. What problem does Human-in-the-loop solve?
A. Some actions are too risky for full autonomy, so it pauses for explicit human approval before proceeding.
Q7. Can patterns be combined in one system?
A. Yes — real systems often compose several patterns together (e.g., Router + RAG + Human-in-the-loop).
Q8. What problem does Planner/Executor solve?
A. Complex goals needing upfront decomposition before execution — separating planning from step-by-step execution.
Q9. Should you adopt a pattern just because it's trendy?
A. No — select patterns based on the actual problem symptom, not trends.
Q10. What does the Tool-use pattern enable?
A. The LLM taking real-world actions by requesting defined functions the application executes.

28. Interview Questions — Intermediate

Q1. How would you diagnose whether a complex problem actually needs the Supervisor/Multi-agent pattern versus a simpler Router pattern?
A. Check whether sub-tasks genuinely need distinct specialized reasoning/tools that benefit from separate, independently-prompted agents (Supervisor), versus simply needing to be dispatched to different but otherwise simple handlers (Router) — if a single handler per category suffices without needing agent-level coordination, Router is the simpler, sufficient choice.
Q2. Why might composing Reflection with Agentic RAG be particularly effective for high-stakes research tasks?
A. Agentic RAG improves retrieval thoroughness through iteration, while Reflection adds a quality check on the synthesized output itself — together they address both input quality (did we find the right information) and output quality (is the answer well-reasoned and consistent with that information), covering more failure modes than either alone.
Q3. What's a practical way to evaluate whether a pattern composition is "earning" its added complexity?
A. Benchmark the composed system against progressively simpler versions (remove one pattern at a time) on your evaluation set, measuring quality/cost/latency at each level — if removing a pattern doesn't measurably hurt quality, it wasn't earning its complexity and should be removed.
Q4. Why is the Event-driven agent pattern architecturally different from the other patterns in this catalog?
A. It's about the trigger mechanism (external events/webhooks initiating agent runs) rather than internal reasoning/coordination structure — it can be combined with any of the other patterns (RAG, ReAct, Supervisor) as the entry point, rather than being an alternative to them.
Q5. How would you explain the relationship between the Tool-use pattern and the ReAct pattern?
A. Tool-use is the mechanism (LLM requests a function call, app executes it); ReAct is the loop structure that uses tool-use repeatedly, interleaved with reasoning steps, to accomplish a multi-step task — ReAct is built on top of the Tool-use pattern, not a separate, independent mechanism.

29. Interview Questions — Advanced

Q1. How would you design a system that dynamically selects which pattern composition to apply based on request characteristics, rather than using a fixed composition for all traffic?
A. Implement an upfront lightweight classification step (similar to Adaptive RAG) that assesses request complexity/risk/type, then routes to a progressively more complex pattern composition only as needed — simple requests get just RAG or a direct answer, moderately complex ones get Agentic RAG, and high-risk ones get the full Reflection + Human-in-the-loop treatment — avoiding uniform worst-case cost/latency for all traffic.
Q2. What's a subtle interaction risk when composing Multi-agent (Supervisor) with Human-in-the-loop?
A. If approval gates are only applied at the Supervisor's final integration step but not within individual specialist agents' actions, a specialist could take an irreversible action before the human ever sees the Supervisor's summary — approval gating needs to be pushed down to wherever the actual risky action occurs, not just applied at the top-level coordination point.

30. Interview Questions — Senior/Architect

Q1. How would you train/onboard a team of engineers new to agentic AI to use this pattern catalog effectively in their own architecture decisions?
A. Teach the "diagnose symptom → select pattern" framework explicitly rather than pattern names in isolation, require a written justification (tied to measured evaluation results, not intuition) for every pattern added beyond the simplest baseline in design reviews, and maintain a few in-house reference implementations of key patterns (RAG, Router, Supervisor) that teams can study and adapt rather than each reinventing them from scratch.

31. Scenario-Based Questions

Scenario 1. A team proposes a 5-pattern composition (Router + Supervisor + Agentic RAG + Reflection + Multi-agent) for what turns out to be a simple FAQ-answering feature. What's your feedback?
A. Recommend starting from the simplest adequate pattern (likely just RAG, possibly with Router if there are genuinely distinct FAQ categories) and only adding further patterns if evaluation on real FAQ traffic shows a measurable gap — a simple FAQ task almost certainly doesn't need Multi-agent or Supervisor-level specialization.
Scenario 2. Your composed Agentic RAG + Reflection system is accurate but takes 15 seconds per response, frustrating users. How do you address this while preserving quality where it matters?
A. Add a complexity classifier (Adaptive-style routing) so simple queries skip the expensive Agentic RAG + Reflection path entirely (using plain RAG instead), reserving the slower, more thorough composition only for queries that actually need it — reducing average latency without sacrificing quality on the harder cases that justified the composition in the first place.

32. Quick revision notes

  • 12 core patterns: RAG, Router, ReAct, Planner/Executor, Supervisor, Reflection/Critic, Human-in-the-loop, Multi-agent, Event-driven, Agentic RAG, Memory, Tool-use.
  • Diagnose the problem symptom first, then select pattern(s).
  • Patterns compose — but each addition must earn its complexity/cost.
  • Start simple; add complexity only with measured evaluation justification.

33. Cheat sheet

RAG=knowledge, Router=dispatch, ReAct/Tool-use=dynamic action, Planner/Executor=decompose, Supervisor/Multi-agent=specialize, Reflection/Critic=quality pass, Human-in-the-loop=safety, Memory=cross-session state, Agentic RAG=iterative retrieval. Diagnose symptom → select → justify with evaluation.
