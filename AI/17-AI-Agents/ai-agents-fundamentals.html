1. What is this?

An AI agent is a system where an LLM autonomously decides a sequence of actions (tool calls, reasoning steps) to accomplish a goal, observing results and adapting its plan, rather than following a fixed, developer-defined sequence of steps.

2. Why does it exist?

Many real tasks can't be fully specified as a fixed pipeline in advance — the right next step depends on what's discovered along the way (a search result, an error, a user's clarification). Agents exist to let the LLM itself make that step-by-step decision, within a loop the application controls.

3. Why is it important?

"Agent" is one of the most overused and most interview-tested terms in 2026 AI engineering — being able to precisely define what makes something an agent (vs. a workflow vs. a simple LLM call) and when NOT to use one is a key differentiator in interviews and in avoiding over-engineered production systems.

4. Where is it used?

Coding assistants, research assistants, customer support automation, autonomous data analysis, any task requiring dynamic multi-step reasoning and tool use.

5. Prerequisites

Tool Calling, Advanced Prompting Patterns (CoT).

6. Core concepts

  • ReAct (Reason + Act): the foundational agent pattern — the model alternates between reasoning (thinking about what to do) and acting (calling a tool), observing results between steps.
  • Planning: the agent forms a multi-step plan before or during execution.
  • Observation: the agent incorporates tool/environment feedback into its next decision.
  • Reflection: the agent critiques its own previous output/plan and revises it.
  • Retry/self-correction: the agent recovers from errors by adjusting its approach, informed by the failure.
  • Memory: the agent retains relevant information across steps or sessions (see Agent Memory).

8. Architecture (ReAct loop)

Goal/Task
 → Reason: "What should I do next?"
 → Act: call a tool
 → Observe: tool result
 → Reason: "Does this complete the goal, or what's next?"
 → (repeat) ...
 → Final answer when goal is satisfied

9. How it works internally

At each iteration, the full conversation history (including all prior reasoning, tool calls, and observations) is sent back to the model, which generates the next reasoning step and/or tool call conditioned on everything so far — the "memory" of the agent's progress is just the growing context, unless externalized to a separate memory store for very long tasks (see Agent Memory).

10. Step-by-step: LLM app vs workflow vs agent

  1. LLM application: a single LLM call producing output from input — no loop, no dynamic branching.
  2. Workflow: a fixed, developer-defined sequence of steps (possibly including LLM calls), where the control flow is hardcoded in advance.
  3. Agent: the LLM itself decides the sequence of steps/actions dynamically at runtime, within a loop, based on the evolving situation.

11. Simple example

Task: "Find the weather in 3 cities and tell me which is warmest." An agent calls the weather tool 3 times (deciding to do so itself, in whatever order/pattern it chooses), compares results, and answers — versus a hardcoded workflow that would call the same tool exactly 3 times in a fixed, pre-written sequence regardless of what's discovered.

12. Real-world example

A coding agent (like this assistant) doesn't follow a fixed script — it reads files, searches code, decides what to edit, runs tests, and reacts to failures, with each next step determined dynamically by what it observes, which is the defining characteristic of an agent rather than a workflow.

13. Code example

def run_agent(goal: str, tools: dict, max_iterations=10):
    messages = [{"role": "user", "content": goal}]
    for i in range(max_iterations):
        response = client.messages.create(
            model="claude-sonnet-5", max_tokens=1000,
            tools=list(tools.values()), messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return response.content[0].text  # final answer
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = tools[block.name]["fn"](**block.input)
                tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(result)})
        messages.append({"role": "user", "content": tool_results})
    return "Max iterations reached without a final answer."

14. Advanced example (reflection)

def run_agent_with_reflection(goal, tools, max_iterations=10):
    result = run_agent(goal, tools, max_iterations)
    critique = client.messages.create(
        model="claude-sonnet-5", max_tokens=300,
        messages=[{"role": "user", "content":
            f"Critique this answer for the goal '{goal}':\n{result}\nAny errors or missing steps?"}],
    ).content[0].text
    if "no issues" not in critique.lower():
        # Feed critique back for a revision pass
        revised = run_agent(f"{goal}\n\nPrevious attempt: {result}\nIssues found: {critique}\nRevise.", tools, max_iterations)
        return revised
    return result

15. Common mistakes

  • Calling any multi-step LLM pipeline an "agent" even when the steps are fully fixed in advance (that's a workflow).
  • Using an agent for a task that's actually deterministic and better served by a fixed workflow (less latency/cost, more predictable).
  • No iteration limit, risking runaway cost on an edge case the agent can't resolve.
  • Not logging/tracing agent reasoning steps, making failures very hard to debug.

16. Best practices

  • Use a workflow instead of an agent whenever the task's steps are actually predictable/fixed — reserve agents for genuine dynamic decision-making needs.
  • Always set a maximum iteration limit.
  • Log full reasoning/tool-call traces for debugging and evaluation.
  • Add reflection/self-critique steps for higher-stakes tasks where a revision pass improves reliability.

17. Production considerations

Treat agent runs as a cost/latency variable, not fixed — track distribution of iteration counts and tool calls per task to catch regressions or runaway cases; add human-approval gates for high-risk actions.

18. Security considerations

Agents combine the "excessive agency" risk (too much autonomy/permission) with tool-call injection risks — apply tight tool permission scoping and treat all intermediate observations (including tool results) as potentially containing injected instructions if they include external/untrusted content.

19. Performance considerations

Each agent iteration is a full LLM round trip — latency scales with iteration count; minimize unnecessary steps via clear tool descriptions and task framing, and consider parallel tool calls where independent sub-tasks allow it.

20. Cost considerations

Agent cost is a function of (iterations × tokens per iteration) and is much harder to predict upfront than a single LLM call — budget for a distribution, not a point estimate, and cap worst-case cost via iteration limits.

21. Debugging/troubleshooting

  • Agent doesn't converge on an answer: check for ambiguous tool results or an unclear goal statement confusing the model about completion criteria.
  • Agent takes an unexpectedly roundabout path: review the full reasoning trace — often a tool description or ordering issue leads it astray.
  • High variance in iteration count across similar tasks: may indicate the task framing itself is ambiguous, not just model inconsistency.

27. Interview Questions — Beginner

Q1. What is an AI agent?
A. A system where an LLM autonomously decides a sequence of actions to accomplish a goal, adapting based on observed results, rather than following a fixed predefined sequence.
Q2. What does ReAct stand for?
A. Reason + Act — alternating between reasoning about what to do and taking an action (tool call), informed by observations.
Q3. What's the key difference between a workflow and an agent?
A. A workflow follows a fixed, developer-defined sequence of steps; an agent's LLM dynamically decides the sequence of actions at runtime.
Q4. What is reflection in the context of agents?
A. The agent critiquing its own previous output or plan and revising it based on that critique.
Q5. Why should agents have a maximum iteration limit?
A. To bound worst-case cost and latency in case the agent fails to converge on an answer.
Q6. Is every multi-step LLM pipeline an "agent"?
A. No — if the steps are fixed and predetermined, it's a workflow, not an agent.
Q7. What does "observation" mean in an agent loop?
A. The agent incorporating the result of its previous action (e.g., a tool's output) into its next decision.
Q8. What is a goal-based agent?
A. An agent operating toward a specified objective, deciding its own steps, rather than following a fixed script.
Q9. Should you always use an agent for multi-step tasks?
A. No — if the steps are predictable/fixed, a workflow is simpler, cheaper, and more predictable; reserve agents for genuine dynamic decision-making needs.
Q10. What provides an agent's "memory" of its progress within a single run?
A. The growing conversation history/context sent back to the model at each iteration.

28. Interview Questions — Intermediate

Q1. Why would you choose a workflow over an agent even when the task technically involves multiple LLM-assisted steps?
A. If the correct sequence of steps is known in advance regardless of intermediate results, a workflow is cheaper, faster, more predictable, and easier to debug than an agent, which incurs extra reasoning overhead and unpredictability for no benefit in that case.
Q2. How does reflection improve agent reliability, and what's its cost trade-off?
A. It catches errors or missed steps the initial pass made, improving final answer quality, but doubles (or more) the LLM calls per task, adding latency and cost — worth it for high-stakes tasks, not for simple/low-stakes ones.
Q3. Why is it important to log the full reasoning trace of an agent, not just its final answer?
A. Debugging agent failures requires understanding the sequence of decisions and observations leading to a wrong outcome — the final answer alone gives no insight into which step in the dynamic decision process went wrong.
Q4. What's a practical risk of giving an agent an ambiguous or overly broad goal statement?
A. The agent may take an unpredictable, inefficient, or incorrect path trying to interpret what "done" means, potentially looping or taking much longer/more expensive routes than a clearly-scoped goal would produce.
Q5. How would you measure whether an agent is actually more effective than a simpler workflow for a given task?
A. Compare success rate, cost, and latency on a representative evaluation set between the agent and an equivalent fixed workflow — if the workflow matches the agent's success rate at lower cost/latency, the task didn't actually need agentic dynamism.

29. Interview Questions — Advanced

Q1. How would you design an agent to recognize when it's stuck in an unproductive loop and change strategy rather than just hitting the iteration limit?
A. Track state/progress signals across iterations (e.g., repeated identical tool calls, no new information gained), and inject an explicit self-check prompt ("have you made progress in the last 2 steps? If not, try a different approach") when such signals are detected, rather than relying purely on a hard iteration cutoff.
Q2. What's the architectural tension between giving an agent more autonomy (fewer constraints) and production reliability requirements?
A. More autonomy increases the agent's ability to handle novel situations but also increases unpredictability, cost variance, and risk of undesired actions (excessive agency); production systems typically need to find a calibrated middle ground — enough autonomy to handle real task variability, with guardrails (tool permission scoping, iteration limits, human approval gates for risky actions) bounding the downside.

30. Interview Questions — Senior/Architect

Q1. A team wants to build an "agent" for a customer support task that's actually: classify ticket → look up order → draft response → send. How do you advise them?
A. Point out this is a fixed, predictable sequence — a workflow, not an agent — and building it as a hardcoded pipeline (possibly with LLM calls at the classification and drafting steps) will be cheaper, faster, and far easier to test/debug/monitor than an agentic implementation that adds unnecessary dynamic decision-making overhead for a task that doesn't need it.
Q2. Design the production safety architecture for a customer-facing autonomous agent that can take real actions (e.g., process refunds).
A. Scope tool permissions tightly to only the specific actions needed; require human approval for actions above a risk/value threshold (e.g., refunds over $X); log full reasoning and action traces for audit; set hard iteration and cost limits per session; add a reflection/verification pass before high-stakes actions execute; and continuously monitor success/error rates with alerting on anomalies.

31. Scenario-Based Questions

Scenario 1. Your "agent" for a document-processing pipeline always executes the exact same 4 steps in the same order regardless of input. Is it really an agent?
A. No — if the sequence never varies based on observed results, it's a workflow, just implemented using an LLM-call-capable framework; relabeling it doesn't change its actual nature, and simplifying it to an explicit fixed pipeline would likely reduce cost/latency with no loss of capability.
Scenario 2. An autonomous research agent occasionally runs for 50+ iterations on simple questions that should take 2-3. How do you fix this?
A. Investigate whether the goal framing or tool result format is ambiguous about "task complete" conditions, add explicit completion criteria to the prompt, and set a reasonable iteration limit with escalation (e.g., return best-effort partial answer) rather than silently running to the cap.

32. Quick revision notes

  • Agent = LLM dynamically decides action sequence; Workflow = fixed sequence; LLM app = single call.
  • ReAct = reason + act + observe, repeated.
  • Use agents only when the task genuinely needs dynamic decision-making.
  • Always bound iterations; log full reasoning traces.

33. Cheat sheet

LLM app = 1 call. Workflow = fixed steps. Agent = LLM decides steps dynamically (ReAct: reason → act → observe → repeat). Use the simplest type that solves the task — don't default to "agent" for predictable pipelines.
