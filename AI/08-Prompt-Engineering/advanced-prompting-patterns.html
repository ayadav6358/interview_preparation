1. What is this?

Beyond basic zero/few-shot prompting, advanced patterns — chain-of-thought (CoT), self-consistency, and task decomposition/prompt chaining — systematically improve reliability on complex reasoning, multi-step, and high-stakes tasks.

2. Why does it exist?

Simple prompting plateaus on genuinely hard, multi-step problems: jumping straight to an answer gives the model no room to "work through" a problem the way allocating more computation would help. These patterns exist to deliberately give the model more inference-time compute and structure to apply to hard problems.

3. Why is it important?

These patterns are the difference between a prompt that works on easy demo cases and one that holds up on genuinely hard production edge cases — critical for any system doing real reasoning (math, planning, multi-step logic, agentic decision-making).

4. Where is it used?

Reasoning-heavy agents, coding assistants, complex data-extraction pipelines, research/analysis tools, and any high-stakes decision support system.

6. Core patterns

  • Chain-of-thought (CoT): instructing the model to "think step by step" before giving a final answer.
  • Self-consistency: sampling multiple independent CoT completions and taking the majority/most consistent final answer.
  • Task decomposition / prompt chaining: splitting a complex task into an explicit pipeline of smaller, narrowly-scoped prompts.

7. Terminology

TermMeaning
Chain-of-thought (CoT)Explicit step-by-step reasoning generated before the final answer.
Self-consistencyMajority-vote across multiple independently sampled reasoning paths.
Task decompositionBreaking a complex task into smaller, independently verifiable sub-tasks/prompts.
Golden datasetA curated set of example inputs with known-correct expected outputs, used for evaluation.
LLM-as-judgeUsing a separate LLM call to score/evaluate the quality of another LLM's output.

8. Architecture

Chain-of-thought:      Question → [reasoning tokens] → Final answer

Self-consistency:      Question → sample N reasoning paths → majority vote → Final answer

Task decomposition:    Complex task → Prompt 1 (extract) → Prompt 2 (classify) → Prompt 3 (format) → Result

9. How it works internally

CoT improves performance because it lets the model allocate more generated tokens (more computation) to work through a problem rather than jumping straight to a guess — autoregressive generation means each token conditions on everything generated so far, so intermediate reasoning tokens genuinely inform the final answer. Self-consistency exploits the fact that errors in individual sampled reasoning paths tend to be somewhat independent, so majority voting across several samples cancels out some of that noise. Modern reasoning models internalize CoT-like behavior by default via dedicated training.

10. Step-by-step: prompt optimization workflow

  1. Write a baseline prompt and define a small evaluation set (golden examples with expected outputs).
  2. Run the prompt against the eval set, score it (exact match, LLM-as-judge, or rule-based checks).
  3. Iterate: add/adjust instructions, few-shot examples, formatting constraints, or CoT instructions.
  4. Re-run evaluation after every change — never tune a prompt "by feel" in production.
  5. Version prompts like code (e.g., in LangSmith, or just git) so regressions are traceable.

11. Simple example

Prompt: "A train leaves at 3:15pm and travels 180 miles at 60mph. What time does it arrive?" Adding "Think step by step" before asking for the final answer markedly improves accuracy on this kind of multi-step arithmetic compared to asking for the answer directly.

12. Real-world example

A legal-document review pipeline decomposes "review this contract for risks" into separate prompts: extract clauses → classify each clause's risk category → summarize risks per category → format final report — far more reliable than one giant "review this contract" prompt.

13. Code example

from anthropic import Anthropic
client = Anthropic()

prompt = """A train leaves at 3:15pm and travels 180 miles at 60mph.
Think step by step, then give the final answer as JSON: {"arrival_time": "..."}"""

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=400,
    messages=[{"role": "user", "content": prompt}],
)
print(response.content[0].text)

14. Advanced example

Self-consistency sampling for a hard reasoning question, trading cost for reliability:

from collections import Counter

def self_consistent_answer(question, n=5):
    answers = []
    for _ in range(n):
        resp = client.messages.create(
            model="claude-sonnet-5", max_tokens=400, temperature=0.7,
            messages=[{"role": "user", "content": f"{question}\nThink step by step, then state FINAL ANSWER: "}]
        )
        answers.append(extract_final_answer(resp.content[0].text))
    return Counter(answers).most_common(1)[0][0]

15. Common mistakes

  • Using self-consistency on every request regardless of cost/latency budget.
  • Assuming chain-of-thought output is always faithful to the model's actual internal process — it's a generated explanation, not necessarily a transparent trace.
  • Decomposing tasks too finely, adding unnecessary latency/cost for simple cases.
  • Tuning a prompt against a tiny or unrepresentative "golden set," causing it to overfit to those specific examples.

16. Best practices

  • Use CoT for genuinely multi-step reasoning tasks; skip it for simple lookups (adds unnecessary tokens/latency).
  • Reserve self-consistency for high-stakes, lower-volume decisions.
  • Keep decomposed sub-prompts narrowly scoped and independently testable.
  • Maintain a representative, regularly-refreshed golden evaluation set.

17. Production considerations

Treat prompts as code: store in version control, write an evaluation suite that runs in CI on prompt changes, track metrics over time, and gate deploys on eval regressions — not on someone feeling "this version sounds better."

18. Security considerations

Decomposed pipelines increase the number of context-injection surfaces (each sub-prompt's inputs); apply the same untrusted-content delimiting discipline at every stage, not just the first.

19. Performance considerations

CoT increases output tokens (and thus latency) compared to direct answers. Self-consistency multiplies latency by the sample count unless run in parallel. Task decomposition adds round-trip latency per additional LLM call in the chain — balance granularity against cumulative latency.

20. Cost considerations

Self-consistency multiplies token cost by N (sample count). Task decomposition multiplies the number of billed calls. Both should be reserved for cases where the quality/reliability gain clearly justifies the added spend — benchmark against a single-call baseline first.

21. Debugging/troubleshooting

  • CoT reasoning looks right but final answer is wrong: check the answer-extraction step — the model may be stating the final answer inconsistently with its own reasoning (a parsing/formatting issue, or a genuine reasoning-to-answer transcription error).
  • Self-consistency majority vote ties: increase sample count or add a tie-breaking criterion (e.g., shortest/most confident reasoning).
  • Decomposed pipeline produces inconsistent final output: check for schema mismatches between consecutive prompt stages (step 2 expecting a different format than step 1 produces).

24. Mini practical exercise

Take a multi-step math or logic question. Run it once with a direct-answer prompt and once with a "think step by step" prompt. Compare accuracy across 5 repeated trials of each.

25. Practical project

Self-Consistency Reasoning API: build an endpoint that accepts a hard reasoning question, internally samples N chain-of-thought completions, extracts and majority-votes the final answer, and returns both the answer and the agreement rate across samples (as a confidence proxy).

27. Interview Questions — Beginner

Q1. What is chain-of-thought prompting?
A. Asking the model to reason step by step before giving a final answer, which improves accuracy on multi-step problems.
Q2. What is self-consistency sampling?
A. Sampling multiple independent reasoning attempts for the same question and taking the majority/most common final answer.
Q3. What is task decomposition in prompting?
A. Breaking a complex task into a sequence of smaller, narrower prompts instead of one large prompt.
Q4. Why would chain-of-thought improve accuracy on a math problem?
A. It gives the model more generated tokens (more computation) to work through intermediate steps rather than guessing the final answer directly.
Q5. Does self-consistency cost more than a single call?
A. Yes — it multiplies cost and latency by the number of samples taken.
Q6. What's a golden dataset?
A. A curated set of example inputs with known-correct expected outputs, used to evaluate prompt/model quality.
Q7. What is LLM-as-judge?
A. Using a separate LLM call to score or evaluate the quality/correctness of another LLM's output.
Q8. Should you always use chain-of-thought, even for simple lookups?
A. No — it adds unnecessary tokens/latency for simple, non-reasoning tasks where a direct answer is already reliable.
Q9. Why should you never tune a prompt "by feel"?
A. Subjective impressions don't reliably indicate quality improvements across the full range of real inputs; only systematic evaluation against a representative test set does.
Q10. What should happen before deploying a prompt change to production?
A. Running it against an evaluation suite/golden dataset to confirm it doesn't regress quality compared to the current version.

28. Interview Questions — Intermediate

Q1. What's the trade-off of self-consistency sampling?
A. It improves accuracy on hard reasoning tasks by sampling multiple reasoning paths and taking a majority answer, but multiplies cost and latency by the number of samples — only worth it for high-stakes, lower-volume calls.
Q2. How do you prevent prompt engineering from becoming "untested, unversioned magic strings" in a production codebase?
A. Treat prompts as code: store them in version control, write an evaluation suite (golden dataset + scoring) that runs in CI on prompt changes, track metrics over time, and gate deploys on eval regressions.
Q3. Why might task decomposition improve reliability even if each sub-prompt individually isn't more "intelligent" than a combined prompt?
A. Each sub-task is narrower and easier to specify/verify correctly, reducing the chance the model drops or conflates instructions the way it might in one large, multi-part prompt — reliability comes from reduced task complexity per call, not increased model capability.
Q4. How would you decide the right number of samples (N) for self-consistency?
A. Start small (e.g., 3–5) and measure the marginal accuracy gain on your eval set as N increases; diminishing returns typically appear quickly, and N should be capped where additional cost no longer yields meaningful reliability improvement.
Q5. Why is "the reasoning looked plausible" not sufficient evidence that chain-of-thought improved correctness?
A. Generated reasoning can be plausible-sounding but not faithfully reflect the actual computation that produced the final answer, and plausible reasoning can still arrive at a wrong conclusion — correctness must be measured against ground truth, not reasoning plausibility.
Q6. What's a practical failure mode of task decomposition pipelines in production?
A. Schema/format mismatches between stages (step 2 expects a field format step 1 doesn't reliably produce), and compounding error/latency across many sequential calls — each stage needs its own validation, not just trust in the prior stage's output.
Q7. When would you choose LLM-as-judge over exact-match scoring for evaluation?
A. When outputs are open-ended/free-text (e.g., summaries, explanations) where there's no single "correct" string, but a rubric-based quality judgment is meaningful — exact match only works for tasks with a well-defined, narrow correct answer.
Q8. How would you reduce the latency cost of self-consistency in a user-facing product?
A. Run the N samples in parallel (concurrent API calls) rather than sequentially, so wall-clock latency approaches that of a single call rather than N times it, though billed cost still scales with N.
Q9. Why might a smaller golden evaluation set lead to a prompt that looks great in testing but underperforms on real traffic?
A. A small/unrepresentative set risks the prompt being tuned (even unintentionally) to quirks of those specific examples rather than the true distribution of real inputs — essentially overfitting the prompt to the eval set.
Q10. What's the relationship between task decomposition and the agent design patterns covered later (planner/executor)?
A. Task decomposition is the prompting-level foundation of agentic planning patterns — a planner/executor agent architecture is essentially task decomposition made dynamic and automated, with the model itself deciding how to split the work rather than a fixed, hand-designed pipeline.

29. Interview Questions — Advanced

Q1. Why doesn't chain-of-thought guarantee faithful reasoning, and how would you test for unfaithfulness?
A. The model generates reasoning text as just another sequence of plausible tokens — it can produce reasoning that sounds coherent but doesn't match the actual computation leading to the answer (post-hoc rationalization). Test by perturbing a problem's surface features while keeping the correct answer's logic intact and checking if the stated reasoning changes in ways inconsistent with genuine step-by-step derivation.
Q2. How would you architect an evaluation pipeline that catches prompt regressions across both exact-match and open-ended task types simultaneously?
A. Maintain separate scoring strategies per task type within one unified eval harness — exact/schema match for structured extraction tasks, rubric-based LLM-as-judge (with human-reviewed judge calibration) for open-ended generation — and aggregate pass/fail or score deltas across both into a single CI gate.
Q3. What's the architectural reasoning behind why task decomposition sometimes outperforms a single larger, more capable model given the same prompt?
A. Decomposition reduces each call's effective task complexity and instruction-following burden, which can matter more for reliability than raw model capability on a monolithic, multi-part task — a smaller model doing one narrow thing well per step can out-reliability a larger model trying to juggle everything in one pass, even if the larger model is "smarter" in aggregate.

30. Interview Questions — Senior/Architect

Q1. How would you decide, for a new complex feature, whether to use a single well-crafted prompt, chain-of-thought, self-consistency, or full task decomposition?
A. Start with the simplest (single prompt) and measure against an eval set; add CoT if the task is genuinely multi-step reasoning and simple prompting underperforms; add self-consistency only if the task is high-stakes/low-volume enough to justify N× cost; move to task decomposition when sub-tasks have meaningfully different, independently verifiable requirements — always justified by measured eval gaps, not by default complexity escalation.
Q2. Design a CI/CD pipeline for prompt changes across a team of 20 engineers building many LLM features.
A. Require every prompt change to run against its feature's golden eval set automatically on PR; block merge on score regressions beyond a defined threshold; version prompts alongside code in the same repo; maintain a shared library of evaluated patterns (CoT templates, decomposition scaffolds) so teams reuse proven structures instead of reinventing them; track production quality metrics post-deploy to catch eval-blind-spot regressions.
Q3. A stakeholder wants near-perfect reliability on a high-stakes reasoning task and is willing to pay for it. Design the most reliable (not necessarily cheapest) prompting architecture.
A. Combine task decomposition (narrow, verifiable sub-steps) with chain-of-thought at each reasoning-heavy step, self-consistency sampling (N≥5) on the final decision step, and a secondary LLM-as-judge verification pass cross-checking the final answer against the decomposed intermediate results — layering multiple reliability techniques since the budget constraint has been relaxed.

31. Scenario-Based Questions

Scenario 1. Your reasoning-heavy agent occasionally gives a wrong final answer despite seemingly correct-looking intermediate reasoning. How do you investigate?
A. Check the answer-extraction/transcription step for a mismatch between the stated reasoning and the final answer, and consider that the reasoning itself may be plausible-but-flawed (post-hoc rationalization) rather than genuinely derived — validate by testing self-consistency across multiple samples to see if the error is consistent or sampling-driven.
Scenario 2. Leadership wants to apply self-consistency sampling to every request to "maximize quality." What do you push back on?
A. Point out the N× cost/latency multiplier applies uniformly regardless of task difficulty — most requests likely don't need it; propose reserving self-consistency for a flagged subset of genuinely hard/high-stakes requests, informed by eval data on where it actually moves accuracy.
Scenario 3. A decomposed 4-step pipeline's final output quality is worse than the single-prompt version it replaced. How do you debug?
A. Instrument and log each stage's output individually, compare against expected intermediate results, and look for compounding errors (small mistakes at an early stage propagating and amplifying through later stages) or schema mismatches between consecutive steps — decomposition isn't automatically better and needs its own evaluation per stage.

32. Quick revision notes

  • CoT = step-by-step reasoning improves multi-step accuracy.
  • Self-consistency = sample+vote for higher reliability at higher cost.
  • Decomposition = chain small, testable prompts instead of one mega-prompt.
  • Always evaluate prompt changes against a golden set, never by feel.

33. Cheat sheet

CoT = step-by-step reasoning improves multi-step accuracy. Self-consistency = sample+vote for higher reliability at higher cost. Decomposition = chain small, testable prompts instead of one mega-prompt. Always evaluate prompt changes against a golden set, never by feel.
