1. What is this?

An AI gateway sits between your application and multiple LLM providers, offering a unified API, routing, fallback, load balancing, cost control, and observability — tools like LiteLLM, Portkey, and OpenRouter are the most widely used implementations.

2. Why does it exist?

Building your own provider abstraction layer (07-LLM-APIs-and-SDKs) solves part of the problem, but reimplementing routing, fallback, rate limiting, and cost tracking for every project is wasteful — AI gateways exist as the productized, reusable version of that abstraction layer.

3. Why is it important?

Gateways have become the standard infrastructure layer for any serious multi-provider or cost-conscious LLM deployment — understanding when to adopt one (versus building custom) is a practical architecture decision many teams face.

4. Where is it used?

Multi-provider production systems, cost-sensitive high-volume applications, teams needing centralized observability/control across many internal AI features.

5. Prerequisites

LLM APIs and SDKs, LLM Providers.

6. Core concepts

  • Unified API: one consistent request/response schema regardless of underlying provider.
  • Routing: directing requests to specific models/providers based on rules (cost, latency, task type).
  • Fallback: automatically switching to a backup provider/model on failure.
  • Load balancing: distributing requests across multiple API keys/providers to manage rate limits.
  • Cost control: budgets, spend tracking, and alerts per team/project/user.
  • Observability: built-in logging/tracing of all requests across providers in one place.

7. Terminology

TermMeaning
LiteLLMAn open-source library/proxy providing a unified API across 100+ LLM providers.
PortkeyA managed AI gateway platform with routing, caching, and observability features.
OpenRouterA unified API/marketplace for accessing many different models through one endpoint.
Virtual keyA gateway-issued API key mapping to underlying provider credentials, enabling centralized control without exposing raw provider keys.

9. How it works internally

Gateways implement a translation layer converting their unified request format into each specific provider's actual API schema, then normalizing the response back into a consistent format — this is the same provider-abstraction pattern covered in 07-LLM-APIs-and-SDKs, productized and extended with routing logic, centralized key management, and built-in observability so individual application teams don't each reimplement it.

10. Step-by-step: adopting a gateway

  1. Choose a gateway (self-hosted LiteLLM, managed Portkey, or OpenRouter) based on control/ops preference.
  2. Configure provider credentials centrally behind the gateway.
  3. Define routing/fallback rules (e.g., primary model → fallback model on failure).
  4. Point application code at the gateway's unified API instead of individual provider SDKs.
  5. Set up cost budgets/alerts and review the gateway's observability dashboard.

import litellm

response = litellm.completion(

12. Real-world example

A company routes all internal AI feature requests through a self-hosted LiteLLM proxy, giving every team a consistent API while centrally enforcing per-team budgets, automatic fallback to a secondary provider during outages, and unified cost dashboards across dozens of internal AI features — without each team building this infrastructure themselves.

15. Common mistakes

  • Building a custom provider abstraction from scratch when a mature gateway would save significant engineering time.
  • Not configuring fallback chains, losing the main benefit of gateway adoption during outages.
  • Ignoring the gateway's own latency overhead in latency-sensitive applications.
  • Exposing raw provider API keys to application code instead of using gateway-managed virtual keys.

16. Best practices

  • Use virtual keys issued by the gateway rather than distributing raw provider credentials.
  • Configure and test fallback chains explicitly, not just assume they work.
  • Set up cost budgets/alerts per team/project from day one.
  • Monitor the gateway's own added latency to ensure it's not a bottleneck.

17. Production considerations

A self-hosted gateway (LiteLLM proxy) becomes a critical piece of infrastructure itself — apply the same reliability engineering (redundancy, monitoring, scaling) as any other production service; a managed gateway (Portkey) shifts this operational burden to the vendor.

18. Security considerations

Centralizing provider credentials behind a gateway reduces credential sprawl (a security benefit) but makes the gateway itself a high-value target — secure it with the same rigor as any system holding sensitive API keys.

19. Performance considerations

A gateway adds a network hop and processing overhead — generally small relative to LLM call latency, but measure it explicitly for latency-sensitive applications rather than assuming it's negligible.

20. Cost considerations

Self-hosted gateways (LiteLLM) have no additional per-request fee beyond your own infrastructure cost; managed gateways (Portkey) typically charge based on usage — factor this into overall cost alongside the underlying LLM provider costs.

21. Debugging/troubleshooting

  • Fallback isn't triggering on provider failure: verify the fallback configuration and test it explicitly (e.g., by simulating a primary provider failure).
  • Unexpected added latency: profile the gateway's own processing time separately from the underlying provider's latency.
  • Cost tracking doesn't match actual provider bills: verify the gateway's pricing configuration is up to date with current provider rates.

27. Interview Questions — Beginner

Q1. What is an AI gateway?
A. A layer sitting between your application and multiple LLM providers, offering a unified API, routing, fallback, and observability.
Q2. Name three popular AI gateway tools.
A. LiteLLM, Portkey, and OpenRouter.
Q3. What problem does an AI gateway solve?
A. It avoids every application/team reimplementing provider abstraction, routing, fallback, and cost tracking individually.
Q4. What is a virtual key?
A. A gateway-issued API key mapping to underlying provider credentials, enabling centralized control without exposing raw provider keys.
Q5. What does routing mean in the context of an AI gateway?
A. Directing requests to specific models/providers based on rules like cost, latency, or task type.
Q6. What does fallback mean in this context?
A. Automatically switching to a backup provider/model if the primary one fails.
Q7. Is LiteLLM self-hosted or a managed service?
A. It can be used as a self-hosted proxy or as an SDK; it's open-source, unlike fully managed platforms.
Q8. Why would centralizing provider credentials behind a gateway be a security benefit?
A. It reduces credential sprawl across many applications/teams, concentrating control in one managed location.
Q9. Does an AI gateway add any latency?
A. Yes — a network hop and processing overhead, generally small but worth measuring explicitly.
Q10. What's a cost control feature a gateway might provide?
A. Spend budgets, tracking, and alerts per team/project/user.

28. Interview Questions — Intermediate

Q1. How does an AI gateway's translation layer work conceptually?
A. It converts a unified request format into each specific provider's actual API schema, then normalizes the response back into a consistent format — the same provider-abstraction pattern an individual team might build themselves, productized and reused across many consumers.
Q2. When would building a custom provider abstraction be preferable to adopting an existing gateway?
A. For very simple, single-provider applications where the overhead of adopting and operating a gateway isn't justified, or when highly specific custom routing logic isn't well supported by available gateway tools — most teams beyond a certain scale/complexity benefit from adopting rather than building, but very small projects may not need either.
Q3. Why should fallback configuration be explicitly tested rather than assumed to work?
A. Misconfigured fallback chains (wrong model names, missing credentials for the fallback) can silently fail exactly when needed most (during an actual outage) — explicit testing (simulating failures) verifies the safety net actually functions before you depend on it in a real incident.
Q4. What's a practical reason a self-hosted gateway like LiteLLM might be preferred over a managed one for a security-conscious enterprise?
A. Self-hosting keeps all request/response data and credential management within the company's own infrastructure boundary, avoiding sending potentially sensitive request content through a third-party managed service — relevant for compliance-sensitive use cases.
Q5. How would you use gateway-level routing to implement the cost-optimization "model routing" pattern discussed elsewhere in this knowledge base?
A. Configure routing rules in the gateway that direct requests to a fast/cheap model for simple/low-complexity tasks and a frontier model for complex tasks, centralizing this routing logic at the gateway layer rather than reimplementing it in every individual application.

29. Interview Questions — Advanced

Q1. How would you design a gateway deployment architecture that itself doesn't become a single point of failure for a company's entire AI infrastructure?
A. Deploy multiple redundant gateway instances behind a load balancer (if self-hosted), ensure the gateway's own failure mode degrades gracefully (e.g., falls back to direct provider calls if the gateway itself is unreachable, for critical paths), and monitor gateway health/latency as a first-class production dependency with its own alerting, just like any other critical infrastructure component.
Q2. What's a subtle risk of relying entirely on gateway-level cost tracking without independent verification against actual provider billing?
A. Gateway pricing configuration can drift out of sync with actual, potentially changing, provider rates, causing the gateway's reported cost to diverge from real billed cost — periodically reconcile gateway-reported spend against actual provider invoices to catch this drift.

30. Interview Questions — Senior/Architect

Q1. Design a company-wide AI gateway strategy for an organization with dozens of teams building independent AI features, balancing centralized control with team autonomy.
A. Deploy a centrally-managed, redundant self-hosted gateway (or adopt a managed platform) as the mandatory entry point for all production LLM calls; issue scoped virtual keys per team with individual budgets/rate limits; centralize fallback and routing policy defaults while allowing teams to override for specific needs; provide centralized observability dashboards per team and company-wide; and establish a change-management process for updating shared routing/fallback configuration that could affect multiple teams simultaneously.

31. Scenario-Based Questions

Scenario 1. During a provider outage, your fallback didn't trigger as expected, causing a production incident. What do you investigate?
A. Review the fallback configuration for errors (wrong model name, missing/expired fallback credentials), check gateway logs from the incident window to see what actually happened when the primary failed, and add this specific scenario to your fallback testing suite to prevent recurrence.
Scenario 2. Your gateway's reported monthly AI spend doesn't match the actual provider invoices, with provider invoices showing higher costs. What do you investigate?
A. Check if the gateway's pricing configuration is outdated relative to current provider rates, verify all actual usage is flowing through the gateway (uninstrumented direct calls bypassing it wouldn't be tracked), and reconcile discrepancies by auditing a sample of individual requests against both the gateway log and the provider's own billing detail.

32. Quick revision notes

  • AI gateway = unified API + routing + fallback + load balancing + cost control + observability.
  • LiteLLM (open-source/self-hosted), Portkey (managed), OpenRouter (managed marketplace).
  • Use virtual keys, not raw provider credentials, in application code.
  • Always test fallback explicitly; don't assume it works.
