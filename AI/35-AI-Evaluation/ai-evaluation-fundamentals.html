1. What is this?

AI evaluation is the discipline of systematically measuring LLM/RAG/agent quality against defined metrics and golden datasets — covering offline evaluation (pre-deployment, against curated test sets), online evaluation (production monitoring), human evaluation, and LLM-as-judge techniques.

2. Why does it exist?

"It looks good to me" is not a reliable way to assess or compare LLM application quality across prompt/model/retrieval changes — evaluation exists to replace subjective impressions with repeatable, quantifiable measurement, the same discipline classic ML has always required.

3. Why is it important?

Without evaluation, every prompt tweak, model upgrade, or RAG change is a gamble — evaluation is the foundation that makes iterative improvement and safe deployment of LLM systems possible, referenced throughout this entire knowledge base as "test against a golden set."

4. Where is it used?

Every serious LLM application: RAG systems, agents, prompt engineering workflows, model/provider migration decisions, continuous production monitoring.

5. Prerequisites

Advanced Prompting Patterns, RAG Fundamentals.

6. Core concepts

  • Offline evaluation: running the system against a static, curated dataset before deployment.
  • Online evaluation: measuring real production traffic/outcomes continuously after deployment.
  • Golden dataset: a curated set of representative inputs with known-correct/expected outputs.
  • LLM-as-judge: using a separate LLM call to score/evaluate another LLM's output against defined criteria.
  • Human evaluation: direct human judgment, the gold standard for subjective quality but expensive/slow to scale.
  • RAG metrics: faithfulness (is the answer supported by retrieved context), relevance, context precision/recall, answer correctness, retrieval quality.
  • Agent metrics: tool success rate, task completion rate, agent trajectory quality.

8. Architecture

Golden dataset (inputs + expected outputs/criteria)
 → Run system under test against each input
 → Score each output:
      - Exact/rule-based match (where applicable)
      - LLM-as-judge (for open-ended quality)
      - Human review (for highest-stakes/ambiguous cases)
 → Aggregate metrics → compare against baseline/previous version
 → Gate deployment on no regression (or require sign-off on regressions)

9. How it works internally (LLM-as-judge)

An LLM-as-judge call is given the original input, the system's output, and explicit scoring criteria/rubric (and often a reference answer), and asked to produce a score or pass/fail judgment with reasoning — this works because evaluating/critiquing a given answer is often an easier task for an LLM than generating the answer from scratch, though the judge itself requires calibration (validating its judgments against human-labeled examples) to trust its scores.

10. Step-by-step: building an eval pipeline

  1. Define what "good" means for your task — specific, measurable criteria.
  2. Curate a golden dataset of representative inputs (and reference outputs/criteria where feasible).
  3. Choose scoring methods: exact match where possible, LLM-as-judge for open-ended quality, human review for calibration/high-stakes cases.
  4. Run the pipeline, aggregate scores, and establish a baseline.
  5. Re-run on every meaningful change (prompt, model, retrieval) and compare against baseline.
  6. Extend to online evaluation: sample production traffic for ongoing quality monitoring.

11. Simple example

A golden dataset of 50 customer-support questions with reference answers; running a new prompt version against this set and scoring answer correctness via exact-match or LLM-as-judge before deploying the change.

12. Real-world example

A production RAG system uses Ragas to compute faithfulness and context precision/recall on a sample of real production queries weekly, alerting the team if faithfulness drops below a threshold — catching silent quality regressions from a provider model update or a retrieval pipeline change before they're reported by users.

13. Code example

def llm_judge(question, answer, context, reference=None):
    prompt = f"""Question: {question}
Context provided: {context}
Generated answer: {answer}
{"Reference answer: " + reference if reference else ""}

Rate the answer's faithfulness to the context on a scale 1-5 (5=fully supported, 1=unsupported/hallucinated).
Respond with just the number."""
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=10, temperature=0,
        messages=[{"role": "user", "content": prompt}],
    )
    return int(resp.content[0].text.strip())

def evaluate_golden_set(golden_set, rag_pipeline):
    scores = []
    for item in golden_set:
        answer, context = rag_pipeline(item["question"])
        score = llm_judge(item["question"], answer, context, item.get("reference"))
        scores.append(score)
    return sum(scores) / len(scores)

14. Advanced example (agent evaluation)

def evaluate_agent_trajectory(task, agent_run_log):
    tool_calls = [step for step in agent_run_log if step["type"] == "tool_call"]
    successful_calls = [c for c in tool_calls if c["result"]["success"]]
    tool_success_rate = len(successful_calls) / len(tool_calls) if tool_calls else 1.0

    completion_judge = client.messages.create(
        model="claude-sonnet-5", max_tokens=10, temperature=0,
        messages=[{"role": "user", "content":
            f"Task: {task}\nFinal result: {agent_run_log[-1]}\nWas the task fully completed? yes/no"}],
    ).content[0].text.strip().lower()

    return {"tool_success_rate": tool_success_rate, "task_completed": completion_judge == "yes",
            "num_steps": len(agent_run_log)}

15. Common mistakes

  • Shipping prompt/model/RAG changes without any evaluation, relying on subjective "looks fine" assessment.
  • Using too small or unrepresentative a golden dataset, overfitting improvements to it.
  • Trusting an uncalibrated LLM-as-judge without validating its judgments against human-labeled examples.
  • Only doing offline evaluation and never monitoring real production quality (online evaluation).

16. Best practices

  • Build a golden dataset early, even a small one — something is far better than nothing.
  • Calibrate LLM-as-judge against a sample of human-labeled judgments before trusting it at scale.
  • Combine offline evaluation (pre-deploy gate) with online evaluation (production monitoring).
  • Version and grow the golden dataset over time as new failure modes are discovered.

17. Production considerations

Gate deployments on evaluation results (no regression beyond a defined threshold); sample and continuously evaluate production traffic, not just a static pre-deploy test — real-world input distributions drift and golden sets alone won't catch everything.

18. Security considerations

Evaluation datasets containing real user data need the same privacy/access controls as any sensitive data; be cautious about what production content gets logged/sampled for evaluation purposes.

19. Performance considerations

LLM-as-judge evaluation adds its own LLM call cost/latency — run offline evaluation asynchronously (not blocking deployment pipelines unnecessarily) and sample (not evaluate 100% of) production traffic for online evaluation to manage cost.

20. Cost considerations

Evaluation itself has real LLM API costs (judge calls) — budget for this as part of the development/operations cost, and balance evaluation frequency/coverage against that cost.

21. Debugging/troubleshooting

  • Evaluation scores don't match intuitive quality assessment: the judge may be miscalibrated — review its scoring against a sample of manually-reviewed cases.
  • Golden dataset results look great but production complaints persist: the golden set likely doesn't represent real production input diversity — expand it with real failure cases.
  • Inconsistent evaluation scores across runs: ensure the judge call uses low/zero temperature for consistency.

27. Interview Questions — Beginner

Q1. What is a golden dataset?
A. A curated set of representative inputs with known-correct or expected outputs, used to evaluate system quality.
Q2. What is LLM-as-judge?
A. Using a separate LLM call to score or evaluate another LLM's output against defined criteria.
Q3. What's the difference between offline and online evaluation?
A. Offline evaluation runs against a static dataset before deployment; online evaluation measures real production traffic continuously after deployment.
Q4. What is faithfulness in RAG evaluation?
A. Whether every claim in a generated answer is actually supported by the retrieved context.
Q5. What is context precision?
A. Of the retrieved chunks, what fraction are actually relevant.
Q6. What is context recall?
A. Of the truly relevant chunks that exist, what fraction were actually retrieved.
Q7. Why shouldn't you trust an LLM-as-judge blindly?
A. It can be miscalibrated; its judgments should be validated against human-labeled examples before being trusted at scale.
Q8. Name one popular RAG evaluation library.
A. Ragas (or DeepEval).
Q9. What is tool success rate in agent evaluation?
A. The fraction of agent tool calls that executed successfully and achieved their intended effect.
Q10. Why is "it looks good to me" not a reliable evaluation method?
A. It's subjective, not repeatable, and doesn't scale to systematically compare changes across many examples.

28. Interview Questions — Intermediate

Q1. Why does LLM-as-judge often work well even though the judge model might make similar mistakes to the model being evaluated?
A. Evaluating/critiquing a given answer against explicit criteria is often an easier task than generating the answer from scratch, and providing the judge with the source context (for faithfulness checks) gives it a more constrained, verifiable task than open-ended generation — though this isn't foolproof, which is why calibration against human judgments matters.
Q2. Why might a system pass all offline golden-set evaluations but still receive user complaints in production?
A. The golden dataset may not represent the actual diversity/distribution of real production inputs — offline evaluation only catches what it was designed to test; online evaluation and continuous golden-set expansion from real failure cases are needed to catch gaps offline testing missed.
Q3. How would you calibrate an LLM-as-judge to trust its scores at scale?
A. Have humans independently score a sample of the same outputs the judge scored, compare agreement rates, and either adjust the judge's prompt/rubric to better align with human judgment or identify systematic biases (e.g., favoring longer answers) to correct for.
Q4. Why is context recall harder to measure than context precision in practice?
A. Precision only requires judging the relevance of what was actually retrieved; recall requires knowing the complete set of truly relevant documents that exist in the corpus for a given query — information that's often not fully known without exhaustive manual labeling, making recall estimation inherently harder.
Q5. What's a practical reason to version and grow your golden dataset over time rather than treating it as fixed?
A. Real production failure cases discovered over time represent genuine gaps in your original test coverage; incorporating them into the golden set prevents the same failure mode from silently regressing again in a future change, continuously strengthening the safety net.

29. Interview Questions — Advanced

Q1. How would you design an evaluation pipeline that catches regressions from a model provider's silent model update (not a change you made)?
A. Run scheduled (e.g., daily/weekly) evaluation against your golden set using the exact production model configuration, tracking scores over time even without any code changes on your side — a sudden score drop with no corresponding deployment on your end strongly suggests an upstream model behavior change, prompting investigation and potential pinning/rollback to a known-good model version.
Q2. What's a subtle risk of using the same model family for both generation and LLM-as-judge evaluation?
A. Shared biases/blind spots between generator and judge (the same model family might consistently misjudge the same types of errors it's also prone to making) can mask systematic quality issues; using a different model or model family for judging, or incorporating rule-based/human-validated checks for known failure patterns, provides more independent verification.

30. Interview Questions — Senior/Architect

Q1. Design a comprehensive evaluation strategy for a production multi-agent RAG platform spanning offline gating, online monitoring, and continuous golden-set improvement.
A. Offline: maintain golden sets per component (retrieval quality, generation faithfulness, agent task completion) gating every deployment with defined regression thresholds; online: continuously sample production traffic for the same metrics via LLM-as-judge, with alerting on metric drift; feedback loop: route flagged production failures (low scores, user complaints) into a review queue that feeds confirmed failure cases back into the golden datasets, growing test coverage organically from real-world gaps; and periodically recalibrate judges against fresh human-labeled samples to prevent judge drift over time.

31. Scenario-Based Questions

Scenario 1. Your evaluation pipeline shows consistently high scores, but a major production incident revealed the system confidently gave wrong answers for weeks. What went wrong with your evaluation strategy?
A. Likely an uncalibrated or too-lenient LLM-as-judge, an unrepresentative golden set missing the specific failure pattern, or no online evaluation catching the drift in real traffic — audit the judge's calibration against human review of the actual incident cases, and add the discovered failure pattern to the golden set and online monitoring.
Scenario 2. After a cloud LLM provider pushed a model update, your eval scores dropped 10% with zero code changes on your end. How do you respond?
A. Confirm the regression is genuinely tied to the model update (compare before/after on identical inputs), consider pinning to the previous model version if available while investigating, and communicate the finding to the provider/community if it represents a broader quality regression — this is exactly the scenario continuous scheduled evaluation is designed to catch.

32. Quick revision notes

  • Offline (pre-deploy gate) + online (production monitoring) evaluation, together.
  • Golden dataset + LLM-as-judge (calibrated) + human review for highest stakes.
  • RAG metrics: faithfulness, relevance, context precision/recall, answer correctness.
  • Agent metrics: tool success rate, task completion rate.
  • Grow golden sets from real production failure cases over time.

33. Cheat sheet

Golden dataset + LLM-as-judge (calibrated) + human review = offline gate. Sample production traffic = online monitoring. RAG: faithfulness, relevance, context precision/recall. Agents: tool success rate, task completion. Never ship without evaluation.
