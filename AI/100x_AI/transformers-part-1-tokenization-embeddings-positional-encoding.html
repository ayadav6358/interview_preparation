Transformers Part 1 — From Text to Attention: Tokenization, Embeddings & Positional Encoding

1. What is this?

This is the "input pipeline" of a Transformer — the three mechanical steps that turn raw human text into the structured, numeric, order-aware representation that self-attention (Part 2) actually operates on: (1) Tokenization — splitting text into subword units and assigning each a unique integer ID; (2) Embeddings — converting those arbitrary IDs into dense, meaning-encoding vectors; (3) Positional Encoding — injecting word-order/sequence information back in, since raw attention is otherwise "bag-of-words" and ignores order entirely.

2. Why does it exist?

Neural networks only operate on numbers, but language is text — this pipeline exists to bridge that gap without losing the two things that matter most about language: meaning (which word embeddings capture) and order (which positional encoding captures). Each of the three stages exists because a simpler, more obvious approach (character-level IDs, word-level IDs, or raw embeddings with no position) was tried first and found to fail in specific, instructive ways.

3. Why is it important?

Tokenization alone directly determines a model's context-window limits, API billing costs, and even its ability to do seemingly trivial tasks (like counting letters in a word) — most "why does the LLM fail at X" surprises trace back to tokenization. Embeddings and positional encoding are the literal first two computations inside every single Transformer forward pass, including every LLM API call you've ever made — understanding them is prerequisite to understanding attention, fine-tuning, or any deeper model internals.

4. Where is it used?

  • Every Transformer-based model's input stage: GPT, Claude, LLaMA, BERT, and all derivatives.
  • Prompt engineering and cost optimization — understanding tokenization directly informs how to write prompts that use fewer tokens.
  • Multilingual model design — tokenizer vocabulary choices directly affect cost/performance equity across languages.
  • The from-scratch MiniLLM build in Building & Training a Modern LLM from Scratch, which uses a (simpler, character-level) tokenizer plus a token embedding table plus RoPE as its positional-encoding mechanism.

6. Core concepts

ConceptOne-line definition
TokenizationSplitting text into discrete units (characters, words, or subwords) and mapping each to a unique integer ID.
Character-level tokenizationOne ID per character — simple but creates very long sequences and forces the model to re-learn vocabulary from scratch.
Word-level tokenizationOne ID per whole word — intuitive, but suffers vocabulary explosion (170,000+ English words) and fails on unseen/rare words (out-of-vocabulary).
Subword tokenizationThe "Goldilocks" middle ground — common words stay whole, rare/complex words split into meaningful fragments (e.g., "understanding" → "under" + "stand" + "ing"); modern standard.
Byte Pair Encoding (BPE)The algorithm that builds a subword vocabulary by starting from individual characters and iteratively merging the most frequent adjacent pair, until a target vocabulary size is reached.
EmbeddingA dense vector (hundreds of numbers) representing a token's meaning, looked up from a trained embedding matrix via its token ID.
Semantic vector arithmeticThe phenomenon where relationships between concepts are encoded as consistent vector offsets (e.g., king − man + woman ≈ queen).
Positional encodingA vector added to each token embedding to inject information about its position in the sequence, since attention is otherwise order-blind.
Sinusoidal positional encodingThe original Transformer's method: using sine/cosine waves of varying frequency per dimension to give every position a unique, generalizable "fingerprint."

7. Terminology

TermMeaning
Out-of-vocabulary (OOV)A word not present in a fixed vocabulary — word-level tokenizers fail/degrade on these; subword tokenizers largely avoid this by falling back to smaller fragments.
Token IDThe arbitrary integer index assigned to a token by the tokenizer, used to look up its row in the embedding matrix.
Embedding matrix / lookup tableA large trained matrix where row i is the embedding vector for token ID i — looking up a token's vector is a simple indexing operation.
Dense vectorA vector where most/all values are non-zero and meaningful (as opposed to a sparse one-hot vector) — embeddings are dense.
Permutation invarianceThe property where a function's output doesn't change if you reorder the input elements — raw attention/embeddings are permutation-invariant (bag-of-words) without positional encoding.
Token densityHow many tokens a given piece of text (in a given language) requires — directly affects cost and context-window usage.
t-SNEA dimensionality-reduction technique used to visualize high-dimensional embedding spaces (e.g., 768 dimensions) in 2D/3D for human inspection.

8. Architecture

Raw text: "The cat sat on the mat."
   ↓ Step 1: Tokenization (BPE / subword)
["The", " cat", " sat", " on", " the", " mat", "."]
   → Token IDs: [1996, 4937, 2938, 2006, 1996, 13523, 1012]
   ↓ Step 2: Embedding (lookup table)
each ID → 768-dim dense vector (e.g., ID 1996 → [0.12, -0.45, 0.88, ...])
   ↓ Step 3: Positional Encoding (sinusoidal, added to embedding)

   final input = token_embedding + positional_encoding, per token
   ↓
   → fed into Self-Attention (Part 2)

9. How it works internally

Tokenization (via Byte Pair Encoding) starts with every character as its own token, then iteratively finds and merges the single most frequent adjacent pair of tokens across the training corpus into one new token, repeating until a target vocabulary size (typically 30k–100k) is reached. This self-organizing process means frequent patterns (common words, common subwords like "-ing" or "under-") collapse into single tokens, while rare patterns stay fragmented into smaller pieces — giving the tokenizer graceful degradation on unseen/rare words instead of hard failure.

Embeddings work as a simple lookup: each token ID indexes directly into a row of a large trained matrix (e.g., 768 columns for a base model), and that row is the token's semantic vector. This vector is learned during training such that semantically similar tokens end up spatially close together (measured by vector distance/cosine similarity), and relationships between concepts are captured as consistent vector offsets — the famous king − man + woman ≈ queen result emerges because the "royalty" direction and the "gender" direction in the embedding space are each roughly consistent across many word pairs.

Positional encoding solves the fact that embeddings alone (and raw attention) are permutation-invariant — "The dog bit the man" and "The man bit the dog" would be seen as the exact same set of tokens without positional information. The original Transformer solution adds a vector built from sine and cosine waves of varying frequency (one wave-pair per embedding dimension) to each token's embedding; because each position gets a unique combination of sine/cosine values across all frequencies, every position has a distinct mathematical "fingerprint," and because the waves are mathematically related to each other, the model can learn to infer relative distance between positions, and the continuous nature of the waves lets it generalize to sequence lengths longer than it saw during training.

10. Step-by-step explanation

  1. Start with raw text: e.g., "Hello world".
  2. Tokenize via BPE: split into subword tokens (e.g., ["Hello", " world"]) and map each to its integer token ID (e.g., [15496, 995]).
  3. Recognize the arbitrary-ID problem: these IDs carry no inherent meaning — 15496 doesn't "know" it's a greeting.
  4. Embed each token ID: look up each ID's row in the trained embedding matrix, producing a dense vector (e.g., 768 dimensions) per token that does encode meaning.
  5. Recognize the order problem: embeddings (and raw attention) are permutation-invariant — a reordered sentence looks identical to the model without more information.
  6. Compute positional encodings: for each position (0, 1, 2, ...) in the sequence, compute a sinusoidal vector of the same dimensionality as the embeddings.
  7. Combine: add the positional encoding vector to each token's embedding vector, producing a final per-token vector that encodes both "what" the token is and "where" it is.
  8. Hand off to self-attention: these combined vectors are what the Transformer's attention layers (Part 2) actually operate on.

11. Simple example

The word "understanding" demonstrates all three tokenization strategies: character-level would need 13 separate tokens (one per letter); word-level would need exactly one token, but only if "understanding" already exists in the fixed vocabulary; subword (BPE) splits it into recognizable, meaningful pieces like ["under", "stand", "ing"] — three tokens that balance granularity and meaning, and that can still represent related unseen words like "standing" or "misunderstand" by recombining known subword pieces.

12. Real-world example

GPT-4's 128K context limit is a limit on tokens, not words or characters — in English this is roughly 1.3 tokens per word, but can be significantly higher for code or for lower-resource languages, which require more subword fragments per word because the tokenizer's vocabulary was trained predominantly on English/high-resource-language text. This directly and unevenly affects both API cost and effective context-window capacity across languages — a real production "language equity" consequence of a tokenization design decision.

13. Code example

import numpy as np

# Simplified embedding lookup (as a real model would do, minus training)
vocab_size, embed_dim = 50000, 768
embedding_matrix = np.random.randn(vocab_size, embed_dim) * 0.02  # trained in reality

def embed(token_ids):
    return embedding_matrix[token_ids]  # simple row lookup, shape: [seq_len, embed_dim]

token_ids = [15496, 995]   # "Hello", " world" (illustrative GPT-style IDs)
embeddings = embed(token_ids)
print("Embeddings shape:", embeddings.shape)   # (2, 768)

# Sinusoidal positional encoding (original Transformer formula)
def positional_encoding(seq_len, dim):
    pe = np.zeros((seq_len, dim))
    position = np.arange(seq_len)[:, None]
    div_term = np.exp(np.arange(0, dim, 2) * -(np.log(10000.0) / dim))
    pe[:, 0::2] = np.sin(position * div_term)
    pe[:, 1::2] = np.cos(position * div_term)
    return pe

pe = positional_encoding(seq_len=2, dim=embed_dim)
final_input = embeddings + pe   # combine meaning + position
print("Final input shape:", final_input.shape)   # (2, 768)

14. Advanced example

A minimal, from-scratch implementation of Byte Pair Encoding's core merge loop — demonstrating how a subword vocabulary self-organizes from character-level beginnings purely by frequency:

from collections import Counter

def get_pair_counts(corpus_tokens):
    pairs = Counter()
    for word_tokens in corpus_tokens:
        for i in range(len(word_tokens) - 1):
            pairs[(word_tokens[i], word_tokens[i + 1])] += 1
    return pairs

def merge_pair(pair, corpus_tokens):
    merged = "".join(pair)
    new_corpus = []
    for word_tokens in corpus_tokens:
        new_word, i = [], 0
        while i < len(word_tokens):
            if i < len(word_tokens) - 1 and (word_tokens[i], word_tokens[i+1]) == pair:
                new_word.append(merged)
                i += 2
            else:
                new_word.append(word_tokens[i])
                i += 1
        new_corpus.append(new_word)
    return new_corpus

# Start: every word as individual characters
corpus = [list(w) for w in ["low", "lower", "lowest", "slow", "slower"]]

for step in range(5):   # run 5 BPE merges
    pairs = get_pair_counts(corpus)
    if not pairs:
        break
    best_pair = max(pairs, key=pairs.get)
    corpus = merge_pair(best_pair, corpus)
    print(f"Merge {step+1}: {best_pair} -> {''.join(best_pair)}")

print("Final tokenized corpus:", corpus)
# Frequent patterns like "lo", "low", "er" self-organize into single tokens

15. Common mistakes

  • Assuming "1 word ≈ 1 token" when estimating context-window usage or API costs — subword tokenization means this ratio varies by language, domain (code vs. prose), and word rarity.
  • Expecting a model to reliably count letters within a word or reverse a word character-by-character — these tasks are hard for Transformers precisely because they see subword tokens, not individual characters.
  • Forgetting that positional encoding is necessary at all — without it, a Transformer's attention mechanism is mathematically permutation-invariant and cannot distinguish "the dog bit the man" from "the man bit the dog."
  • Treating embeddings as static, context-aware representations — the raw embedding (pre-attention) is the isolated, context-free meaning of a token; context-dependent meaning only emerges after self-attention (Part 2) processes it.
  • Assuming word-level tokenization would be "better" because it's more intuitive — it suffers vocabulary explosion (170,000+ English words → huge embedding matrices) and catastrophic failure on any out-of-vocabulary word.

16. Best practices

  • When estimating cost/context usage for a prompt, actually run it through the target model's tokenizer (e.g., tiktoken for OpenAI models) rather than estimating from word count.
  • When debugging strange model failures on character-level tasks (spelling, counting, reversing), consider whether tokenization — not model "intelligence" — is the root cause.
  • For multilingual applications, be aware that tokenizer vocabulary coverage directly affects both cost and quality per language — evaluate token density across your target languages, not just English.
  • Use subword tokenization (BPE or similar) as the default choice for any new text-processing pipeline — it balances vocabulary size, OOV robustness, and sequence length far better than character- or word-level alternatives.

17. Production considerations

Production LLM serving pipelines must count tokens (not characters or words) to enforce context-window limits and compute accurate request costs before or during generation — this requires using the exact tokenizer the target model was trained with, since different models use different vocabularies and will produce different token counts for identical text.

18. Security considerations

Tokenization boundaries can be exploited in prompt-injection or jailbreak attempts — splitting sensitive words across unexpected token boundaries, or using unicode/encoding tricks that tokenize unusually, has historically been used to bypass naive keyword-based content filters that operate on raw text rather than being aware of how the model actually perceives the tokenized input.

19. Performance considerations

Sequence length (in tokens, not characters) directly drives compute cost in self-attention, which scales quadratically with sequence length — a tokenizer that produces fewer tokens for the same text (better subword efficiency) directly reduces both training and inference compute cost, which is part of why subword tokenization beat character-level approaches (the "Step Problem": a 13-character word needs 13 processing steps at character level vs. 1-3 at subword level).

20. Cost considerations

API billing for virtually every commercial LLM is based on token counts, not characters or words — understanding tokenization directly translates into cost control: denser prompts (fewer, more information-rich tokens) cost less than verbose ones, and awareness of per-language token density matters for any multilingual product's unit economics.

21. Debugging/troubleshooting

  • Model fails at letter-counting or spelling tasks: expected behavior — the model sees subword tokens, not individual characters, so it has no direct access to a word's letter-by-letter composition unless that happens to align with token boundaries.
  • Prompt that "looks short" uses far more tokens than expected: check actual tokenization — code, non-English text, or unusual formatting/whitespace can tokenize far less efficiently than plain English prose.
  • Context window exceeded unexpectedly: count actual tokens (via the model's tokenizer) rather than estimating from word/character count — the 1.3 tokens/word rule of thumb is English-specific and approximate.
  • Model confuses word order (e.g., "who did what to whom"): if working with a custom/from-scratch architecture, verify positional encoding is actually being added to embeddings before attention — without it, order information is lost entirely.

27. Interview Questions — Beginner

Q1. Why can't neural networks process raw text directly?
A. Neural networks only operate on numbers; text must first be converted into a numeric representation via tokenization and embedding before any computation can happen.
Q2. What's the problem with character-level tokenization?
A. It creates very long sequences (e.g., 13 steps for "understanding") and forces the model to learn vocabulary, grammar, and meaning entirely from individual characters, which is highly inefficient.
Q3. What's the problem with word-level tokenization?
A. It requires a huge vocabulary (170,000+ English words), creating massive embedding matrices, and it fails on any word not in that fixed vocabulary (the out-of-vocabulary problem) — typos, slang, and rare terms all break it.
Q4. What is subword tokenization, and why is it the modern standard?
A. It splits text into units bigger than characters but smaller than whole words — common words stay whole, rare words break into meaningful fragments — balancing vocabulary size (30k–100k) against sequence length, avoiding both the character-level step problem and the word-level vocabulary explosion.
Q5. What is Byte Pair Encoding (BPE)?
A. An algorithm that builds a subword vocabulary by starting with individual characters and iteratively merging the most frequent adjacent pair of tokens into a new single token, repeating until a target vocabulary size is reached.
Q6. What is a word/token embedding?
A. A dense vector of numbers representing a token's meaning, looked up from a trained embedding matrix using the token's ID — semantically similar tokens end up with similar (close) vectors.
Q7. What does "king − man + woman ≈ queen" demonstrate?
A. That embeddings encode relationships between concepts as consistent vector offsets/directions — the same "gender" direction that separates man/woman also roughly separates king/queen.
Q8. Why is positional encoding necessary?
A. Because raw embeddings and attention are permutation-invariant (bag-of-words) — without positional information, "the dog bit the man" and "the man bit the dog" would look identical to the model, even though word order determines meaning.
Q9. How does the original Transformer encode position?
A. By adding a vector built from sine and cosine waves of varying frequency (per dimension) to each token's embedding — every position gets a unique combination of values, creating a distinct "fingerprint."
Q10. Why does GPT-4's context limit matter in tokens rather than words?
A. Because the model actually processes tokens (subword units), and the token-to-word ratio varies (roughly 1.3 tokens per English word, higher for code or other languages) — "words" isn't the unit the model or its context window actually operates on.

28. Interview Questions — Intermediate

Q1. Why does BPE's "self-organizing" merge process tend to produce linguistically meaningful subwords (like "under", "stand", "ing") even though it's purely frequency-driven with no linguistic rules?
A. Because linguistically meaningful units (common prefixes, suffixes, roots) are, by their nature, frequently recurring patterns across a large corpus — BPE's purely statistical "merge the most frequent adjacent pair" process ends up discovering many of the same units a linguist would identify by hand, simply because frequency and linguistic regularity are highly correlated in natural language, even though the algorithm has no explicit notion of morphology.
Q2. Why do strange model failures in letter-counting or word-reversal tasks trace back to tokenization rather than "lack of intelligence"?
A. Because the model's actual input units are subword tokens, not individual characters — a word like "strawberry" might be a single token or split into 2-3 subword tokens, and the model has no direct, reliable access to the individual character sequence within those tokens; it must infer character-level structure indirectly from training data patterns, which is unreliable, explaining why these specific task types fail disproportionately compared to tasks that operate at the token/word level the model actually perceives.
Q3. Explain mathematically why sinusoidal positional encoding allows the model to represent relative position as a linear function.
A. For sinusoidal encodings using sin/cos pairs at each frequency, there exists a fixed rotation-matrix-like linear transformation that maps the encoding at position p to the encoding at position p+k for any fixed offset k, due to standard trigonometric angle-addition identities (sin(p+k) and cos(p+k) can be expressed as linear combinations of sin(p), cos(p) for fixed k) — this means the relative offset between any two positions is linearly recoverable from their encodings, which is part of why this scheme was chosen: it makes learning to attend by relative position straightforward for the model, without needing to memorize all possible absolute position pairs.
Q4. Why is embedding described as the "isolated" or context-free representation of a token, and what does that limitation actually look like in practice?
A. The embedding lookup is a static operation — the same token ID always maps to the exact same vector regardless of surrounding context, so the word "bank" gets one fixed embedding whether it appears in "river bank" or "savings bank"; disambiguating between those meanings based on context is specifically the job of the self-attention layers that come after embedding + positional encoding (Part 2), not something embeddings alone can do.
Q5. Why does adding (rather than concatenating) positional encoding to the token embedding work, given that it seems to "mix" two different kinds of information into the same vector space?
A. Because the embedding space has enough dimensionality (hundreds of dimensions) that the learned token-meaning directions and the fixed position-encoding directions can coexist largely orthogonally — in practice, training allows the model's subsequent layers to learn to disentangle and separately make use of both signals from the single combined vector, and addition (vs. concatenation) keeps the dimensionality fixed, which is computationally convenient and was empirically validated to work well in the original Transformer architecture.

29. Interview Questions — Advanced

Q1. The deck notes sinusoidal positional encoding requires "no learned parameters." What's the practical trade-off of fixed vs. learned positional encodings, and why might a production LLM choose one over the other?
A. Fixed (sinusoidal) encodings have the theoretical advantage of generalizing to sequence lengths beyond what was seen in training, since the sine/cosine functions are defined continuously for any position value, and they add zero extra trainable parameters; learned positional embeddings (a trainable lookup table per position, as used in original BERT/GPT-2) can in principle fit the specific positional patterns most useful for the training data/task better than a fixed mathematical scheme, but they fail to generalize beyond the maximum sequence length seen in training (there's no learned vector for position 10,000 if training only ever saw up to position 2,048). Many modern production LLMs instead use Rotary Positional Embeddings (RoPE, see Building & Training a Modern LLM from Scratch), which combine properties of both: a fixed mathematical scheme (no extra parameters) that's applied via rotation directly to Query/Key vectors inside attention (rather than added to the input embedding), empirically shown to generalize better to longer contexts than either sinusoidal or learned absolute positional encoding.
Q2. How would you design a tokenizer to minimize the "language equity" cost/performance disparity the deck raises, without retraining the entire underlying LLM?
A. The core lever is the training corpus used to build the BPE vocabulary itself — if the corpus is predominantly English, high-resource-language text and subwords dominate the frequency statistics that drive BPE merges, so lower-resource languages end up systematically under-represented in the vocabulary and must fall back to much finer-grained (more numerous) subword splits; building the BPE vocabulary from a more balanced, multilingual corpus (with deliberate per-language sampling weights rather than naive frequency-proportional sampling, which would still favor high-resource languages) directly produces more efficient, equitable per-language tokenization without touching the downstream model architecture at all — this is a tokenizer-training-time decision, fully decoupled from the LLM's own training.

30. Interview Questions — Senior/Architect

Q1. You're designing a domain-specific LLM (e.g., for legal or medical text) and need to decide whether to use an existing general-purpose tokenizer (e.g., GPT-4's) or train a custom one. Walk through the trade-offs.
A. A custom tokenizer trained on in-domain text (legal contracts, medical records) will typically achieve much better token efficiency on domain-specific vocabulary (specialized terminology, Latin medical/legal phrases, boilerplate clauses) that a general-purpose tokenizer would otherwise fragment into many inefficient subword pieces — this directly reduces both inference cost and effective context-window usage for domain documents. However, a custom tokenizer requires retraining (or at minimum fine-tuning) any model from scratch with the new vocabulary, since embedding matrices and token IDs are tokenizer-specific and incompatible across vocabularies — you can't swap tokenizers on an already-pretrained model without retraining the embedding and output layers at minimum. The practical default for most teams is to start with an existing general-purpose tokenizer (leveraging a pretrained base model) unless domain token-efficiency losses are measured to be severe enough (e.g., via a token-count audit on representative in-domain documents) to justify the retraining cost of a custom vocabulary — this is a build-vs-reuse cost/benefit decision, not a technical requirement.

31. Scenario-Based Questions

Scenario 1. Your product serves users in both English and a lower-resource language, and you notice the lower-resource-language users are hitting context-window limits far more often on equivalent-length conversations. What's the likely root cause, and what are your options?
A. Likely root cause: the tokenizer's vocabulary (built predominantly from English/high-resource text) requires more subword tokens per word of the lower-resource language, consuming context-window budget faster for equivalent semantic content — the deck's "Language Equity" issue manifesting directly in product UX. Options: measure actual token-density differences across languages to confirm, consider a tokenizer with better multilingual vocabulary coverage (if switching models is feasible), or as a stopgap, surface token-usage warnings earlier for affected languages and consider per-language context-window budgets in UX design.
Scenario 2. A teammate proposes switching your production model's tokenizer mid-deployment to reduce costs, without retraining the model. What do you tell them?
A. This isn't possible without retraining — a model's embedding matrix and output (un-embedding) layer are indexed by the specific tokenizer's vocabulary and token IDs it was trained with; swapping tokenizers changes what each token ID means, making the existing trained embeddings and all downstream weights meaningless for the new ID scheme. Cost reduction via tokenization would instead need to come from prompt-engineering (reducing token-inefficient phrasing/formatting) or, for a larger investment, training a new model from scratch (or at least retraining the embedding/output layers) with the more efficient tokenizer.
Scenario 3. A custom Transformer implementation your team built shows the model performing identically regardless of input word order during early testing. What's the most likely bug, given this deck?
A. Most likely bug: positional encoding is either missing, not being correctly added to the token embeddings before being passed into attention, or is being added but then accidentally dropped/overwritten somewhere in the pipeline — without positional information, attention and embeddings are mathematically permutation-invariant, exactly matching the described symptom (identical behavior regardless of word order), so this is the first thing to check and verify in the forward pass.

32. Quick revision notes

  • Neural networks need numbers; text needs translating via tokenization → embedding → positional encoding.
  • Character-level tokenization: too granular, long sequences, inefficient ("Step Problem").
  • Word-level tokenization: vocabulary explosion (170k+ words), fails on out-of-vocabulary words.
  • Subword tokenization (BPE): the modern standard, 30k–100k vocabulary, balances granularity.
  • BPE algorithm: start with characters → iteratively merge most frequent adjacent pair → repeat to target vocab size.
  • Embeddings: dense vectors from a lookup table; similar meaning = close vectors; relationships = consistent offsets (king−man+woman≈queen).
  • Embeddings alone are context-free/isolated — context-aware meaning comes later, from self-attention.
  • Attention/embeddings are permutation-invariant (bag-of-words) without positional encoding.
  • Sinusoidal positional encoding: sine/cosine waves per dimension, unique fingerprint per position, no learned parameters, generalizes to longer sequences.
  • Final Transformer input = token embedding + positional encoding, combined per token.
  • Tokenization directly drives context-window limits, API cost, and multilingual cost/performance equity.

33. Cheat sheet

Pipeline: text → tokenize (BPE, subword) → token IDs → embed (lookup, dense vectors, captures meaning) → + positional encoding (sin/cos, captures order) → ready for attention. Char-level=too granular. Word-level=vocab explosion + OOV fails. Subword=Goldilocks. No positional encoding = bag-of-words, order lost. 1 word ≈ 1.3 English tokens, varies by language/domain.
