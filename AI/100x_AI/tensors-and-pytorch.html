1. What is this?

This is the mathematical and tooling foundation underneath everything covered so far: scalars, vectors, matrices, and tensors as a single generalizing concept (just "how many dimensions"); matrix multiplication as the one operation that secretly powers neural network forward passes, backpropagation, and Transformer attention; and PyTorch — the library that represents all of this as tensors, accelerates it on GPUs, and automatically computes gradients via autograd, so you never have to hand-derive calculus for a real model.

2. Why does it exist?

Every formula seen in earlier material — weights * inputs + bias, backprop(gradients), Q = X * Wq, attention = softmax(Q * K.T) * V — was secretly the same underlying operation (matrix multiplication) dressed up in different variable names. This material exists to pull back that curtain explicitly, and then to introduce PyTorch as the practical tool that makes working with these operations at scale (thousands to billions of numbers, differentiated automatically, run on GPUs) feasible without writing raw linear algebra and manual calculus by hand.

3. Why is it important?

Tensor shapes are the single most common source of real bugs when building or debugging any deep learning model — understanding shape notation ([batch, heads, tokens, dim]) lets you "read" any model's code or error messages. Understanding autograd specifically demystifies .backward(), zero_grad(), and no_grad() — calls every PyTorch training loop uses, that are otherwise easy to treat as unexplained incantations.

4. Where is it used?

  • Every deep learning framework's internals (PyTorch, TensorFlow, JAX) — tensors and matrix multiplication are the universal substrate.
  • GPU/accelerator hardware design — matrix multiplication's "embarrassingly parallel" nature is literally why GPUs (and later, TPUs) became the standard hardware for AI.
  • Every from-scratch model build in this course, including Building & Training a Modern LLM from Scratch, which is built entirely in PyTorch using nn.Module, tensors, and autograd.
  • Production ML engineering roles — reading/debugging tensor shape mismatches is one of the most common daily tasks for anyone implementing or fine-tuning models.

MatrixA grid of numbers arranged in rows and columns — 2 dimensions (e.g., a weight matrix).
TensorThe generalization of all of the above — an N-dimensional array; scalar=0D tensor, vector=1D tensor, matrix=2D tensor, and 3D/4D/5D+ tensors handle batches, sequences, attention heads, etc.

Matrix multiplication (MatMul)The core operation of deep learning — computes a new matrix/vector from two inputs; underlies forward passes, backpropagation, and attention.
Dot productThe atomic operation inside matrix multiplication — multiplies corresponding elements of two vectors and sums them; conceptually measures similarity/alignment between two vectors.

PyTorchThe standard deep learning framework (used by OpenAI, Anthropic, Google DeepMind, Tesla) providing GPU-accelerated tensors, automatic differentiation (autograd), and high-level model-building blocks (nn.Module).

7. Terminology

TermMeaning

.shapeA tensor attribute returning its dimensions/sizes, e.g., torch.Size([2, 3, 4]).
@ operator / torch.matmul()PyTorch's matrix multiplication operator — requires inner dimensions to match: (a, b) @ (b, c) → (a, c).

BroadcastingPyTorch's automatic "stretching" of a smaller tensor to match a larger tensor's shape during element-wise operations, when dimensions are equal or one of them is 1.

nn.Linear(in, out)A fully-connected layer — internally stores a weight matrix (shape [out, in]) and bias vector, computing output = input @ weight.T + bias.

8. Architecture

Scalar (0D)  →  Vector (1D)  →  Matrix (2D)  →  Tensor (3D, 4D, 5D...)
   number         list            grid           cube / hypercube

Deep learning tensor shapes, by example:
  One sentence, 3 tokens, 768-dim embeddings → [3, 768]        (2D)
  A batch of 8 such sentences                → [8, 3, 768]     (3D)
  Multi-head attention, 12 heads, 64-dim/head → [8, 12, 3, 64]  (4D)

Matrix multiplication is EVERYWHERE in a model:
  Forward Pass:      X @ W                   (learned transformations)
  Backpropagation:   dL/dY @ W.T              (computing gradients)
  Attention:          Q @ K.T                  (measuring similarity)
  Word Embeddings:    One-hot @ W_embed        (looking up meaning)

PyTorch's 5-line training pattern (identical from MNIST to GPT-4):
  1. Forward Pass    → y_pred = model(x_batch)
  2. Compute Loss    → loss = criterion(y_pred, y_batch)
  3. Clear Gradients → optimizer.zero_grad()
  4. Backward Pass   → loss.backward()
  5. Update Weights  → optimizer.step()

9. How it works internally

A matrix multiplied by a vector is not just data storage — it's a transformation machine. The matrix [[0,-1],[1,0]] applied to the vector [1,0] (pointing right) produces [0,1] (pointing up) — the matrix rotated the vector 90°. Other matrices scale, stretch/squish, reflect, or project vectors; in a neural network, the weight matrices the model "learns" during training are exactly this — the model is searching for the specific transformation matrices that map input data (e.g., image pixels) to correct outputs (e.g., digit labels). Matrix multiplication itself is built from repeated dot products: each output cell is the dot product of a row from the first matrix and a column from the second, and a dot product's value measures how aligned/similar two vectors are — which is exactly why attention = softmax(Q @ K.T) * V works: Q @ K.T computes a dot product (similarity score) between every pair of tokens' Query and Key vectors, and the learned W matrices (Wq, Wk, Wv) rotate raw embeddings into a space where "relevant" and "pointing in a similar direction" become mathematically the same thing.

Inside PyTorch, every tensor stores two things: the actual numbers, and metadata (shape, device, dtype) telling PyTorch how to interpret that data. When a tensor is created with requires_grad=True, PyTorch begins recording every operation performed on it into a dynamic computation graph. Calling .backward() on a final output traverses that graph in reverse, applying the chain rule at every step (exactly like the manual backpropagation from Neural Networks from Scratch) to compute the gradient of every tensor that contributed to the output — this is autograd, and it is specifically why PyTorch exists: it replaces error-prone, hand-derived calculus with one reliable, automatic call.

10. Step-by-step explanation

  1. Recognize the hidden pattern: every formula from Neural Networks (weights * inputs + bias) and Transformers (Q = X * Wq, attention = softmax(Q * K.T) * V) is matrix multiplication.
  2. Build up the tensor hierarchy: scalar (0D) → vector (1D) → matrix (2D) → tensor (3D+), understanding each as "what if we keep adding dimensions?"
  3. Understand matrices as transformations: a matrix times a vector produces a new, transformed vector (rotation, scaling, etc.) — not just storage.
  4. Learn matrix multiplication's rule: inner dimensions must match: (a, b) @ (b, c) → (a, c).
  5. Understand the dot product as the atomic unit: element-wise multiply then sum — conceptually measures similarity/alignment between two vectors.
  6. Connect to GPUs: matrix multiplication is "embarrassingly parallel" (every output cell can be computed independently and simultaneously), which is exactly what GPU architecture (thousands of simple cores) is built for.
  7. Install the tool: PyTorch represents all of this as tensors, moves them to GPU via .to(device), and performs matrix multiplication via @ or torch.matmul().
  8. Understand autograd: set requires_grad=True, perform operations, call .backward() — PyTorch automatically computes every gradient via the chain rule, replacing manual backpropagation.
  9. Build a model with nn.Module: declare layers (each one a learned matrix transformation) in __init__, define the data flow in forward().
  10. Run the universal 5-line training loop: forward pass → compute loss → zero_grad() → backward() → optimizer.step() — identical in structure whether training a toy MNIST classifier or a GPT-4-scale model.

11. Simple example

Rotating a vector 90° via matrix multiplication: the vector [1, 0] (pointing right) multiplied by the matrix [[0, -1], [1, 0]] produces [0, 1] (pointing up) — a concrete, visualizable demonstration that "a matrix is a transformation machine," not just a static grid of numbers.

12. Real-world example

Training an MNIST digit classifier (as in the deck's live-demo walkthrough) is literally four matrix transformations in sequence: a [28,28] image is flattened to [784], transformed by a learned [784,128] weight matrix into [128] features, passed through ReLU, then transformed by a second learned [128,10] weight matrix into [10] digit scores — "training" is nothing more than search for the specific values inside those two weight matrices that correctly map pixel patterns to digit labels, achievable to ~98% accuracy in under 60 seconds on a GPU.

13. Code example

import torch

# Scalars, vectors, matrices, and tensors — all the same underlying type
x = torch.tensor(5.0)                       # 0D: scalar
v = torch.tensor([1.0, 2.0, 3.0])            # 1D: vector
m = torch.tensor([[1, 2], [3, 4]])           # 2D: matrix
t = torch.zeros(2, 3, 4)                     # 3D+: tensor
print(t.shape)                               # torch.Size([2, 3, 4])

# Matrix multiplication — the @ operator
A = torch.randn(3, 4)        # Shape: [3, 4]
B = torch.randn(4, 5)        # Shape: [4, 5]
C = A @ B                    # Shape: [3, 5]  (inner dims 4, 4 must match)
C_alt = torch.matmul(A, B)   # equivalent explicit call

# GPU acceleration — the one line that matters
device = "cuda" if torch.cuda.is_available() else "cpu"
A = A.to(device)
B = B.to(device)
C = A @ B                    # now runs on GPU, up to 100x faster

14. Advanced example

Autograd in action — automatic differentiation computing a derivative with one call, then building a full trainable model with nn.Module and the universal 5-line training loop:

import torch
import torch.nn as nn

# --- Autograd basics ---
x = torch.tensor(2.0, requires_grad=True)   # track this tensor
y = x**2 + 5                                 # y = x^2 + 5
y.backward()                                 # compute dy/dx automatically
print(x.grad)                                # tensor(4.0)  (dy/dx = 2x = 2*2)

# --- A real model with nn.Module ---
class SimpleNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = nn.Linear(784, 128)   # weight matrix: [128, 784]
        self.relu = nn.ReLU()
        self.layer2 = nn.Linear(128, 10)    # weight matrix: [10, 128]

    def forward(self, x):
        x = self.layer1(x)
        x = self.relu(x)
        x = self.layer2(x)
        return x

model = SimpleNet()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
criterion = nn.CrossEntropyLoss()

x_batch = torch.randn(32, 784)              # batch of 32 flattened 28x28 images
y_batch = torch.randint(0, 10, (32,))       # batch of 32 digit labels

for epoch in range(10):
    y_pred = model(x_batch)                  # 1. Forward Pass
    loss = criterion(y_pred, y_batch)        # 2. Compute Loss
    optimizer.zero_grad()                    # 3. Clear Old Gradients
    loss.backward()                          # 4. Backward Pass (autograd)
    optimizer.step()                         # 5. Update Weights
    print(f"epoch {epoch}, loss {loss.item():.4f}")

15. Common mistakes

  • Forgetting optimizer.zero_grad() — PyTorch accumulates (adds to) gradients by default across .backward() calls, so skipping this makes gradients silently pile up and training diverge/"explode."
  • Confusing .view() with .permute() — .view() only reinterprets shape (total elements must stay the same, and the underlying memory layout must support it), while .permute() actually reorders axes; using the wrong one produces silently wrong (not erroring) results in some cases.
  • Mismatching matrix multiplication dimensions — A @ B requires A's last dimension to equal B's second-to-last dimension; shape mismatches here are among the most common PyTorch runtime errors.
  • Forgetting to move both the model and the data to the same device (.to(device)) — a model on GPU cannot operate on CPU tensors, and vice versa, producing a device-mismatch error.
  • Not wrapping inference/evaluation code in torch.no_grad() — this wastes memory and compute building an unnecessary computation graph when gradients won't be used.
  • Treating tensor shape as an afterthought rather than the primary thing to check first when debugging — nearly every cryptic PyTorch error traces back to a shape mismatch somewhere in the pipeline.

16. Best practices

  • Print and verify .shape liberally while building or debugging any model — shape is "everything," as the deck states, and understanding it lets you read any unfamiliar model's code.
  • Always pair optimizer.zero_grad(), loss.backward(), and optimizer.step() together in that order inside every training loop — this is the universal, non-negotiable pattern.
  • Use torch.no_grad() around any inference/evaluation code where gradients aren't needed, to save memory and compute.
  • Move both model and data to the same device early and consistently, rather than scattered .to(device) calls throughout the code.
  • Default to nn.Module + its standard __init__/forward pattern for any custom model — it's the idiomatic, expected structure across the entire PyTorch ecosystem.

17. Production considerations

Production training pipelines run this exact 5-line pattern across many GPUs simultaneously (data/model parallelism), with mixed-precision tensors (fp16/bf16) to reduce memory and increase throughput, and gradient accumulation across multiple forward/backward passes before a single optimizer step when the desired batch size exceeds what fits in GPU memory — all built on the same fundamental autograd and matrix multiplication mechanics covered here.

18. Security considerations

Not directly covered in this conceptual material; a practical note: loading PyTorch model checkpoints with torch.load() can execute arbitrary code if the file is untrusted (it uses Python's pickle format by default) — always set weights_only=True or verify the source of any checkpoint file before loading it.

19. Performance considerations

Matrix multiplication is "embarrassingly parallel" — every output cell can be computed independently and simultaneously — which is precisely why GPUs (thousands of simple cores optimized for parallel tasks) outperform CPUs (8–16 complex cores optimized for sequential tasks) by up to 100x for large matrix math; moving tensors to GPU via .to(device) is the single highest-leverage performance action available for most deep learning code.

20. Cost considerations

GPU compute is the dominant cost driver in training and serving deep learning models — the 100x speedup from GPU-accelerated matrix multiplication directly translates to proportionally lower wall-clock training time and cloud compute cost versus running equivalent operations on CPU; efficient shape/memory management (avoiding unnecessary large intermediate tensors, using appropriate batch sizes) further reduces GPU memory and cost requirements.

21. Debugging/troubleshooting

  • "RuntimeError: size mismatch" during matrix multiplication: check that inner dimensions actually match — (a, b) @ (c, d) requires b == c; print both tensors' .shape to diagnose.
  • Model loss explodes / becomes NaN after a few steps: check first whether optimizer.zero_grad() is missing or misplaced — accumulated gradients from skipped zeroing is a very common cause.
  • "RuntimeError: expected all tensors to be on the same device": ensure both the model (model.to(device)) and every input tensor (x.to(device)) are moved to the same device before any operation between them.
  • Unexpected/garbage values after .view(): verify the tensor is contiguous in memory (use .contiguous() before .view() if it followed a .permute() or .transpose()) and that the total element count truly matches the target shape.
  • Out-of-memory (OOM) errors on GPU: check for accidentally retaining the computation graph during inference (wrap in torch.no_grad()), reduce batch size, or verify intermediate tensors aren't unnecessarily large relative to available GPU memory.

27. Interview Questions — Beginner

Q1. What is a tensor, in relation to scalars, vectors, and matrices?
A. A tensor is the generalization of all of them — a scalar is a 0D tensor (single number), a vector is a 1D tensor (list of numbers), a matrix is a 2D tensor (grid of numbers), and tensors extend this to 3D, 4D, or higher dimensions.
Q2. What does it mean to say "a matrix is a transformation"?
A. Multiplying a vector by a matrix produces a different, transformed vector — the matrix can rotate, scale, stretch, reflect, or otherwise reshape the input, rather than just storing data passively.
Q3. What is the rule for matrix multiplication dimensions?
A. The inner dimensions must match: a matrix of shape (a, b) can be multiplied by one of shape (b, c), producing a result of shape (a, c).
Q4. What is a dot product, conceptually?
A. Multiplying corresponding elements of two vectors and summing the results — conceptually, it measures similarity/alignment: a high value means the vectors point in a similar direction, a low or zero value means they don't.
Q5. Why are GPUs so much faster than CPUs for deep learning?
A. Matrix multiplication is "embarrassingly parallel" — every output cell can be computed independently at the same time — and GPUs have thousands of simple cores built exactly for this kind of parallel task, versus a CPU's 8–16 complex cores optimized for sequential logic.
Q6. What is PyTorch?
A. The standard deep learning framework used by organizations like OpenAI, Anthropic, Google DeepMind, and Tesla — it provides GPU-accelerated tensors, automatic differentiation (autograd), and high-level model-building blocks (nn.Module).
Q7. What does requires_grad=True do?
A. It tells PyTorch to start tracking every operation performed on that tensor, building a computation graph so gradients can later be computed automatically via .backward().
Q8. Why must you call optimizer.zero_grad() before loss.backward() in a training loop?
A. Because PyTorch accumulates (adds to) gradients by default across multiple .backward() calls — without clearing them first, gradients from previous steps would incorrectly pile up on top of the current step's gradients.
Q9. What is the purpose of torch.no_grad()?
A. It tells PyTorch to stop tracking operations (no computation graph is built), which is used during inference/evaluation to save memory and compute since gradients aren't needed at that point.
Q10. What does nn.Linear(784, 128) actually store internally?
A. A weight matrix of shape [128, 784] and a bias vector of shape [128] — passing data through it computes input @ weight.T + bias.

28. Interview Questions — Intermediate

Q1. Explain how the Transformer attention formula softmax(Q @ K.T) * V is "just" matrix multiplication and dot products.
A. Q @ K.T computes, for every pair of tokens, the dot product between that token's Query vector and every other token's Key vector — since a dot product measures directional similarity, this produces a matrix of "how relevant is token j to token i" scores; softmax normalizes these into attention weights, and multiplying by V computes a weighted sum (another matrix multiplication) of Value vectors according to those weights — the entire mechanism reduces to two matrix multiplications and a normalization, with the Q/K/V projection matrices (Wq, Wk, Wv) being the learned parameters that determine what "relevant" means for the model.
Q2. What's the practical difference between .view() and .permute(), and why does .permute() sometimes require .contiguous() before a subsequent .view()?
A. .view() reinterprets a tensor's shape while keeping the same underlying linear memory layout and the same total number of elements (e.g., flattening [8,3,768] into [24,768]); .permute() actually reorders the tensor's axes (e.g., swapping heads and tokens), which changes how the data is conceptually laid out but does so via a view with different strides rather than physically moving memory — this can leave the tensor non-contiguous in memory, and .view() requires a contiguous memory layout to safely reinterpret shape, so .contiguous() is needed to physically reorder the underlying memory first.
Q3. Why does PyTorch build a "dynamic" computation graph rather than a static one?
A. PyTorch builds the graph on the fly as operations actually execute in Python (define-by-run), rather than requiring the entire computation to be pre-defined/compiled ahead of time (define-and-run, as older TensorFlow 1.x did) — this lets you use ordinary Python control flow (if-statements, loops, debugging with print statements) directly inside model code, at some cost to the ahead-of-time optimization opportunities a static graph would allow.
Q4. How does broadcasting let you add a matrix and a vector of different shapes, and what's the rule governing when it's valid?
A. PyTorch "stretches" the smaller tensor to match the larger one's shape without actually copying data in memory — e.g., adding a [4] vector to a [3,4] matrix conceptually adds that vector to every row; the rule is that, comparing shapes from the rightmost dimension inward, each pair of dimensions must either be equal or one of them must be 1 (or absent) for broadcasting to be valid.
Q5. Why is understanding tensor shape described as "if you understand shape, you can read any model"?
A. A tensor's shape directly encodes the semantic structure of the data at that point in the model — e.g., [8, 12, 3, 64] immediately tells you batch size (8), number of attention heads (12), sequence length (3), and per-head dimension (64) — so tracing shapes through a model's forward pass reveals exactly what transformation is happening at each step, even without deep familiarity with that specific architecture's code.

29. Interview Questions — Advanced

Q1. Why is the statement "every computation in a modern AI model is essentially a series of matrix multiplications" both true and an oversimplification? What else is actually involved?
A. It's true in the sense that the dominant, most computationally expensive operations (linear layers, attention's Q@K.T and the weighted-sum-by-V, embedding lookups via one-hot@W_embed) are indeed matrix multiplications, and this is why GPU-style parallel hardware is the right fit for AI workloads. It's an oversimplification because non-matmul operations are also essential and non-trivial: non-linear activation functions (ReLU, GELU, softmax) are element-wise, not matrix operations, and are precisely what prevents a deep network from mathematically collapsing into a single linear layer (per the Neural Networks material); normalization layers (LayerNorm/RMSNorm) involve mean/variance computation, not matrix multiplication; and the overall architecture design (how layers are composed, residual connections, attention masking) is a separate design layer on top of the raw linear algebra. The matmul-centric framing is pedagogically useful and computationally accurate for where the FLOPs go, but the activations, normalization, and architecture choices are equally necessary for a model to actually learn anything useful.
Q2. Explain, mechanically, how autograd's reverse-mode automatic differentiation relates to the manual backpropagation math from the Neural Networks material, and why reverse mode specifically is efficient for deep learning.
A. Autograd's .backward() performs exactly the same chain-rule-based gradient computation as manual backpropagation — PyTorch's computation graph records each operation (e.g., **2, then +5) as a node, and .backward() traverses this graph from the output back to each input, at each step multiplying the local derivative of that operation by the accumulated gradient from downstream (exactly the chain rule). Reverse-mode differentiation is specifically efficient for deep learning because a typical model has many inputs (millions/billions of parameters) but a single scalar output (the loss) — reverse mode computes the gradient of that one output with respect to all inputs in a single backward traversal, with cost roughly proportional to one additional forward pass, whereas forward-mode differentiation would require a separate pass per input parameter, making it computationally infeasible at the scale of modern neural networks.

30. Interview Questions — Senior/Architect

Q1. You're onboarding a strong software engineer with no deep learning background onto an ML infrastructure team. How would you use this material's "it's all matrix multiplication" framing to accelerate their ramp-up, and where would you deliberately go beyond it?
A. I'd start exactly where this material does: show them that the formulas in neural networks and Transformers they'll see in code (weight updates, attention) are all instances of one operation (matrix multiplication, built from dot products), and that PyTorch's tensor/autograd abstractions exist specifically to make that operation fast (GPU-parallel) and differentiable (automatic gradients) without hand-derived calculus — this framing gives an experienced engineer a fast, accurate mental model instead of treating ML code as unfamiliar magic. I'd deliberately go beyond it quickly into: (1) shape-debugging as a practical skill, since that's where most real bugs live day-to-day; (2) the role of non-linear activations and normalization, which the matmul framing can understate; (3) memory/performance considerations specific to infra work — mixed precision, gradient checkpointing, distributed training strategies — since an infra engineer needs these even though they're outside this introductory material's scope. The goal is using the matmul framing as a fast on-ramp to correct intuition, then layering in the practical, infra-specific depth their role actually requires.

31. Scenario-Based Questions

Scenario 1. A teammate's training script runs fine for one epoch, then the loss suddenly becomes NaN on epoch two. What's the first thing you check, based on this material?
A. First check whether optimizer.zero_grad() is present and correctly placed before loss.backward() in the training loop — the deck explicitly flags this as the single most common cause of exploding/NaN losses, since gradients accumulate (add up) across steps by default if not cleared, compounding until the loss destabilizes.
Scenario 2. Your team's custom attention implementation throws a shape-mismatch error after a .permute() call that worked fine in isolation during testing. What's the likely issue?
A. Likely issue: a subsequent .view() call after the .permute() without first calling .contiguous() — .permute() reorders axes via strides without physically rearranging memory, leaving the tensor non-contiguous, and .view() requires contiguous memory to safely reinterpret shape; the fix is inserting .contiguous() between the .permute() and the .view() call.
Scenario 3. A junior engineer asks why their model trains correctly on CPU but throws a device-mismatch error only after they tried to "speed it up" by moving the model to GPU. What's your diagnosis?
A. Diagnosis: they moved the model to GPU (model.to(device)) but forgot to also move the input data/batches to the same device — PyTorch requires every tensor involved in an operation to be on the same device, so a GPU model receiving CPU tensors (or vice versa) throws a device-mismatch error; the fix is ensuring both the model and every batch of data are consistently moved to the same device before any forward pass.

32. Quick revision notes

  • Scalar=0D, Vector=1D, Matrix=2D, Tensor=generalization to N dimensions.
  • A matrix is a transformation (rotate/scale/stretch/reflect), not just storage.
  • Matrix multiplication rule: (a,b) @ (b,c) → (a,c) — inner dimensions must match.
  • Dot product = element-wise multiply + sum = similarity measure.
  • Forward pass, backprop, and attention are all fundamentally matrix multiplication.
  • GPUs beat CPUs here because matmul is "embarrassingly parallel" (every cell computed independently).
  • PyTorch tensors store data + metadata (shape, device); .shape tells you everything.
  • .view() reinterprets shape (same memory); .permute() reorders axes; broadcasting auto-stretches compatible shapes.
  • Autograd: requires_grad=True → PyTorch tracks ops → .backward() computes all gradients via the chain rule, automatically.
  • Always: zero_grad() → backward() → step(), in that order, every training step.
  • torch.no_grad() for inference (no graph, saves memory/compute).
  • Universal 5-line training loop: forward → loss → zero_grad → backward → step. Same from MNIST to GPT-4.

33. Cheat sheet

Tensor hierarchy: scalar(0D)→vector(1D)→matrix(2D)→tensor(ND). Matrix = transformation machine. MatMul rule: (a,b)@(b,c)→(a,c). Dot product = similarity. GPU wins because matmul is parallel. PyTorch: tensor = data+metadata. requires_grad=True → track ops → .backward() = auto gradients. Always zero_grad() before backward(). no_grad() for inference. 5-line loop: forward→loss→zero_grad→backward→step.
