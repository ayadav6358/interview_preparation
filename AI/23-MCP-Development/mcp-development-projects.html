1. What is this?

Hands-on MCP server development: building a simple server, defining tools/resources/prompts, connecting to a database and a REST API, and using an agent (including LangGraph) to consume MCP tools — progressing from the simplest possible server to realistic production integrations.

2. Why build these projects?

Reading MCP Fundamentals explains the protocol; building servers surfaces the real engineering decisions — schema design, error handling, authentication, and how an agent framework actually consumes MCP tools in practice.

3. Why is it important?

Building MCP servers is now a commonly requested skill for AI engineering roles — companies increasingly want their internal systems exposed to AI tools via MCP rather than one-off integrations.

4. Where is it used?

Internal developer tooling, coding agent integrations, enterprise data/system connectors.

5. Prerequisites

MCP Fundamentals, Python for AI.

9. How it works internally

FastMCP (the common high-level SDK pattern) handles the protocol-level JSON-RPC handshake, discovery responses, and message routing automatically — developers just decorate plain Python functions with `@mcp.tool()`, `@mcp.resource()`, or `@mcp.prompt()`, and the SDK introspects their type hints/docstrings to generate the schema the client needs for discovery.

10. Step-by-step: database-connected server

  1. Set up the database connection (e.g., Postgres via psycopg2).
  2. Define tools wrapping specific, scoped queries (not a generic "run any SQL" tool).
  3. Validate all tool arguments before building any SQL query (parameterized queries only).
  4. Return structured results (not raw DB rows) matching a defined output schema.
  5. Add error handling returning informative messages on query failure.

11. Simple example (MCP tool)

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("calculator")

@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers."""
    return a + b

if __name__ == "__main__":
    mcp.run(transport="stdio")

12. Real-world example

A company builds an internal MCP server exposing scoped tools like `get_employee_pto_balance(employee_id)` (backed by their HR database) and `search_internal_docs(query)` (backed by their knowledge base), letting any MCP-compatible internal AI tool query these systems safely without direct database credentials.

13. Code example (DB + REST API servers)

# Database-connected MCP server
from mcp.server.fastmcp import FastMCP
import psycopg2

mcp = FastMCP("db-server")
conn = psycopg2.connect("dbname=company")

@mcp.tool()
def get_order_status(order_id: int) -> dict:
    """Look up the status of an order by ID."""
    cur = conn.cursor()
    cur.execute("SELECT status, updated_at FROM orders WHERE id = %s", (order_id,))
    row = cur.fetchone()
    if not row:
        return {"error": f"Order {order_id} not found"}
    return {"status": row[0], "updated_at": str(row[1])}

# REST-API-connected MCP server
import httpx

@mcp.tool()
async def get_github_issue(repo: str, issue_number: int) -> dict:
    """Fetch a GitHub issue's details."""
    async with httpx.AsyncClient() as client:
        resp = await client.get(f"https://api.github.com/repos/{repo}/issues/{issue_number}")
        resp.raise_for_status()
        data = resp.json()
        return {"title": data["title"], "state": data["state"], "body": data["body"][:500]}

14. Advanced example (LangGraph + MCP)

from langchain_mcp_adapters.client import MultiServerMCPClient
from langgraph.prebuilt import create_react_agent
from langchain_anthropic import ChatAnthropic

async def main():
    client = MultiServerMCPClient({
        "db-server": {"command": "python", "args": ["db_server.py"], "transport": "stdio"},
    })
    tools = await client.get_tools()
    model = ChatAnthropic(model="claude-sonnet-5")
    agent = create_react_agent(model, tools=tools)
    result = await agent.ainvoke({"messages": [{"role": "user", "content": "What's the status of order 42?"}]})
    print(result["messages"][-1].content)

15. Common mistakes

  • Building a generic `run_sql(query)` tool instead of scoped, specific tools — a major SQL-injection and excessive-agency risk.
  • Not using parameterized queries, risking SQL injection from LLM-generated arguments.
  • Forgetting `async`/`await` consistency when wrapping async REST calls in tool handlers.
  • Returning huge, unstructured raw data (e.g., entire DB table dumps) instead of concise, relevant structured results.

16. Best practices

  • Expose narrow, purpose-specific tools, never generic query/execution primitives.
  • Always use parameterized queries for any database tool.
  • Return concise, structured results — summarize/filter rather than dumping raw data.
  • Add timeouts to any external API calls within tool handlers.

17. Production considerations

Run database/API-connected MCP servers with connection pooling, proper error handling and logging, and monitoring for tool call latency/failure rates — they're production services, not scripts.

18. Security considerations

Parameterize all database queries; never construct SQL via string formatting with LLM-provided input. Validate and scope REST API calls (e.g., restrict which repos/resources are accessible). Apply the same excessive-agency caution as general tool calling.

19. Performance considerations

Use connection pooling for database-connected servers; use async HTTP clients for REST-API-connected servers to avoid blocking; add caching for frequently-requested, slow-changing data.

20. Cost considerations

MCP server infrastructure cost (hosting, database/API usage) is separate from LLM token cost — monitor both, especially for high-traffic remote MCP servers.

21. Debugging/troubleshooting

  • Tool call fails with a generic error: add detailed server-side logging to capture the actual underlying exception (DB connection issue, API timeout, etc.).
  • Async tool handler hangs: check for missing `await` or a blocking call inside an async function.
  • LangGraph agent doesn't see MCP tools: verify `get_tools()` actually returned the expected tool list before passing to the agent.

27. Interview Questions — Beginner

Q1. What does FastMCP provide?
A. A high-level Python SDK abstraction for building MCP servers using simple decorators like `@mcp.tool()`.
Q2. What transport does a local MCP server typically use?
A. stdio (standard input/output of a local subprocess).
Q3. Why should a database-connected MCP tool use parameterized queries?
A. To prevent SQL injection from LLM-generated or otherwise untrusted arguments.
Q4. Why shouldn't you expose a generic "run any SQL query" tool?
A. It gives far too much unscoped capability/risk — a classic excessive-agency and injection vulnerability; expose narrow, purpose-specific tools instead.
Q5. What does `MultiServerMCPClient` do in the LangGraph + MCP integration?
A. Connects to one or more MCP servers and exposes their tools in a format LangGraph/LangChain agents can use directly.
Q6. Why use async HTTP clients for REST-API-connected MCP tools?
A. To avoid blocking the server while waiting on network I/O, especially under concurrent tool-call load.
Q7. What should a tool return when a requested resource (like an order) isn't found?
A. A structured error/not-found response the model can understand and react to, not a crash or unclear exception.
Q8. What's the difference between a Tool and a Resource in MCP?
A. A Tool is a callable function performing an action; a Resource is readable data/content the server provides.
Q9. Why add timeouts to external API calls inside tool handlers?
A. To prevent a slow/unresponsive external service from hanging the entire tool call indefinitely.
Q10. What's the benefit of returning concise, structured results instead of raw data dumps from a tool?
A. It keeps context usage efficient and makes the result easier for the model to correctly interpret and use.

28. Interview Questions — Intermediate

Q1. How does FastMCP generate a tool's schema for discovery, and why does this matter for writing tool functions?
A. It introspects the function's type hints and docstring to automatically generate the JSON schema clients see during discovery — meaning precise type hints and a clear docstring directly become the tool's documentation and validation contract, not just internal code style.
Q2. Why might you choose to expose `get_order_status(order_id)` rather than a more general `query_orders(filters)` tool?
A. Narrow, specific tools are easier to validate, reason about, and secure (clear expected input/output, limited blast radius if misused) compared to general filter-based query tools, which risk becoming a backdoor for broader, less controlled database access.
Q3. What's a practical reason to add connection pooling to a database-connected MCP server rather than opening a new connection per tool call?
A. Opening a new DB connection per call adds significant latency and resource overhead, especially under concurrent load; pooling reuses existing connections, improving throughput and reducing database load.
Q4. How would you test that your MCP server's tool argument validation actually prevents SQL injection attempts?
A. Write a test case passing a malicious string (e.g., containing `'; DROP TABLE`) as a tool argument and verify the parameterized query handles it safely as literal data rather than executable SQL, and that the result is either a normal "not found" response or a validation error, never an actual injection effect.
Q5. Why does the LangGraph + MCP integration pattern (via `MultiServerMCPClient`) matter architecturally compared to writing custom LangChain tools directly?
A. It lets the same MCP servers be reused across any MCP-compatible host or framework (not just LangGraph), preserving MCP's core reusability benefit, rather than locking the tool implementation into LangChain-specific tool definitions that wouldn't work with other hosts.

29. Interview Questions — Advanced

Q1. How would you design an MCP server exposing a large internal database such that it's both useful and safely scoped, avoiding both a dangerously broad "run any query" tool and an overly narrow set of tools that can't handle real use cases?
A. Start by cataloging the actual query patterns real use cases need, expose each as a dedicated, parameterized tool with validated inputs (e.g., `search_orders_by_customer`, `get_order_status`), and for genuinely flexible reporting needs, consider a constrained query builder tool that only allows selecting from an allowlisted set of columns/filters rather than arbitrary SQL — balancing flexibility against the injection/excessive-agency risk of unconstrained query construction.
Q2. What's a subtle reliability issue with async MCP tool handlers that make concurrent calls to the same external API, and how would you address it?
A. Without care, concurrent tool calls could exceed the external API's own rate limits, causing cascading failures across multiple simultaneous agent tool calls; address with a shared rate-limiter/semaphore within the MCP server itself, ensuring the server as a whole respects the backend API's limits regardless of how many concurrent client requests arrive.

30. Interview Questions — Senior/Architect

Q1. Design the rollout strategy for an organization building its first set of internal MCP servers across multiple teams, covering standards, review, and governance.
A. Establish a shared internal library/template for MCP server scaffolding (consistent error handling, logging, auth patterns), require security review for any tool exposing write/destructive actions or sensitive data, mandate parameterized queries and input validation as a non-negotiable standard, set up centralized discovery/registry so teams can find existing servers before building duplicates, and require versioning discipline for any schema changes given downstream hosts depend on stability.

31. Scenario-Based Questions

Scenario 1. A newly built MCP server's `get_order_status` tool is occasionally returning results for the wrong order due to a race condition under concurrent calls. What's the likely cause?
A. Likely a shared, non-thread-safe database connection or cursor being reused across concurrent requests without proper isolation — fix with connection pooling that provides each request its own connection/cursor, or ensure proper async-safe database access patterns.
Scenario 2. Your REST-API-connected MCP server starts failing intermittently under moderate load. What do you investigate?
A. Check whether you're hitting the external API's rate limits (common cause under concurrent tool calls), verify timeout and retry/backoff logic exists for transient failures, and check for connection pool exhaustion in the async HTTP client under load.

32. Quick revision notes

  • FastMCP: decorator-based (`@mcp.tool()`, `@mcp.resource()`, `@mcp.prompt()`).
  • Expose narrow, specific tools; never generic query/execution primitives.
  • Always parameterize DB queries; always validate arguments server-side.
  • Use connection pooling and async clients for production-grade servers.
  • LangGraph + MCP via `MultiServerMCPClient` preserves cross-host reusability.

33. Cheat sheet

FastMCP decorators build servers fast. Expose narrow, specific, parameterized tools — never generic SQL/execution primitives. Use connection pooling + async clients. Validate server-side always. LangGraph connects via MultiServerMCPClient, preserving MCP's cross-host reusability.
