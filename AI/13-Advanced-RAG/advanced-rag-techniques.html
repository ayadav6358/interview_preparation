1. What is this?

Advanced RAG covers techniques that improve on naive "embed → retrieve top-k → generate" RAG: semantic/structure-aware chunking, parent-child retrieval, hybrid search (BM25 + vectors), reranking, query rewriting, multi-query retrieval, context compression, self-query retrieval, Corrective RAG, Adaptive RAG, Agentic RAG, Graph RAG, and Multimodal RAG.

2. Why does it exist?

Naive RAG's weakest point is almost always retrieval precision/recall, not generation — these techniques exist because real-world retrieval is messy: queries are ambiguous, relevant information spans multiple chunks or document types, and embedding similarity alone doesn't capture every notion of relevance.

3. Why is it important?

Most production RAG quality problems are solved by one of these techniques, not by a bigger/better LLM — this is where senior AI engineers differentiate themselves from those who only know the basic RAG pattern.

4. Where is it used?

Any production RAG system that has moved past prototype stage and needs measurably better precision/recall, especially over large, heterogeneous, or complex document collections.

6. Core techniques

TechniqueProblem it solves
Semantic chunkingFixed-size chunking breaks logical units; split at natural semantic boundaries instead.
Parent-child retrievalSmall chunks retrieve precisely but lack context; retrieve small chunks, return their larger parent chunk/document for generation.
Hybrid search (BM25 + vector)Pure embedding search misses exact keyword/term matches; combine lexical and semantic signals.
RerankingInitial retrieval (fast, approximate) over-fetches; a slower, more accurate reranker re-scores the top candidates for final precision.
Query rewritingUser queries are often ambiguous/colloquial; rewrite into a clearer retrieval-optimized query before embedding.
Multi-query retrievalA single query embedding may miss relevant angles; generate multiple query variants and retrieve for each.
Context compressionRetrieved chunks contain irrelevant filler; compress/extract only the relevant sentences before passing to the LLM.
Self-query retrievalLet the LLM translate a natural-language query into structured metadata filters + a semantic query automatically.
Corrective RAG (CRAG)Detect poor/irrelevant retrieval and trigger a fallback (e.g., web search or query reformulation) before generating.
Adaptive RAGDynamically decide whether retrieval is even needed, and how much, based on query complexity.
Agentic RAGLet an agent iteratively plan, retrieve, and refine across multiple steps rather than one-shot retrieval.
Graph RAGUse a knowledge graph for retrieval/reasoning over entity relationships, not just vector similarity (see Graph RAG).
Multimodal RAGRetrieve and reason over images/tables/audio alongside text.

7. Terminology

TermMeaning
BM25A classic lexical ranking algorithm scoring documents by term frequency/rarity — the standard keyword-search baseline.
Reranker / cross-encoderA model that jointly scores a (query, document) pair for relevance, more accurate but slower than embedding similarity alone.
Reciprocal Rank Fusion (RRF)A method for combining multiple ranked result lists (e.g., BM25 and vector search) into one fused ranking.
Query decompositionBreaking a complex question into simpler sub-questions, each retrieved separately.

8. Architecture

Query
 → (optional) Query rewriting / decomposition
 → Hybrid retrieval: BM25 + Vector search (over-fetch, e.g., top 20 each)
 → Fusion (RRF) → candidate pool
 → Reranker (cross-encoder) → top-k final (e.g., top 5)
 → (optional) Context compression
 → Prompt construction → LLM → Answer
 → (Corrective RAG) if retrieval judged poor: fallback (web search / reformulate) before generating

9. How it works internally

Rerankers (cross-encoders) work differently from embedding similarity: instead of independently encoding query and document then comparing vectors, a cross-encoder processes the query and document together through a single model pass, letting it directly model fine-grained relevance interactions — more accurate but too slow to run over an entire corpus, hence the two-stage pattern (fast approximate retrieval, then precise reranking of a small candidate set).

10. Step-by-step: diagnosing which technique to add

  1. If retrieval misses exact-term matches (product codes, names) → add hybrid search (BM25 + vector).
  2. If top-k results are semantically related but not precisely relevant → add reranking.
  3. If user queries are vague/colloquial → add query rewriting.
  4. If questions require synthesizing multiple facts → add multi-query retrieval or query decomposition.
  5. If retrieval sometimes returns clearly irrelevant results → add Corrective RAG with a relevance-check gate.
  6. If some queries need retrieval and others don't (e.g., "hello" vs a factual question) → add Adaptive RAG routing.

11. Simple example

A user searches for "error code E402" — pure embedding search might miss this exact code if it's rare in training data, but BM25 (hybrid search) catches the exact term match reliably.

12. Real-world example

A legal-document RAG system reranks its top 20 vector-retrieved clauses using a cross-encoder fine-tuned on legal relevance judgments, reducing "semantically similar but legally irrelevant" clauses from the final context — directly improving the quality of legal Q&A answers.

13. Code example

# Hybrid search + reranking pipeline
def hybrid_retrieve(query, k=20):
    vector_results = vector_search(embed(query), top_k=k)
    bm25_results = bm25_search(query, top_k=k)
    return reciprocal_rank_fusion(vector_results, bm25_results)

def rerank(query, candidates, final_k=5):
    scores = cross_encoder.predict([(query, c.content) for c in candidates])
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return [c for c, _ in ranked[:final_k]]

def rag_answer(query):
    candidates = hybrid_retrieve(query)
    top_chunks = rerank(query, candidates)
    return generate(query, top_chunks)

14. Advanced example (Corrective RAG)

def corrective_rag(query):
    chunks = hybrid_retrieve(query)
    relevance = judge_relevance(query, chunks)  # LLM-as-judge or classifier
    if relevance == "low":
        # Fallback: reformulate query or fall back to web search
        reformulated = rewrite_query(query)
        chunks = hybrid_retrieve(reformulated) or web_search(reformulated)
    return generate(query, rerank(query, chunks))

15. Common mistakes

  • Adding reranking without first over-fetching enough candidates for it to meaningfully re-sort.
  • Naively summing BM25 and vector scores without normalization (they're on incompatible scales) instead of using rank fusion.
  • Applying the same advanced technique universally without measuring whether it actually helps your specific corpus/query distribution.
  • Over-engineering with agentic multi-step retrieval for simple lookup queries that don't need it (added latency/cost for no benefit).

16. Best practices

  • Add techniques incrementally, measuring retrieval/answer quality improvement against a golden set after each addition.
  • Use Adaptive RAG routing so simple queries skip expensive techniques (reranking, multi-query) that complex queries need.
  • Prefer rank fusion (RRF) over naive score combination for hybrid search.
  • Fine-tune or carefully select a reranker matched to your domain if off-the-shelf rerankers underperform.

17. Production considerations

Each added technique increases latency and/or cost — measure the marginal quality gain against the marginal cost for your specific use case, and consider Adaptive RAG to apply expensive techniques only when needed.

18. Security considerations

Corrective RAG's fallback to web search introduces untrusted external content into context — apply the same prompt-injection precautions as any externally-sourced content (see AI Security).

19. Performance considerations

Reranking adds latency proportional to candidate count × reranker inference time — tune the over-fetch count (e.g., retrieve 20, rerank to 5) to balance quality and speed; run reranking on GPU if volume justifies it.

20. Cost considerations

Query rewriting, multi-query retrieval, and Corrective RAG's relevance judging each add extra LLM calls — quantify their cost multiplier and apply selectively (Adaptive RAG) rather than universally.

21. Debugging/troubleshooting

  • Reranking doesn't improve results: check if the initial retrieval's candidate pool (before reranking) already excludes the truly relevant documents — reranking can't fix a recall problem, only a precision/ordering problem among what's already retrieved.
  • Hybrid search performs worse than vector-only: check your score fusion method; naive score combination without normalization is a common culprit.
  • Corrective RAG's fallback triggers too often: the relevance-judging threshold may be miscalibrated — tune against labeled examples.

27. Interview Questions — Beginner

Q1. What is reranking?
A. A second-stage step that re-scores an initial set of retrieved candidates more precisely, typically using a cross-encoder, to improve final ranking quality.
Q2. What is hybrid search?
A. Combining lexical (keyword, e.g., BM25) search with semantic (vector embedding) search for better retrieval precision.
Q3. What is query rewriting?
A. Reformulating an ambiguous or colloquial user query into a clearer form better suited for retrieval, before embedding it.
Q4. What is multi-query retrieval?
A. Generating multiple variations of a query and retrieving for each, to capture different relevant angles a single query embedding might miss.
Q5. What is Corrective RAG?
A. A pattern that detects poor/irrelevant retrieval results and triggers a fallback (like query reformulation or web search) before generating an answer.
Q6. What is parent-child retrieval?
A. Retrieving small, precise chunks for matching, but returning their larger parent chunk/document to provide fuller context for generation.
Q7. Why would you need BM25 if embeddings already capture semantic meaning?
A. Embeddings can under-weight exact term matches (like specific codes or names); BM25 excels at exact/rare term matching that embeddings sometimes miss.
Q8. What is Adaptive RAG?
A. Dynamically deciding whether retrieval is needed at all, and how much, based on the complexity/nature of the query.
Q9. Is a reranker typically faster or slower than initial vector retrieval?
A. Slower — it processes query and document jointly for higher accuracy, which is why it's only applied to a smaller candidate pool after initial fast retrieval.
Q10. What's a cross-encoder?
A. A model that scores relevance by processing a query and document together in one pass, rather than comparing independently-computed embeddings.

28. Interview Questions — Intermediate

Q1. Why can't reranking fix a retrieval recall problem?
A. Reranking only reorders candidates already in the retrieved pool; if the truly relevant document was never retrieved into that pool in the first place, reranking has nothing to surface it from.
Q2. How does Reciprocal Rank Fusion combine BM25 and vector search results, and why is it preferred over naive score summation?
A. RRF combines results based on each item's rank position in each list (e.g., 1/(rank+k)) rather than raw scores, avoiding the problem of BM25 and cosine similarity scores being on incompatible scales that naive summation would mishandle.
Q3. When would query decomposition (breaking a question into sub-questions) be more effective than multi-query retrieval (generating paraphrased variants)?
A. When the question genuinely requires combining distinct pieces of information (e.g., "compare X's pricing to Y's pricing") — each sub-question targets a different information need, whereas multi-query variants are paraphrases of the same single need and wouldn't separately retrieve both pieces of information needed.
Q4. How would you implement Adaptive RAG's "does this query need retrieval at all" decision?
A. Use a lightweight classifier or a quick LLM call to classify the query type (e.g., chit-chat vs. factual question vs. requires-specific-document-lookup), routing only queries that genuinely need grounding through the full retrieval pipeline, skipping it for conversational/greeting-type inputs.
Q5. Why might a fine-tuned domain-specific reranker outperform a general-purpose one significantly?
A. General-purpose rerankers are trained on broad relevance judgments that may not reflect domain-specific notions of relevance (e.g., legal precedent relevance differs from general semantic similarity); fine-tuning on domain-labeled relevance data aligns the reranker's scoring with what actually matters for that domain.

29. Interview Questions — Advanced

Q1. How would you design an evaluation framework to determine which advanced RAG technique(s) to invest in for a specific production system?
A. Build a diagnostic golden set labeled by failure type (missed exact-term match, low-precision results, ambiguous query misinterpretation, multi-fact synthesis failure), run the current pipeline against it to identify which failure types dominate, then add and A/B test only the specific technique(s) targeting the actual observed failure modes — rather than adding techniques speculatively.
Q2. What's a risk of Corrective RAG's relevance-judging step becoming a new source of errors?
A. The relevance judge (LLM-as-judge or classifier) itself can be miscalibrated — too permissive (letting genuinely poor retrieval through) or too strict (triggering unnecessary, costly fallbacks for actually-adequate retrieval) — requiring its own calibration and evaluation against labeled relevance judgments, not just trusting it blindly.

30. Interview Questions — Senior/Architect

Q1. Design an Adaptive RAG architecture that routes queries through different pipelines (simple retrieval, hybrid+rerank, agentic multi-step) based on complexity, for a platform serving many different query types.
A. Build a lightweight query classifier (rule-based or small model) estimating complexity/type upfront, route simple factual lookups through fast single-pass retrieval, route queries flagged as ambiguous through query rewriting + hybrid + rerank, and route queries requiring multi-document synthesis through an agentic decomposition pipeline — instrument each path with its own evaluation metrics and continuously tune routing thresholds based on observed outcomes per path.

31. Scenario-Based Questions

Scenario 1. Despite adding a reranker, a RAG system still misses clearly relevant documents for certain queries. What's the likely issue?
A. The initial retrieval stage (before reranking) likely isn't returning the relevant documents into the candidate pool at all — investigate whether the embedding model or chunking strategy is failing at the recall stage, since reranking can only reorder what's already retrieved.
Scenario 2. A product team wants every query to go through the full agentic multi-step RAG pipeline "to maximize quality." What's your pushback?
A. Point out the latency/cost multiplier applies even to simple queries that don't need it; propose Adaptive RAG routing so only genuinely complex queries incur that cost, informed by actual measured query complexity distribution in production traffic.
Scenario 3. Your hybrid search's results got worse after adding BM25 scoring. What do you check first?
A. Check the score fusion method — naive summation of BM25 and cosine similarity scores (incompatible scales) is a very common bug; switch to rank-based fusion (RRF) instead of raw score combination.

32. Quick revision notes

  • Most RAG quality problems are retrieval problems, not generation problems.
  • Hybrid search (BM25 + vector) catches exact-term matches embeddings miss.
  • Reranking improves precision among already-retrieved candidates; can't fix recall.
  • Use RRF for combining ranked lists, not naive score summation.
  • Adaptive RAG applies expensive techniques only where needed.

33. Cheat sheet

Problem → Solution: missing exact terms → hybrid search. Low precision → reranking. Ambiguous queries → query rewriting. Multi-fact questions → multi-query/decomposition. Bad retrieval detection → Corrective RAG. Query-dependent pipeline choice → Adaptive RAG.
