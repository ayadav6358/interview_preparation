1. What is this?

AI system design applies classic system-design methodology (requirements → architecture → data flow → scaling → trade-offs) to AI-specific systems: ChatGPT-like applications, enterprise RAG, AI customer support, AI coding assistants, research agents, multi-agent platforms, MCP platforms, voice AI, multimodal RAG, and agentic workflow platforms.

2. Why does it exist?

AI systems introduce new architectural concerns (LLM latency/cost, retrieval pipelines, agent loops, hallucination mitigation) on top of standard distributed-systems concerns — this discipline exists to extend proven system-design thinking to these new building blocks.

3. Why is it important?

AI system design interviews are now standard for senior AI engineering roles — this page synthesizes nearly every other topic in this knowledge base (RAG, agents, LLM APIs, observability, security, cost) into the integrated architectural thinking those interviews test.

4. Where is it used?

Senior/staff AI engineering interviews, real architectural planning for new AI products.

5. Prerequisites

Most of this knowledge base — especially RAG, AI Agents, Performance and Scaling, Enterprise AI.

6. The standard AI system design framework

  1. Requirements: functional (what must it do) and non-functional (latency, scale, availability, compliance).
  2. Architecture: major components and how they connect.
  3. Data flow: trace a request end-to-end through the system.
  4. Data stores: database, cache, vector DB, queue — what each holds and why.
  5. LLM/model choices: which models, why, and the routing/fallback strategy.
  6. Security: tenant isolation, injection defense, access control.
  7. Observability: tracing, evaluation, monitoring.
  8. Scaling: how the system handles growth in users/data/traffic.
  9. Failure handling: what happens when any component fails.
  10. Cost: major cost drivers and optimization levers.
  11. Trade-offs: what was sacrificed for what, and why.

7. Terminology

TermMeaning
Functional requirementWhat the system must do (features/capabilities).
Non-functional requirementHow well it must do it (latency, availability, scale, compliance).
Data flowThe end-to-end path a request takes through the system's components.
Trade-offA deliberate choice sacrificing one quality (e.g., cost) for another (e.g., latency).

8. Architecture: ChatGPT-like application

Requirements: multi-turn conversation, streaming responses, conversation history, millions of concurrent users.

Client (web/mobile) → API Gateway → Auth
 → Conversation Service (loads/saves history from DB)
 → LLM Gateway (routing, fallback, rate limiting)
 → LLM Provider(s) (streaming response)
 → Response streamed back to client
 → Async: usage/cost logging, content moderation check

Data stores: relational/NoSQL DB for conversation history, cache for active sessions, object storage for any uploaded files. Scaling: horizontally scale the stateless API/conversation service layer; conversation history sharded by user ID. Failure handling: fallback LLM provider; graceful degradation (cached "service busy" message) rather than hard failure.

9. Architecture: Enterprise RAG

Requirements: multi-tenant document Q&A, strict access control, citations, compliance/audit.

Document sources (SharePoint, Confluence, uploads)
 → Ingestion pipeline (loader → parser → chunker → embed) — per-tenant scoped
 → Vector DB (tenant_id + permission metadata on every chunk)
 → Query: Auth/RBAC check → retrieve (tenant+permission filtered) → rerank
 → LLM generates answer with citations
 → Audit log every query + retrieval + answer

See Enterprise AI for the full tenant-isolation and compliance treatment this design relies on.

10. Architecture: AI Coding Assistant

Requirements: repo-aware code understanding, multi-file edits, test execution, human review gate.

IDE/CLI (user request)
 → Agent orchestrator (plan → search/read repo → edit → test loop)
 → Tool layer: file I/O, code search (grep/semantic), shell execution (sandboxed)
 → MCP servers (optional: external tool/data access — issue trackers, DBs)
 → LLM (with repo context, tool definitions)
 → Diff presented for human review → commit on approval

See Coding Agents for the detailed loop this design implements.

11. Architecture: Multi-Agent Platform

Requirements: route tasks to specialist agents, parallel/sequential coordination, observability across agents.

Task → Supervisor agent (classify + route)
 → Specialist agents (parallel or sequential, each scoped tools/prompts)
 → Shared state (LangGraph-style) coordinating the workflow
 → Synthesis/integration step → final output
 → Full tracing across every agent's steps (see LLM Observability)

See Multi-Agent Systems for the underlying coordination patterns.

12. Real-world example

A real enterprise RAG deployment combines all of the above patterns: SSO-authenticated users, RBAC-scoped retrieval, a reranking step for precision, full LangSmith tracing, cost dashboards per department, and a nightly evaluation job gating any prompt/retrieval changes before they reach production — the synthesis of nearly every topic in this knowledge base into one running system.

13. Code example (capacity estimation)

# Back-of-envelope capacity estimation for a ChatGPT-like app
daily_active_users = 1_000_000
avg_messages_per_user_per_day = 10
avg_tokens_per_message_pair = 500  # input + output combined

daily_tokens = daily_active_users * avg_messages_per_user_per_day * avg_tokens_per_message_pair
peak_qps = (daily_active_users * avg_messages_per_user_per_day) / (24 * 3600) * 3  # 3x peak factor

print(f"Daily tokens: {daily_tokens:,}")
print(f"Estimated peak QPS: {peak_qps:.1f}")
# Use these numbers to size LLM provider rate-limit tier, gateway capacity, and DB throughput

14. Advanced example (failure handling)

# Layered failure handling for the ChatGPT-like app's LLM call
def get_response(messages):
    try:
        return primary_llm_gateway.stream(messages)
    except CircuitOpenError:
        try:
            return fallback_llm_gateway.stream(messages)
        except Exception:
            return cached_degraded_response()  # "We're experiencing issues, please retry shortly"

15. Common mistakes

  • Jumping straight to architecture diagrams without first clarifying functional/non-functional requirements.
  • Ignoring failure handling and security until explicitly asked — these should be designed in from the start.
  • Not quantifying scale (back-of-envelope estimates) before proposing a specific architecture.
  • Treating every AI system design the same, ignoring domain-specific needs (e.g., voice AI's latency budget vs. batch document processing's throughput focus).

16. Best practices

  • Always start with requirements clarification before architecture.
  • Quantify scale with back-of-envelope math to justify architectural choices.
  • Explicitly address security, observability, and failure handling, not just the happy path.
  • State trade-offs explicitly — system design is about justified choices, not a single "correct" answer.

17. Production considerations

Every architecture sketched here assumes the supporting practices covered elsewhere in this knowledge base (observability, evaluation, security, cost monitoring) are actually implemented — a system design interview answer that mentions these briefly demonstrates more maturity than one that only describes the happy-path data flow.

18. Security considerations

Every design above needs tenant isolation (if multi-tenant), prompt-injection defense (if processing untrusted content), and least-privilege tool scoping (if agentic) — these aren't optional add-ons, they're core requirements for any production AI system design.

19. Performance considerations

Identify the actual latency-critical path (e.g., for voice AI, the full STT→LLM→TTS loop; for batch document processing, throughput matters more than individual latency) and design around that specific bottleneck rather than generic "make it fast" statements.

20. Cost considerations & trade-offs

Every design should identify its dominant cost driver (LLM generation tokens, embedding/retrieval calls, GPU infrastructure for self-hosting) and at least one lever to control it (model routing, caching, batch processing) — see Cost Optimization.

21. Debugging/troubleshooting

  • Interview answer feels too shallow: go one level deeper on data flow — trace exactly what happens to one specific request end-to-end, including failure branches.
  • Can't decide on an architecture: return to requirements — the "right" architecture should be derivable from stated functional/non-functional requirements, not chosen arbitrarily.

27. Interview Questions — Beginner

Q1. What's the difference between functional and non-functional requirements?
A. Functional requirements define what the system must do (features); non-functional requirements define how well it must do it (latency, scale, availability, compliance).
Q2. Why start a system design with requirements before architecture?
A. The right architecture should be derived from actual requirements, not chosen arbitrarily — skipping this step risks designing for the wrong constraints.
Q3. What's a data flow in system design?
A. The end-to-end path a request takes through the system's components, from input to output.
Q4. Why include failure handling in an AI system design from the start?
A. LLM APIs and other components can and will fail; designing graceful degradation from the start avoids a brittle happy-path-only system.
Q5. What's a back-of-envelope estimate used for?
A. Quantifying expected scale (requests/sec, data volume) to justify and size architectural choices.
Q6. Why does a ChatGPT-like app need streaming?
A. To improve perceived latency by showing partial output as it's generated, rather than waiting for the full response.
Q7. What's the core security requirement for an enterprise RAG system?
A. Strict tenant/permission-scoped data isolation, ensuring users only retrieve data they're authorized to access.
Q8. Why does an AI coding assistant need a human review gate?
A. To catch errors or unintended changes before they're committed to production code, regardless of how confident the agent is.
Q9. What's a trade-off in system design?
A. A deliberate choice sacrificing one quality (e.g., cost) for another (e.g., latency or quality).
Q10. Why is observability a required component, not an optional add-on, for AI system designs?
A. Without it, debugging production issues in a non-deterministic, multi-step AI system is nearly impossible.

28. Interview Questions — Intermediate

Q1. How would you estimate the peak QPS and token throughput needed for a ChatGPT-like app with 1 million daily active users?
A. Estimate average messages per user per day and average tokens per message pair, multiply to get daily token volume, then apply a peak-to-average traffic factor (e.g., 3x) divided across daily seconds to estimate peak QPS — using these numbers to size LLM provider rate-limit tiers and gateway/infrastructure capacity.
Q2. Why does an enterprise RAG system's ingestion pipeline need to be tenant-scoped, not just the query path?
A. If ingestion isn't properly scoped, one tenant's documents could be mistakenly indexed as accessible to another tenant from the start — tenant isolation must be enforced at every stage data enters and is queried from the system, not just at query time.
Q3. How would you design the failure-handling path for an AI coding assistant if the sandboxed test-execution environment becomes unavailable?
A. Detect the sandbox failure explicitly, inform the agent/user that verification couldn't be performed (rather than silently proceeding as if tests passed), and either retry with backoff or escalate to human review before presenting any change as "verified," since presenting an unverified change as tested would be worse than an honest failure.
Q4. Why might a multi-agent platform's observability requirements be more complex than a single-agent system's?
A. Failures can originate in any specialist agent, the supervisor's routing logic, or the coordination/synthesis step — full tracing needs to capture the relationship between agents (which agent did what, in what order, with what result) to debug effectively, not just each agent's isolated behavior.
Q5. What's a key trade-off between using a single large frontier model versus a model-routing architecture for a ChatGPT-like app?
A. A single frontier model simplifies the architecture and guarantees consistent quality but costs more at scale; model routing reduces average cost significantly but adds complexity (classifier accuracy risk, more testing surface) and risks quality inconsistency if routing misclassifies a complex query as simple.

29. Interview Questions — Advanced

Q1. How would you design an AI research agent system to balance thoroughness (more searches/sources) against latency and cost for a user-facing product?
A. Implement an adaptive stopping criterion (e.g., diminishing new-information returns across successive searches, or a confidence threshold on synthesized findings) rather than a fixed search count, expose a "quick" vs "thorough" mode to let users explicitly choose their latency/thoroughness trade-off, and cap worst-case cost/time with a hard limit regardless of mode.
Q2. What's a subtle architectural challenge in designing an MCP platform that serves as a central registry/gateway for many internal MCP servers across an organization?
A. Balancing centralized governance (consistent auth, logging, discoverability) against the autonomy individual teams need to iterate quickly on their own servers — an overly centralized gatekeeping process can become a bottleneck, while too little governance risks inconsistent security practices across servers; the right balance often involves self-service registration with automated compliance checks (schema validation, required auth) rather than fully manual central review for every server.

30. Interview Questions — Senior/Architect

Q1. Walk through how you would lead a system design discussion for a "ChatGPT-like application," covering what you'd clarify, propose, and defend.
A. Start by clarifying scale (DAU, message volume), latency expectations, multi-turn/history requirements, and any compliance needs; propose an architecture (API gateway → conversation service → LLM gateway with routing/fallback → streaming response, with conversation history in a sharded DB and full observability); quantify capacity with back-of-envelope math; explicitly address security (rate limiting, content moderation, tenant isolation if multi-tenant), failure handling (circuit breakers, fallback providers, graceful degradation), and cost (token usage monitoring, model routing); and conclude with explicit trade-offs (e.g., "we chose model routing for cost at the expense of added classification complexity and a small quality-consistency risk, mitigated by continuous evaluation").

31. Scenario-Based Questions

Scenario 1. In a system design interview, you're asked to design an "AI customer support" system but given no scale numbers. How do you proceed?
A. Explicitly ask clarifying questions (expected ticket volume, SLA requirements, integration needs) rather than assuming; if the interviewer wants you to proceed with assumptions, state them explicitly and reasonably (e.g., "assuming 10K tickets/day") so your architecture can be evaluated against stated assumptions rather than silently guessing.
Scenario 2. Partway through presenting your multi-agent platform design, the interviewer asks "what happens if the supervisor agent itself fails?" How do you respond?
A. Treat the supervisor as a critical-path component needing its own resilience: health checks, a defined timeout/fallback behavior (e.g., route to a default specialist or return a graceful "unable to process" response), and consider whether a stateless, horizontally-scaled supervisor design avoids a single point of failure — demonstrating that failure handling was considered for every component, not just the "main" happy path.

32. Quick revision notes

  • Framework: requirements → architecture → data flow → stores → models → security → observability → scaling → failure handling → cost → trade-offs.
  • Always quantify scale with back-of-envelope estimates.
  • Security, observability, failure handling are required, not optional extras.
  • State trade-offs explicitly — there's no single "correct" architecture.

33. Cheat sheet

Requirements → Architecture → Data flow → Stores → Models → Security → Observability → Scaling → Failure handling → Cost → Trade-offs. Quantify scale. Address security/observability/failure handling always. State trade-offs explicitly.
