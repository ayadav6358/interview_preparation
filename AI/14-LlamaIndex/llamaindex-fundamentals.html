1. What is this?

LlamaIndex is a framework specifically focused on data ingestion, indexing, and retrieval for LLM applications — it provides Documents, Nodes, Indexes, Retrievers, Query Engines, Agents, and Workflows as composable building blocks optimized around the RAG problem space.

2. Why does it exist?

While general-purpose orchestration frameworks like LangChain cover broad LLM application needs, LlamaIndex exists specifically to make the data-ingestion-to-retrieval pipeline (connectors, parsing, chunking, indexing strategies) as frictionless and well-abstracted as possible — its original and still-core focus.

3. Why is it important?

For RAG-heavy applications, LlamaIndex's purpose-built abstractions (especially its wide range of data connectors and indexing strategies) can save significant integration effort compared to building retrieval pipelines from scratch.

4. Where is it used?

Document Q&A systems, enterprise search, knowledge-base chatbots — any application centered on retrieval over structured/unstructured data sources.

6. Core concepts

  • Document: a raw piece of source content (a file, a database row, a web page).
  • Node: a chunk of a Document with associated metadata — LlamaIndex's unit of retrieval.
  • Index: a data structure (vector index, list index, tree index, keyword index) organizing Nodes for efficient retrieval.
  • Retriever: queries an Index to fetch relevant Nodes.
  • Query Engine: combines a Retriever with a response-synthesis step to answer a query end-to-end.
  • Workflows: LlamaIndex's mechanism for building more complex, multi-step, agentic pipelines beyond simple query engines.

8. Architecture

Data Connectors (PDF, Notion, DB, web, etc.)
 → Documents
 → Node Parser (chunking) → Nodes
 → Index (VectorStoreIndex, etc.) → stores embeddings
 → Retriever → top Nodes for a query
 → Query Engine → Retriever + Response Synthesizer → Answer

9. How it works internally

LlamaIndex's Query Engine abstracts the full RAG loop: it calls the Retriever to get relevant Nodes, then passes them to a response-synthesis strategy (e.g., "compact" — stuff as many Nodes as fit into one LLM call, or "refine" — iteratively update an answer across Nodes one at a time) depending on how much retrieved content there is relative to the context window.

10. Step-by-step: building a basic index

  1. Load documents via a data connector/loader.
  2. Parse documents into Nodes (chunks).
  3. Build a VectorStoreIndex from the Nodes (embeds and stores them).
  4. Create a Query Engine from the index.
  5. Call `.query()` with a natural-language question.

11. Simple example

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("data/").load_data()
index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine()
response = query_engine.query("What is our refund policy?")
print(response)

12. Real-world example

A company connects LlamaIndex to its Notion workspace via a built-in data connector, automatically syncing and indexing documentation changes, letting employees query internal docs in natural language without a custom ingestion pipeline.

13. Code example

from llama_index.core import VectorStoreIndex, Settings
from llama_index.vector_stores.postgres import PGVectorStore
from llama_index.embeddings.openai import OpenAIEmbedding

Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")

vector_store = PGVectorStore.from_params(
    database="ragdb", host="localhost", table_name="llamaindex_nodes",
)
index = VectorStoreIndex.from_vector_store(vector_store)
query_engine = index.as_query_engine(similarity_top_k=5)
response = query_engine.query("How long do refunds take?")
print(response.response)
for node in response.source_nodes:
    print(node.node.text[:100], node.score)

14. Advanced example (Workflows)

from llama_index.core.workflow import Workflow, step, StartEvent, StopEvent

class RAGWorkflow(Workflow):
    @step
    async def retrieve(self, ev: StartEvent) -> "RetrievedEvent":
        nodes = query_engine.retriever.retrieve(ev.query)
        return RetrievedEvent(nodes=nodes, query=ev.query)

    @step
    async def synthesize(self, ev: "RetrievedEvent") -> StopEvent:
        answer = synthesize_response(ev.query, ev.nodes)
        return StopEvent(result=answer)

15. Common mistakes

  • Using the default chunking/node-parsing settings without tuning for your specific document types.
  • Not configuring a persistent vector store (defaults to in-memory, lost on restart) for production use.
  • Treating Query Engine's default response synthesis as sufficient without evaluating against your actual use case's accuracy needs.

16. Best practices

  • Use a persistent, production-grade vector store (pgvector, Pinecone, etc.) rather than defaults for anything beyond prototyping.
  • Tune node parser chunk size for your document types.
  • Evaluate response synthesis strategies (compact vs refine vs tree summarize) against your actual query patterns.

17. Production considerations

Configure a durable vector store backend, monitor query latency and token usage per query engine call, and plan for incremental re-indexing as source data changes.

18. Security considerations

Apply the same metadata-filtering and access-control discipline as any RAG system — LlamaIndex supports metadata filters on retrieval, which must be wired to your actual authorization model.

19. Performance considerations

Response synthesis strategy affects both latency and cost — "compact" (fewer LLM calls, more context per call) is typically faster/cheaper than "refine" (iterative, more LLM calls) for most use cases, but may lose precision on very large retrieved sets.

20. Cost considerations

Each embedding call (ingestion and query) and LLM synthesis call incurs cost — monitor and tune `similarity_top_k` (how many nodes are retrieved) to avoid unnecessarily large synthesis prompts.

21. Debugging/troubleshooting

  • Query engine returns empty/irrelevant answers: inspect `response.source_nodes` to see what was actually retrieved and debug from there.
  • Data not persisting across restarts: check whether you're using the default in-memory store instead of a configured persistent vector store.

27. Interview Questions — Beginner

Q1. What is LlamaIndex primarily focused on?
A. Data ingestion, indexing, and retrieval for LLM applications — the RAG problem space specifically.
Q2. What's the difference between a Document and a Node in LlamaIndex?
A. A Document is raw source content; a Node is a chunked unit of a Document, the actual granularity used for retrieval.
Q3. What is a Query Engine?
A. A component combining a Retriever and a response synthesizer into a single end-to-end query interface.
Q4. What is a VectorStoreIndex?
A. The most common LlamaIndex index type, backing similarity search over embedded Nodes.
Q5. How do you inspect what content was actually used to answer a query?
A. Check the `source_nodes` attribute on the query response.
Q6. What's LlamaIndex's main strength compared to general orchestration frameworks?
A. Rich, purpose-built data connectors and indexing strategies specifically for the retrieval/RAG problem.
Q7. What is a Workflow in LlamaIndex?
A. A composable, event-driven mechanism for building more complex multi-step pipelines beyond simple query engines.
Q8. Can LlamaIndex be used alongside LangChain?
A. Yes — many teams use LlamaIndex for retrieval and LangChain/LangGraph for broader orchestration.
Q9. Why shouldn't you rely on the default in-memory vector store in production?
A. It doesn't persist across restarts; production needs a durable backend like pgvector or Pinecone.
Q10. What does `similarity_top_k` control?
A. How many of the most similar nodes are retrieved for a query.

28. Interview Questions — Intermediate

Q1. What's the difference between "compact" and "refine" response synthesis modes, and when would you choose each?
A. "Compact" stuffs as many retrieved nodes as fit into a single LLM call for efficiency; "refine" iteratively updates an answer by processing nodes one at a time, useful when retrieved content exceeds context limits but adds more LLM calls (cost/latency). Choose compact for most cases; refine when you have many nodes that can't fit in one call and need incremental synthesis.
Q2. Why might you choose LlamaIndex specifically over building a custom retrieval pipeline from scratch?
A. To leverage its built-in data connectors, node parsing strategies, and indexing abstractions, saving significant integration effort — especially valuable when ingesting from many heterogeneous data sources.
Q3. How would you combine LlamaIndex with LangGraph in a single application?
A. Use LlamaIndex's Query Engine as a retrieval tool/node within a LangGraph agent graph, letting LangGraph handle broader multi-step orchestration (planning, other tools, state management) while LlamaIndex handles the specific retrieval sub-task it's optimized for.
Q4. Why is tuning the Node Parser's chunk size important even when using LlamaIndex's defaults?
A. Default chunk sizes are generic and may not match your specific document structure (e.g., legal clauses vs. short FAQ entries), directly affecting retrieval precision — defaults are a starting point, not a guarantee of good performance for your corpus.
Q5. How would you debug a LlamaIndex query engine returning an answer that contradicts the source documents?
A. Inspect `response.source_nodes` to verify what was actually retrieved, check if the response synthesis prompt properly constrains the model to use only that content, and verify the retrieved nodes themselves are correct before suspecting a generation-level hallucination issue.

29. Interview Questions — Advanced

Q1. How would you architect a LlamaIndex-based system to support multiple, independently-updatable data sources with different ingestion cadences?
A. Use separate indexes (or namespaces within one vector store) per data source, each with its own ingestion pipeline/schedule, and compose a router query engine that directs queries to the appropriate index(es) based on query classification or metadata, rather than one monolithic index for all sources.
Q2. What's a subtle issue with using LlamaIndex's default similarity-based retrieval for queries requiring exact structured filtering (e.g., "documents from Q3 2025 only")?
A. Pure similarity search doesn't guarantee respecting structured constraints; you need metadata filters applied alongside vector search (LlamaIndex supports this), or a self-query retriever that translates the natural-language query into both a semantic query and explicit metadata filters.

30. Interview Questions — Senior/Architect

Q1. When would you recommend LlamaIndex over LangChain (or vice versa) for a new enterprise RAG platform, and how would you justify combining both?
A. Recommend LlamaIndex-first if the core challenge is ingesting/indexing diverse data sources with high retrieval quality; recommend LangChain/LangGraph-first if the core challenge is complex multi-step agent orchestration beyond retrieval. Justify combining both by using each for its strength: LlamaIndex as the retrieval layer, LangGraph as the orchestration layer coordinating retrieval with other tools/agents — avoiding forcing one framework to do a job the other is better suited for.

31. Scenario-Based Questions

Scenario 1. Your LlamaIndex-based Q&A tool works in development but returns nothing in production. What do you check first?
A. Verify the production environment is configured with a persistent vector store (not the in-memory default that was fine for local testing) and that the index was actually built/populated against production data.
Scenario 2. Users complain that answers ignore recent document updates. What's the likely cause?
A. The ingestion pipeline isn't re-indexing updated documents — check whether old Nodes for the updated Document are being properly removed/replaced in the vector store on re-ingestion.

32. Quick revision notes

  • LlamaIndex = RAG-focused: Documents → Nodes → Index → Retriever → Query Engine.
  • LlamaIndex excels at data connectors/indexing; LangChain/LangGraph excels at broader orchestration.
  • Use a persistent vector store backend for production, not the in-memory default.
  • Inspect `source_nodes` to debug retrieval/answer quality.

33. Cheat sheet

LlamaIndex: Document → Node → Index (VectorStoreIndex) → Retriever → Query Engine (retriever + synthesizer). RAG-focused framework; combine with LangGraph for broader agentic orchestration if needed.
