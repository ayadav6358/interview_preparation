1. What is this?

LLM inference serving engines (vLLM, SGLang, TGI, TensorRT-LLM) are specialized systems for running open-weight models efficiently at scale — optimizing GPU utilization, memory management (KV cache), and request batching to maximize throughput and minimize latency/cost per request.

2. Why does it exist?

Naively running a model (e.g., directly via a basic Transformers library call) is extremely inefficient at scale — it wastes GPU memory and compute, especially under concurrent requests. These serving engines exist to apply systems-engineering optimizations specific to the autoregressive generation workload.

3. Why is it important?

If you self-host any open-weight model in production, the serving engine you choose is the single biggest lever on cost and latency — this is the deepest technical layer connecting the Transformer internals (04-Transformers) to real production performance.

4. Where is it used?

Any self-hosted open-weight model deployment at meaningful scale; also used internally by some API providers to serve their own models.

5. Prerequisites

Transformers (especially KV cache), Local LLMs.

6. Core concepts

  • Continuous batching: dynamically adding new requests to an in-progress batch as earlier ones complete, rather than waiting for a fixed batch to fully finish.
  • PagedAttention (vLLM): manages KV cache memory in non-contiguous "pages," similar to OS virtual memory, dramatically reducing memory waste from naive KV cache allocation.
  • Quantization: reducing weight precision to shrink memory footprint and increase throughput.
  • Speculative decoding: using a smaller draft model to propose tokens the larger model verifies in parallel, reducing sequential forward passes.
  • GPU utilization: the percentage of available GPU compute actually being used — serving engines aim to maximize this under concurrent load.

7. Terminology

TermMeaning
ThroughputTotal tokens/requests processed per unit time across all concurrent requests.
Latency (TTFT, TPOT)Time-to-first-token and time-per-output-token — key per-request latency metrics.
KV cacheCached attention keys/values avoiding recomputation during generation (see Transformers).
BatchingProcessing multiple requests simultaneously to better utilize GPU parallelism.
Tensor parallelismSplitting a single large model's computation across multiple GPUs.

8. Architecture

Incoming requests (varying arrival times)
 → Continuous batching scheduler
 → GPU(s) running the model, with PagedAttention-managed KV cache
 → Tokens streamed back per request as generated
 → Request completes, its batch slot freed for a new incoming request

9. How it works internally (continuous batching)

Traditional static batching waits for a fixed group of requests to all arrive and processes them together, wasting GPU time when requests finish at different lengths (the batch is only as fast as its slowest member). Continuous batching instead treats the batch as a dynamic pool: as soon as one request finishes generating, a new waiting request is immediately added to the batch at the next generation step, keeping GPU utilization consistently high rather than idling or being blocked by a few long-running requests.

10. Step-by-step: serving an open model efficiently

  1. Choose a serving engine (vLLM for general-purpose throughput, SGLang for structured generation performance, TensorRT-LLM for NVIDIA-specific maximum optimization).
  2. Load the model (optionally quantized) with tensor parallelism across available GPUs if needed.
  3. Configure batching and KV cache memory settings based on expected concurrency.
  4. Expose an OpenAI-compatible API endpoint for application integration.
  5. Load-test under realistic concurrent request patterns, tuning for your actual latency/throughput targets.

12. Real-world example

A company self-hosting Llama for a high-volume internal tool uses vLLM specifically for its PagedAttention memory management, allowing significantly higher concurrent request throughput on the same GPU hardware compared to a naive Hugging Face Transformers serving setup — directly translating to lower cost per request at their production scale.

15. Common mistakes

  • Using naive Hugging Face Transformers serving for production traffic instead of a purpose-built inference engine.
  • Not tuning batch size / concurrency settings for actual production traffic patterns.
  • Ignoring GPU memory utilization settings, leaving significant throughput on the table.
  • Choosing quantization aggressively without validating quality impact on the actual task.

16. Best practices

  • Use a dedicated serving engine (vLLM, SGLang, TensorRT-LLM) for any production self-hosted deployment.
  • Load-test under realistic concurrency before finalizing configuration.
  • Monitor GPU utilization, throughput, and per-request latency continuously in production.
  • Validate quantization's quality impact against your actual task before adopting it for cost savings.

17. Production considerations

Treat the serving engine configuration as a first-class production concern — autoscaling, health checks, and request queuing behavior under load all need explicit design, not just default settings.

18. Security considerations

Self-hosted inference endpoints need the same API authentication/access control as any internal service — don't expose an unauthenticated inference endpoint on a reachable network.

19. Performance considerations

Continuous batching + PagedAttention-style memory management are the primary levers for throughput at scale; speculative decoding can reduce latency for individual requests without sacrificing output distribution correctness.

20. Cost considerations

Higher achievable throughput directly reduces cost-per-request by better amortizing fixed GPU costs across more served requests — the choice of serving engine can be a larger cost lever than the choice of GPU hardware itself.

21. Debugging/troubleshooting

  • Low GPU utilization despite high request volume: check batching configuration and whether requests are being queued/blocked rather than continuously batched.
  • Out-of-memory errors under load: tune `gpu-memory-utilization` and max concurrent sequence settings; consider more aggressive quantization.
  • High latency variance: check for a few very long requests blocking shorter ones under a non-continuous-batching configuration.

27. Interview Questions — Beginner

Q1. What is vLLM?
A. A specialized inference serving engine for LLMs, known for its PagedAttention memory management, optimized for throughput at scale.
Q2. What is continuous batching?
A. Dynamically adding new requests to an in-progress batch as earlier ones complete, rather than waiting for a fixed batch to fully finish.
Q3. What is PagedAttention?
A. vLLM's technique for managing KV cache memory in non-contiguous pages, reducing memory waste compared to naive allocation.
Q4. What does throughput measure in LLM serving?
A. Total tokens/requests processed per unit time across all concurrent requests.
Q5. What does quantization do for inference serving?
A. Reduces model weight precision, shrinking memory footprint and often increasing throughput, at some quality cost.
Q6. Why not just use basic Hugging Face Transformers `generate()` for production serving?
A. It's not optimized for concurrent, high-throughput serving the way dedicated engines like vLLM are, leading to much lower GPU utilization and higher cost per request at scale.
Q7. What is tensor parallelism?
A. Splitting a single large model's computation across multiple GPUs.
Q8. What is speculative decoding?
A. Using a smaller draft model to propose tokens that the larger model verifies in parallel, reducing the number of expensive sequential forward passes.
Q9. Name two popular LLM serving engines besides vLLM.
A. SGLang and TGI (or TensorRT-LLM).
Q10. Why does GPU utilization matter for cost?
A. Higher utilization serves more requests per unit of (fixed) GPU cost, directly reducing cost per request.

28. Interview Questions — Intermediate

Q1. Why does naive static batching underperform continuous batching for real-world traffic with varying request lengths?
A. Static batching must wait for the entire batch's slowest-finishing request before processing a new batch, wasting GPU capacity on already-finished requests' slots; continuous batching immediately fills freed slots with new requests, maintaining high utilization regardless of individual request length variance.
Q2. How does PagedAttention's approach to KV cache memory differ from naive contiguous allocation, and why does that matter?
A. Naive allocation reserves a large contiguous memory block per request sized for the maximum possible sequence length, wasting memory for shorter sequences; PagedAttention allocates memory in smaller, non-contiguous pages as needed, similar to OS virtual memory paging, dramatically reducing wasted memory and allowing more concurrent requests to fit in the same GPU memory.
Q3. Why might speculative decoding provide a larger latency benefit for some tasks than others?
A. Its benefit depends on how often the draft model's proposed tokens match what the larger target model would have generated — for highly predictable continuations (common patterns, templated text), acceptance rates are high and speedup is large; for highly creative/unpredictable generation, acceptance rates drop and the benefit shrinks.
Q4. What's the trade-off of increasing `gpu-memory-utilization` settings in vLLM?
A. Higher settings allow more KV cache memory (supporting more concurrent requests/longer contexts), but leave less safety margin, increasing risk of out-of-memory errors under unexpected load spikes — tuning requires balancing throughput against stability margin.
Q5. Why would tensor parallelism be necessary for serving a very large model even on a high-end single GPU?
A. Very large models' weights (plus KV cache for concurrent requests) may simply not fit in a single GPU's memory regardless of how powerful that GPU is, requiring the model's computation to be split across multiple GPUs' combined memory.

29. Interview Questions — Advanced

Q1. How would you diagnose whether a production inference deployment's bottleneck is compute-bound or memory-bound, and how would the fix differ?
A. Profile GPU compute utilization and memory utilization separately under load; if compute is near 100% while memory has headroom, the bottleneck is compute (consider a faster GPU, quantization for faster compute, or speculative decoding); if memory is saturated while compute has headroom, the bottleneck is memory (consider PagedAttention-style memory management, more aggressive quantization to free memory, or more/larger-memory GPUs via tensor parallelism).
Q2. What's a subtle interaction between quantization and continuous batching that affects overall system throughput?
A. Quantization reduces per-request memory footprint, which — combined with continuous batching — allows significantly more concurrent requests to fit in the same GPU memory simultaneously, compounding the throughput benefit beyond what either optimization would provide alone; the two techniques are complementary, not independent, levers.

30. Interview Questions — Senior/Architect

Q1. Design a self-hosted LLM serving architecture for a product with highly variable traffic (10x spikes during peak hours), covering serving engine choice, scaling, and cost optimization.
A. Use vLLM (or similar) with continuous batching and tuned memory utilization settings as the serving layer, deploy on an autoscaling GPU instance pool that scales out during peak and back during off-peak (accepting cold-start latency trade-offs), apply quantization validated against quality requirements to increase per-GPU throughput and reduce the scaling ceiling needed, and implement request queuing with backpressure (graceful degradation or overflow to a cloud API fallback) for traffic exceeding even the scaled capacity, rather than either over-provisioning for peak constantly or failing hard under spikes.

31. Scenario-Based Questions

Scenario 1. Your self-hosted model serving GPU utilization sits around 30% even under decent request volume. What do you investigate?
A. Check whether continuous batching is actually enabled/configured correctly, whether requests are being artificially queued/limited before reaching the GPU, and whether `max-num-seqs`/concurrency settings are set too conservatively relative to actual available GPU memory.
Scenario 2. After switching from naive Transformers serving to vLLM, throughput improved but a few users report occasional request failures under peak load. What do you investigate?
A. Check for out-of-memory errors in server logs during peak concurrency — likely the `gpu-memory-utilization` setting is too aggressive for actual peak load patterns; tune it down slightly or add request queuing/backpressure so excess requests wait rather than causing OOM failures.

32. Quick revision notes

  • vLLM/SGLang/TGI: purpose-built inference engines, far more efficient than naive Transformers serving.
  • Continuous batching + PagedAttention = the core throughput/memory optimizations.
  • Quantization and speculative decoding are complementary performance levers.
  • Serving engine choice is often a bigger cost lever than GPU hardware choice alone.

33. Cheat sheet

vLLM/SGLang/TGI = purpose-built serving, far beyond naive Transformers calls. Continuous batching + PagedAttention = throughput + memory efficiency. Quantization + speculative decoding = complementary performance levers. Load-test under realistic concurrency before finalizing config.
