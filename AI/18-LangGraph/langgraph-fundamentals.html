1. What is this?

LangGraph is a framework for building stateful, multi-step LLM applications as explicit graphs: Nodes (steps/functions), Edges (transitions, including conditional branching), and a shared State object threaded through execution — purpose-built for agents, cycles, human-in-the-loop, and durable execution that simple linear chains can't express.

2. Why does it exist?

Real agents need loops (retry until success), branching (different paths based on model decisions), persistence (resume after a crash or pause for human input), and explicit state management — LangChain's linear LCEL chains don't naturally express cycles or complex control flow, so LangGraph exists as the purpose-built runtime for this control-flow complexity.

3. Why is it important?

LangGraph is the recommended, most widely adopted way to build production-grade agents in the LangChain ecosystem — understanding its state/graph model is essential for building anything beyond a single tool-calling loop, and is heavily referenced in agent-related interviews.

4. Where is it used?

Multi-step agents, multi-agent systems, RAG agents with retry/correction logic, human-approval workflows, any application needing durable, resumable, branching execution.

5. Prerequisites

AI Agents, LangChain.

6. Core concepts

  • State: a shared, typed object (often a TypedDict or Pydantic model) threaded through every node, accumulating/updating as execution proceeds.
  • Node: a function (often wrapping an LLM call or tool) that reads and updates state.
  • Edge: a transition from one node to another; can be fixed or conditional.
  • Conditional edge: a function deciding, based on current state, which node to go to next.
  • Cycles: graphs can loop back to previous nodes, enabling retry/iteration patterns naturally.
  • Checkpointing/persistence: saving graph state at each step, enabling pause/resume and recovery after failure.
  • Interrupts/human-in-the-loop: explicitly pausing execution for human review/approval before continuing.
  • Streaming: emitting intermediate state/output as the graph executes, not just the final result.

9. How it works internally (checkpointing)

After each node executes, LangGraph persists the updated state (and which node ran) to the configured checkpointer backend, keyed by a thread/session ID. This enables resuming an interrupted graph exactly where it left off (crash recovery), pausing indefinitely for human input (interrupts), and even time-travel debugging (inspecting/replaying from any previous checkpoint) — capabilities a stateless linear chain architecture cannot offer.

10. Step-by-step: building the 5 core graphs

  1. Basic agent: a single LLM node with conditional edge looping back to itself for tool calls until done.
  2. RAG agent: retrieve node → generate node → (conditional) quality-check node looping back to retrieve if poor.
  3. Research agent: plan node → search node (loop) → synthesize node.
  4. Human approval agent: propose-action node → interrupt (pause for human) → execute node (only on approval).
  5. Multi-agent system: supervisor node routing to specialist agent nodes based on task type.

12. Real-world example

A production customer-support agent uses LangGraph with an interrupt before any refund action over $50, pausing the graph and notifying a human reviewer via a separate channel; once approved, the graph resumes from its exact checkpoint and executes the refund — a pattern impossible to build cleanly with a stateless linear chain.

13. Code example (RAG agent + conditional edges)

from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class RAGState(TypedDict):
    question: str
    context: list
    answer: str
    quality: str

def retrieve(state: RAGState) -> RAGState:
    return {"context": retriever.invoke(state["question"])}

def generate(state: RAGState) -> RAGState:
    answer = (prompt | model | parser).invoke({"context": state["context"], "question": state["question"]})
    return {"answer": answer}

def check_quality(state: RAGState) -> RAGState:
    quality = "good" if is_grounded(state["answer"], state["context"]) else "poor"
    return {"quality": quality}

def route(state: RAGState) -> str:
    return "retrieve" if state["quality"] == "poor" else END

graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_node("check_quality", check_quality)
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "generate")
graph.add_edge("generate", "check_quality")
graph.add_conditional_edges("check_quality", route, {"retrieve": "retrieve", END: END})

app = graph.compile()
result = app.invoke({"question": "What's our refund policy?"})

14. Advanced example (human-in-the-loop)

from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.types import interrupt

def propose_refund(state):
    amount = calculate_refund(state["order_id"])
    if amount > 50:
        approval = interrupt({"action": "approve_refund", "amount": amount})
        if not approval:
            return {"status": "rejected"}
    return {"status": "approved", "amount": amount}

graph = StateGraph(RefundState)
graph.add_node("propose", propose_refund)
# ... edges ...
app = graph.compile(checkpointer=SqliteSaver.from_conn_string(":memory:"))

# First call pauses at interrupt; resumed later with human's decision
config = {"configurable": {"thread_id": "order-123"}}
app.invoke({"order_id": "123"}, config=config)
app.invoke(Command(resume=True), config=config)  # human approved

15. Common mistakes

  • Building a complex graph when a simple linear chain or even a single LLM call would suffice.
  • Forgetting to configure a checkpointer, losing the ability to pause/resume or recover from failures.
  • Creating unintentional infinite cycles without a termination condition.
  • Putting too much logic in a single node instead of decomposing into smaller, testable nodes.

16. Best practices

  • Keep each node's responsibility narrow and independently testable.
  • Always configure a persistent checkpointer (not just in-memory) for production.
  • Explicitly define termination conditions for every cycle.
  • Use interrupts for any high-risk/irreversible action rather than trusting the agent's own judgment alone.

17. Production considerations

Use a durable checkpointer backend (Postgres, not SQLite-in-memory) so graphs can survive process restarts; monitor graph execution traces (via LangSmith) to catch unexpected cycles or stuck states.

18. Security considerations

Interrupt/human-approval gates are a core security control for agentic systems with real-world side effects — ensure they can't be bypassed by a cleverly-crafted model response, and validate that resumed state hasn't been tampered with between pause and resume.

19. Performance considerations

Checkpointing adds I/O overhead per step — for very high-throughput, low-latency graphs, benchmark checkpointer backend performance; use streaming to improve perceived latency for long-running graphs.

20. Cost considerations

Cycles multiply LLM call cost with each iteration — bound cycles with explicit limits, and monitor actual iteration-count distributions in production to catch cost regressions.

21. Debugging/troubleshooting

  • Graph runs forever: check conditional edge logic for a missing/incorrect termination condition.
  • State not persisting across restarts: verify a persistent checkpointer (not default in-memory) is configured for the deployed environment.
  • Interrupt never resumes correctly: verify the thread_id/config used for resume matches exactly the one used for the initial pause.

27. Interview Questions — Beginner

Q1. What is LangGraph?
A. A framework for building stateful, multi-step LLM applications as explicit graphs of nodes, edges, and shared state.
Q2. What is a Node in LangGraph?
A. A function (often wrapping an LLM call or tool) that reads and updates the shared graph state.
Q3. What is a conditional edge?
A. An edge whose destination is decided dynamically by a function based on the current state.
Q4. What is checkpointing?
A. Persisting graph state at each step, enabling pause/resume and recovery after a crash.
Q5. What is an interrupt?
A. A mechanism to pause graph execution, typically for human review/approval, resumable later.
Q6. Why would a graph need cycles?
A. To support retry/iteration patterns, like retrying retrieval if generated answer quality is poor.
Q7. What's human-in-the-loop in LangGraph used for?
A. Pausing execution before high-risk or irreversible actions until a human explicitly approves.
Q8. Why is LangGraph preferred over plain LCEL chains for complex agents?
A. LCEL chains are linear; LangGraph natively supports cycles, branching, persistent state, and interrupts that complex agents need.
Q9. What does "durable execution" mean?
A. Execution that can survive process restarts/crashes by resuming from the last saved checkpoint.
Q10. What's a StateGraph?
A. LangGraph's main class for defining a graph of nodes and edges operating over a shared state object.

28. Interview Questions — Intermediate

Q1. How does LangGraph's checkpointing enable "time-travel debugging"?
A. Since state is persisted after every node execution, you can inspect or resume execution from any previous checkpoint, letting you replay or branch from an earlier point to debug exactly what happened at each step.
Q2. Why must every cycle in a LangGraph graph have an explicit termination condition?
A. Without one, a conditional edge could route back into the same cycle indefinitely, causing an infinite loop that never reaches END — termination conditions (iteration counts, quality checks, explicit done flags) are essential safety requirements.
Q3. How would you implement a supervisor/router pattern in LangGraph for a multi-agent system?
A. Create a supervisor node whose function examines the task/state and returns which specialist node to route to next via a conditional edge, with each specialist node performing its sub-task and routing back to the supervisor for the next decision.
Q4. Why is an in-memory checkpointer inappropriate for production but fine for development?
A. In-memory state is lost on process restart, making pause/resume and crash recovery impossible in production; a persistent backend (SQLite file, Postgres) is needed to actually survive restarts, while in-memory is convenient and sufficient for quick local testing.
Q5. How would you test that a human-in-the-loop interrupt correctly pauses and resumes a graph?
A. Invoke the graph up to the interrupt point, verify execution actually paused (state reflects the pre-interrupt point, no further nodes ran), then resume with a simulated approval/rejection and verify the graph proceeds down the correct branch based on that input.

29. Interview Questions — Advanced

Q1. How would you design a LangGraph-based multi-agent system where specialist agents can fail independently without crashing the whole graph?
A. Wrap each specialist node's execution in error handling that captures failures into the state (e.g., a status field) rather than raising uncaught exceptions, route failed specialist results to a recovery/fallback node via conditional edges, and use checkpointing so a failure in one branch doesn't lose progress made in completed branches.
Q2. What's a subtle concurrency concern when multiple graph instances share the same checkpointer backend under high load?
A. Concurrent writes to the same thread_id's checkpoint could race if not properly isolated; production checkpointer backends need to handle concurrent access safely (e.g., via database-level locking/transactions), and application code should ensure one thread_id isn't being invoked concurrently from multiple processes unless the backend explicitly supports it.

30. Interview Questions — Senior/Architect

Q1. Design a production LangGraph architecture for a multi-agent customer support platform with human escalation, covering state design, persistence, and failure handling.
A. Define a shared state schema capturing conversation history, current specialist assignment, and escalation status; use a supervisor node routing between specialist agent nodes (billing, technical, account) based on classified intent; configure a durable Postgres checkpointer keyed by conversation thread_id for crash recovery and multi-turn persistence; add interrupt nodes before any action with real-world consequences (refunds, account changes) requiring human approval; implement per-node error handling that routes failures to a human-escalation node rather than crashing; and instrument full LangSmith tracing for observability across the whole multi-agent flow.

31. Scenario-Based Questions

Scenario 1. A LangGraph agent occasionally runs in an infinite loop in production, incurring runaway costs. What's your immediate fix and long-term solution?
A. Immediate: add a hard iteration/step limit to the graph (fail-safe termination) if not already present. Long-term: audit the conditional edge logic causing the loop, add explicit progress-tracking state to detect non-productive cycles, and add monitoring/alerting on iteration-count distributions to catch this class of issue earlier.
Scenario 2. After a server restart, in-progress human-approval-pending agent sessions were lost. How do you prevent this in the future?
A. Switch from an in-memory checkpointer to a persistent backend (Postgres/SQLite file) so paused/interrupted sessions survive process restarts, and verify this with an explicit restart-recovery test as part of the deployment process.
Scenario 3. Your RAG agent's retry-on-poor-quality cycle sometimes loops through the same unhelpful retrieval result repeatedly. How do you fix it?
A. Vary the retrieval strategy on retry (e.g., query rewriting, different k, or fallback to web search) rather than retrying with identical parameters, and add a cycle counter that, after N retries, routes to a "best effort" or human-escalation path instead of looping indefinitely on the same failing approach.

32. Quick revision notes

  • LangGraph: State + Nodes + Edges (including conditional) + Checkpointing.
  • Supports cycles, branching, persistence, interrupts — things linear LCEL chains can't do.
  • Always bound cycles; always use a persistent checkpointer in production.
  • Interrupts enable human-in-the-loop for high-risk actions.

33. Cheat sheet

LangGraph = State + Nodes + Edges (conditional/cyclic) + Checkpointer. Use for agents needing loops, branching, persistence, or human-in-the-loop. Always bound cycles; use a durable checkpointer in production.
