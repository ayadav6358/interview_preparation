1. What is this?

A complete, buildable RAG document Q&A system using PostgreSQL with the pgvector extension as the vector store — chosen specifically because it requires no new infrastructure beyond Postgres, making it the most practical first production RAG implementation for a typical software engineering team.

2. Why build this project?

Reading about RAG concepts (RAG Fundamentals) doesn't build the muscle memory of handling real issues: PDF parsing quirks, chunk boundary decisions, embedding batch management, and prompt construction under token budgets. This project forces those decisions.

3. Why is it important?

This is the single most commonly requested "build me an AI feature" project in real companies — a document Q&A assistant over internal docs, contracts, or support articles — making it one of the highest-leverage projects for both interviews and real work.

4. Where would this be used?

Internal documentation assistants, customer support knowledge bases, contract/policy Q&A tools, onboarding assistants.

5. Prerequisites

RAG Fundamentals, Vector Databases, basic SQL and Python.

6. Requirements

  • Functional: ingest PDF/text documents; answer natural-language questions grounded in those documents with citations; support incremental document updates.
  • Non-functional: p95 query latency under 3 seconds; graceful "I don't know" for unsupported questions; no cross-tenant data leakage if multi-tenant.

8. Architecture

Ingestion:
 PDF/text files → pypdf loader → text cleanup
  → chunker (800 tokens, 100 overlap)
  → embed each chunk → INSERT INTO chunks (content, embedding, doc_id, metadata)

Query:
 FastAPI /ask {question, tenant_id}
  → embed question
  → SELECT ... WHERE tenant_id = $1 ORDER BY embedding <=> $2 LIMIT 5
  → construct prompt with numbered context
  → Claude API call
  → return {answer, sources}

9. Database design

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    title TEXT,
    tenant_id INT,
    uploaded_at TIMESTAMP DEFAULT now()
);

CREATE TABLE chunks (
    id SERIAL PRIMARY KEY,
    document_id INT REFERENCES documents(id) ON DELETE CASCADE,
    tenant_id INT,
    content TEXT,
    embedding VECTOR(1536),
    chunk_index INT
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks (tenant_id);

10. Implementation steps

  1. Set up PostgreSQL with pgvector extension enabled.
  2. Build the ingestion script: load PDF → parse → chunk → embed → insert.
  3. Build the FastAPI `/ask` endpoint: embed query → retrieve → construct prompt → call LLM → return answer + sources.
  4. Add tenant-scoped filtering to every retrieval query.
  5. Add an evaluation script testing retrieval + answer quality against a small golden set.
  6. Add logging of token usage, latency, and retrieval results per request.

13. Code example (full pipeline)

import psycopg2, os
from anthropic import Anthropic
from pypdf import PdfReader

conn = psycopg2.connect(os.environ["DATABASE_URL"])
client = Anthropic()

def chunk_text(text, size=800, overlap=100):
    words = text.split()
    chunks = []
    for i in range(0, len(words), size - overlap):
        chunks.append(" ".join(words[i:i+size]))
    return chunks

def ingest(tenant_id, title, file_path):
    reader = PdfReader(file_path)
    full_text = "\n".join(page.extract_text() for page in reader.pages)
    cur = conn.cursor()
    cur.execute("INSERT INTO documents (title, tenant_id) VALUES (%s, %s) RETURNING id",
                (title, tenant_id))
    doc_id = cur.fetchone()[0]
    for i, chunk in enumerate(chunk_text(full_text)):
        vec = embed(chunk)
        cur.execute(
            "INSERT INTO chunks (document_id, tenant_id, content, embedding, chunk_index) VALUES (%s,%s,%s,%s,%s)",
            (doc_id, tenant_id, chunk, vec, i),
        )
    conn.commit()

def ask(tenant_id, question, k=5):
    q_vec = embed(question)
    cur = conn.cursor()
    cur.execute(
        "SELECT id, content FROM chunks WHERE tenant_id = %s ORDER BY embedding <=> %s LIMIT %s",
        (tenant_id, q_vec, k),
    )
    results = cur.fetchall()
    context = "\n\n".join(f"[{i+1}] {c}" for i, (_, c) in enumerate(results))
    prompt = f"""Context:\n{context}\n\nQuestion: {question}
Answer only from context above, citing [1], [2] etc. If not covered, say so."""
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=400,
        messages=[{"role": "user", "content": prompt}],
    )
    return {"answer": resp.content[0].text,
            "sources": [{"id": r[0], "content": r[1]} for r in results]}

15. Common mistakes

  • Forgetting the `tenant_id` filter on the retrieval query — a critical security bug.
  • Not cleaning up old chunks when a document is re-ingested/updated, leaving stale duplicates.
  • Chunking by raw character count without respecting word/sentence boundaries, producing broken mid-word chunks.
  • No evaluation set — shipping without ever measuring retrieval/answer quality.

16. Best practices

  • Always filter by tenant_id (or equivalent) at the SQL level, never only in application code.
  • Delete old chunks for a document before re-inserting updated ones (`DELETE FROM chunks WHERE document_id = ...`).
  • Log every retrieval's chunk IDs and scores for debugging and evaluation.
  • Build a golden evaluation set early, even just 20 question/answer pairs.

17. Production considerations / deployment

Run ingestion as an idempotent batch job (safe to re-run); deploy the API behind the same resilience patterns as any LLM API integration (timeouts, retries, fallback — see LLM APIs and SDKs); monitor retrieval latency and LLM latency separately.

18. Security considerations

Tenant isolation must be enforced at the SQL query level (`WHERE tenant_id = $1`), never trusted to application-layer filtering alone; sanitize any user-uploaded document content before display to prevent stored XSS if rendered in a web UI.

19. Performance considerations

The HNSW index on `embedding` is critical at scale — without it, `ORDER BY embedding <=> $1` falls back to a full scan; monitor `EXPLAIN ANALYZE` on retrieval queries as data grows.

20. Cost considerations

Embedding cost is incurred once per chunk at ingestion and once per query; generation cost scales with context size (number of retrieved chunks × their length) and output length — the dominant cost driver at scale.

21. Testing & debugging

  • Unit test chunking logic for boundary correctness.
  • Integration test tenant isolation explicitly (insert data for 2 tenants, verify no cross-contamination in results).
  • Evaluate against a golden set of Q&A pairs, tracking retrieval recall and answer faithfulness over time.

27. Interview Questions — Beginner

Q1. Why was PostgreSQL + pgvector chosen for this project instead of a dedicated vector DB?
A. It avoids introducing new infrastructure when the team already runs Postgres, while still providing adequate vector similarity search via the pgvector extension.
Q2. What does the `tenant_id` column protect against?
A. Cross-tenant data leakage — ensuring one tenant's query never retrieves another tenant's documents.
Q3. Why do we delete old chunks before re-inserting updated document chunks?
A. To avoid stale, duplicate, or outdated chunks remaining searchable after a document update.
Q4. What's the purpose of the HNSW index in this schema?
A. It enables fast approximate nearest-neighbor search instead of a slow full table scan for similarity queries.
Q5. Why does the prompt include numbered context like [1], [2]?
A. To enable the model to cite specific sources, making answers verifiable and traceable back to source chunks.
Q6. What happens if a question isn't covered by any retrieved chunk?
A. The prompt instructs the model to say so rather than fabricate an answer.
Q7. Why chunk a PDF instead of embedding the whole document as one vector?
A. Whole-document embeddings lose fine-grained relevance signal and often exceed context/embedding size limits; chunking enables precise retrieval of just the relevant portion.
Q8. What's the role of the FastAPI layer in this architecture?
A. It exposes the ingestion and query logic as HTTP endpoints that other applications/UIs can call.
Q9. Why test tenant isolation explicitly rather than assuming the filter works?
A. Because a missing or buggy filter is a security-critical failure mode that's easy to introduce accidentally (e.g., during refactoring) and must be caught by automated tests, not just code review.
Q10. What's a golden evaluation set used for in this project?
A. A curated set of question/answer pairs used to measure and track retrieval and answer quality over time, catching regressions.

28. Interview Questions — Intermediate

Q1. How would you modify this project's ingestion pipeline to support incremental updates efficiently for a large, frequently-changing document set?
A. Track a content hash or last-modified timestamp per document, skip re-processing unchanged documents, and only delete+re-insert chunks for documents that actually changed, rather than re-ingesting the entire corpus each run.
Q2. Why might `chunk_text`'s simple word-count-based splitting be suboptimal for this project, and what would you improve?
A. It can split mid-sentence or across logical sections (like a heading from its content), hurting chunk coherence; improve by splitting at natural boundaries (paragraphs, sentences, or markdown headers) while still respecting an approximate token budget.
Q3. How would you add observability to this project to debug a specific user's "wrong answer" complaint?
A. Log the full request (question, tenant_id), the retrieved chunk IDs and similarity scores, the exact prompt sent to the LLM, and the raw response — enabling you to replay and inspect exactly what context the model saw for that specific answer.
Q4. Why is `EXPLAIN ANALYZE` useful when the retrieval query starts slowing down as data grows?
A. It reveals whether PostgreSQL is actually using the HNSW index for the similarity search or falling back to a sequential scan, which is the most common cause of unexpected vector-query slowdowns at scale.
Q5. How would you extend the `/ask` endpoint to support conversational follow-up questions (e.g., "what about international orders?" referring to a previous question about refunds)?
A. Include recent conversation history in the retrieval query construction (e.g., rewrite the follow-up into a standalone query using the LLM, or concatenate recent context before embedding) so the retriever has enough context to find relevant chunks for an otherwise ambiguous follow-up.

29. Interview Questions — Advanced

Q1. How would you redesign this project's schema and ingestion to support versioned documents, where users can ask questions against a specific historical version?
A. Add a `version` column to both `documents` and `chunks`, never delete old versions' chunks (mark them inactive instead), and include a version filter in retrieval queries alongside tenant_id — allowing both "latest" queries (filter to active version) and historical queries (filter to a specific version) from the same schema.
Q2. What's a subtle data-leak risk if tenant_id filtering is applied only in the embedding/retrieval step but the LLM is also given tool access to a general document-search function?
A. If the LLM can independently invoke a search tool without the application enforcing the same tenant scoping on that tool's execution, it could retrieve or be influenced by cross-tenant data through that side channel — every tool/function the model can call must independently enforce the same access-control boundaries as the primary retrieval path.

30. Interview Questions — Senior/Architect

Q1. This project currently uses synchronous embedding calls during ingestion. How would you redesign it to ingest 100,000 documents efficiently?
A. Batch embedding API calls where the provider supports it, parallelize across async workers with rate-limit-aware concurrency control, use a job queue (e.g., for retries on individual document failures without restarting the whole batch), and stream progress/status to allow monitoring and resumability on failure.

31. Scenario-Based Questions

Scenario 1. A customer reports seeing another company's refund policy in their chatbot's answer. How do you respond and what's the root-cause investigation?
A. Immediately audit the retrieval query for missing/broken tenant_id filtering — this is a critical security incident requiring immediate patch and incident disclosure; verify via logs which specific request leaked data and to what extent, and add a regression test ensuring this specific failure mode is covered going forward.
Scenario 2. After re-ingesting an updated policy document, the chatbot still answers using the old policy content. What's wrong?
A. The ingestion pipeline likely didn't delete the old chunks before/during re-insertion, so both old and new chunks are in the index and the old ones are still being retrieved — fix by deleting existing chunks for that document_id before inserting the updated ones.
Scenario 3. Query latency has crept up from 200ms to 3 seconds over 6 months as the document corpus grew. What do you investigate first?
A. Run EXPLAIN ANALYZE on the retrieval query to check if the HNSW index is still being used effectively, verify index maintenance/health hasn't degraded, and check if the growing corpus size now needs index parameter tuning or a different indexing/sharding strategy for the new scale.

32. Quick revision notes

  • pgvector = no new infra if already using Postgres.
  • Always filter by tenant_id at the SQL level.
  • Delete old chunks before re-inserting updated document chunks.
  • HNSW index is critical for retrieval performance at scale.
  • Build a golden eval set early; log full request/retrieval/response for debugging.

33. Cheat sheet

pgvector RAG: documents + chunks tables, HNSW index, mandatory tenant_id filter, numbered-context prompt with citation instructions and "I don't know" fallback. Delete-then-reinsert on document updates. Log everything for debugging/eval.
