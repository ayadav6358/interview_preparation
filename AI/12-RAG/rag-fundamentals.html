1. What is this?

RAG (Retrieval-Augmented Generation) is an architecture pattern that retrieves relevant documents from an external knowledge source at query time and injects them into the LLM's prompt, so the model generates answers grounded in that retrieved content instead of relying solely on its frozen parametric (training-time) knowledge.

2. Why does it exist?

LLMs have a training cutoff and fixed parametric knowledge — they can't know about your private documents, recent events, or frequently-changing information. Fine-tuning for every knowledge update is slow and expensive. RAG exists to inject fresh, verifiable, source-attributable knowledge into the model's context at inference time, without touching model weights.

3. Why is it important?

RAG is the single most common pattern for building production LLM applications over private/proprietary/frequently-changing data — virtually every "chat with your documents" or enterprise knowledge assistant product is fundamentally a RAG system, making it one of the highest-value skills for an AI engineer.

4. Where is it used?

Enterprise knowledge assistants, customer support bots, legal/medical document Q&A, code-base-aware coding assistants, internal documentation search, any chatbot needing to cite or ground answers in specific source material.

5. Prerequisites

Embeddings, Vector Databases.

6. Core concepts

  • Document ingestion: loading raw source documents (PDFs, web pages, databases) into the pipeline.
  • Chunking: splitting documents into smaller pieces sized appropriately for embedding and retrieval.
  • Embedding + Indexing: converting chunks to vectors and storing them in a vector database.
  • Retrieval: finding the most relevant chunks for a given query.
  • Prompt construction: assembling retrieved chunks + the user's question into a single prompt.
  • Generation: the LLM produces an answer grounded in the provided context.

7. Terminology

TermMeaning
LoaderComponent that reads raw documents (PDF, HTML, DB rows) into a usable text format.
ParserExtracts clean, structured text from raw loaded content (e.g., stripping PDF formatting noise).
ChunkerSplits parsed text into smaller segments (chunks) for embedding.
Chunk size/overlapHow large each chunk is, and how much adjacent chunks overlap to preserve context across boundaries.
RetrieverComponent that queries the vector DB (and/or lexical index) to fetch relevant chunks.
GroundingTying generated answers to retrieved source material, reducing hallucination risk.
CitationExplicitly referencing which retrieved source supports a claim in the answer.

8. Architecture

Documents
 → Loader (read raw files)
 → Parser (extract clean text)
 → Chunker (split into retrievable segments)
 → Embedding (convert chunks to vectors)
 → Vector DB (store + index)

Query time:
 User question
 → Embed question
 → Retriever (vector DB similarity search, + optional metadata filter/rerank)
 → Retrieved chunks → Context
 → Prompt = Context + Question
 → LLM → Answer (ideally with citations)

9. How it works internally

At ingestion time, documents are chunked and embedded once (offline/batch), stored with metadata in a vector DB. At query time, the user's question is embedded with the same model, and a similarity search retrieves the top-k most relevant chunks. These chunks are concatenated into the prompt's context section, and the LLM is instructed to answer based only on that context — shifting the task from "recall from training" to "read comprehension over provided text," which is both more accurate and auditable.

10. Step-by-step explanation

  1. Load raw documents (PDFs, web pages, database exports).
  2. Parse into clean text, removing formatting noise.
  3. Chunk text into appropriately sized segments (with overlap).
  4. Embed each chunk and store it with metadata in a vector DB.
  5. At query time, embed the user's question.
  6. Retrieve the top-k most similar chunks (optionally filtered/reranked).
  7. Construct a prompt combining retrieved chunks and the question.
  8. Generate the answer, instructing the model to cite sources and avoid unsupported claims.

11. Simple example

A user asks "What's our refund policy?" The system retrieves the "Refund Policy" document chunk, includes it in the prompt, and the LLM answers directly from that text rather than guessing from general knowledge.

12. Real-world example

An enterprise internal-docs assistant indexes thousands of Confluence pages; when an employee asks about VPN setup, it retrieves the specific IT documentation page, grounds the answer in it, and cites the source page so the employee can verify/read further — far more trustworthy than an ungrounded LLM guess.

13. Code example

from anthropic import Anthropic
import psycopg2

client = Anthropic()
conn = psycopg2.connect("dbname=ragdb")

def retrieve(query: str, k=3):
    query_vec = embed(query)
    cur = conn.cursor()
    cur.execute(
        "SELECT content FROM documents ORDER BY embedding <=> %s LIMIT %s",
        (query_vec, k),
    )
    return [row[0] for row in cur.fetchall()]

def answer(question: str):
    chunks = retrieve(question)
    context = "\n\n".join(chunks)
    prompt = f"""Answer the question using ONLY the context below. If the answer isn't in the context, say so.

Context:
{context}

Question: {question}"""
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=400,
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.content[0].text

14. Advanced example

Adding citation tracking so the answer references which chunk supported each claim:

def answer_with_citations(question: str):
    chunks = retrieve(question, k=5)
    numbered_context = "\n\n".join(f"[{i+1}] {c}" for i, c in enumerate(chunks))
    prompt = f"""Context:
{numbered_context}

Question: {question}
Answer using the context above. Cite sources like [1], [2] after each claim. If unsupported, say so."""
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=500,
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.content[0].text, chunks  # return sources for UI display

15. Common mistakes

  • Chunking too large (dilutes relevance) or too small (loses context) without testing against real queries.
  • Not instructing the model to say "I don't know" when retrieved context doesn't cover the question.
  • Retrieving too many chunks "to be safe," diluting attention (lost in the middle).
  • Forgetting metadata filtering in multi-tenant RAG, risking cross-tenant data leakage.
  • Not re-indexing after source documents are updated/deleted, serving stale answers.

16. Best practices

  • Tune chunk size/overlap empirically against your actual query patterns and document structure.
  • Require citations and explicitly allow "I don't know" responses.
  • Add a reranking step for retrieval precision (see Advanced RAG).
  • Evaluate retrieval quality and answer faithfulness separately (see AI Evaluation).
  • Keep the ingestion pipeline idempotent and re-runnable for easy updates.

17. Production considerations

Build an incremental ingestion pipeline (only re-process changed documents), monitor retrieval quality continuously (not just at launch), and have a defined process for removing/updating stale or deleted source documents from the index.

18. Security considerations

Enforce tenant/permission-scoped retrieval filtering rigorously — RAG systems are a common source of accidental data leaks when document-level access controls aren't mirrored in the retrieval filtering logic. Treat retrieved content as untrusted input for prompt-injection purposes if it includes user-generated or external content.

19. Performance considerations

Retrieval latency (vector search + optional reranking) adds to total response time before generation even starts — profile and optimize this path separately from LLM generation latency; consider caching frequent queries' retrieval results.

20. Cost considerations

Embedding costs are incurred at ingestion (once per document) and at query time (once per query) — much cheaper than LLM generation; the main RAG cost driver is usually the generation call's input tokens, which scale with how much retrieved context you include.

21. Debugging/troubleshooting

  • Answers ignore retrieved context: check prompt construction — ensure context is clearly presented and the instruction to use it is explicit and prominent.
  • Wrong/irrelevant chunks retrieved: check embedding model consistency, chunk size, and consider adding reranking.
  • Answers cite sources that don't actually support the claim: the model may be fabricating citations — verify citation-claim alignment with an automated check.

27. Interview Questions — Beginner

Q1. What does RAG stand for?
A. Retrieval-Augmented Generation.
Q2. Why does RAG exist?
A. To let an LLM answer using fresh, private, or frequently-changing knowledge not present in its frozen training data, without retraining the model.
Q3. What is chunking?
A. Splitting documents into smaller segments sized appropriately for embedding and retrieval.
Q4. What's the difference between RAG and fine-tuning for adding new knowledge?
A. RAG injects knowledge via retrieved context at inference time (no weight changes); fine-tuning bakes new behavior/knowledge into the model's weights through additional training.
Q5. What is a retriever?
A. The component that finds and returns the most relevant document chunks for a given query, typically via vector similarity search.
Q6. Why should a RAG system be able to say "I don't know"?
A. To avoid hallucinating an answer when the retrieved context doesn't actually contain relevant information.
Q7. What does "grounding" mean in RAG?
A. Tying the generated answer to retrieved source material, reducing the risk of fabricated/unsupported claims.
Q8. What's a citation in a RAG answer?
A. An explicit reference indicating which retrieved source supports a specific claim in the answer.
Q9. Does RAG change the LLM's weights?
A. No — it only changes what's in the context/prompt at inference time.
Q10. Name one real-world RAG use case.
A. An enterprise knowledge assistant answering questions from internal documentation.

28. Interview Questions — Intermediate

Q1. Why might retrieving too many chunks hurt RAG answer quality despite providing more information?
A. It dilutes attention across more (often less relevant) content, risking "lost in the middle" effects and confusing synthesis — precision of retrieval matters more than raw recall/volume.
Q2. How would you choose chunk size for a RAG pipeline over long legal documents versus short FAQ entries?
A. Legal documents often need larger chunks (or overlap) to preserve clause-level context that spans sentences/paragraphs; FAQ entries are typically self-contained and can use smaller, tighter chunks — the right size should be validated empirically against real queries for each corpus type.
Q3. What's the risk of not instructing the model to only use the provided context?
A. The model may blend its own parametric (training) knowledge with the retrieved context, producing answers that seem grounded but actually include unverified or outdated information not actually present in the retrieved sources.
Q4. How would you detect that your RAG system is hallucinating despite having correct retrieval?
A. Run an automated faithfulness check (LLM-as-judge or rule-based) comparing each claim in the generated answer against the actual retrieved chunks, flagging any claim not supported by the retrieved content even when retrieval itself was accurate.
Q5. Why is RAG often preferred over fine-tuning for knowledge that changes frequently (e.g., current pricing)?
A. Updating the retrieval corpus (adding/editing a document) is immediate and cheap; fine-tuning requires a full retraining cycle each time the knowledge changes, which is far slower and more expensive for frequently-updated information.
Q6. What's a practical reason to add overlap between chunks?
A. Without overlap, information spanning a chunk boundary can be split across two chunks and lose coherence when retrieved individually; overlap helps preserve local context across boundaries.
Q7. How would you evaluate whether your RAG system's retrieval step itself is the bottleneck versus the generation step?
A. Separately evaluate retrieval quality (e.g., recall@k against a labeled set of question-to-relevant-chunk mappings) and generation faithfulness (given correct retrieved chunks, does the answer accurately reflect them) — isolating each stage pinpoints where quality issues originate.
Q8. Why might a RAG system perform worse on questions requiring synthesis across multiple documents compared to single-document lookup questions?
A. Multi-document synthesis requires the retriever to find and the model to correctly integrate information from several, possibly differently-worded chunks simultaneously — a harder retrieval and reasoning problem than matching a single clearly relevant chunk.
Q9. What's the role of metadata in a RAG system beyond access control?
A. Metadata (e.g., document date, source type, section) enables filtering retrieval to more relevant subsets (e.g., "only the latest policy version") and can be surfaced to users as part of citations for trust/verification.
Q10. Why is RAG not a complete solution to hallucination, even with perfect retrieval?
A. The generation step can still misinterpret, overgeneralize, or blend retrieved content with ungrounded parametric knowledge; perfect retrieval only ensures the right information is available, not that the model will use it faithfully.

29. Interview Questions — Advanced

Q1. How would you architect a RAG system to handle both frequently-updated and rarely-updated document types with different freshness requirements?
A. Separate ingestion pipelines/cadences per document type (e.g., real-time or near-real-time ingestion for frequently-updated sources, batch/scheduled for stable ones), tag chunks with freshness metadata, and potentially weight retrieval ranking by recency for time-sensitive queries.
Q2. Why might naive chunking by fixed character/token count underperform semantic or structure-aware chunking for technical documentation?
A. Fixed-size chunking can split a logically coherent unit (a code example, a numbered procedure, a table) mid-way, destroying its meaning when retrieved in isolation; semantic/structure-aware chunking (splitting at natural boundaries like headers, paragraphs, or code blocks) preserves coherent units better, improving both retrieval relevance and generation quality.
Q3. How would you measure and improve the "faithfulness" metric for a production RAG system at scale?
A. Use an automated LLM-as-judge pipeline that, for a sample of production answers, checks each claim against the actually-retrieved context and flags unsupported claims; track this metric over time, investigate spikes (often correlating with specific query types, prompt changes, or model updates), and use the flagged failures to refine prompting (e.g., stricter "only use context" instructions) or retrieval precision.

30. Interview Questions — Senior/Architect

Q1. Design a production enterprise RAG system end to end, covering ingestion, retrieval, generation, security, and evaluation.
A. Ingestion: incremental pipeline with loaders/parsers per document type, chunking tuned per content type, embedding with a consistent versioned model. Retrieval: vector DB with mandatory tenant/permission-scoped metadata filtering, hybrid search + reranking for precision. Generation: strict "answer only from context" prompting with mandatory citations and explicit "I don't know" fallback. Security: access control mirrored from source systems into retrieval filters, audit logging of all queries/retrievals. Evaluation: continuous automated faithfulness and retrieval-quality monitoring against a golden set, with alerting on regression.
Q2. How would you decide between RAG, fine-tuning, and long-context stuffing for a new enterprise knowledge product, and how might you combine them?
A. Default to RAG for large/frequently-changing/private corpora needing source attribution; consider fine-tuning only for durable behavior/style/domain-reasoning adaptations, not primarily for facts; consider long-context stuffing only for genuinely small, stable corpora where lost-in-the-middle isn't a measured problem. In practice, combine: RAG for knowledge grounding, with a lightly fine-tuned model for domain-specific tone/format if justified by evaluation data.

31. Scenario-Based Questions

Scenario 1. Users report the RAG chatbot "lies confidently" about company policy despite having the correct documents indexed. How do you fix it?
A. Tighten the generation prompt to strictly require answering only from provided context, add mandatory citations, instruct explicit "I don't know" when context is insufficient, and add an automated faithfulness check flagging unsupported claims for review.
Scenario 2. A security review finds that updating a source document doesn't remove the old version's content from search results. What's the fix?
A. Implement a proper document lifecycle in the ingestion pipeline — deleting/invalidating old chunks associated with a document ID before or atomically with inserting new chunks on update, rather than purely additive ingestion.
Scenario 3. Your RAG system performs well on single-fact lookup questions but poorly on questions requiring combining information from 3 different documents. How do you improve this?
A. Increase retrieved chunk diversity/count for complex queries (possibly via query decomposition — breaking the question into sub-questions each separately retrieved), improve reranking to ensure complementary (not redundant) chunks are selected, and consider an agentic multi-step retrieval pattern (see Agentic RAG) for genuinely complex synthesis questions.

32. Quick revision notes

  • RAG = retrieve relevant chunks + inject into prompt + generate grounded answer.
  • Pipeline: load → parse → chunk → embed → index → retrieve → prompt → generate.
  • Require citations and "I don't know" fallback to reduce hallucination.
  • Tune chunk size/overlap and retrieval precision (reranking) empirically.
  • Enforce tenant/permission-scoped filtering for security.

33. Cheat sheet

RAG: Documents → Loader → Parser → Chunker → Embedding → Vector DB → Retriever → Context → LLM → Answer. Always require citations + "I don't know" fallback. Tune chunking and retrieval precision empirically. Enforce access-control-aware filtering.
