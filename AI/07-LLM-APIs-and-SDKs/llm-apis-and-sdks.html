1. What is this?

The practical engineering layer for calling LLMs reliably in production: authentication, request/response handling, streaming, structured output, tool/function calling, retries, timeouts, rate limits, batch processing, token/cost tracking, and model fallback.

2. Why does it exist?

Raw model capability is only half the story — LLM APIs are network services with real-world failure modes (timeouts, rate limits, transient errors) just like any other external dependency, and production systems need the same engineering discipline (retries, circuit breakers, abstraction) applied to any unreliable third-party API.

3. Why is it important?

Most production LLM incidents are not "the model got dumber" — they're API-integration issues: unhandled rate limits, missing retries, no fallback, or untracked cost/token usage. This is the engineering discipline that separates a demo from a production system.

4. Where is it used?

Every production LLM application's networking/integration layer.

5. Prerequisites

LLM Providers, Python for AI (async).

6. Core concepts

  • Streaming: receiving tokens incrementally rather than waiting for the full response.
  • Structured output / JSON schema: constraining the model's output to match a defined schema.
  • Tool/function calling: the model requests a defined function be called with structured arguments.
  • Retries with backoff: automatically retrying transient failures (rate limits, timeouts) with increasing delay.
  • Model fallback: switching to a secondary model/provider when the primary fails or is unavailable.
  • Provider abstraction: a common interface decoupling business logic from any single provider's SDK.

9. How it works internally

A streaming API call opens a persistent connection (typically Server-Sent Events) and the server pushes partial tokens as they're generated, rather than buffering the full response — the client's SDK exposes this as an iterator/async-generator the application consumes incrementally. Structured output modes typically work either via constrained decoding (the server restricts sampling to only schema-valid tokens) or via a strong prompting + validation + retry loop, depending on provider maturity.

10. Step-by-step: a resilient API call

  1. Set a reasonable request timeout.
  2. Wrap the call in try/except for provider-specific exceptions (rate limit, timeout, server error).
  3. On rate limit/transient error, retry with exponential backoff up to a max attempt count.
  4. On repeated failure, fail over to a secondary model/provider if configured.
  5. Log request/response metadata (tokens, latency, model, success/failure) for observability.
  6. Surface a graceful degraded response to the end user if all retries/fallbacks exhaust.

12. Real-world example

A production customer-support bot wraps every LLM call with: a 10-second timeout, 3 retries with exponential backoff on 429/5xx errors, fallback to a secondary model on persistent failure, and structured logging of token usage per request for cost dashboards — turning a simple API call into a resilient production dependency.

13. Code example

import time
from anthropic import Anthropic, APIStatusError, APITimeoutError

client = Anthropic()

def call_with_retry(messages, max_retries=3):
    for attempt in range(max_retries):
        try:
            return client.messages.create(
                model="claude-sonnet-5", max_tokens=300,
                messages=messages, timeout=10.0,
            )
        except (APIStatusError, APITimeoutError) as e:
            wait = 2 ** attempt
            print(f"Retrying in {wait}s due to {e}")
            time.sleep(wait)
    raise RuntimeError("Max retries exceeded")

14. Advanced example

# Provider fallback with cost/usage tracking
def call_with_fallback(messages, primary, fallback):
    try:
        resp = primary.complete(messages)
        log_usage(provider="primary", tokens=resp.usage)
        return resp
    except Exception as e:
        log_error("primary_failed", error=str(e))
        resp = fallback.complete(messages)
        log_usage(provider="fallback", tokens=resp.usage)
        return resp

15. Common mistakes

  • No timeout set, causing requests to hang indefinitely on network issues.
  • Retrying immediately without backoff, worsening rate-limit storms.
  • Not tracking token usage per request, leading to surprise cost bills.
  • Treating structured-output "JSON mode" as a 100% guarantee without validation.

16. Best practices

  • Always set explicit timeouts.
  • Implement exponential backoff retries for transient errors.
  • Validate structured outputs with a schema library regardless of provider guarantees.
  • Log token usage and cost per request from day one.
  • Build a provider abstraction layer to enable fallback.

17. Production considerations

Treat the LLM API exactly like any other critical third-party dependency: circuit breakers, health checks, fallback providers, and SLA monitoring. Rate-limit your own outbound request rate proactively rather than reactively handling 429s.

18. Security considerations

Store API keys in a secret manager, rotate regularly, and scope keys with least privilege where providers support it. Validate/sanitize any user input that flows into tool-call arguments before executing them.

19. Performance considerations

Use streaming for user-facing responses to improve perceived latency. Use async/concurrent calls for batch workloads. Consider the provider's dedicated Batch API for large non-real-time workloads, often at a cost/throughput advantage.

20. Cost considerations

Log input/output tokens per call; aggregate into per-feature and per-user cost dashboards; use cheaper model tiers and prompt/context caching wherever quality permits.

21. Debugging/troubleshooting

  • Intermittent timeouts: check network/provider status, increase timeout cautiously, add retries.
  • 429 rate limit errors under normal load: check your actual tier limits and implement client-side rate limiting/queuing.
  • Unexpected cost spike: audit per-request token logs for a regression (e.g., unbounded context growth).

27. Interview Questions — Beginner

Q1. What does streaming mean in the context of an LLM API?
A. Receiving generated tokens incrementally as they're produced, rather than waiting for the full response.
Q2. What's a rate limit?
A. A cap on how many requests/tokens a client can send in a given time window, enforced by the provider.
Q3. Why should you set a timeout on API calls?
A. To prevent a request from hanging indefinitely if the network or provider is slow/unresponsive.
Q4. What is exponential backoff?
A. A retry strategy that increases the wait time between attempts exponentially, reducing load on a struggling service.
Q5. What is model fallback?
A. Switching to a secondary model/provider when the primary one fails or is unavailable.
Q6. What is a provider abstraction layer?
A. A common interface that decouples application logic from any single provider's specific SDK.
Q7. Why track token usage per request?
A. To monitor and control cost, and to detect regressions like unbounded context growth.
Q8. What is a Batch API?
A. An interface for submitting many requests for asynchronous bulk processing, often at a cost discount for non-real-time workloads.
Q9. Should you retry every type of API error?
A. No — retry transient errors (rate limits, timeouts, server errors); don't retry errors caused by invalid input, which will just fail again.
Q10. What is a circuit breaker pattern?
A. A pattern that stops sending requests to a failing dependency after repeated failures, to avoid cascading overload, resuming only after a cooldown or health check passes.

28. Interview Questions — Intermediate

Q1. How would you implement exponential backoff with jitter, and why add jitter?
A. Compute delay as `base * 2^attempt` plus a small random jitter value; jitter prevents many clients retrying in lockstep (thundering herd) from all hammering the service at the exact same moments after a shared outage.
Q2. Why might you want client-side rate limiting even though the provider already enforces limits server-side?
A. Proactively throttling your own request rate avoids wasting time on guaranteed-to-fail requests, reduces 429 error-handling overhead, and smooths load rather than bursting up to the limit and backing off reactively.
Q3. What's a risk of blindly retrying a failed tool-call request without checking the error type?
A. If the failure was due to invalid arguments or a permanent error (not transient), retrying identically will just fail again, wasting time/cost; the retry logic should distinguish transient (retry-worthy) from permanent (don't retry) failures.
Q4. How would you design cost tracking that attributes LLM spend to specific product features or users?
A. Tag every LLM call with metadata (feature name, user/tenant ID) at call time, log token usage alongside that metadata, and aggregate in a cost dashboard grouped by feature/user — enabling per-feature cost accountability.
Q5. Why is a Batch API not suitable for a user-facing chat feature?
A. Batch APIs are designed for asynchronous, non-real-time bulk processing (results may take minutes to hours), incompatible with the low-latency, synchronous response a chat interface requires.

29. Interview Questions — Advanced

Q1. How would you design a circuit breaker for an LLM API dependency, including its state transitions?
A. Track a rolling failure rate; transition from Closed (normal) to Open (reject calls immediately, serve fallback/cached response) after failures exceed a threshold within a time window; after a cooldown period, transition to Half-Open (allow a small number of test requests through); if those succeed, return to Closed, else back to Open — preventing cascading overload while allowing automatic recovery detection.
Q2. What's a subtle issue with naive retry logic on a non-idempotent LLM call that also triggers a side-effecting tool call?
A. If a tool call (e.g., "send an email," "charge a payment") succeeded but the response delivery failed/timed out, a naive retry could re-execute the side effect; mitigate with idempotency keys on tool executions or by only retrying the LLM reasoning step, not already-executed side effects.

30. Interview Questions — Senior/Architect

Q1. Design the resiliency architecture for a company-wide internal LLM gateway serving dozens of product teams.
A. Centralize provider credentials and routing behind a gateway service; implement per-team rate limiting/quotas, circuit breakers per provider, automatic fallback chains, centralized cost/usage logging and dashboards per team, and a consistent structured-output validation layer — so individual product teams don't each reimplement resiliency logic inconsistently.

31. Scenario-Based Questions

Scenario 1. Your LLM-powered feature starts throwing 429 errors during a traffic spike, even though you have retry logic. What's missing?
A. Retry-with-backoff alone doesn't prevent exceeding limits; add client-side rate limiting/request queuing to stay under the provider's actual rate limit proactively, rather than relying solely on reactive retries.
Scenario 2. A tool-calling feature occasionally double-charges a customer because a retry re-executed a payment tool call after a network timeout masked a successful first attempt. How do you fix the architecture?
A. Add idempotency keys to the payment tool call so a retry with the same key is recognized as a duplicate and safely no-ops, decoupling retry safety from whether the original request actually succeeded server-side.

32. Quick revision notes

  • Treat the LLM API like any critical third-party dependency: timeouts, retries, circuit breakers, fallback.
  • Track tokens/cost per request from day one.
  • Validate structured output even with provider "JSON mode" guarantees.
  • Build a provider abstraction layer early.

33. Cheat sheet

Timeout + retry-with-backoff + fallback provider + token/cost logging + structured-output validation = a production-grade LLM API integration. Treat it like any unreliable network dependency.
