1. What is this?

LangChain is a general-purpose framework for building LLM applications: it provides standardized abstractions for Models, Prompts, Messages, Output Parsers, Runnables/Chains, Retrievers, Tools, and Agents, plus integrations with hundreds of providers, vector stores, and external services, and LangSmith for observability.

2. Why does it exist?

Before LangChain, every team building LLM applications reinvented the same plumbing (prompt templating, output parsing, chaining calls, tool integration) from scratch against each provider's distinct SDK. LangChain exists to standardize these patterns into reusable, composable abstractions and provide pre-built integrations.

3. Why is it important?

It's one of the most widely adopted LLM orchestration frameworks, meaning both its patterns (chains, agents, tools) and its specific APIs frequently appear in interviews and real production codebases — fluency with it is a practical, high-demand skill.

4. Where is it used?

RAG applications, agents, chatbots, tool-calling pipelines, any LLM application needing standardized provider abstraction and composability.

5. Prerequisites

Prompt Engineering, RAG Fundamentals, Tool Calling.

6. Core concepts

  • Models: standardized wrappers over LLM providers' chat/completion APIs.
  • Prompts/Messages: templated, structured representations of system/user/assistant messages.
  • Output Parsers: convert raw LLM output into structured Python objects.
  • Runnable / LCEL (LangChain Expression Language): a unified interface (`invoke`, `stream`, `batch`) letting components be composed with the `|` pipe operator into Chains.
  • Retrievers: standardized interface over vector stores/search backends.
  • Tools: functions the LLM can call, with structured schemas.
  • Agents: LLM-driven loops that decide which tools to call and when.
  • Memory/persistence: mechanisms for maintaining conversation state across turns.
  • LangSmith: LangChain's companion observability/tracing/evaluation platform.

8. Architecture

Prompt Template → Model → Output Parser   (a simple Chain via LCEL: prompt | model | parser)

Retriever → Prompt (with context) → Model → Parser   (RAG chain)

Model + Tools → Agent Loop:
   LLM decides tool → execute tool → feed result back → repeat until final answer

9. How it works internally (Runnable/LCEL)

Every LangChain component implements the `Runnable` interface (`invoke`, `batch`, `stream`, and async variants), which is what makes the `|` pipe operator work — `prompt | model | parser` is syntactic sugar for composing Runnables into a `RunnableSequence`, where each component's output becomes the next component's input, uniformly supporting streaming and batching across the whole chain.

10. Step-by-step: building the 4 core apps

  1. Simple LLM app: prompt template | model | output parser.
  2. RAG app: add a retriever step before prompt construction, injecting retrieved context.
  3. Tool-calling app: bind tools to the model, let it decide when to call them, execute and feed results back.
  4. Agent app: wrap tool-calling in a loop (via LangGraph, LangChain's recommended agent runtime) that continues until a final answer is reached.

11. Simple example (LLM app)

from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = ChatAnthropic(model="claude-sonnet-5")
prompt = ChatPromptTemplate.from_template("Explain {topic} in 2 sentences.")
chain = prompt | model | StrOutputParser()

print(chain.invoke({"topic": "RAG"}))

12. Real-world example

A company's internal support bot is a LangChain RAG chain (retriever over their Qdrant vector store, piped into a prompt template, piped into Claude, piped into a citation-aware output parser) wrapped in a FastAPI endpoint — a direct, typical production use of the LCEL pattern.

13. Code example (RAG + Tool-calling + Agent)

# RAG chain
from langchain_core.runnables import RunnablePassthrough

retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
rag_prompt = ChatPromptTemplate.from_template(
    "Answer using only this context:\n{context}\n\nQuestion: {question}"
)
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | rag_prompt | model | StrOutputParser()
)
print(rag_chain.invoke("What's our refund policy?"))

# Tool-calling
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    return f"Weather in {city}: sunny, 22C"

model_with_tools = model.bind_tools([get_weather])
response = model_with_tools.invoke("What's the weather in Paris?")
print(response.tool_calls)

# Agent (via LangGraph's prebuilt ReAct agent, the recommended path)
from langgraph.prebuilt import create_react_agent

agent = create_react_agent(model, tools=[get_weather])
result = agent.invoke({"messages": [{"role": "user", "content": "Weather in Tokyo?"}]})

14. Advanced example (middleware/memory)

from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import ChatMessageHistory

store = {}
def get_history(session_id):
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

chain_with_memory = RunnableWithMessageHistory(
    rag_chain, get_history,
    input_messages_key="question", history_messages_key="history",
)
chain_with_memory.invoke({"question": "And what about international orders?"},
                          config={"configurable": {"session_id": "user123"}})

15. Common mistakes

  • Using legacy `Chain` classes (e.g., old `LLMChain`) instead of modern LCEL composition — current LangChain strongly favors LCEL/Runnables.
  • Building complex multi-step agents directly in LangChain instead of using LangGraph, which is the recommended tool for anything beyond simple tool-calling loops.
  • Not setting up LangSmith tracing, making chain debugging much harder.
  • Ignoring streaming support (`.stream()`) and defaulting to blocking `.invoke()` for user-facing latency-sensitive features.

16. Best practices

  • Use LCEL (`|` composition) for chains; use LangGraph for anything with loops/branching/state beyond a linear pipeline.
  • Enable LangSmith tracing from day one for debugging and evaluation.
  • Keep prompt templates and chain definitions version-controlled, not inline ad hoc strings.
  • Use `.batch()` for processing many independent inputs efficiently.

17. Production considerations

Wrap chains with the same resilience patterns as any LLM API integration (timeouts, retries, fallback models via `.with_fallbacks()`); monitor via LangSmith or an equivalent observability tool.

18. Security considerations

Tool-calling/agent chains must validate tool arguments before execution (see Tool Calling) and scope retriever access per tenant/user — LangChain doesn't enforce these automatically.

19. Performance considerations

Use `.batch()` for bulk processing and `.stream()` for user-facing latency; LCEL chains support both uniformly across composed components.

20. Cost considerations

Agent loops can make many LLM calls per task — monitor per-agent-run token usage via LangSmith and set iteration limits to bound worst-case cost.

21. Debugging/troubleshooting

  • Chain output doesn't match expected format: inspect each Runnable's output independently (`.invoke()` on a sub-chain) to isolate where the format breaks.
  • Agent loops forever / hits iteration limit: check tool definitions for clarity and whether the model has a clear path to a final answer; add an explicit max-iteration safeguard.
  • Hard to debug multi-step chains: enable LangSmith tracing to visualize the full execution path.

27. Interview Questions — Beginner

Q1. What is LangChain?
A. A general-purpose framework providing standardized abstractions (models, prompts, chains, tools, agents) and integrations for building LLM applications.
Q2. What is LCEL?
A. LangChain Expression Language — the `|` pipe syntax for composing Runnables into chains.
Q3. What is a Runnable?
A. LangChain's unified interface (invoke/batch/stream) implemented by any composable component like models, parsers, or retrievers.
Q4. What is a Tool in LangChain?
A. A function exposed to the LLM with a name, description, and argument schema, which the model can request to call.
Q5. What is an Agent?
A. A loop where the LLM decides step by step which tools to call to accomplish a task, until reaching a final answer.
Q6. What is LangSmith?
A. LangChain's companion platform for observability, tracing, and evaluation of LLM application runs.
Q7. What does an Output Parser do?
A. Converts raw LLM text output into structured Python objects.
Q8. What's the recommended tool for building complex, stateful agents in the LangChain ecosystem?
A. LangGraph.
Q9. What's the difference between `.invoke()` and `.stream()` on a Runnable?
A. `.invoke()` returns the full result after completion; `.stream()` yields incremental results as they're produced.
Q10. Why would you use `.batch()` instead of calling `.invoke()` in a loop?
A. `.batch()` can process multiple independent inputs more efficiently (e.g., concurrently), rather than sequentially waiting for each `.invoke()` call.

28. Interview Questions — Intermediate

Q1. How does the `|` operator in LCEL actually compose components under the hood?
A. It constructs a `RunnableSequence` where each component's `invoke` output is passed as the next component's input, with the composed sequence itself implementing the same Runnable interface, supporting uniform invoke/batch/stream semantics across the whole chain.
Q2. Why does LangChain recommend LangGraph over its own legacy agent executors for complex agents?
A. LangGraph provides explicit state management, branching, cycles, and checkpointing suited to complex multi-step agent behavior, whereas legacy agent executors were simpler, more implicit loops less suited to production-grade control flow, debugging, and human-in-the-loop needs.
Q3. How would you add a fallback model to a LangChain chain in case the primary model fails?
A. Use `.with_fallbacks([fallback_model])` on the Runnable, which automatically retries with the fallback if the primary raises an exception.
Q4. Why is it important to scope a RAG chain's retriever by tenant/user even though LangChain's retriever interface doesn't enforce this automatically?
A. LangChain provides the retrieval abstraction but not business-specific access control logic — the application must configure the retriever (e.g., via metadata filters) to respect tenant/user boundaries, or risk cross-tenant data leakage.
Q5. How would you debug a LangChain agent that keeps calling the wrong tool?
A. Inspect the tool's description and argument schema for ambiguity (the model relies entirely on these to decide when/how to call it), use LangSmith tracing to see the model's actual reasoning/tool-call decisions, and consider adding few-shot examples demonstrating correct tool selection.

29. Interview Questions — Advanced

Q1. How would you design a LangChain-based system to support hot-swapping the underlying LLM provider without changing chain logic?
A. Rely on LangChain's standardized Model interface (e.g., `ChatAnthropic`, `ChatOpenAI` all implement the same Runnable/chat-model interface) — chain logic built against the abstract interface rather than provider-specific details can swap the model instance via configuration, as long as provider-specific features (certain tool-calling nuances) are avoided or abstracted.
Q2. What's a subtle performance pitfall of composing many small Runnables in a long LCEL chain?
A. Each step in the chain, even simple ones, adds a small amount of overhead (serialization, callback handling); for very long or high-throughput chains, this can accumulate — profiling via LangSmith traces helps identify whether chain-overhead or actual LLM latency dominates.

30. Interview Questions — Senior/Architect

Q1. How would you decide, for a new complex agent application, whether to use LangChain's simple tool-calling pattern versus building the agent in LangGraph from the start?
A. If the task is a single-step or simple linear tool-calling flow, LangChain's direct tool-binding is sufficient; if the task requires branching, cycles, persistent state across steps, human-in-the-loop interrupts, or multi-agent coordination, start directly in LangGraph — retrofitting a simple tool-calling pattern into a complex stateful agent later is more disruptive than starting with the right abstraction.

31. Scenario-Based Questions

Scenario 1. Your LangChain RAG chain's answers are inconsistent, and you can't tell if it's a retrieval or generation issue. How do you debug it?
A. Enable LangSmith tracing (or manually invoke the retriever sub-component in isolation) to inspect exactly what context was retrieved for a given query, separating retrieval-quality issues from prompt/generation issues.
Scenario 2. An agent built with LangChain's legacy agent executor is hard to extend with a human-approval step. What do you recommend?
A. Migrate the agent to LangGraph, which natively supports interrupts/human-in-the-loop checkpoints, rather than trying to retrofit that capability into the legacy executor pattern.

32. Quick revision notes

  • LCEL (`|`) composes Runnables (model, prompt, parser, retriever) into Chains.
  • Tools = functions the LLM can call; Agents = loops deciding which tools to call.
  • Use LangGraph for complex stateful/branching agents; LangChain for standardized abstractions and simple chains.
  • Enable LangSmith tracing for debugging and evaluation.

33. Cheat sheet

LangChain: Model + Prompt + Output Parser composed via LCEL (`|`) into Chains. Retriever → RAG chain. Tools + Agent loop → tool-calling/agent apps. Use LangGraph for complex agents. Enable LangSmith for tracing/eval.
