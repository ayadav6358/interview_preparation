1. What is this?

A knowledge graph represents information as entities (nodes) and relationships (edges) between them, stored in a graph database (e.g., Neo4j) — enabling queries about how things connect, not just what individual facts exist.

2. Why does it exist?

Relational databases and vector similarity search both struggle with multi-hop relationship questions ("who are the colleagues of people who worked on project X?") — knowledge graphs exist to natively model and query this kind of connected, relationship-centric information.

3. Why is it important?

Knowledge graphs are foundational to Graph RAG (next section) and to any application needing to reason about entity relationships rather than just document similarity — an increasingly important complement to vector-based retrieval.

4. Where is it used?

Enterprise knowledge management, fraud detection (relationship patterns), recommendation systems, biomedical/scientific research (entity relationships), Graph RAG systems.

5. Prerequisites

Vector Databases (for contrast).

6. Core concepts

  • Entities (nodes): the "things" in the graph — people, organizations, products, concepts.
  • Relationships (edges): typed, directional connections between entities (e.g., "WORKS_AT", "ACQUIRED").
  • Graph traversal: following relationships from one entity to discover connected entities, often multiple hops deep.
  • Knowledge graph construction: the process of extracting entities and relationships from unstructured text (often via LLM-based extraction) to populate the graph.
  • Graph embeddings: vector representations of nodes/edges capturing structural graph information, enabling similarity/ML over graph structure.

7. Terminology

TermMeaning
NodeAn entity in the graph.
Edge/RelationshipA typed, directional connection between two nodes.

Multi-hop queryA query traversing multiple relationships to answer a question (e.g., friend-of-a-friend).
Entity extractionIdentifying entities and relationships from unstructured text, often via NLP/LLM.

8. Architecture

Unstructured text
 → Entity/relationship extraction (NLP or LLM-based)
 → Knowledge graph (nodes + typed edges) stored in Neo4j
 → Query via Cypher (graph traversal) or natural language → Cypher translation
 → Results: connected entities, relationship paths

9. How it works internally

Unlike relational databases, which require expensive JOIN operations to traverse relationships (cost grows with hops), graph databases store relationships as first-class, directly traversable pointers between nodes — making multi-hop traversal queries (e.g., "find all paths of length ≤3 between A and B") efficient operations native to the storage engine, rather than increasingly expensive JOIN chains.

10. Step-by-step: building a knowledge graph

  1. Define the entity types and relationship types relevant to your domain (schema design).
  2. Extract entities and relationships from source data (structured imports or LLM-based extraction from text).
  3. Load into a graph database (Neo4j or similar).
  4. Write queries (Cypher) for the relationship questions your application needs to answer.
  5. Periodically update the graph as source data changes.

11. Simple example

A graph with nodes `(Alice)`, `(Bob)`, `(ProjectX)` and edges `Alice -[WORKS_ON]-> ProjectX`, `Bob -[WORKS_ON]-> ProjectX` lets you easily query "who else works on projects Alice works on" via a 2-hop traversal.

12. Real-world example

A fraud-detection system models accounts, transactions, and devices as a graph, using multi-hop traversal to detect suspicious patterns (e.g., multiple seemingly-unrelated accounts sharing a device or payment method) that would be extremely difficult to express as SQL joins at scale.

13. Code example

// Cypher query example in Neo4j
MATCH (alice:Person {name: "Alice"})-[:WORKS_ON]->(project:Project)<-[:WORKS_ON]-(colleague:Person)
WHERE colleague.name <> "Alice"
RETURN colleague.name, project.name

from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))

def find_colleagues(tx, person_name):
    result = tx.run("""
        MATCH (p:Person {name: $name})-[:WORKS_ON]->(proj:Project)<-[:WORKS_ON]-(colleague:Person)
        WHERE colleague.name <> $name
        RETURN colleague.name AS name, proj.name AS project
    """, name=person_name)
    return [record.data() for record in result]

with driver.session() as session:
    print(session.execute_read(find_colleagues, "Alice"))

15. Common mistakes

  • Using a knowledge graph for problems that are actually simple lookups better served by a relational DB or vector search.
  • Poor relationship-type design, leading to an overly generic graph that's hard to query meaningfully.
  • LLM-based entity extraction without validation, introducing noisy/incorrect graph data.
  • Not planning for graph updates as source data changes, leading to a stale graph.

16. Best practices

  • Design a clear, purposeful schema (entity types, relationship types) before bulk loading data.
  • Validate LLM-extracted entities/relationships before committing them to the graph.
  • Use graph databases specifically for genuinely relationship-centric queries — not as a universal database replacement.
  • Plan incremental update/sync processes for evolving source data.

17. Production considerations

Graph databases require their own operational expertise (query optimization, indexing strategy) distinct from relational DB operations — factor this into team skill investment before committing to a graph-centric architecture.

18. Security considerations

Apply the same access-control scoping as any database — multi-tenant knowledge graphs need relationship-level or subgraph-level access control, not just node-level.

19. Performance considerations

Multi-hop traversal performance depends on proper indexing and relationship design; very deep/unbounded traversals can still be expensive — bound traversal depth in queries where possible.

20. Cost considerations

LLM-based entity/relationship extraction at ingestion time adds per-document LLM call cost; batch processing and caching reduce this for large-scale graph construction.

21. Debugging/troubleshooting

  • Queries return no/incomplete results: verify relationship direction and type names match exactly what was used during graph construction.
  • Graph grows inconsistent/noisy over time: review LLM extraction validation and deduplication logic for entities.
  • Slow multi-hop queries: check indexing on node properties used in traversal filters, and consider bounding traversal depth.

27. Interview Questions — Beginner

Q1. What is a knowledge graph?
A. A representation of information as entities (nodes) and relationships (edges) between them.
Q2. What is a graph database?
A. A database (e.g., Neo4j) specialized for storing and querying graph-structured data with relationships as first-class citizens.
Q3. What is Cypher?
A. Neo4j's graph query language, analogous to SQL for relational databases.
Q4. What is a multi-hop query?
A. A query that traverses multiple relationships to answer a question, like finding friends-of-friends.
Q5. Why are relational databases less suited to deep multi-hop relationship queries?
A. They require increasingly expensive JOIN operations as the number of hops grows, unlike graph databases where relationships are directly traversable.
Q6. What is entity extraction in the context of knowledge graphs?
A. Identifying entities and relationships from unstructured text to populate a knowledge graph.
Q7. Should you use a knowledge graph for every data storage need?
A. No — use it specifically for genuinely relationship-centric queries; simple lookups are better served by relational or vector databases.
Q8. What are graph embeddings?
A. Vector representations of nodes/edges capturing structural graph information.
Q9. Give one real-world use case for knowledge graphs.
A. Fraud detection, identifying suspicious relationship patterns between accounts/transactions/devices.
Q10. What's the relationship between knowledge graphs and Graph RAG?
A. Graph RAG uses a knowledge graph as its retrieval/reasoning backbone instead of (or alongside) vector similarity search.

28. Interview Questions — Intermediate

Q1. Why does graph database traversal performance scale better than relational JOINs for deep multi-hop queries?
A. Graph databases store relationships as direct, indexed pointers between nodes, so traversal cost grows roughly with the number of hops and actual connections, not with a combinatorial JOIN cost across potentially large tables as in relational databases.
Q2. What's a key risk of using LLM-based extraction to automatically populate a knowledge graph from unstructured text?
A. The LLM can hallucinate or incorrectly identify entities/relationships, introducing noisy or inaccurate graph data; validation (confidence thresholds, human review, or cross-referencing extracted facts against source text) is needed before trusting the extracted graph data.
Q3. How would you design a knowledge graph schema to balance flexibility against query performance?
A. Define a focused, purposeful set of entity and relationship types matching actual query needs rather than an overly generic schema, since well-typed relationships enable more efficient, targeted traversal queries than a catch-all generic "RELATED_TO" relationship type would.
Q4. Why might a knowledge graph complement rather than replace a vector database in a RAG system?
A. Vector search excels at finding semantically similar content; knowledge graphs excel at answering relationship/connection questions — combining both (Graph RAG) lets a system handle both "what documents are about X" and "how is X connected to Y" style queries.
Q5. How would you keep a knowledge graph's data synchronized as the underlying source data changes frequently?
A. Build an incremental update pipeline that detects changes in source data and applies corresponding node/relationship updates (rather than full graph rebuilds), similar in spirit to incremental RAG re-indexing, to keep the graph current without excessive reprocessing cost.

29. Interview Questions — Advanced

Q1. How would you design a knowledge graph construction pipeline that balances LLM-extraction flexibility against data quality for a large, continuously growing document corpus?
A. Use LLM extraction for candidate entities/relationships, but add a validation layer (confidence scoring, deduplication against existing graph entities, cross-document consistency checks) before committing extractions to the graph, and periodically audit a sample of extracted data against source documents to measure and improve extraction accuracy over time.
Q2. What's a subtle performance pitfall of unbounded-depth traversal queries in a large production knowledge graph?
A. Without a depth limit, a traversal query can expand combinatorially across a densely connected graph, potentially visiting an enormous number of paths and causing severe latency/resource issues; production queries should bound traversal depth explicitly and consider timeout/result-limit safeguards.

30. Interview Questions — Senior/Architect

Q1. Design a Graph RAG-ready knowledge graph architecture for an enterprise with both structured (CRM) and unstructured (documents) data sources.
A. Build a unified entity schema covering both data sources, ingest structured CRM data directly as typed nodes/relationships, extract entities/relationships from unstructured documents via validated LLM extraction linking back to source documents (for citation), maintain incremental sync pipelines for both sources, and expose both direct Cypher-based relationship queries and a Graph RAG retrieval layer combining graph traversal with vector similarity for hybrid structured+semantic queries.

31. Scenario-Based Questions

Scenario 1. Your LLM-populated knowledge graph has accumulated many duplicate entities (e.g., "Acme Corp" and "Acme Corporation" as separate nodes). How do you fix this?
A. Implement entity resolution/deduplication logic (fuzzy matching, embedding similarity, or an LLM-based disambiguation step) during ingestion to merge likely-duplicate entities, and run a one-time cleanup pass to consolidate existing duplicates in the current graph.
Scenario 2. A multi-hop query that worked fine in testing becomes extremely slow in production as the graph has grown. What do you investigate?
A. Check if the query has an unbounded traversal depth that's now expanding combinatorially across a much larger, more densely connected graph; add explicit depth limits and verify appropriate indexes exist on the properties used for traversal filtering.

32. Quick revision notes

  • Knowledge graph = entities (nodes) + relationships (edges), queried via graph traversal (Cypher in Neo4j).
  • Better than relational DBs for deep multi-hop relationship queries.
  • LLM-based extraction can populate graphs from text, but needs validation.
  • Complements vector search in Graph RAG for relationship-aware retrieval.

33. Cheat sheet

Knowledge graph = nodes + typed edges, queried via Cypher (Neo4j). Best for multi-hop relationship questions relational DBs struggle with. Validate LLM-based extraction before trusting it. Complements vector search in Graph RAG.
