1. What is this?

Tool calling (function calling) lets an LLM request that a specific, developer-defined function be executed with structured arguments, then incorporate that function's result into its response — the mechanism that turns a pure text generator into a system that can take real-world actions (look up data, call APIs, run calculations).

2. Why does it exist?

LLMs can't directly access live data, execute code, or affect external systems — tool calling exists as the standardized interface letting the model request such actions from the surrounding application, which executes them and returns results, since the model itself has no execution environment.

3. Why is it important?

Tool calling is the foundation of every agent, every MCP integration, and every "AI that does things" product — understanding the full loop (decide → generate args → execute → return → incorporate) is essential before building any agentic system.

4. Where is it used?

Agents, coding assistants (file/shell tools), RAG systems (retrieval as a tool), customer support bots (order lookup, refund processing), MCP servers (tools are MCP's core primitive).

Structured Output.

6. Core concepts

  • Tool schema: a name, description, and structured argument schema (JSON Schema) defining a callable function.
  • Tool selection: the model decides, based on the user's request and available tools' descriptions, whether and which tool to call.
  • Argument generation: the model generates structured arguments matching the tool's schema.
  • Execution: the application (not the model) actually runs the function with those arguments.
  • Result incorporation: the tool's result is fed back to the model, which uses it to produce a final response or call another tool.
  • Parallel tool calls: some providers support the model requesting multiple independent tool calls in one turn.

7. Terminology

TermMeaning
Tool/function schemaJSON Schema describing a tool's name, purpose, and expected arguments.
Tool callThe model's structured request to invoke a specific tool with specific arguments.
Tool resultThe output returned by executing the tool, fed back into the conversation.
Tool permissionApplication-level control over which tools a given context/user is allowed to invoke.
Tool error handlingReturning a structured error to the model when tool execution fails, enabling self-correction.

8. Architecture

LLM
 → decides tool
 → generates arguments (structured output against tool schema)
 → application executes tool (real code, not the model)
 → tool returns result
 → result appended to conversation
 → LLM processes result
 → final answer (or another tool call)

9. How it works internally

Tool definitions are included in the model's context as part of the request (not hidden infrastructure) — the model has learned, through training, to recognize when a user's request matches an available tool's description and to generate a structured tool-call response (special output format, often a dedicated content block) instead of or alongside free text, which the SDK/application parses and dispatches to the actual function implementation.

10. Step-by-step: the full tool-call loop

  1. Define tools with clear names, descriptions, and argument schemas.
  2. Send the user message along with available tool definitions.
  3. Model responds with either text or a tool-call request (name + arguments).
  4. Application validates arguments, executes the actual function.
  5. Application appends the tool's result to the conversation and calls the model again.
  6. Model incorporates the result into a final answer, or requests another tool call — repeat until done.

11. Simple example

User: "What's the weather in Paris?" The model recognizes it needs live data it doesn't have, calls a `get_weather(city="Paris")` tool, the application executes a real weather API call, returns the result, and the model phrases a natural-language answer using it.

12. Real-world example

Claude Code (this assistant) uses tool calling extensively: when you ask it to "fix this bug," it calls Read, Grep, Edit tools — each a defined function with a schema — executed by the harness, with results fed back so the model can decide its next action, forming the full agent loop.

13. Code example

from anthropic import Anthropic

client = Anthropic()

tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a city.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

def get_weather(city: str) -> str:
    return f"Weather in {city}: 22C, sunny"

messages = [{"role": "user", "content": "What's the weather in Tokyo?"}]
response = client.messages.create(model="claude-sonnet-5", max_tokens=300, tools=tools, messages=messages)

if response.stop_reason == "tool_use":
    tool_use = next(b for b in response.content if b.type == "tool_use")
    result = get_weather(**tool_use.input)
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": tool_use.id, "content": result}
    ]})
    final = client.messages.create(model="claude-sonnet-5", max_tokens=300, tools=tools, messages=messages)
    print(final.content[0].text)

14. Advanced example (parallel tools)

def execute_tool_calls(response, tool_registry):
    results = []
    for block in response.content:
        if block.type == "tool_use":
            fn = tool_registry[block.name]
            try:
                result = fn(**block.input)
            except Exception as e:
                result = f"Error: {e}"  # structured error, lets model self-correct
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(result)})
    return results
# Supports multiple tool_use blocks in one response -> parallel execution

15. Common mistakes

  • Vague tool descriptions, causing the model to misuse or never use a tool appropriately.
  • Executing tool arguments without validation, risking injection into shell commands, SQL, or file paths.
  • Not handling tool execution errors gracefully — crashing instead of returning a structured error the model can react to.
  • Giving the model overly broad tool permissions (e.g., unrestricted shell access) without scoping.

16. Best practices

  • Write clear, specific tool descriptions — the model relies entirely on them for correct selection.
  • Validate all tool arguments with a schema library before executing.
  • Return structured, informative errors on failure so the model can retry/adjust.
  • Scope tool permissions tightly (least privilege) per context/user.
  • Set limits on tool-call iterations to bound cost/risk of runaway loops.

17. Production considerations

Log every tool call and its result for auditability; apply rate limiting/timeouts per tool execution; have a circuit breaker for tools that fail repeatedly (e.g., a flaky external API).

18. Security considerations

Treat tool arguments generated by the LLM as untrusted input requiring the same validation/sanitization as any external user input — never pass them directly into shell commands, SQL queries, or file paths without validation (see AI Security — excessive agency).

19. Performance considerations

Each tool-call round trip (model decides → execute → feed back → model continues) adds latency; parallel tool calls (when supported) reduce total round trips for independent actions.

20. Cost considerations

Each round in the tool-call loop is a separate billed LLM call — complex multi-tool tasks can accumulate significant cost; set iteration limits and monitor average tool-calls-per-task.

21. Debugging/troubleshooting

  • Model never calls the expected tool: improve the tool's description/examples; check if a competing tool's description is more appealing to the model for that query type.
  • Model calls a tool with malformed arguments: add a few-shot example or tighten the schema (e.g., enums instead of free strings).
  • Infinite tool-call loop: add a hard iteration limit and investigate whether the tool's result format is confusing the model about task completion.

27. Interview Questions — Beginner

Q1. What is tool calling?
A. A mechanism letting an LLM request that a defined function be executed with structured arguments, incorporating the result into its response.
Q2. Who actually executes the tool — the model or the application?
A. The application — the model only requests the call; it has no execution environment of its own.
Q3. What does a tool schema define?
A. The tool's name, description, and the structure/types of arguments it expects.
Q4. Why does the model need a clear tool description?
A. It relies entirely on the description to decide whether and when that tool is appropriate for a given request.
Q5. What should happen if a tool execution fails?
A. Return a structured error back to the model so it can react/retry/adjust, rather than crashing the application.
Q6. What is a parallel tool call?
A. The model requesting multiple independent tool calls in a single turn, which can be executed concurrently.
Q7. Should you trust LLM-generated tool arguments without validation?
A. No — validate them like any other untrusted input before executing, to prevent injection attacks.
Q8. What's tool permission scoping?
A. Restricting which tools a given context/user is allowed to invoke, following least-privilege principles.
Q9. What happens after a tool returns a result?
A. The result is fed back into the conversation, and the model processes it to produce a final answer or call another tool.
Q10. Is tool calling only used in "agents"?
A. No — it's also used in simpler single-step integrations like RAG (retrieval as a tool) or structured data lookups, not only in multi-step agent loops.

28. Interview Questions — Intermediate

Q1. Why is tool argument validation especially critical compared to validating typical user input?
A. LLM-generated arguments can be subtly malformed or even adversarially influenced by injected content in context, and because they're generated by a probabilistic model rather than a predictable UI form, they need the same rigor as any untrusted input before touching sensitive operations (shell, SQL, file paths).
Q2. How would you design tool descriptions to minimize the model calling the wrong tool among several similar options?
A. Make descriptions specific and mutually exclusive in scope, include example use cases in the description, and avoid overlapping functionality between tools — ambiguous or overlapping tool purposes are a common cause of misselection.
Q3. Why might you set a maximum iteration limit on a tool-calling loop even for a well-designed agent?
A. To bound worst-case cost and latency in case of an edge case causing the model to loop (e.g., misinterpreting a tool result as incomplete) — a safety net against runaway execution regardless of how well-tuned the happy path is.
Q4. How does returning a structured error (vs. crashing) from a failed tool call improve agent reliability?
A. It gives the model the information needed to adjust its approach (retry with different arguments, try a different tool, or inform the user of the limitation) rather than ending the interaction abruptly with an unhandled exception.
Q5. Why is "tool calling" considered the foundational mechanism underlying both agents and MCP?
A. Both build on the same core loop (model decides action → structured request → execution → result fed back); agents apply this iteratively for complex tasks, and MCP standardizes how tools are discovered and exposed across different applications — but the fundamental mechanism is identical.

29. Interview Questions — Advanced

Q1. How would you design a tool-calling system that safely allows a model to execute shell commands for a coding agent, without giving it unrestricted system access?
A. Sandbox execution (containerized or restricted environment), maintain an allowlist of permitted commands/patterns rather than arbitrary execution, require explicit user approval for destructive operations, log every executed command, and apply resource/time limits per execution — treating the model's requests as suggestions requiring policy enforcement, not direct unchecked execution.
Q2. What's a subtle failure mode when a tool's result is very large (e.g., a huge database query result) and gets fed back into the conversation?
A. It can consume a large portion of the context window, pushing out other important context (lost in the middle) or even exceeding the window; mitigate by truncating/summarizing large tool results before feeding them back, or having the tool itself return a paginated/filtered summary rather than raw full output.

30. Interview Questions — Senior/Architect

Q1. Design a tool permission and audit system for an enterprise AI agent platform where different user roles should have access to different tools.
A. Maintain a role-based tool registry mapping user/context roles to allowed tool sets, enforce this at the application layer before even presenting tools to the model (never rely on the model to self-restrict), log every tool call with user identity and arguments for audit, and require explicit human approval workflows for high-risk tools (e.g., financial transactions, data deletion) regardless of role.

31. Scenario-Based Questions

Scenario 1. A coding agent executed a destructive shell command it generated, deleting important files. How do you prevent this going forward?
A. Require explicit user approval before executing any destructive/irreversible command, sandbox execution to limit blast radius, and maintain an allowlist/denylist of command patterns rather than permitting arbitrary shell execution.
Scenario 2. Your agent occasionally calls the same tool repeatedly with slightly different arguments, never converging on an answer. How do you debug and fix it?
A. Inspect the tool's result format for clarity/completeness — the model may not be recognizing that it already has sufficient information; add a hard iteration limit as an immediate safeguard, and improve the tool description/result format to make task completion clearer to the model.

32. Quick revision notes

  • Tool calling: LLM decides → generates args → app executes → result fed back → LLM continues/answers.
  • Model never executes anything itself — the application does.
  • Always validate tool arguments; never trust them directly.
  • Scope permissions, set iteration limits, log everything.

33. Cheat sheet

Tool calling loop: LLM decides tool → generates args → app validates + executes → result fed back → LLM continues. Always validate args, scope permissions (least privilege), handle errors gracefully, bound iterations.
