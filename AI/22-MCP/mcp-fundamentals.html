1. What is this?

MCP (Model Context Protocol) is an open standard protocol for connecting LLM applications (hosts) to external tools, data sources, and prompts via a standardized client-server interface — think of it as a "USB-C port for AI applications," letting any MCP-compatible host connect to any MCP server without custom integration code per combination.

2. Why does it exist?

Before MCP, every AI application needed custom, one-off integration code for every external tool/data source it wanted to connect to (N applications × M tools = N×M integrations). MCP exists to standardize this into N+M: any MCP host works with any MCP server.

3. Why is it important?

MCP has rapidly become the dominant standard for AI-to-tool integration since its introduction, adopted across major AI coding tools and agent platforms — understanding its architecture is now essential baseline knowledge for AI engineers, not a niche specialty.

4. Where is it used?

Claude Code and other coding agents (file system, git, database access), IDE integrations, enterprise data connectors (Slack, GitHub, databases), any agent needing standardized, reusable tool/data access.

Tool Calling.

6. Core concepts

  • MCP Host: the AI application the user interacts with (e.g., Claude Code, Claude Desktop) that wants to use external capabilities.
  • MCP Client: the component within the host that connects to and communicates with MCP servers.
  • MCP Server: a separate process/service exposing Tools, Resources, and Prompts over the MCP protocol.
  • Tools: callable functions an MCP server exposes (like standard tool calling, but standardized and discoverable).
  • Resources: data/content an MCP server can provide (files, database records, API responses) for the host to read.
  • Prompts: reusable prompt templates an MCP server can expose for the host to use.
  • Transport: the communication channel between client and server — stdio (local process) or HTTP/SSE (remote).

7. Terminology

TermMeaning
Local MCPAn MCP server running as a local subprocess, communicating via stdio — typical for file system/local tool access.
Remote MCPAn MCP server accessed over the network (HTTP/SSE), typical for cloud services/enterprise data sources.
MCP discoveryThe process by which a host learns what tools/resources/prompts a server exposes.
Authentication/AuthorizationRemote MCP servers typically require auth (e.g., OAuth) to control access to sensitive data/actions.

9. How it works internally

On connection, the MCP client queries the server for its capabilities (available tools/resources/prompts and their schemas) — this discovery step is what lets a host dynamically support any MCP server without hardcoded knowledge of it. When the LLM decides to use a tool, the host's client sends a standardized JSON-RPC-based request to the server, which executes the actual logic (hitting a database, calling an API) and returns a structured result, following essentially the same tool-calling mechanics covered in 16-Tool-Calling, but with the server as a separate, reusable, standardized component instead of bespoke in-application code.

10. Step-by-step: a tool call over MCP

  1. Host starts/connects to an MCP server (local subprocess or remote endpoint).
  2. Client performs discovery, learning the server's available tools/resources/prompts.
  3. Host presents discovered tools to the LLM as available tool-call options.
  4. LLM decides to call a specific tool; host's client sends the request to the MCP server.
  5. Server executes the actual logic and returns a structured result.
  6. Host feeds the result back to the LLM, which continues or produces a final answer.

11. Simple example

A local MCP server exposes a `read_file(path)` tool; Claude Code (the host) discovers this tool, and when the user asks to "look at config.py," the LLM requests the tool call, the MCP server reads the actual file from disk, and returns its content.

12. Real-world example

An enterprise connects a remote MCP server exposing their internal ticketing system's API as Tools (create_ticket, search_tickets) and Resources (ticket details) — any MCP-compatible AI tool in the company (coding assistants, chat assistants) can now interact with the ticketing system without each needing custom integration code.

13. Code example

# Minimal MCP server using the official Python SDK
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    return f"Weather in {city}: 22C, sunny"

@mcp.resource("config://settings")
def get_settings() -> str:
    return '{"theme": "dark"}'

if __name__ == "__main__":
    mcp.run(transport="stdio")

// Host configuration connecting to this local MCP server
{
  "mcpServers": {
    "demo-server": {
      "command": "python",
      "args": ["demo_server.py"]
    }
  }
}

14. Advanced example (remote MCP + auth)

from mcp.server.fastmcp import FastMCP
from mcp.server.auth import OAuthProvider

mcp = FastMCP("enterprise-server", auth=OAuthProvider(
    authorization_endpoint="https://auth.company.com/authorize",
    token_endpoint="https://auth.company.com/token",
))

@mcp.tool()
def search_tickets(query: str, user_context: dict) -> list:
    # user_context carries authenticated user identity for scoped access
    return ticketing_db.search(query, tenant_id=user_context["tenant_id"])

if __name__ == "__main__":
    mcp.run(transport="sse", port=8080)  # remote, network-accessible

15. Common mistakes

  • Exposing overly broad/dangerous tools (e.g., unrestricted shell access) via MCP without scoping.
  • Not validating tool arguments server-side, trusting the host/LLM's generated input blindly.
  • Running remote MCP servers without proper authentication, exposing sensitive data/actions.
  • Poor tool/resource descriptions, leading to the same misuse issues as any poorly-described tool.

16. Best practices

  • Scope each tool to the minimum necessary capability (least privilege).
  • Validate all arguments server-side regardless of client trust.
  • Use proper authentication/authorization for any remote MCP server handling sensitive data.
  • Write clear, specific tool/resource descriptions, just as critical as in direct tool calling.

17. Production considerations

Treat MCP servers as production services: health checks, logging, rate limiting, and versioning of tool schemas (breaking schema changes can silently break hosts depending on them).

18. Security considerations

MCP servers are a significant attack surface — they can expose powerful capabilities (file access, database access, code execution) to an LLM-driven caller; apply authentication for remote servers, strict argument validation, least-privilege tool scoping, and treat any content returned via Resources as potentially injectable content requiring the same prompt-injection precautions as other untrusted data. See AI Security.

19. Performance considerations

Local (stdio) MCP servers have minimal transport overhead; remote (HTTP/SSE) servers add network latency — cache discovery results where appropriate and avoid unnecessary round trips for frequently-used tools.

20. Cost considerations

MCP itself doesn't add LLM token cost beyond standard tool calling, but hosting remote MCP servers has its own infrastructure cost (compute, bandwidth) — factor this into overall platform cost alongside LLM API spend.

21. Debugging/troubleshooting

  • Host doesn't see expected tools: check server connection/discovery — verify the server started correctly and the host's configuration points to it correctly.
  • Tool calls fail silently: check server-side logs for argument validation failures or execution errors not being properly surfaced back to the host.
  • Remote server access denied: verify authentication/authorization configuration and token validity.

27. Interview Questions — Beginner

Q1. What is MCP?
A. Model Context Protocol — an open standard for connecting LLM applications to external tools, data, and prompts via a standardized client-server interface.
Q2. What is an MCP Host?
A. The AI application the user interacts with that wants to use external capabilities via MCP (e.g., Claude Code).
Q3. What is an MCP Server?
A. A separate process/service exposing Tools, Resources, and Prompts over the MCP protocol.
Q4. What problem does MCP solve?
A. It avoids N×M custom integrations between every AI application and every tool/data source by standardizing the interface to N+M.
Q5. What's the difference between local and remote MCP?
A. Local MCP runs as a subprocess communicating via stdio; remote MCP is accessed over the network via HTTP/SSE.
Q6. What are MCP Resources?
A. Data/content an MCP server can provide (files, records, API responses) for the host to read.
Q7. What are MCP Prompts?
A. Reusable prompt templates an MCP server can expose for the host to use.
Q8. What is MCP discovery?
A. The process by which a host learns what tools/resources/prompts a connected server exposes.
Q9. Who executes an MCP tool's actual logic — the host or the server?
A. The server — the host's client only sends the request; the server performs the real work.
Q10. Why do remote MCP servers typically need authentication?
A. To control access to potentially sensitive data/actions exposed over the network.

28. Interview Questions — Intermediate

Q1. How does MCP's standardization reduce integration effort compared to custom tool integrations?
A. Without MCP, every host-to-tool pairing needs bespoke integration code (N hosts × M tools); with MCP, any compliant host can connect to any compliant server through the same protocol, reducing the effort to roughly N+M (each host implements the client once, each tool provider implements the server once).
Q2. Why is MCP's discovery mechanism important for its "USB-C for AI" value proposition?
A. It lets a host dynamically learn what a server offers at connection time, without needing hardcoded prior knowledge of that specific server — the same way a USB-C port doesn't need to know in advance what device will be plugged in.
Q3. Why must MCP servers validate tool arguments server-side even though the host/LLM generated them?
A. The server has no guarantee the connecting host validated anything, and the LLM-generated arguments are untrusted input from the server's perspective — the server is the actual execution boundary and must independently enforce correctness/safety.
Q4. What's the architectural difference between MCP and a traditional REST API integration?
A. MCP standardizes discovery (the host learns available tools/resources dynamically) and is specifically designed for LLM-driven tool-call semantics (structured arguments matched to a model's tool-calling capability); a traditional REST API requires the integrating application to have prior, hardcoded knowledge of its endpoints and schemas.
Q5. Why might an enterprise expose internal systems via a remote MCP server rather than giving the AI host direct API credentials?
A. Centralizing access through an MCP server lets the organization enforce consistent authentication, authorization, logging, and rate limiting at one controlled boundary, rather than distributing raw API credentials to every AI host/application that needs access.

29. Interview Questions — Advanced

Q1. How would you design an MCP server's tool schema to minimize the risk of excessive agency while still providing useful capability?
A. Expose narrow, purpose-specific tools (e.g., `create_ticket_in_category_X` rather than a generic `execute_database_query`) rather than broad, general-purpose capabilities, require explicit parameters that constrain scope (e.g., mandatory tenant/category fields validated server-side), and avoid exposing any tool whose blast radius if misused exceeds what's actually needed for the intended use cases.
Q2. What's a subtle risk of an MCP server's Resources feature when the host passes resource content directly into the LLM's context?
A. Resource content (e.g., a file's contents, a database record) is external, potentially untrusted data from the model's perspective — if it contains text that looks like instructions, it's a prompt-injection vector exactly like any other externally-sourced content in RAG or tool results, requiring the same defensive framing/delimiting.

30. Interview Questions — Senior/Architect

Q1. Design an enterprise MCP platform strategy for exposing internal systems (ticketing, CRM, internal docs) to multiple AI tools across the company securely.
A. Build/deploy dedicated remote MCP servers per internal system, each enforcing its own authentication (tied to the company's SSO/identity provider) and authorization scoped to the calling user's actual permissions (not a shared service-account with broad access), implement centralized logging/auditing of all tool calls across servers, version tool schemas carefully to avoid breaking changes for dependent hosts, and apply rate limiting per server to prevent any single AI integration from overwhelming backend systems.

31. Scenario-Based Questions

Scenario 1. A security review finds an MCP server exposes a generic `run_shell_command` tool with no restrictions. What's your recommendation?
A. Replace the generic tool with a set of narrow, purpose-specific tools covering only the actually-needed operations, remove unrestricted shell access entirely, and if shell-like flexibility is genuinely required, sandbox execution with a strict allowlist and mandatory human approval for anything destructive.
Scenario 2. An AI host using a remote MCP server starts behaving oddly after the server team pushed an update. What's the likely issue and how do you prevent it in the future?
A. Likely a breaking change in the tool schema (renamed parameter, changed return format) that the host wasn't expecting; prevent by versioning MCP server tool schemas and following a deprecation/migration process for breaking changes rather than silently modifying live schemas that dependent hosts rely on.

32. Quick revision notes

  • MCP = standardized protocol connecting AI hosts to tools/data/prompts, "USB-C for AI."
  • Host → Client → Server (local stdio or remote HTTP/SSE) → external system.
  • Discovery lets hosts dynamically learn server capabilities.
  • Validate arguments server-side; scope tools tightly; auth for remote servers.

33. Cheat sheet

MCP: Host → Client → Server (stdio/local or HTTP-SSE/remote) → external system. Exposes Tools, Resources, Prompts. Discovery removes need for hardcoded integration knowledge. Validate server-side, scope tightly, auth for remote.
