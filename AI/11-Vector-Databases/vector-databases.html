1. What is this?

A vector database stores embedding vectors and performs fast similarity search (nearest-neighbor lookup) at scale, typically with metadata filtering and sometimes hybrid lexical+semantic search. Major options: PostgreSQL + pgvector, Pinecone, Qdrant, Weaviate, Milvus, Chroma.

2. Why does it exist?

Brute-force comparing a query vector against millions/billions of stored vectors is too slow for real-time applications; vector databases exist to provide Approximate Nearest Neighbor (ANN) indexing structures that trade a small amount of accuracy for dramatic speed improvements at scale.

3. Why is it important?

The vector database is the retrieval backbone of every production RAG system — its indexing algorithm, filtering capability, and scaling characteristics directly determine retrieval latency, accuracy, and cost at scale.

4. Where is it used?

RAG retrieval, semantic search products, recommendation systems, deduplication, anomaly detection at scale.

5. Prerequisites

Embeddings.

6. Core concepts

  • ANN (Approximate Nearest Neighbor): algorithms (HNSW, IVF) that find "good enough" nearest neighbors much faster than exact brute-force search.
  • Similarity search: retrieving the top-k most similar vectors to a query vector.
  • Metadata filtering: restricting similarity search to a subset of vectors matching structured criteria (e.g., `tenant_id = X`).
  • Hybrid search: combining semantic (vector) search with lexical (keyword/BM25) search for better precision.

7. Terminology

TermMeaning
HNSWHierarchical Navigable Small World — a popular graph-based ANN indexing algorithm.
IVFInverted File index — clusters vectors and searches only relevant clusters.
Recall@kThe fraction of true top-k nearest neighbors actually found by the (approximate) search.
Metadata filterA structured condition (e.g., date range, tenant ID) applied alongside vector similarity search.
Hybrid searchCombining vector similarity with lexical/keyword search (e.g., BM25) in one query.

8. Architecture

Documents → Embed → Insert {vector, metadata} into Vector DB (builds ANN index)

Query → Embed → Vector DB.search(query_vector, top_k, filters)
 → Approximate nearest neighbors (ranked by similarity)
 → (optional) Rerank → Final context for LLM

9. How it works internally (ANN indexing)

HNSW builds a multi-layer graph where each node (vector) connects to its approximate nearest neighbors; search starts at a sparse top layer and greedily navigates down through denser layers toward the query's region, achieving logarithmic-ish search time instead of scanning every vector. This trades a small, tunable amount of recall accuracy for massive speed gains — a core trade-off every vector DB exposes via configuration parameters.

10. Step-by-step: setting up vector search

  1. Choose a vector DB based on scale, hosting preference, and metadata filtering needs.
  2. Embed and insert documents with relevant metadata (source, date, tenant, etc.).
  3. Configure the ANN index (e.g., HNSW parameters) balancing recall vs. speed.
  4. At query time, embed the query, apply metadata filters, and retrieve top-k results.
  5. Optionally rerank results before passing to the LLM.

11. Simple example

Storing 10,000 FAQ embeddings in Chroma (a lightweight, local-first vector DB) for a small internal tool — simple to set up, no separate infrastructure needed.

12. Real-world example

An enterprise RAG system uses PostgreSQL + pgvector specifically because the company already runs Postgres for other data, avoiding the operational overhead of a separate specialized vector database while still getting adequate ANN search performance (HNSW support) for their scale.

13. Code example

-- PostgreSQL + pgvector
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    embedding VECTOR(1536),
    tenant_id INT
);

CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);

-- Similarity search with metadata filter
SELECT content, 1 - (embedding <=> '[0.1, 0.2, ...]') AS similarity
FROM documents
WHERE tenant_id = 42
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;

# Qdrant example
from qdrant_client import QdrantClient

client = QdrantClient(url="http://localhost:6333")
results = client.search(
    collection_name="docs",
    query_vector=query_embedding,
    query_filter={"must": [{"key": "tenant_id", "match": {"value": 42}}]},
    limit=5,
)

def hybrid_search(query, alpha=0.5, top_k=10):
    vector_results = vector_search(embed(query), top_k=top_k*2)

15. Common mistakes

  • Not setting up metadata filtering for multi-tenant data, risking cross-tenant data leaks in retrieval.
  • Using brute-force exact search at a scale where it becomes a latency bottleneck instead of configuring ANN properly.
  • Ignoring recall/speed trade-off tuning, leaving default ANN parameters that may be poorly suited to the actual data scale.
  • Forgetting to rebuild/update the index after bulk document updates.

16. Best practices

  • Always scope metadata filters per tenant/user in multi-tenant systems — never rely on embedding similarity alone for isolation.
  • Benchmark recall@k vs. latency for your actual data distribution before committing to ANN parameters.
  • Combine vector search with reranking for production-grade precision.
  • Choose a vector DB matching your operational constraints (managed vs self-hosted, existing infra reuse).

17. Production considerations

Monitor index build/update latency for frequently-changing corpora; plan capacity for index memory footprint, which grows with vector count × dimensionality; have a reindexing strategy for embedding model upgrades.

18. Security considerations

Enforce metadata-based access control (tenant/user scoping) at the query level — a RAG system that doesn't filter retrieval by tenant can leak one customer's data into another's context, a serious security/compliance failure.

19. Performance considerations

ANN index type and parameters (e.g., HNSW's `ef_search`) directly trade recall against latency; tune based on measured production query patterns, not defaults alone.

20. Cost considerations

Managed vector DBs (Pinecone) charge based on vector count/dimensionality and query volume; self-hosted options (pgvector, Qdrant, Milvus) shift cost to infrastructure/ops overhead — compare total cost of ownership, not just sticker price.

21. Debugging/troubleshooting

  • Retrieval missing obviously relevant documents: check ANN recall settings (may be too aggressively approximate) or embedding/indexing mismatch.
  • Slow queries at scale: check index configuration, consider sharding/partitioning, or verify metadata filters aren't forcing a full scan.
  • Cross-tenant data appearing in results: audit metadata filtering logic immediately — this is a security incident.

27. Interview Questions — Beginner

Q1. What is a vector database?
A. A database specialized for storing embedding vectors and performing fast similarity search at scale.
Q2. What is ANN search?
A. Approximate Nearest Neighbor search — algorithms that find "good enough" nearest neighbors much faster than exact brute-force comparison.
Q3. Why not just use brute-force similarity search for everything?
A. It's too slow at scale (millions/billions of vectors); ANN indexing trades a small accuracy loss for major speed gains.
Q4. What is metadata filtering in a vector DB?
A. Restricting similarity search to vectors matching structured criteria, like a specific tenant or date range.
Q5. Name one popular ANN indexing algorithm.
A. HNSW (Hierarchical Navigable Small World) or IVF (Inverted File index).
Q6. What's hybrid search?
A. Combining semantic (vector) search with lexical/keyword search (like BM25) for better retrieval precision.
Q7. Why would you use pgvector instead of a dedicated vector DB?
A. If you're already running PostgreSQL, pgvector avoids introducing new infrastructure while still providing adequate vector search capability.
Q8. What's recall@k?
A. The fraction of the true top-k nearest neighbors that an approximate search actually finds.
Q9. Why is metadata filtering critical for multi-tenant RAG systems?
A. Without it, a query could retrieve another tenant's data purely based on semantic similarity, causing a serious data leak.
Q10. Is Chroma suitable for large-scale production use?
A. It's better suited for prototyping/small-scale apps; larger scale typically needs Qdrant, Milvus, Pinecone, or similar.

28. Interview Questions — Intermediate

Q1. How does HNSW achieve fast approximate search, conceptually?
A. It builds a multi-layer graph of vectors connected to their approximate neighbors; search starts at a sparse top layer and greedily navigates toward the query's region through progressively denser layers, avoiding a full scan.
Q2. What's the trade-off exposed by ANN index tuning parameters (e.g., HNSW's ef_search)?
A. Higher values search more candidates, improving recall accuracy at the cost of higher latency; lower values are faster but may miss some true nearest neighbors — this must be tuned against your actual data and latency requirements.
Q3. Why would you choose Qdrant or Weaviate over pgvector for a complex multi-tenant filtering use case?
A. Dedicated vector DBs often have more mature, flexible, and performant filtering capabilities purpose-built for combining vector search with complex metadata conditions at scale, compared to pgvector's extension-on-relational-DB approach, which can face different performance characteristics under heavy filtered search.
Q4. How would you test that your multi-tenant vector search never leaks cross-tenant data?
A. Write automated tests that insert documents for multiple tenants, then query as one tenant and assert the result set never contains documents belonging to another tenant, regardless of semantic similarity.
Q5. Why is reindexing necessary after an embedding model upgrade, and what's a safe migration strategy?
A. New embeddings are incompatible with the old vector space; a safe strategy re-embeds the full corpus into a new index/collection using the new model, validates it, then cuts over query traffic, avoiding mixing old and new vectors in the same searchable index.

29. Interview Questions — Advanced

Q1. How would you design a sharding strategy for a vector database holding billions of vectors across many tenants?
A. Consider sharding by tenant (keeps each tenant's data physically isolated, simplifies per-tenant deletion/compliance, but can create hot shards for large tenants) versus sharding by a hash of document ID (more even load distribution, but complicates per-tenant operations) — choice depends on tenant size distribution and compliance/isolation requirements.
Q2. What's a subtle failure mode of combining BM25 and vector search scores naively (e.g., simple weighted sum) in hybrid search?
A. BM25 and cosine similarity scores are on different, non-comparable scales and distributions; naively summing them without proper normalization can let one signal dominate unpredictably across different queries — proper hybrid search needs score normalization or rank-fusion techniques (e.g., reciprocal rank fusion) rather than raw score combination.

30. Interview Questions — Senior/Architect

Q1. Design a vector database architecture for an enterprise RAG platform serving hundreds of tenants with strict data isolation and compliance requirements.
A. Enforce tenant isolation at multiple layers (separate collections/namespaces per tenant or strict mandatory metadata filtering with no query path bypassing it), implement audit logging of all retrieval queries, support per-tenant data deletion for compliance (right-to-be-forgotten), choose a vector DB with mature multi-tenancy features, and load-test filtered-query performance at realistic tenant-count and data-scale before committing to an architecture.

31. Scenario-Based Questions

Scenario 1. A security audit discovers that a RAG system's retrieval occasionally returns documents belonging to a different customer. What's the root cause and fix?
A. Missing or improperly enforced tenant-scoped metadata filtering in the vector search query — fix by making tenant filtering mandatory and unbypassable at the query layer, and add automated tests specifically verifying tenant isolation.
Scenario 2. Your vector search latency degrades significantly as the corpus grows past a few million documents. What do you investigate?
A. Check ANN index configuration (parameters may need tuning for the new scale), consider whether sharding/partitioning is needed, and verify metadata filters aren't forcing inefficient full scans instead of leveraging the index properly.

32. Quick revision notes

  • Vector DB = embeddings + fast ANN similarity search + metadata filtering.
  • HNSW/IVF trade recall accuracy for speed.
  • Always enforce tenant/metadata filtering for multi-tenant systems.
  • Choose DB based on scale, hosting preference, filtering needs.

33. Cheat sheet

Vector DB = ANN indexing (HNSW/IVF) + metadata filtering + optional hybrid search. Enforce tenant isolation at the query layer, always. Choose based on scale/ops preference: pgvector (reuse Postgres), Pinecone (managed), Qdrant/Weaviate (flexible filtering), Milvus (massive scale), Chroma (prototyping).
