Introduction to LangChain

LangChain is an open-source framework for building applications powered by LLMs. It gives ready-made building blocks so you can connect a model with your data, prompts, memory and tools without writing all the glue code yourself.

1. Why do we need LangChain?

The course explains this through a real example: a "Chat with your PDF" app. A user uploads a book and asks questions like "Explain page 5 like I'm a beginner". To build this you need many moving parts:

  • Load the PDF and store it (e.g. cloud storage).
  • Split it into small chunks (pages / paragraphs).
  • Embed each chunk into a vector and store in a vector database.
  • Semantic search: convert the question into a vector and find the most similar chunks.
  • Send the question + relevant chunks to an LLM and return the answer.
flowchart TB
  subgraph Indexing
    P["PDF upload"] --> L["Document Loader"] --> S["Text Splitter"] --> E["Embedding Model"] --> V[("Vector DB")]
  end
  subgraph Query
    Q["User question"] --> QE["Embed question"] --> SS["Semantic search"]
    V --> SS
    SS --> C["Top-k chunks"]
    C --> LLM["LLM (Brain)"]
    Q --> LLM
    LLM --> A["Answer"]
  end

Challenges without a framework

  • The "brain" (NLU + text generation) is hard — solved by LLM APIs.
  • Hosting big models is costly — solved by API providers.
  • Orchestration is hard: many components (loader, splitter, embeddings, DB, LLM) must talk to each other, and switching any one (e.g. OpenAI → Gemini) means rewriting code. This is the gap LangChain fills.

2. Benefits of LangChain

  • Concept of chains — output of one step automatically becomes input of the next.
  • Model agnostic — swap OpenAI, Anthropic, Google, HuggingFace with minimal code change.
  • Complete ecosystem — 100s of loaders, splitters, vector stores, tools.
  • Memory & state handling — keep conversation history.

3. What can you build?

  • Conversational chatbots (customer support)
  • AI knowledge assistants (chat on your company docs)
  • AI agents (chatbots that can take actions, e.g. book tickets)
  • Workflow automation, summarization / research helpers

4. Alternatives

LlamaIndex (strong for data/RAG) and Haystack (search pipelines).

Key takeaway: LLM = brain. LangChain = the nervous system that connects the brain to data, memory and tools.

LangChain Components

LangChain has 6 core components. Every later video goes deep into one of these.

1. Models

The core interface to talk to AI models. Every provider has a different API format; LangChain gives one standard interface, so switching provider is a one-line change. Two types: Language models (text in → text out) and Embedding models (text in → vector out).

2. Prompts

The input given to the LLM. Output quality depends heavily on the prompt, so LangChain gives templates for:

  • Dynamic & reusable prompts — "Summarize {topic} in {tone} tone".
  • Role-based prompts — system: "You are an experienced {profession}".
  • Few-shot prompts — give examples first, then ask.

3. Chains

Build pipelines where output of one step is input to the next. Types: sequential, parallel, conditional.

4. Memory

LLM API calls are stateless — the model forgets the previous message. Memory types:

  • ConversationBufferMemory — stores the whole chat.
  • ConversationBufferWindowMemory — keeps only last N messages.
  • Summarizer-based memory — keeps a running summary.
  • Custom memory — store specific facts (user preferences).

5. Indexes

Connect your app to external knowledge (PDFs, websites, DBs). Made of 4 parts: Document Loader → Text Splitter → Vector Store → Retriever.

6. Agents

A chatbot with reasoning + tools. It can decide what steps to take and call APIs (e.g. calculator, weather, booking).

Key takeaway: Models + Prompts = basic call. Chains = composition. Memory = context. Indexes = your data. Agents = actions.

The Model component is the bridge between your code and different AI models.

1. LLMs vs Chat Models

FeatureLLMsChat Models
InputPlain stringList of messages (system / human / AI)
Memory of conversationNo conceptSupports chat history
Role awarenessNoYes (system role)

2. Closed-source chat models

from langchain_openai import ChatOpenAI
from dotenv import load_dotenv
load_dotenv()                     # reads OPENAI_API_KEY from .env

model = ChatOpenAI(model="gpt-4o-mini", temperature=0.7, max_completion_tokens=100)
result = model.invoke("What is the capital of India?")
print(result.content)

Same pattern for ChatAnthropic (langchain_anthropic) and ChatGoogleGenerativeAI (langchain_google_genai).

Important parameters

  • temperature (0 – 2): randomness. 0–0.3 for facts/code, 0.7+ for creative writing.
  • max tokens: limit on output length (controls cost).

3. Open-source models

Free to use, can run locally, full control and privacy, can be fine-tuned. Downsides: need good hardware (GPU), setup complexity, less polished than top closed models.

  • HuggingFaceEndpoint — use model through HF Inference API.
  • HuggingFacePipeline — download and run locally.
from langchain_huggingface import ChatHuggingFace, HuggingFaceEndpoint
llm = HuggingFaceEndpoint(repo_id="TinyLlama/TinyLlama-1.1B-Chat-v1.0", task="text-generation")
model = ChatHuggingFace(llm=llm)
print(model.invoke("What is LangChain?").content)

4. Embedding models

Convert text into a vector of numbers that captures meaning. Similar meaning → vectors close together.

from langchain_openai import OpenAIEmbeddings
emb = OpenAIEmbeddings(model="text-embedding-3-small", dimensions=32)
v1 = emb.embed_query("Delhi is the capital of India")
vs = emb.embed_documents(["doc one", "doc two"])

5. Mini project: Document similarity

Embed several documents + a query, then use cosine similarity to find the most relevant document. This is the seed idea of semantic search and RAG.

from sklearn.metrics.pairwise import cosine_similarity
doc_emb = emb.embed_documents(documents)
q_emb   = emb.embed_query("Tell me about Virat Kohli")
scores  = cosine_similarity([q_emb], doc_emb)[0]
best    = scores.argmax()
print(documents[best], scores[best])
Key takeaway: Use chat models for generation, embedding models for search. Everything has the same .invoke() style API.
Video 4

Prompts

Prompts are the instructions sent to the model. LangChain helps make them dynamic, reusable and role-aware.

1. Static vs Dynamic prompts

Static: the user types the full prompt — inconsistent, error-prone. Dynamic: you design a template, the user only fills values (e.g. paper name, style, length from dropdowns in a Streamlit "Research Paper Summarizer" app).

2. PromptTemplate

from langchain_core.prompts import PromptTemplate
template = PromptTemplate(
    template="Summarize the paper '{paper}' in {style} style, {length} length.",
    input_variables=["paper", "style", "length"],
    validate_template=True
)
prompt = template.invoke({"paper": "Attention Is All You Need",
                          "style": "beginner-friendly", "length": "short"})
result = model.invoke(prompt)

Why PromptTemplate instead of f-string?

  • Validation — catches missing variables early.
  • Reusability — save to JSON (template.save("t.json")) and load with load_prompt.
  • LangChain ecosystem — it is a Runnable, so it works in chains: template | model.

3. Messages

sequenceDiagram
  participant S as SystemMessage
  participant H as HumanMessage
  participant M as Model
  S->>M: You are a helpful assistant
  H->>M: Tell me about LangChain
  M-->>H: AIMessage (answer)
  Note over H,M: append AIMessage to chat_history<br/>so the next turn has context
  • SystemMessage — sets behavior/role.
  • HumanMessage — the user's input.
  • AIMessage — the model's reply.
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage
chat_history = [SystemMessage(content="You are a helpful AI assistant")]
while True:
    user = input("You: ")
    if user == "exit": break
    chat_history.append(HumanMessage(content=user))
    result = model.invoke(chat_history)
    chat_history.append(AIMessage(content=result.content))
    print("AI:", result.content)
Problem solved here: without storing history, the chatbot forgets ("Which is bigger, 2 or 0?" then "Multiply the bigger number by 10" fails). Labelling each message by role fixes confusion.

4. ChatPromptTemplate (dynamic multi-message prompts)

from langchain_core.prompts import ChatPromptTemplate
chat_template = ChatPromptTemplate([
    ("system", "You are a helpful {domain} expert"),
    ("human", "Explain in simple terms, what is {topic}")
])
prompt = chat_template.invoke({"domain": "cricket", "topic": "Dusra"})

5. MessagesPlaceholder

A slot inside a ChatPromptTemplate where you insert a full list of past messages at runtime (e.g. chat history loaded from DB).

from langchain_core.prompts import MessagesPlaceholder
chat_template = ChatPromptTemplate([
    ("system", "You are a helpful customer support agent"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{query}")
])
prompt = chat_template.invoke({"chat_history": history, "query": "Where is my refund?"})
Key takeaway: Single-turn → PromptTemplate. Multi-turn/role-based → ChatPromptTemplate + MessagesPlaceholder.

Structured Output

Making the LLM return data in a fixed format (like JSON) so other systems — databases, APIs, tools — can use it.

1. Why structured output?

  • Data extraction — pull name, skills, experience from a resume into a DB.
  • API building — e.g. analyze product reviews and return topic, pros, cons, sentiment.
  • Agents — tools need exact inputs (e.g. calculator needs two numbers, not a sentence).
flowchart LR
  T["Unstructured text<br/>(review)"] --> M["Chat model<br/>.with_structured_output(schema)"]
  S["Schema<br/>TypedDict / Pydantic / JSON"] --> M
  M --> J["Structured object<br/>{summary, sentiment, pros, cons}"]
  J --> DB[("Database / API / Tool")]

2. Two kinds of models

  • Models that support structured output natively (OpenAI, Gemini, Claude) → use with_structured_output().
  • Models that don't (many open-source) → use Output Parsers (next video).

3. Ways to define the schema

a) TypedDict

Python type hints only — no runtime validation. Annotated adds a description for the LLM; Optional and Literal are supported.

from typing import TypedDict, Annotated, Optional, Literal
class Review(TypedDict):
    key_themes: Annotated[list[str], "Key themes discussed in the review"]
    summary: Annotated[str, "A brief summary"]
    sentiment: Annotated[Literal["pos", "neg"], "Sentiment of the review"]
    pros: Annotated[Optional[list[str]], "List of pros"]
    cons: Annotated[Optional[list[str]], "List of cons"]

structured_model = model.with_structured_output(Review)
result = structured_model.invoke(review_text)   # returns a dict
print(result["summary"])

b) Pydantic (recommended)

Data validation library: type checking, default values, type coercion ("32" → 32), EmailStr, constraints with Field(gt=0, lt=10), and .model_dump() / .model_dump_json().

from pydantic import BaseModel, Field
class Review(BaseModel):
    summary: str = Field(description="A brief summary")
    sentiment: Literal["pos", "neg"]
    rating: float = Field(gt=0, lt=5)
    name: Optional[str] = None

result = model.with_structured_output(Review).invoke(review_text)  # Review object

c) JSON Schema

Language-independent — useful when the project mixes Python and JavaScript backends.

TypedDictPydanticJSON Schema
ValidationNoYesYes (structure)
Defaults / coercionNoYesNo
Cross-languageNoNoYes
Best forQuick Python hintsMost Python appsMulti-language projects

4. method parameter

with_structured_output(schema, method="json_mode") for plain JSON, or method="function_calling" (default for OpenAI) which uses the model's tool-calling ability.

Key takeaway: For capable models, with_structured_output(PydanticModel) is the cleanest way to get reliable, typed output.

Output Parsers

Output parsers convert raw LLM text into structured formats. They work with any model — including those without native structured output.

flowchart TB
  OP["Output Parsers"] --> A["StrOutputParser<br/>AIMessage to plain string"]
  OP --> B["JsonOutputParser<br/>any JSON, no schema enforced"]
  OP --> C["StructuredOutputParser<br/>JSON with given fields, no validation"]
  OP --> D["PydanticOutputParser<br/>schema + validation"]

1. StrOutputParser

Extracts .content from the model's message. Very useful in chains — the next prompt receives a clean string.

from langchain_core.output_parsers import StrOutputParser
template1 = PromptTemplate.from_template("Write a detailed report on {topic}")
template2 = PromptTemplate.from_template("Write a 5-line summary of:\n{text}")
chain = template1 | model | StrOutputParser() | template2 | model | StrOutputParser()
print(chain.invoke({"topic": "black hole"}))

2. JsonOutputParser

Asks the model for JSON using parser.get_format_instructions(). Fast and easy, but you can't force the exact structure.

from langchain_core.output_parsers import JsonOutputParser
parser = JsonOutputParser()
template = PromptTemplate(
    template="Give 5 facts about {topic}\n{format_instruction}",
    input_variables=["topic"],
    partial_variables={"format_instruction": parser.get_format_instructions()})
chain = template | model | parser

3. StructuredOutputParser

Define the fields using ResponseSchema (name + description). Enforces structure but does not validate data types.

from langchain.output_parsers import StructuredOutputParser, ResponseSchema
schema = [ResponseSchema(name="fact_1", description="Fact 1 about the topic"),
          ResponseSchema(name="fact_2", description="Fact 2 about the topic")]
parser = StructuredOutputParser.from_response_schemas(schema)

4. PydanticOutputParser

Strict schema + type validation + easy integration. Best of the four.

from langchain_core.output_parsers import PydanticOutputParser
class Person(BaseModel):
    name: str = Field(description="Name of the person")
    age: int = Field(gt=18, description="Age of the person")
    city: str
parser = PydanticOutputParser(pydantic_object=Person)
template = PromptTemplate(
    template="Generate name, age and city of a fictional {place} person\n{format_instruction}",
    input_variables=["place"],
    partial_variables={"format_instruction": parser.get_format_instructions()})
chain = template | model | parser
print(chain.invoke({"place": "Indian"}))
Key takeaway: with_structured_output when the model supports it; otherwise PydanticOutputParser. StrOutputParser is used in almost every chain.

Chains

A chain connects multiple steps into one pipeline using the pipe operator |. You call invoke once and data flows automatically.

1. Simple / Sequential chain

chain = prompt | model | StrOutputParser()
chain.invoke({"topic": "cricket"})
chain.get_graph().print_ascii()   # visualize the chain
flowchart LR
  I["{topic}"] --> P1["Prompt 1: detailed report"] --> M1["LLM"] --> S1["Parser"] --> P2["Prompt 2: 5 key points"] --> M2["LLM"] --> S2["Parser"] --> O["Output"]

2. Parallel chain

Run two chains at the same time on the same input, then merge. Example: from a text, generate notes (model 1) and a quiz (model 2), then a third step merges them into one document.

from langchain_core.runnables import RunnableParallel
parallel_chain = RunnableParallel({
    "notes": prompt1 | model1 | parser,
    "quiz":  prompt2 | model2 | parser,
})
merge_chain = prompt3 | model1 | parser
chain = parallel_chain | merge_chain
chain.invoke({"text": long_text})
flowchart LR
  T["Text"] --> N["Notes chain (model 1)"]
  T --> Q["Quiz chain (model 2)"]
  N --> MG["Merge prompt + LLM"]
  Q --> MG
  MG --> O["Final document"]

3. Conditional chain

Choose which branch to run based on a condition. Example: classify customer feedback sentiment (structured with Pydantic), then send a positive or negative reply.

from langchain_core.runnables import RunnableBranch, RunnableLambda
class Feedback(BaseModel):
    sentiment: Literal["positive", "negative"]
classifier_chain = prompt1 | model | PydanticOutputParser(pydantic_object=Feedback)

branch_chain = RunnableBranch(
    (lambda x: x.sentiment == "positive", prompt_pos | model | parser),
    (lambda x: x.sentiment == "negative", prompt_neg | model | parser),
    RunnableLambda(lambda x: "Could not find sentiment")   # default
)
chain = classifier_chain | branch_chain
flowchart LR
  F["Feedback"] --> C["Classifier chain"] --> D{"sentiment?"}
  D -->|positive| P["Thank-you reply"]
  D -->|negative| N["Apology reply"]
  D -->|else| X["Default"]
Key takeaway: Sequential = step by step, Parallel = side by side, Conditional = if/else. All built from Runnables (next video).

Runnables — Why and What

This video explains the "why" behind the | operator: the Runnable interface that standardizes every LangChain component.

1. The history / problem

  • After ChatGPT (2022) LangChain built components for everything: models, prompts, loaders, retrievers, parsers.
  • Each component had different methods: models used predict(), prompts used format(), retrievers used get_relevant_documents().
  • To connect them, LangChain created many ready-made chains: LLMChain, RetrievalQAChain, SequentialChain… — the codebase became huge and hard to learn.
Root cause: components were not standardized, so they couldn't connect automatically.

2. The solution: Runnables

A Runnable is a unit of work. Every Runnable:

  • takes input, does work, gives output;
  • follows a common interface: invoke() (one input), batch() (many inputs), stream() (token by token);
  • can be connected with another Runnable, and the result is also a Runnable — like Lego blocks.
flowchart LR
  subgraph R1["Runnable"]
    A["invoke / batch / stream"]
  end
  subgraph R2["Runnable"]
    B["invoke / batch / stream"]
  end
  subgraph R3["Runnable"]
    C["invoke / batch / stream"]
  end
  R1 --> R2 --> R3
  R3 --> W["Whole chain = one bigger Runnable"]

3. Building the idea from scratch

The video recreates this with plain Python: an abstract class Runnable with an abstract invoke(); dummy classes NakliLLM and NakliPromptTemplate implement it; then a RunnableConnector class takes a list of runnables and calls each one's invoke passing the output forward. Since the connector itself is a Runnable, connectors can be chained together too.

from abc import ABC, abstractmethod
class Runnable(ABC):
    @abstractmethod
    def invoke(self, input_data): ...

class RunnableConnector(Runnable):
    def __init__(self, runnable_list):
        self.runnable_list = runnable_list
    def invoke(self, input_data):
        for r in self.runnable_list:
            input_data = r.invoke(input_data)
        return input_data
Key takeaway: Because everything is a Runnable with the same invoke, any component can plug into any other — that's why prompt | model | parser works.

Runnable Primitives & LCEL

Two kinds of runnables: task-specific (ChatOpenAI, PromptTemplate, retrievers — do real work) and runnable primitives (control how runnables connect).

flowchart TB
  R["Runnable primitives"] --> S["RunnableSequence<br/>A then B"]
  R --> P["RunnableParallel<br/>A and B together, dict output"]
  R --> T["RunnablePassthrough<br/>returns input as is"]
  R --> L["RunnableLambda<br/>any Python function"]
  R --> B["RunnableBranch<br/>if / else routing"]

1. RunnableSequence

from langchain_core.runnables import RunnableSequence
chain = RunnableSequence(prompt, model, parser)   # same as prompt | model | parser

2. RunnableParallel

Each branch gets the same input; output is a dictionary. Example: generate a tweet and a LinkedIn post on one topic.

chain = RunnableParallel({
    "tweet":    RunnableSequence(prompt_tweet, model, parser),
    "linkedin": RunnableSequence(prompt_li, model, parser),
})

3. RunnablePassthrough

Passes input unchanged. Useful when you need both the original and processed value. Example: generate a joke, then output both the joke and its explanation.

from langchain_core.runnables import RunnablePassthrough
joke_chain = RunnableSequence(prompt_joke, model, parser)
parallel = RunnableParallel({
    "joke": RunnablePassthrough(),
    "explanation": RunnableSequence(prompt_explain, model, parser),
})
final = RunnableSequence(joke_chain, parallel)

4. RunnableLambda

Turns any Python function into a Runnable — preprocessing, word counting, formatting.

from langchain_core.runnables import RunnableLambda
word_count = RunnableLambda(lambda text: len(text.split()))
parallel = RunnableParallel({"joke": RunnablePassthrough(), "words": word_count})

5. RunnableBranch

Conditional routing. Example: generate a report; if it's longer than 300 words summarize it, else pass it through.

branch = RunnableBranch(
    (lambda x: len(x.split()) > 300, RunnableSequence(prompt_summary, model, parser)),
    RunnablePassthrough()
)

6. LCEL — LangChain Expression Language

The declarative pipe syntax a | b | c replaces RunnableSequence(a, b, c). It's the standard way to write chains today.

Key takeaway: Sequence, Parallel, Passthrough, Lambda, Branch + the | operator = enough to build almost any pipeline (and the core idea behind LangGraph later).

Document Loaders

First step of RAG: bring data from any source into a standard Document format.

flowchart LR
  A["txt"] --> TL["TextLoader"]
  B["pdf"] --> PL["PyPDFLoader"]
  C["folder"] --> DL["DirectoryLoader"]
  D["web page"] --> WL["WebBaseLoader"]
  E["csv"] --> CL["CSVLoader"]

  PL --> DOC
  DL --> DOC
  WL --> DOC

1. The Document object

Document(page_content="actual text…", metadata={"source": "file.pdf", "page": 0})

2. Common loaders

TextLoader

from langchain_community.document_loaders import TextLoader
docs = TextLoader("cricket.txt", encoding="utf-8").load()
chain.invoke({"poem": docs[0].page_content})

PyPDFLoader

Loads a PDF page by page — one Document per page. Best for text PDFs; for scanned/complex layouts use PDFPlumberLoader, UnstructuredPDFLoader, AmazonTextractPDFLoader, PyMuPDFLoader.

from langchain_community.document_loaders import PyPDFLoader
docs = PyPDFLoader("dl-curriculum.pdf").load()
print(len(docs), docs[0].metadata)

DirectoryLoader

from langchain_community.document_loaders import DirectoryLoader
loader = DirectoryLoader("books", glob="*.pdf", loader_cls=PyPDFLoader)

WebBaseLoader

Uses requests + BeautifulSoup to read static web pages (for JS-heavy pages use SeleniumURLLoader).

CSVLoader

One Document per row.

3. load() vs lazy_load()

load()lazy_load()
Eager — loads everything into memory at once, returns a listLazy — returns a generator, one Document at a time
Good for a few small filesGood for hundreds of PDFs / big data
for doc in loader.lazy_load():
    print(doc.metadata)

4. Custom loaders

If no loader exists for your source, subclass BaseLoader and implement load() / lazy_load(). Many community loaders exist for Notion, Slack, YouTube, S3, etc.

Key takeaway: Whatever the source, the output is always a list of Document objects — so the rest of the pipeline doesn't care where data came from.

Text Splitters

Break large documents into small chunks that an LLM / embedding model can handle well.

1. Why split?

  • Model limits — context window / embedding input size.
  • Better embeddings — one chunk = one focused meaning; a whole book in one vector loses detail.
  • Better semantic search — precise matches.
  • Optimized computation — less memory, parallel processing.
flowchart TB
  TS["Text Splitters"] --> L["1. Length based<br/>CharacterTextSplitter"]
  TS --> R["2. Text structure based<br/>RecursiveCharacterTextSplitter"]
  TS --> D["3. Document structure based<br/>code, markdown, html"]
  TS --> S["4. Semantic meaning based<br/>SemanticChunker"]

2. Length-based

Cut every N characters/tokens. Simple and fast, but may cut a word or sentence in half.

from langchain_text_splitters import CharacterTextSplitter
splitter = CharacterTextSplitter(chunk_size=100, chunk_overlap=0, separator="")
chunks = splitter.split_documents(docs)

chunk_overlap: number of characters shared between neighbouring chunks — keeps context across the cut. Rule of thumb: 10–20% of chunk_size.

3. Text-structure-based (most used)

RecursiveCharacterTextSplitter tries separators in order: paragraph "\n\n" → line "\n" → word " " → character "". It keeps paragraphs/sentences together whenever they fit in chunk_size.

from langchain_text_splitters import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_text(text)
flowchart LR
  T["Text"] --> P{"fits after split on paragraphs?"}
  P -->|yes| OK["Chunk"]
  P -->|no| Ln{"split on lines"}
  Ln -->|fits| OK
  Ln -->|no| W{"split on words"}
  W -->|fits| OK
  W -->|no| C["split on characters"] --> OK

4. Document-structure-based

For code / markdown, split on language syntax (class, def, headings).

from langchain_text_splitters import Language
splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON, chunk_size=300, chunk_overlap=0)

5. Semantic-meaning-based

Embeds each sentence and splits where the meaning changes (big drop in similarity). Good when one paragraph mixes topics (e.g. cricket then terrorism). Still experimental.

from langchain_experimental.text_splitter import SemanticChunker
splitter = SemanticChunker(OpenAIEmbeddings(),
           breakpoint_threshold_type="standard_deviation", breakpoint_threshold_amount=1)
Key takeaway: Default to RecursiveCharacterTextSplitter with some overlap; use language-aware splitting for code.

Vector Stores

A system to store embeddings and search them by similarity.

1. Why vector stores? (Movie recommender example)

Keyword matching (same director/actor/genre) gives poor recommendations. Better: embed each movie's plot and recommend movies with similar vectors. With millions of movies you need three things: storage for vectors, fast semantic search, and indexing. A normal SQL DB can't do this well.

2. Features of a vector store

  • Storage — in-memory or on-disk.
  • Similarity search — find nearest vectors to a query.
  • Indexing — e.g. clustering / ANN (approximate nearest neighbour) for speed on millions of vectors.
  • CRUD — add, update, delete vectors.

3. Vector store vs Vector database

Vector StoreVector Database
Lightweight library (storage + search)Full DB features: distributed, backups, ACID, auth, concurrency
FAISSPinecone, Milvus, Weaviate, Qdrant
Prototypes / small appsProduction scale

Every vector database is a vector store, but not every vector store is a database. Chroma sits in between — easy to start, persists to disk.

flowchart LR
  D["Documents"] --> E["Embedding model"] --> VS[("Vector Store<br/>Chroma / FAISS / Pinecone")]
  Q["Query"] --> QE["Embed query"] --> VS
  VS --> R["Top-k similar docs + scores"]

4. Vector stores in LangChain

All share a common interface: from_documents, add_documents, similarity_search, delete… so switching store is easy.

from langchain_chroma import Chroma
vector_store = Chroma(embedding_function=OpenAIEmbeddings(),
                      persist_directory="my_chroma_db", collection_name="ipl_players")

vector_store.add_documents([doc1, doc2, doc3])          # metadata e.g. {"team": "CSK"}
vector_store.get(include=["embeddings", "documents", "metadatas"])
vector_store.similarity_search("Who is a bowler?", k=2)
vector_store.similarity_search_with_score("Who is a bowler?", k=2)  # lower = closer
vector_store.similarity_search_with_score("", filter={"team": "CSK"})  # metadata filter
vector_store.update_document(document_id="…", document=new_doc)
vector_store.delete(ids=["…"])
Key takeaway: Embeddings + vector store = semantic memory for your app. Chroma/FAISS for learning, a managed vector DB for production.

Retrievers

A retriever takes a query and returns relevant Documents from a data source. Retrievers are Runnables, so they plug straight into chains.

flowchart TB
  R["Retrievers"] --> DS["By data source"]
  R --> SS["By search strategy"]
  DS --> W["WikipediaRetriever"]
  DS --> V["VectorStoreRetriever"]
  DS --> AR["ArxivRetriever"]
  SS --> MMR["MMR"]
  SS --> MQ["MultiQueryRetriever"]
  SS --> CC["ContextualCompressionRetriever"]
  SS --> O["ParentDocument, SelfQuery, Ensemble, MultiVector"]

1. Wikipedia Retriever

Searches Wikipedia using the query (keyword-based) and returns article content as Documents. It's a retriever (not a loader) because it decides relevance.

from langchain_community.retrievers import WikipediaRetriever
retriever = WikipediaRetriever(top_k_results=2, lang="en")
docs = retriever.invoke("India Pakistan conflict history")

2. Vector Store Retriever

vector_store = Chroma.from_documents(docs, OpenAIEmbeddings(), collection_name="demo")
retriever = vector_store.as_retriever(search_kwargs={"k": 2})
retriever.invoke("What is Chroma used for?")

Why not just similarity_search? The retriever is a Runnable (works in chains) and supports different search strategies.

3. MMR — Maximal Marginal Relevance

Problem: top results are often near-duplicates. MMR picks results that are relevant AND diverse.

retriever = vector_store.as_retriever(search_type="mmr",
            search_kwargs={"k": 3, "lambda_mult": 0.5})   # 1 = relevance only, 0 = max diversity

4. Multi-Query Retriever

Ambiguous query ("How can I stay healthy?") → LLM writes several versions (diet? exercise? sleep?) → retrieve for each → merge unique results.

from langchain.retrievers.multi_query import MultiQueryRetriever
mq = MultiQueryRetriever.from_llm(retriever=vector_store.as_retriever(search_kwargs={"k": 5}),
                                  llm=ChatOpenAI())
flowchart LR
  Q["Original query"] --> L["LLM"]
  L --> Q1["Query 1"]
  L --> Q2["Query 2"]
  L --> Q3["Query 3"]
  Q1 --> R["Retriever"]
  Q2 --> R
  Q3 --> R
  R --> U["Unique merged docs"]

5. Contextual Compression Retriever

Retrieved docs often contain irrelevant parts. A compressor (LLM) keeps only the sentences relevant to the query.

from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor
compressor = LLMChainExtractor.from_llm(ChatOpenAI())
cc = ContextualCompressionRetriever(base_retriever=base, base_compressor=compressor)
Key takeaway: Retrieval quality decides RAG quality. Start with a vector retriever, add MMR / multi-query / compression when results are weak.

RAG — Retrieval Augmented Generation

RAG gives an LLM access to external, up-to-date or private information at query time, by putting relevant context into the prompt.

1. Problems with plain LLMs

  • Private data — the model was never trained on your company docs.
  • Knowledge cutoff — doesn't know recent events.
  • Hallucination — confidently makes up facts.

2. Solution options

Fine-tuning

Further train the model on domain data (supervised fine-tuning, LoRA/QLoRA). Drawbacks: expensive, needs ML expertise, and must re-train every time data changes.

In-context learning

LLMs can learn from examples/context inside the prompt (an emergent property of large models). RAG = in-context learning where the context is fetched automatically.

3. The 4 steps of RAG

flowchart LR
  subgraph S1["1. Indexing (offline)"]
    A["Load docs"] --> B["Split chunks"] --> C["Embed"] --> D[("Vector store")]
  end
  subgraph S2["2. Retrieval"]
    Q["Query"] --> R["Retriever"]
    D --> R
  end
  subgraph S3["3. Augmentation"]
    R --> P["Prompt = query + retrieved context"]
  end
  subgraph S4["4. Generation"]
    P --> L["LLM"] --> Ans["Grounded answer"]
  end
  1. Indexing — document ingestion (loaders) → chunking (splitters) → embedding → storage (vector store).
  2. Retrieval — embed the query, find the most relevant chunks (semantic search, MMR etc.).
  3. Augmentation — put query + context into a prompt: "Answer ONLY from the provided context. If the context is insufficient, say you don't know."
  4. Generation — the LLM generates the final answer using its own knowledge + the context.

4. RAG vs Fine-tuning

RAGFine-tuning
CostLowHigh
Updating knowledgeJust re-index documentsRe-train
TransparencyCan show sourcesBlack box
Hallucination controlBetter (grounded)Limited
Key takeaway: RAG solves private data, cutoff and hallucination cheaply — every component from videos 10–13 is one part of the pipeline.

RAG Project — YouTube Video Chatbot

Build a chatbot that answers questions about a long YouTube video (e.g. a 2-hour podcast) — like a "chat with this video" feature.

flowchart TB
  YT["YouTube video ID"] --> TR["youtube-transcript-api<br/>fetch transcript"]
  TR --> SP["RecursiveCharacterTextSplitter<br/>chunk 1000, overlap 200"]
  SP --> EM["OpenAIEmbeddings"]
  EM --> FS[("FAISS")]
  FS --> RT["Retriever k=4"]
  Q["Question"] --> PAR["RunnableParallel"]
  RT --> FD["format_docs (RunnableLambda)"] --> PAR
  PAR --> PR["PromptTemplate"] --> LLM["ChatOpenAI"] --> OP["StrOutputParser"] --> A["Answer"]

Step 1 — Indexing

from youtube_transcript_api import YouTubeTranscriptApi, TranscriptsDisabled
video_id = "Gfr50f6ZBvo"
try:
    transcript_list = YouTubeTranscriptApi.get_transcript(video_id, languages=["en"])
    transcript = " ".join(chunk["text"] for chunk in transcript_list)
except TranscriptsDisabled:
    print("No captions available")

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.create_documents([transcript])
vector_store = FAISS.from_documents(chunks, OpenAIEmbeddings(model="text-embedding-3-small"))

Step 2 — Retrieval

retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 4})

Step 3 — Augmentation

prompt = PromptTemplate(template="""You are a helpful assistant.
Answer ONLY from the provided transcript context.
If the context is insufficient, just say you don't know.
{context}
Question: {question}""", input_variables=["context", "question"])

Step 4 — Generation, as one chain

def format_docs(docs):
    return "\n\n".join(d.page_content for d in docs)

parallel_chain = RunnableParallel({
    "context": retriever | RunnableLambda(format_docs),
    "question": RunnablePassthrough(),
})
main_chain = parallel_chain | prompt | ChatOpenAI(model="gpt-4o-mini", temperature=0.2) | StrOutputParser()
main_chain.invoke("Can you summarize the video?")

Improvements suggested

  • UI — Streamlit app or Chrome extension that works on the open YouTube tab.
  • Evaluation — RAGAS (faithfulness, answer relevancy, context precision), LangSmith tracing.
  • Indexing — better transcripts (translation for Hindi videos), smarter chunking, better vector DB.
  • Retrieval — query rewriting, multi-query, domain-aware routing, MMR, hybrid search, re-ranking.
  • Augmentation — prompt templating, answer grounding, context window optimization.
  • Generation — answer with citations, guard-railing.
  • Advanced — multimodal RAG, agentic RAG, memory-based RAG, HyDE.
Key takeaway: The whole RAG app is just Runnables: retriever + lambda + parallel + prompt + model + parser.

Tools

LLMs can think and talk but can't do things (no internet, no live data, unreliable maths). A tool is a Python function packaged so an LLM can understand when and how to call it.

flowchart TB
  T["Tools"] --> B["Built-in tools"]
  T --> C["Custom tools"]
  B --> B1["DuckDuckGoSearchRun"]
  B --> B2["WikipediaQueryRun"]
  B --> B3["PythonREPLTool / ShellTool"]
  B --> B4["RequestsGetTool, GmailSendMessageTool"]
  C --> C1["@tool decorator"]
  C --> C2["StructuredTool + Pydantic"]
  C --> C3["BaseTool subclass"]
  T --> K["Toolkits = group of related tools"]

1. How a tool helps an AI agent

LLM = brain (reasoning/decision). Tools = hands (action). Agent = brain + hands.

2. Built-in tools

from langchain_community.tools import DuckDuckGoSearchRun
search = DuckDuckGoSearchRun()
print(search.invoke("IPL news today"))
print(search.name, search.description, search.args)
Careful: ShellTool runs real terminal commands — never give it to an LLM in production without sandboxing.

3. Custom tools

a) @tool decorator (simplest)

Needs a docstring (becomes the description) and type hints (become the schema).

from langchain_core.tools import tool
@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers"""
    return a * b

multiply.invoke({"a": 3, "b": 5})
print(multiply.args_schema.model_json_schema())   # what the LLM actually sees

b) StructuredTool + Pydantic (strict input)

from langchain_core.tools import StructuredTool
class MultiplyInput(BaseModel):
    a: int = Field(required=True, description="First number")
    b: int = Field(required=True, description="Second number")
multiply_tool = StructuredTool.from_function(func=lambda a, b: a * b,
    name="multiply", description="Multiply two numbers", args_schema=MultiplyInput)

c) BaseTool subclass (full control, async support)

from langchain_core.tools import BaseTool
class MultiplyTool(BaseTool):
    name: str = "multiply"
    description: str = "Multiply two numbers"
    args_schema: type[BaseModel] = MultiplyInput
    def _run(self, a: int, b: int) -> int:
        return a * b

4. Toolkits

A collection of related tools for one service — e.g. GoogleDriveToolkit (upload, search, read), or your own MathToolkit returning [add, multiply].

Key takeaway: A good tool = clear name + clear description + typed input schema. The LLM only sees that schema, not your code.

Tool Calling

How an LLM actually uses tools: binding → calling → execution. The LLM never runs the tool itself — it only suggests the call; your code (or LangChain) executes it.

sequenceDiagram
  participant U as User
  participant L as LLM (with bound tools)
  participant T as Tool (your code)
  U->>L: HumanMessage "multiply 3 and 10"
  L-->>U: AIMessage with tool_calls [multiply a=3 b=10]
  U->>T: tool.invoke(tool_call)
  T-->>U: ToolMessage content=30
  U->>L: [Human, AI, ToolMessage]
  L-->>U: AIMessage "3 x 10 = 30"

1. Tool binding

Register tools with the model so it knows their names, descriptions and input schemas. Only models that support tool calling can do this.

llm_with_tools = ChatOpenAI().bind_tools([multiply])

2. Tool calling

When the model decides a tool is needed, the reply has an empty/short content and a tool_calls list (name, args, id). For normal chat ("hi") it just replies normally.

messages = [HumanMessage("Can you multiply 3 with 10?")]
ai_msg = llm_with_tools.invoke(messages)
messages.append(ai_msg)
print(ai_msg.tool_calls)   # [{'name': 'multiply', 'args': {'a': 3, 'b': 10}, 'id': 'call_…'}]

3. Tool execution

Invoke the tool with the tool_call; LangChain returns a ToolMessage (linked by tool_call_id). Send the full history back so the LLM writes the final answer.

tool_result = multiply.invoke(ai_msg.tool_calls[0])   # ToolMessage
messages.append(tool_result)
final = llm_with_tools.invoke(messages)
print(final.content)

4. Project: Currency conversion

Two tools: get_conversion_factor(base, target) (calls an exchange-rate API) and convert(base_value, conversion_rate). Problem: the LLM would try to fill conversion_rate itself. Fix: mark it with InjectedToolArg so the LLM doesn't fill it — your code injects the value from the first tool's result.

from langchain_core.tools import InjectedToolArg
from typing import Annotated
@tool
def convert(base_value: int, conversion_rate: Annotated[float, InjectedToolArg]) -> float:
    """Given a currency conversion rate, convert the base value"""
    return base_value * conversion_rate

for tc in ai_msg.tool_calls:
    if tc["name"] == "get_conversion_factor":
        msg = get_conversion_factor.invoke(tc); rate = json.loads(msg.content)["conversion_rate"]
        messages.append(msg)
    if tc["name"] == "convert":
        tc["args"]["conversion_rate"] = rate
        messages.append(convert.invoke(tc))
This manual loop works, but it's not autonomous — you wrote the control flow. An agent automates this loop (next video).
Key takeaway: bind_tools → model returns tool_calls → you execute → send ToolMessage back → model answers.

AI Agents

An AI agent is an intelligent system that receives a high-level goal, then autonomously plans, decides, and executes a sequence of actions using tools, memory and reasoning.

1. Why agents? (Travel planning example)

Planning a Delhi → Goa trip normally means checking trains/flights, hotels, budget, itinerary across many sites. An agent takes one instruction ("Plan a 3-day budget trip to Goa in May") and does all the steps itself.

2. Characteristics

  • Goal-driven — you say what, it figures out how.
  • Supports planning — breaks a goal into steps.
  • Reasoning — thinks before acting.
  • Tool-aware — knows what tools exist and when to use them.
  • Context-aware — uses memory / previous observations.

3. ReAct pattern (Reasoning + Acting)

The agent repeats Thought → Action → Observation until it reaches a Final Answer.

flowchart LR
  Q["User goal"] --> TH["Thought<br/>what should I do?"]
  TH --> AC["Action<br/>call a tool with input"]
  AC --> OB["Observation<br/>tool result"]
  OB --> TH
  TH -->|enough info| FA["Final Answer"]

Example: "Find the capital of the state where Mumbai is, and its current weather" → Thought: find the state → Action: search → Observation: Maharashtra, capital Mumbai → Thought: need weather → Action: weather tool → Final Answer.

4. Agent vs AgentExecutor

flowchart TB
  U["User query"] --> AE["AgentExecutor (orchestrator / loop)"]
  AE --> AG["Agent (LLM + ReAct prompt)<br/>decides next step"]
  AG -->|AgentAction| AE
  AE --> TL["Run tool"]
  TL -->|observation| AE
  AG -->|AgentFinish| OUT["Final answer"]
  • Agent — the decision maker: given the query + scratchpad, outputs either an AgentAction (tool + input) or AgentFinish.
  • AgentExecutor — runs the loop: calls agent, executes the tool, appends the observation to the agent_scratchpad, repeats.

5. Code

from langchain import hub
from langchain.agents import create_react_agent, AgentExecutor
from langchain_community.tools import DuckDuckGoSearchRun

@tool
def get_weather_data(city: str) -> str:
    """Fetch current weather data for a given city"""
    return requests.get(f"https://api.weatherstack.com/current?access_key=KEY&query={city}").json()

prompt = hub.pull("hwchase17/react")      # standard ReAct prompt template
agent = create_react_agent(llm=ChatOpenAI(), tools=[DuckDuckGoSearchRun(), get_weather_data], prompt=prompt)
agent_executor = AgentExecutor(agent=agent, tools=[DuckDuckGoSearchRun(), get_weather_data], verbose=True)

agent_executor.invoke({"input": "Find the capital of Madhya Pradesh, then its current weather"})

With verbose=True you can watch every Thought / Action / Observation.

6. What's next — LangGraph

LangChain's AgentExecutor is good for simple agents, but complex agentic systems (multi-agent, human-in-the-loop, branching, persistence) need explicit state and graphs. That is what LangGraph provides — the natural next course after this playlist.

Key takeaway: Agent = LLM + Tools + ReAct loop. Tool calling (video 17) gave the mechanism; the agent automates the loop.
