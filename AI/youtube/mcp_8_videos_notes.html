What is MCP & Why Do We Need It?

MCP (Model Context Protocol) is an open standard, introduced by Anthropic in November 2024, that defines one common way for AI applications to connect to external tools and data. Often described as "USB-C for AI apps".

1. The evolution of AI apps

flowchart LR
  A["Chatbot<br/>only training knowledge"] --> B["Copy-paste context<br/>user pastes docs into chat"]
  B --> C["Function calling / plugins<br/>each app writes custom integrations"]
  C --> D["MCP<br/>standard plug for any tool"]
  • Context is everything — an LLM is only as useful as the information and actions it can reach (your files, GitHub, Slack, DB, calendar).
  • Early on, users manually copy-pasted context into the chat — slow and tiring ("context fragmentation").
  • Then came function calling / tool calling: developers wrote integrations so the LLM could call APIs.

2. The problem: M × N integrations

Every AI app (ChatGPT, Claude, Cursor, your own chatbot) had to build its own connector for every service (GitHub, Drive, Slack, Jira…).

flowchart LR
  subgraph Before["Without MCP: M x N"]
    A1["App 1"] --> S1["GitHub"]
    A1 --> S2["Slack"]
    A1 --> S3["Drive"]
    A2["App 2"] --> S1
    A2 --> S2
    A2 --> S3
  end
  subgraph After["With MCP: M + N"]
    B1["App 1"] --> P(("MCP"))
    B2["App 2"] --> P
    P --> T1["GitHub server"]
    P --> T2["Slack server"]
    P --> T3["Drive server"]
  end
  • Huge duplicated effort; each integration has different auth, formats and error handling.
  • Maintenance pain when an API changes.
  • Security inconsistencies across custom code.

3. What MCP changes

  • Service providers write one MCP server; it works with every MCP-compatible app.
  • App developers implement the MCP client once; they get access to the whole ecosystem.
  • Users plug in new capabilities without waiting for the app vendor.

4. Why it spread fast

Open spec, SDKs in many languages, and adoption by major AI apps and IDEs (Claude, ChatGPT, Cursor, VS Code, and others), plus thousands of community servers.

Key takeaway: MCP doesn't add new AI intelligence — it standardizes how AI apps get context and take actions, turning M×N custom integrations into M+N.

MCP Architecture — Host, Client, Server

MCP follows a client-server architecture with three roles.

flowchart LR
  subgraph HOST["MCP Host (e.g. Claude Desktop, IDE, your chatbot)"]
    LLM["LLM"]
    C1["MCP Client 1"]
    C2["MCP Client 2"]
    C3["MCP Client 3"]
  end
  C1 <-->|stdio| S1["Local server<br/>File system"]
  C2 <-->|stdio| S2["Local server<br/>SQLite"]
  C3 <-->|Streamable HTTP| S3["Remote server<br/>GitHub"]
  S1 --> D1[("Local files")]
  S2 --> D2[("Database")]
  S3 --> D3["GitHub API"]

1. Host

The AI application the user interacts with — Claude Desktop, Cursor, VS Code, or your own LangGraph chatbot. It contains the LLM, manages the UI, permissions and user consent, and creates the clients.

2. Client

A component inside the host that maintains a 1:1 connection with one server. It handles the protocol: discovering capabilities, sending requests, receiving responses. A host with 3 servers has 3 clients.

3. Server

A program that exposes capabilities (tools, resources, prompts) for one service — e.g. a GitHub server, a Postgres server, an expense-tracker server. It wraps the real API/DB.

4. Local vs Remote servers

Local serverRemote server
Runs whereOn the user's machine (as a subprocess of the host)On the internet / cloud
TransportstdioStreamable HTTP
Good forFiles, local DB, private toolsSaaS services, shared team tools
AuthUsually not neededOAuth / API keys

5. Example flow

sequenceDiagram
  participant U as User
  participant H as Host + LLM
  participant C as MCP Client
  participant S as GitHub MCP Server
  U->>H: Summarize my open PRs
  H->>C: LLM chooses tool list_pull_requests
  C->>S: tools/call list_pull_requests
  S->>S: call GitHub API
  S-->>C: result (PR list)
  C-->>H: tool result
  H-->>U: Summary of PRs
Key takeaway: Host = the app, Client = the connector (one per server), Server = the capability provider.

Server Primitives — Tools, Resources, Prompts

An MCP server can expose three kinds of things. They differ by who controls when they are used.

flowchart TB
  S["MCP Server"] --> T["Tools<br/>actions / functions<br/>model-controlled"]
  S --> R["Resources<br/>read-only data<br/>application-controlled"]
  S --> P["Prompts<br/>reusable templates<br/>user-controlled"]

1. Tools (model-controlled)

Functions the LLM can decide to call — they can do things and have side effects: create a GitHub issue, query a DB, send a message, add an expense.

  • Each tool has a name, description and JSON Schema for inputs.
  • Methods: tools/list (discover), tools/call (execute).
  • Optional annotations like read-only / destructive help hosts ask for confirmation.

2. Resources (application-controlled)

Data the server makes available for context, identified by a URI: file contents, DB schema, log files, API docs.

  • Like GET endpoints — read-only, no side effects.
  • Static (file:///project/README.md) or templated (expense://categories/{year}).
  • Methods: resources/list, resources/read; clients can subscribe to updates.
  • The host app decides which resources to attach (often user picks them).

3. Prompts (user-controlled)

Pre-written prompt templates the server offers, which the user explicitly chooses — often shown as slash commands (/summarize-pr, /code-review). They can take arguments and embed resources.

  • Methods: prompts/list, prompts/get.

4. Comparison

ToolsResourcesPrompts
Controlled byModel (LLM decides)ApplicationUser
PurposeTake actions / computeProvide context dataReusable workflows
Side effectsPossibleNoNo
Exampleadd_expense(amount, category)expense://categories"Monthly spending summary"
Key takeaway: Tools = verbs (do), Resources = nouns (read), Prompts = templates (ask). In practice most servers start with tools.

Protocol Internals — JSON-RPC, Lifecycle & Transports

MCP has two layers: the data layer (what messages mean) and the transport layer (how bytes travel).

1. Data layer: JSON-RPC 2.0

All MCP messages are JSON-RPC 2.0 — a simple, language-independent format. Three message types:

  • Request — has id, method, params; expects a response.
  • Response — same id, with result or error.
  • Notification — no id, no response expected (e.g. "tool list changed").
// request
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "add_expense", "arguments": {"amount": 250, "category": "food"}}}

// response
{"jsonrpc": "2.0", "id": 7,
 "result": {"content": [{"type": "text", "text": "Expense added with id 12"}], "isError": false}}

2. Connection lifecycle

sequenceDiagram
  participant C as Client
  participant S as Server
  Note over C,S: 1. Initialization
  C->>S: initialize (protocolVersion, capabilities, clientInfo)
  S-->>C: result (protocolVersion, capabilities, serverInfo)
  C->>S: notifications/initialized
  Note over C,S: 2. Operation
  C->>S: tools/list
  S-->>C: list of tools with schemas
  C->>S: tools/call
  S-->>C: result
  S--)C: notifications/tools/list_changed
  Note over C,S: 3. Shutdown
  C->>S: close connection / end process
  • Initialization — version negotiation + capability negotiation (server says "I support tools and resources"; client says "I support sampling, roots, elicitation").
  • Operation — discovery (*/list) and usage (tools/call, resources/read, prompts/get), plus notifications.
  • Shutdown — transport closes (stdio: close input and end process; HTTP: close connections).

Also supported: ping (health check), progress notifications for long tasks, cancellation, and logging.

3. Transport layer

stdioStreamable HTTP
HowHost launches the server as a subprocess; messages over stdin / stdoutServer runs as a web service; client sends HTTP POST, server can stream responses (SSE)
UseLocal serversRemote servers, many clients
NetworkNone — very fast, simpleNeeds auth, HTTPS
The older HTTP + SSE transport (two endpoints) is deprecated in favour of Streamable HTTP (single endpoint, optional streaming, session ids).
Key takeaway: Same JSON-RPC messages, two ways to carry them: stdio for local, Streamable HTTP for remote. Initialization negotiates what each side can do.

Build a Local MCP Server (FastMCP)

Project: an Expense Tracker MCP server backed by SQLite, then connect it to Claude Desktop so you can say "I spent ₹450 on groceries today".

flowchart LR
  U["User in Claude Desktop"] --> H["Host + LLM"]
  H <-->|stdio| S["expense-tracker server<br/>FastMCP, main.py"]
  S --> DB[("expenses.db<br/>SQLite")]
  S --> R["resource: expense://categories"]

1. Setup

# using uv (fast Python package manager)
uv init expense-tracker-mcp
cd expense-tracker-mcp
uv add fastmcp

2. Server code

from fastmcp import FastMCP
import sqlite3, os

DB_PATH = os.path.join(os.path.dirname(__file__), "expenses.db")
mcp = FastMCP("ExpenseTracker")

def init_db():
    with sqlite3.connect(DB_PATH) as c:
        c.execute("""CREATE TABLE IF NOT EXISTS expenses(
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            date TEXT NOT NULL, amount REAL NOT NULL,
            category TEXT NOT NULL, subcategory TEXT DEFAULT '', note TEXT DEFAULT '')""")
init_db()

@mcp.tool()
def add_expense(date: str, amount: float, category: str, subcategory: str = "", note: str = "") -> dict:
    """Add a new expense entry. date format: YYYY-MM-DD."""
    with sqlite3.connect(DB_PATH) as c:
        cur = c.execute("INSERT INTO expenses(date, amount, category, subcategory, note) VALUES (?,?,?,?,?)",
                        (date, amount, category, subcategory, note))
        return {"status": "ok", "id": cur.lastrowid}

@mcp.tool()
def list_expenses(start_date: str, end_date: str) -> list[dict]:
    """List expenses between two dates (inclusive)."""
    with sqlite3.connect(DB_PATH) as c:
        cur = c.execute("SELECT id, date, amount, category, subcategory, note FROM expenses "
                        "WHERE date BETWEEN ? AND ? ORDER BY date", (start_date, end_date))
        cols = [d[0] for d in cur.description]
        return [dict(zip(cols, r)) for r in cur.fetchall()]

@mcp.tool()
def summarize(start_date: str, end_date: str, category: str | None = None) -> list[dict]:
    """Total spend by category between two dates."""
    q = "SELECT category, SUM(amount) AS total FROM expenses WHERE date BETWEEN ? AND ?"
    params = [start_date, end_date]
    if category:
        q += " AND category = ?"; params.append(category)
    q += " GROUP BY category ORDER BY total DESC"
    with sqlite3.connect(DB_PATH) as c:
        return [{"category": r[0], "total": r[1]} for r in c.execute(q, params)]

@mcp.resource("expense://categories", mime_type="application/json")
def categories() -> str:
    """List of allowed categories and subcategories."""
    return open(os.path.join(os.path.dirname(__file__), "categories.json")).read()

if __name__ == "__main__":
    mcp.run()          # default transport = stdio

FastMCP reads the type hints to build the JSON Schema and the docstring as the tool description — write both carefully, the LLM only sees these.

3. Test with MCP Inspector

uv run fastmcp dev main.py      # opens the Inspector in the browser
# or: npx @modelcontextprotocol/inspector uv run main.py

The Inspector lets you connect, list tools/resources, call them with test inputs and see raw JSON-RPC messages.

4. Connect to Claude Desktop

uv run fastmcp install claude-desktop main.py

Or edit claude_desktop_config.json manually:

{
  "mcpServers": {
    "expense-tracker": {
      "command": "uv",
      "args": ["run", "--with", "fastmcp", "fastmcp", "run", "/full/path/to/main.py"]
    }
  }
}

Restart Claude Desktop; the tools appear in the tools menu. Try: "Add ₹450 for groceries today" → "How much did I spend on food this month?"

Common errors: wrong absolute path, uv not on PATH (use full path to uv), relative DB path (use __file__), printing to stdout in a stdio server (it corrupts the protocol — log to stderr).
Key takeaway: @mcp.tool() + type hints + docstring = a working tool. Inspector to test, config file to plug into a host.

Remote MCP Server & Deployment

A local server only works on your machine. A remote server runs on the internet so many users and apps can connect — over Streamable HTTP.

flowchart LR
  U1["Claude (custom connector)"] -->|HTTPS| GW["Remote MCP server<br/>https://my-expense.example.com/mcp"]
  U2["Your LangGraph app"] -->|HTTPS| GW
  U3["Cursor / VS Code"] -->|HTTPS| GW
  GW --> AUTH["Auth<br/>OAuth 2.1 / API key"]
  GW --> DB[("Cloud DB<br/>Postgres")]

1. Switch transport

if __name__ == "__main__":
    mcp.run(transport="http", host="0.0.0.0", port=8000)   # endpoint: /mcp

2. Async tools

A remote server handles many requests at once, so use async def tools and async DB drivers (aiosqlite, asyncpg) to avoid blocking.

import aiosqlite
@mcp.tool()
async def add_expense(date: str, amount: float, category: str) -> dict:
    """Add a new expense entry."""
    async with aiosqlite.connect(DB_PATH) as db:
        cur = await db.execute("INSERT INTO expenses(date, amount, category) VALUES (?,?,?)",
                               (date, amount, category))
        await db.commit()
        return {"status": "ok", "id": cur.lastrowid}

3. Deployment options

  • FastMCP Cloud — connect the GitHub repo, pick the entry file, get a public URL.
  • Any cloud — Docker container on Render, Railway, Fly.io, Cloud Run, EC2.
  • Use a real database (Postgres) — container file systems are often temporary.

4. Connecting clients

  • Claude — add the URL as a custom connector in settings.
  • Claude Desktop (if a client only supports stdio) — use a proxy like mcp-remote: "command": "npx", "args": ["mcp-remote", "https://…/mcp"].
  • Your code — see video 7.

5. Authentication & multi-user

  • MCP's auth spec is based on OAuth 2.1: the client gets a token from an authorization server and sends it as a Bearer token.
  • Simpler setups use an API key header.
  • For multi-user apps, store a user_id with every row and read it from the authenticated token — never trust a user id passed as a tool argument.
Key takeaway: Remote = transport="http" + async tools + persistent DB + auth + deploy. The tool code barely changes.

Build an MCP Client

Instead of Claude Desktop, build your own host: a chatbot that connects to any MCP servers and lets an LLM use their tools.

flowchart TB
  UI["Streamlit chat UI"] --> AG["LangGraph agent<br/>chat_node + ToolNode"]
  AG --> MC["MultiServerMCPClient"]
  MC -->|stdio| L1["math server (local)"]
  MC -->|Streamable HTTP| R1["expense server (remote)"]
  MC -->|Streamable HTTP| R2["any public MCP server"]
  AG --> LLM["Chat model with tools bound"]

1. Low-level: official Python SDK

import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="python", args=["math_server.py"])

async def main():
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()                        # handshake
            tools = await session.list_tools()
            print([t.name for t in tools.tools])
            result = await session.call_tool("add", {"a": 5, "b": 7})
            print(result.content[0].text)
asyncio.run(main())

This shows the protocol steps directly: connect → initialize → list → call. You'd still need to pass the tool schemas to the LLM and run the tool-calling loop yourself.

2. High-level: LangChain MCP adapters + LangGraph

from langchain_mcp_adapters.client import MultiServerMCPClient
from langgraph.graph import StateGraph, START, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI

SERVERS = {
    "math":    {"transport": "stdio", "command": "python", "args": ["math_server.py"]},
    "expense": {"transport": "streamable_http", "url": "https://my-expense.example.com/mcp"},
}

async def build_agent():
    client = MultiServerMCPClient(SERVERS)
    tools = await client.get_tools()            # MCP tools -> LangChain tools
    llm = ChatOpenAI(model="gpt-4o-mini").bind_tools(tools)

    async def chat_node(state: MessagesState):
        return {"messages": [await llm.ainvoke(state["messages"])]}

    g = StateGraph(MessagesState)
    g.add_node("chat_node", chat_node)
    g.add_node("tools", ToolNode(tools))
    g.add_edge(START, "chat_node")
    g.add_conditional_edges("chat_node", tools_condition)
    g.add_edge("tools", "chat_node")
    return g.compile()

# usage
agent = await build_agent()
out = await agent.ainvoke({"messages": [("user", "Add ₹300 for food today, then show this month's total")]})

3. The tool-calling loop

sequenceDiagram
  participant U as User
  participant A as Agent (LLM)
  participant M as MCP Client
  participant S as MCP Server
  U->>A: Add 300 for food
  A-->>M: tool_call add_expense(...)
  M->>S: tools/call
  S-->>M: result
  M-->>A: ToolMessage
  A-->>U: Done, expense added

4. Practical notes

  • MCP tools are async → use ainvoke/astream; in Streamlit run a background event loop.
  • Show tool activity in the UI ("Using add_expense…") for transparency.
  • Ask for user confirmation before destructive tools.
  • Too many tools confuse the model — connect only the servers you need.
Key takeaway: Your app becomes an MCP host: the client discovers tools from servers, the LLM decides, the client executes.

Advanced Features & Security

Beyond tools/resources/prompts, MCP lets servers ask things from the client. And because MCP gives an LLM real power, security needs careful thought.

1. Client primitives (server → client requests)

flowchart LR
  S["MCP Server"] -->|sampling/createMessage| C1["Sampling<br/>ask host's LLM to generate text"]
  S -->|elicitation/create| C2["Elicitation<br/>ask the user for input"]
  S -->|roots/list| C3["Roots<br/>which folders / URIs it may access"]
  • Sampling — the server asks the host's LLM for a completion (e.g. summarize data) without needing its own API key. The user/host can review and approve.
  • Elicitation — the server asks the user for missing information mid-task with a simple schema ("Which account: personal or business?").
  • Roots — the client tells the server which directories/URIs it is allowed to work in.

Other useful features: notifications (list changed, resource updated), progress updates, logging, cancellation, structured tool output.

2. Security risks

RiskWhat happens
Prompt injectionMalicious text in a document, email or web page (read via a tool) instructs the LLM to do something harmful.
Tool poisoningA malicious server hides instructions in tool descriptions that the LLM obeys.
Rug pullA server you trusted changes its tools later to behave maliciously.
Tool shadowingOne server's tool description manipulates how another server's tools are used.
Data exfiltrationCombining a private-data tool with an internet tool leaks data.
Over-broad permissions / token passthroughServer has more access than needed, or forwards user tokens unsafely.
Command injectionServer builds shell/SQL commands from unsanitized input.

3. Best practices

  • Install servers only from trusted sources; review code; pin versions.
  • Least privilege — scope tokens and file access (roots) tightly.
  • Human approval for destructive or sensitive tools.
  • Validate inputs; use parameterized SQL; never eval or run raw shell from arguments.
  • Use OAuth properly for remote servers; HTTPS only; validate the token audience.
  • Log and monitor tool calls; rate-limit.
  • Treat everything a tool returns as untrusted data, not instructions.

4. Ecosystem & where to go next

  • Official and community servers: file system, GitHub, Postgres, Slack, Google Drive, browser automation, and many more.
  • SDKs: Python, TypeScript, Java, C#, Go, and others.
  • Project ideas: a personal finance server (this course), a company-docs RAG server, a server wrapping your own web app's API (good fit for a React/Node developer).
Key takeaway: MCP = standard plug + powerful capabilities. Use client primitives for richer interactions, and design every server with least privilege and human approval in mind.
