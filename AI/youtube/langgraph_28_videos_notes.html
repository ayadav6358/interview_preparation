Generative AI vs Agentic AI

Generative AI creates content when asked. Agentic AI pursues a goal: it plans, takes actions with tools, checks results and adapts — with little human guidance.

1. Generative AI

Models that learn patterns from data and generate new text, images, audio or code (LLMs, diffusion models). Examples: ChatGPT answering a question, Midjourney making an image.

  • Reactive — waits for a prompt, gives one response.
  • No memory of goals, doesn't take actions on its own.

2. The evolution (example: an HR recruiter hiring a backend engineer)

flowchart LR
  G["Plain GenAI chatbot<br/>writes a JD when asked"] --> R["RAG chatbot<br/>uses company docs and past JDs"]
  R --> T["Tool-augmented chatbot<br/>can post jobs, read resumes, send mail<br/>but human drives each step"]
  T --> A["Agentic AI<br/>given the goal, it plans and runs<br/>the whole hiring process"]
  1. LLM chatbot — writes a job description, but generic and not company-specific.
  2. RAG chatbot — grounded in company data, but still only answers.
  3. Tool-augmented chatbot — can call LinkedIn / email / calendar APIs, but the recruiter must ask for every step.
  4. Agentic AI — the recruiter says "Hire a backend engineer" and the agent drafts the JD, posts it, monitors applications, shortlists, schedules interviews, and asks the human only for approvals.

3. Comparison

Generative AIAgentic AI
NatureReactiveProactive, goal-driven
OutputContentCompleted task / outcome
StepsSingle turnMulti-step plan + execution
Tools & memoryOptionalCore
RelationGenerative AI is a building block (the brain) of Agentic AI.
Key takeaway: GenAI answers; Agentic AI acts. An agent = LLM + planning + tools + memory + feedback loop.

What is Agentic AI — Characteristics

Agentic AI is software that takes a goal from a user and works towards it autonomously, planning, acting, adapting and asking for help only when needed.

mindmap
  root((Agentic AI))
    Autonomous
      decides next step
      controlled autonomy
    Goal oriented
      persistent goal
      constraints
    Planning
      break into sub-goals
      choose best plan
    Reasoning
      decisions
      tool selection
    Adaptability
      failures
      changing info
    Context aware
      short-term memory
      long-term memory

1. Autonomy

Makes decisions and executes steps without a human prompting every step. It can be autonomous in execution, decision making and tool usage.

Controlled autonomy: too much autonomy is risky (e.g. sending an offer letter with a wrong salary). Use permission scopes, human-in-the-loop checkpoints, override controls and guardrails.

2. Goal-oriented

A persistent objective guides every action. Goals can have constraints ("hire within ₹X budget, in 3 weeks") and are often stored in memory as structured data (goal, status, progress).

3. Planning

Break a high-level goal into a sequence of steps: generate candidate plans → evaluate them (efficiency, tools available, cost, risk) → select the best one.

4. Reasoning

Cognitive process for interpreting information and deciding: during planning (goal decomposition) and during execution (decision making, tool selection, error handling).

5. Adaptability

Modify plans when things change: a tool fails (job portal API down → use another), external feedback (few applications → widen the JD), or goal changes.

6. Context awareness

Understand and use relevant information: original goal, progress, environment state, tool responses, user preferences. Implemented through short-term memory (current session) and long-term memory (across sessions).

Key takeaway: Six traits — Autonomy, Goal, Planning, Reasoning, Adaptability, Context. Every LangGraph feature later maps to one of these.

Components of Agentic AI

An agentic system is built from five parts. LangGraph gives you a way to wire them together.

flowchart TB
  U["User goal"] --> B["Brain (LLM)<br/>goal interpretation, planning,<br/>reasoning, tool selection"]
  B <--> O["Orchestrator<br/>task sequencing, conditional routing,<br/>retries, loops"]
  O <--> T["Tools<br/>APIs, DBs, RAG, code exec"]
  O <--> M["Memory<br/>short-term + long-term"]
  S["Supervisor / Human<br/>approvals, guardrails, escalation"] --> O
  O --> R["Result"]

1. Brain (LLM)

Understands the goal, plans, reasons, chooses tools and generates responses.

2. Orchestrator

Executes the plan: sequencing steps, conditional routing, retries and loops, passing data between steps. LangGraph is the orchestrator.

3. Tools

Let the agent interact with the world: external APIs, knowledge bases (RAG), code execution, databases.

4. Memory

  • Short-term — the current session's messages and intermediate state.
  • Long-term — facts, preferences and history that persist across sessions.
  • Also: state tracking (what's done, what's pending).

5. Supervisor

Human-in-the-loop approvals, guardrails, edge-case handling and escalation.

Key takeaway: Brain decides, Orchestrator executes, Tools act, Memory remembers, Supervisor keeps it safe.

LangChain vs LangGraph — Why LangGraph?

LangChain is great for linear chains. LangGraph is an orchestration framework for stateful, multi-step, branching and looping LLM workflows, represented as a graph.

1. The use case: automated hiring workflow

Create JD → human approval → post job → wait → check applications → (if few, modify JD and repost — a loop) → shortlist → interview → (pass/fail branch) → offer letter.

2. Problems when building this with LangChain

ChallengeLangChainLangGraph
Control flow (branches, loops, jumps)Lots of glue Python code around chainsNative: conditional edges and cycles
State handlingManual dictionaries passed aroundShared typed State object
Event-driven / long waitsChains run start-to-end in one goPause and resume with checkpointers
Fault toleranceRestart from beginningResume from last checkpoint
Human-in-the-loopHard to pause for daysinterrupt() + resume
Nested workflowsMessySubgraphs
ObservabilityPartial (glue code not traced)Full graph traced in LangSmith
flowchart LR
  S((START)) --> JD["Create JD"] --> H{"Approved?"}
  H -->|no| JD
  H -->|yes| P["Post job"] --> W["Wait / monitor"] --> C{"Enough applicants?"}
  C -->|no| M["Modify JD"] --> P
  C -->|yes| SH["Shortlist"] --> I["Interview"] --> D{"Selected?"}
  D -->|yes| O["Send offer"] --> E((END))
  D -->|no| R["Reject mail"] --> E

3. When to use which

  • LangChain — simple linear pipelines: prompt → LLM → parser, basic RAG.
  • LangGraph — agents, multi-step workflows with branching/loops, long-running or human-approved processes. LangGraph is built on top of LangChain components (models, tools, retrievers still come from LangChain).
Key takeaway: LangChain = building blocks. LangGraph = the flowchart engine that connects them with state, loops and checkpoints.

LangGraph Core Concepts

Every LangGraph app is a graph: nodes (work), edges (flow), and a shared state that every node can read and update.

flowchart LR
  S((START)) --> N1["Node A<br/>function(state) returns update"]
  N1 --> N2["Node B"]
  N1 --> N3["Node C"]
  N2 --> N4["Node D"]
  N3 --> N4
  N4 --> E((END))
  ST[("Shared State<br/>TypedDict / Pydantic")] -. read and update .-> N1
  ST -.-> N2
  ST -.-> N3
  ST -.-> N4

1. Graph, Nodes, Edges

  • Node — a Python function: takes the state, returns a partial update (dict of changed keys). Can call an LLM, a tool, or plain logic.
  • Edge — decides which node runs next. Types: normal (fixed), conditional (router function), parallel (fan-out), and loops (edge back to an earlier node).
  • START / END — special entry and exit points.

2. State

A shared, mutable memory that flows through the graph — like a shared whiteboard. Defined with TypedDict (or Pydantic).

from typing import TypedDict
class HiringState(TypedDict):
    job_description: str
    approved: bool
    applicants: list[str]
    shortlisted: list[str]

3. Reducers

A reducer defines how an update is merged into the state for a key. Default = replace. With a reducer you can append/merge instead — essential for chat history and parallel branches.

from typing import Annotated
import operator
class State(TypedDict):
    messages: Annotated[list, operator.add]   # append instead of overwrite

4. Execution model (Pregel-inspired)

  1. Graph definition — declare state, nodes, edges.
  2. Compilation — graph.compile() checks structure (no orphan nodes etc.).
  3. Execution — runs in super-steps: nodes that are triggered run (in parallel if several), send updates, reducers merge them, then the next set of nodes is activated. Ends when no node is active.
Key takeaway: State = data, Nodes = what to do, Edges = when to do it, Reducers = how updates merge.

LLM Workflow Patterns

A workflow is a series of tasks executed in order to reach a goal. These five common LLM workflow patterns are the building blocks of agentic systems — and each maps directly to LangGraph features.

1. Prompt chaining

Call the LLM several times in sequence; each output feeds the next (topic → outline → blog). Optional "gate" checks in between.

flowchart LR
  I["Topic"] --> L1["LLM: outline"] --> G{"Gate check"} --> L2["LLM: blog"] --> O["Output"]

2. Routing

An LLM classifies the input and sends it to the right specialized handler (refund query → refund flow, technical query → tech flow).

flowchart LR
  Q["Query"] --> R{"LLM router"}
  R --> A["Refund handler"]
  R --> B["Tech support handler"]
  R --> C["Sales handler"]

3. Parallelization

Split a task into independent subtasks that run at the same time, then aggregate (e.g. check a YouTube video for community guidelines, misinformation and sexual content in parallel).

4. Orchestrator–Workers

Like parallelization, but the subtasks are not known in advance — an orchestrator LLM decides them at runtime and spawns workers (e.g. a research assistant deciding which sources to search). In LangGraph this uses the Send API.

flowchart LR
  Q["Task"] --> O["Orchestrator LLM<br/>plans subtasks"]
  O --> W1["Worker 1"]
  O --> W2["Worker 2"]
  O --> W3["Worker N"]
  W1 --> S["Synthesizer"]
  W2 --> S
  W3 --> S

5. Evaluator–Optimizer

One LLM generates, another evaluates and gives feedback; loop until accepted (e.g. writing an email or a tweet).

flowchart LR
  G["Generator LLM"] --> E{"Evaluator LLM<br/>approved?"}
  E -->|no + feedback| G
  E -->|yes| O["Final output"]
Key takeaway: Chaining = sequential edges, Routing = conditional edges, Parallel = fan-out edges, Orchestrator = Send API, Evaluator = loop.

Sequential Workflows

The simplest graph: nodes run one after another. The video builds three examples of increasing complexity.

1. Non-LLM example: BMI calculator

from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class BMIState(TypedDict):
    weight_kg: float
    height_m: float
    bmi: float
    category: str

def calculate_bmi(state: BMIState) -> BMIState:
    bmi = state["weight_kg"] / (state["height_m"] ** 2)
    return {"bmi": round(bmi, 2)}          # partial update

def label_bmi(state: BMIState) -> BMIState:
    b = state["bmi"]
    cat = "Underweight" if b < 18.5 else "Normal" if b < 25 else "Overweight" if b < 30 else "Obese"
    return {"category": cat}

graph = StateGraph(BMIState)
graph.add_node("calculate_bmi", calculate_bmi)
graph.add_node("label_bmi", label_bmi)
graph.add_edge(START, "calculate_bmi")
graph.add_edge("calculate_bmi", "label_bmi")
graph.add_edge("label_bmi", END)

workflow = graph.compile()
print(workflow.invoke({"weight_kg": 80, "height_m": 1.73}))
flowchart LR
  S((START)) --> A["calculate_bmi"] --> B["label_bmi"] --> E((END))

2. Simple LLM workflow: Q&A

from langchain_openai import ChatOpenAI
model = ChatOpenAI(model="gpt-4o-mini")

class LLMState(TypedDict):
    question: str
    answer: str

def llm_qa(state: LLMState):
    return {"answer": model.invoke(f"Answer: {state['question']}").content}

3. Prompt chaining: Blog generator

State: title, outline, content (+ optionally evaluation). Node 1 creates an outline, node 2 writes the blog from title + outline, node 3 rates it.

flowchart LR
  S((START)) --> O["create_outline"] --> B["create_blog"] --> R["evaluate_blog"] --> E((END))

4. Visualizing the graph

from IPython.display import Image
Image(workflow.get_graph().draw_mermaid_png())
Key takeaway: Steps: define State → write node functions → add nodes & edges → compile → invoke with initial state. Nodes return only the keys they change.

Parallel Workflows & Reducers

Fan-out to several nodes that run in the same super-step, then fan-in to a node that combines their results.

1. Non-LLM example: Cricket batsman stats

From runs, balls, 4s, 6s compute strike rate, balls per boundary and boundary % in parallel, then build a summary.

class BatsmanState(TypedDict):
    runs: int; balls: int; fours: int; sixes: int
    sr: float; bpb: float; boundary_percent: float
    summary: str

def calculate_sr(state):  return {"sr": state["runs"] / state["balls"] * 100}
def calculate_bpb(state): return {"bpb": state["balls"] / (state["fours"] + state["sixes"])}
def calculate_boundary_percent(state):
    return {"boundary_percent": (state["fours"]*4 + state["sixes"]*6) / state["runs"] * 100}

g = StateGraph(BatsmanState)
for n, f in [("sr", calculate_sr), ("bpb", calculate_bpb), ("bp", calculate_boundary_percent), ("summary", summary)]:
    g.add_node(n, f)
for n in ["sr", "bpb", "bp"]:
    g.add_edge(START, n)
    g.add_edge(n, "summary")
g.add_edge("summary", END)
flowchart LR
  S((START)) --> A["strike rate"]
  S --> B["balls per boundary"]
  S --> C["boundary %"]
  A --> D["summary"]
  B --> D
  C --> D
  D --> E((END))
Common error: if parallel nodes return the whole state, LangGraph raises InvalidUpdateError (multiple values for the same key in one step). Always return only the keys you update.

2. LLM example: UPSC essay evaluator

Three parallel evaluators check language, depth of analysis and clarity of thought, each returning feedback + score (via structured output). A final node averages the scores and writes overall feedback.

from pydantic import BaseModel, Field
class EvaluationSchema(BaseModel):
    feedback: str = Field(description="Detailed feedback")
    score: int = Field(description="Score out of 10", ge=0, le=10)
structured_model = model.with_structured_output(EvaluationSchema)

class UPSCState(TypedDict):
    essay: str
    language_feedback: str
    analysis_feedback: str
    clarity_feedback: str
    overall_feedback: str
    individual_scores: Annotated[list[int], operator.add]   # reducer!
    avg_score: float

def evaluate_language(state):
    out = structured_model.invoke(f"Evaluate the language quality:\n{state['essay']}")
    return {"language_feedback": out.feedback, "individual_scores": [out.score]}

3. Why the reducer matters

All three branches write to individual_scores in the same super-step. With Annotated[list, operator.add], the lists are concatenated → [7, 8, 6]. Without it, LangGraph doesn't know how to merge and raises an error.

Key takeaway: Parallel = multiple edges from one node. Fan-in node waits for all. Shared keys written in parallel need a reducer.

Conditional Workflows

Route to different nodes based on the current state using add_conditional_edges and a router function.

1. Non-LLM example: Quadratic equation solver

Compute discriminant D = b² − 4ac; then branch: D > 0 → two real roots, D = 0 → repeated root, D < 0 → no real roots.

from typing import Literal
def check_condition(state) -> Literal["real_roots", "repeated_root", "no_real_roots"]:
    d = state["discriminant"]
    if d > 0:  return "real_roots"
    if d == 0: return "repeated_root"
    return "no_real_roots"

g.add_edge(START, "show_equation")
g.add_edge("show_equation", "calculate_discriminant")
g.add_conditional_edges("calculate_discriminant", check_condition)
for n in ["real_roots", "repeated_root", "no_real_roots"]:
    g.add_edge(n, END)
flowchart LR
  S((START)) --> A["show_equation"] --> B["calculate_discriminant"] --> C{"check_condition"}
  C -->|D gt 0| R1["real_roots"]
  C -->|D eq 0| R2["repeated_root"]
  C -->|D lt 0| R3["no_real_roots"]
  R1 --> E((END))
  R2 --> E
  R3 --> E

2. LLM example: Customer review reply system

  1. find_sentiment — structured output: Literal["positive","negative"].
  2. If positive → positive_response: thank-you message.
  3. If negative → run_diagnosis: structured output with issue_type (UX/Performance/Bug/Support), tone (angry/frustrated/calm), urgency (low/medium/high) → negative_response: empathetic reply that uses the diagnosis.
flowchart LR
  S((START)) --> F["find_sentiment"] --> C{"sentiment?"}
  C -->|positive| P["positive_response"] --> E((END))
  C -->|negative| D["run_diagnosis"] --> N["negative_response"] --> E

Optional third argument maps router output to node names: add_conditional_edges("x", fn, {"yes": "a", "no": "b"}).

Key takeaway: The router function reads state and returns the name of the next node. Use structured output so the LLM's decision is reliable.

Iterative Workflows (Loops)

Graphs can have cycles. This implements the evaluator–optimizer pattern: generate → evaluate → improve → evaluate… until approved or a max iteration limit.

Project: X (Twitter) post generator

  • generate — LLM writes a funny, original tweet on a topic.
  • evaluate — a second LLM (strict critic) returns evaluation: "approved" | "needs_improvement" + feedback (structured output).
  • optimize — rewrites the tweet using the feedback, increments iteration.
  • Loop back to evaluate until approved or iteration >= max_iteration.
class TweetState(TypedDict):
    topic: str
    tweet: str
    evaluation: Literal["approved", "needs_improvement"]
    feedback: str
    iteration: int
    max_iteration: int
    tweet_history: Annotated[list[str], operator.add]
    feedback_history: Annotated[list[str], operator.add]

def route_evaluation(state):
    if state["evaluation"] == "approved" or state["iteration"] >= state["max_iteration"]:
        return "approved"
    return "needs_improvement"

g.add_edge(START, "generate")
g.add_edge("generate", "evaluate")
g.add_conditional_edges("evaluate", route_evaluation,
                        {"approved": END, "needs_improvement": "optimize"})
g.add_edge("optimize", "evaluate")      # the loop

workflow.invoke({"topic": "Indian Railways", "iteration": 1, "max_iteration": 5})
flowchart LR
  S((START)) --> G["generate"] --> EV{"evaluate"}
  EV -->|approved or max iter| E((END))
  EV -->|needs_improvement| O["optimize"]
  O --> EV
Always add a stop condition. Without max_iteration the loop could run forever (LangGraph also has a default recursion_limit of 25 steps).
Tip: Use different models (or temperatures) for generator and evaluator, and history lists with reducers to inspect how the output improved.

Building a Chatbot in LangGraph

The simplest chatbot is a one-node graph whose state is a list of messages.

1. State with add_messages

from langgraph.graph.message import add_messages
from langchain_core.messages import BaseMessage, HumanMessage

class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

add_messages is a reducer specialised for messages: it appends new ones, and updates a message if the same ID comes again. (MessagesState is a ready-made class with exactly this.)

2. Graph

llm = ChatOpenAI()
def chat_node(state: ChatState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

g = StateGraph(ChatState)
g.add_node("chat_node", chat_node)
g.add_edge(START, "chat_node")
g.add_edge("chat_node", END)
chatbot = g.compile()
flowchart LR
  S((START)) --> C["chat_node<br/>llm.invoke(messages)"] --> E((END))

3. The memory problem

while True:
    user = input("You: ")
    if user in ("exit", "quit", "bye"): break
    out = chatbot.invoke({"messages": [HumanMessage(content=user)]})
    print("AI:", out["messages"][-1].content)
Each invoke starts with a fresh state, so "My name is Amit" → "What's my name?" fails. The state is erased after the graph ends. Solution: persistence (next video).
Key takeaway: Chatbot = MessagesState + one LLM node. Memory across turns needs a checkpointer.

Persistence & Checkpointers

Persistence = saving the graph's state so it can be restored later. LangGraph saves a checkpoint at every super-step.

flowchart LR
  subgraph T1["thread_id = 1"]
    C0["checkpoint 0<br/>input"] --> C1["checkpoint 1<br/>after node A"] --> C2["checkpoint 2<br/>after node B"]
  end
  subgraph T2["thread_id = 2"]
    D0["checkpoint 0"] --> D1["checkpoint 1"]
  end
  CP[("Checkpointer<br/>InMemorySaver / SqliteSaver / Postgres")] --- T1
  CP --- T2

1. Checkpointer + threads

from langgraph.checkpoint.memory import InMemorySaver
checkpointer = InMemorySaver()
chatbot = g.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "1"}}
chatbot.invoke({"messages": [HumanMessage("Hi, my name is Amit")]}, config=config)
chatbot.invoke({"messages": [HumanMessage("What is my name?")]}, config=config)  # remembers!

A thread = one conversation / one run history. Different thread_id = separate memory.

2. Inspecting state

chatbot.get_state(config)                 # latest snapshot: values, next, config
list(chatbot.get_state_history(config))   # all checkpoints, newest first

3. Benefits of persistence

  • Short-term memory — chat history across turns.
  • Fault tolerance — if a node crashes, re-invoke with None input and same thread to resume from the last checkpoint.
  • Human-in-the-loop — pause indefinitely and resume.
  • Time travel — replay or fork from any old checkpoint (checkpoint_id), or edit state with update_state.
# resume after a crash
chatbot.invoke(None, config)
# time travel: replay from an older checkpoint
old = {"configurable": {"thread_id": "1", "checkpoint_id": "1ef..."}}
chatbot.invoke(None, old)
# edit the past and fork
chatbot.update_state(old, {"topic": "samosa"})
Key takeaway: compile(checkpointer=...) + thread_id unlocks memory, fault tolerance, HITL and time travel.

Streamlit UI for the Chatbot

Separate the project into a backend (the LangGraph chatbot) and a frontend (Streamlit chat UI).

flowchart LR
  U["User"] --> FE["Streamlit frontend<br/>st.chat_input, st.chat_message"]
  FE -->|invoke with thread_id| BE["LangGraph backend<br/>chatbot = graph.compile(checkpointer)"]
  BE --> LLM["LLM"]
  BE --> FE
  FE --> SS[("st.session_state<br/>message_history")]

1. Backend file

langgraph_backend.py exports the compiled chatbot with an InMemorySaver.

2. Frontend

import streamlit as st
from langgraph_backend import chatbot
from langchain_core.messages import HumanMessage

CONFIG = {"configurable": {"thread_id": "thread-1"}}
if "message_history" not in st.session_state:
    st.session_state["message_history"] = []

for m in st.session_state["message_history"]:          # re-draw old messages
    with st.chat_message(m["role"]):
        st.text(m["content"])

user_input = st.chat_input("Type here")
if user_input:
    st.session_state["message_history"].append({"role": "user", "content": user_input})
    with st.chat_message("user"): st.text(user_input)
    resp = chatbot.invoke({"messages": [HumanMessage(user_input)]}, config=CONFIG)
    ai = resp["messages"][-1].content
    st.session_state["message_history"].append({"role": "assistant", "content": ai})
    with st.chat_message("assistant"): st.text(ai)
Streamlit re-runs the whole script on every interaction — that's why messages are stored in st.session_state and re-drawn.
Key takeaway: Backend owns memory (checkpointer); frontend only displays and sends messages with a thread_id.

Streaming

Show the response token-by-token as the LLM generates it, instead of waiting for the full answer — like ChatGPT's typing effect.

1. Why stream?

  • Faster perceived response (low time-to-first-token).
  • Better UX for long answers; user can stop early.
  • Shows progress in multi-step agents (which node is running, which tool was called).

2. Stream modes

stream_modeWhat you get
"values"Full state after each step
"updates"Only what each node changed
"messages"LLM tokens as (message_chunk, metadata) — for chat UIs
"custom"Your own events from inside nodes
for chunk, meta in chatbot.stream(
        {"messages": [HumanMessage("Write a recipe for pasta")]},
        config=CONFIG, stream_mode="messages"):
    if chunk.content:
        print(chunk.content, end="", flush=True)

3. Streaming in Streamlit

with st.chat_message("assistant"):
    ai_message = st.write_stream(
        chunk.content for chunk, meta in chatbot.stream(
            {"messages": [HumanMessage(user_input)]}, config=CONFIG, stream_mode="messages")
    )
st.session_state["message_history"].append({"role": "assistant", "content": ai_message})

Database Persistence (SQLite)

InMemorySaver loses everything when the app restarts. Use a database-backed checkpointer for real persistence.

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("chatbot.db", check_same_thread=False)  # Streamlit uses multiple threads
checkpointer = SqliteSaver(conn=conn)
chatbot = g.compile(checkpointer=checkpointer)

def retrieve_all_threads():
    threads = set()
    for cp in checkpointer.list(None):
        threads.add(cp.config["configurable"]["thread_id"])
    return list(threads)

Tools in LangGraph

Give the chatbot tools (search, calculator, stock price API). The LLM decides when to call them; a ToolNode executes them; the graph loops back to the LLM.

from langgraph.prebuilt import ToolNode, tools_condition
from langchain_community.tools import DuckDuckGoSearchRun
from langchain_core.tools import tool
import requests

search_tool = DuckDuckGoSearchRun(region="us-en")

@tool
def calculator(first_num: float, second_num: float, operation: str) -> dict:
    """Perform add, sub, mul, div on two numbers."""
    ops = {"add": first_num + second_num, "sub": first_num - second_num,
           "mul": first_num * second_num,
           "div": first_num / second_num if second_num else "division by zero"}
    return {"result": ops.get(operation, "unsupported operation")}

@tool
def get_stock_price(symbol: str) -> dict:
    """Fetch latest stock price for a symbol (e.g. AAPL) using Alpha Vantage."""
    url = f"https://www.alphavantage.co/query?function=GLOBAL_QUOTE&symbol={symbol}&apikey=KEY"
    return requests.get(url).json()

tools = [search_tool, calculator, get_stock_price]
llm_with_tools = llm.bind_tools(tools)

def chat_node(state: ChatState):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

g = StateGraph(ChatState)
g.add_node("chat_node", chat_node)
g.add_node("tools", ToolNode(tools))
g.add_edge(START, "chat_node")
g.add_conditional_edges("chat_node", tools_condition)   # tool_calls? -> "tools" else END
g.add_edge("tools", "chat_node")                        # loop back
chatbot = g.compile(checkpointer=checkpointer)
flowchart LR
  S((START)) --> C["chat_node<br/>LLM with tools"]
  C --> D{"tools_condition<br/>has tool_calls?"}
  D -->|yes| T["ToolNode<br/>runs tools, returns ToolMessages"]
  T --> C
  D -->|no| E((END))

This loop is the ReAct agent pattern. The prebuilt shortcut is create_react_agent(model, tools).

Showing tool use in the UI

While streaming, check isinstance(chunk, ToolMessage) and show a status like "🔧 Using calculator…" with st.status; only display AIMessage chunks as text.

Key takeaway: bind_tools + ToolNode + tools_condition + edge back = a working agent in ~10 lines.

MCP Integration

MCP (Model Context Protocol) is an open standard to expose tools to any AI app. Instead of writing every tool yourself, connect to MCP servers (local or remote) and LangGraph gets their tools automatically.

1. Why MCP?

  • Without MCP: every app writes its own integration for GitHub, Drive, DBs… (M apps × N tools).
  • With MCP: a tool provider writes one server; any MCP client can use it (M + N).
flowchart LR
  subgraph Client["Your LangGraph app (MCP client)"]
    G["Graph"] --> MC["MultiServerMCPClient"]
  end
  MC -->|stdio| S1["Local server<br/>math / expense tracker"]
  MC -->|streamable http| S2["Remote server<br/>e.g. GitHub, Notion"]
  S1 --> T1["tools"]
  S2 --> T2["tools"]

2. Code

import asyncio
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "arith": {"command": "python", "args": ["math_server.py"], "transport": "stdio"},
    "expense": {"url": "https://example.com/mcp", "transport": "streamable_http"},
})

async def build_graph():
    tools = await client.get_tools()          # MCP tools become LangChain tools
    llm_with_tools = llm.bind_tools(tools)

    async def chat_node(state: ChatState):
        return {"messages": [await llm_with_tools.ainvoke(state["messages"])]}

    g = StateGraph(ChatState)
    g.add_node("chat_node", chat_node)
    g.add_node("tools", ToolNode(tools))
    g.add_edge(START, "chat_node")
    g.add_conditional_edges("chat_node", tools_condition)
    g.add_edge("tools", "chat_node")
    return g.compile()

async def main():
    chatbot = await build_graph()
    out = await chatbot.ainvoke({"messages": [HumanMessage("Add 45 and 23")]})
    print(out["messages"][-1].content)
asyncio.run(main())
Async: MCP tools are async, so use ainvoke/astream and async checkpointers (AsyncSqliteSaver). In Streamlit, run a background event loop and submit coroutines to it.
Key takeaway: MCP turns "write a tool" into "connect a server". The graph shape stays the same as video 18.

Agentic RAG with LangGraph

Instead of always retrieving, the agent decides when to retrieve, checks if the documents are relevant, and can rewrite the question and retry.

1. RAG as a tool (simple version)

loader = PyPDFLoader("intro-to-ml.pdf"); docs = loader.load()
chunks = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200).split_documents(docs)
retriever = FAISS.from_documents(chunks, OpenAIEmbeddings()).as_retriever(search_kwargs={"k": 4})

@tool
def rag_tool(query: str) -> dict:
    """Retrieve relevant information from the PDF document for the query."""
    result = retriever.invoke(query)
    return {"query": query, "context": [d.page_content for d in result],
            "metadata": [d.metadata for d in result]}

tools = [rag_tool, search_tool, calculator]   # the agent chooses

2. Full agentic RAG (with grading & rewriting)

flowchart LR
  S((START)) --> A["agent<br/>decide: retrieve or answer"]
  A -->|tool call| R["retrieve"]
  A -->|no tool| E((END))
  R --> G{"grade_documents<br/>relevant?"}
  G -->|yes| GEN["generate answer"] --> E
  G -->|no| RW["rewrite question"] --> A
  • agent — LLM with the retriever tool bound; small talk is answered directly.
  • grade_documents — structured output binary_score: "yes"/"no" for relevance.
  • rewrite — LLM improves the query (clearer, better keywords), then tries again.
  • generate — answer using only the relevant context.

3. Per-thread documents (chat with your PDF UI)

Store a separate retriever per thread_id (dict in backend), upload a PDF from the Streamlit sidebar, and pass thread_id into the tool so each chat only searches its own document.

Key takeaway: Classic RAG = fixed pipeline. Agentic RAG = graph with decisions: retrieve? relevant? rewrite?

Human-in-the-Loop (HITL)

Pause the graph, ask a human to approve / edit / provide input, then resume exactly where it stopped. Needs a checkpointer.

1. Why HITL?

  • High-stakes actions: buying stocks, sending emails, payments, deleting data.
  • Ambiguity: the agent needs clarification.
  • Quality review: approve a draft before publishing.

2. interrupt() and Command(resume=...)

from langgraph.types import interrupt, Command

@tool
def purchase_stock(symbol: str, quantity: int) -> dict:
    """Purchase given quantity of stock for the symbol."""
    decision = interrupt(f"Approve buying {quantity} shares of {symbol}? (yes/no)")
    if isinstance(decision, str) and decision.lower() == "yes":
        return {"status": "success", "message": f"Bought {quantity} {symbol}"}
    return {"status": "cancelled", "message": "Purchase declined by human"}

# run
config = {"configurable": {"thread_id": "t1"}}
result = chatbot.invoke({"messages": [HumanMessage("Buy 10 shares of AAPL")]}, config)
if "__interrupt__" in result:
    question = result["__interrupt__"][0].value
    answer = input(question)
    result = chatbot.invoke(Command(resume=answer), config)   # continues from the pause
sequenceDiagram
  participant U as Human
  participant G as Graph
  participant CP as Checkpointer
  U->>G: Buy 10 AAPL
  G->>G: chat_node -> tool call purchase_stock
  G->>CP: save state
  G-->>U: __interrupt__ Approve?
  Note over U: can take minutes or days
  U->>G: Command(resume="yes")
  CP->>G: restore state
  G->>G: node re-runs, interrupt returns "yes"
  G-->>U: Bought 10 AAPL
Important: on resume, the node runs again from its start; interrupt() then returns the resume value. Keep side-effects after the interrupt, not before.

3. Common HITL patterns

  • Approve / reject an action.
  • Edit state — human corrects a draft, resume with the edited value.
  • Review tool calls — edit tool arguments before execution.
  • Validate input — ask again until valid.
Key takeaway: interrupt() pauses, the checkpointer remembers, Command(resume=...) continues.

Subgraphs

A subgraph is a compiled graph used as a node inside another graph — for modularity, reuse, and building multi-agent systems.

1. Why subgraphs?

  • Break big workflows into smaller, testable modules.
  • Reuse one graph (e.g. a "translator" or "research" agent) in many parent graphs.
  • Different teams can own different subgraphs.

2. Case A — Shared state keys: add the subgraph directly as a node

class ParentState(TypedDict):
    question: str
    answer_eng: str
    answer_hin: str

class SubState(TypedDict):        # shares answer_eng / answer_hin keys
    answer_eng: str
    answer_hin: str

def translate(state: SubState):
    return {"answer_hin": llm.invoke(f"Translate to Hindi:\n{state['answer_eng']}").content}

sub = StateGraph(SubState)
sub.add_node("translate", translate)
sub.add_edge(START, "translate"); sub.add_edge("translate", END)
translator = sub.compile()

parent = StateGraph(ParentState)
parent.add_node("answer", answer_node)
parent.add_node("translator", translator)     # compiled graph as a node
parent.add_edge(START, "answer"); parent.add_edge("answer", "translator"); parent.add_edge("translator", END)

3. Case B — Different state: call the subgraph inside a node function

class SubState(TypedDict):
    input_text: str
    translated_text: str

def translate_node(state: ParentState):
    out = translator.invoke({"input_text": state["answer_eng"]})   # map in
    return {"answer_hin": out["translated_text"]}                   # map out
flowchart LR
  S((START)) --> A["answer (English)"] --> SG
  subgraph SG["translator subgraph"]
    T1((start)) --> T["translate"] --> T2((end))
  end
  SG --> E((END))
Key takeaway: Same keys → add compiled subgraph as a node. Different schema → wrap it in a function that maps state in and out.

Short-term Memory Management

Short-term memory = the message history in a thread (via checkpointer). Long chats grow too large for the context window and cost more — so we manage it.

1. Problems with long history

  • Exceeds the model's context window.
  • Higher latency and token cost.
  • Model gets distracted by old, irrelevant messages.

2. Techniques

flowchart TB
  M["Long message history"] --> T["Trim<br/>keep last N tokens / messages"]
  M --> D["Delete<br/>RemoveMessage by id"]
  M --> S["Summarize<br/>replace old messages with a summary"]

a) Trimming (only what is sent to the LLM)

from langchain_core.messages.utils import trim_messages, count_tokens_approximately
def chat_node(state):
    msgs = trim_messages(state["messages"], strategy="last",
                         token_counter=count_tokens_approximately, max_tokens=150)
    return {"messages": [llm.invoke(msgs)]}

b) Deleting from state

from langchain_core.messages import RemoveMessage
def delete_old(state):
    if len(state["messages"]) > 6:
        return {"messages": [RemoveMessage(id=m.id) for m in state["messages"][:-6]]}
    return {}

c) Summarization

class ChatState(MessagesState):
    summary: str

def summarize(state):
    prompt = f"Existing summary: {state.get('summary','')}\nExtend it with the new messages above."
    resp = llm.invoke(state["messages"] + [HumanMessage(prompt)])
    return {"summary": resp.content,
            "messages": [RemoveMessage(id=m.id) for m in state["messages"][:-2]]}

def should_summarize(state):
    return "summarize" if len(state["messages"]) > 6 else END
flowchart LR
  S((START)) --> C["chat_node<br/>system: summary + recent msgs"] --> D{"more than 6 messages?"}
  D -->|yes| SU["summarize + delete old"] --> E((END))
  D -->|no| E
Key takeaway: Trim what you send, delete what you don't need, summarize what you want to keep compactly.

Long-term Memory (Store)

Checkpointers remember within a thread. A Store remembers across all threads — user name, preferences, past facts — like ChatGPT's memory feature.

flowchart TB
  subgraph ST["Short-term (checkpointer)"]
    T1["thread 1 messages"]
    T2["thread 2 messages"]
  end
  subgraph LT["Long-term (Store)"]
    N["namespace: (user_id, 'memories')<br/>key: uuid, value: fact"]
  end
  T1 -->|extract facts| LT
  LT -->|retrieve relevant facts| T2

1. Types of long-term memory

  • Semantic — facts about the user ("works in React, lives in Noida").
  • Episodic — past experiences / interactions (few-shot examples of what worked).
  • Procedural — rules/instructions the agent learns (updated system prompt).

2. Store API

Multi-Agent Systems

One agent with too many tools and responsibilities gets confused. Split into specialised agents that collaborate.

1. Why multi-agent?

  • Specialization — each agent has a focused prompt and few tools.
  • Modularity — develop, test and improve agents separately.
  • Control — explicit communication between agents.

2. Architectures

flowchart TB
  subgraph SUP["Supervisor"]
    S["Supervisor LLM"] --> A1["Research agent"]
    S --> A2["Math agent"]
    S --> A3["Writer agent"]
    A1 --> S
    A2 --> S
    A3 --> S
  end
  subgraph NET["Network"]
    B1["Agent A"] <--> B2["Agent B"]
    B2 <--> B3["Agent C"]
    B1 <--> B3
  end
  • Network — any agent can hand off to any other.
  • Supervisor — a central agent decides who works next (most common).
  • Hierarchical — supervisors of supervisors (teams), built with subgraphs.
  • Custom workflow — fixed edges between agents.

3. Supervisor with Command (handoffs)

from langgraph.prebuilt import create_react_agent
from langgraph.types import Command

research_agent = create_react_agent(llm, [search_tool], prompt="You are a researcher.")
math_agent     = create_react_agent(llm, [calculator],  prompt="You are a math expert.")

class Router(BaseModel):
    next: Literal["researcher", "math", "FINISH"]

def supervisor(state: MessagesState) -> Command[Literal["researcher", "math", "__end__"]]:
    decision = llm.with_structured_output(Router).invoke(
        [SystemMessage("Decide which worker acts next, or FINISH.")] + state["messages"])
    return Command(goto=END if decision.next == "FINISH" else decision.next)

def researcher(state) -> Command[Literal["supervisor"]]:
    out = research_agent.invoke(state)
    return Command(update={"messages": [AIMessage(out["messages"][-1].content, name="researcher")]},
                   goto="supervisor")

Command(update=..., goto=...) lets a node update state and choose the next node in one return — no separate conditional edge needed.

Key takeaway: Supervisor pattern = router LLM + worker agents (often subgraphs) + Command handoffs.

Fault Tolerance, Retries & Time Travel

Long-running agents will hit API errors, timeouts and crashes. LangGraph's checkpoints make recovery cheap.

1. Resume after failure

If node 3 of 5 crashes, nodes 1–2's results are already checkpointed. Fix the issue and call graph.invoke(None, config) — execution resumes from the failed node, not from the beginning. (Successful writes from other parallel nodes in the same step are also kept — "pending writes".)

flowchart LR
  S((START)) --> A["step 1 ✓"] --> B["step 2 ✓"] --> C["step 3 ✗ crash"]
  C -.->|"invoke(None, same thread)"| C2["step 3 retried"] --> D["step 4"] --> E((END))

2. Automatic retries

from langgraph.types import RetryPolicy
g.add_node("call_api", call_api,
           retry_policy=RetryPolicy(max_attempts=3, initial_interval=1.0, backoff_factor=2.0))

3. Time travel

  • Replay — re-run from a past checkpoint (debug a decision).
  • Fork — update_state on an old checkpoint to change a value, then continue on a new branch ("what if the topic was different?").
history = list(graph.get_state_history(config))
target = history[2].config                          # an older checkpoint
new_cfg = graph.update_state(target, {"topic": "pizza"})
graph.invoke(None, new_cfg)                          # alternate timeline

4. Durability modes

Control how often checkpoints are written: "exit" (fastest, only at end), "async" (default balance), "sync" (safest).

Key takeaway: Checkpoints = save game. Retry policies handle flaky APIs; time travel helps debugging and "what-if" exploration.

from fastapi import FastAPI

@app.post("/chat/{thread_id}")
