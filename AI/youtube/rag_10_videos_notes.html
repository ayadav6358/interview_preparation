What is RAG & Why Do We Need It?

RAG (Retrieval Augmented Generation) lets an LLM answer using external knowledge fetched at question time, instead of relying only on what it memorized during training.

1. How an LLM "knows" things

An LLM stores knowledge in its parameters (weights), learned from training data. This is called parametric knowledge. To use it, you just prompt the model.

2. Problems with parametric knowledge only

  • Private data — the model never saw your company docs, your code, your notes.
  • Knowledge cutoff — it doesn't know events after its training date.
  • Hallucination — when it doesn't know, it may confidently invent facts.
  • No sources — you can't easily verify where an answer came from.

3. Solution 1: Fine-tuning

Train the pre-trained model further on your domain data (supervised fine-tuning, continued pre-training, LoRA / QLoRA).

  • Steps: collect data → choose method → train → evaluate → deploy.
  • Drawbacks: expensive compute, needs ML expertise, and every time data changes you must re-train. Also doesn't fully stop hallucination.

4. Solution 2: In-context learning

Large LLMs can learn a task from examples or information placed inside the prompt, without changing weights (an emergent ability seen in GPT-3 scale models). Few-shot prompting is one example.

RAG = in-context learning where the context is fetched automatically from your knowledge base for every question.

flowchart LR
  Q["Question"] --> R["Retriever<br/>search knowledge base"]
  KB[("Your documents")] --> R
  R --> C["Relevant context"]
  Q --> P["Prompt = question + context"]
  C --> P
  P --> L["LLM"] --> A["Grounded answer"]

5. RAG vs Fine-tuning

RAGFine-tuning
CostLow (no training)High
Updating knowledgeAdd/re-index documentsRe-train model
Private / fresh dataYesOnly what was trained
Citations / transparencyCan show sourcesNo
Changes style / behaviourLimitedYes — good for tone, format, domain language
Key takeaway: Use RAG to give the model knowledge; use fine-tuning to change its behaviour. Many production systems use both.

RAG Architecture — The 4 Steps

Every RAG system has an offline indexing phase and an online query phase.

flowchart TB
  subgraph OFF["Offline: Indexing"]
    D["Documents<br/>PDF, web, DB"] --> L["1a. Load"] --> S["1b. Chunk"] --> E["1c. Embed"] --> V[("1d. Vector store")]
  end
  subgraph ON["Online: Query time"]
    Q["User query"] --> QE["Embed query"] --> R["2. Retrieve top-k"]
    V --> R
    R --> AU["3. Augment prompt"]
    Q --> AU
    AU --> G["4. Generate with LLM"] --> A["Answer + sources"]
  end

Step 1 — Indexing

  1. Document ingestion — load data from sources into Document objects (text + metadata).
  2. Text chunking — split into small, meaningful pieces.
  3. Embedding generation — convert each chunk into a dense vector.
  4. Storage — save vectors + text + metadata in a vector store.

Step 2 — Retrieval

Embed the question with the same embedding model, search the vector store for nearest chunks (cosine similarity / dot product), optionally re-rank, return top-k.

Step 3 — Augmentation

Combine query + retrieved chunks into a prompt with clear instructions:

You are a helpful assistant.
Answer ONLY from the provided context.
If the context is insufficient, say "I don't know".

Context:
{context}

Question: {question}

Step 4 — Generation

The LLM produces the answer using the context (plus its general language ability). Optionally cite chunk sources.

Golden rule: RAG quality = retrieval quality. If the right chunk is not retrieved, even the best LLM cannot answer correctly.
Key takeaway: Index → Retrieve → Augment → Generate. The next videos zoom into each box.

Data Ingestion & Document Parsing

Garbage in, garbage out. Getting clean text and useful metadata out of messy sources is the most underrated part of RAG.

1. Common sources

flowchart LR
  P["PDF"] --> DL["Loaders / Parsers"]
  W["Web pages"] --> DL
  YT["YouTube transcripts"] --> DL
  DB["SQL / CSV"] --> DL
  N["Notion, Drive, Confluence"] --> DL
  DL --> DOC["Document<br/>page_content + metadata"]
  
from langchain_community.document_loaders import PyPDFLoader, WebBaseLoader, CSVLoader, DirectoryLoader
docs = PyPDFLoader("handbook.pdf").load()          # one Document per page
docs = DirectoryLoader("data", glob="**/*.pdf", loader_cls=PyPDFLoader).load()
print(docs[0].page_content[:200], docs[0].metadata)  # {'source': 'handbook.pdf', 'page': 0}

2. Hard cases in PDFs

  • Scanned PDFs — no text layer → need OCR (Tesseract, cloud OCR).
  • Tables — plain extraction scrambles rows/columns → use layout-aware parsers (pdfplumber, Unstructured, Docling, LlamaParse) or convert tables to Markdown.
  • Multi-column layouts, headers/footers, page numbers — clean them out.
  • Images & charts — caption them with a vision model (multimodal RAG).

3. Metadata matters

Store source, page, section, date, author, department… Metadata enables filtering ("only 2025 policies"), citations and access control.

4. Cleaning checklist

  • Normalize whitespace, fix broken hyphenation, remove boilerplate.
  • De-duplicate repeated documents.
  • Keep structure (headings) — it helps chunking later.
  • For large data use lazy_load() (generator) instead of load().
Key takeaway: Spend time on parsing. Clean text + rich metadata gives better chunks, better retrieval, better answers.

Chunking Strategies

Chunking decides what unit of text gets embedded and retrieved. Too big = noisy, diluted embeddings. Too small = missing context.

1. Why chunk?

  • Embedding models and LLM context windows have limits.
  • One focused idea per vector = more accurate semantic search.
  • Send only relevant parts to the LLM → cheaper, less distraction.
flowchart TB
  C["Chunking strategies"] --> F["Fixed size<br/>every N chars/tokens"]
  C --> R["Recursive<br/>paragraph, line, word"]
  C --> D["Document structure<br/>Markdown headers, code, HTML"]
  C --> S["Semantic<br/>split where meaning changes"]
  C --> A["Advanced<br/>parent-child, late chunking"]

2. Fixed-size chunking

from langchain_text_splitters import CharacterTextSplitter
splitter = CharacterTextSplitter(chunk_size=500, chunk_overlap=50, separator="")

Simple, but can cut sentences in half.

3. Recursive character splitting (default choice)

from langchain_text_splitters import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(docs)          # metadata is copied to each chunk

Tries "\n\n" → "\n" → " " → "" so paragraphs stay together when possible.

4. Structure-aware

from langchain_text_splitters import MarkdownHeaderTextSplitter
md = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "h1"), ("##", "h2")])
chunks = md.split_text(markdown_text)            # headers go into metadata

5. Semantic chunking

Embed sentences; start a new chunk where similarity between neighbours drops sharply. Better topic boundaries, more compute.

6. Chunk overlap

Repeats the end of one chunk at the start of the next so ideas crossing the boundary aren't lost. Typical: 10–20% of chunk size.

7. Choosing chunk size

ContentTypical size
FAQs, short facts200–500 tokens
Articles, docs500–1000 tokens
Long reasoning / legal1000+ or parent-child
Key takeaway: Start with recursive splitting (~1000 chars, 200 overlap), then tune using evaluation (video 9). Never guess — measure.

Embeddings & Vector Databases

Embeddings turn text into vectors where similar meaning = nearby points. Vector databases store them and find nearest neighbours fast.

1. Embeddings

  • A dense vector (e.g. 384, 768, 1536, 3072 dimensions).
  • "How to reset password" and "forgot my login" end up close even with no common words.
  • Use the same model for documents and queries.
from langchain_openai import OpenAIEmbeddings
emb = OpenAIEmbeddings(model="text-embedding-3-small")
v = emb.embed_query("What is RAG?")             # list of floats
# open-source alternative
from langchain_huggingface import HuggingFaceEmbeddings
emb = HuggingFaceEmbeddings(model_name="sentence-transformers/all-MiniLM-L6-v2")

2. Similarity metrics

  • Cosine similarity — angle between vectors (most common).
  • Dot product — same as cosine for normalized vectors.
  • Euclidean (L2) distance — lower = closer.

3. Why a vector database?

Comparing a query against millions of vectors one by one is too slow. Vector DBs use Approximate Nearest Neighbour (ANN) indexes:

flowchart LR
  Q["Query vector"] --> IDX["ANN index"]
  IDX --> H["HNSW<br/>graph layers, fast and accurate"]
  IDX --> IVF["IVF<br/>cluster then search nearby clusters"]
  IDX --> PQ["PQ<br/>compress vectors to save memory"]
  H --> K["Top-k nearest chunks"]
  IVF --> K
  PQ --> K

4. Popular options

ToolTypeGood for
FAISSLibrary (in-memory)Prototypes, fast local search
ChromaLightweight DB, persists to diskLearning, small apps
PineconeManaged cloudProduction without ops
Qdrant / Weaviate / MilvusOpen-source DBProduction, self-hosted, hybrid search
pgvectorPostgres extensionWhen you already use Postgres
from langchain_community.vectorstores import FAISS
vs = FAISS.from_documents(chunks, emb)
vs.save_local("faiss_index")
vs.similarity_search_with_score("refund policy", k=4)
Key takeaway: Embedding model choice affects quality; vector DB choice affects speed, scale and features (filters, hybrid search).

Retrieval Strategies

Plain top-k similarity search is a start. Several techniques improve recall (find the right chunk) and precision (avoid wrong chunks).

mindmap
  root((Retrieval))
    Basic
      Similarity top-k
      Score threshold
      Metadata filter
    Diversity
      MMR
    Keyword plus semantic
      BM25
      Hybrid search
      RRF fusion
    Query transformation
      Multi-query
      Query rewriting
      HyDE
      Step-back
    Structure
      Parent document
      Self-query

1. Similarity search, threshold & filters

retriever = vs.as_retriever(search_kwargs={"k": 4})
retriever = vs.as_retriever(search_type="similarity_score_threshold",
                            search_kwargs={"score_threshold": 0.5})
chroma_vs.similarity_search("leave policy", k=4, filter={"department": "HR"})

2. MMR — Maximal Marginal Relevance

Balances relevance and diversity so top results aren't near-duplicates.

vs.as_retriever(search_type="mmr", search_kwargs={"k": 4, "fetch_k": 20, "lambda_mult": 0.5})

3. Hybrid search (BM25 + dense)

Dense embeddings understand meaning but can miss exact terms (product codes, names, error IDs). BM25 keyword search catches those. Combine both and merge with Reciprocal Rank Fusion.

from langchain_community.retrievers import BM25Retriever
from langchain.retrievers import EnsembleRetriever
bm25 = BM25Retriever.from_documents(chunks); bm25.k = 4
dense = vs.as_retriever(search_kwargs={"k": 4})
hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])
flowchart LR
  Q["Query"] --> B["BM25 keyword"]
  Q --> D["Dense vector"]
  B --> F["Reciprocal Rank Fusion"]
  D --> F
  F --> K["Merged top-k"]

4. Query transformation

  • Multi-query — LLM writes 3–5 versions of the question; retrieve for each; union results.
  • Query rewriting — turn a vague/chatty question into a clear search query (also uses chat history: "what about its price?" → "price of iPhone 16").
  • HyDE — LLM writes a hypothetical answer; embed that and search (answers look more like documents than questions do).
  • Step-back prompting — ask a more general question first to fetch background.

5. Parent-document retrieval

Search on small child chunks (precise matching) but return the larger parent chunk (full context) to the LLM.

6. Self-query retriever

LLM extracts filters from natural language: "movies by Nolan after 2010 about space" → query "space" + filter director="Nolan", year > 2010.

Key takeaway: Hybrid search + query rewriting fix most "it didn't find the right document" problems.

Re-ranking & Context Optimization

Retrieve broadly (high recall), then re-rank precisely (high precision), then send only the best, compact context to the LLM.

flowchart LR
  Q["Query"] --> R["First-stage retriever<br/>fast, top 20-50"]
  R --> RR["Re-ranker<br/>cross-encoder scores each pair"]
  RR --> T["Top 3-5"]
  T --> CC["Compression<br/>keep relevant sentences"]
  CC --> O["Order + format context"]
  O --> L["LLM"]

1. Bi-encoder vs Cross-encoder

Bi-encoder (embeddings)Cross-encoder (re-ranker)
HowQuery and doc embedded separately, compare vectorsQuery + doc read together by one model, outputs a relevance score
SpeedVery fast (vectors pre-computed)Slow (runs per pair)
AccuracyGoodBetter
UseFirst stage over millionsSecond stage over top 20–50
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

model = HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-base")
reranker = CrossEncoderReranker(model=model, top_n=4)
retriever = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=vs.as_retriever(search_kwargs={"k": 20}))

Hosted alternatives: Cohere Rerank, Jina, Voyage rerankers.

2. Contextual compression

An LLM (LLMChainExtractor) or embedding filter (EmbeddingsFilter) removes irrelevant sentences from each retrieved chunk.

3. "Lost in the middle"

LLMs pay most attention to the beginning and end of long contexts. Put the most relevant chunks first and last (LongContextReorder), and don't stuff too many chunks.

4. Context formatting

def format_docs(docs):
    return "\n\n".join(f"[{i+1}] (source: {d.metadata.get('source')}, page {d.metadata.get('page')})\n{d.page_content}"
                       for i, d in enumerate(docs))

Numbered sources let the LLM cite [1], [2] in its answer.

Key takeaway: Two-stage retrieval (fast retrieve → accurate re-rank) is one of the highest-impact RAG upgrades.

Building an End-to-End RAG App

Put everything together: a "Chat with your PDF" app with a LangChain backend and Streamlit UI.

flowchart TB
  UP["Upload PDF"] --> LD["PyPDFLoader"] --> SP["RecursiveCharacterTextSplitter"] --> EM["Embeddings"] --> VS[("FAISS / Chroma")]
  Q["Question + chat history"] --> RW["Rewrite to standalone question"]
  RW --> RT["Retriever + re-ranker"]
  VS --> RT
  RT --> FD["format_docs"]
  FD --> PR["Prompt"]
  Q --> PR
  PR --> LLM["Chat model"] --> OUT["Answer with citations"]

1. Indexing

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import FAISS

docs = PyPDFLoader("book.pdf").load()
chunks = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200).split_documents(docs)
vs = FAISS.from_documents(chunks, OpenAIEmbeddings(model="text-embedding-3-small"))
retriever = vs.as_retriever(search_type="mmr", search_kwargs={"k": 4})

2. The RAG chain (LCEL)

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer ONLY from the context. Cite sources like [1]. "
               "If the answer is not in the context, say you don't know.\n\nContext:\n{context}"),
    ("human", "{question}")
])
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

rag_chain = (
    RunnableParallel({"context": retriever | RunnableLambda(format_docs),
                      "question": RunnablePassthrough()})
    | prompt | llm | StrOutputParser()
)
print(rag_chain.invoke("What does chapter 3 say about gradient descent?"))

3. Conversational RAG (chat history)

Follow-ups like "explain it simply" need context. First rewrite the question into a standalone question using chat history, then retrieve.

contextualize = ChatPromptTemplate.from_messages([
    ("system", "Rewrite the latest question as a standalone question using the chat history."),
    MessagesPlaceholder("chat_history"), ("human", "{question}")])
standalone_q = contextualize | llm | StrOutputParser()

4. Streamlit UI (sketch)

file = st.sidebar.file_uploader("Upload PDF", type="pdf")
if file and "vs" not in st.session_state:
    st.session_state.vs = build_index(file)          # cache the index
q = st.chat_input("Ask about the document")
if q:
    with st.chat_message("assistant"):
        st.write_stream(rag_chain.stream(q))

5. Practical tips

  • temperature=0 for factual answers.
  • Cache embeddings / persist the index — don't re-embed on every run.
  • Return source documents alongside the answer for the UI.
  • Add a fallback message when nothing relevant is found.
Key takeaway: A complete RAG app is ~40 lines of LCEL: retriever + format + prompt + LLM + parser, plus question rewriting for chat.

RAG Evaluation

You can't improve what you don't measure. Evaluate the retriever and the generator separately to know which part is failing.

flowchart LR
  Q["Question"] --> RET["Retriever"] --> CTX["Context"]
  CTX --> GEN["Generator"] --> ANS["Answer"]
  GT["Ground-truth answer"]
  CTX -. context precision and recall .-> GT
  ANS -. faithfulness .-> CTX
  ANS -. answer relevancy .-> Q
  ANS -. answer correctness .-> GT

1. Retrieval metrics

  • Context precision — are the retrieved chunks actually relevant (and ranked high)?
  • Context recall — did we retrieve everything needed to answer?
  • Classic IR metrics: Hit rate / Recall@k, MRR (how high the first correct chunk ranks), nDCG.

2. Generation metrics

  • Faithfulness (groundedness) — is every claim in the answer supported by the context? (catches hallucination)
  • Answer relevancy — does the answer address the question?
  • Answer correctness — matches the ground-truth answer?

3. Building an evaluation dataset

  1. Collect 30–100 real questions (or generate with an LLM from your docs).
  2. Write / verify reference answers (and ideally which chunk contains them).
  3. Run the pipeline, store question, contexts, answer.
  4. Score with metrics; compare configurations (chunk size, k, hybrid, re-ranker).

4. RAGAS

from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall
from datasets import Dataset

data = Dataset.from_dict({
    "question": questions,
    "answer": answers,              # from your RAG chain
    "contexts": contexts,           # list of retrieved chunk texts per question
    "ground_truth": references,
})
scores = evaluate(data, metrics=[faithfulness, answer_relevancy, context_precision, context_recall])
print(scores.to_pandas())

These metrics use an LLM-as-a-judge internally. Other tools: LangSmith evaluations, TruLens, DeepEval, Arize Phoenix.

5. Diagnosing failures

SymptomLikely causeFix
Low context recallRight chunk not foundBetter chunking, hybrid search, multi-query, higher k
Low context precisionToo much noiseRe-ranker, metadata filters, smaller k
Low faithfulnessLLM ignores contextStricter prompt, temperature 0, better model
Low answer relevancyOff-topic answerPrompt clarity, query rewriting
Key takeaway: Separate retrieval and generation metrics; change one setting at a time and re-run the same dataset.

Advanced RAG Patterns

Naive RAG retrieves once and answers. Advanced RAG adds decisions, self-checks and richer knowledge structures.

flowchart LR
  N["Naive RAG<br/>retrieve, then generate"] --> A["Advanced RAG<br/>pre-retrieval + post-retrieval steps"]
  A --> M["Modular / Agentic RAG<br/>LLM decides when and how to retrieve"]

1. Agentic RAG

The retriever is a tool. The agent decides whether to retrieve, which source (vector DB, web search, SQL), and can retrieve multiple times for multi-hop questions. Usually built with LangGraph.

2. Corrective RAG (CRAG)

Grade retrieved documents; if they're irrelevant or weak, rewrite the query and fall back to web search before answering.

flowchart LR
  Q["Query"] --> R["Retrieve"] --> G{"Grade docs<br/>relevant?"}
  G -->|yes| GEN["Generate"]
  G -->|no / ambiguous| RW["Rewrite query"] --> WS["Web search"] --> GEN
  GEN --> A["Answer"]

3. Self-RAG

The model reflects on its own output: Is retrieval needed? Are the docs relevant? Is my answer supported by them? Is it useful? If not, retry.

flowchart LR
  Q["Query"] --> D{"Need retrieval?"}
  D -->|no| GEN["Generate"]
  D -->|yes| R["Retrieve + grade"] --> GEN
  GEN --> H{"Grounded in docs?"}
  H -->|no| GEN
  H -->|yes| U{"Answers the question?"}
  U -->|no| RW["Rewrite query"] --> R
  U -->|yes| A["Final answer"]

4. Adaptive RAG / Routing

Classify the query first: simple → answer directly; needs docs → vector RAG; current events → web search; numbers → SQL.

5. GraphRAG

Extract entities and relationships into a knowledge graph; retrieve connected facts and community summaries. Great for "global" questions ("What are the main themes across all reports?") and multi-hop reasoning.

6. Multimodal RAG

Index images, charts and tables (via captions or multimodal embeddings) and send relevant images to a vision LLM.

7. Production concerns

  • Freshness — incremental indexing, delete/update stale chunks.
  • Access control — filter by user permissions via metadata.
  • Latency & cost — caching, smaller embeddings, limit re-ranking depth.
  • Guardrails — prompt-injection in retrieved docs, PII handling.
  • Monitoring — trace with LangSmith, track faithfulness over time.
Key takeaway: Start naive, measure, then add only the advanced pieces your failures need: hybrid → re-rank → query rewriting → corrective/agentic.
