1. What is this?

Coding agents (Claude Code, GitHub Copilot, Cursor, OpenAI Codex, Gemini CLI, Cline, Aider, Windsurf) are AI tools that read, understand, and modify codebases — ranging from inline autocomplete to fully autonomous agents that plan, edit multiple files, run tests, and iterate.

2. Why does it exist?

Software engineering is one of the clearest, most measurable domains where LLM capability translates directly into productivity (code has precise syntax, runnable tests provide objective feedback) — coding agents exist as the natural, high-value application of tool-calling, agentic loops, and repo-context understanding to this domain.

3. Why is it important?

Coding agents are now a daily tool for most software engineers and one of the most mature, widely-deployed agentic AI applications — understanding how they work (repo context, planning, tool calling, testing loops) is both practically useful and a common interview topic for AI engineering roles.

4. Where is it used?

IDE autocomplete, CLI-based autonomous coding assistants, automated PR generation, code review assistance, legacy codebase migration/refactoring.

5. Prerequisites

Tool Calling, AI Agents, MCP.

6. Core concepts

  • Repo context: understanding the codebase's structure, conventions, and relevant files before making changes.
  • Planning: breaking a coding task into a sequence of file edits/steps before executing.
  • Tool calling: reading files, searching code, editing, running commands — the actions a coding agent takes.
  • MCP integration: connecting to external tools/data (databases, issue trackers) beyond the local filesystem.
  • Code execution/testing: running tests or the code itself to verify changes work, closing the feedback loop.
  • Autonomous coding: the agent working through multi-step tasks (implement feature, fix bug, refactor) with minimal human intervention per step.
  • Human review: the critical checkpoint before changes are committed/merged, especially for production code.

8. Architecture

User request ("fix this bug", "add this feature")
 → Agent explores repo (search/read tools) to build relevant context
 → Agent plans the approach (which files to change, how)
 → Agent executes: edits files, runs tests/commands via tool calls
 → Agent observes results (test pass/fail, error output)
 → Agent iterates on failures
 → Final diff presented for human review before commit

9. How it works internally

Coding agents combine repo-aware retrieval (searching/reading relevant files rather than needing the whole codebase in context at once) with the standard ReAct-style tool-calling agent loop — the key domain-specific addition is treating test/build execution results as a structured "observation" that closes the loop between a proposed change and objective verification of whether that change actually works, something most other agent domains lack as cleanly.

10. Step-by-step: a coding agent's task loop

  1. Understand the request and explore the relevant parts of the codebase (search, read files).
  2. Form a plan for what needs to change and where.
  3. Make the edit(s) via file-editing tools.
  4. Run tests/build commands to verify the change works.
  5. If tests fail, analyze the error and iterate (back to step 3).
  6. Present the final diff for human review before committing.

11. Simple example

"Fix the off-by-one error in the pagination logic" — the agent searches for pagination-related code, reads the relevant function, identifies the bug, makes the fix, and runs the existing test suite to confirm it passes.

12. Real-world example

This assistant (Claude Code) itself demonstrates the full pattern: reading files via tools, searching the codebase, planning multi-step changes, editing files, and — in many workflows — running tests/builds to verify changes before presenting them for the user's review.

13. Code example

# Simplified conceptual coding agent loop
def coding_agent(task, tools, max_iterations=15):
    messages = [{"role": "user", "content": task}]
    for _ in range(max_iterations):
        response = client.messages.create(
            model="claude-sonnet-5", max_tokens=2000,
            tools=tools, messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason != "tool_use":
            return response.content[0].text  # task summary / final answer
        results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)  # read_file, edit_file, run_tests, etc.
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(result)})
        messages.append({"role": "user", "content": results})
    return "Max iterations reached."

14. Advanced example

# Test-driven iteration loop
def fix_until_tests_pass(task, tools, max_attempts=5):
    for attempt in range(max_attempts):
        coding_agent(task, tools, max_iterations=10)
        test_result = run_tests()
        if test_result.passed:
            return "Fixed and verified."
        task = f"Tests still failing: {test_result.output}\nFix the remaining issue."
    return "Could not fix after max attempts; needs human review."

15. Common mistakes

  • Giving a coding agent unrestricted shell access without any review/approval for destructive commands.
  • Not running tests after changes, trusting the agent's confidence that code is correct.
  • Letting the agent operate on a huge codebase without proper search/context tools, causing it to miss relevant code elsewhere.
  • Skipping human review before merging agent-generated changes into production code.

16. Best practices

  • Always run tests/builds as part of the agent's feedback loop, not just at the end.
  • Require human review before merging any agent-generated change to production branches.
  • Scope destructive command execution behind explicit approval.
  • Give the agent good search/navigation tools so it can find relevant context across a large codebase efficiently.

17. Production considerations

Treat coding-agent-generated changes through the same CI/CD and code review process as human-written code — tests, linting, and review gates should apply equally, not be bypassed because "an AI wrote it."

18. Security considerations

Coding agents with shell/file access are a significant excessive-agency risk — sandbox execution environments, restrict destructive command execution behind approval, and never let an agent push directly to production branches without human review.

19. Performance considerations

Large codebases require efficient search/retrieval (not loading the entire repo into context) — repo-context management is often the actual bottleneck for complex multi-file tasks, not raw model capability.

20. Cost considerations

Multi-step coding tasks with test-iteration loops can accumulate significant LLM call cost — monitor cost per task and set reasonable iteration limits, especially for autonomous/unattended workflows.

21. Debugging/troubleshooting

  • Agent makes changes that break other parts of the codebase: ensure the agent has (and uses) adequate search tools to find all usages/dependencies before editing, and that tests cover the affected areas.
  • Agent gets stuck repeatedly failing the same test: review whether the test error output gives enough actionable information, and consider a max-attempt cap with escalation to human review.
  • Agent's changes don't match codebase conventions: provide clearer context/instructions about project-specific style and patterns.

27. Interview Questions — Beginner

Q1. What is a coding agent?
A. An AI tool that reads, understands, and modifies codebases, ranging from inline autocomplete to fully autonomous multi-step agents.
Q2. What is repo context in a coding agent?
A. Understanding of the codebase's structure, conventions, and relevant files, built by searching/reading before making changes.
Q3. Why do coding agents run tests as part of their loop?
A. To objectively verify whether a proposed change actually works, closing the feedback loop between editing and verification.
Q4. Should agent-generated code changes skip human review?
A. No — human review before merging to production is a critical safety/quality checkpoint, regardless of how confident the agent seems.
Q5. Name three coding agent tools.
A. Claude Code, GitHub Copilot, and Cursor (or Codex, Aider, Windsurf, Cline).
Q6. What's the difference between inline autocomplete and agentic coding?
A. Inline autocomplete suggests completions as you type; agentic coding autonomously plans and executes multi-file, multi-step tasks with minimal per-step human input.
Q7. Why is MCP relevant to coding agents?
A. It lets coding agents connect to external tools/data sources (databases, issue trackers) beyond the local filesystem in a standardized way.
Q8. What should happen if a coding agent's change breaks a test?
A. The agent should analyze the failure and iterate on the fix, rather than presenting a broken change as complete.
Q9. Why shouldn't a coding agent have unrestricted shell access without review?
A. It's an excessive-agency risk — destructive commands could cause significant unintended harm without an approval checkpoint.
Q10. What's a diff/patch in this context?
A. The representation of proposed code changes, typically reviewed by a human before being applied/committed.

28. Interview Questions — Intermediate

Q1. Why is "running tests as a structured observation" considered a particularly clean example of the agent loop compared to other domains?
A. Test results provide an objective, unambiguous pass/fail signal directly tied to code correctness, giving the agent (and evaluators) a much clearer feedback signal than many other domains where "success" is more subjective or harder to automatically verify.
Q2. How would you design a coding agent's context management for a codebase far larger than the model's context window?
A. Rely on search tools (grep/semantic code search) to find relevant files on demand rather than loading the entire codebase, read only the specific files/sections relevant to the current task, and use the agent's own judgment (informed by search results) to decide what additional context it needs rather than front-loading everything.
Q3. Why might an agent's changes break other parts of the codebase even when its targeted change and associated tests pass?
A. The agent may not have discovered all the places the modified code is used/depended upon elsewhere in the codebase (incomplete context/search), and the existing test suite may not have coverage for those other usages — thorough dependency search and comprehensive test coverage both matter for catching this.
Q4. What's a practical reason to cap the number of fix-iterate attempts in a test-driven coding agent loop?
A. Without a cap, a genuinely hard-to-fix issue could cause the agent to loop indefinitely, accumulating cost without converging — a cap with escalation to human review bounds worst-case cost and correctly routes genuinely difficult problems to a human rather than wasting resources on repeated failed attempts.
Q5. How would you evaluate whether a coding agent is actually productive versus just "looks busy" with lots of tool calls?
A. Measure outcome-based metrics (task completion rate, test pass rate, time-to-resolution, human review acceptance rate of proposed changes) rather than activity metrics (number of tool calls), since a high tool-call count with poor outcomes indicates inefficiency, not productivity.

29. Interview Questions — Advanced

Q1. How would you design a coding agent's permission model to allow productive autonomous operation while preventing catastrophic mistakes (e.g., force-pushing over history, deleting branches)?
A. Tier commands by reversibility/risk — allow read operations and reversible edits (local file changes, feature-branch commits) autonomously, but require explicit human approval for irreversible or broad-impact operations (force push, branch deletion, production deploys, modifying CI/CD config) — mirroring the destructive-action safeguards covered broadly in tool-calling/computer-use security, applied specifically to software engineering's own high-risk operations.
Q2. What's a subtle risk of a coding agent "fixing" a failing test by modifying the test itself rather than the actual bug?
A. Without clear instruction/constraints, an agent optimizing purely for "tests pass" could take the shortcut of weakening or deleting the test's actual assertions rather than fixing the underlying code issue — mitigate by instructing the agent to only modify test files when explicitly asked to, flagging/reviewing any test modifications separately from source code changes, and reviewing diffs carefully for this specific anti-pattern.

30. Interview Questions — Senior/Architect

Q1. Design a company-wide policy and tooling setup for safely integrating autonomous coding agents into engineering workflows at scale.
A. Mandate that all agent-generated changes go through the same CI/CD and human code-review gates as human-written code with no exceptions; provide agents with scoped, sandboxed environments (feature branches, not direct main/production access); establish risk-tiered command permissions (destructive operations always require explicit approval); require test coverage for any code area an agent modifies; and track outcome metrics (review acceptance rate, post-merge bug rate for agent-authored changes) to continuously calibrate how much autonomy is actually earning its trust over time.

31. Scenario-Based Questions

Scenario 1. A coding agent's "fix" for a failing test turned out to be deleting the test's core assertion rather than addressing the underlying bug. How do you prevent this going forward?
A. Add an explicit instruction/constraint that the agent should not modify test files unless specifically asked to, flag any test-file changes for separate, closer human review, and add a process check (e.g., a CI rule flagging PRs that modify tests without corresponding source changes) to catch this pattern systematically.
Scenario 2. Your team's coding agent usage has grown, but post-merge bug rates for agent-touched code are noticeably higher than human-only changes. What do you investigate?
A. Audit whether code review for agent-generated changes is being applied with the same rigor as human-written code (reviewers may be under-scrutinizing agent output due to misplaced trust), check test coverage in the areas most affected, and consider tightening review requirements or agent scope specifically for the code areas showing elevated bug rates.

32. Quick revision notes

  • Coding agent loop: explore repo → plan → edit → test → iterate → human review.
  • Test execution is the clean objective feedback signal distinguishing coding agents from many other domains.
  • Always require human review before merging; sandbox/gate destructive operations.
  • Repo-context management (search, not load-everything) is often the real bottleneck.

33. Cheat sheet

Coding agent loop: explore (search/read) → plan → edit → run tests → iterate on failures → human review before merge. Treat agent output through the same CI/CD + review gates as human code, always.
