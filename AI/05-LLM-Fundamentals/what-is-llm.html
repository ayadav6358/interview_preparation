1. What is this?

A Large Language Model (LLM) is a neural network — almost always a Transformer decoder — trained on massive amounts of text to predict the next token given everything before it. From this single objective, applied at huge scale (billions of parameters, trillions of training tokens), models develop broad emergent capabilities: writing, reasoning, coding, translation, summarization, and tool use.

2. Why does it exist?

Hand-coding language understanding (classic rule-based NLP: grammars, regexes, decision trees over linguistic features) never scaled to the richness, ambiguity, and context-dependence of real human language. Statistical/neural approaches that learn patterns directly from huge text corpora turned out to generalize far better. LLMs are the current end-point of that trajectory: n-gram models → RNN/LSTM language models → Transformer-based LLMs, each step removing more hand-engineering and relying more on data + scale.

3. Why is it important?

LLMs are the first general-purpose language technology: one model, with no task-specific retraining, can draft emails, write code, answer questions, translate, summarize, and reason about novel problems via prompting alone. This generality is why LLMs sit at the center of the 2026 AI stack — RAG, agents, MCP, multimodal systems, and coding assistants are all built on top of an LLM's core next-token-prediction ability.

4. Where is it used?

  • Conversational assistants (ChatGPT, Claude, Gemini)
  • Coding agents and IDE copilots (Claude Code, Copilot, Cursor)
  • RAG-based knowledge assistants and enterprise search
  • Autonomous/semi-autonomous agents (research, customer support, ops)
  • Content generation, summarization, translation, classification pipelines
  • Structured data extraction from unstructured documents

5. Prerequisites

To get the most from this page, you should already understand: basic neural network concepts (parameters, training, inference — see AI Lifecycle), and ideally have skimmed Transformers (tokenization, attention) since LLMs are built on that architecture.

6. Core concepts

  • Autoregressive generation: the model generates one token at a time, feeding each generated token back in as input for the next step.
  • Emergent capability: abilities (e.g., arithmetic, chain-of-thought reasoning) that appear only past a certain scale, not present in smaller models trained the same way.
  • Alignment: the process of shaping a raw pretrained model's behavior to be helpful, harmless, and honest.
  • Context-conditioned generation: everything the model outputs is conditioned on the tokens currently in its context window — it has no persistent memory beyond that.

8. Architecture

Input text
 → Tokenizer → token IDs
 → Embedding layer (token ID → vector) + positional encoding
 → N × [Multi-head self-attention → Feed-forward network] (Transformer decoder blocks)
 → Final linear layer → probability distribution over vocabulary
 → Sampling → next token
 → (token appended, repeat)

9. How it works internally

Each transformer block lets every token "attend" to every previous token (causal/masked self-attention — a token cannot see future tokens), building a contextual representation. Stacking many such blocks lets the model build increasingly abstract representations (syntax → semantics → task-level reasoning patterns) purely from the next-token-prediction objective. A KV cache stores previously computed attention keys/values so each new token doesn't require recomputing attention over the whole sequence from scratch — critical for making autoregressive generation fast.

10. Step-by-step explanation (prompt → response)

  1. User prompt is tokenized into token IDs.
  2. Tokens are embedded and combined with positional information.
  3. The sequence passes through all transformer layers, producing a probability distribution for the next token.
  4. A token is sampled per temperature/top-p/top-k settings.
  5. That token is appended to the sequence; steps 3–4 repeat (autoregressive loop).
  6. Generation stops at an end-of-sequence token, a stop sequence, or the max-token limit.
  7. The full response is returned (or streamed token-by-token) to the caller.

11. Simple example

Prompt: "The capital of France is" → the model assigns very high probability to the token "Paris" because that pattern was extremely common in training data, and samples it (especially at low temperature).

12. Real-world example

Claude Code (this assistant) is an LLM-based coding agent: your request is tokenized, sent through the model with system instructions and tool definitions in context, and the model generates either natural-language text or a structured tool call (e.g., "read this file") — all via the same next-token-prediction mechanism described above.

13. Code example

from anthropic import Anthropic

client = Anthropic()
response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=300,
    temperature=0.3,
    messages=[
        {"role": "user", "content": "Explain what a context window is, in 2 sentences."}
    ],
)
print(response.content[0].text)
print("Tokens used:", response.usage.input_tokens, response.usage.output_tokens)

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 300,
  messages: [{ role: "user", content: "Explain context windows briefly." }],
});

console.log(response.content[0].text);

14. Advanced example

Streaming + token accounting for a cost-aware production call:

with client.messages.stream(
    model="claude-sonnet-5",
    max_tokens=500,
    messages=[{"role": "user", "content": "Write a haiku about distributed systems."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()
    cost_estimate = final.usage.input_tokens * 0.000003 + final.usage.output_tokens * 0.000015
    print(f"\nEstimated cost: ${cost_estimate:.6f}")

15. Common mistakes

  • Treating LLM output as a database lookup ("it said X, so X must be true") instead of a probabilistic generation.
  • Assuming the model "remembers" past conversations outside the current context window.
  • Using high temperature for tasks needing determinism (extraction, classification, code).
  • Ignoring that every API call is stateless inference — no learning happens from your usage.

16. Best practices

  • Match temperature to task type (low for factual/structured, higher for creative).
  • Ground factual claims with retrieval (RAG) rather than relying on parametric memory.
  • Use system prompts for stable behavior; keep user prompts focused and specific.
  • Track token usage (input/output) per request for cost and performance visibility.

17. Production considerations

Treat every LLM call like a network call to an unreliable, costly, rate-limited external service: implement retries with backoff, timeouts, graceful degradation (fallback model or cached response), and monitor latency/error rates per model/provider.

18. Security considerations

Untrusted text in context (user input, scraped pages, tool outputs) can carry prompt-injection attempts. Never give a model unrestricted tool/file/network access without permission boundaries. Avoid putting secrets in prompts that might be logged by a provider. See 38-AI-Security.

19. Performance considerations

Latency scales with output token count (generation is sequential) far more than input size (input is processed in parallel). Streaming responses improves perceived latency. KV caching and prompt/context caching reduce repeated-computation costs for shared prefixes (e.g., a stable system prompt).

20. Cost considerations

Cost = (input tokens × input price) + (output tokens × output price), summed per call. Larger/more capable models cost more per token — route simple tasks to smaller/faster models and reserve frontier models for complex reasoning (model routing). See 40-Cost-Optimization.

21. Debugging/troubleshooting

  • Inconsistent outputs across calls: check temperature/top-p settings; even at temperature 0, minor provider-side nondeterminism can occur.
  • Truncated output: check `max_tokens` and stop sequences; the response may have hit the token cap mid-thought.
  • Unexpectedly expensive calls: log `usage.input_tokens`/`usage.output_tokens` per call; often caused by unbounded conversation history or oversized retrieved context.
  • Model "forgets" earlier instructions: likely a context-window/attention-dilution issue in a long conversation — summarize/compact history.

27. Interview Questions — Beginner

Q1. What is an LLM fundamentally trained to do?
A. Predict the next token given preceding tokens.
Q2. What is a token?
A. A sub-word unit of text produced by the tokenizer; not the same as a word or character.
Q3. What is the context window?
A. The maximum number of tokens (input + output combined) a model can process in one request.
Q4. Does an LLM remember previous separate conversations?
A. No, unless that history is explicitly re-sent in the context; the model itself is stateless between API calls.
Q5. What does temperature control?
A. The randomness of next-token sampling; 0 is near-deterministic, higher values increase diversity.
Q6. What is a hallucination?
A. Fluent but factually incorrect or unsupported output.
Q7. Is an LLM generative or discriminative?
A. Generative — it models and samples from a distribution over possible text.
Q8. What architecture do modern LLMs use?
A. The Transformer (typically a decoder-only variant).
Q9. What's the difference between pretraining and fine-tuning?
A. Pretraining learns general language ability from huge raw text; fine-tuning further adapts the model on a smaller, task/behavior-specific dataset.
Q10. Why can't you just "tell the model to stop hallucinating"?
A. Hallucination comes from generating plausible continuations without a built-in fact-checking mechanism; instruction wording alone can't add real-time verification.

28. Interview Questions — Intermediate

Q1. Explain the difference between a base model and an instruction-tuned/chat model.
A. A base model only continues text plausibly from pretraining; instruction tuning (SFT) and RLHF/DPO further adapt it to follow instructions and converse helpfully and safely.
Q2. Why does input context cost money even though the model isn't "generating" it?
A. The model must process every input token through all layers (attention + feed-forward), consuming compute, so providers bill input tokens separately from output tokens.
Q3. What is a KV cache and why does it matter for performance?
A. It caches previously computed attention keys/values so each new generated token doesn't require recomputing attention over the whole sequence, making autoregressive generation much faster.
Q4. What's the difference between top-p and top-k sampling?
A. Top-k always samples from a fixed number of candidates; top-p (nucleus sampling) adapts the candidate pool size based on cumulative probability mass, so it naturally narrows when the model is confident and widens when uncertain.
Q5. Why is output generation slower than processing input of the same length?
A. Input tokens are processed in parallel in one forward pass; output tokens are generated sequentially, one at a time, each depending on the previous one.
Q6. What causes "the model forgot my earlier instruction" in a long conversation?
A. Context window limits and attention dilution across a long history — relevant instructions get diluted or pushed out as more content accumulates.
Q7. What is an emergent capability?
A. A capability (e.g., multi-step arithmetic) that appears only once model scale crosses some threshold, absent in smaller models trained the same way.
Q8. How does streaming change the user-perceived latency of an LLM response?
A. Streaming returns tokens as they're generated rather than waiting for the full response, so users see output start almost immediately even though total generation time is unchanged.
Q9. Why might the same prompt at temperature 0 occasionally still produce slightly different outputs?
A. Provider-side implementation details (batching, floating-point non-associativity, hardware-level nondeterminism) can introduce tiny variations even at the lowest-randomness setting.
Q10. What's the practical difference between RAG and relying on the model's parametric knowledge?
A. Parametric knowledge is frozen at training time and can be outdated/wrong; RAG injects fresh, verifiable, sourced information into the prompt at inference time.
Q11. Why do code and non-English text often use more tokens per character than English prose?
A. The tokenizer's vocabulary is typically trained with a bias toward common English patterns, so less-common scripts/symbols split into more, smaller tokens.
Q12. What's the risk of setting max_tokens too low?
A. The response can be truncated mid-thought or mid-structure (e.g., incomplete JSON), breaking downstream parsing.
Q13. Why is a reasoning model slower and more expensive than a standard model for the same question?
A. It generates additional internal reasoning tokens before the final answer, increasing total output tokens and latency even though the user-visible answer may be the same length.
Q14. How would you reduce the cost of a chat application with long conversation histories?
A. Summarize/compact older turns, cap history length, and use prompt/context caching for stable prefixes like the system prompt.
Q15. What does it mean that an LLM API call is "stateless"?
A. The model has no memory of prior calls; all context (history, instructions) must be explicitly resent each time.

29. Interview Questions — Advanced

Q1. Why can't you fully eliminate hallucination by lowering temperature to 0?
A. Hallucination stems from the model's learned knowledge and lack of grounding, not primarily from sampling randomness — even the single most-probable continuation can be factually wrong if that's what the training distribution favored.
Q2. Explain why "lost in the middle" happens with very long contexts.
A. Attention mechanisms don't weight all positions in a long context equally reliably; information placed in the middle of a huge context is statistically under-attended compared to content near the start or end, degrading retrieval/synthesis accuracy.
Q3. How does self-consistency sampling improve reliability, and what does it cost?
A. By sampling multiple independent reasoning paths and taking the majority/most consistent final answer, it reduces the chance a single unlucky sampling path dominates — at the cost of multiplying latency and token spend by the number of samples.
Q4. Why do dense, decoder-only Transformers dominate modern LLMs over encoder-decoder or RNN-based architectures?
A. Decoder-only architectures scale well with parallelizable training (unlike RNNs), unify pretraining and generation under one autoregressive objective, and have proven empirically to scale smoothly with data/compute (scaling laws), whereas encoder-decoder adds complexity mainly useful for specific seq2seq tasks like translation.
Q5. What's the architectural reason output tokens can't be generated in parallel the way input tokens are processed?
A. Each output token's probability distribution depends on all previously generated tokens (causal/autoregressive dependency) — you cannot compute token N+1 without first sampling token N, enforcing a sequential loop, unlike the fully parallel forward pass over a fixed input.
Q6. How would you detect that a model's "confidence" (output probability) is not a reliable indicator of correctness?
A. Compare token-level log-probabilities against factual correctness on a labeled eval set — models are frequently miscalibrated, especially after RLHF, often sounding equally confident whether correct or hallucinating, so you must validate against ground truth/retrieval, not the model's own probability.
Q7. Why might instruction tuning slightly degrade raw language-modeling capability compared to the base model?
A. SFT/RLHF optimize for a narrower distribution (helpful, aligned responses) which can trade off some of the raw diversity/calibration of the broader pretraining distribution — sometimes called the "alignment tax."
Q8. What's the difference between model-level nondeterminism and application-level nondeterminism in an LLM pipeline?
A. Model-level: sampling randomness, floating-point/batching effects inside the model itself. Application-level: nondeterminism introduced by your own pipeline — e.g., retrieval returning different documents due to index updates, or race conditions in concurrent tool calls — which can look like "the model is inconsistent" but isn't.
Q9. How do context-window limits interact with KV-cache memory usage in serving infrastructure?
A. KV-cache size grows linearly with sequence length and batch size; longer context windows directly increase GPU memory pressure per concurrent request, which is why serving very long contexts at high concurrency requires techniques like paged attention or cache eviction.
Q10. Why is "more parameters" not always better for a given production use case?
A. Larger models cost more and are slower per token; for narrow, well-defined tasks a smaller fine-tuned or well-prompted model can match quality at a fraction of the latency/cost — bigger models matter most for tasks needing broad generalization or complex reasoning.
Q11. What causes repetition loops in generated text, and how is it mitigated?
A. Greedy/low-temperature decoding can get stuck favoring a locally high-probability repeated phrase; mitigations include repetition penalties, frequency penalties, and slightly higher temperature/top-p.
Q12. Why is evaluating "hallucination rate" harder than evaluating classification accuracy?
A. Hallucination is open-ended (any claim could be wrong in many different ways, not a fixed label set), context-dependent (correctness may depend on retrieved sources), and often requires another model or human judge rather than exact-match scoring.
Q13. How does speculative decoding speed up LLM inference?
A. A smaller/faster "draft" model proposes several candidate next tokens, which the larger target model verifies in parallel in a single forward pass, accepting the matching prefix — reducing the number of expensive sequential forward passes of the large model.
Q14. Why might two different providers' models disagree substantially on temperature=0 output for the same prompt?
A. Different training data, alignment procedures, tokenizers, and even default sampling implementation details mean "deterministic" only means low-variance within that model, not convergence toward some shared ground truth across models.
Q15. What's the relationship between scaling laws and the decision to use a reasoning model vs a bigger non-reasoning model?
A. Scaling laws show predictable quality gains from more parameters/data/compute at pretraining time; reasoning models instead trade additional inference-time compute (more generated reasoning tokens) for quality gains on complex tasks — a different lever (test-time compute) than raw model size, often more cost-effective for reasoning-heavy, lower-volume workloads.

30. Interview Questions — Senior/Architect

Q1. How would you design model routing across multiple LLMs (cheap/fast vs expensive/reasoning) for a production chat product?
A. Classify incoming requests by estimated complexity (heuristics, a cheap classifier, or the first few tokens of a fast model's attempt), route simple queries to a small/fast model, escalate to a reasoning/frontier model on low-confidence or explicitly complex tasks, and track cost/quality metrics per route to continuously tune the routing policy.
Q2. A client wants byte-identical reproducibility from an LLM-based pipeline for compliance reasons. How do you respond?
A. Explain that true determinism isn't guaranteed even at temperature 0 due to provider-side implementation details; instead propose capturing full request/response pairs for audit logging, pinning model versions, and — if the use case truly needs determinism — moving the decision logic to deterministic code with the LLM used only for non-authoritative steps (e.g., drafting, not final decisions).
Q3. How would you architect fallback behavior when your primary LLM provider has an outage?
A. Maintain a provider abstraction layer (see 07-LLM-APIs-and-SDKs) with a secondary provider/model configured as fallback, circuit-breaker logic to detect sustained failures, health checks, and graceful degradation (e.g., serve cached/previous answers or a reduced-capability mode) rather than hard failing user-facing requests.
Q4. Your team wants to fine-tune a model to "fix hallucinations." Is this the right lever, and what would you recommend instead?
A. Fine-tuning can improve style/format/behavior consistency but doesn't give the model new verified facts or runtime fact-checking — it's the wrong lever for factual grounding. Recommend RAG for up-to-date/verifiable knowledge, and reserve fine-tuning for teaching behavior patterns (tone, output format, domain-specific reasoning style) rather than facts.
Q5. How do you estimate and budget for LLM inference cost at scale before launch?
A. Profile typical request/response token counts across representative use cases, multiply by expected request volume and provider per-token pricing, add margin for context growth (conversation history, RAG chunks), and build in monitoring/alerting on per-request and aggregate spend from day one, with model-routing as the primary cost lever.
Q6. How would you design observability for an LLM-powered production system?
A. Trace every request end-to-end (prompt, retrieved context, tool calls, final output, token usage, latency, cost) using something like LangSmith/Langfuse/OpenTelemetry, log at the span level per pipeline stage, and build dashboards/alerts on latency, error rate, token spend, and quality-proxy metrics (e.g., flagged hallucinations from an evaluator).
Q7. When would you advise against using an LLM at all for a given feature?
A. When the task is a bounded, stable classification/regression problem better solved by classic ML (cheaper, faster, more auditable); when outputs must be strictly deterministic/byte-reproducible; when latency budgets are far below LLM inference times; or when the "intelligence" required is really just rule-based logic that doesn't need language understanding.
Q8. How do you handle multi-tenant isolation when multiple customers share the same LLM-backed service?
A. Ensure no cross-tenant data leaks into context (strict per-tenant retrieval/data scoping), separate rate limits/quotas per tenant, avoid caching responses across tenant boundaries unless content is tenant-agnostic, and audit-log per-tenant usage for both security and billing.
Q9. How would you version and safely roll out a change to the underlying model (e.g., upgrading from one model version to a newer one)?
A. Run the new model against your evaluation suite/golden dataset first, A/B test on a small traffic percentage while monitoring quality and cost metrics, keep the old model available as instant rollback, and communicate behavior-change risk (even same-family model upgrades can shift output style/format).
Q10. How do you reconcile "bigger context windows" marketing claims with actual production retrieval quality?
A. Treat window size as a ceiling, not a target — validate empirically (via your own eval set) how retrieval/synthesis quality actually degrades as you add more context, and architect retrieval to maximize precision (fewer, more relevant chunks) rather than maximizing recall by stuffing the window.

31. Scenario-Based Questions

Scenario 1. Users report the chatbot "lies confidently" about company policy. How do you fix it?
A. Add RAG grounding against the actual policy documents, require citations, instruct the model to say "I don't know" when the retrieved context doesn't cover the question, and add an evaluation suite specifically testing policy-question faithfulness.
Scenario 2. Your LLM costs tripled after adding conversation history to every request. What do you do?
A. Audit token usage per request, implement history summarization/compaction after N turns, cap the number of retained turns, and consider prompt caching for the stable system prompt portion.
Scenario 3. A user pastes a webpage into the chat and the model starts following instructions embedded in that page instead of the user's request. What happened and how do you prevent it?
A. Indirect prompt injection — untrusted content contained instructions the model treated as commands. Prevent by clearly delimiting/labeling untrusted content as data, instructing the model explicitly to never follow instructions found inside quoted/retrieved content, and restricting tool permissions available during such interactions.
Scenario 4. Response times spike under load even though the model provider reports normal latency. Where do you look?
A. Check your own queuing/concurrency limits, rate-limit backoff/retry storms, context size growth under heavy sessions, and network/serialization overhead in your own service — "model latency" is often not the actual bottleneck.
Scenario 5. Leadership wants to swap your Claude integration for a cheaper model to cut costs, but quality dropped noticeably. How do you evaluate and communicate the trade-off?
A. Run both models against your evaluation suite (golden dataset with scored outputs), quantify the quality delta in business terms (e.g., task success rate, escalation rate), and present a cost-vs-quality trade-off with a recommended middle path (e.g., model routing: cheap model for easy cases, original model for hard cases) rather than an all-or-nothing swap.
Scenario 6. A compliance team asks "can you guarantee the model never outputs X?" How do you respond?
A. Explain that generative models can't offer hard guarantees on output content; propose defense-in-depth instead — strong system prompts, output guardrails/classifiers scanning generated text before it reaches the user, and human review for high-risk categories, with monitoring to catch and respond to failures.
Scenario 7. Your structured-output pipeline occasionally receives malformed JSON from the model. How do you make it robust?
A. Use the provider's structured-output/JSON-schema mode where available, validate with a schema library (e.g., Pydantic/Zod) and retry with an error-correction prompt on failure, and never directly `eval`/parse untrusted model output without validation.
Scenario 8. Two near-identical requests return very different quality answers. How do you debug this?
A. Diff the actual prompts/contexts sent (not just the user-facing question) — look for differences in retrieved context, conversation history length, or sampling parameters; log full requests/responses for exactly this kind of comparison.
Scenario 9. You need the model to never reveal its system prompt even if asked directly. How realistic is this, and what do you do?
A. No prompt is 100% unextractable from a sufficiently motivated adversary; treat the system prompt as not fully secret, avoid putting true secrets (API keys, confidential logic) in it, add instructions declining to reveal it, and rely on application-level access controls for anything truly sensitive.
Scenario 10. After a model provider update, your eval scores silently dropped 8%. What's your process?
A. This is why you pin model versions and run continuous eval monitoring — detect via automated eval-suite regression alerts, diff outputs on the same golden set before/after, and either roll back to the pinned version or adjust prompts/retrieval to recover quality before rolling the update out broadly.

32. Quick revision notes

  • LLM = Transformer decoder trained to predict next tokens.
  • Pretrain → instruction-tune (SFT) → align (RLHF/DPO) → optionally reasoning-train.
  • Every API call = stateless inference; no learning happens at call time.
  • Temperature/top-p/top-k control sampling randomness.
  • Hallucination is inherent to generation — mitigate via RAG/grounding, not prompting alone.
  • Input tokens process in parallel; output tokens generate sequentially (slower).

33. Cheat sheet

LLM = transformer trained to predict next tokens → pretrained (raw completion) → instruction-tuned (follows instructions) → RLHF/DPO-aligned (helpful/safe) → optionally reasoning-trained. Every API call is pure inference: tokenize → embed → attend → sample → repeat. Cost = input tokens + output tokens, priced separately. Hallucination is structural, not a bug — ground with RAG.
