1. What is this?

LLMs don't see raw characters — they see tokens, sub-word units produced by a tokenizer (e.g., byte-pair encoding / BPE). The context window is the hard limit on how many tokens (prompt + conversation history + retrieved docs + output) a single request can contain.

2. Why does it exist?

Tokenization exists because a fixed-size vocabulary must represent arbitrary text (any word, rare terms, code, emoji, other languages) efficiently — sub-word units let the model handle unseen words by composing known pieces instead of needing every possible word pre-registered. The context window exists because transformer self-attention cost grows (quadratically, in the naive form) with sequence length — hardware and architecture limits translate directly into a maximum processable sequence length.

3. Why is it important?

Tokens are the literal unit of both cost and capacity — every pricing decision, truncation bug, and "why did my prompt get cut off" incident traces back to token counting. Understanding this is foundational to building any reliable, cost-aware LLM application.

4. Where is it used?

Every LLM API call, every RAG pipeline (context budget for retrieved chunks), every agent loop (tracking conversation + tool-output tokens), every cost-estimation and billing system.

6. Core concepts

  • Tokenization is deterministic and reversible per model/tokenizer version — the same text always produces the same tokens for a given tokenizer.
  • The context window is shared between input and output — a large prompt leaves less room for the response.
  • "Lost in the middle": information buried deep in a huge context is statistically under-weighted by attention compared to content near the start/end.

8. Architecture

Raw text
 → Tokenizer (BPE/similar) → token IDs
 → [ System prompt tokens | History tokens | Retrieved context tokens | User message tokens ]
 → Total must be ≤ context window − reserved output tokens
 → Model processes all input tokens, generates output tokens up to the remaining budget

9. How it works internally

A tokenizer is trained once (on a large corpus) to build a fixed vocabulary of the most useful sub-word units via frequency-based merging (BPE or similar). At inference time, tokenization is just a lookup/greedy-merge process — fast and deterministic. Common English words are often single tokens; rare words, code symbols, and non-English text often use more tokens per character because the vocabulary was optimized for the training corpus's distribution.

10. Step-by-step explanation

  1. Raw input text is split into tokens by the tokenizer.
  2. Token count is checked against the model's context window.
  3. If under budget, all tokens (system + history + retrieved context + user message) are sent for processing.
  4. The model reserves remaining window space for output generation (set via `max_tokens`).
  5. If input would exceed the window, the application must truncate, summarize, or retrieve more selectively before sending.

11. Simple example

"unbelievable" might split into tokens like un, believ, able. Rule of thumb: ~4 characters ≈ 1 token in English prose; code and non-Latin scripts are typically less token-efficient.

12. Real-world example

A RAG chatbot with a 200K-token context window still can't just "retrieve everything" — stuffing in 150K tokens of marginally relevant documents dilutes attention and often produces worse answers than a well-ranked 10K-token context, despite technically fitting within the window.

13. Code example

import anthropic

client = anthropic.Anthropic()

# Count tokens before sending, to budget context usage
count = client.messages.count_tokens(
    model="claude-sonnet-5",
    messages=[{"role": "user", "content": "How many tokens is this sentence?"}],
)
print("Input tokens:", count.input_tokens)

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=100,
    messages=[{"role": "user", "content": "Summarize: " + "long document text..." }],
)
print("Output tokens used:", response.usage.output_tokens)

14. Advanced example

A token-budget manager for a multi-turn chat app that reserves space for output, caps history, and summarizes overflow:

MAX_WINDOW = 200_000
RESERVED_OUTPUT = 2_000

def fit_to_budget(system_tokens, history, retrieved_tokens, count_fn):
    budget = MAX_WINDOW - RESERVED_OUTPUT - system_tokens - retrieved_tokens
    while count_fn(history) > budget:
        history = summarize_oldest_turn(history)  # compact instead of hard-truncate
    return history

15. Common mistakes

  • Assuming "bigger context window" always improves answer quality — ignoring lost-in-the-middle effects.
  • Not reserving output token budget, causing responses to truncate mid-structure (e.g., incomplete JSON).
  • Estimating cost/length in "words" instead of actual tokens, leading to inaccurate budgeting.
  • Blindly concatenating full conversation history forever instead of summarizing/trimming it.

16. Best practices

  • Count tokens programmatically (API-provided counters) rather than estimating from character count for anything cost-sensitive.
  • Rank and trim retrieved context for relevance rather than maximizing recall by including everything that fits.
  • Place the most important instructions/content near the start or end of context, not buried in the middle.
  • Use prompt/context caching for stable, repeated prefixes (system prompts, static reference docs).

17. Production considerations

Implement a token-budget check before every request with graceful truncation/summarization rather than runtime errors. Monitor average/peak token usage per request type to catch runaway context growth (e.g., unbounded chat history) before it becomes a cost or reliability incident.

18. Security considerations

Large contexts increase the attack surface for prompt injection — more room for an attacker to embed instructions in retrieved/pasted content. Also, verbose contexts can inadvertently leak sensitive data (e.g., full documents) to logs/providers if not scoped carefully.

19. Performance considerations

Processing more input tokens increases latency (even though input is parallelized, more layers' worth of attention computation is needed); output token count dominates latency even more since generation is sequential. Prompt/context caching for repeated prefixes significantly reduces both latency and cost on subsequent calls.

20. Cost considerations

Cost scales directly with total tokens (input often priced lower than output per token). Trimming unnecessary context, summarizing history, and using caching for repeated static content are the primary token-cost levers.

21. Debugging/troubleshooting

  • Request errors with "context length exceeded": count tokens before sending and truncate/summarize proactively.
  • Response cuts off mid-sentence: increase `max_tokens` or check if input consumed most of the window, leaving little room for output.
  • Model ignores instructions given early in a long context: likely lost-in-the-middle or attention dilution — move critical instructions closer to the end, or shorten the context.

27. Interview Questions — Beginner

Q1. Is a token the same as a word?
A. No — a token is a sub-word unit from the tokenizer's vocabulary; common words are often one token, but longer or rarer words split into multiple tokens.
Q2. What is the context window?
A. The maximum number of tokens (input + output combined) a model can process in a single request.
Q3. Roughly how many characters is one token in English?
A. About 4 characters per token, as a rough rule of thumb.
Q4. Does the context window apply only to input, or input and output combined?
A. Both — input and output tokens share the same total context window budget.
Q5. What tokenization algorithm is commonly used by LLMs?
A. Byte-Pair Encoding (BPE) or similar sub-word tokenization schemes.
Q6. Why might code use more tokens than the same length of English prose?
A. Code symbols and formatting are often less common in the tokenizer's training distribution, so they split into more, smaller tokens.
Q7. What happens if your input + desired output exceeds the context window?
A. The request can error out or the response gets truncated, depending on the API and settings.
Q8. What is "long context"?
A. Models supporting very large context windows (128K to 1M+ tokens), enabling much more input text per request.
Q9. Is it always better to use the maximum context window available?
A. No — larger contexts can dilute attention ("lost in the middle") and increase cost/latency; relevance matters more than raw size.
Q10. What is context engineering?
A. Deliberately curating and ordering what content (instructions, history, retrieved docs) goes into the context window to get reliable model behavior.

28. Interview Questions — Intermediate

Q1. Why does input context cost money even though you're not generating it?
A. The model must process (attend over) every input token through all its layers, consuming compute just like generation — hence providers bill input and output tokens separately.
Q2. What's the "lost in the middle" phenomenon and why does it happen?
A. Information placed in the middle of a long context tends to be recalled/attended to less reliably than information near the start or end — likely related to how attention patterns and positional encodings behave over long sequences during training.
Q3. Why can increasing retrieved chunks in RAG from 5 to 50 sometimes make answers worse despite more information being available?
A. Adding many loosely relevant chunks introduces noise, dilutes attention on the truly relevant content, and can confuse answer synthesis — precision in retrieval often matters more than recall/volume.
Q4. What's prompt/context caching and when is it useful?
A. Reusing precomputed attention state for a repeated prefix (e.g., a stable system prompt or static reference document) across multiple requests, reducing redundant computation and therefore cost and latency — useful whenever the same large prefix is reused frequently.
Q5. How would you design token-budget management for a multi-turn chat product with RAG and tool calls?
A. Maintain a running token budget: reserve tokens for system prompt + expected output, summarize/compact older conversation turns, cap retrieved-context tokens with a reranker, and track real usage via the API's usage fields to catch budget overruns before they cause truncation or errors.
Q6. Why is "words per minute" or character count a poor proxy for cost estimation?
A. Token-to-character ratio varies by language, content type (code vs prose), and tokenizer, so character-based estimates can be significantly off from actual billed token counts.
Q7. What's a practical reason to summarize conversation history rather than simply truncating the oldest messages?
A. Truncation can silently drop important earlier context (e.g., a key constraint the user stated); summarization preserves the gist while reducing token count, maintaining more continuity.
Q8. How does context window size interact with KV-cache memory usage during serving?
A. KV-cache size grows with sequence length (and batch size); longer contexts directly increase memory pressure on the serving infrastructure per concurrent request.
Q9. Why might two semantically identical prompts have different token counts?
A. Different phrasing, word choice, or formatting (e.g., extra whitespace, different punctuation) can tokenize differently even if the meaning is equivalent.
Q10. What's the risk of not reserving output token budget separately from input budget?
A. If input consumes nearly the entire context window, there may be too little room left for `max_tokens`, causing truncated or empty responses.
Q11. Why do some teams build a custom reranking step before stuffing retrieved chunks into context, rather than relying on the LLM to "figure out" what's relevant?
A. Rerankers are cheaper and more precise at filtering relevance than relying on the LLM's attention over a noisy, over-stuffed context — it's more reliable to do relevance filtering explicitly before the expensive generation step.
Q12. How would you test whether your RAG system suffers from lost-in-the-middle effects?
A. Construct eval cases where the correct answer's supporting chunk is deliberately placed at different positions (start, middle, end) within the retrieved context, and measure whether accuracy drops when it's in the middle.
Q13. What's a reasonable strategy when a single document is larger than the model's context window?
A. Chunk the document and use retrieval (RAG) to select only relevant chunks, or use a map-reduce summarization approach (summarize chunks, then summarize the summaries) rather than attempting to fit the whole document at once.
Q14. Why is tokenization deterministic, and why does that matter for caching?
A. The same text always maps to the same token sequence for a given tokenizer version, which is what makes prefix-based prompt caching reliable — the cached prefix's tokens are guaranteed identical across repeated calls as long as the text itself hasn't changed.
Q15. How does model provider tokenizer difference affect cross-provider cost comparison?
A. The same text can tokenize into different counts across providers/tokenizers, so comparing "$ per token" alone across providers can be misleading — compare actual $ per request/task on representative content instead.

29. Interview Questions — Advanced

Q1. Explain why self-attention's naive computational cost grows quadratically with sequence length, and how this bounds context window size.
A. Standard self-attention computes pairwise interactions between every pair of tokens in the sequence (an N×N attention matrix for N tokens), so compute and memory scale roughly quadratically with N — this is the core architectural reason context windows have practical upper bounds, though techniques like sparse/linear attention and efficient KV-cache management push that bound higher.
Q2. How would you architect a system that needs to reason over a corpus far larger than any single context window (e.g., millions of documents)?
A. Use retrieval (vector search + reranking) to select only the most relevant subset per query rather than attempting to fit the corpus into context at all; for tasks needing broader synthesis, use hierarchical/map-reduce summarization or an agentic multi-step retrieval loop that iteratively narrows down relevant content.
Q3. Why might increasing context window size alone not solve a RAG accuracy problem, even if the correct document is successfully retrieved?
A. If the correct document's key passage lands in a "lost in the middle" position among many other retrieved chunks, the model may still fail to use it correctly — the fix is about retrieval precision and context ordering/ranking, not raw window capacity.

30. Interview Questions — Senior/Architect

Q1. Design a context-budget management system for a production multi-agent platform with RAG, long conversation history, and tool outputs all competing for context space.
A. Implement a central token-budget allocator that reserves fixed slices for system/tool instructions, dynamically ranks and caps retrieved RAG content via a reranker, summarizes/compacts conversation history beyond a turn threshold, logs real usage per component, and alerts when any component's typical usage approaches its allocated slice — treating context space like a scarce, explicitly managed resource rather than an afterthought.
Q2. How would you reconcile marketing claims of "1M token context windows" with your own production evaluation findings that quality degrades well before that limit?
A. Treat the advertised window as a hard ceiling, not a target; run your own empirical evaluation (precision/recall on retrieval, task success rate) as a function of context size on your actual data, and set internal guidelines/limits based on measured quality degradation points rather than the provider's maximum.

31. Scenario-Based Questions

Scenario 1. Your RAG system's answers got worse after the team increased retrieved chunks from 5 to 50 to "be safe." How do you diagnose and fix it?
A. Suspect attention dilution/lost-in-the-middle; run an eval comparing both configurations on a labeled set, and if confirmed, reduce chunk count but improve retrieval precision (better embeddings, reranking) instead of relying on volume.
Scenario 2. Users report the chat app "forgets" instructions given 20 messages ago. What's your fix?
A. Diagnose whether this is lost-in-the-middle (long history diluting attention) or actual truncation (history exceeded context window); implement conversation summarization/compaction and consider re-stating critical constraints near the end of context on each turn.
Scenario 3. Finance flags unexpectedly high LLM costs this month. Token usage logs show average request size tripled. How do you investigate?
A. Check whether conversation history is being capped/summarized as intended, check if retrieved-context size grew (e.g., a reranker was disabled or chunk size increased), and audit for any new feature sending redundant or oversized context.

32. Quick revision notes

  • Token ≈ sub-word unit (~4 chars/token in English).
  • Context window = shared budget for input+output.
  • Bigger window ≠ automatically better — use context engineering (rank, trim, place strategically) over "dump everything."
  • Prompt/context caching cuts cost/latency for repeated prefixes.
