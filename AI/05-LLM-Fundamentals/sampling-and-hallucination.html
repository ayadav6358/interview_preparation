1. What is this?

At each generation step, the model produces a probability distribution over the entire vocabulary for "what token comes next." Sampling is the process of turning that distribution into an actual chosen token, controlled by temperature, top-p, and top-k. Hallucination is fluent, confident, plausible-sounding output that is factually incorrect, unsupported, or inconsistent with provided context.

2. Why does it exist?

Sampling controls exist because pure "always pick the highest probability token" (greedy decoding) produces repetitive, bland, sometimes looping text; controlled randomness produces more natural and varied output. Hallucination exists as an inherent consequence of generative sampling from a learned distribution that has no built-in fact-checking or grounding mechanism by default — the model is optimized to be plausible, not necessarily correct.

3. Why is it important?

Misunderstanding sampling leads to picking the wrong settings for a task (e.g., high temperature for data extraction, causing inconsistent results). Misunderstanding hallucination leads to shipping products that confidently state wrong facts to users — one of the most common and damaging failure modes in production GenAI systems.

4. Where is it used?

Every text-generation API call exposes sampling parameters. Hallucination mitigation is relevant anywhere an LLM output could be presented as fact: chatbots, summarization, Q&A, code generation, RAG systems.

6. Core concepts

  • Greedy decoding (temperature 0) always picks the single most probable next token — deterministic but can be repetitive/bland.
  • Sampling methods (temperature, top-p, top-k) introduce controlled randomness for more natural, varied text.
  • Hallucination is structural, not a bug to be "fixed" by prompting alone — mitigation requires external grounding.

7. Terminology

TermMeaning
TemperatureScales the probability distribution before sampling; 0 ≈ deterministic, higher = more diverse/random.
Top-p (nucleus sampling)Samples only from the smallest set of tokens whose cumulative probability ≥ p.
Top-kSamples only from the k most probable tokens.
Greedy decodingAlways picks the single highest-probability token (equivalent to temperature → 0).
HallucinationFluent but factually incorrect or unsupported output.
GroundingTying model output to verifiable external sources (e.g., via RAG) to reduce hallucination risk.
Self-consistencySampling multiple outputs and taking the majority/most consistent answer for higher reliability.

8. Architecture

Model's raw output logits (one score per vocabulary token)
 → scaled by temperature
 → restricted by top-p and/or top-k to a candidate pool
 → converted to a probability distribution over that pool
 → sampled → next token

9. How it works internally

The model outputs unnormalized scores (logits) for every token in the vocabulary. Temperature divides logits before the softmax normalization: lower temperature sharpens the distribution (making the top token even more dominant), higher temperature flattens it (making many tokens more competitive). Top-p/top-k then restrict which tokens are even eligible to be sampled, before the final random draw.

10. Step-by-step explanation

  1. Model computes logits for every token in the vocabulary given current context.
  2. Logits are divided by temperature, then passed through softmax to get probabilities.
  3. Top-p and/or top-k filter the candidate pool to the most likely subset.
  4. A token is randomly drawn from that filtered, re-normalized distribution.
  5. The chosen token is appended; the process repeats for the next token.

11. Simple example

Prompt: "The capital of France is" → the model assigns very high probability to "Paris." At temperature 0, it's always chosen; at higher temperature, a less likely (and possibly wrong) token has a small but nonzero chance of being sampled instead.

12. Real-world example

A legal-document summarizer set at temperature 0.7 occasionally invents a clause that "sounds like" standard legal boilerplate but doesn't actually appear in the source document — a classic hallucination caused by the model filling gaps with plausible-sounding learned patterns rather than grounded extraction.

13. Code example

from anthropic import Anthropic
client = Anthropic()

# Deterministic-ish: good for extraction / structured tasks
precise = client.messages.create(
    model="claude-sonnet-5", max_tokens=50, temperature=0,
    messages=[{"role": "user", "content": "Extract the city from: 'I live in Austin, Texas.'"}]
)

# Creative: good for brainstorming
creative = client.messages.create(
    model="claude-sonnet-5", max_tokens=200, temperature=0.9,
    messages=[{"role": "user", "content": "Brainstorm 5 unusual startup ideas about coffee."}]
)

14. Advanced example

Self-consistency sampling for a hard reasoning question: sample N completions at moderate temperature, extract each candidate's final answer, and return the majority vote — trading cost for reliability on high-stakes, lower-volume questions.

answers = []
for _ in range(5):
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=300, temperature=0.7,
        messages=[{"role": "user", "content": "Solve step by step, then give final answer: ..."}]
    )
    answers.append(extract_final_answer(resp.content[0].text))

from collections import Counter
majority_answer = Counter(answers).most_common(1)[0][0]

15. Common mistakes

  • Using high temperature for factual extraction/classification tasks, introducing unnecessary inconsistency.
  • Believing temperature=0 fully eliminates hallucination — it only reduces sampling-driven variance, not knowledge errors.
  • Combining top-p and top-k carelessly without understanding how they interact (both apply as filters; the more restrictive one dominates).
  • Not testing sampling parameter changes against an evaluation set before deploying to production.

16. Best practices

  • Use low temperature (0–0.3) for extraction, classification, structured output, code.
  • Use higher temperature (0.6–1.0) for creative writing, brainstorming, varied content generation.
  • Ground factual claims with RAG and require citations rather than relying on sampling settings alone.
  • Use self-consistency sampling only for high-stakes, lower-volume decisions due to its cost multiplier.

17. Production considerations

Pin sampling parameters per use case and version them like code — a silent default change by a provider can shift product behavior. Monitor hallucination-prone tasks (e.g., via LLM-as-judge or user feedback) continuously, since hallucination rate isn't a one-time-measured constant.

18. Security considerations

Hallucinated outputs presented as authoritative (e.g., fabricated security advice, invented API behavior in generated code) can cause real harm if trusted blindly — always validate/sandbox LLM-generated code or security-relevant content rather than executing it unchecked.

19. Performance considerations

Sampling parameter choice doesn't materially affect latency (the forward pass cost is the same); self-consistency sampling (multiple full generations) does multiply latency and cost linearly with sample count.

20. Cost considerations

Self-consistency and other multi-sample techniques directly multiply token spend — reserve them for cases where the accuracy gain justifies N× the cost of a single call.

21. Debugging/troubleshooting

  • Outputs too repetitive/bland: raise temperature or top-p slightly.
  • Outputs too random/incoherent: lower temperature, tighten top-p/top-k.
  • Model confidently states something false: this is hallucination, not a sampling bug — add retrieval grounding, ask for citations, or add a verification pass.
  • Inconsistent results across identical requests: check that temperature isn't accidentally left high for a task needing determinism.

27. Interview Questions — Beginner

Q1. What does temperature=0 mean?
A. It makes generation nearly deterministic — the model almost always picks the highest-probability next token (greedy decoding), reducing randomness/creativity.
Q2. What is hallucination in the context of LLMs?
A. Fluent, confident output that is factually wrong, fabricated, or unsupported by the given context.
Q3. What does top-p (nucleus sampling) control?
A. It restricts sampling to the smallest set of tokens whose cumulative probability reaches a threshold p, adapting pool size to model confidence.
Q4. What does top-k control?
A. It restricts sampling to only the k most probable next tokens, regardless of their probability mass.
Q5. Is hallucination a bug that can be fully patched?
A. No — it's an inherent property of generative sampling without built-in fact-checking; it can only be mitigated, not fully eliminated.
Q6. Which sampling setting would you use for extracting a date from text?
A. Low temperature (near 0), for consistent, deterministic extraction.
Q7. Which sampling setting would you use for brainstorming creative ideas?
A. Higher temperature (e.g., 0.7–1.0), for more diverse, varied output.
Q8. What is greedy decoding?
A. Always picking the single highest-probability next token at each step — equivalent to temperature near 0.
Q9. Name one way to reduce hallucination in a Q&A system.
A. Ground answers with retrieval (RAG) against verified source documents.
Q10. Does higher temperature make the model "smarter"?
A. No — it only increases output randomness/diversity; it has no effect on the model's actual knowledge or reasoning ability.

28. Interview Questions — Intermediate

Q1. Why can't you fully eliminate hallucination just by setting temperature to 0?
A. Hallucination stems from the model's learned (possibly wrong or outdated) knowledge and lack of grounding, not just from sampling randomness — even the single most-probable continuation can be factually wrong if that's what the training distribution favored.
Q2. Explain the difference between top-p and top-k sampling with an example where they'd behave differently.
A. Top-k always considers exactly k candidates regardless of confidence. Top-p adapts: if the model is very confident (one token has 95% probability), top-p with p=0.9 might consider only 1–2 tokens; if the model is uncertain, top-p considers more candidates. Top-k could force inclusion of low-probability "wrong" candidates when the model is confident, or force too narrow a set when it's uncertain.
Q3. Why might a model hallucinate more on questions about recent events than on well-established facts?
A. The model's parametric knowledge is frozen at its training cutoff; for events after that cutoff, it has no real knowledge and will generate plausible-sounding but fabricated details unless grounded via retrieval.
Q4. What's the trade-off of self-consistency sampling?
A. It improves accuracy on hard reasoning tasks by sampling multiple reasoning paths and taking a majority answer, but multiplies cost and latency by the number of samples — only worth it for high-stakes, lower-volume calls.
Q5. Why is asking the model to "cite sources" not a complete hallucination fix on its own?
A. Without actual retrieval grounding, the model can hallucinate plausible-looking but fake citations just as easily as it hallucinates facts — citations need to be verified against real retrieved content, not just requested in the prompt.
Q6. How would you measure hallucination rate for a RAG system in an automated evaluation pipeline?
A. Use an LLM-as-judge or rule-based checker to compare each claim in the generated answer against the retrieved source documents, flagging claims not supported by any source, and aggregate the unsupported-claim rate across a labeled eval set.
Q7. Why might combining a very low top-p with a very high top-k (or vice versa) be redundant?
A. The more restrictive of the two filters effectively determines the candidate pool — if top-p already narrows to 3 tokens, setting top-k to 50 has no additional effect, and vice versa.
Q8. What's a concrete production risk of using high temperature for a code-generation feature?
A. Increased chance of syntactically or logically inconsistent code across repeated generations for the same prompt, making the feature feel unreliable and harder to test/cache.
Q9. How does hallucination differ from a model simply being "wrong" due to lack of training data on a topic?
A. They're related but distinct: lack of training data causes genuine uncertainty that should ideally produce a hedge or "I don't know"; hallucination is the failure mode where the model instead generates a confident, fabricated-sounding answer despite that uncertainty.
Q10. Why would you want a model to explicitly be instructed to say "I don't know" when context is insufficient?
A. Without that explicit permission/instruction, models are statistically biased toward generating a plausible-sounding answer rather than admitting uncertainty, since confident completions were more common in training data than hedged ones.

29. Interview Questions — Advanced

Q1. How would you design an automated hallucination-detection system for a production RAG pipeline, and what are its failure modes?
A. Use a secondary LLM-as-judge pass that cross-checks each claim in the generated answer against the retrieved source documents, scoring claim-level support; failure modes include the judge model itself hallucinating a "supported" verdict, subtle paraphrasing that's technically unsupported but judged as fine, and cost/latency overhead from the extra verification call.
Q2. Why might a reasoning model still hallucinate even after producing seemingly rigorous step-by-step reasoning?
A. Chain-of-thought reasoning improves logical consistency and reduces certain error classes, but the reasoning itself is still generated text — it can contain plausible-sounding but incorrect intermediate claims (e.g., citing a wrong fact mid-reasoning) that then get carried forward into a confidently stated, still-wrong final answer.
Q3. How would you calibrate a model's stated confidence to actually correlate with correctness?
A. Post-hoc calibration techniques: collect a labeled dataset of model answers with correctness labels, analyze whether the model's self-reported confidence (if elicited via prompting) or token-level log-probabilities correlate with actual accuracy, and if not, build an external calibration layer (e.g., a secondary classifier) rather than trusting the model's native confidence signal.

30. Interview Questions — Senior/Architect

Q1. You're building a financial-advice chatbot. How do you architect against hallucination given it's a generative model?
A. Ground every factual claim in retrieved, auditable sources (RAG) with mandatory citations; keep temperature low; constrain outputs to a validated schema separating "facts from source" vs "general guidance"; add a verification/guardrail pass that flags unsupported claims; require human review for high-stakes recommendations; log everything for audit/compliance.
Q2. How would you set organization-wide sampling parameter defaults and governance across many LLM-powered features built by different teams?
A. Publish guidelines mapping task type to recommended temperature/top-p ranges (e.g., extraction: 0; creative: 0.7+), require teams to justify deviations in code review, version sampling parameters alongside prompts in source control, and run eval-suite regression checks whenever defaults change.
Q3. A regulator asks you to prove your system doesn't hallucinate on a specific class of high-stakes questions. How do you respond?
A. Explain that a hard guarantee against hallucination isn't possible for any generative system; present instead a defense-in-depth evidence package: grounding architecture (RAG with citations), automated+human evaluation results on a representative test set, monitoring/alerting for detected hallucinations in production, and an escalation/human-review process for the highest-stakes question classes.

31. Scenario-Based Questions

Scenario 1. A customer-support bot occasionally invents a refund policy that doesn't exist. How do you fix it?
A. Ground all policy answers in RAG against the actual current policy documents, require the model to quote/cite the specific policy clause, and instruct it to say it doesn't know rather than guess when no matching policy is found.
Scenario 2. Your code-generation tool sometimes produces code calling APIs/functions that don't exist. What's happening and how do you reduce it?
A. Classic hallucination — the model generates plausible-sounding but fabricated API usage based on general patterns rather than your actual codebase; mitigate by grounding generation in actual repo context (retrieval over real code/docs) and validating/compiling generated code before presenting it as final.
Scenario 3. Leadership wants to increase temperature across all production features to make outputs "feel more natural." What do you flag?
A. Flag that this is a blanket change affecting tasks with very different needs — factual/extraction features will become less consistent and more hallucination-prone, while only genuinely creative features benefit; recommend per-feature tuning validated against each feature's own eval set instead of a global change.

32. Quick revision notes

  • Temperature/top-p/top-k control randomness of next-token sampling.
  • Hallucination is inherent to generation, not a bug.
  • Mitigate via RAG, low temperature for factual tasks, structured output + validation, citations, and human review — not by "asking it to be careful."
  • Self-consistency trades cost for reliability on hard reasoning tasks.

33. Cheat sheet

Temperature/top-p/top-k control randomness of next-token sampling. Hallucination is inherent to generation, not a bug — mitigate via RAG, low temperature for factual tasks, structured output + validation, citations, and human review, not by "asking it to be careful."
