1. What is this?

Cost optimization for LLM applications covers token optimization, prompt/context caching, model routing (cheap vs. frontier models), batch processing, semantic caching, and context reduction — the practical levers for controlling what's often the largest line-item cost in a production AI system.

2. Why does it exist?

Unlike traditional software where compute cost is often a minor line item, LLM token costs scale directly and significantly with usage — cost optimization exists because naive implementations can be 10-100x more expensive than necessary for the same user-facing quality.

3. Why is it important?

Cost is frequently the limiting factor determining whether an AI feature is viable at scale — every technique covered elsewhere in this knowledge base (model routing, caching, RAG precision) ultimately connects back to this practical bottom line.

4. Where is it used?

Every production LLM application at meaningful scale; especially critical for high-volume consumer products and agentic systems with multi-call loops.

5. Prerequisites

Tokens & Context Window, LLM APIs and SDKs.

6. Core concepts

  • Token optimization: reducing unnecessary tokens in prompts/context without sacrificing quality.
  • Prompt/context caching: reusing precomputed attention state for repeated prefixes (e.g., stable system prompts), reducing cost/latency on cache hits.
  • Model routing: sending simple tasks to cheap/fast models, complex tasks to frontier models.
  • Small vs large models: matching model capability to task complexity rather than defaulting to the most powerful (and expensive) option everywhere.
  • Batch processing: using a provider's batch API for non-real-time workloads, often at a cost discount.
  • Semantic caching: caching responses for semantically similar (not just identical) queries.
  • Context reduction: summarization/compaction of history, precise retrieval instead of over-fetching.

8. Architecture

      → Hit: return cached response (near-zero cost)
      → Miss: continue
 → Model routing (classify complexity)
      → Simple: cheap/fast model
      → Complex: frontier model
 → Prompt/context caching for stable prefixes (system prompt, static docs)
 → Response + cost logging

9. How it works internally

Prompt caching works by having the provider cache the internal attention computation (KV cache) for a prompt prefix, so a subsequent request sharing that exact prefix skips recomputing attention for those tokens — billed at a steep discount compared to processing them fresh. Semantic caching works differently: it embeds incoming queries and checks similarity against previously-answered queries, serving a cached response if similarity exceeds a threshold — appropriate for FAQ-style workloads with repeated semantically-similar questions, but risky for tasks needing precise, query-specific answers.

10. Step-by-step: a cost optimization audit

  1. Log token usage and cost per request, broken down by feature/endpoint.
  2. Identify the highest-cost features/endpoints by volume × per-request cost.
  3. For each, ask: does this need the current model tier? Is context over-sized? Is there repeated/cacheable content?
  4. Apply the appropriate lever (routing, caching, context reduction) per finding.
  5. Re-measure cost and quality after each change — never trade quality for cost without evaluation.

11. Simple example

Routing simple FAQ-style questions to a fast/cheap model tier and only escalating genuinely complex, multi-step reasoning questions to a frontier model — cutting average cost per request significantly for a support chatbot where most questions are simple.

12. Real-world example

A company implements prompt caching for its RAG system's large, static system prompt (containing formatting instructions and tool definitions), cutting the input-token cost for that unchanging portion of every request by a significant discount, compounding across millions of daily requests into substantial savings.

13. Code example (cost calculator)

PRICING = {  # illustrative $ per 1M tokens
    "frontier": {"input": 3.00, "output": 15.00},
    "fast": {"input": 0.25, "output": 1.25},
}

def estimate_cost(model_tier, input_tokens, output_tokens):
    rates = PRICING[model_tier]
    return (input_tokens / 1_000_000 * rates["input"]) + (output_tokens / 1_000_000 * rates["output"])

def compare_routing_savings(num_requests, pct_simple, avg_in, avg_out):
    all_frontier = estimate_cost("frontier", avg_in, avg_out) * num_requests
    routed = (estimate_cost("fast", avg_in, avg_out) * num_requests * pct_simple +
              estimate_cost("frontier", avg_in, avg_out) * num_requests * (1 - pct_simple))
    return {"all_frontier_cost": all_frontier, "routed_cost": routed, "savings": all_frontier - routed}

print(compare_routing_savings(num_requests=100_000, pct_simple=0.8, avg_in=500, avg_out=200))

14. Advanced example (semantic caching)

cache_store = []  # list of (embedding, query, response)

def semantic_cache_lookup(query, threshold=0.95):
    q_vec = embed(query)
    for cached_vec, cached_query, cached_response in cache_store:
        if cosine_similarity(q_vec, cached_vec) >= threshold:
            return cached_response
    return None

def answer_with_cache(query):
    cached = semantic_cache_lookup(query)
    if cached:
        return cached  # near-zero cost
    response = generate_llm_response(query)
    cache_store.append((embed(query), query, response))
    return response

15. Common mistakes

  • Defaulting to the most expensive/capable model for every request regardless of task complexity.
  • Semantic caching with too loose a similarity threshold, serving wrong cached answers to subtly different questions.
  • Not monitoring token usage per feature, missing the actual cost drivers.
  • Retrieving far more RAG context than needed "to be safe," inflating generation cost without quality benefit.

16. Best practices

  • Route by task complexity; don't use a frontier model for everything by default.
  • Use prompt caching for any stable, repeated prefix (system prompts, static reference docs).
  • Tune semantic cache similarity thresholds carefully and monitor for incorrect cache hits.
  • Measure and attribute cost per feature/endpoint continuously, not just in aggregate.

17. Production considerations

Build cost monitoring and attribution into observability from day one (see LLM Observability); set budget alerts per feature to catch regressions (e.g., unbounded context growth) before they become large bills.

18. Security considerations

Semantic/exact caching must respect tenant/user data isolation — never serve a cached response containing one user's data to a different user's semantically similar query.

19. Performance considerations

Caching (prompt or semantic) typically improves both cost and latency simultaneously — a rare case where the cost optimization directly benefits user experience too.

20. Cost considerations (meta)

Cost optimization itself has engineering cost (building routing logic, cache infrastructure, evaluation to ensure quality isn't sacrificed) — prioritize optimizations by actual cost impact (highest-volume, highest-cost features first) rather than optimizing uniformly everywhere.

21. Debugging/troubleshooting

  • Costs higher than expected despite "optimization": verify caching is actually hitting (check cache hit rate) and routing logic is correctly classifying requests as simple vs. complex.
  • Semantic cache serving wrong answers: tighten the similarity threshold and audit a sample of cache hits for correctness.
  • Model routing misclassifying complex requests as simple: review and refine the complexity classifier/heuristic against real failure examples.

27. Interview Questions — Beginner

Q1. What is model routing in the context of cost optimization?
A. Sending simple tasks to cheap/fast models and complex tasks to frontier models, rather than using one model tier for everything.
Q2. What is prompt/context caching?
A. Reusing precomputed attention state for a repeated prefix (like a stable system prompt), reducing cost/latency on subsequent requests sharing that prefix.
Q3. What is semantic caching?
A. Caching responses for semantically similar (not just identical) queries, using embedding similarity to detect matches.
Q4. What is a Batch API used for in cost optimization?
A. Processing non-real-time bulk workloads asynchronously, often at a cost discount compared to real-time calls.
Q5. Why is retrieving too much RAG context a cost problem?
A. More retrieved context means more input tokens, directly increasing generation cost without necessarily improving (and sometimes hurting) answer quality.
Q6. Does caching usually help or hurt latency alongside cost?
A. It usually helps both — a cache hit is both cheaper and faster than a fresh LLM call.
Q7. What's a risk of semantic caching with too loose a similarity threshold?
A. Serving an incorrect cached answer to a query that's similar but not actually asking the same thing.
Q8. Why should you log token usage per feature/endpoint, not just in aggregate?
A. To identify which specific features are actually driving cost, enabling targeted optimization rather than guessing.
Q9. Should you always use the most capable/expensive model for best quality?
A. No — matching model capability to task complexity often achieves similar quality at much lower cost for simpler tasks.
Q10. What's one way to reduce cost from conversation history growth?
A. Summarize/compact older turns rather than sending the full unbounded history on every request.

28. Interview Questions — Intermediate

Q1. How does prompt caching achieve its cost discount technically?
A. The provider caches the internal attention computation (KV cache) for a matching prompt prefix, so subsequent requests sharing that exact prefix skip recomputing attention for those tokens, billed at a discount compared to fresh processing.
Q2. Why must semantic caching respect tenant/user data isolation just like RAG retrieval?
A. A cached response generated for one user's query could contain that user's specific data; serving it to a different user whose query is merely semantically similar would constitute a data leak, just as an improperly-scoped RAG retrieval would.
Q3. What's a practical approach to building a "complexity classifier" for model routing without a dedicated training pipeline?
A. Start with simple heuristics (query length, presence of multi-step keywords, whether it's a known simple-FAQ pattern) or a cheap LLM call specifically prompted just to classify complexity, validating the classifier's routing decisions against a labeled set of known-simple and known-complex examples before trusting it in production.
Q4. Why might aggressive context reduction (summarization) sometimes hurt quality more than it saves in cost?
A. Summarization can lose nuanced details needed for a later, more specific question — if the lost information causes incorrect answers or additional clarification round-trips, the net effect (extra turns, degraded user experience) can outweigh the token savings from the shorter context.
Q5. How would you measure whether a model-routing cost optimization actually preserved quality?
A. Run the routed system against an evaluation golden set covering both simple and complex query types, comparing quality metrics before and after the routing change — cost savings alone don't validate the optimization; quality must be confirmed unchanged (or acceptably impacted) via evaluation.

29. Interview Questions — Advanced

Q1. How would you design a dynamic cost-optimization system that automatically adjusts routing thresholds based on observed quality/cost trade-offs over time?
A. Continuously log outcomes (quality signals like user feedback or escalation rate) alongside routing decisions, periodically analyze whether the "simple" tier's error/escalation rate for specific query patterns exceeds an acceptable threshold, and adjust routing rules (or retrain the complexity classifier) to shift the boundary — effectively a feedback loop tuning the cost/quality trade-off empirically rather than via a fixed, manually-set threshold.
Q2. What's a subtle interaction between prompt caching and frequently-changing system prompts that could reduce caching's effectiveness?
A. If the system prompt includes any dynamic content (e.g., a timestamp, a per-request variable) even in a small portion, the cached prefix match can break entirely since caching typically requires an exact prefix match — structuring prompts to keep genuinely static content separate from dynamic content (placing dynamic parts after the cacheable static prefix) preserves caching effectiveness.

30. Interview Questions — Senior/Architect

Q1. Design a comprehensive cost-governance program for a company running dozens of AI features across many teams.
A. Mandate per-feature token/cost logging and attribution as a standard requirement (via a shared observability/gateway layer); establish company-wide model-routing guidelines and a shared complexity-classification utility teams can reuse rather than each building their own; require evaluation-gated validation for any cost optimization claiming savings (no quality trade-off without explicit, measured sign-off); set per-team cost budgets with alerting; and run periodic cost-audit reviews identifying the highest-cost features company-wide for targeted optimization investment.

31. Scenario-Based Questions

Scenario 1. After implementing model routing to cut costs, customer satisfaction scores dropped slightly. What do you investigate?
A. Check whether the complexity classifier is misrouting some genuinely complex queries to the cheap model tier, review a sample of low-satisfaction interactions to see which tier handled them, and consider tightening the routing threshold (routing more borderline cases to the frontier model) based on this evidence.
Scenario 2. Your semantic cache's hit rate looks great, but a user reported receiving an answer meant for a completely different question. What's the fix?
A. Tighten the similarity threshold used for cache hits, audit a sample of recent cache hits for correctness to gauge how widespread the issue is, and consider adding a secondary verification step (e.g., a quick check that the cached answer is still contextually appropriate) before serving cached responses for ambiguous similarity scores.

32. Quick revision notes

  • Model routing: match model tier to task complexity.
  • Prompt caching: cache stable prefixes for cost+latency win.
  • Semantic caching: cache similar (not just identical) queries — tune threshold carefully, respect tenant isolation.
  • Always validate cost optimizations against an evaluation set — never trade quality blindly.

33. Cheat sheet

Model routing (cheap vs frontier) + prompt caching (stable prefixes) + semantic caching (similar queries, tuned threshold) + batch API (non-real-time) + context reduction. Always validate against an eval set — never trade quality blindly for cost.
