1. What is this?

AI infrastructure covers the deployment layer for AI applications and self-hosted models: containerization (Docker), orchestration (Kubernetes), GPU provisioning, cloud platforms (AWS/Azure/GCP), model serving, and CI/CD pipelines adapted for AI-specific artifacts (models, embeddings, prompts).

2. Why does it exist?

AI applications need the same deployment rigor as any production software, plus AI-specific concerns (GPU resource management, model versioning, large artifact storage) that standard web-app infrastructure patterns don't fully address out of the box.

3. Why is it important?

Most of this knowledge base's "production considerations" sections ultimately rely on this infrastructure layer existing and being well-designed — it's the operational foundation everything else runs on.

4. Where is it used?

Any self-hosted model deployment, any production AI application requiring reliable, scalable infrastructure, CI/CD for AI-specific artifacts.

5. Prerequisites

General software infrastructure familiarity; LLM Inference for GPU-specific context.

6. Core concepts

  • Docker: containerizing AI services (including model serving engines) for consistent, portable deployment.
  • Kubernetes: orchestrating containerized AI workloads at scale, including GPU-aware scheduling.
  • GPU provisioning: allocating and managing GPU resources, often the most expensive and contended infrastructure resource for self-hosted AI.
  • Model serving: deploying model inference as a reliable, scalable service (see LLM Inference for the engine-level detail).
  • CI/CD for AI: automated pipelines for testing/deploying not just code but prompts, evaluation suites, and (if applicable) model artifacts.

7. Terminology

TermMeaning
GPU schedulingKubernetes' mechanism for allocating GPU resources to pods, typically via device plugins.
Model registryA system for versioning and tracking model artifacts (and sometimes prompts/configs) through their lifecycle.
AutoscalingAutomatically adjusting the number of running instances based on load.
Cold startThe latency penalty when scaling up a new instance that needs to load a large model into memory first.

8. Architecture

CI/CD pipeline
 → build container image (app code + serving engine + dependencies)
 → push to registry
 → Kubernetes deployment (GPU-scheduled pods for self-hosted models)
 → autoscaling based on request load / queue depth
 → load balancer → application traffic

9. How it works internally

Kubernetes GPU scheduling works via device plugins that expose GPU resources to the scheduler, letting pods request specific GPU counts/types just like they request CPU/memory — the scheduler places pods only on nodes with available matching GPU resources, and autoscaling can be configured based on custom metrics (queue depth, GPU utilization) rather than just generic CPU-based autoscaling, which is often a poor proxy for actual LLM serving load.

10. Step-by-step: containerizing an AI service

  1. Write a Dockerfile including your application code, dependencies, and (if self-hosting) the serving engine.
  2. Build and test the container locally.
  3. Push to a container registry.
  4. Define a Kubernetes deployment manifest specifying resource requests (including GPU if needed).
  5. Configure autoscaling based on meaningful load metrics.
  6. Set up CI/CD to automate build → test → deploy on code changes.

12. Real-world example

A company self-hosting an open-weight model deploys vLLM in a Kubernetes cluster with GPU-scheduled pods, custom autoscaling based on request queue depth (not generic CPU metrics, which don't reflect actual GPU-bound load), and a CI/CD pipeline that runs the evaluation suite against any model/config change before promoting to production.

13. Code example

# Kubernetes deployment snippet requesting a GPU
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-server
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: vllm
          image: myregistry/vllm-server:latest
          resources:
            limits:
              nvidia.com/gpu: 1
          ports:
            - containerPort: 8000

14. Advanced example (K8s GPU deployment)

# Horizontal Pod Autoscaler based on a custom queue-depth metric
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-server-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm-server
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Pods
      pods:
        metric:
          name: inference_queue_depth
        target:
          type: AverageValue
          averageValue: "5"

15. Common mistakes

  • Using generic CPU-based autoscaling for GPU-bound inference workloads, which doesn't reflect actual load.
  • Not accounting for cold-start latency (loading a large model) when scaling up new instances under load.
  • No CI/CD gating for AI-specific artifacts (prompts, evaluation results), only standard code tests.
  • Underestimating GPU provisioning lead time/cost when planning capacity.

16. Best practices

  • Autoscale based on meaningful AI-specific metrics (queue depth, GPU utilization), not generic CPU metrics.
  • Keep a warm pool of instances if cold-start latency is unacceptable for your use case.
  • Integrate evaluation suite runs into CI/CD for any prompt/model/config change.
  • Plan GPU capacity with realistic lead time given potential scarcity/cost.

17. Production considerations

Treat self-hosted model serving infrastructure with the same operational rigor as any critical production service: health checks, monitoring, rolling deployments, and disaster recovery planning.

18. Security considerations

Secure container images (scan for vulnerabilities), restrict network access to inference endpoints, and manage secrets (API keys, model registry credentials) via proper secret management, not embedded in container images or code.

19. Performance considerations

GPU utilization and cold-start latency are the dominant performance concerns specific to AI infrastructure beyond standard web-app infrastructure considerations — design autoscaling and warm-pool strategies around these.

20. Cost considerations

GPU instances are typically the most expensive infrastructure line item — right-size instance types/counts to actual load, use autoscaling to avoid over-provisioning during low-traffic periods, and consider spot/preemptible instances for fault-tolerant batch workloads.

21. Debugging/troubleshooting

  • Pods stuck pending: check GPU resource availability/quota in the cluster.
  • Autoscaling not responding to actual load: verify the custom metrics pipeline is correctly reporting queue depth/GPU utilization to the autoscaler.
  • High latency during scale-up events: investigate cold-start time and consider a warm pool or pre-scaling strategy for predictable traffic patterns.

27. Interview Questions — Beginner

Q1. What is Docker used for in AI infrastructure?
A. Containerizing AI services for consistent, portable deployment across environments.
Q2. What is Kubernetes used for?
A. Orchestrating containerized workloads at scale, including GPU-aware scheduling for AI inference.
Q3. Why is GPU scheduling different from standard CPU scheduling in Kubernetes?
A. It requires device plugins to expose GPU resources to the scheduler, letting pods request specific GPU counts/types similar to how they request CPU/memory.
Q4. What is a cold start in the context of AI infrastructure?
A. The latency penalty when scaling up a new instance that needs to load a large model into memory before it can serve requests.
Q5. Why is CPU-based autoscaling often a poor fit for GPU-bound inference workloads?
A. It doesn't accurately reflect the actual bottleneck (GPU utilization or request queue depth), so scaling decisions based on it can be mistimed or ineffective.
Q6. Name three major cloud providers relevant to AI infrastructure.
A. AWS, Azure, and GCP.
Q7. What is CI/CD for AI, beyond standard code testing?
A. Automated pipelines that also test/validate AI-specific artifacts like prompts and evaluation results, not just code.
Q8. Why are GPU instances typically the biggest infrastructure cost for self-hosted AI?
A. GPUs are expensive, scarce hardware resources, and AI inference/training workloads are GPU-intensive by nature.
Q9. What's a model registry used for?
A. Versioning and tracking model artifacts (and sometimes prompts/configs) through their deployment lifecycle.
Q10. Should secrets like API keys be embedded in container images?
A. No — they should be managed via proper secret management, not baked into images or code.

28. Interview Questions — Intermediate

Q1. How would you design autoscaling for a self-hosted LLM serving deployment to actually reflect real load?
A. Use a custom metric like inference request queue depth or GPU utilization (exposed via the serving engine's metrics endpoint) as the autoscaler's target, rather than generic CPU utilization, since CPU usage often stays low even under heavy GPU-bound inference load.
Q2. Why might cold-start latency be a significant concern for autoscaled LLM serving but less so for typical stateless web services?
A. Loading a large model's weights into GPU memory takes meaningfully longer than starting a typical lightweight web service process, so a newly-scaled-up pod can't serve requests immediately — this latency gap matters more for LLM serving where model loading dominates startup time.
Q3. What's a practical reason to integrate evaluation suite runs into CI/CD rather than just running them manually before major releases?
A. Automated, consistent evaluation on every change (including small prompt tweaks that might not trigger a "major release" mentally) catches regressions early and consistently, rather than relying on developers remembering to manually evaluate every change, especially smaller ones that feel low-risk but can still cause quality regressions.
Q4. Why might a company use spot/preemptible GPU instances for some workloads but not others?
A. Spot instances are cheaper but can be reclaimed with short notice; they're suitable for fault-tolerant, resumable batch workloads (e.g., non-urgent document processing) but risky for latency-sensitive, continuously-available real-time serving that can't tolerate sudden instance loss.
Q5. How would you keep a "warm pool" of instances to mitigate cold-start latency, and what's the trade-off?
A. Maintain a minimum number of always-running instances with the model already loaded (setting a higher `minReplicas` even during low traffic), trading some baseline infrastructure cost (paying for idle capacity) for consistently low latency during traffic spikes, rather than scaling fully down to zero and incurring cold-start delay on every scale-up event.

29. Interview Questions — Advanced

Q1. How would you design a multi-region AI infrastructure deployment balancing latency, cost, and GPU availability across regions?
A. Deploy serving infrastructure in regions close to major user populations to minimize latency, account for GPU availability/pricing differences across regions/providers in capacity planning, implement cross-region failover for resilience, and consider routing traffic to the lowest-latency healthy region dynamically rather than a fixed single-region deployment, while being mindful of data residency constraints that might restrict which regions can process certain data.
Q2. What's a subtle challenge in building a CI/CD pipeline that gates deployment on evaluation scores when evaluation itself involves non-deterministic LLM-as-judge scoring?
A. Non-deterministic scoring can cause flaky CI runs (a borderline change might pass or fail the gate unpredictably run to run); mitigate by using low/zero temperature for judge calls, averaging scores across multiple runs rather than a single pass/fail check, and setting a reasonable tolerance band rather than a razor-thin threshold that amplifies evaluation noise into false CI failures.

30. Interview Questions — Senior/Architect

Q1. Design the full production infrastructure for a company self-hosting open-weight models at significant scale, covering deployment, scaling, cost, and reliability.
A. Containerize serving (vLLM or similar) with Kubernetes orchestration and GPU device-plugin scheduling; autoscale based on custom queue-depth/GPU-utilization metrics with a warm-pool baseline sized to typical traffic to mitigate cold starts; implement CI/CD gating deployments on both standard tests and AI evaluation suite results; plan multi-AZ/region redundancy for critical serving paths; right-size GPU instance types/counts against measured load with regular capacity reviews; and use spot instances only for fault-tolerant batch workloads, reserving on-demand/reserved capacity for latency-sensitive real-time serving.

31. Scenario-Based Questions

Scenario 1. Your self-hosted model deployment scales up fine but users experience latency spikes right after each scale-up event. What's happening and how do you fix it?
A. Cold-start latency from newly-scaled pods loading the model into memory before they can serve requests; mitigate with a warm-pool baseline (higher minimum replica count) sized to absorb typical traffic growth without needing to scale from zero/low baseline, or pre-scale proactively ahead of known traffic patterns.
Scenario 2. A GPU-based deployment shows low CPU utilization in monitoring dashboards even while users report slow responses under load. What's misleading about the monitoring setup?
A. CPU utilization is the wrong metric for a GPU-bound inference workload — the actual bottleneck (GPU utilization, inference queue depth) isn't being monitored or isn't driving autoscaling decisions; add GPU-specific and queue-depth metrics to properly reflect and respond to actual load.

32. Quick revision notes

  • Docker (containerize) + Kubernetes (orchestrate, GPU-aware scheduling) + CI/CD (gate on tests + evaluation).
  • Autoscale on GPU utilization/queue depth, not generic CPU metrics.
  • Cold start = model-loading latency penalty on scale-up; mitigate with warm pools.
  • GPU is the dominant cost; right-size and consider spot instances for fault-tolerant workloads.

33. Cheat sheet

Docker + Kubernetes (GPU-aware scheduling) + CI/CD (gated on eval suite). Autoscale on queue depth/GPU utilization, not CPU. Mitigate cold starts with warm pools. GPU is the dominant cost — right-size and use spot instances for fault-tolerant workloads.
