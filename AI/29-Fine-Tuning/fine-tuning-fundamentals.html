1. What is this?

Fine-tuning further trains a pretrained model's weights on a smaller, task-specific dataset to change its behavior, style, or domain knowledge — ranging from full fine-tuning (updating all weights) to parameter-efficient methods like LoRA/QLoRA (updating only a small set of additional parameters).

2. Why does it exist?

Prompting and RAG can't change a model's underlying behavior patterns, output style, or deeply ingrained domain reasoning — fine-tuning exists for cases where you need to durably teach the model a new skill, format, or tone that persists without needing to re-specify it in every prompt.

3. Why is it important?

Knowing when fine-tuning is (and isn't) the right tool — versus prompting or RAG — is one of the most consequential architecture decisions in AI engineering, since fine-tuning is the most expensive and operationally heavy of the three options.

4. Where is it used?

Domain-specific assistants needing a particular reasoning style, models needing to reliably produce a custom output format, cost optimization (fine-tuning a small model to match a larger model's behavior on a narrow task).

5. Prerequisites

AI Lifecycle, Open-Source LLMs.

6. Core concepts

  • When to use prompting: the task just needs better instructions/examples — try this first, always.
  • When to use RAG: the task needs fresh/verifiable external knowledge the model doesn't have.
  • When to fine-tune: the task needs a durable behavior/format/style change, or the specific reasoning pattern can't be reliably elicited via prompting alone.
  • SFT (Supervised Fine-Tuning): training on (input, ideal output) pairs to directly teach a behavior.
  • LoRA (Low-Rank Adaptation): freezes the original model weights and trains a small number of additional low-rank matrices, dramatically reducing training cost/memory versus full fine-tuning.
  • QLoRA: combines LoRA with quantization of the frozen base model, further reducing memory requirements.
  • PEFT (Parameter-Efficient Fine-Tuning): the broader category of techniques (including LoRA) that update only a small fraction of parameters.

8. Architecture

Base pretrained model (frozen, in LoRA/QLoRA)
 + small trainable LoRA adapter matrices (injected into specific layers)
 → train on task-specific dataset
 → at inference: base model forward pass + LoRA adapter's small contribution merged in
 → behavior adapted without touching the vast majority of original weights

9. How it works internally (LoRA)

LoRA inserts, alongside each targeted weight matrix in the model, two small low-rank matrices whose product approximates the weight update that full fine-tuning would have made — since the rank is much smaller than the full matrix dimensions, the number of trainable parameters is a tiny fraction of the full model, dramatically reducing memory and compute needed for training while the frozen base model still provides its full original capability as a foundation.

10. Step-by-step: prompting vs RAG vs fine-tuning decision

  1. Try prompting first — can better instructions/examples solve this?
  2. If the issue is missing/stale knowledge → use RAG.
  3. If the issue is a persistent behavior/style/format problem prompting can't reliably fix → consider fine-tuning.
  4. If fine-tuning: start with LoRA/QLoRA (cheaper, faster) before considering full fine-tuning.
  5. Evaluate the fine-tuned model against a held-out test set and against the prompting/RAG baseline.

11. Simple example

Fine-tuning a model to always respond in a specific JSON schema for a classification task, when prompting alone produced inconsistent formatting across edge cases.

12. Real-world example

A company fine-tunes a small open model via LoRA on thousands of examples of their specific customer-support tone and resolution patterns, achieving consistent, on-brand responses at a fraction of the cost of repeatedly sending long few-shot examples to a larger API model on every request.

13. Code example

from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from trl import SFTTrainer

model = AutoModelForCausalLM.from_pretrained("mistralai/Mistral-7B-Instruct")
tokenizer = AutoTokenizer.from_pretrained("mistralai/Mistral-7B-Instruct")

lora_config = LoraConfig(
    r=16, lora_alpha=32, target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05, task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)

trainer = SFTTrainer(
    model=model, train_dataset=dataset,
    args=TrainingArguments(output_dir="./out", per_device_train_batch_size=4, num_train_epochs=3),
)
trainer.train()

15. Common mistakes

  • Fine-tuning to "teach the model new facts" when RAG would be the right tool and far cheaper to update.
  • Using too small or low-quality a training dataset, causing overfitting or inconsistent learned behavior.
  • Skipping a held-out evaluation set, unable to verify the fine-tune actually improved anything.
  • Jumping straight to full fine-tuning when LoRA/QLoRA would achieve the goal at a fraction of the cost.

16. Best practices

  • Always try prompting and RAG first — fine-tune only when those genuinely can't solve the problem.
  • Start with LoRA/QLoRA before considering full fine-tuning.
  • Maintain a held-out evaluation set to objectively measure improvement.
  • Curate high-quality, representative training examples over sheer quantity.

17. Production considerations

Fine-tuned models need the same serving infrastructure as any self-hosted model (see LLM Inference); version and evaluate fine-tunes like any other model artifact before promoting to production.

18. Security considerations

Training data can leak into model outputs in rare cases (memorization) — avoid including sensitive/confidential data in fine-tuning datasets unless you've specifically validated against this risk.

19. Performance considerations

LoRA/QLoRA dramatically reduce training time and memory requirements compared to full fine-tuning, often enabling fine-tuning on a single consumer/prosumer GPU rather than requiring a multi-GPU cluster.

20. Cost considerations

LoRA/QLoRA fine-tuning is orders of magnitude cheaper than full fine-tuning or pretraining; weigh this against the ongoing cost of achieving the same result purely through longer/repeated prompting (e.g., large few-shot examples sent on every API call).

21. Debugging/troubleshooting

  • Fine-tuned model performs worse than the base model on general tasks: likely overfit to the narrow fine-tuning dataset ("catastrophic forgetting") — consider a lower learning rate, fewer epochs, or mixing in general-purpose data.
  • No measurable improvement after fine-tuning: check training data quality/quantity, and verify the evaluation set actually reflects the intended behavior change.
  • Training loss doesn't decrease: check learning rate, LoRA rank, and target module selection.

27. Interview Questions — Beginner

Q1. What is fine-tuning?
A. Further training a pretrained model's weights on a smaller, task-specific dataset to change its behavior, style, or knowledge.
Q2. What is SFT?
A. Supervised Fine-Tuning — training on labeled (input, ideal output) examples.
Q3. What is LoRA?
A. Low-Rank Adaptation — a technique that freezes the original model weights and trains only a small number of additional low-rank matrices.
Q4. What is QLoRA?
A. LoRA combined with quantizing the frozen base model, further reducing memory requirements.
Q5. When should you try prompting before fine-tuning?
A. Always — prompting is the cheapest, fastest lever and should be tried first before considering fine-tuning.
Q6. When should you use RAG instead of fine-tuning?
A. When the issue is missing or outdated knowledge, not a behavior/style/format problem.
Q7. What is PEFT?
A. Parameter-Efficient Fine-Tuning — the umbrella term for techniques like LoRA that update only a small fraction of model parameters.
Q8. Why is LoRA cheaper than full fine-tuning?
A. It trains a much smaller number of additional parameters instead of updating all of the model's original weights.
Q9. What is catastrophic forgetting?
A. When fine-tuning on a narrow dataset degrades the model's general capabilities outside that narrow task.
Q10. Should you fine-tune to teach a model new facts?
A. Generally no — RAG is the better tool for injecting knowledge; fine-tuning is better suited to behavior/style/format changes.

28. Interview Questions — Intermediate

Q1. How does LoRA's low-rank matrix approach reduce trainable parameters while still effectively adapting model behavior?
A. It approximates the full weight update a fine-tune would need using the product of two much smaller matrices (rank r, much less than the full dimension), capturing most of the useful adaptation signal with far fewer trainable parameters than updating the full weight matrix directly.
Q2. Why might QLoRA be necessary rather than plain LoRA for fine-tuning a large model on limited hardware?
A. Even with LoRA's reduced trainable parameters, the frozen base model's full-precision weights still need to be loaded into memory; QLoRA additionally quantizes the frozen base model, substantially reducing the memory footprint needed just to hold the base model during training.
Q3. What's a practical sign that a team should consider fine-tuning instead of continuing to iterate on prompting?
A. When prompting (including extensive few-shot examples) still can't reliably achieve the needed consistency/format/behavior across the full range of real inputs, and/or when the cost of sending large few-shot context on every single API call exceeds the amortized cost of fine-tuning for a high-volume use case.
Q4. Why is curating a smaller, high-quality fine-tuning dataset often better than a larger, noisier one?
A. Fine-tuning datasets directly teach the model's behavior; noisy or inconsistent examples teach inconsistent behavior, whereas a smaller set of carefully curated, consistent examples more reliably shapes the intended behavior without introducing conflicting signals.
Q5. How would you evaluate whether a fine-tuned model has suffered catastrophic forgetting?
A. Test the fine-tuned model against a general-capability evaluation set (unrelated to the fine-tuning task) in addition to the task-specific evaluation set, and compare against the base model's performance on that same general set — a significant regression indicates forgetting.

29. Interview Questions — Advanced

Q1. How would you decide the appropriate LoRA rank (r) for a given fine-tuning task, and what's the trade-off?
A. Lower rank means fewer trainable parameters (faster, cheaper, less prone to overfitting on small datasets) but less capacity to capture complex behavior changes; higher rank increases capacity at the cost of more parameters/compute and higher overfitting risk on small datasets — typically tuned empirically starting from common defaults (e.g., r=8 or 16) and adjusted based on validation performance.
Q2. What's a subtle risk of fine-tuning a model on a narrow, company-specific dataset without any general-capability data mixed in?
A. The model can overfit to the narrow distribution, losing general reasoning/language capabilities it had before fine-tuning (catastrophic forgetting) even while excelling at the narrow task — mitigated by mixing in some general-purpose instruction data alongside the task-specific data, or using techniques that constrain how far the fine-tune can drift from the base model's original behavior.

30. Interview Questions — Senior/Architect

Q1. A team wants to fine-tune a model to "know about" their constantly-changing product catalog. How do you redirect this decision, and what would you actually recommend?
A. Explain that fine-tuning bakes knowledge into frozen weights at training time, making it a poor fit for frequently-changing information — every catalog update would require re-fine-tuning, which is slow and expensive compared to updating a RAG retrieval corpus; recommend RAG for the catalog knowledge, reserving fine-tuning (if needed at all) for something durable like a consistent response format or domain-specific reasoning style that doesn't change with each catalog update.

31. Scenario-Based Questions

Scenario 1. After fine-tuning, your model performs great on the specific task but noticeably worse on general conversation. What happened and how do you fix it?
A. Likely catastrophic forgetting from overfitting on the narrow fine-tuning dataset; fix by reducing training epochs/learning rate, mixing in general-purpose instruction data, or using a lower LoRA rank to limit how much the model's behavior can drift from its original general capability.
Scenario 2. Your fine-tuned model's training loss looked great, but production users report it doesn't actually follow the intended format consistently. What do you investigate?
A. Check whether the training data itself was consistent and representative of real production inputs (training loss only reflects fit to the training distribution, not necessarily generalization to real-world input variety), and build a held-out evaluation set from actual production-like inputs to properly measure real-world consistency rather than relying on training loss alone.

32. Quick revision notes

  • Prompting first, then RAG for knowledge, then fine-tuning for durable behavior/format/style change.
  • LoRA/QLoRA = cheap, parameter-efficient fine-tuning; full fine-tuning rarely needed.
  • Fine-tuning is NOT the right tool for frequently-changing knowledge — use RAG.
  • Always evaluate against a held-out set; watch for catastrophic forgetting.

33. Cheat sheet

Prompting → RAG → Fine-tuning (LoRA/QLoRA first, full fine-tune rarely). Fine-tune for durable behavior/style/format, not facts (use RAG for facts). Watch for catastrophic forgetting; always evaluate against a held-out set.
