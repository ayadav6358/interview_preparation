1. What is this?

Performance and scaling for AI applications covers the software-engineering layer around LLM calls: latency management, throughput under concurrency, rate limiting, retries, circuit breakers, caching, queue-based architecture, and async processing — making an inherently slow, rate-limited external dependency behave well at scale.

2. Why does it exist?

LLM API calls are slow (seconds, not milliseconds) and rate-limited compared to typical internal service calls — standard scaling patterns from distributed systems (queues, circuit breakers, async processing) exist to absorb this fundamental characteristic without degrading the overall application's responsiveness.

3. Why is it important?

This is where general software engineering and AI engineering converge — the patterns here are standard distributed-systems practice applied specifically to the LLM-call bottleneck, essential for any AI feature serving real production traffic.

4. Where is it used?

Any production LLM application with meaningful concurrent traffic, especially agentic systems with multiple sequential LLM calls per user request.

5. Prerequisites

LLM APIs and SDKs.

6. Core concepts

  • Latency: time for a single request to complete — critical for user-facing features.
  • Throughput: total requests/tokens processed per unit time across all traffic.
  • Concurrency: handling many requests simultaneously without blocking each other unnecessarily.
  • Streaming: returning partial results as they're generated, improving perceived latency.
  • Rate limiting (client-side): proactively capping your own outbound request rate to stay within provider limits.
  • Retries with backoff: handling transient failures gracefully.
  • Circuit breakers: stopping requests to a failing dependency temporarily to avoid cascading failure.
  • Queue-based architecture: decoupling request intake from processing for non-real-time workloads, smoothing load spikes.
  • Async processing: using non-blocking I/O to maximize throughput per server resource.

8. Architecture

Real-time path (user-facing):
 Request → rate limiter → LLM call (streaming) → response
 → circuit breaker wraps the LLM call; fallback on open circuit

Async/batch path (non-real-time):
 Request → Queue → Worker pool (concurrent, rate-limited)
 → LLM calls → results stored → notify/poll for completion

9. How it works internally

A circuit breaker tracks a rolling failure rate for calls to a dependency (the LLM API); once failures exceed a threshold within a time window, it "opens," immediately failing (or routing to fallback) further calls without even attempting them for a cooldown period — avoiding wasting time/resources on calls likely to fail and giving the struggling dependency room to recover, then periodically testing ("half-open") whether it has recovered before fully resuming normal traffic.

10. Step-by-step: scaling an LLM application

  1. Measure baseline latency/throughput for your current implementation.
  2. Add streaming for user-facing latency perception improvement.
  3. Add client-side rate limiting matched to your actual provider tier limits.
  4. Add retry-with-backoff and a circuit breaker for resilience.
  5. For non-real-time/bulk workloads, move to a queue-based async architecture.
  6. Load-test under realistic concurrent traffic and iterate.

11. Simple example

Using `asyncio.gather` with a concurrency-limiting semaphore to process a batch of 1000 independent LLM calls efficiently without exceeding the provider's rate limit.

12. Real-world example

A document-processing pipeline uses a queue (e.g., backed by Redis or SQS): incoming documents are queued, a pool of worker processes pulls from the queue at a controlled concurrency rate matching the LLM provider's rate limits, and results are stored for later retrieval — decoupling document submission (fast) from actual processing (slow, rate-limited) and smoothing out traffic spikes.

13. Code example

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()
semaphore = asyncio.Semaphore(10)  # max 10 concurrent requests

async def rate_limited_call(prompt):
    async with semaphore:
        return await client.messages.create(
            model="claude-sonnet-5", max_tokens=200,
            messages=[{"role": "user", "content": prompt}],
        )

async def process_batch(prompts):
    return await asyncio.gather(*(rate_limited_call(p) for p in prompts))

14. Advanced example (circuit breaker)

import time

class CircuitBreaker:
    def __init__(self, failure_threshold=5, cooldown=30):
        self.failures = 0
        self.failure_threshold = failure_threshold
        self.cooldown = cooldown
        self.opened_at = None

    def call(self, fn, *args, **kwargs):
        if self.opened_at:
            if time.time() - self.opened_at < self.cooldown:
                raise RuntimeError("Circuit open — failing fast")
            self.opened_at = None  # half-open: try again
        try:
            result = fn(*args, **kwargs)
            self.failures = 0
            return result
        except Exception as e:
            self.failures += 1
            if self.failures >= self.failure_threshold:
                self.opened_at = time.time()
            raise

15. Common mistakes

  • Calling LLM APIs sequentially in a loop for independent, batchable work.
  • No client-side rate limiting, causing frequent 429 errors under load.
  • No circuit breaker, letting a struggling provider cause cascading failures across your application.
  • Using a synchronous real-time architecture for workloads that would be better served by a queue-based async design.

16. Best practices

  • Use async/concurrent calls with rate-limit-aware semaphores for batchable work.
  • Stream responses for user-facing latency improvement.
  • Implement circuit breakers around any LLM API dependency.
  • Move non-real-time workloads to a queue-based architecture to smooth load and decouple intake from processing.

17. Production considerations

Monitor p50/p99 latency (not just average), queue depth/backlog for async systems, and circuit breaker state transitions as first-class production metrics.

18. Security considerations

Rate limiting also protects against abuse (a malicious or buggy client flooding your system with requests) — apply it per-user/tenant, not just globally, to prevent one bad actor from exhausting shared capacity.

19. Performance considerations (meta)

Profile to find the actual bottleneck (LLM call latency vs. your own application overhead vs. network) before optimizing — premature optimization of the wrong layer wastes effort.

20. Cost considerations

Better concurrency/throughput reduces wall-clock time for a given workload but doesn't reduce per-token cost — cost and performance optimization are related but distinct levers (see Cost Optimization for the cost-specific techniques).

21. Debugging/troubleshooting

  • Frequent 429 rate-limit errors: implement/tighten client-side rate limiting to match actual provider limits.
  • Cascading failures during a provider outage: add a circuit breaker to fail fast and protect the rest of the system.
  • Growing queue backlog: check worker concurrency settings and whether processing rate is keeping up with intake rate.

27. Interview Questions — Beginner

Q1. What's the difference between latency and throughput?
A. Latency is the time for a single request to complete; throughput is the total requests/tokens processed per unit time across all traffic.
Q2. What is a circuit breaker?
A. A pattern that stops sending requests to a failing dependency after repeated failures, to avoid cascading overload, resuming after a cooldown.
Q3. Why does streaming improve perceived latency?
A. It returns partial results as they're generated rather than waiting for the full response, so users see output start almost immediately.
Q4. What is client-side rate limiting?
A. Proactively capping your own outbound request rate to stay within the provider's actual limits, rather than reactively handling 429 errors.
Q5. What's a queue-based architecture used for?
A. Decoupling request intake from processing for non-real-time workloads, smoothing load spikes.
Q6. What does p99 latency mean?
A. The response time below which 99% of requests complete — revealing tail latency issues that average/median latency can hide.
Q7. Why use async/concurrent calls instead of a sequential loop for batch processing?
A. To process multiple independent requests in parallel, dramatically reducing total wall-clock time compared to waiting for each one sequentially.
Q8. What is a dead letter queue?
A. Where permanently-failed queued jobs are routed for manual review rather than endless automatic retry.
Q9. Why might you rate-limit per-user/tenant rather than just globally?
A. To prevent one user/tenant from exhausting shared capacity and degrading service for everyone else.
Q10. What are the three states of a circuit breaker?
A. Closed (normal operation), Open (failing fast, rejecting calls), Half-Open (testing if the dependency has recovered).

28. Interview Questions — Intermediate

Q1. Why might a circuit breaker's half-open state send only a limited number of test requests rather than immediately resuming full traffic?
A. Immediately resuming full traffic risks overwhelming a dependency that's only partially recovered; sending a small number of test requests first verifies recovery with minimal additional risk before committing to full traffic resumption.
Q2. How would you decide the right concurrency limit (semaphore size) for a batch processing job calling an LLM API?
A. Match it to the provider's actual rate limits for your account tier (requests per minute/tokens per minute), accounting for other concurrent traffic sharing that same rate limit, rather than picking an arbitrary number — exceeding the real limit just causes 429s and wasted retries.
Q3. Why might a queue-based architecture be preferable to a purely synchronous one even for moderately real-time workloads?
A. It decouples intake from processing, letting the system absorb traffic spikes gracefully (requests queue rather than fail or time out) and enabling independent scaling of the worker pool based on queue depth, rather than the intake path being directly coupled to and limited by processing capacity.
Q4. What's a practical reason to monitor p99 latency separately from average latency?
A. Average latency can mask a significant fraction of users experiencing much worse performance (tail latency); p99 reveals this, which matters because the worst-experienced users often drive support complaints and churn disproportionately to their small percentage of traffic.
Q5. How would backpressure be implemented in a queue-based LLM processing system approaching capacity?
A. The intake API could start rejecting or delaying new submissions (returning a "try again later" signal) once queue depth exceeds a defined threshold, rather than accepting unlimited work the worker pool can't keep up with, preventing unbounded queue growth and resource exhaustion.

29. Interview Questions — Advanced

Q1. How would you design a multi-tier rate-limiting system that fairly allocates a shared LLM API rate limit across many internal teams/features with different priority levels?
A. Implement a token-bucket or similar rate-limiting scheme with per-team quotas summing to (but with some slack below) the overall provider limit, prioritize higher-priority features' requests when overall demand approaches the limit, and provide teams visibility into their own quota usage so they can self-manage rather than being surprised by throttling.
Q2. What's a subtle risk of applying a circuit breaker too aggressively (low failure threshold, long cooldown) to an LLM API dependency?
A. Transient, brief error spikes (which LLM APIs can experience even when fundamentally healthy) could trigger an unnecessarily long full outage from the application's perspective, degrading availability more than the actual underlying issue warranted — threshold and cooldown tuning should be based on the dependency's actual observed failure patterns, not just defensively conservative defaults.

30. Interview Questions — Senior/Architect

Q1. Design the full resilience and scaling architecture for a high-volume document-processing platform handling millions of LLM calls daily across bursty traffic patterns.
A. Use a queue-based architecture (e.g., SQS/Kafka) decoupling intake from processing; scale worker pools dynamically based on queue depth; implement per-provider circuit breakers with fallback to a secondary provider on sustained failure; apply token-bucket rate limiting matched to each provider's actual limits with priority tiers for different workload types; route failed-after-retries items to a dead-letter queue with alerting for manual review; and monitor p50/p99 latency, queue depth, circuit breaker state, and throughput as core production dashboards with alerting on anomalies in any of them.

31. Scenario-Based Questions

Scenario 1. Your application experiences cascading failures whenever your LLM provider has even brief degraded performance. What's missing architecturally?
A. Likely missing a circuit breaker — without one, continued retries against a struggling dependency compound the problem (each retry adds load to an already-struggling service and consumes your own resources waiting); add a circuit breaker to fail fast and protect the rest of the system during provider issues.
Scenario 2. A batch job processing 50,000 items via sequential LLM calls is projected to take 18 hours. How do you redesign it?
A. Convert to async/concurrent processing with a semaphore matched to the provider's rate limits (dramatically reducing wall-clock time), and/or use the provider's Batch API if available for non-real-time bulk workloads at a cost/throughput advantage — sequential processing of independent, batchable work is almost always the wrong default for this scale.

32. Quick revision notes

  • Latency (per-request) vs throughput (aggregate) — different metrics, different optimizations.
  • Stream for perceived latency; rate-limit client-side; circuit-break for resilience.
  • Queue-based async architecture for non-real-time, bursty, or bulk workloads.
  • Monitor p99, not just average; monitor queue depth and circuit breaker state.

33. Cheat sheet

Stream for perceived latency. Rate-limit client-side to match provider limits. Circuit-break for resilience. Queue + async workers for bulk/non-real-time workloads. Monitor p99, queue depth, circuit state — not just averages.
