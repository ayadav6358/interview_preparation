1. What is this?

Agentic AI architectures are recurring organizational patterns for structuring agent systems: Planner/Executor (separate planning from execution), Supervisor (a coordinator delegating to specialists), Router (directs requests to the right handler), Reflection/Critic (a separate pass evaluates and improves output), and combinations thereof for parallel/sequential multi-agent systems.

2. Why does it exist?

A single LLM trying to plan, execute, and self-evaluate all in one undifferentiated loop often performs worse than when those responsibilities are separated into specialized roles/passes — these architectures exist because decomposing agent responsibilities, much like decomposing prompts, improves reliability.

3. Why is it important?

These are the standard vocabulary and design patterns senior AI engineers use to describe and justify agent system designs — fluency here is directly tested in system-design interviews for agentic AI roles.

4. Where is it used?

Complex research agents, multi-agent customer support platforms, coding agents, any system where a single undifferentiated agent loop underperforms a decomposed architecture.

5. Prerequisites

AI Agents, LangGraph.

6. Core architectures

PatternDescription
Planner/ExecutorA planner decomposes the goal into steps; an executor carries out each step, possibly re-planning if execution reveals new information.
SupervisorA coordinating agent routes sub-tasks to specialist agents and integrates their results.
RouterClassifies an incoming request and directs it to the appropriate handler/agent, without necessarily coordinating multi-step execution.
Reflection/CriticA separate pass (or agent) evaluates the primary agent's output and provides feedback for revision.
ReviewerSimilar to critic, often framed as a final quality gate before output is finalized/delivered.
Parallel agentsMultiple agents work on independent sub-tasks simultaneously, results aggregated afterward.
Sequential agentsAgents run one after another, each building on the previous one's output.

7. Terminology

TermMeaning
PlannerComponent/agent responsible for decomposing a goal into an ordered set of steps.
ExecutorComponent/agent responsible for carrying out individual steps.
SupervisorA coordinating agent delegating to and integrating results from specialist agents.
CriticA component evaluating output quality and providing corrective feedback.
Autonomous workflowA multi-step process requiring minimal human intervention end to end.

8. Architecture

Planner/Executor:
 Goal → Planner (produces step list) → Executor (runs step 1..N, possibly re-planning)

Supervisor:
 Task → Supervisor → routes to [Specialist A | Specialist B | Specialist C] → Supervisor integrates → Answer

Reflection/Critic:
 Draft → Critic (evaluates) → feedback → Reviser (produces improved draft) → (loop or finalize)

9. How it works internally

Each specialized role is typically just a differently-prompted (and sometimes differently-sized/model) LLM call, operating on a narrower, more clearly-defined sub-task than an undifferentiated "do everything" agent — the architectural benefit comes from task decomposition (same principle as in prompt engineering) applied at the agent-role level, often implemented as distinct nodes in a LangGraph-style state graph.

10. Step-by-step: choosing an architecture

  1. If the task needs distinct, clearly-defined expertise areas → Supervisor + specialists.
  2. If the task needs upfront decomposition before execution → Planner/Executor.
  3. If output quality benefits from self-critique → add a Reflection/Critic pass.
  4. If sub-tasks are independent and can run concurrently → Parallel agents.
  5. If sub-tasks must build on each other in order → Sequential agents.
  6. If none of the above adds measurable value over a single agent/workflow → don't use agents at all (see "When NOT to use agents").

11. Simple example

A trip-planning agent: a Planner decomposes "plan a 3-day Tokyo trip" into steps (find flights, find hotels, suggest itinerary); an Executor carries out each step via tools; a final Critic checks the overall plan for consistency (e.g., no overlapping bookings) before presenting it.

12. Real-world example

A multi-agent customer-support platform uses a Supervisor to classify incoming tickets and route to specialist agents (billing, technical, account-security), each with tools and prompts scoped to their domain — far more reliable and maintainable than one agent trying to handle every ticket type with one giant prompt.

13. Code example

from langgraph.graph import StateGraph, START, END

def supervisor(state):
    category = classify(state["ticket"])
    return {"route": category}

def billing_agent(state):
    return {"response": handle_billing(state["ticket"])}

def technical_agent(state):
    return {"response": handle_technical(state["ticket"])}

graph = StateGraph(SupportState)
graph.add_node("supervisor", supervisor)
graph.add_node("billing", billing_agent)
graph.add_node("technical", technical_agent)
graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", lambda s: s["route"], {
    "billing": "billing", "technical": "technical",
})
graph.add_edge("billing", END)
graph.add_edge("technical", END)
app = graph.compile()

14. Advanced example (critic loop)

def draft(state):
    return {"draft": generate_draft(state["task"])}

def critique(state):
    feedback = evaluate(state["draft"], state["task"])
    return {"feedback": feedback, "approved": "no issues" in feedback.lower()}

def revise(state):
    return {"draft": revise_draft(state["draft"], state["feedback"])}

graph.add_node("draft", draft)
graph.add_node("critique", critique)
graph.add_node("revise", revise)
graph.add_edge("draft", "critique")
graph.add_conditional_edges("critique", lambda s: END if s["approved"] else "revise", {END: END, "revise": "revise"})
graph.add_edge("revise", "critique")  # loop back for re-evaluation

15. Common mistakes

  • Adding a Supervisor/Planner/Critic architecture when a single well-prompted agent already performs adequately.
  • Creating specialist agents with overlapping, ambiguous responsibilities, confusing the Supervisor's routing.
  • Infinite critique loops without a maximum revision count.
  • Not giving the Planner enough information to produce a realistic, executable plan.

16. Best practices

  • Only decompose into specialized roles when evaluation shows it measurably improves outcomes over a simpler architecture.
  • Keep specialist agent responsibilities clearly non-overlapping.
  • Bound reflection/critique loops with a maximum revision count.
  • Let the Planner re-plan when execution reveals the original plan was flawed, rather than rigidly executing a stale plan.

17. Production considerations

Each additional role/pass adds latency and cost — measure the marginal quality improvement of each architectural layer against its marginal cost, same discipline as Advanced RAG technique selection.

18. Security considerations

A Supervisor routing to specialist agents with different tool permissions must enforce that routing decision cannot be manipulated by injected content to grant a lower-privilege specialist higher-privilege tool access.

19. Performance considerations

Parallel agent patterns can significantly reduce wall-clock latency for independent sub-tasks compared to sequential execution — use parallelism wherever sub-tasks don't have dependencies.

20. Cost considerations

Reflection/critic loops and multi-agent supervisor patterns multiply LLM calls per task — quantify this multiplier and validate it's justified by measured quality improvement, not assumed.

21. Debugging/troubleshooting

  • Supervisor routes to the wrong specialist: review classification logic/prompt for ambiguity between specialist domains.
  • Critic loop never converges: check if the critic's feedback is actionable/specific enough for the reviser to actually address, and add a max-iteration cap.
  • Planner produces unrealistic plans: ensure the planner has access to the same tool/capability information the executor will actually have.

23. When NOT to use agents

  • The task has a fixed, predictable sequence of steps regardless of intermediate results (use a workflow).
  • Latency/cost budgets can't tolerate multi-step LLM round trips.
  • The task requires strict determinism/reproducibility (agents introduce variability).
  • A simpler single-prompt or single-agent solution already meets quality requirements — added architecture must be justified by measured gains, not assumed sophistication.

27. Interview Questions — Beginner

Q1. What is the Planner/Executor pattern?
A. A planner decomposes a goal into steps; an executor carries out each step, separating planning responsibility from execution.
Q2. What does a Supervisor agent do?
A. Coordinates by routing sub-tasks to specialist agents and integrating their results.
Q3. What is a Critic/Reviewer in agentic AI?
A. A component that evaluates an agent's output and provides corrective feedback for revision.
Q4. What's the difference between parallel and sequential agents?
A. Parallel agents work on independent sub-tasks simultaneously; sequential agents run one after another, each building on the previous output.
Q5. Why would you decompose a single agent into a Supervisor + specialists?
A. To give each specialist a narrower, clearer responsibility and tool scope, often improving reliability over one agent trying to handle everything.
Q6. Should you always add a Critic pass to improve output quality?
A. No — it adds cost/latency; only add it when evaluation shows a measurable quality improvement justifying that cost.
Q7. What is a Router pattern?
A. Classifying an incoming request and directing it to the appropriate handler/agent.
Q8. Name one scenario where you should NOT use an agent.
A. When the task has a fixed, predictable sequence of steps regardless of intermediate results — use a workflow instead.
Q9. Why does a Planner sometimes need to re-plan mid-execution?
A. Because execution can reveal new information showing the original plan is flawed or infeasible, requiring adaptation.
Q10. What's a risk of an unbounded critique/revision loop?
A. It could run indefinitely without converging, incurring unbounded cost — needs a maximum iteration cap.

28. Interview Questions — Intermediate

Q1. Why might decomposing an agent into specialized roles improve reliability even though each role is still "just an LLM call"?
A. Narrower, more clearly-scoped responsibilities reduce the chance of the model conflating or dropping instructions the way a single do-everything prompt might, similar to how task decomposition improves prompt reliability generally — specialization reduces cognitive/instructional load per call.
Q2. How would you prevent a Supervisor's misrouting from causing a specialist agent to handle a request outside its competence?
A. Add a confidence threshold to the routing decision — if classification confidence is low, route to a fallback/general handler or request clarification rather than forcing a potentially wrong specialist assignment; also evaluate routing accuracy against a labeled test set to catch systematic misclassification patterns.
Q3. What's the trade-off between Parallel and Sequential agent execution for a multi-part research task?
A. Parallel execution reduces wall-clock latency for genuinely independent sub-tasks but can't handle dependencies between sub-tasks; Sequential execution naturally handles dependencies (each step building on prior results) but takes longer overall — choose based on whether sub-tasks are actually independent.
Q4. Why is a Critic agent's feedback quality itself a potential failure point in the Reflection pattern?
A. If the critic's feedback is vague, unhelpful, or itself wrong (the critic can hallucinate issues or miss real ones), the reviser can't effectively improve the draft — the critic needs its own evaluation/calibration, not blind trust that "having a critic" automatically improves quality.
Q5. How would you measure whether a multi-agent Supervisor architecture is actually outperforming a single well-prompted agent for your task?
A. Run both architectures against the same evaluation set, comparing success rate, cost, and latency — if the single-agent baseline matches multi-agent quality at lower cost, the added architectural complexity isn't earning its keep.

29. Interview Questions — Advanced

Q1. How would you design a Planner/Executor system that gracefully handles the Executor discovering the Planner's assumptions were wrong partway through?
A. Have the Executor report structured failure/discrepancy information back to the Planner (not just raw errors), trigger a re-planning step that incorporates this new information to produce a revised plan, and maintain state tracking which steps already completed successfully so re-planning doesn't redundantly redo completed work.
Q2. What's a subtle risk of a Critic agent being the same underlying model/prompt family as the agent producing the draft it's critiquing?
A. The critic may share the same blind spots/biases as the generator (correlated errors), reducing its ability to catch certain classes of mistakes — using a different model, a differently-prompted critic focusing on specific failure modes, or incorporating external verification (rule-based checks, retrieval-grounded fact-checking) can provide more independent, effective critique.

30. Interview Questions — Senior/Architect

Q1. Design a multi-agent research platform combining Planner/Executor, Supervisor, and Critic patterns, justifying each architectural choice.
A. Planner decomposes the research goal into sub-questions; a Supervisor routes each sub-question to specialist research agents (web search, data analysis, document retrieval) running in parallel where independent; each specialist's output passes through a Critic checking source quality and factual consistency before being accepted; the Planner re-plans if critic feedback reveals a sub-question needs a different approach; final synthesis combines all accepted specialist outputs — each layer justified by addressing a specific failure mode (decomposition for complexity, specialization for domain accuracy, critique for quality assurance) rather than added for its own sake.

31. Scenario-Based Questions

Scenario 1. Your team built a 5-agent Supervisor architecture for a task that a single well-prompted agent handles just as well in evaluation. What do you recommend?
A. Recommend simplifying to the single-agent approach — the added architectural complexity isn't earning its cost/latency overhead if evaluation shows no quality benefit; reserve the multi-agent architecture for tasks where it's measurably justified.
Scenario 2. A Critic/Reviser loop in production occasionally runs 20+ revision cycles before giving up. How do you fix it?
A. Add a hard maximum revision count with a defined fallback (return best-effort draft or escalate to human) when hit, and investigate whether the critic's feedback is specific/actionable enough for the reviser to actually converge, rather than vague recurring criticism.
Scenario 3. A Supervisor occasionally routes sensitive account-security tickets to the general-purpose billing specialist, which lacks proper security protocols. How do you fix this architecturally?
A. Treat this as a security-relevant misrouting risk, not just a quality issue — add stricter, higher-confidence-threshold routing rules for security-sensitive categories, default to a secure fallback (human review) rather than any general specialist when classification confidence is uncertain for sensitive categories, and audit-log all security-category routing decisions.

32. Quick revision notes

  • Planner/Executor, Supervisor, Router, Reflection/Critic — standard agentic architecture patterns.
  • Each pattern exists to decompose responsibility, improving reliability over one undifferentiated agent.
  • Only adopt added architecture when evaluation shows measurable benefit over simpler alternatives.
  • Know when NOT to use agents at all.

33. Cheat sheet

Planner/Executor = decompose then execute. Supervisor = route to specialists + integrate. Critic/Reflection = evaluate + revise. Parallel = independent sub-tasks concurrently. Sequential = dependent sub-tasks in order. Only add complexity that's measurably justified.
