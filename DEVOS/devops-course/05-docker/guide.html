Docker & Containers: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: "Mere laptop pe chal raha hai, server pe nahi chal raha." Without Docker, every machine has a different OS, Node/Python version and library set, so the same app behaves differently. With Docker, the application and its dependencies are packaged into one image that runs the same way on a laptop, a CI server and production.

PROBLEM: app works on developer machine, fails on server
      |
      v
TRADITIONAL APPROACH: install runtime + libraries by hand or with scripts on each server (or one VM per app)
      |
      v
PAIN: version drift, 'works on my machine', slow VM boot, wasted RAM/CPU, hard rollbacks
      |
      v
TECHNOLOGY: Docker (image + container, sharing the host Linux kernel)
      |
      v
SOLUTION: build once (image), run anywhere (container), start in seconds
      |
      v
REAL-WORLD BENEFIT: identical dev/test/prod, fast CI/CD, easy rollback, higher server density

Docker did not invent containers. Linux already had namespaces (isolation) and cgroups (resource limits). Docker made them easy to use: a simple CLI, the Dockerfile format and image registries.

2. End-to-End Flow

Developer
   |
   v
Dockerfile (recipe)
   |  docker build
   v
Docker Image (read-only layers)
   |  docker push
   v
Registry (Docker Hub / ECR / Harbor)
   |  docker pull
   v
Docker Host
   |  docker run
   v
Container (image + writable layer + namespaces + cgroups)
   |
   v
Application (listening on a port)
   |
   v
Logs (docker logs) / Metrics (docker stats, Prometheus) / Monitoring (Grafana)

Developer writes source code and a Dockerfile. docker build executes each instruction and produces an image made of read-only layers (cached, so rebuilds are fast). docker push uploads the image to a registry so other machines can get it. On the server, docker pull downloads the layers and docker run creates a container: a new writable layer on top of the image, its own namespaces (PID, network, mount...) and cgroup limits. The application starts as PID 1 inside it. Then you observe it with docker logs, docker stats or a monitoring stack. If something is wrong you fix the code, rebuild with a new tag and redeploy; rollback means running the previous tag.

Docker vs a VM tool such as Vagrant: containers share the host kernel, so they start in seconds and use far less memory. Docker Hub vs Harbor: Docker Hub is public and simple; Harbor is self-hosted with RBAC, scanning and replication for company use.

5. Troubleshooting Playbook

Problem: Container is running but application is not accessible
Possible cause: Port not published, app listens on 127.0.0.1 only, wrong port, firewall/security group
How to check: docker ps (check PORTS column), docker logs web, docker inspect web, docker exec -it web sh, then curl localhost:PORT inside and outside the container
Fix: Publish with -p 8080:80; make the app bind to 0.0.0.0; open the cloud security group.
Prevention: Add a HEALTHCHECK, document ports in compose, test with curl in CI smoke test.
Problem: Container exits immediately (Exited (0) or (1))
Possible cause: PID 1 finished or crashed; missing env variable; wrong CMD
How to check: docker ps -a, docker logs <id>, docker inspect --format '{{.State.ExitCode}}' <id>
Fix: Fix the command or env; for a long-running process use foreground mode (nginx -g 'daemon off;').
Prevention: Run the image locally in CI before deploy.
Problem: exec format error
Possible cause: Image built for another CPU architecture (arm64 vs amd64)
How to check: docker image inspect img --format '{{.Architecture}}', uname -m
Fix: Build multi-arch: docker buildx build --platform linux/amd64,linux/arm64.
Prevention: Always build multi-arch or pin the platform in CI.
Problem: Cannot connect to the Docker daemon
Possible cause: Daemon not running or user not in docker group
How to check: systemctl status docker, groups
Fix: sudo systemctl start docker; sudo usermod -aG docker $USER then re-login.
Prevention: Enable at boot with systemctl enable docker.
Problem: Build is slow on every code change
Possible cause: Layer cache invalidated because source is copied before dependency install
How to check: docker build output shows no CACHED for the install step
Fix: Copy package.json first, install, then copy the rest.
Prevention: Review Dockerfile order in code review; add .dockerignore.
Problem: OOMKilled (exit code 137)
Possible cause: Container exceeded memory limit
How to check: docker inspect c --format '{{.State.OOMKilled}}', docker stats
Fix: Increase --memory or fix the memory leak.
Prevention: Load-test and set realistic limits.

6. Production Best Practices

Development

  • Use docker compose for the full stack locally.
  • Mount source with bind mounts for hot reload; use named volumes for DB data.
  • Keep a .dockerignore.

Production

  • Pin image tags (never latest) or use digests.
  • Set restart policy and healthchecks.
  • Set CPU/memory limits.
  • One process per container; log to stdout/stderr.

Security

  • Run as non-root (USER).
  • Use minimal/distroless base images.
  • Scan with Trivy in CI, sign with cosign, generate SBOM with Syft.
  • Never mount /var/run/docker.sock or use --privileged without a strong reason.
  • Use --read-only, --cap-drop ALL, no-new-privileges.

Performance

  • Multi-stage builds for small images.
  • Order layers from least to most frequently changing.
  • Use BuildKit cache mounts.

Reliability

  • restart: unless-stopped.
  • Healthchecks + depends_on: condition: service_healthy.
  • Store data in volumes and back them up.

Cost Optimization

  • Small images reduce registry storage and pull time.
  • Prune unused images/volumes regularly (docker system prune).

Monitoring & Logging

  • docker stats, cAdvisor + Prometheus + Grafana.
  • Use a logging driver or ship stdout to Loki/ELK; configure log rotation (max-size, max-file).

Backup & Disaster Recovery

  • Back up named volumes with a tar container.
  • Keep Dockerfiles and compose files in Git; images are reproducible from source + registry.

7. Common Mistakes

Beginner mistakes

  • Using latest tag: pin versions.
  • Storing data inside the container: use volumes.
  • Thinking EXPOSE opens the port: use -p.

Developer mistakes

  • Copying the whole project before installing dependencies (cache miss).
  • Forgetting .dockerignore so node_modules/.git bloat the image.
  • Listening on localhost inside the container.

DevOps mistakes

  • No healthchecks or resource limits.
  • Not cleaning old images so the disk fills up.
  • Building different images per environment instead of one image + config.

Production mistakes

  • Running as root.
  • Logs without rotation filling the disk.
  • No rollback tag kept.

Security mistakes

  • Baking secrets into image layers (ENV PASSWORD=..., COPY .env).
  • Mounting docker.sock into containers.
  • Never scanning or updating base images.

8. Version / Environment Notes

  • Compose: use docker compose (v2 plugin). The old docker-compose (v1, Python) is deprecated and the version: key in compose files is obsolete.
  • BuildKit is the default builder in current Docker Engine; docker buildx provides multi-platform builds.
  • Docker Desktop (Windows/macOS) runs Docker inside a VM/WSL2; Linux runs the engine natively. Networking host mode behaves differently on Docker Desktop.
  • docker scan (Snyk) was removed; use docker scout or Trivy.
  • Commands and defaults change between releases: check docker version and the official docs at docs.docker.com for your version.

11. How I Explain This to a Client

30-second explanation

Docker packages an application together with everything it needs into a single unit called an image. That image runs exactly the same on a developer laptop, a test server and production. It removes 'it works on my machine' problems, speeds up releases and lets us run more applications on the same servers.

2-minute explanation

Traditionally we installed the runtime and libraries on every server, and small differences caused failures. With Docker, we describe the environment once in a Dockerfile and build an image. The image is stored in a registry, and any server can pull it and start a container in seconds. Containers share the operating system kernel, so they are much lighter than virtual machines. For your team this means faster onboarding (one command to run the full stack), consistent deployments, easy rollback (run the previous image version) and better server utilisation. We also add security scanning to the pipeline so vulnerable images never reach production.

5-minute deep explanation

Let me explain in four parts. First, the problem: applications depend on the operating system, language version and libraries. Different environments cause failures that are hard to reproduce. Second, the solution: a Docker image is a read-only, layered package of the app plus dependencies. A container is a running instance of it, isolated using Linux namespaces and limited using cgroups. Third, how we use it in your project: developers build the image through a Dockerfile in CI, the image is scanned, signed and pushed to a private registry such as Harbor, and the deployment platform, Docker Compose for small setups or Kubernetes for scale, pulls that exact version. Configuration and secrets are injected at runtime, and data lives in volumes. Fourth, operations and risk: we set health checks, CPU and memory limits, log rotation and monitoring, we run containers as non-root and keep base images updated. The business outcome is faster and safer releases, lower infrastructure cost and simple rollbacks.

13. Mini Project: React + Node.js + PostgreSQL + Redis with Docker Compose

Browser --> Nginx (:80, serves React build, proxies /api)
                 |
                 v
            Node.js API (:3000, internal only)
              |            |
              v            v
      PostgreSQL (:5432)  Redis (:6379)
        volume pgdata      (cache)
All on custom network 'appnet'; only Nginx publishes a host port.
Pipeline: Git > CI build > Trivy scan > push to registry > compose pull/up

Step 1: Project layout

myapp/
  frontend/  (React, Dockerfile)
  api/       (Node.js, Dockerfile)
  nginx/default.conf
  compose.yml
  .env        (gitignored)

One folder per service. Each service has its own Dockerfile so it can be built and scanned separately.

Step 2: API Dockerfile

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
EXPOSE 3000
HEALTHCHECK CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node","server.js"]

Dependencies are copied first for cache, the app runs as the non-root node user, and the healthcheck lets Compose know when the API is ready.

Step 3: compose.yml

services:
  web:
    build: ./frontend
    ports: ["80:80"]
    depends_on: [api]
    networks: [appnet]
  api:
    build: ./api
    environment:
      DB_URL: postgres://app:${DB_PASSWORD}@db:5432/app
      REDIS_URL: redis://cache:6379
    depends_on:
      db: { condition: service_healthy }
    networks: [appnet]
  db:
    image: postgres:16
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: "${DB_PASSWORD}", POSTGRES_DB: app }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL","pg_isready -U app"], interval: 5s, retries: 10 }
    networks: [appnet]
  cache:
    image: redis:7-alpine
    networks: [appnet]
networks: { appnet: {} }
volumes: { pgdata: {} }

Only web publishes a port. api, db, cache are reachable only inside appnet by service name (DNS). The DB password comes from .env, not from the file. Data survives in the pgdata volume.

Step 4: Run, verify, scan

docker compose up -d --build
docker compose ps
curl -i http://localhost/api/health
trivy image myapp-api:latest --severity HIGH,CRITICAL
docker compose logs -f api

Start the stack, confirm all services are healthy, hit the API through Nginx, scan the image, and read logs. In CI, the same build + scan runs and the pipeline pushes to Harbor; the server then pulls the tagged image and runs docker compose up -d.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Docker?

A platform to build, ship and run applications in containers. A container packages the app and its dependencies and shares the host kernel.

Why: Interviewers check that you know the core problem: environment consistency.

Real-world example: A Node app runs the same in dev, CI and production because the same image is used.

Q2. Image vs container?

Image is a read-only template made of layers; a container is a running instance with a writable layer.

Why: Most common confusion.

Real-world example: One nginx image can start many containers.

Q3. What is a Dockerfile?

A text file with instructions (FROM, COPY, RUN, CMD...) that docker build runs to create an image.

Why: Shows you understand reproducible builds.

Real-world example: Node Dockerfile: FROM node, COPY, RUN npm ci, CMD node server.js.

Q4. What is Docker Hub?

The default public registry for images.

Why: Registries are how images move between machines.

Real-world example: docker pull nginx downloads from Docker Hub.

Q5. How do you list running and all containers?

docker ps shows running; docker ps -a shows all including stopped.

Why: Basic debugging skill.

Real-world example: A crashed container appears only with -a and status Exited.

Q6. What does docker run -d -p 8080:80 nginx do?

Starts nginx in the background and maps host port 8080 to container port 80.

Why: Tests port mapping understanding.

Real-world example: Then open http://localhost:8080.

Q7. How to see logs of a container?

docker logs -f <name>.

Why: First step of every troubleshooting.

Real-world example: See a stack trace when the app crashes.

Q8. How to enter a running container?

docker exec -it <name> sh (or bash).

Why: Used to inspect files and test connectivity.

Real-world example: curl localhost:3000 from inside the container.

Q9. Why do we use volumes?

Container filesystem is ephemeral; volumes persist data outside the container lifecycle.

Why: Data loss is a classic production incident.

Real-world example: PostgreSQL data dir mounted to a named volume.

Q10. docker stop vs docker kill?

stop sends SIGTERM then SIGKILL after a timeout (default 10s); kill sends SIGKILL immediately.

Why: Graceful shutdown matters for databases and in-flight requests.

Real-world example: App needs SIGTERM to flush data.

Intermediate (15)

Q11. Explain image layers and caching.

Each Dockerfile instruction creates a read-only layer, identified by content hash. If an instruction and its inputs are unchanged, the cached layer is reused; a changed layer invalidates all layers after it.

Why: Directly affects build speed and image size.

Real-world example: Copy package.json and run npm ci before copying source so code changes do not reinstall dependencies.

Q12. CMD vs ENTRYPOINT?

ENTRYPOINT defines the executable; CMD gives default arguments and is overridable at docker run. Together they make a flexible CLI-like image.

Why: Tests Dockerfile depth.

Real-world example: ENTRYPOINT ["curl"], CMD ["--help"].

Q13. EXPOSE vs -p?

EXPOSE is metadata; -p publishes the port to the host.

Why: Common wrong assumption.

Real-world example: Without -p, the port is reachable only from other containers on the same network.

Q14. Bridge vs host vs overlay network?

Bridge: private network on one host with NAT. Host: shares host network stack (no isolation, no port mapping). Overlay: spans multiple hosts (Swarm/K8s-like).

Why: Shows networking knowledge.

Real-world example: Custom bridge for a Compose stack.

Q15. Why can't containers on the default bridge use names?

The default bridge has no automatic DNS; user-defined networks provide embedded DNS.

Why: Frequent real issue.

Real-world example: API cannot resolve db until both are on appnet.

Q16. Volume vs bind mount?

Volumes are managed by Docker and portable; bind mounts map a host path and depend on host layout.

Why: Choosing storage correctly.

Real-world example: Bind mount for dev hot reload, volume for DB.

Q17. What is a multi-stage build?

Multiple FROM stages; you build in one stage and copy only artifacts to a small final stage.

Why: Size and security.

Real-world example: Go/Java/Node builds shrink from ~1GB to ~100MB.

Q18. What does depends_on guarantee?

Only start order, not readiness, unless you use condition: service_healthy with a healthcheck.

Why: Classic race condition.

Real-world example: API crashes because Postgres is still initialising.

Q19. How to limit CPU and memory?

--memory=256m --cpus=0.5 or deploy.resources/mem_limit in Compose.

Why: Prevents noisy neighbours.

Real-world example: One leaking container should not kill the host.

Q20. What is a tag vs digest?

A tag is a mutable label; a digest (sha256) is an immutable content hash.

Why: Supply-chain safety.

Real-world example: Pin nginx@sha256:... in production.

Q21. How do you pass secrets?

Runtime env/secret files, Docker secrets or a secret manager; never bake into image layers.

Why: Security basics.

Real-world example: Use .env (gitignored) locally and Vault/AWS Secrets Manager in production.

Q22. How do you reduce image size?

Slim/alpine/distroless base, multi-stage, combine RUN commands, clean caches, .dockerignore.

Why: Speed and attack surface.

Real-world example: python:3.12-slim instead of python:3.12.

Q23. What is a healthcheck?

A command Docker runs periodically to decide if the container is healthy.

Why: Readiness and self-healing.

Real-world example: HEALTHCHECK CMD curl -f http://localhost/health.

Q24. How do containers log?

Apps write to stdout/stderr; Docker's logging driver captures it (json-file by default).

Why: Twelve-factor logging.

Real-world example: docker logs, then Fluent Bit ships to Loki.

Q25. docker compose down vs down -v?

down removes containers and networks; -v also removes named volumes (data loss).

Why: Avoid deleting DB data.

Real-world example: Run down -v only in dev.

Advanced (15)

Q26. Explain Docker architecture.

CLI talks via REST API to dockerd, which manages images/networks/volumes and delegates container lifecycle to containerd, which uses runc (OCI runtime) to create the container through the Linux kernel.

Why: Shows internals.

Real-world example: Kubernetes can use containerd directly without dockerd.

Q27. How are containers isolated?

Namespaces (pid, net, mnt, uts, ipc, user) give isolated views; cgroups limit CPU/memory/IO; capabilities and seccomp reduce privileges.

Why: Core internals.

Real-world example: unshare --pid --fork demonstrates a PID namespace.

Q28. Explain overlay filesystem.

OverlayFS stacks read-only image layers (lowerdir) with a writable upperdir; copy-on-write on modification.

Why: Explains layer sharing and write performance.

Real-world example: Many containers share the same image layers on disk.

Q29. What is PID 1 problem in containers?

The main process is PID 1, which does not get default signal handlers and must reap zombies. Shell form CMD makes sh PID 1 and swallows SIGTERM.

Why: Graceful shutdown bugs.

Real-world example: Use exec form or tini/--init.

Q30. Rootless Docker vs root?

Rootless runs the daemon and containers without root using user namespaces, reducing host risk but with networking/storage limitations.

Why: Security hardening.

Real-world example: Shared CI hosts.

Q31. How does BuildKit improve builds?

Parallel stage execution, better caching, cache mounts, secret mounts, and multi-platform builds.

Why: Modern build knowledge.

Real-world example: RUN --mount=type=cache speeds npm/pip installs.

Q32. How to build multi-architecture images?

docker buildx build --platform linux/amd64,linux/arm64 --push, producing a manifest list.

Why: ARM (Graviton, Apple Silicon) is common.

Real-world example: Same tag works on M-series Mac and x86 server.

Q33. Secure a container image supply chain.

Minimal base, pinned digests, scan (Trivy), SBOM (Syft), sign (cosign), verify in admission control, private registry.

Why: Security maturity.

Real-world example: Kubernetes admission policy only allows signed images.

Q34. Why is mounting docker.sock dangerous?

Access to the socket equals root on the host because the container can start privileged containers.

Why: Frequent security finding.

Real-world example: CI job that builds images should use Kaniko/BuildKit rootless.

Q35. Docker networking internals for bridge?

A virtual docker0/custom bridge, veth pairs per container, iptables NAT for published ports, embedded DNS at 127.0.0.11.

Why: Debugging connectivity.

Real-world example: iptables -t nat -L shows the DNAT rule for -p.

Q36. What happens on docker run?

CLI calls API; daemon checks local image, pulls if absent, creates container config, sets up namespaces/cgroups/network/mounts via containerd+runc, starts the process.

Why: End-to-end understanding.

Real-world example: First run is slow because of the pull.

Q37. Capabilities and seccomp?

Capabilities split root power into units; Docker drops many by default. Seccomp filters syscalls. Use --cap-drop ALL then add only what is needed.

Why: Least privilege.

Real-world example: Web server only needs NET_BIND_SERVICE for port 80.

Q38. How to handle log growth?

Set --log-opt max-size=10m --log-opt max-file=3 or configure daemon.json; or use a remote logging driver.

Why: Disk-full incidents.

Real-world example: Unbounded json-file logs filled a production disk.

Q39. Docker Swarm vs Kubernetes?

Swarm is simpler and built in; Kubernetes has a richer ecosystem, extensibility and industry adoption.

Why: Tool selection reasoning.

Real-world example: Most companies choose Kubernetes for new platforms.

Q40. Immutable infrastructure with containers?

Never patch a running container; build a new image and replace. Config comes from environment.

Why: Reliability and reproducibility.

Real-world example: Rollback = redeploy previous tag.

Scenario-Based (15)

Q41. API cannot reach Postgres in Compose.

Check both are in the same network, use the service name as host, check DB health, credentials and port 5432 inside the network (not host port).

Why: Tests systematic debugging.

Real-world example: docker compose exec api nc -zv db 5432.

Q42. Image is 1.5 GB, make it small.

Multi-stage, slim/distroless base, .dockerignore, remove build tools, --omit=dev, check layers with dive.

Why: Practical optimisation.

Real-world example: Java app with JRE-only final image.

Q43. Disk on the Docker host is full.

docker system df, prune unused images/containers/build cache, check large logs and volumes, set log rotation.

Why: Frequent ops incident.

Real-world example: docker system prune -a after checking what is unused.

Q44. Container keeps restarting.

docker logs, exit code, OOMKilled, healthcheck, restart policy loop, config missing.

Why: Diagnosis order matters.

Real-world example: Exit 137 means OOM or SIGKILL.

Q45. Database data disappeared after redeploy.

No volume, or down -v used, or volume path wrong. Restore from backup and mount a named volume.

Why: Data safety.

Real-world example: Postgres path must be /var/lib/postgresql/data.

Q46. Critical CVE reported in production image.

Rebuild on patched base, pin digest, redeploy, add scan gate to CI, automate updates with Renovate/Dependabot.

Why: Security process.

Real-world example: openssl vulnerability in base image.

Q47. Need zero-downtime deploy with Compose.

Compose alone is limited; use rolling with multiple replicas behind a proxy, or move to Kubernetes/Swarm.

Why: Knowing the tool's limits.

Real-world example: Nginx upstream + --scale api=2 then replace one by one.

Q48. Different behaviour in dev and prod.

Ensure the same image is promoted; move differences to env/config; compare docker inspect, env and mounts.

Why: Environment parity.

Real-world example: Dev used bind mount with different node_modules.

Q49. App works on Mac M1 but fails on the Linux server.

Architecture mismatch; build multi-arch or set --platform linux/amd64.

Why: Modern issue.

Real-world example: exec format error in logs.

Q50. Team wants to run 100 containers across servers.

Recommend Kubernetes (or ECS): scheduling, self-healing, service discovery, rolling updates.

Why: Knowing when to move beyond Docker.

Real-world example: Compose on one host cannot survive node failure.

Q51. How to secure CI image builds?

Use rootless BuildKit/Kaniko, no docker.sock, scan and sign, short-lived registry credentials.

Why: DevSecOps.

Real-world example: GitHub Actions with OIDC to ECR.

Q52. A container needs a secret at startup.

Inject via runtime secret/env from a secret manager; never commit or bake into the image.

Why: Secrets handling.

Real-world example: Docker/Kubernetes secret mounted as a file.

Q53. How do you roll back a bad release?

Redeploy previous immutable tag/digest; keep last N tags in registry.

Why: Release safety.

Real-world example: docker compose up -d with IMAGE_TAG=1.4.2.

Q54. Two services need to share files.

Use a shared named volume (read-only on the consumer) or an object store; avoid bind mounts across hosts.

Why: Design judgement.

Real-world example: Uploads volume shared by API and worker.

Q55. Reduce build time in CI.

Layer order, BuildKit cache export/import (--cache-from/--cache-to), smaller context, parallel stages.

Why: Pipeline performance.

Real-world example: Registry cache cut build from 8 to 2 minutes.

Troubleshooting-Based (10)

Q56. Port already allocated error?

Another process/container uses the host port; find it with ss -tulpn or docker ps and change the mapping.

Why: Common start failure.

Real-world example: Two nginx containers mapped to 80.

Q57. Permission denied on bind mount?

UID/GID mismatch between host files and container user; fix ownership or use a named volume. SELinux hosts may need :z.

Why: File permission issues.

Real-world example: Postgres cannot write to a host folder.

Q58. Container cannot resolve external DNS.

Check host DNS/resolv.conf, corporate proxy, set --dns, test with nslookup in the container.

Why: Networking debug.

Real-world example: VPN changes DNS and breaks builds.

Q59. Container cannot reach the internet.

Check IP forwarding, iptables/firewall rules, proxy variables, MTU.

Why: Network layers.

Real-world example: Docker + ufw blocking forward chain.

Q60. docker build fails at RUN npm install.

Read the error: network/proxy, missing lockfile, native build tools missing on alpine, memory. Reproduce with docker run -it base sh.

Why: Build debugging.

Real-world example: bcrypt needs python/make on alpine.

Q61. Container healthy but requests time out.

App binds to 127.0.0.1, wrong proxy upstream, port mismatch, security group, or DB slowness.

Why: Layered diagnosis.

Real-world example: Fix HOST=0.0.0.0.

Q62. docker logs is empty.

App logs to a file instead of stdout, or crashes before logging. Redirect logs to stdout; check docker inspect for log driver.

Why: Logging convention.

Real-world example: Symlink /var/log/nginx/access.log to /dev/stdout.

Q63. Image pull fails: rate limit or unauthorized.

Docker Hub pull limits or missing docker login/expired token; use a registry mirror or private registry.

Why: Registry operations.

Real-world example: CI hitting Docker Hub limits.

Q64. Compose changes not applied.

Need docker compose up -d again (recreates changed services); images need --build; check docker compose config.

Why: Workflow knowledge.

Real-world example: Env change requires recreate.

Q65. Container uses too much memory.

docker stats, profile the app, set limits, watch OOMKilled, check log/tmpfs usage.

Why: Resource control.

Real-world example: Node heap growth needs --max-old-space-size.

Definitions

  • Image: read-only layered template. Container: running instance. Registry: image store.
  • Layer: result of one Dockerfile instruction, cached by hash.
  • Namespace = SEE; cgroup = USE.
  • Volume: Docker-managed persistent storage.

Commands

  • docker build -t app:1.0 . | docker run -d --name web -p 8080:80 app:1.0
  • docker ps [-a] | docker logs -f web | docker exec -it web sh

  • docker inspect web | docker stats | docker system df | docker system prune
  • docker network create n | docker volume create v
  • docker compose up -d --build | docker compose down [-v] | docker compose logs -f svc
  • docker buildx build --platform linux/amd64,linux/arm64 --push .

Files

  • Dockerfile
  • .dockerignore
  • compose.yml (or docker-compose.yml)
  • .env
  • /etc/docker/daemon.json

Architecture

  • Docker CLI > Docker API > dockerd > containerd > runc > Linux kernel > container

Ports

  • HTTP 80, HTTPS 443, Node 3000, PostgreSQL 5432, MySQL 3306, Redis 6379, MongoDB 27017, Docker API TCP 2375 (insecure) / 2376 (TLS)
