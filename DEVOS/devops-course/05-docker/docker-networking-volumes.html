Docker Networking & Volumes

Intermediate Docker & Containers

Concept (What & Why)

Containers ko aapas mein baat karwana (networks) aur data persist karna (volumes). Container delete hone par uska data chala jata hai, isliye volumes.

Definition Deep-Dive

QuestionAnswer
Simple definitionNetworks let containers talk to each other; volumes keep data after a container is deleted.
Technical definitionDocker networking uses virtual bridges, veth pairs, iptables NAT and an embedded DNS server (127.0.0.11) on user-defined networks. Storage uses named volumes (managed under /var/lib/docker/volumes), bind mounts and tmpfs mounts.
Why does it exist?Isolation and service discovery between containers; persistent state.
What happens without it?Hard-coded IPs and lost data.
When to useAny multi-container app or stateful service.
When NOT to useDo not use the host network without a reason (no isolation).
Real-world analogyNetwork = office intercom by name; volume = external hard-disk that survives changing laptops.

Diagram & Internal Working

Custom bridge network 'appnet':
  [web] --http--> [api] --tcp 5432--> [db]   (resolve by service name)
  host:8080 -> web:80 (port publish)

Storage: volume (managed by Docker) | bind mount (host path) | tmpfs (memory)

How it works internally (diagram explained)

On a user-defined bridge, Docker creates a Linux bridge and a veth pair per container. Containers get private IPs; an embedded DNS resolves service names to IPs. -p 8080:80 adds an iptables DNAT rule from the host port to the container IP:port. A volume is a directory managed by Docker mounted into the container's mount namespace, so it lives independently of the container's writable layer.

Real-World Example

host:8080 -> [web:80] --appnet--> [api:3000] --appnet--> [db:5432]
                                                       |
                                                 volume pgdata

Only web publishes a port. api reaches db at db:5432 using DNS on appnet. Postgres data is stored in pgdata. If api fails, web returns 502 and Prometheus alerts; if db is recreated, data remains in pgdata. Backups are taken by a tar container.

Install / Setup

# built into Docker

Practical Examples

User-defined network & volume

docker network create appnet
docker volume create pgdata
docker run -d --name db --network appnet -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16
docker run -d --name api --network appnet -e DB_HOST=db -p 3000:3000 myapp:1.0
docker network inspect appnet; docker volume ls

Backup a volume

docker run --rm -v pgdata:/data -v $PWD:/backup alpine tar czf /backup/pgdata.tgz -C /data .

Important Commands Explained

docker network inspect appnet
What does it do?
Shows subnet, gateway and connected containers with IPs.
Important options
--format '{{json .Containers}}'.
Expected output
JSON with Containers section.
Common mistake
Inspecting the wrong network (default bridge).
Troubleshooting
Container missing from the list? It was started without --network appnet.
docker volume ls / docker volume inspect pgdata
What does it do?
Lists volumes / shows mountpoint on host.
Important options
docker volume prune removes unused volumes.
Expected output
Name, driver local, Mountpoint.
Common mistake
Pruning volumes that look unused but hold data.
Troubleshooting
Verify with docker ps -a --filter volume=pgdata.

Hands-On Lab

Lab Goal

Create a network and a volume, run Postgres + a client and prove data persists.

Prerequisites

  • Docker installed

Step 1

docker network create appnet && docker volume create pgdata

Creates a user-defined bridge network and a named volume.

Step 2

docker run -d --name db --network appnet -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16

Starts Postgres with data stored in the volume.

Step 3

docker run --rm --network appnet postgres:16 psql -h db -U postgres -c 'create table t(id int); insert into t values (1);'

The client resolves db by DNS. Expected: INSERT 0 1 (password: set PGPASSWORD=secret).

Step 4

docker rm -f db && docker run -d --name db --network appnet -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16

New container, same volume: the table t still exists. Data survived because it lives in the volume.

Real-World Problems & Fixes (Troubleshooting)

Problem: API can't connect to DB by name
Cause: Default bridge has no DNS
Fix: Use user-defined network so container names resolve.
Problem: Data lost after docker rm
Cause: No volume used
Fix: Mount named volume for stateful paths.
Problem: Permission denied on bind mount
Cause: UID mismatch
Fix: Match user IDs / chown, or use named volumes.

Best Practices

Production

  • Expose only the reverse proxy port.
  • Use named volumes and back them up.

Security

  • Keep DB on an internal network (internal: true).

Common Mistakes

Beginner mistakes

  • Publishing DB port 5432 to the world.
  • Using localhost to reach another container.

Hinglish Explanation

Default bridge par containers naam se ek dusre ko nahi dhoondh paate. User-defined network banao to naam (DNS) se connect ho jata hai. Database ka data hamesha volume mein rakho.

Memory Tricks

ConceptMemory trick
PortsHOST first, CONTAINER second: -p 8080:80
StorageVolume for data, bind for code, tmpfs for secrets

Interview Questions

Q1. Volume vs bind mount?

Volume managed by Docker (portable, preferred); bind mount maps host path (dev convenience).

Q2. Network drivers?

bridge, host, overlay (multi-host), macvlan, none.

Q3. How do containers on same network talk?

By container/service name via embedded DNS.

Q4. EXPOSE vs -p?

EXPOSE documents port only; -p actually publishes to host.

Q5. How to persist DB data?

Mount volume at DB data dir.

Q6. How does -p work internally?

Docker adds iptables DNAT rules (and a docker-proxy for some cases) forwarding host:port to containerIP:port on the bridge.

Why: Debugging connectivity.

Real-world example: iptables -t nat -L DOCKER shows the mapping.
