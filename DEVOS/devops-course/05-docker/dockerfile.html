Dockerfile & Image Optimization

Intermediate Docker & Containers

Concept (What & Why)

Dockerfile image ka recipe hai. Layer order, cache, multi-stage builds, non-root user aur chhoti image production ke liye zaroori hain.

Warning: Anything you COPY or ENV into a layer stays in image history even if you delete it in a later layer. Never bake secrets.

Definition Deep-Dive

QuestionAnswer
Simple definitionA Dockerfile is a recipe: step by step instructions to build an image.
Technical definitionA Dockerfile is a text file of instructions parsed by BuildKit; each filesystem-changing instruction creates a cached layer, and the final layers form an OCI image with metadata (CMD, ENV, EXPOSE, USER).
Why does it exist?Reproducible, reviewable and versioned image creation.
What happens without it?Manual image creation via docker commit, not reproducible.
When to useEvery application you ship as a container.
When NOT to useDo not put secrets or large data in it.
Real-world analogyA cooking recipe: same steps, same dish every time.

Diagram & Internal Working

Stage 1 (build): node:20 + devDeps + compile  --\
                                                 +--> COPY artifacts only
Stage 2 (run):   node:20-alpine (small) <-------/     => 1GB -> ~100MB

How it works internally (diagram explained)

docker build sends the build context (files in the folder, minus .dockerignore) to BuildKit. BuildKit executes stages in order: each instruction is hashed with its inputs; an unchanged hash reuses the cached layer. COPY --from=build copies only the final artifacts into a tiny runtime stage, so build tools never reach production. The resulting image has layers + a config (CMD, USER, ENV).

Install / Setup

docker build -t myapp:1.0 .
winget/apt install hadolint dive   # lint + inspect layers

Configuration Explained Line by Line

Node.js multi-stage Dockerfile explained

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER node
EXPOSE 3000
HEALTHCHECK CMD wget -qO- localhost:3000/health || exit 1
CMD ["node","dist/server.js"]
LineMeaning / WHY it exists
FROM node:20-alpine AS buildBase image: node = runtime, 20 = major version (pinned so builds are repeatable), alpine = tiny Linux. AS build names this stage.
WORKDIR /appSets the working directory; creates it if missing so later commands use relative paths.
COPY package*.json ./Copies only dependency manifests first. If they do not change, the next RUN npm ci layer is served from cache.
RUN npm ciClean, reproducible install from the lockfile (faster and stricter than npm install).
COPY . .Copies the rest of the source AFTER dependencies so code edits do not invalidate the install layer.
FROM node:20-alpineStarts a fresh, small final stage; build tools from stage 1 are left behind.
ENV NODE_ENV=productionMakes frameworks run in production mode.
COPY --from=build ...Pulls only built artifacts from the build stage.
USER nodeRuns as a non-root user to limit damage if the app is compromised.
EXPOSE 3000Documents the port; does NOT publish it (use -p).
HEALTHCHECK ...Lets Docker/Compose know if the app is really serving.
CMD ["node","dist/server.js"]Exec form so node is PID 1 and receives SIGTERM for graceful shutdown.

Practical Examples

Optimized multi-stage Dockerfile

FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./          # copy deps first -> cache friendly
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
USER node
EXPOSE 3000
HEALTHCHECK CMD wget -qO- localhost:3000/health || exit 1
CMD ["node","dist/server.js"]

Important Commands Explained

docker build -t myapp:1.0 -f Dockerfile .
What does it do?
Builds an image from a Dockerfile and a context folder.
Important options
-t name:tag, -f file, --no-cache, --target stage, --build-arg K=V, --platform.
Expected output
Step-by-step build log, then naming to docker.io/library/myapp:1.0.
Common mistake
Building from a huge folder without .dockerignore.
Troubleshooting
COPY failed: file not found: the path is outside the build context.

Hands-On Lab

Lab Goal

Build a small Node.js image, compare cache behaviour and run it.

Prerequisites

  • Docker installed
  • A folder with package.json, server.js and the Dockerfile above

Step 1

docker build -t myapp:1.0 .

Builds the image. Watch each step; first build has no CACHED.

Step 2

echo '// change' >> server.js && docker build -t myapp:1.1 .

Only layers after COPY . . rebuild; npm ci shows CACHED, proving correct layer order.

Step 3

docker images myapp && docker history myapp:1.1

Shows image size and the size contributed by every layer.

Step 4

docker run -d --name app -p 3000:3000 myapp:1.1 && curl localhost:3000/health

Runs and tests it. Expected: your health response.

Real-World Problems & Fixes (Troubleshooting)

Problem: Every code change reinstalls all dependencies (slow builds)
Cause: COPY . before package install breaks cache
Fix: Copy manifest first, install, then copy source.
Problem: Image is 1.2GB
Cause: Full base image, build tools included
Fix: Multi-stage, slim/alpine/distroless, .dockerignore.
Problem: App can't be stopped gracefully
Cause: Shell form CMD makes shell PID 1
Fix: Use exec form CMD ["node",...]; use tini.

Best Practices

Production

  • Pin base image version or digest.
  • Multi-stage, non-root, healthcheck, exec-form CMD.

Security

  • No secrets in ENV/COPY; use BuildKit --secret.
  • Scan with Trivy; lint with hadolint.

Performance

  • Use BuildKit cache mounts and .dockerignore.

Common Mistakes

Developer mistakes

  • COPY . . before installing dependencies.
  • Using shell-form CMD so SIGTERM is ignored.
  • Leaving build tools in the final image.

Security mistakes

  • COPY .env into the image.
  • Running as root.

Hinglish Explanation

Dockerfile mein dependencies pehle copy karo, source baad mein, taaki har code change par npm install dobara na chale. Multi-stage build se final image chhoti aur secure hoti hai.

Memory Tricks

ConceptMemory trick
Layer orderLeast changing first, most changing last.
Cache ruleOne changed layer invalidates everything below it.

Version / Environment Notes

  • BuildKit is the default builder in current Docker; --mount=type=cache and --mount=type=secret need BuildKit.
  • Alpine uses musl libc; some prebuilt binaries need libc6-compat or a Debian slim base.

Interview Questions

Q1. CMD vs ENTRYPOINT?

ENTRYPOINT is fixed executable; CMD provides default args (overridable). Combine for flexible CLIs.

Q2. COPY vs ADD?

ADD also extracts tar and fetches URLs; prefer COPY.

Q3. Why multi-stage builds?

Smaller, safer final image without build tools.

Q4. How to reduce image size?

Slim base, multi-stage, combine RUN, clean caches, .dockerignore.

Q5. Why not run as root?

Limits impact of container breakout; use USER.

Q6. How would you pass an npm token during build without leaking it?

Use BuildKit secrets: RUN --mount=type=secret,id=npmrc ... and docker build --secret id=npmrc,src=.npmrc. The secret is not stored in layers.

Why: Secure builds.

Real-world example: Private npm registry in CI.
