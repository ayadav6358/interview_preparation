Container Security & Internals

Advanced Docker & Containers

Concept (What & Why)

Container = Linux process + namespaces + cgroups. Security: non-root, minimal images, scanning, read-only FS, dropped capabilities, signing.

Warning: Containers share the host kernel: a kernel vulnerability affects all containers. For hostile multi-tenant workloads consider gVisor, Kata Containers or VMs.

Definition Deep-Dive

QuestionAnswer
Simple definitionContainers are isolated processes; security means limiting what they can see, use and do.
Technical definitionContainer isolation = namespaces (pid, net, mnt, uts, ipc, user, cgroup) + cgroups (resource limits) + capabilities + seccomp/AppArmor/SELinux + optional user namespaces/rootless, executed by containerd/runc according to the OCI spec.
Why does it exist?A shared kernel means a container breakout can compromise the host, so we reduce privileges.
What happens without it?Root containers with full capabilities: one vulnerable app can own the host.
When to useAlways.
When NOT to useN/A
Real-world analogyApartments in one building (kernel): separate rooms and rules, but one shared structure.

Diagram & Internal Working

Container = process with
  namespaces: pid, net, mnt, uts, ipc, user   (isolation)
  cgroups   : cpu, memory, io limits           (resource control)
  overlayfs : layered filesystem
  runtime   : containerd -> runc

How it works internally (diagram explained)

runc calls clone()/unshare() to create namespaces, sets cgroup limits, drops capabilities, applies the seccomp profile, pivots root into the image's filesystem (overlayfs) and executes the entrypoint. Each layer of protection blocks a different attack: namespaces hide other processes, cgroups stop resource abuse, capabilities/seccomp limit dangerous syscalls, read-only FS stops persistence, image scanning removes known CVEs.

Install / Setup

# Trivy scanner
sudo apt install trivy   # or: docker run aquasec/trivy image nginx:1.27
# cosign for signing: https://github.com/sigstore/cosign

Configuration Explained Line by Line

Hardened run flags explained

docker run -d --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --user 10001 --pids-limit 200 myapp:1.0
LineMeaning / WHY it exists
--read-onlyMakes the root filesystem read-only, so malware cannot write binaries.
--tmpfs /tmpGives the app a writable in-memory temp directory.
--cap-drop ALLRemoves all Linux capabilities; add back only what is required with --cap-add.
--security-opt no-new-privilegesPrevents gaining privileges via setuid binaries.
--user 10001Non-root UID.
--pids-limit 200Stops fork bombs.

Practical Examples

Hardened run

docker run -d --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --user 10001 --pids-limit 200 myapp:1.0

Scan and sign

trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:1.0
cosign sign --key cosign.key registry/myapp:1.0
syft myapp:1.0 -o spdx-json > sbom.json

See namespaces in action

sudo unshare --pid --fork --mount-proc bash   # own PID namespace
ps aux    # only shows processes in this namespace

Hands-On Lab

Lab Goal

See a PID namespace and scan an image.

Prerequisites

  • Linux host or WSL2
  • Docker
  • Trivy (or use the aquasec/trivy container)

Step 1

sudo unshare --pid --fork --mount-proc bash
ps aux

You are in a new PID namespace; ps shows only a few processes, proving isolation without Docker.

Step 2

exit
docker run --rm aquasec/trivy image --severity HIGH,CRITICAL nginx:1.27

Scans the image for HIGH/CRITICAL CVEs and prints a table.

Step 3

docker run --rm --read-only alpine sh -c 'touch /x'

Fails with Read-only file system, proving the hardening flag works.

Real-World Problems & Fixes (Troubleshooting)

Problem: Critical CVE found in production image
Cause: Old base image
Fix: Rebuild on updated base, pin digest, automate with Renovate/Dependabot, gate in CI.
Problem: Container can access host
Cause: Mounted /var/run/docker.sock or --privileged
Fix: Never mount docker.sock; avoid privileged; use rootless/Kaniko in CI.

Best Practices

Security

  • Non-root, minimal/distroless images.
  • Scan in CI, sign with cosign, produce SBOM, verify at deploy.
  • Never mount docker.sock; avoid --privileged.
  • Use rootless Docker/Podman on shared hosts.

Common Mistakes

Security mistakes

  • --privileged for convenience.
  • Secrets in image layers or environment printed in logs.
  • Ignoring base image updates.

Hinglish Explanation

Container ek normal Linux process hi hai. Namespace decide karta hai ki wo kya *dekh* sakta hai, cgroups decide karta hai ki wo kitna *use* kar sakta hai. Security ke liye non-root, minimal image, scan aur read-only filesystem lagao.

Version / Environment Notes

  • Rootless mode and user-namespace remap have feature limits (low ports, some storage drivers).
  • docker scan is removed; use docker scout or Trivy.
  • Docker's default seccomp profile blocks ~44 syscalls; verify in the docs for your version.

Interview Questions

Q1. What makes containers isolated?

Namespaces (what you see) and cgroups (what you can use).

Q2. What is --privileged?

Gives near-full host access; avoid.

Q3. Docker vs containerd vs runc?

Docker is full tooling; containerd is runtime manager; runc is low-level OCI runtime.

Q4. How to secure images in CI?

Scan (Trivy), minimal base, sign (cosign), SBOM, admission policy verification.

Q5. What is distroless?

Images with only app + runtime, no shell/package manager; smaller attack surface.

Q6. How do you prove an image running in production came from your pipeline?

Sign with cosign in CI, store signature in the registry, and enforce verification with an admission controller (Kyverno/Sigstore policy).

Why: Supply-chain security.

Real-world example: Only signed images from Harbor are allowed in the cluster.
