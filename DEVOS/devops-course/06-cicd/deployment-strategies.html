Deployment Strategies & Pipeline Security

Advanced CI/CD

Concept (What & Why)

Zero-downtime release techniques: rolling, blue-green, canary. Saath mein pipeline security (SAST, SCA, secrets, signing).

Definition Deep-Dive

QuestionAnswer
Simple definitionDeployment strategies are safe ways to release a new version to users.
Technical definitionRolling update, recreate, blue/green, canary, A/B and shadow deployments trade off risk, cost and speed; progressive delivery automates metric-based promotion and rollback.
Why does it exist?Minimise downtime and blast radius of bad releases.
What happens without it?Big-bang releases causing outages.
When to useEvery production release.
When NOT to useBlue/green for very expensive or stateful environments without planning.
Real-world analogyOpening a new bridge lane by lane vs closing the whole bridge.

Diagram & Internal Working

Rolling:    v1 v1 v1 -> v2 v1 v1 -> v2 v2 v1 -> v2 v2 v2
Blue-Green: LB -> BLUE(v1) | GREEN(v2) idle -> switch LB to GREEN -> keep BLUE for rollback
Canary:     v1 100% -> v2 5% -> 25% -> 50% -> 100% (auto-rollback on error-rate rise)

How it works internally (diagram explained)

Rolling: Deployment replaces Pods gradually while readiness gates traffic. Blue/green: two full environments; a Service selector/load balancer switches all traffic. Canary: traffic split (ingress weights, service mesh, Argo Rollouts) sends 5% > 25% > 100% while analysis compares error rate/latency; failure aborts and shifts traffic back.

Real-World Example

Users --> Ingress --95%--> api v1 (stable)
             \--5%---> api v2 (canary) --> metrics (errors, latency) --> promote or rollback

A payments API releases v2 as a 5% canary. Prometheus queries compare error rate and p95 latency; if error rate stays below the SLO for 10 minutes traffic goes to 25%, then 100%. If it breaches, Argo Rollouts automatically reverts to v1.

Install / Setup

kubectl create ns argo-rollouts
kubectl apply -n argo-rollouts -f https://github.com/argoproj/argo-rollouts/releases/latest/download/install.yaml

Practical Examples

Argo Rollouts canary

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: myapp }
spec:
  replicas: 5
  selector: { matchLabels: { app: myapp } }
  template:
    metadata: { labels: { app: myapp } }
    spec: { containers: [{ name: myapp, image: myapp:v2 }] }
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: { duration: 5m }
      - setWeight: 50
      - pause: { duration: 10m }

Hands-On Lab

Lab Goal

Practise blue/green with Kubernetes Services.

Prerequisites

  • Cluster
  • kubectl

Step 1

cat > bg.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: { name: app-blue }
spec:
  replicas: 2
  selector: { matchLabels: { app: app, ver: blue } }
  template:
    metadata: { labels: { app: app, ver: blue } }
    spec: { containers: [{ name: web, image: "nginx:1.26" }] }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: app-green }
spec:
  replicas: 2
  selector: { matchLabels: { app: app, ver: green } }
  template:
    metadata: { labels: { app: app, ver: green } }
    spec: { containers: [{ name: web, image: "nginx:1.27" }] }
---
apiVersion: v1
kind: Service
metadata: { name: app }
spec:
  selector: { app: app, ver: blue }
  ports: [{ port: 80 }]
EOF
kubectl apply -f bg.yaml

Creates both versions (blue = nginx 1.26, green = nginx 1.27) and a Service that currently selects blue only.

Step 2

kubectl get endpoints app

Endpoints list only the blue Pod IPs, so all traffic goes to blue.

Step 3

kubectl patch svc app -p '{"spec":{"selector":{"app":"app","ver":"green"}}}'

Instant switch of ALL traffic to green. Run kubectl get endpoints app again to see the green IPs.

Step 4

kubectl patch svc app -p '{"spec":{"selector":{"app":"app","ver":"blue"}}}'

Rollback is the same one-line switch back to blue.

Real-World Problems & Fixes (Troubleshooting)

Problem: Bad release hit all users at once
Cause: Big-bang deploy
Fix: Canary with metrics analysis + auto-rollback.
Problem: DB schema change breaks old version during rolling deploy
Cause: Non backward-compatible migration
Fix: Expand/contract pattern: add new columns first, deploy code, then remove old later.

Best Practices

Production

  • Readiness probes + PDB for rolling; metrics-based canary analysis; automated rollback; DB migrations backward compatible.

Security

  • Scan and sign before promote; verify signature at admission.

Common Mistakes

Production mistakes

  • Canary without metrics.
  • Schema changes that break the old version.

Version / Environment Notes

  • Kubernetes has no native canary/blue-green object: use Argo Rollouts, Flagger, ingress annotations or a service mesh; features differ by tool version.

Interview Questions

Q1. Blue-green vs canary?

Blue-green swaps all traffic at once with instant rollback (2x infra); canary shifts gradually to limit blast radius.

Q2. How to do DB migrations with zero downtime?

Backward-compatible, expand-contract, run migrations separately from app deploy.

Q3. What is SLSA?

Framework for supply chain integrity (provenance, build isolation).

Q4. How to avoid long-lived cloud keys in CI?

OIDC federation to short-lived role credentials.

Q5. What is a feature flag benefit?

Deploy dark, release gradually, instant kill switch.

Q6. How do you handle DB schema changes with blue/green?

Use backward-compatible expand/contract migrations so both versions work against the same database, then clean up later.

Why: Real blocker for blue/green.

Real-world example: Add column first, remove old column in a later release.
