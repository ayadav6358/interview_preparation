CI/CD Concepts & Pipeline Design

Basic CI/CD

Concept (What & Why)

CI: har commit par build+test. Continuous Delivery: hamesha deployable, release manual approval se. Continuous Deployment: har pass hua change automatic prod mein.

Definition Deep-Dive

QuestionAnswer
Simple definitionCI/CD is an automatic path from code commit to running application.
Technical definitionCI verifies each change via automated build/test/analysis in a shared pipeline; CD automates packaging and release to environments with gates and strategies.
Why does it exist?Reduce risk by releasing small changes frequently with fast feedback.
What happens without it?Big-bang releases and manual mistakes.
When to useAny team shipping software regularly.
When NOT to useNever 'avoid' but start simple: a small pipeline beats none.
Real-world analogyFactory assembly line with quality inspection at each station.

Diagram & Internal Working

commit -> [Build] -> [Unit test] -> [Lint/SAST] -> [Package image] -> [Scan] -> [Deploy dev] -> [Integration/e2e] -> [Approve] -> [Deploy prod] -> [Smoke test]
  fail fast: koi bhi stage fail -> pipeline stop -> developer ko notify

How it works internally (diagram explained)

Trigger (push/PR/schedule/manual) > CI server allocates an agent > checkout > run stages in order; each stage is a set of commands returning an exit code. Non-zero fails the pipeline and stops later stages (fail fast). Outputs (artifacts, test reports, images) are stored and reused by later stages/environments.

Install / Setup

# Choose tool: GitHub Actions (cloud), Jenkins (self-hosted), GitLab CI

Practical Examples

Pipeline design checklist

1. Fast feedback (<10 min for CI)
2. Same artifact promoted across envs (build once, deploy many)
3. Immutable, versioned artifacts (image tag = git sha)
4. Config/secrets injected per env, not baked in
5. Automated rollback & smoke tests
6. Everything as code (Jenkinsfile / workflow yaml)

Hands-On Lab

Lab Goal

Create a minimal CI pipeline for a Node app on GitHub.

Prerequisites

  • GitHub account and repo
  • A Node project with npm test

Step 1

mkdir -p .github/workflows

Workflows must be in this folder.

Step 2

cat > .github/workflows/ci.yml <<'EOF'
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npm test
EOF

Defines a two-trigger workflow that installs and tests.

Step 3

git add . && git commit -m 'add ci' && git push

Push triggers the workflow. Open the Actions tab: green check = pass.

Step 4

Break a test, push again

The pipeline fails and blocks the PR: that is the value of CI.

Real-World Problems & Fixes (Troubleshooting)

Problem: Works in staging, breaks in prod
Cause: Rebuilt artifact per env / config drift
Fix: Build once, promote same image; keep env config separate.
Problem: Pipeline takes 40 minutes
Cause: No caching / serial stages
Fix: Cache deps, parallelize tests, use path filters.

Best Practices

Production

  • Build once, deploy everywhere.
  • Fast pipelines (<10 min for PR checks).

Security

  • Least privilege credentials.

Common Mistakes

Beginner mistakes

  • No tests in the pipeline.
  • Secrets in YAML.

Hinglish Explanation

CI = code push par automatic build aur test. CD = tested code ka automatic deploy. Jo bhi stage fail ho, pipeline wahin ruk jati hai (fail fast).

Interview Questions

Q1. CI vs CD vs Continuous Deployment?

CI = integrate+test often; Delivery = always releasable with manual gate; Deployment = fully automatic to prod.

Q2. What are DORA metrics?

Deployment frequency, lead time for changes, change failure rate, MTTR.

Q3. Why build once?

Guarantees what you tested is what you deploy.

Q4. What is a quality gate?

Automated threshold (coverage, vulnerabilities) that blocks promotion.

Q5. Artifact vs image?

Artifact is any build output (jar, binary, image); image is container artifact.

Q6. Why 'build once, deploy many'?

Ensures the exact tested artifact reaches production; rebuilding can change dependencies and behavior.

Why: Reliability.

Real-world example: Same image SHA from staging to prod.
