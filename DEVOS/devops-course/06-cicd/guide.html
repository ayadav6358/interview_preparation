CI/CD: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Manual releases are slow, risky and inconsistent: someone builds on a laptop, forgets to run tests, copies files to a server by hand, and a bug reaches users. CI/CD (Continuous Integration / Continuous Delivery or Deployment) automates the path from a code commit to a running application, with tests and checks at every step.

PROBLEM: releasing software by hand is slow and error-prone
      |
      v
TRADITIONAL APPROACH: big releases every few weeks, manual build, manual tests, manual copy to servers
      |
      v
PAIN: integration bugs found late, 'release nights', no traceability, hard rollbacks
      |
      v
TECHNOLOGY: CI/CD pipelines (Jenkins, GitHub Actions, GitLab CI, ArgoCD)
      |
      v
SOLUTION: every commit is built, tested, scanned and (after approval or automatically) deployed
      |
      v
REAL-WORLD BENEFIT: small frequent safe releases, fast feedback, audit trail, quick rollback

CI = Continuous Integration: merge code often and verify each change automatically (build + tests). CD = Continuous Delivery (every change is *ready* to deploy, a human approves) or Continuous Deployment (every passing change is deployed automatically).

2. End-to-End Flow

Developer
   | git push / Pull Request
   v
Git Repository (GitHub/GitLab)
   | webhook
   v
CI Server (Jenkins / GitHub Actions runner)
   v
Build (compile / npm ci)
   v
Unit Tests
   v
Code Quality (SonarQube) --> Quality Gate
   v
Docker Build
   v
Security Scan (Trivy, secrets, SCA)
   v
Push to Registry (Harbor / ECR)  [tag = git sha]
   v
Deploy to Staging (Helm / ArgoCD)
   v
Smoke / Integration Tests
   v
Approval Gate (for prod) --> Deploy to Production
   v
Kubernetes runs the application
   v
Monitoring (Prometheus/Grafana) + Notifications (Slack)  --> failure? Rollback

A push or pull request triggers a webhook: Git tells the CI server something changed. The CI server allocates an agent/runner, checks out the code and runs the pipeline stages. Build compiles and installs dependencies; unit tests prove logic; SonarQube analyses code quality and the quality gate fails the pipeline if standards are not met. Docker build creates the image, Trivy scans it and dependency/secret scans run. The image is tagged with the commit SHA (immutable, traceable) and pushed to the registry. CD then deploys that same image to staging, runs smoke tests, waits for an approval gate for production and deploys with a safe strategy (rolling/canary/blue-green). Monitoring watches the new release; if error rate rises, the pipeline or ArgoCD rolls back, and notifications tell the team at every failure.

Jenkins vs GitHub Actions: Jenkins is self-hosted, extremely flexible with many plugins but you maintain it; GitHub Actions is managed, YAML in the repo, easy start, great marketplace, cost per minute for private repos. 5. Troubleshooting Playbook

Problem: Pipeline does not trigger on push
Possible cause: Webhook not configured/failing, branch filter, path filter, wrong event
How to check: Repo webhook delivery log; workflow on: / Jenkins multibranch scan log
Fix: Fix webhook URL/secret or trigger config.
Prevention: Test webhook after setup; keep triggers simple.
Problem: Build works locally but fails in CI
Possible cause: Different tool versions, missing env/secrets, cached files, OS differences
How to check: Read the failing step log; compare versions; run in the same container image locally
Fix: Pin versions; build in a container; provide required secrets.
Prevention: Use the same Docker image for local and CI.
Problem: Flaky tests
Possible cause: Shared state, timing, external services, order dependence
How to check: Re-run history; run test alone/in isolation
Fix: Fix test isolation, use test containers/mocks, retry only as last resort.
Prevention: Quarantine flaky tests and track them.
Problem: Docker push denied/unauthorized
Possible cause: Missing/expired registry credentials or wrong repo path
How to check: docker login output; check secret; repo permissions
Fix: Refresh credentials; use OIDC short-lived tokens.
Prevention: Avoid long-lived static credentials.
Problem: Deployment succeeded but app is broken
Possible cause: No smoke test/readiness gate, config mismatch, bad migration
How to check: App logs, kubectl rollout status, dashboards
Fix: Roll back to previous image tag; fix forward.
Prevention: Add smoke tests, readiness probes, automatic rollback.
Problem: Secrets leaked in pipeline logs
Possible cause: echo of variable, debug mode, unmasked secrets
How to check: Search logs; secret scanner
Fix: Rotate the secret immediately; mask/never print.
Prevention: Use masked secrets and secret managers; scanning in CI.

6. Production Best Practices

Development

  • Small commits and short-lived branches; run the same checks locally (pre-commit).

Production

  • Build once, deploy the same immutable image everywhere; tag with git SHA.
  • Environment promotion: dev > staging > prod with the same artifact.
  • Automatic rollback and post-deploy smoke tests.

Security

  • Least-privilege pipeline credentials; OIDC instead of static keys; secrets in a vault; never print secrets.
  • SAST, SCA, secret scan, image scan, SBOM, signing; branch protection and required reviews; pin action versions/SHAs.

Performance

  • Cache dependencies and Docker layers; parallelise stages; use ephemeral/autoscaling agents.

Reliability

  • Timeouts and retries for infra steps; idempotent deploy scripts; pipeline as code with review.

Cost Optimization

  • Auto-scale runners, cancel superseded runs, spot agents, cleanup old artifacts.

Monitoring & Logging

  • Track lead time, deployment frequency, change failure rate, MTTR (DORA metrics); notify on failure.

Backup & Disaster Recovery

  • Back up Jenkins home/config as code (JCasC); keep pipeline definitions in Git.

7. Common Mistakes

Beginner mistakes

  • Hard-coding secrets in the pipeline file.
  • One giant stage that does everything.

Developer mistakes

  • Skipping tests to 'get it green'.
  • Committing to main directly with no PR.

DevOps mistakes

  • Rebuilding a different image per environment.
  • No rollback plan.
  • Snowflake Jenkins servers without config as code.

Production mistakes

  • Deploying on Friday without monitoring/automatic rollback.
  • No approval gate for prod when required by policy.

Security mistakes

  • Running pipelines from forks with secrets.
  • Using latest and unpinned third-party actions/plugins.
  • Over-privileged deploy credentials.

8. Version / Environment Notes

  • GitHub Actions: pin actions by major version or commit SHA (for example actions/checkout@v4); check the marketplace for current versions; Node runtime versions of actions change.
  • Jenkins: use LTS releases; Declarative Pipeline is preferred over Scripted for most cases; plugins need regular updates; check the security advisories.
  • ArgoCD: Application CRD fields and sync options change between versions; check argo-cd docs for your version.
  • Deprecated: Docker latest-only deployments, Jenkins freestyle-only jobs and storing credentials in job config; use pipeline as code and credential stores.

11. How I Explain This to a Client

30-second explanation

CI/CD is an automated assembly line for software. Every code change is automatically built, tested, security-checked and delivered, so we release faster, with fewer errors, and can roll back quickly if something goes wrong.

2-minute explanation

Without CI/CD, releases depend on manual steps: someone builds, tests and copies files by hand, which is slow and error-prone. With CI/CD, when a developer pushes code, a pipeline automatically builds the application, runs tests, checks code quality and security, packages it as a container image and stores it in a registry. Then the same image is deployed to staging and, after approval or automatically, to production with a safe strategy such as rolling or canary. You get faster releases, consistent quality, a full audit trail of who released what, and a one-step rollback. We also track delivery metrics so you can see improvement over time.

5-minute deep explanation

Think of four layers. First, integration: developers merge small changes often; each change triggers a pipeline that builds and runs automated tests, and a quality gate blocks poor code. Second, security and packaging: the pipeline scans dependencies, secrets and the container image, then produces one immutable, versioned image in a private registry. Third, delivery: the same image is promoted through environments. In Kubernetes we use GitOps with ArgoCD, so the desired state lives in Git, deployments are pull-based and auditable, and drift is corrected automatically. Production releases use rolling, blue/green or canary strategies with automatic rollback based on monitoring. Fourth, governance and improvement: approvals for regulated environments, secrets in a vault, notifications, and DORA metrics (deployment frequency, lead time, change failure rate, recovery time). The outcome is shorter time to market, lower release risk and predictable operations.

13. Mini Project: GitHub Actions pipeline: build, test, scan, push, deploy via ArgoCD

Git push --> GitHub Actions
   build+test -> SonarQube gate -> docker build -> Trivy scan -> push to Harbor/ECR (tag=SHA)
   -> update image tag in GitOps repo (PR/commit)
   -> ArgoCD detects change -> syncs to Kubernetes (staging, then prod after approval)
   -> Prometheus/Grafana + Slack notification

Step 1: Workflow file .github/workflows/ci.yml

name: ci
on:
  push: { branches: [main] }
  pull_request:
permissions: { contents: read }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm test
      - name: Build image
        run: docker build -t registry.example.com/shop/api:${{ github.sha }} .
      - name: Scan image
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: registry.example.com/shop/api:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: '1'
      - name: Login and push
        if: github.ref == 'refs/heads/main'
        run: |
          echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login registry.example.com -u "${{ secrets.REGISTRY_USER }}" --password-stdin
          docker push registry.example.com/shop/api:${{ github.sha }}

on defines triggers; permissions limits the token; checkout gets code; setup-node with cache speeds installs; tests run before build; the image is tagged with the commit SHA so every deployment is traceable; Trivy fails the job (exit-code: 1) on HIGH/CRITICAL findings; push happens only on main. Secrets come from repository secrets (or use OIDC in production). Action versions vary: check the marketplace for current tags.

Step 2: Update GitOps repo

git clone https://github.com/acme/gitops.git && cd gitops
yq -i '.image.tag = "'$GITHUB_SHA'"' apps/api/values-staging.yaml
git commit -am "api: deploy $GITHUB_SHA" && git push

CI does not touch the cluster. It changes the desired state in Git; ArgoCD pulls and applies it (auditable and reversible with git revert).

Step 3: ArgoCD Application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata: { name: api-staging, namespace: argocd }
spec:
  project: default
  source: { repoURL: https://github.com/acme/gitops.git, path: apps/api, targetRevision: main, helm: { valueFiles: [values-staging.yaml] } }
  destination: { server: https://kubernetes.default.svc, namespace: staging }
  syncPolicy: { automated: { prune: true, selfHeal: true } }

automated sync applies Git changes; selfHeal reverts manual drift; prune removes deleted resources. For production use manual sync or an approval step.

Step 4: Verify and roll back

argocd app get api-staging
kubectl -n staging rollout status deploy/api
git revert HEAD && git push   # rollback = revert the commit

Check sync/health, confirm rollout and roll back by reverting the Git commit.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is CI/CD?

CI automatically builds and tests every code change; CD automatically delivers/deploys tested changes to environments.

Why: Foundation.

Real-world example: Push triggers build, tests and deployment to staging.

Q2. What is a pipeline?

An automated sequence of stages (build, test, scan, deploy) defined as code.

Why: Basic vocabulary.

Real-world example: Jenkinsfile or workflow YAML.

Q3. What is a webhook?

An HTTP callback that Git sends to the CI server on events like push.

Why: How triggers work.

Real-world example: GitHub webhook to Jenkins.

Q4. What is an artifact?

A build output such as a jar, zip or Docker image stored for later stages.

Why: Build once, deploy many.

Real-world example: Image in Harbor.

Q5. What is Jenkins?

An open-source, self-hosted automation server for CI/CD with a large plugin ecosystem.

Why: Very common tool.

Real-world example: Multibranch pipeline building on each PR.

Q6. What is GitHub Actions?

GitHub's built-in CI/CD using YAML workflows run on hosted or self-hosted runners.

Why: Modern default.

Real-world example: .github/workflows/ci.yml.

Q7. What is a stage vs a job/step?

Stage: logical phase; job: unit run on one runner; step: single command/action.

Why: Terminology.

Real-world example: Job build with steps checkout, test.

Q8. Why run tests in CI?

Catch bugs early before merge and keep main releasable.

Why: Quality gate.

Real-world example: PR blocked when tests fail.

Q9. What is a rollback?

Returning to the previous known-good version.

Why: Safety.

Real-world example: Deploy previous image tag.

Q10. What is a quality gate?

A rule (for example coverage, no critical issues) that must pass or the pipeline fails.

Why: Quality control.

Real-world example: SonarQube gate.

Intermediate (14)

Q11. Continuous Delivery vs Deployment?

Delivery keeps every change deployable but prod release needs approval; Deployment automatically releases every passing change.

Why: Common question.

Real-world example: Bank: delivery; SaaS: deployment.

Q12. Describe a full CI/CD flow for a containerised app.

Push > webhook > build/test > Sonar > docker build > scan > push registry > deploy staging > smoke test > approval > prod > monitor/rollback.

Why: Big-picture skill.

Real-world example: See e2e diagram.

Q13. How do you handle secrets in pipelines?

Store in the CI secret store or a vault, inject at runtime, mask in logs, prefer OIDC/short-lived credentials, rotate.

Why: Security basics.

Real-world example: GitHub OIDC to AWS role.

Q14. How to speed up pipelines?

Cache dependencies/layers, parallel jobs, matrix builds, incremental builds, smaller images, ephemeral autoscaled runners.

Why: Efficiency.

Real-world example: Cache npm and Docker layers.

Q15. What is a Jenkins agent?

A node that executes pipeline stages, keeping the controller free; can be static or dynamic (Kubernetes Pods).

Why: Jenkins architecture.

Real-world example: Pod agents per build.

Q16. Jenkinsfile: Declarative vs Scripted?

Declarative has a structured pipeline {} syntax and validation; Scripted is free-form Groovy. Prefer Declarative.

Why: Jenkins depth.

Real-world example: Use script blocks sparingly.

Q17. What is environment promotion?

Moving the same artifact through dev, staging, prod with increasing gates.

Why: Release management.

Real-world example: Same image SHA in all environments.

Q18. How do you version images?

Immutable tags (git SHA or semver), avoid latest, optionally digest pinning.

Why: Traceability.

Real-world example: api:1.4.2-3fa9c1d.

Q19. What is a matrix build?

Running the same job with multiple parameters (OS, language versions) in parallel.

Why: Compatibility testing.

Real-world example: Node 18/20/22.

Q20. What is a reusable workflow / shared library?

Central pipeline templates reused across repos (GitHub reusable workflows, Jenkins shared libraries).

Why: Standardisation.

Real-world example: Company-wide build template.

Q21. How do you protect the main branch?

Branch protection: required reviews, status checks, no force-push, signed commits.

Why: Governance.

Real-world example: PR must pass CI.

Q22. What is GitOps?

Git holds the desired state; an in-cluster agent (ArgoCD/Flux) continuously reconciles the cluster to Git.

Why: Modern CD.

Real-world example: Rollback with git revert.

Q23. Push-based vs pull-based deployment?

Push: CI has cluster credentials and applies; Pull: agent in cluster pulls from Git (no inbound credentials, drift correction).

Why: Security trade-off.

Real-world example: ArgoCD pull model.

Q24. Explain Jenkins architecture.

Controller (schedules, UI, config) and agents (execute builds), plugins, credentials store, jobs/pipelines.

Why: Common Jenkins question.

Real-world example: Kubernetes plugin spins agent Pods.

Advanced (15)

Q25. Design a secure pipeline.

Least privilege runners, OIDC, secret scanning, SAST/SCA/image scan, SBOM, signing, provenance (SLSA), branch protection, no secrets for forks, pinned dependencies, audit logs.

Why: DevSecOps.

Real-world example: Cosign-signed images verified at admission.

Q26. Blue/green vs canary vs rolling?

Rolling replaces gradually (simple); blue/green switches all traffic between two environments (fast rollback, 2x cost); canary sends small traffic share and observes metrics before increasing.

Why: Release strategy.

Real-world example: Canary 5% > 25% > 100% with Argo Rollouts.

Q27. How do you achieve zero-downtime deployment with DB changes?

Expand/contract migrations: backward-compatible schema first, deploy code, then remove old columns later; feature flags.

Why: Hard real-world problem.

Real-world example: Add nullable column first.

Q28. How do you implement automatic rollback?

Health checks and metrics analysis (Argo Rollouts analysis, Helm --atomic, Kubernetes rollout status) trigger rollback on failure.

Why: Reliability.

Real-world example: helm upgrade --atomic --timeout 5m.

Q29. Monorepo vs polyrepo CI strategy?

Monorepo: path filters and affected-build tooling to avoid rebuilding everything; polyrepo: simpler pipelines but cross-repo changes harder.

Why: Scale design.

Real-world example: Trigger only changed service paths.

Q30. What is SLSA/supply chain security?

Framework for build integrity: provenance, signed artifacts, hermetic builds, verified dependencies.

Why: Modern security.

Real-world example: Cosign + provenance attestation.

Q31. How do you scale Jenkins?

Distributed agents (Kubernetes/EC2 spot), controller HA practices, JCasC, plugin hygiene, separate controllers per team.

Why: Ops maturity.

Real-world example: Ephemeral Pod agents.

Q32. Explain OIDC authentication from CI to cloud.

CI issues a short-lived signed token; the cloud trusts it via an identity provider and grants a role without stored keys.

Why: Removes static secrets.

Real-world example: GitHub Actions to AWS IAM role.

Q33. How do you manage database migrations in pipelines?

Versioned tools (Flyway/Liquibase), run as a job before/with deploy, idempotent, tested in staging, backup/rollback plan.

Why: Data safety.

Real-world example: Flyway job in Helm hook.

Q34. Feature flags vs deployment?

Decouple deployment from release: deploy dark, enable per user segment; reduces risk.

Why: Modern delivery.

Real-world example: LaunchDarkly/Unleash.

Q35. What are DORA metrics?

Deployment frequency, lead time for changes, change failure rate, time to restore service.

Why: Measuring DevOps.

Real-world example: Weekly dashboard.

Q36. Ephemeral vs long-lived agents?

Ephemeral agents are clean and secure per job; long-lived accumulate state and risk.

Why: Security and reproducibility.

Real-world example: Kubernetes agent Pods.

Q37. How do you promote artifacts securely across environments?

Immutable image, signature verification, environment-specific config only, approvals, audit trail.

Why: Governance.

Real-world example: Same digest from staging to prod.

Q38. Progressive delivery?

Automated gradual rollout guided by metrics (canary analysis), using Argo Rollouts/Flagger.

Why: Advanced CD.

Real-world example: Rollback on error-rate SLO breach.

Q39. Handling long-running or flaky integration tests?

Parallelise, split suites, test containers, retry with limits, nightly runs, quarantine flakies.

Why: Pipeline health.

Real-world example: Smoke tests on PR, full suite nightly.

Scenario-Based (15)

Q40. Design CI/CD for 20 microservices.

Shared pipeline templates, per-service pipelines with path filters, common registry, GitOps repo per env, ArgoCD ApplicationSets, standard quality/security gates, DORA dashboards.

Why: Scale design.

Real-world example: Reusable workflow + Helm chart.

Q41. Prod deploy broke the site at 2am.

Roll back immediately (previous tag/revert), communicate, gather logs/metrics, postmortem, add tests/gates, improve rollout strategy.

Why: Incident handling.

Real-world example: git revert then ArgoCD sync.

Q42. Audit requires approvals and traceability.

Continuous delivery with environment approval gates, signed commits, PR reviews, immutable artifacts, logs retained.

Why: Compliance.

Real-world example: GitHub environment protection rules.

Q43. Pipeline takes 40 minutes.

Profile stages, cache, parallelise, split tests, use faster runners, skip unchanged components.

Why: Optimisation.

Real-world example: Reduced to 12 minutes.

Q44. A dependency has a critical CVE.

SCA scan fails build, update/pin dependency, rebuild, rescan, redeploy; automate with Dependabot/Renovate.

Why: Security response.

Real-world example: log4j style incident.

Q45. Developers deploy from laptops.

Remove direct access, enforce pipeline-only deploys, RBAC, GitOps, audit.

Why: Governance.

Real-world example: Only the CI ServiceAccount can deploy.

Q46. Need multi-region deployments.

Pipeline promotes to region A then B, health check between, global traffic routing, per-region GitOps apps.

Why: Scale/HA.

Real-world example: Staged region rollout.

Q47. Secrets exposed in a public repo.

Revoke/rotate immediately, purge history, add pre-commit and CI secret scanning, move to a vault.

Why: Security response.

Real-world example: Gitleaks.

Q48. Migrate from Jenkins to GitHub Actions.

Inventory jobs, map stages to workflows, replace plugins with actions, move secrets, run both in parallel, cut over gradually.

Why: Migration planning.

Real-world example: Start with simplest services.

Q49. Different config per environment.

Same image; config via Helm values/Kustomize overlays/secrets per environment.

Why: Twelve-factor.

Real-world example: values-prod.yaml.

Q50. How to deploy to Kubernetes securely from CI?

Prefer GitOps; otherwise short-lived credentials/OIDC, namespaced RBAC, no cluster-admin.

Why: Least privilege.

Real-world example: ArgoCD instead of kubectl in CI.

Q51. Reduce failed deployments.

More automated tests, staging parity, progressive delivery, feature flags, health-gated rollouts, rollback automation.

Why: Change failure rate.

Real-world example: Canary with analysis.

Q52. Team wants to release on demand.

Trunk-based development, feature flags, automated tests, continuous delivery.

Why: Process design.

Real-world example: Short-lived branches.

Q53. Build agents are overloaded.

Autoscaling ephemeral agents, queue metrics, parallelism limits, cache layers.

Why: Capacity planning.

Real-world example: Kubernetes-based Jenkins agents.

Q54. Third-party action compromised.

Pin to commit SHAs, allowlist actions, review updates, minimal permissions, rotate exposed secrets.

Why: Supply chain.

Real-world example: tj-actions incident style.

Troubleshooting-Based (10)

Q55. Webhook delivered but pipeline did not start.

Check branch/path filters, Jenkins job type/multibranch scan, webhook secret/response code, permissions.

Why: Trigger debugging.

Real-world example: Response 403 from Jenkins.

Q56. Pipeline fails only on CI: 'command not found'.

Tool not installed on agent/runner; use container agent or setup step and pin versions.

Why: Environment parity.

Real-world example: node/npm version missing.

Q57. Docker build fails in CI with 'permission denied /var/run/docker.sock'.

Agent user lacks Docker access or Docker-in-Docker not set; use a Docker-enabled agent or Kaniko/BuildKit.

Why: Common CI issue.

Real-world example: Add user to docker group or use rootless builder.

Q58. Cache not restored.

Key changed, cache scope/branch mismatch, size limit; check restore logs.

Why: Speed issues.

Real-world example: Key uses lockfile hash.

Q59. Deploy step hangs.

Rollout stuck (readiness), missing timeout, cluster unreachable; add --timeout and inspect Pods.

Why: Deployment debugging.

Real-world example: kubectl rollout status hangs.

Q60. Pipeline passes but wrong image deployed.

Tag mismatch/latest, GitOps repo not updated, ArgoCD out-of-sync; verify digest.

Why: Traceability.

Real-world example: Use SHA tags.

Q61. Jenkins is slow/out of memory.

Too many builds on controller, plugin issues, heap size, disk; move builds to agents, tune JVM, clean workspace.

Why: Jenkins ops.

Real-world example: Run zero executors on controller.

Q62. Secrets unavailable in PR from fork.

By design forks do not receive secrets; use pull_request_target carefully or run trusted checks after review.

Why: Security model.

Real-world example: GitHub Actions fork rules.

Q63. SonarQube gate fails unexpectedly.

New-code coverage threshold, new issues, wrong baseline; view the Sonar report.

Why: Quality gate.

Real-world example: Coverage on new code < 80%.

Q64. ArgoCD stuck OutOfSync/Degraded.

Check diff, resource health, hooks, RBAC and events in the Application; hard refresh; fix manifest.

Why: GitOps debugging.

Real-world example: Immutable field changed.

15. QUICK REVISION CHEAT SHEET

Definitions

  • CI: build+test every change. Continuous Delivery: releasable + approval. Continuous Deployment: auto release.
  • Artifact: build output. Quality gate: pass/fail standard. GitOps: Git is source of truth.
  • Rolling/Blue-Green/Canary: release strategies.

Commands

  • git push (trigger) | docker build -t reg/app:$SHA . | docker push reg/app:$SHA
  • trivy image --severity HIGH,CRITICAL --exit-code 1 img
  • helm upgrade --install app ./chart -f values.yaml --atomic --timeout 5m
  • kubectl rollout status|undo deploy/app | argocd app sync|get|rollback app
  • gitleaks detect | sonar-scanner

Files

  • Jenkinsfile
  • .github/workflows/*.yml
  • .gitlab-ci.yml
  • Dockerfile
  • Helm values-*.yaml
  • ArgoCD Application YAML

Architecture

  • Git > webhook > CI runner > build > test > quality > scan > registry > CD (GitOps) > cluster > monitoring.

Differences

  • CI vs CD; Delivery vs Deployment; Jenkins vs Actions; push vs pull CD; blue/green vs canary; artifact vs image.

Troubleshooting commands

  • Build once/deploy many, SHA tags, pipeline as code, OIDC, scan + sign, approvals for prod, automated rollback, DORA metrics.
