Pods, ReplicaSets & Deployments

Basic Kubernetes

Concept (What & Why)

Pod = smallest unit (1+ containers sharing network/storage). Deployment pods ko manage karta hai: replicas, rolling update, rollback.

Definition Deep-Dive

QuestionAnswer
Simple definitionA Pod runs your containers; a Deployment makes sure the right number of Pods are always running.
Technical definitionA Pod is the atomic scheduling unit sharing a network namespace and volumes. A Deployment manages ReplicaSets declaratively to provide rolling updates and rollbacks.
Why does it exist?Pods are ephemeral; Deployments provide desired count and controlled updates.
What happens without it?A bare Pod that dies stays dead.
When to useStateless applications.
When NOT to useDatabases needing stable identity (use StatefulSet).
Real-world analogyPod = a worker; Deployment = manager who ensures N workers are always on shift.

Diagram & Internal Working

Deployment -> ReplicaSet (v2) -> Pod, Pod, Pod
           \-> ReplicaSet (v1)  (kept for rollback; scaled to 0)
Pod: [app container][sidecar]  shared IP, localhost, volumes

How it works internally (diagram explained)

Deployment > ReplicaSet (one per version) > Pods. On image change the Deployment creates a new ReplicaSet and scales it up while scaling the old one down, respecting maxSurge and maxUnavailable and waiting for readiness. Old ReplicaSets are kept (revisionHistoryLimit) for rollback.

Deployment explained

kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: web
        image: nginx:1.27
        resources: { requests: { cpu: 100m, memory: 64Mi }, limits: { memory: 128Mi } }
        readinessProbe: { httpGet: { path: /, port: 80 } }
LineMeaning / WHY it exists
apiVersion: apps/v1API group and version for Deployments (check with kubectl api-resources).
replicas: 3Desired number of Pods; the controller keeps this true.
selector.matchLabelsHow the Deployment finds its Pods; must equal template labels.
template.metadata.labelsLabels put on each Pod so Services can select them.
image: nginx:1.27Pinned version for reproducible deploys.
resources.requestsWhat the scheduler reserves; also basis for HPA percentages.
resources.limits.memoryHard cap; exceeding it gives OOMKilled.
readinessProbePod receives Service traffic only after it passes.

Practical Examples

Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  strategy: { type: RollingUpdate, rollingUpdate: { maxSurge: 1, maxUnavailable: 0 } }
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
      - name: web
        image: nginx:1.27
        ports: [{ containerPort: 80 }]
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { cpu: 500m, memory: 256Mi }
        readinessProbe: { httpGet: { path: /, port: 80 }, initialDelaySeconds: 3 }
        livenessProbe:  { httpGet: { path: /, port: 80 }, initialDelaySeconds: 10 }

Operate it

kubectl apply -f web.yaml
kubectl scale deploy web --replicas=5
kubectl set image deploy/web web=nginx:1.28
kubectl rollout status deploy/web
kubectl rollout history deploy/web
kubectl rollout undo deploy/web

Hands-On Lab

Lab Goal

Deploy, scale, update and roll back an app.

Prerequisites

  • Running cluster (kind/minikube)

Step 1

kubectl create deployment web --image=nginx:1.26 --replicas=3 && kubectl get pods

Creates a Deployment with 3 Pods.

Step 2

kubectl set image deploy/web nginx=nginx:1.27 && kubectl rollout status deploy/web

Rolling update. kubectl get rs shows old and new ReplicaSets.

Step 3

kubectl set image deploy/web nginx=nginx:does-not-exist && kubectl get pods

Simulates a bad release: new Pods show ImagePullBackOff while old Pods keep serving because rolling update protects availability.

Step 4

kubectl rollout undo deploy/web && kubectl rollout history deploy/web

Rolls back to the working revision.

Real-World Problems & Fixes (Troubleshooting)

Problem: CrashLoopBackOff
Cause: App crashes on start (bad config/missing env/OOM)
Fix: kubectl logs pod --previous, describe pod (Last State, exit code 137 = OOM), fix config.
Problem: ImagePullBackOff
Cause: Wrong image name/tag or private registry without pull secret
Fix: Verify image; create imagePullSecrets.
Problem: Pod Pending
Cause: Insufficient CPU/mem or unbound PVC or taints
Fix: describe pod Events show reason; add nodes/adjust requests.

Best Practices

Production

  • 3+ replicas, probes, requests/limits, PDB.
  • Use maxUnavailable: 0 for critical services.

Common Mistakes

Beginner mistakes

  • Running bare Pods.
  • Selector not matching template labels.

Hinglish Explanation

Bare Pod kabhi mat chalao. Deployment use karo: wo Pod mar jaye to naya bana deta hai aur rolling update/rollback deta hai.

Interview Questions

Q1. Pod vs container?

Pod wraps one or more containers sharing network and storage.

Q2. Liveness vs readiness vs startup probe?

Liveness restarts unhealthy container; readiness removes from Service endpoints; startup protects slow-start apps.

Q3. Requests vs limits?

Requests used for scheduling and guarantees; limits are caps (CPU throttled, memory OOM-killed).

Q4. How does rolling update work?

New ReplicaSet scales up while old scales down respecting maxSurge/maxUnavailable.

Q5. Deployment vs StatefulSet?

Deployment for stateless; StatefulSet gives stable identity/storage/order.

Q6. A new version fails only in prod. How does Kubernetes limit the damage?

Readiness probes stop traffic to bad Pods and rolling update keeps old Pods until new ones are Ready; then rollout undo.

Why: Release safety.

Real-world example: Bad config caused new Pods to fail readiness; users unaffected.
