Helm, RBAC & Cluster Security

Advanced Kubernetes

Concept (What & Why)

Helm K8s package manager (templates + values). RBAC access control. Policies (Kyverno/OPA) aur Pod Security se hardening.

Definition Deep-Dive

QuestionAnswer
Simple definitionHelm packages Kubernetes YAML; RBAC controls who can do what; other controls harden the cluster.
Technical definitionHelm renders Go-templated charts with values into manifests and tracks releases. RBAC binds verbs on resources to subjects. Pod Security, NetworkPolicy and admission policies enforce runtime safety.
Why does it exist?Reuse and version deployments; enforce least privilege.
What happens without it?Copy-paste YAML per environment; everyone is admin.
When to useEvery real cluster.
When NOT to useOverly complex templates.
Real-world analogyHelm = installer with settings; RBAC = access badges.

Diagram & Internal Working

Helm chart = templates/ + values.yaml -> helm install -> release (versioned, rollback)
RBAC: Subject (user/SA) --RoleBinding--> Role (verbs on resources) in namespace

How it works internally (diagram explained)

helm upgrade --install renders templates + values into YAML, sends them to the API server and stores release history as Secrets in the namespace (enabling helm rollback). RBAC: the API server checks each request: subject (user/ServiceAccount) > Role/ClusterRole rules (verbs, resources) via RoleBinding.

Install / Setup

winget install Helm.Helm     # or: curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
helm repo add bitnami https://charts.bitnami.com/bitnami

Configuration Explained Line by Line

Role and RoleBinding explained

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: shop, name: deployer }
rules:
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get","list","patch"]
---
kind: RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata: { namespace: shop, name: ci-deployer }
subjects: [{ kind: ServiceAccount, name: ci, namespace: shop }]
roleRef: { kind: Role, name: deployer, apiGroup: rbac.authorization.k8s.io }
LineMeaning / WHY it exists
RoleNamespaced set of permissions (ClusterRole is cluster-wide).
verbsOnly get/list/patch: least privilege.
RoleBinding.subjectsWho gets the permissions (a ServiceAccount used by CI).
roleRefWhich Role is granted.

Practical Examples

Helm usage

helm create myapp
helm install web ./myapp -f values-prod.yaml -n prod --create-namespace
helm upgrade web ./myapp --set image.tag=v2 --atomic
helm rollback web 1; helm list -A; helm template ./myapp   # render only

RBAC read-only user

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: dev }
rules: [{ apiGroups: [""], resources: [pods, pods/log], verbs: [get, list, watch] }]
---
kind: RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata: { name: read-pods, namespace: dev }
subjects: [{ kind: User, name: anup }]
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
# check: kubectl auth can-i delete pods --as anup -n dev

Kyverno policy: disallow latest tag

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: no-latest }
spec:
  validationFailureAction: Enforce
  rules:
  - name: no-latest
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "Use a pinned image tag"
      pattern: { spec: { containers: [{ image: "!*:latest" }] } }

Hands-On Lab

Lab Goal

Install a chart and test RBAC.

Prerequisites

  • Helm 3
  • Cluster

Step 1

helm repo add bitnami https://charts.bitnami.com/bitnami && helm install web bitnami/nginx --set replicaCount=2

Installs a release.

Step 2

helm list && helm upgrade web bitnami/nginx --set replicaCount=3 && helm rollback web 1

Upgrade and rollback a release.

Step 3

kubectl create sa ci && kubectl auth can-i delete pods --as=system:serviceaccount:default:ci

Answers no: new ServiceAccounts have no permissions.

Real-World Problems & Fixes (Troubleshooting)

Problem: Helm upgrade half-applied and stuck
Cause: Failed hook/timeouts
Fix: Use --atomic --timeout; helm rollback.
Problem: 'forbidden' errors for a service account
Cause: Missing RBAC
Fix: kubectl auth can-i --as=system:serviceaccount:ns:sa ...; add minimal Role.

Best Practices

Security

  • Least privilege RBAC; separate ServiceAccounts; Pod Security restricted; default-deny NetworkPolicy; admission policies; scan images.
  • Pin chart versions; helm diff before upgrade.

Common Mistakes

Security mistakes

  • cluster-admin for CI.
  • Privileged Pods.

Hinglish Explanation

Interview Questions

Q1. Role vs ClusterRole?

Role namespaced; ClusterRole cluster-wide (or reusable definition).

Q2. Helm vs Kustomize?

Helm templating with values and releases; Kustomize overlays/patches on plain YAML.

Q3. How to secure a cluster?

RBAC least privilege, network policies, PSS, image scanning, secrets encryption, audit logs, private API endpoint.

Q4. What is a service account?

Identity for pods to call the API; use IRSA for AWS.

Q5. What is Pod Security Standards?

privileged, baseline, restricted profiles enforced per namespace.

Q6. How do you give a CI pipeline deploy access safely?

Dedicated ServiceAccount + namespaced Role limited to needed verbs, short-lived credentials (OIDC/IRSA), or GitOps so CI never touches the cluster.

Why: Least privilege.

Real-world example: ArgoCD applies; CI only pushes to Git.
