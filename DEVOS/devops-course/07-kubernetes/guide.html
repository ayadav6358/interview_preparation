Kubernetes: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Docker runs containers on one machine. In production you need dozens or hundreds of containers across many servers. Who restarts a crashed container? Who spreads load? Who does rolling updates without downtime? Kubernetes (K8s) is the container orchestrator that does this automatically: you declare the desired state ("run 3 copies of this image") and Kubernetes keeps reality equal to it.

PROBLEM: many containers on many servers must stay up, scale and update safely
      |
      v
TRADITIONAL APPROACH: shell scripts, manual `docker run` on each host, hand-made load balancers
      |
      v
PAIN: a node dies and apps stay down, manual scaling, downtime during deploys, no service discovery
      |
      v
TECHNOLOGY: Kubernetes (control plane + worker nodes + controllers)
      |
      v
SOLUTION: declarative YAML; controllers reconcile desired vs actual state continuously
      |
      v
REAL-WORLD BENEFIT: self-healing, autoscaling, rolling updates/rollback, portable across clouds

Container vs Kubernetes: a container is one packaged process; Kubernetes is the system that schedules, connects, scales and heals many containers. Kubernetes does not build images; it runs them.

2. End-to-End Flow

kubectl apply -f deploy.yaml
      |
      v
API Server (authenticate, authorize, validate)
      |
      v
etcd (stores desired state)
      |
      v
Controller Manager (Deployment > ReplicaSet > Pods needed)
      |
      v
Scheduler (picks a node for each Pod)
      |
      v
kubelet on node (talks to container runtime, starts containers)
      |
      v
Container runtime (containerd) pulls image, runs container
      |
      v
kube-proxy / CNI (Service networking) -> Application reachable
      |
      v
Controllers keep comparing DESIRED vs ACTUAL and fix any difference

kubectl sends your YAML to the API Server, the only component that talks to etcd (the cluster database). The API server authenticates you (who are you), authorizes (RBAC: are you allowed) and validates the object. The Deployment controller inside the controller manager notices "desired 3 replicas, actual 0" and creates a ReplicaSet, which creates 3 Pod objects. The scheduler assigns each unscheduled Pod to a node based on resources, taints and affinity. The kubelet on that node sees a Pod assigned to it, asks the container runtime (containerd) to pull the image and start containers, and reports status back. kube-proxy (or the CNI plugin) programs rules so a Service IP load-balances to the Pods. This loop never stops: if a Pod dies, the ReplicaSet controller creates a new one. That is self-healing.

5. Troubleshooting Playbook

Problem: Pod stuck in Pending
Possible cause: Not enough CPU/memory, node taints, unbound PVC, nodeSelector mismatch
How to check: kubectl describe pod X (Events), kubectl get nodes, kubectl get pvc
Fix: Add nodes/resources, fix requests, add tolerations, bind PVC.
Prevention: Right-size requests; use cluster autoscaler.
Problem: ImagePullBackOff / ErrImagePull
Possible cause: Wrong image/tag, private registry without imagePullSecret, rate limit
How to check: kubectl describe pod X; kubectl get events
Fix: Fix image name/tag, create docker-registry secret and reference it.
Prevention: Pin tags, use private registry with credentials.
Problem: CrashLoopBackOff
Possible cause: App exits at start: bad config, missing env/secret, failing probe, OOM
How to check: kubectl logs X --previous, kubectl describe pod X (Last State, Exit Code)
Fix: Fix config/command; raise memory limit if OOMKilled (137); fix liveness probe.
Prevention: Test image locally; use startupProbe for slow apps.
Problem: Service not reachable
Possible cause: Selector does not match Pod labels, wrong targetPort, no ready endpoints, NetworkPolicy
How to check: kubectl get endpoints svc, kubectl get pods --show-labels, kubectl exec -it pod -- curl svc:port
Fix: Match labels/ports; fix readiness probe; adjust NetworkPolicy.
Prevention: Use consistent labels and templates (Helm).
Problem: Ingress returns 404/502
Possible cause: Wrong host/path, backend service/port wrong, controller not installed, unhealthy backend
How to check: kubectl describe ingress, controller logs, kubectl get endpoints
Fix: Fix rules and service port; ensure controller and IngressClass exist.
Prevention: Smoke test after deploy.
Problem: Node NotReady
Possible cause: kubelet down, disk/memory pressure, network problem
How to check: kubectl describe node, journalctl -u kubelet on node
Fix: Restart kubelet, free disk, replace node.
Prevention: Node monitoring, autoscaling group health checks.

6. Production Best Practices

Development

  • Use kind/minikube locally; kubectl diff and --dry-run=client -o yaml before applying.

Production

  • Always set resource requests and limits.
  • Liveness, readiness and startup probes.
  • At least 2-3 replicas with PodDisruptionBudget and anti-affinity across zones.
  • Namespaces per team/env; labels everywhere; pin image tags.

Security

  • RBAC least privilege, dedicated ServiceAccounts.
  • NetworkPolicy default-deny.
  • Pod Security Standards (restricted), non-root, read-only root FS.
  • Secrets from an external store (External Secrets/Vault); encrypt etcd.
  • Scan images; admission policies (Kyverno/OPA).

Performance

  • HPA for scaling, right-sized requests, topology spread, node autoscaling.

Reliability

  • Rolling update with maxUnavailable=0 for critical services; PDBs; multi-AZ; backup etcd/Velero.

Cost Optimization

  • Right-size requests, Spot nodes for stateless workloads, cluster autoscaler/Karpenter, delete idle namespaces.

Monitoring & Logging

  • Prometheus + kube-state-metrics + Grafana; Loki/ELK for logs; alert on Pod restarts, Pending Pods, node pressure.

Backup & Disaster Recovery

  • etcd snapshots (self-managed), Velero for resources and volumes, GitOps repo as source of truth.

7. Common Mistakes

Beginner mistakes

  • Using bare Pods instead of Deployments.
  • Editing objects by hand instead of YAML in Git.
  • Using latest tag.

Developer mistakes

  • No readiness probe so traffic hits a starting Pod.
  • Hard-coding config instead of ConfigMap/Secret.

DevOps mistakes

  • No requests/limits (noisy neighbours, evictions).
  • Giving cluster-admin to everyone.

Production mistakes

  • Single replica for critical services.
  • No backups of persistent volumes.
  • Skipping version upgrades until unsupported.

Security mistakes

  • Treating base64 Secrets as encrypted.
  • Running privileged/root Pods.
  • No NetworkPolicy so any Pod can talk to any Pod.

8. Version / Environment Notes

  • Kubernetes releases about 3 times a year and supports roughly the latest three minor versions; check kubernetes.io for the current list.
  • Dockershim was removed in v1.24: nodes use containerd or CRI-O; docker commands on nodes do not show K8s containers (use crictl).
  • PodSecurityPolicy was removed in v1.25; use Pod Security Admission or Kyverno/OPA.
  • apiVersion values change (for example extensions/v1beta1 Ingress was removed): use networking.k8s.io/v1 and run kubectl explain / kubectl api-resources for your cluster.
  • Managed clusters (EKS/GKE/AKS) differ in load balancer annotations, storage classes and IAM integration.

11. How I Explain This to a Client

30-second explanation

Kubernetes is the platform that runs our containerised applications reliably in production. You tell it what you want, for example three copies of the app, and it keeps that true: it restarts failures, scales with traffic and updates without downtime.

2-minute explanation

Docker packages applications, but in production you need something to run them across many servers. Kubernetes schedules containers onto machines, restarts them if they fail, spreads traffic between copies and performs rolling updates so users see no downtime. Everything is described in version-controlled YAML, so environments are repeatable and auditable. For the business this means higher availability, faster releases, easy scaling during peak load and less vendor lock-in because it runs on any cloud. The trade-off is operational complexity, which is why we often use a managed service such as EKS.

5-minute deep explanation

I will cover four points. One, architecture: a control plane (API server, etcd, scheduler, controllers) decides what should run; worker nodes with kubelet run it. Two, how we deploy: the application is a Deployment with resource requests/limits and health probes, exposed through a Service and Ingress with TLS, with configuration in ConfigMaps and secrets from a secret manager. Three, delivery: the CI pipeline builds, tests, scans and pushes an image; ArgoCD or Helm updates the cluster from Git, using rolling updates with automatic rollback. Four, operations and security: autoscaling (HPA and node autoscaling), monitoring with Prometheus and Grafana, RBAC and network policies, backups, and regular version upgrades. The result is a platform that self-heals, scales and can be audited, and the team ships changes many times a day with lower risk.

13. Mini Project: Deploy a 3-tier app to Kubernetes with Ingress, HPA and Prometheus

Internet -> Ingress (TLS) -> Service web -> Deployment web (3 pods)
                                   -> Service api -> Deployment api (HPA 2-10)
                                                       -> Service db  -> StatefulSet postgres (PVC)
                                                       -> Service redis
Pipeline: Git > CI (build, test, scan) > Harbor/ECR > ArgoCD > Cluster > Prometheus/Grafana

Step 1: Local cluster

kind create cluster --name demo
kubectl cluster-info
kubectl create namespace shop

Creates a local cluster in Docker and a namespace. On EKS/GKE the cluster already exists.

Step 2: API Deployment + Service

apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: shop }
spec:
  replicas: 3
  selector: { matchLabels: { app: api } }
  strategy: { type: RollingUpdate, rollingUpdate: { maxUnavailable: 0, maxSurge: 1 } }
  template:
    metadata: { labels: { app: api } }
    spec:
      containers:
      - name: api
        image: myrepo/api:1.0.0
        ports: [{ containerPort: 3000 }]
        envFrom: [{ configMapRef: { name: api-config } }, { secretRef: { name: api-secret } }]
        resources: { requests: { cpu: 100m, memory: 128Mi }, limits: { cpu: 500m, memory: 256Mi } }
        readinessProbe: { httpGet: { path: /health, port: 3000 }, periodSeconds: 5 }
        livenessProbe: { httpGet: { path: /health, port: 3000 }, initialDelaySeconds: 15 }
---
apiVersion: v1
kind: Service
metadata: { name: api, namespace: shop }
spec:
  selector: { app: api }
  ports: [{ port: 80, targetPort: 3000 }]

The Deployment keeps 3 Pods, rolls out with zero unavailable Pods, and only sends traffic to Pods passing readinessProbe. selector must match the Pod labels, otherwise the Service has no endpoints. port is the Service port, targetPort the container port.

Step 3: Ingress + HPA

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop, namespace: shop }
spec:
  ingressClassName: nginx
  rules:
  - host: shop.example.com
    http:
      paths:
      - { path: /api, pathType: Prefix, backend: { service: { name: api, port: { number: 80 } } } }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api, namespace: shop }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

Ingress routes shop.example.com/api to the api Service (needs an ingress controller installed). HPA scales between 2 and 10 Pods to keep average CPU near 70% of requests (needs metrics-server).

Step 4: Apply, verify, roll back

kubectl apply -f k8s/
kubectl -n shop get pods,svc,ingress,hpa
kubectl -n shop rollout status deploy/api
kubectl -n shop set image deploy/api api=myrepo/api:1.1.0
kubectl -n shop rollout undo deploy/api

Apply manifests, check status, perform a rolling update by changing the image and roll back if the new version misbehaves. In production ArgoCD does the apply from Git.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Kubernetes?

An open-source container orchestration platform that schedules, scales, heals and updates containerised apps across a cluster.

Why: Foundation question.

Real-world example: Running 50 microservices across 10 nodes.

Q2. What is a Pod?

The smallest deployable unit: one or more containers sharing network and storage.

Why: Core object.

Real-world example: App container + sidecar log shipper in one Pod.

Q3. What is a Deployment?

A controller that manages ReplicaSets/Pods, providing scaling, rolling updates and rollback.

Why: How stateless apps are run.

Real-world example: kubectl create deployment web --image=nginx --replicas=3.

Q4. What is a Service?

A stable virtual IP/DNS name that load-balances to a set of Pods chosen by label selector.

Why: Pods are ephemeral with changing IPs.

Real-world example: api.shop.svc.cluster.local.

Q5. What is a Namespace?

A virtual partition of a cluster for isolation, quotas and RBAC.

Why: Multi-team/env usage.

Real-world example: dev, staging, prod namespaces.

Q6. What are labels and selectors?

Key-value tags on objects; selectors query them. Services and Deployments use them to find Pods.

Why: Glue of Kubernetes.

Real-world example: app=api label matches Service selector.

Q7. What is kubectl?

The CLI client for the Kubernetes API.

Why: Daily tool.

Real-world example: kubectl get pods -A.

Q8. ConfigMap vs Secret?

ConfigMap holds non-sensitive config; Secret holds sensitive data (base64-encoded, not encrypted by default).

Why: Config and security.

Real-world example: DB host in ConfigMap, DB password in Secret.

Q9. What is self-healing?

Controllers replace failed Pods, restart failing containers and reschedule from dead nodes.

Why: Main K8s benefit.

Real-world example: Delete a Pod and watch the ReplicaSet create a new one.

Q10. What is the difference between kubectl apply and create?

create fails if the object exists; apply is declarative and updates to match the file.

Why: GitOps friendliness.

Real-world example: Re-running apply -f in CI.

Intermediate (15)

Q11. Explain Kubernetes architecture.

Control plane: API server, etcd, scheduler, controller manager (and cloud controller). Nodes: kubelet, kube-proxy, container runtime.

Why: Tests component knowledge.

Real-world example: On EKS the control plane is managed by AWS.

Q12. What happens when you run kubectl apply?

Request to API server > authN/authZ/admission > stored in etcd > controllers create ReplicaSet/Pods > scheduler assigns node > kubelet starts containers > status reported.

Why: End-to-end flow.

Real-world example: See e2e diagram.

Q13. Service types?

ClusterIP, NodePort, LoadBalancer, ExternalName (and headless with clusterIP: None).

Why: Networking basics.

Real-world example: LoadBalancer creates an AWS ELB on EKS.

Q14. Ingress vs LoadBalancer Service?

Each LoadBalancer Service creates one cloud LB (L4); Ingress shares one entry point with host/path routing and TLS (L7) via a controller.

Why: Cost and design.

Real-world example: One ALB for 20 services.

Q15. Liveness vs readiness vs startup probe?

Liveness restarts a hung container; readiness removes the Pod from Service endpoints; startup delays the other probes for slow starters.

Why: Reliability.

Real-world example: Java app needs a startup probe.

Q16. Requests vs limits?

Requests are used by the scheduler and guarantee minimum resources; limits cap usage (CPU throttled, memory OOMKilled).

Why: Resource management.

Real-world example: Request 100m, limit 500m CPU.

Q17. How does a rolling update work?

Deployment creates a new ReplicaSet, scaling it up while scaling the old one down within maxSurge/maxUnavailable, gated by readiness.

Why: Zero-downtime deploys.

Real-world example: kubectl rollout status.

Q18. How to roll back?

kubectl rollout undo deployment/api (or --to-revision); GitOps: revert the commit.

Why: Release safety.

Real-world example: Bad image tag rolled back in seconds.

Q19. PV, PVC and StorageClass?

PV is storage; PVC is a request for storage; StorageClass enables dynamic provisioning.

Why: Stateful workloads.

Real-world example: EBS volume for Postgres via gp3 StorageClass.

Q20. StatefulSet vs Deployment?

StatefulSet gives stable network identity, ordered rollout and per-Pod persistent volumes.

Why: Databases.

Real-world example: kafka-0, kafka-1, kafka-2.

Q21. What is HPA?

HorizontalPodAutoscaler scales replicas from metrics such as CPU (needs metrics-server).

Why: Elasticity.

Real-world example: Scale 2 to 10 Pods at 70% CPU.

Q22. What is a DaemonSet?

Ensures one Pod runs on every (or selected) node.

Why: Node agents.

Real-world example: Fluent Bit, node-exporter.

Q23. Jobs and CronJobs?

Job runs to completion; CronJob runs Jobs on a schedule.

Why: Batch tasks.

Real-world example: Nightly DB backup.

Q24. How do Pods discover services?

CoreDNS provides svc.namespace.svc.cluster.local; env vars are also injected.

Why: Service discovery.

Real-world example: API calls http://db:5432.

Q25. What is Helm?

Package manager using charts with templates and values.yaml; supports releases, upgrades and rollbacks.

Why: Reusable deployments.

Real-world example: helm upgrade --install api ./chart -f prod.yaml.

Advanced (14)

Q26. What does etcd do and how do you protect it?

Consistent key-value store holding all cluster state. Protect with TLS, restricted access, regular snapshots, encryption at rest and 3/5 member HA.

Why: Cluster recovery.

Real-world example: etcdctl snapshot save.

Q27. Explain the scheduler's decision process.

Filter nodes (resources, taints, affinity, selectors) then score and choose the best; bind Pod to node.

Why: Placement control.

Real-world example: Use nodeAffinity for GPU nodes.

Q28. Taints and tolerations vs affinity?

Taints repel Pods unless tolerated; affinity attracts Pods to nodes/Pods. Use taints to reserve nodes, affinity to prefer placement.

Why: Scheduling design.

Real-world example: Taint spot nodes; only batch Pods tolerate.

Q29. How does kube-proxy implement Services?

Programs iptables or IPVS rules on each node to DNAT Service IPs to Pod endpoints (some CNIs like Cilium replace it with eBPF).

Why: Networking internals.

Real-world example: iptables -t nat -L KUBE-SERVICES.

Q30. CNI and Pod networking model?

Every Pod gets its own IP and can reach every other Pod without NAT; a CNI plugin (Calico, Cilium, AWS VPC CNI) implements it.

Why: Networking depth.

Real-world example: AWS VPC CNI assigns VPC IPs to Pods.

Q31. RBAC components?

Role/ClusterRole define permissions; RoleBinding/ClusterRoleBinding bind them to users, groups or ServiceAccounts.

Why: Security.

Real-world example: CI ServiceAccount allowed only to patch Deployments in one namespace.

Q32. How to secure a cluster?

RBAC least privilege, NetworkPolicy, Pod Security Standards, secrets encryption/external secrets, image scanning and signing, admission policies, audit logs, regular upgrades.

Why: Defence in depth.

Real-world example: Kyverno blocks privileged Pods.

Q33. PodDisruptionBudget?

Limits voluntary disruptions (drains, upgrades) so a minimum number of Pods stay available.

Why: Safe node maintenance.

Real-world example: minAvailable: 2 for api.

Q34. What is a Custom Resource / Operator?

CRDs extend the API; an operator is a controller that manages an app's lifecycle using CRDs.

Why: Extensibility.

Real-world example: Postgres operator creates HA clusters.

Q35. Cluster autoscaler vs Karpenter vs HPA?

HPA scales Pods; Cluster Autoscaler/Karpenter add/remove nodes for pending Pods.

Why: Full autoscaling story.

Real-world example: HPA adds Pods, then nodes are added.

Q36. How do you upgrade a cluster with zero downtime?

Upgrade control plane first, then nodes one by one (cordon, drain respecting PDBs), check API deprecations beforehand, test in staging.

Why: Operational maturity.

Real-world example: EKS managed node group rolling upgrade.

Q37. What is a sidecar and service mesh?

Sidecar is a helper container in the Pod; a service mesh (Istio/Linkerd) uses sidecars/eBPF for mTLS, retries and traffic shifting.

Why: Advanced networking.

Real-world example: Canary via Istio VirtualService.

Q38. Explain the Kubernetes API request lifecycle.

AuthN > AuthZ (RBAC) > Mutating admission > Schema validation > Validating admission > persist to etcd > watchers notified.

Why: Security/policy hooks.

Real-world example: Kyverno is an admission webhook.

Q39. Difference between Deployment Recreate and RollingUpdate?

Recreate kills all old Pods first (downtime); RollingUpdate replaces gradually.

Why: Strategy choice.

Real-world example: Recreate for apps that cannot run two versions.

Scenario-Based (15)

Q40. Design HA deployment for a critical API.

3+ replicas across AZs (topologySpreadConstraints), PDB, readiness/liveness probes, HPA, resource requests, rolling update maxUnavailable 0, multi-AZ nodes, monitoring and alerts.

Why: Design thinking.

Real-world example: Zone failure leaves 2/3 Pods running.

Q41. Zero-downtime deployment requirements?

Readiness probes, rolling update, preStop hook/graceful shutdown, enough replicas, PDB, connection draining at LB.

Why: Detail matters.

Real-world example: Users saw 502s until preStop sleep added.

Q42. Traffic spikes on Black Friday.

HPA with sane limits, cluster autoscaler/Karpenter, pre-scale, cache, load test, PDBs.

Why: Scaling plan.

Real-world example: Pre-scale replicas at 8am.

Q43. A namespace consumes all cluster resources.

ResourceQuota and LimitRange per namespace, requests/limits mandatory via policy.

Why: Multi-tenant fairness.

Real-world example: Dev team's job consumed 90% CPU.

Q44. Secrets committed to Git.

Rotate immediately, purge history, use Sealed Secrets/External Secrets/SOPS, add secret scanning.

Why: Security response.

Real-world example: Gitleaks in CI.

Q45. Move from Compose to Kubernetes.

Translate services to Deployments/Services, config to ConfigMaps/Secrets, volumes to PVCs, add probes/limits, Ingress, CI/CD, migrate step by step (Kompose helps as a start).

Why: Migration path.

Real-world example: Start with stateless services.

Q46. Database on Kubernetes or managed?

Prefer managed (RDS) for reliability and backups; run in-cluster only with an operator, PVs, backups and expertise.

Why: Judgement.

Real-world example: Postgres via CloudNativePG operator vs RDS.

Q47. Multi-environment configuration.

Same image, per-env values (Helm values/Kustomize overlays), namespaces, GitOps promotion.

Why: Environment parity.

Real-world example: values-dev.yaml, values-prod.yaml.

Q48. Restrict who can deploy to prod.

RBAC + GitOps: only ArgoCD ServiceAccount writes to prod, humans via PR approval, branch protection.

Why: Governance.

Real-world example: Prod repo requires 2 approvals.

Q49. Reduce cluster cost by 30%.

Right-size requests using metrics, Spot nodes, autoscaler, delete unused resources, schedule dev clusters off-hours.

Why: FinOps.

Real-world example: Karpenter consolidation.

Q50. Need to run a batch job every night.

CronJob with concurrencyPolicy Forbid, backoffLimit, resource limits, history limits, alert on failure.

Why: Batch workloads.

Real-world example: Report generator.

Q51. Application needs to talk to AWS S3 securely.

Use IRSA/Pod Identity (IAM role for ServiceAccount) instead of static keys.

Why: Cloud integration.

Real-world example: S3 read-only role on the api ServiceAccount.

Q52. Isolate database from other Pods.

NetworkPolicy default deny and allow only api Pods to port 5432.

Why: Zero-trust networking.

Real-world example: Requires a CNI that enforces policy (Calico/Cilium).

Q53. Blue/green on Kubernetes.

Two Deployments (blue/green) and switch the Service selector or use Argo Rollouts/ingress weights; keep old version for quick rollback.

Why: Release strategy.

Real-world example: Change selector version: green.

Q54. Observe a microservice slow response.

Check Pod CPU throttling, HPA, DB latency, use traces/metrics/logs, compare RED metrics.

Why: Observability.

Real-world example: CPU limit too low causing throttling.

Troubleshooting-Based (10)

Q55. Pod is Pending.

kubectl describe pod Events: insufficient resources, taints, PVC unbound, nodeSelector. Fix accordingly.

Why: Scheduling issues.

Real-world example: 0/3 nodes are available: Insufficient memory.

Q56. CrashLoopBackOff.

kubectl logs --previous, describe for exit code, check env/Secrets/probes/OOM.

Why: Most common failure.

Real-world example: Missing DB_URL env variable.

Q57. ImagePullBackOff.

Check image name/tag, imagePullSecret, registry reachability and rate limits.

Why: Registry issues.

Real-world example: Typo in tag.

Q58. Service has no endpoints.

Selector/label mismatch or Pods not ready. kubectl get endpoints, --show-labels.

Why: Networking basics.

Real-world example: Label app: api vs app: apis.

Q59. OOMKilled Pod.

Exit code 137/OOMKilled in describe. Increase memory limit or fix leak; check requests.

Why: Resource limits.

Real-world example: Node app heap exceeded 256Mi.

Q60. Ingress 502/503.

Backend Pods not ready or wrong port; check controller logs, endpoints, service targetPort.

Why: L7 debugging.

Real-world example: targetPort 8080 vs app 3000.

Q61. Node NotReady.

kubectl describe node, kubelet logs, disk/memory pressure, CNI issues; cordon/drain and replace.

Why: Node health.

Real-world example: Disk full from logs.

Q62. kubectl: Unauthorized/Forbidden.

Check kubeconfig context/credentials (Unauthorized) and RBAC with kubectl auth can-i (Forbidden).

Why: AuthN vs AuthZ.

Real-world example: Expired EKS token.

Q63. Rollout stuck.

kubectl rollout status, new Pods not ready (probe, image, quota); rollout undo.

Why: Deployment debugging.

Real-world example: Readiness probe path wrong.

Q64. DNS not resolving inside Pods.

Check CoreDNS Pods/logs, kubectl exec -- nslookup svc, NetworkPolicy blocking UDP 53.

Why: Cluster DNS.

Real-world example: CoreDNS OOM.
