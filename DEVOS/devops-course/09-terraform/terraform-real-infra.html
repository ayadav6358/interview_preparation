Real Project: VPC + EKS + RDS

Intermediate Infrastructure as Code: Terraform

Concept (What & Why)

Full production-style stack Terraform mein: network, cluster, database, IAM. Community modules reuse karo.

Definition Deep-Dive

QuestionAnswer
Simple definitionUse Terraform to build a realistic stack: network, Kubernetes cluster and database.
Technical definitionLayered stacks (network > platform (EKS) > data (RDS)) exchange values through outputs/remote state or data sources; community modules (terraform-aws-modules) provide well-tested building blocks.
Why does it exist?Real environments are composed of several dependent parts.
What happens without it?One unmanageable file.
When to useProduction platforms.
When NOT to useCoupling everything in one state.
Real-world analogyBuilding a house in stages: foundation, structure, interior.

Diagram & Internal Working

terraform/
 ├─ modules/ (vpc, rds)
 └─ envs/prod: vpc -> eks -> rds -> outputs
Dependencies flow via outputs (module.vpc.private_subnets -> eks.subnet_ids)

How it works internally (diagram explained)

Stack 1 creates the VPC and outputs subnet IDs. Stack 2 (EKS) reads them via terraform_remote_state or SSM/data sources, creates the cluster with IAM/OIDC. Stack 3 creates RDS in database subnets, with a security group allowing only the node/app SG. Each has its own state and plan.

Install / Setup

terraform init && terraform plan   # in envs/prod

Configuration Explained Line by Line

Composition example explained

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
  name = "prod"
  cidr = "10.0.0.0/16"
  azs             = ["ap-south-1a", "ap-south-1b"]
  private_subnets = ["10.0.10.0/24", "10.0.11.0/24"]
  public_subnets  = ["10.0.0.0/24", "10.0.1.0/24"]
  enable_nat_gateway = true
}
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"
  cluster_name    = "prod"
  vpc_id          = module.vpc.vpc_id
  subnet_ids      = module.vpc.private_subnets
}
LineMeaning / WHY it exists
terraform-aws-modulesWidely used community modules: pin versions and read their upgrade notes.
module.vpc.private_subnetsPassing outputs between modules.
subnet_idsCluster nodes live in private subnets.

Practical Examples

VPC + EKS using registry modules

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
  name = "prod"
  cidr = "10.0.0.0/16"
  azs  = ["ap-south-1a", "ap-south-1b", "ap-south-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]
  enable_nat_gateway = true
  single_nat_gateway = false
}

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"
  cluster_name    = "prod"
  cluster_version = "1.30"
  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets
  eks_managed_node_groups = {
    default = { instance_types = ["t3.large"], min_size = 2, max_size = 6, desired_size = 3 }
  }
}

resource "aws_db_instance" "pg" {
  identifier              = "prod-pg"
  engine                  = "postgres"
  instance_class          = "db.t3.medium"
  allocated_storage       = 50
  multi_az                = true
  storage_encrypted       = true
  backup_retention_period = 7
  db_subnet_group_name    = aws_db_subnet_group.db.name
  vpc_security_group_ids  = [aws_security_group.db.id]
  username                = "app"
  manage_master_user_password = true   # stored in Secrets Manager, not in state
}

Hands-On Lab

Lab Goal

Plan (not apply) a VPC + EKS + RDS composition.

Prerequisites

  • Terraform
  • AWS credentials

Step 1

Write the modules above plus an aws_db_instance in database subnets

Complete stack.

Step 2

terraform init && terraform plan

Review the resources to be created and estimated complexity; EKS and NAT cost real money.

Step 3

Only apply in a sandbox account, then terraform destroy

Avoid surprise bills.

Real-World Problems & Fixes (Troubleshooting)

Problem: Destroying VPC fails
Cause: Dependencies (ENIs from LBs/EKS) still exist
Fix: Delete K8s LoadBalancer Services / Ingress first, then terraform destroy.
Problem: DB password ends up in state
Cause: Hard-coded/plain variable
Fix: Use manage_master_user_password or Secrets Manager data source; encrypt state.

Best Practices

Production

  • Separate state per layer; prevent_destroy on data; pinned module versions.

Cost Optimization

  • Sandbox destroy schedule; single NAT for dev.

Common Mistakes

Production mistakes

  • Everything in one state.

Hinglish Explanation

Bade project mein network, cluster, database ko alag stacks mein rakho, taaki galti ka blast radius chhota rahe.

Version / Environment Notes

  • terraform-aws-modules major versions change inputs; always check the module's upgrade guide.

Interview Questions

Q1. How do modules pass data?

Outputs of one module become inputs of another.

Q2. How to avoid secrets in state?

Managed passwords, external secret stores, mark sensitive, restrict state access.

Q3. How to handle multiple environments?

Separate dirs/backends + shared modules + tfvars.

Q4. What is terraform drift?

Real infra changed outside Terraform; detect via plan/refresh.

Q5. prevent_destroy purpose?

Blocks accidental destroy of critical resources.

Q6. How do stacks share values?

Outputs via terraform_remote_state, SSM Parameter Store/Secrets Manager, or data sources; prefer data sources to avoid tight state coupling.
