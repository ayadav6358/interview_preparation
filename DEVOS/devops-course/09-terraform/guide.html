Infrastructure as Code: Terraform: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Creating cloud infrastructure by clicking in a console is slow, undocumented and impossible to reproduce exactly. Terraform (Infrastructure as Code, IaC) lets you describe infrastructure in files, review it like code, and create, change or destroy it repeatably with one workflow.

PROBLEM: infrastructure must be created and changed consistently
      |
      v
TRADITIONAL APPROACH: console clicking ('click-ops') or ad-hoc scripts
      |
      v
PAIN: drift, no review, no history, can't recreate environments, mistakes in production
      |
      v
TECHNOLOGY: Terraform (declarative HCL, providers, state, plan/apply)
      |
      v
SOLUTION: code in Git > plan (preview) > review > apply
      |
      v
REAL-WORLD BENEFIT: repeatable environments, audit trail, safe changes, disaster recovery

Terraform is declarative: you state the desired end result and Terraform works out the steps. It keeps a state file mapping your code to real resources and uses providers (plugins) to talk to AWS, Azure, Kubernetes and hundreds of other APIs.

2. End-to-End Flow

Engineer writes main.tf (HCL)
   | git push / PR
   v
CI: terraform fmt + validate + tflint + security scan (tfsec/checkov)
   v
terraform init  (download providers, configure backend)
   v
terraform plan  (compare code vs state vs real world -> preview)
   v
Review / approval (policy checks: OPA/Sentinel)
   v
terraform apply (provider API calls create/update/destroy)
   v
State updated in remote backend (S3 + DynamoDB lock / Terraform Cloud)
   v
Infrastructure ready -> outputs used by CI/CD, Ansible, Kubernetes

init prepares the working directory: it downloads providers and configures the backend where state is stored. plan reads your code, the state and the real infrastructure (refresh) and prints exactly what will be added, changed or destroyed, without doing it. After review, apply executes the plan by calling the provider APIs in dependency order (Terraform builds a dependency graph). The state is updated; a lock prevents two people from applying at once. Outputs expose values (like a load balancer DNS) to other tools.

Terraform vs CloudFormation: Terraform is multi-cloud with a large provider ecosystem; CloudFormation is AWS-native with deep integration and no state file to manage. Terraform vs Ansible: Terraform provisions infrastructure (declarative, stateful); Ansible configures software inside servers (procedural/idempotent, agentless). Terraform vs OpenTofu: OpenTofu is a community-driven open-source fork after Terraform's licence change; syntax is largely compatible: check versions.

5. Troubleshooting Playbook

Problem: Error acquiring the state lock
Possible cause: Another apply running or a crashed run left a lock
How to check: Check who holds it (lock info), CI runs
Fix: Wait; if stale, terraform force-unlock <ID> after confirming no run is active.
Prevention: Run applies only via CI with concurrency limits.
Problem: Plan wants to destroy/recreate a resource unexpectedly
Possible cause: Immutable attribute changed, renamed resource, count index shift
How to check: Read # forces replacement in the plan
Fix: Use moved blocks / terraform state mv, avoid changing immutable fields, use for_each.
Prevention: Always review plan; use prevent_destroy for critical resources.
Problem: Drift: real resources differ from code
Possible cause: Manual console changes
How to check: terraform plan shows changes
Fix: Apply to restore, or import/update code if the change is desired.
Prevention: Restrict console write access; scheduled drift detection.
Problem: resource already exists
Possible cause: Resource created outside Terraform
How to check: Cloud console / CLI
Fix: terraform import (or import block) then adjust code.
Prevention: Create everything through IaC.
Problem: Provider auth errors
Possible cause: Missing/expired credentials or wrong region/profile
How to check: aws sts get-caller-identity, env vars
Fix: Fix credentials/role; use OIDC in CI.
Prevention: No static keys in code.
Problem: State corrupted/lost
Possible cause: Local state deleted or backend misconfigured
How to check: Backend config, bucket versioning
Fix: Restore from versioned S3 bucket; re-import if necessary.
Prevention: Remote backend with versioning, encryption and locking.

6. Production Best Practices

Development

  • terraform fmt, validate, small modules, meaningful variable descriptions/types, pin provider and Terraform versions.

Production

  • Remote state with locking; separate state per environment/component; plan in PR, apply from CI after approval; modules versioned with tags.

Security

  • Never commit *.tfstate or secrets; mark variables sensitive; encrypt state; least-privilege IAM/OIDC for CI; scan with tfsec/checkov; policy as code.

Performance

  • Split large stacks; use -target only for emergencies; parallelism tuned; avoid huge monoliths.

Reliability

  • prevent_destroy on data stores; backups of state; create_before_destroy for zero-downtime replacement.

Cost Optimization

  • Tagging via default_tags; scheduled dev environments; cost estimation (Infracost) in PRs.

Monitoring & Logging

  • Log plan/apply output in CI; alert on drift.

Backup & Disaster Recovery

  • Versioned state bucket with replication; IaC allows rebuilding an environment in a new region.

7. Common Mistakes

Beginner mistakes

  • Editing infrastructure manually after Terraform created it.
  • Using apply -auto-approve locally without reading the plan.

Developer mistakes

  • Hard-coded values instead of variables.
  • Copy-pasting instead of modules.

DevOps mistakes

  • One giant state file for everything.
  • No provider version pinning.
  • Local state in a team.

Production mistakes

  • Applying without review.
  • No prevent_destroy on databases.

Security mistakes

  • Secrets or state in Git.
  • Over-privileged CI credentials.

8. Version / Environment Notes

  • Terraform 1.x is stable; features like moved, import blocks, check blocks need recent 1.x versions. Pin with required_version.
  • Licence change in 2023 (BSL) led to OpenTofu, a compatible open-source fork: verify compatibility for your version and providers.
  • Provider versions change resource arguments (e.g. AWS provider v4/v5 split S3 bucket settings into separate resources): pin ~> versions and read upgrade guides.
  • terraform workspace semantic differs in Terraform Cloud vs CLI workspaces.

11. How I Explain This to a Client

30-second explanation

Terraform lets us define your cloud infrastructure as code. That means environments can be created, reviewed, changed and rebuilt in a repeatable, auditable way instead of by manual clicking.

2-minute explanation

Instead of building servers and networks by hand, we write them as code and store it in Git. Every change goes through a pull request; a plan shows exactly what will change before anything is applied. This removes configuration drift between environments, gives a full audit trail, and lets us recreate the whole platform quickly for testing or disaster recovery. We keep the state securely in a shared, locked location and scan the code for security problems before deployment. You get faster, safer changes and consistent environments.

5-minute deep explanation

Consider four points. Model: Terraform is declarative: we describe the desired infrastructure (VPC, Kubernetes cluster, database), and Terraform computes the changes using providers for each cloud service. Workflow: code in Git, automated format/validate/security checks, plan in the pull request for review, then apply from the pipeline after approval, using short-lived credentials. State and structure: remote encrypted state with locking, separate stacks per environment, and versioned reusable modules so teams follow the same secure patterns. Governance: policy as code to block risky configurations, cost estimates in PRs, drift detection, and prevent_destroy on critical data stores. Together this reduces risk, speeds delivery and provides compliance evidence.

13. Mini Project: VPC + EC2 with remote state and a reusable module

Git repo
  envs/dev/main.tf --> module "network" (VPC, subnets) --> module "web" (EC2 + SG)
  backend: S3 bucket (versioned, encrypted) + DynamoDB lock table
CI: fmt, validate, tflint, checkov > plan (PR comment) > apply (approved)

Step 1: Provider and backend

terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
  backend "s3" {
    bucket         = "my-tf-state-123456"
    key            = "dev/network/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"
    encrypt        = true
  }
}
provider "aws" {
  region = var.region
  default_tags { tags = { Env = "dev", ManagedBy = "terraform" } }
}

required_version/version pin tool versions. The S3 backend stores state remotely; dynamodb_table provides locking (newer Terraform releases also support S3-native locking: check the docs for your version). default_tags tags every resource for cost tracking. The bucket and table must exist before init.

Step 2: Variables and outputs

variable "region"   { type = string  default = "ap-south-1" }
variable "vpc_cidr" { type = string  default = "10.0.0.0/16" }
variable "db_password" { type = string  sensitive = true }

output "vpc_id" { value = aws_vpc.main.id }

Typed variables document inputs; sensitive hides values in output; outputs feed other stacks or CI.

Step 3: Resources

resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  tags = { Name = "dev-vpc" }
}

resource "aws_subnet" "public" {
  for_each          = { a = "10.0.0.0/24", b = "10.0.1.0/24" }
  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value
  availability_zone = "${var.region}${each.key}"
  tags = { Name = "public-${each.key}" }
}

Referencing aws_vpc.main.id creates an implicit dependency, so Terraform creates the VPC first. for_each creates one subnet per map key with stable addresses (adding/removing a key does not shift others).

Step 4: Run the workflow

terraform fmt -check && terraform init
terraform validate
terraform plan -out tfplan
terraform apply tfplan
terraform output
terraform destroy   # when finished, to avoid cost

plan -out then apply tfplan guarantees you apply exactly what was reviewed. Always destroy lab resources.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Terraform?

An IaC tool using declarative HCL to provision and manage infrastructure across providers.

Why: Foundation.

Real-world example: Create a VPC with code.

Q2. What is IaC?

Managing infrastructure through versioned code rather than manual processes.

Why: Concept.

Real-world example: Same code for dev and prod.

Q3. Explain init, plan, apply, destroy.

init downloads providers/backends; plan previews; apply executes; destroy removes resources.

Why: Workflow.

Real-world example: Plan before apply.

Q4. What is a provider?

A plugin that translates Terraform resources into API calls for a platform.

Why: Architecture.

Real-world example: aws, azurerm, kubernetes.

Q5. What is the state file?

JSON mapping Terraform resources to real objects and metadata.

Why: Core concept.

Real-world example: terraform.tfstate.

Q6. What is a resource vs data source?

Resource creates/manages something; data source reads existing information.

Why: Syntax.

Real-world example: data aws_ami.

Q7. What are variables and outputs?

Inputs and exposed values of a configuration/module.

Why: Reusability.

Real-world example: Output ALB DNS.

Q8. What is terraform fmt and validate?

fmt formats code; validate checks syntax and consistency.

Why: Quality.

Real-world example: Run in CI.

Q9. What does terraform destroy do?

Destroys all managed resources in the configuration.

Why: Cleanup.

Real-world example: Tear down lab.

Q10. What language does Terraform use?

HCL (HashiCorp Configuration Language).

Why: Basics.

Real-world example: resource "aws_instance" "web" {}.

Intermediate (13)

Q11. Why remote state and locking?

Share state across a team safely and prevent concurrent applies that corrupt it.

Why: Team workflow.

Real-world example: S3 + DynamoDB.

Q12. What are modules?

Reusable packages of Terraform config with inputs and outputs.

Why: DRY.

Real-world example: vpc module reused for each env.

Q13. count vs for_each?

count uses numeric index (removal shifts indexes); for_each uses keys for stable addressing.

Why: Common pitfall.

Real-world example: for_each for subnets.

Q14. Explain implicit vs explicit dependencies.

References create implicit dependencies; depends_on declares explicit ones.

Why: Ordering.

Real-world example: SG before instance.

Q15. What is terraform import?

Bring an existing resource under Terraform management by adding it to state (code must exist).

Why: Adoption.

Real-world example: Import a console-made bucket.

Q16. What are lifecycle rules?

create_before_destroy, prevent_destroy, ignore_changes, replace_triggered_by.

Why: Safety controls.

Real-world example: prevent_destroy on RDS.

Q17. Workspaces vs separate dirs?

Workspaces share config with separate state; directories/stacks isolate environments more strongly.

Why: Env strategy.

Real-world example: Prod in own state and account.

Q18. How to handle secrets?

Do not hardcode; use variables marked sensitive from a secret store/CI, reference Secrets Manager/Vault data sources; remember values may still land in state.

Why: Security.

Real-world example: Encrypt state.

Q19. What is a data source used for?

Read info such as latest AMI, existing VPC, caller identity.

Why: Composition.

Real-world example: aws_caller_identity.

Q20. What are provisioners and why avoid them?

local-exec/remote-exec run scripts at create time; last resort as they are not declarative; prefer cloud-init/Ansible/images.

Why: Best practice.

Real-world example: user_data instead.

Q21. How do you pin versions?

required_version, required_providers with ~>, lock file .terraform.lock.hcl committed.

Why: Reproducibility.

Real-world example: Avoid surprise upgrades.

Q22. What is terraform taint/-replace?

Force recreation of a resource; use terraform apply -replace=addr (taint is deprecated).

Why: Modern syntax.

Real-world example: Rebuild a bad instance.

Q23. How to structure a Terraform repo?

Modules directory, envs directories, per-component states, README, CI checks.

Why: Organisation.

Real-world example: modules/, envs/dev/.

Advanced (11)

Q24. How does Terraform build the execution plan?

Loads config and state, refreshes real state, builds a dependency graph, diffs desired vs current, outputs actions, executes in parallel where independent.

Why: Internals.

Real-world example: Graph via terraform graph.

Q25. How do you refactor without recreating resources?

moved blocks or terraform state mv; import blocks; careful plan review.

Why: Maintenance.

Real-world example: Rename resource to module.

Q26. How to detect and handle drift?

Scheduled plan -detailed-exitcode, refresh, alerts; reconcile by applying or updating code; restrict console access.

Why: Ops.

Real-world example: Nightly drift job.

Q27. Design multi-account, multi-region Terraform.

Separate state and provider aliases per account/region, assume-role/OIDC, modules, layered stacks (network, platform, apps).

Why: Enterprise design.

Real-world example: Provider alias aws.dr.

Q28. Secure the CI pipeline for Terraform.

OIDC federation, least-privilege role per environment, plan in PR with read-only role, apply with approval, policy checks, no secrets in logs.

Why: Security.

Real-world example: GitHub Actions to AWS.

Q29. Policy as code options?

Sentinel (Terraform Cloud), OPA/Conftest, Checkov/tfsec rules.

Why: Governance.

Real-world example: Deny public S3.

Q30. How do you test Terraform?

validate, tflint, terraform test, Terratest, ephemeral environments, plan assertions.

Why: Quality.

Real-world example: Terratest for modules.

Q31. State locking internals with S3/DynamoDB?

Terraform writes a lock item with ID/who/operation; concurrent runs fail until released; newer versions offer native S3 lock files.

Why: State handling.

Real-world example: force-unlock caution.

Q32. Explain sensitive values and state.

Sensitive hides values in CLI output but they are stored in state in plain text; protect the state.

Why: Security nuance.

Real-world example: DB passwords.

Q33. Terraform vs Kubernetes operators for infrastructure?

Crossplane/operators provide continuous reconciliation in cluster; Terraform is run-based with explicit plan/apply.

Why: Design choices.

Real-world example: Crossplane for self-service infra.

Q34. How to manage large blast radius?

Split state by lifecycle and ownership, use targeted plans carefully, approvals, prevent_destroy.

Why: Risk control.

Real-world example: Separate network and app states.

Scenario-Based (10)

Q35. Two engineers ran apply at the same time.

Locking should prevent this; without locking state may corrupt. Enforce remote backend with lock and apply through CI only.

Why: Team safety.

Real-world example: Backend misconfigured.

Q36. Plan shows database will be destroyed.

Stop, inspect why (forces replacement), avoid apply, adjust code or use lifecycle, take a snapshot first.

Why: Risk handling.

Real-world example: Changed identifier.

Q37. Infrastructure was changed in the console.

Run plan to see drift, decide to revert (apply) or codify, then lock down access.

Why: Governance.

Real-world example: SG rule added manually.

Q38. Onboard existing infrastructure to Terraform.

Inventory, write code, import blocks, plan until no diff, gradually adopt with modules.

Why: Migration.

Real-world example: Legacy VPC.

Q39. State file leaked.

Treat all secrets in state as compromised: rotate, restrict access, encrypt bucket, audit access.

Why: Incident response.

Real-world example: Public bucket.

Q40. Need dev/stage/prod with minimal duplication.

Reusable modules + per-environment root modules/tfvars, separate state and accounts.

Why: Structure.

Real-world example: envs/prod/main.tf calls module.

Q41. Terraform is slow with 2000 resources.

Split stacks, increase parallelism carefully, reduce refresh with targeted plans in emergencies, use data sources sparingly.

Why: Scale.

Real-world example: Network vs app split.

Q42. Upgrade a provider major version safely.

Read upgrade guide, test in dev with plan, fix deprecated args, roll out gradually.

Why: Change management.

Real-world example: AWS provider v4 to v5.

Q43. How do you deploy to multiple regions?

Provider aliases or per-region stacks, shared modules, region variable.

Why: Multi-region.

Real-world example: DR region.

Q44. Prevent public S3 buckets by policy.

Block Public Access resource, checkov/OPA rule in CI, SCP.

Why: Preventive control.

Real-world example: Fail PR on violation.

Troubleshooting-Based (10)

Q45. Error: No valid credential sources found.

Provider cannot find credentials; set env/profile/OIDC role.

Why: Auth.

Real-world example: CI missing role.

Q46. Provider produced inconsistent result after apply.

Provider bug or eventual consistency; re-run apply, upgrade provider, check known issues.

Why: Provider issues.

Real-world example: Tags propagation.

Q47. Error: Cycle.

Circular dependency between resources; break with separate resources or data references.

Why: Graph.

Real-world example: SG rules referencing each other: use aws_security_group_rule.

Q48. Inconsistent lock file.

Provider versions changed; run terraform init -upgrade and commit the lock file.

Why: Version control.

Real-world example: After bumping version.

Q49. Apply stuck creating a resource.

Waiting on API/dependencies/quotas; check cloud console, timeouts, quotas.

Why: Ops.

Real-world example: NAT gateway or EKS creation is slow.

Q50. Error: Invalid for_each argument.

Keys must be known at plan time; use static keys or apply in stages.

Why: Language limit.

Real-world example: Keys from resource attributes.

Q51. Plan differs every time (perpetual diff).

Provider normalises values (case/order/JSON); use jsonencode, ignore_changes where justified.

Why: Idempotency.

Real-world example: IAM policy JSON.

Q52. AccessDenied during apply.

CI role lacks the action; use CloudTrail to find the denied API call and add least privilege.

Why: IAM.

Real-world example: Missing iam:PassRole.
