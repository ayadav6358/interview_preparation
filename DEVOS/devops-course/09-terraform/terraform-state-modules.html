Remote State, Modules & Variables

Intermediate Infrastructure as Code: Terraform

Concept (What & Why)

Team mein kaam karne ke liye remote state + locking. Modules reuse ke liye. Variables, locals, for_each, dynamic blocks.

Definition Deep-Dive

QuestionAnswer
Simple definitionState remembers what Terraform created; modules let you reuse code.
Technical definitionState maps resource addresses to real IDs and attributes; backends store and lock it. Modules encapsulate resources behind input variables and outputs and can be versioned.
Why does it exist?Team collaboration and DRY code.
What happens without it?Conflicts and copy-paste.
When to useAny team project.
When NOT to useOver-abstracted modules.
Real-world analogyState = the builder's notebook; modules = prefab building parts.

Diagram & Internal Working

envs/dev  --\
envs/prod --+--> module "vpc" (modules/vpc)  ==> same code, different inputs
Remote state: S3 bucket (versioned, encrypted) + DynamoDB lock table (or use_lockfile)

How it works internally (diagram explained)

With an S3 backend, init configures the backend; each operation takes a DynamoDB lock item, reads state, works, writes new state and releases the lock. A module call creates a child scope: inputs become variables, outputs return values, and resources are addressed as module.name.resource.

Practical Examples

Backend

terraform {
  backend "s3" {
    bucket         = "acme-tfstate"
    key            = "prod/network.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"
    encrypt        = true
  }
}

Module structure and usage

modules/vpc/{main.tf,variables.tf,outputs.tf}

module "vpc" {
  source = "../../modules/vpc"
  name   = "prod"
  cidr   = "10.0.0.0/16"
  azs    = ["ap-south-1a", "ap-south-1b"]
}
# use output: module.vpc.private_subnet_ids

for_each and dynamic

variable "buckets" { default = ["logs", "backups"] }
resource "aws_s3_bucket" "b" {
  for_each = toset(var.buckets)
  bucket   = "acme-${each.key}"
}
resource "aws_security_group" "sg" {
  dynamic "ingress" {
    for_each = [80, 443]
    content { from_port = ingress.value, to_port = ingress.value, protocol = "tcp", cidr_blocks = ["0.0.0.0/0"] }
  }
}

Hands-On Lab

Lab Goal

Configure remote state.

Prerequisites

  • AWS credentials

Step 1

aws s3 mb s3://my-tf-state-<unique> && aws s3api put-bucket-versioning --bucket my-tf-state-<unique> --versioning-configuration Status=Enabled

Versioned state bucket.

Step 2

aws dynamodb create-table --table-name tf-locks --attribute-definitions AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST

Lock table.

Step 3

Add the backend block and run terraform init -migrate-state

Moves local state to S3.

Real-World Problems & Fixes (Troubleshooting)

Problem: Error acquiring state lock
Cause: Another run or crashed run holds lock
Fix: Verify nobody is running; terraform force-unlock <ID>.
Problem: Changing list order recreates resources
Cause: Using count with lists
Fix: Use for_each with stable keys.

Best Practices

Security

  • Encrypt and restrict state bucket; no secrets in outputs.

Common Mistakes

DevOps mistakes

  • Local state for teams.

Interview Questions

Q1. count vs for_each?

count index-based (fragile on removal); for_each key-based (stable).

Q2. Why state locking?

Prevents concurrent applies corrupting state.

Q3. Workspaces vs directories per env?

Workspaces share config; directories give clearer isolation and separate backends (preferred for prod).

Q4. How to import existing resource?

terraform import or import block, then write matching config.

Q5. Module versioning?

Pin version/git tag to avoid surprise changes.

Q6. State bucket deleted accidentally.

Restore from bucket versioning/backup; protect with deletion policy and MFA delete; re-import if lost.

Why: DR for state.

Real-world example: Enable versioning up front.
