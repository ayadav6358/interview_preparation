Configuration Management: Ansible: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: After servers exist, each one still needs packages, users, config files, patches and app deployments. Doing that by hand or with one-off scripts makes servers different from each other (configuration drift). Ansible describes the desired configuration in simple YAML and applies it to many servers over SSH, safely repeatable (idempotent), with no agent to install.

PROBLEM: many servers must be configured, patched and deployed consistently
      |
      v
TRADITIONAL APPROACH: SSH into each server and run commands or copy scripts
      |
      v
PAIN: drift, mistakes, no record, slow at scale
      |
      v
TECHNOLOGY: Ansible (inventory + playbooks + modules over SSH)
      |
      v
SOLUTION: YAML playbooks describe desired state; modules make only needed changes
      |
      v
REAL-WORLD BENEFIT: identical servers, fast patching, documented, repeatable operations

Idempotent means running the playbook again changes nothing if the server is already correct. Ansible is agentless: the control node connects with SSH (Linux) or WinRM (Windows), copies small modules, runs them and removes them.

2. End-to-End Flow

Terraform creates servers
   v
Inventory (static file or dynamic AWS/Azure plugin)
   v
ansible-playbook site.yml   (control node)
   v
SSH to each managed node (parallel, forks=5 default)
   v
Module runs (apt, copy, template, service...) -> reports ok / changed / failed
   v
Handlers run if something changed (e.g. restart nginx)
   v
Recap: ok=12 changed=3 failed=0
   v
Re-run later: changed=0 (idempotent)  -> use in CI / AWX for scheduling

The control node reads the inventory to know which hosts exist and their groups. For each play, it connects to the hosts in parallel over SSH, executes tasks in order using modules (small programs that check current state and change only if needed), and reports ok, changed, failed or unreachable. Handlers are special tasks triggered only when notified by a change, for example restart nginx after its config file changed. The recap summarises results. Because modules are idempotent, the same playbook can be run repeatedly to enforce state.

Ansible vs Terraform: Terraform creates infrastructure; Ansible configures inside servers. Ansible vs Puppet/Chef: Ansible is agentless and uses push over SSH with simple YAML; Puppet/Chef use agents and pull models (strong for continuous enforcement at large scale). Ansible vs shell scripts: modules are idempotent, structured, cross-platform and give clear change reporting.

5. Troubleshooting Playbook

Problem: UNREACHABLE! Permission denied (publickey)
Possible cause: Wrong user/key, key not on host, SSH config
How to check: ansible host -m ping -vvv, ssh -i key user@host
Fix: Set ansible_user, ansible_ssh_private_key_file; fix authorized_keys.
Prevention: Standardise SSH access and use SSM/bastion configuration.
Problem: Task always shows changed
Possible cause: Using command/shell without creates/changed_when
How to check: Run twice and compare recap
Fix: Use proper module or add creates:/changed_when.
Prevention: Lint with ansible-lint.
Problem: sudo: a password is required
Possible cause: become needs a password or NOPASSWD sudo
How to check: Run with -K or check sudoers
Fix: Configure passwordless sudo for the automation user or pass --ask-become-pass.
Prevention: Dedicated automation user with scoped sudo.
Problem: Variable is undefined
Possible cause: Wrong precedence/scope, typo, missing var file
How to check: ansible-playbook -vv, debug: var=...
Fix: Define in group_vars/host_vars or defaults; use default() filter.
Prevention: Use defaults/main.yml in roles.
Problem: Playbook slow
Possible cause: Fact gathering, serial tasks, many forks
How to check: ANSIBLE_STDOUT_CALLBACK=profile_tasks
Fix: gather_facts: false, enable pipelining, increase forks, use async.
Prevention: Cache facts; ControlPersist SSH.
Problem: Python not found on target
Possible cause: Minimal images without Python
How to check: Error mentions interpreter
Fix: Install python or set ansible_python_interpreter; use raw module to bootstrap.
Prevention: Bake Python into images.

6. Production Best Practices

Development

  • Use roles; keep tasks small; name every task; use --check --diff before applying; lint with ansible-lint and yamllint.

Production

  • Separate inventories per environment; group_vars; run from CI/AWX; serial for rolling changes; tags for partial runs.

Security

  • Encrypt secrets with Ansible Vault or pull from a secret manager; least-privilege become; SSH keys not passwords; pin collection versions; no_log: true for secret tasks.

Performance

  • Pipelining, SSH multiplexing, gather_facts off when not needed, more forks, strategy: free where safe.

Reliability

  • Idempotent tasks, handlers for restarts, serial and max_fail_percentage, health checks between batches.

Cost Optimization

  • Automate patching and start/stop schedules; bake images with Packer to avoid repeated configuration.

Monitoring & Logging

  • Store run logs in AWX/CI; alert on failed runs; callbacks to Slack.

Backup & Disaster Recovery

  • Playbooks in Git rebuild servers; back up vault passwords securely.

7. Common Mistakes

Beginner mistakes

  • Using shell for everything.
  • Indentation errors in YAML.

Developer mistakes

  • Hard-coded values instead of variables.
  • Huge single playbooks instead of roles.

DevOps mistakes

  • Not running in check mode first.
  • Unpinned roles/collections.

Production mistakes

  • Running on all hosts at once (no serial).
  • Restarting services on every run instead of via handlers.

Security mistakes

  • Plain-text secrets in vars.
  • Committing the vault password.

8. Version / Environment Notes

  • Use fully qualified collection names (FQCN) such as ansible.builtin.apt; modules moved into collections since Ansible 2.10.
  • ansible (package with collections) vs ansible-core (minimal): check which you install; core versions require specific Python versions.
  • Windows targets use WinRM/ansible.windows collection; network devices use dedicated connection plugins.
  • Package manager modules differ per OS: apt (Debian), dnf/yum (RHEL family), or the generic package module.

11. How I Explain This to a Client

30-second explanation

Ansible is our tool for configuring servers automatically and consistently. We describe the desired setup once, and it applies it to any number of servers, so patching and deployments are fast, repeatable and auditable.

2-minute explanation

When new servers are created, they still need software, security settings and application configuration. Doing this manually leads to differences between servers and mistakes. With Ansible we write the desired configuration as simple, versioned playbooks and run them over SSH without installing agents. Running the playbook again only fixes what is out of line, so it also detects and corrects drift. We use it for hardening, patching and application deployment, keep secrets encrypted, and run it from a pipeline or a central platform that records who ran what. You get consistency, speed and audit trails.

5-minute deep explanation

Let me cover the model, the practice and the controls. Model: an inventory lists hosts and groups (static or from the cloud API), playbooks map groups to roles, roles contain idempotent tasks, templates and handlers. Practice: Terraform creates the infrastructure, Ansible then applies the OS baseline (users, SSH hardening, packages), deploys applications and performs rolling patching with batches and health checks; for immutable setups we use Ansible inside Packer to build golden images. Controls: secrets in Vault or an external secret manager, least-privilege escalation, check mode and diff before changes, code review in Git and execution through AWX or CI with role-based access and logging. Result: reduced drift, faster patch cycles and evidence for compliance audits.

13. Mini Project: Deploy hardened Nginx to a fleet with roles, template, handler and vault

Control node --SSH--> web1, web2 (group [web])
 role nginx: install > template nginx.conf > ensure started > handler reload
 group_vars/web.yml (vars) + vault.yml (secrets)
 ansible-playbook -i inventory site.yml --check --diff  then apply, serial: 1

Step 1: Inventory

# inventory.ini
[web]
web1 ansible_host=10.0.10.11
web2 ansible_host=10.0.10.12

[web:vars]
ansible_user=ubuntu
ansible_ssh_private_key_file=~/.ssh/deploy.pem

Hosts and shared connection variables. Test with ansible web -i inventory.ini -m ping, expecting pong.

Step 2: Role tasks (roles/nginx/tasks/main.yml)

- name: Install nginx
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: true
  become: true

- name: Render site config
  ansible.builtin.template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
    mode: "0644"
  become: true
  notify: Reload nginx

- name: Ensure nginx is running and enabled
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true
  become: true

apt with state: present installs only if missing (idempotent). template renders Jinja2 with variables; if the file changes it notifys the handler. become: true uses sudo. Each task has a name for readable output.

Step 3: Handler and template

# roles/nginx/handlers/main.yml
- name: Reload nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
  become: true

# roles/nginx/templates/site.conf.j2
server {
    listen {{ nginx_port | default(80) }};
    server_name {{ server_name }};
    location / { proxy_pass http://127.0.0.1:{{ app_port }}; }
}

The handler runs once at the end of the play, only if notified. Template variables come from group_vars/web.yml; default(80) provides a safe fallback.

Step 4: Playbook and safe run

# site.yml
- hosts: web
  serial: 1
  roles: [nginx]

# commands
ansible-playbook -i inventory.ini site.yml --check --diff
ansible-playbook -i inventory.ini site.yml
ansible-playbook -i inventory.ini site.yml   # second run: changed=0
ansible-vault encrypt group_vars/web/vault.yml

serial: 1 updates one server at a time, keeping the service available. --check --diff previews changes. The second run demonstrates idempotency (changed=0). Vault encrypts secrets before they are committed.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Ansible?

An agentless automation tool for configuration management, deployment and orchestration using YAML playbooks.

Why: Foundation.

Real-world example: Configure 50 web servers with one command.

Q2. What does agentless mean?

No software is installed on managed nodes; Ansible uses SSH/WinRM and Python already present.

Why: Key differentiator.

Real-world example: Compared to Puppet agents.

Q3. What is an inventory?

A list of managed hosts organised in groups with variables.

Why: Core concept.

Real-world example: [web], [db] groups.

Q4. What is a playbook?

YAML file with plays that map hosts to tasks/roles.

Why: Core concept.

Real-world example: site.yml.

Q5. What is a module?

A unit of work such as apt, copy, service that does one thing idempotently.

Why: Building block.

Real-world example: ansible.builtin.copy.

Q6. What is idempotency?

Applying the same operation multiple times gives the same result without extra changes.

Why: Most asked.

Real-world example: Second run shows changed=0.

Q7. What is ansible all -m ping?

Ad-hoc command testing connectivity and Python on all hosts.

Why: First check.

Real-world example: Returns pong.

Q8. What is a task and a handler?

A task is one action; a handler runs only when notified by a changed task.

Why: Flow control.

Real-world example: Restart service after config change.

Q9. What are facts?

System information gathered automatically (OS, IPs, memory) available as variables.

Why: Conditionals.

Real-world example: ansible_os_family.

Q10. How do you run a playbook?

ansible-playbook -i inventory playbook.yml.

Why: Basics.

Real-world example: Add --check first.

Intermediate (13)

Q11. What is a role?

A standard directory structure (tasks, handlers, templates, defaults, vars, files, meta) to package reusable automation.

Why: Reuse.

Real-world example: Role nginx used by many playbooks.

Q12. Variable precedence in Ansible?

Many levels; from lowest: role defaults < inventory/group_vars < host_vars < play vars < task vars < extra vars (-e) highest.

Why: Debugging vars.

Real-world example: -e overrides everything.

Q13. Jinja2 templates?

Text templates with variables/filters/loops rendered on the control node.

Why: Config generation.

Real-world example: nginx.conf.j2.

Q14. What is Ansible Vault?

Encrypts sensitive variables/files with a password; decrypted at runtime.

Why: Secrets.

Real-world example: ansible-vault encrypt vars.yml.

Q15. Loops and conditionals?

loop: (or with_items) and when: conditions.

Why: Logic.

Real-world example: Install a list of packages.

Q16. What does become do?

Privilege escalation (sudo) for tasks or plays.

Why: Permissions.

Real-world example: become: true.

Q17. command vs shell vs raw?

command runs without shell; shell uses shell features; raw sends a raw SSH command without Python; all are non-idempotent by default.

Why: Module choice.

Real-world example: Bootstrapping Python with raw.

Q18. How do you make command tasks idempotent?

Use creates, removes, changed_when and when guards, or prefer real modules.

Why: Best practice.

Real-world example: creates: /opt/app/.installed.

Q19. What are tags?

Labels to run a subset of tasks.

Why: Efficiency.

Real-world example: --tags config.

Q20. Dynamic inventory?

Inventory generated from cloud APIs/plugins so hosts stay current.

Why: Cloud usage.

Real-world example: amazon.aws.aws_ec2 plugin.

Q21. What is --check and --diff?

Check mode simulates without changes; diff shows file differences.

Why: Safe changes.

Real-world example: Review before prod.

Q22. How to run ordered rolling updates?

serial, max_fail_percentage, health checks between batches, delegate_to for load balancer drain.

Why: Zero-downtime.

Real-world example: Update 1 of N servers at a time.

Q23. What is Ansible Galaxy?

Repository/CLI for sharing roles and collections.

Why: Reuse.

Real-world example: ansible-galaxy install.

Advanced (13)

Q24. Explain how Ansible executes a module.

Control node generates module code with args, copies it to a temp directory on the target via SSH (or pipelines it), executes with Python, returns JSON, then cleans up.

Why: Internals.

Real-world example: Pipelining reduces SSH ops.

Q25. How would you speed up large playbook runs?

Pipelining, ControlPersist, increase forks, disable/cached facts, async/poll, strategy free, mitogen where suitable.

Why: Performance.

Real-world example: Patching 500 hosts.

Q26. Design a patching workflow.

Dynamic inventory groups, drain from LB, snapshot/backup, patch in batches (serial), reboot if required, health check, re-add, stop on failure, report.

Why: Ops design.

Real-world example: Rolling kernel patching.

Q27. Testing roles?

Molecule with containers/VMs, ansible-lint, yamllint, idempotence test, CI.

Why: Quality.

Real-world example: Molecule scenario for nginx role.

Q28. Collections vs roles?

Collections package modules, plugins and roles with versioning and namespaces; roles are simpler content units.

Why: Modern structure.

Real-world example: amazon.aws, community.general.

Q29. How do you manage secrets at scale?

Vault with vault-ids, or lookup plugins for HashiCorp Vault/AWS Secrets Manager, no_log, AWX credentials.

Why: Security.

Real-world example: Fetch DB password at runtime.

Q30. What is AWX/Ansible Automation Platform?

Web UI/API with RBAC, credentials, scheduling, inventories, job templates and audit for Ansible.

Why: Enterprise use.

Real-world example: Self-service patching jobs.

Q31. Ansible with Packer and Terraform: how?

Terraform provisions, Packer + Ansible builds golden images, Ansible handles remaining runtime config or is replaced by immutable images.

Why: Toolchain design.

Real-world example: AMI pipeline.

Q32. Handling Windows hosts?

WinRM/SSH connection, ansible.windows collection, win_* modules.

Why: Heterogeneous fleets.

Real-world example: IIS deployment.

Q33. What is delegate_to and run_once?

delegate_to runs a task on another host (e.g. LB API); run_once runs on one host only.

Why: Orchestration.

Real-world example: DB migration once.

Q34. Callback plugins and logging?

Customise output/notifications (profile_tasks, JSON, Slack).

Why: Observability.

Real-world example: Send failures to Slack.

Q35. Error handling in playbooks?

ignore_errors, block/rescue/always, failed_when, any_errors_fatal.

Why: Robustness.

Real-world example: Rollback in rescue.

Q36. Pull mode with ansible-pull?

Nodes fetch playbooks from Git and run locally on a schedule; useful for edge/autoscaled hosts.

Why: Alternative model.

Real-world example: Cron + ansible-pull.

Scenario-Based (12)

Q37. Patch 200 servers without downtime.

Group by role, serial batches (10%), drain from LB, patch, reboot, health check, re-enable; abort on failures.

Why: Ops scenario.

Real-world example: AWS ALB deregistration via delegate_to.

Q38. Config drifted on some servers.

Run playbook in check mode to see drift, apply to correct, add scheduled run and restrict manual access.

Why: Drift control.

Real-world example: Nightly AWX job.

Q39. New joiner needs SSH access on all servers.

Role managing users/authorized_keys via ansible.posix.authorized_key from a central vars file; offboarding removes.

Why: Access management.

Real-world example: Remove leavers quickly.

Q40. Secrets are in plain text in vars.

Encrypt with Vault, rotate exposed secrets, add pre-commit scan, move to secret manager.

Why: Security fix.

Real-world example: Vault ids per environment.

Q41. Different config per environment.

Separate inventories/group_vars for dev/stage/prod and the same roles.

Why: Structure.

Real-world example: inventories/prod/group_vars.

Q42. A play must change only one host of a group.

--limit host, or delegate_to/when: inventory_hostname == ....

Why: Targeting.

Real-world example: Test change on canary host.

Q43. Deploy an app then run DB migration once.

Deploy on all hosts, run migration task with run_once: true and delegate_to one host.

Why: Orchestration.

Real-world example: Rails migrate.

Q44. Terraform created hosts with dynamic IPs; how does Ansible find them?

Dynamic inventory via aws_ec2 plugin filtering by tags, or Terraform outputs to inventory.

Why: Toolchain integration.

Real-world example: tag:Role=web.

Q45. Run playbooks from CI securely.

Runner with vault password from secret store, SSH via bastion/SSM with short-lived keys, check mode on PR, apply after merge.

Why: CI usage.

Real-world example: GitHub Actions with OIDC.

Q46. Harden Linux servers to CIS level.

Use a maintained hardening role, review, test in staging with Molecule, apply with check mode first, exceptions documented.

Why: Compliance.

Real-world example: dev-sec hardening collection.

Q47. Slow playbook due to fact gathering.

Disable facts where unnecessary, use fact caching, gather subsets.

Why: Performance.

Real-world example: gather_subset: min.

Q48. Need to roll back a config change.

Templates in Git: revert and re-run; use backup: true for copy/template; snapshots for risky changes.

Why: Recovery.

Real-world example: Keep last config file.

Troubleshooting-Based (10)

Q49. UNREACHABLE for some hosts.

SSH, DNS/IP, security groups, host key checking, wrong user, jump host config.

Why: Connectivity.

Real-world example: Bastion not configured.

Q50. Failed to connect to the host via ssh: Host key verification failed.

New/changed host key; add to known_hosts (or set host_key_checking deliberately for ephemeral labs).

Why: SSH.

Real-world example: Rebuilt server.

Q51. YAML syntax error / mapping values not allowed.

Indentation or missing quotes (especially with : or {{ }}); validate with ansible-playbook --syntax-check and yamllint.

Why: Syntax.

Real-world example: Quote strings starting with {{.

Q52. Template renders wrong/empty values.

Undefined variable/precedence; -vvv, debug, check ansible_facts.

Why: Vars.

Real-world example: Wrong group name.

Q53. Handler did not run.

No task reported changed, or the play failed before handlers ran (use meta: flush_handlers), or name mismatch.

Why: Handlers.

Real-world example: Name typo in notify.

Q54. Missing sudo password.

Set passwordless sudo or -K.

Why: Privilege.

Real-world example: Automation user lacks NOPASSWD.

Q55. Module not found.

Collection not installed or wrong FQCN; ansible-galaxy collection install.

Why: Collections.

Real-world example: community.docker.

Q56. Playbook hangs.

Waiting on prompts/background process holding SSH; use async, -vvv, timeouts, avoid interactive commands.

Why: Debugging.

Real-world example: Service start attached to session.

Q57. Changes work in check mode but fail on real run.

Some modules cannot fully simulate (command/shell); test in staging.

Why: Limitations.

Real-world example: shell tasks skip in check.

Q58. Vault decryption failed.

Wrong password/vault-id or file encrypted with another id.

Why: Vault.

Real-world example: Use --vault-id prod@prompt.
