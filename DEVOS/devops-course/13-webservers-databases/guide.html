Web Servers, Databases & Messaging: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: An application alone is not a production system. It needs a fast front door (web server / reverse proxy), durable storage (database), a way to avoid hitting the database for every request (cache) and a way to handle slow or bursty work without blocking users (message queues). DevOps engineers deploy, tune, secure and troubleshoot all of these.

PROBLEM: one app process cannot serve traffic, store data safely and stay fast under load
      |
      v
TRADITIONAL APPROACH: app talks directly to users and to a single database for everything
      |
      v
PAIN: slow pages, database overload, lost data, tight coupling, downtime on spikes
      |
      v
TECHNOLOGY: Nginx (proxy), PostgreSQL/MySQL (data), Redis (cache), RabbitMQ/SQS/Kafka (queues)
      |
      v
SOLUTION: specialised components each doing one job well, connected by clear interfaces
      |
      v
REAL-WORLD BENEFIT: scalability, resilience, faster responses, decoupled services

Typical request: Nginx terminates TLS and routes; the app reads from Redis first (cache hit = fast), otherwise queries the database and stores the result in Redis; slow tasks (emails, reports) are put on a queue and processed by workers.

2. End-to-End Flow

Client
  v
Nginx (TLS, gzip, rate limit, static files, reverse proxy)  :443
  v
App servers (stateless, 2+ instances)  :3000
  |-- read --> Redis (cache/session)  :6379  -- miss --> PostgreSQL primary :5432 (+ read replicas)
  |-- publish job --> Queue (RabbitMQ/SQS/Kafka)  --> Workers --> DB / email / third-party
  v
Response to client
Ops: backups (pg_dump/WAL), replication, monitoring (exporters), logs, failover

Nginx is the entry point: it terminates TLS, serves static files, compresses and forwards dynamic requests to app servers (reverse proxy and load balancer). The app checks Redis for the data; a cache miss falls through to the database, and the result is stored in Redis with a TTL for next time. The database keeps the authoritative data with a primary (writes) and optional replicas (reads, failover). Work that does not need to finish before responding is published as a message to a queue; workers consume and process it asynchronously, enabling retries and smoothing spikes. Each component is monitored and backed up.

Redis vs Memcached: Redis supports data structures, persistence and replication; Memcached is simple multi-threaded caching. RabbitMQ vs Kafka: RabbitMQ is a smart broker for task queues and routing; Kafka is a durable distributed log for high-throughput event streaming and replay. SQS vs RabbitMQ: SQS is fully managed and simple; RabbitMQ gives richer routing and protocols but needs operation. Postgres vs MySQL: both solid; Postgres has advanced features (JSONB, extensions), MySQL is widely used and simple to operate.

5. Troubleshooting Playbook

Problem: 502 Bad Gateway from Nginx
Possible cause: Upstream app down/slow, wrong upstream address/port, socket permissions
How to check: tail /var/log/nginx/error.log, curl upstream directly, ss -tulpn
Fix: Fix/restart app, correct proxy_pass, tune timeouts.
Prevention: Health checks, nginx -t in CI.
Problem: Database too many connections
Possible cause: Connection leaks, no pooling, low max_connections
How to check: SELECT count(*) FROM pg_stat_activity;, app pool config
Fix: Use pgBouncer, fix leaks, adjust pool sizes.
Prevention: Pooling by default; alert at 80% of max.
Problem: Slow queries
Possible cause: Missing index, full table scan, bad plan, lock contention
How to check: EXPLAIN (ANALYZE, BUFFERS), pg_stat_statements, slow query log
Fix: Add index, rewrite query, vacuum/analyze, cache result.
Prevention: Query review and performance tests.
Problem: Replica lag / stale reads
Possible cause: Heavy writes, network, long-running queries on replica
How to check: pg_stat_replication, SHOW REPLICA STATUS
Fix: Reduce load, tune replication, route critical reads to primary.
Prevention: Monitor lag with alert.
Problem: Redis memory full / evictions
Possible cause: No TTL, big keys, wrong maxmemory-policy
How to check: INFO memory, redis-cli --bigkeys, INFO stats evicted_keys
Fix: Set TTLs, choose allkeys-lru, increase memory, fix big keys.
Prevention: Key naming/TTL standards; memory alerts.
Problem: Queue backlog grows
Possible cause: Consumers slow/down, poison message, burst
How to check: Queue depth metrics, consumer logs, DLQ
Fix: Scale consumers, fix failing job, move bad message to DLQ.
Prevention: Autoscale on queue depth; DLQ + alerts.

6. Production Best Practices

Development

  • Use connection pooling and timeouts; parameterised queries; idempotent consumers; migrations via Flyway/Liquibase.

Production

  • Nginx: worker_processes auto, keep-alive, gzip, rate limiting; DB: primary + replica, automated failover; Redis: persistence/replication chosen per use; queue: DLQ and retries.

Security

  • TLS everywhere; DB not public; least-privilege DB users; secrets in vault; Redis requirepass/ACLs and no public exposure; Nginx hides version, security headers.

Performance

  • Index wisely; cache hot reads; connection pooling; tune shared_buffers, work_mem; use read replicas; HTTP caching/CDN.

Reliability

  • Backups tested with restore drills; replication + failover; queue durability; graceful shutdown of workers.

Cost Optimization

  • Right-size DB instances; cache to reduce DB load; archive old data; managed services trade-off.

Monitoring & Logging

  • Exporters for each component; slow query log; Nginx access/error logs; queue depth and consumer lag.

Backup & Disaster Recovery

  • PostgreSQL: base backups + WAL archiving (PITR); MySQL: binlog + xtrabackup; cross-region copies; defined RPO/RTO.

7. Common Mistakes

Beginner mistakes

  • Exposing DB/Redis ports publicly.
  • Using default passwords.

Developer mistakes

  • N+1 queries.
  • No timeouts.
  • Caching without invalidation strategy.

DevOps mistakes

  • Replication treated as backup.
  • No restore tests.
  • Editing Nginx config without nginx -t.

Production mistakes

  • No connection pooling.
  • Unbounded queues without DLQ.
  • Running Redis without maxmemory policy.

Security mistakes

  • Wide-open 0.0.0.0/0 database security groups.
  • Superuser DB account used by the app.

8. Version / Environment Notes

  • Nginx open source vs Nginx Plus features differ; Ingress-NGINX (Kubernetes) uses different annotations than plain Nginx config.
  • PostgreSQL major versions require pg_upgrade/dump-restore; recovery.conf was removed in v12 (use standby.signal); check docs for your version.
  • MySQL 8 changed default auth plugin (caching_sha2_password) which can break old clients.
  • Redis licence changed in 2024 (Valkey is a community fork): verify which distribution/version you deploy.
  • Kafka no longer requires ZooKeeper with KRaft mode in recent versions.

11. How I Explain This to a Client

30-second explanation

Behind every application there are a few key building blocks: a web server that receives traffic, a database that stores data, a cache that makes it fast, and queues that handle background work. We deploy and operate these so the application stays fast, safe and available.

2-minute explanation

Our web layer uses Nginx to handle secure connections and distribute requests across application servers. Business data lives in a managed relational database with replicas for availability and automated backups so we can restore to any point in time. Frequently used data is cached in Redis, which reduces database load and response times. Long-running or bursty tasks, such as sending emails or generating reports, are placed on a message queue and processed in the background so users are never kept waiting. Each component is monitored, secured and sized for your traffic, and we regularly test restores and failover.

5-minute deep explanation

I will walk through the request path and the operations behind it. Edge: Nginx terminates TLS, serves static content, applies rate limits and proxies to stateless application instances. Data: PostgreSQL holds the source of truth, with a primary and replicas, connection pooling, indexing and query monitoring; backups use base snapshots plus write-ahead-log archiving for point-in-time recovery, and we rehearse restores. Speed: Redis caches hot reads and sessions using a cache-aside pattern with TTLs and an eviction policy. Decoupling: queues like SQS or RabbitMQ absorb spikes and enable retries with dead-letter queues, while Kafka is used where event streaming and replay are needed. Operations: metrics exporters, dashboards and alerts for latency, connections, replication lag and queue depth, plus security hardening and least-privilege access. This yields predictable performance, resilience to failures and clear recovery targets.

13. Mini Project: Nginx + Node API + PostgreSQL + Redis + worker queue (Compose)

Browser --> Nginx :80 --> API :3000 --> Redis (cache) / PostgreSQL (data)
                                 |-- enqueue job --> Redis list/BullMQ or RabbitMQ --> Worker --> PostgreSQL
Volumes: pgdata ; healthchecks ; backup job (pg_dump) ; Prometheus exporters optional

Step 1: compose.yml

services:
  nginx:
    image: nginx:1.27
    ports: ["80:80"]
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"]
    depends_on: [api]
  api:
    build: ./api
    environment: { DB_URL: "postgres://app:${DB_PASSWORD}@db:5432/app", REDIS_URL: "redis://cache:6379" }
    depends_on: { db: { condition: service_healthy } }
  worker:
    build: ./api
    command: ["node","worker.js"]
    environment: { DB_URL: "postgres://app:${DB_PASSWORD}@db:5432/app", REDIS_URL: "redis://cache:6379" }
    depends_on: { db: { condition: service_healthy } }
  db:
    image: postgres:16
    environment: { POSTGRES_USER: app, POSTGRES_PASSWORD: "${DB_PASSWORD}", POSTGRES_DB: app }
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: { test: ["CMD-SHELL","pg_isready -U app"], interval: 5s, retries: 10 }
  cache:
    image: redis:7-alpine
    command: ["redis-server","--maxmemory","128mb","--maxmemory-policy","allkeys-lru"]
volumes: { pgdata: {} }

The worker reuses the API image with a different command. Redis has a memory cap and LRU eviction so it behaves as a cache. Only Nginx publishes a port; DB and Redis stay internal.

Step 2: nginx.conf

upstream api { server api:3000; keepalive 16; }
server {
  listen 80;
  gzip on;
  location /api/ { proxy_pass http://api; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_read_timeout 30s; }
  location / { root /usr/share/nginx/html; try_files $uri /index.html; }
}

upstream names the backend pool with keep-alive connections; proxy_pass forwards API calls; static files are served directly and single-page-app routes fall back to index.html. Validate with nginx -t before reload.

Step 3: Cache-aside in code (Node, illustrative)

async function getUser(id) {
  const key = `user:${id}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);
  const { rows } = await pg.query('SELECT id, name FROM users WHERE id = $1', [id]);
  await redis.set(key, JSON.stringify(rows[0]), { EX: 60 });
  return rows[0];
}

Check cache first; on miss query with a parameterised query (prevents SQL injection) and store with a 60 second TTL. Invalidate or update the key when the user changes.

Step 4: Backup and restore drill

docker compose exec -T db pg_dump -U app -Fc app > backup.dump
docker compose exec -T db psql -U app -c "CREATE DATABASE restore_test;"
docker compose exec -T db pg_restore -U app -d restore_test < backup.dump
docker compose exec db psql -U app -d restore_test -c "\dt"

A backup only counts once a restore is proven. This dumps in custom format, restores into a new database and lists tables. Production should use base backups + WAL archiving for point-in-time recovery.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is a web server?

Software that serves HTTP requests: static files and proxying to applications.

Why: Basics.

Real-world example: Nginx serving a React build.

Q2. What is a reverse proxy?

A server in front of backends that forwards client requests, adding TLS, caching and load balancing.

Why: Architecture.

Real-world example: Nginx in front of Node.

Q3. What is a database?

Organised storage for persistent data with query capability.

Why: Basics.

Real-world example: PostgreSQL.

Q4. SQL vs NoSQL?

SQL is relational with a fixed schema and ACID transactions; NoSQL offers flexible models and horizontal scale.

Why: Selection.

Real-world example: Orders in SQL, sessions in Redis.

Q5. What is caching?

Storing frequently used data in fast storage to reduce latency and backend load.

Why: Performance.

Real-world example: Redis.

Q6. What is a message queue?

A buffer that decouples producers and consumers so work can be processed asynchronously.

Why: Decoupling.

Real-world example: Email sending.

Q7. What is an index?

A data structure that speeds up lookups on columns at the cost of extra writes/storage.

Why: DB performance.

Real-world example: Index on email.

Q8. What is a primary key?

A unique, non-null identifier for each row.

Why: Relational basics.

Real-world example: id column.

Q9. What is a backup?

A copy of data used to restore after loss or corruption.

Why: Reliability.

Real-world example: Nightly pg_dump.

Q10. What is Redis?

An in-memory data store used for cache, sessions, queues and counters.

Why: Common tool.

Real-world example: Session storage.

Intermediate (15)

Q11. How does Nginx handle many connections?

Event-driven, asynchronous worker processes using epoll; each worker handles thousands of connections without a thread per connection.

Why: Nginx internals.

Real-world example: worker_processes auto.

Q12. Nginx location matching order?

Exact =, then longest prefix with ^~, then regex in order, then longest prefix.

Why: Config correctness.

Real-world example: location /api/.

Q13. What is ACID?

Atomicity, Consistency, Isolation, Durability guarantees of transactions.

Why: DB fundamentals.

Real-world example: Money transfer.

Q14. Explain indexes and when they hurt.

B-tree indexes speed reads; each write must update indexes; too many indexes slow writes and use space; low-selectivity columns help little.

Why: Tuning.

Real-world example: Index on boolean is rarely useful.

Q15. How do you find a slow query?

Slow query log/pg_stat_statements, then EXPLAIN (ANALYZE) to see plan; fix with index/rewrite.

Why: Troubleshooting.

Real-world example: Seq scan on 10M rows.

Q16. Replication types?

Asynchronous (fast, possible lag/loss), synchronous (no loss, higher latency); physical (WAL) vs logical.

Why: HA.

Real-world example: Postgres streaming replication.

Q17. Why connection pooling?

Database connections are expensive; pooling reuses a limited number, preventing exhaustion.

Why: Scaling.

Real-world example: pgBouncer in transaction mode.

Q18. Redis persistence options?

RDB snapshots and AOF append-only log; combine for durability trade-offs; cache-only may disable both.

Why: Redis ops.

Real-world example: AOF everysec.

Q19. Redis eviction policies?

noeviction, allkeys-lru, volatile-lru, allkeys-lfu, etc. when maxmemory reached.

Why: Memory management.

Real-world example: allkeys-lru for cache.

Q20. Cache invalidation strategies?

TTL, explicit delete/update on write, versioned keys, write-through.

Why: Hard problem.

Real-world example: Delete key after user update.

Q21. RabbitMQ concepts?

Producers publish to exchanges, routed by bindings to queues; consumers ack messages; DLQ for failures.

Why: Messaging.

Real-world example: Direct/topic/fanout exchanges.

Q22. SQS Standard vs FIFO?

Standard: at-least-once, best-effort ordering, high throughput; FIFO: exactly-once processing and ordering with lower throughput.

Why: AWS messaging.

Real-world example: Order processing in FIFO.

Q23. Kafka basics?

Topics split into partitions on brokers; producers append; consumer groups read with offsets; retention allows replay.

Why: Streaming.

Real-world example: Clickstream events.

Q24. How to secure Nginx?

TLS 1.2+, hide version, security headers, rate limiting, restrict methods, keep updated, run as non-root worker, WAF/ModSecurity if needed.

Why: Hardening.

Real-world example: server_tokens off.

Q25. HTTP caching headers?

Cache-Control, ETag, Expires; Nginx proxy_cache for upstream responses.

Why: Performance.

Real-world example: Cache static for 1 year with hashed filenames.

Advanced (14)

Q26. Explain PostgreSQL MVCC and VACUUM.

MVCC keeps row versions so readers do not block writers; VACUUM reclaims dead tuples and prevents bloat/transaction wraparound; autovacuum needs tuning.

Why: Postgres internals.

Real-world example: Bloated table slowing queries.

Q27. Design point-in-time recovery for PostgreSQL.

Periodic base backups + continuous WAL archiving to object storage; restore base then replay WAL to a target time; test regularly (pgBackRest/WAL-G).

Why: DR design.

Real-world example: Recover to 10 min before a bad deploy.

Q28. How does automatic failover work?

A manager (Patroni, RDS, orchestrator) detects primary failure via health checks/consensus, promotes a replica, and repoints clients via VIP/DNS/proxy; fencing prevents split-brain.

Why: HA.

Real-world example: Patroni + etcd.

Q29. CAP theorem and practical meaning?

During a network partition a system must choose consistency or availability; many systems tune per operation.

Why: Distributed systems.

Real-world example: DynamoDB eventual vs strong reads.

Q30. Transaction isolation anomalies?

Dirty read, non-repeatable read, phantom read, write skew; isolation levels trade correctness for performance.

Why: DB depth.

Real-world example: Serializable for financial invariants.

Q31. Scaling databases?

Vertical scale, read replicas, caching, partitioning/sharding, CQRS, choose appropriate storage per workload.

Why: Scale design.

Real-world example: Shard by tenant ID.

Q32. Cache stampede and mitigations?

Many requests rebuild an expired hot key simultaneously; use request coalescing/locks, jittered TTLs, stale-while-revalidate, pre-warming.

Why: Reliability.

Real-world example: Homepage key expiry.

Q33. Kafka delivery semantics?

At-most-once, at-least-once, exactly-once (idempotent producers + transactions); consumers commit offsets after processing for at-least-once.

Why: Messaging guarantees.

Real-world example: Idempotent consumers.

Q34. Kafka partitions and ordering?

Ordering is guaranteed only within a partition; key-based partitioning keeps related events ordered; consumer parallelism is limited by partition count.

Why: Design detail.

Real-world example: Key by order ID.

Q35. How does Redis Cluster/Sentinel differ?

Sentinel gives HA/failover for a primary+replicas; Cluster shards data across nodes with hash slots.

Why: Redis scaling.

Real-world example: Sentinel for small setups.

Q36. Nginx performance tuning?

worker_processes auto, worker_connections, keepalive to upstream, gzip/brotli, sendfile, open_file_cache, buffers, HTTP/2, caching, rate limits.

Why: Tuning.

Real-world example: Tune on evidence with load tests.

Q37. Zero-downtime schema changes?

Expand/contract migrations, online index creation (CREATE INDEX CONCURRENTLY), avoid long locks, backfill in batches.

Why: Ops.

Real-world example: Add nullable column then backfill.

Q38. Outbox pattern?

Write business change and an outbox event in one DB transaction; a relay publishes to the broker, ensuring consistency between DB and messages.

Why: Reliable messaging.

Real-world example: Order created event.

Q39. Managed database vs self-hosted?

Managed (RDS/Cloud SQL) reduces operations (patching, backups, failover) at higher cost/less control; self-host for special needs and expertise.

Why: Decision-making.

Real-world example: Default to managed.

Scenario-Based (13)

Q40. Website is slow only during peak.

Check Nginx/app saturation, DB connections/slow queries, cache hit ratio, queue backlog; add caching, indexes, pooling, scale out.

Why: Systematic diagnosis.

Real-world example: Cache hit ratio dropped to 30%.

Q41. Database disk is filling up.

Find large tables/WAL/logs/temp files, vacuum/archive, expand storage, retention, alert early.

Why: Ops.

Real-world example: Unarchived WAL growing.

Q42. Accidental DELETE without WHERE in production.

Stop writes if needed, restore from PITR to just before the mistake into a new instance, extract data and repair, add safeguards (permissions, transactions, reviews).

Why: Recovery.

Real-world example: Point-in-time restore.

Q43. Need to migrate to a bigger DB with minimal downtime.

Set up replica/logical replication or DMS, sync, switch over quickly, validate, keep rollback.

Why: Migration.

Real-world example: Cutover in 30 seconds.

Q44. Emails must be sent reliably after checkout.

Publish a message to a queue in the same transaction pattern (outbox), workers with retries, idempotency and DLQ.

Why: Async design.

Real-world example: Order confirmation email.

Q45. Redis outage takes down the site.

App must degrade gracefully: timeouts, fall back to DB with rate limiting, circuit breaker, Redis HA (Sentinel/managed), avoid using Redis as sole store.

Why: Resilience.

Real-world example: Sessions in signed cookies/DB fallback.

Q46. Design rate limiting.

Nginx limit_req at the edge plus Redis-based token bucket per API key in the app for fine-grained limits.

Why: Protection.

Real-world example: 100 req/min per key.

Q47. Queue has millions of messages backlog.

Scale consumers, check poison messages/DLQ, increase batch/prefetch, fix downstream slowness, temporarily shed low-priority work.

Why: Recovery.

Real-world example: Autoscale on queue depth.

Q48. Choose between RabbitMQ and Kafka.

Task queues with routing and acknowledgements: RabbitMQ/SQS; high-volume event streams, replay and multiple independent consumers: Kafka.

Why: Tool selection.

Real-world example: Payments events on Kafka.

Q49. Zero-downtime Nginx config change.

nginx -t then nginx -s reload (graceful), canary in a staging box, version config in Git.

Why: Change safety.

Real-world example: New upstream added.

Q50. Database credentials rotation.

Use secret manager with rotation, app fetches secrets and reconnects, dual-user rotation strategy to avoid downtime.

Why: Security ops.

Real-world example: RDS rotation Lambda.

Q51. Read-heavy workload overloads primary.

Add read replicas and route reads, add caching, optimise queries, materialised views.

Why: Scaling reads.

Real-world example: Reporting on replica.

Q52. How do you keep two services consistent without distributed transactions?

Event-driven sagas/outbox, idempotent handlers, compensating actions, eventual consistency.

Why: Microservices data.

Real-world example: Order/payment saga.

Troubleshooting-Based (10)

Q53. Nginx upstream timed out (110).

Backend too slow/unresponsive; check app/DB latency, increase proxy_read_timeout only after fixing root cause.

Why: Proxy debugging.

Real-world example: Slow query in API.

Q54. Nginx connect() failed (111: Connection refused).

Upstream not listening or wrong host/port; verify with curl/ss.

Why: Proxy debugging.

Real-world example: App crashed.

Q55. PostgreSQL FATAL: remaining connection slots are reserved.

max_connections reached; use pooling, kill idle sessions, raise limits carefully.

Why: DB capacity.

Real-world example: Leaked connections.

Q56. Deadlocks in database.

Concurrent transactions lock resources in different order; keep transactions short, consistent lock order, retry on deadlock.

Why: Concurrency.

Real-world example: Two updates crossing.

Q57. Replica is far behind.

Long-running queries, IO, network, heavy write burst; check lag, tune, move heavy reads.

Why: Replication.

Real-world example: Analytics query on replica.

Q58. Redis OOM command not allowed.

maxmemory reached with noeviction; set eviction policy/TTL or raise memory.

Why: Redis ops.

Real-world example: Queue in Redis exhausted memory.

Q59. Messages processed twice.

At-least-once delivery, ack timeouts or retries; make consumers idempotent (dedupe key).

Why: Messaging semantics.

Real-world example: Duplicate charge prevented by idempotency key.

Q60. Kafka consumer lag increasing.

Consumers slower than producers; scale consumers (up to partitions), optimise processing, check rebalances/GC.

Why: Streaming ops.

Real-world example: Lag alert.

Q61. TLS error on Nginx after renewal.

Certificate/chain file wrong, key mismatch, not reloaded; check nginx -t and openssl s_client.

Why: TLS.

Real-world example: Used cert.pem instead of fullchain.

Q62. Backup restores but app fails.

Version/extension/role mismatch or missing WAL/config; verify restore procedure and app compatibility in drills.

Why: DR quality.

Real-world example: Missing extension.
