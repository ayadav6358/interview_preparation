Branching, Merge, Rebase & Conflicts

Intermediate Git & Version Control

Concept (What & Why)

Branch se parallel kaam hota hai. Merge history preserve karta hai, rebase linear history banata hai. Conflict resolve karna seekho.

Definition Deep-Dive

QuestionAnswer
Simple definitionBranches let you work separately, merging combines the work.
Technical definitionA branch is a ref to a commit; merge creates a commit with two parents (or fast-forwards); rebase replays commits onto a new base.
Why does it exist?Parallel work without breaking main.
What happens without it?Everyone editing one line of history.
When to useEvery feature/fix.
When NOT to useRebase on shared branches.
Real-world analogyParallel roads that later merge.

Diagram & Internal Working

merge:                          rebase:
main:  A--B--C-----M            main:  A--B--C
        \       /                        \
feat:    D--E--                 feat:      D'--E'   (replayed on top of C)

Rule: never rebase shared/public branches.

How it works internally (diagram explained)

Merge finds the common ancestor of both tips and performs a three-way merge; conflicts occur where both sides changed the same lines. Rebase temporarily removes your commits, moves the base to the target tip and re-applies each, which can conflict per commit.

# git already installed

Practical Examples

Feature branch workflow

git switch -c feature/login
# ...work...
git add -A && git commit -m "feat(login): add form"
git fetch origin && git rebase origin/main
git push -u origin feature/login   # open PR
git merge --no-ff feature/login    # merge with merge commit

Resolve conflict

git merge main
# CONFLICT in app.js -> edit markers <<<<<<< ======= >>>>>>>
git add app.js && git commit
# or abort: git merge --abort

Useful helpers

git stash push -m wip; git stash pop
git cherry-pick <sha>
git bisect start; git bisect bad; git bisect good v1.2   # find breaking commit
git reflog   # recover 'lost' commits

Hands-On Lab

Lab Goal

Create and resolve a conflict.

Prerequisites

  • Git

Step 1

git init c && cd c && echo one > f && git add f && git commit -m base && git switch -c a && echo A > f && git commit -am a && git switch main && echo B > f && git commit -am b

Two branches change the same line.

Step 2

git merge a

CONFLICT reported.

Step 3

Edit f to the desired text, then: git add f && git commit

Conflict resolved and merged.

Real-World Problems & Fixes (Troubleshooting)

Problem: Lost commits after wrong reset --hard
Cause: Thought they were gone
Fix: git reflog -> git reset --hard <sha>; reflog keeps ~90 days.
Problem: Force-push overwrote teammate's work
Cause: Used --force on shared branch
Fix: Use --force-with-lease, protect main with branch protection.

Best Practices

Development

  • Rebase your feature branch on main before PR; merge into main via PR.

Common Mistakes

Developer mistakes

  • Rebasing shared branches.
  • Resolving conflicts without running tests.

Hinglish Explanation

Conflict ka matlab dono ne same line badli. File edit karo, git add, phir commit. Shared branch par rebase nahi.

Interview Questions

Q1. Merge vs rebase?

Merge keeps history with merge commit; rebase rewrites commits onto new base for linear history.

Q2. reset vs revert?

reset moves branch pointer (rewrites history); revert creates a new commit undoing changes (safe for shared branches).

Q3. What is cherry-pick?

Apply a specific commit from another branch.

Q4. How to recover a deleted branch?

Find sha via git reflog and git branch name sha.

Q5. What is fast-forward merge?

Branch pointer simply moves ahead when no divergence.

Q6. You rebased and now the push is rejected.

History was rewritten; on your own feature branch use git push --force-with-lease (never on shared branches).

Why: Safe force push.

Real-world example: --force-with-lease protects against overwriting others' work.
