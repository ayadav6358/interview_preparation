Git & Version Control: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Many people change the same code, configs and infrastructure files. Without version control you get "final_v2_new_FINAL.zip", overwritten work, no history and no way to undo a bad change. Git records every change as a commit, lets people work in parallel on branches, and merges the work safely.

PROBLEM: many people editing the same files, changes get lost or break things

REAL-WORLD BENEFIT: full history, safe collaboration, code review, CI triggers, GitOps

In DevOps, Git holds more than app code: Dockerfiles, Kubernetes YAML, Terraform, pipelines and dashboards. It is the single source of truth and the trigger for CI/CD and GitOps.

2. End-to-End Flow

Working directory (edit files)
   | git add
   v
Staging area (index)
   | git commit
   v
Local repository (history)
   | git push
   v
Remote (GitHub/GitLab)
   | Pull Request + review + CI checks
   v
Merge to main
   | webhook
   v
CI/CD pipeline > deploy

You edit files in the working directory, choose what to include with git add (staging area), and git commit to store a snapshot with a message in your local repository. git push uploads commits to the remote. Teammates review through a pull request while CI runs checks. After approval the change is merged into main, which triggers the pipeline. git pull (fetch + merge/rebase) brings others' changes back to you.

5. Troubleshooting Playbook

Problem: Merge conflict
Possible cause: Same lines changed in both branches
How to check: git status, git diff --name-only --diff-filter=U
Fix: Edit conflict markers, git add, git commit (or git rebase --continue).
Prevention: Small PRs, frequent rebases, clear ownership.
Problem: Pushed a secret
Possible cause: Credential committed
How to check: gitleaks detect, git log -S 'secret'
Fix: Rotate the secret FIRST, then remove from history (git filter-repo/BFG) and force-push if policy allows.
Prevention: Pre-commit scanning, secrets manager.
Problem: rejected (non-fast-forward) on push
Possible cause: Remote has commits you do not have
How to check: git fetch && git log HEAD..origin/main
Fix: git pull --rebase then push. Never force-push shared branches.
Prevention: Pull frequently.
Problem: Committed to wrong branch
Possible cause: Forgot to switch
How to check: git branch, git log
Fix: git switch correct && git cherry-pick <sha>, then reset the wrong branch (if unpublished).
Prevention: Check git status before committing.
Problem: Lost commits after reset
Possible cause: Hard reset/rebase
How to check: git reflog
Fix: git checkout -b rescue <sha> from reflog.
Prevention: Avoid --hard without checking.
Problem: Large file blocks push
Possible cause: Binary over size limit
How to check: git count-objects -vH, git rev-list --objects --all
Fix: Remove from history (filter-repo), use Git LFS.
Prevention: .gitignore and LFS rules.

6. Production Best Practices

Development

  • Small focused commits with clear messages (Conventional Commits).
  • Pull/rebase often; branch per task.

Production

  • Protect main: required reviews and passing checks; tag releases; signed tags/commits.

Security

  • Never commit secrets; pre-commit + CI secret scan; least-privilege repo access; SSH keys/PATs with expiry; signed commits.

Performance

  • Shallow clone in CI (--depth 1), sparse checkout for monorepos, Git LFS for binaries.

Reliability

  • Mirror/backup critical repos; protect against force-push and branch deletion.

Monitoring & Logging

  • Audit logs for repo access; alerts for secret exposure.

7. Common Mistakes

Beginner mistakes

  • git add . staging junk/secrets.
  • Committing directly to main.
  • Vague messages like 'fix'.

Developer mistakes

  • Force-pushing shared branches.
  • Huge PRs that are hard to review.

DevOps mistakes

  • No branch protection.
  • State files (e.g. terraform.tfstate) or .env in Git.

Production mistakes

  • Deploying from an unreviewed branch.
  • No tags so releases cannot be identified.

Security mistakes

  • Secrets in history (deleting the file is not enough).
  • Long-lived personal access tokens with wide scope.

8. Version / Environment Notes

  • Modern Git: prefer git switch and git restore over overloaded git checkout.
  • Default branch name is now often main (older repos use master): git config --global init.defaultBranch main.
  • GitHub no longer accepts account passwords for Git operations: use SSH keys or personal access tokens/OIDC.
  • git filter-branch is discouraged; use git filter-repo.

11. How I Explain This to a Client

30-second explanation

Git is our version control system: it records every change to code and infrastructure files, lets many people work in parallel, and makes review and rollback easy. It is also what triggers our automated builds and deployments.

2-minute explanation

Every change to the application and to our infrastructure is stored in Git with who changed what and why. Developers work on separate branches and submit pull requests. Before anything is merged, automated tests and security scans run and a colleague reviews it. If a release has a problem we can identify the exact change and revert it. Because deployments are triggered from Git, the repository becomes the audit trail for compliance and the single source of truth for what is running.

5-minute deep explanation

Three ideas. History and collaboration: Git stores snapshots called commits, so we can compare versions, find who changed what and restore anything; branches let people work independently and pull requests provide review. Governance: we protect the main branch with required reviews and checks, use signed commits and tags for releases, and scan for secrets before code is accepted. Automation: merges trigger CI pipelines, and with GitOps the repository defines the desired state of the environments, so a rollback is a Git revert. We choose a branching model that fits the release cadence, typically trunk-based development with short-lived branches for continuous delivery. The result is a traceable, secure and repeatable delivery process.

13. Mini Project: Team workflow with PR, protection and secret scanning

feature branch --> push --> Pull Request
   CI: tests + gitleaks + lint  --> review (CODEOWNERS)
   --> squash merge to main --> tag v1.0.0 --> pipeline deploys

Step 1: Create repo and first commit

git init demo && cd demo
git config user.name "Your Name" && git config user.email "you@example.com"
printf 'node_modules\n.env\n' > .gitignore
echo '# demo' > README.md
git add . && git commit -m "chore: initial commit"
git branch -M main

.gitignore prevents committing dependencies and secrets. The first commit forms the root of the history.

Step 2: Work on a feature branch

git switch -c feature/login
echo 'login page' > login.txt
git add login.txt && git commit -m "feat: add login page"
git push -u origin feature/login

Branch per feature keeps main stable. -u links the local branch to the remote for future pushes.

Step 3: Pre-commit secret scan

cat > .pre-commit-config.yaml <<'EOF'
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.4
    hooks: [{ id: gitleaks }]
EOF
pip install pre-commit && pre-commit install

Blocks commits containing secrets. Pin the rev to a current release: check the project's tags.

Step 4: Merge, tag and recover

git switch main && git pull
git merge --no-ff feature/login
git tag -a v1.0.0 -m "first release" && git push origin main --tags
git reflog | head   # recover anything lost

Merge with a merge commit, tag the release for the pipeline, and know that reflog can restore lost commits.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Git?

A distributed version control system that tracks changes and supports collaboration.

Why: Foundation.

Real-world example: Track code and Terraform files.

Q2. Git vs GitHub?

Git is the tool; GitHub is a hosting service for Git repositories.

Why: Common confusion.

Real-world example: GitLab and Bitbucket are alternatives.

Q3. What is a commit?

A snapshot of tracked files with author, message and parent pointer(s), identified by a SHA.

Why: Core concept.

Real-world example: git commit -m 'msg'.

Q4. What is the staging area?

A place where you assemble the next commit.

Why: Understand add.

Real-world example: git add -p to stage parts.

Q5. What is a branch?

A movable pointer to a commit for parallel work.

Why: Workflow.

Real-world example: git switch -c feature/x.

Q6. What is .gitignore?

File listing paths Git should not track.

Why: Avoid junk/secrets.

Real-world example: node_modules, .env.

Q7. clone vs fork?

Clone copies a repo locally; fork copies a repo to your account on the host for contributing.

Why: Open source workflow.

Real-world example: Fork then PR.

Q8. What is git pull?

Fetch remote changes and integrate them (merge or rebase).

Why: Sync.

Real-world example: git pull --rebase.

Q9. How do you see history?

git log --oneline --graph --decorate.

Why: Basics.

Real-world example: Find who changed a line: git blame.

Q10. What is a tag?

A named pointer to a commit, used for releases.

Why: Versioning.

Real-world example: v1.2.0.

Intermediate (14)

Q11. merge vs rebase?

Merge joins histories with a merge commit; rebase replays commits on a new base for linear history; do not rebase published commits.

Why: Very common.

Real-world example: Rebase local feature branch on main.

Q12. How to resolve a merge conflict?

Open conflicted files, choose the correct content, remove markers, git add, then commit/continue.

Why: Practical skill.

Real-world example: Use a merge tool.

Q13. reset vs revert vs restore?

restore discards working changes; reset moves the branch pointer (soft/mixed/hard); revert creates an inverse commit.

Why: Undo strategies.

Real-world example: Revert on main.

Q14. What is git stash?

Temporarily saves uncommitted changes.

Why: Context switching.

Real-world example: git stash pop.

Q15. cherry-pick?

Applies a specific commit onto the current branch.

Why: Hotfix backport.

Real-world example: Copy a fix to release branch.

Q16. What is a pull request?

A request to merge a branch with discussion, review and CI checks.

Why: Team process.

Real-world example: Two approvals required.

Q17. Explain fast-forward vs no-ff merge.

Fast-forward moves the pointer without a merge commit; --no-ff always creates one to preserve branch context.

Why: History design.

Real-world example: Squash for clean history.

Q18. Squash merge?

Combines all PR commits into one on main.

Why: Clean history.

Real-world example: One commit per feature.

Q19. What is HEAD?

Pointer to the current commit/branch checked out; detached HEAD means it points to a commit, not a branch.

Why: Internals.

Real-world example: git checkout <sha>.

Q20. How to undo the last commit but keep changes?

git reset --soft HEAD~1.

Why: Common task.

Real-world example: Fix commit message.

Q21. What are Git hooks?

Scripts triggered by Git events (pre-commit, commit-msg, pre-push).

Why: Quality gates.

Real-world example: Lint before commit.

Q22. Branching strategies?

Trunk-based, GitHub Flow, GitFlow.

Why: Process.

Real-world example: Trunk-based for CI/CD.

Q23. What is CODEOWNERS?

File mapping paths to required reviewers.

Why: Governance.

Real-world example: /infra/ @platform-team.

Q24. How to sync a fork?

Add upstream, fetch, merge/rebase, push.

Why: OSS.

Real-world example: git remote add upstream.

Advanced (14)

Q25. How does Git store data?

Content-addressed objects (blob, tree, commit, tag) in .git/objects, referenced by SHA; branches are refs.

Why: Internals.

Real-world example: git cat-file -p HEAD.

Q26. What is git reflog?

Local log of where HEAD/branches pointed; lets you recover commits after resets.

Why: Recovery.

Real-world example: Undo a bad rebase.

Q27. Interactive rebase use cases?

Squash, reorder, edit, drop commits before sharing.

Why: History hygiene.

Real-world example: git rebase -i HEAD~5.

Q28. How do you remove a secret from history?

Rotate secret, rewrite history with git filter-repo/BFG, force-push, ask collaborators to re-clone, add scanning.

Why: Security response.

Real-world example: AWS key leaked.

Q29. git bisect?

Binary search through commits to find the one that introduced a bug.

Why: Debugging.

Real-world example: git bisect start; good; bad.

Q30. Submodules vs subtrees vs monorepo?

Submodule pins another repo at a commit; subtree merges another repo's history; monorepo keeps everything in one repo with tooling.

Why: Repo strategy.

Real-world example: Shared library across services.

Q31. How to enforce quality on a team?

Branch protection, required CI/reviews, CODEOWNERS, signed commits, commit lint, pre-commit and server-side hooks.

Why: Governance.

Real-world example: GitHub rulesets.

Q32. Explain shallow clone and its uses.

--depth N fetches limited history for speed; used in CI but some tools need full history (versioning, blame).

Why: CI optimisation.

Real-world example: GitHub Actions fetch-depth.

Q33. What is Git LFS?

Stores large binaries outside the repo, keeping pointers in Git.

Why: Large files.

Real-world example: Design assets, datasets.

Q34. Signed commits and tags?

GPG/SSH signatures verify authorship.

Why: Supply chain.

Real-world example: Required on protected branches.

Q35. GitOps and Git?

Git as source of truth for desired state; controllers reconcile clusters to it.

Why: Modern delivery.

Real-world example: ArgoCD watching a repo.

Q36. Trunk-based development needs what?

Small changes, strong automated tests, feature flags, fast reviews.

Why: Prerequisites.

Real-world example: Deploy daily.

Q37. Explain three-way merge.

Git uses common ancestor and both tips to combine changes; conflicts appear when both changed same region.

Why: Merge internals.

Real-world example: Merge base via git merge-base.

Q38. How do you handle a monorepo CI?

Path filters/affected detection, caching, sparse checkout, CODEOWNERS per path.

Why: Scale.

Real-world example: Nx/Bazel.

Scenario-Based (14)

Q39. You accidentally pushed a password.

Revoke/rotate immediately, remove from history, force-push per policy, scan repo, add pre-commit hook.

Why: Incident response.

Real-world example: See troubleshooting.

Q40. Production is broken after a merge.

Revert the merge/PR commit (git revert -m 1 <merge>), redeploy, then fix forward via new PR.

Why: Rollback.

Real-world example: Revert instead of reset.

Q41. Two developers changed the same file.

Rebase/merge, resolve conflicts communicating with the author, run tests, push.

Why: Collaboration.

Real-world example: Ask the author intent.

Q42. Need a hotfix on an old release.

Branch from release tag, fix, cherry-pick to main, tag patch version.

Why: Release management.

Real-world example: v1.2.1 from v1.2.0.

Q43. Repo is huge and slow.

Find large objects, move to LFS, shallow/partial clone, gc, split repo.

Why: Performance.

Real-world example: Removed 2GB of binaries.

Q44. Enforce that only tested code reaches main.

Protected branch with required status checks and reviews, no direct pushes.

Why: Governance.

Real-world example: Required CI job.

Q45. Choose branching strategy for weekly releases and hotfixes.

GitHub Flow or trunk-based with release branches/tags; GitFlow only if multiple supported versions.

Why: Design judgement.

Real-world example: Mobile app with staged releases.

Q46. Someone force-pushed and lost commits.

Recover from other clones, reflog on server, CI caches; then disable force-push via branch protection.

Why: Recovery and prevention.

Real-world example: git reflog from a teammate.

Q47. Team unsure which commit is deployed.

Tag releases, embed git SHA in the image/build metadata, expose /version endpoint.

Why: Traceability.

Real-world example: Image tag equals SHA.

Q48. Manage environment configs in Git.

Separate config repo or folders per env, no secrets, use overlays and GitOps.

Why: IaC hygiene.

Real-world example: values-prod.yaml.

Q49. Contractors need limited repo access.

Team-based least privilege, forks or scoped roles, time-boxed access, audit.

Why: Access control.

Real-world example: Read-only role.

Q50. Code review is a bottleneck.

Smaller PRs, CODEOWNERS, automation for style, review SLAs, pairing.

Why: Process.

Real-world example: Limit PR size to 400 lines.

Q51. Need to find who introduced a bug in a line.

git blame, git log -L, git bisect.

Why: Investigation.

Real-world example: Blame plus PR link.

Q52. Migrate from SVN/another VCS.

Use git-svn or import tooling, keep history, train team, freeze old repo.

Why: Migration.

Real-world example: Move with authors mapping.

Troubleshooting-Based (10)

Q53. fatal: not a git repository.

Not inside a repo or .git missing; git init or cd to the right dir.

Why: Basics.

Real-world example: Wrong directory.

Q54. Permission denied (publickey) on push.

SSH key not added to the account/agent; check ssh -T git@github.com, ssh-add -l.

Why: Auth.

Real-world example: Wrong key loaded.

Q55. detached HEAD state.

You checked out a commit; create a branch to keep work: git switch -c new.

Why: State confusion.

Real-world example: After checking out a tag.

Q56. refusing to merge unrelated histories.

Repos have no common ancestor; use --allow-unrelated-histories deliberately.

Why: Repo joins.

Real-world example: Merging a new repo into an existing one.

Q57. Pre-commit hook blocks commit.

Read the message, fix the issue; skip only with justification (--no-verify) and never for secret scans.

Why: Hooks.

Real-world example: Lint error.

Q58. File tracked despite .gitignore.

Already tracked: git rm --cached file, commit.

Why: Ignore rules.

Real-world example: .env accidentally committed.

Q59. Line ending changes everywhere.

Set .gitattributes/core.autocrlf; normalise once.

Why: Cross-platform teams.

Real-world example: Windows vs Linux.

Q60. Cannot delete a branch.

You are on it or it is unmerged: switch away; -D to force after checking.

Why: Branch cleanup.

Real-world example: git branch -d feature.

Q61. Push rejected due to file size.

Remove large file from history/use LFS.

Why: Size limits.

Real-world example: 100MB GitHub limit.

Q62. CI cannot clone private repo.

Missing deploy key/token, expired PAT, org SSO not authorised.

Why: CI access.

Real-world example: Use GitHub App/OIDC.
