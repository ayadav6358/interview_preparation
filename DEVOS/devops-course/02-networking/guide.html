Networking: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Applications, users, databases and cloud services are on different machines. Networking is the set of rules (protocols) and devices that lets them find each other and exchange data reliably and securely. Most production incidents ("site is down", "timeout", "cannot connect to DB") are network problems until proven otherwise.

PROBLEM: computers must find and talk to each other across the world
      |
      v
TRADITIONAL APPROACH: point-to-point cables and fixed addresses
      |
      v
PAIN: not scalable, no naming, no security, no routing
      |
      v
TECHNOLOGY: TCP/IP stack, IP addressing, DNS, HTTP/TLS, routers, load balancers, firewalls
      |
      v
SOLUTION: layered protocols; each layer solves one problem
      |
      v
REAL-WORLD BENEFIT: any client can reach any service by name, securely, with load spread and failures hidden

The OSI model (7 layers) is a teaching map; real networks use TCP/IP (Link, Internet, Transport, Application). Each layer only talks to the same layer on the other side and to the layer below.

2. End-to-End Flow

User types https://shop.example.com
   |
   v
DNS lookup (browser cache > OS > resolver > root > TLD > authoritative)  => IP 203.0.113.10
   |
   v
TCP 3-way handshake (SYN, SYN-ACK, ACK) to port 443
   |
   v
TLS handshake (certificate check, keys)
   |
   v
HTTP request (GET /) --> CDN / WAF --> Load Balancer --> Reverse proxy (Nginx) --> App --> DB
   |
   v
HTTP response (200 + HTML) travels back
   |
   v
Browser renders; connection kept alive or closed

First the browser needs an IP, so DNS resolves the name. Then the client opens a TCP connection (three-way handshake) to the server's port 443 so data is delivered reliably and in order. TLS then authenticates the server with a certificate and creates encryption keys. Only now is the HTTP request sent. Traffic passes through edge components (CDN, WAF), the load balancer which chooses a healthy backend, a reverse proxy and the application, which may call a database. The response returns along the same path. Failures can occur at any hop, so troubleshooting means testing each step in order.

5. Troubleshooting Playbook

Problem: Website not reachable
Possible cause: DNS wrong, port blocked, service down, TLS problem, LB unhealthy
How to check: dig site, nc -zv host 443, curl -vI https://site, traceroute/mtr
Fix: Fix at the failing layer: DNS record, SG/firewall, service, certificate.
Prevention: Synthetic monitoring, health checks.
Problem: Connection timeout vs connection refused
Possible cause: Timeout = packets dropped (firewall/route); refused = host reachable but nothing listening
How to check: nc -zv host port, ss -tulpn on server, SG rules
Fix: Timeout: open firewall/route. Refused: start service or bind correct interface.
Prevention: Document ports; test after deploy.
Problem: DNS resolves wrong/old IP
Possible cause: TTL caching, wrong record, split-horizon
How to check: dig +short host, dig @8.8.8.8, dig +trace
Fix: Fix record; wait TTL; flush cache.
Prevention: Lower TTL before migrations.
Problem: TLS/certificate error
Possible cause: Expired, wrong hostname, missing intermediate, clock skew
How to check: openssl s_client -connect host:443 -servername host, curl -v
Fix: Renew/replace cert, install full chain.
Prevention: Automate renewals (cert-manager/ACM) and alert on expiry.
Problem: 502 / 504 from proxy or LB
Possible cause: Backend down or slow, wrong upstream port, timeout too low
How to check: Proxy error log, backend health, curl backend directly
Fix: Fix backend; adjust timeouts; correct upstream.
Prevention: Health checks and readiness gates.
Problem: Intermittent packet loss / latency
Possible cause: Congestion, bad link, MTU, DNS delay
How to check: mtr host, ping -c 50, ip -s link
Fix: Fix network path; MTU; provider ticket.
Prevention: Network monitoring.

6. Production Best Practices

Development

  • Use service names not IPs; test connectivity with curl/nc from the same network as the app.

Production

  • Multi-AZ, health checks, timeouts and retries with backoff; DNS TTL planning.

Security

  • TLS everywhere (1.2+), least-privilege security groups, private subnets for databases, WAF, no open 0.0.0.0/0 admin ports.

Performance

  • Keep-alive, HTTP/2, CDN caching, compression, connection pooling.

Reliability

  • Redundant load balancers, multiple DNS records/health-based routing, graceful failover.

Cost Optimization

  • Reduce NAT gateway/inter-AZ transfer, use VPC endpoints and CDN.

Monitoring & Logging

  • Flow logs, LB access logs, latency and error-rate dashboards.

7. Common Mistakes

Beginner mistakes

  • Confusing port with protocol.
  • Testing from your laptop and assuming the server can reach it too.

Developer mistakes

  • Hard-coded IPs.
  • No timeouts on outbound calls.

DevOps mistakes

  • Overlapping CIDR blocks between VPCs.
  • Forgetting return routes or security group rules.

Production mistakes

  • Certificate expiry.
  • Long DNS TTL during migration.

Security mistakes

  • SSH/DB open to the world.
  • Terminating TLS without re-encrypting where required.

8. Version / Environment Notes

  • ifconfig, netstat, nslookup are legacy: prefer ip, ss, dig.
  • TLS 1.0/1.1 are deprecated; use TLS 1.2 or 1.3. HTTP/3 uses QUIC over UDP.
  • IPv6 support varies across cloud services: verify per service.
  • Cloud specifics: AWS security groups are stateful, Azure NSGs and GCP firewall rules differ in defaults and priorities.

11. How I Explain This to a Client

30-second explanation

Networking is how our users, applications and databases find and talk to each other securely. We design it so traffic is encrypted, spread across healthy servers and protected by firewalls, which keeps the service fast and available.

2-minute explanation

When a customer opens your website, DNS turns the name into an address, a secure connection is created with TLS, and a load balancer sends the request to a healthy server. Our design places public components such as load balancers in public subnets and applications and databases in private subnets, controlled by firewalls that only allow required ports. We add a CDN for speed, health checks for automatic failover, and monitoring for latency and errors. This gives you availability across multiple data centres, protection from attacks and clear visibility when something breaks.

5-minute deep explanation

Let me walk through a request. Name resolution: DNS records in Route 53 map the domain to a load balancer, with health-based routing for failover. Secure transport: TLS certificates, issued and renewed automatically, encrypt traffic; we enforce TLS 1.2+. Distribution: an application load balancer routes by host and path to targets in multiple availability zones and removes unhealthy ones. Segmentation: a VPC with public subnets (load balancer, NAT) and private subnets (apps, databases); security groups allow only necessary flows such as LB to app on 8080 and app to database on 5432. Performance and protection: CDN caching, WAF rules, rate limiting, HTTP/2 and keep-alive. Operations: flow logs, load balancer logs and dashboards, and a troubleshooting runbook: DNS, port, TLS, HTTP. The business benefit is availability, security and predictable performance.

13. Mini Project: Build and debug a small network path: DNS > Nginx > app

client (curl) --> DNS name app.local (/etc/hosts)
   --> Nginx :80 (reverse proxy, TLS optional)
   --> app :3000 (private)
Tools: dig/curl/ss/tcpdump to prove each hop

Step 1: Run app and proxy

docker network create demo
docker run -d --name app --network demo hashicorp/http-echo -text=hello -listen=:3000
cat > default.conf <<'EOF'
server { listen 80; location / { proxy_pass http://app:3000; proxy_set_header Host $host; } }
EOF
docker run -d --name proxy --network demo -p 8080:80 -v $PWD/default.conf:/etc/nginx/conf.d/default.conf:ro nginx:1.27

App is only reachable inside the demo network; Nginx is the single public entry on host port 8080. proxy_pass uses the container name (Docker DNS).

Step 2: Test each hop

curl -i http://localhost:8080
docker exec proxy sh -c 'getent hosts app'
docker exec proxy curl -s http://app:3000

First proves the full path, second proves DNS inside the network, third proves proxy to app connectivity.

Step 3: Break it and read the symptoms

docker stop app
curl -i http://localhost:8080   # 502 Bad Gateway
docker logs proxy | tail -3

Proxy is up but upstream is down: 502 with a connect error in the log. Restart app to recover.

Step 4: Capture traffic

sudo tcpdump -i any -nn port 8080 -c 10   # Linux host
curl -s http://localhost:8080 >/dev/null

Shows the TCP handshake and HTTP request/response packets. On Docker Desktop, run tcpdump inside a container instead.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is an IP address?

A numerical address identifying a device on a network (IPv4 32-bit, IPv6 128-bit).

Why: Foundation.

Real-world example: 192.168.1.10.

Q2. What is a port?

A 16-bit number identifying a service on a host.

Why: Services share one IP.

Real-world example: HTTPS 443, SSH 22.

Q3. What is DNS?

System that translates domain names to IP addresses.

Why: Every request starts here.

Real-world example: google.com to an IP.

Q4. TCP vs UDP?

TCP reliable and ordered; UDP fast connectionless.

Why: Protocol choice.

Real-world example: HTTP uses TCP; DNS queries use UDP.

Q5. What is HTTP status 200/404/500?

200 OK, 404 not found, 500 server error.

Why: Debugging basics.

Real-world example: 502/503/504 are gateway/availability errors.

Q6. What is a firewall?

Filters traffic by rules (IP, port, protocol).

Why: Security.

Real-world example: Allow 443, block others.

Q7. What is NAT?

Translates private IPs to a public IP so many hosts share one address.

Why: Internet access from private networks.

Real-world example: NAT gateway for private subnets.

Q8. What is a subnet?

A segment of an IP network defined by a mask/CIDR.

Why: Network design.

Real-world example: 10.0.1.0/24.

Q9. What is a load balancer?

Distributes traffic across multiple servers and removes unhealthy ones.

Why: Availability.

Real-world example: ALB in front of EC2.

Q10. What is HTTPS?

HTTP over TLS: encrypted and authenticated.

Why: Security basics.

Real-world example: Padlock in browser.

Intermediate (14)

Q11. What happens when you type a URL in the browser?

DNS resolution, TCP handshake, TLS handshake, HTTP request through CDN/LB/proxy to app, response rendered.

Why: Classic full-stack question.

Real-world example: See e2e diagram.

Q12. Explain the TCP three-way handshake.

SYN, SYN-ACK, ACK establish sequence numbers before data flows.

Why: Transport fundamentals.

Real-world example: Visible in tcpdump.

Q13. Explain CIDR: how many hosts in /24, /16, /28?

/24=256 addresses (254 usable), /16=65,536, /28=16 (cloud providers reserve some addresses, for example AWS reserves 5 per subnet).

Why: Subnetting skill.

Real-world example: AWS /28 gives 11 usable.

Q14. Public vs private subnet in AWS?

Public has a route to an Internet Gateway; private routes outbound via NAT and is not directly reachable.

Why: VPC design.

Real-world example: DB in private subnet.

Q15. Explain DNS record types.

A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail), TXT (verification/SPF), NS (name servers), SOA, SRV.

Why: DNS depth.

Real-world example: CNAME can't be at zone apex; use alias.

Q16. What is TTL in DNS?

How long resolvers may cache a record.

Why: Migrations.

Real-world example: Lower TTL before cutover.

Q17. Reverse proxy vs load balancer?

Reverse proxy fronts servers (TLS, caching, routing); load balancer distributes across many; often one component does both (Nginx, ALB).

Why: Terminology.

Real-world example: Nginx doing both.

Q18. Load balancing algorithms?

Round robin, least connections, IP hash, weighted.

Why: Traffic distribution.

Real-world example: Sticky sessions via cookie/IP hash.

Q19. What is TLS termination?

The proxy/LB decrypts TLS and forwards plain or re-encrypted traffic to backends.

Why: Cert management.

Real-world example: ALB with ACM cert.

Q20. 502 vs 503 vs 504?

502 bad response from upstream; 503 service unavailable/no healthy backend; 504 upstream timeout.

Why: Incident triage.

Real-world example: 504 means slow backend.

Q21. What is a CDN?

Global cache network serving content near users.

Why: Performance.

Real-world example: CloudFront.

Q22. What is the difference between stateful and stateless firewall?

Stateful tracks connections so return traffic is automatically allowed; stateless needs explicit rules both ways.

Why: SG vs NACL.

Real-world example: NACL needs ephemeral ports rule.

Q23. How to test a port is open?

nc -zv host port, curl, telnet, Test-NetConnection on Windows.

Why: Debugging.

Real-world example: nc -zv db 5432.

Q24. What is MTU and why does it matter?

Maximum packet size; mismatch causes fragmentation or hangs, especially with VPNs/tunnels.

Why: Subtle issues.

Real-world example: Large uploads hang over VPN.

Advanced (16)

Q25. Explain the OSI vs TCP/IP model.

OSI has 7 layers, TCP/IP 4; mapping: application layers 5-7 to Application, Transport, Internet (Network), Link (Data link + Physical).

Why: Framework knowledge.

Real-world example: Firewalls L3/L4; WAF L7.

Q26. Explain the TLS handshake.

ClientHello (versions, ciphers, SNI), ServerHello + certificate, key exchange (ECDHE), verification of chain, session keys derived, encrypted traffic (TLS 1.3 needs 1 round trip).

Why: Security depth.

Real-world example: openssl s_client.

Q27. What is mTLS?

Both client and server present certificates for mutual authentication.

Why: Zero trust.

Real-world example: Service mesh between pods.

Q28. HTTP/1.1 vs HTTP/2 vs HTTP/3?

1.1 has head-of-line blocking per connection; 2 multiplexes streams over one TCP connection; 3 uses QUIC (UDP) to avoid TCP head-of-line blocking.

Why: Performance.

Real-world example: Enable HTTP/2 on LB.

Q29. How does DNS resolution work recursively?

Stub resolver > recursive resolver > root > TLD > authoritative; answers cached by TTL.

Why: DNS depth.

Real-world example: dig +trace.

Q30. How does ARP work?

Maps IP to MAC on a local network via broadcast request and reply.

Why: L2/L3 link.

Real-world example: Duplicate IP causes ARP conflicts.

Q31. How do you design a VPC for 3 tiers?

Public subnets (ALB, NAT), private app subnets, private DB subnets across 2-3 AZs, SGs chained (ALB > app > DB), route tables, endpoints.

Why: Architecture.

Real-world example: See AWS VPC topic.

Q32. What is anycast?

Same IP announced from many locations; routing sends users to the nearest.

Why: Global services.

Real-world example: CDN and DNS providers.

Q33. TCP congestion control and retransmission?

TCP adapts window size to network conditions and retransmits lost segments; causes latency during loss.

Why: Performance tuning.

Real-world example: Lossy links slow uploads.

Q34. Explain conntrack exhaustion.

Stateful NAT/firewall keeps connection table; full table drops new connections.

Why: Real production problem.

Real-world example: Kubernetes nodes with many short connections.

Q35. What is SNI?

TLS extension telling the server which hostname the client wants, enabling many certificates on one IP.

Why: TLS hosting.

Real-world example: Multi-tenant ingress.

Q36. Explain BGP at high level.

Protocol exchanging routing information between autonomous systems on the internet.

Why: Internet routing.

Real-world example: Route leaks cause outages.

Q37. Symmetric vs asymmetric encryption in TLS?

Asymmetric authenticates and exchanges keys; symmetric encrypts bulk data quickly.

Why: Crypto basics.

Real-world example: ECDHE + AES-GCM.

Q38. How would you reduce latency to global users?

CDN, edge caching, regional deployments, anycast/latency routing, keep-alive, HTTP/3, database read replicas.

Why: Architecture.

Real-world example: Route 53 latency routing.

Q39. What is a bastion host?

Hardened jump server for admin access to private networks; alternatives include SSM Session Manager.

Why: Secure access.

Real-world example: SSH via bastion to private DB.

Q40. Explain VPN vs Direct Connect/peering.

VPN is encrypted over the internet; Direct Connect is a dedicated link; peering connects VPCs privately (non-transitive).

Why: Hybrid networking.

Real-world example: Peering doesn't route through third VPC.

Scenario-Based (15)

Q41. Users in one country cannot reach the site.

Check DNS resolution from there, CDN/edge, geo-blocking/WAF, ISP routing; use external probes.

Why: Regional issues.

Real-world example: WAF rule blocking a country.

Q42. Application cannot connect to database after deploy.

Security group, subnet route/NACL, DNS name, port, credentials, DB max connections.

Why: Layered thinking.

Real-world example: SG missing app to DB rule.

Q43. Site slow only at peak.

Check LB metrics, backend CPU/DB, connection limits, autoscaling, CDN hit ratio.

Why: Capacity.

Real-world example: Connection pool exhaustion.

Q44. Migrate domain to a new server with no downtime.

Lower TTL in advance, deploy new server, test with hosts file, switch record, monitor, restore TTL, keep old for rollback.

Why: Change planning.

Real-world example: TTL 60s day before.

Q45. Certificate expired on production.

Renew and deploy immediately (full chain), reload proxy, add expiry monitoring and auto-renewal.

Why: Ops maturity.

Real-world example: cert-manager/ACM.

Q46. Design secure access for developers to private databases.

Bastion/SSM tunnel, IAM auth, short-lived credentials, audit logs, no public DB.

Why: Security design.

Real-world example: SSM port forwarding.

Q47. Two VPCs have overlapping CIDR and must connect.

Cannot peer; re-address one, use NAT/PrivateLink for specific services.

Why: Design consequence.

Real-world example: Plan CIDRs company-wide.

Q48. API intermittently returns 504.

Increase upstream timeouts only after finding the slow dependency; check backend latency, DB, retries and idle timeouts (LB idle timeout vs app keep-alive).

Why: Root cause vs symptom.

Real-world example: ALB idle timeout 60s vs app 30s.

Q49. Traffic must be restricted to office IPs.

Security group/WAF IP allow-list, VPN, or Zero Trust access proxy.

Why: Access control.

Real-world example: Admin panel behind VPN.

Q50. Prevent DDoS impact.

CDN/edge absorption, AWS Shield/WAF rate limits, autoscaling, blackhole abusers, cache.

Why: Availability.

Real-world example: Rate limit per IP.

Q51. Choose ALB or NLB.

ALB for HTTP path/host routing and WAF; NLB for TCP/UDP, static IPs, ultra-low latency.

Why: Service selection.

Real-world example: gRPC/TCP service on NLB.

Q52. Internal services must resolve names privately.

Private hosted zones/Route 53 resolver, CoreDNS in Kubernetes.

Why: Private DNS.

Real-world example: db.internal.

Q53. A microservice cannot reach the internet from a private subnet.

Check route to NAT gateway, NAT in public subnet with EIP, SG/NACL egress, DNS.

Why: Common VPC issue.

Real-world example: Missing 0.0.0.0/0 route.

Q54. Load balancer shows targets unhealthy.

Health check path/port/response, SG allowing LB to target, app not listening.

Why: LB debugging.

Real-world example: Health check returns 302.

Q56. Connection timed out.

Packets dropped: firewall/SG/NACL/route/host down. Test with nc, traceroute, check rules both sides.

Why: Symptom mapping.

Real-world example: SG missing rule.

Q57. Connection refused.

Host reachable, no listener or wrong interface/port. ss -tulpn on server.

Why: Symptom mapping.

Real-world example: App bound to 127.0.0.1.

Q58. Could not resolve host.

DNS failure: check resolver, record, network; dig against different resolvers.

Why: DNS.

Real-world example: Wrong /etc/resolv.conf.

Q59. SSL certificate problem: unable to get local issuer.

Missing CA/intermediate; fix chain or trust store.

Why: TLS.

Q60. Ping works but the app does not.

ICMP allowed but TCP port blocked or service down; test with nc/curl.

DNS issue or virtual host/SNI requires Host header; check dig, curl --resolve.

Q62. Random resets (ECONNRESET).

Idle timeout mismatch, proxy/LB closing, app crash, conntrack; check timeouts and logs.

Q63. Very slow first request, fast later.

Peering route tables both sides, SG referencing, NACL, DNS resolution options, overlapping CIDR.

Why: Peering.

Why: Partial failures.

Definitions

  • IP identifies host; port identifies service; DNS maps names; TCP reliable; UDP fast; TLS encrypts; NAT translates; CIDR /n notation.

Commands

  • ip a ip r ss -tulpn ping -c 4 host traceroute/mtr host
  • dig +short host dig @8.8.8.8 host dig +trace host nslookup host
  • curl -vI https://host curl --resolve host:443:IP https://host nc -zv host port
  • openssl s_client -connect host:443 -servername host tcpdump -i any -nn port 443

Files

  • /etc/hosts /etc/resolv.conf /etc/nginx/nginx.conf /etc/haproxy/haproxy.cfg

Architecture

  • Client > DNS > CDN/WAF > LB > reverse proxy > app > DB, with public/private subnets.

Ports

  • HTTP 80, HTTPS 443, SSH 22, DNS 53, SMTP 25/587, RDP 3389, MySQL 3306, PostgreSQL 5432, Redis 6379

Differences

  • TCP vs UDP; L4 vs L7 LB; SG vs NACL; forward vs reverse proxy; 502 vs 504; timeout vs refused.

  • DNS: dig | Reachability: ping/mtr | Port: nc/ss | TLS: openssl | HTTP: curl -v | Packets: tcpdump

Best practices

  • TLS 1.2+, least-privilege SGs, private subnets for data, multi-AZ, health checks, timeouts/retries, auto-renew certs.
