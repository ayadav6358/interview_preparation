DNS Deep Dive

Intermediate Networking

Concept (What & Why)

DNS name ko IP mein badalta hai. Aadhe production outages DNS ki wajah se hote hain. Records, TTL aur resolution flow samjho.

Definition Deep-Dive

QuestionAnswer
Simple definitionDNS is the internet's phone book: names to IP addresses.
Technical definitionHierarchical distributed database; recursive resolvers query root, TLD and authoritative servers; records have types and TTLs; caching happens at multiple levels.
Why does it exist?Humans use names; machines use IPs; IPs change.
What happens without it?Remember IP addresses.
When to useEvery service.
When NOT to useHard-coded IPs.
Real-world analogyPhone contacts.

Diagram & Internal Working

Browser -> Resolver(ISP/8.8.8.8) -> Root (.) -> TLD (.com) -> Authoritative (Route53) -> IP
                 └── cache (TTL) ──┘

Records: A (IPv4) | AAAA (IPv6) | CNAME (alias) | MX (mail) | TXT (SPF/verify) | NS | SRV

How it works internally (diagram explained)

Browser cache > OS cache > recursive resolver (ISP/8.8.8.8) > root server (points to TLD) > .com TLD (points to authoritative) > authoritative server returns the A record > answer cached for TTL.

Install / Setup

sudo apt install dnsutils -y   # dig, nslookup

Practical Examples

Query records

dig example.com A +short
dig example.com MX; dig example.com TXT
dig +trace example.com
dig @1.1.1.1 example.com                # bypass local resolver
nslookup -type=NS example.com

Route53 weighted record (Terraform)

resource "aws_route53_record" "app" {
  zone_id = var.zone_id
  name    = "app.example.com"
  type    = "A"
  set_identifier = "blue"
  weighted_routing_policy { weight = 90 }
  alias { name = aws_lb.blue.dns_name  zone_id = aws_lb.blue.zone_id  evaluate_target_health = true }
}

Important Commands Explained

dig +short api.example.com A
What does it do?
Queries a record type and prints only the answer.
Important options
+trace full path, @server choose resolver, -x reverse lookup.
Expected output
203.0.113.10
Common mistake
Testing with a cached resolver and assuming global state.
Troubleshooting
Compare dig @8.8.8.8 and dig @authoritative-ns.

Real-World Problems & Fixes (Troubleshooting)

Problem: After migration, some users still hit old server
Cause: High TTL (86400) cached
Fix: Lower TTL to 60s a day BEFORE migration, raise after.
Problem: Pods can't resolve external names
Cause: CoreDNS/ndots issue or upstream DNS blocked
Fix: kubectl exec -it pod -- nslookup google.com; check CoreDNS logs/configmap.

Best Practices

Reliability

  • Health-checked failover records; low TTL for changing endpoints.

Common Mistakes

Production mistakes

  • Long TTL during cutover.

Hinglish Explanation

DNS problem ho to dig use karo aur different resolvers se compare karo. TTL kam karo migration se pehle.

ConceptMemory trick
ResolutionCache > Recursive > Root > TLD > Authoritative

Interview Questions

Q1. CNAME vs A record?

A maps name to IP; CNAME maps name to another name. CNAME cannot exist at zone apex (use ALIAS).

Q2. What is TTL?

How long resolvers cache the record.

Q3. Recursive vs authoritative DNS?

Recursive resolver does lookups for clients; authoritative holds the actual zone records.

Q4. What is split-horizon DNS?

Different answers for internal vs external queries (private hosted zone).

Q5. Why does DNS use UDP 53 and sometimes TCP?

UDP for small fast queries; TCP for large responses, zone transfers, DNSSEC.

Q6. Some users see the old IP after a change.

Caching until TTL expires at resolvers/clients; verify authoritative answer, wait or flush caches.

Why: TTL.

Real-world example: Prevent with lower TTL.
