DevSecOps & Security: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: If security checks happen only at the end (a penetration test before go-live), vulnerabilities are found late, fixes are expensive and releases are blocked. DevSecOps builds security into every step of the delivery pipeline ("shift left") and into runtime, so problems are caught early, automatically and continuously.

PROBLEM: software and infrastructure ship with vulnerabilities and leaked secrets
      |
      v
TRADITIONAL APPROACH: separate security team reviews at the end
      |
      v
PAIN: late findings, delays, friction, breaches from known issues
      |
      v
TECHNOLOGY: DevSecOps (SAST, SCA, secret scan, image/IaC scan, DAST, policy, runtime security)
      |
      v
SOLUTION: automated checks in pipeline + least privilege + secrets management + monitoring
      |
      v
REAL-WORLD BENEFIT: fewer incidents, faster compliant releases, security as shared responsibility

Core principles: least privilege, defence in depth (multiple layers), zero trust (verify every request), secure by default, and assume breach (detect and respond). The CIA triad (Confidentiality, Integrity, Availability) frames what we protect.

2. End-to-End Flow

Developer IDE / pre-commit (secret scan, lint)
   v
Git PR (branch protection, code review, signed commits)
   v
CI pipeline:
   SAST (code)  +  SCA (dependencies)  +  Secret scan  +  IaC scan (Terraform/K8s YAML)
   v
Build image (minimal base) -> Image scan (Trivy) -> SBOM (Syft) -> Sign (cosign)
   v
Registry (private, scanning, immutable tags)
   v
Deploy gate: policy admission (Kyverno/OPA) verifies signature, non-root, no privileged
   v
Runtime: NetworkPolicy, Pod Security, RBAC, secrets from Vault/Secrets Manager, WAF
   v
DAST on staging, runtime detection (Falco/GuardDuty), logging/SIEM
   v
Vulnerability management: patch, rotate, incident response, audit

Security starts before commit with local secret scanning and continues in CI: SAST analyses source code, SCA checks third-party dependencies for known CVEs, secret scanning blocks leaked credentials, IaC scanning checks Terraform/Kubernetes files for misconfiguration. The built image is scanned, an SBOM (Software Bill of Materials) is produced and the image is signed. At deploy time an admission controller enforces policies (only signed images, non-root, no privileged containers). At runtime, NetworkPolicies limit traffic, RBAC limits API access, secrets come from a vault, and tools such as Falco/GuardDuty detect suspicious behaviour. DAST tests the running staging app. Findings feed a patching and incident-response process.

SAST vs DAST: SAST reads source without running it (early, code-level, false positives); DAST attacks the running app from outside (finds runtime/config issues, later in cycle). 5. Troubleshooting Playbook

Problem: Secret found in Git history
Possible cause: Committed key/token
How to check: gitleaks detect, git log -S
Fix: Rotate immediately, remove from history, invalidate sessions, audit usage in CloudTrail.
Prevention: Pre-commit hook + push protection + secret manager.
Problem: Pipeline blocked by a critical CVE
Possible cause: Vulnerable base image or library
How to check: Trivy/Snyk report shows package and fixed version
Fix: Update package/base image, rebuild; if no fix, assess exploitability and add time-boxed exception.
Prevention: Automated dependency updates; regular base image rebuilds.
Problem: Too many false positives from scanners
Possible cause: Default rules too broad
How to check: Review findings and rule IDs
Fix: Tune rules, baseline, suppress with justification and expiry.
Prevention: Security champions review exceptions.
Problem: Pod blocked by admission policy
Possible cause: Policy violation (root, privileged, unsigned image)
How to check: kubectl describe, event message from Kyverno/Gatekeeper
Fix: Fix the manifest (runAsNonRoot, drop capabilities, sign image).
Prevention: Provide compliant templates/Helm charts.
Problem: Suspicious outbound traffic from a container
Possible cause: Compromised container or cryptominer
How to check: Falco alerts, kubectl exec inspection, flow logs, NetworkPolicy
Fix: Isolate (NetworkPolicy/quarantine), collect evidence, redeploy from clean image, rotate secrets.
Prevention: Default-deny egress, runtime detection.
Problem: IAM key exposed
Possible cause: Key in code/log/public repo
How to check: CloudTrail activity for the key, IAM credential report
Fix: Deactivate and rotate key, review activity, revoke sessions.
Prevention: Use roles/OIDC, no long-lived keys.

6. Production Best Practices

Development

  • Threat model new features; input validation; parameterised queries; dependency updates; pre-commit secret scan.

Production

  • Patch regularly; least-privilege IAM; network segmentation; WAF; backups; incident response plan.

Security

  • Encrypt in transit and at rest; MFA; rotate secrets; sign artifacts; verify at admission; audit logging; CIS benchmarks; scan continuously; vulnerability SLAs (e.g. critical in 7 days).

Performance

  • Run scans incrementally/cached and in parallel; scan schedule for heavy DAST.

Reliability

  • Security controls should fail closed but with break-glass; test policies in audit mode before enforce.

Cost Optimization

  • Prioritise by risk (exploitability, exposure); avoid tool sprawl; use open-source scanners where suitable.

Monitoring & Logging

  • Central audit logs (CloudTrail, K8s audit), SIEM alerts, GuardDuty; retention per compliance.

Backup & Disaster Recovery

  • Immutable/offline backups (ransomware); tested restore; runbooks for incident response.

7. Common Mistakes

Beginner mistakes

  • Hard-coding passwords.
  • Using default credentials.

Developer mistakes

  • String-concatenated SQL.
  • Ignoring dependency alerts.
  • Logging sensitive data.

DevOps mistakes

  • Scanning but never fixing (no ownership/SLAs).
  • Over-privileged CI credentials.
  • Running containers as root.

Production mistakes

  • Unpatched systems.
  • No incident response plan.
  • Public S3/DB.

Security mistakes

  • Security only at the end.
  • Sharing accounts.
  • Disabling security tools to 'get it working'.

8. Version / Environment Notes

  • OWASP Top 10 is updated periodically (2021 edition current at time of writing): check owasp.org for the latest.
  • Kubernetes Pod Security Admission replaced PodSecurityPolicy (removed in v1.25).
  • Sigstore/cosign supports keyless signing (OIDC) as well as key-based; check current CLI syntax.
  • Scanner databases update continuously: always run the latest DB and pin scanner versions in CI; some tools changed licences (verify for your use).
  • Compliance frameworks (SOC 2, ISO 27001, PCI DSS, HIPAA, GDPR) have their own requirements: consult your compliance owner.

11. How I Explain This to a Client

30-second explanation

DevSecOps means security is built into every step of how we build and run software, automatically. That finds problems early, keeps secrets safe and lowers the risk of breaches without slowing down releases.

2-minute explanation

Instead of a security review at the end, we run automatic checks throughout the pipeline: scanning for leaked passwords, vulnerabilities in our code and in third-party libraries, and weaknesses in container images and infrastructure code. Only images that pass and are digitally signed can be deployed. In production we use least-privilege access, encrypted data, network segmentation and monitoring for suspicious activity. Secrets live in a vault, not in code. This reduces the chance and impact of an incident and gives you evidence for audits.

5-minute deep explanation

I will describe four layers. Code: pre-commit secret scanning, code review, SAST and dependency scanning with automated update pull requests. Build and supply chain: minimal container images, image and infrastructure-as-code scanning, an SBOM for each release and cryptographic signing, with policies that fail the build on critical findings. Deployment and runtime: admission controls that only allow signed, non-root images, RBAC and network policies, encrypted secrets from a vault with rotation, WAF and runtime threat detection. Governance: centralised audit logs, vulnerability SLAs, tested incident-response and backup procedures, and mapping of controls to compliance frameworks such as ISO 27001 or SOC 2. Security becomes a repeatable, measured process instead of a last-minute gate.

13. Mini Project: Secure pipeline: secret scan + SAST/SCA + Trivy + SBOM + signing

PR --> gitleaks --> unit tests --> semgrep (SAST) + dependency audit (SCA)
    --> docker build --> trivy image (fail on HIGH/CRITICAL) --> syft SBOM --> cosign sign
    --> push registry --> Kyverno verifies signature at admission

Step 1: Secret scanning

gitleaks detect --source . --verbose
# CI: fail the job on any finding (exit code 1)

Detects API keys and tokens in the working tree and history. Rotate anything found before cleaning up.

Step 2: SAST and SCA

pip install semgrep pip-audit
semgrep --config auto --error .
pip-audit -r requirements.txt
# JS: npm audit --audit-level=high

--error returns non-zero when findings exist. pip-audit/npm audit find known vulnerable dependencies. Tune rules to control false positives.

Step 3: Image scan, SBOM, sign

docker build -t registry.example.com/app:${GIT_SHA} .
trivy image --severity HIGH,CRITICAL --exit-code 1 registry.example.com/app:${GIT_SHA}
syft registry.example.com/app:${GIT_SHA} -o spdx-json > sbom.json
docker push registry.example.com/app:${GIT_SHA}
cosign sign --yes registry.example.com/app:${GIT_SHA}

Trivy blocks vulnerable images; Syft records what is inside; cosign signs the pushed image (keyless signing uses the CI's OIDC identity: verify CLI flags for your cosign version). Sign after push because signatures attach to the registry digest.

Step 4: Enforce at admission (Kyverno)

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-nonroot }
spec:
  validationFailureAction: Enforce
  rules:
  - name: run-as-non-root
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "Containers must run as non-root."
      pattern:
        spec:
          securityContext: { runAsNonRoot: true }

The cluster rejects Pods that do not declare runAsNonRoot: true. Start with Audit mode to measure impact, then switch to Enforce. A second policy (verifyImages) can require valid cosign signatures.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is DevSecOps?

Integrating security practices into DevOps: automated, continuous, shared responsibility.

Why: Definition.

Real-world example: Scanners in the CI pipeline.

Q2. What is shift-left security?

Moving security checks earlier in the development lifecycle.

Why: Key idea.

Real-world example: Secret scan before commit.

Q3. What is the CIA triad?

Confidentiality, Integrity, Availability.

Why: Foundations.

Real-world example: Encryption = confidentiality.

Q4. What is least privilege?

Granting only the permissions needed for a task.

Why: Principle.

Real-world example: Read-only role for reports.

Q5. What is MFA?

Multi-factor authentication: two or more proofs (password + device).

Why: Account security.

Real-world example: TOTP on AWS root.

Q6. What is a vulnerability vs a threat vs risk?

Vulnerability is a weakness; threat is a potential attacker/event; risk is likelihood times impact.

Why: Terminology.

Real-world example: Unpatched server = vulnerability.

Q7. What is encryption at rest and in transit?

Protecting stored data (disk/DB) and data moving over networks (TLS).

Why: Data protection.

Real-world example: S3 SSE-KMS and HTTPS.

Q8. What is OWASP Top 10?

List of the most critical web application security risks.

Why: Awareness.

Real-world example: Injection, broken access control.

Q9. Why not store secrets in Git?

History keeps them, repos are widely accessible, bots scan for leaks.

Why: Secrets.

Real-world example: AWS key abused in minutes.

Q10. What is a CVE?

Common Vulnerabilities and Exposures: a public identifier for a known vulnerability.

Why: Vulnerability mgmt.

Real-world example: CVE-2021-44228 (Log4Shell).

Intermediate (14)

Q11. SAST vs DAST vs SCA?

SAST analyses source; DAST tests running app; SCA finds vulnerable dependencies.

Why: Tool coverage.

Real-world example: SonarQube, ZAP, Snyk.

Q12. What is an SBOM and why?

A list of components in software; helps find affected systems when a new CVE appears.

Why: Supply chain.

Real-world example: Log4Shell impact query.

Q13. How do you scan container images?

Trivy/Grype against OS packages and language dependencies; fail on severity thresholds; rescan registry images regularly.

Why: Container security.

Real-world example: trivy image --exit-code 1.

Q14. Explain secrets management best practices.

Central vault, dynamic short-lived credentials, rotation, least-privilege access, audit logs, never in code/images.

Why: Secrets.

Real-world example: Vault database secrets engine.

Q15. What is RBAC?

Role-based access control assigns permissions to roles, roles to users.

Why: AuthZ.

Real-world example: K8s Role/RoleBinding.

Q16. What is SQL injection and prevention?

Attacker input alters a query; prevent with parameterised queries/ORM, validation and least-privilege DB accounts.

Why: App security.

Real-world example: ' OR 1=1 --.

Q17. What is XSS/CSRF?

XSS injects scripts into pages; CSRF tricks a browser into unwanted authenticated requests; prevent with output encoding/CSP and CSRF tokens/SameSite cookies.

Why: Web security.

Real-world example: Stored XSS in comments.

Q18. How do you secure Docker containers?

Non-root user, minimal image, read-only FS, drop capabilities, no privileged/docker.sock, scan/sign images, resource limits.

Why: Container hardening.

Real-world example: See Docker guide.

Q19. What is a WAF?

Web application firewall filtering HTTP traffic for attacks (SQLi, XSS, bots).

Why: Perimeter.

Real-world example: AWS WAF on ALB.

Q20. What is TLS/mTLS?

TLS encrypts and authenticates server; mTLS authenticates both sides.

Why: Transport security.

Real-world example: Service mesh mTLS.

Q21. How to secure CI/CD?

Least-privilege runners, OIDC not static keys, protected branches, secret scanning, pinned actions/plugins, isolated ephemeral agents, signed artifacts.

Why: Pipeline security.

Real-world example: GitHub Actions hardening.

Q22. What is IaC scanning?

Checking Terraform/CloudFormation/K8s manifests for misconfigurations before deployment.

Why: Prevent misconfig.

Real-world example: Checkov finds open SG.

Q23. What is a security group misconfiguration example?

Allowing 0.0.0.0/0 to SSH/DB ports.

Why: Cloud security.

Real-world example: Exposed MongoDB.

Q24. What is IAM best practice?

No root use, MFA, roles instead of keys, least privilege, rotate, review with Access Analyzer.

Why: Cloud IAM.

Real-world example: Assume-role for admins.

Advanced (14)

Q25. How would you design a secure CI/CD pipeline end to end?

Pre-commit + protected branches; CI with SAST/SCA/secret/IaC/image scans; SBOM+signing; private registry; admission verification; OIDC creds; approvals; audit logs.

Why: Architecture.

Real-world example: See mini project.

Q26. Explain supply chain attacks and mitigations.

Compromising dependencies, build systems or registries; mitigate with pinning, provenance (SLSA), signed artifacts, SBOM, private mirrors, review of updates, least privilege builds.

Why: Modern threat.

Real-world example: SolarWinds/xz-style incidents.

Q27. How do you secure a Kubernetes cluster?

RBAC least privilege, NetworkPolicy default deny, Pod Security Standards, admission policies, secrets encryption/external, image signing, audit logs, runtime detection, node hardening, regular upgrades.

Why: K8s security.

Real-world example: Kyverno + Falco.

Q28. What is threat modelling (STRIDE)?

Systematic identification of threats using data-flow diagrams and categories: Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege.

Why: Design security.

Real-world example: Model login flow.

Q29. What is zero trust?

Never trust by network location; authenticate, authorise and encrypt every request with least privilege and continuous verification.

Why: Architecture.

Real-world example: BeyondCorp-style access.

Q30. Vault dynamic secrets?

Vault generates short-lived credentials on demand (DB users/AWS keys) with TTL and automatic revocation.

Why: Secrets depth.

Real-world example: DB user valid 1 hour.

Q31. How do you handle a compromised credential?

Revoke/rotate, determine scope via audit logs, contain, eradicate persistence, recover, communicate, postmortem, add prevention.

Why: Incident response.

Real-world example: Leaked AWS key.

Q32. Explain IAM policy evaluation and privilege escalation risks.

Explicit deny wins; risky permissions (iam:PassRole, iam:CreatePolicyVersion, sts:AssumeRole broadly) allow escalation; use boundaries/SCPs.

Why: Cloud security depth.

Real-world example: PassRole to admin role.

Q33. What is container escape and how to prevent it?

Breaking out of isolation to the host via kernel bugs or misconfig (privileged, docker.sock, hostPath); prevent by hardening, updates, seccomp/AppArmor, gVisor/Kata for untrusted workloads.

Why: Container internals.

Real-world example: Privileged Pod.

Q34. SLSA framework?

Levels of supply-chain assurance: scripted builds, provenance, hardened isolated builds, verification.

Why: Supply chain.

Real-world example: Provenance attestation with GitHub.

Q35. How to manage vulnerabilities at scale?

Inventory (SBOM), prioritise by exploitability/exposure (EPSS/KEV), SLAs, ownership, automated updates, exceptions with expiry, metrics.

Why: Vuln mgmt.

Real-world example: Critical in 7 days.

Q36. Explain secure secret injection in Kubernetes.

External Secrets Operator/CSI driver/Vault agent fetching at runtime, avoiding Git-stored secrets; encrypt etcd; short-lived tokens.

Why: K8s secrets.

Real-world example: ESO syncing from Secrets Manager.

Q37. What is a security incident lifecycle?

Preparation, detection, containment, eradication, recovery, lessons learned (NIST).

Why: IR process.

Real-world example: Runbooks and drills.

Q38. How do you audit and monitor for threats?

CloudTrail, K8s audit, VPC flow logs, GuardDuty, SIEM correlation, alerts on anomalies, retention.

Why: Detection.

Real-world example: Alert on root login.

Scenario-Based (14)

Q39. A developer pushed an AWS key to GitHub.

Deactivate/rotate key immediately, check CloudTrail for use, purge history, enable push protection, move to role/OIDC.

Why: Classic incident.

Real-world example: See troubleshooting.

Q40. Critical CVE in a base image used by 30 services.

Identify via SBOM/registry scan, update base image centrally, rebuild and redeploy in priority order, verify, add gate.

Why: Scale response.

Real-world example: Renovate opens PRs across repos.

Q41. Auditor asks for proof of change control.

Show PR approvals, signed commits, pipeline logs, artifact signatures, deployment history and CloudTrail.

Why: Compliance.

Real-world example: GitOps audit trail.

Q42. Security scans slow the pipeline.

Cache DBs, run in parallel, incremental SAST, full scans nightly, gate only on new findings.

Why: Balance speed/safety.

Real-world example: Trivy DB cache.

Q43. Developers bypass security gates.

Make secure path easiest (templates), enforce server-side (branch protection, admission), educate, measure exceptions.

Why: Culture.

Real-world example: Golden pipeline.

Q44. Database credentials shared in chat.

Rotate, move to secret manager with dynamic creds, restrict access, policy and training.

Why: Secrets hygiene.

Real-world example: Vault DB engine.

Q45. Public S3 bucket with customer data.

Block access immediately, assess exposure via access logs, notify per policy/regulation, enable account-level Block Public Access and Config rules.

Why: Data breach response.

Real-world example: Config auto-remediation.

Q46. Ransomware risk mitigation.
