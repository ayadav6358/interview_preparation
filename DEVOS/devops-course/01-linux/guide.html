Linux: Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Almost every server, container, CI runner and cloud VM runs Linux. If you cannot operate Linux from the command line, you cannot deploy, debug or secure anything else in DevOps. Linux gives a stable, scriptable, free operating system where everything is a file and every task can be automated.

PROBLEM: servers have no GUI and must be managed remotely and at scale
      |
      v
TRADITIONAL APPROACH: click through a GUI on each machine
      |
      v
PAIN: slow, not repeatable, impossible for 100 servers
      |
      v
TECHNOLOGY: Linux shell + core utilities + systemd + SSH + bash scripts
      |
      v
SOLUTION: text commands that can be combined, scripted and run over SSH
      |
      v
REAL-WORLD BENEFIT: fast troubleshooting, automation, consistent servers

Linux is the kernel; a distribution (Ubuntu, RHEL, Amazon Linux) adds package manager, init system and tools. Containers use the host's Linux kernel features (namespaces, cgroups), so Linux knowledge is also container knowledge.

2. End-to-End Flow

Engineer laptop
   | ssh user@server  (key-based)
   v
sshd (port 22) authenticates
   v
Shell (bash) reads your command
   v
Kernel system call (open/read/fork/exec)
   v
Process runs (managed by systemd or shell)
   v
Output -> stdout / stderr / log files (/var/log, journalctl)
   v
Monitor: top, free, df, ss, journalctl  -> fix -> script it

You connect with SSH; sshd verifies your key and starts a shell. The shell parses your command, finds the program in PATH and asks the kernel (via fork and exec) to run it as a process. The process reads/writes files (including devices and sockets) using permissions of your user. Long-running services are supervised by systemd. Output goes to the terminal, to files in /var/log or to the journal. When something is wrong you check CPU/memory/disk/network with standard tools, fix the cause and turn the fix into a script so it is repeatable.

5. Troubleshooting Playbook

Problem: Server is slow
Possible cause: High CPU, memory pressure/swap, disk I/O wait, network
How to check: uptime, top/htop, free -h, vmstat 1, iostat -x 1
Fix: Identify the top consumer, restart/scale/tune; fix leak.
Prevention: Monitoring and alerts on load, memory, disk.
Problem: Disk full (No space left on device)
Possible cause: Logs, old artifacts, deleted-but-open files, inode exhaustion
How to check: df -h, df -i, du -xh / --max-depth=2 | sort -h, lsof +L1
Fix: Delete/rotate logs, clean packages, restart process holding deleted file.
Prevention: logrotate, disk alerts at 80%.
Problem: Permission denied
Possible cause: Wrong owner/mode, missing group, SELinux/AppArmor, ACL
How to check: ls -l, id, namei -l path, getenforce
Fix: chown/chmod minimal needed, add to group.
Prevention: Use groups and umask policies.
Problem: Service fails to start
Possible cause: Bad config, port in use, missing dependency
How to check: systemctl status svc, journalctl -u svc -xe, ss -tulpn
Fix: Fix config, free port, restart.
Prevention: Config validation (nginx -t) before reload.
Problem: Cannot SSH
Possible cause: Wrong key/permissions, firewall/security group, sshd down
How to check: ssh -vvv, key perms 600, systemctl status sshd, ss -tlnp | grep 22
Fix: Fix key mode, open port, restart sshd.
Prevention: Keep a second admin access path.
Problem: Out of memory (OOM killer)
Possible cause: Process exceeded RAM
How to check: dmesg -T | grep -i oom, free -h
Fix: Add memory, fix leak, set limits.
Prevention: cgroup/systemd limits and monitoring.

6. Production Best Practices

Development

  • Use shell scripts with set -euo pipefail; test in a clean container/VM.

Production

  • Run services under systemd as non-root users; keep packages patched; use config management for consistency.

Security

  • SSH keys only, disable root login and password auth; least privilege with sudo; firewall (ufw/nftables/security groups); fail2ban; auditd.
  • Set correct file permissions (600 for keys).

Performance

  • Know the baseline (load, memory, IO); tune limits (ulimit, sysctl) based on evidence.

Reliability

  • Auto-restart services (Restart=on-failure); logrotate; NTP time sync.

Cost Optimization

  • Right-size instances; clean unused packages/logs/images.

Monitoring & Logging

  • Centralize logs (journald > Loki/ELK); node_exporter metrics.

Backup & Disaster Recovery

  • Automate backups (rsync/tar/snapshots) and test restores.

7. Common Mistakes

Beginner mistakes

  • chmod 777 to fix permissions.
  • Running everything as root.
  • rm -rf with a variable that might be empty.

Developer mistakes

  • Scripts without error handling or quoting variables.
  • Relative paths in cron jobs.

DevOps mistakes

  • Editing servers by hand (config drift).
  • No log rotation.
  • Ignoring inode usage.

Production mistakes

  • Restarting services without checking config.
  • Filling disk with debug logs.

Security mistakes

  • Password SSH login with weak passwords.
  • World-readable secrets/keys.
  • Blind curl | sudo bash from unknown sources.

8. Version / Environment Notes

  • Package managers differ: apt (Debian/Ubuntu), dnf (RHEL 8+/Fedora/Amazon Linux 2023), yum (older RHEL/Amazon Linux 2).
  • ifconfig/netstat (net-tools) are deprecated: use ip and ss.
  • Firewall front-ends differ: ufw (Ubuntu), firewalld (RHEL), nftables underneath; iptables is legacy on modern distros.
  • cgroups v2 is the default on modern distributions; some tooling paths differ from v1.
  • On WSL2 and macOS some commands (systemctl, /proc) behave differently or are missing.

11. How I Explain This to a Client

30-second explanation

Linux is the operating system that runs almost all servers and cloud infrastructure. We manage it through secure remote commands and scripts, which makes our systems fast to operate, easy to automate and simple to secure.

2-minute explanation

Our applications run on Linux servers in the cloud and inside containers. Linux is stable, secure and fully scriptable, so we can manage hundreds of machines the same way. Administrators connect with SSH keys, services are supervised by systemd so they restart automatically, and logs and metrics are collected centrally. We apply security basics: least-privilege users, key-only SSH, firewalls and regular patching. This gives you reliability, faster troubleshooting and lower operational cost because tasks are automated instead of manual.

5-minute deep explanation

I will explain in four parts. Foundation: Linux is an open-source kernel with distributions like Ubuntu or Amazon Linux; its principle is that everything is a file and every tool does one job, so tools can be combined. Operations: we manage access with users, groups and permissions, run applications as systemd services with restart policies, and manage software through package managers. Reliability: we monitor CPU, memory, disk and network, rotate logs, keep time in sync and back up data. Security and automation: SSH keys only, no root login, firewalls, patching, audit logging, and configuration by scripts or Ansible so servers are identical and rebuildable. Containers and Kubernetes build directly on Linux features (namespaces and cgroups), so this base skill benefits the whole platform.

13. Mini Project: Provision and monitor a hardened web server by script

Laptop --ssh key--> Ubuntu VM
   nginx (systemd service) + ufw firewall + logrotate
   cron: backup /var/www -> /backup (rsync) ; health-check script -> log
   Monitoring: node_exporter (9100) / df, free alerts

Step 1: Create user and harden SSH

sudo adduser deploy && sudo usermod -aG sudo deploy
sudo -u deploy mkdir -p ~deploy/.ssh && sudo chmod 700 ~deploy/.ssh
# put your public key in ~deploy/.ssh/authorized_keys (chmod 600)
sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/; s/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sshd -t && sudo systemctl reload ssh

Creates a non-root admin, then disables root and password login. sshd -t validates the config BEFORE reload so you do not lock yourself out. Service name is ssh on Ubuntu, sshd on RHEL.

Step 2: Install and firewall

sudo apt update && sudo apt install -y nginx ufw
sudo ufw allow OpenSSH && sudo ufw allow 'Nginx Full' && sudo ufw --force enable
systemctl status nginx --no-pager

Installs nginx, allows only SSH and HTTP/HTTPS. Allow SSH BEFORE enabling the firewall.

Step 3: Health check script

#!/usr/bin/env bash
set -euo pipefail
LOG=/var/log/health.log
disk=$(df / --output=pcent | tail -1 | tr -dc '0-9')
if [ "$disk" -gt 80 ]; then echo "$(date -Is) DISK ${disk}%" >> "$LOG"; fi
curl -fsS -o /dev/null http://localhost || echo "$(date -Is) nginx down" >> "$LOG"

set -euo pipefail stops on errors and undefined variables; quotes protect values; it logs problems instead of failing silently.

Step 4: Schedule and verify

sudo install -m 755 health.sh /usr/local/bin/health.sh
( crontab -l 2>/dev/null; echo '*/5 * * * * /usr/local/bin/health.sh' ) | crontab -
sudo journalctl -u nginx -n 20 --no-pager
ss -tulpn | grep -E ':80|:22'

Runs the check every 5 minutes (use absolute paths in cron). Then confirm service logs and listening ports.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is Linux?

A free open-source Unix-like operating system kernel; distributions package it with tools.

Why: Basics.

Real-world example: Ubuntu, RHEL, Amazon Linux.

Q2. What does ls -l show?

Long listing: permissions, links, owner, group, size, date, name.

Why: Everyday command.

Real-world example: -rwxr-xr-- 1 root dev.

Q3. Explain rwx and chmod 755.

Owner rwx (7), group r-x (5), others r-x (5).

Why: Permissions are heavily tested.

Real-world example: Scripts are 755, private keys 600.

Q4. Absolute vs relative path?

Absolute starts at /; relative starts from the current directory.

Why: Navigation.

Real-world example: /etc/nginx vs ../conf.

Q5. What is sudo?

Runs a command as another user (root) if permitted by sudoers.

Why: Privilege control.

Real-world example: sudo systemctl restart nginx.

Q6. How to view a large file?

less, head, tail -f for live logs.

Why: Log reading.

Real-world example: tail -f /var/log/nginx/error.log.

Q7. What is a package manager?

Tool that installs/updates/removes software and dependencies.

Why: Provisioning.

Real-world example: apt install nginx.

Q8. Difference between > and >>?

> overwrites, >> appends.

Why: Redirection.

Real-world example: echo x >> file.

Q9. How do you find a file?

find / -name file or locate.

Why: Basic search.

Real-world example: find /var/log -name '*.log' -mtime +7.

Q10. What is the root user?

Superuser with UID 0 and full privileges.

Why: Security.

Real-world example: Avoid daily use.

Intermediate (15)

Q11. Explain pipes and redirection.

Pipe | sends stdout of one command to stdin of another; redirection sends streams to files; stderr is fd 2.

Why: Command composition.

Real-world example: grep ERROR app.log | sort | uniq -c.

Q12. What is a process vs daemon?

Process is a running program; a daemon is a background service process.

Why: System concepts.

Real-world example: sshd is a daemon.

Q13. How to check listening ports?

ss -tulpn (modern) or netstat -tulpn.

Why: Networking debugging.

Real-world example: Find what uses port 8080.

Q14. What is systemd and a unit file?

Init system/service manager; unit files define services, timers, mounts.

Why: Service management.

Real-world example: /etc/systemd/system/app.service.

Q15. Explain inode.

Metadata structure for a file (owner, permissions, block pointers); filenames map to inodes.

Why: Filesystem depth.

Real-world example: df -i shows inode exhaustion.

Q16. Hard link vs symlink?

Hard link is another name for the same inode; symlink is a path pointer.

Why: Classic question.

Real-world example: ln -s /opt/app-v2 /opt/app.

Q17. Special permissions setuid/setgid/sticky?

setuid runs as owner, setgid group inheritance/run as group, sticky prevents deleting others' files in a directory.

Why: Security.

Real-world example: /tmp has sticky bit.

Q18. How does SSH key authentication work?

Client proves possession of private key matching a public key in authorized_keys via challenge signature; no password sent.

Why: Secure access.

Real-world example: ssh-keygen -t ed25519.

Q19. What is cron syntax?

m h dom mon dow command.

Why: Scheduling.

Real-world example: 0 2 * * * backup.sh.

Q20. grep vs sed vs awk?

grep searches, sed edits streams, awk processes columns/fields.

Why: Text processing.

Real-world example: awk '{print $1}' access.log.

Q21. What is /etc/fstab?

Defines filesystems mounted at boot.

Why: Storage.

Real-world example: Mount EBS at /data with nofail.

Q22. What are environment variables?

Key-value pairs inherited by processes; PATH decides where commands are found.

Why: Scripting/config.

Real-world example: export DB_URL=....

Q23. What is load average?

Average number of runnable/uninterruptible tasks over 1, 5, 15 minutes; compare with CPU count.

Why: Performance.

Real-world example: Load 8 on 4 CPUs means overloaded.

Q24. How to check memory usage?

free -h, vmstat, top; look at 'available' not just 'free'.

Why: Common confusion.

Real-world example: Cache is reclaimable.

Q25. What is nohup and &?

& runs in background; nohup keeps running after logout; prefer systemd/tmux for services.

Why: Process control.

Real-world example: Long job over SSH.

Advanced (15)

Q26. Explain the Linux boot process.

BIOS/UEFI > bootloader (GRUB) > kernel + initramfs > systemd (PID 1) > targets/services > login.

Why: Deep system knowledge.

Real-world example: Rescue mode by editing GRUB.

Q27. Explain namespaces and cgroups.

Namespaces isolate views (pid, net, mnt, uts, ipc, user); cgroups limit/account resources; together they form containers.

Why: Links Linux to Docker.

Real-world example: unshare, systemd-run --property=MemoryMax=.

Q28. How does the OOM killer choose a victim?

Kernel scores processes by memory use and oom_score_adj; kills the highest to free memory.

Why: Memory incidents.

Real-world example: Protect sshd with negative adj.

Q29. Explain LVM.

Physical volumes > volume group > logical volumes; allows resizing/snapshots without repartitioning.

Why: Storage management.

Real-world example: lvextend -r to grow online.

Q30. What is strace used for?

Traces system calls to see what a process is doing (files, network, errors).

Why: Deep debugging.

Real-world example: Find a missing config path.

Q31. Explain iowait and how to find the cause.

CPU waiting for disk I/O. Use iostat -x, iotop, pidstat -d, check saturation/latency.

Why: Performance.

Real-world example: Backup job saturating disk.

Q32. TCP connection states and TIME_WAIT?

TIME_WAIT keeps closed connections briefly for delayed packets; many are normal on busy clients but may exhaust ports.

Why: Network tuning.

Real-world example: ss -s.

Q33. How would you harden a Linux server?

Patching, key-only SSH, no root login, firewall, least privilege sudo, minimal packages, auditd, fail2ban, CIS benchmarks, SELinux/AppArmor enforcing.

Why: Security.

Real-world example: Ansible hardening role.

Q34. What are ulimits and file descriptors?

Per-process limits such as open files; too low causes 'Too many open files'. Set in limits.conf or systemd LimitNOFILE.

Why: High-traffic servers.

Real-world example: Nginx with 100k connections.

Q35. Difference between kill, pkill, killall?

kill targets PID; pkill matches name pattern; killall kills all by exact name.

Why: Process control.

Real-world example: pkill -f gunicorn.

Q36. Explain swap and swappiness.

Swap extends memory using disk; swappiness controls tendency to swap; heavy swapping means memory pressure.

Why: Memory tuning.

Real-world example: Kubernetes nodes usually disable swap.

Q37. How do you troubleshoot a zombie process?

A zombie is a finished child not reaped by its parent; fix the parent (or kill it); zombies use no resources except a PID entry.

Why: Process knowledge.

Real-world example: PID 1 in containers must reap children.

Q38. What is journald and how to filter logs?

systemd's binary log; journalctl -u svc --since '1 hour ago' -p err.

Why: Modern logging.

Real-world example: Persistent storage configured in journald.conf.

Q39. Explain rsync vs scp.

rsync transfers only differences, supports resume/delete/permissions; scp copies whole files.

Why: Data transfer.

Real-world example: Backup with rsync -aHAX --delete.

Q40. tmpfs and /proc /sys?

tmpfs is RAM-backed FS; /proc and /sys are virtual filesystems exposing kernel/process info.

Why: Kernel interfaces.

Real-world example: cat /proc/meminfo.

Scenario-Based (15)

Q41. Server disk is 100% full at night.

df -h find FS, du for big dirs, check logs and deleted-open files with lsof +L1, rotate/truncate logs, expand volume, add alert.

Why: Frequent incident.

Real-world example: Nginx debug log grew to 40GB.

Q42. You cannot SSH to a server.

Check network/security group, key permissions and username, verbose ssh, console access, sshd status/config.

Why: Access problems.

Real-world example: Key file mode 644 rejected.

Q43. A service keeps restarting.

systemctl status, journalctl -u, exit code, config test, resource limits, dependencies, Restart= policy.

Why: Service debugging.

Real-world example: Wrong environment file path.

Q44. High CPU on a production box.

top to find process, pidstat/perf, check recent deploy, threads, runaway loop; mitigate by restart/scale, then fix root cause.

Why: Incident handling.

Real-world example: Regex catastrophic backtracking.

Q45. Need to analyse 5GB log for top IPs.

awk '{print $1}' access.log | sort | uniq -c | sort -nr | head, or use zcat for rotated logs.

Why: Text processing.

Real-world example: Find abusive clients.

Q46. Give a developer limited access to deploy only.

Dedicated user/group, sudo rule for specific command, SSH key, restrict shell/directory permissions.

Why: Least privilege.

Real-world example: sudoers: deploy ALL=(root) NOPASSWD: /bin/systemctl restart app.

Q47. Automate nightly backup.

Script with rsync/tar to remote/S3, cron or systemd timer, logging, retention, restore test, alerts on failure.

Why: Automation.

Real-world example: Timer with Persistent=true.

Q48. Time drift causes TLS/auth errors.

Enable chrony/NTP, check timedatectl, firewall for UDP 123.

Why: Common hidden issue.

Real-world example: Kerberos/JWT expiry failing.

Q49. New disk must be added without downtime.

Attach, partition or LVM pv/vg/lv, create FS, mount, add to fstab with UUID and nofail.

Why: Storage ops.

Real-world example: Grow EBS then growpart and resize2fs.

Q50. Application says 'Too many open files'.

Check ulimit -n, systemd LimitNOFILE, leaks via lsof -p PID | wc -l, raise limits and fix leak.

Why: Limits.

Real-world example: Proxy under load.

Q51. Reduce attack surface on a fleet.

Remove unused packages/services, patch, config management, CIS baseline, central logging, immutable images.

Why: Security at scale.

Real-world example: Golden AMI with Packer.

Q52. Script works manually but fails in cron.

cron has a minimal environment: use absolute paths, set PATH, redirect output, check cron logs.

Why: Classic gotcha.

Real-world example: node not found in cron.

Q53. Move files between servers reliably.

rsync over SSH with checksums/resume, or object storage; verify with sha256sum.

Why: Data movement.

Real-world example: Migrating uploads.

Q54. Container host is out of inodes.

df -i, find directories with many tiny files (find | wc), clean images/logs.

Why: Hidden capacity issue.

Real-world example: Millions of session files.

Q55. Prevent accidental rm -rf / type mistakes.

Use least privilege, quoting and set -u, --preserve-root default, backups, review scripts, dry runs (echo).

Why: Operational safety.

Real-world example: Empty variable expanded to /.

Troubleshooting-Based (10)

Q56. Permission denied running a script.

No execute bit or noexec mount or wrong shebang; chmod +x, check ls -l, mount.

Why: Permissions.

Real-world example: Script from a noexec /tmp.

Q57. command not found.

Not installed or not in PATH; check which, echo $PATH, use full path.

Why: Environment.

Real-world example: Different PATH in sudo/cron.

Q58. Address already in use.

Another process on the port: ss -tulpn | grep PORT, stop it or change port.

Why: Networking.

Real-world example: Old process still running.

Q59. System is swapping heavily.

free -h, vmstat 1, find memory hog, add RAM/limit process.

Why: Memory.

Real-world example: JVM heap too large.

Q60. Log file exists but deleted space not freed.

A process still has it open: lsof +L1, restart process or truncate.

Why: Disk.

Real-world example: Rotated log not reopened.

Q61. DNS fails on a server.

resolvectl status//etc/resolv.conf, dig @8.8.8.8 host, firewall UDP/TCP 53.

Why: Network.

Real-world example: systemd-resolved stub misconfigured.

Q62. Cannot write to a file although permissions look fine.

Check ACLs (getfacl), immutable attribute (lsattr), read-only mount, disk full, SELinux.

Why: Permissions depth.

Real-world example: chattr +i set.

Q63. Sudden reboot of the server.

last -x, journalctl -b -1, dmesg, check OOM/kernel panic/hardware, cloud events.

Why: Postmortem data.

Real-world example: OOM causing panic.

Q64. Command hangs on network mount.

NFS server unreachable; use timeout, mount -o soft, showmount, check network.

Why: Storage.

Real-world example: df blocks on stale NFS.

Q65. sudo: unable to resolve host.

Hostname missing in /etc/hosts; add entry or fix hostname.

Why: Config detail.

Real-world example: After cloning a VM.
