Linux Networking & SSH

Intermediate Linux

Concept (What & Why)

Server se connect karna, ports check karna, aur connectivity debug karna. SSH remote access ka standard hai, keys use karo, passwords nahi.

Definition Deep-Dive

QuestionAnswer
Simple definitionCommands to see and test a server's network, and SSH to log in securely.
Technical definitionLinux exposes networking via ip/ss (netlink), DNS resolvers and firewall (nftables); SSH provides an encrypted channel with key-based authentication, port forwarding and file transfer.
Why does it exist?Servers are remote and services talk over the network.
What happens without it?No remote access or diagnosis.
When to useAlways.
When NOT to usePassword SSH on the internet.
Real-world analogySSH is a locked, private tunnel to the machine.

Diagram & Internal Working

Laptop --ssh (22)--> Bastion (public subnet) --ssh--> Private server
        key-based auth            ProxyJump

Debug ladder:  ping IP -> dig DNS -> curl -v URL -> ss -tulpn (is port listening?) -> firewall (ufw/iptables/SG)

How it works internally (diagram explained)

SSH: TCP connect > key exchange establishes an encrypted session > server sends its host key (verified against known_hosts) > client proves identity by signing a challenge with the private key > shell/subsystem starts.

Install / Setup

sudo apt install openssh-server net-tools dnsutils tcpdump -y

Practical Examples

SSH keys and config

ssh-keygen -t ed25519 -C "anup@laptop"
ssh-copy-id user@server
# ~/.ssh/config
Host prod
  HostName 10.0.1.5
  User ubuntu
  IdentityFile ~/.ssh/id_ed25519
  ProxyJump bastion
# then just: ssh prod

Tunnels and file copy

ssh -L 5432:db.internal:5432 bastion      # local port forward to private DB
scp file.tar.gz prod:/tmp/ ; rsync -avz --progress ./dist/ prod:/var/www/app/

Network debugging

ip a; ip route
ss -tulpn                    # who listens on which port
curl -v https://example.com/health
dig +short example.com; dig @8.8.8.8 example.com
sudo tcpdump -i eth0 port 80 -nn
sudo ufw allow 22/tcp && sudo ufw enable

Harden SSH

# /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
# sudo systemctl reload ssh

Important Commands Explained

ss -tulpn
What does it do?
Lists listening TCP/UDP sockets with processes.
Important options
-t TCP, -u UDP, -l listening, -p process, -n numeric.
Expected output
LISTEN 0 511 0.0.0.0:80 users:((nginx...))
Common mistake
Needs sudo for process names.
Troubleshooting
Not listening? service down or bound to 127.0.0.1.
ssh -i ~/.ssh/key.pem -L 5433:db:5432 user@bastion
What does it do?
SSH with local port forward through a bastion.
Important options
-L local, -R remote, -J jump host, -vvv debug.
Expected output
Shell on the bastion; localhost:5433 reaches db.
Common mistake
Wrong key permissions (must be 600).
Troubleshooting
Permission denied (publickey): user, key, authorized_keys perms.
curl -v http://host:port/health
What does it do?
Tests HTTP with verbose details.
Important options
-I headers, -k insecure, --resolve, -w.
Expected output
Request/response info.
Common mistake
Confusing DNS vs connection failure.
Troubleshooting
Use dig, nc -zv host port.

Hands-On Lab

Lab Goal

Set up key-based SSH.

Prerequisites

  • Two Linux machines/VMs or WSL + a VM

Step 1

ssh-keygen -t ed25519 -C 'me@laptop'

Creates a key pair in ~/.ssh.

Step 2

ssh-copy-id user@server

Adds your public key to ~/.ssh/authorized_keys on the server.

Step 3

ssh user@server 'hostname'

Logs in without a password.

Step 4

ss -tulpn | grep :22

On the server confirm sshd is listening.

Real-World Problems & Fixes (Troubleshooting)

Problem: Permission denied (publickey)
Cause: Wrong key, wrong user, or perms on ~/.ssh too open
Fix: chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys; ssh -vvv for details.
Problem: Port 8080 app running but not reachable from outside
Cause: App bound to 127.0.0.1 or firewall/security group closed
Fix: ss -tulpn shows 127.0.0.1:8080 -> bind 0.0.0.0; open SG/ufw.
Problem: Servers see brute-force attempts
Cause: Public SSH with passwords
Fix: Disable passwords, use fail2ban, restrict SG to office IP/bastion.

Best Practices

Security

  • Key-only, disable root login, use bastion/SSM, fail2ban, rotate keys.

Common Mistakes

Security mistakes

  • Key permissions 644.
  • Sharing private keys.

Hinglish Explanation

SSH mein private key kabhi share mat karo, sirf public key server par daalo. Network problem ho to layer by layer check karo.

Memory Tricks

ConceptMemory trick
Debug networkLayer by layer: link (ip a) > route (ip r) > DNS (dig) > port (nc/ss) > app (curl)

Version / Environment Notes

  • ip/ss replace ifconfig/netstat.
  • Ed25519 keys are preferred over RSA-2048 where supported.

Interview Questions

Q1. How to check which process uses port 80?

sudo ss -tulpn | grep :80 or lsof -i :80.

Q2. Difference between ssh -L and -R?

-L forwards local port to remote destination; -R exposes a local service via a port on the remote server (reverse).

Q3. How does SSH key auth work?

Server has your public key; it sends a challenge encrypted with it; only your private key can answer. Private key never leaves your machine.

Q4. Ping works but curl fails. Why?

ICMP allowed but TCP port blocked/app down/TLS issue/DNS to different name. Test with curl -v, nc -zv host port.

Q5. What is a bastion host?

Hardened public jump server used to reach private instances, with logging and restricted access.

Q6. How to see DNS resolution path?

dig +trace example.com; check /etc/resolv.conf, resolvectl status.

Q7. How would you access a private DB safely?

Via bastion/SSM with SSH tunnel or port forward, no public DB exposure, audited access.

Why: Secure access.

Real-world example: SSM Session Manager port forwarding.
