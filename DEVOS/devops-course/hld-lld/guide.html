HLD & LLD (Design + Diagrams + Real Examples): Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: In senior interviews and real projects you are asked to *design* a system, not just use a tool: "Design a highly available web app on AWS", "Design a CI/CD platform". A good answer needs a repeatable method. HLD (High-Level Design) shows the big picture: components, flow and technology choices with reasons. LLD (Low-Level Design) shows the implementation detail: CIDRs, security group rules, YAML, pipeline, alerts, runbooks.

PROBLEM: 'design X' questions and real architecture decisions are open-ended
      |
      v
TRADITIONAL APPROACH: jump straight to tools or draw random boxes
      |
      v
PAIN: missing requirements, no failure thinking, unjustified choices, cannot implement the design
      |
      v
TECHNOLOGY: a design framework (requirements > HLD > LLD > review) with diagrams and trade-offs
      |
      v
SOLUTION: clarify needs, draw components, justify choices, then specify exact configuration
      |
      v
REAL-WORLD BENEFIT: clear, defensible designs that teams can build and operate

HLD answers what and why (components, data flow, scaling, HA, security, cost). LLD answers how (exact subnets, rules, manifests, commands). Always finish with failure modes and trade-offs: seniors are judged on these.

2. End-to-End Flow

1. Clarify requirements
   functional (what it does) + non-functional (users, RPS, SLA 99.9%, RPO/RTO, compliance, budget)
   v
2. Constraints and assumptions (team skills, cloud, deadlines)
   v
3. HLD: boxes and arrows, technology choices with WHY
   v
4. Data/traffic flow + deployment flow (request path, CI/CD path)
   v
5. Scale + HA + DR (autoscaling, Multi-AZ, backup, failover)
   v
6. Security + observability + cost
   v
7. LLD: CIDR/SG/YAML/pipeline/alerts/runbooks
   v
8. Failure analysis (AZ down? DB down? bad deploy? traffic spike?)
   v
9. Trade-offs, risks, alternatives, next steps

Start by asking questions: expected users and traffic, uptime target, data sensitivity, budget and team skills. Turn answers into numbers (for example 99.9 percent means about 43 minutes downtime per month). Draw the HLD and explain each choice ("ALB because HTTP path routing and health checks"). Describe the request flow and the deployment flow. Then explicitly cover scaling, high availability, disaster recovery, security, observability and cost. Drop to LLD for the critical parts on request: subnet plan, security group chaining, Kubernetes manifests, pipeline. Finish by walking through failure scenarios and stating trade-offs honestly.

5. Troubleshooting Playbook

Problem: Design has a single point of failure
Possible cause: One instance/AZ/NAT/database without redundancy
How to check: Walk the diagram asking 'what if this fails?' for every box
Fix: Add redundancy (multi-AZ, replicas, multiple NATs/LBs), automatic failover.
Prevention: Failure-mode review as part of every design.
Problem: Design cannot scale for peak
Possible cause: Stateful servers, DB bottleneck, no caching/queue
How to check: Estimate RPS and data size; find the narrowest component
Fix: Stateless app + autoscaling, cache, read replicas, async processing, CDN.
Prevention: Load test against the design assumptions.
Problem: Security groups too open
Possible cause: 0.0.0.0/0 rules, shared SG for all tiers
How to check: Review SG/NACL/IAM in LLD
Fix: Chain SGs (ALB > app > DB), private subnets, least-privilege IAM roles.
Prevention: IaC scanning and design review checklist.
Problem: Cost overruns after launch
Possible cause: Over-provisioned instances, NAT data, cross-AZ traffic, idle environments
How to check: Cost model per component; Cost Explorer by tag
Fix: Rightsize, VPC endpoints, schedules, commitments, caching.
Prevention: Cost estimate in the design doc; budgets.
Problem: Design works on paper but ops cannot run it
Possible cause: Too complex, no observability/runbooks, unfamiliar tech
How to check: Ask 'who will run this at 3am and how?'
Fix: Simplify, add dashboards/alerts/runbooks, train, prefer managed services.
Prevention: Include operations in design review.
Problem: Diagram unclear in interview
Possible cause: Too many boxes, no flow, no labels
How to check: Ask if a stranger could follow the request path
Fix: Number the steps, label ports/protocols, separate HLD and LLD views.
Prevention: Practise a consistent diagram style.

6. Production Best Practices

Development

  • Write short design docs and ADRs; keep diagrams in Git (Mermaid).

Production

  • Multi-AZ; stateless services; managed services where sensible; IaC for every LLD element; runbooks.

Security

  • Least privilege, private subnets for data, encryption in transit/at rest, WAF, secrets in a manager, audit logs.

Performance

  • Cache, CDN, async processing, right database choice, load testing.

Reliability

  • Define SLOs and RPO/RTO; health checks, autoscaling, graceful degradation, DR tested.

Cost Optimization

  • Cost per component in the design; commitments/spot/serverless where fit; lifecycle policies.

Monitoring & Logging

  • Golden signals per tier, central logs, tracing, alerts tied to SLOs with runbooks.

Backup & Disaster Recovery

  • Backup + PITR for data stores, cross-region copies, DR strategy chosen by RPO/RTO, regular drills.

7. Common Mistakes

Beginner mistakes

  • Starting with tools instead of requirements.
  • Drawing boxes with no request flow.

Developer mistakes

  • Ignoring operations and failure handling.
  • Tight coupling through synchronous chains.

DevOps mistakes

  • Over-engineering (Kubernetes for a static site).
  • No cost or security consideration.

Production mistakes

  • Single AZ/NAT/DB.
  • No tested restore or failover.

Security mistakes

  • Public databases, wide-open SGs, shared IAM users.

8. Version / Environment Notes

  • Cloud services, limits and prices change: verify service quotas (for example subnets per VPC, ALB limits) and pricing on the provider's documentation before finalising an LLD.
  • AWS reserves 5 IP addresses per subnet; other clouds reserve a different number.
  • Kubernetes API versions (apps/v1, networking.k8s.io/v1, autoscaling/v2) differ across cluster versions: validate manifests against your cluster (kubectl apply --dry-run=server).
  • Managed offering names differ by cloud (EKS/AKS/GKE, RDS/Cloud SQL/Azure DB).

11. How I Explain This to a Client

30-second explanation

A good design starts from your business needs: how many users, how much downtime you can tolerate, what data must be protected, and your budget. We then propose an architecture, explain every choice, and specify exactly how to build and operate it.

2-minute explanation

We begin by agreeing requirements: expected traffic, availability targets, recovery objectives and compliance needs. From these we create a high-level design showing the main components, how requests flow, how the system scales and how it survives failures. We then produce low-level specifications, such as network ranges, firewall rules, deployment files and alert definitions, so the engineering team can implement it consistently through infrastructure as code. We review the design against failure scenarios, security and cost, and document the trade-offs so decisions are transparent and can be revisited as the business grows.

5-minute deep explanation

I will describe our approach in five steps. Requirements: we quantify availability, performance, data protection and budget, for instance a 99.9 percent SLO with an RPO of five minutes. High-level design: we choose components, for example CDN, load balancer, stateless application tier, managed database with standby, cache and queues, and show request and deployment flows with the reasoning for each choice. Resilience and scale: multi-zone deployment, autoscaling, backups and a disaster recovery strategy matched to your recovery objectives. Low-level design: address plan, security group chaining, Kubernetes manifests with probes, limits and network policies, the CI/CD and GitOps pipeline, and the alert rules and runbooks the on-call team will use. Review: we walk through failure scenarios, security and cost, list risks and alternatives, and record decisions in short architecture decision records. This gives you a design that is understandable, buildable and operable.

13. Mini Project: Design and specify: HA 3-tier web app on AWS with CI/CD and monitoring

Users --> Route 53 --> CloudFront+WAF --> ALB (public subnets, 2 AZ)
        --> EKS/ASG app tier (private subnets) --> RDS Multi-AZ (isolated) + Redis + S3
CI/CD: GitHub > Actions (build, scan, sign) > ECR > ArgoCD > EKS
Observability: Prometheus/Grafana/Loki, alerts > Alertmanager > PagerDuty ; CloudTrail/GuardDuty

Step 1: Requirements (quantified)

Users: 50k daily, peak 500 RPS
Availability SLO: 99.9% (~43 min/month)
RPO 5 min, RTO 30 min
Data: PII (encrypt, audit)
Budget: moderate; team of 6 knows Kubernetes
Assumptions: single region (ap-south-1) with backup copies to a second region

Turning vague goals into numbers drives every later decision. State assumptions explicitly so the interviewer/stakeholder can correct them.

Step 2: HLD flow and choices

1 User > Route 53 (DNS, health-checked)
2 CloudFront + WAF (cache static, block attacks, TLS)
3 ALB in 2 public subnets (L7 routing, health checks)
4 App on EKS (stateless pods, HPA) in private subnets
5 RDS PostgreSQL Multi-AZ (primary + standby) in isolated subnets
6 Redis for cache/sessions; S3 for uploads
7 SQS + workers for async jobs
Why: managed services reduce ops; stateless tier scales horizontally; Multi-AZ meets 99.9%

Each box has a reason. The request flow is numbered so it can be explained in order. State what you did NOT choose and why (for example DynamoDB: relational data and transactions fit PostgreSQL).

Step 3: LLD: network and security

VPC 10.0.0.0/16
public  a/b: 10.0.0.0/24, 10.0.1.0/24     (ALB, NAT)
app     a/b: 10.0.10.0/24, 10.0.11.0/24   (EKS nodes)
db      a/b: 10.0.20.0/24, 10.0.21.0/24   (RDS)
alb-sg : in 443 from 0.0.0.0/0
app-sg : in 8080 from alb-sg
db-sg  : in 5432 from app-sg
NAT gateway per AZ; S3/ECR VPC endpoints; flow logs on

Exact address plan and SG chaining. One NAT per AZ avoids cross-AZ dependency; endpoints reduce NAT cost and keep traffic private. (AWS reserves 5 addresses per subnet.)

Step 4: Failure analysis and trade-offs

AZ-a down       -> ALB stops sending to AZ-a targets; HPA/ASG keep capacity in AZ-b; RDS fails over (~1-2 min)
DB primary fail -> Multi-AZ automatic failover; app retries with backoff
Bad deploy      -> readiness fails, rolling update halts; argocd rollback / git revert
Traffic spike   -> CloudFront cache, HPA + node autoscaling, queue absorbs writes
Region outage   -> restore from cross-region backups (RTO 30 min needs runbook + IaC), upgrade to warm standby if RTO tightens
Trade-offs: EKS gives portability but more ops than ECS; Multi-AZ RDS doubles DB cost; single region accepted for cost

Seniors are judged on this section. Every failure has a detection, an automatic or manual response and a measurable time. Trade-offs are stated honestly with the option to upgrade later.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is HLD?

High-Level Design: the overall architecture showing major components, their relationships, data flow and technology choices.

Why: Basics.

Real-world example: Boxes and arrows of a 3-tier app.

Q2. What is LLD?

Low-Level Design: detailed implementation specs such as network ranges, configuration files, schemas and code structure.

Why: Basics.

Real-world example: Subnet CIDRs and SG rules.

Q3. What are functional vs non-functional requirements?

Functional describe what the system does; non-functional describe qualities: performance, availability, security, cost.

Why: Requirement gathering.

Real-world example: Login vs 99.9% uptime.

Q4. What is a single point of failure?

A component whose failure stops the whole system.

Why: Reliability.

Real-world example: One database instance.

Q5. What is high availability?

Designing so the system stays operational despite component failures, typically through redundancy and failover.

Why: Core goal.

Real-world example: Multi-AZ.

Q6. Why use a load balancer?

Distributes traffic, performs health checks and hides individual server failures.

Why: Basic building block.

Real-world example: ALB in front of app servers.

Q7. What is a CDN?

A network of edge servers caching content close to users.

Why: Performance.

Real-world example: CloudFront.

Q8. What is caching in design?

Storing frequently accessed data in fast storage to cut latency and load.

Why: Performance.

Real-world example: Redis in front of DB.

Q9. What is scalability?

Ability to handle growth by adding resources (vertical or horizontal).

Why: Core goal.

Real-world example: Autoscaling group.

Q10. What is a diagram used for in design?

To communicate components and flows clearly among stakeholders.

Why: Communication.

Real-world example: draw.io/Mermaid.

Intermediate (14)

Q11. Give a framework for answering a design question.

Clarify requirements, state constraints/assumptions, HLD, components with reasons, data flow, scale/HA/DR, security, observability, cost, failure modes, trade-offs.

Why: Interview technique.

Real-world example: See e2e diagram.

Q12. Design a highly available 3-tier web app on AWS.

Route 53, CloudFront/WAF, ALB across 2 AZs, ASG/EKS in private subnets, RDS Multi-AZ, Redis, S3, NAT per AZ, SG chaining, monitoring, backups.

Why: Most common design.

Real-world example: See mini project.

Q13. How do you calculate availability from SLO?

Downtime = (1 - SLO) x period: 99.9% is about 43 minutes per 30 days; 99.99% about 4.3 minutes.

Why: Numbers matter.

Real-world example: Explain nines to business.

Q14. Vertical vs horizontal scaling?

Vertical adds power to one machine (limits, downtime); horizontal adds machines (needs stateless design, gives redundancy).

Why: Scaling choice.

Real-world example: Stateless web tier.

Q15. How do you make an app stateless?

Externalise state: sessions in Redis/DB/JWT, files in S3, config via environment.

Why: Design for scale.

Real-world example: Move uploads to S3.

Q16. How to design security groups for 3 tiers?

ALB SG allows 443 from internet; app SG allows app port only from ALB SG; DB SG allows DB port only from app SG.

Why: Least privilege.

Real-world example: SG referencing SG.

Q17. Sync vs async communication?

Sync gives immediate answers but couples services; async decouples and buffers via queues/events.

Why: Architecture.

Real-world example: Email sending via SQS.

Q18. Design a CI/CD platform.

Git > CI (build/test/scan/sign) > registry > GitOps repo > ArgoCD > Kubernetes with progressive delivery, secrets management, observability and rollback.

Why: DevOps design.

Real-world example: See HLD 2.

Q19. What is RPO/RTO and how does it drive DR design?

RPO limits data loss, RTO limits downtime; tighter targets require warmer, costlier DR (backup/restore < pilot light < warm standby < active-active).

Why: DR.

Real-world example: RPO 5 min needs continuous replication.

Q20. Design an observability platform.

Metrics (Prometheus/Thanos), logs (Loki), traces (Tempo/OTel), Grafana, Alertmanager routing, SLO dashboards, retention and access control, multi-cluster labels.

Why: Ops design.

Real-world example: See HLD 3.

Q21. How do you estimate capacity?

Convert users to peak RPS, measure per-instance throughput via load test, add headroom (30-50%) and redundancy (N+1/N+2), consider data growth.

Why: Sizing.

Real-world example: 500 RPS / 100 RPS per pod = 5 pods + headroom.

Q22. What is an Architecture Decision Record?

A short document capturing a decision, context, options and consequences.

Why: Governance.

Real-world example: Why we chose EKS.

Q23. Where should databases live in a VPC?

Isolated private subnets with no internet route, accessible only from the app tier.

Why: Security.

Real-world example: RDS subnet group.

Q24. Explain multi-AZ vs multi-region.

Multi-AZ protects against data-centre failure within a region (low latency, automatic); multi-region protects against regional failures and adds complexity/cost.

Why: Resilience level.

Real-world example: Most apps start with multi-AZ.

Advanced (13)

Q25. Design multi-region active-active.

Global DNS/anycast routing, stateless services in each region, data replication strategy (multi-master or partitioned ownership), conflict resolution, global session/cache handling, consistent deployments, cost and testing.

Why: Hard design.

Real-world example: DynamoDB global tables.

Q26. How do you handle data consistency across services?

Avoid distributed transactions; use sagas, outbox pattern, idempotency and eventual consistency where acceptable.

Why: Microservices data.

Real-world example: Order/payment saga.

Q27. Explain graceful degradation and load shedding.

When overloaded or dependencies fail, serve reduced functionality or reject low-priority requests to protect core flows.

Why: Resilience.

Real-world example: Disable recommendations.

Q28. Design rate limiting for a public API.

Edge (WAF/CDN) coarse limits plus token-bucket per API key in Redis; return 429 with Retry-After; monitoring and burst allowance.

Why: Protection.

Real-world example: 100 req/min per key.

Q29. How do you design zero-downtime deployments including DB changes?

Progressive delivery, backward-compatible expand/contract migrations, feature flags, readiness probes and automated rollback.

Why: Release engineering.

Real-world example: Add column then backfill then switch.

Q30. Security architecture for a regulated workload.

Multi-account isolation, private networking, KMS encryption, IAM least privilege, audit logging, WAF, vulnerability management, segregation of duties, evidence collection.

Why: Compliance.

Real-world example: PCI DSS segmentation.

Q31. How to choose between ECS, EKS and Lambda?

Lambda for event-driven; ECS for simple containers with less ops; EKS for Kubernetes ecosystem, portability and complex platforms; consider team skills and cost.

Why: Trade-off reasoning.

Real-world example: Team with K8s experience picks EKS.

Q32. Design for cost efficiency.

Right-size, autoscale, commitments for baseline, Spot for stateless, caching/CDN, lifecycle policies, VPC endpoints, tagging and budgets, architecture simplification.

Why: FinOps.

Real-world example: NAT cost reduced by endpoints.

Q33. How do you validate a design?

Failure-mode review, load tests, game days, security review, Well-Architected review, cost estimate, prototype critical paths.

Why: Verification.

Real-world example: Chaos test AZ loss.

Q34. What are the main bottlenecks in a typical web architecture?

Database (connections, queries), single-threaded/stateful components, network egress (NAT), synchronous dependencies, cache stampedes.

Why: Performance analysis.

Real-world example: Pooling and read replicas.

Q35. Explain how to design multi-tenant SaaS.

Tenant isolation model (silo/pool/bridge), tenant-aware auth and data partitioning, noisy-neighbour controls, per-tenant metrics and cost allocation.

Why: SaaS architecture.

Real-world example: Row-level security per tenant.

Q36. Design a GitOps-based platform for 50 microservices.

Config repos per environment, ApplicationSets, shared pipeline templates, policy as code, secrets via external secrets, progressive delivery, per-team namespaces/RBAC and cost tags.

Why: Platform design.

Real-world example: Golden path templates.

Q37. How would you design logging at scale?

Structured logs, agents to Kafka/Loki, retention tiers, sampling, PII redaction, access control, cost budgets, correlation IDs.

Why: Observability at scale.

Real-world example: Hot 7 days, cold 90 days.

Scenario-Based (14)

Q38. Design a URL shortener's infrastructure.

Read-heavy: CDN/cache (Redis), stateless API behind ALB, key-value store (DynamoDB) for mappings, ID generation service, analytics via async queue, rate limiting, multi-AZ.

Why: Classic design.

Real-world example: 99.99% redirect availability.

Troubleshooting-Based (10)

Q52. Users report intermittent 502s after a scale-out.

New instances failing health checks or registered before ready; check readiness/warm-up, ALB target health, deregistration delay, app startup time.

Why: Design edge case.

Real-world example: Slow start on ALB.

Q53. Database CPU high after launching a feature.

New queries without indexes/N+1, missing cache, connection storms; use slow query log, add indexes/caching, pooling.

Why: Capacity design.

Real-world example: Missing index on new column.

Q54. Costs spiked after multi-AZ rollout.

Cross-AZ data transfer and extra NAT/replicas; review traffic patterns, use AZ-aware routing/endpoints.

Why: Cost design.

Real-world example: Chatty services across AZs.

Q55. Failover test took 20 minutes instead of 5.

Manual steps, DNS TTL, cold standby, unverified runbook; automate promotion, lower TTL, warm capacity, rehearse.

Why: DR validation.

Real-world example: Route 53 TTL 3600.

Q56. Private subnet instances cannot pull images from ECR.

No NAT route or VPC endpoints for ECR/S3, SG blocks, missing IAM permission; add endpoints or NAT.

Why: LLD detail.

Real-world example: ecr.api, ecr.dkr and S3 endpoints.

Q57. Kubernetes pods cannot reach RDS.

SG for RDS does not allow node/pod SG, subnet/route, DNS, credentials; fix SG referencing and network policies.

Why: Network design.

Real-world example: SG for pods.

Q58. Pipeline deploys but ArgoCD does not sync.

Repo/credentials, path/branch mismatch, app project restrictions, webhook/refresh interval; check app events and diff.

Why: GitOps design.

Real-world example: Wrong targetRevision.

Q59. Alerts fire but on-call cannot act.

No runbook/dashboard link, unclear ownership, non-actionable thresholds; redesign alerts with symptom focus and runbooks.

Why: Operational design.

Real-world example: Add runbook annotation.

Q60. Autoscaling oscillates (flapping).

Thresholds too tight, short cooldown/stabilisation window, metric lag; tune target, cooldowns, use step scaling.

Why: Scaling design.

Real-world example: HPA stabilisation window.

Q61. Disaster recovery plan exists but nobody knows it.

No drills/ownership; schedule game days, keep runbooks in Git, assign owners, measure actual RTO/RPO.

Why: Process.

Real-world example: Quarterly DR test.
