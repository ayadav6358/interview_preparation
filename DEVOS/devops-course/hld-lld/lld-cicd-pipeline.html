LLD 2: CI Pipeline, Dockerfile & Deploy Config

Intermediate HLD & LLD (Design + Diagrams + Real Examples)

Concept (What & Why)

Exact GitHub Actions workflow, Dockerfile aur GitOps tag update ka implementation.

Definition Deep-Dive

QuestionAnswer
Simple definitionThe actual workflow, Dockerfile and deploy configuration that implement the delivery design.
Technical definitionA concrete GitHub Actions workflow with cache, test, scan, build/push by SHA, sign, and a step that updates the GitOps repository; Dockerfile multi-stage non-root; ArgoCD Application per environment.
Why does it exist?Turns HLD into working automation.
What happens without it?Ideas without implementation.
When to useEvery service.
When NOT to useCopy-pasting without understanding.
Real-world analogyThe detailed wiring diagram after the electrical plan.

Diagram & Internal Working

push main -> checkout -> test -> trivy fs -> OIDC assume role -> buildx -> trivy image -> push ECR(sha)
          -> yq set image.tag in gitops repo -> git push (bot) -> ArgoCD syncs

How it works internally (diagram explained)

On merge, the workflow authenticates to the registry via OIDC, builds the image with cache, scans with Trivy (fail on HIGH/CRITICAL), pushes :sha, signs with cosign, then clones the GitOps repo, updates values.yaml image.tag, and pushes. ArgoCD detects the commit and syncs.

Install / Setup

# secrets: none for AWS (OIDC). GITOPS_TOKEN fine-grained PAT or GitHub App for config repo

Configuration Explained Line by Line

Workflow explained

name: release
on: { push: { branches: [main] } }
permissions: { id-token: write, contents: read }
jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::123456789012:role/gha-ecr, aws-region: ap-south-1 }
      - uses: aws-actions/amazon-ecr-login@v2
      - run: docker build -t $ECR/app:${{ github.sha }} .
      - run: trivy image --exit-code 1 --severity HIGH,CRITICAL $ECR/app:${{ github.sha }}
      - run: docker push $ECR/app:${{ github.sha }}
      - run: cosign sign --yes $ECR/app:${{ github.sha }}
LineMeaning / WHY it exists
id-token: writeOIDC federation, no static AWS keys.
ecr-loginShort-lived registry token.
tag = github.shaImmutable, traceable version.
trivy exit-code 1Blocks vulnerable images before push.
cosign signSignature verified later at admission. Set ECR env to your registry URI and check current action versions.

Practical Examples

Workflow

name: ci
on: { push: { branches: [main] }, pull_request: }
permissions: { id-token: write, contents: read }
env: { REGION: ap-south-1, REPO: myapp }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test
      - uses: aquasecurity/trivy-action@master
        with: { scan-type: fs, severity: 'HIGH,CRITICAL', exit-code: '1' }
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: "arn:aws:iam::123456789012:role/gha-ecr", aws-region: "${{ env.REGION }}" }
      - id: ecr
        uses: aws-actions/amazon-ecr-login@v2
      - name: Build, scan, push
        run: |
          IMG=${{ steps.ecr.outputs.registry }}/$REPO:${{ github.sha }}
          docker build -t $IMG .
          trivy image --exit-code 1 --severity CRITICAL $IMG
          [ "${{ github.ref }}" = "refs/heads/main" ] && docker push $IMG || true
  deploy-config:
    if: github.ref == 'refs/heads/main'
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { repository: acme/gitops, token: "${{ secrets.GITOPS_TOKEN }}" }
      - run: |
          yq -i '.image.tag = "${{ github.sha }}"' charts/myapp/values-dev.yaml
          git config user.name bot && git config user.email bot@acme.io
          git commit -am "myapp: ${{ github.sha }}" && git push

IAM trust policy for OIDC

{
 "Effect":"Allow","Principal":{"Federated":"arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"},
 "Action":"sts:AssumeRoleWithWebIdentity",
 "Condition":{"StringLike":{"token.actions.githubusercontent.com:sub":"repo:acme/myapp:ref:refs/heads/main"}}
}

Real-World Problems & Fixes (Troubleshooting)

Problem: Pipeline can assume role from any repo/branch
Cause: Trust policy too broad
Fix: Restrict sub claim to repo and branch/environment.

Interview Questions

Q1. Why tag with git sha?

Immutable, traceable to code.

Q2. Why OIDC?

No long-lived secrets, short-lived credentials, scoped by repo/branch.

Q3. How to speed up builds?

Layer caching (buildx gha cache), dependency caching, parallel jobs.

Q4. How to prevent deploying unscanned image?

Gate build on scan; admission controller verifying signatures.

Q5. Where is approval enforced?

GitHub Environment protection for prod or PR approval on config repo.

Q6. Why tag images with the commit SHA?

It is immutable and links a running container to exact source; latest is mutable and hides what is deployed.

Why: Traceability.
