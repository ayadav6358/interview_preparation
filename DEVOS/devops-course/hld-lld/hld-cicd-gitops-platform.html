HLD 2: End-to-End CI/CD + GitOps Platform

Advanced HLD & LLD (Design + Diagrams + Real Examples)

Concept (What & Why)

Developer push se production tak. Build once, scan, sign, deploy via GitOps, observe and rollback.

Definition Deep-Dive

QuestionAnswer
Simple definitionAn end-to-end delivery platform from code push to production, with security and rollback built in.
Technical definitionGit-based CI builds, tests, scans, signs and publishes immutable images; a GitOps repository holds environment state; ArgoCD reconciles clusters; progressive delivery and observability provide safe rollouts and rollback.
Why does it exist?Fast, safe, auditable releases across many teams.
What happens without it?Manual, inconsistent deployments.
When to useOrganisations with multiple services.
When NOT to useExcess complexity for one small app.
Real-world analogyAn automated factory line with inspection stations and a return chute.

Diagram & Internal Working

Dev -> GitHub (PR, checks, CODEOWNERS)
        |
   GitHub Actions (OIDC)  ── test -> SAST -> build image -> Trivy -> cosign -> push ECR
        |
   update image tag in GitOps repo (PR/auto-commit)
        |
   ArgoCD (per cluster) ── sync ──> EKS dev -> staging -> prod (canary via Argo Rollouts)
        |
   Prometheus/Grafana/Loki ── SLO alerts ── PagerDuty ; auto-rollback on failed analysis
Infra: Terraform (VPC, EKS, IAM, ECR) via separate pipeline + policy checks (Checkov/OPA)
Secrets: Vault/Secrets Manager + External Secrets

How it works internally (diagram explained)

Developer opens a PR > CI runs unit tests, SAST/SCA/secrets > merge to main > CI builds image tagged with SHA, scans, signs, pushes to registry > CI updates the image tag in the GitOps repo (PR or commit) > ArgoCD detects the change, syncs to staging > smoke tests and analysis > promotion to production (approval) > progressive rollout monitored by metrics > auto rollback via Argo Rollouts or git revert.

Real-World Example

Dev > GitHub PR > Actions (test, scan, build, sign) > ECR
   > GitOps repo (tag bump) > ArgoCD > EKS staging > tests > approval > EKS prod (canary)
   Prometheus analysis -> promote or rollback ; Slack notifications

Twenty microservices share a pipeline template. Developers only push code; the platform handles images, environment promotion and rollbacks. Auditors can trace every production change to a reviewed commit and a signed image.

Practical Examples

Key decisions

GitOps pull model: cluster creds never leave cluster
Separate app repo and config repo: clean audit trail, different permissions
Immutable tags (git sha) + image digest pinning
Progressive delivery with automated metric analysis
Promotion via PR between env folders

Failure modes

Bad image -> caught by scan gate | Bad config -> canary aborts, ArgoCD rollback
ArgoCD down -> running workloads unaffected, deployments pause | GitHub down -> hotfix via break-glass procedure

Real-World Problems & Fixes (Troubleshooting)

Problem: Prod and Git state diverge
Cause: Manual kubectl edits
Fix: selfHeal on, restrict kubectl write RBAC, all changes via PR.
Problem: Pipeline is single point of failure
Cause: Only one runner/instance
Fix: HA runners, autoscaled ephemeral runners, documented break-glass path.

Best Practices

Security

  • Signed images, admission verification, OIDC, least privilege.

Reliability

  • Progressive delivery with automated analysis.

Common Mistakes

DevOps mistakes

  • Rebuilding per environment.
  • CI with cluster-admin.

Hinglish Explanation

Image ek baar build, Git se promote, ArgoCD se deploy, metrics se verify, aur rollback = git revert. CI ko cluster credentials mat do.

Interview Questions

Q1. Why separate config repo?

Different lifecycle/permissions, clean deploy history, avoids CI loops.

Q2. How to promote dev->prod?

PR changing tag/values in prod overlay with approval, or automated promotion after checks.

Q3. How do you ensure only trusted images run?

cosign signatures + admission policy (Kyverno/Sigstore policy-controller).

Q4. How to rollback?

Revert Git commit or Argo Rollouts abort; ArgoCD syncs previous state.

Q5. How to secure the pipeline?

OIDC, least-privilege, pinned actions, isolated runners, scan everything, protected branches.

Q6. How do you promote from staging to prod safely?

Promote the same image digest by changing the tag/digest in the prod GitOps overlay via PR with approval, after tests and policy checks; roll out progressively and monitor SLOs.

Why: Release governance.

Real-world example: Prod overlay PR requires two reviewers.
