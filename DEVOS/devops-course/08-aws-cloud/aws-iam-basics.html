AWS Basics, Account Setup & IAM

Basic Cloud (AWS)

Concept (What & Why)

Region = geographic area, AZ = isolated data center in region. IAM decides WHO can do WHAT. Root account use mat karo, MFA lagao.

Definition Deep-Dive

QuestionAnswer
Simple definitionIAM decides who can do what in your AWS account.
Technical definitionIAM evaluates requests against identity-based policies, resource-based policies, permission boundaries, session policies and Organizations SCPs; explicit deny overrides allow; default is deny.
Why does it exist?Control access and provide temporary credentials.
What happens without it?Everyone shares root-level access.
When to useAlways.
When NOT to useUsing the root user or long-lived access keys.
Real-world analogyBuilding security badges with access levels.

Diagram & Internal Working

AWS Account
 ├── Region (ap-south-1)
 │    ├── AZ a | AZ b | AZ c
 └── IAM: User/Group/Role + Policy (JSON) -> allow/deny actions on resources
Role = temporary credentials for services (EC2, Lambda) or cross-account

How it works internally (diagram explained)

A request (principal + action + resource + context) reaches IAM. IAM gathers applicable policies and evaluates: explicit deny? SCP/boundary allow? identity or resource policy allow? If allowed, the action proceeds and CloudTrail logs it. Roles issue temporary credentials through STS AssumeRole.

Install / Setup

# AWS CLI v2
winget install Amazon.AWSCLI   # or: curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o a.zip && unzip a.zip && sudo ./aws/install
aws configure sso     # preferred over static keys
aws sts get-caller-identity

Configuration Explained Line by Line

Least-privilege policy explained

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::my-app-bucket/reports/*",
    "Condition": {"IpAddress": {"aws:SourceIp": "203.0.113.0/24"}}
  }]
}
LineMeaning / WHY it exists
Effect: AllowGrants; without an allow the request is denied.
ActionOnly read objects: no put/delete.
Resource ARNLimited to the reports/ prefix.
ConditionAdditional guard by source IP; can also require MFA or tags.

First-day security checklist

1 Enable MFA on root; don't create root access keys
2 Create admin IAM Identity Center user; use SSO
3 Budget alert at $5/$10 (Billing -> Budgets)
4 Enable CloudTrail; set region restrictions via SCP later

Hands-On Lab

Lab Goal

Secure a new account and use a role.

Prerequisites

  • AWS account
  • AWS CLI v2

Step 1

Enable MFA on the root user and create an admin via IAM Identity Center (or an IAM user with MFA) for daily use

Root is used only for account-level tasks.

Step 2

aws configure sso && aws sts get-caller-identity

Uses short-lived SSO credentials; the output shows the assumed role ARN.

Step 3

Create a budget with alerts (Billing > Budgets)

Protects against surprise costs.

Real-World Problems & Fixes (Troubleshooting)

Problem: Huge unexpected AWS bill
Cause: Forgotten EC2/NAT/EBS/ELB, or leaked keys mining crypto
Fix: Budgets + alerts, Cost Explorer, tag everything, delete unused; rotate/revoke leaked keys.
Problem: AccessDenied though policy looks right
Cause: Explicit deny, SCP, permission boundary, or resource policy
Fix: Use IAM Policy Simulator and CloudTrail event to see denying policy.

Best Practices

Security

  • MFA, SSO, least privilege, no wildcards, rotate/eliminate keys, review with Access Analyzer.

Interview Questions

Q1. IAM user vs role?

User has long-term credentials; role is assumed for temporary credentials (preferred for services).

Q2. What is the shared responsibility model?

AWS secures the cloud; you secure what you put in it.

Q3. Policy evaluation logic?

Default deny; explicit deny always wins; else needs an allow.

Q4. What is STS?

Service issuing temporary credentials (AssumeRole).

Q5. Region vs AZ?

Region = independent geography; AZ = isolated datacenters within it; deploy across AZs for HA.

Q6. How does cross-account access work?

Account B role trusts Account A principal; A's identity policy allows sts:AssumeRole; A assumes the role and gets temporary credentials.

Why: IAM depth.

Real-world example: Central security account auditing others.
