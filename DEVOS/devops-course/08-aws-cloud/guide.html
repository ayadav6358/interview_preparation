Cloud (AWS): Deep Guide

Big picture, tools, troubleshooting, best practices, client talk, roadmap, mini project, interview prep and cheat sheet.

1. The Big Picture: What Problem Does This Solve?

Problem it solves: Buying, racking and maintaining servers takes weeks and large upfront cost, and you must provision for peak load. Cloud (AWS = Amazon Web Services) gives you computing, storage, databases and networking on demand, paid per use, in minutes, across many data centres.

PROBLEM: need infrastructure quickly, at variable scale, with high availability
      |
      v
TRADITIONAL APPROACH: buy hardware, own data centre, plan capacity for years
      |
      v
PAIN: slow, expensive, over/under-provisioned, single site failure
      |
      v
TECHNOLOGY: AWS (regions, availability zones, managed services)
      |
      v
SOLUTION: on-demand resources, pay-as-you-go, managed HA services, APIs for automation
      |
      v
REAL-WORLD BENEFIT: faster delivery, elasticity, resilience, lower ops burden

Key building blocks: Region (geographic area) > Availability Zone (AZ) (isolated data centre group) > services. Security follows the shared responsibility model: AWS secures the cloud itself; you secure what you put in it (IAM, data, OS patches on EC2, security groups).

2. End-to-End Flow

User
  v
Route 53 (DNS)
  v
CloudFront (CDN) + WAF
  v
Application Load Balancer (public subnets, 2+ AZs)
  v
EC2 Auto Scaling group / ECS / EKS (private app subnets)
  v
RDS Multi-AZ + ElastiCache (private DB subnets)   S3 (static/files)
  v
CloudWatch (metrics/logs/alarms) + CloudTrail (audit) + IAM (access)
  v
Cost: Budgets / Cost Explorer / tags

DNS in Route 53 points users to CloudFront, which caches content and passes requests through WAF. The ALB sits in public subnets across at least two AZs and forwards requests to application servers (EC2 Auto Scaling, ECS or EKS) in private subnets. The app uses RDS (managed database with Multi-AZ failover) in isolated subnets, ElastiCache for caching and S3 for objects. Every access is governed by IAM roles. CloudWatch collects metrics and logs and triggers alarms; CloudTrail records API activity for audit; Budgets and tags control cost.

5. Troubleshooting Playbook

Problem: EC2 instance not reachable via SSH
Possible cause: Security group, NACL, route/IGW, key pair, public IP, instance state/status checks
How to check: EC2 console status checks, SG inbound rule 22, route table has IGW, ssh -vvv
Fix: Fix SG/route/key; use SSM Session Manager as alternative.
Prevention: Use SSM; avoid public SSH.
Problem: AccessDenied / UnauthorizedOperation
Possible cause: IAM policy, SCP, permission boundary or resource policy
How to check: Error message names action; CloudTrail; IAM policy simulator
Fix: Add least-privilege action; check explicit denies/SCP.
Prevention: Use least privilege with tests.
Problem: Private instance has no internet
Possible cause: Missing route to NAT gateway, NAT in wrong subnet, SG/NACL egress
How to check: Route table of the private subnet, NAT status
Fix: Add 0.0.0.0/0 to NAT; ensure NAT is in a public subnet with EIP.
Prevention: IaC modules for standard VPC.
Problem: Unexpected AWS bill
Possible cause: Idle resources, NAT/data transfer, unattached EBS, forgotten instances
How to check: Cost Explorer by service/tag, Budgets
Fix: Delete/stop unused resources, VPC endpoints, rightsizing.
Prevention: Budgets, alerts, tagging, automation.
Problem: ALB targets unhealthy
Possible cause: Health check path/port mismatch, SG blocks ALB, app down
How to check: Target group health reason, SG rules, curl app locally
Fix: Fix path/port; allow ALB SG to app SG.
Prevention: Match health check to a lightweight endpoint.
Problem: RDS connection timeout
Possible cause: SG missing, not in same VPC/subnet route, public accessibility, max connections
How to check: SG inbound 5432/3306, nc -zv endpoint port, RDS events
Fix: Allow app SG to DB SG; check subnet group.
Prevention: Chain SGs (app SG to DB SG).

6. Production Best Practices

Development

  • Use separate accounts/environments; IaC (Terraform) instead of console; use free tier carefully with budget alerts.

Production

  • Multi-AZ everywhere; Auto Scaling; managed services; backups; tagging standards; separate AWS accounts (AWS Organizations).

Security

  • Enable MFA; never use root; least-privilege IAM roles; no long-lived keys; encrypt at rest (KMS) and in transit; private subnets for data; CloudTrail, GuardDuty, Security Hub; S3 Block Public Access.

Performance

  • Right-size instances; CloudFront; caching (ElastiCache); read replicas; gp3 volumes.

Reliability

  • Multi-AZ, health checks, automated failover, backups tested, defined RPO/RTO.

Cost Optimization

  • Budgets and alarms; Savings Plans/Reserved for baseline; Spot for batch; delete unused EBS/EIPs/snapshots; S3 lifecycle; VPC endpoints to cut NAT costs; schedule dev environments.

Monitoring & Logging

  • CloudWatch metrics/alarms/log groups; ALB and VPC flow logs; CloudTrail to S3.

Backup & Disaster Recovery

  • RDS automated backups + snapshots, S3 versioning and cross-region replication, AWS Backup; pilot light/warm standby/multi-site DR by RPO/RTO.

7. Common Mistakes

Beginner mistakes

  • Using the root account daily.
  • Leaving resources running.
  • Public S3 buckets.

Developer mistakes

  • Access keys in code/Git.
  • Hard-coded region/account IDs.

DevOps mistakes

  • Manual console changes (drift).
  • Overly broad *:* IAM policies.
  • Single AZ deployments.

Production mistakes

  • No backup restore test.
  • No cost alerts.
  • Database publicly accessible.

Security mistakes

  • Security group 0.0.0.0/0 on SSH/DB.
  • No MFA.
  • Unencrypted data.

8. Version / Environment Notes

  • AWS services and console UI change often; confirm limits, prices and regions in the official documentation and pricing pages.
  • AWS CLI v2 is current (v1 is legacy). Use SSO (aws configure sso) over static keys.
  • Amazon Linux 2 is being replaced by Amazon Linux 2023 (dnf-based); check end-of-support dates.
  • IMDSv2 should be required on EC2 (HttpTokens=required) to reduce SSRF risk.
  • Azure/GCP have equivalent concepts with different names (VPC=VNet, IAM roles=Managed identities/Service accounts).

11. How I Explain This to a Client

30-second explanation

AWS lets us run your applications on demand in secure, highly available data centres and pay only for what we use. We can scale quickly, recover from failures automatically and avoid buying hardware.

2-minute explanation

Instead of buying servers, we use AWS to build your environment as code in minutes. Your application runs in a private network across multiple availability zones, so a data centre failure does not stop the service. Access is controlled with IAM roles and MFA, data is encrypted, and all activity is logged. We use managed services like RDS for databases and S3 for storage to reduce maintenance, Auto Scaling to handle traffic peaks, and budgets, tagging and rightsizing to keep costs under control. You get faster delivery, better resilience and a clear view of cost.

5-minute deep explanation

I will explain in five layers. Foundation: an AWS Organization with separate accounts for production and non-production, SSO with MFA and centralised logging. Network: a VPC across at least two availability zones with public subnets for load balancers, private subnets for applications and isolated subnets for databases, controlled with security groups. Compute and data: Auto Scaling EC2 or containers on ECS/EKS, RDS with Multi-AZ, S3 for objects, ElastiCache for performance. Security and compliance: least-privilege IAM roles, KMS encryption, CloudTrail, GuardDuty, WAF and patching. Operations and cost: everything defined in Terraform, CloudWatch dashboards and alarms, backups with tested restores, and Savings Plans, Spot and lifecycle policies to lower cost. This design targets high availability, security and predictable spend.

13. Mini Project: Highly available web app on EC2 with ALB, Auto Scaling and RDS

Internet --> ALB (public subnets, AZ-a/AZ-b) --> Auto Scaling group (private app subnets)
                                                      --> RDS Multi-AZ (private DB subnets)
S3 for static files ; CloudWatch alarms ; NAT for outbound ; SSM for admin access

Step 1: Network plan

VPC 10.0.0.0/16
public-a 10.0.0.0/24   public-b 10.0.1.0/24     (ALB, NAT)
app-a    10.0.10.0/24  app-b    10.0.11.0/24    (EC2)
db-a     10.0.20.0/24  db-b     10.0.21.0/24    (RDS)

Two AZs and three tiers. Only the ALB is internet facing.

Step 2: Security groups (chain)

alb-sg : inbound 80/443 from 0.0.0.0/0
app-sg : inbound 8080 from alb-sg
db-sg  : inbound 5432 from app-sg

Referencing security groups instead of IPs means each tier only accepts traffic from the tier in front of it.

Step 3: Launch template + ASG via CLI (illustrative)

aws ec2 create-launch-template --launch-template-name web-lt \
  --launch-template-data '{"ImageId":"ami-xxxx","InstanceType":"t3.micro","SecurityGroupIds":["sg-app"],"IamInstanceProfile":{"Name":"web-profile"},"MetadataOptions":{"HttpTokens":"required"}}'
aws autoscaling create-auto-scaling-group --auto-scaling-group-name web-asg \
  --launch-template LaunchTemplateName=web-lt,Version='$Latest' \
  --min-size 2 --max-size 6 --desired-capacity 2 \
  --vpc-zone-identifier "subnet-app-a,subnet-app-b" --target-group-arns arn:aws:elasticloadbalancing:...

AMI IDs, subnets and ARNs are placeholders you must replace. HttpTokens=required enforces IMDSv2. In real projects define all of this in Terraform.

Step 4: Verify and monitor

aws elbv2 describe-target-health --target-group-arn <arn>
curl -I http://<alb-dns-name>
aws cloudwatch put-metric-alarm --alarm-name web-cpu-high --metric-name CPUUtilization --namespace AWS/EC2 \
  --statistic Average --period 300 --threshold 70 --comparison-operator GreaterThanThreshold --evaluation-periods 2 \
  --dimensions Name=AutoScalingGroupName,Value=web-asg --alarm-actions <sns-topic-arn>

Check targets are healthy, call the ALB, and create a CPU alarm that notifies an SNS topic. Remember to delete resources afterward to avoid charges.

14. Interview Preparation (Question, Answer, Why, Real-world example)

Beginner (10)

Q1. What is cloud computing?

On-demand delivery of IT resources over the internet with pay-as-you-go pricing.

Why: Foundation.

Real-world example: Launch a server in minutes.

Q2. Region vs Availability Zone?

Region is a geographic area; AZ is an isolated data centre location within it.

Why: HA basics.

Real-world example: ap-south-1a and 1b.

Q3. What is EC2?

Virtual servers in the cloud.

Why: Core compute.

Real-world example: t3.micro web server.

Q4. What is S3?

Object storage with high durability, used for files, backups and static sites.

Why: Core storage.

Real-world example: Store images and logs.

Q5. What is IAM?

Service to manage identities and permissions.

Why: Security base.

Real-world example: Roles for EC2.

Q6. What is a VPC?

Your isolated virtual network in AWS.

Why: Networking.

Real-world example: 10.0.0.0/16.

Q7. What is the shared responsibility model?

AWS secures the infrastructure; customer secures configuration, data, identities and guest OS.

Why: Security basics.

Real-world example: You patch EC2; AWS patches RDS engine hardware.

Q8. What is an AMI?

Machine image template used to launch EC2 instances.

Why: Provisioning.

Real-world example: Golden AMI.

Q9. What is a security group?

Stateful virtual firewall for instances.

Why: Access control.

Real-world example: Allow 443 only.

Q10. What is CloudWatch?

Monitoring service for metrics, logs and alarms.

Why: Operations.

Real-world example: CPU alarm.

Intermediate (15)

Q11. Explain public vs private subnet.

Public subnet route table has a route to an Internet Gateway; private subnets do not and use NAT for outbound.

Why: VPC design.

Real-world example: DB in private.

Q12. What is NAT Gateway?

Managed service allowing private subnets outbound internet without inbound exposure; in a public subnet with an Elastic IP.

Why: Connectivity and cost.

Real-world example: OS updates from private EC2.

Q13. IAM role vs user?

Users have long-term credentials; roles provide temporary credentials assumed by services/people.

Why: Best practice: roles.

Real-world example: Lambda execution role.

Q14. Explain S3 storage classes and lifecycle.

Standard, Standard-IA, One Zone-IA, Glacier tiers; lifecycle rules transition/expire objects to reduce cost.

Why: Cost.

Real-world example: Move logs to Glacier after 90 days.

Q15. EBS volume types?

gp3/gp2 general SSD, io1/io2 provisioned IOPS, st1/sc1 HDD throughput/cold.

Why: Storage design.

Real-world example: gp3 for most workloads.

Q16. How does Auto Scaling work?

Launch template + ASG with min/max/desired and scaling policies on metrics; replaces unhealthy instances across AZs.

Why: Elasticity.

Real-world example: Target tracking 50% CPU.

Q17. ALB vs NLB vs CLB?

ALB L7, NLB L4, CLB legacy.

Why: Load balancing.

Real-world example: ALB for web apps.

Q18. RDS Multi-AZ vs read replicas?

Multi-AZ = availability/failover; read replica = read scaling.

Why: Database design.

Real-world example: Read replica for reporting.

Q19. What is Route 53 routing policies?

Simple, weighted, latency, failover, geolocation, multi-value.

Why: DNS.

Real-world example: Failover to DR region.

Q20. What is CloudTrail?

Records AWS API calls for audit and security analysis.

Why: Governance.

Real-world example: Who deleted the bucket?

Q21. Explain SNS vs SQS.

SNS is pub/sub push; SQS is a queue (pull) for decoupling; combine for fan-out.

Why: Messaging.

Real-world example: S3 event to SNS to multiple SQS.

Q22. What is an Elastic IP?

Static public IPv4 address you can remap between instances; chargeable when idle.

Why: Networking/cost.

Real-world example: NAT gateway EIP.

Q23. What is Infrastructure as Code on AWS?

Define resources in CloudFormation/Terraform for repeatable, versioned deployments.

Why: Automation.

Real-world example: terraform apply.

Q24. How do you connect on-premises to AWS?

Site-to-Site VPN or Direct Connect (plus Transit Gateway).

Why: Hybrid.

Real-world example: VPN as quick start.

Q25. What is AWS Organizations and SCP?

Multi-account management; SCPs set maximum permission guardrails.

Why: Governance.

Real-world example: Deny leaving regions.

Advanced (14)

Q26. Explain IAM policy evaluation logic.

Default deny; explicit deny always wins; an allow is needed from identity policy (and resource policy where applicable) and must not be blocked by SCP/boundary/session policy.

Why: Security depth.

Real-world example: SCP denies overrides admin allow.

Q27. Design a highly available 3-tier app.

ALB across 2-3 AZs, ASG in private subnets, RDS Multi-AZ, ElastiCache, S3/CloudFront, SG chaining, NAT per AZ, Route 53, monitoring and backups.

Why: Architecture.

Real-world example: See mini project.

Q28. DR strategies and RPO/RTO?

Backup & restore (hours), pilot light, warm standby, multi-site active-active; choose by RPO/RTO and cost.

Why: Resilience.

Real-world example: Cross-region RDS replica.

Q29. VPC peering vs Transit Gateway vs PrivateLink?

Peering is 1:1 non-transitive; TGW is a hub for many VPCs/VPNs; PrivateLink exposes a service privately without full network connectivity.

Why: Networking design.

Real-world example: Shared services VPC via TGW.

Q30. S3 security best practices.

Block Public Access, bucket policies with least privilege, encryption (SSE-KMS), versioning, MFA delete, access logs, VPC endpoints.

Why: Data protection.

Real-world example: Prevent public bucket leaks.

Q31. How would you reduce NAT gateway costs?

Gateway VPC endpoints for S3/DynamoDB, interface endpoints for other services, consolidate egress carefully, cache/proxy.

Why: FinOps.

Real-world example: S3 traffic via endpoint.

Q32. ECS vs EKS vs Lambda selection?

Lambda for event-driven short tasks; ECS/Fargate for simple containers; EKS for Kubernetes portability/ecosystem.

Why: Compute choice.

Real-world example: Team already runs Kubernetes: EKS.

Q33. How do IAM roles for service accounts (IRSA) work?

EKS OIDC provider lets a Kubernetes ServiceAccount assume an IAM role via web identity tokens, giving pods least-privilege AWS access.

Why: EKS security.

Real-world example: Pod reads only one S3 bucket.

Q34. Explain DynamoDB partition key design.

Choose high-cardinality keys to spread load; avoid hot partitions; use GSIs for alternate access patterns.

Why: NoSQL design.

Real-world example: userId as partition key.

Q35. How does KMS envelope encryption work?

A data key encrypts data; KMS master key encrypts the data key; only the encrypted data key is stored.

Why: Encryption.

Real-world example: S3 SSE-KMS.

Q36. Well-Architected Framework?

Six pillars: operational excellence, security, reliability, performance efficiency, cost optimization, sustainability.

Why: Design review.

Real-world example: Review before go-live.

Q37. What is eventual consistency in DynamoDB/S3 context?

Reads may briefly see stale data; S3 now provides strong read-after-write consistency, DynamoDB offers strongly consistent read option.

Why: Data semantics.

Real-world example: ConsistentRead=true.

Q38. Multi-account strategy?

Separate accounts for prod, non-prod, security, logging, shared services; Organizations, SCPs, centralised identity.

Why: Enterprise setup.

Real-world example: Control Tower landing zone.

Q39. How to secure EC2 metadata?

Require IMDSv2, least-privilege instance roles, restrict SSRF vectors.

Why: Cloud security.

Real-world example: Prevent credential theft.

Scenario-Based (15)

Q40. Website went down in one AZ.

Multi-AZ design keeps serving; check ALB target health, ASG replaces, RDS fails over; investigate AZ event.

Why: HA in practice.

Real-world example: RDS failover in ~1-2 minutes.

Q41. AWS bill doubled this month.

Cost Explorer by service/account/tag, find NAT/data transfer/EC2/Snapshots, remove idle, set budgets and anomaly detection.

Why: FinOps.

Real-world example: Forgotten GPU instance.

Q42. Developers need temporary production access.

IAM Identity Center with time-limited permission sets, approval, session logging, no shared keys.

Why: Access governance.

Real-world example: Break-glass role.

Q43. S3 bucket was made public accidentally.

Enable Block Public Access at account level, review policies/ACLs, check access logs, rotate exposed data, add AWS Config rule.

Why: Incident response.

Real-world example: Config rule s3-bucket-public-read-prohibited.

Q44. Need to migrate a database with minimal downtime.

AWS DMS with continuous replication, cut over, validate, rollback plan.

Why: Migration.

Real-world example: On-prem MySQL to RDS.
