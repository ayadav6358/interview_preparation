Lambda, ECS/EKS, CloudWatch & Cost

Advanced Cloud (AWS)

Concept (What & Why)

Serverless (Lambda), containers (ECS Fargate/EKS), monitoring (CloudWatch/CloudTrail), aur cost optimization (FinOps).

Definition Deep-Dive

QuestionAnswer
Simple definitionLambda runs code without servers; ECS/EKS run containers; CloudWatch watches everything; cost tools control spending.
Technical definitionLambda executes functions per event with managed scaling; ECS/EKS orchestrate containers (EC2 or Fargate); CloudWatch provides metrics, logs, alarms and dashboards; Cost Explorer/Budgets track spend.
Why does it exist?Reduce operations and control cost.
What happens without it?Idle servers and blind operations.
When to useEvent-driven tasks (Lambda), container workloads (ECS/EKS).
When NOT to useLambda for long-running (>15 min) or steady heavy compute.
Real-world analogyLambda is a taxi you pay per ride; EC2 is a car you own.

Diagram & Internal Working

API Gateway -> Lambda -> DynamoDB          (serverless)
S3 event -> Lambda -> process -> SNS/SQS
ECS Fargate: task definition -> service -> ALB (no servers to manage)
CloudWatch: metrics + logs + alarms -> SNS -> Slack/PagerDuty

How it works internally (diagram explained)

An event (S3 upload, API Gateway request, schedule) invokes Lambda; AWS starts an execution environment (cold start) if none is warm, runs your handler with the function's IAM role, and logs to CloudWatch Logs. CloudWatch alarms evaluate metrics and trigger SNS/Auto Scaling actions.

pip install aws-sam-cli   # local Lambda dev

Configuration Explained Line by Line

Lambda handler explained

import json, os

def handler(event, context):
    name = event.get("name", "world")
    print(json.dumps({"msg": "invoked", "name": name}))
    return {"statusCode": 200, "body": f"hello {name}"}
LineMeaning / WHY it exists
handler(event, context)Entry point; event holds trigger data.
print(json...)Goes to CloudWatch Logs (structured logging).
Return dictAPI Gateway proxy response format.

aws cloudwatch put-metric-alarm --alarm-name high-cpu --namespace AWS/EC2 --metric-name CPUUtilization \
 --statistic Average --period 300 --threshold 80 --comparison-operator GreaterThanThreshold --evaluation-periods 2 \
 --alarm-actions arn:aws:sns:ap-south-1:123456789012:ops-alerts

Real-World Problems & Fixes (Troubleshooting)

Problem: Lambda cold starts slow API
Cause: Large package / VPC / runtime
Fix: Provisioned concurrency, smaller package, SnapStart.
Problem: CloudWatch logs bill explosion
Cause: Verbose debug logs, infinite retention
Fix: Set retention, sample logs, filter before shipping.

Best Practices

Cost Optimization

  • Right-size memory, use Savings Plans, Fargate Spot, budgets and anomaly detection.

Monitoring & Logging

  • Structured logs, alarms on errors/latency, X-Ray tracing.

Common Mistakes

Production mistakes

  • No alarms.
  • Unbounded Lambda concurrency hitting the database.

Hinglish Explanation

Lambda chhote event-driven kaam ke liye. CloudWatch alarms aur Budgets lagana mat bhoolo.

Version / Environment Notes

  • Lambda runtimes are deprecated on a schedule: check supported Python/Node versions. Limits (timeout, memory, package size) change: see AWS docs.

Interview Questions

Q1. Lambda limits?

15 min max, memory up to 10GB, 250MB package (10GB container), concurrency limits.

Q2. ECS vs EKS?

ECS AWS-native simpler; EKS managed Kubernetes for portability/ecosystem.

Q3. CloudWatch vs CloudTrail?

CloudWatch = metrics/logs; CloudTrail = API audit logs.

Q4. Well-Architected pillars?

Operational excellence, security, reliability, performance efficiency, cost optimization, sustainability.

Q5. DR strategies?

Backup&restore, pilot light, warm standby, multi-site active-active (increasing cost, decreasing RTO).

Q6. Lambda has high latency on the first request.

Cold start: reduce package size, use provisioned concurrency, avoid heavy init, avoid VPC where unnecessary.

Why: Serverless performance.

Real-world example: Provisioned concurrency for APIs.
