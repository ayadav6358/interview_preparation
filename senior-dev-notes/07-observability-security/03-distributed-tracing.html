    Distributed Tracing

    ⏱ ~2.5 hrs📍 Chapter 3 of 6

    One-line summary: A distributed trace is the explicit causal tree of a single request as it crosses process/service boundaries — OpenTelemetry is the vendor-neutral standard for generating and propagating that tree, and reading its waterfall view is the fastest way to find exactly which hop caused a latency spike.

    On this page

      Why It Matters for a Senior Developer

      "Walk me through how you'd debug a slow checkout flow across 6 microservices" is a staple senior/staff interview question, and the expected answer increasingly assumes distributed tracing, not log archaeology. Tracing is also the piece most engineers have heard of but never actually implemented correctly — getting context propagation right across HTTP, message queues, and async boundaries is genuinely subtle, and being able to explain it precisely (not just "OpenTelemetry does it automatically") signals real production experience.

      Prerequisites

      Comfortable with the correlation ID concept from logging and async programming in Node. Related: Logging, Metrics, Monitoring & Alerting.

      Core Concepts

      Traces, spans, and context

      A trace represents one end-to-end request/operation and is identified by a single trace_id shared by every unit of work inside it. A span represents one unit of work within that trace (an HTTP call, a DB query, a function) and has its own span_id, a parent_span_id (forming a tree, not a flat list), a start/end timestamp, attributes (key-value metadata, like HTTP status or DB statement), and events (timestamped log-like annotations within the span). Context propagation is the mechanism that carries the current trace/span IDs across every boundary a request crosses — in-process (function calls, async callbacks) and cross-process (HTTP headers, queue message metadata) — so every span in a multi-service request links back into the same trace tree, with correct parent/child relationships that reflect actual causality.

      The W3C Trace Context standard

      Before OpenTelemetry, every vendor (Zipkin, Jaeger, Datadog) used a different header format for propagating trace context, which broke tracing the moment a request crossed a vendor boundary. The W3C Trace Context spec standardizes this as a single HTTP header: traceparent: 00-<32-hex-trace-id>-<16-hex-parent-span-id>-<2-hex-flags> (e.g., 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01, where the trailing 01 flag means "sampled"). An optional tracestate header carries vendor-specific extra state. Any OpenTelemetry-instrumented service reads an incoming traceparent, creates a new span as a child of it, and forwards an updated traceparent (same trace_id, new parent_span_id = this span's ID) to its own downstream calls — this is exactly how a trace stays connected across completely different companies' services if everyone speaks this standard.

      OpenTelemetry architecture: SDK, API, Collector

      OpenTelemetry separates the API (the stable interface application/library code calls, e.g. "start a span") from the SDK (the actual implementation: sampling decisions, batching, exporting) — this means instrumentation libraries can depend only on the API and remain backend-agnostic. Auto-instrumentation libraries (@opentelemetry/instrumentation-http, -express, -pg) monkey-patch common libraries to create spans automatically without you writing any code for standard operations (incoming HTTP request, outgoing HTTP call, DB query). The OpenTelemetry Collector is an optional but strongly recommended separate process/sidecar that receives spans/metrics/logs from all your services, can batch/filter/transform them, and exports to one or more backends (Jaeger, Tempo, Honeycomb, Datadog) — this decouples your application from any specific vendor and lets you change backends by reconfiguring the Collector, not redeploying every service.

      Sampling strategies

      Tracing every single request at full detail is often too expensive at scale (both in overhead and storage). Head-based sampling decides whether to trace a request at its very start (e.g., sample 10% of requests randomly, or always sample if a specific header is present) — cheap, but you commit to the decision before you know if the request turns out to be interesting (e.g., slow or erroring). Tail-based sampling buffers all spans for a trace until it completes, then decides whether to keep it based on its actual outcome (always keep errors and high-latency traces, sample the rest) — this gives you the traces you actually care about, at the cost of needing a buffering layer (the Collector) that holds spans in memory until the trace is complete, which adds latency/complexity and memory pressure at very high request volume.

      Correlating traces with logs and metrics (exemplars)

      The three pillars are most powerful connected, not siloed. A modern pattern: metrics expose exemplars — a sampled trace_id attached to a specific histogram bucket observation — so you can click from "this is the latency spike on the p99 line" directly into the actual trace that produced that data point. Similarly, structured logs should include trace_id/span_id fields so you can jump from a specific error log line into its full trace waterfall, and from the trace into every log line emitted during that span.

      How It Works Under the Hood

      When a service starts handling a request, the OpenTelemetry SDK checks for an incoming traceparent header. If present, it extracts the trace_id and parent_span_id and creates a new span as a child of that remote context. If absent (this is the start of a new trace), it generates a fresh trace_id. Either way, a sampler (configured once, e.g. ParentBased(TraceIdRatioBased(0.1))) decides whether this trace is sampled — importantly, the sampling decision made at the root is typically respected by all descendant spans (ParentBased) so you never get a trace with only some of its spans recorded. Spans are buffered in memory and periodically flushed in batches by a BatchSpanProcessor (batching avoids a network call per span, which would be prohibitively expensive) to an exporter — either directly to a backend or, more commonly, to a local OpenTelemetry Collector via OTLP (OpenTelemetry Protocol, usually gRPC or HTTP/protobuf). The Collector then handles further processing (tail-sampling, PII scrubbing, batching across services) before exporting onward to long-term storage like Jaeger or Grafana Tempo, which index spans by trace_id and support the waterfall visualization.

      Code Examples

      // -----------------------------------------------------------------------
// 1. OpenTelemetry Node SDK bootstrap: auto-instrumentation + OTLP export
//    This file must be required/imported BEFORE any other application
//    code (e.g., via `node --require ./tracing.js app.js`), so that
//    monkey-patching of http/express/pg happens before those modules
//    are first loaded.
// -----------------------------------------------------------------------
import { NodeSDK } from "@opentelemetry/sdk-node";
import { getNodeAutoInstrumentations } from "@opentelemetry/auto-instrumentations-node";
import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-grpc";
import { Resource } from "@opentelemetry/resources";
import { SemanticResourceAttributes } from "@opentelemetry/semantic-conventions";

const sdk = new NodeSDK({
  resource: new Resource({
    [SemanticResourceAttributes.SERVICE_NAME]: "orders-service",
    [SemanticResourceAttributes.SERVICE_VERSION]: process.env.GIT_SHA ?? "dev",
  }),
  traceExporter: new OTLPTraceExporter({ url: "http://otel-collector:4317" }),
  instrumentations: [
    getNodeAutoInstrumentations({
      // Avoid tracing noisy internal health checks — reduces volume/cost
      // without losing anything debuggable.
      "@opentelemetry/instrumentation-http": {
        ignoreIncomingRequestHook: (req) => req.url === "/healthz",
      },
    }),
  ],
});

sdk.start();
process.on("SIGTERM", () => sdk.shutdown().finally(() => process.exit(0)));

// -----------------------------------------------------------------------
// 2. Manual span for a business operation, with attributes and events
// -----------------------------------------------------------------------
import { trace, SpanStatusCode } from "@opentelemetry/api";

const tracer = trace.getTracer("orders-service");

async function applyDiscount(order: Order, code: string) {
  return tracer.startActiveSpan("applyDiscount", async (span) => {
    span.setAttribute("order.id", order.id);
    span.setAttribute("discount.code", code);
    try {
      const discount = await lookupDiscount(code);
      if (!discount) {
        span.addEvent("discount_not_found");
        span.setStatus({ code: SpanStatusCode.ERROR, message: "invalid discount code" });
        throw new Error("invalid discount code");
      }
      span.setAttribute("discount.percent", discount.percent);
      return applyPercent(order, discount.percent);
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR, message: (err as Error).message });
      throw err;
    } finally {
      span.end(); // ALWAYS end the span, success or failure, or it leaks
                  // and never appears in the trace (silent data loss).
    }
  });
}

// -----------------------------------------------------------------------
// 3. Propagating trace context manually across a message queue
//    (auto-instrumentation covers HTTP automatically; queues usually need
//    explicit propagation since there's no standard "queue header" spec
//    as universal as W3C Trace Context for HTTP.)
// -----------------------------------------------------------------------
import { propagation, context, trace } from "@opentelemetry/api";

async function publishFulfillmentJob(orderId: string) {
  const carrier: Record = {};
  // Serializes the CURRENT active span's context into carrier using the
  // same W3C traceparent format, so any OTel-aware consumer can resume it.
  propagation.inject(context.active(), carrier);
  await queue.add("fulfill-order", { orderId, otelContext: carrier });
}

queue.process("fulfill-order", async (job) => {
  const parentCtx = propagation.extract(context.active(), job.data.otelContext);
  const tracer = trace.getTracer("fulfillment-worker");
  await context.with(parentCtx, () =>
    tracer.startActiveSpan("fulfillOrder", async (span) => {
      span.setAttribute("order.id", job.data.orderId);
      await doFulfillment(job.data.orderId);
      span.end();
    })
  );
});

// -----------------------------------------------------------------------
// 4. Tail-based sampling config (OTel Collector YAML) — always keep
//    errors and slow traces, sample the rest at 5%.
// -----------------------------------------------------------------------
/*
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: always-keep-errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: always-keep-slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: sample-the-rest
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
*/

      Real-World Production Scenario at Scale

      At scale

      A fintech platform's checkout latency intermittently spiked to 3s (from a normal 200ms) but only for ~0.5% of requests — invisible in aggregate metrics, which averaged out fine, and nearly impossible to spot in logs because nothing errored. Head-based sampling at 1% was missing most of the slow requests entirely (sampling decision made before the slowness was known). Switching the Collector to tail-based sampling (always keep traces over 1s, regardless of the head-based coin flip) immediately surfaced the pattern: the slow traces all shared one span — a Redis GET on a specific cache key that occasionally missed and fell through to a cold, unindexed Postgres query. The trace waterfall made the root cause visually obvious in minutes; metrics alone had been showing "everything's fine on average" for weeks.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting to call span.end() on every code path (especially error paths wrapped in try/catch without a finally) is the most common OpenTelemetry bug — the span simply never appears in the exported trace, with no error or warning, making debugging the debugging tool itself painful. Always end spans in a finally block, or use startActiveSpan's callback form carefully with explicit end calls on every branch.

      • Auto-instrumentation must be loaded before the instrumented module (http, express, pg) is first required — load order matters, which is why the SDK bootstrap file is loaded via --require, not a normal top-of-file import in your entrypoint.
      • Don't put high-cardinality or sensitive data in span attributes that get exported to a third-party tracing backend — same PII discipline as logs applies.
      • Context propagation across message queues, WebSockets, and cron-triggered jobs usually needs explicit handling; don't assume auto-instrumentation covers every transport.
      • Pick sampling strategy deliberately — head-based is simpler and cheaper to run but will miss rare slow/erroring requests unless combined with "always sample on error/slow" rules, which effectively pushes you toward tail-based sampling for anything beyond a toy setup.

      Interview Questions

      Basic

      What is the difference between a trace and a span?

      A trace is the whole end-to-end request, identified by one trace_id; a span is one unit of work within it, with its own span_id and a parent_span_id forming a tree.

      Follow-up: how is the parent/child relationship between spans determined?
      What problem does the W3C Trace Context standard solve?

      It standardizes the HTTP header format (traceparent) for propagating trace context, so tracing works across different vendors/tools instead of breaking at any boundary using a different proprietary header format.

      Follow-up: what does the "sampled" flag in traceparent mean?
      What is context propagation and why is it hard across a message queue?

      It's carrying the current trace/span context across every boundary a request crosses. It's hard across queues because there's no in-process context (new process, different time) and no universal standard header like HTTP's traceparent, so you must serialize context into the message payload explicitly.

      Follow-up: how would you propagate context across a WebSocket connection?
      What does the OpenTelemetry Collector do?

      A separate process that receives telemetry (traces/metrics/logs) from services, can process/filter/sample it, and exports it to one or more backends — decoupling apps from specific vendors.

      Follow-up: why would you want tail-based sampling to happen in the Collector rather than in each service?
      What's the difference between head-based and tail-based sampling?

      Head-based decides to sample at the start of a request, before its outcome is known; tail-based buffers spans until the trace completes, then decides based on actual outcome (always keeping errors/slow traces).

      Follow-up: what's the main operational cost of tail-based sampling?
      What is auto-instrumentation in OpenTelemetry?

      Libraries that monkey-patch common modules (http, express, pg) to automatically create spans for standard operations, without the developer writing manual span code.

      Follow-up: why must it be loaded before the instrumented module is required?

      Medium

      Walk through exactly what happens, header by header, when a request flows through a gateway, two services, and a database, in terms of trace context.

      Gateway has no incoming traceparent, generates a new trace_id and root span, forwards traceparent (trace_id + its own span_id) to Service A; Service A creates a child span with parent = gateway's span_id, and forwards an updated traceparent (same trace_id, new parent = its own span_id) to Service B; Service B does the same, and its DB call is typically an in-process child span (DB driver instrumentation), not a cross-network propagated context since the DB itself isn't trace-aware.

      Follow-up: how would two independent requests ever end up sharing a trace_id by mistake, and what would that look like in the UI?
      Why might a trace appear with missing/orphaned spans even though every service is instrumented?

      Common causes: a span was created but .end() was never called on an error path; the sampling decision excluded that trace in a service using independent (non-parent-based) sampling so some spans were dropped; context wasn't propagated correctly across a non-HTTP boundary (queue, cron) so a downstream span started a brand-new, disconnected trace instead of joining the existing one.

      Follow-up: how would you detect disconnected/orphaned traces systematically rather than noticing by accident?
      How do exemplars connect metrics and traces, and why does that matter operationally?

      A histogram observation can carry a sampled trace_id as an exemplar; when looking at a latency spike on a dashboard, you can click directly into the specific trace that produced that data point instead of guessing which request to investigate — closing the loop from "symptom in aggregate" to "concrete example."

      Follow-up: why can't every single observation carry an exemplar?
      Your service's traces show accurate timing but completely wrong parent/child nesting for a specific async operation. What's the likely cause?

      Likely an async context loss bug — the span was started correctly but the subsequent async work (e.g., a detached promise, an event-emitter callback, or a setTimeout) ran outside the active context, so a later span attached to the wrong (or no) parent. Node's AsyncLocalStorage-based context manager usually handles standard async/await correctly, but fire-and-forget patterns and some third-party callback-style APIs can escape it.

      Follow-up: how would you fix a library that breaks context propagation internally?
      How would you decide which operations deserve a manual span versus relying only on auto-instrumentation?

      Add manual spans around business-meaningful operations whose internal timing you'd want to inspect separately from the surrounding HTTP/DB calls — e.g., a pricing calculation, a fraud-check call, a multi-step workflow — especially anything with meaningful internal branching or where you'd want custom attributes (discount code, feature flag value) attached.

      Follow-up: what's the risk of adding too many fine-grained manual spans?

      Advanced

      Design a tracing strategy for a system doing 1M requests/sec where naive full tracing/tail-sampling isn't feasible.

      Use head-based sampling at a low base rate (e.g., 0.1%) combined with deterministic, consistent sampling keyed on trace_id (so the same logical request is sampled consistently across services even without coordination) plus an explicit "always sample" override triggered by specific signals (a debug header, a known VIP customer, a canary deployment) — true tail-based sampling at this volume would require buffering an infeasible amount of span data per second, so you accept missing some rare issues in exchange for operability, and lean more heavily on metrics/logs for catching those.

      Follow-up: how does consistent/deterministic sampling work mechanically (hashing the trace_id)?
      How would you use distributed tracing to debug a cross-service deadlock or cascading timeout, where no single span shows an obvious long duration?

      Look at the trace waterfall for a pattern of many short spans each waiting on the next, where the SUM of serialized/sequential calls (rather than any one call) is the latency — classic N+1-across-services pattern; or look for spans with duration suspiciously close to a configured timeout value repeated across a cycle of services calling each other, indicating a timeout-retry storm rather than a single slow operation.

      Follow-up: what trace shape would indicate a retry storm versus genuine sequential latency?
      Your org has 3 different teams using 3 different tracing backends (Jaeger, Datadog, Honeycomb) after acquisitions. How do you unify observability without a risky big-bang migration?

      Standardize on OpenTelemetry instrumentation (API/SDK) across all services regardless of backend — since OTel is vendor-neutral, each team's existing backend keeps working via its own exporter config — then route everything through a shared Collector fleet that can fan out to multiple backends during a gradual migration, letting you consolidate backends later without re-instrumenting application code, which is the expensive/risky part.

      Follow-up: what's the main risk of exporting the same traces to multiple backends simultaneously?
      How do you handle trace context propagation across a boundary where you don't control the downstream service (a third-party API)?

      You generally still send the traceparent header if the third party might honor it (harmless if ignored), but you close your own outgoing span based purely on your own observed request/response timing — treat the third-party call as a black-box span with as much attribute detail as you can control (status code, retry count, timeout value) since you can't see inside their system regardless.

      Follow-up: how would you still estimate the third party's internal latency breakdown without their cooperation?
      What are the privacy/compliance implications of distributed tracing, and how do you architect around them?

      Span attributes can easily leak PII (user emails in a query parameter, request bodies attached as attributes) into a tracing backend that may be a third-party SaaS vendor, creating the same compliance exposure as logs — mitigate via attribute allowlisting/scrubbing at the Collector level (processor that strips/hashes known-sensitive attribute keys before export), data residency-aware backend choice for regulated data, and the same retention discipline as logs.

      Follow-up: why is scrubbing at the Collector better than relying on every service to scrub its own attributes?

      Practice Assignments

      Beginner (30-60 min)

      Auto-instrument a single Express service

      Add the OpenTelemetry Node SDK with auto-instrumentation to an Express app with a route that calls another HTTP endpoint (even a mocked one) and queries a database. Export traces to a local Jaeger via Docker Compose.

      • Confirm in the Jaeger UI that one request produces a trace with nested spans (HTTP in, HTTP out, DB query).
      • Confirm the trace_id is consistent across all spans in that trace.

      Acceptance criteria: A single trace in Jaeger shows at least 3 spans with correct parent/child nesting and realistic durations.

      Hints

      Remember the SDK bootstrap must run before your app code requires http/express/pg — use node --require ./tracing.js app.js.

      Bonus: Add a manual span around one business-logic function with custom attributes.

      Intermediate (2-4 hrs)

      Propagate trace context across a message queue

      Build a producer/consumer pair (BullMQ + Redis or similar) where the producer is part of an HTTP request's trace, and the consumer's processing span correctly joins that same trace as a child, using manual propagation.inject/extract.

      • Verify in Jaeger/Tempo that the queue consumer's span appears nested under the original HTTP request's trace, not as a separate trace.
      • Break it on purpose (skip the inject/extract) and observe what happens to the trace — document the difference.

      Acceptance criteria: One trace_id spans both the HTTP request and the asynchronously processed queue job, visible end-to-end in the UI.

      Hints

      The job payload is the only thing that survives the process boundary — context must be serialized into it explicitly, same principle as correlation IDs in logging.

      Bonus: Add a second consumer step so the trace has 3+ hops across process boundaries.

      Advanced (1-2 days)

      Tail-based sampling pipeline with a deliberately injected latency bug

      Set up an OpenTelemetry Collector with tail-based sampling (always keep errors/slow traces, sample 5% of the rest). Build a small multi-service app with a bug that causes rare (~1%) slow requests (e.g., an occasional cold-cache fallback to a slow query). Use head-based-only sampling first and show it's unreliable at catching the bug, then switch to tail-based and show it reliably captures every slow trace.

      • Produce a before/after comparison: with head-based 1% sampling, how many of the slow requests actually got traced out of 1000 requests, vs. with tail-based.
      • Write up the root cause you find from reading the captured traces.
      Hints

      This is intentionally open-ended — think about where the buffering/decision_wait window needs to be relative to your actual request duration for tail-sampling to work correctly.

      Bonus: Add an exemplar-linked metric so you can click from a Grafana latency panel directly into one of the captured slow traces.

      Quick Revision Cheat Sheet

      • Trace = whole request (one trace_id); span = one unit of work (span_id + parent_span_id, forms a tree).
      • W3C traceparent header standardizes cross-vendor context propagation over HTTP.
      • OTel separates API (stable interface) from SDK (implementation) — instrumentation stays vendor-neutral.
      • Auto-instrumentation must load before the instrumented module is required (load-order matters).
      • Non-HTTP boundaries (queues, WebSockets, cron) usually need explicit propagation.inject/extract.
      • Head-based sampling decides before outcome is known; tail-based decides after, buffering spans until trace completion.
      • Always keep error and slow traces regardless of sampling rate for routine traffic.
      • Always end spans in a finally block — a missed .end() silently drops the span from the trace.
      • Exemplars link a metric data point to a concrete sample trace for one-click drill-down.
      • Scrub PII from span attributes the same way you would from logs, ideally at the Collector.
