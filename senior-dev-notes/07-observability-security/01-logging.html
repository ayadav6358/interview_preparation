    Logging & Centralized Logging

    ⏱ ~2.5 hrs📍 Chapter 1 of 6

    One-line summary: Logs are the raw, unstructured truth of what happened — structured logging plus correlation IDs plus centralized aggregation (ELK/Loki) turns that truth into something you can actually query during an incident at 3am.

    On this page

      Why It Matters for a Senior Developer

      Every senior engineer has debugged a production issue with nothing but logs. The difference between a junior and a senior response is speed: a junior greps through unstructured text across 12 pods; a senior filters a structured query by correlation_id and has the full request lifecycle in 10 seconds. Interviewers ask about logging because it reveals whether you've actually operated a distributed system versus only built one. It also intersects with cost (log volume at scale is a real line item), security (logs are a common place secrets leak), and compliance (PII in logs is a GDPR/SOC2 problem).

      Prerequisites

      Comfortable with Node.js middleware, async context, and basic familiarity with a logging library (console.log doesn't count). Related: Metrics, Monitoring & Alerting, Distributed Tracing.

      Core Concepts

      Log levels and when to use them

      Standard levels (most libraries, e.g. Pino, follow this): fatal (process about to die), error (operation failed, needs attention), warn (unexpected but recovered), info (business-relevant events: "order created", "user logged in"), debug (developer detail, off in prod by default), trace (very verbose, rarely enabled). A senior calibration rule: if an error log doesn't represent something a human needs to look at, it's actually a warn. Alert fatigue is almost always caused by over-use of error.

      Structured (JSON) logging

      Plain-text logs like "User 123 failed login from 1.2.3.4" are human-friendly but machine-hostile — you can't filter, aggregate, or alert on them reliably because the schema lives only in someone's head. Structured logging emits each log line as a JSON object with consistent field names (level, time, msg, userId, ip, correlationId, service, env). This lets a log aggregator index and query by field instead of doing full-text regex search over billions of lines. Pino is the standard choice for Node in 2025–26 because it's asynchronous and extremely low-overhead (it offloads JSON serialization to avoid blocking the event loop on hot paths), compared to Winston which is more flexible/plugin-rich but slower under load.

      Correlation IDs and request context propagation

      A correlation ID (a.k.a. request ID or trace ID in simpler setups) is generated once at the edge (API gateway or the first service that receives the request) and threaded through every log line and every downstream call for that request's entire lifecycle, including async work (queue jobs, background tasks). Without it, finding all the log lines for one user's one request across 5 microservices and 3 async workers is close to impossible under real traffic. The mechanics: generate a UUID/ULID per request if the caller didn't supply one (respect an incoming X-Request-Id header if present — it lets a client or upstream gateway control it), store it in a per-request context (Node's AsyncLocalStorage is the correct primitive — it survives across await boundaries without manual threading), inject it into every outbound HTTP header and every message queue payload, and have your logger auto-attach it from that context to every log call so application code never has to pass it explicitly.

      PII and secrets redaction

      Logging a full request body is a classic rookie mistake — passwords, credit card numbers, auth tokens, and session cookies end up in plaintext in a log aggregator that dozens of engineers (and sometimes third-party support vendors) can query. Pino supports a redact option that replaces configured paths (req.headers.authorization, req.body.password) with [Redacted] before serialization — this must happen before the log line leaves the process, not as a downstream cleanup step, because once it's shipped to the aggregator it may already be replicated/backed up.

      Sampling and log volume at scale

      At high QPS, logging every request at info level is expensive (both in log-ingestion cost and in signal-to-noise). Common senior-level patterns: always log 100% of warn/error, but sample info-level success logs (e.g., log 1 in 100 successful health-check-adjacent requests), and always log 100% of a request if it was slow (duration over some threshold) regardless of status — slow successful requests are often the first signal of a brewing incident.

      How It Works Under the Hood

      The ELK stack (Elasticsearch, Logstash, Kibana) — or its modern lighter-weight cousin, Grafana Loki + Promtail/Fluent Bit + Grafana — works roughly like this: a log shipper (Filebeat, Fluent Bit, or Promtail) runs as a sidecar or DaemonSet on each node/pod, tailing stdout/stderr or a log file. It batches and forwards lines to an ingestion pipeline (Logstash does parsing/enrichment; Loki skips this and treats logs more like Prometheus treats metrics — indexing only labels, not full text, which makes it dramatically cheaper to run at scale). The ingested logs land in a storage/index layer (Elasticsearch's inverted index for full-text search; Loki's chunked object storage keyed by label set). Kibana or Grafana then queries that layer. The key architectural tradeoff: Elasticsearch gives you full-text search over any field at the cost of a much larger storage/indexing footprint; Loki is far cheaper because it only indexes labels (like service, env, level) and does a linear scan over compressed log chunks for the actual text — fine at the query patterns most teams actually use ("show me logs for service X with correlation ID Y"), bad if you need arbitrary full-text search across unindexed fields.

      Code Examples

      // -----------------------------------------------------------------------
// 1. Pino structured logger with redaction, correlation ID via AsyncLocalStorage
// -----------------------------------------------------------------------
import pino from "pino";
import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";
import express, { NextFunction, Request, Response } from "express";

type RequestContext = { correlationId: string; userId?: string };
export const requestContext = new AsyncLocalStorage();

const baseLogger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  redact: {
    paths: [
      "req.headers.authorization",
      "req.headers.cookie",
      "body.password",
      "body.creditCard",
      "*.apiKey",
    ],
    censor: "[Redacted]",
  },
  // mixin runs on every log call and merges in context without the caller
  // having to pass correlationId explicitly every time.
  mixin() {
    const ctx = requestContext.getStore();
    return ctx ? { correlationId: ctx.correlationId, userId: ctx.userId } : {};
  },
});

export function correlationMiddleware(req: Request, res: Response, next: NextFunction) {
  const incoming = req.header("x-request-id");
  const correlationId = incoming && /^[\w-]{8,64}$/.test(incoming) ? incoming : randomUUID();
  res.setHeader("x-request-id", correlationId);
  requestContext.run({ correlationId }, () => next());
}

const app = express();
app.use(correlationMiddleware);

app.post("/orders", (req, res) => {
  // No need to pass correlationId manually — mixin() injects it.
  baseLogger.info({ orderTotal: req.body.total }, "order received");
  res.status(202).json({ status: "queued" });
});

// -----------------------------------------------------------------------
// 2. Propagating correlation ID downstream — over HTTP and over a queue
// -----------------------------------------------------------------------
import axios from "axios";

async function callInventoryService(sku: string) {
  const ctx = requestContext.getStore();
  return axios.get(`http://inventory-svc/stock/${sku}`, {
    headers: ctx ? { "x-request-id": ctx.correlationId } : {},
  });
}

async function publishFulfillmentJob(orderId: string) {
  const ctx = requestContext.getStore();
  await queue.add("fulfill-order", {
    orderId,
    correlationId: ctx?.correlationId, // must be carried in the payload —
                                        // the worker runs in a different process/tick.
  });
}

// Worker side: re-establish the context from the job payload before doing
// any work, so every log line inside the job handler is correlated too.
queue.process("fulfill-order", async (job) => {
  await requestContext.run({ correlationId: job.data.correlationId }, async () => {
    baseLogger.info({ orderId: job.data.orderId }, "fulfillment started");
    await doFulfillment(job.data.orderId);
    baseLogger.info({ orderId: job.data.orderId }, "fulfillment complete");
  });
});

// -----------------------------------------------------------------------
// 3. BAD vs GOOD: logging sensitive data
// -----------------------------------------------------------------------
// BAD — logs the entire request body, including password, in plaintext.
// This will be in Kibana/Loki, replicated, backed up, and queryable by
// anyone with log access — including third-party support contractors.
app.post("/login-bad", (req, res) => {
  console.log("Login attempt:", JSON.stringify(req.body)); // { email, password }
  // ...
});

// GOOD — redact() strips sensitive fields before the line is even serialized,
// and we never log the raw body at all; we log only what's needed to debug.
app.post("/login-good", (req, res) => {
  baseLogger.info({ email: req.body.email, ip: req.ip }, "login attempt");
  // password never touches a log line, redacted or not.
});

// -----------------------------------------------------------------------
// 4. Sampling: log 100% of errors/slow requests, sample the rest
// -----------------------------------------------------------------------
app.use((req, res, next) => {
  const start = Date.now();
  res.on("finish", () => {
    const durationMs = Date.now() - start;
    const isSlow = durationMs > 500;
    const isError = res.statusCode >= 500;
    const sampled = Math.random() < 0.01; // 1% sample for routine success
    if (isError || isSlow || sampled) {
      baseLogger.info({ path: req.path, status: res.statusCode, durationMs }, "request completed");
    }
  });
  next();
});

      Real-World Production Scenario at Scale

      At scale

      A payments company runs 40 microservices on Kubernetes, ~200k requests/min at peak. Logging every request at info without sampling generated ~4TB/day into Elasticsearch, costing more in storage/compute than the actual application infra. The fix: move to Loki (label-based indexing instead of full-text), keep correlation IDs as a label on every stream, sample successful info logs at 1%, and log 100% of anything with status >= 400 or durationMs > p95. Log volume dropped ~85% with zero loss of incident-debugging capability, because the lines that actually get queried during an incident are the error/slow ones, not the routine successes. The team also set a hard rule: any PR that adds a new log.info call touching req.body or any field matching /token|password|secret|key/i fails CI via a custom ESLint rule.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Using console.log in production code paths blocks the event loop synchronously on some platforms/terminals and has no structure, level, or redaction — it's fine for a local script, never for a service. Another common gotcha: forgetting that AsyncLocalStorage context is lost across a message queue boundary (new process/tick) unless you explicitly serialize the correlation ID into the job payload and re-establish the context on the consumer side — this is the #1 cause of "the logs just stop" mid-request-lifecycle.

      • Never log raw request/response bodies by default; log specific, intentional fields.
      • Always propagate (or generate) a correlation ID at the very first point of entry, before any other middleware runs, so even early rejections (auth failures, rate limits) are correlated.
      • Set retention policy consciously — logs older than N days should be deleted or moved to cold storage, not kept forever "just in case" (cost + compliance liability).
      • Timestamp every log line in UTC with milliseconds; never rely on the aggregator's ingestion time as the event time — under backpressure, ingestion time can lag event time by minutes.

      Interview Questions

      Basic

      What's the difference between structured and unstructured logging?

      Unstructured logging is free-text ("User 123 failed login"); structured logging emits each entry as a consistent object (usually JSON) with named fields, enabling filtering, aggregation, and alerting by field instead of regex over text.

      Follow-up: why does this matter more at scale than for a single-server app?
      What is a correlation ID and why do you need one?

      A unique identifier generated per request (or per logical unit of work) and attached to every log line and downstream call it causes, so you can reconstruct the full lifecycle of one request across multiple services/processes.

      Follow-up: where should it be generated if the client doesn't supply one?
      Name the standard log levels and when you'd use each.

      fatal (process dying), error (failed operation needing attention), warn (recovered but unexpected), info (business events), debug (dev detail), trace (very verbose). Calibration: if an "error" doesn't need human attention, it should be a warn.

      Follow-up: what's alert fatigue and how does log-level discipline prevent it?
      Why shouldn't you log a full request body by default?

      It often contains PII or secrets (passwords, tokens, card numbers) that get replicated into log aggregators accessible to many people/vendors — a compliance and security risk.

      Follow-up: how does Pino's redact option work mechanically?
      What's the difference between Pino and Winston?

      Pino is built for performance — low overhead, async-friendly serialization, good for high-throughput hot paths. Winston is more flexible with transports/formats but has higher overhead.

      Follow-up: when would Winston's flexibility actually matter?
      What is log sampling and why would you do it?

      Logging only a fraction of routine/successful events (while always logging errors and slow requests) to control volume/cost without losing the signal that actually matters during an incident.

      Follow-up: what types of events should never be sampled?
      What is Elasticsearch/Logstash/Kibana (ELK) used for?

      A stack for centralizing, indexing (full-text), and visually querying logs across many services/hosts instead of SSHing into each machine.

      Follow-up: what's the main cost driver of running ELK at scale?

      Medium

      Walk through how a correlation ID survives a request that goes through an API gateway, a service, and a message queue job.

      Gateway generates/forwards it as a header; the service reads it into an AsyncLocalStorage-like context for the synchronous request lifecycle; before publishing to the queue, the correlation ID is explicitly serialized into the job payload (context doesn't survive process boundaries); the worker re-establishes the context from the payload before processing, so its logs are still correlated.

      Follow-up: what breaks if you forget the explicit serialization step?
      Why does Node's AsyncLocalStorage matter here instead of just passing correlationId as a function parameter?

      Threading an ID through every function signature across a deep call stack with many async boundaries is invasive and error-prone. AsyncLocalStorage attaches context to the async execution chain itself, so any code (including third-party middleware) can read it without being explicitly passed it, and it correctly survives awaits.

      Follow-up: what's a limitation of AsyncLocalStorage under heavy load (perf overhead)?
      Compare Loki vs Elasticsearch architecturally — why is Loki cheaper?

      Elasticsearch builds a full inverted index over every field/token in every log line, which is powerful but storage/compute heavy. Loki only indexes a small set of labels (like Prometheus does for metrics) and stores the actual log text as compressed chunks, scanning them linearly at query time — cheap to ingest and store, as long as your queries are mostly label-filtered.

      Follow-up: what query pattern would make Loki perform badly?
      How would you design PII redaction so a bug in application code can't accidentally leak secrets into logs?

      Configure redaction at the logger level (path-based, e.g. Pino's redact) so it's enforced centrally regardless of what fields a given call site passes, rather than relying on every developer to remember to scrub manually; back it up with a lint rule that flags logging of req.body/headers wholesale, and periodic audits of log samples.

      Follow-up: what's a weakness of path-based redaction (e.g., dynamic/unknown field names)?
      How do you decide log retention policy for a regulated (e.g., fintech) system?

      Balance operational need (how far back do you realistically debug?) against compliance requirements (some regulations mandate minimum retention for audit trails) and cost; typically hot storage for 7–30 days, cold/archive storage for longer mandated retention, with PII-bearing logs having stricter/shorter retention or field-level encryption.

      Follow-up: how do you handle a "right to be forgotten" request against logs you've already shipped?
      Your logs show a spike in error rate but no clear pattern in the log messages. What's your next step?

      Pivot to correlation IDs of a handful of the failing requests, pull their full cross-service log trail, and cross-reference with metrics/traces for the same time window to see if it's one downstream dependency, a deploy correlation, or a resource exhaustion issue.

      Follow-up: what would make you suspect a deploy-caused regression versus an external dependency issue?
      How would you prevent a new feature's logging from silently exploding log volume/cost in production?

      Code review checklist for new log.info calls in hot paths, default to debug level for verbose new features until proven necessary at info, dashboard/alert on log ingestion volume itself, and load-test with logging enabled before shipping.

      Follow-up: how would you detect this issue after the fact rather than prevent it?

      Advanced

      Design a logging strategy for a system processing 500k events/sec where even 1% sampling is still too much volume.

      Tiered approach: emit metrics (counters/histograms) for the high-volume hot path instead of per-event logs (metrics are pre-aggregated, far cheaper); log only exceptional events (errors, outliers by duration) at full fidelity; use adaptive/dynamic sampling that increases sample rate automatically when error rate rises, so you get more detail exactly when you need it; consider structured "wide events"/trace spans instead of logs for ultra-high-cardinality debugging needs (this is the core argument behind the observability 2.0 movement).

      Follow-up: what's the tradeoff of dynamic/adaptive sampling vs fixed-rate sampling?
      How would you detect and prevent secrets accidentally logged in production before they're exfiltrated by someone with log access?

      Defense in depth: logger-level redaction by field path and by regex pattern-matching values that look like secrets (JWTs, AWS keys, high-entropy strings) as a catch-all; a log-ingestion-side scanner that flags/quarantines lines matching known secret patterns even if redaction was missed; automatic secret rotation triggered the moment a leak is confirmed; and restricting log access via RBAC so even a leak has limited blast radius.

      Follow-up: why is regex-based secret detection on log values insufficient alone?
      How does log correlation differ from distributed tracing, and when is logging alone insufficient?

      Correlation IDs tie log lines together but give you no inherent sense of causality, parent/child relationships, or timing breakdown between spans — you have to manually reconstruct order from timestamps. Distributed tracing (OpenTelemetry) captures the causal tree explicitly (span parent/child, start/end times) so you can see exactly which hop in a multi-service call dominated latency without manual reconstruction.

      Follow-up: can you get "good enough" causal visibility from logs alone with disciplined practices?
      You're migrating 40 services from ELK to Loki to cut costs. What's your migration risk and how do you de-risk it?

      Risk: losing full-text search capability teams depend on for ad-hoc debugging, and query pattern mismatches causing slow Loki queries. De-risk via dual-write/shadow period comparing query results and latency, auditing actual historical query patterns in Kibana to confirm they're mostly label-filterable, and keeping a short-retention ELK fallback for a transition window.

      Follow-up: how would you quantify "cost savings" convincingly to justify the migration to leadership?
      A log aggregator outage means you have zero logs during an active incident. What do you fall back on, and how do you architect against this recurring?

      Fall back to metrics/dashboards (usually a separate system) and direct access to the affected hosts/pods (kubectl logs, SSH) for the most recent window. To architect against recurrence: decouple log shipping from the critical path (never block application logic on the aggregator being up), keep a local ring buffer/short retention on-host as a last resort, and ensure your metrics/alerting pipeline is on genuinely independent infrastructure from your logging pipeline.

      Follow-up: why is it dangerous for metrics and logging to share the same underlying infrastructure?

      Practice Assignments

      Beginner (30-60 min)

      Structured request logger with correlation ID

      Build an Express app with two routes. Add middleware that generates (or forwards) a correlation ID and logs every request/response with Pino in JSON, including the correlation ID on every line.

      • Logger must use JSON output with level, time, msg, correlationId.
      • Correlation ID must be returned in the response header so a client can report it.
      • Incoming X-Request-Id header should be respected if present and valid.

      Acceptance criteria: Hitting both routes produces log lines in Kibana/terminal that share a correlation ID per request, and a malformed/missing header still produces a valid new ID.

      Hints

      Use AsyncLocalStorage or a simple per-request object attached to req; validate the incoming header with a regex before trusting it (never trust client input blindly, even for an ID).

      Bonus: Add redaction for an Authorization header.

      Intermediate (2-4 hrs)

      Cross-service correlation through a queue

      Build two services: an API that accepts a job and pushes it to a queue (BullMQ + Redis, or an in-memory queue if you want to skip infra), and a worker that processes it. Correlation ID must flow from the original HTTP request into the worker's logs.

      • API logs "job enqueued" with correlationId.
      • Worker logs "job started" and "job finished" with the same correlationId, re-established via AsyncLocalStorage from the job payload.
      • Simulate 50 concurrent requests and prove (via a script that greps logs by correlationId) that no IDs cross-contaminate between concurrent jobs.

      Acceptance criteria: A script given one correlation ID can print the complete cross-process lifecycle of that one request in order.

      Hints

      The queue payload is the only thing that survives the process boundary — don't rely on in-memory context there. Watch for ID collisions under concurrency if you use a predictable (non-random) ID scheme.

      Bonus: Ship logs to a local Loki + Grafana stack via Docker Compose and query by correlationId in Grafana Explore.

      Advanced (1-2 days)

      Production-grade logging pipeline with sampling and cost controls

      Design and partially implement a logging pipeline for a simulated high-traffic service: adaptive sampling (100% of errors/slow requests, 1% of routine success, bumped automatically to 100% for a rolling window when error rate crosses a threshold), PII redaction, and a Loki + Promtail + Grafana Docker Compose setup with a dashboard showing log volume over time.

      • Load-test the service and demonstrate log volume reduction vs. unsampled baseline, with numbers.
      • Demonstrate the adaptive trigger: inject a burst of errors and show sampling rate increasing automatically, then decaying back down.
      • Write a one-page design doc justifying your retention policy and redaction field list.
      Hints

      This is intentionally open-ended — think about where the sampling decision needs to live (must happen before the expensive serialization/IO, not after) and how you'd detect the error-rate trigger without adding significant overhead itself.

      Bonus: Add a CI lint rule (custom ESLint rule) that fails a PR if it detects a raw req.body or req.headers object passed directly into a log call.

      Quick Revision Cheat Sheet

      • Structured (JSON) logs > free text — enables filtering/alerting by field.
      • Generate/forward a correlation ID at the edge; propagate via headers (HTTP) and payload fields (queues) — context doesn't survive process boundaries automatically.
      • Use AsyncLocalStorage in Node to avoid manually threading correlationId through every function.
      • Redact secrets/PII at the logger level (path-based + pattern-based), before the line is serialized.
      • Log levels: fatal/error/warn/info/debug/trace — if an "error" doesn't need human attention, downgrade it.
      • Sample routine success logs; never sample errors or slow requests.
      • Pino for high-throughput Node services; Winston when you need more transport flexibility.
      • ELK = full-text search, expensive at scale; Loki = label-indexed, far cheaper, less flexible for free-text queries.
      • Set explicit log retention; it's a cost and compliance decision, not a default.
      • Decouple log shipping from the request's critical path — never block app logic on the log pipeline.
