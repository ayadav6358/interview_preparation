    Secure Auth, Secrets Management, CORS, CSP, XSS, CSRF

    ⏱ ~3 hrs📍 Chapter 5 of 6

    One-line summary: This chapter goes deep on the browser-security primitives (CORS, CSP, cookie flags) and auth architecture decisions (session vs JWT, refresh rotation, secrets management) that sit underneath most of the OWASP Top 10 and are the most commonly misconfigured parts of a real production app.

    On this page

      Why It Matters for a Senior Developer

      "Session or JWT, and why" and "explain exactly how CSRF works and how you'd stop it" are near-universal senior interview questions, because the answer requires understanding browser same-origin policy, cookie semantics, and token lifecycle tradeoffs simultaneously — not just naming a library. This is also the area where a single wrong default (a wildcard CORS origin with credentials, a JWT with no expiry, a secret committed to git) causes real breaches, so interviewers use it to gauge whether you've actually operated auth in production.

      Prerequisites

      HTTP, cookies, and basic JWT structure. Related: OWASP Top 10.

      Core Concepts

      Session cookies vs JWT

      Session-based auth: server generates a random session ID, stores session data server-side (Redis/DB), sends the ID to the browser as an HttpOnly, Secure, SameSite cookie. Revocation is trivial (delete the server-side session). Scaling requires a shared session store across instances. JWT-based auth: server issues a signed token containing claims (userId, roles, expiry), the client stores and sends it (ideally also as an HttpOnly cookie, not localStorage — see below), and the server verifies the signature statelessly without a DB lookup. The tradeoff: statelessness makes horizontal scaling trivial, but revocation is hard — a JWT is valid until it expires no matter what, unless you maintain a denylist (which reintroduces the statefulness you were trying to avoid) or keep expiry very short and rely on refresh token rotation.

      Where to store a JWT on the client: localStorage vs cookie

      Storing a JWT in localStorage is vulnerable to theft via any XSS on the page — JS can read localStorage, so one successful XSS injection anywhere on the origin exfiltrates every user's token. Storing it in an HttpOnly cookie makes it inaccessible to JS entirely (immune to XSS theft), but cookies are automatically attached to every request to that domain, which is exactly what opens the door to CSRF — so an HttpOnly cookie must be paired with SameSite and/or a CSRF token to be safe. The senior-level answer: HttpOnly + Secure + SameSite=Strict/Lax cookie, with a separate CSRF mitigation layered on top for state-changing requests, is strictly safer than localStorage for session tokens, despite localStorage's apparent convenience.

      Refresh token rotation

      Access tokens should be short-lived (minutes) to limit the damage window if stolen. A longer-lived refresh token is used to mint new access tokens without re-login. Rotation: every time a refresh token is used, it's invalidated and a new one issued — if a stolen refresh token is ever used by an attacker after the legitimate user has already used (and rotated past) it, the server detects reuse of an invalidated token and can revoke the entire token family, flagging likely theft. This is the mechanism behind "you've been logged out everywhere" security responses.

      CSRF: the actual attack mechanics

      Cross-Site Request Forgery exploits the fact that browsers attach cookies automatically to requests regardless of which site initiated them. If a bank's transfer endpoint relies solely on a session cookie for auth, a malicious page the victim visits can submit a form (or fire a fetch, for non-preflighted simple requests) to bank.com/transfer — the browser attaches the victim's valid session cookie automatically, and the bank's server, having no way to tell the request didn't originate from its own UI, processes it. Defenses: (1) SameSite=Lax or Strict cookies prevent the cookie from being sent on most cross-site requests; (2) a CSRF token — a random value embedded in the page and required as a parameter/header on state-changing requests, which an attacker's page cannot read (same-origin policy blocks reading the victim's page content) and therefore cannot forge; (3) checking the Origin/ Referer header server-side as a defense-in-depth signal.

      CORS: what it actually protects (and doesn't)

      CORS is a browser-enforced relaxation of the Same-Origin Policy — it does not protect your server from non-browser clients (curl, a server-to-server call) at all; it only controls whether a browser running JS from origin A is allowed to read a response from origin B. The server opts in via Access-Control-Allow-Origin. A critical interview gotcha: Access-Control-Allow-Origin: * combined with Access-Control-Allow-Credentials: true is actually disallowed by browsers (and should never be configured), because it would let any site on the internet make authenticated requests using the victim's cookies and read the response — the correct pattern is an explicit, validated allowlist of trusted origins, never a wildcard, when credentials are involved.

      Content Security Policy (CSP)

      CSP is a response header (Content-Security-Policy) that tells the browser which sources are allowed to load scripts/styles/images/fonts/connect, acting as a second line of defense against XSS even if a sanitization bug lets malicious markup through — a strict CSP that disallows inline scripts (script-src 'self', no 'unsafe-inline') means an injected <script>alert(1)</script> simply won't execute, because the browser refuses to run any script not from an allowlisted source. Modern CSP favors nonces (a random per-request value added to both the CSP header and the legitimate inline script tags) over broad allowlisting, since an attacker injecting markup can't guess the nonce for that response.

      Secrets management

      Hardcoding API keys/DB passwords in source code is the single most common real-world secret leak vector — committed once, it's in git history forever even if removed later (requires history rewriting + key rotation to actually remediate). The senior-level pattern: secrets live in a dedicated secrets manager (AWS Secrets Manager, HashiCorp Vault, Doppler) or at minimum environment variables injected at deploy time (never committed .env files with real values — only a .env.example template), fetched by the application at startup/runtime, with automatic rotation where supported and strict least-privilege IAM access to who/what can read them. CI/CD secrets (deploy keys, cloud credentials) need the same discipline — a secret scanner (gitleaks, GitHub secret scanning) in CI catches accidental commits before they merge.

      How It Works Under the Hood

      A browser's Same-Origin Policy is enforced at the network-stack/rendering-engine level, comparing scheme+host+port of the requesting page against the resource's origin for script-level reads (not for simple cross-origin requests themselves, which are sent — only the JS's ability to read the response is blocked without CORS headers). For a "non-simple" request (custom headers, methods other than GET/POST/HEAD, or a non-standard Content-Type like application/json), the browser first sends an OPTIONS preflight request asking the server to confirm the actual request is allowed, before sending the real one — this is why a JSON POST triggers a visible extra OPTIONS call in network tools while a simple form POST doesn't. SameSite cookie attributes are enforced by the browser at cookie-attach time: `Strict` never attaches the cookie on a cross-site navigation/request; `Lax` attaches it only for top-level cross-site GET navigations (so clicking a link works, but a cross-site form POST or fetch doesn't carry the cookie); `None` (requiring `Secure`) always attaches it, explicitly opting back into the CSRF-exposed behavior for cases like a legitimate third-party embed that needs it.

      Code Examples

      // =========================================================================
// A07 — BROKEN AUTH: weak JWT handling, vulnerable vs fixed
// =========================================================================
// VULNERABLE — no expiry, weak/guessable secret, no algorithm pinning.
// Exploit: an attacker who learns (or brute-forces) the weak secret
// "secret123" can forge a token for ANY userId/role, including admin.
import jwt from "jsonwebtoken";

function issueTokenBad(userId: string) {
  return jwt.sign({ userId }, "secret123"); // no expiresIn, weak secret
}
function verifyTokenBad(token: string) {
  return jwt.verify(token, "secret123"); // also vulnerable to alg:none
                                          // bypass in older library versions
                                          // if algorithms aren't pinned.
}

// FIXED — strong random secret from a secrets manager, short expiry,
// explicit algorithm allowlist (prevents alg-confusion attacks where an
// attacker swaps RS256 for HS256 and signs with the public key as a secret).
function issueTokenGood(userId: string, role: string) {
  return jwt.sign(
    { userId, role },
    process.env.JWT_SIGNING_SECRET!, // from secrets manager, 256-bit random
    { expiresIn: "15m", algorithm: "HS256", issuer: "api.myapp.com" }
  );
}
function verifyTokenGood(token: string) {
  return jwt.verify(token, process.env.JWT_SIGNING_SECRET!, {
    algorithms: ["HS256"], // pin explicitly — never trust the token's own header
    issuer: "api.myapp.com",
  });
}

// =========================================================================
// CSRF defense: SameSite cookie + double-submit CSRF token
// =========================================================================
app.post("/login", async (req, res) => {
  const token = issueTokenGood(user.id, user.role);
  res.cookie("session", token, {
    httpOnly: true,  // JS cannot read it — immune to XSS-based theft
    secure: true,    // only sent over HTTPS
    sameSite: "lax", // not attached on cross-site POST/fetch
    maxAge: 15 * 60 * 1000,
  });
  // Separate, readable CSRF token the client must echo back explicitly —
  // defense-in-depth even with SameSite set, and required for SameSite=None cases.
  const csrfToken = crypto.randomBytes(32).toString("hex");
  res.cookie("csrf_token", csrfToken, { secure: true, sameSite: "lax" });
  res.json({ csrfToken }); // also returned in body so JS can read & echo it
});

function requireCsrfToken(req: Request, res: Response, next: NextFunction) {
  const cookieToken = req.cookies.csrf_token;
  const headerToken = req.header("x-csrf-token");
  // Evil.com cannot read the victim's csrf_token cookie (same-origin policy
  // blocks reading it) and therefore cannot set a matching header value.
  if (!cookieToken || cookieToken !== headerToken) {
    return res.status(403).json({ error: "CSRF token mismatch" });
  }
  next();
}
app.post("/transfer", requireCsrfToken, transferHandler);

// =========================================================================
// CORS: explicit allowlist, never wildcard + credentials
// =========================================================================
import cors from "cors";

// BAD — never do this with credentials; browsers reject it anyway, but
// doing it without credentials is still a soft misconfiguration risk.
// app.use(cors({ origin: "*", credentials: true })); // DON'T

const ALLOWED_ORIGINS = new Set(["https://app.myapp.com", "https://admin.myapp.com"]);
app.use(cors({
  origin: (origin, callback) => {
    if (!origin || ALLOWED_ORIGINS.has(origin)) return callback(null, true);
    callback(new Error("origin not allowed"));
  },
  credentials: true,
}));

// =========================================================================
// CSP via helmet, with a per-request nonce for inline scripts
// =========================================================================
import helmet from "helmet";
import { randomBytes } from "node:crypto";

app.use((req, res, next) => {
  res.locals.cspNonce = randomBytes(16).toString("base64");
  next();
});
app.use((req, res, next) => {
  helmet.contentSecurityPolicy({
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'", `'nonce-${res.locals.cspNonce}'`], // no 'unsafe-inline'
      styleSrc: ["'self'"],
      imgSrc: ["'self'", "https://trusted-cdn.com"],
      connectSrc: ["'self'", "https://api.myapp.com"],
      objectSrc: ["'none'"],
      frameAncestors: ["'none'"], // also blocks clickjacking
    },
  })(req, res, next);
});

// =========================================================================
// Secrets: BAD (hardcoded) vs GOOD (secrets manager)
// =========================================================================
// BAD — committed to git, visible in history forever even after deletion.
const STRIPE_KEY_BAD = "sk_live_51H8x...actualRealKeyHere";

// GOOD — fetched at runtime, never touches source control.
import { SecretsManagerClient, GetSecretValueCommand } from "@aws-sdk/client-secrets-manager";
const smClient = new SecretsManagerClient({ region: "us-east-1" });
async function getStripeKey(): Promise {
  const resp = await smClient.send(new GetSecretValueCommand({ SecretId: "prod/stripe-key" }));
  return resp.SecretString!;
}

      Real-World Production Scenario at Scale

      At scale

      A fintech startup stored JWTs in localStorage "for simplicity" and had a third-party analytics script (added by marketing, outside engineering review) that got compromised upstream and began exfiltrating localStorage contents from every visitor's browser, including auth tokens. Because tokens had a 7-day expiry and no rotation/denylist mechanism, every stolen token remained valid and exploitable for up to a week after the compromise was detected and the malicious script removed. The actual incident remediation required forcing a global logout by rotating the JWT signing secret (invalidating every outstanding token, including legitimate users'), a far blunter and more disruptive instrument than if tokens had been HttpOnly cookies (immune to the exfiltration entirely) with short expiry and refresh rotation (limiting the compromise window to minutes, and allowing targeted revocation of only the affected refresh token family rather than a global secret rotation).

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      SameSite=Lax (the modern browser default when unspecified) does NOT protect against CSRF via a cross-site top-level GET navigation that triggers a state change server-side — if your API has a state-changing action reachable via GET (it shouldn't, but legacy code sometimes does), SameSite=Lax alone won't stop it. State-changing operations must use POST/PUT/DELETE and should never be triggerable by a simple link click regardless of cookie settings.

      • Never put a long-lived secret in a JWT itself (e.g., embedding a DB password in a claim) — JWTs are signed, not encrypted; anyone can base64-decode and read the payload.
      • Rotate secrets on a schedule and immediately on suspected compromise or when an employee with access leaves.
      • CORS misconfiguration and CSRF are independent problems — fixing CORS doesn't fix CSRF, and vice versa; they protect against different attack directions (CORS: can a foreign script read your data; CSRF: can a foreign page trigger an action using your credentials).
      • A CSP with 'unsafe-inline' in script-src provides almost no XSS protection — it's the single most common CSP misconfiguration that defeats the policy's purpose.

      Interview Questions

      Basic

      What's the fundamental tradeoff between session cookies and JWTs?

      Sessions need a server-side store but allow instant revocation; JWTs are stateless and scale horizontally easily but are hard to revoke before they expire.

      Follow-up: how would you get revocation-like behavior with JWTs?
      Why is storing a JWT in localStorage risky?

      Any JS running on the page (including from an XSS injection) can read localStorage, so a single XSS vulnerability anywhere on the origin can steal every user's token.

      Follow-up: what's the safer storage location and what new risk does it introduce?
      Explain CSRF in one sentence.

      A malicious site tricks a victim's browser into sending a state-changing request to another site, where the browser automatically attaches the victim's valid auth cookie, making the request appear legitimate.

      Follow-up: what are two independent defenses against it?
      What does CORS actually protect against?

      It controls whether a browser running JS from one origin can read a response from another origin — it's a browser-enforced relaxation of the same-origin policy, not a server-side access control mechanism.

      Follow-up: does CORS protect your API from a curl request? Why or why not?
      What is CSP and what attack does it mitigate?

      Content Security Policy, a response header restricting which sources can load scripts/styles/etc. It's a second line of defense against XSS — even if malicious markup is injected, the browser won't execute scripts from non-allowlisted sources.

      Follow-up: why does 'unsafe-inline' defeat most of CSP's XSS protection?
      Why shouldn't you hardcode secrets in source code?

      They end up in git history permanently (even after deletion from HEAD) and are visible to anyone with repo access, including in forks/clones made before removal — requiring full key rotation to remediate, not just a code change.

      Follow-up: what's the correct place for secrets instead?

      Medium

      Walk through exactly how SameSite=Lax mitigates CSRF, and what gap it leaves.

      SameSite=Lax prevents the cookie from being attached on most cross-site requests (forms/fetch POST from another origin), but still attaches it on a top-level cross-site GET navigation (clicking a link) — so if a state-changing action is reachable via GET, Lax alone doesn't protect it; state-changing actions must use POST/PUT/DELETE.

      Follow-up: when would you need SameSite=None instead, and what must accompany it?
      Explain refresh token rotation and how it detects token theft.

      Each refresh triggers invalidation of the used token and issuance of a new one. If an attacker steals a refresh token and uses it after the legitimate user already rotated past it, the server sees a reuse of an already-invalidated token — a strong signal of theft — and can revoke the entire token family, forcing re-login everywhere.

      Follow-up: what happens if the attacker uses the stolen token BEFORE the legitimate user does?
      Why is "Access-Control-Allow-Origin: * with credentials: true" dangerous, and how do browsers handle it?

      It would let any site make authenticated cross-origin requests using the victim's cookies and read the response — browsers actually refuse to honor a wildcard origin when credentials are involved, forcing an explicit origin to be echoed back, so a correctly-coded server should validate the request's Origin against an allowlist and echo only that specific origin, never a literal wildcard.

      Follow-up: what's the risk of an overly permissive origin-validation function (e.g., a loose regex)?
      How would you design a CSP for a React SPA that uses a CDN for some assets and needs inline styles from a CSS-in-JS library?

      Allowlist the specific CDN origin for script-src/img-src/font-src as needed; for CSS-in-JS requiring inline styles, prefer a nonce-based style-src over 'unsafe-inline' if the library supports nonce injection, or accept a scoped 'unsafe-inline' for style-src specifically (styles are lower risk than scripts) while keeping script-src strict with nonces — never relax script-src for convenience.

      Follow-up: why is relaxing style-src generally lower risk than relaxing script-src?
      What's algorithm confusion in JWT verification, and how do you prevent it?

      If a server verifies a JWT using whatever algorithm the token's own header claims (instead of pinning an expected algorithm), an attacker can take a token meant to be verified with an RSA public key (RS256) and resubmit it signed with HS256 using the public key (which is, well, public) as the HMAC secret — if the library blindly trusts the header's declared algorithm, this forged token verifies successfully. Prevention: always explicitly pass an algorithms allowlist to the verify call, never derive it from the token.

      Follow-up: why is the public key being "public" the crux of this exploit?

      Advanced

      Design a full auth architecture for a multi-tenant SaaS with a React SPA, a mobile app, and server-to-server API access, covering token storage and revocation for each client type.

      SPA: HttpOnly/Secure/SameSite cookie for the session, with a short-lived access token and refresh rotation handled via a same-origin refresh endpoint (cookie-based refresh avoids exposing the refresh token to JS at all). Mobile: refresh/access tokens stored in platform secure storage (Keychain/Keystore), since cookies don't apply the same way — CSRF isn't a concern for non-browser clients, but token theft via device compromise still is, so short access-token expiry still matters. Server-to-server: client credentials grant (OAuth2) issuing short-lived tokens scoped tightly per integration, with per-client rate limiting and audit logging. Revocation: maintain a short-lived denylist cache (Redis) keyed by token ID for emergency revocation within the access-token's short window, backed by refresh-token-family revocation for anything longer-lived.

      Follow-up: how do you handle token refresh for the mobile app without a browser's cookie mechanism?
      How would you detect and respond to a credential-stuffing attack (A07) at scale, distinguishing it from normal failed-login noise?

      Credential stuffing shows a distinctive pattern: a high volume of login attempts from a wide/shifting IP range or ASN, each attempt a DIFFERENT username/password pair tried once or twice (not the same account repeatedly, which looks more like simple brute force), often correlated with known-breach credential lists. Detection: rate-limit per-IP AND per-account independently, track failed-login velocity with anomaly detection (sudden spike vs. baseline), and use a bot-detection/device-fingerprinting signal alongside credential checks. Response: progressive friction (CAPTCHA after N failures) rather than a hard block that could itself enable a DoS against legitimate users whose credentials appear in the attack list, plus proactive forced password reset for accounts matched against known breach corpora (have-i-been-pwned-style checks at signup/login).

      Follow-up: why is a flat per-account lockout policy itself exploitable as a denial-of-service vector?
      Your org wants to move all secrets to a centralized secrets manager (Vault) but has 60 services with hardcoded env-var based configs. Design the migration.

      Introduce an abstraction layer first (a small config-loading library every service already imports or can adopt incrementally) that reads from env vars by default but can be pointed at Vault via a feature flag per service — this lets you migrate one service at a time without a coordinated big-bang cutover. Rotate every migrated secret immediately upon migration (the old hardcoded/env value should be considered compromised by virtue of having existed in plaintext config). Use dynamic secrets (Vault-issued short-lived DB credentials) where supported instead of static secrets, eliminating long-lived credentials entirely for those integrations. Gate the migration's completion on a secret-scanning CI check across all 60 repos to catch any remaining hardcoded values.

      Follow-up: why are dynamic, short-lived secrets strictly better than even a well-managed static secret in Vault?
      How would you architect defenses against a token replay attack even with short-lived JWTs and HTTPS everywhere?

      Even over HTTPS, a token can be captured via a compromised client device, a malicious browser extension, or a MITM on a misconfigured network — short expiry limits but doesn't eliminate the window. Add binding: tie the token to additional context (e.g., a device fingerprint or a DPoP-style proof-of-possession key the client must sign each request with) so a bare stolen token string is insufficient without also controlling the bound private key; combine with anomaly detection (sudden impossible-travel IP geolocation jump between consecutive requests on the same token) to flag likely replay even within the token's valid window.

      Follow-up: what is DPoP (Demonstrating Proof of Possession) and how does it change the threat model?
      Critique this design: "We'll just disable CORS entirely to stop fighting with it" — what actually happens, and what's the real fix for the underlying frustration?

      "Disabling CORS" usually means setting an overly permissive policy (wildcard origin, or echoing back any origin) rather than actually disabling a browser-enforced mechanism you don't control server-side — this removes the protection CORS provides against malicious sites reading your API responses with a victim's credentials, directly enabling cross-origin credential-based data theft. The real fix for CORS frustration during development is usually a proper local dev proxy (so the frontend and API appear same-origin in dev) and a correctly maintained explicit allowlist in every real environment, not loosening production policy to make local development easier.

      Follow-up: how would you set up local development to avoid CORS friction without weakening production config?

      Practice Assignments

      Beginner (30-60 min)

      Implement HttpOnly cookie auth with SameSite

      Build a login endpoint that sets a session as an HttpOnly, Secure, SameSite=Lax cookie instead of returning a token in the JSON body. Build a protected route that reads it.

      • Confirm via devtools that JS (document.cookie) cannot read the session cookie.
      • Confirm the cookie is NOT sent on a simulated cross-site POST (use a second local origin to test).

      Acceptance criteria: A screenshot/console log proving document.cookie doesn't expose the session value, and a cross-origin test proving the cookie isn't attached.

      Hints

      Run two local servers on different ports to simulate cross-origin for the SameSite test — different ports count as different origins.

      Bonus: Add a CSRF double-submit token and a test proving a request without it is rejected.

      Intermediate (2-4 hrs)

      Build a CSRF exploit against an unprotected endpoint, then fix it

      Build an app with a state-changing POST endpoint relying only on a SameSite=None (or unset, pre-2020 browser behavior simulation) cookie for auth. Build a second "evil" HTML page with an auto-submitting form targeting it, served from a different origin, and demonstrate the forged request succeeding. Then fix it with SameSite=Lax and/or a CSRF token and show the evil page's attack now fails.

      • Evil page is a separate static HTML file served on a different port/origin.
      • Document the exact state change that occurred without the victim's intent.
      • After the fix, the same evil page's attack must fail (cookie not attached, or CSRF token mismatch).

      Acceptance criteria: Before/after proof that the identical evil page succeeds, then fails.

      Hints

      You'll need to explicitly set SameSite=None to simulate the vulnerable case on modern browsers, since Lax is now the default — that itself is worth noting in your write-up.

      Bonus: Add Origin-header validation as a third, independent defense layer.

      Advanced (1-2 days)

      Full auth system with refresh rotation, theft detection, and secrets management

      Build an auth system with short-lived JWT access tokens (15 min), refresh token rotation stored server-side (hashed), theft detection (reuse of an invalidated refresh token revokes the whole family), and CSP + CORS configured correctly for a separate frontend origin. Store the JWT signing secret via environment variables loaded from a local secrets-manager-style setup (even a simple Vault dev-mode container), not hardcoded.

      • Demonstrate normal refresh flow working across multiple refresh cycles.
      • Simulate theft: capture a refresh token, let the legitimate client rotate past it, then replay the stolen one and show the system detects reuse and revokes the family.
      • Confirm CSP blocks an injected inline script in a deliberately-left XSS test page.
      Hints

      This is intentionally open-ended — think about what server-side state you need (even with "stateless" JWTs) to detect reuse, since pure statelessness and theft detection are in tension.

      Bonus: Add device/session fingerprinting so the user can see and revoke individual active sessions.

      Quick Revision Cheat Sheet

      • Session cookies: easy revocation, needs shared store. JWT: stateless/scalable, hard to revoke before expiry.
      • Store auth tokens in HttpOnly+Secure+SameSite cookies, never localStorage (XSS-proof vs. not).
      • CSRF: browser auto-attaches cookies cross-site; defend with SameSite + CSRF token + Origin check.
      • CORS protects browser JS from reading cross-origin responses — it is not a server access-control mechanism and doesn't stop curl.
      • Never combine wildcard origin with credentials: true.
      • CSP is defense-in-depth against XSS; 'unsafe-inline' in script-src defeats most of its value — use nonces instead.
      • Pin JWT algorithms explicitly on verify; never trust the token header's declared algorithm.
      • Refresh token rotation + reuse detection gives you theft detection without full statefulness on every request.
      • Never hardcode secrets — use a secrets manager/env vars injected at deploy time, scan for leaks in CI.
      • SameSite=Lax still allows cookie attach on top-level cross-site GET navigation — never make state changes via GET.
