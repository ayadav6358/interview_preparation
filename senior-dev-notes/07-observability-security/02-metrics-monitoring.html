    Metrics, Monitoring & Alerting

    ⏱ ~2.5 hrs📍 Chapter 2 of 6

    One-line summary: Metrics are pre-aggregated numeric time series (counters, gauges, histograms) that are cheap to collect at any volume and form the backbone of dashboards and alerting — Prometheus is the de facto standard for collecting them, Grafana for visualizing them.

    On this page

      Why It Matters for a Senior Developer

      Logs tell you what happened to one request; metrics tell you the health of the whole system at a glance and are what pages you at 3am before a customer complains. A senior engineer is expected to instrument new services with the right metrics from day one (not bolt them on after the first outage), design alerts that detect real problems without paging on noise, and reason about the RED/USE methods when asked "what would you monitor for this service" in an interview. This is also where SLIs/SLOs/error budgets — a very common senior/staff interview topic — come from.

      Prerequisites

      Basic familiarity with HTTP services and time-series concepts. Related: Logging, Distributed Tracing.

      Core Concepts

      Metric types: counter, gauge, histogram, summary

      A counter only increases (resets to 0 on restart) — total requests served, total errors. A gauge can go up or down — current memory usage, active connections, queue depth. A histogram buckets observations (e.g., request duration) into configurable ranges and lets you compute approximate quantiles (p50, p95, p99) server-side at query time from the bucket counts — this is what Prometheus recommends because bucket counts aggregate correctly across multiple instances. A summary computes quantiles client-side before exposing them, which is more precise per-instance but cannot be meaningfully aggregated across instances (you can't average two p99s and get a correct p99) — this is why histograms are generally preferred for anything you'll aggregate across a fleet.

      The RED and USE methods

      RED (for request-driven services): Rate (requests/sec), Errors (error rate), Duration (latency distribution). This is the minimum viable instrumentation for any HTTP/RPC service — if you have only these three per endpoint, you can answer "is this service healthy" in one glance. USE (for resources, from Brendan Gregg): Utilization, Saturation, Errors — used for infrastructure-level resources like CPU, disk, network (e.g., CPU utilization %, CPU saturation = run-queue length, disk errors). Senior interview framing: RED for your services, USE for the infra underneath them.

      Pull vs push metric collection

      Prometheus uses a pull model: it scrapes a /metrics HTTP endpoint on each target at a configured interval (e.g., every 15s). This is simpler to operate (no need for every service to know where to push to, no fan-in bottleneck) and makes "is this target even reachable" itself an observable signal (the up metric). The downside: short-lived jobs (e.g., a serverless function, a batch job) may finish before a scrape happens — Prometheus solves this with a Pushgateway, where such jobs push their final metrics once, and Prometheus scrapes the gateway instead. StatsD/Graphite use a push model (every instance pushes metrics proactively), which fits short-lived processes more naturally but requires the collector to handle fan-in from every instance.

      Labels and cardinality

      Prometheus metrics have key-value labels (http_requests_total{method="GET", route="/orders", status="200"}) that let you slice and dice at query time. The critical senior-level gotcha: every unique combination of label values creates a new time series. Using a label like userId or a raw URL (instead of a normalized route template like /orders/:id) on a metric is a cardinality explosion — millions of users or raw paths means millions of time series, which can take down a Prometheus instance's memory and query performance. Always use bounded, low-cardinality labels; push high-cardinality data (user IDs, request IDs) to logs or traces instead.

      SLIs, SLOs, and error budgets

      An SLI (Service Level Indicator) is a measured metric — e.g., "% of requests served in under 300ms." An SLO (Service Level Objective) is a target for that SLI — e.g., "99.9% of requests under 300ms, measured over 30 days." The error budget is the allowed failure margin implied by the SLO (0.1% here) — once you've "spent" your error budget for the period (too many slow or failed requests), the team should stop shipping risky changes and focus on reliability until the budget resets. This reframes alerting from "page on every error" to "page when we're burning error budget too fast to hit the SLO" — this is the basis of Google SRE's multi-window, multi-burn-rate alerting, a favorite staff-level interview topic.

      How It Works Under the Hood

      Prometheus's server has three core pieces: a scraper that pulls /metrics text-format output from each target on an interval, a time-series database (TSDB) that stores samples on disk in compressed chunks keyed by metric+label-set, and PromQL, a query language for slicing/aggregating those series (rate(), histogram_quantile(), sum by (route) (...)). Alertmanager is a separate component: Prometheus evaluates alerting rules (PromQL expressions that, when true for a configured duration, fire an alert) and sends firing alerts to Alertmanager, which handles deduplication, grouping (so 50 pods failing the same way becomes 1 page, not 50), silencing, and routing (Slack, PagerDuty, email) based on label-matching rules. Grafana is purely a query/visualization layer on top — it doesn't store data itself, it queries Prometheus (or Loki, or other data sources) live.

      Code Examples

      // -----------------------------------------------------------------------
// 1. prom-client: RED metrics for an Express app, with route templates
//    (not raw URLs) to avoid cardinality explosion.
// -----------------------------------------------------------------------
import express from "express";
import client from "prom-client";

const register = new client.Registry();
client.collectDefaultMetrics({ register }); // process/CPU/memory/event-loop metrics

const httpRequestsTotal = new client.Counter({
  name: "http_requests_total",
  help: "Total HTTP requests",
  labelNames: ["method", "route", "status"],
  registers: [register],
});

const httpRequestDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "HTTP request duration in seconds",
  labelNames: ["method", "route", "status"],
  buckets: [0.01, 0.05, 0.1, 0.3, 0.5, 1, 2, 5], // tuned to this service's expected latency
  registers: [register],
});

const app = express();

app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    // IMPORTANT: req.route.path gives the route TEMPLATE ("/orders/:id"),
    // never req.path/req.originalUrl — that would create one time series
    // per unique order ID = cardinality explosion.
    const route = req.route?.path ?? "unmatched";
    const labels = { method: req.method, route, status: String(res.statusCode) };
    const durationSeconds = Number(process.hrtime.bigint() - start) / 1e9;
    httpRequestsTotal.inc(labels);
    httpRequestDuration.observe(labels, durationSeconds);
  });
  next();
});

app.get("/orders/:id", (req, res) => res.json({ id: req.params.id }));

app.get("/metrics", async (_req, res) => {
  res.set("Content-Type", register.contentType);
  res.end(await register.metrics());
});

      Real-World Production Scenario at Scale

      At scale

      An e-commerce platform added a metric labeled by raw request path during a Black Friday prep sprint (http_requests_total{path="/products/skateboard-xl-navy-blue"} for every unique product slug). Within hours, Prometheus memory usage climbed from 4GB to 40GB and queries started timing out — a textbook cardinality explosion, with hundreds of thousands of unique product slugs each creating their own time series. The fix was immediate: redeploy with the label changed to a normalized route template (/products/:slug), delete the exploded series, and add a cardinality-limit alert (prometheus_tsdb_symbol_table_size_bytes trending up) so this class of regression pages someone before it takes down monitoring itself — which is especially dangerous because losing monitoring during your highest-traffic period of the year is its own incident.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Alerting directly on raw thresholds ("CPU > 80%") without context causes chronic false pages — 80% CPU might be totally fine for a batch-processing node and catastrophic for a latency-sensitive API node. Alert on symptoms that map to user impact (latency, error rate, SLO burn) rather than causes (CPU, memory) wherever possible; use the resource metrics for debugging once paged, not as the page trigger itself.

      • Use histograms (not summaries) for anything you need to aggregate across instances.
      • Pick bucket boundaries deliberately based on your actual latency distribution — default buckets are rarely right for your service.
      • Default Prometheus retention is short (often 15 days) — pair with long-term storage (Thanos, Mimir, Cortex) if you need historical trend analysis.
      • Alertmanager grouping/inhibition rules matter as much as the alert rule itself — ungrouped alerts during a real outage can page an on-call engineer hundreds of times in minutes.

      Interview Questions

      Basic

      What are the four main Prometheus metric types?

      Counter (monotonically increasing), Gauge (goes up/down), Histogram (bucketed observations with aggregatable quantiles), Summary (client-side quantiles, not aggregatable).

      Follow-up: why can't you average two summaries' p99 across instances?
      Explain the RED method.

      Rate, Errors, Duration — the minimum metrics to instrument any request-driven service to answer "is this healthy" at a glance.

      Follow-up: what's the USE method and when would you use it instead?
      What's the difference between pull-based and push-based metric collection?

      Pull: the monitoring system scrapes a metrics endpoint on each target on an interval (Prometheus). Push: each instance proactively sends metrics to a collector (StatsD/Graphite).

      Follow-up: how does Prometheus handle a short-lived job that would finish before a scrape?
      What is cardinality in the context of metrics, and why is it dangerous?

      The number of unique label-value combinations for a metric. High-cardinality labels (user IDs, raw URLs) create unbounded numbers of time series, which can exhaust memory/storage on the metrics backend.

      Follow-up: where should high-cardinality data go instead?
      What does Grafana do, and what does it not do?

      It's a visualization/dashboarding layer that queries data sources (Prometheus, Loki, etc.) live; it does not store the data itself.

      Follow-up: what happens to a Grafana dashboard if the underlying Prometheus instance is down?
      What is Alertmanager and how does it relate to Prometheus?

      A separate component that receives firing alerts from Prometheus and handles deduplication, grouping, silencing, and routing to notification channels (Slack, PagerDuty).

      Follow-up: why is grouping important during a large-scale outage?
      What is an SLO and how does it differ from an SLA?

      An SLO is an internal reliability target (e.g., 99.9% of requests under 300ms); an SLA is an external, often contractual, commitment to customers, usually with consequences (credits/penalties) if missed, and typically looser than the internal SLO.

      Follow-up: why would you set your SLO stricter than your SLA?

      Medium

      Why does Prometheus prefer histograms over summaries for service-level latency metrics?

      Histogram bucket counts can be summed across instances at query time and then a quantile computed from the aggregated buckets — giving a fleet-wide p95/p99. Summary quantiles are computed client-side per instance and mathematically cannot be correctly combined across instances (averaging percentiles is not valid).

      Follow-up: what's the cost of histograms (what do you pay for this aggregatability)?
      Design an alerting strategy for an API with a 99.9% monthly availability SLO.

      Use multi-window, multi-burn-rate alerts: a fast-burn alert (short window, high burn rate threshold) for "page now, we'll exhaust the budget in hours," and a slow-burn alert (long window, lower threshold) for "ticket, not page, we're trending toward exhausting the budget over days" — this avoids paging on brief blips while still catching slow degradations.

      Follow-up: why use two windows instead of just one threshold?
      How would you instrument a service to avoid cardinality explosions while still being able to debug per-customer issues?

      Keep metric labels bounded (route templates, status codes, a small fixed set of tiers/plans) and push identifying, high-cardinality context (customerId, requestId) to logs/traces, correlating via a shared ID when you need to go from "metric shows a spike" to "which specific customers/requests."

      Follow-up: what's an acceptable cardinality budget rule of thumb for a label?
      Explain error budgets and how they change team behavior day to day.

      An error budget is the allowed unreliability implied by an SLO over a period. While budget remains, teams can ship faster/take more risk; once exhausted, the team should pause risky releases and prioritize reliability work until the budget replenishes — this gives a data-driven, non-political way to balance velocity vs. stability.

      Follow-up: who should own the decision to freeze releases when budget is exhausted?
      Your Prometheus instance is running out of memory. How do you diagnose and fix it?

      Check prometheus_tsdb_head_series and look for metrics/labels with unexpectedly high series counts (often a recently added high-cardinality label); fix by removing/relabeling the offending label, and consider remote-write to long-term storage (Thanos/Mimir) with downsampling instead of keeping everything in local TSDB.

      Follow-up: how would you prevent this class of issue from recurring across teams?
      What's the difference between Thanos/Mimir/Cortex and vanilla Prometheus?

      They provide horizontally scalable, long-term, highly-available storage and global querying across many Prometheus instances, since vanilla Prometheus is single-node with limited local retention by design.

      Follow-up: why might a small team not need this yet?

      Advanced

      Design the full monitoring/alerting architecture for a multi-region, 200-service platform.

      Per-cluster Prometheus (or Agent mode) scraping locally to avoid cross-region scrape latency/cost, remote-writing into a global long-term store (Thanos/Mimir) for cross-region queries and historical analysis, Alertmanager in HA pairs per region with a global routing tree, SLO dashboards per service owned by that team, and a platform-level "meta-monitoring" layer watching the monitoring stack itself (so monitoring outages are themselves detected).

      Follow-up: how do you avoid the global store becoming a single point of failure for alerting?
      How would you design multi-burn-rate alerting mathematically, and justify the burn-rate multiplier you choose?

      If your error budget is (1 - SLO) over a period P, a burn rate of 1x exhausts the budget exactly at P. A short-window fast-burn alert might trigger at 14.4x burn rate over 1 hour (exhausts a 30-day budget in ~2 days) — tuned to balance detection speed against false-positive rate for short traffic blips; a slow-burn alert might trigger at 6x over 6 hours, catching sustained degradation that a 1-hour window would miss or dismiss as noise.

      Follow-up: how do you validate your chosen multipliers don't produce excessive false pages in practice?
      A key metric silently stopped reporting for 3 days before anyone noticed — how do you prevent this class of failure?

      Add "metric absence" alerts (alert if a critical series hasn't been scraped/updated in N minutes, using absent() or the up metric), treat dashboards going flat/empty as itself suspicious rather than assuming "no news is good news," and include synthetic/canary traffic that should always produce a baseline metric value so true silence is distinguishable from "genuinely zero errors."

      Follow-up: why is "no alerts fired" not the same as "system is healthy"?
      How do you decide what NOT to alert on, given that over-alerting is as dangerous as under-alerting?

      Every alert should map to concrete, immediate human action and real user impact — if an alert's runbook is "just look at it" or it routinely gets ack'd and ignored, it should be downgraded to a dashboard/ticket instead of a page. Periodically audit alert-to-action ratio and prune/demote alerts with low actionability.

      Follow-up: how would you measure "alert quality" quantitatively across a team?
      Compare building your own Prometheus/Grafana/Alertmanager stack vs. a managed vendor (Datadog, Grafana Cloud) for a Series B startup scaling fast.

      Self-hosted gives cost control at real scale and full data ownership but requires dedicated ops investment (HA, storage scaling, upgrades); managed vendors get you production-grade observability immediately with less ops burden but costs scale aggressively with volume/cardinality and you're dependent on their roadmap/pricing changes. Most fast-scaling startups start managed and migrate to self-hosted once volume makes the vendor bill a board-level conversation.

      Follow-up: what specific metric (cost per metric point, cost per host) would you track to know when to switch?

      Practice Assignments

      Beginner (30-60 min)

      Instrument an Express app with RED metrics

      Add prom-client to an Express app with 2-3 routes. Expose a /metrics endpoint with a counter and histogram following the RED method, using route templates as labels.

      • Counter: total requests by method/route/status.
      • Histogram: request duration by method/route/status.
      • Verify in a raw curl to /metrics that labels use route templates, not raw paths.

      Acceptance criteria: Hitting /orders/1 and /orders/2 produces metrics under the same route="/orders/:id" label, not two separate series.

      Hints

      Express exposes the matched route template at req.route.path — use that, not req.path.

      Bonus: Run Prometheus + Grafana via Docker Compose and scrape your app.

      Intermediate (2-4 hrs)

      PromQL dashboard + alert rule

      Using the instrumented app from the beginner assignment, write PromQL queries for request rate, error rate %, and p95 latency per route, build a Grafana dashboard with them, and write a Prometheus alert rule that fires when error rate exceeds 5% for 5 minutes.

      • Dashboard has at least 3 panels: rate, error %, p95 latency.
      • Alert rule defined in YAML, loaded into Prometheus, verified to actually fire (inject errors to trigger it).
      • Route the alert to a webhook or log output via Alertmanager config.

      Acceptance criteria: You can demonstrate the alert transitioning from inactive → pending → firing in the Prometheus UI.

      Hints

      Use for: 5m in the alert rule to require sustained breach, not a single noisy sample.

      Bonus: Add a cardinality-exploding label on purpose, observe the series count grow, then fix it.

      Advanced (1-2 days)

      Multi-burn-rate SLO alerting system

      Define a 99.9% latency SLO (e.g., 99.9% of requests under 500ms over 30 days) for your instrumented service. Implement fast-burn and slow-burn alert rules, load-test to intentionally burn budget at different rates, and verify each alert fires at the appropriate severity/urgency.

      • Calculate and justify your burn-rate multipliers and windows in a short write-up.
      • Demonstrate a short traffic blip NOT triggering the slow-burn alert but triggering fast-burn if severe enough.
      • Demonstrate a sustained moderate degradation triggering slow-burn without ever tripping fast-burn.
      Hints

      This is intentionally open-ended — think in terms of budget-exhaustion time, not raw thresholds, when picking your multipliers.

      Bonus: Add a second SLI (error rate) and combine both into one SLO dashboard.

      Quick Revision Cheat Sheet

      • 4 metric types: Counter, Gauge, Histogram, Summary — use Histogram for aggregatable quantiles.
      • RED for services (Rate, Errors, Duration); USE for infra resources (Utilization, Saturation, Errors).
      • Prometheus = pull model (scrapes /metrics); Pushgateway bridges short-lived jobs into the pull model.
      • Never put unbounded values (user IDs, raw URLs) in metric labels — cardinality explosion.
      • Use route templates, not raw paths, as labels.
      • SLI = measured indicator; SLO = internal target; SLA = external/contractual commitment.
      • Error budget = allowed unreliability from the SLO; exhausting it should slow down risky shipping.
      • Alert on symptoms (latency/error rate/SLO burn), not raw causes (CPU%) — fewer false pages.
      • Multi-window, multi-burn-rate alerting catches both sharp spikes and slow sustained degradation.
      • Grafana visualizes; it doesn't store data — Prometheus/Loki/Tempo are the actual stores.
