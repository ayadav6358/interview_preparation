    Event Loop Internals & libuv

    ⏱ 3 hrs📍 Chapter 1 of 9

    One-line summary: Node's "single-threaded, non-blocking" story is a simplification over a multi-phase C event loop (libuv) backed by a real OS thread pool — knowing the six phases and exactly when microtasks drain is what separates "I've used async/await" from "I can debug event-loop starvation in prod."

    On this page

      Why It Matters for a Senior Developer

      Every "why is my API p99 latency spiking under load" and "why did this setInterval drift" and "why does this Promise.then fire before this setTimeout(fn,0)" incident traces back to event loop mechanics. At senior level you're expected to reason about event loop lag (the gap between when a callback should run and when it actually runs) as a first-class production metric, not just know that Node is "async." Interviewers use this topic to separate candidates who've memorized "Node is single-threaded" from those who understand that I/O is handled by a real OS-level thread pool (libuv) and that a single slow synchronous call blocks every request on the process, including ones that have nothing to do with it.

      Why

      A CPU-bound JSON.parse on a 50MB payload, a synchronous bcrypt.hashSync, or a poorly written regex (catastrophic backtracking) all block the single JS thread. Nothing else runs — no other request, no timer, no I/O callback — until it returns. This is the single most common cause of "random" latency spikes in Node services at scale, and senior engineers are expected to spot it from a flame graph or an event-loop-lag metric within minutes.

      Prerequisites

      Comfortable with async/await, Promises, and basic Node APIs (fs, http, setTimeout). Related: Streams & Backpressure, Worker Threads & Clustering.

      Core Concepts

      The basics: call stack, heap, and the "non-blocking" illusion

      V8 runs JavaScript on a single thread with one call stack. "Non-blocking I/O" means: when you call fs.readFile, Node doesn't block that thread waiting for disk — it hands the request to libuv, which either issues an async syscall (on Linux: io_uring/epoll for network; for file I/O, historically no universal async file API, so libuv uses its thread pool) and registers a callback. The JS thread is immediately free to do other work. When the OS/thread pool reports completion, libuv queues your callback to run on the next appropriate event loop phase.

      The six libuv phases, in exact order

      Each iteration of the event loop ("a tick") runs these phases in this fixed order. After every callback (and after every phase transition) Node drains the microtask queue (Promise callbacks, queueMicrotask) and then process.nextTick queue (nextTick has even higher priority than microtasks, draining first).

      1. timers — runs callbacks scheduled by setTimeout/setInterval whose threshold has elapsed. Not exact: "after at least N ms," not "at exactly N ms" — the loop may be busy in another phase.
      2. pending callbacks (a.k.a. pending I/O callbacks) — some system errors (e.g. certain TCP errors) are deferred here to run just after timers.
      3. idle/prepare — internal libuv housekeeping, rarely user-visible.
      4. poll — the heart of the loop. Retrieves new I/O events (completed reads/writes, incoming connections) and executes their callbacks. If no timers are due, poll will block here waiting for events (this is how Node avoids busy-spinning the CPU when idle). If timers exist, poll computes how long it may block based on the next timer deadline.
      5. check — runs setImmediate callbacks. This phase exists specifically so you can schedule "run right after I/O, before the next timer phase" — this is why setImmediate inside an I/O callback always fires before a setTimeout(fn,0) scheduled at the same point, but the ordering between them at the top level (outside any I/O callback) is not guaranteed.
      6. close callbacks — socket.on('close', ...) and similar cleanup handlers.

      Between every single callback (not just between phases), Node checks and fully drains: process.nextTick queue first, then the Promise microtask queue, until both are empty — including any new nextTicks/microtasks scheduled by callbacks that ran during the drain. This is why a tight recursive process.nextTick loop can starve the event loop entirely (I/O never gets a chance to run) — a classic "senior" gotcha question.

      libuv's thread pool, and what actually goes through it

      libuv maintains a thread pool (default size 4, configurable via UV_THREADPOOL_SIZE, env var, must be set before any thread-pool-using call) used for operations the OS has no good async primitive for, or that Node chooses to offload: most fs module file operations, DNS lookups via dns.lookup (but not dns.resolve*, which use c-ares async and don't touch the pool), crypto.pbkdf2/scrypt/randomBytes (async variants), and zlib compression. Network I/O (TCP/HTTP sockets) does not use the thread pool — it uses the OS's native async mechanisms (epoll/kqueue/IOCP) directly via poll. This distinction matters: 4 slow fs.readFile calls in flight will exhaust the thread pool and queue a 5th behind them, even though your HTTP server can still accept new connections just fine — but if that 5th fs call is on the critical path of every request, you still get a latency cliff.

      Gotcha

      Increasing UV_THREADPOOL_SIZE is a legitimate, common production tuning knob when you're bottlenecked on file I/O or bcrypt/crypto throughput — but it's capped around 1024 and every thread costs memory; it does nothing for CPU-bound JS or network I/O bottlenecks. Interviewers love asking "will raising the thread pool size fix slow API responses" — the answer is "only if the slowness is from one of the specific thread-pool-backed APIs, which network-bound APIs usually aren't."

      How It Works Under the Hood

      Microtasks vs macrotasks, precisely: a "macrotask" is any phase-scheduled callback (timer, I/O, setImmediate, close). A "microtask" is a Promise reaction or queueMicrotask callback. The browser and Node agree that microtasks drain fully before the next macrotask — but Node adds process.nextTick as a third, higher-priority queue that drains before the Promise microtask queue, every single time, even interleaved mid-drain. Practically: nextTick(a); Promise.resolve().then(b); nextTick(c); prints a, c, b — both nextTicks fully drain (including any nextTick added by a itself) before the Promise queue is touched at all.

      Why does setTimeout(fn, 0) sometimes run before, sometimes after, an immediately-resolved Promise chain relative to I/O? Because the engine clamps minimum timer delay (effectively ~1ms) and whether the poll phase has anything pending changes how long the loop waits before reaching the timers phase again. At the top of a fresh script (no pending I/O), setImmediate vs setTimeout(fn,0) ordering is non-deterministic because it depends on process startup timing; inside an I/O callback it is always deterministic (setImmediate wins, because check comes right after poll).

      Code Examples

      // 1) Ordering proof: nextTick > microtask > timers/setImmediate
console.log('start');

setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));

console.log('end');

// Output (guaranteed): start, end, nextTick, promise, then timeout/immediate
// (timeout vs immediate order is NOT guaranteed at top level)


// 2) Inside an I/O callback, setImmediate ALWAYS wins over setTimeout(fn, 0)
import { readFile } from 'node:fs';

readFile(__filename, () => {
  setTimeout(() => console.log('timeout inside I/O'), 0);
  setImmediate(() => console.log('immediate inside I/O'));
  // Deterministic: 'immediate inside I/O' always logs first here,
  // because check phase runs immediately after poll, before the loop
  // cycles back around to timers.
});


// 3) BAD: blocking the event loop with synchronous crypto
import { createHash } from 'node:crypto';
app.post('/hash', (req, res) => {
  // Blocks the ENTIRE process for the duration — every other
  // in-flight request stalls. On a busy API this is a p99 killer.
  const hash = createHash('sha256').update(req.body.data).digest('hex');
  res.json({ hash });
});

// GOOD: offload CPU-bound work to the thread pool or a worker thread
import { pbkdf2 } from 'node:crypto';
app.post('/hash', (req, res) => {
  pbkdf2(req.body.data, 'salt', 100_000, 64, 'sha512', (err, derivedKey) => {
    if (err) return res.status(500).end();
    res.json({ hash: derivedKey.toString('hex') });
  });
  // Runs on libuv's thread pool — event loop stays free for other requests.
});


// 4) Measuring real event-loop lag in production (use this metric, not CPU%)
import { monitorEventLoopDelay } from 'node:perf_hooks';

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  // p50/p99 lag in milliseconds — alert if p99 > ~50-100ms sustained
  console.log({ p50: histogram.mean / 1e6, p99: histogram.percentile(99) / 1e6 });
  histogram.reset();
}, 10_000).unref(); // unref() so this interval alone can't keep the process alive

      Real-World Production Scenario at Scale

      At scale

      A payments API served ~3k req/s fine in staging, but in production p99 latency periodically spiked to 2-4 seconds for a few seconds at a time, seemingly randomly, correlated with no CPU or memory alert (CPU avg looked fine — 40%). The team added monitorEventLoopDelay and found event-loop lag spiking to 1800ms exactly when the spikes happened. Root cause: a reporting endpoint, hit a few times a minute by an internal dashboard, did a synchronous JSON.parse + in-memory .filter().map().sort() over a multi-MB array pulled from Redis — fine at low traffic, catastrophic under concurrent load because it blocked the entire process, including unrelated payment requests, for the duration of that one slow request. Average CPU looked healthy because the blocking was bursty, not sustained. Fix: moved the heavy transform to a worker thread (see Chapter 3) and added event-loop-lag as a first-class dashboard metric and alert, not just CPU/memory.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Treating async functions as "non-blocking by magic." An async function that does heavy synchronous work before its first await blocks exactly as much as a non-async function — async only changes how the return value is wrapped and scheduled, not whether the body runs synchronously up to the first await.

      • Never use CPU-heavy synchronous APIs (`*Sync` variants, synchronous crypto/zlib, big JSON parses, naive regex) on the request path of a high-throughput service — offload to worker_threads or the thread pool.
      • Prefer `setImmediate` over `setTimeout(fn, 0)` when you mean "run after I/O, as soon as possible" — it communicates intent and has deterministic ordering relative to I/O callbacks.
      • Don't build unbounded `process.nextTick` recursion — it can starve I/O indefinitely since nextTick fully drains (including newly queued ones) before the loop can proceed.
      • Monitor event-loop lag (`monitorEventLoopDelay`) as a core production metric, not just CPU/memory — it's the direct signal for "is the loop currently responsive."
      • Remember `dns.lookup` uses the thread pool but `dns.resolve4`/`resolve6` don't — under thread-pool contention, swapping to `dns.resolve4` can unblock unrelated file I/O.

      Interview Questions

      Basic

      Is Node.js single-threaded?

      The JS execution thread is single-threaded, but Node itself is not — libuv runs a thread pool (default 4 threads) for certain blocking operations (file I/O, DNS lookup, some crypto, zlib), and the OS handles network I/O asynchronously via its own async primitives (epoll/kqueue/IOCP), not the JS thread. "Single-threaded" refers specifically to where your JS callbacks execute.

      Follow-up: name three Node APIs that use the thread pool and one common API that does not.
      What's the difference between setTimeout(fn, 0) and setImmediate(fn)?

      setTimeout schedules into the timers phase (first phase); setImmediate schedules into the check phase (right after poll/I/O). Inside an I/O callback, setImmediate always fires first since check immediately follows poll. At the top level of a script, the order between them is not guaranteed.

      Follow-up: why is the ordering guaranteed inside an I/O callback but not at the top level?
      What is process.nextTick and how does it differ from a microtask?

      process.nextTick is a Node-specific queue that runs before the Promise microtask queue, after the current operation completes, and is drained fully (including newly added nextTicks) before microtasks get a turn. It predates Promises in Node's history.

      Follow-up: can you starve I/O with process.nextTick? How?
      What does "blocking the event loop" mean and give an example.

      It means running synchronous code that takes a long time on the single JS thread, preventing any other callback (timers, I/O, requests) from running until it finishes. Example: a synchronous bcrypt hash, a huge JSON.parse, or a catastrophic-backtracking regex on user input.

      Follow-up: how would you detect this is happening in production right now?
      What is the poll phase and why can it "block"?

      Poll is where the loop retrieves and processes new I/O events. If there are no pending timers, the loop can sit blocked in poll waiting for I/O rather than busy-spinning, which is a deliberate efficiency design, not a bug.

      Follow-up: how does the loop decide how long it's allowed to block in poll?
      Does async/await make a function non-blocking?

      No — async/await is sugar over Promises for control flow; code before the first await in an async function runs synchronously exactly like normal code and will block the loop if it's heavy.

      Follow-up: show an async function that still blocks the event loop for 2 seconds.
      What's UV_THREADPOOL_SIZE and what's its default?

      An environment variable controlling libuv's internal thread pool size, default 4, used by certain fs, dns.lookup, crypto, and zlib operations. Must be set before those modules are first used (effectively before/at process start).

      Follow-up: would raising it help a network-I/O-bound API? Why or why not?

      Medium

      Walk through the exact output order of: nextTick, then(), setTimeout(0), setImmediate(), console.log, all scheduled at the top level.

      Synchronous console.log statements run first (in source order), then process.nextTick queue drains fully, then the Promise microtask queue drains fully, then the loop proceeds to timers/check phases where setTimeout and setImmediate race — their relative order at the top level is not guaranteed because it depends on process startup/event-loop-entry timing.

      Follow-up: how would the answer change if this code ran inside an fs.readFile callback instead of at the top level?
      Why can dns.lookup cause unrelated file reads to slow down, but dns.resolve4 doesn't?

      dns.lookup uses libuv's thread pool (it calls the OS's getaddrinfo via a worker thread), competing with fs operations for the same fixed-size pool. dns.resolve4/6 use the c-ares library's own async I/O directly, bypassing the thread pool entirely, so they don't contend with fs.* calls.

      Follow-up: how would you prove this is the bottleneck in a live incident without guessing?
      You observe CPU usage looks fine (40% avg) but p99 latency spikes periodically. What's your diagnostic approach?

      Average CPU hides short, bursty blocking — a single slow synchronous call can max one core for 200-500ms, enough to spike p99, without moving the averaged CPU metric much. Add monitorEventLoopDelay as a metric, correlate spikes with specific endpoints/timestamps via APM traces, and look for synchronous CPU-heavy code (JSON parsing, crypto, regex, big array operations) on those endpoints' paths.

      Follow-up: once found, what are your two main remediation options and their tradeoffs?
      Explain why a recursive process.nextTick call can starve I/O but a recursive setImmediate call cannot.

      process.nextTick's queue is drained completely — including nextTicks scheduled during that very drain — before the loop can proceed to any other phase, so infinite nextTick recursion never lets poll/timers run. setImmediate callbacks run once per check phase per loop iteration; each iteration still passes through poll, giving I/O a chance to run between setImmediate calls.

      Follow-up: is the same true for recursive Promise.resolve().then() chains? Why or why not?
      How would you offload a CPU-heavy JSON transform without an existing async API for it?

      There's no thread-pool-backed API for arbitrary CPU work, so the correct tool is worker_threads — spin up a worker, pass the data (ideally via a transferable/SharedArrayBuffer to avoid copy cost for large payloads), do the transform there, and message the result back, keeping the main loop free.

      Follow-up: when would you instead just accept the blocking and scale horizontally with cluster/K8s replicas?
      Why does Promise microtask draining happen "between every callback," and what does that imply for a chain of 10,000 chained .then() calls?

      Each .then() queues the next reaction as a microtask, and the engine drains the microtask queue to empty before returning control to the macrotask loop — so a long synchronous chain of resolved promises can run many microtask turns back-to-back without yielding to I/O or timers, effectively starving the loop temporarily even though no single callback looks "slow" in isolation.

      Follow-up: how would you break up such a chain to let I/O interleave?

      Advanced

      Design an event-loop-lag-based auto-scaling or load-shedding strategy for a Node API fleet.

      Expose monitorEventLoopDelay p99 as a /metrics endpoint consumed by your orchestrator/APM; set a threshold (e.g. sustained p99 > 100ms over a rolling window) that triggers either horizontal scale-out (K8s HPA on a custom metric) or local load-shedding (reject/503 new requests above a queue depth to protect latency for in-flight ones). Pair with per-route tracing to find the actual offending handler, not just a fleet-wide signal.

      Follow-up: why is CPU utilization a poor signal to drive this specific scaling decision compared to event-loop lag?
      A teammate proposes increasing UV_THREADPOOL_SIZE to 128 to fix API slowness under load. Walk through how you'd validate or reject this.

      First confirm the slow calls are actually thread-pool-backed (fs, dns.lookup, crypto.pbkdf2/scrypt, zlib) via profiling/async_hooks, not network I/O or synchronous CPU work (which the thread pool can't help with at all). If confirmed, test incrementally — thread pool threads aren't free (each has a stack, context-switch cost), and over-provisioning can thrash the OS scheduler and add latency instead of reducing it. Benchmark before and after under realistic concurrency, not just the suspected bottleneck in isolation.

      Follow-up: what's a scenario where raising this value makes p99 latency worse, not better?
      Explain precisely why "Node handles 10k concurrent connections on one thread" is true for I/O-bound workloads but misleading for CPU-bound ones, with the libuv mechanism.

      For I/O-bound work, the OS's async I/O primitives (epoll/kqueue/IOCP) let a single poll-phase call retrieve many ready events at once with near-zero per-connection CPU cost while waiting — so thousands of idle/slow-network connections cost almost nothing on the JS thread. For CPU-bound work, every request needs actual JS-thread execution time; there's no async primitive that makes computation itself concurrent on one thread, so CPU-bound concurrency is fundamentally bounded by single-core throughput, and queueing/latency degrades linearly (or worse) with load regardless of how good libuv's I/O model is.

      Follow-up: how does this change your capacity planning math for a mixed I/O+CPU workload like image resizing + API serving on the same process?
      How would you build a minimal async_hooks-based profiler to attribute event-loop lag to a specific async operation/route?

      Use async_hooks to track init/before/after/destroy for async resources, tagging each with the triggering request's correlation ID (e.g., via AsyncLocalStorage), and combine with high-resolution timestamps at 'before'/'after' to measure how long each resource's callback actually ran; aggregate by route to find which handlers' callbacks consistently run long and correlate with lag spikes. In practice, most teams use battle-tested APM agents (which do exactly this) rather than hand-rolling it, but understanding the mechanism is what interviewers probe.

      Follow-up: what's the performance overhead risk of enabling async_hooks broadly in production, and how do you mitigate it?
      Why doesn't adding more worker_threads indefinitely improve throughput for a CPU-bound workload on an 8-core machine?

      Each worker thread needs real CPU time to execute; beyond the number of physical/logical cores available, additional workers just add context-switching and scheduling overhead without additional parallel compute capacity, and each worker also carries its own V8 isolate memory overhead. The right worker count is typically close to os.cpus().length (minus headroom for the main thread and OS), not an arbitrarily large number.

      Follow-up: how would cluster mode interact with worker_threads if you tried to use both for the same CPU-bound workload?

      Quick Revision Cheat Sheet

      • Loop phases in order: timers → pending callbacks → idle/prepare → poll → check (setImmediate) → close callbacks.
      • Priority order between every callback: process.nextTick queue (full drain) → Promise microtask queue (full drain) → next phase.
      • Thread-pool-backed APIs: fs.* (most), dns.lookup, crypto.pbkdf2/scrypt/randomBytes (async), zlib. NOT network I/O, NOT dns.resolve*.
      • Network I/O uses OS-native async (epoll/kqueue/IOCP) directly, not the thread pool — scales to thousands of connections cheaply when I/O-bound.
      • async/await does not make code non-blocking by itself — only code after an actual await yields.
      • Inside an I/O callback, setImmediate always fires before setTimeout(fn, 0); at top level, order is unspecified.
      • monitorEventLoopDelay is the correct production metric for "is the loop responsive," not CPU% alone.
      • UV_THREADPOOL_SIZE (default 4) only helps thread-pool-backed bottlenecks — never CPU-bound JS or network I/O.
      • Recursive process.nextTick can starve I/O indefinitely; recursive setImmediate cannot (poll runs between iterations).
