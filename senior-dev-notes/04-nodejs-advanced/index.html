    Node.js Advanced

    📚 9 chapters⏱ ~21–25 hrs total

    Node.js is the runtime most senior/lead interviews probe hardest once you claim "strong backend" — and most candidates with 8-10 years of Express experience still can't explain what actually happens between a timer firing and a promise resolving. This topic goes under the hood of the event loop and libuv, streams and real backpressure, worker threads vs cluster vs child processes, V8's generational GC and leak hunting with heap snapshots, error-handling architecture at scale, and the production concerns — API framework choice, auth (JWT/OAuth2/SSO done correctly), background job queues, and horizontal scaling with PM2/K8s and graceful shutdown.

    Learning Outcomes

    • Explain the six libuv event loop phases and where microtasks are drained relative to each one — not the simplified "macrotask vs microtask" version.
    • Implement backpressure-correct streaming pipelines and diagnose why a naive pipe() or unthrottled write starves memory.
    • Choose between worker_threads, cluster, and child_process for a given CPU-bound or isolation problem, and justify the choice with numbers.
    • Read a V8 heap snapshot, identify a real memory leak (closures, listeners, caches, timers), and fix it.
    • Design an error-handling strategy (operational vs programmer errors, central error middleware, process-level handlers) that doesn't crash production silently.
    • Build a layered, production-grade API (controllers/services/repositories) and defend Express vs Fastify vs NestJS tradeoffs.
    • Implement JWT access/refresh token auth and OAuth2/OIDC flows correctly, including the security pitfalls interviewers probe for.
    • Design a reliable background job system (BullMQ) with retries, idempotency, and dead-letter handling.
    • Scale a Node service horizontally with PM2/Kubernetes, including zero-downtime deploys and graceful shutdown under in-flight requests.

    🏆 Capstone Project: Build a Production-Grade Node.js API Service

    Problem statement: Build a backend service (e.g., a task/notification platform) that demonstrates every chapter in this topic working together: layered architecture, secure auth with refresh tokens, async background processing, resilient I/O, and clean shutdown — then prove it survives load.

    Required features:

    • Layered architecture: HTTP layer (controllers) → services (business logic) → repositories (data access), with dependency injection so each layer is unit-testable in isolation.
    • JWT access tokens (short-lived) + refresh tokens (long-lived, rotated, stored hashed) with logout/revocation and refresh-token reuse detection.
    • A BullMQ-backed worker for an async task (e.g., sending emails, generating reports) with retries, exponential backoff, and a dead-letter queue.
    • Streaming endpoint (e.g., CSV/large JSON export) that respects backpressure instead of buffering the whole response in memory.
    • Graceful shutdown: in-flight requests finish, new connections are refused, the job worker finishes its current job, DB pool drains cleanly, all within a bounded timeout.
    • Structured JSON logging (request ID correlation) and a centralized error-handling middleware distinguishing operational vs programmer errors.
    • A load test (autocannon or k6) against the streaming and queue-producing endpoints, documenting what happens under backpressure/overload and what you changed to fix it.

    Tech stack suggestion: Node.js 22 LTS + TypeScript, Fastify, BullMQ + Redis, Postgres (pg or Prisma), pino for logging, Docker Compose for local dev, autocannon or k6 for load testing.

    Milestones:

    1. Scaffold layered architecture + health/readiness endpoints + structured logging with request-ID correlation.
    2. Implement auth: register/login, JWT access + rotating refresh tokens, revocation list, protected routes.
    3. Add the BullMQ worker with a real async job, retry/backoff policy, and dead-letter queue + a way to inspect failed jobs.
    4. Add a streaming export endpoint built on Node streams, verified not to buffer the entire payload in memory (profile it).
    5. Wire graceful shutdown (SIGTERM handling, connection draining, worker drain, DB pool close) and test it mid-request with a kill signal.
    6. Load-test with autocannon/k6, capture latency/throughput under increasing concurrency, identify the actual bottleneck (event loop lag? DB pool? queue backlog?), fix it, and re-measure.

    Evaluation checklist:

    • ☐ Can explain exactly what happens, phase by phase, when a request triggers a DB call and a queued job.
    • ☐ Refresh token rotation actually detects and blocks reuse of a stolen/old refresh token.
    • ☐ Killing the process mid-request does not drop that request's response or corrupt an in-progress job.
    • ☐ Heap usage during the streaming load test stays flat, not growing with payload size.
    • ☐ Can show the load test numbers and explain the actual bottleneck found, not a guessed one.
