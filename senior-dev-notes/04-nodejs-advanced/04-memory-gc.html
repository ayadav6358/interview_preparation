    Memory Management & Garbage Collection

    ⏱ 2.5 hrs📍 Chapter 4 of 9

    One-line summary: V8's generational garbage collector is tuned for short-lived objects and punishes long-lived growing heaps with expensive full-heap pauses — knowing the generations, when GC pauses actually block your event loop, and how to read a heap snapshot is what turns "we have a memory leak" into "line 247 of the cache module never evicts."

    On this page

      Why It Matters for a Senior Developer

      Memory leaks in long-running Node processes are one of the most common senior-level production debugging scenarios — unlike a crash, a leak looks fine for hours or days, then OOM-kills under exactly the traffic pattern that matters most. Senior engineers are expected to recognize the leak shape (steadily climbing RSS/heap that never comes back down after GC) versus normal sawtooth GC behavior, and to actually use heap snapshots and allocation profiling to find root causes rather than guessing and restarting pods on a schedule as a "fix."

      Why

      A service that "needs restarting every 6 hours" because of a slow leak is a ticking production risk disguised as a workaround — it fails exactly when traffic is highest (the leak accumulates faster) or when a deploy/restart is delayed. Interviewers ask about memory leaks specifically to see whether you reach for tooling (heap snapshots, --inspect, clinic.js) or just guess.

      Prerequisites

      Basic understanding of references and closures in JS. Related: Streams & Buffers, Event Loop Internals.

      Core Concepts

      V8's heap structure

      V8 divides the managed heap into new space (young generation — small, fast to collect, where almost all objects are initially allocated) and old space (old generation — objects that survive multiple young-generation collections get "promoted" here). There's also large object space (big objects allocated directly, bypassing new space), code space, and map space (hidden class metadata) — but new/old generation is what matters for GC behavior reasoning. Separately, Buffers and TypedArrays backed by large allocations live largely off this managed heap (in what Node calls "external" memory), visible in `process.memoryUsage().external` and RSS but not in `heapUsed`.

      Scavenge (minor GC) vs Mark-Sweep-Compact (major GC)

      Young generation collection is called Scavenge: new space is split into two halves; live objects are copied from the active half to the other half (and anything surviving a second Scavenge gets promoted to old space), then the original half is wholesale cleared — fast because it only has to touch live objects, not scan the whole space for garbage, and new space is kept small specifically so this is cheap and frequent. Old generation collection is Mark-Sweep-Compact (major GC): mark all reachable objects from GC roots, sweep unreachable ones, and periodically compact to reduce fragmentation. This is fundamentally more expensive because old space is large and the full mark phase must traverse the live object graph — in V8 this is incremental and partially concurrent/parallel (to minimize how much runs "stop-the-world" on the main thread) but a sufficiently large old-generation heap still produces measurable main-thread GC pauses, which show up directly as event-loop lag spikes.

      What actually causes a leak, and heap snapshot methodology

      A leak is simply: objects kept reachable (via some retained reference) long after they're logically no longer needed, so GC correctly never collects them — GC only collects unreachable garbage, it has no concept of "logically done with this." Classic retained-reference leak sources: event listeners added but never removed (each holds a closure over its context), timers/intervals never cleared, closures capturing large objects unintentionally, global/module-level caches or Maps with no eviction policy, and detached DOM- like patterns in server contexts (e.g., retaining full request/response objects in a long-lived log buffer).

      Methodology: take a heap snapshot (via `--inspect` + Chrome DevTools, or `node --heapsnapshot-signal` / the `v8` module's `writeHeapSnapshot()`), compare two snapshots taken minutes apart under steady load — the "Comparison" view in DevTools shows objects that grew in count/retained size between snapshots. For each suspicious growing type, use "Retainers" to trace the actual reference chain keeping it alive back to a GC root — this chain is almost always the direct answer to "what line of code causes this."

      How It Works Under the Hood

      --max-old-space-size sets the ceiling for old-generation heap size (default scales with available system memory, but in containers it's critical to set explicitly — V8 historically could misdetect available memory in a cgroup-limited container and allow the heap to grow past the container's actual memory limit, triggering an OOM kill from the OS/kubelet rather than a clean V8 "out of memory" error with a stack trace). As old space approaches this limit, V8 runs GC more aggressively and eventually synchronously/more disruptively, which is why climbing memory pressure often correlates with climbing latency before the eventual crash — GC isn't free, and a near-full heap means GC runs more often and does more work per run (since there's less slack to find garbage quickly).

      process.memoryUsage() fields, precisely: heapUsed/heapTotal are V8's managed JS heap; external is memory for objects bound to JS but managed outside V8 (most Buffers); arrayBuffers is a subset of external specifically for ArrayBuffer/SharedArrayBuffer; rss (resident set size) is the actual physical memory the OS has allocated to the whole process — the number that matters for OOM kills, and it includes heap + external + the V8 engine's own overhead + native module memory. A leak purely in Buffers can grow RSS steadily while `heapUsed` looks perfectly flat — checking only `heapUsed` is a common mistake that hides exactly this class of leak.

      Code Examples

      // Classic leak #1: listener never removed, closure retains large context
class RequestLogger {
  private buffer: any[] = [];
  constructor(private emitter: EventEmitter) {
    // BAD: this listener is added once per RequestLogger instance but
    // never removed. If a new RequestLogger is created per-request,
    // every one of them (and everything they close over) leaks forever.
    emitter.on('log', (entry) => this.buffer.push(entry));
  }
}

// GOOD: explicit cleanup, or use a shared singleton instead of per-request instances
class RequestLoggerFixed {
  private buffer: any[] = [];
  private handler = (entry: any) => this.buffer.push(entry);
  constructor(private emitter: EventEmitter) {
    emitter.on('log', this.handler);
  }
  dispose() {
    this.emitter.off('log', this.handler); // breaks the retaining reference
  }
}


// Classic leak #2: unbounded cache, no eviction
const cache = new Map(); // BAD: grows forever, never evicted
function getCached(key: string, compute: () => Buffer) {
  if (!cache.has(key)) cache.set(key, compute());
  return cache.get(key)!;
}

// GOOD: bounded with an LRU eviction policy (e.g., using `lru-cache`)
import { LRUCache } from 'lru-cache';
const boundedCache = new LRUCache({ max: 500, ttl: 1000 * 60 * 10 });


// Classic leak #3: timer never cleared, keeps a per-request closure alive
app.get('/poll-status', (req, res) => {
  // BAD: if the client disconnects, this interval and its closure
  // (capturing req/res) keeps running and leaking forever.
  const interval = setInterval(() => checkStatus(req.query.id), 1000);
});

// GOOD: tied to the request lifecycle explicitly
app.get('/poll-status', (req, res) => {
  const interval = setInterval(() => checkStatus(req.query.id), 1000);
  req.on('close', () => clearInterval(interval));
});


// Taking a heap snapshot programmatically for later analysis in DevTools
import { writeHeapSnapshot } from 'node:v8';
process.on('SIGUSR2', () => {
  const filename = writeHeapSnapshot();
  console.log(`heap snapshot written to ${filename}`);
});
// trigger in prod with: kill -USR2 <pid>, then load the .heapsnapshot
// file into Chrome DevTools Memory tab for Comparison analysis.


// Correct container memory configuration — avoid V8 overshooting cgroup limits
// package.json / Dockerfile CMD:
// node --max-old-space-size=1536 server.js   (for a 2GB container, leaving headroom
// for external/RSS overhead beyond just the old-space JS heap)

      Real-World Production Scenario at Scale

      At scale

      An API's memory climbed steadily over about 18 hours before every OOM-restart, heapUsed looked almost flat the whole time, but RSS grew linearly. The team initially chased a JS-level leak (checked heap snapshots, found nothing growing meaningfully) before realizing the issue was in `external` memory: a websocket library buffered unacknowledged outgoing messages per-connection in a plain array with no cap, and a subset of mobile clients on flaky connections never acked fast enough, so their buffers grew unbounded — each held as Buffer-backed chunks, invisible to heap snapshots which only see the managed JS heap. The fix was a per-connection buffer cap with a disconnect-and-drop policy once exceeded, plus adding `external` and `rss` (not just `heapUsed`) to the standard memory dashboard going forward.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Monitoring only `heapUsed` for "is there a leak" — this misses any leak in Buffers/external memory entirely, which is extremely common in I/O-heavy services (websockets, streaming, native modules). Always track `rss` as the primary OOM-risk signal, and `external` separately when heapUsed looks healthy but RSS doesn't.

      • A sawtooth memory graph (climbs, drops sharply on major GC, repeats) is normal and healthy — a leak looks like the sawtooth's floor (post-GC baseline) steadily rising over time, never returning to its earlier low.
      • Always set `--max-old-space-size` explicitly in containers, sized with real headroom below the container memory limit for external/RSS overhead, not equal to it.
      • Event listeners, timers, and module-level caches are the three most common real-world leak sources — audit these first.
      • Use heap snapshot comparison (two snapshots under steady load, minutes apart), not a single snapshot — a single snapshot can't show you what's growing.
      • `global.gc()` (only available with `--expose-gc`) can be useful for isolating leak investigation (force a collection, then snapshot) but should never be called in normal production code paths.

      Interview Questions

      Basic

      What's the difference between new space and old space in V8's heap?

      New space (young generation) holds newly allocated, mostly short-lived objects and is collected frequently via a cheap Scavenge algorithm. Old space holds objects that survived multiple young-gen collections (promoted/"tenured") and is collected less often via the more expensive Mark-Sweep-Compact.

      Follow-up: why is new space kept deliberately small?
      What causes a memory leak in a garbage-collected language like JavaScript?

      An object remains reachable (some live reference chain leads to it from a GC root) long after it's logically no longer needed — GC only reclaims unreachable memory, so a forgotten reference (listener, timer, cache entry) prevents collection indefinitely.

      Follow-up: name three common real-world sources of such lingering references.
      What does heapUsed vs rss tell you differently in process.memoryUsage()?

      heapUsed is memory within V8's managed JS heap; rss is total physical memory the OS has allocated to the whole process, including the JS heap, external/Buffer memory, and engine overhead — rss is what actually triggers an OOM kill.

      Follow-up: can heapUsed look flat while rss grows? How?
      What's a healthy memory usage graph supposed to look like over time, vs a leak?

      Healthy: a sawtooth pattern — memory climbs as objects allocate, drops sharply when major GC runs, and the post-GC floor stays roughly constant over time. A leak: the same sawtooth pattern, but the floor itself steadily climbs over time and never returns to earlier lows.

      Follow-up: how would you distinguish a slow leak from legitimately growing cache/working-set size?
      What tool would you reach for first to investigate a suspected Node memory leak?

      Heap snapshots via --inspect and Chrome DevTools' Memory tab (or node:v8's writeHeapSnapshot), comparing two snapshots taken minutes apart under steady load to see what object types/counts grew.

      Follow-up: why is comparing two snapshots more useful than examining a single one?

      Medium

      Why is Mark-Sweep-Compact (major GC) more likely to cause a visible latency spike than Scavenge (minor GC)?

      Scavenge only has to copy the (usually small) set of live objects in new space, proportional to live data, not total space size, so it's fast and frequent. Mark-Sweep-Compact must traverse the full reachable object graph in old space to mark live objects and sweep the rest, work that scales with old-generation heap size, and even with V8's incremental/concurrent optimizations, a large or fragmented old generation can still produce a measurable main-thread pause.

      Follow-up: how would this pause show up in your production monitoring?
      Explain how a leak purely in Buffer/external memory could evade a heap-snapshot-based investigation that only looks at the JS heap.

      Buffers and other large typed-array-backed allocations are tracked outside V8's managed heap (in Node's "external" memory), so a Chrome DevTools heap snapshot — which captures the managed JS object graph — will show the small JS wrapper object referencing the Buffer, but won't necessarily make the scale of the retained external memory obvious the way it highlights growing plain-object counts; you need to separately track process.memoryUsage().external/arrayBuffers over time to catch this class of leak.

      Follow-up: what server-side pattern (hint: websockets) commonly causes exactly this kind of leak?
      Why should you set --max-old-space-size explicitly inside a container rather than relying on V8's default detection?

      V8's default heap size heuristics are based on detecting total system memory, which in a cgroup-limited container can historically diverge from the container's actual memory limit — V8 might allow the heap to grow toward a default sized for the host's full memory, well past what the container is permitted, resulting in the OS/kubelet OOM-killing the process abruptly rather than V8 hitting its own limit and failing more predictably/with a stack trace.

      Follow-up: how would you size the value relative to the container's memory limit, and why leave headroom?
      You find a Map used as a cache that's growing without bound. Walk through root-causing it with heap snapshots before just adding an LRU wrapper.

      Take two heap snapshots minutes apart under steady traffic, use DevTools' Comparison view to confirm the Map (or its entries' types) are what's growing in count. Use Retainers on a sample growing entry to trace the reference chain back to confirm it really is this Map (not, say, closures capturing request objects that happen to also reference the Map) and understand why entries never get removed — e.g., no eviction logic was ever written, or eviction logic has a bug (wrong key comparison, TTL never actually checked).

      Follow-up: after adding an LRU cap, how would you verify the fix actually worked under the same load pattern?
      Why can raising --max-old-space-size make a real leak's symptoms worse, not better, in production?

      It doesn't stop the leak — it just delays the crash and lets more memory accumulate before OOM, meaning when it does eventually hit the limit (or when the container's absolute memory ceiling is hit first), GC pressure and pause times will have been climbing for longer and be worse at the point of failure, and you've bought a longer but still-inevitable failure window instead of fixing the underlying unbounded retention.

      Follow-up: when IS raising this value the correct fix rather than a leak workaround?

      Advanced

      Design a production memory-health monitoring and alerting strategy for a fleet of Node services, covering what to track and what thresholds to alert on.

      Track rss, heapUsed/heapTotal, and external/arrayBuffers per instance over time (not just instantaneous values — the trend/slope matters more than any single point). Alert on: (1) rss as a percentage of container memory limit sustained above a threshold (e.g., 80% for 10+ minutes) as an imminent-OOM signal, (2) the post-major-GC floor of heapUsed trending upward over a multi-hour window (the leak signature) rather than alerting on raw heapUsed which naturally saws. Correlate with deploy timestamps to catch leaks introduced by a specific release quickly, and keep automated heap-snapshot capture triggered by the rss threshold so you have a snapshot from near the actual incident, not from a cold/healthy state.

      Follow-up: how would you avoid snapshot capture itself (which pauses the process) making an already-struggling instance worse?
      A heap snapshot comparison shows a specific Closure type growing by thousands between snapshots, but you can't find an obvious module-level cache. What's your next investigative step?

      Use DevTools' Retainers panel on a sample of the growing closures to trace the actual reference chain to a GC root — this will typically reveal something non-obvious holding them, like an EventEmitter's internal listener array (if listeners are added per-request and never removed), a Promise chain that never resolves/rejects (each pending .then() closure stays retained), or a timer that's never cleared. The retainer chain is the ground truth; guessing based on code review alone misses leaks caused by third-party library internals.

      Follow-up: how would async_hooks or a Promise-tracking tool help confirm the "never-resolving Promise" hypothesis specifically?
      Explain the tradeoff a team faces choosing between "restart pods on a memory threshold" (a common K8s liveness-probe pattern) as a standing mitigation versus treating every leak as a must-fix bug.

      A memory-threshold restart is a legitimate safety net for resilience (any process can leak unexpectedly, and automatic recycling bounds the blast radius) but becomes dangerous if relied on as the primary fix: it masks the leak's existence from normal monitoring, risks restarting mid-request (dropping in-flight work if graceful shutdown isn't correctly wired — see Chapter 9), and the leak's growth rate may outpace the probe's check interval under a traffic spike, OOM-killing before the probe acts. The right posture: keep the safety net, but treat any newly observed leak as a tracked bug with a root cause, not accept "it just restarts" as the resolution.

      Follow-up: how does this interact with graceful shutdown handling covered in the scaling chapter?
      How would you profile and reduce GC pause impact for a service with a legitimately large, long-lived old-generation heap (e.g., a large in-memory index/cache by design, not a leak)?

      Use `--trace-gc` / Chrome DevTools Performance recording to measure actual major-GC pause durations and frequency; consider reducing allocation churn in hot paths (object pooling, avoiding needless intermediate allocations in request handling) since GC cost correlates with how much garbage must be scanned/collected, not just total live-heap size. If the large structure is genuinely static/long-lived (not garbage, never needs collecting), consider moving it off the V8 managed heap entirely (e.g., a native-backed structure, or an external cache like Redis) so V8's GC doesn't need to repeatedly scan it as part of mark phases.

      Follow-up: why would moving a large static structure off-heap reduce GC pause time even though it was never going to be collected anyway?
      Two services show identical heapUsed growth curves, but only one is a real leak — the other is a legitimately growing cache that will plateau. How do you distinguish them with evidence, not assumption, before paging anyone?

      Extend the observation window and correlate growth with known bounding logic — a legitimate cache plateaus once its key space is exhausted or its TTL/LRU eviction reaches steady state (growth rate should visibly decelerate and flatten); a real leak continues climbing linearly or accelerates regardless of traffic pattern changes, and typically correlates with request volume in a way that never saturates (e.g., scales with total requests served, not with distinct cache keys). Pull two heap snapshots a few hours apart during the growth and check whether the growing object types match the cache's expected key/value shape and whether the count is bounded by a known business quantity (e.g., number of active users) — if growth exceeds that bound, it's a leak.

      Follow-up: what's a case where a "legitimate cache" turns out to actually be an unintentional leak because its supposed bound was never actually enforced in code?

      Practice Assignments

      Beginner (30-60 min)

      Create and observe a deliberate leak

      Write a small server with an endpoint that adds an item to a module-level array on every call and never removes anything. Hit it in a loop with 10,000 requests, logging `process.memoryUsage()` every 500 requests.

      • Must show heapUsed and rss climbing together.
      • Must log at regular intervals, not just before/after.

      Acceptance criteria: A clear, logged, monotonically climbing memory trend with no GC-driven drops returning to baseline.

      Hints

      Push plain objects with a moderately sized string/array payload so the growth is visible within a reasonable request count.

      Bonus: Fix the leak with a bounded array (cap size, drop oldest) and show memory stabilizing.

      Intermediate (2-4 hrs)

      Diagnose a hidden leak using heap snapshots

      Build a server with one of the three classic leak patterns from this chapter (listener, timer, or cache) hidden somewhere in a moderately-sized set of modules (at least 5 files, only one containing the actual bug). Without looking at the source first, use `--inspect` + Chrome DevTools heap snapshot comparison to find and fix it.

      • Diagnosis must be snapshot-driven (screenshot/description of the Comparison + Retainers view), not source-reading.
      • Must identify the exact retaining reference chain.

      Acceptance criteria: Can show the specific growing object type in the Comparison view and trace its Retainers chain to the exact line of code responsible.

      Hints

      Generate load with autocannon between the two snapshots to make the leak's growth clearly visible in the comparison.

      Bonus: Reproduce the same investigation using the `v8` module's writeHeapSnapshot() triggered by a SIGUSR2 signal instead of the inspector UI, simulating a real production capture.

      Advanced (1-2 days)

      Build a memory-health monitoring harness

      Build a monitoring module for a Node service that tracks rss/heapUsed/external over time, computes a rolling "post-GC floor" trend (e.g., sample memory right after you detect a drop, indicating a GC just ran), and triggers an automatic heap snapshot write when the floor's slope over the last N minutes exceeds a threshold. Validate it against both a healthy service (plateauing cache) and a leaking one, showing it correctly distinguishes the two.

      • Must distinguish "legitimate growth that plateaus" from "leak that keeps climbing" with a concrete, justified heuristic.
      • Must trigger an actual heap snapshot write, not just an alert log.
      Hints

      Detect GC events heuristically by watching for memory drops of a meaningful size, or use the `perf_hooks` GC performance observer to detect actual major GC events directly rather than inferring them.

      Bonus: Wire the snapshot trigger to also capture a CPU profile simultaneously, to correlate memory pressure with any GC-induced latency spike at the same moment.

      Quick Revision Cheat Sheet

      • New space (young gen): small, frequent, cheap Scavenge collection. Old space (old gen): large, expensive Mark-Sweep-Compact.
      • Objects surviving ~2 Scavenges get promoted ("tenured") to old space.
      • Buffers/large TypedArrays live in "external" memory, outside the managed JS heap — invisible to heapUsed, visible in RSS.
      • RSS is what actually gets OOM-killed by the OS/kubelet — monitor it, not just heapUsed.
      • Healthy memory = sawtooth with a flat floor; a leak = sawtooth with a climbing floor.
      • Top 3 real-world leak sources: unremoved event listeners, uncleared timers, unbounded caches.
      • Always set --max-old-space-size explicitly in containers, with headroom below the container's hard memory limit.
      • Diagnose with heap snapshot Comparison (two snapshots under load) + Retainers, not single snapshots or guessing.
      • GC pauses show up directly as event-loop lag spikes — correlate the two metrics during an incident.
