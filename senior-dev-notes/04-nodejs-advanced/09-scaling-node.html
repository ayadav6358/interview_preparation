    Scaling Node in Production: PM2, Horizontal Scaling, Graceful Shutdown

    ⏱ 2.5 hrs📍 Chapter 9 of 9

    One-line summary: Node's single-threaded event loop means scaling is never "just add more CPU to one process" — it's about cluster/process-per-core, horizontal replication across machines, and getting graceful shutdown's drain sequence exactly right, because a deploy that kills in-flight requests is an outage you caused, not one that happened to you.

    On this page

      Why It Matters for a Senior Developer

      A senior engineer is expected to own the full lifecycle of a Node service in production, not just the application code — how it's clustered across cores, how it scales horizontally across instances, and critically, how it shuts down. Nearly every "why did we get 502s during the deploy" incident traces back to a missing or incorrect graceful shutdown sequence. This is one of the highest-leverage topics for a senior/staff interview because it tests operational maturity that most mid-level engineers have simply never had to think about.

      Why

      A single Node process uses one CPU core for its JS execution (the event loop itself is single-threaded, even though libuv's thread pool handles some I/O concurrently) — so scaling vertically by adding cores to a box does nothing for your throughput unless you actually run multiple Node processes to use them. This is the foundational reason cluster mode / PM2 / container replica counts exist: they're not optional tuning, they're the mechanism by which a multi-core machine's capacity becomes usable by a single-threaded runtime at all.

      Prerequisites

      Comfortable with the event loop model and process-level error handling. Related: Error Handling Strategy, Background Jobs & Scheduling, Event Loop Internals & libuv.

      Core Concepts

      Cluster mode: multi-process, not multi-thread

      Node's built-in cluster module (and PM2's cluster mode, which wraps it) forks N worker processes, each with its own event loop and V8 instance, sharing the same listening port via the OS/master process round-robining incoming connections across workers. This is process-level parallelism, not shared-memory threading — each worker has its own heap, so there's no shared in-memory state between them (a naive in-memory cache or rate-limiter will behave inconsistently across workers unless backed by something external like Redis). The practical rule of thumb: run one worker per CPU core (os.cpus().length), since more workers than cores just adds context-switching overhead without added throughput.

      Horizontal scaling: stateless design as the actual prerequisite

      Scaling beyond a single machine (horizontal scaling across containers/VMs behind a load balancer) only works cleanly if your application is stateless — no in-memory session data, no local file writes that other instances need to see, no in-process job scheduling that would duplicate across instances (see the previous chapter's distributed-lock discussion). Session/auth state needs to live in a shared store (Redis, a DB) or be entirely stateless (JWTs, per the authentication chapter) specifically so that any instance can serve any request — this is the real prerequisite for horizontal scaling, and it's an architectural decision made far earlier than the scaling conversation itself, which is why retrofitting statelessness onto a service built assuming a single instance is often a significant rewrite.

      Graceful shutdown: the drain sequence that prevents deploy-time errors

      A graceful shutdown on receiving SIGTERM (what orchestrators like Kubernetes/PM2 send before killing a process) must, in order: (1) stop accepting new connections (server.close(), or for a load-balanced setup, first deregister from the load balancer/readiness check so it stops receiving new traffic before even calling close), (2) allow in-flight requests to finish naturally within a bounded timeout, (3) close downstream resources (DB pools, Redis connections, message queue consumers) only after in-flight work has actually drained, and (4) exit. Skipping step 1's readiness-deregistration is a very common subtle bug: you stop accepting new TCP connections, but the load balancer doesn't know yet and keeps routing new requests to you for a window, which then fail outright rather than being gracefully redirected elsewhere. Kubernetes specifically gives a configurable grace period (terminationGracePeriodSeconds) between SIGTERM and a forceful SIGKILL — your drain sequence must complete within that window or in-flight work gets hard-killed anyway.

      How It Works Under the Hood

      PM2 cluster mode's master process forks N workers and uses the OS's SO_REUSEPORT (or a round-robin dispatch, depending on platform) to distribute incoming connections. On a rolling restart, PM2 (and Kubernetes rolling deployments at a higher level) brings up new instances/workers before tearing down old ones, and tears down old ones gracefully — sending SIGTERM, waiting for the drain sequence, then SIGKILL after a grace period if the process hasn't exited. The key correctness property your app must provide: reacting to SIGTERM correctly (not ignoring it, not exiting immediately without draining) is entirely the application's responsibility — the orchestrator sends the signal and waits, but doesn't know how to drain your specific in-flight work; that logic has to be written into your process.

      Code Examples

      // --- PM2 cluster mode config (ecosystem.config.js) ---
module.exports = {
  apps: [{
    name: 'api',
    script: './dist/server.js',
    instances: 'max',       // one worker per CPU core
    exec_mode: 'cluster',
    kill_timeout: 10000,    // ms PM2 waits after SIGTERM before SIGKILL - must exceed your drain time
    wait_ready: true,       // wait for process.send('ready') before considering restart complete
    listen_timeout: 8000,
  }],
};

// --- Graceful shutdown sequence ---
import http from 'http';

const server = http.createServer(app);
server.listen(3000, () => process.send?.('ready')); // tell PM2 this instance is actually ready

let isShuttingDown = false;

async function gracefulShutdown(signal: string) {
  if (isShuttingDown) return; // idempotent - SIGTERM can arrive more than once
  isShuttingDown = true;
  logger.info({ signal }, 'shutdown initiated');

  // Step 1: fail readiness checks immediately so the LB stops routing new traffic
  isReady = false; // a /health/ready endpoint reads this and returns 503 once false

  // Give the LB time to notice the failed readiness check before we stop accepting connections
  await new Promise((r) => setTimeout(r, 2000));

  // Step 2: stop accepting new connections, let in-flight ones finish
  await new Promise((resolve) => server.close(() => resolve()));

  // Step 3: close downstream resources only after HTTP has drained
  await Promise.allSettled([
    dbPool.end(),
    redisClient.quit(),
    queueWorker.close(),
  ]);

  logger.info('shutdown complete');
  process.exit(0);
}

// Step 4: hard timeout - never hang indefinitely regardless of what's stuck
function withHardTimeout(signal: string) {
  gracefulShutdown(signal);
  setTimeout(() => {
    logger.fatal('graceful shutdown timed out, forcing exit');
    process.exit(1);
  }, 15000).unref(); // unref so this timer alone doesn't keep the process alive
}

process.on('SIGTERM', () => withHardTimeout('SIGTERM'));
process.on('SIGINT', () => withHardTimeout('SIGINT'));

// --- BAD: no drain, kills in-flight requests on every deploy ---
// process.on('SIGTERM', () => process.exit(0)); // instantly kills active connections mid-response

      Real-World Production Scenario at Scale

      At scale

      A team running Node on Kubernetes saw a consistent spike in 502s during every rolling deploy, roughly matching pod termination timing. Root cause: the app had no SIGTERM handler at all, so Kubernetes's default behavior (wait out the grace period, then SIGKILL) meant every in-flight request on a terminating pod was simply dropped the instant the grace period expired, and worse, the pod kept receiving new traffic from the Service for several seconds after SIGTERM because its readiness probe wasn't wired to fail immediately on shutdown. The fix: a readiness endpoint that flips to failing the instant SIGTERM is received (removing the pod from the Service's endpoint list quickly), combined with an actual drain sequence closing the HTTP server only after a short buffer, eliminating the 502 spike entirely on the next deploy.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting that cluster-mode workers don't share memory — an in-process rate limiter, cache, or WebSocket connection registry built as a simple in-memory Map works fine in dev (single process) and then behaves inconsistently in production the moment you run more than one worker, because each worker has its own independent copy with no visibility into the others.

      Gotcha

      Setting a shutdown grace period/timeout shorter than your actual drain time (e.g., PM2's kill_timeout or Kubernetes's terminationGracePeriodSeconds set to 5s while your longest in-flight request can legitimately take 20s) — the orchestrator SIGKILLs the process before your graceful logic finishes, producing exactly the dropped-request problem you built the drain sequence to prevent.

      • Run one worker per CPU core in cluster mode — more doesn't help, it just adds context-switch overhead.
      • Make shutdown idempotent — SIGTERM can be delivered more than once; a second signal shouldn't restart the drain sequence or throw.
      • Always enforce a hard timeout on shutdown that force-exits regardless of what's hung, so a stuck cleanup step can't leave a zombie process the orchestrator has to forcibly kill anyway.
      • Fail your readiness probe immediately on SIGTERM, separately from and before closing the HTTP server — the load balancer needs time to notice before new traffic truly stops arriving.
      • Never assume in-memory state is safe once you're running more than one process instance — externalize shared state (Redis, DB) from the start if horizontal scaling is even a future possibility.

      Interview Questions

      Basic

      Why doesn't adding more CPU cores to a server automatically make a single Node process faster?

      A single Node process's JS execution runs on one thread (the event loop) regardless of how many cores are available — extra cores go unused unless you actually run multiple processes (cluster mode) to take advantage of them.

      Follow-up: does this mean Node is single-threaded for everything? What's the exception?
      What does PM2/Node's cluster module actually do under the hood?

      It forks N worker processes, each with its own independent event loop and memory, and distributes incoming connections across them (round-robin or OS-level socket sharing) while sharing the same listening port.

      Follow-up: do cluster workers share any memory with each other by default?
      What signal does an orchestrator typically send to request a graceful shutdown, and what follows if the process doesn't exit in time?

      SIGTERM is sent first, giving the process a grace period to shut down cleanly; if it hasn't exited by the end of that grace period, a SIGKILL forcibly terminates it, which does not allow any further cleanup.

      Follow-up: what Kubernetes setting controls the length of this grace period?
      Why is in-memory state (like a simple rate limiter Map) problematic once you run more than one Node process?

      Each process has its own independent memory — state isn't shared between them, so a rate limiter tracking counts in a local Map will undercount actual request volume across all instances combined, allowing effectively N times the intended rate limit.

      Follow-up: what's the typical fix for this?
      What's the minimum correct first step when handling SIGTERM in an HTTP server?

      Stop accepting new connections (via server.close()) while letting existing in-flight requests finish, rather than immediately exiting and dropping active requests.

      Follow-up: what step should ideally happen even before that, in a load-balanced setup?
      Why does stateless application design matter for horizontal scaling?

      Horizontal scaling assumes any instance can serve any request — if session or other request-relevant state lives only in one instance's memory, requests routed to a different instance won't have access to it, breaking functionality unpredictably depending on load balancer routing.

      Follow-up: where should session state live instead?

      Medium

      Design a complete graceful shutdown sequence for a Node HTTP API behind a load balancer with health checks. Put the steps in the correct order and justify each.

      1) On SIGTERM, immediately fail the readiness check (not the liveness check) so the load balancer stops routing new traffic — this needs a brief buffer since the LB takes some time to notice. 2) Call server.close() to stop accepting new connections while letting in-flight ones complete. 3) Await in-flight request completion up to a bounded timeout. 4) Close downstream resources (DB pool, Redis, queue consumers) only now, since closing them earlier would break in-flight requests still using them. 5) Exit. A parallel hard timeout force-exits regardless, in case any step hangs.

      Follow-up: why specifically fail the readiness check rather than the liveness check?
      Why should PM2's kill_timeout (or Kubernetes's terminationGracePeriodSeconds) be set with explicit knowledge of your longest realistic in-flight request duration?

      If the grace period is shorter than how long a legitimate in-flight request can take, the orchestrator will SIGKILL the process before your graceful drain finishes, defeating the purpose of having graceful shutdown logic at all — the request gets hard-killed exactly as if you'd done nothing. The grace period must be set to comfortably exceed your actual drain time, including the readiness-check propagation buffer.

      Follow-up: how would you determine a realistic value for this in a service with highly variable request durations?
      What's the difference between vertical scaling, cluster mode, and horizontal scaling for a Node service, and when does each stop being sufficient?

      Vertical scaling (bigger single machine) stops helping a single Node process past one core's worth of CPU, since JS execution is single-threaded — you need cluster mode to use more cores on that same machine. Cluster mode stops being sufficient once you've saturated a single machine's total capacity (cores, memory, network) or need redundancy across machine/availability-zone failure — that's when you need horizontal scaling across multiple machines/containers behind a load balancer, which in turn requires the application to be stateless.

      Follow-up: can you combine cluster mode with horizontal scaling? What does that look like?
      A service has graceful shutdown logic but no hard timeout fallback. What production risk does this create?

      If any step in the drain sequence hangs (a DB pool that never resolves its close() call due to a stuck connection, a cleanup function with a bug), the process never exits — the orchestrator eventually SIGKILLs it after its own grace period anyway, but you've now lost the benefit of controlled logging/cleanup for whatever got stuck, and in environments without an orchestrator enforcing a hard kill, the process could hang indefinitely, consuming resources while appearing "stuck mid-deploy" to anyone watching rollout status.

      Follow-up: how would you choose the hard timeout's duration relative to the orchestrator's own grace period?
      Why can a readiness probe and a liveness probe require fundamentally different logic during shutdown?

      Readiness should fail immediately on SIGTERM (tells the LB "stop sending me new traffic, I'm draining") while the process is still alive and healthy, actively finishing in-flight work — if liveness also failed at that same moment, the orchestrator might interpret the healthy-but-draining process as broken and kill it prematurely, cutting the drain short. Liveness should only fail if the process is genuinely stuck/unresponsive, not merely in the process of a controlled shutdown.

      Follow-up: what would happen if you accidentally wired readiness and liveness to the same check?

      Advanced

      Design a zero-downtime rolling deploy strategy for a Node service with active WebSocket connections, where graceful HTTP shutdown alone isn't sufficient (you can't simply wait for a long-lived WebSocket connection to "finish naturally").

      WebSocket connections need an explicit application-level close protocol, not just waiting: on shutdown signal, send a "server restarting, please reconnect" message to each connected client over the existing socket, give clients a short window to receive and act on it (reconnecting to a different, still-healthy instance via the load balancer), then forcibly close any sockets still open after that window rather than waiting indefinitely. The reconnect logic must be client-side aware (exponential backoff reconnect, ideally with the new connection able to resume any session state via a shared store) so the user experience is a brief reconnect blip, not a dropped feature. This also requires sticky-session-free load balancing or a shared state store, since the client may reconnect to a different instance than before.

      Follow-up: how would you handle in-flight state within a WebSocket session (e.g., a half-completed multi-step interaction) across this reconnect?
      Critique: "We run cluster mode with max instances and horizontal scaling across 20 containers, so our service is infinitely scalable." What's wrong with this claim?

      Stateless compute scaling only addresses compute/connection-handling capacity — it does nothing for a shared bottleneck like a single DB instance, a Redis instance, or a downstream third-party API's rate limits, all of which don't scale just because you added more app instances calling into them. "Infinitely scalable" ignores that most real systems have a narrowest point (often the database) that becomes the actual ceiling well before app-layer compute does, and scaling the app layer past what the shared dependencies can handle just produces more concurrent load against an already-saturated bottleneck, worsening latency/errors rather than improving throughput.

      Follow-up: how would you identify which component is the actual bottleneck before scaling the app layer further?
      How would you design health/readiness checks for a Node service whose startup involves warming an in-memory cache from a slow downstream source, to avoid both premature traffic routing and unnecessarily slow rollouts?

      Use a distinct "warming" state separate from both "not ready" and "ready" — readiness should fail (keep traffic away) until the cache warm completes, but you want visibility into warm progress (e.g., exposing % warmed or a timestamp) rather than a binary flag, so rollout tooling and on-call engineers can distinguish "still warming, expected" from "actually stuck." Set the deployment's readiness check initial delay/failure threshold generously enough to tolerate normal warm time, but add alerting if warm time exceeds a known-normal ceiling, since that itself signals a problem with the downstream source feeding the cache.

      Follow-up: should a slow-warming instance be allowed to serve a subset of traffic (e.g., cache-miss-tolerant endpoints) before fully warm, or should it stay fully out of rotation?
      A team's graceful shutdown works correctly in staging (tested with curl) but still drops requests under real production load during deploys. What are the most likely causes you'd investigate?

      First, the readiness-check propagation delay: under real load with a load balancer that polls readiness every few seconds, there's a window between failing the check and the LB actually stopping new traffic that staging's low-traffic curl test wouldn't surface as a problem — under production concurrency, that window drops a meaningful number of requests. Second, connection keep-alive: if clients hold persistent HTTP keep-alive connections, server.close() alone won't close those idle-but-open sockets by default in older Node behavior, so you may need to explicitly track and close idle connections after the drain window. Third, check whether the grace period is actually long enough for production's real p99 request duration versus whatever staging's lighter load exhibited.

      Follow-up: how would you reproduce this class of bug reliably in a pre-production environment instead of only discovering it in production?
      How would you architect capacity planning and autoscaling policy for a Node service with highly spiky traffic (e.g., a flash-sale e-commerce endpoint), given cluster mode and horizontal scaling both take non-zero time to actually add capacity?

      Reactive autoscaling (scale up when CPU/request-latency crosses a threshold) has an inherent lag — new instances take time to start, warm up (per the earlier cache-warming question), and register as ready, during which the spike has already hit existing capacity. For known, scheduled spikes (a flash sale with a known start time), pre-scale proactively ahead of the event rather than relying purely on reactive triggers. For unpredictable spikes, combine a lower reactive threshold (scale earlier, before saturation, accepting some over-provisioning cost) with request queuing/load shedding at the edge (reject or queue excess requests gracefully rather than letting them degrade every in-flight request's latency) as a buffer while new capacity comes online.

      Follow-up: how would you decide which specific endpoints should have load-shedding versus which must never shed load (e.g., checkout completion)?

      Practice Assignments

      Beginner (30-60 min)

      Set up PM2 cluster mode and observe worker distribution

      Run a simple Express/Fastify API under PM2 in cluster mode with multiple instances. Add an endpoint that returns the worker's process ID, and demonstrate requests being distributed across different worker processes.

      • Must demonstrate at least 2 different worker PIDs responding across repeated requests.
      • Must demonstrate an in-memory counter behaving inconsistently across workers (to concretely observe the no-shared-memory gotcha).

      Acceptance criteria: A short load test shows roughly even distribution across workers, and the in-memory counter demo clearly shows per-worker independent state.

      Hints

      Use `process.pid` in the response and hit the endpoint with several sequential curl calls or a tiny loop script.

      Bonus: Fix the counter gotcha by backing it with Redis and show consistent counts across workers.

      Intermediate (2-4 hrs)

      Implement and load-test a full graceful shutdown sequence

      Build the complete SIGTERM drain sequence (readiness-fail, server.close, bounded wait, resource cleanup, hard timeout fallback) from the code examples. Under a sustained load test, trigger SIGTERM mid-test and prove zero failed requests during the drain window, then verify a deliberately-hung cleanup step still force-exits via the hard timeout.

      • Must demonstrate zero dropped/failed requests during a SIGTERM-triggered shutdown under load.
      • Must demonstrate the hard timeout correctly force-exiting when a cleanup step is made to hang deliberately.

      Acceptance criteria: Load test output shows 100% success rate for requests in flight at the moment SIGTERM is sent, and the hard-timeout test shows the process exits within the configured timeout even with a hung cleanup step.

      Hints

      Use autocannon with a duration overlapping your manual `kill -TERM <pid>` call, and compare request success counts before/after.

      Bonus: Add the readiness-check propagation delay and measure how request failure rate changes if you skip it.

      Advanced (1-2 days)

      Design and implement zero-downtime WebSocket-aware rolling deploys

      Extend a service with active WebSocket connections to handle graceful shutdown per the advanced interview question's design: notify connected clients of impending restart, give them a reconnect window to a different healthy instance (simulate at least 2 instances behind a basic load balancer), and force-close any stragglers after the window. Verify no message/state loss for a client that reconnects mid-interaction.

      • Must demonstrate a client receiving the restart notice and successfully reconnecting to a different instance.
      • Must demonstrate session state (stored externally) being correctly resumed after reconnect.
      Hints

      Use Redis (or a similar shared store) for session state so reconnecting to any instance can resume it; don't rely on sticky sessions as your only mechanism.

      Bonus: Add metrics tracking reconnect latency and failed-reconnect rate across a simulated rolling deploy of all instances.

      Quick Revision Cheat Sheet

      • Node's event loop is single-threaded for JS execution — more cores need more processes (cluster mode), not just a bigger machine.
      • Cluster-mode workers don't share memory — in-memory caches/rate-limiters/counters need an external store (Redis) to behave consistently.
      • Horizontal scaling requires stateless app design — session/job-scheduling state must live externally, not in process memory.
      • Graceful shutdown order: fail readiness check → stop accepting new connections → drain in-flight work (bounded) → close downstream resources → exit.
      • Always enforce a hard timeout that force-exits regardless of what's hung in the drain sequence.
      • Set your shutdown grace period (PM2 kill_timeout / k8s terminationGracePeriodSeconds) comfortably longer than your real p99 request duration.
      • Readiness and liveness probes serve different purposes during shutdown — readiness fails fast, liveness shouldn't, during a controlled drain.
      • WebSocket/long-lived connections need an explicit app-level close protocol — "wait for it to finish naturally" doesn't apply like it does for short HTTP requests.
      • App-layer scaling (cluster + horizontal) doesn't scale shared bottlenecks (DB, Redis, third-party rate limits) — identify the real ceiling before assuming more instances helps.
