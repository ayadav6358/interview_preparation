    Express Basics: Routing & Middleware

    ⏱ 2 hrs📍 Chapter 5 of 6

    One-line summary: Express is, at its core, exactly the middleware-array-plus-router pattern you'd build yourself on raw http (Chapter 4) — the senior-level skill isn't knowing the API, it's reasoning precisely about middleware order, because almost every "weird Express bug" is actually an ordering bug.

    On this page

      Why It Matters for a Senior Developer

      You've used Express for years, but can you explain exactly why putting app.use(authMiddleware) after your routes means it never runs for them? Can you explain why an error thrown inside an async route handler doesn't automatically reach your error-handling middleware in Express 4.x without extra work, but behaves differently in Express 5.x? These aren't edge cases — they're the actual cause of real incidents (an auth check that silently never ran, an unhandled rejection crashing the process). This chapter is the "say the mental model precisely" refresher, not an introduction to app.get.

      Why

      Middleware order is not a style preference — it's the entire request pipeline's control flow, executed top-to-bottom in registration order. A security-critical middleware (auth, rate limiting) registered after the routes it's meant to protect provides zero protection; this is a genuinely common real-world vulnerability, not a theoretical gotcha.

      Prerequisites

      Comfortable with the raw node:http module's req/res model. Related in this topic: HTTP Module & Basic Servers (what Express is automating), REST API Fundamentals (applying this chapter's routing to a well-designed API surface). Related elsewhere: Production APIs (Express/Fastify/Nest) for production hardening beyond these basics, and Secure Auth, Secrets, CORS/CSP/XSS/CSRF for what real auth/security middleware needs to cover.

      Core Concepts

      The app object and the middleware chain

      express() returns an app — itself a request handler function compatible with http.createServer(app), plus a routing/middleware API layered on top. Every app.use(fn) and every route handler (app.get/post/...) is, under the hood, added to the same ordered middleware chain. Express walks that chain top-to-bottom, in the exact order you registered things, for every request — a middleware either calls next() to pass control forward, or ends the response (res.send/json/end) to stop the chain there. If a middleware does neither, the request hangs forever (same failure mode as Chapter 4's raw http handler that never calls res.end()).

      Middleware signatures: (req, res, next) vs error middleware

      A normal middleware/route handler has the signature (req, res, next). An error-handling middleware has four parameters: (err, req, res, next) — Express detects this by function arity (checking fn.length === 4) and only invokes such functions when next(err) was called somewhere upstream, skipping every normal middleware in between. Error-handling middleware must be registered last, after all routes, or it will never be reached for errors from routes registered after it.

      Route params, query strings, and static files

      app.get('/bookmarks/:id', handler) populates req.params.id automatically — exactly the manual segment-matching from Chapter 4, done for you. req.query gives you the already-parsed query string as a plain object (?tag=js&sort=asc → { tag: 'js', sort: 'asc' }). express.static(dir) is itself just a middleware — mounted via app.use(express.static('public')) — that checks if the request path matches a file in dir and serves it directly, calling next() to fall through to your routes if no matching file exists.

      How It Works Under the Hood

      Express's router matches routes by converting each path pattern (including :param segments and wildcards) into a regular expression internally (historically via the path-to-regexp library), tested against the request path in registration order — the first matching route/middleware for a given method+path wins and runs; later matching routes are simply never reached unless the earlier handler calls next() instead of ending the response. This is why route order matters even among routes, not just among middleware: a broad pattern registered before a more specific one can "shadow" it.

      Async error handling is a known sharp edge. In Express 4.x, if an async route handler throws or its returned Promise rejects, Express does not automatically catch it and route it to your error middleware — an unhandled rejection in a plain async function used as a handler can crash the process (depending on your global unhandledRejection policy) rather than cleanly produce a 500. The standard 4.x fix is wrapping every async handler (manually, or via a small helper/library) to catch rejections and call next(err) explicitly. Express 5.x changes this: route handlers that return a rejected Promise are automatically forwarded to next(err) for you, closing this gap at the framework level — but understanding the 4.x behavior is still essential since a huge share of production Express code in 2025-26 is still on the 4.x line.

      Code Examples

      import express from 'express';

const app = express();

// ---- Middleware order matters: these run top-to-bottom for every matching request ----
app.use((req, res, next) => {                 // 1) logging — runs first, always
  const start = Date.now();
  res.on('finish', () => {
    console.log(`${req.method} ${req.originalUrl} ${res.statusCode} ${Date.now() - start}ms`);
  });
  next();
});

app.use(express.json({ limit: '1mb' }));       // 2) body parsing — must run before routes that read req.body

// BAD: auth middleware registered AFTER the routes it's meant to protect — does nothing for them
// app.get('/bookmarks', listBookmarks);
// app.use(requireAuth);

// GOOD: auth middleware registered BEFORE the routes it protects
app.use('/bookmarks', requireAuth);            // 3) scoped to a path prefix

function requireAuth(req, res, next) {
  const token = req.headers.authorization;
  if (!token) return res.status(401).json({ error: 'Missing Authorization header' });
  next();                                       // pass control forward — don't forget this!
}

let bookmarks = [];
let nextId = 1;

app.get('/bookmarks', (req, res) => {
  const { tag } = req.query;                   // already parsed — no manual URL parsing needed
  const result = tag ? bookmarks.filter(b => b.tags?.includes(tag)) : bookmarks;
  res.json(result);
});

app.get('/bookmarks/:id', (req, res) => {       // :id auto-populates req.params.id
  const item = bookmarks.find(b => b.id === Number(req.params.id));
  if (!item) return res.status(404).json({ error: 'Not found' });
  res.json(item);
});

app.post('/bookmarks', (req, res) => {
  const { url, title } = req.body;              // parsed by express.json() middleware above
  if (!url || !title) return res.status(400).json({ error: 'url and title are required' });
  const item = { id: nextId++, url, title };
  bookmarks.push(item);
  res.status(201).json(item);
});

// ---- Express 4.x: async handlers do NOT auto-catch rejections — wrap them ----
function asyncHandler(fn) {
  return (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);
}
app.get('/bookmarks-from-db/:id', asyncHandler(async (req, res) => {
  const item = await fakeDbLookup(req.params.id);   // if this rejects, asyncHandler forwards to next(err)
  res.json(item);
}));

// ---- 404 fallback: must come after all real routes ----
app.use((req, res) => res.status(404).json({ error: 'Route not found' }));

// ---- Error-handling middleware: 4 args, MUST be registered last ----
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.statusCode || 500).json({ error: err.message || 'Internal Server Error' });
});

app.listen(3000, () => console.log('Listening on http://localhost:3000'));

      Real-World Production Scenario at Scale

      At scale

      A security review flagged that a newly added "export all data as CSV" admin endpoint was reachable without authentication, despite the team being confident requireAuth was applied globally. Root cause: the endpoint was added via app.get('/admin/export', exportHandler) directly on the main app module, which was imported and its routes registered before the shared app.use(requireAuth) line further down in the bootstrap file — an easy mistake in a growing codebase where route registration got spread across multiple files imported in a particular order. The fix was immediate (reorder), but the longer-term fix was structural: the team moved to Express's Router objects per feature, with auth middleware applied explicitly at the router-mount level (app.use('/admin', requireAuth, adminRouter)) rather than relying on a single easily-misordered global middleware list, making the protection visually obvious at every mount point instead of implicit in file-load order.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Registering auth/validation middleware after the routes it's meant to protect. Express runs middleware strictly in registration order — a later app.use provides zero protection to routes already matched and responded to above it.

      Gotcha

      Assuming Express 4.x automatically catches a rejected Promise from an async route handler. It doesn't — you must wrap async handlers (manually or with a helper) to forward rejections to next(err), or they can surface as an unhandled rejection instead of a clean 500 response. Express 5.x fixes this specifically for route handlers, but check your actual version.

      • Error-handling middleware (4-arg signature) must be registered last — after every route and every normal middleware — or errors from later-registered routes will never reach it.
      • Always call next() in a middleware that isn't ending the response — forgetting it hangs the request exactly like a raw http handler that never calls res.end().
      • Prefer Router objects mounted with explicit middleware at the mount point over a single flat list of global app.use calls as the app grows — it makes protection scope visually unambiguous.
      • Don't forget express.json() only parses JSON bodies — a different content type (e.g. multipart form uploads) needs a different middleware (e.g. multer) entirely.

      Interview Questions

      Basic

      What does calling next() in a middleware do?

      It passes control to the next middleware/route handler in the chain; without calling it (and without ending the response another way), the request hangs with no response ever sent.

      Follow-up: what are the two valid ways a middleware can "finish" handling a request?
      How does Express distinguish a normal middleware from an error-handling middleware?

      By function arity — a 4-parameter function (err, req, res, next) is treated as error-handling middleware, only invoked when next(err) was called upstream; a 3-parameter function (req, res, next) is normal middleware.

      Follow-up: where must error-handling middleware be registered relative to your routes?
      How do you access a route parameter like :id in Express?

      Via req.params.id for a route registered as app.get('/bookmarks/:id', handler) — Express parses it automatically from the matched URL segment.

      Follow-up: how do you access query string parameters instead?
      Does middleware registration order matter in Express?

      Yes — Express runs middleware strictly in the order it was registered for every matching request; a middleware registered after a route it was meant to guard provides no protection to that route.

      Follow-up: give a concrete security consequence of getting this order wrong.
      What does express.json() do and where must it be registered?

      It's middleware that parses a JSON request body into req.body; it must be registered before any route handler that reads req.body, since middleware only affects requests that reach it after registration order.

      Follow-up: what happens if you try to read req.body in a route without express.json() registered first?
      What is express.static and how does it interact with next()?

      It's middleware that serves files directly from a given directory if the request path matches a file; if no matching file exists, it calls next() to pass control to subsequent middleware/routes instead of responding with a 404 itself.

      Follow-up: where would you typically register it relative to your API routes?

      Medium

      Why doesn't Express 4.x automatically catch an error thrown inside an async route handler?

      Express's internal route-dispatch call wraps synchronous handler execution in a try/catch, but when an async function is called, it returns a Promise immediately — a synchronous throw inside that function actually becomes a Promise rejection, not a synchronous exception Express's wrapper can see; Express 4.x's dispatcher doesn't attach a .catch() to that returned Promise, so the rejection goes unhandled unless the developer calls next(err) explicitly or wraps the handler.

      Follow-up: what specifically changed in Express 5.x to fix this?
      Explain why app.use('/admin', requireAuth, adminRouter) is a stronger pattern than a single global app.use(requireAuth) for a growing codebase.

      Mounting middleware explicitly at the specific path prefix it protects makes the protection visually co-located with the routes it applies to, immune to ordering mistakes elsewhere in a large bootstrap file where routes might be registered across many imported modules. A single global app.use(requireAuth) relies on every future route being registered after that one line, in every file, forever — a fragile assumption at scale.

      Follow-up: what's a scenario where a global middleware is still the better choice over per-route-group mounting?
      How does Express's router decide which of two overlapping route patterns matches a given request?

      Routes are matched in registration order; the first pattern (converted internally to a regex) that matches the request's method and path wins, and execution stops there unless that handler calls next() to fall through. A broadly-matching route registered before a more specific one can "shadow" it, which is why route-order among routes themselves (not just among middleware) can be a real bug source.

      Follow-up: give an example of two route patterns where registration order changes which one actually handles a request.
      What's the practical difference between express.json() and a hand-rolled body parser like the one you'd write on raw http?

      Functionally similar (collect chunks, concatenate, JSON.parse), but express.json() adds production-necessary guardrails out of the box: a configurable size limit (protecting against unbounded memory growth from a malicious payload), correct Content-Type checking (only parses bodies actually claiming to be JSON), and consistent error forwarding (a parse failure calls next(err) with a proper error object rather than throwing raw).

      Follow-up: what status code does express.json() typically produce for a payload exceeding its configured limit, and why that code specifically?
      Why would a 404 handler registered via app.use((req,res) => ...) before your actual routes break your entire app?

      Because it has no path restriction, it matches every request regardless of method or path, and since middleware runs in registration order, it would intercept and respond to every single request before any real route is ever reached — your routes would become entirely unreachable dead code.

      Follow-up: why does it work correctly when registered as the very last app.use, after all real routes?
      How would you test that your auth middleware is actually applied to every intended route, not just manually verify by reading the code?

      Write integration tests that hit every protected route without an Authorization header and assert a 401, as part of the standard test suite — this converts "we're pretty sure auth is applied everywhere" into an automatically-enforced, regression-proof guarantee that fails CI the moment a new route is added without it, rather than relying on code review catching a misordered app.use.

      Follow-up: how would you structure this test to automatically cover new routes added in the future without manually listing every path?

      Advanced

      Design a codebase convention/lint rule that makes "middleware registered in the wrong order" structurally hard to get wrong as a team scales past a handful of engineers.

      Mandate Router-per-feature with explicit middleware passed at the mount point (app.use('/admin', requireAuth, adminRouter)) rather than ever calling bare global app.use(authMiddleware) in the main bootstrap file — this makes the protection visible at the single call site where a route group is wired in, rather than depending on file-import order elsewhere. Pair this with an automated test (as described in the medium section) that asserts every route under a given prefix actually 401s without credentials, run in CI, so a future engineer adding a route without realizing it needs protection gets caught immediately rather than in a security review months later.

      Follow-up: how would you retrofit this convention onto an existing large Express app that currently uses flat global middleware, with minimal risk during the migration?
      Explain precisely why an async route handler's unhandled rejection in Express 4.x can crash the entire process, and what Node-level mechanism is responsible.

      A Promise rejection with no attached .catch() anywhere in its chain triggers Node's 'unhandledRejection' process event; depending on the Node version and configuration, the default behavior (since Node 15) is to terminate the process with a non-zero exit code if nothing handles that event, treating unhandled rejections roughly as seriously as uncaught exceptions. Since Express 4.x's route dispatcher doesn't attach a .catch() to an async handler's returned Promise, a thrown error inside it becomes exactly this kind of unhandled rejection unless the developer's own code (an asyncHandler wrapper, or Express 5.x's built-in handling) catches it first.

      Follow-up: how would you add a last-resort global safety net for this without fixing every individual handler, and what are its limits?
      How would you benchmark whether Express's middleware-chain overhead is meaningful for your specific service's latency budget, versus just assuming "Express is slower than Fastify" from blog posts?

      Build a minimal representative endpoint in both frameworks doing your actual workload's typical work (a DB call, JSON serialization of a realistic payload size), load test both under your production-realistic concurrency with the same tooling (autocannon), and compare p50/p99 latency and throughput directly — framework dispatch overhead is usually dwarfed by I/O-bound work (a DB round trip) for typical CRUD APIs, so the generic "Fastify is faster" claim may be irrelevant to your actual bottleneck. Only treat framework overhead as a real optimization lever if profiling shows meaningful time spent specifically in framework dispatch code relative to your actual handler logic.

      Follow-up: in what kind of workload would framework-level overhead actually become the dominant cost, making this optimization worth pursuing?
      Design an error-handling middleware strategy that distinguishes operational errors (expected, e.g. validation failures, not-found) from programmer errors (bugs, e.g. a null reference), and explain why the distinction matters for production stability.

      Create a custom error class hierarchy (e.g. AppError with a statusCode and isOperational flag) that route handlers throw/next() with for expected failure cases; the centralized error middleware checks isOperational — for true, it safely returns the error's message and status code to the client; for false (a genuine bug, e.g. a TypeError), it logs the full stack internally but returns a generic "Internal Server Error" to the client (never leaking internal error details/stack traces) and, depending on severity, may trigger a process-level alert or even a controlled restart, since an unexpected programmer error indicates the process may be in an unknown, potentially corrupted state that's riskier to keep serving traffic from indefinitely.

      Follow-up: why is leaking a raw error message/stack trace to the client a real security concern, not just a cosmetic one?
      You need to apply a middleware to every route except one specific public health-check endpoint. What are your options and their tradeoffs?

      Option 1: register the health-check route before the middleware in the chain (order-based exclusion) — simple, but fragile if routes get reordered later. Option 2: use a path-based mount so the middleware only applies to a specific prefix the health check isn't under (e.g. mount auth only on '/api', leave '/healthz' outside it) — clearer intent, scales better. Option 3: have the middleware itself check req.path and call next() immediately for excluded paths — flexible but embeds exclusion logic inside the middleware rather than at the routing/composition level, which is harder to audit at a glance. Prefer path-based mounting (option 2) as the default for clarity; reserve in-middleware exclusion checks for cases where the exclusion logic is genuinely dynamic/conditional.

      Follow-up: how would your answer change if the exclusion needed to be based on something only known at request time, like a feature flag?

      Practice Assignments

Deliberately register the auth middleware AFTER the route, demonstrate the route is reachable without credentials, then fix the order and demonstrate it now correctly returns 401 without a token.

      • Must show both the broken and fixed behavior with actual curl/HTTP output.
      • Must include a one-paragraph written explanation of why order caused the bug.

      Acceptance criteria: Clear before/after demonstration with correct reasoning about Express's top-to-bottom middleware execution.

      Hints

      Express matches and runs middleware/routes in registration order — a route handler that already sent a response is simply never reached by middleware registered after it.

      Bonus: Refactor to use app.use('/protected', authMiddleware, protectedRouter) instead and explain why it's more robust against future ordering mistakes.

      Intermediate (2-4 hrs)

      Express bookmarks CRUD API (part 2 of the capstone)

      Rebuild the raw-http bookmarks API from Chapter 4 in Express: proper routing with :id params, express.json() for body parsing, a logging middleware, centralized 4-arg error-handling middleware registered last, and a 404 fallback. Keep the file-based JSON storage from Chapter 3.

      • All 5 endpoints functionally identical to the raw-http version from the client's perspective.
      • Every error path routes through the single centralized error middleware.

      Acceptance criteria: The same curl test script from Chapter 4's assignment passes unmodified against this Express version.

      Hints

      Wrap async route handlers with an asyncHandler helper (or upgrade to Express 5.x) so thrown/rejected errors inside them correctly reach next(err).

      Bonus: Write a short README documenting, line by line, what Express saved you from writing by hand compared to the Chapter 4 raw version.

      Advanced (1-2 days)

      Harden the API: validation, rate limiting, and structured logging

      Extend the Express bookmarks API with: request body validation middleware (reject malformed input with a 400 and field-level error details, hand-rolled or using a library like zod), basic per-IP rate limiting middleware (hand-rolled with an in-memory counter, or using express-rate-limit), and structured JSON request logging (method, path, status, duration, a request ID) instead of plain console.log strings.

      • Validation errors must return a consistent error shape matching this topic's REST conventions (see Chapter 6).
      • Rate limiting must return 429 with a clear error body once exceeded.
      Hints

      Generate a request ID (crypto.randomUUID()) in your logging middleware and attach it to req for downstream handlers/error middleware to include in every log line for that request.

      Bonus: Add graceful shutdown handling (SIGTERM) that stops accepting new connections and lets in-flight requests finish before exiting.

      Quick Revision Cheat Sheet

      • Express middleware runs top-to-bottom in strict registration order — order is control flow, not cosmetic.
      • A middleware must call next() or end the response — doing neither hangs the request.
      • Error-handling middleware has 4 params (err, req, res, next); Express detects it by arity and only calls it after next(err).
      • Error-handling middleware must be registered LAST, after all routes and normal middleware.
      • req.params comes from :route segments; req.query comes from the parsed query string — both automatic, unlike raw http.
      • Express 4.x does NOT auto-catch async handler rejections — wrap with asyncHandler or call next(err) explicitly; Express 5.x fixes this for route handlers.
      • express.static calls next() when no matching file exists, falling through to your routes.
      • Prefer Router-per-feature mounted with explicit middleware over a single flat global app.use list as the app grows.
      • A 404 catch-all middleware with no path must be registered after every real route, or it swallows everything.
      • Test that protective middleware (auth, validation) is actually applied via integration tests, not code review alone.
