    Node.js Basics: Runtime & Modules

    ⏱ 2 hrs📍 Chapter 1 of 6

    One-line summary: Node.js is V8 plus libuv plus a set of C++/JS bindings exposed as globals and core modules — and the CommonJS-vs-ESM split isn't a style preference, it's two genuinely different module systems with different resolution algorithms, loading semantics (sync vs async), and interop rules you're expected to state precisely in a senior interview.

    On this page

      Why It Matters for a Senior Developer

      You've shipped Node services for years, but "explain what Node.js actually is" and "explain exactly how require resolves a module path" are two questions that trip up experienced engineers in interviews because day-to-day you never need the precise mental model — you just write code that works. At senior/staff level, interviewers use this topic to check whether you can reason about module interop bugs (the single most common real-world Node packaging headache in 2025-26: a dependency shipping ESM-only while your codebase is CommonJS, or vice versa), explain startup/cold-start cost in serverless contexts, and justify architectural choices like "why did we pick ESM for this new service" with more than a vibe.

      Why

      Module system mismatches are a leading cause of "works on my machine, breaks in the pipeline" bugs when upgrading dependencies — a package goes ESM-only in a major version bump, and your CommonJS codebase's require() throws ERR_REQUIRE_ESM. Knowing the exact interop rules (CJS can't synchronously require ESM; ESM can import CJS with caveats) turns a confusing runtime error into a two-minute fix.

      Prerequisites

      Comfortable writing and running JavaScript day-to-day; basic command-line usage. Related in this topic: npm & Package Management (package.json's "type" field controls module resolution), HTTP Module & Basic Servers. Related elsewhere: JavaScript Fundamentals for closures/scope that underpin module encapsulation, and Event Loop Internals & libuv once you want the deep runtime internals beyond this refresher.

      Core Concepts

      What Node.js actually is

      Node.js is not "JavaScript on the server" in the sense of a spec — it's a C++ program that embeds V8 (Google's JS engine: parser, bytecode interpreter/Ignition, optimizing compiler/Turbofan, garbage collector) and libuv (a C library providing an event loop, async I/O, and a thread pool), and glues them together with a layer of C++ bindings and JS "internal" modules that implement the Node-specific APIs you call every day — fs, http, process, Buffer, etc. V8 alone has no concept of a filesystem, a socket, or setTimeout — those are all Node/libuv additions. This is precisely why the same JS runs differently in a browser vs Node: the language is identical (both use ECMAScript), but the host-provided APIs around it differ completely.

      CommonJS vs ECMAScript Modules (ESM): two real systems, not a style choice

      CommonJS (CJS) is Node's original module system: require(), module.exports, synchronous resolution and loading, and each file wrapped in an implicit function giving you require, module, exports, __filename, __dirname as locals. ESM is the standard JS module system: import/export syntax, asynchronous and statically-analyzable (imports are resolved and hoisted before any code runs — this is what enables live bindings and tree-shaking), and it has no __dirname/__filename/ require by default (you reconstruct them from import.meta.url).

      Node decides which system a file uses via, in order of precedence: a .mjs/.cjs extension (always wins), else the nearest parent package.json's "type" field ("module" → ESM, "commonjs" or absent → CJS, historically), else CJS. Interop rules that actually bite in practice: ESM can import a CJS module (its module.exports becomes the default export, with best-effort named-export detection for simple cases); CJS cannot synchronously require() a pure-ESM module — as of modern Node (22 LTS), require() of a synchronous ESM module graph is supported experimentally/stably in recent versions, but top-level-await-using ESM still cannot be required synchronously, so the universally safe pattern remains a dynamic import() (which returns a Promise) from CJS when you need an ESM-only dependency.

      module.exports vs exports, and the require cache

      Inside a CJS file, exports is just a local variable that initially points to the same object as module.exports. Assigning properties onto exports.foo = ... works because you're mutating the shared object; reassigning exports = {...} breaks the link (now exports points elsewhere while module.exports — the thing actually returned by require — is unchanged). The safe habit: always export via module.exports directly when replacing the whole export object, and exports.x = ... only when adding named properties.

      require() caches modules by resolved absolute file path — the first require('./x') executes the file and caches module.exports; every subsequent require('./x') anywhere in the process returns the same cached object reference, which is why mutable singleton state (DB connections, config objects) "just works" via plain requires, and also why circular requires can hand back a partially-populated object (the cache entry exists before the file finishes executing).

      How It Works Under the Hood

      CJS module resolution (the algorithm behind require('x')) is synchronous and file-system-walking: for a relative/absolute path, Node tries the exact path, then path.js, then path/index.js, then checks package.json "main". For a bare specifier (require('lodash')), Node walks up through node_modules directories starting from the current file's directory to the filesystem root, checking each for a matching package — this is why a deeply nested dependency can resolve to a different installed version than a top-level one (version hoisting/dedup in the lockfile affects exactly this walk).

      ESM resolution is different in kind: it's specified by the ECMAScript spec plus Node's resolution algorithm, is asynchronous end-to-end, and supports package.json "exports" maps (which can expose different entry points for import vs require, or restrict which subpaths of a package are importable at all — a "dual package" ships both and picks based on how it's loaded). Because ESM imports are statically declared, Node can build the entire module graph and detect missing exports before executing any module body — a class of error CJS can only catch at runtime when the property turns out to be undefined.

      Code Examples

      // ---- CommonJS: math.js ----
function add(a, b) { return a + b; }
function multiply(a, b) { return a * b; }

module.exports = { add, multiply };          // GOOD: replace whole export object
// exports.add = add;                        // also fine: named property assignment
// exports = { add, multiply };               // BAD: breaks the module.exports link, require() won't see this

// ---- CommonJS: app.js ----
const { add, multiply } = require('./math');
console.log(add(2, 3), __dirname, __filename); // __dirname/__filename are free locals in CJS


// ---- ESM: math.mjs (or "type": "module" in package.json) ----
export function add(a, b) { return a + b; }
export function multiply(a, b) { return a * b; }
export default { add, multiply };

// ---- ESM: app.mjs ----
import { add, multiply } from './math.mjs';
import defaultExport from './math.mjs';
import { fileURLToPath } from 'node:url';
import path from 'node:path';

const __filename = fileURLToPath(import.meta.url);   // ESM has no __filename by default
const __dirname = path.dirname(__filename);           // ...so you reconstruct it


// ---- The interop pain point: requiring an ESM-only dependency from CJS ----
// BAD (throws ERR_REQUIRE_ESM if "esm-only-pkg" is pure ESM):
// const pkg = require('esm-only-pkg');

// GOOD: dynamic import returns a Promise, works from CJS
async function loadPkg() {
  const pkg = await import('esm-only-pkg');
  return pkg.default ?? pkg;
}


// ---- require cache: singleton behavior ----
// db.js
let connection = null;
module.exports = {
  getConnection() {
    if (!connection) connection = { connectedAt: Date.now() }; // created once
    return connection;
  }
};
// Every require('./db') across the whole app returns the SAME module.exports object,
// so getConnection() keeps returning the same connection after the first call.

      Real-World Production Scenario at Scale

      At scale

      A mid-sized API team bumped a logging library's minor version in a routine dependency update PR. CI failed everywhere with Error [ERR_REQUIRE_ESM]: require() of ES Module ... not supported. The library had quietly shipped an ESM-only build starting from that minor (a semver-irresponsible move, but common in the ecosystem). The team's entire codebase was CommonJS (package.json had no "type": "module", every file used require). Two real fixes existed: pin the dependency to the last CJS-compatible version (fast, technical-debt-accruing), or convert the one import site to a dynamic await import() wrapped behind a small async-initialized singleton (correct, slightly more invasive since the call site needed to become async). They chose the dynamic import fix for that one module and used it as the trigger to start a deliberate, module-by-module migration plan toward ESM across the codebase, rather than reactively pinning versions forever as more dependencies go ESM-only (a one-way trend across the npm ecosystem since ~2022-2023).

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Assuming "type": "module" in package.json is purely cosmetic. It changes real runtime behavior: .js files are now parsed as ESM (no require, no __dirname, this at module top level is undefined instead of module.exports), and any script relying on CJS globals breaks immediately — this is the single most common "it worked yesterday" bug after someone adds that field to migrate the project.

      Gotcha

      Reassigning exports instead of mutating it (exports = { foo }) and then being confused why require() doesn't see foo. Only module.exports is ever returned by require() — exports is a convenience alias that stops being useful the moment you reassign it.

      • Don't mix require and top-level import in the same file — pick the module system per file/package, and bridge with dynamic import() when truly necessary.
      • Check a package's "exports" map in package.json before assuming require('pkg/internal/thing') will keep working — modern packages often lock down which subpaths are importable.
      • Remember circular require()s can hand back a partially-built object — order-sensitive circular dependencies are a design smell, not a Node quirk to "fix" with workarounds.

      Interview Questions

      Basic

      What is Node.js, precisely?

      A C++ program that embeds the V8 JavaScript engine and the libuv library (event loop, async I/O, thread pool), exposing filesystem, networking, and other OS-level capabilities to JavaScript through core modules and C++ bindings. It is not part of the JS language spec — it's a runtime/host environment.

      Follow-up: name one thing V8 provides and one thing libuv provides.
      What's the difference between require() and import?

      require() is CommonJS: synchronous, dynamic (can be called conditionally/anywhere), returns module.exports from a cache. import is ESM: asynchronous under the hood, statically analyzed/hoisted (must appear at top level in standard usage), and supports live bindings.

      Follow-up: can you call require() conditionally inside an if block? Can you do the same with static import syntax?
      What does module.exports do?

      It's the object that require() actually returns for that file; whatever module.exports references at the end of the file's execution is what callers receive.

      Follow-up: what's the difference between module.exports and the exports shorthand variable?
      How does Node decide if a .js file is CommonJS or ESM?

      In order: explicit .mjs/.cjs extension wins outright; otherwise it looks at the nearest parent package.json's "type" field ("module" = ESM, "commonjs" or absent = CJS).

      Follow-up: what happens if you put .mjs code in a file but the nearest package.json says "type": "commonjs"?
      What are __dirname and __filename, and why don't they exist in ESM by default?

      They're CJS-only locals injected by the module wrapper function giving the current file's directory/path. ESM has no implicit module wrapper providing these; you derive them from import.meta.url via node:url's fileURLToPath.

      Follow-up: write the two lines needed to get __dirname equivalent behavior in an ESM file.
      Is require() cached? What does that mean practically?

      Yes — cached by resolved absolute file path. The module's code runs once; every subsequent require of the same resolved path returns the same object reference, enabling singleton patterns like a shared DB connection object.

      Follow-up: what would happen if you deleted the require cache entry manually and required it again?

      Medium

      Can a CommonJS file require() a pure ESM module synchronously? What's the workaround?

      Not for ESM modules that use top-level await; those cannot be required synchronously because require() is fundamentally synchronous and such ESM evaluation is inherently asynchronous. The portable workaround is a dynamic import() call, which returns a Promise, from an async context in the CJS file.

      Follow-up: why can ESM import a CJS module more easily than the reverse?
      Explain the package.json "exports" field and why it matters for library authors.

      It's an explicit map of which subpaths of a package are importable/requirable and what file each resolves to (optionally different files for "import" vs "require" conditions, enabling dual CJS/ESM packages). It replaces blanket access to every file in the package, letting authors enforce a public API surface and prevent consumers from depending on internals.

      Follow-up: what breaks for a consumer doing require('pkg/src/internal/util') if the exports map doesn't list that subpath?
      Walk through exactly how require('lodash') resolves when called from deep inside nested node_modules.

      Node starts at the current file's directory, checks for a node_modules/lodash there; if absent, walks up to the parent directory's node_modules, repeating until found or reaching the filesystem root. This means a deeply nested dependency can resolve to a different installed version of lodash than a sibling package higher in the tree, depending on how the package manager deduped/hoisted during install.

      Follow-up: how does npm's flat node_modules structure (vs older nested structures) change this in practice?
      Why can reassigning exports = {...} inside a CJS file silently break your module?

      exports starts as a reference to the same object as module.exports, but it's just a local variable — reassigning it points that local variable elsewhere while module.exports (the thing require() actually returns) is untouched, so none of the new properties are visible to callers.

      Follow-up: what's the fix, and why does exports.foo = ... still work fine?
      What's a circular require() and what actually happens at runtime?

      When module A requires B and B (directly or transitively) requires A again before A finishes executing, the second require gets whatever partial module.exports A has built so far (often an incomplete object), not the final version — because the cache entry is created before the module body finishes running, specifically to handle this case without infinite recursion.

      Follow-up: how would you refactor two circularly-dependent modules to remove the cycle?
      Why does V8 alone not provide setTimeout or fetch, and where do those actually come from in Node?

      V8 implements only the ECMAScript language spec — no I/O, timers, or networking. setTimeout, fetch, and similar are Node-provided globals implemented via libuv (timers) and Node's own HTTP client code (fetch, added as a built-in using undici under the hood), injected into the global scope by Node's bootstrap process, not by V8 itself.

      Follow-up: why does this mean the exact same setTimeout behaves slightly differently in a browser vs Node for edge cases?

      Advanced

      You're migrating a large CJS codebase to ESM incrementally. Describe your strategy for doing this safely without a single big-bang rewrite.

      Start by auditing dependency ESM-only status (several haven't gone ESM-only; prioritize migrating leaf modules with no circular dependencies first). Use file extensions (.mjs/.cjs) rather than flipping the package.json "type" field globally too early, since that field affects every plain .js file at once. Convert module-by-module leaf-to-root, running a dual-mode test suite, and keep a dynamic-import bridge available for stragglers. Only flip "type": "module" once the dependency graph is majority converted and you've validated top-level await usage doesn't break synchronous startup assumptions elsewhere (e.g., clustering, process managers expecting synchronous require at boot).

      Follow-up: what's uniquely risky about flipping the "type" field as the very first step instead of the last?
      Explain precisely why ESM enables tree-shaking and dead-code elimination in bundlers but CJS fundamentally resists it.

      ESM imports/exports are static and declared at the top level — a bundler can build the full dependency graph and determine, without executing any code, exactly which exports are used where, then drop unused ones. CJS exports are the result of arbitrary runtime code (module.exports could be conditionally assigned, computed, or mutated based on control flow), so a bundler cannot safely prove which parts are dead without actually running the code — it must conservatively keep nearly everything.

      Follow-up: can a bundler tree-shake a CJS module that's required by an ESM entry point? Why or why not, in general?
      Design a dual-package (CJS + ESM) build strategy for a library you maintain, and explain the pitfalls of getting it wrong.

      Ship separate build outputs (e.g. dist/cjs and dist/esm) and use package.json "exports" with "require"/"import" conditions pointing to each, keeping a single source of truth compiled by your bundler/tsc with two targets. The classic pitfall is the "dual package hazard": if your library has internal singleton state (e.g., a cache, a registry) and a consumer's dependency tree pulls in both the CJS and ESM build simultaneously (common with transitive deps), you get two separate module instances with two separate copies of that state, causing subtle bugs like "my singleton isn't shared" that are very hard to diagnose.

      Follow-up: how would you detect in your test suite that a dual package hazard is actually occurring for your library?
      How does Node's ESM loader's static analysis enable detecting a missing named export at load time, and why can't CJS do the same?

      Because ESM import statements must name their bindings statically, Node's module loader can build the complete module graph, resolve what each module exports, and verify at link time (before any module body executes) that every named import actually exists on the target module — producing a SyntaxError/ReferenceError-class failure before a single line runs. CJS exports are just properties on a plain object assembled by arbitrary runtime code, so "does this property exist" can only be answered after the required module has fully executed — any missing property just resolves to undefined at the use site, a runtime TypeError waiting to happen rather than a load-time failure.

      Follow-up: is this early-detection property still true if the ESM module being imported is itself a CJS module under the hood (default-export interop)? Why or why not?
      In a serverless/Lambda context, how does the choice between CJS and ESM affect cold start time, and why?

      CJS's synchronous, eager module resolution can be marginally faster for small dependency graphs typical of serverless functions since there's less async overhead in the loading machinery itself, but the dominant cold-start cost is almost always V8 parsing/compiling your bundled code and initializing SDK clients, not the module system per se. In practice, bundling (esbuild/webpack) to a single flattened file collapses most of this difference regardless of source module system, so the module-system choice matters far less than whether you've bundled and minimized dependency footprint at all.

      Follow-up: given that, why do many serverless style guides still recommend CJS for Lambda specifically, historically?

      Practice Assignments

      Beginner (30-60 min)

      Convert a small CJS module to ESM and back

      Write a tiny utility module (3-4 functions) in CommonJS. Convert it to ESM (rename to .mjs, convert require/module.exports to import/export), get the equivalent of __dirname working via import.meta.url, then convert it back to CJS. Note every single line that had to change.

      • Must run correctly in both forms via `node file.mjs` / `node file.cjs`.
      • Must include a working __dirname-equivalent in the ESM version.

      Acceptance criteria: Both versions produce identical console output; you can explain why each changed line had to change.

      Hints

      Use `node:url`'s `fileURLToPath(import.meta.url)` plus `node:path`'s `dirname()` for the ESM __dirname equivalent.

      Bonus: Add a default export in the ESM version and show how a CJS consumer sees it via require() (it lands on `.default` unless Node's CJS/ESM interop collapses it).

      Intermediate (2-4 hrs)

      Build and diagnose a circular require

      Create two CommonJS modules, A and B, that require each other at the top level, each exporting a function that calls the other's exported function. Run it, observe the actual failure/partial-object behavior, then fix it using a lazy-require pattern (require the other module inside the function body, not at the top) and explain why that fixes it.

      • Must demonstrate the broken behavior first with console output showing a partial/undefined export.
      • Must then show the fixed version working correctly.

      Acceptance criteria: Written explanation correctly ties the broken behavior to require's caching-before-completion mechanism.

      Hints

      The module that gets required second in the cycle will see the first module's exports object as it existed at the moment of the circular require call — likely missing properties defined after that point in the file.

      Bonus: Reproduce the same scenario in ESM and compare the error/behavior difference.

      Advanced (1-2 days)

      Build a dual CJS/ESM npm package from scratch

      Create a tiny utility library, write its source once, and produce two build outputs (a CJS build and an ESM build) using a bundler or tsc. Configure package.json's "exports" field to correctly route `require()` and `import` consumers to the right build. Write two tiny test projects (one CJS, one ESM) that both consume your package and verify both work correctly.

      • Must work when installed via a local `npm link` or `file:` dependency, not just in-repo.
      • Must correctly expose TypeScript types for both if you use TS.
      Hints

      Use the "exports" field's conditional exports (`"require"` and `"import"` keys) under your package's main export entry; test with both a `.cjs` and `.mjs` consumer script.

      Bonus: Deliberately introduce a dual-package hazard (shared singleton state) and demonstrate it breaking, then document the fix.

      Quick Revision Cheat Sheet

      • Node.js = V8 (JS engine) + libuv (event loop, thread pool, async I/O) + C++ bindings + core JS modules. Not part of the JS spec itself.
      • CJS: require/module.exports, synchronous, dynamic, cached by resolved absolute path.
      • ESM: import/export, asynchronous under the hood, statically analyzed/hoisted, no require/__dirname/__filename by default.
      • Module type decided by: .mjs/.cjs extension (wins) → nearest package.json "type" field → default CJS.
      • CJS cannot synchronously require a top-level-await-using ESM module — bridge with dynamic import().
      • exports is a convenience alias for module.exports; reassigning exports breaks the link, module.exports is what require() actually returns.
      • package.json "exports" field locks down which subpaths of a package are importable and can route require vs import to different builds (dual packages).
      • Circular require() can hand back a partially-built module.exports — a design smell to refactor, not just patch around.
      • Dual-package hazard: if both a CJS and ESM build of the same library load simultaneously, singleton state isn't shared between them.
