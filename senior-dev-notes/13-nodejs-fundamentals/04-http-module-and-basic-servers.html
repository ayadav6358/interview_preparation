    HTTP Module & Basic Servers

    ⏱ 2 hrs📍 Chapter 4 of 6

    One-line summary: Every framework you've ever used — Express, Fastify, Nest — is built on top of the same node:http module you can use directly; building a raw server once is what makes "middleware," "routing," and "body parsing" stop being framework magic and become three specific, understandable problems you're watching the framework solve for you.

    On this page

      Why It Matters for a Senior Developer

      You've written hundreds of Express routes. Fewer senior candidates can explain what req and res actually are (they're Node streams — specifically a Readable and a Writable), why a request body doesn't arrive as a parameter but as a stream of data events, or why calling res.end() twice throws. Interviewers probe this because it reveals whether you understand your framework's foundation or have only ever worked one abstraction layer above it — and because debugging a genuinely weird production HTTP issue (a hung connection, a missing Content-Length, a streaming response that never flushes) requires dropping down to this layer.

      Why

      When Express "just works" for 99% of requests but intermittently hangs or double-sends a response under a specific edge case (a client disconnect mid-stream, an error thrown after headers are already sent), the fix usually requires understanding that res is a writable stream with real state (headersSent, finished) — not a black box object with a .json() method.

      Prerequisites

      Comfortable with async/await and basic networking concepts. Related elsewhere: HTTP & Networking Basics for the protocol fundamentals this chapter assumes, and Streams, Buffers & Backpressure for the stream mechanics req/res are built on in depth.

      Core Concepts

      http.createServer and the request/response objects

      http.createServer((req, res) => {...}) returns a server instance; the callback fires once per incoming request. req (an IncomingMessage) is a Readable stream giving you req.method, req.url (path + query string, not parsed into parts for you), and req.headers (lowercased keys) synchronously, but the request body arrives asynchronously as a stream of 'data' events (Buffer chunks) followed by an 'end' event — there's no built-in "give me the parsed body" without writing that yourself. res (a ServerResponse) is a Writable stream: you set res.statusCode, call res.setHeader(name, value), then res.write(chunk) any number of times, and finally res.end([data]) exactly once — calling end() twice, or writing after it, throws.

      Manual routing: matching method and URL yourself

      With no framework, "routing" is just reading req.method and parsing req.url yourself (via node:url's URL class, or simple string splitting) and branching — typically an if/else chain or a small lookup table keyed by `${method} ${pathname}`. There's no built-in concept of route parameters (/:id) — you implement that by splitting the path into segments and comparing positionally, or with a regex. Doing this by hand once is exactly what makes it obvious what Express's router is actually automating.

      Parsing a request body manually

      Because the body is a stream, parsing JSON from it means: collect every 'data' chunk into an array (or concatenate into a growing Buffer), wait for 'end', concatenate all chunks into one Buffer, convert to a UTF-8 string, then JSON.parse it — wrapped in a try/catch since client input is never trusted to be valid JSON. This is precisely what express.json() (and body-parser before it) does for you automatically, with additional guardrails like a size limit to prevent a malicious or buggy client from streaming gigabytes into memory before you ever get to validate anything.

      How It Works Under the Hood

      Each incoming TCP connection is handled by Node's networking layer using the OS's native async I/O (epoll/kqueue/IOCP — not the libuv thread pool, see Event Loop Internals), which is exactly why Node scales to large numbers of concurrent idle or slow connections cheaply. HTTP/1.1 keep-alive means a single TCP connection can carry multiple sequential request/response exchanges — the http module manages this transparently, but it's part of why a hung handler (one that never calls res.end()) can tie up a connection indefinitely rather than failing fast.

      Headers must be sent before any body bytes — calling res.setHeader after the first res.write() or after res.end() has already flushed headers throws ERR_HTTP_HEADERS_SENT, because HTTP/1.1 framing requires headers first, as one block, before the body starts. This is the underlying reason a common Express bug ("Cannot set headers after they are sent") happens: some code path called res.json()/res.end() once, and a later error handler or async callback tries to send a second response for the same request.

      Code Examples

      import http from 'node:http';
import { URL } from 'node:url';

// ---- Manual body-parsing helper ----
function readJsonBody(req) {
  return new Promise((resolve, reject) => {
    const chunks = [];
    req.on('data', (chunk) => chunks.push(chunk));
    req.on('end', () => {
      if (chunks.length === 0) return resolve(null);
      try {
        resolve(JSON.parse(Buffer.concat(chunks).toString('utf-8')));
      } catch (err) {
        reject(new Error('Invalid JSON body'));
      }
    });
    req.on('error', reject);
  });
}

function sendJson(res, statusCode, payload) {
  const body = JSON.stringify(payload);
  res.writeHead(statusCode, {
    'Content-Type': 'application/json',
    'Content-Length': Buffer.byteLength(body),
  });
  res.end(body);
}

// ---- A minimal raw-http bookmarks API with manual routing ----
let bookmarks = [];
let nextId = 1;

const server = http.createServer(async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const segments = url.pathname.split('/').filter(Boolean); // ['bookmarks'] or ['bookmarks', '42']

  try {
    if (req.method === 'GET' && segments[0] === 'bookmarks' && segments.length === 1) {
      return sendJson(res, 200, bookmarks);
    }

    if (req.method === 'GET' && segments[0] === 'bookmarks' && segments[1]) {
      const item = bookmarks.find(b => b.id === Number(segments[1]));
      if (!item) return sendJson(res, 404, { error: 'Not found' });
      return sendJson(res, 200, item);
    }

    if (req.method === 'POST' && segments[0] === 'bookmarks' && segments.length === 1) {
      const body = await readJsonBody(req);
      if (!body?.url || !body?.title) {
        return sendJson(res, 400, { error: 'url and title are required' });
      }
      const item = { id: nextId++, url: body.url, title: body.title };
      bookmarks.push(item);
      return sendJson(res, 201, item);
    }

    return sendJson(res, 404, { error: 'Route not found' });
  } catch (err) {
    // GOOD: centralized catch — any synchronous or awaited error in the handler ends up here
    return sendJson(res, 500, { error: err.message });
  }
});

server.listen(3000, () => console.log('Listening on http://localhost:3000'));

      Real-World Production Scenario at Scale

      At scale

      A team saw intermittent "Cannot set headers after they are sent to the client" errors in production logs, only under load, never reproducible locally. Root cause: a route handler awaited two independent async operations (a DB lookup and a cache write) without properly sequencing error handling — under normal timing, the DB lookup's error path sent a 404 response and returned; under load (DB occasionally slower than cache), the cache write's own unrelated error fired asynchronously after the 404 had already been sent, and a generic top-level error handler tried to send a second, 500 response for the same already-completed request. The fix was disciplined: every async branch that could independently fail needed to check res.headersSent before attempting to respond, and the underlying lesson generalized into a lint rule requiring all route logic to funnel through a single response-sending point rather than multiple scattered res.json() call sites.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting that req.url includes the query string and is not automatically parsed — treating req.url === '/bookmarks' when it's actually '/bookmarks?tag=js' silently fails every route match. Always parse with new URL(req.url, base) and compare against .pathname.

      Gotcha

      Not setting a body size limit when manually parsing — an unbounded chunks.push() loop will happily buffer gigabytes from a malicious or buggy client into memory before you ever get to reject it. Always track accumulated size and abort/destroy the connection past a sane limit.

      • Always check res.headersSent before attempting to send an error response from an async error path — you may already be too late.
      • Remember res.end() must be called exactly once per request, even on error paths — a hung handler that never calls it leaks the connection.
      • Don't trust `Content-Type` headers blindly — a client claiming `application/json` can still send garbage; always try/catch your JSON.parse.
      • Wrap the entire handler in try/catch (or equivalent) so no unhandled synchronous throw crashes the process via an uncaught exception.

      Interview Questions

      Basic

      What type of object is req in an http.createServer callback?

      An IncomingMessage, which is a Readable stream — headers/method/url are available synchronously, but the body arrives asynchronously as a stream of data events.

      Follow-up: what type is res, and what stream type is it?
      Does req.url include the query string?

      Yes — req.url is the full path plus query string as sent by the client (e.g. '/bookmarks?tag=js'), not pre-parsed into separate parts. You parse it yourself, typically with the URL class.

      Follow-up: what method/class would you use to split it into pathname and query parameters?
      How do you read a request body with the raw http module?

      Listen for 'data' events (Buffer chunks) on req, accumulate them, and on the 'end' event concatenate and parse the full body — there's no built-in synchronous "get the body" accessor.

      Follow-up: why might you want to track accumulated size while collecting chunks?
      What happens if you call res.end() twice?

      It throws an error — a response stream can only be ended once per request; the second call is writing/ending an already-finished stream.

      Follow-up: what property can you check before attempting to send a response to avoid this?
      Does the raw http module provide route parameters like /:id out of the box?

      No — there's no built-in routing concept at all; you implement path matching and parameter extraction yourself, typically by splitting the pathname into segments and comparing positionally or with a regex.

      Follow-up: what is a framework's router actually automating over this manual approach?

      Medium

      What does res.headersSent tell you and why does it matter in async error handling?

      It's true once headers have actually been flushed to the client (via writeHead, the first write, or end) — once true, you cannot set new headers or send a different status code. In async code where multiple independent operations might each try to send an error response, checking headersSent before responding prevents a "Cannot set headers after they are sent" crash when an earlier code path already responded.

      Follow-up: is checking headersSent sufficient to make your error handling fully correct, or just to prevent the crash?
      Why must headers be sent before any body bytes in HTTP/1.1, and what Node error results if you violate this?

      HTTP/1.1 message framing requires the status line and headers as one block before the body begins, since the client needs to know things like Content-Length/Transfer-Encoding before it can correctly parse the incoming body stream. Calling setHeader after write()/end() has already flushed headers throws ERR_HTTP_HEADERS_SENT.

      Follow-up: how does Transfer-Encoding: chunked change when the client knows the body is complete, versus Content-Length?
      Why is manually parsing JSON bodies risky without a size limit, and what's the fix?

      Without bounding accumulated chunk size, a malicious or buggy client can stream an arbitrarily large body, exhausting process memory before you ever get the chance to validate or reject it — a basic denial-of-service vector. The fix: track running byte total as chunks arrive and destroy the connection/respond with 413 once a sane limit is exceeded, exactly what express.json({ limit }) does for you.

      Follow-up: where specifically would you check the size — on every chunk, or only at the end?
      Explain what HTTP keep-alive means for a raw http server and why a hung handler is worse than it sounds.

      Keep-alive lets one TCP connection serve multiple sequential request/response exchanges without reconnecting. A handler that never calls res.end() doesn't just fail that one request — it holds that TCP connection (and the associated server resources) open indefinitely, and if connection limits are reached, can prevent new clients from connecting at all.

      Follow-up: how would you add a safety-net timeout to guarantee every request eventually completes or fails?
      How would you implement route parameters (e.g. /bookmarks/:id) manually with the raw http module?

      Split both the registered route pattern and the incoming pathname into segments by '/', compare them positionally, treating any pattern segment starting with ':' as a wildcard that captures the corresponding incoming segment's value into a params object, and requiring equal segment length (or using a trailing wildcard) for a match.

      Follow-up: how would you handle multiple competing route patterns matching the same path (e.g. a static route vs a parameterized one)?
      What's the risk of using string .includes() or naive splitting on req.url for routing instead of the URL class?

      Query strings, encoded characters (%20, %2F), and trailing slashes can all cause naive string matching to behave incorrectly or inconsistently — e.g. '/bookmarks' matching '/bookmarks-archive' via a loose .includes() check, or failing to strip a query string before comparing the path. The URL class gives you a correctly parsed, decoded pathname and separate searchParams, removing an entire bug class.

      Follow-up: what base URL argument does the URL class need when parsing a relative req.url, and why?

      Advanced

      Design a minimal middleware system (array of functions with next()) on top of raw http.createServer, explaining exactly what it needs to replicate Express's core behavior.

      Maintain an ordered array of handler functions, each accepting (req, res, next). A dispatcher function tracks an index, invokes handlers[index](req, res, () => dispatch(index+1)) — calling next() advances to the next middleware, and any middleware can instead call res.end() to terminate the chain early without calling next(). Error handling requires a convention: next(err) with an argument skips directly to a special error-handling middleware (checked via function arity or an explicit separate error-middleware array), mirroring Express's actual (req, res, next) vs (err, req, res, next) signature-based dispatch.

      Follow-up: how would you prevent a middleware that forgets to call next() (and doesn't end the response either) from hanging the request forever?
      Explain exactly why a single slow raw-http request handler (synchronous CPU-bound work) blocks all other concurrent connections on that process, tying this back to the event loop.

      Node's http server accepts new TCP connections via OS-native async I/O, but the JS callback that processes each request's data still executes on the single JS thread; if that callback does synchronous CPU-bound work (a big JSON.parse, a crypto hash, a tight loop), the thread is occupied for that entire duration, and no other request's callback — regardless of which connection it's on — can run until it returns, since there is exactly one JS call stack for the whole process.

      Follow-up: does this change at all if the server is handling requests via a cluster of multiple Node processes?
      How would you add graceful shutdown (SIGTERM handling, draining in-flight requests, closing the server cleanly) to a raw http server for a production deployment?

      On SIGTERM, call server.close() (which stops accepting new connections but lets in-flight requests finish), track open connections/sockets to actively close idle keep-alive ones that aren't mid-request (server.close() alone won't forcibly close persistent idle connections), and set a hard deadline timer (e.g. 10-30s) after which you forcibly destroy remaining sockets and exit, so a stuck request can't block deployment forever. Signal readiness-probe failure (if using Kubernetes) immediately on SIGTERM receipt, before draining starts, so the load balancer stops routing new traffic to this instance during the drain window.

      Follow-up: why is it important to fail the readiness probe before, not after, you stop accepting connections?
      What's the difference in how raw http and Express actually handle an uncaught synchronous throw inside a request handler, and why does it matter for process stability?

      In a raw http.createServer callback, an uncaught synchronous throw propagates as an uncaught exception at the process level (since there's no framework wrapping your callback in a try/catch) — by default this crashes the entire process unless you have a global uncaughtException handler, taking down every other in-flight connection too. Express wraps each route handler's synchronous execution so a thrown error is caught and routed to its error-handling middleware instead of crashing the process — but critically, this safety net does NOT extend to errors thrown inside an async callback or a rejected Promise unless you explicitly call next(err) or (in modern Express/async wrappers) rely on async-error-catching middleware, which is a frequent source of "but Express catches errors for me" false confidence.

      Follow-up: in modern Express (4.x with async handlers, or 5.x), what specifically changed about async rejection handling, and what's still the developer's responsibility?
      Why does streaming a large response body with res.write() in a loop risk unbounded memory growth if you ignore backpressure, and how do you fix it?

      res.write() returns false when the underlying socket's internal buffer is full (the client/network can't drain data as fast as you're writing it); if you ignore this return value and keep calling write() anyway (e.g. in a tight loop reading from a fast source and writing to a slow client), data queues up in memory inside Node's internal buffers unboundedly. The fix is respecting backpressure: pause writing when write() returns false, and resume only after the 'drain' event fires — or, far more simply, use stream.pipe() (source.pipe(res)) which implements this backpressure handling correctly for you.

      Follow-up: why is piping a Readable stream directly to res generally preferred over manually reading-then-writing chunks yourself?

      Practice Assignments

      Build a 3-route raw http server

      Using only node:http, build a server with GET /, GET /time (returns current server time as JSON), and a 404 fallback for anything else. No framework, no npm dependencies.

      • Must set correct Content-Type headers on every response.
      • Must return proper JSON for /time and a clear 404 JSON body for unmatched routes.

      Acceptance criteria: curl against all 3 cases returns correct status codes and bodies.

      Use req.method and new URL(req.url, 'http://localhost').pathname to branch; always call res.end() exactly once per branch.

      Bonus: Add a query-string-driven route, e.g. GET /greet?name=X returning a personalized greeting.

      Raw-http bookmarks CRUD API (part 1 of the capstone)

Include manual body parsing, manual route matching (including the :id parameter), and a centralized try/catch per request with a consistent JSON error shape.

      • All 5 capstone endpoints working against bookmarks.json.

      Build a tiny middleware-and-router library on raw http

      Build a minimal library (your own, not a dependency) on top of node:http that provides: an Express-like `app.get/post/put/delete(path, handler)` API with `:param` support, a middleware chain with `next()`, centralized error handling via `next(err)`, and automatic JSON body parsing middleware with a size limit. Then rebuild the bookmarks API using your own library instead of raw http directly.

      Hints

      Store routes as an array of {method, pathPattern, paramNames, handler} and match by converting the pattern to a regex with named capture groups, or by segment-splitting and comparing positionally.

      Bonus: Add support for middleware scoped to a path prefix (like Express's app.use('/api', subRouter)).

      Quick Revision Cheat Sheet

      • req is a Readable stream (IncomingMessage); res is a Writable stream (ServerResponse).
      • req.url includes the query string unparsed — always parse with the URL class, compare against .pathname.
      • Request body arrives as 'data' events (Buffer chunks) + a final 'end' event — no built-in parsed-body accessor.
      • res.end() must be called exactly once per request; calling it twice throws.
      • Check res.headersSent before sending an error response from an async path — you may already be too late.
      • Headers must be fully sent before any body bytes (HTTP/1.1 framing) — late setHeader throws ERR_HTTP_HEADERS_SENT.
      • No built-in routing or route params (:id) — you implement path matching/param extraction yourself without a framework.
      • Always bound manual body-parsing size to avoid a memory-exhaustion DoS vector.
      • A hung handler (never calling res.end()) ties up a keep-alive connection indefinitely.
      • res.write() respects backpressure via its boolean return value and the 'drain' event — prefer stream.pipe() over manual write loops for large payloads.
