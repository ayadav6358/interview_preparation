    Node.js Fundamentals

    📚 6 chapters⏱ ~11–13 hrs total

    A fast, crisp refresher of the fundamentals layer — runtime, modules, npm, core modules, raw HTTP servers, Express, and REST basics — stated precisely and completely the way a senior developer should be able to explain it in an interview. This is the on-ramp before Node.js Advanced (event loop internals, streams, worker threads, memory/GC, production APIs), not a beginner tutorial. If you've been writing Node code for years but have never had to articulate "what exactly is CommonJS vs ESM" or "why does npm ci exist" out loud in an interview, this is the topic that closes that gap.

    Learning Outcomes

    • Explain precisely what the Node.js runtime is (V8 + libuv + Node APIs) and how CommonJS and ESM module resolution actually differ, not just "use import instead of require."
    • Read and reason about package.json, semantic versioning ranges, the lockfile, and the difference between npm install and npm ci in CI/CD.
    • Use fs, path, and os correctly across sync/async/promise-based APIs, and know when each is appropriate.
    • Build a working HTTP server from the raw http module — routing, parsing, and responding — before reaching for a framework.
    • Build the same API in Express, with correct middleware ordering, and explain why each layer exists.
    • Design a REST API surface (resource naming, HTTP method mapping, status codes, error shape) that a senior reviewer would approve without comments.

    🏆 Capstone Project: Build a "Bookmarks API" Twice — Raw Node, Then Express

    Problem statement: Build a small CRUD API for managing bookmarks (url, title, tags, createdAt) with file-based JSON storage. Build it twice: first with nothing but the raw http module and the fs module (to prove you understand what a framework is doing for you), then rebuild the exact same API surface in Express. Both versions must be functionally identical from the client's point of view.

    Required features (both versions):

    • GET /bookmarks — list all, with optional ?tag= query filter.
    • GET /bookmarks/:id — fetch one, 404 if missing.
    • POST /bookmarks — create, validate body (url and title required), 201 with Location-style response.
    • PUT /bookmarks/:id — full replace, 404 if missing, validation errors return 400.
    • DELETE /bookmarks/:id — remove, 204 on success.
    • Storage: a single bookmarks.json file read/written via the fs module — no database.
    • Middleware/equivalent: request logging (method, path, status, duration) and centralized error handling that always returns a consistent JSON error shape.
    • npm scripts: start, dev (with --watch), and test (even a minimal smoke test).

    Milestones:

    1. Design the resource model and REST contract on paper first (endpoints, status codes, error shape) — see Chapter 6.
    2. Build the raw http version: manual routing (method + URL parsing), manual body parsing/buffering, manual JSON read/write to disk.
    3. Add request logging and centralized error handling to the raw version without a framework (you'll feel exactly why Express exists after this).
    4. Rebuild in Express: convert manual routing to app.get/post/put/delete, convert body parsing to express.json(), convert logging/error handling to proper middleware with correct ordering.
    5. Add npm scripts and a package.json with sane semver ranges for your two dependencies (express, maybe nodemon).
    6. Write a short README comparing the two implementations: what Express saved you from writing by hand, line for line.

    Evaluation checklist:

    • ☐ Both versions pass the identical set of manual curl/Postman requests with identical status codes and bodies.
    • ☐ Can explain exactly what express.json(), a router, and next(err) are doing under the hood because you wrote the raw equivalent by hand.
    • ☐ Concurrent requests don't corrupt bookmarks.json (discuss the race condition even if you don't fully solve it).
    • ☐ Every error path (bad JSON body, missing fields, not-found id) returns the same consistent error JSON shape.
    • ☐ package.json scripts and dependency versions are deliberate choices, not defaults left untouched.
