    Core Modules: fs, path, os

    ⏱ 2 hrs📍 Chapter 3 of 6

    One-line summary: fs gives you three parallel APIs for the same operations (sync, callback-based async, and promise-based) with real performance and correctness implications for which one you reach for; path and os exist specifically so your code doesn't silently break the moment it runs on a different OS than the one it was written on.

    On this page

      Why It Matters for a Senior Developer

      Every Node service that touches the filesystem — config loading, log writing, temp file handling, the capstone's JSON-file storage — routes through this module. The senior-level distinction isn't "do you know fs.readFile exists," it's: do you know exactly when a synchronous fs call is acceptable (startup/CLI scripts) versus a request-path landmine (blocks the entire event loop for every concurrent request, see Event Loop Internals), and do you reflexively build file paths with path.join instead of string concatenation, which breaks the moment someone runs your code on Windows or inside certain container base images.

      Why

      String-concatenated paths (dir + '/' + file) are a classic bug that passes code review and every test on a developer's Mac/Linux machine, then breaks for a Windows contributor or a CI runner with different path-separator conventions. path.join/path.resolve cost nothing and eliminate the entire bug class.

      Prerequisites

      Comfortable with callbacks, Promises, and async/await. Related in this topic: Node.js Basics: Runtime & Modules, HTTP Module & Basic Servers (the capstone's file-based storage uses exactly this chapter's APIs). Related elsewhere: Event Loop Internals & libuv for precisely why sync fs calls on the request path are dangerous, and Streams, Buffers & Backpressure for handling files too large to read fully into memory.

      Core Concepts

      fs's three parallel APIs: sync, callback, and promises

      Every common fs operation exists in three forms. Sync (fs.readFileSync): blocks the JS thread until the OS call completes — simple to reason about, but on a server handling concurrent requests it stalls every in-flight request for the duration. Callback-based async (fs.readFile(path, cb)): the original Node pattern, non-blocking, offloaded to libuv's thread pool (file I/O has no universal OS-native async primitive, so Node uses worker threads under the hood even though it "looks" async from your code's perspective). Promise-based (fs.promises.readFile, or equivalently importing from node:fs/promises): the modern default for anything you'll await — same underlying thread-pool mechanism as the callback API, just wrapped in a Promise-returning interface that composes with async/await instead of nested callbacks.

      Rule of thumb for 2025-26 code: use fs/promises for all request-path and general application code; reserve the sync API for startup-time config loading, one-off CLI scripts, or places where you've deliberately decided blocking briefly is fine (e.g., reading a small config file once before the server starts accepting connections at all).

      path: OS-aware path manipulation

      path.join(...) concatenates segments using the current OS's correct separator and normalizes the result (collapsing ../. segments). path.resolve(...) does the same but always returns an absolute path, resolving from the current working directory if no absolute segment is given — the key practical difference: join is purely textual, resolve mimics how a shell resolves a sequence of cd commands. path.basename, path.dirname, and path.extname pull apart a path's filename, directory, and extension respectively. path.sep is the OS-specific separator (/ on POSIX, \ on Windows) — you should essentially never hardcode a separator character yourself.

      os: querying the runtime environment

      os.platform() returns the OS identifier ('linux', 'darwin', 'win32'); os.cpus() returns per-core info (used for sizing worker pools/cluster fork counts, see Worker Threads & Clustering); os.totalmem()/os.freemem() report system memory; os.tmpdir() returns the platform-correct temp directory (never hardcode /tmp — it doesn't exist on Windows); os.homedir() returns the current user's home directory cross-platform.

      How It Works Under the Hood

      Async fs operations are backed by libuv's thread pool (default size 4, see Event Loop Internals) because, unlike network sockets, most operating systems have no universal native async file I/O primitive Node can rely on uniformly — so Node dispatches the actual read/write syscall to a worker thread and the JS thread is notified via the event loop when it completes. This is why a burst of concurrent fs.promises.readFile calls beyond the thread pool size queues the extras behind the first four, even though each individual call is "non-blocking" from the JS thread's perspective.

      File descriptors are a finite OS resource. Every fs.open (and internally, every read/write-file call that doesn't explicitly close its handle) consumes one until closed; forgetting to close handles in a long-running process is a real, slow-burning resource leak that eventually throws EMFILE: too many open files. The promise and callback convenience methods (readFile/writeFile) open and close the descriptor internally per call, so the leak risk is specifically around manual fs.open/stream usage, not the convenience wrappers.

      Code Examples

      import { readFile, writeFile, mkdir, readdir, stat } from 'node:fs/promises';
import { existsSync } from 'node:fs';
import path from 'node:path';
import os from 'node:os';

// ---- BAD: sync fs call on a request handler path ----
// app.get('/bookmarks', (req, res) => {
//   const data = fs.readFileSync('./bookmarks.json', 'utf-8'); // blocks ALL concurrent requests
//   res.json(JSON.parse(data));
// });

// ---- GOOD: promise-based, non-blocking ----
async function loadBookmarks(filePath) {
  try {
    const raw = await readFile(filePath, 'utf-8');
    return JSON.parse(raw);
  } catch (err) {
    if (err.code === 'ENOENT') return [];      // file doesn't exist yet — treat as empty
    throw err;                                  // anything else is a real error, rethrow
  }
}

async function saveBookmarks(filePath, bookmarks) {
  const dir = path.dirname(filePath);
  await mkdir(dir, { recursive: true });        // ensure directory exists, no error if it already does
  await writeFile(filePath, JSON.stringify(bookmarks, null, 2), 'utf-8');
}

// ---- path: always build paths this way, never string concatenation ----
const dataDir = path.join(process.cwd(), 'data');          // textual join, OS-correct separator
const bookmarksFile = path.resolve(dataDir, 'bookmarks.json'); // absolute, resolved from CWD
console.log(path.basename(bookmarksFile));   // 'bookmarks.json'
console.log(path.extname(bookmarksFile));    // '.json'
console.log(path.dirname(bookmarksFile));    // the data dir, absolute

// ---- os: environment-aware config ----
const workerCount = Math.max(1, os.cpus().length - 1);  // leave one core for the main process
const tmpUploadDir = path.join(os.tmpdir(), 'myapp-uploads'); // cross-platform temp dir, never hardcode /tmp

// ---- reading a directory ----
async function listJsonFiles(dir) {
  const entries = await readdir(dir, { withFileTypes: true });
  return entries
    .filter(e => e.isFile() && path.extname(e.name) === '.json')
    .map(e => path.join(dir, e.name));
}

// ---- sync is fine here: one-time startup config, before server starts accepting traffic ----
const configExists = existsSync('./config.json');

      Real-World Production Scenario at Scale

      At scale

      A small internal tool (the kind that starts as "just a quick JSON file, we'll add a real DB later") used fs.readFileSync/writeFileSync on every API request to read and rewrite a shared JSON data file. It worked fine with a handful of users. When a company-wide rollout brought concurrent usage from ~5 to ~200 users, p99 latency on every endpoint — not just the file-backed ones — spiked badly, because each sync file operation blocked the entire single-threaded process for the full read/write duration, serializing all concurrent requests behind each other regardless of which endpoint they hit. The fix wasn't "add a database" immediately (that was the longer-term plan) — it was a same-day change to fs/promises plus an in-memory write queue (serializing only the writes to that one file to avoid corrupting it under concurrent writes, see Chapter 6's race-condition discussion), which bought enough headroom to ship the real datastore migration without an outage in between.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Using any *Sync fs function inside a request handler "because it was simpler to write." It blocks the entire process for every concurrent request for the duration of that one disk operation — acceptable at startup, never on a hot request path.

      Gotcha

      Building file paths with string concatenation (dir + '/' + filename) instead of path.join. Breaks on Windows, breaks when dir already has a trailing slash (double slash), and misses path normalization — always use path.join/path.resolve.

      • Check err.code === 'ENOENT' specifically rather than assuming any readFile failure means "file doesn't exist" — permission errors (EACCES), directory-vs-file mismatches (EISDIR), and others have distinct codes worth handling differently.
      • Prefer { recursive: true } on mkdir to avoid manually checking existence first (and the TOCTOU race that check introduces).
      • Don't forget that concurrent writes to the same file from multiple requests can interleave/corrupt it — plain fs has no file-level locking; serialize writes yourself (an in-process queue) or use a real database.
      • Never hardcode /tmp or C:\Users\... — use os.tmpdir()/os.homedir().

      Interview Questions

      Basic

      Name the three forms of most fs operations.

      Synchronous (blocking, e.g. readFileSync), callback-based asynchronous (e.g. readFile(path, cb)), and promise-based (fs/promises, usable with async/await).

      Follow-up: which underlying mechanism do the async and promise versions share?
      Why is path.join preferred over string concatenation for building file paths?

      It uses the correct OS-specific path separator and normalizes the result (collapsing redundant slashes and .. segments), so code behaves correctly across operating systems instead of assuming a POSIX-style separator.

      Follow-up: what's the difference between path.join and path.resolve?
      What does os.tmpdir() give you, and why not just hardcode /tmp?

      The platform-correct temporary directory path — /tmp on most POSIX systems, but a different path on Windows (no /tmp exists there), so hardcoding breaks cross-platform code.

      Follow-up: name one other os module function useful for sizing a worker pool.
      What error code do you check to detect "file does not exist" from an fs read call?

      err.code === 'ENOENT' (Error NO ENTry).

      Follow-up: name one other common fs error code and what it means.
      What does { recursive: true } do on fs.mkdir?

      Creates all missing parent directories in the path and does not throw if the target directory already exists, avoiding a manual existence check beforehand.

      Follow-up: what race condition does this avoid compared to "check exists, then mkdir if not"?
      When is using a synchronous fs call acceptable?

      At process startup before the server begins accepting requests (e.g. loading a config file once), or in one-off CLI scripts with no concurrent request path to block.

      Follow-up: why specifically is this safe when it's unsafe on a request path?

      Medium

      Why does async fs.readFile still use a thread pool internally even though it "feels" async from your code?

      Most operating systems lack a universal native async file I/O primitive comparable to epoll/kqueue for sockets, so Node dispatches the actual read/write syscall to one of libuv's worker pool threads; the JS thread is freed immediately and notified via the event loop once that worker thread's syscall completes. It's "non-blocking from the JS thread's perspective" via real OS threads underneath, not via a kernel-native async file API.

      Follow-up: what happens to the 5th concurrent fs.readFile call if the thread pool size is 4 and all 4 are busy?
      What's a file descriptor leak, and how do convenience methods like readFile/writeFile avoid it?

      Every open file consumes a finite OS file descriptor; if you manually fs.open and never fs.close, descriptors accumulate until the process hits EMFILE ("too many open files"). readFile/writeFile open and close the descriptor internally per call, so the leak risk is specific to manual fs.open/stream usage, not these convenience wrappers.

      Follow-up: what's a realistic scenario where even using readFile/writeFile you could still leak resources?
      How would you safely handle concurrent writes to the same JSON file from multiple simultaneous requests?

      Plain fs has no file-level locking, so interleaved writes can corrupt the file (partial overwrite). A practical in-process fix is an async write queue (serialize all writes to that file through a single in-memory promise chain/mutex) so only one write is in flight at a time; a cross-process fix requires actual file locking (proper-lockfile style libraries) or, better, migrating to a real database with transactional guarantees.

      Follow-up: does an in-process write queue protect you if you run multiple Node processes (cluster mode) against the same file?
      Explain the practical difference between path.join('/a', '../b') and path.resolve('/a', '../b').

      Both normalize the .. segment the same way here since an absolute segment is present, resulting in '/b' for both — the real difference shows when no absolute segment is given: path.join('a', '../b') returns the textual 'b' relative path, while path.resolve('a', '../b') returns an absolute path resolved against process.cwd(), e.g. '/current/dir/b'.

      Follow-up: when would you deliberately want join's relative-path behavior instead of resolve's absolute behavior?
      Why might reading a very large file fully with fs.readFile be a bad idea even using the async/promise API?

      readFile loads the entire file into memory as one Buffer/string before resolving — for very large files this can spike memory usage significantly and delay the first byte of processing until the whole file is read. A stream-based approach (fs.createReadStream) processes data incrementally with bounded memory and lets you start processing before the full file arrives.

      Follow-up: at roughly what file size would you start reaching for streams instead of readFile, and why isn't there a hard universal number?
      What's the risk of using fs.existsSync followed by a separate fs.readFile/writeFile call, and what's the better pattern?

      This is a TOCTOU (time-of-check to time-of-use) race: the file's existence can change between the existsSync check and the subsequent operation (another process/request deletes or creates it in between), making the check meaningless under concurrency. Better: attempt the operation directly and handle the specific error code (ENOENT) in the catch block, which is also just fewer syscalls.

      Follow-up: is this race condition realistic in a single-process Node app, or only relevant with multiple processes/external actors touching the file?

      Advanced

      Design a file-based storage layer (like the capstone's bookmarks.json) that's safe under concurrent writes within a single Node process, and explain its limits.

      Maintain an in-memory queue/mutex: every write operation is appended as a function to a promise chain that resolves sequentially (e.g., `let queue = Promise.resolve(); function enqueueWrite(fn) { queue = queue.then(fn, fn); return queue; }`), guaranteeing writes to the file never interleave within that process. Reads can either go through the same queue (slower, always consistent) or read optimistically with the understanding they might occasionally read slightly stale data mid-write. Its fundamental limit: this only serializes writes within one process — a second Node process (another server instance, or cluster worker) touching the same file has its own independent queue and can still race with the first, so this pattern is only correct for a strictly single-process deployment.

      Follow-up: how would you extend this to be safe across multiple processes/instances without migrating to a real database?
      Explain exactly what happens at the libuv/OS level when 10 concurrent fs.promises.readFile calls are issued against a thread pool of size 4.

      libuv dispatches the first 4 read operations to its 4 worker threads immediately; the remaining 6 are queued internally within libuv, waiting for a thread to free up. As each of the first 4 completes, its result is queued back to the JS thread via the event loop's poll phase, the worker thread becomes free, and libuv immediately assigns it the next queued request — so the 10 requests complete in roughly 3 waves of up to 4 concurrent operations rather than all in parallel, meaning wall-clock completion time for the batch scales with (10/4) rounded up, times the per-read duration, not with pure parallelism.

      Follow-up: would raising UV_THREADPOOL_SIZE to 10 here definitely improve throughput? What else could bottleneck it (e.g., disk I/O contention itself)?
      How would you benchmark and decide the threshold file size at which you should switch from fs.readFile to streaming for a specific production workload?

      Benchmark actual memory and latency-to-first-byte under realistic concurrency for representative file sizes in your workload, tracking peak RSS and event-loop lag (monitorEventLoopDelay) during the read, not just wall-clock read time. The threshold isn't a fixed universal number — it depends on available container memory, expected concurrent request volume at that size, and whether downstream processing can genuinely benefit from incremental/streamed data (e.g., piping straight to an HTTP response) versus needing the whole buffer anyway (e.g., JSON.parse requires the complete string regardless, so streaming only helps the I/O phase, not the parse phase).

      Follow-up: for a workload that must JSON.parse the full file content regardless, what does streaming actually buy you versus readFile?
      Your service migrated from JSON-file storage to a real database, but a legacy batch job still reads the old file format for backward compatibility. How would you structure this transition period's code to minimize risk?

      Keep the file-read path completely isolated behind the same repository/interface abstraction the database-backed path uses, so callers never know which backend served a given read — this lets you dual-write during a transition window (write to both store and file) and run a reconciliation job comparing them before fully cutting over reads. Treat the legacy file as read-only once the cutover begins (stop writing to it from the app, let the batch job finish consuming it on its own schedule), and set a hard decommission date for removing file-read code entirely rather than letting "backward compatibility" become permanent technical debt.

      Follow-up: what's a concrete way to prove the database and file representations actually agree before fully decommissioning the file path?
      Why can EMFILE errors appear seemingly randomly in production under load even when your code correctly closes every file handle it opens?

      EMFILE is governed by a process-wide (and often OS-wide) file descriptor limit (ulimit -n on Linux) shared across every open file, socket, and pipe in the process — not just ones your fs code opens. A connection-handling bug elsewhere (leaked sockets, unclosed HTTP keep-alive connections, an accumulating log stream) can exhaust the same descriptor budget your fs calls draw from, making fs operations fail with EMFILE even though your fs-specific code is flawless. Diagnosing this requires looking at total open descriptors for the process (lsof -p <pid> on Linux), not just auditing fs.open call sites.

      Follow-up: what's a production mitigation for this beyond "find and fix the leak" — is there a safe stopgap?

      Practice Assignments

      Beginner (30-60 min)

      Build a small CLI file-stats tool

      Write a Node script (using fs/promises, path, and os) that takes a directory path as a CLI argument, lists all files in it, and prints each file's name, size, and extension, plus a summary line using os.platform() and os.totalmem().

      • Must use path.join/path.extname, not string concatenation.
      • Must handle a non-existent directory gracefully (clear error message, not a stack trace dump).

      Acceptance criteria: Runs correctly against a real directory and prints accurate per-file stats plus the OS summary line.

      Hints

      Use fs.promises.readdir with { withFileTypes: true } and fs.promises.stat per file for size.

      Bonus: Add a recursive mode that walks subdirectories too.

      Intermediate (2-4 hrs)

      Implement a safe-write JSON store module

      Build a small module exposing `read()` and `write(data)` functions backed by a JSON file, where write() is safe against concurrent calls within the same process (no interleaved/corrupted writes) using an in-memory write queue. Prove correctness by firing 50 concurrent write() calls (each appending a unique item) and verifying the final file contains exactly 50 well-formed, non-corrupted items.

      • Must demonstrate the bug first without the queue (corrupted/lost writes under concurrency).
      • Must then show the queued version passing the same concurrency test cleanly.

      Acceptance criteria: The 50-concurrent-write test passes reliably across multiple runs with the queue in place.

      Hints

      Chain each write operation onto a single module-level `let queue = Promise.resolve()` variable, reassigning it to `queue.then(doWrite)` for each new write.

      Bonus: Add a read-your-writes guarantee: a write() call's returned promise only resolves after that specific write has been durably flushed to disk.

      Advanced (1-2 days)

      Benchmark sync vs async fs under concurrent load

      Build two versions of a tiny Express (or raw http) endpoint that reads a ~5MB JSON file on every request: one using fs.readFileSync, one using fs/promises. Load test both with a tool like autocannon at a realistic concurrency (e.g. 50 connections) and measure p50/p99 latency and throughput for each. Also add a second, unrelated lightweight endpoint (e.g. a simple health check) and show how its latency degrades under load from the sync version but not the async version.

      • Must produce real before/after numbers from an actual load test, not theoretical reasoning alone.
      • Must demonstrate the "unrelated endpoint" latency contagion from the sync version specifically.
      Hints

      Use autocannon with two separate terminal windows — one hammering the file-read endpoint, one hammering the health-check endpoint — and compare health-check latency between the sync and async server runs.

      Bonus: Add a worker_thread-backed version of the file read and show it also protects the unrelated endpoint's latency.

      Quick Revision Cheat Sheet

      • fs has 3 parallel APIs: sync (blocking), callback async, promise-based (fs/promises) — default to fs/promises for application code.
      • Async/promise fs calls still run on libuv's thread pool (default size 4) — not a kernel-native async file API.
      • Never use *Sync fs calls on a request path — only at startup or in CLI scripts.
      • Always build paths with path.join/path.resolve, never string concatenation — cross-platform correctness, free.
      • path.join: textual concat + normalize. path.resolve: always absolute, resolved from CWD like cd commands.
      • Check err.code (ENOENT, EACCES, EISDIR, EMFILE) rather than assuming every fs error means "missing file."
      • Use { recursive: true } on mkdir to avoid a TOCTOU existence-check race.
      • os.tmpdir()/os.homedir() instead of hardcoded /tmp or user paths — cross-platform correctness.
      • Plain fs has no file-level locking — concurrent writes to the same file need your own queue/mutex or a real database.
      • EMFILE errors draw from a process-wide fd limit shared with sockets/pipes — not only fs.open calls.
