    REST API Fundamentals

    ⏱ 1.5–2 hrs📍 Chapter 6 of 6

    One-line summary: REST is a small set of precise conventions — resources as nouns, HTTP methods as the only verbs, status codes that mean something specific, consistent error shapes — and a senior reviewer judges your API by how consistently you apply them, not by whether you can recite the Fielding dissertation's six constraints.

    On this page

      Why It Matters for a Senior Developer

      You've built dozens of REST endpoints. The interview-relevant skill isn't "can you build a CRUD route," it's: can you design a resource model and status-code contract that a frontend team can integrate against without asking clarifying questions, and can you defend specific choices (why 422 vs 400, why PUT vs PATCH, why nested vs flat resource URLs) under pushback. This is also the chapter that connects most directly to System Design: API Design — the fundamentals here are exactly what that topic assumes you already have internalized before adding versioning, pagination, and idempotency concerns at scale.

      Why

      An inconsistent API (sometimes 200 with an error field in the body, sometimes a proper 4xx; sometimes /getUser, sometimes /users/:id) forces every consumer to write defensive, inconsistent client code and erodes trust in the API's contract — this is a recurring, concrete source of integration bugs between frontend and backend teams, not a style nitpick.

      Prerequisites

      Comfortable building routes in Express (Chapter 5) or raw http (Chapter 4). Related elsewhere: HTTP & Networking Basics for the protocol-level status code and method semantics this chapter applies, and System Design: API Design for the advanced follow-on (versioning, pagination, idempotency, GraphQL/gRPC comparison) once these fundamentals are solid.

      Core Concepts

      Resource naming: nouns, not verbs

      A REST resource URL names a thing, plural, not an action: /bookmarks not /getBookmarks; /bookmarks/:id not /deleteBookmark?id=5. The HTTP method is the verb — GET /bookmarks/:id fetches, DELETE /bookmarks/:id deletes; putting a verb in the path duplicates and often contradicts the method. Nest resources only when there's a genuine ownership/containment relationship (/users/:userId/bookmarks for "this user's bookmarks") — don't nest arbitrarily deep (/users/:id/bookmarks/:id/tags/:id/... becomes unwieldy; consider a flatter resource with a filter query param instead past 2 levels).

      HTTP methods mapped to CRUD, precisely

      GET — read, must be safe (no side effects) and idempotent (calling it N times has the same effect as once). POST — create a new resource (or trigger a non-idempotent action); not idempotent by default — calling it twice creates two resources unless you add explicit idempotency handling. PUT — full replace of a resource at a known URL; idempotent — sending the same PUT twice leaves the resource in the same end state. PATCH — partial update; not guaranteed idempotent in general, though many practical implementations are. DELETE — remove a resource; idempotent in the sense that deleting an already-deleted resource should still result in "it's gone" (commonly implemented as returning 204 either way, or 404 on the second call — both are defensible, pick one and document it).

      Status codes that actually mean something

      Group by first digit, then pick precisely within the group: 2xx — 200 OK (generic success with a body), 201 Created (POST succeeded, include the created resource and ideally a Location header), 204 No Content (success, deliberately no body — typical for DELETE). 4xx (client's fault) — 400 Bad Request (malformed request, e.g. invalid JSON), 401 Unauthorized (missing/invalid authentication — you don't know who this is), 403 Forbidden (authenticated, but not allowed to do this), 404 Not Found (resource doesn't exist), 409 Conflict (request conflicts with current state, e.g. a duplicate unique field), 422 Unprocessable Entity (well-formed request, but semantically invalid — e.g. valid JSON with a field failing business validation; many APIs use 400 for this too, pick one convention and be consistent). 5xx (server's fault) — 500 Internal Server Error (generic, unexpected failure), 503 Service Unavailable (temporarily down, typically with a Retry-After hint).

      How It Works Under the Hood

      "RESTful" in the strict, original sense (Roy Fielding's dissertation) includes constraints most "REST APIs" in production don't fully satisfy — notably HATEOAS (responses include hypermedia links describing available next actions) is almost universally skipped in practice. What the industry actually means by "REST API" in 2025-26 is closer to "a resource-oriented HTTP API using methods and status codes conventionally" — understanding this gap matters for an interview: a senior answer acknowledges the difference rather than conflating "RESTful" with "the thing everyone builds and calls REST."

      A consistent error shape is a contract just like your success response shape. A common, defensible convention: every error response is JSON with at minimum an error field (a human-readable message) and ideally a machine-readable code field (e.g. "VALIDATION_ERROR") and, for validation failures, a details array of field-level issues ([{ field: 'url', message: 'must be a valid URL' }]) — this lets a frontend render field-level errors without string-parsing a human message.

      Code Examples

      // ---- A consistent error shape used across every failure path ----
class ApiError extends Error {
  constructor(statusCode, code, message, details = null) {
    super(message);
    this.statusCode = statusCode;
    this.code = code;
    this.details = details;
  }
}

function sendError(res, err) {
  const statusCode = err.statusCode || 500;
  const body = {
    error: err.message || 'Internal Server Error',
    code: err.code || 'INTERNAL_ERROR',
  };
  if (err.details) body.details = err.details;
  res.status(statusCode).json(body);
}

// ---- Validation, returning field-level details ----
function validateBookmarkInput(body) {
  const details = [];
  if (!body?.url || typeof body.url !== 'string') {
    details.push({ field: 'url', message: 'url is required and must be a string' });
  } else {
    try { new URL(body.url); } catch { details.push({ field: 'url', message: 'url must be a valid URL' }); }
  }
  if (!body?.title || typeof body.title !== 'string') {
    details.push({ field: 'title', message: 'title is required and must be a string' });
  }
  if (details.length) throw new ApiError(422, 'VALIDATION_ERROR', 'Invalid bookmark input', details);
}

// ---- Resource naming: nouns + methods, not verbs in the path ----
// BAD:
// app.post('/createBookmark', handler);
// app.get('/getBookmarkById', handler);
// app.post('/deleteBookmark', handler);   // using POST to delete — contradicts HTTP semantics

// GOOD:
app.get('/bookmarks', listBookmarks);               // read collection
app.get('/bookmarks/:id', getBookmark);             // read one
app.post('/bookmarks', createBookmark);             // create — 201 on success
app.put('/bookmarks/:id', replaceBookmark);         // full replace — idempotent
app.patch('/bookmarks/:id', updateBookmarkFields);  // partial update
app.delete('/bookmarks/:id', deleteBookmark);       // delete — 204 on success

async function createBookmark(req, res, next) {
  try {
    validateBookmarkInput(req.body);
    const item = await bookmarksStore.create(req.body);
    res.status(201).location(`/bookmarks/${item.id}`).json(item);
  } catch (err) {
    next(err);  // centralized error middleware (Chapter 5) calls sendError
  }
}

async function getBookmark(req, res, next) {
  const item = await bookmarksStore.findById(req.params.id);
  if (!item) return next(new ApiError(404, 'NOT_FOUND', `Bookmark ${req.params.id} not found`));
  res.json(item);
}

async function deleteBookmark(req, res, next) {
  await bookmarksStore.delete(req.params.id);  // idempotent by convention: always 204, even if already gone
  res.status(204).end();
}

// Centralized error middleware, registered last (Chapter 5)
app.use((err, req, res, next) => sendError(res, err));

      Real-World Production Scenario at Scale

      At scale

      A mobile team integrating against an internal API kept hitting confusing bugs: some endpoints returned 200 OK with { success: false, error: "..." } in the body on failure, while others correctly used 4xx status codes — because different endpoints had been written by different engineers over 18 months with no documented convention. The mobile app's generic HTTP client treated any 200 as success, silently swallowing real errors from the inconsistent endpoints, which surfaced as "the save button does nothing" bug reports that took hours to trace because logs showed a "successful" 200 response. The fix was a one-page internal API style guide (status codes mean what they say, every error is a real non-2xx status with the agreed `{error, code, details}` shape), enforced going forward via a shared Express error-middleware helper every new service imported, plus a backlog ticket to migrate the legacy inconsistent endpoints — turning "everyone remembers the convention" into "the shared code makes the convention the path of least resistance."

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Returning 200 OK with an error flag in the body instead of a real non-2xx status code. This breaks HTTP-level tooling (caching, monitoring, generic retry logic, API gateways) that correctly assumes 2xx means success, and forces every client to parse the body just to know if the call failed.

      Gotcha

      Putting verbs in resource URLs (/getUser, /createOrder) instead of letting the HTTP method be the verb. It's redundant at best (POST /createBookmark) and contradictory at worst (GET /deleteBookmark?id=5 — GET is supposed to be safe/side-effect-free).

      • Pick one convention for "validation failure" (400 or 422) and apply it consistently across every endpoint — the specific choice matters less than the consistency.
      • Never leak a stack trace or internal error message to the client in a 5xx response — log it server-side, return a generic message client-side.
      • Don't conflate 401 (who are you?) and 403 (I know who you are, but no) — they communicate genuinely different situations to the client.
      • Use PUT only when the client sends the resource's complete representation; if they send partial fields, that's PATCH semantics even if you implement it loosely.

      Interview Questions

      Basic

      Why should resource URLs use nouns rather than verbs?

      Because the HTTP method already is the verb (GET/POST/PUT/PATCH/DELETE) — putting a verb in the path duplicates or contradicts that, e.g. GET /deleteUser directly conflicts with GET's "safe, no side effects" expectation.

      Follow-up: give an example of a bad URL and its corrected REST equivalent.
      What's the difference between 401 and 403?

      401 Unauthorized means the server doesn't know who you are (missing/invalid authentication); 403 Forbidden means it does know who you are, but you're not allowed to perform this action.

      Follow-up: which one should a login endpoint return for wrong credentials?
      What status code should a successful POST that creates a resource return?

      201 Created, typically with the created resource in the response body and ideally a Location header pointing to its new URL.

      Follow-up: what status code is conventional for a successful DELETE?
      What does "idempotent" mean for an HTTP method, and which methods are idempotent?

      Idempotent means calling the operation multiple times has the same effect as calling it once. GET, PUT, and DELETE are idempotent by convention; POST and (generally) PATCH are not.

      Follow-up: why is POST not idempotent by default, with a concrete example?
      What's the difference between PUT and PATCH?

      PUT replaces the entire resource with the data provided (a full representation); PATCH applies a partial update, modifying only the fields included in the request.

      Follow-up: what would happen if you sent a partial object to a strictly-implemented PUT endpoint?
      Why is returning 200 OK with { success: false } in the body a bad practice?

      It breaks the meaning of HTTP status codes for any tooling or client code that correctly assumes 2xx means success (caching layers, monitoring, generic retry/circuit-breaker logic, API gateways), forcing every consumer to parse the body just to know if a call actually succeeded.

      Follow-up: what should this response use instead?

      Medium

      When would you choose 422 over 400 for a validation failure, and does the distinction actually matter?

      422 signals "the request was well-formed (valid JSON, correct types) but fails business/semantic validation" (e.g. a URL field that's a valid string but not a valid URL), while 400 is more general "malformed request" (e.g. invalid JSON syntax). The distinction is genuinely debated in the industry — many well-regarded APIs use 400 for both — so what matters most for an interview answer and for a real codebase is picking one convention deliberately and applying it consistently, not which specific code is "more correct."

      Follow-up: what would you put in your team's API style guide to settle this definitively?
      Design a consistent error response shape for an API and justify each field.

      At minimum: an `error` field (human-readable message, safe to show in a generic UI toast), a `code` field (a stable machine-readable identifier like VALIDATION_ERROR, so client code can branch on it without string-matching the message), and for validation failures a `details` array of {field, message} objects so a frontend can render per-field errors. The code field matters because human-readable messages can change wording without warning and shouldn't be used as a program's branching logic.

      Follow-up: should the error message field ever be localized/translated, and where should that happen?
      How would you decide when to nest a resource URL (/users/:userId/bookmarks) versus keep it flat (/bookmarks?userId=X)?

      Nest when there's a genuine ownership/containment relationship and the nested resource genuinely cannot exist independently of its parent in the domain model (a comment that only ever exists under a specific post). Prefer flat with a filter query param when the resource can be queried/accessed independently of any single parent, or when nesting would need to go more than 1-2 levels deep, since deeply nested URLs become unwieldy to construct and the "canonical" URL for a resource becomes ambiguous if it could be reached via multiple parent paths.

      Follow-up: should a nested resource's "GET one" endpoint also be reachable via a flat /resources/:id URL? Why might you want both?
      Is DELETE on an already-deleted resource idempotent? Walk through the nuance.

      Idempotency means repeated calls produce the same end state (the resource is gone), which is true whether you return 204 both times or 404 on the second call — the end state is identical either way. The nuance is purely about response consistency, not idempotency itself: returning 204 both times treats "already gone" as success (simpler for clients that retry blindly), while 404 on the second call is more informative but means a naive retry-on-error client might incorrectly treat a successful retry as a failure. Pick one and document it; both are defensible idempotent designs.

      Follow-up: which choice would you make for a payment-related DELETE endpoint specifically, and why?
      Why is "strict REST" (Fielding's full definition, including HATEOAS) rarely what people mean by "REST API" in practice?

      Fielding's dissertation defines REST via six architectural constraints, including hypermedia-driven navigation (HATEOAS) where responses include links describing available next actions/state transitions, letting clients navigate the API dynamically rather than hardcoding URL structures. Almost no production "REST API" implements this fully — most are better described as "resource-oriented HTTP APIs using conventional methods and status codes," a pragmatic subset the industry still calls REST.

      Follow-up: what's one practical benefit HATEOAS would actually provide if implemented, and why do most teams decide it's not worth the complexity?
      How should an API signal that a PATCH request partially succeeded (some fields updated, one failed validation)?

      Most defensible approach: treat the entire PATCH as a single atomic operation — validate all fields first, and if any fail, reject the whole request with 422/400 and field-level details, applying no changes at all. Avoid a "partial success" response (e.g. 207 Multi-Status, borrowed from WebDAV) for a single-resource PATCH — it's confusing for clients and rarely worth the complexity outside of true batch/bulk operation endpoints where multiple independent sub-resources are being modified in one call.

      Follow-up: when would 207 Multi-Status actually be the right tool, if ever, in a typical REST API?

      Advanced

      Design the full REST contract (endpoints, methods, status codes, error shape) for a "notes" API supporting soft-delete, and justify every status code choice.

      GET /notes (200, list), GET /notes/:id (200, or 404 if not found or soft-deleted — treat soft-deleted as "not found" to external consumers), POST /notes (201 + Location header), PUT /notes/:id (200 with updated resource, full replace, 404 if missing), PATCH /notes/:id (200, partial update), DELETE /notes/:id (this is the interesting one for soft-delete: return 204 to the client — the external contract shouldn't leak the soft-delete implementation detail; internally it's a flag flip not a row deletion), and optionally POST /notes/:id/restore (200) as an explicit un-delete action if the product needs it, modeled as its own resource-action rather than overloading PUT. Every error path returns the shared {error, code, details} shape from this chapter regardless of which endpoint.

      Follow-up: should a soft-deleted note be visible to a GET /notes list call for the owning user, with some kind of "deleted" flag, or fully invisible? What drives that product decision?
      How would you version a REST API (URL path /v2/, header-based, or content negotiation) and what are the real tradeoffs senior engineers weigh?

      URL path versioning (/v1/bookmarks, /v2/bookmarks) is the most explicit and cache-friendly (different URLs cache independently, easy to route at a load-balancer/gateway level, trivially visible in logs) but duplicates route definitions and can fragment documentation across versions. Header-based versioning (a custom Accept-Version header or content-type parameter) keeps URLs stable (better for REST's "resource has one canonical identity" principle, cleaner for hypermedia-style APIs) but is harder to test with a browser/curl casually, invisible in access logs without extra config, and less cache-friendly unless the cache key explicitly includes the header. Most teams pragmatically choose URL path versioning for its operational simplicity despite the theoretical purity argument against it — this is exactly the kind of "defend a specific choice" question senior interviews probe.

      Follow-up: how do you handle a breaking change to a single field deep in a large response payload without bumping the entire API's major version?
      A client team wants your DELETE endpoint to be "undo-able" for 30 seconds. How does this change your REST design, and does it compromise DELETE's idempotency semantics?

      Implement it as a soft-delete with a `deletedAt` timestamp set by DELETE (still returns 204, still idempotent — re-deleting an already-soft-deleted resource is a no-op with the same end state), and a separate explicit POST /bookmarks/:id/restore endpoint that only succeeds within the 30-second window (409 Conflict or 404 after expiry, your call, documented). This doesn't compromise DELETE's idempotency at all — idempotency is about repeated identical requests producing the same end state, not about whether that state is "truly" permanent; a background job that hard-deletes after 30 seconds is an internal implementation detail invisible to the DELETE contract itself.

      Follow-up: what HTTP status code should the restore endpoint return if called after the 30-second window has already expired, and why?
      Explain the relationship (and the real tradeoffs) between choosing REST, GraphQL, and gRPC for a given API surface, beyond "REST is simple, GraphQL is flexible."

      REST's resource-oriented, cacheable-by-URL model works well when access patterns map cleanly to CRUD-shaped resources and broad client compatibility (any HTTP client, browser-native fetch, simple caching at CDN/gateway level) matters — its weakness is over-fetching/under-fetching when a client needs a specific shape spanning multiple resources, often solved with ad hoc query params that erode REST's cleanliness over time. GraphQL solves exactly that over/under-fetching problem by letting clients specify exact field shapes in one round trip, at the cost of losing HTTP-level caching simplicity (a single POST /graphql endpoint means CDN/browser caching by URL no longer works out of the box) and added server-side complexity (resolver N+1 problems, query cost analysis to prevent abuse). gRPC trades human-readability and broad client compatibility for raw performance (binary protobuf serialization, HTTP/2 multiplexing, strongly-typed contracts) — ideal for internal service-to-service calls where you control both ends and need low latency/high throughput, poor for public-facing APIs needing broad, easy client adoption including from browsers (which need grpc-web, an extra translation layer).

      Follow-up: would you ever expose the same backend logic through both a REST API (for public/partner consumers) and gRPC (for internal services)? What does that architecture look like?
      How would you design rate limiting responses (429 Too Many Requests) to be genuinely useful to a well-behaved client, not just a bare status code?

      Return 429 with a Retry-After header (seconds or an HTTP date) telling the client exactly when to retry, plus conventional rate-limit headers (X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset) on every response — not just the 429 — so well-behaved clients can proactively back off before hitting the limit at all, rather than discovering it only via repeated 429s. The error body itself should still follow your standard {error, code, details} shape (code: 'RATE_LIMITED') so generic error-handling client code doesn't need a special case just for this status.

      Follow-up: should rate limit state be tracked per-API-key, per-IP, or per-authenticated-user, and what's the tradeoff of each for a public API with both authenticated and anonymous traffic?

      Quick Revision Cheat Sheet

      • Resource URLs are plural nouns; the HTTP method is the verb — never put a verb in the path.
      • GET/PUT/DELETE are idempotent by convention; POST and PATCH generally are not.
      • 2xx: 200 generic success, 201 created (+ Location header), 204 success with no body.
      • 4xx: 400 malformed request, 401 "who are you," 403 "I know who you are, but no," 404 not found, 409 conflict, 422 well-formed but semantically invalid (or use 400 for both — just be consistent).
      • 5xx means the server's fault — never leak stack traces/internal messages to the client in a 5xx body.
      • Never return 200 with a success:false flag in the body — use the real status code.
      • A consistent error shape ({error, code, details}) across every endpoint is as much a contract as your success response shape.
      • Nest resource URLs only for genuine ownership/containment, and rarely past 2 levels deep.
      • "Strict REST" (HATEOAS included) is rarely what production APIs implement — most are "resource-oriented HTTP APIs," which is fine as long as you're consistent.
      • 429 responses should include Retry-After and rate-limit headers, not just the bare status code.
