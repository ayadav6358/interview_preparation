    TDD, Coverage, Testing in CI

    ⏱ 3 hrs📍 Chapter 6 of 6

    One-line summary: TDD, coverage metrics, and CI pipeline design are the three disciplines that turn "we have tests" into "we trust our tests" — and a senior engineer needs to know not just how to apply each one, but exactly how each one can be gamed or misread, and how to design around that.

    On this page

      Why It Matters for a Senior Developer

      Most engineers can write a passing test. Fewer can explain why a red-green-refactor cycle produces fundamentally different code than "write the implementation, then write tests to match it." Fewer still can look at a dashboard showing "87% coverage" and correctly say whether that number means anything, or design a CI pipeline that stays fast and trustworthy as a codebase and team scale into the hundreds of PRs per week. These are exactly the judgment calls a Tech Lead is expected to own: deciding whether TDD is worth mandating for a given team, setting (and defending) a coverage policy that doesn't become security theater, and owning the CI pipeline's design so it gates real risk instead of just burning compute and developer patience. In an interview, being able to go a level deeper than "we use Jest and run it in GitHub Actions" — into mutation testing's limitations, flaky test quarantine policy, or why branch coverage of 100% still misses bugs — is a strong, fast signal of real production experience.

      Core Concepts

      The real red-green-refactor cycle — not "write tests first"

      TDD is frequently reduced to "write the test before the code," which misses what actually makes it valuable. The discipline is a tight, disciplined loop with three distinct phases, each with a specific job:

      • Red: write the smallest possible failing test that describes one new increment of behavior — and actually run it to confirm it fails, and fails for the right reason (a missing implementation, not a typo in the test itself). Skipping this confirmation is the single most common way people "do TDD" while accidentally writing a test that can never fail.
      • Green: write the minimum code to pass that one test — not the most elegant, general, or complete solution you can imagine, just enough to turn the test green. This constraint is deliberate: it stops you from speculatively building abstractions the tests haven't yet demanded, a discipline often called YAGNI-by-construction.
      • Refactor: with the safety net of a passing test suite, now improve the internal structure — rename, extract, deduplicate, simplify — without changing behavior, re-running tests after every small change to stay in a continuously-green state throughout.

      The compounding effect across many cycles is what matters: because every line of production code was written to satisfy a test that existed first, the resulting codebase has near-complete test coverage as a byproduct, not as a retrofitted goal — and because the design only grew exactly as far as a test demanded, it tends to end up with fewer speculative abstractions and more naturally testable (loosely coupled, dependency- injectable) interfaces, since untestable code simply can't pass through Red.

      Worked kata: FizzBuzz via strict TDD, cycle by cycle

      A kata is a small, well-known problem used specifically to drill the TDD cycle itself, not to produce interesting production code. Walking through one cycle-by-cycle is the fastest way to see the discipline's actual shape:

      • Cycle 1 — Red: test('returns "1" for 1', () => expect(fizzbuzz(1)).toBe('1')). Run it — fails, because fizzbuzz doesn't exist yet. Correct failure.
      • Cycle 1 — Green: function fizzbuzz(n) { return '1'; } — yes, this is a deliberately absurd hard-coded stub. It is the minimum code that passes, and that's the point.
      • Cycle 2 — Red: test('returns "2" for 2', ...) — fails against the hard-coded stub.
      • Cycle 2 — Green: return String(n); — now forced to generalize, because the hard-coded stub can no longer satisfy two tests at once. This is the mechanism: generalization is pulled out of you by triangulation between multiple examples, not designed up front.
      • Cycle 3 — Red/Green: test for fizzbuzz(3) === 'Fizz' forces n % 3 === 0 ? 'Fizz' : String(n).
      • Cycle 4 — Red/Green: test for fizzbuzz(5) === 'Buzz' forces the n % 5 branch.
      • Cycle 5 — Red/Green: test for fizzbuzz(15) === 'FizzBuzz' forces checking the combined case — and critically, forces you to realize the 15 case must be checked before the individual 3 and 5 checks, or order-of-conditions becomes a real bug the test cycle just caught.
      • Refactor pass: only now, with 5 passing tests as a safety net, extract the duplicated modulo-and-string-return pattern into something cleaner if desired — e.g., building the string from an ordered list of [divisor, word] rules — re-running all 5 tests after the change to confirm nothing broke.

      Notice what never happened: no test for an input that wasn't yet a requirement, no premature abstraction (a "divisor-rule engine") before two concrete cases demanded generalization, and the final design emerged from the accumulated constraints rather than being architected up front.

      Coverage metric types — what each one actually proves

      "Coverage" is not one number; conflating the types is a common and costly interview mistake:

      • Line coverage — percentage of executable lines run at least once by the suite. The weakest and most gameable metric: a line can execute without any assertion checking its output was correct.
      • Branch coverage — percentage of each conditional's branches (both the true and false path of every if, each case of a switch) that were taken. Catches the common line-coverage blind spot of an if whose body runs but whose else never does — but still says nothing about assertion quality.
      • Function/statement coverage — variants on the same theme at different granularity; same fundamental limitation as line coverage.
      • Mutation coverage (mutation testing) — a fundamentally different and much stronger signal. A mutation testing tool (Stryker for JS/TS, PIT for Java) automatically introduces small deliberate bugs ("mutants") into your production code — flipping a > to >=, negating a boolean, changing a + to - — and re-runs your suite against each mutant. A mutant that still passes the full suite is a surviving mutant: concrete proof that your tests would not catch that exact class of real bug, even though line/branch coverage may read 100% on that code. Mutation score (percentage of mutants killed) is a far harder metric to game than line/branch coverage, precisely because it measures assertion strength, not just execution reach — but it is computationally expensive (every mutant re-runs the relevant suite), so it's typically run on a subset of critical modules or in a slower nightly/weekly job rather than on every PR.

      How coverage gets gamed — and why 100% is not the goal

      Coverage numbers are an easy target for Goodhart's law: once a team is measured on "80% line coverage," engineers under time pressure will hit the number without improving test quality. Common gaming patterns: writing a test that calls a function and asserts nothing meaningful (expect(result).toBeDefined() on everything), writing one test that happens to traverse many lines without checking the specific business outcomes at each branch, or excluding "hard to test" files from the coverage calculation entirely via config rather than actually testing them. The deeper problem is structural: line and branch coverage measure reach, not correctness verification — a test suite can have 100% branch coverage and still miss an off-by-one error, a wrong error message, or a subtly incorrect calculated value, because every branch executed but no assertion checked the specific thing that was wrong. This is exactly what mutation testing is designed to expose, and exactly why a senior engineer should treat a coverage percentage as a floor that flags completely untested code, not a ceiling or proxy for test quality.

      CI test pipeline design — parallelization, caching, and gating

      At scale, a CI pipeline's job is to answer "is this PR safe to merge" as fast, cheaply, and reliably as possible, which pulls against each other in specific ways a senior engineer should be able to balance:

      • Parallelization / sharding: split the test suite across N parallel workers/runners (Jest's --shard, Playwright's built-in sharding) so wall-clock time scales down roughly with worker count rather than suite size — critical once a suite grows past a few minutes, since serial execution eventually makes every PR's feedback loop too slow to be useful.
      • Dependency/build caching: cache node_modules (keyed on the lockfile hash) and build outputs across runs so each CI run doesn't re-download/re-compile everything from scratch — often the single biggest lever on pipeline wall-clock time, bigger than test parallelization itself for many JS/TS projects.
      • Test result caching / selective re-running: tools like Nx, Turborepo, or Bazel can skip re-running tests for packages whose inputs haven't changed since the last green run on that exact input hash — valuable in a monorepo where a single PR usually touches a small fraction of packages.
      • Fail-fast ordering: run cheap, fast checks (lint, typecheck, unit tests) before expensive ones (integration, E2E) so a PR with a trivial type error fails in 30 seconds instead of waiting 10 minutes for an E2E shard to get around to failing on the same root cause.
      • Required-checks gating: branch protection rules mark specific CI jobs as required before merge is allowed — the critical design decision is exactly which jobs are required. Everything required must be deterministic and fast enough not to become a merge bottleneck; anything flaky or slow that still provides real signal belongs in a non-blocking job whose failures are tracked and triaged, not one that blocks every PR on an unrelated flake.
      • Flaky test quarantine: a test that fails intermittently without a code change is actively harmful to a team's trust in CI — the standard remedy is an automated or manual quarantine process: tag the test, move it out of the required/blocking job into a separate tracked, non-blocking job, and open a ticket to fix or delete it, rather than letting it either block merges randomly or get "fixed" with a retry that just hides the problem (see the E2E chapter's trace-based diagnosis approach). A quarantined test must have an expiry/review mechanism — an un-triaged quarantine list that only ever grows is a slow-motion loss of coverage.

      How It Works Under the Hood

      A production-grade CI test pipeline is really a dependency graph of jobs, not a single linear script. On every push, the CI system first resolves what changed (often via a monorepo tool's affected-package detection) and restores caches for dependencies and any previously-computed task outputs keyed by a hash of their inputs. Fast static checks run first and gate everything downstream. The test execution stage then fans out: unit/component suites are sharded across several parallel runners, each shard's results (and, on failure, artifacts like traces/screenshots/coverage data) are uploaded, and a final aggregation step merges per-shard coverage reports into one number and collects pass/fail across all shards before the required-check status is reported back to the PR. Mutation testing, being expensive, typically runs as a separate, slower, non-blocking scheduled job rather than inline per-PR — its signal (surviving mutants on critical modules) is reviewed on a cadence, not gated per merge. The whole system's throughput is bounded by whichever stage is both slow and non-parallelizable — in most real pipelines, that's either a cold dependency install (fixed by caching) or a handful of long-running E2E tests that don't shard well (fixed by keeping that layer small, per the pyramid principle from the Testing Strategy chapter).

      Real-World Production Scenario at Scale

      At scale

      A fintech's engineering leadership mandated "90% line coverage on all new code" as a quality gate after a production incident, enforced by failing the PR check if coverage dropped below threshold. Within two quarters, coverage dashboards showed healthy 90%+ numbers across the org, yet production incidents from logic bugs in covered code hadn't meaningfully decreased. An audit (prompted by a senior engineer who'd seen this pattern before) ran Stryker mutation testing against the highest-incident-rate module — the billing calculation service, which reported 94% line coverage — and found a 38% mutation score: most of its tests called the pricing function and asserted only `expect(result).toBeDefined()` or checked an unrelated field, satisfying the line-coverage requirement without verifying the actual computed price was correct. The fix wasn't more tests — it was deleting the line-coverage gate as the primary metric and replacing it with two things: a mutation-testing job (scheduled nightly, non-blocking, with a dashboard trend reviewed weekly) scoped to the handful of modules with real financial/safety impact, and a lightweight PR-review checklist item asking "does this test's assertion actually verify the specific thing that could go wrong" for new code in those modules. Line coverage was kept only as a floor (flagging genuinely untested files) at a much lower, non-gating threshold. Six months later, the billing module's mutation score was above 85% and its incident rate had actually dropped — the metric change, not a raw increase in test count, was what correlated with the quality improvement.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Treating a coverage percentage as a target to hit rather than a floor that flags obviously untested code is the single most common and costly misunderstanding of this whole area. A team that optimizes for the number will get the number, via assertion-free tests, excluded files, or tests that exercise code without checking outcomes — and will not get better bug detection, which was presumably the actual goal. Every coverage policy should be paired with spot-checks of assertion quality (manual review, or periodic mutation testing) or the number will quietly decouple from what it was meant to proxy for.

      Gotcha

      "We require 100% test-level retries to pass before merge" and similar blanket retry policies, carried over from the E2E layer, quietly erode CI trust across the whole pipeline if applied without quarantine discipline — a flaky unit or integration test that "passes on retry" still fails some nonzero fraction of the time, and without a tracked quarantine/triage process, that fraction only grows as more flaky tests accumulate, until engineers routinely re-run red CI without reading why, which is the exact failure mode a required-checks gate exists to prevent.

      • Mistake: running mutation testing on every PR instead of a scheduled job on critical modules — it's computationally expensive enough (re-running the suite per mutant) that gating every PR on it turns a 5-minute CI run into a 45-minute one for marginal added signal on low-risk code.
      • Mistake: doing "TDD" by writing the whole implementation first and then retrofitting tests that happen to pass against it — this produces tests that confirm what the code does, not tests that specify what it should do, and silently skips the Red step's main value: catching a test that can't actually fail.
      • Mistake: sharding tests naively by file-count instead of by historical run time — this leaves one shard with a handful of slow integration tests taking 8 minutes while three others finish in 90 seconds, so the pipeline's wall-clock time is still bottlenecked on the slowest shard. Most modern test runners support time-based/historical balancing specifically to avoid this.
      • Best practice: make the required-checks list a deliberate, reviewed decision, not an accumulation of "whatever CI jobs exist" — every required job should be fast, deterministic, and have an owner responsible for its health; anything that doesn't meet that bar becomes a tracked non-blocking job instead.
      • Best practice: give quarantined tests an expiry or a recurring review cadence (e.g., a weekly bot comment listing tests quarantined >30 days) — an unreviewed quarantine list is coverage loss that nobody notices until the next incident.

      Interview Questions

      Basic

      What are the three phases of the TDD cycle, and what is each one actually for?

      Red: write a failing test for one small new increment of behavior, and confirm it fails for the right reason. Green: write the minimum code to pass that test, resisting the urge to over-build. Refactor: with tests as a safety net, improve the code's internal structure without changing behavior, re-running tests continuously.

      Follow-up: what goes wrong if you skip confirming the test actually fails during Red?
      What's the difference between line coverage and branch coverage?

      Line coverage measures the percentage of executable lines run at least once. Branch coverage measures whether each conditional's branches (both true and false paths) were taken — it catches cases like an `if` whose body ran but whose `else` never did, which line coverage would miss.

      Follow-up: can you have 100% branch coverage and still have a bug? How?
      What is mutation testing, in one sentence?

      A technique that automatically introduces small deliberate bugs ("mutants") into production code and re-runs your test suite against each one — a mutant that still passes is a "surviving mutant," proving your tests wouldn't catch that class of real bug.

      Follow-up: why is mutation testing usually run on a schedule rather than on every PR?
      Why might a codebase have 95% line coverage and still ship frequent logic bugs?

      Line coverage only measures that code executed, not that any assertion verified its output was correct — tests can run through a line (even every branch of it) while asserting on the wrong thing, or nothing meaningful at all, leaving real bugs undetected despite a high coverage number.

      Follow-up: what metric would expose this gap that line coverage can't?
      What does "parallelization" or "sharding" mean in a CI test pipeline?

      Splitting a test suite across multiple CI workers/runners that execute concurrently, so wall-clock pipeline time scales down with worker count rather than growing linearly with suite size.

      Follow-up: what commonly bottlenecks the benefit of sharding even with many workers?
      What is a "flaky test," and why is it a problem beyond just the one test?

      A test that intermittently fails without any related code change. Beyond wasting time on that one test, it erodes trust in CI generally — engineers start re-running red pipelines reflexively instead of reading why, which can let a real failure slip through unnoticed among the "probably just flaky" noise.

      Follow-up: what's the difference between fixing a flaky test and quarantining it?
      What's a "required check" in a CI/branch-protection setup?

      A specific CI job marked in branch protection rules as mandatory to pass before a PR can be merged — the design decision of which jobs are required determines what actually gates merges versus what's just informational.

      Follow-up: what properties should a job have before it's made required?

      Medium

      Walk through why strict TDD on a FizzBuzz-style problem tends to produce the correct conditional ordering (checking the combined case before individual cases) without the author "designing" that ordering up front.

      Each new test triangulates against the existing implementation: after `fizzbuzz(3)` and `fizzbuzz(5)` force individual modulo checks, writing a test for `fizzbuzz(15)` will fail against an implementation that checks `% 3` first (since it returns 'Fizz', not 'FizzBuzz') — the Red phase surfaces exactly this ordering bug as a failing test, and Green forces reordering the checks (combined case first) to make it pass. The design falls out of the accumulated test constraints rather than being anticipated.

      Follow-up: what would happen if you wrote the fizzbuzz(15) test first, before the individual cases?
      A team reports 90% line coverage but a mutation testing run on the same code shows a 40% mutation score. Explain the gap and what it implies about their tests.

      The gap means most of their code executes under test (high line coverage) but most introduced mutants still pass the suite — meaning the tests' assertions are too weak or absent to detect specific changes in behavior (wrong comparison operators, flipped booleans, off-by-one changes) even on code that technically "ran." It implies many tests exercise code paths without verifying the specific correctness of what happened on them — a strong signal of coverage gaming or just weak assertions, not a suite that would actually catch real regressions.

      Follow-up: would you mandate mutation testing org-wide in response, or something more targeted — why?
      Design a fail-fast ordering for a CI pipeline with lint, typecheck, unit tests, integration tests, and E2E tests. Justify the order.

      Order by (speed × likelihood of catching the same root cause early): lint and typecheck first (seconds, catch an entire class of errors before any test even runs), then unit tests (fast, broad logic coverage), then integration tests (slower, fewer, verify cross-component wiring), then E2E last (slowest, smallest suite, verifies true end-to-end critical journeys). Each stage only runs if the previous one passed, so a trivial type error fails in seconds instead of after a 10-minute E2E shard gets around to failing on the same underlying cause.

      Follow-up: would you ever want integration and E2E to run in parallel instead of strictly sequentially — when?
      Why should a flaky test be quarantined with an expiry/review mechanism rather than just moved to a non-blocking job indefinitely?

      An indefinitely non-blocking job with no review cadence becomes a silent coverage sink — tests pile up there, nobody looks at the dashboard, and the team gradually loses real test coverage without any specific decision ever being made to accept that loss. A review cadence (e.g., a weekly report of tests quarantined >30 days) forces an explicit triage decision — fix, delete, or re-justify the quarantine — on each one instead of letting quarantine become a permanent, invisible dumping ground.

      Follow-up: who should own triaging the quarantine list in a mid-sized engineering org?
      Explain why doing TDD strictly (never writing more production code than the current failing test demands) tends to produce more testable, loosely-coupled designs as a side effect.

      Code that's hard to test (tightly coupled to a global, a singleton, a concrete hard-to-construct dependency) is, by the same token, hard to drive through a fast Red-Green cycle — the friction of writing the test surfaces the coupling problem immediately, before the code exists, rather than after it's already been built and depended on elsewhere. This creates continuous pressure toward dependency injection and small, focused units, not because anyone designed for testability as a separate goal, but because untestable code simply resists passing through the cycle at all.

      Follow-up: can TDD still produce a badly-designed system — what's a failure mode where it does?
      How would you decide which modules in a large codebase deserve mutation testing coverage, given it's too slow to run everywhere?

      Prioritize by (blast radius of a bug × historical incident rate × how business-critical the logic is) — billing/pricing calculations, auth/authorization checks, and data-integrity-critical transforms are typical candidates, versus low-risk UI formatting or logging code where a surviving mutant's real-world cost is low. Run it as a scheduled job on that prioritized subset, track mutation score trend over time per module, and expand the scope only as compute budget and team bandwidth to act on findings allow.

      Follow-up: how would you present a newly-discovered low mutation score on a critical module to a team that's proud of its "90% coverage"?

      Advanced

      You're asked to roll out a company-wide coverage policy for a 200-engineer organization. Design one that avoids the gaming failure mode described in the production scenario.

      Set line/branch coverage as a low, non-gaming floor (e.g., flag anything under 50-60% as a review flag, not a hard block) to catch genuinely untested code without incentivizing assertion-free tests to hit a high target. Separately, identify a tier of critical modules (by incident history and business impact) and apply mutation testing to that tier only, as a scheduled job with a tracked trend dashboard reviewed by each team monthly, not a per-PR gate. Pair both with a lightweight PR-review norm (a checklist prompt, not an automated gate) asking whether new tests on critical-path code actually assert the specific thing that matters. Explicitly communicate that the coverage percentage is a floor, not a target, to prevent the org from re-converging on gaming behavior under delivery pressure — and track incident rate per module over time as the actual outcome metric, not the coverage number itself.

      Follow-up: how would you measure whether this policy is actually working, a year in?
      Design the CI pipeline topology (job graph, caching strategy, required checks) for a monorepo with 40 packages, where a typical PR touches 2-3 packages.

      Use an affected-package detection tool (Nx/Turborepo) to compute which packages changed and their dependents, and only run lint/typecheck/test for that affected set rather than the whole monorepo — this is the single biggest lever at this scale, since a 2-3-package PR shouldn't pay for 40 packages' worth of CI. Layer a remote build/task-output cache keyed by content hash on top, so even re-runs of the same affected set across different branches/PRs reuse previous results when inputs haven't changed. Shard whatever test execution remains necessary across parallel runners, balanced by historical run time rather than file count. Required checks should cover only the fast, deterministic, affected-scoped jobs; a slow full-repo nightly job (covering cross-package integration risk the affected-detection might miss) runs separately and non-blocking, with its own alerting if it goes red.

      Follow-up: what's the risk of relying purely on affected-package detection, and how would you mitigate it?
      A team claims "we do TDD" but your review of their git history shows production code and test code committed together in single commits, tests clearly written to match existing implementation behavior. How would you verify whether real TDD discipline is happening, and does it matter if it isn't?

      Git history granularity is a weak signal either way — disciplined TDD can still be squash-committed as one commit, and separate commits don't prove tests were written first. Better signals: ask the engineer to live-code a small feature TDD-style and observe whether they can actually run a test and watch it fail for the right reason before writing implementation; review whether their test suites tend to have redundant/defensive tests covering cases that were never a real requirement (a tell of test-first thinking) versus suites that suspiciously exactly match the implementation's exact branches with no extra edge-case coverage (a tell of test-after). Whether it matters depends on the goal: if the actual objective is well-tested, low-coupling code with good coverage, and the team reliably achieves that via disciplined test-after instead, the TDD label itself is less important than the outcome — TDD is a means, and a team achieving the same design and coverage outcomes through a different discipline hasn't actually failed the goal.

      Follow-up: are there specific classes of bugs where you'd argue TDD provides a benefit that disciplined test-after structurally cannot?
      Your mutation testing job reports a declining mutation score trend over several months on a module with stable, even improving, line coverage. Diagnose the likely cause and your response.

      Stable/improving line coverage with declining mutation score implies new tests are being added that execute new code paths (sustaining or growing line coverage) but with assertions weaker than the existing baseline — a common cause is delivery pressure pushing engineers toward coverage-satisfying but low-rigor tests (smoke-test-style assertions) for new features, while the module's surface area and complexity grow faster than assertion quality keeps pace. Respond by reviewing a sample of recently-added tests in that module directly (not just the aggregate metric) to confirm the hypothesis, then address it at the review-process level — a specific review prompt for that module's PRs, or pairing junior engineers writing in that module with someone experienced in mutation-resistant assertion style — rather than purely adding a stricter automated gate, since the root cause is a skill/process gap, not something a threshold alone fixes.

      Follow-up: would you consider this module a candidate for a TDD mandate specifically, versus the rest of the codebase — why?
      How would you redesign a required-checks policy for a team that has accumulated 15 required CI checks over two years, several of which are known to be occasionally flaky, causing frequent "just re-run it" merges?

      Audit each of the 15 for: historical flake rate (pull CI run history, not anecdote), what unique risk it actually catches versus overlapping with another required check, and its typical run time. Checks with a real, non-overlapping risk signal and low flake rate stay required. Checks with meaningful flake rate get root-caused first (often fixable, per the E2E chapter's trace-based approach) — if genuinely not fixable short-term, move to a tracked non-blocking job with an owner and a re-evaluation date, not silently dropped. Checks that substantially overlap another required check's risk coverage get merged or removed outright, since redundant required checks only add latency and flake-surface without adding safety. The end state should be fewer, faster, higher-signal required checks plus a visible (not hidden) tracked list of what's deliberately non-blocking and why — reversing the "accumulate checks forever" default that produced the problem.

      Follow-up: how would you prevent this same accumulation problem from recurring over the next two years?

      Practice Assignments

      Beginner (30-60 min)

      Drill the TDD cycle on a small kata

      Pick a small, well-specified problem (FizzBuzz, a string-reversal with Unicode edge cases, or a simple Roman-numeral converter) and implement it using strict red-green-refactor, writing down each cycle.

      • For every cycle, write the failing test, run it and confirm the failure message, then write only the minimum code to pass.
      • Do at least one deliberate refactor pass after 4-5 cycles, re-running all tests after each change.
      • Keep a short log of each Red/Green/Refactor step as you go.

      Acceptance criteria: a cycle-by-cycle log showing the final design wasn't anticipated up front but emerged from triangulation between tests.

      Hints

      If you catch yourself writing code that no current test requires, stop — that's the "Green phase discipline" being violated; write the test that would demand it first.

      Bonus: have a colleague review your log and identify any point where you skipped confirming a genuine Red before moving to Green.

      Intermediate (2-4 hrs)

      Measure the coverage-vs-mutation-score gap on real code

      Take an existing small-to-medium module in a personal or work project (ideally one with some business logic, not just UI glue). Run line/branch coverage, then run a mutation testing tool (Stryker for JS/TS, PIT for Java, mutmut for Python) against it.

      • Record both numbers.
      • Pick 3 surviving mutants and manually verify each represents a real gap — i.e., confirm by hand that introducing that exact bug would not be caught by any existing test.
      • Write one new test per surviving mutant specifically designed to kill it, and confirm it does.

      Acceptance criteria: documented before/after mutation score; a short writeup explaining why line coverage didn't catch what the surviving mutants revealed.

      Hints

      Modules with many conditionals and arithmetic (pricing, validation, date logic) tend to produce the most illustrative surviving mutants quickly.

      Bonus: propose a mutation-score threshold and scope (which modules) you'd actually recommend gating on for this codebase, with justification.

      Advanced (1-2 days)

      Design and build a tiered CI pipeline with quarantine and caching

      Take a small-to-medium project (yours, or one you build for this exercise) with a CI config on GitHub Actions (or equivalent) and build a complete tiered pipeline.

      • Implement fail-fast ordering: lint/typecheck/unit before integration before E2E.
      • Add dependency caching keyed on the lockfile hash and measure the before/after pipeline time.
      • Shard at least one test stage across 2+ parallel jobs, balanced by historical run time if your runner supports it.
      • Deliberately introduce one flaky test, then implement a quarantine mechanism: a tag, a separate non-blocking job, and a written policy for when it gets revisited.
      • Document exactly which jobs are required-checks and justify each one in writing.

      Acceptance criteria: pipeline runs green on a clean checkout; measured time improvement from caching/sharding is documented; the quarantine mechanism correctly keeps the flaky test out of the merge-blocking path while still reporting its results somewhere visible.

      Hints

      GitHub Actions' `needs:` field and a `matrix` strategy cover fail-fast ordering and sharding respectively without needing a third-party tool; `continue-on-error: true` on a job is the simplest non-blocking quarantine mechanism to start with.

      Bonus: add a scheduled (non-blocking) mutation-testing job on one critical module and report its mutation score alongside the regular coverage number, discussing what each one tells you that the other doesn't.

      Quick Revision Cheat Sheet

      • TDD cycle: Red (failing test, confirm it fails for the right reason) → Green (minimum code to pass) → Refactor (improve structure, tests stay green).
      • Design emerges via triangulation between accumulated tests, not upfront architecture — untestable code structurally resists the cycle, pushing toward loose coupling as a side effect.
      • Line coverage = lines executed; branch coverage = both paths of every conditional taken — neither verifies assertion correctness, only reach.
      • Mutation testing introduces deliberate bugs ("mutants") and checks if your suite catches them — a surviving mutant proves a real detection gap that line/branch coverage can't see.
      • Coverage percentage is a floor to flag untested code, never a target — optimizing for the number produces gamed, assertion-free tests (Goodhart's law in action).
      • Mutation testing is expensive — run it scheduled, non-blocking, scoped to critical/high-risk modules, not inline on every PR.
      • CI pipeline speed levers, roughly in order of impact: dependency/build caching, fail-fast ordering (cheap checks first), then test parallelization/sharding.
      • Flaky tests get quarantined (tagged, moved to a non-blocking tracked job) with an expiry/review cadence — never left as a silent, ever-growing dumping ground, and never "fixed" with a blanket retry.
      • Required-checks should be fast, deterministic, owned, and deliberately chosen — not an accumulation of every CI job that happens to exist.
