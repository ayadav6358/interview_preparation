    Testing

    📚 6 chapters⏱ ~15–17 hrs total

    Testing is where senior candidates separate themselves from mid-level ones. Anyone can write a test that passes; a senior engineer designs a test strategy that catches real regressions, stays fast, and doesn't rot into a maintenance burden. This topic covers the test pyramid and what deserves a test at all, unit testing with real mocking internals, React Testing Library's user-centric philosophy, API/integration testing against real databases, E2E testing with Playwright's auto-waiting model, and wiring all of it into CI with coverage gates that actually mean something.

    Learning Outcomes

    • Design a test strategy (pyramid shape, what to test, what to deliberately skip) for a real product, and defend it under interviewer pushback.
    • Explain the mechanical difference between a mock, a stub, a spy and a fake — and when each is the wrong tool.
    • Diagnose and fix flaky tests from first principles: timing, shared state, network, test order dependence.
    • Write component tests that test behavior (RTL) instead of implementation details, and API tests against an isolated, resettable test database.
    • Build and debug E2E suites with Playwright, understanding its auto-wait/retry model instead of fighting it with manual sleeps.
    • Set up coverage gates in CI that catch real risk, and explain why 100% line coverage is not the same as a well-tested system.

    🏆 Capstone Project: Full Test Suite for a Full-Stack App

    Problem statement: Take a small full-stack app (React frontend + Node/Express API, e.g. a task tracker or a bookmarking tool) and build a complete, layered test suite that would survive a real code review at a company with high testing standards — then wire it into a CI pipeline with coverage gates that block merges on real risk, not vanity percentages.

    Required features:

    • Unit tests (Vitest) for pure business logic and utility functions, with mocks/spies/fakes used correctly and justified.
    • Component tests (React Testing Library) for every interactive component, written against user-visible behavior, not internals.
    • API/integration tests (Supertest) against a real, isolated test database that resets cleanly between tests (transaction rollback or truncate strategy).
    • End-to-end tests (Playwright) covering the 2–3 critical user journeys (signup → core action → verify result), running against a built app in CI.
    • A CI pipeline (GitHub Actions) that runs all four layers, fails fast on the cheapest layer first, and enforces a branch-level coverage threshold with a documented exception policy.
    • A short ADR-style writeup explaining the pyramid shape you chose and what you explicitly decided not to test.

    Tech stack suggestion: React + TypeScript, Vitest + RTL, Node/Express API, Postgres (or SQLite for a lighter test DB), Supertest, Playwright, GitHub Actions, Istanbul/v8 coverage via Vitest.

    Milestones:

    1. Write the test strategy doc first: pyramid shape, what's in scope, what's deliberately out of scope.
    2. Unit-test the business logic layer; identify and eliminate any hidden I/O that makes "unit" tests slow or flaky.
    3. Component-test the UI with RTL, including async states (loading, error, optimistic update) using correct async utilities.
    4. Stand up a test database lifecycle (setup/teardown per test file or per test) and write Supertest integration tests for every route.
    5. Write Playwright E2E tests for the critical paths, running headless in CI against a production build.
    6. Wire it all into a GitHub Actions pipeline: parallel jobs, fail-fast ordering, coverage gate with a sensible threshold, and flaky-test retry policy.

    Evaluation checklist:

    • ☐ Can explain, for any given test, which layer it belongs in and why it isn't duplicated at another layer.
    • ☐ No test relies on real wall-clock sleeps; async waits use proper polling/auto-wait utilities.
    • ☐ The suite is deterministic: running it 20 times in a row produces 20 green runs, including in CI's constrained environment.
    • ☐ Coverage gate is tied to meaningful paths (branches touched), not just line count inflated by trivial getters.
    • ☐ Can defend at least one thing deliberately left untested, and why that was the right call.
