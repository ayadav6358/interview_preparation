      Why It Matters for a Senior Developer

      Every system design interview loop eventually asks you to design something close to one of these seven systems — they're not arbitrary, they're chosen because each one forces a specific, well-known tradeoff that doesn't show up anywhere else (hash collisions, fanout strategy, geospatial indexing, idempotent payments). Memorizing a generic "clarify, estimate, design" template (covered in Chapter 14) gets you through the first five minutes; what actually earns a strong hire signal is recognizing which specific tradeoff this particular system is testing and discussing it with real numbers and real alternatives, not generic boxes-and-arrows.

      Case Study 1: URL Shortener

      Requirements

      Functional: shorten a long URL to a short code, redirect short code → long URL, optional custom aliases and expiry. Non-functional: redirects must be low-latency (<50ms p99) and highly available (redirects are on the critical path of other people's content); writes (shortening) can tolerate slightly higher latency than reads.

      Capacity estimation

      Assume 100M new URLs/day shortened, and a 100:1 read:write ratio typical for link redirect services (links get clicked far more than created) → 10B redirects/day ≈ 115K reads/sec average, ~350K/sec at 3x peak. Writes: 100M/86,400 ≈ 1,160/sec average. Storage: 100M URLs/day × ~500 bytes (long URL + metadata) × 365 × 5 years ≈ 90TB — easily fits a sharded relational store or key-value store.

      API design

      POST /api/v1/shorten   { longUrl: string; customAlias?: string; expiresAt?: string }
                        -> { shortUrl: string; code: string }
GET  /{code}           -> 302 redirect to long URL (or 410 Gone if expired)

      Data model

      urls(code VARCHAR(8) PK, long_url TEXT, created_at, expires_at, owner_id, click_count) — code is the primary key, so lookups are O(1) on an index without needing a separate ID column.

      Component diagram

      flowchart LR C[Client] --> LB[Load Balancer] LB --> API[Shortener API servers] API --> Cache[(Redis cache:
      code -> long URL)] API --> DB[(Sharded KV/SQL store)] API --> IDGen[Distributed ID/
      Base62 encoder] Cache -.miss.-> DB

      Key tradeoff: generating the short code

      Option A — hash + collision handling: MD5/SHA256 the long URL, take the first 6-8 chars base62-encoded. Fast, deterministic (same URL always maps to the same code, which can be a feature), but collisions are possible (two different long URLs hashing to the same prefix) — must check the DB on write and retry with a different salt/suffix on collision. Option B — counter + base62 encoding: a distributed counter (e.g., a range of IDs pre-allocated per app server, or Snowflake-style ID generation) assigns a strictly increasing integer ID, base62-encoded to a short string. No collisions possible by construction, but codes are sequential/guessable (minor information leak — competitors can estimate your link volume) unless you add a deterministic shuffle/bit-mix step. Most production systems (Bitly-style) use Option B for its collision-free simplicity, with a bit-mixing step to avoid obviously sequential codes. Redirect caching (Option discussion): cache hot codes in Redis with a TTL, and consider a CDN edge cache for extremely hot links (viral tweets) since a redirect response is cacheable and doesn't require hitting your origin at all.

      Case Study 2: Chat Application

      Requirements

      Functional: 1:1 and group messaging, delivery and read receipts, online presence, message history. Non-functional: low-latency delivery (<200ms for online recipients), messages must not be lost (durability), ordering must be consistent per-conversation.

      Capacity estimation

      50M DAU, 40 messages/user/day average → 2B messages/day ≈ 23K messages/sec average, ~70K/sec peak. Each message ~1KB (text + metadata) → ~2TB/day raw, requiring tiered storage (hot recent messages in a fast store, older history archived).

      API / protocol design

      WebSocket for real-time bidirectional delivery (not polling — polling at this message rate would be prohibitively expensive and still add latency); REST/HTTP for history fetch and non-realtime operations (fetch older messages, search).

      Data model

      messages(message_id, conversation_id, sender_id, content, sent_at, seq_no) partitioned by conversation_id so a conversation's messages are co-located and can be fetched/ordered cheaply; receipts(message_id, user_id, status, timestamp) for delivered/read tracking.

      Component diagram

      flowchart TD U1[User A] -- WebSocket --> GW1[Gateway/Connection server 1] U2[User B] -- WebSocket --> GW2[Gateway/Connection server 2] GW1 --> MQ[(Message Queue)] MQ --> Router[Message Router /
      Fanout service] Router --> GW2 Router --> Store[(Message store,
      partitioned by conversation)] Router --> Presence[(Presence service)]

      Key tradeoffs: connection management, ordering, group fanout

      WebSocket connection management: each gateway server holds a long-lived connection per online user; since a single server can hold maybe 50-100K concurrent WebSocket connections, 50M DAU with even 10% concurrently online (5M) needs ~50-100 gateway servers, with a presence/connection-registry service (often Redis) mapping user_id → which gateway server holds their connection, since messages must be routed to the specific server holding the recipient's socket. Ordering: use a per-conversation monotonic sequence number (not wall-clock timestamp, which can skew across servers) so clients can detect and request missing/out-of-order messages. Read receipts: must not block message delivery — write the receipt asynchronously and let the sender's client poll/subscribe for receipt updates separately from the message stream itself. Group fanout: for a group of N members, one sent message must be delivered to N-1 others — for small groups this is cheap fanout-on-write (push to each online member's gateway immediately), but for very large groups (broadcast channels, thousands of members) fanout-on-write at send time becomes expensive, so large-group/broadcast-style chat often switches to a fanout-on-read model (the news feed case study below covers this exact tradeoff in depth).

      Case Study 3: Notification System

      Requirements

      Functional: send notifications across multiple channels (push, email, SMS, in-app) triggered by application events, with templating and per-user channel preferences. Non-functional: must not overwhelm users (rate limiting per channel/user) or third-party providers (rate limiting per provider), must tolerate provider outages without losing notifications.

      Capacity estimation

      200M notification events/day from upstream services → ~2,300/sec average, with sharp bursts around specific triggers (e.g., a flash sale notifying 10M users within minutes) — burst handling, not average throughput, is the real design driver here.

      API design

      POST /api/v1/notifications
  { userId: string; templateId: string; data: object; channels?: ("push"|"email"|"sms")[] }
  -> { notificationId: string; status: "queued" }

      Data model

      notification_templates(template_id, channel, subject, body_template); user_preferences(user_id, channel, opted_in); notification_log(notification_id, user_id, channel, status, sent_at) for delivery tracking and dedup/idempotency.

      Component diagram

      flowchart LR App[Upstream services] --> API[Notification API] API --> Q[(Event Queue)] Q --> Worker[Fanout Worker] Worker --> Pref[(User preference
      + template store)] Worker --> RL1{Rate limiter:
      per-channel/provider} RL1 --> Push[Push provider] RL1 --> Email[Email provider] RL1 --> SMS[SMS provider]

      Key tradeoff: multi-channel fanout and per-channel rate limiting

      A single trigger event (e.g., "order shipped") fans out to multiple channels per user based on preference — this must happen asynchronously via a queue, not synchronously in the triggering request path, both because channel delivery (especially SMS/email, which call third-party APIs) is slow and unreliable, and because a burst trigger (flash sale to 10M users) would otherwise overwhelm the triggering service itself. Each channel needs its own rate limiter (token bucket per provider, see Chapter 11) because providers like Twilio/SendGrid impose their own hard rate caps and will throttle or ban you for bursting past them — the queue + per-channel-worker-pool architecture naturally smooths bursts into each provider's sustainable rate (this is leaky-bucket-style smoothing in practice). Templating should render server-side at send time (not pre-rendered and stored) so a template fix doesn't require re-sending already-queued notifications.

      Case Study 4: News Feed

      Requirements

      Functional: users see a reverse-chronological or ranked feed of posts from people/pages they follow. Non-functional: feed load must be fast (<500ms) even for users following thousands of accounts; must handle highly skewed follower distributions (celebrities with 100M followers posting).

      Capacity estimation

      500M DAU, average 300 follows/user, 100M posts/day → at naive full fanout, one post from an average user generates 300 feed-insert operations, but one post from a celebrity with 50M followers generates 50M feed-insert operations — this asymmetry is the entire design problem.

      Component diagram

      flowchart TD Post[User posts] --> Decide{Follower count
      above threshold?} Decide -- No, normal user --> FanoutWrite[Fanout-on-write:
      push post ID to each
      follower's feed cache] Decide -- Yes, celebrity --> SkipFanout[Skip fanout;
      store post only] FanoutWrite --> FeedCache[(Per-user feed cache,
      list of post IDs)] Read[User opens feed] --> Merge[Merge: feed cache
      + live pull from
      followed celebrities] FeedCache --> Merge SkipFanout --> Merge

      Key tradeoff: fanout-on-write vs fanout-on-read, and the celebrity problem

      Fanout-on-write: when a user posts, immediately push the post ID into every follower's precomputed feed list (cached). Reads are then extremely fast (just read your own precomputed list). But write cost scales with follower count — a celebrity post triggers millions of writes, and if a follower is inactive for weeks, all that fanout work was wasted on someone who may never see it. Fanout-on-read: store posts normally; at read time, pull recent posts from everyone the user follows and merge them on the fly. Write cost is trivial (O(1) per post regardless of follower count), but read cost scales with how many accounts you follow, and reads are slower/more expensive since they happen on every single feed load rather than once per post. The hybrid used by essentially every major platform at scale: fanout-on-write for normal users (most posts, most followers — keeps reads fast for the common case), fanout-on-read (pull-based) specifically for celebrity/high-follower-count accounts above a threshold, merged at read time with the precomputed feed. This caps worst-case write amplification while keeping typical reads fast.

      Case Study 5: File Storage/Sharing (Dropbox-style)

      Requirements

      Functional: upload/download files, sync across devices, share with other users, versioning. Non-functional: must handle large files efficiently (resumable uploads), must minimize storage cost via deduplication, must scale to billions of files.

      Capacity estimation

      500M users, average 10GB stored/user → 5 exabytes total — this is why metadata and blob storage must be split: metadata (file names, folder structure, permissions, version pointers) is small and needs transactional/relational semantics, while the actual file bytes are enormous and need cheap, horizontally-scalable blob storage (S3-style object storage), not a traditional database.

      Data model

      files(file_id, owner_id, name, folder_id, current_version_id); file_versions(version_id, file_id, content_hash, size, created_at); blocks(content_hash PK, storage_url, ref_count) — the blocks table is the dedup layer.

      Component diagram

      flowchart LR Client -- chunk + hash --> API[Upload API] API --> Dedup{Hash already
      in blocks table?} Dedup -- Yes --> Ref[Increment ref_count,
      point version at
      existing block] Dedup -- No --> Blob[(Blob storage, e.g. S3)] Blob --> Register[Register new block
      + hash in metadata DB] Ref --> Meta[(Metadata DB)] Register --> Meta

      Key tradeoff: chunking, content-hash dedup, metadata/blob split

      Large files are split into fixed or content-defined chunks (e.g., 4MB blocks); each chunk is hashed (SHA-256), and before uploading a chunk's bytes, the client/server checks whether that hash already exists in the blocks table — if so, only a reference is created (no bytes re-uploaded or re-stored), which is what makes storing "the same stock photo uploaded by 10,000 users" cost roughly 1x instead of 10,000x. Content-defined chunking (splitting on content boundaries rather than fixed byte offsets) is what lets dedup work even when a file is slightly edited — a fixed-offset chunker would shift every subsequent chunk's boundary after an insertion, destroying dedup for the whole rest of the file, while content-defined chunking (rolling hash boundary detection) keeps unchanged regions aligned to the same chunk boundaries. The metadata/blob split matters because the two have wildly different scaling and consistency needs: metadata needs strong consistency (you don't want two devices to both think they have the "current" version after a conflicting edit) and is small enough for a traditional sharded relational store, while blobs are append-only, enormous, and best served by purpose-built object storage with its own replication/durability guarantees.

      Case Study 6: Ride Booking (Uber-style)

      Requirements

      Functional: rider requests a ride, system matches to a nearby available driver, real-time location tracking during the trip. Non-functional: matching must happen in seconds, location updates must be near-real-time (few seconds staleness acceptable), must scale to dense urban areas with thousands of drivers per square km.

      Capacity estimation

      5M active drivers sending location updates every 4 seconds → ~1.25M location writes/sec globally; a single dense city might have 50K drivers each updating every 4s → 12,500 writes/sec for that city's geo-index alone — this is why geospatial indexing must be regionally partitioned, not a single global structure.

      Component diagram

      flowchart TD Driver[Driver app] -- location every 4s --> LocSvc[Location Ingest Service] LocSvc --> GeoIndex[(Geospatial index,
      sharded by region,
      geohash/quadtree)] Rider[Rider requests ride] --> MatchSvc[Matching Service] MatchSvc --> GeoIndex MatchSvc --> Driver MatchSvc --> TripSvc[Trip Service]

      Key tradeoff: geospatial indexing and driver matching

      Geohash: encodes a lat/lng pair into a short string where nearby locations share string prefixes — makes "find all drivers near me" a prefix-range query on a sorted structure (e.g., a Redis sorted set or a DB index on the geohash string), which is simple to shard (shard by geohash prefix, naturally keeping nearby points co-located) but has an edge-case problem: two points can be geographically very close but fall on opposite sides of a geohash cell boundary and share no prefix, so a real implementation must check neighboring cells too. Quadtree: recursively subdivides space into quadrants, with denser regions (city centers) subdivided more finely than sparse ones — gives more uniform query cost regardless of density but is a tree structure that's harder to shard cleanly across machines than a flat geohash string. In practice, Uber's own published H3 (hexagonal hierarchical index) addresses geohash's boundary problem by using hexagonal cells (which have uniform adjacency, unlike geohash's rectangular cells where corner-adjacency is awkward). Matching: given a candidate set of nearby available drivers, the matching service scores by distance/ETA, driver rating, and current driver utilization (don't always send requests to the same top-rated driver — this is itself a small instance of the "hot node" / load distribution problem), then dispatches and waits for accept/reject with a timeout before trying the next candidate. Location updates are deliberately not strongly consistent — a few seconds of staleness is an acceptable tradeoff (PACELC's Latency-over-Consistency choice) given how much cheaper eventually-consistent location propagation is versus synchronizing every driver's position everywhere instantly.

      Case Study 7: E-commerce Checkout

      Requirements

      Functional: add to cart, checkout (reserve inventory, charge payment, create order), order status tracking. Non-functional: must never oversell inventory beyond acceptable business tolerance, must never double-charge a customer, must handle partial failures (payment succeeds but order creation fails) without leaving the system in an inconsistent state.

      Capacity estimation

      Flash-sale scenario: 1M concurrent users competing for 10,000 units of a limited item in a 10-minute window — peak checkout attempt rate can hit tens of thousands/sec against a single hot inventory row, which is a concurrency/contention problem, not just a throughput problem.

      Component diagram

      flowchart TD Checkout[Checkout request] --> Saga[Order Saga Orchestrator] Saga --> Inv[Inventory Service:
      reserve stock] Saga --> Pay[Payment Service:
      charge, idempotency key] Saga --> Order[Order Service:
      create order record] Inv -. compensate: release .-> Saga Pay -. compensate: refund .-> Saga Order -. compensate: cancel .-> Saga

      Key tradeoff: inventory consistency, payment idempotency, order saga

      Inventory consistency: a single global strongly-consistent counter avoids overselling but becomes a severe contention bottleneck under flash-sale load (every request serializes on one row/lock); a common mitigation is reserving stock with a short-lived hold (decrement optimistically with a conditional update, e.g. UPDATE inventory SET stock = stock - 1 WHERE stock > 0, which atomically fails once stock hits zero) combined with a hold/expiry so abandoned checkouts release stock back automatically rather than requiring a background sweep alone. Payment idempotency: every charge request carries a client-generated idempotency key; the payment service persists (key → result) and, on a retried request with the same key (due to a network blip or client retry), returns the original result instead of charging again — this is the direct, concrete application of the idempotency discussion in Chapter 11 to the single most consequence-heavy place it matters. Order saga: checkout spans three independent services (inventory, payment, order) that can't be wrapped in a single ACID transaction because they're separate systems — the Saga pattern (detailed in Chapter 7) sequences them with compensating actions: if payment fails after inventory was reserved, the saga triggers a compensating "release reservation" action; if order creation fails after payment succeeded, the saga triggers a compensating refund. The orchestrator-based saga (a central coordinator explicitly driving each step and its compensation) is generally preferred over a choreography-based saga (each service reacting to the previous one's event) for checkout specifically, because the business logic ("what counts as a successful checkout, and in what order do compensations happen") is complex enough to want centralized visibility rather than being implicit across many independently-reacting services.

      Code Examples

      // Geohash encoding (simplified) — interleaves lat/lng bits to produce a prefix-sortable string
const BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz";
function encodeGeohash(lat: number, lng: number, precision = 8): string {
  let latRange: [number, number] = [-90, 90];
  let lngRange: [number, number] = [-180, 180];
  let isEven = true;
  let bit = 0, ch = 0;
  let hash = "";
  while (hash.length < precision) {
    if (isEven) {
      const mid = (lngRange[0] + lngRange[1]) / 2;
      if (lng > mid) { ch |= (1 << (4 - bit)); lngRange[0] = mid; } else { lngRange[1] = mid; }
    } else {
      const mid = (latRange[0] + latRange[1]) / 2;
      if (lat > mid) { ch |= (1 << (4 - bit)); latRange[0] = mid; } else { latRange[1] = mid; }
    }
    isEven = !isEven;
    if (bit < 4) bit++; else { hash += BASE32[ch]; bit = 0; ch = 0; }
  }
  return hash;
}
// encodeGeohash(37.7749, -122.4194) -> roughly "9q8yyk2z" (San Francisco) — nearby points share prefixes

      // Idempotent payment charge — the core correctness mechanism for case study 7
interface ChargeResult { transactionId: string; status: "succeeded" | "failed"; }
class PaymentService {
  constructor(private db: { getByIdempotencyKey(k: string): Promise<ChargeResult | null>;
                             saveResult(k: string, r: ChargeResult): Promise<void> }) {}

  async charge(amount: number, idempotencyKey: string): Promise<ChargeResult> {
    const existing = await this.db.getByIdempotencyKey(idempotencyKey);
    if (existing) return existing; // retried request — return original result, do NOT charge again

    const result = await this.callPaymentProvider(amount); // real charge happens exactly once
    await this.db.saveResult(idempotencyKey, result);
    return result;
  }
  private async callPaymentProvider(amount: number): Promise<ChargeResult> {
    return { transactionId: crypto.randomUUID(), status: "succeeded" };
  }
}

      Real-World Production Scenario at Scale

      At scale

      A mid-size e-commerce platform ran a flash sale on a limited-edition item (10,000 units) and saw their naive "SELECT stock, then UPDATE if available" checkout flow oversell by 400 units within the first 90 seconds — a classic check-then-act race condition under extreme concurrency, since many requests read the same "stock available" value before any of them had committed their decrement. The fix combined two case-study patterns from this chapter: an atomic conditional decrement (UPDATE inventory SET stock = stock - 1 WHERE item_id = ? AND stock > 0, checked via affected-row-count rather than a separate read) to eliminate the race at the database level, and a short-lived reservation hold (60 seconds) so a user who reserved stock but abandoned checkout didn't permanently lock it away — on expiry, a background job released unconfirmed holds back to available stock. Post-fix, the same sale pattern oversold by zero units while keeping checkout latency under 300ms p99, because the contention was resolved at the database's own atomic-operation level rather than via a slower distributed lock.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Designing fanout-on-write for every account uniformly, without a celebrity-threshold exception — this is the single most common "sounds fine until you do the follower-count math" mistake candidates make in feed design interviews.

      Gotcha

      Treating payment idempotency as "just retry carefully on the client" instead of a server-side guarantee keyed by a client-generated idempotency key — client-side carefulness alone cannot prevent double charges across genuinely independent retry attempts (e.g., a mobile app retry after an ambiguous network timeout where the first request actually succeeded server-side).

      • For every case study, state explicitly which component is CP and which is AP — interviewers want to hear the justification tied to business cost, not a default guess.
      • Always separate "hot path" (needs to be fast, simple, synchronous) from "cold path" (can be async, batched, eventually consistent) within a single system — most of these case studies are really about drawing that line correctly.
      • Quote real numbers (QPS, storage, follower-count skew) even if approximate — a design justified by "because it's a lot of users" is weaker than one justified by "500M DAU times 300 follows means naive fanout averages 150B feed-inserts/day."

      Interview Questions

      Basic

      Why would a URL shortener prefer a counter + base62 encoding over hashing the long URL?

      Counter-based IDs are collision-free by construction, avoiding the need to detect and retry on hash collisions; hashing requires a collision-check-and-retry step on every write.

      Why does a chat app use WebSockets instead of HTTP polling?

      Polling at a scale of tens of thousands of messages/sec would require constant request overhead and still introduce latency equal to the poll interval; WebSockets give a persistent bidirectional connection enabling true low-latency push delivery.

      What is the "celebrity problem" in news feed design?

      A small number of accounts with extremely high follower counts make fanout-on-write prohibitively expensive for their posts (millions of feed-insert operations per post), requiring a different strategy (fanout-on-read) specifically for those accounts.

      Why does Dropbox-style file storage split metadata from blob storage?

      Metadata is small and needs strong consistency/transactional semantics; blob data is enormous and needs cheap, horizontally-scalable object storage — the two have fundamentally different scaling and consistency requirements.

      What does an idempotency key prevent in a payment flow?

      It prevents a retried charge request (due to network blips or client retry logic) from actually charging the customer twice, by letting the server recognize the retry and return the original result instead of processing a new charge.

      Why is a geohash's prefix property useful for finding nearby drivers?

      Nearby locations tend to share string prefixes, so a range/prefix query on sorted geohash strings efficiently returns points in roughly the same area without scanning the whole dataset.

      Medium

      Design the reservation-hold mechanism for flash-sale inventory and explain what happens if the hold expires mid-checkout.

      On "add to checkout," atomically decrement available stock and create a reservation row with an expiry (e.g., 60-120s). If the user completes payment before expiry, convert the reservation to a confirmed order. If it expires first, a background sweep (or lazy check on next access) releases the held stock back to available — if the user's payment then succeeds after expiry, the saga's compensating action must handle the now-invalid reservation (refund and apologize, or attempt re-reservation if stock still exists).

      Why might a chat app's group fanout threshold differ from a news feed's celebrity threshold?

      Chat fanout targets must all receive the message in near-real-time with delivery guarantees (it's a conversation), so even moderately large groups may still warrant push-based fanout up to a higher member count than you'd tolerate for feed fanout, where feed consumers tolerate eventual/pull-based delivery much more readily; the exact threshold is a product decision balancing latency needs against fanout cost for each system separately.

      How would you detect and handle a corrupted/incomplete file chunk in the Dropbox-style dedup design?

      Verify the uploaded chunk's bytes against its claimed content hash server-side before registering it in the blocks table (reject on mismatch); since blocks are reference-counted and shared, never allow a client to overwrite an existing hash's stored bytes — a hash collision or corruption must be treated as upload failure, not an in-place fix, to protect every other file referencing that block.

      In the ride-booking case study, why is driver location data eventually consistent rather than strongly consistent, and what would strong consistency cost here?

      Strong consistency would require synchronizing every driver's position across all replicas/services before any read, adding significant latency and coordination overhead for data that's inherently stale within seconds anyway (drivers keep moving) — the business cost of a few seconds of staleness is negligible compared to the latency cost of strict consistency, so PACELC's Else-Latency choice is the right one.

      Why does the e-commerce case study use an orchestrator-based saga rather than choreography?

      Checkout's compensation logic (what to do if payment fails after inventory reservation, what to do if order creation fails after payment) is complex enough that centralizing the sequencing and failure handling in one orchestrator keeps the business logic visible and testable in one place, versus choreography's implicit cross-service event reactions which get harder to reason about as the number of compensating cases grows.

      Advanced

      Design a hybrid fanout threshold policy for news feed that adapts dynamically rather than using a single fixed follower-count cutoff.

      Instead of a static threshold, factor in posting frequency (a celebrity who posts rarely is cheaper to fanout-on-write despite high follower count) and follower activity (fanning out to followers who haven't opened the app in weeks wastes writes) — a dynamic score combining follower count × posting frequency × follower activity rate can decide per-account whether to eagerly fan out, with a periodic re-evaluation as these factors change, rather than a single fixed number chosen once.

      How would you extend the URL shortener's design to support analytics (click counts, referrer tracking) without adding write latency to the redirect path?

      Log the redirect event to an async queue immediately after serving the 302 (fire-and-forget from the redirect's perspective — the user's redirect isn't blocked waiting for analytics to persist), and have a separate consumer aggregate click counts/referrer data into an analytics store; this keeps the hot redirect path's latency unaffected by analytics write volume or any analytics-store slowness.

      In the ride-booking system, how would you handle a region boundary problem where a rider and the nearest available driver are geographically close but fall into different geospatial shard partitions?

      Query not just the rider's own shard/cell but also neighboring cells (a standard geohash/H3 technique — check the 8 neighboring cells around the rider's cell in addition to the rider's own cell) before considering the match complete; this adds a small constant number of extra lookups but correctly handles drivers just across a partition boundary.

      Critique the saga pattern's weakness in the e-commerce checkout case: what happens if a compensating action itself fails (e.g., the refund call to the payment provider times out)?

      Compensating actions must themselves be retried with their own idempotency guarantees and backoff, and if they persistently fail, the saga needs a dead-letter/manual-intervention path rather than silently giving up — this is why production saga implementations track saga state explicitly (e.g., "compensation pending," "compensation failed — needs ops review") rather than assuming compensations always succeed on the first attempt.

      How would the notification system's design change if a single event needed to notify 50M users within a 2-minute SLA (e.g., a critical security alert)?

      This requires massively parallelizing the fanout worker pool (horizontal scale-out proportional to the volume/SLA, likely with dedicated capacity reserved for this priority class) and prioritizing this event ahead of routine notification traffic in the queue (priority queues or a separate high-priority topic), while accepting that per-channel provider rate limits (SMS/push providers' own caps) may become the hard bottleneck regardless of your own infrastructure capacity — at that point the design conversation shifts to negotiating higher rate limits with providers or using multiple provider accounts/providers in parallel to fan the load out across independent rate-limit buckets.

      Practice Assignments

      Beginner (30-60 min)

      Capacity estimation for a polling/voting system

      Design is not required — just do the capacity math (QPS, storage) for a real-time polling system (like Twitter polls) with 20M DAU where 5% of users vote on an average of 3 polls/day, each vote being a tiny (50 byte) write, with a 5x peak multiplier around major live events.

      • State average and peak QPS, and yearly storage.
      • State one architectural implication (e.g., does this need sharding, or is it small enough for a single well-indexed table with a cache in front?).

      Acceptance criteria: Correct arithmetic and a one-sentence architectural takeaway.

      Hints (direction only, not a full solution)

      Research Operational Transform (OT) and CRDTs (Conflict-free Replicated Data Types) as the two dominant approaches — OT requires a central server to sequence operations, CRDTs allow fully peer-to-peer merge without a central sequencer but have higher per-edit metadata overhead. The live-editing path favors availability/low-latency (AP/EL); the periodic persisted-save path can afford to be strongly consistent since it's infrequent and not on the interactive critical path.

      Quick Revision Cheat Sheet

      • URL shortener: counter + base62 avoids collisions; hashing needs collision-check-and-retry. Cache hot redirects aggressively, even at CDN edge.
      • Chat: WebSockets for push delivery; per-conversation sequence numbers for ordering, not wall-clock time; presence registry maps user → gateway server.
      • Notifications: always async via queue; per-channel/provider rate limiting is mandatory, not optional, because providers enforce their own hard caps.
      • News feed: fanout-on-write for normal accounts, fanout-on-read for celebrities/high-follower accounts — hybrid by threshold, not a single global strategy.
      • File storage: content-hash dedup + content-defined chunking; split metadata (strong consistency, small) from blobs (cheap object storage, huge).
      • Ride booking: geohash/quadtree/H3 for spatial indexing, sharded regionally; location data is intentionally eventually consistent (PACELC Latency choice).
      • E-commerce checkout: atomic conditional inventory decrement + reservation hold prevents overselling under contention; idempotency keys prevent double charges; Saga pattern (orchestrator-based) sequences cross-service steps with compensations.
      • Every case study's real test: identify the hot path vs cold path, and the one tradeoff (fanout strategy, consistency model, indexing structure) that defines the system.
