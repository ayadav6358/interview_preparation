    System Design

    📚 14 chapters⏱ ~28–34 hrs total

    The single most important topic for Senior/Tech Lead interviews. Covers the fundamentals (scalability, CAP), the building blocks (networking, load balancers, caching, databases, queues), architecture (microservices, API design, resilience), LLD (SOLID, design patterns), and full HLD case studies with a repeatable interview framework.

    Learning Outcomes

    • Reason about latency, throughput, availability and consistency tradeoffs with real numbers.
    • Design a system end-to-end in 35–45 minutes using a repeatable framework and back-of-envelope math.
    • Pick the right database, caching strategy, and messaging pattern for a given access pattern.
    • Apply SOLID and classic design patterns to keep a codebase maintainable at scale.
    • Explain and defend tradeoffs (not just name technologies) under interviewer pushback.

    🏆 Capstone Project: Design & Partially Build a "Scalable Notification Platform"

    Problem statement: Design a notification platform (email, push, SMS, in-app) that can send 50M notifications/day, supports templating, per-user rate limits, delivery retries, and user preference management, with an admin dashboard for campaign stats.

    Required features:

    • Ingestion API that accepts notification requests and queues them (idempotent on a client-supplied request ID).
    • Fan-out worker pool consuming from a queue, respecting per-channel rate limits (e.g., SMS provider limits).
    • Retry with exponential backoff + dead-letter queue for permanently failed sends.
    • User preference service (opt-outs, quiet hours, channel priority).
    • Delivery status tracking (queued → sent → delivered/failed) exposed via a status API.
    • Basic caching layer for template rendering and user preference lookups.

    Tech stack suggestion: Node.js (Fastify) + TypeScript, Redis (rate limiting + cache), Kafka or BullMQ (queue), Postgres (status + preferences), Docker Compose for local dev.

    Milestones:

    1. Write the HLD doc: capacity estimation, API contracts, data model, component diagram (Mermaid).
    2. Build ingestion API + queue producer with idempotency keys.
    3. Build worker consumer with retry/backoff + dead-letter queue.
    4. Add rate limiting per channel (token bucket in Redis) and preference checks.
    5. Add status tracking API and a minimal dashboard (counts by status).
    6. Load-test with a script simulating 10k requests/min; document bottlenecks found and fixed.

    Evaluation checklist:

    • ☐ Can explain every component's purpose and what breaks if it's removed.
    • ☐ Capacity math is written down and matches the architecture (queue partitions, worker count).
    • ☐ Idempotency actually prevents duplicate sends under retry.
    • ☐ System degrades gracefully when a downstream provider (e.g., SMS) is slow/down.
    • ☐ Can defend at least 2 alternative designs you rejected, and why.
