    Networking Basics: DNS, HTTP/1.1 vs 2 vs 3, TCP vs UDP, WebSockets vs SSE

    ⏱ 2.5 hrs📍 Chapter 2 of 14

    One-line summary: Every system design diagram has arrows between boxes — those arrows are real protocols with real latency and failure costs, and a senior engineer must know what happens on the wire before claiming a design "will be fast" or "will scale."

    On this page

      Why It Matters for a Senior Developer

      You've built REST APIs and maybe a WebSocket chat feature, but interviewers at Staff/Tech Lead level probe whether you understand why a design choice works — "why did you pick HTTP/2 here," "why not just poll every second," "why does this mobile app feel slow on 4G but fine on wifi." Those questions are answered at the transport and application-protocol layer, not the business logic layer. This chapter gives you the vocabulary to reason about connection setup cost, head-of-line blocking, and the real tradeoffs between push-based and pull-based communication — concepts that resurface in load balancing (Chapter 3), caching (Chapter 4), and every HLD case study (Chapter 13).

      Prerequisites

      Read Fundamentals first — latency/throughput vocabulary and the tail-at-scale problem are used throughout this chapter. This chapter feeds directly into Load Balancing & Reverse Proxies, where these protocols get distributed across many servers.

      Core Concepts

      DNS resolution: recursive vs authoritative, TTL, caching

      DNS translates a hostname into an IP address through a chain of lookups. When your laptop resolves api.example.com, it typically asks a recursive resolver (your ISP's, or a public one like 8.8.8.8 / 1.1.1.1) to do the full chain on its behalf: root servers → TLD servers (.com) → the domain's authoritative nameserver, which holds the actual records. The recursive resolver caches the answer according to the record's TTL (time-to-live, in seconds) so subsequent lookups from other clients don't repeat the chain.

      Authoritative servers are the source of truth for a zone — they answer definitively, not from cache. A recursive resolver is a middleman that caches to save round trips; it never "owns" the data.

      TTL tradeoffs: a low TTL (e.g., 30–60s) lets you redirect traffic quickly (useful for blue-green deploys, failover, or canary rollouts) but increases load on authoritative servers and adds resolution latency variance since caches expire often. A high TTL (hours/days) is cheap and fast but means a bad record change (or a failover) takes a long time to propagate — this is why many outage postmortems mention "stale DNS cached on client devices" as an amplifying factor. Senior-level practice: lower your TTL *before* a planned migration, wait for the old TTL to fully expire everywhere, then cut over.

      DNS caching layers stack: browser DNS cache → OS resolver cache → router → ISP recursive resolver → authoritative. A `dig` or `nslookup` from your laptop often returns a cached answer that's several hops removed from the authoritative truth, which is why "I updated the DNS record and it's not working" is almost always a caching/TTL issue, not a propagation failure.

      HTTP/1.1 vs HTTP/2 vs HTTP/3

      HTTP/1.1 is text-based, one request per TCP connection waits for its response before the next can be sent on that connection (unless you open multiple parallel TCP connections — browsers historically capped this at 6 per host). This causes head-of-line (HOL) blocking at the application layer: a slow response blocks everything queued behind it on that connection.

      HTTP/2 introduces multiplexing: a single TCP connection carries multiple concurrent "streams," each request/response broken into frames that interleave on the wire. This removes application-layer HOL blocking — many requests are genuinely in flight on one connection. It also adds HPACK header compression (headers are repetitive across requests — cookies, user-agent — so HPACK maintains a shared compression table between client and server rather than re-sending full header text every time) and binary framing instead of text parsing. Server push (server proactively sends resources it predicts the client needs) was part of HTTP/2 but is now deprecated/removed from Chrome and most browsers — in practice it caused cache-coherency problems and was rarely a net win over simply inlining critical resources or using ``.

      HTTP/2's remaining weakness: it still multiplexes over a single TCP connection, so if a single TCP packet is lost, TCP's in-order delivery guarantee blocks *all* streams until that packet is retransmitted — this is transport-layer HOL blocking, and HTTP/2 cannot fix it because it's baked into TCP itself.

      HTTP/3 solves this by replacing TCP with QUIC, a transport protocol built on top of UDP. QUIC implements its own reliability and congestion control per-stream, so a lost packet on one stream only blocks that stream, not the others — true elimination of HOL blocking at both layers. QUIC also supports 0-RTT connection resumption: if a client has previously connected to a server, it can cache cryptographic parameters and send application data on the very first packet of a reconnection, skipping the handshake round trip entirely (with some replay-attack caveats that limit which requests are safe to send 0-RTT, e.g., only idempotent ones). Because QUIC is UDP-based, middleboxes/firewalls that don't understand it can block or throttle it, which is why HTTP/3 deployments always fall back to HTTP/2 gracefully (advertised via the `Alt-Svc` header).

      TCP vs UDP, and when UDP wins

      TCP is connection-oriented and reliable: it guarantees ordered, complete delivery via the three-way handshake (SYN → SYN-ACK → ACK) to establish a connection, sequence numbers to reorder/detect loss, and retransmission on missing ACKs. Congestion control (e.g., TCP Cubic, BBR) ramps the send rate up slowly (slow start), backs off sharply on detected loss, and probes for available bandwidth continuously — this is why a fresh TCP connection on a high-latency link takes a few round trips before it reaches full throughput ("TCP slow start penalty"), a real cost for short-lived connections.

      UDP is connectionless and makes no delivery guarantees — no handshake, no retransmission, no ordering. UDP wins when: (1) you need minimum latency and can tolerate loss (live video/audio, multiplayer game state — a dropped frame is better than waiting for a retransmit of a now-stale frame); (2) you're building your own reliability semantics tuned to your use case (QUIC does exactly this — it's UDP with custom reliability on top, giving more control than TCP's one-size-fits-all); (3) simple request-response where the cost of retry-at-the-application-layer is cheaper than a stateful connection (DNS queries are UDP for this reason, falling back to TCP only for large responses).

      Senior framing: "TCP vs UDP" is really "do you need the kernel's generic reliability, or do you need custom reliability tuned to your data's actual tolerance for loss/reordering." QUIC is proof that the answer is increasingly "build custom reliability on UDP."

      WebSockets vs SSE vs long-polling

      Long-polling: client sends a request, server holds it open until there's data (or a timeout), responds, client immediately re-requests. Simple, works over plain HTTP/infra everyone already supports, but each cycle pays connection/header overhead and there's inherent latency between a timeout-close and the next request.

      Server-Sent Events (SSE): a single long-lived HTTP connection where the server streams a sequence of text events (`text/event-stream`) to the client; it's one-way (server → client only). Built-in auto-reconnect with a `Last-Event-ID` header lets the client resume from where it left off after a drop — this is handled natively by `EventSource` in the browser, no custom reconnection logic needed. Infra-wise, SSE is just HTTP — it works through standard proxies, load balancers, and CDNs without special configuration, which is a huge operational win over WebSockets.

      WebSockets: start as an HTTP request with an `Upgrade: websocket` header; the server responds `101 Switching Protocols` and from then on the same TCP connection carries a different framing protocol entirely — full-duplex, either side can send at any time, binary or text. Needed when the client must push frequent data to the server too (chat, collaborative editing, multiplayer) — SSE/long-polling can't do that without a second channel. Cost: WebSocket connections are stateful and sticky, don't play as nicely with plain HTTP load balancers (need L4/L7 awareness, see Chapter 3), and don't automatically reconnect — you must implement your own backoff/retry and resume logic.

      Decision rule: need bidirectional, high-frequency, low-latency → WebSockets. Need server-to-client streaming only (notifications, live scores, LLM token streaming) → SSE, simpler infra wins. Need occasional updates and can't use either (old infra, strict corporate proxies) → long-polling as the fallback.

      How It Works Under the Hood

      Before any HTTP request flows, three things typically happen in sequence for a fresh HTTPS connection: DNS resolution, TCP three-way handshake, then TLS handshake (certificate exchange + key agreement). On a cold connection with TLS 1.2 this is 3 full round trips before the first byte of actual data moves; TLS 1.3 cuts this to effectively 1-RTT (and QUIC/HTTP3's 0-RTT resumption can cut it further on reconnect). This is why connection reuse (HTTP keep-alive, HTTP/2 multiplexing over one connection) matters so much at scale — paying the handshake cost once and amortizing it over many requests beats paying it per-request.

      For HTTP/2's multiplexing specifically: the server assigns each request a stream ID, breaks the response into frames tagged with that stream ID, and interleaves frames from different streams on the wire. The client's HTTP/2 layer reassembles frames by stream ID. This is why one slow backend response doesn't block a fast one on the same connection — they're genuinely concurrent at the framing level, not just logically concurrent.

      Code Examples

      SSE server (Node/Express) with reconnect-friendly event IDs, vs a naive WebSocket server for comparison:

      // SSE endpoint — simple, one-way, auto-reconnect handled by the browser's EventSource
import { Request, Response } from "express";

let lastEventId = 0;

export function sseHandler(req: Request, res: Response) {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("Connection", "keep-alive");

  // Resume support: client sends Last-Event-ID header after a dropped connection
  const resumeFrom = Number(req.headers["last-event-id"] ?? 0);
  console.log(`client resuming from event ${resumeFrom}`);

  const interval = setInterval(() => {
    lastEventId++;
    const payload = JSON.stringify({ price: (Math.random() * 100).toFixed(2) });
    // id: field is what enables auto-resume — EventSource tracks it automatically
    res.write(`id: ${lastEventId}\ndata: ${payload}\n\n`);
  }, 1000);

  req.on("close", () => clearInterval(interval));
}

      Real-World Production Scenario at Scale

      At scale

      A trading dashboard streaming live prices to 200,000 concurrent browser tabs initially used WebSockets for "future-proofing," even though data only flows server→client. At that scale, WebSocket connections required sticky sessions at the load balancer (each connection pinned to one backend instance for its lifetime), which made rolling deploys painful — every deploy had to either forcibly drop connections (causing a visible reconnect storm) or wait out long-lived connections before rotating instances. Switching to SSE let the team drop sticky-session requirements (SSE still benefits from affinity but tolerates reconnects to a different instance gracefully via Last-Event-ID), simplified the load balancer config to standard HTTP/2 multiplexing, and let CDN edge nodes terminate and buffer-forward the stream in some regions — something that doesn't work cleanly with WebSockets. The lesson: don't reach for full-duplex infrastructure complexity when your actual data flow is one-way.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Assuming HTTP/2 multiplexing eliminates all head-of-line blocking. It only fixes the application-layer HOL blocking; a single lost TCP packet still blocks every stream on that connection until retransmitted — only HTTP/3 (QUIC/UDP) fixes transport-layer HOL blocking.

      Gotcha

      Setting a DNS TTL of several hours "for performance" right before a planned migration, then being surprised that a meaningful fraction of traffic is still hitting the old IP a day later. Lower TTL well ahead of any planned cutover.

      • Reuse connections aggressively (HTTP keep-alive, connection pooling) — the handshake + TLS cost dwarfs most individual request processing time on fast endpoints.
      • Default to SSE over WebSockets unless you specifically need client→server push on the same channel — simpler infra, automatic reconnect, works through existing proxies.
      • Don't treat UDP as "unreliable and therefore unusable" — QUIC/HTTP3 proves custom reliability on UDP can beat generic TCP reliability for web traffic.

      Interview Questions

      Basic

      What's the difference between a recursive resolver and an authoritative nameserver?

      The recursive resolver does the lookup chain on the client's behalf and caches results by TTL. The authoritative nameserver is the source of truth for a domain's records and answers definitively, not from cache.

      What problem does HTTP/2 multiplexing solve?

      It removes application-layer head-of-line blocking by letting multiple request/response streams share one TCP connection concurrently, instead of HTTP/1.1's one-at-a-time-per-connection model.

      What does the TCP three-way handshake accomplish?

      It synchronizes initial sequence numbers and confirms both sides can send and receive before any application data is exchanged: SYN, SYN-ACK, ACK.

      Name one scenario where UDP is preferable to TCP.

      Live video/audio or multiplayer game state, where a dropped packet is better handled by skipping to the next update than waiting for retransmission of now-stale data.

      What is SSE and how does it differ from a WebSocket?

      SSE is a one-way, server-to-client stream over a plain long-lived HTTP connection with built-in auto-reconnect. WebSockets are full-duplex and require custom reconnect logic but allow the client to push too.

      What is DNS TTL and what's the tradeoff of setting it very low?

      TTL is how long a resolver may cache a record. Low TTL enables fast failover/cutover but increases load on authoritative servers and adds resolution overhead since caches expire frequently.

      What HTTP header initiates a WebSocket connection?

      The client sends `Upgrade: websocket` (with `Connection: Upgrade`); the server responds `101 Switching Protocols` and the same TCP connection switches framing protocols.

      Medium

      Explain why HTTP/2 doesn't fully eliminate head-of-line blocking, and what does.

      HTTP/2 multiplexes at the application layer, but all streams still ride one TCP connection; a lost packet forces TCP to block all streams until retransmission (transport-layer HOL blocking). HTTP/3's QUIC, built on UDP with independent per-stream reliability, eliminates this because loss on one stream doesn't block others.

      Follow-up: why can't you just fix this by patching TCP itself?
      What is HPACK and why does it matter at scale?

      HPACK is HTTP/2's header compression scheme using a shared dynamic table between client and server so repetitive header fields (cookies, user-agent) aren't fully retransmitted on every request. At scale with many small requests, header overhead can dominate payload size, so this meaningfully reduces bandwidth and latency.

      Why is QUIC's 0-RTT resumption powerful, and what's the security caveat?

      A returning client can send encrypted application data on the very first packet by reusing cached session parameters from a prior connection, skipping a full round trip. The caveat is replay risk — an attacker could resend the captured 0-RTT packet — so 0-RTT is generally limited to idempotent requests.

      Why do WebSocket deployments typically need sticky sessions at the load balancer, and what operational problem does that cause?

      A WebSocket connection is long-lived and stateful, pinned to one backend instance for its duration. This complicates rolling deploys/autoscaling since you either forcibly drop connections (reconnect storm) or must drain slowly, unlike stateless HTTP requests that any instance can serve.

      Why does TCP slow start matter for short-lived connections specifically?

      TCP ramps send rate up gradually over several round trips before reaching full available bandwidth. A connection that only lasts a few requests never gets to amortize past this ramp-up, so connection reuse (keep-alive, multiplexing) matters disproportionately for latency-sensitive, short-request workloads.

      Why might a mobile app see worse performance on HTTP/2 than HTTP/3 on a lossy cellular network?

      Packet loss is more common on cellular networks; with HTTP/2's single TCP connection, any loss blocks all multiplexed streams until retransmit. HTTP/3's QUIC isolates loss to the affected stream, so the rest of the page's requests keep flowing.

      Advanced

      Design the real-time layer for a live-auction platform where bids must be pushed to all watchers within 200ms and bidders must also submit bids over the same low-latency channel. Justify WebSockets vs SSE vs polling.

      WebSockets, because bidders need low-latency client→server push (placing a bid) and all watchers need low-latency server→client push (updated price) — a genuinely bidirectional, high-frequency requirement that SSE can't satisfy on one channel. Mitigate the sticky-session/deploy pain with a pub-sub backplane (e.g., Redis) so any instance can broadcast bid updates regardless of which instance holds which connection, and implement explicit client-side reconnect-with-backoff plus a sequence number so a reconnecting client can detect and request missed updates.

      A CDN wants to cache and accelerate SSE streams at the edge. What makes this hard compared to caching ordinary HTTP responses, and how could it still be done partially?

      SSE responses never "complete" — there's no final Content-Length, so traditional whole-response caching doesn't apply. Partial acceleration is possible by having edge nodes terminate the TCP/TLS connection to the client and act as a fan-out proxy, maintaining one upstream connection to origin and streaming the same event sequence to many downstream clients — effectively a pub-sub relay rather than a cache in the traditional sense.

      Why does QUIC implement congestion control and loss recovery itself instead of relying on the kernel's TCP stack, and what does this enable?

      Building reliability in userspace (as part of the QUIC library) rather than the OS kernel's TCP stack means protocol improvements can ship with application/library updates instead of waiting on OS kernel upgrades across billions of devices. It also enables QUIC to multiplex independent streams with independent loss recovery, something impossible with TCP's single ordered byte stream.

      Your API gateway terminates TLS and speaks HTTP/2 to clients but HTTP/1.1 to backend services. What problem could this architecture introduce, and how would you detect it?

      The gateway must demultiplex HTTP/2 streams into separate HTTP/1.1 connections (or a connection pool) to backends — if the pool is undersized relative to concurrent multiplexed streams, requests queue at the gateway even though the client-facing connection looks fully parallel, creating a hidden bottleneck. Detect it via backend connection pool saturation metrics and comparing client-observed latency to backend-observed latency for the same request.

      Explain why lowering DNS TTL alone is not sufficient to guarantee fast failover, and what else is required.

      Many resolvers and client OS/browser caches don't strictly honor TTL (some apply minimums, some cache longer for performance), and some clients cache a resolved connection itself (keep-alive) independent of DNS, so they keep talking to an old IP even after DNS changes. Fast failover needs client-side retry/circuit-breaker logic, short-lived connections, or a layer (e.g., anycast IP, load balancer VIP) that doesn't require DNS propagation at all.

      Practice Assignments

      Beginner (30-60 min)

      Measure the handshake cost

      Using your browser's DevTools Network tab, load a page over HTTPS and inspect the timing breakdown (DNS lookup, initial connection, TLS, waiting/TTFB) for the first request to a new host versus a subsequent request on a reused connection.

      • Record both timing breakdowns.
      • Explain in 2-3 sentences why the second request's connection-related phases are near zero.

      Acceptance criteria: Actual captured timings with a correct explanation referencing connection reuse.

      Hints

      Look at the "Connection," "SSL," and "TTFB" rows in Chrome DevTools' waterfall view; compare the very first request to the host against a later one.

      Bonus: Repeat on a page served over HTTP/2 vs one still on HTTP/1.1 and compare how many connections the browser opens to the same host.

      Intermediate (2-4 hrs)

      Build an SSE price ticker with resume support

      Implement the SSE server from the Code Examples section (or similar) that streams incrementing events with IDs, plus a simple HTML page using `EventSource`. Kill the server mid-stream, restart it, and verify the client resumes correctly using `Last-Event-ID`.

      • Demonstrate the resume behavior with logs showing the server reading the `Last-Event-ID` header.
      • Explain what would break if you used long-polling instead for this use case at 10,000 concurrent clients.

      Acceptance criteria: Working resume demo plus a written comparison against long-polling at scale.

      Hints

      You'll need to persist a small ring buffer of recent events server-side keyed by ID so a resuming client can be replayed events it missed, not just future ones.

      Bonus: Add a Redis pub-sub backplane so the SSE endpoint can be served by multiple horizontally-scaled instances.

      Advanced (1-2 days)

      Design the real-time layer for a multiplayer collaborative whiteboard

      50 users can simultaneously draw on a shared canvas; every stroke from any user must appear on every other user's screen within ~100ms. Design the protocol choice, connection topology, and conflict/ordering strategy.

      • Justify your transport choice (WebSockets vs SSE vs something else) given the bidirectional, high-frequency requirement.
      • Address what happens when a user's connection drops mid-stroke and reconnects — how do they catch up without replaying the entire drawing history?
      • Address horizontal scaling: if whiteboard sessions are sharded across multiple server instances, how do strokes from a user on instance A reach a user on instance B watching the same board?

      Acceptance criteria: A written design covering transport choice, reconnect/catch-up strategy, and cross-instance fan-out, with explicit tradeoffs stated for each decision.

      Hints

      Think WebSockets for the bidirectional low-latency stroke stream, a periodic snapshot/checkpoint of canvas state so a reconnecting client only needs the latest snapshot plus strokes since, and a pub-sub backplane (Redis/Kafka) keyed by board ID so any instance can broadcast to all connections subscribed to that board regardless of which instance holds them.

      Bonus: How would you handle two users drawing conflicting strokes in the exact same region at nearly the same time — does ordering matter, and how would you guarantee consistent ordering across instances?

      Quick Revision Cheat Sheet

      • DNS: recursive resolvers cache by TTL; authoritative servers are the source of truth. Lower TTL before planned cutovers.
      • HTTP/1.1: one request in flight per connection (serial). HTTP/2: multiplexed streams over one TCP connection, plus HPACK header compression.
      • HTTP/2 still has transport-layer HOL blocking because it rides one TCP connection — a lost packet blocks all streams.
      • HTTP/3 (QUIC over UDP) eliminates transport-layer HOL blocking with independent per-stream reliability, and supports 0-RTT resumption.
      • Server push (HTTP/2) is deprecated — use preload hints or inline critical resources instead.
      • TCP = reliable, ordered, handshake + congestion control overhead. UDP = no guarantees, minimal overhead — wins for loss-tolerant, latency-sensitive data.
      • WebSockets: full-duplex, no built-in reconnect, sticky-session friction. SSE: one-way, built-in auto-reconnect via Last-Event-ID, plain-HTTP-friendly infra.
      • Default to SSE unless you truly need client→server push on the same channel.
      • A fresh HTTPS connection pays DNS + TCP handshake + TLS handshake before any data — reuse connections to amortize this cost.
