    Next.js App Router, Layouts, Routing, Middleware

    ⏱ 2.5 hrs📍 Chapter 6 of 11

    One-line summary: The App Router is a file-system router built directly on React Server Components and Suspense — every folder is a route segment, every layout.js wraps its children persistently across navigations, and the routing tree itself determines what streams and what stays static.

    On this page

      Why It Matters for a Senior Developer

      Most teams migrating from Pages Router or CRA get the mental model wrong in the same few places: treating layouts like Pages Router's _app.js, not understanding why state resets across route changes, and misusing middleware for things that belong in a layout or Server Component. This chapter is what interviewers probe when they ask you to design routing for a real app.

      Prerequisites

      Read Concurrent React first (streaming/Suspense). Related: Server vs Client Components, Rendering Strategies.

      Core Concepts

      File-system routing conventions

      • app/dashboard/page.js → route /dashboard, the leaf UI for that segment.
      • layout.js → wraps the segment and all its children; persists across navigations within it (its React state is not remounted when a nested page changes).
      • loading.js → an automatic Suspense boundary + fallback around the segment's page.js (and everything below it) while it streams in.
      • error.js → an automatic Error Boundary for the segment (must be a Client Component).
      • template.js → like layout, but remounts (fresh state, re-run effects) on every navigation — useful for enter/exit animations.
      • route.js → a Route Handler (API endpoint) for that path, replacing Pages Router's pages/api.
      • (groupName) → a route group: organizes files without affecting the URL path.
      • [id], [...slug], [[...slug]] → dynamic, catch-all, and optional catch-all segments.
      • @slotName → a parallel route slot, rendered alongside siblings in the same layout (e.g., a modal slot rendered next to the main content).

      Why layouts don't remount on navigation

      The App Router keeps a persistent in-memory tree of the currently rendered route segments on the client. When you navigate to a sibling route that shares a layout, Next.js only re-renders the changed segment's subtree — the shared layout's React component instance, and therefore its state (open sidebar, scroll position, a mounted WebSocket), survives untouched. This matches exactly how React's own reconciliation works (Ch. 1): same component type/position in the tree → fiber reused, not torn down.

      Middleware: edge-level request interception

      middleware.js at the project root runs on every matching request before routing resolves, in an Edge runtime (a restricted V8-isolate environment, not full Node.js — no filesystem access, limited APIs). Common uses: auth-gate redirects based on a cookie, A/B test bucket assignment via a rewritten URL, locale detection/redirect, and request header injection. It should stay fast and side-effect-light — it runs on the hot path of every request matching its matcher config.

      Parallel and intercepting routes

      Parallel routes (@slot folders) let a layout render multiple independent, simultaneously resolving subtrees — e.g., a dashboard's main feed plus a sidebar panel that load/stream independently, each with its own loading.js. Intercepting routes ((.)folder, (..)folder syntax) let a navigation "intercept" and render a route inside a modal overlay (e.g., clicking a photo opens it in a modal, but a hard refresh or direct link to that URL renders the full dedicated page) — the classic Instagram-style photo-modal pattern, now natively supported.

      How It Works Under the Hood

      On first load, the server renders the full route's React tree (Server Components resolved, Client Component boundaries serialized as placeholders — see Ch. 7) and streams HTML. On subsequent client-side navigations, Next.js's router doesn't re-fetch/re-render the whole page — it requests only the RSC payload (a serialized description of the new segment's tree, not HTML) for the segments that actually changed, diffs it against the client's in-memory route tree, and patches just that portion, re-using the unaffected layout instances. This is why App Router navigations feel like an SPA (no full page reload, state preserved in shared layouts) while still being built on server rendering for each segment's content.

// middleware.ts — auth gate + header injection at the edge
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const token = request.cookies.get("session")?.value;
  if (!token && request.nextUrl.pathname.startsWith("/dashboard")) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  const response = NextResponse.next();
  response.headers.set("x-request-id", crypto.randomUUID());
  return response;
}

      Real-World Production Scenario at Scale

      At scale

      A SaaS dashboard's sidebar navigation re-mounted (losing scroll position and a live WebSocket connection) on every page change because the team had accidentally used template.js instead of layout.js for the shell (copy-pasted from an animation example), not realizing template.js's entire point is to remount on every navigation. Switching to layout.js fixed state persistence immediately; a separate, narrower template.js was reintroduced only around the specific page-transition-animation wrapper that actually needed remount-per-navigation semantics.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Route groups (marketing)/(app) are invisible in the URL — engineers new to App Router sometimes expect app/(marketing)/about/page.js to serve /marketing/about when it actually serves /about. Use route groups purely for file organization and to apply different root layouts to different sections, not as URL namespacing.

      • Putting heavy/slow logic in middleware — it runs on every matching request in a constrained Edge runtime, and slow middleware adds latency to every navigation.
      • Using template.js by default — most shells want persistence, which is layout.js's job.
      • Forgetting that error.js must be a Client Component (`"use client"`) since it needs interactivity (`reset()`) and error boundaries are a client-only React feature.
      • Not scoping middleware's matcher — an unscoped middleware runs on every single request including static assets, adding needless overhead.

      Interview Questions

      Basic

      What's the difference between layout.js and page.js?

      page.js is the actual UI for a route segment (the leaf). layout.js wraps that page (and any nested segments) and persists across navigations within its scope.

      Follow-up: Can a route have a layout.js but no page.js?
      What does loading.js do automatically?

      Wraps the segment's page in a Suspense boundary and uses loading.js's export as the fallback while the segment streams in, without you writing Suspense manually.

      Follow-up: Does loading.js apply to nested child segments too?
      What is middleware and where does it run?

      Code in middleware.js that runs on every matching request before routing resolves, in a restricted Edge runtime — commonly used for auth redirects, locale detection, and header injection.

      Follow-up: Can middleware access a database directly?
      What is a route group, syntactically, and what's its purpose?

      A folder named in parentheses, e.g. `(marketing)`, that organizes files without adding a segment to the URL — used to apply different layouts to different sections or just for organization.

      Follow-up: Does it change the URL path at all?
      What's the difference between layout.js and template.js?

      layout.js persists its component instance (and state) across nested navigations; template.js creates a new instance on every navigation, remounting and re-running effects each time.

      Follow-up: Give a use case where template.js is actually the right choice.

      Medium

      Explain exactly why a shared layout's state survives a navigation to a sibling route, down to what Next.js actually does on the client.

      The router maintains an in-memory tree of currently-rendered segments. Navigating to a sibling that shares an ancestor layout only fetches/re-renders the RSC payload for the segments below the shared layout; the layout's own React component instance in the tree is never unmounted, so its fiber (and therefore its state) is reused exactly as React would reuse a fiber for a same-type, same-position element during normal reconciliation.

      Follow-up: What would force the layout to remount despite this — what change would make it a "different" layout instance to React?
      Design the routing structure for a photo-sharing app where clicking a thumbnail opens a lightbox modal, but sharing the lightbox's URL directly loads a full dedicated page.

      Use an intercepting route: `app/feed/@modal/(.)photo/[id]/page.js` intercepts navigation to `/photo/[id]` when navigated to *from within* the feed route, rendering it in a parallel `@modal` slot as an overlay; a direct/hard-navigation to `/photo/[id]` (no client-side intercept context) renders the plain `app/photo/[id]/page.js` as a full page instead.

      Follow-up: What differs in the matching convention between `(.)`, `(..)`, and `(...)`?
      Why should expensive logic (DB calls, heavy computation) generally not live in middleware?

      Middleware runs in a constrained Edge runtime (no full Node APIs, limited execution time/CPU budget on many platforms) and executes on every single matching request before any caching/routing has happened — so any latency it adds is latency added to every page view in its matcher scope, with none of the caching benefits a Server Component or Route Handler further downstream might get.

      Follow-up: What's an appropriate place to move a "check feature flag from a database" check instead?
      How do parallel routes enable independently streaming sections of a dashboard, and what's the role of each slot's own loading.js?

      Each `@slot` is rendered by the parent layout as a named prop, and Next.js can resolve/stream each slot's content independently — a slow slot's own `loading.js` fallback shows while that specific slot's data resolves, without blocking the other slot(s) which may resolve faster, giving per-section Suspense granularity without manually nesting Suspense boundaries.

      Follow-up: What happens to a slot's content on a navigation that doesn't target that slot at all?

      Advanced

      Explain what actually travels over the network on a client-side App Router navigation to a sibling route, and why this is cheaper than a traditional SPA client-side route render.

      The client requests the RSC payload (not HTML, not a JSON blob of raw data either) for just the segments that changed — a serialized description of the new React tree for those segments, including already-resolved Server Component output and references to Client Component modules by ID. This is cheaper than a typical SPA fetch-then-render because the server has already done all Server Component data-fetching/rendering work; the client only needs to reconcile the new serialized tree into its existing fiber tree, not fetch raw JSON and run render logic for Server-Component-equivalent work on the client.

      Follow-up: Does this payload include the actual markup/HTML for Client Components, or something else?
      A deeply nested layout wraps a Context Provider for theme. A sibling route navigation changes the theme via a Server Action. Why might the new theme not immediately reflect across the persisted layout's subtree?

      Because the layout instance (and its Context Provider, if it reads server-derived initial state only once on mount) persists across the navigation by design, a Server Action changing data on the server doesn't automatically push a new value into an already-mounted client-side Provider unless something explicitly triggers a re-read — e.g., `revalidatePath`/`router.refresh()` to re-fetch the RSC payload for the relevant segment (including the layout, if its data changed) or passing the updated value down through props that genuinely change reference, forcing the Provider's consumers to pick up the new value.

      Follow-up: What's the difference between router.refresh() and a full page reload in terms of what gets re-rendered?
      Why does Next.js restrict middleware to a constrained Edge runtime rather than full Node.js, architecturally?

      Middleware is designed to run geographically close to the user (at CDN edge locations) on every matching request with minimal cold-start latency; a full Node.js runtime's startup cost and footprint would undermine the "runs on every request, everywhere, fast" design goal. The V8-isolate-based Edge runtime starts in microseconds rather than the hundreds of milliseconds a full Node process might take cold, at the cost of API surface (no filesystem, limited subset of Node built-ins).

      Follow-up: What happens if your middleware genuinely needs a Node-only API — what's the recommended workaround?
      Design a multi-tenant app where the subdomain determines the active tenant's layout and data, using middleware plus the App Router. What does middleware do vs. what does the layout do?

      Middleware inspects the request's `Host` header, extracts the subdomain, and rewrites the URL (via `NextResponse.rewrite`) to an internal path encoding the tenant (e.g., `/_tenant/[tenantId]/...`) or sets a header/cookie the layout can read — middleware should NOT fetch full tenant configuration from a database per request if avoidable (latency on every request); it should do the minimal routing decision. The matched `app/_tenant/[tenantId]/layout.js` Server Component then does the actual tenant config fetch (ideally cached/memoized) and renders the tenant-specific shell, keeping the expensive/full data-dependent work in the Server Component layer where Next.js's caching and streaming apply.

      Follow-up: How would you cache the tenant-config lookup so it isn't refetched on every nested navigation?

      Practice Assignments

      Beginner (30-60 min)

      Build a nested layout hierarchy and observe persistence

      Create `app/dashboard/layout.js` with a sidebar holding local state (e.g., an expanded/collapsed toggle), and two sibling pages `app/dashboard/overview/page.js` and `app/dashboard/settings/page.js`. Navigate between them and confirm the sidebar's state survives.

      Acceptance criteria: Toggling the sidebar, then navigating between the two pages, preserves the toggle state.

      Hints

      If state resets, check you used layout.js and not template.js.

      Bonus: Add a root-level layout.js and a nested one, and explain which one's state would reset on a navigation to an entirely different top-level section.

      Intermediate (2-4 hrs)

      Build an intercepting-route photo modal

      Build a photo feed where clicking a thumbnail opens a lightbox modal via an intercepting route, but a direct URL visit or page refresh on that same photo URL renders a full dedicated page instead.

      • Verify both navigation paths (in-app click vs. direct URL) render correctly.

      Acceptance criteria: Both the modal and full-page variants work and share the same underlying photo-detail component.

      Hints

      Use a parallel `@modal` slot plus the `(.)` intercepting convention matching the photo route's folder depth.

      Bonus: Add a close button that navigates back without a full page reload.

      Advanced (1-2 days)

      Build subdomain-based multi-tenant routing with middleware

      Build an app where `tenant-a.localhost:3000` and `tenant-b.localhost:3000` each render a different tenant's branded dashboard, using middleware to detect the subdomain and rewrite to an internal tenant-scoped route, with the actual tenant config lookup happening in a layout Server Component (not middleware).

      • Design appropriate caching for the tenant-config lookup.
      Hints

      Consider using Next.js's `fetch` caching or React's `cache()` function to dedupe the tenant lookup across the layout and any nested pages needing the same data within one request.

      Quick Revision Cheat Sheet

      • Folders = route segments; page.js = leaf UI; layout.js = persistent wrapper; template.js = remounting wrapper.
      • loading.js = automatic Suspense boundary; error.js = automatic Error Boundary (must be Client Component).
      • Route groups (name) organize files without affecting the URL.
      • Parallel routes (@slot) render independent, independently-streaming sections in one layout.
      • Intercepting routes let a navigation show a modal while a direct URL hit shows the full page.
      • Middleware runs on the Edge runtime, before routing resolves — keep it fast and side-effect-light.
      • Client-side navigations fetch only the changed segments' RSC payload, not full HTML/full JSON.
      • Shared layouts persist React state across sibling navigations — same fiber, same reconciliation rules as Ch.1.
