    React & Next.js Advanced

    📚 11 chapters⏱ ~26–30 hrs total

    For engineers who already build React apps daily and need to go one level deeper: the actual reconciliation algorithm and Fiber architecture, the lane-based scheduler behind Concurrent React, how Server Components serialize across the wire, and the rendering-strategy and performance tradeoffs that separate a mid-level React dev from a Staff/Tech Lead candidate who can defend every decision under interviewer pushback.

    Learning Outcomes

    • Explain Fiber's reconciliation algorithm, double buffering, and the commit phase well enough to answer "what happens when you call setState" at any depth.
    • Reason about the lane model and priority scheduling behind Suspense, transitions, and concurrent rendering.
    • Choose the right state-management tool (Context, Redux Toolkit, Zustand, React Query) for a given access pattern and justify it.
    • Profile and fix real React performance problems: unnecessary re-renders, large lists, expensive derived state.
    • Design a Next.js App Router application with the correct mix of Server/Client Components, Server Actions, and caching layers.
    • Pick the correct rendering strategy (CSR/SSR/SSG/ISR/PPR) per route and justify it with Core Web Vitals data.
    • Measure and optimize LCP, INP, and CLS using real tooling (Lighthouse, CrUX, web-vitals library, React Profiler).
    • Structure a frontend codebase (folder structure, design system, micro-frontends) that scales to dozens of engineers.

    🏆 Capstone Project: Production-Grade Analytics Dashboard (Next.js App Router)

    Problem statement: Build a multi-tenant analytics dashboard (think: a lightweight Mixpanel/Amplitude clone) that lists and drills into millions of simulated events, using Next.js 15 App Router end to end, and apply every chapter in this topic to it.

    Required features:

    • App Router layout hierarchy with nested layouts, route groups, parallel routes for a modal detail view, and middleware-based tenant resolution from a subdomain.
    • Server Components fetch and stream the dashboard shell; Server Actions handle filter mutations, saved-view creation, and CSV export triggers without client-side fetch boilerplate.
    • A client-side virtualized data table (10k+ rows, windowed rendering) with column sort/filter, backed by React Query for cache + background refetch and useOptimistic for inline row edits (e.g., renaming a saved view).
    • Suspense boundaries + streaming SSR so the shell paints before slow aggregate queries resolve; a route using Partial Prerendering for the mostly-static settings page.
    • State split correctly: server cache (React Query) vs. local UI state (Zustand) vs. ephemeral form state — no single global store for everything.
    • Core Web Vitals instrumented with the web-vitals library reporting to an API route, plus a Lighthouse CI budget gate.

    Tech stack suggestion: Next.js 15 (App Router, TypeScript), React 19, TanStack Query + TanStack Virtual, Zustand, Tailwind, Vercel/self-hosted Node runtime, Playwright for E2E.

    Milestones:

    1. Scaffold App Router structure: layouts, route groups, loading/error boundaries, middleware for tenant routing.
    2. Build the Server Component data-fetching layer with streaming and Suspense; wire one slow aggregate query behind its own boundary.
    3. Build the virtualized table as a Client Component; wire React Query for list data and useOptimistic/Server Actions for edits.
    4. Add the settings route with Partial Prerendering; compare its TTFB/LCP against a fully dynamic route.
    5. Instrument Core Web Vitals, run Lighthouse CI, and fix at least two real regressions found (not hypothetical ones).
    6. Write a short architecture doc explaining every rendering-strategy choice per route and why.

    Evaluation checklist:

    • ☐ Can explain exactly which parts of the tree are Server vs Client Components and why each boundary is placed there.
    • ☐ The virtualized table stays smooth (no dropped frames) scrolling 10k+ rows.
    • ☐ Optimistic edits roll back correctly on server rejection, with no UI flash/inconsistency.
    • ☐ Lighthouse scores and real web-vitals numbers are recorded before/after each optimization.
    • ☐ Can defend the rendering-strategy choice (CSR/SSR/SSG/ISR/PPR) for every route in the app.
