    React Internals: Reconciliation, Fiber & the Rendering Lifecycle

    ⏱ 3 hrs📍 Chapter 1 of 11

    One-line summary: React doesn't "re-render the DOM" — it builds a linked-list tree of work units called Fibers, diffs two of those trees, and commits the minimal set of host-tree mutations in a single synchronous pass; understanding that tree and its two-phase (render/commit) model is the single highest-leverage thing you can know for a senior React interview.

    On this page

      Why It Matters for a Senior Developer

      Every "why does my component re-render twice," "why is this state update not showing immediately," "how does React batch updates," and "what's the difference between the virtual DOM and Fiber" question traces back to this chapter. Interviewers use it to separate candidates who've memorized hook rules from candidates who can reason about React as a runtime. It's also the prerequisite for Concurrent React (Ch. 5) and Server Components (Ch. 7) — both are built directly on the Fiber architecture.

      Prerequisites

      You should already be comfortable writing components, hooks, and JSX day-to-day. Related: Hooks Deep Dive, Concurrent React.

      Core Concepts

      The "virtual DOM" is really just a tree of plain objects

      JSX compiles to React.createElement() (or, with the modern JSX transform, calls into react/jsx-runtime) calls, which produce plain JS objects describing what you want rendered — type, props, children, key. React never touches the real DOM from this description directly. Instead it builds an internal data structure — the Fiber tree — that mirrors this description and tracks enough metadata to do incremental, interruptible work.

      What a Fiber actually is

      A Fiber is a JS object, one per component instance / host element, that acts as both a unit of work and a linked-list node. Key fields (from React's actual source, simplified):

      type Fiber = {
  tag: WorkTag;              // FunctionComponent, HostComponent, HostRoot, etc.
  key: string | null;
  type: any;                 // the function/class/'div' this fiber represents
  stateNode: any;             // DOM node, class instance, or null

  // Fiber tree pointers — this is the key insight: it's a linked list, not an array tree
  return: Fiber | null;       // parent
  child: Fiber | null;        // first child
  sibling: Fiber | null;      // next sibling

  // Work-in-progress bookkeeping
  pendingProps: any;
  memoizedProps: any;
  memoizedState: any;         // hooks linked list lives here for function components
  updateQueue: UpdateQueue | null;

  alternate: Fiber | null;    // the "other" tree's corresponding fiber (double buffering)
  flags: Flags;               // side-effect bitmask (Placement, Update, Deletion...)
  subtreeFlags: Flags;        // bubbled-up effects so we can bail out of entire subtrees
  lanes: Lanes;                // priority bitmask for scheduling (see Concurrent chapter)
};

      The parent/child/sibling pointers mean React can walk the entire tree with an iterative depth-first traversal and no recursion — which is exactly what makes the work interruptible (a recursive call stack can't be paused and resumed; a while loop walking pointers can).

      Double buffering: current tree vs work-in-progress tree

      React keeps two Fiber trees alive at once:

      • current — the tree that matches what's on screen right now.
      • workInProgress (WIP) — the tree being built for the next render, created by cloning the current fiber via createWorkInProgress() (reusing the object when possible instead of allocating new ones — a deliberate GC-pressure optimization).

      Each fiber's alternate field points to its counterpart in the other tree. When the WIP tree finishes and commits, React simply flips a pointer — FiberRootNode.current = finishedWork — and the WIP tree becomes the current tree. This is why React can throw away an in-progress render without ever having mutated the real DOM: nothing was touched until commit.

      The three phases: render, reconciliation, commit

      1. Render phase (can be interrupted/thrown away, no side effects): React walks the WIP tree calling your function components (and resolving class lifecycle/hook state), producing new React elements for each fiber's children.
      2. Reconciliation (the "diff"), part of the render phase: for each fiber, React compares the new element(s) to the existing child fiber(s) and decides: reuse (update), create (placement), or remove (deletion) — tagging each fiber's flags bitmask accordingly. This is the beginWork() / reconcileChildren() machinery.
      3. Commit phase (synchronous, cannot be interrupted): React walks the flags-tagged effect list and applies the real DOM mutations (commitMutationEffects), then runs layout effects synchronously, flips current, then schedules passive effects (useEffect) for after paint.

      The actual diffing algorithm (reconcileChildren)

      React does not run a generic tree-diff algorithm (that's O(n³) and far too slow). It uses two heuristics that make diffing O(n):

      • Different element types at the same position → tear down the whole subtree. If a <div> becomes a <span>, React doesn't try to patch attributes — it unmounts the old fiber (and all its children, running cleanup) and mounts a brand new one.
      • Same type → reuse the fiber, diff props, recurse into children. Only changed props reach the DOM.
      • Lists need explicit keys because without them React's list-diff falls back to positional index comparison, which misattributes state across reorders, insertions and deletions. With stable keys, React uses a single-pass algorithm that detects the common case (items only appended/removed at the edges) in O(n) and only falls back to a slower per-item move-detection pass when keys are out of order.

      Bailouts: how React skips whole subtrees

      During beginWork, if a fiber's props, state, and context haven't changed and its lanes indicate no pending work, React calls bailoutOnAlreadyFinishedWork and skips calling your component function entirely — it just clones the existing child fibers. This is the actual mechanism behind React.memo and is why subtreeFlags exists: a parent can bail out of its own re-render but must still check whether any descendant has pending work bubbled up into that bitmask.

      How It Works Under the Hood

      End-to-end for setCount(c => c + 1) inside an event handler:

      1. The update is wrapped in an Update object and enqueued onto the fiber's hook queue; scheduleUpdateOnFiber marks the fiber (and its ancestors, via lanes bubbling up the return pointers) as having pending work on a specific lane (priority bucket).
      2. React (via the Scheduler package) decides synchronously or asynchronously when to start work, begins building a new WIP tree from the root, re-cloning only fibers on the path to/through the updated fiber (siblings outside that path are bailout-skipped).
      3. beginWork calls your function component, which calls hooks in order against the fiber's memoizedState linked list, returns new React elements.
      4. reconcileChildren diffs new elements against the old child fibers, tagging flags.
      5. When the whole WIP tree finishes (completeWork bubbling back up), React enters the commit phase: mutate DOM → run useLayoutEffects synchronously → flip current pointer → paint → schedule useEffects asynchronously.

      Diagrams

      flowchart TD A[State update scheduled] --> B[scheduleUpdateOnFiber marks lanes] B --> C{Scheduler: sync or concurrent?} C -->|Sync, e.g. discrete event| D[Render phase: build WIP tree] C -->|Concurrent, e.g. transition| D D --> E[beginWork: call components, reconcile children, tag flags] E --> F{Work interrupted by higher-priority update?} F -->|Yes| D F -->|No, tree complete| G[Commit phase: mutate DOM] G --> H[Run useLayoutEffect synchronously] H --> I[Flip current pointer -- WIP becomes current] I --> J[Browser paints] J --> K[Run useEffect asynchronously]

      Real-World Production Scenario at Scale

      At scale

      A dashboard with a 5,000-row table re-rendered the entire table on every keystroke in a filter input because the table and the input shared one parent component and the table rows weren't keyed by a stable ID (they were keyed by array index). Every filter kept the array length similar but changed row identity under the hood, so React's index-based diff reused fibers for the wrong logical rows, causing input-focus loss, incorrect animation states, and full subtree re-renders instead of bailouts. The fix: stable entity IDs as keys, lifting the filter input's state out of the table's re-render path (into a sibling, or via useDeferredValue, covered in Ch. 5), and wrapping row components in memo. Root-caused with the React DevTools Profiler's flame graph, which showed every row fiber re-rendering despite unchanged content.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      "Virtual DOM is always faster than direct DOM manipulation" is false and will get called out in a senior interview — Fiber's advantage is not raw speed, it's incremental/interruptible rendering and the ability to batch and prioritize updates. A hand-tuned direct DOM update for one hot path will always beat Fiber's render+commit overhead; React wins on maintainability and scheduling, not on being intrinsically faster than manual DOM writes.

      • Using array index as key for lists that reorder/filter — breaks fiber reuse identity.
      • Believing state updates are always synchronous — since React 18, updates are batched automatically even outside event handlers (e.g. in fetch().then()), which surprises code relying on reading updated state immediately after calling a setter.
      • Assuming useLayoutEffect and useEffect run at the same time — layout effects run synchronously in the commit phase before paint; passive effects run asynchronously after paint.
      • Mutating props/state objects directly — breaks the reference-equality checks that bailouts and memo depend on.

      Interview Questions

      Basic

      What is the virtual DOM and why does React use it?

      It's a lightweight JS object tree describing the desired UI. React diffs it against the previous tree to compute the minimal set of real DOM mutations, instead of re-rendering everything, and it lets React batch/schedule work before touching the (expensive) real DOM.

      Follow-up: Is virtual DOM diffing always faster than manual DOM updates?
      What is a Fiber?

      A JS object representing a unit of work for one component/element instance, with pointers to its parent, first child, and next sibling, plus fields for pending/memoized props and state. It's both a tree node and a resumable work unit.

      Follow-up: Why a linked list instead of a recursive tree walk?
      What triggers a re-render?

      A state update (via a hook setter or class setState), a parent re-rendering (unless bailed out via memo), a context value change for consumers, or a force update.

      Follow-up: Does a parent re-rendering always re-render its children?
      What's the difference between render and commit phases?

      Render phase computes what should change (can be paused/thrown away, no DOM writes, no side effects allowed). Commit phase actually applies DOM mutations and runs layout effects synchronously — it cannot be interrupted.

      Follow-up: Why must render phase be side-effect free?
      Why does React need a `key` prop in lists?

      To give each list item a stable identity across renders so React's diff algorithm can match old fibers to new elements correctly — reusing state/DOM nodes for unchanged items and correctly creating/destroying ones that were added/removed, rather than falling back to error-prone positional matching.

      Follow-up: What breaks specifically if you use array index as key on a sortable list?
      What does React.memo do internally?

      Wraps a component so that during beginWork, if the shallow prop comparison (or custom comparator) says props are equal and there's no pending work on that fiber's lanes, React bails out and skips calling the component function.

      Follow-up: Does memo stop context changes from re-rendering the component?

      Medium

      Explain double buffering in Fiber.

      React keeps two Fiber trees: `current` (on screen) and `workInProgress` (being built). Each fiber has an `alternate` pointer to its counterpart in the other tree. Building WIP never mutates `current` or the real DOM; on completion React flips `FiberRootNode.current` to the finished tree. This lets React discard an in-progress render safely.

      Follow-up: What happens to the alternate tree if a render is abandoned?
      Walk through what happens, fiber-by-fiber, when you call a state setter inside an onClick handler.

      Update object enqueued on the fiber's hook queue -> scheduleUpdateOnFiber marks lanes up the return-pointer chain to the root -> since it's a discrete event, React schedules (often synchronously-ish/batched within the event) a render -> beginWork walks from root, bailing out subtrees without pending lanes -> reconcileChildren diffs and tags flags -> completeWork bubbles subtreeFlags -> commit phase mutates DOM, runs layout effects, flips current, schedules passive effects.

      Follow-up: How does this differ if the setState happens inside a startTransition?
      Why can't side effects run during the render phase?

      Render phase work can be paused, abandoned, or re-run multiple times for the same commit (e.g., under Concurrent rendering with Strict Mode double-invocation, or when a higher-priority update interrupts it) before anything is actually shown. A side effect (DOM write, subscription, mutation) run during an abandoned render would leak or run redundantly, since there is no guarantee that render corresponds to what eventually commits.

      Follow-up: Where specifically does React enforce or encourage this separation?
      How does React decide whether changing an element's type tears down the subtree vs. updates it?

      In reconcileChildren, if the new element's `type` differs from the old fiber's `type` at the same position, React treats it as a full replace: unmount old fiber subtree (cleanup effects, remove DOM), create a brand-new fiber subtree. Same type -> reuse fiber, just diff/update props and recurse into children.

      Follow-up: Does this apply to conditionally rendering `
      ` vs `` wrapping the same children?
      What is `subtreeFlags` and why does it exist?

      A bitmask on a fiber summarizing side-effect flags of its entire subtree (bubbled up during completeWork). It lets the commit phase skip walking into subtrees that have no pending effects at all, rather than visiting every single fiber to check.

      Follow-up: How does this interact with a bailed-out subtree that still has one deeply nested effect?
      Why does React recommend against using array index as key, concretely?

      When items are inserted/removed/reordered, the index-to-item mapping shifts, so React matches old fiber at index i to the new element at index i even though they represent different logical items — causing it to reuse/mutate the wrong component instance's local state and DOM (e.g., an input losing focus or showing the wrong value, uncontrolled component state "sticking" to the wrong row).

      Follow-up: Is it ever safe to use index as key?

      Advanced

      How does React implement the O(n) list-diff instead of a full O(n³) tree-edit-distance algorithm, and what's the actual tradeoff being made?

      React assumes two heuristics hold in practice: (1) elements of different types produce substantially different trees — so it never tries to match across type boundaries, and (2) the developer can hint stable identity via `key`. Given keyed children, React's `reconcileChildren` does essentially a single forward pass trying to match by key in order, and only does extra bookkeeping (tracking a "lastPlacedIndex") to detect moves when keys appear out of their expected order, insertion/deletion handled by diffing against a Map of key->old fiber built once. This trades perfect minimal-edit-distance correctness for linear time, correct in the common app case where reordering is rare relative to appends/removals.

      Follow-up: What pathological key pattern makes this degrade toward worse performance?
      Explain how Strict Mode's double-invocation of components/effects in development interacts with the Fiber render phase, and why it's safe.

      Strict Mode intentionally calls function component bodies (and, for effects, mounts/unmounts/remounts) twice during development to surface impure render logic or effects lacking proper cleanup. Because render-phase work is required to be pure/side-effect-free by the Fiber model (nothing commits until the WIP tree completes), re-invoking it twice is observably safe for correct code — it only breaks code that smuggles side effects (mutating module-level variables, starting a subscription inline) into the render phase, which was already relying on undefined behavior.

      Follow-up: Why does this not double-invoke in production builds?
      A fiber bails out of re-rendering via memo, but one of its grandchildren has pending work on a transition lane. How does that grandchild's work still get processed?

      Bailout at a fiber only skips calling that fiber's own component function and reconciling its direct children from scratch; React still checks `childLanes`/`subtreeFlags` bubbled up from descendants. If any descendant has pending lanes, React still walks down into that subtree (cloning only the fibers on the path to the fiber with pending work) even though the bailed-out fiber itself isn't re-rendered or its sibling subtrees untouched.

      Follow-up: What does this imply about clone cost for a bailout deep in a wide tree?
      Why does React need two full Fiber trees (current + WIP) instead of diffing the new element tree directly against the DOM?

      The DOM alone doesn't carry React's bookkeeping (hook state linked lists, pending update queues, fiber-level flags, lane priorities) and reading element attributes/structure back out of the DOM to reconstruct that would be slow and lossy. Maintaining a parallel in-memory tree lets React do cheap, interruptible, side-effect-free comparisons entirely in JS, and only touch the real (expensive) DOM once, in the commit phase, with a minimal mutation list.

      Follow-up: What would break if React mutated `current` in place during render instead of building a separate WIP tree?
      How does `completeWork` differ from `beginWork` in traversal direction, and why does React need both passes?

      `beginWork` walks top-down (parent before child), calling components and reconciling children, effectively a depth-first descent. `completeWork` runs bottom-up as the traversal unwinds back toward the root, finalizing each fiber (e.g., creating/updating actual host instances for HostComponents, bubbling `subtreeFlags` and `childLanes` upward). The descent decides *what* changed per node top-down (since a parent's output determines its children's props), while the ascent is needed to aggregate child-level effect information into something the commit phase can use without re-walking the whole tree.

      Follow-up: At which pass are actual host DOM nodes created for new elements?

      Practice Assignments

      Beginner (30-60 min)

      Observe bailouts with console logs

      Build a parent component with a counter button and three child components wrapped in memo, each receiving a different kind of prop: a primitive, a stable object (created with useMemo), and a fresh inline object literal created every render.

      • Log inside each child on every render.
      • Click the counter and record which children re-render.

      Acceptance criteria: You can explain in your own words, per child, exactly why it re-rendered or bailed out.

      Hints

      Memo does a shallow (Object.is per-prop) comparison. A fresh object literal is never equal by reference across renders even if its contents are identical.

      Bonus: Add the React DevTools Profiler and visually confirm the flame graph matches your console logs.

      Intermediate (2-4 hrs)

      Build a keyed vs. unkeyed list bug reproduction

      Build a list of 10 rows, each containing an uncontrolled text input (so it has local DOM state). Implement a "shuffle" and a "remove first item" button for two versions of the list: one keyed by array index, one keyed by a stable per-item ID.

      • Type distinct text in each input before shuffling/removing.
      • Document which version "loses" the correct text-to-row association and why.

      Acceptance criteria: A written explanation referencing fiber reuse/identity, not just "it looks buggy."

      Hints

      Uncontrolled inputs store their value in the DOM node itself, which is only preserved if React decides to reuse the same host fiber for that logical row.

      Bonus: Reproduce the same bug with CSS transition state instead of input text.

      Advanced (1-2 days)

      Instrument a mental model of the Fiber tree

      Using React DevTools' "Profiler" + "Components" tabs (and optionally the open-source React source), build a small app with 4-5 levels of nesting and deliberately cause: a full subtree remount (type change), a bailout, and a prop-driven update that only touches one branch. For each case, write down what you'd expect `beginWork`/`completeWork`/commit to do, then verify against the Profiler's commit details (which fibers rendered, render duration per fiber).

      • No full solution is provided — this is a research-and-verify exercise against real React behavior.
      Hints

      The Profiler's flamegraph literally color-codes components that rendered during a commit; a bailed-out fiber won't appear as "rendered" even though its parent did.

      Quick Revision Cheat Sheet

      • Fiber = linked-list node (return/child/sibling) + unit of work, one per component instance.
      • Two trees always exist: current (on screen) and workInProgress (being built), linked via `alternate`.
      • Render phase: pure, interruptible, no DOM writes. Commit phase: synchronous, mutates DOM, runs layout effects.
      • Diffing is O(n), not full tree-edit-distance: same type -> reuse+diff; different type -> tear down+rebuild.
      • `key` gives list items stable identity across renders — critical for correct fiber reuse.
      • Bailout = React skips calling your component function when props/state/context unchanged and no pending lanes.
      • `subtreeFlags`/`childLanes` let commit and render skip whole subtrees with no pending work.
      • Virtual DOM's win is incremental/prioritizable rendering, not raw speed over direct DOM writes.
