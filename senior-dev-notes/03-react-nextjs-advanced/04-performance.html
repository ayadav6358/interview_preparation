    React Performance: memo, useMemo, useCallback, Profiling, Virtualization

    ⏱ 2.5 hrs📍 Chapter 4 of 11

    One-line summary: React performance work is measure-first, fix-the-cause: almost every real-world slowdown is either an unnecessary re-render cascade, an expensive render of too many DOM nodes, or a genuinely expensive computation — and each has a distinct, specific fix.

    On this page

      Why It Matters for a Senior Developer

      Interviewers test this by handing you a janky component and asking you to fix it. The senior-level answer always starts with the Profiler, not with sprinkling memo everywhere — demonstrating that process is as important as knowing the APIs.

      Prerequisites

      Read React Internals first — this chapter is the applied version of the bailout mechanics described there. Related: Concurrent React.

      Core Concepts

      The three distinct performance problems

      • Unnecessary re-renders: a component re-renders when its output would be identical. Fix: stabilize props/state identity so memo bailouts can work, or restructure component boundaries so state lives closer to where it changes.
      • Expensive renders: a component legitimately needs to re-render but does too much work doing so (huge DOM subtree, thousands of list items). Fix: virtualization, code-splitting the subtree, or reducing DOM node count.
      • Expensive computation: a pure function (sort, filter, aggregate) is genuinely slow and re-runs every render. Fix: useMemo, or move the work off the main thread (Web Worker) if it's heavy enough.

      Misdiagnosing which bucket a slowdown belongs to is the most common mistake — wrapping an expensive render in useMemo does nothing (useMemo only caches a value, not a render), and virtualizing a list that's already short wastes engineering time on a non-problem.

      memo, useMemo, useCallback — what they actually buy you

      React.memo(Component) makes React compare new props to old (shallow Object.is per prop, or a custom comparator) before calling the component function, bailing out if equal — see Ch. 1 for the fiber-level mechanics. useMemo(fn, deps) caches the return value of fn across renders while deps are unchanged; it does not prevent the component itself from re-rendering. useCallback(fn, deps) is literally useMemo(() => fn, deps) — it exists purely to give a function stable identity, which only matters if that identity feeds into a dependency array or a memoized child's props.

      Using the React DevTools Profiler correctly

      Record a profiling session around the exact interaction that feels slow (not a full page load). The flame graph shows every fiber that rendered during each commit, color-coded by render duration, with a "why did this render" panel per component (props changed / state changed / parent rendered / context changed / hooks changed). This is the single fastest way to confirm or deny a hypothesis about what's actually re-rendering — guessing is a wasted interview signal.

      Virtualization: rendering only what's visible

      For a list with thousands of rows, rendering all of them creates thousands of DOM nodes even though only ~20 are visible in the viewport at once — both the initial render and every scroll-triggered re-render pay that cost. Virtualization (via @tanstack/react-virtual or react-window) renders only the rows currently in (and slightly beyond) the viewport, measuring/tracking scroll offset and absolutely positioning a small rendered "window" of rows inside a correctly-sized scroll container, recycling DOM nodes as the window moves.

      How It Works Under the Hood

      A windowed/virtualized list keeps a single scroll container with a total height equal to rowCount × rowHeight (or a measured estimate for variable-height rows), but only mounts fiber subtrees for rows whose index falls in [scrollTop / rowHeight - overscan, (scrollTop + viewportHeight) / rowHeight + overscan]. As the user scrolls, the library recomputes this range on each scroll event (throttled to animation frames) and React's own reconciliation handles mounting newly visible rows and unmounting ones that left the window — keyed by stable row ID so state doesn't leak across recycled positions (the same key-identity concern from Ch. 1).

      Real-World Production Scenario at Scale

      At scale

      An internal admin tool rendering a 3,000-row order table (unvirtualized) took ~1.8s to become interactive and janked on every filter keystroke. Profiling showed two separate problems stacked together: (1) the filter input and the table shared a parent, so every keystroke re-rendered all 3,000 row components even though only the filtered subset changed, and (2) even the filtered render mounted hundreds of real DOM nodes per keystroke. Fix: virtualized the table (only ~20 DOM rows ever mounted) and moved the filter input's state into a sibling using useDeferredValue (Ch. 5) so typing stayed responsive while the filtered list update was deprioritized. Interaction-to-next-paint dropped from ~400ms to under 50ms, measured with the Profiler and Chrome's Performance panel.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Wrapping everything in memo/useMemo/useCallback "just in case" has a real cost: every memoized value needs a comparison each render, and memoized components still re-render when context or state they depend on changes — so unmeasured blanket memoization often adds complexity and a small constant overhead without fixing anything. Profile first.

      • Memoizing a component whose props change every render anyway (inline object/array/function props) — the comparison always fails, pure overhead.
      • Virtualizing a 50-row list — the engineering cost exceeds the (nonexistent) performance problem.
      • Using useMemo to "fix" a slow component render instead of a slow computation — it does nothing for render cost.
      • Not measuring before/after — "I added memo so it's faster" without Profiler numbers is not evidence.

      Interview Questions

      Basic

      What does React.memo do?

      Skips re-rendering a component if its props are shallow-equal to the previous render's props (or pass a custom comparator), by bailing out during the fiber's beginWork step.

      Follow-up: Does memo help if the component re-renders due to its own internal state change?
      What's the difference between useMemo and useCallback?

      useMemo caches a computed value; useCallback caches a function reference. useCallback(fn, deps) is equivalent to useMemo(() => fn, deps).

      Follow-up: When does a stable function reference actually matter?
      Why would you virtualize a list?

      To avoid mounting DOM nodes for off-screen items, which otherwise costs memory and render/commit time proportional to total item count rather than visible count.

      Follow-up: What's the tradeoff of virtualizing vs. paginating?
      How do you find out why a component re-rendered?

      React DevTools Profiler's "render reasons" panel, or manual console logging of props/state between renders, or `why-did-you-render` library in dev.

      Follow-up: What does the Profiler flame graph's color intensity represent?
      Does wrapping a component in useMemo make it render faster?

      No — useMemo caches a value, not a render. To skip a component's render entirely you need memo (or avoid re-rendering the parent in the first place).

      Follow-up: What's an example where this confusion leads to a wasted optimization?

      Medium

      You added React.memo to a child component but it still re-renders every time. Walk through the likely causes.

      Most likely an inline prop (object/array/function literal) created fresh every parent render breaking shallow equality; also possible: the child reads a Context whose value changed, or the child has its own internal state update, or the parent passes `children` as JSX which is itself a new element reference each render.

      Follow-up: Does passing children as a render prop function fix the JSX-children issue?
      Explain, step by step, how you'd diagnose a janky scroll in a list of 500 cards.

      Profile the scroll interaction specifically; check whether cards are re-rendering during scroll (if state tied to scroll position lives too high in the tree) vs. purely a paint/layout cost from too many DOM nodes/expensive CSS (box-shadow, filters) — these need different fixes (memoization/state relocation vs. virtualization/CSS simplification). Chrome DevTools' Performance panel's "Rendering" and "Paint" flame sections distinguish JS-render cost from paint/composite cost.

      Follow-up: What CSS properties are the most common composite/paint cost offenders?
      What's the overscan parameter in a virtualizer and what tradeoff does it control?

      The number of extra rows rendered beyond the visible viewport, in each direction. Higher overscan reduces blank-flash risk during fast scrolling (since more rows are pre-mounted) at the cost of more DOM nodes/render work per scroll frame; lower overscan is cheaper but can show empty space momentarily on fast scroll/fling.

      Follow-up: How would variable row heights change the virtualizer's measurement strategy?
      Why might adding useCallback actually make performance worse in some cases?

      useCallback itself has a cost (storing the deps array, comparing it each render) and if nothing downstream depends on the function's reference identity (no memoized child consuming it, no effect depending on it), you've added overhead with zero benefit — the underlying function would've been garbage collected and recreated trivially cheaply anyway.

      Follow-up: How would the React Compiler (React 19) change this calculus?

      Advanced

      Design a virtualized table that supports variable row heights, sticky headers, and column-level sort without breaking scroll-position stability during data updates.

      Use a virtualizer that supports a measurement callback (e.g., `measureElement` in TanStack Virtual) rather than a fixed `estimateSize`, so row heights are measured after mount and the virtualizer recalculates offsets; keep the header in a separate non-scrolling (or `position: sticky`) container outside the virtualized row list so it's never unmounted/remounted by the windowing logic. For sort/update stability, key rows by stable entity ID (not index) so the virtualizer's internal position cache maps correctly to the same logical row even as its index shifts, and preserve scroll offset by anchoring to a specific row ID's measured position rather than a raw pixel offset when the dataset changes size.

      Follow-up: What happens to scroll position if you key rows by index instead of ID after a sort?
      A component passes `{...props}` spread through several wrapper components before reaching a memoized leaf. Why can this silently defeat memoization, and how would you detect it?

      Spreading often re-creates new object/array/function values at each layer (e.g., a wrapper computing a derived prop inline, or JSX children being a new element each render), so even though the "same" data conceptually flows through, the actual reference reaching the memoized leaf changes every render. Detect it with the Profiler's render-reason panel on the leaf (it'll show "props changed" and list which prop), or temporarily log `Object.is` comparisons of each prop across renders at the boundary.

      Follow-up: What's a structural fix that avoids this without manually memoizing every intermediate layer?
      How does the React Compiler (React 19's optional compiler) change the manual memo/useMemo/useCallback calculus, and what does it NOT solve?

      The compiler statically analyzes component code and automatically inserts memoization (effectively auto-generating the equivalent of memo/useMemo/useCallback) for values and sub-renders it can prove are safe to cache, removing the need to hand-write most of this chapter's APIs for compiler-compatible code. It does NOT solve algorithmic/structural problems: it can't virtualize an unbounded list for you, can't fix a bad component-boundary/state-location decision, and can't know a computation is "expensive enough to be worth caching" vs. negligible — it mechanizes correctness of memoization, not architectural judgment.

      Follow-up: What coding patterns defeat the compiler's static analysis (force it to bail out of optimizing a component)?
      Explain why "move expensive work to a Web Worker" is sometimes wrong even when the computation is provably slow.

      Workers can't touch the DOM and serialization cost (structured clone) to move data in/out can itself dominate for large/complex objects, sometimes costing more than the computation saved; also, if the result is needed synchronously to avoid a layout flash (e.g., measuring before paint), a worker's inherent asynchrony reintroduces the problem you were trying to avoid. It's the right tool specifically when the computation is CPU-heavy, the input/output data is reasonably small/serializable, and a brief async delay before showing the result is acceptable.

      Quick Revision Cheat Sheet

      • Three distinct problems: unnecessary re-renders, expensive renders, expensive computations — different fixes.
      • Always profile the specific interaction before optimizing; guesses waste engineering time and interview credibility.
      • memo bails out of calling the component; useMemo caches a value; useCallback caches a function reference.
      • Inline object/array/function props defeat memo's shallow comparison every time.
      • Virtualize lists with hundreds+ of rows; don't bother for short lists.
      • Key virtualized/list rows by stable entity ID, never array index.
      • useMemo does not make a component's render faster — it only skips recomputing a value.
      • React 19's compiler automates most manual memoization for compiler-compatible code, but not architecture decisions.
