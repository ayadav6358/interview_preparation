    Hooks Deep Dive: Rules, Closures, Custom Hooks, useEffect Pitfalls

    ⏱ 2.5 hrs📍 Chapter 2 of 11

    One-line summary: Hooks are not magic — they're a linked list stored on the fiber's memoizedState, read in strict call-order every render, which is exactly why the "rules of hooks" exist and exactly why stale-closure bugs happen.

    On this page

      Why It Matters for a Senior Developer

      Senior interviews rarely ask "what does useState do" — they ask "why can't hooks be conditional," "why did this effect fire with a stale value," and "how would you build this custom hook correctly." Answering those well requires knowing the actual storage model (a linked list indexed by call order), not just the API surface.

      Prerequisites

      Read React Internals first — hooks live inside the Fiber model described there. Related: Concurrent React.

      Core Concepts

      How hooks are actually stored: a linked list, not an array

      Each function component fiber has a memoizedState field that, for function components, points to the first Hook object in a singly linked list — one node per hook call, in call order:

      type Hook = {
  memoizedState: any;        // e.g., current state value for useState, deps array for useEffect
  baseState: any;
  queue: UpdateQueue | null; // pending updates for useState/useReducer
  next: Hook | null;          // next hook called in this render
};

      On every render, React resets a cursor to the fiber's first hook and advances it one node per hook call your component makes. This is why hooks must be called unconditionally in the same order every render — if render N calls useState, useEffect, useState and render N+1 calls useState, useState (skipping the effect because it was inside an if), React reads the second useState's state out of the hook node that actually belongs to the old useEffect — silent data corruption, not just a warning.

      Closures: every render captures its own props/state

      A function component is literally just a function — called fresh on every render. Any closure created inside it (an event handler, an effect callback, a memoized callback) captures the variables as they were in that specific render's scope. There's no "current state" that handlers automatically see — each render's handler closes over that render's state, forever. This is the entire reason stale-closure bugs exist and the entire reason the dependency array exists: it tells React which render's version of a callback is still valid to keep around vs. needs replacing.

      useEffect's actual contract

      Conceptually, useEffect(fn, deps) says: "after this render commits and paints, if any value in deps changed since the last run (compared with Object.is, shallowly, per element), run the cleanup from last time, then run fn again." No deps array = run after every commit. Empty array = run once after the first commit (and once on cleanup, at unmount). This is layered on the Fiber effect list: each hook with a pending effect contributes an entry, and after commit React schedules a pass to run all pending passive effects asynchronously (not blocking paint), in the order they were declared.

      Custom hooks are just functions that call other hooks

      There's no separate runtime concept — "custom hook" is a naming convention (useXxx) plus the rule that it must call hooks unconditionally. Each call site gets its own slice of the hook linked list on the calling fiber; two components calling the same custom hook do not share state — each gets independent hook nodes.

      How It Works Under the Hood

      useState is implemented on top of useReducer's machinery: calling the setter doesn't mutate anything synchronously — it creates an Update object, appends it to the hook's queue, and calls scheduleUpdateOnFiber. During the next render, React walks the queue, applies updates in order (processing functional updaters like c => c + 1 against the previous result), and that becomes the new memoizedState for that hook node. Multiple setState calls in the same event handler are batched: React doesn't re-render after each call, it processes the whole queue once before the next render — which is also why reading the state variable immediately after calling its setter, in the same function body, still shows the old value.

      Code Examples

      // Classic stale closure bug
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      // BUG: this closure captured `count` as 0 from the FIRST render's
      // effect run (deps=[] means this effect, and this closure, never
      // re-runs), so it always logs/sets based on stale `count`.
      setCount(count + 1);
    }, 1000);
    return () => clearInterval(id);
  }, []); // eslint-disable-line react-hooks/exhaustive-deps -- the bug

  return 
      {count}
      ;
}

// FIX 1: functional updater sidesteps the stale closure entirely
function TimerFixed() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setCount(c => c + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return 
      {count}
      ;
}

// FIX 2 (when you need the latest value of something that isn't state
// you're deriving from): a ref that always holds the latest value.
function useLatest(value) {
  const ref = useRef(value);
  useEffect(() => { ref.current = value; }); // runs after every render
  return ref;
}

// A correctly-built custom hook: data fetching with cancellation
function useFetchJSON(url) {
  const [state, setState] = useState({ data: null, error: null, loading: true });

  useEffect(() => {
    let cancelled = false;
    setState(s => ({ ...s, loading: true }));

    fetch(url)
      .then(res => res.json())
      .then(data => { if (!cancelled) setState({ data, error: null, loading: false }); })
      .catch(error => { if (!cancelled) setState({ data: null, error, loading: false }); });

    return () => { cancelled = true; }; // prevents setting state from a stale request
  }, [url]);

  return state;
}

      Real-World Production Scenario at Scale

      At scale

      A search-as-you-type feature fired a network request per keystroke and occasionally rendered results for an older query after a newer one, because the fetch effect had no cancellation guard — the "last request wins" assumption was broken under slow/jittery networks where request order ≠ response order. Fixed with the cancellation-flag pattern shown above (and, longer term, migrated to React Query which handles request deduplication/cancellation and race conditions out of the box — see State Management).

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Disabling react-hooks/exhaustive-deps instead of fixing the dependency is the single most common source of stale-closure bugs in production codebases. If you find yourself wanting to omit a dependency, the real fix is almost always a functional state updater, a ref for "latest value without re-running the effect," or restructuring so the effect doesn't need that value at all.

      • Calling hooks inside conditionals/loops/nested functions — breaks the call-order contract silently.
      • Forgetting cleanup in useEffect for subscriptions/timers/listeners — leaks across remounts.
      • Using an object/array literal as a `useEffect`/`useMemo` dependency — new reference every render defeats memoization; use primitives or a stable memoized reference.
      • Reaching for useEffect to derive state from props/state instead of just computing it during render — adds an unnecessary extra render.

      Interview Questions

      Basic

      Why can't hooks be called conditionally?

      React tracks hook state as a linked list tied to call order, not by name. A conditional hook call changes how many hook nodes exist or which node corresponds to which call across renders, causing React to read/write the wrong hook's state.

      Follow-up: What actually happens internally if you do this — not just "it's a lint error"?
      What's the difference between useEffect and useLayoutEffect?

      useLayoutEffect runs synchronously after DOM mutations but before the browser paints (blocking paint); useEffect runs asynchronously after paint. Use layout effect only when you must measure/mutate the DOM before the user sees it (e.g., avoiding visual flicker).

      Follow-up: What's the perf cost of overusing useLayoutEffect?
      What is a stale closure?

      A function created during a specific render that captured that render's props/state values, which doesn't see later updates because it's never recreated — common in effects/callbacks with incomplete dependency arrays.

      Follow-up: Give two different fixes for the same stale closure bug.
      What does the dependency array actually do?

      Tells React which values the effect/memo/callback closure depends on, so React can shallow-compare them render over render and decide whether to re-run the effect or recreate the memoized value/callback.

      Follow-up: What happens with an object literal in the deps array?
      What is a custom hook, mechanically?

      Just a regular function that calls other hooks, following the naming convention `useXxx` so lint rules and React itself (dev-mode checks) can verify the rules of hooks are followed. Each call site gets its own independent hook state.

      Follow-up: Do two components using the same custom hook share state?
      Why does calling a state setter twice in the same handler only cause one re-render?

      React batches updates within an event handler (and, since React 18, in most async contexts too) — it queues both updates and processes the whole queue before the next render, rather than re-rendering after each call.

      Follow-up: Is this still true inside a raw setTimeout callback in React 18+?

      Medium

      Explain exactly how useState's setter avoids reading stale state when given a function updater.

      `setCount(c => c + 1)` enqueues an updater function rather than a value. When React processes the hook's update queue at render time, it applies updaters in order against the result of the previous one in the queue (not against whatever `count` was in the closure that called setCount), so even multiple queued updates compose correctly regardless of which render's closure called them.

      Follow-up: Why doesn't `setCount(count + 1)` called twice in a row produce +2?
      Why is "derive state in an effect" usually wrong, and what's the actual cost?

      It introduces an extra render: render 1 commits with stale derived value, the effect runs after paint, calls setState, causing render 2. If the value can be computed from existing props/state, computing it inline during render (optionally memoized) avoids that double-render and the flash of stale UI.

      Follow-up: When is deriving state in an effect actually correct?
      How would you build a `useDebouncedValue` custom hook correctly, and what's the subtle bug novices introduce?

      Store the raw value and a debounced copy in state; in an effect keyed on the raw value, set a timeout to update the debounced copy, and return a cleanup that clears the timeout so an in-flight timer doesn't fire after a newer value arrives. The common bug: forgetting the cleanup, so rapid updates schedule multiple timers that all eventually fire and "flicker" the debounced value backward.

      Follow-up: How would you unit test the debounce timing without real timers?
      What's the real difference between useMemo/useCallback as a correctness tool vs. a performance tool?

      As a performance tool, they avoid recomputation/recreation across renders. As a correctness tool, they stabilize reference identity so dependent effects, memoized children, or other hooks' dependency arrays don't fire spuriously — e.g., a useCallback-wrapped function passed as a dependency to another effect. React does NOT guarantee memoized values survive forever (they can be discarded and recomputed, e.g., under memory pressure in future React versions), so code must stay correct even if the memoization never "hit."

      Follow-up: Does React 19's compiler change how often you should write useMemo manually?
      Why does an effect with `[]` deps still see fresh props on its *first* run but stale ones afterward?

      The effect closure is created fresh every render, but with `[]` deps React only ever executes the one created during the very first render (where "first-run" props happened to be current); every later render creates a new closure that is simply discarded without being called, since the effect never re-runs.

      Follow-up: How do you fix this without re-running the effect on every render?

      Advanced

      Design a `useEventCallback` hook that gives you a stable function identity that always calls the latest version of a handler, and explain exactly why naive approaches fail.

      Store the latest handler in a ref (updated every render, e.g. via useInsertionEffect or a plain assignment during render guarded correctly), and return a `useCallback(() => {}, [])`-stable wrapper function that calls `ref.current(...)`. Naive `useCallback(handler, [handler])` churns identity whenever the inline handler prop changes (which is every render if it's an inline arrow), defeating the purpose; storing it directly in a ref without updating via an effect risks reading a value from a stale commit if updated at the wrong phase (e.g., during render, which is disallowed for mutating refs read elsewhere during the same render pass).

      Follow-up: Why is useInsertionEffect specifically relevant here over a plain useEffect?
      Two sibling components both call the same custom hook `useToggle()`. Explain, down to the fiber level, why their boolean states are independent.

      Hook state lives in the calling fiber's own `memoizedState` linked list, one node per hook call *on that fiber*. Each sibling is a distinct fiber with its own independent hook linked list; calling the same JS function (`useToggle`) just runs the same `useState` call against whichever fiber is currently rendering (React tracks "current rendering fiber" in module-level state during render), so each call site's node lives entirely within its own fiber's list — nothing is shared by virtue of calling the same function.

      Follow-up: What would it take to actually share state across two sibling calls to the same hook?
      Explain precisely why batching state updates across a `setTimeout` callback works differently pre- and post-React 18, and what changed under the hood.

      Pre-18, React only auto-batched updates inside events it controlled (synthetic event handlers) — updates inside timers/promises/native event listeners each triggered a separate synchronous render. React 18's `createRoot` enabled "automatic batching" by changing the scheduler to batch any updates that occur before the microtask/macrotask yields control back, regardless of trigger source, by wrapping the update-processing in the same `unstable_batchedUpdates`-style mechanism universally rather than only inside React's own event dispatch.

      Follow-up: How can you opt out of batching for a specific update if you truly need synchronous re-render?
      Why does mutating a ref's `.current` during render (rather than in an effect or event handler) break React's concurrent rendering guarantees?

      Render-phase work is required to be pure and may be run multiple times for the same eventual commit (interrupted and restarted, or double-invoked under Strict Mode) without the component's author being able to tell. Mutating a ref during render means a discarded/replayed render still leaves behind a side effect, and under concurrent rendering, two in-progress renders (at different priorities) could even interleave and race on the same ref — refs are explicitly documented as safe to mutate only in effects/handlers/imperative code, not the render body itself.

      Follow-up: Is reading (not writing) a ref during render safe?
      What is the "temporal dead zone" problem React's exhaustive-deps lint rule cannot fully solve, and how do you handle it manually?

      exhaustive-deps works on syntactic dependency extraction — it can't know that a value is logically stable (e.g., a setter from useState, or a value you've proven monotonically-memoized through external means) versus genuinely needing to be tracked, nor can it detect dependencies hidden behind indirection (e.g., a value read via a ref, or a module-level mutable singleton). Handling it manually means either exposing the true dependency explicitly (even if the lint rule would've been silent), or consciously documenting + justifying an eslint-disable with a comment explaining the invariant that makes omission safe (e.g., "setCount identity is guaranteed stable by React").

      Follow-up: Give a concrete example where exhaustive-deps produces a false positive.

      Quick Revision Cheat Sheet

      • Hooks live in a linked list on the fiber, indexed by call order — never call conditionally.
      • Every render = a fresh function call = a fresh closure capturing that render's values.
      • Dependency arrays tell React which captured values make a closure "stale" when they change.
      • Functional updaters (`setX(x => ...)`) sidestep stale closures for the updated value itself.
      • Refs for "latest value without re-running an effect"; state for "value that should trigger render."
      • useLayoutEffect blocks paint (sync); useEffect runs after paint (async).
      • Custom hooks share no state across call sites — each call gets independent hook nodes.
      • React 18 batches updates everywhere by default, not just inside synthetic events.
      • Deriving state in an effect costs an extra render — compute inline when possible.
