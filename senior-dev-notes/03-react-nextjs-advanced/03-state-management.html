    State Management: Context, Redux Toolkit, Zustand, React Query

    ⏱ 2.5 hrs📍 Chapter 3 of 11

    One-line summary: The single highest-leverage decision in frontend architecture is classifying every piece of state as server cache, global client state, local UI state, or URL state — and picking a tool per category instead of forcing one store to do everything.

    On this page

      Why It Matters for a Senior Developer

      "Should this go in Redux?" is a trick question in a senior interview — the correct answer is almost always "it depends what kind of state it is," and demonstrating that taxonomy (plus knowing the real mechanics of Context re-renders) is what separates a senior from someone who's only used one tool.

      Prerequisites

      Read React Internals and Hooks Deep Dive first. Related: Performance.

      Core Concepts

      The four kinds of state

      • Server cache state: data that actually lives on a server and your client has a cached, possibly-stale copy of (user profile, product list). This is not client state at all — it needs revalidation, dedup, background refetch, and cache invalidation semantics that tools like Redux/Zustand don't provide out of the box. React Query (TanStack Query) or SWR exist specifically for this.
      • Global client state: state that's genuinely client-only and needed across distant parts of the tree (auth session, theme, feature flags, shopping cart). Context, Zustand, or Redux Toolkit.
      • Local UI state: state scoped to one component/subtree (form input value, modal open/ closed, hover state). Plain useState/useReducer, always — never lift this into a global store "just in case."
      • URL state: state that should survive a refresh or be shareable/bookmarkable (current tab, filters, pagination page). Belongs in the URL (search params), not in any JS store.

      How Context actually triggers re-renders

      Every component that calls useContext(MyContext) subscribes to that context. When the <MyContext.Provider value={...}> re-renders with a new value (compared by Object.is), React re-renders every subscribed consumer in the subtree, regardless of whether that consumer actually uses the specific field of the value object that changed — Context has no field-level selector mechanism built in. This is why putting a frequently-changing value (like mouse position) and a rarely-changing value (like theme) in the same context object is a classic performance mistake: every mouse-move re-renders every theme consumer too.

      Redux Toolkit: when the ceremony is worth it

      Redux Toolkit (RTK) is "Redux with the boilerplate removed" — createSlice generates action types/creators/reducers from a single object using Immer under the hood (so you write "mutating" code that's actually translated into immutable updates). RTK Query layers server-cache features (similar to React Query) on top of the same store. Reach for RTK when: multiple teams need a single predictable state shape with time-travel debugging, strict action-based auditability, or you're already deep in the Redux ecosystem (middleware, selectors with reselect/RTK's built-in memoized selectors). Its cost is verbosity and a learning curve for the action/reducer/selector mental model.

      Zustand: minimal global state without the ceremony

      Zustand is a small store built on a plain closure + useSyncExternalStore under the hood (the same primitive React itself uses for subscribing to external stores safely under concurrent rendering). Components subscribe with a selector function, and Zustand only re-renders a component when the selected slice actually changes (shallow-compared) — giving you Context's ergonomics without Context's "every consumer re-renders" problem. No providers required by default (though you can scope stores per-subtree if needed).

      React Query: solving the server-cache problem correctly

      React Query treats server data as a cache with a key (queryKey), not as state you manually store and update. It handles: deduplication of identical in-flight requests, background refetch on window focus/reconnect, stale-while-revalidate semantics, automatic retries with backoff, and cache invalidation via queryClient.invalidateQueries. Trying to replicate this with Redux/Zustand means hand-rolling loading/error/staleness logic for every endpoint — this is the #1 reason senior engineers reach for React Query over a general-purpose store for anything that originates from an API.

      How It Works Under the Hood

      Zustand and most modern libraries use useSyncExternalStore(subscribe, getSnapshot) — the React 18 primitive designed exactly for "state lives outside React, but components need to safely read it under concurrent rendering (torn reads must be avoided when a render is interrupted mid-flight)." The getSnapshot function must return a value that's referentially stable across calls unless the underlying data truly changed, or React re-renders in a loop. React Query internally uses the same primitive to subscribe components to query cache entries.

      Code Examples

      // Context pitfall: one object, mixed update frequencies -> over-rendering
const AppContext = createContext(null);
function AppProvider({ children }) {
  const [theme, setTheme] = useState("dark");
  const [cursor, setCursor] = useState({ x: 0, y: 0 }); // changes constantly
  // BAD: every cursor move creates a new object -> every consumer re-renders,
  // including ones that only care about `theme`.
  const value = { theme, setTheme, cursor, setCursor };
  return {children};
}

// FIX: split into two contexts by update frequency
const ThemeContext = createContext(null);
const CursorContext = createContext(null);
// Theme consumers never re-render on cursor movement, and vice versa.

// Zustand: selector-based subscription avoids the Context problem entirely
import { create } from "zustand";

const useCartStore = create((set) => ({
  items: [],
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
  removeItem: (id) => set((s) => ({ items: s.items.filter(i => i.id !== id) })),
}));

// Only re-renders when `items.length` changes, not on unrelated store updates
function CartBadge() {
  const count = useCartStore((s) => s.items.length);
  return {count};
}

// React Query: server cache done correctly
import { useQuery, useMutation, useQueryClient } from "@tanstack/react-query";

function useTodos() {
  return useQuery({
    queryKey: ["todos"],
    queryFn: () => fetch("/api/todos").then(r => r.json()),
    staleTime: 30_000, // treat data as fresh for 30s, skip refetch on remount
  });
}

function useAddTodo() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (todo) => fetch("/api/todos", { method: "POST", body: JSON.stringify(todo) }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["todos"] }), // refetch after mutation
  });
}

      Real-World Production Scenario at Scale

      At scale

      A dashboard app stored API responses (users, orders, metrics) directly inside a single Redux store, manually tracking loading/error flags per slice. As the number of endpoints grew past ~40, every new feature required hand-written thunk boilerplate for fetch/retry/cache invalidation, and stale data bugs (showing week-old cached orders after a mutation elsewhere) became common because invalidation was manual and inconsistent across slices. Migrating server-derived state to React Query (keeping Redux/Zustand only for genuinely client-only global state like UI panel visibility) cut the data-fetching code by roughly 60% and eliminated an entire category of staleness bugs by centralizing invalidation through query keys.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Putting server data into Redux/Zustand/Context "because that's our global store" is the most common senior-level architecture mistake in this space — it works, but it means hand-rolling cache invalidation, staleness, retries, and race-condition handling that a dedicated server-cache library already solved. The tell in an interview: if you need to ask "when do I refetch this?", it's server cache state.

      • One giant Context value mixing high- and low-frequency state — causes unrelated re-renders.
      • Lifting local UI state (e.g., a single input's focus state) into global state "for consistency."
      • Storing derived data in state instead of computing it from the source on render/selector.
      • Forgetting that Redux/Zustand selectors need to return stable references (or use shallow-compare) to avoid re-render loops.

      Interview Questions

      Basic

      When would you use Context vs. a dedicated state library?

      Context for simple, infrequently-changing global values with a small number of consumers. A dedicated library (Zustand/Redux) when state changes frequently, many unrelated components consume slices of it, and you need selective re-rendering.

      Follow-up: Does Context support selective subscription out of the box?
      What problem does React Query solve that useState/useEffect data fetching doesn't?

      Caching, deduplication of concurrent identical requests, background revalidation, retries with backoff, and consistent loading/error state — all without hand-written bookkeeping per endpoint.

      Follow-up: How does it know when cached data is "stale"?
      What is "lifting state up" and when should you NOT do it?

      Moving state to the nearest common ancestor of components that need it. You shouldn't do it when the state is genuinely local (e.g., one input's value) — lifting it unnecessarily causes extra re-renders in the ancestor's whole subtree.

      Follow-up: What's the alternative to lifting state for sharing it between distant siblings?
      What is URL state and why keep filters/pagination there?

      State encoded in the URL (search params/path) so it survives refresh, is shareable via link, and participates in browser back/forward navigation naturally — things no JS store gives you for free.

      Follow-up: What library/hook would you use in Next.js to read/write it?
      What does Redux Toolkit add on top of plain Redux?

      `createSlice` to generate actions/reducers from one object with Immer-powered "mutating" syntax, built-in `configureStore` with sensible middleware defaults (including thunk and dev tools), and RTK Query for server-cache management.

      Follow-up: What does Immer let you write that plain Redux reducers wouldn't allow?

      Medium

      Explain why a single Context re-renders all consumers even when they use different fields of the value.

      `useContext` subscribes a component to the nearest Provider's value as a whole; React has no built-in way to know a consumer only reads `value.theme` and not `value.cursor` — any new value reference triggers every subscriber's re-render. Selector-based libraries solve this by comparing the *selected slice*, not the whole object.

      Follow-up: How would you manually work around this using multiple contexts or memoized sub-components?
      How does Zustand avoid Context's over-rendering problem mechanically?

      Each `useStore(selector)` call subscribes via `useSyncExternalStore` and Zustand only notifies that subscriber if the selector's output changed (shallow equality by default); unrelated state changes in the same store don't trigger re-renders for selectors that didn't touch the changed slice.

      Follow-up: What happens if your selector returns a new object/array every call?
      Design the state architecture for a filterable, paginated data table in a dashboard app. What goes where?

      Filter values + page number -> URL search params (shareable, survives refresh). The actual row data for the current filter/page -> React Query keyed on those params (cache, refetch, loading/error state). Row selection / expanded-row UI state -> local useState in the table component. Any cross-page "saved views" feature -> Zustand or server-persisted via its own React Query mutation.

      Follow-up: Where would you put "is this column sortable ascending or descending" state?
      Why can RTK Query and React Query coexist awkwardly in a codebase, and when would you actually want both?

      They solve the same problem (server cache) with different APIs/cache stores, so using both means duplicated caching logic and two mental models. It can make sense transitionally during a migration, or if a team already has heavy Redux Toolkit investment (selectors, devtools, middleware) and wants RTK Query specifically for that ecosystem fit while a newer part of the app adopts React Query — but it should be a deliberate, temporary choice, not a steady state.

      Follow-up: What's the migration risk of having two separate caches for overlapping data?
      What's wrong with storing a fetched list's "filtered/sorted" derived version in state instead of computing it on render?

      It creates two sources of truth that can desync (the base list updates but the derived copy doesn't, or vice versa) and requires manual synchronization via effects, adding render cycles and bug surface. Computing the derived view inline (optionally via useMemo if the computation is expensive) guarantees it's always consistent with the current base data.

      Follow-up: When would caching the derived value with useMemo actually be necessary vs. premature?

      Advanced

      Explain how `useSyncExternalStore` prevents "tearing" under concurrent rendering, and why external stores needed a new primitive in React 18.

      Under concurrent rendering, React may render a tree at different points in time for different priority lanes, or restart a render after being interrupted. An external store (one React doesn't manage) can mutate between those renders; without a dedicated primitive, different parts of the same tree could read different snapshots of that external state during a single logical update, producing an inconsistent ("torn") UI. `useSyncExternalStore` forces a synchronous, consistent snapshot check (and forces a synchronous re-render if the snapshot changed since last render) specifically to rule this out, which is why library authors (Redux, Zustand, React Query) migrated their subscription internals to it.

      Follow-up: What would you have to do to make an external store "tearing-safe" in React 17 without this primitive?
      You need global state that's updated 60 times/second (e.g., a live cursor-position overlay shared across many components) without causing jank. Compare Context, Zustand, and a non-React approach.

      Context is disqualified outright — every update re-renders every consumer regardless of relevance. Zustand with a tightly-scoped selector only re-renders components that read the specific changing slice, which is viable but still pays React's render+commit cost per update for each subscriber. A non-React approach (directly mutating a DOM element's style/transform via a ref and an external event subscription, bypassing React's render cycle entirely for just that hot value) avoids React scheduling overhead altogether and is the standard pattern for this specific "very high frequency, purely visual" case.

      Follow-up: How would you still keep this testable/debuggable if you bypass React's render cycle?
      How does React Query decide a query is "stale" vs "fresh," and what's the actual mechanism for background refetch without flashing a loading state?

      Each query has a `staleTime` window after a successful fetch during which cached data is served with zero refetch on mount/focus. Past that window, a refetch triggers on relevant triggers (refocus, reconnect, mount) but the UI keeps showing the previous (now "stale") data via `isFetching` (background) rather than `isLoading` (no data yet) state, so consumers can choose to show a subtle "refreshing" indicator instead of blanking the UI — this is the stale-while-revalidate pattern implemented at the hook-state level.

      Follow-up: How would you implement optimistic updates on top of this without fighting the background refetch?
      Critique: "We put everything in Redux because it's the single source of truth and makes debugging easier." What's right and wrong about this in a 2025+ React/Next.js app?

      Right: a single predictable store with time-travel debugging genuinely helps for complex client-only state machines. Wrong: server data isn't a "client state" problem at all — forcing it through Redux means reimplementing cache invalidation/staleness/retry logic Redux has no opinion on, and in an App Router app a meaningful amount of data should never reach client JS as mutable state in the first place (it can be fetched in Server Components and streamed, with Server Actions handling mutations) — treating "single source of truth" as "one client store for everything" ignores that the server itself is often the actual source of truth.

      Follow-up: In an App Router app, what client-state categories genuinely still need Zustand/Redux?
      Design a selector memoization strategy for a Redux Toolkit app with deeply nested normalized state and explain the failure mode of a naive selector.

      A naive selector like `state => state.orders.map(id => state.ordersById[id])` returns a new array every call even if nothing changed, defeating `useSelector`'s reference-equality bailout and causing the consuming component to re-render on every unrelated store update. The fix is memoized selectors (via RTK's `createSelector`/reselect) that cache based on their actual input references (`state.orders`, `state.ordersById`), only recomputing the derived array when one of those inputs' references change — and structuring normalized state (entities keyed by id + an ids array) specifically so those input references stay stable across unrelated updates.

      Follow-up: What breaks this memoization if `ordersById` is rebuilt on every reducer run regardless of what changed?

      Practice Assignments

      Beginner (30-60 min)

      Classify and fix a Context over-rendering bug

      Build an app with one Context holding both `theme` and rapidly-updating `mouseCoords`. Add a console log in a component that only reads `theme`. Move the mouse and observe unnecessary re-renders; then split into two contexts and confirm the fix.

      Acceptance criteria: The theme-only consumer no longer re-renders on mouse movement.

      Hints

      React re-renders all consumers of a Provider whose value reference changed, with no field-level granularity.

      Bonus: Add a memoized selector-style wrapper component pattern as a third fix, without changing the context structure.

      Build the same feature twice: Zustand vs. React Query

      Build a "favorites" list feature where favorites are persisted server-side. Implement it once storing favorites in a Zustand store that manually fetches/syncs with the server, and once using React Query with optimistic updates via `useMutation`'s `onMutate`.

      • Simulate network latency and a failed mutation case.

      Acceptance criteria: Document which implementation handles the failed-mutation rollback more cleanly and why.

      Hints

      React Query's `onMutate`/`onError` pair is purpose-built for optimistic update + rollback; replicating it manually in Zustand means hand-writing the rollback snapshot logic yourself.

      Bonus: Add query invalidation so a second browser tab's favorites list updates after a window refocus.

      Advanced (1-2 days)

      Design a full state architecture for a multi-tab dashboard

      Given a hypothetical dashboard with: live metrics (polling), user-configurable saved views (server-persisted), a filter bar (should be shareable via URL), and a multi-step "create alert" wizard (local, ephemeral, multi-field), produce an architecture doc classifying every piece of state into one of the four categories and naming the specific tool/hook for each, with justification.

      • No single "put it all in Redux" answers accepted — justify each category independently.
      Hints

      Think about what should survive a refresh, what's shareable via link, and what truly needs cross-component subscription vs. local-only state.

      Quick Revision Cheat Sheet

      • Four categories: server cache, global client, local UI, URL state — pick a tool per category.
      • Server data -> React Query/SWR, never hand-rolled fetch+useState for anything nontrivial.
      • Context re-renders ALL consumers on any value change — no built-in field-level selectors.
      • Zustand/Redux selectors give field-level subscription via reference/shallow comparison.
      • Local UI state should stay local — don't lift "just in case."
      • Filters/pagination/active-tab -> URL search params, not a JS store.
      • Redux Toolkit = Redux + Immer-powered createSlice + RTK Query, worth it for large teams needing structure.
      • useSyncExternalStore is the React 18 primitive behind safe external-store subscriptions (tearing prevention).
