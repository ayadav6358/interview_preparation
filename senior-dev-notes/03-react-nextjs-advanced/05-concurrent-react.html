    Concurrent React: Suspense, Transitions, Streaming

    ⏱ 2.5 hrs📍 Chapter 5 of 11

    One-line summary: Concurrent React is a priority-based scheduler (the "lane model") that lets React prepare multiple versions of the UI at different urgencies and interrupt low-priority work for high-priority work — Suspense, transitions, and streaming SSR are all built on this one mechanism.

    On this page

      Why It Matters for a Senior Developer

      "Concurrent React" is widely used as a buzzword without engineers understanding the actual scheduling model underneath it. Being able to explain lanes, why Suspense needs them, and the difference between "concurrent" and "async" is a strong differentiator in Staff-level interviews, and it's the direct prerequisite for understanding Server Components streaming (Ch. 7).

      Core Concepts

      The lane model: priority as a bitmask

      Each unit of pending work is tagged with a lane — a bit in a 31-bit integer bitmask (SyncLane, InputContinuousLane, DefaultLane, TransitionLanes — a range of lanes for transitions, RetryLanes, IdleLane, etc.). Using a bitmask (rather than a single numeric priority) lets React represent and merge multiple simultaneous pending priorities on the same fiber with cheap bitwise operations (lanes | newLane to add, lanes & mask to check membership) instead of list/queue management. When React picks "the next lane to work on," it picks the highest-priority bit set anywhere in the tree and builds a render pass that satisfies all lanes at or above that priority, batching compatible updates together.

      startTransition / useTransition: marking work as low priority

      startTransition(callback) tells React: "state updates inside this callback are not urgent — render them as a lower-priority (transition) lane, and if something higher priority comes in before this finishes, throw away the in-progress work and handle that first." Critically, this does not debounce or delay the call — the update is scheduled immediately, just at lower priority, and React can still interrupt rendering it if the user keeps typing. useTransition adds an isPending boolean so you can show a stale-but-interactive UI with a loading affordance while the transition's render is in flight.

      useDeferredValue: a transition for a value you don't own

      useDeferredValue(value) returns a version of value that "lags behind" during urgent updates — internally it's implemented as a transition that updates an internal copy of the value once the urgent render is done, letting an expensive subtree keep rendering the old value (fast, already computed) while the fast-changing source value updates immediately elsewhere (e.g., the input box itself stays responsive, the filtered results underneath catch up a beat later).

      How Suspense actually works: throwing a promise

      Suspense's trick is almost absurdly simple at its core: a component that isn't ready to render throws a Promise instead of returning JSX. React catches that throw during the render phase, walks up to the nearest ancestor <Suspense> boundary, and renders its fallback instead — while registering a .then() on the thrown promise to retry rendering that subtree once it resolves. This is why use(promise) and Suspense-enabled data libraries (React Query's suspense mode, Next.js's fetch in Server Components) can transparently "pause" a component: they throw the in-flight promise the first time, and once it resolves and is cached, the retry render reads the resolved value synchronously instead of re-throwing.

      Streaming: rendering doesn't wait for the slowest child

      On the server, streaming SSR means React can flush HTML for the fallback of a Suspense boundary first, then — once the slow data resolves — stream a small inline <script> that swaps the fallback markup for the real content in place client-side, without a full page reload. This is the mechanism behind Next.js App Router's loading.js and nested <Suspense> boundaries — the page's shell can reach the browser and become visible far before the slowest data-dependent section finishes.

      How It Works Under the Hood

      When React starts a render, it collects the set of lanes with pending work and determines the render lanes for this pass (usually the highest-priority lane plus any lanes that can be batched with it safely). If, mid-render, an update comes in on a lane of strictly higher priority than the one currently rendering, React doesn't try to merge it into the current in-progress WIP tree — it abandons that WIP tree (safe, because nothing has committed — see the double-buffering model in Ch. 1) and starts a fresh render at the new higher-priority lane. Once that higher-priority work commits, React returns to the lower-priority (e.g., transition) lane and resumes/restarts rendering it. This is the literal mechanism behind "typing in an input stays responsive even while a big list re-filters in the background" — the keystroke's lane always wins.

      Real-World Production Scenario at Scale

      At scale

      A product catalog page re-filtered 20,000 items on every keystroke in a price-range slider, freezing the slider's own drag interaction for ~150ms per step because both the slider's own state and the expensive filtered-list render were part of the same synchronous update. Wrapping the filtered list's update in startTransition (keeping the slider's own visual position update urgent/outside the transition) let the slider track the mouse at full frame rate while the list caught up a moment later with a subtle pending indicator — no debounce delay was introduced, since the filtering still started immediately, it just yielded to drag-input updates.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      "Concurrent" does not mean "runs in parallel" or "asynchronous" — React is still single-threaded and synchronous during each actual render/commit pass. "Concurrent" means React can interleave preparing multiple versions of the UI at different priorities over time, interrupting lower-priority work, not that two renders literally execute simultaneously.

      • Wrapping the state update for the input's own value inside startTransition — this makes typing itself feel laggy, since the input's visual feedback is now deprioritized too.
      • Expecting startTransition to debounce — it doesn't delay the call, only deprioritizes the resulting render.
      • Using Suspense fallback for errors — a thrown non-promise (an actual Error) is not caught by Suspense, you need an Error Boundary alongside it.
      • Forgetting that a Suspense boundary resets all state of its children on re-suspend unless explicitly preserved (e.g., with `key` strategy or `startTransition` to avoid the fallback entirely during a revisit).

      Interview Questions

      Basic

      What problem does Concurrent React solve?

      It lets React prepare UI updates at different priorities and interrupt lower-priority rendering work when something more urgent (like user input) comes in, keeping the app responsive during expensive updates.

      Follow-up: Does this make React multi-threaded?
      What's the difference between useTransition and useDeferredValue?

      useTransition wraps a state update you trigger, marking it low priority and exposing an isPending flag. useDeferredValue takes an existing value (often from props) and returns a lagging copy for use in expensive derived rendering, without you controlling the original update site.

      Follow-up: Can you use both together?
      How does Suspense know when to show the fallback?

      A descendant component throws a Promise during render; React catches it, finds the nearest Suspense ancestor, and shows its fallback until the promise resolves, then retries rendering that subtree.

      Follow-up: What happens if a plain Error (not a Promise) is thrown inside a Suspense boundary?
      What is streaming SSR?

      Sending HTML to the browser in chunks as it becomes ready, instead of waiting for the entire page's data to resolve — fast parts of the page (and Suspense fallbacks for slow parts) reach the browser first, with slow sections swapped in once ready.

      Follow-up: What HTTP mechanism allows a server to send a response in chunks?
      Does startTransition delay when the update happens?

      No — the update is scheduled immediately, just at lower priority, meaning React may interrupt it for higher-priority work before it finishes, not that it waits before starting.

      Follow-up: How is this different from debouncing?

      Medium

      Explain the lane model and why React uses a bitmask rather than a single numeric priority value.

      A bitmask lets a single fiber represent multiple simultaneously-pending priorities (e.g., a sync update and a transition update both pending on the same component) and lets the scheduler use cheap bitwise operations to merge/check/clear priorities across a whole subtree, rather than needing list/queue structures per fiber. Picking "what to render next" becomes finding the highest-priority set bit across the root's aggregated lanes.

      Follow-up: What happens when two different lanes' updates touch overlapping parts of the tree?
      Walk through exactly what happens when a higher-priority update arrives while a transition render is in progress.

      React does not try to merge the new update into the in-progress WIP tree. Because nothing has committed yet (double buffering — the WIP tree is disposable), React abandons that in-progress render, starts a fresh render pass for the higher-priority lane (potentially on the same WIP fiber objects, just restarted), commits it, and only afterward returns to restart the transition lane's render from scratch.

      Follow-up: Is any work from the abandoned transition render reused, or is it fully redone?
      Why does `use(promise)` need to be paired with a cache, and what breaks if you call fetch() directly inside use()?

      Suspense works by throwing and re-rendering on retry; if you create a brand-new Promise inside the component body every render (e.g., calling fetch directly without caching), each retry throws a *new* unresolved promise instead of eventually reading a resolved cached one, causing an infinite suspend loop instead of ever rendering the resolved value.

      Follow-up: How do frameworks like Next.js handle this caching for you automatically?
      Why does a Suspense boundary reset its children's state when it re-suspends, and how would you avoid losing scroll position on a revisit?

      When a subtree re-suspends, React unmounts the previously-rendered content and shows the fallback again by default (since the content may be stale/incorrect once a dependency changes) — mounted state (local component state, scroll position) is lost with the unmount. To preserve it on predictable navigations, wrap the triggering update in startTransition so React prefers keeping the old content visible (showing isPending) rather than falling back to the Suspense boundary, when supported by the data source.

      Follow-up: Does this avoid-fallback behavior work for the *initial* mount of a Suspense boundary?

      Advanced

      Explain why Suspense "throwing a promise" needed the fiber double-buffering model from Ch. 1 to be safe, specifically.

      Throwing out of a component mid-render means the render phase is abandoned for that subtree without committing anything — which is only safe because render-phase work never mutates the current (on-screen) tree or the real DOM; it only builds the disposable WIP tree. If render-phase work were allowed to have side effects or partially mutate shared state, a thrown promise mid-render would leave the UI/state in an inconsistent half-updated condition. Suspense is, in effect, a deliberate exploitation of the render phase's purity/interruptibility guarantee that Fiber was built to provide.

      Follow-up: Could Suspense have been implemented pre-Fiber, on the old stack reconciler?
      Two components in the same tree suspend on different promises at the same time, under one shared Suspense boundary. Explain exactly how React decides when to stop showing the fallback.

      React tracks all thrown promises registered against that boundary's render attempt; the boundary only retries rendering (and stops showing fallback) once *all* outstanding suspensions for that commit have resolved — it doesn't partially render with one resolved and one still-pending, since that would mean committing an incomplete tree. This is why granular loading UX requires multiple nested Suspense boundaries rather than one shared one, if you want independent resolve-and-reveal per section.
