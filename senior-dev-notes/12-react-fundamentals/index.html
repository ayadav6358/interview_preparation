    React Fundamentals

    📚 6 chapters⏱ ~11–13 hrs total

    A fast, precise refresher of the React fundamentals layer — written for someone who already ships React daily but wants the "complete mental model, stated correctly" before moving into React & Next.js Advanced (Fiber, concurrent rendering, Server Components). No beginner hand-holding: every chapter assumes you can already write a component, but makes sure the fundamentals are stated with the precision a senior interviewer expects — JSX semantics, props/state/events, the hooks you touch 100 times a day, forms, routing, and how a real project is actually structured and tooled in 2025–26 (Vite, React 19).

    Learning Outcomes

    • Explain precisely what JSX compiles to and why component composition is React's core abstraction — not inheritance.
    • Articulate the exact contract of props vs. state, and correctly apply "lifting state up" to fix shared-state bugs.
    • Use useState and useEffect correctly, including dependency arrays and cleanup, without reaching for the Fiber-level internals (that's topic 03).
    • Build controlled forms with validation and multi-step flows without a form library, and know when to reach for one.
    • Wire up client-side routing with React Router — nested routes, params, protected routes — from memory.
    • Set up and reason about a modern Vite-based React project: file layout, env vars, build/bundle basics, npm scripts.

    🏆 Capstone Project: Build a "Recipe Book" Multi-Page React App

    Problem statement: Build a small, deliberately fundamentals-only multi-page app (Vite + React 19, plain client-side React Router — no Next.js, no Server Components, no RSC) that lets a user browse recipes fetched from a public API, search/filter them, view a detail page, and manage a personal "favorites" list with a multi-step "add your own recipe" form.

    Required features:

    • Componentized UI: a reusable RecipeCard, SearchBar, FavoritesList, layout shell with nav — clean props-down composition, no prop-drilling past 2 levels (lift state or use Context where it genuinely helps).
    • Routing: a home/list route, a recipe detail route with a URL param (/recipes/:id), a favorites route, and a protected "add recipe" route that redirects to a fake login if "not authenticated" (local state is fine).
    • Data fetching from a public API (e.g. TheMealDB or similar) inside useEffect, with explicit loading, error, and empty states — no silent failures.
    • A multi-step controlled form ("add your own recipe": basics → ingredients → review) with field-level validation and a working back/next flow that preserves state across steps.
    • Favorites persisted to localStorage, synced via a small custom hook.

    Tech stack suggestion: Vite, React 19, React Router v6/v7, plain CSS or a lightweight utility framework — no Next.js, no server components, no external state library (useState/useContext is enough at this scale).

    Milestones:

    1. Scaffold with Vite, set up project structure and npm scripts (Ch. 6), get a static component tree rendering.
    2. Wire up React Router with all routes including the param route and a protected route guard.
    3. Fetch real data in useEffect with loading/error/empty states; componentize the list and detail views.
    4. Build the multi-step add-recipe form with controlled inputs and validation (Ch. 4).
    5. Add the favorites feature with a custom useLocalStorage hook; lift/share state correctly (Ch. 2–3).
    6. Polish: env var for the API base URL, a production build, and a short README documenting the file structure.

    Evaluation checklist:

    • ☐ No component receives a prop it doesn't use just to pass it further down (no needless prop-drilling).
    • ☐ Every useEffect that subscribes/fetches has a correct dependency array and, where needed, a cleanup function.
    • ☐ Form state is fully controlled and validation runs at the right time (not just on submit, not on every keystroke if that's noisy).
    • ☐ Refreshing the browser on a deep route (e.g. /recipes/42) still works.
    • ☐ Can explain, out loud, why this app deliberately does NOT need Next.js, RSC, or a global state library at this scale.
