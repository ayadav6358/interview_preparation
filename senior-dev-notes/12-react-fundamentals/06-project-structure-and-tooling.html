    Project Structure & Tooling: Vite, File Layout, Build & Env Vars

    ⏱ 1.5 hrs📍 Chapter 6 of 6

    One-line summary: A modern React project is a thin layer of your source files on top of a build tool (Vite, in 2025–26 the default choice over Create React App) that bundles, transforms, and serves them — knowing what that tool actually does, how to organize files by feature, and how env vars/npm scripts fit together is table-stakes project literacy for a senior dev.

    On this page

      Why It Matters for a Senior Developer

      Every real React job involves onboarding into (or designing) a project structure, debugging a build failure, and knowing why an env var "isn't working." These are mundane, high-frequency problems that separate someone who's only ever worked inside a pre-built scaffold from someone who understands what's actually happening when npm run dev and npm run build execute. It's also directly relevant to system design-adjacent interview questions about bundle size, code splitting, and why Create React App was officially deprecated in favor of Vite-based tooling.

      Prerequisites

      Requires general comfort with npm/Node.js tooling — see npm & Package Management (Node.js Fundamentals topic) if that's shaky. Builds on everything in this topic since it's the "how do all these files and routes and components actually get organized and shipped" capstone chapter. Contrast with React & Next.js Advanced, where the framework (Next.js) takes over most of these concerns (routing-by-file, built-in bundling decisions, server/client boundaries).

      Core Concepts

      Why Vite, and what it actually does

      Create React App is officially deprecated/unmaintained as of recent years; Vite is the standard modern choice. The core difference that matters: CRA's dev server bundled your entire app with webpack before serving anything, so dev-server startup and rebuild-on-change got slower as the app grew. Vite serves source files over native ES modules in development — the browser itself requests each module as needed, and Vite transforms files on-demand (via esbuild, which is 10-100x faster than JS-based bundlers for transforms) — so dev startup is near-instant regardless of app size, and only the files that actually changed are re-transformed on save. For production, Vite switches to Rollup to produce an optimized, bundled, code-split, minified build — dev and prod intentionally use different strategies optimized for their different goals (fast iteration vs. smallest/fastest-loading output).

      Organizing files: by feature, not by file type

      Two broad conventions exist. "By type" (a top-level components/, hooks/, pages/ folder each holding everything of that kind) scales poorly past a small app — finding everything related to "recipes" means hunting across 4+ folders. "By feature/domain" colocates a feature's components, hooks, and styles together, with only truly cross-cutting things (a generic Button, a useDebounce hook) living in a shared top-level folder. Most teams at scale converge on feature-based structure:

      src/
  app/              # top-level App, router setup, providers
  features/
    recipes/
      RecipeCard.jsx
      RecipeList.jsx
      useRecipes.js
      recipes.api.js
    favorites/
      FavoritesList.jsx
      useFavorites.js
  components/       # truly shared, generic UI (Button, Modal, Spinner)
  hooks/            # truly shared, generic hooks (useDebounce, useLocalStorage)
  lib/              # non-React utilities (formatters, constants)
  main.jsx          # entry point -- createRoot().render(<App />)
index.html          # Vite's actual entry point -- not public/index.html like CRA

      Note the inverted entry point compared to CRA: in Vite, index.html lives at the project root and directly <script type="module" src="/src/main.jsx">-references your source — CRA hid this behind webpack config and a public/index.html with a magic %PUBLIC_URL% placeholder.

      Environment variables: build-time, not runtime, and intentionally exposed

      Vite exposes env vars to client code only if prefixed VITE_ (a deliberate security boundary — anything NOT prefixed stays server/build-tool-only and never reaches the browser bundle, preventing accidental leakage of secrets meant only for the build process). Access via import.meta.env.VITE_API_URL, not process.env (that's Node/webpack/CRA's convention; Vite's is ESM-native import.meta.env). Critically, these are baked in at build time, not read at runtime — a production build has the values from whatever .env file was present when you ran vite build literally inlined into the bundled JS; changing the env var after building does nothing until you rebuild.

      # .env.development
VITE_API_URL=http://localhost:3001

# .env.production
VITE_API_URL=https://api.myrecipeapp.com
      const res = await fetch(`${import.meta.env.VITE_API_URL}/recipes`);

      npm scripts: the actual commands behind the workflow

      A Vite React project's package.json scripts, and what each literally does:

      {
  "scripts": {
    "dev": "vite",            // starts the dev server with HMR, native ESM, instant startup
    "build": "vite build",     // produces an optimized dist/ build via Rollup -- minified, code-split
    "preview": "vite preview", // serves the dist/ build locally to sanity-check prod behavior
    "lint": "eslint ."         // static analysis -- catches hook-rule violations, unused vars, etc.
  }
}

      Senior-level detail that gets tested: vite build output is static files — HTML/JS/CSS — meant to be served by any static file server or CDN; there's no Node.js server required to run a plain Vite React app in production (unlike Next.js's server-rendering model), which is exactly why the SPA-fallback deployment gotcha from Chapter 5 exists.

      How It Works Under the Hood

      What actually happens on npm run build:

      1. Vite reads index.html as the entry point, following its <script type="module"> reference into your source graph (every import statement, transitively).
      2. JSX/TS is transformed to plain JS (via esbuild) for every file in that graph.
      3. Rollup bundles the transformed modules together, applying tree-shaking (removing exported code that's never actually imported anywhere) and code-splitting (separate chunks for lazy-loaded routes, so users don't download JS for pages they haven't visited).
      4. Assets (CSS, images) are processed, hashed for cache-busting filenames, and emitted into dist/ alongside the final HTML with correct <script>/<link> tags injected.
      5. import.meta.env.VITE_* references are replaced with their literal values at this build step — they do not exist as runtime lookups in the shipped code.

      flowchart TD A[npm run dev] --> B[Vite dev server starts] B --> C[Browser requests index.html] C --> D[Browser requests main.jsx as native ES module] D --> E[Vite transforms JSX/TS on-demand via esbuild] E --> F[Only changed files re-transformed on save -- HMR] G[npm run build] --> H[Vite resolves full import graph from index.html] H --> I[esbuild transforms all files] I --> J[Rollup bundles + tree-shakes + code-splits] J --> K[dist/ -- static HTML/JS/CSS, ready for any static host]

      Code Examples

      // A feature-colocated custom hook -- keeps data-fetching logic out of
// components and out of a generic "hooks/" grab-bag, since it's specific
// to the recipes feature.
// src/features/recipes/useRecipes.js
import { useState, useEffect } from "react";

export function useRecipes() {
  const [recipes, setRecipes] = useState([]);
  const [status, setStatus] = useState("idle"); // idle | loading | success | error

  useEffect(() => {
    const controller = new AbortController();
    setStatus("loading");

    fetch(`${import.meta.env.VITE_API_URL}/recipes`, { signal: controller.signal })
      .then(res => res.json())
      .then(data => { setRecipes(data); setStatus("success"); })
      .catch(err => { if (err.name !== "AbortError") setStatus("error"); });

    return () => controller.abort();
  }, []);

  return { recipes, status };
}

      Real-World Production Scenario at Scale

      At scale

      A team hardcoded their staging API's base URL directly into several fetch calls across the codebase "temporarily" during a sprint, intending to parameterize it later. Weeks later, a production deploy shipped with staging URLs baked into several (but not all) bundled chunks, causing a subset of features to silently talk to the staging backend in production — invisible until someone noticed staging data appearing live. Because env values are inlined at build time, there was no way to "fix" this without a full rebuild and redeploy (a runtime config change could not have patched it). The fix: centralize every external base URL behind import.meta.env.VITE_API_URL, add a lint rule banning hardcoded URLs matching the known API domains, and add a build-time assertion that fails the build if the expected VITE_* vars aren't set for the target environment.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Expecting an env var change to take effect without rebuilding: because Vite inlines import.meta.env.VITE_* values at build time, changing a .env file (or a deployment platform's environment variable setting) and just restarting the already-built app does nothing — you must re-run vite build for the new value to actually appear in the shipped JS. This differs from server-side runtime env vars (e.g. in a Node.js backend), which genuinely are read fresh at process start — a common source of confusion for developers moving between frontend and backend env-var mental models.

      • Putting a secret (API key meant to stay server-side) in a VITE_-prefixed var — it gets bundled directly into client-visible JS; anything truly secret must stay out of the client bundle entirely and live behind a backend proxy.
      • Organizing by file-type (components/, hooks/) past the point an app outgrows it, making every feature change require touching 3+ unrelated top-level folders — migrate to feature-based structure before this becomes painful, not after.
      • Assuming vite build output needs a Node server to run — it's static files; deploying it behind an unnecessary Node/SSR server adds operational complexity a plain SPA doesn't need.

      Interview Questions

      Basic

      Why has the React community largely moved from Create React App to Vite?

      CRA is officially deprecated/unmaintained and its webpack-based dev server bundled the whole app before serving anything, getting slower as apps grew. Vite serves native ES modules on-demand in dev (near-instant startup regardless of app size) and uses esbuild for fast transforms, switching to Rollup for an optimized production build.

      Follow-up: Does Vite use the same bundler for dev and production?
      How do you expose an environment variable to client-side code in Vite?

      Prefix it `VITE_` in a `.env` file, then access it via `import.meta.env.VITE_YOUR_VAR` in your code -- unprefixed vars are not exposed to client bundles.

      Follow-up: What happens if you try to access a non-VITE_-prefixed var from client code?
      What does `npm run build` actually produce, and how is it typically deployed?

      A `dist/` folder of static HTML/JS/CSS assets, ready to be served by any static file host or CDN -- no Node.js server is required to run a plain Vite React app in production.

      Follow-up: What deployment gotcha does this create for client-side routing?
      What's the practical difference between organizing files "by type" vs. "by feature"?

      By-type groups files by what they ARE (all components together, all hooks together); by-feature groups files by what they BELONG TO (everything for "recipes" together). By-feature scales better as an app grows since related changes stay colocated.

      Follow-up: What kind of code should still live in a shared, by-type-ish folder even in a feature-based structure?

      Medium

      Why are Vite env vars inlined at build time rather than read at runtime, and what practical consequence does that have?

      Because the production output is static JS with no runtime process to read `process.env` from -- there's no server process executing your React code in the browser. The consequence: changing an env var after a build is deployed has zero effect until you rebuild and redeploy; this differs from backend Node.js services where env vars genuinely are read at process startup from the live environment.

      Follow-up: How would a CI/CD pipeline need to be structured to support different env values per environment (staging vs. prod)?
      Why is the `VITE_` prefix requirement a deliberate security boundary, not just a naming convention?

      A Vite project's `.env` files often also hold values meant only for build-time tooling or local scripts (database URLs, deploy tokens) that must never end up in client-visible JS. Requiring an explicit `VITE_` prefix to expose a var to `import.meta.env` means forgetting the prefix is the SAFE default (var stays build-tool-only) rather than the dangerous default (var leaks to the browser) -- an intentional fail-safe design choice.

      Follow-up: What would the safer vs. more dangerous design look like if the prefix requirement were inverted?
      What does tree-shaking actually require from your code to work correctly, and what can defeat it?

      Tree-shaking relies on statically analyzable ES module `import`/`export` statements -- the bundler needs to determine, without running the code, which exports are never imported anywhere so it can remove them. It's defeated by patterns that hide usage from static analysis: dynamic `require()`-style access, re-exporting an entire module as a namespace object and using only one property off it (sometimes), or side-effectful module code the bundler can't prove is safe to remove even if its exports are unused.

      Follow-up: Why might a `import * as utils from "./utils"` followed by `utils.formatDate()` tree-shake worse than a named import?

      Advanced

      Why does Vite deliberately use different bundling strategies for dev (esbuild, native ESM, no real bundling) vs. prod (Rollup, full bundling)?

      Dev and prod optimize for different, partially conflicting goals. Dev wants the fastest possible iteration loop -- startup time and per-save rebuild time matter far more than final output size, since nothing in dev is actually shipped to users; serving native ES modules lets the browser fetch only what's needed per page load with zero bundling step, and esbuild's speed advantage (written in Go, highly parallel) minimizes per-file transform latency. Prod wants the smallest, most cache-efficient, fewest-request output for real users on real networks -- which needs full bundling, tree-shaking, and code-splitting, a fundamentally different (slower, more thorough) analysis that would be wasteful to re-run on every file save during development.

      Follow-up: Why doesn't Vite just use Rollup for dev too, given it's "more correct" bundling?
      A teammate wants to read a "live" feature-flag value from a backend at runtime rather than bake it into the Vite build. How would you architect that, and why can't `import.meta.env` do it?

      `import.meta.env.VITE_*` values are replaced with literal constants at build time -- there's no code left at runtime that "looks up" the value, so it fundamentally cannot change without a rebuild. For genuinely dynamic, runtime-configurable flags, you need an actual runtime data source: a fetch to a feature-flag/config endpoint on app load (stored in state, not baked into the bundle), or a small `config.json` served alongside the static build that's fetched at startup and can be edited/redeployed independently of the JS bundle.

      Follow-up: What's the tradeoff of the config.json approach vs. a feature-flag service API call?
      How does code-splitting interact with React Router to affect what a user actually downloads on first load?

      Combining Rollup's code-splitting with `React.lazy()` + route-level dynamic `import()` means each route's component code becomes its own chunk, fetched only when that route is actually navigated to, rather than the entire app's JS (every route's code) being downloaded upfront in one bundle. This is a deliberate architectural choice at the routing layer -- Vite/Rollup CAN split automatically at dynamic import boundaries, but the DEVELOPER decides where those boundaries are by choosing to lazy-load a route versus statically importing it.

      Follow-up: What's a reasonable heuristic for which routes/components are worth lazy-loading vs. not?

      Practice Assignments

      Beginner (30-60 min)

      Scaffold and inspect a Vite project

      Run npm create vite@latest (React template), then without writing any app code, read through the generated index.html, vite.config.js, and package.json scripts. Run dev, build, and preview, and inspect the generated dist/ folder's contents.

      Acceptance criteria: You can explain, in your own words, what each of the three npm scripts actually does and point to the specific files in dist/ that correspond to your source code.

      Hints

      Open the hashed JS filename in `dist/assets/` and search for a distinctive string from your source code to confirm it's really in there.

      Bonus: Add a `VITE_` env var, use it in `App.jsx`, and confirm it appears as a literal string in the built JS (search the `dist/` output for it).

      Intermediate (2-4 hrs)

      Migrate a flat project to feature-based structure

      Given (or reusing your own) a small app with a flat components//hooks/ structure, reorganize it into feature-based folders, correctly separating truly shared/generic code from feature-specific code, updating all imports.

      Acceptance criteria: App still builds and runs identically; a reviewer can find every file related to one feature in a single folder.

      Hints

      If you're unsure whether something is "shared" or "feature-specific," ask: would a second, unrelated feature plausibly reuse this exact code unmodified?

      Bonus: Set up path aliases (e.g. `@/features/...`) in `vite.config.js` to avoid long relative import chains.

      Advanced (1-2 days)

      Finalize the capstone's structure, env config, and production build

      Reorganize the capstone project into a feature-based structure (recipes/, favorites/, auth/), centralize the API base URL behind a VITE_API_URL env var with separate .env.development/.env.production values, add React.lazy() code-splitting for at least the add-recipe route, and verify a full production build + preview works correctly including the deep-route-refresh behavior from Chapter 5.

      Quick Revision Cheat Sheet

      • Vite replaces CRA (deprecated): native ESM + esbuild in dev, Rollup for optimized prod builds.
      • Organize by feature/domain past trivial app size — not by file type (components/, hooks/ grab-bags).
      • Env vars need the VITE_ prefix to reach client code; access via import.meta.env.
      • Env values are inlined at build time — changing them requires a rebuild, not just a restart.
      • Never put real secrets in VITE_-prefixed vars — they ship visibly in the client bundle.
      • vite build output is static files — no Node server needed to run a plain SPA in prod.
      • Static-host deploys of an SPA need a rewrite/fallback rule to serve index.html for unmatched paths.
      • React.lazy() + route-level dynamic import gives real code-splitting — users don't download unvisited routes' JS.
