    Hooks Basics: useState and useEffect, Solid Working Knowledge

    ⏱ 2.5 hrs📍 Chapter 3 of 6

    One-line summary: useState gives a component memory across renders, useEffect lets it synchronize with something outside React (the DOM, a subscription, a fetch) after render — this chapter gets you to "solid working knowledge" of both; the Fiber-level "why" behind hook ordering and scheduling lives in topic 03's deeper hooks chapter.

    On this page

      Why It Matters for a Senior Developer

      These two hooks are used in nearly every component you'll ever write, which means their misuse (wrong dependency array, missing cleanup, derived state stored redundantly) is also the single largest source of real production bugs: memory leaks from unremoved subscriptions, infinite fetch loops, stale closures reading old prop values. An interviewer asking "what's wrong with this `useEffect`" is testing whether you've actually internalized the dependency-array contract, not whether you've memorized the hook's signature.

      Requires Props, State & Events (state fundamentals). Feeds into Forms & Controlled Components and the capstone's data-fetching requirement.       Core Concepts

      useState: the working model

      const [state, setState] = useState(initialValue). Two forms of the setter matter: setState(newValue) replaces the value outright; setState(prev => next) (the updater function) computes the next value from the current one, and is the only safe form when the new value depends on the previous value and you can't guarantee you're reading the latest state (e.g., multiple rapid updates, or updates inside a closure created earlier). initialValue can also be a function (useState(() => expensiveInit())) — "lazy initialization" — which React calls only once, on mount, instead of on every render (important if computing the initial value is non-trivial).

      useEffect: synchronizing with something outside React

      The mental model that actually holds up: useEffect is not "run code after render" in a generic sense — it's specifically for synchronizing a component with an external system (DOM APIs, network subscriptions, timers, third-party widgets, browser storage). Its signature:

      useEffect(() => {
  // setup: runs after the DOM has been updated for this render
  return () => {
    // cleanup: runs before the NEXT effect run, and on unmount
  };
}, [dep1, dep2]); // dependency array

      The dependency array tells React when to re-run the effect: React compares each dependency to its value from the previous render using Object.is; if any changed, the old cleanup runs first, then the new setup runs. Three distinct array forms, three distinct behaviors — this is the single most interview-tested fact in this chapter:

      • No array at all — effect runs after every single render. Rarely what you want.
      • [] (empty array) — effect runs once after the first render (mount) only, cleanup runs once on unmount.
      • [a, b] — effect re-runs whenever a or b changes between renders (by reference for objects/arrays/functions, by value for primitives).

      Cleanup functions: preventing leaks and stale subscriptions

      Anything an effect sets up that outlives a single render — an event listener, an interval, a WebSocket, an in-flight fetch you want to ignore if the component unmounts — needs a cleanup function that undoes it. React calls cleanup (a) right before re-running the effect due to a dependency change, and (b) when the component unmounts. Skipping cleanup for a subscription is the single most common memory-leak pattern in real React codebases.

      useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/recipes/${id}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setRecipe)
    .catch(err => {
      if (err.name !== "AbortError") setError(err);
    });

  return () => controller.abort(); // cancel stale in-flight request if `id` changes or we unmount
}, [id]);

      The dependency-array pitfalls that actually bite in production

      • Missing a dependency (e.g. using userId inside the effect but not listing it) means the effect's closure captures a stale value from whenever it was last created — the effect won't re-run when userId changes, silently showing data for the wrong user. eslint-plugin-react-hooks's exhaustive-deps rule catches this and should never be disabled casually.
      • Objects/functions as dependencies created fresh every render (e.g. an inline { id } object or an inline arrow function) make the dependency array "always different," causing the effect to re-run every render regardless of whether the logically-meaningful value changed — the fix is to depend on primitives directly, or stabilize the reference with useMemo/useCallback.
      • Fetching without a request-cancellation guard — if id changes quickly (fast navigation between two recipes), an older, slower response can resolve after a newer one and overwrite it with stale data ("race condition"). Guard with AbortController or an "is this still the latest request" flag.

      How It Works Under the Hood

      At the fundamentals level (full scheduling mechanics are in topic 03):

      1. React renders the component, calling hooks in the exact same order every render — this is why hooks can't be called conditionally or in loops: React tracks each hook's state by call order/position, not by name.
      2. After the render commits and the DOM is updated, React runs effect setup functions in the order they were declared (and runs any pending cleanup from the previous commit for that effect first).
      3. On the next render where a listed dependency changed, React runs that effect's cleanup (from the previous run), then its new setup — using the fresh closure with current values.
      4. On unmount, React runs every active effect's cleanup one final time, in roughly reverse declaration order.

      Code Examples

      // BAD: stale closure bug -- effect doesn't list `step`, so clicking
// "faster" has no effect because the interval's closure still has the old step.
function Counter() {
  const [count, setCount] = useState(0);
  const [step, setStep] = useState(1);

  useEffect(() => {
    const id = setInterval(() => setCount(c => c + step), 1000);
    return () => clearInterval(id);
  }, []); // missing `step` dependency -- bug

  return (
    <>
      <p>{count}</p>
      <button onClick={() => setStep(s => s + 1)}>faster</button>
    </>
  );
}

// GOOD: list every value the effect reads; interval correctly restarts
// with the new step each time it changes.
function Counter() {
  const [count, setCount] = useState(0);
  const [step, setStep] = useState(1);

  useEffect(() => {
    const id = setInterval(() => setCount(c => c + step), 1000);
    return () => clearInterval(id);
  }, [step]); // correct

  return (
    <>
      <p>{count}</p>
      <button onClick={() => setStep(s => s + 1)}>faster</button>
    </>
  );
}

      Real-World Production Scenario at Scale

      At scale

      A dashboard's "live price ticker" component subscribed to a WebSocket inside useEffect with dependencies [], intending "subscribe once on mount." The symbol the user was watching was actually a prop (symbol) that could change when the user switched tickers from a dropdown — but because symbol wasn't in the dependency array, the effect never re-ran, so switching tickers kept the OLD WebSocket subscription alive (showing stale prices for the wrong symbol) while also never cleaning up the original connection when the component eventually unmounted elsewhere in the app, leaking one live WebSocket connection per ticker switch. Root cause: the dependency array was treated as "run once" configuration rather than "re-synchronize when these values change," and the missing cleanup compounded it into a connection leak. Fixed by adding symbol to the array and returning a cleanup that closes the socket.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      "I'll just disable exhaustive-deps for this one effect" is almost always treating a symptom. If a dependency genuinely shouldn't trigger a re-run (e.g., a setter function from useState, which is guaranteed stable across renders), that's fine to omit with justification — but omitting a value that actually changes and matters is how stale-closure bugs enter production code silently, since nothing crashes, it just silently uses old data.

      • Calling hooks conditionally or inside loops/nested functions — React requires hooks to run in the identical order on every render; conditional hook calls corrupt that order and throw at runtime.
      • Using useEffect to derive/sync state that could just be computed directly during render (e.g., useEffect(() => setFullName(first + " " + last), [first, last])) — this adds an extra render pass for no reason; just compute const fullName = first + " " + last inline.

      Interview Questions

      Basic

      What are the three forms of a `useEffect` dependency array and what does each mean?

      No array: runs after every render. Empty array `[]`: runs once on mount, cleanup once on unmount. Array with values: re-runs whenever any listed value changes between renders (by Object.is comparison).

      Follow-up: What happens if you list a dependency that never actually changes?
      When does the cleanup function returned from `useEffect` run?

      Right before the effect re-runs due to a changed dependency, and once when the component unmounts.

      Follow-up: What happens if an effect has no cleanup function and the component unmounts?
      Why can't you call a hook inside an `if` statement?

      React tracks each hook's state by the order hooks are called in, not by name -- calling hooks conditionally would change that order between renders, corrupting which stored state/effect corresponds to which hook call.

      Follow-up: How would you conditionally apply effect logic without conditionally calling the hook itself?
      What's the difference between `setState(5)` and `setState(prev => prev + 1)`?

      The first replaces state with a fixed new value. The second computes the new value from whatever the current state actually is at update time -- safer when multiple updates might be queued or when reading from a potentially-stale closure.

      Follow-up: Give an example where using the direct-value form produces a bug.
      What is `useEffect` meant to be used for, conceptually?

      Synchronizing a component with something outside React's rendering model -- a DOM API, a subscription, a network request, a timer -- not as a generic "run this after render" hook for things that could be computed during render.

      Follow-up: Give an example of code that's commonly put in an effect but shouldn't be.

      Medium

      Explain the "stale closure" bug with a concrete dependency-array example.

      An effect's function closes over whatever values were in scope when it was created. If that effect is only re-created when certain dependencies change (per the array), any other value it reads but doesn't list stays frozen at whatever it was during the render that created the still-active closure -- e.g., an interval callback reading a `step` state variable that isn't in the dependency array keeps using the ORIGINAL step value forever, even after the user updates it, because the effect (and its interval) never re-runs to pick up a fresh closure.

      Follow-up: Does using the updater-function form of setState fix a stale closure bug on its OWN state, and why does that work but not fix a stale read of OTHER state?
      Why is fetching inside `useEffect` without cancellation a race-condition risk, specifically?

      If the dependency driving the fetch (e.g. an ID) changes before the previous fetch resolves, you now have two in-flight requests. Network timing isn't guaranteed to match request order -- the older request can resolve AFTER the newer one, and if nothing guards against it, its `.then()` callback will blindly overwrite state with stale data for the wrong ID, even though a newer, correct response already arrived first.

      Follow-up: Besides AbortController, what's a lightweight manual way to guard against this?
      Why does React call effect cleanup before the NEXT effect run, not just on unmount?

      Because an effect represents "the current synchronization with an external system for the current dependency values" -- when a dependency changes, the OLD synchronization (old subscription, old interval, old listener) must be torn down before establishing the NEW one, otherwise you'd have both the stale and fresh subscriptions active simultaneously, which is exactly the leak/double-subscription bug this mechanism prevents.

      Follow-up: What would you observe (symptom-wise) if cleanup didn't run between dependency changes?
      Is it ever correct to intentionally omit a dependency that does change, with eslint-disable?

      Rarely, and only with a clear comment justifying it -- e.g., intentionally wanting an effect to use only the INITIAL value of a prop ("capture on mount, ignore later changes") is a real, if uncommon, requirement. The disable should be scoped to that one line with a reasoning comment, never applied blanket, since it silences the exact check that catches the majority of real hook bugs.

      Follow-up: What's a cleaner alternative to eslint-disable for "only care about the initial value" semantics?

      Advanced

      Why does React guarantee hooks run in the same order every render, and what data structure makes that guarantee meaningful? (High-level only -- full detail in topic 03.)

      At the fundamentals level: each hook call within a component corresponds to a slot in that component's per-fiber memoized state, associated by call position/order rather than by name or key. As long as the same hooks are called in the same order every render, React can correctly match each call to its persisted state slot across renders. The full Fiber-level linked-list mechanics are covered in the advanced Hooks Deep Dive chapter.

      Follow-up: What observable error does React throw if you violate this, and what does the error message tell you?
      Why doesn't deriving a value via `useEffect` + extra state just work equivalently to computing it inline, even though both eventually show the correct value?

      Deriving via effect introduces an extra full render cycle: render with stale/default derived value -> commit -> effect runs -> setState -> second render with correct value. Users can observe a flash of incorrect UI, and if anything else depends on that derived value during the FIRST render (e.g., conditional logic), it operates on stale data. Computing inline during render guarantees the derived value is always correct and consistent within that single render pass, with no extra render needed.

      Follow-up: Is there a legitimate case where you WOULD want to sync derived state via an effect rather than compute inline?
      How would you reason about whether an effect needs an AbortController vs. a simple "ignore stale response" boolean flag?

      AbortController actually cancels the underlying network request (saving bandwidth/server work and triggering a real abort signal the fetch API understands), which matters for expensive requests or ones with side effects on the server beyond just a read. A boolean "ignore" flag is cheaper to write and sufficient when you only care about not setting state with stale data -- the request still completes server-side and over the wire, you just discard the result client-side. For GET requests to idempotent read endpoints, either is acceptable; for anything with server-side cost or side effects, prefer actual cancellation.

      Follow-up: Does AbortController cancellation guarantee the server stops processing the request?

      Practice Assignments

      Beginner (30-60 min)

      Find and fix three broken dependency arrays

      Given three small provided components, each with a subtly wrong `useEffect` dependency array (missing dep, unnecessary dep causing extra runs, and an inline object dep causing infinite re-runs), identify and fix each one.

      Acceptance criteria: `eslint-plugin-react-hooks` reports zero `exhaustive-deps` violations, and you can explain out loud what bug each original version caused.

      Hints

      The infinite-loop one is almost always an object/array/function literal created fresh inside the component body and placed in the dependency array.

      Bonus: Reproduce each bug's symptom with a console.log before fixing it, to see the actual broken behavior.

      Intermediate (2-4 hrs)

      Build a cancel-safe data-fetching hook

      Build a custom useFetch(url) hook returning { data, loading, error } that correctly handles: rapid URL changes (no race conditions), cleanup/abort on unmount, and re-fetching when the URL changes. Test it by rapidly switching between several recipe IDs.

      Acceptance criteria: Rapidly clicking through 5 different IDs never shows data for the wrong ID, even on a throttled/slow network (test with DevTools network throttling).

      Hints

      AbortController's `signal` passed to `fetch` plus checking `err.name === 'AbortError'` in the catch block is the standard pattern.

      Bonus: Add a simple in-memory cache keyed by URL so revisiting an already-fetched ID doesn't show a loading flash.

      Quick Revision Cheat Sheet

      • useState setter schedules a re-render; doesn't mutate the current closure's value.
      • Use the updater-function form (prev => next) when the new value depends on the old one.
      • Lazy init: useState(() => expensive()) runs only once, on mount.
      • No array = every render. [] = mount/unmount only. [deps] = re-run when any changes.
      • Cleanup runs before the next effect run AND on unmount — always clean up subscriptions/timers/listeners.
      • Never omit a dependency that actually changes and matters — stale closures are silent, not crashy.
      • Objects/functions created inline every render make "stable" dependencies look like they always changed.
      • Guard async effects against race conditions (AbortController or an ignore-flag).
      • Don't use an effect to derive a value that can simply be computed inline during render.
      • Hooks must run in the same order every render — never call them conditionally or in loops.
