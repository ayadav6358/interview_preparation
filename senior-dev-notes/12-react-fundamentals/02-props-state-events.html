    Props, State & Events: The Data-Flow Contract

    ⏱ 2 hrs📍 Chapter 2 of 6

    One-line summary: Props flow one direction (parent → child, read-only), state is private memory owned by a component that triggers a re-render when changed, events are how a child tells a parent "something happened" — and "lifting state up" is the single pattern that resolves 90% of "how do two sibling components share data" interview questions.

    On this page

      Why It Matters for a Senior Developer

      Almost every "my UI is out of sync" bug a senior dev debugs in practice is a data-flow modeling mistake, not a React bug: state living in the wrong component, a prop being mutated instead of flowing down immutably, or an event handler not actually notifying the right ancestor. Interviewers probe this constantly with "two sibling components need to share X, how do you wire it up" — the correct, confident answer ("lift the state to the nearest common ancestor") separates people who've internalized unidirectional data flow from people who reach for a state library reflexively.

      Prerequisites

      Requires React Basics: JSX & Components. Feeds directly into Hooks Basics (state is implemented via the useState hook) and Forms & Controlled Components (controlled inputs are this chapter's pattern applied to form fields). For the deeper "why does state update trigger exactly this much re-rendering" mechanics, see React Internals.

      Core Concepts

      Props: the read-only, one-directional contract

      Props are the arguments a parent passes to a child — plain data, functions, elements, anything. The contract is strict: a component must never mutate its own props. Not "should not" — React doesn't runtime-enforce it in production, but violating it breaks the fundamental assumption every other part of React relies on (that a parent's data and a child's view of that data stay consistent). Props always flow down; there is no mechanism for a child to "write back" to a parent's props directly — that's what callback props (events, below) are for.

      // BAD: mutating a prop directly
function Cart({ items }) {
  items.push({ id: 99, name: "surprise" }); // mutates the parent's array in place
  return <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>;
}

// GOOD: derive new data, never mutate what was passed in
function Cart({ items, onAdd }) {
  return (
    <>
      <ul>{items.map(i => <li key={i.id}>{i.name}</li>)}</ul>
      <button onClick={() => onAdd({ id: 99, name: "surprise" })}>Add</button>
    </>
  );
}

      State: private memory with a re-render contract

      State is data a component owns, that can change over time, and whose change should cause the UI to update. useState is the primitive: const [value, setValue] = useState(initial). Two things senior candidates must state precisely: (1) calling the setter schedules a re-render — it does not mutate value in place synchronously, so reading value immediately after calling setValue in the same function body still gives you the old value; (2) state is scoped to the component instance — each time you render a component at a given position in the tree, it keeps its own independent state, but unmounting and remounting (e.g. via a changed key or a conditional that removes then re-adds it) resets that state entirely.

      Events: how a child reports upward

      React wraps native DOM events in a cross-browser SyntheticEvent (in React 17+, these are attached at the root container and use native event delegation, not per-node listeners — detail covered in topic 03). From a fundamentals standpoint, what matters: event handler props are just regular callback props by convention named onX (e.g. onClick, or a custom onAdd/onSubmit for your own components), and the standard way for a child to "talk to" a parent is to accept a callback prop and call it with relevant data — the parent decides what to do, keeping the child "dumb" and reusable.

      function FavoriteButton({ recipeId, onToggleFavorite }) {
  return (
    <button onClick={() => onToggleFavorite(recipeId)}>
      ☆ Favorite
    </button>
  );
}

      Lifting state up: the canonical fix for "siblings need to share data"

      When two sibling components both need access to (or both need to modify) the same piece of data, the state does not belong in either sibling — it belongs in their nearest common ancestor, which then passes the current value down as props to both and passes callback props down so either child can request a change. This is "lifting state up," and it's the default-correct answer before reaching for Context or an external state library — those exist to avoid prop-drilling many levels, not to replace this pattern at shallow depth.

      function SearchableRecipeList({ recipes }) {
  const [query, setQuery] = useState("");
  const filtered = recipes.filter(r => r.name.toLowerCase().includes(query.toLowerCase()));

  return (
    <>
      {/* SearchBar doesn't own the query -- it's lifted to the common parent */}
      <SearchBar value={query} onChange={setQuery} />
      <RecipeList recipes={filtered} />
    </>
  );
}

      How It Works Under the Hood

      When setQuery("pasta") runs inside an onChange handler:

      1. React enqueues the update against SearchableRecipeList's internal state slot for that useState call (not against the DOM, not against the child components directly).
      2. React schedules a re-render of SearchableRecipeList (and, by default, its subtree — SearchBar and RecipeList both get called again with their new props).
      3. SearchableRecipeList's function body re-runs top to bottom: query is now "pasta", filtered is recomputed fresh, and new elements are produced for both children with the new props.
      4. React diffs the new element tree against the previous one and patches only the DOM nodes that actually changed (e.g., the list items, not the search input's unrelated siblings).

      Code Examples

      // Full lifted-state example: two siblings (Filter + List) share state
// owned by their parent, communicating purely via props and callbacks.
import { useState } from "react";

function FavoritesToggle({ isFavorite, onToggle }) {
  return <button onClick={onToggle}>{isFavorite ? "★" : "☆"}</button>;
}

function RecipeRow({ recipe, isFavorite, onToggleFavorite }) {
  return (
    <li>
      {recipe.name}
      <FavoritesToggle isFavorite={isFavorite} onToggle={() => onToggleFavorite(recipe.id)} />
    </li>
  );
}

function RecipeBook({ recipes }) {
  const [favoriteIds, setFavoriteIds] = useState(() => new Set());

  function handleToggleFavorite(id) {
    setFavoriteIds(prev => {
      const next = new Set(prev); // never mutate prev state directly
      next.has(id) ? next.delete(id) : next.add(id);
      return next;
    });
  }

  return (
    <ul>
      {recipes.map(r => (
        <RecipeRow
          key={r.id}
          recipe={r}
          isFavorite={favoriteIds.has(r.id)}
          onToggleFavorite={handleToggleFavorite}
        />
      ))}
    </ul>
  );
}

      Real-World Production Scenario at Scale

      At scale

      A checkout flow had a "quantity stepper" component that kept its own local state for the current quantity and a parent cart summary that separately tracked item totals from props passed down at mount time. The two fell out of sync whenever the stepper changed quantity because the stepper's local state was never propagated back up via a callback — it was "fire and forget" UI state with no single source of truth. The fix was textbook lifting-state-up: the cart (parent) became the sole owner of quantities; the stepper became fully controlled (value + onChange props, no internal state at all), guaranteeing the displayed total always matched what was rendered. This is the exact failure mode interviewers are probing for when they ask "where should this state live?"

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Reading state right after calling its setter and expecting the new value: setCount(count + 1); console.log(count) logs the OLD value — the setter schedules an update for the next render, it doesn't mutate the variable in your current closure. If you need the next value immediately in the same function, compute it into a local variable first, or use the updater-function form (setCount(c => c + 1)) when the new value depends on the previous one.

      • Storing derived data in state instead of computing it on each render (e.g., storing filteredRecipes in useState instead of deriving it from recipes and query every render) — causes stale-derived-data bugs when the source changes but you forget to re-sync the derived state.
      • Initializing state from props and assuming it stays in sync: useState(props.value) only uses props.value on the first render — later prop changes do not update that state automatically; this needs either full lifting (preferred) or an explicit effect/key reset.
      • Passing a brand-new inline function/object as a prop on every render when the child is wrapped in memo — defeats the memoization because reference equality fails every time (full mechanics in topic 03's Internals chapter, but the fundamentals-level fix is the same: keep prop references stable with useCallback/useMemo when it matters).

      Tradeoffs

      ApproachUse whenAvoid whenAlternative
      Local component stateData only that component (and maybe its direct children) needsMultiple distant components need the same dataLift state up, or Context for deep trees
      Lifting state to nearest common ancestorA handful of siblings/cousins need shared data, shallow treeMany deeply nested consumers — causes prop-drilling painContext API, or a state library
      Storing derived values in stateThe computation is genuinely expensive and needs cachingCheap derivations that can just be recomputed inlineCompute inline during render, or useMemo if proven expensive

      Interview Questions

      Basic

      What's the difference between props and state?

      Props are passed in from a parent and are read-only from the child's perspective; state is private data a component owns and manages itself, and changing it triggers a re-render.

      Follow-up: Can a component change its own props?
      Why shouldn't you mutate props directly?

      It breaks the parent's data consistency (the parent's data silently changes without the parent's knowledge) and violates the one-directional data flow React's model depends on. The fix is to call a callback prop so the parent can update its own state intentionally.

      Follow-up: What would go wrong specifically if you mutated an array prop in place?
      What does calling a `useState` setter actually do?

      It schedules a state update and a re-render; it does not synchronously mutate the variable you destructured, so code immediately after the call still sees the old value in that render's closure.

      Follow-up: How do you get the next value immediately within the same handler?
      What is "lifting state up"?

      Moving state from a child component up to its nearest common ancestor so that multiple children can read and modify it consistently via props and callbacks, instead of each keeping an out-of-sync local copy.

      Follow-up: When would you NOT lift state, even with two components needing related data?
      How does a child component communicate an event back to its parent?

      Via a callback prop passed down by the parent (e.g. `onToggleFavorite`); the child calls it with relevant data, and the parent decides what state change, if any, results.

      Follow-up: Is this different from how native DOM events like onClick work?

      Medium

      Why does `useState(props.value)` not keep local state synced to prop changes?

      The argument to `useState` is only used to compute the INITIAL state on the component's first render (technically, first mount of that fiber) -- it's ignored on every subsequent render. So if `props.value` changes later, the already-initialized state variable keeps its old value unless something explicitly re-syncs it.

      Follow-up: What are the two common fixes, and what's the tradeoff between them?
      Why is storing derived/computed data in state usually a mistake?

      It creates two sources of truth: the source data and the derived copy. Any code path that updates the source but forgets to also update the derived state produces a stale-UI bug. Deriving fresh on every render (or memoizing with useMemo if proven expensive) guarantees the derived value can never go stale relative to its inputs.

      Follow-up: When is caching a derived value with useMemo actually justified?
      What's the difference between controlled "dumb" components and components that manage their own internal state, in terms of lifting?

      A fully controlled component has no internal state of its own for the value in question -- it receives `value` and `onChange` and is purely a rendering/event-reporting layer; the owning state lives entirely in an ancestor. A self-managing component keeps that state internally and only reports out when something crosses a boundary (e.g., form submission). The controlled approach keeps a single source of truth but adds prop-plumbing; the self-managed approach is simpler locally but risks the "two sources of truth" sync bug if the parent also needs to know the value.

      Follow-up: Which approach does a form input library typically default to, and why?
      Why does passing a new inline arrow function as a callback prop on every render matter even if the child isn't wrapped in `memo`?

      If the child isn't memoized, it re-renders regardless of prop reference equality, so in isolation a fresh function reference costs only a trivial allocation per render -- not a correctness issue. It only becomes a performance issue once memoization (or a dependency array elsewhere, like an effect) is relying on that reference staying stable, which is why the "fix" (useCallback) is a targeted response to a measured problem, not a default habit.

      Follow-up: Give a concrete case where an inline function prop breaks correctness, not just performance.

      Advanced

      Two sibling components are both children of a router-rendered route and need shared state, but they're on different routes (not simultaneously mounted). Does "lift state up" still apply?

      Lifting works only while both consumers are simultaneously mounted under the common ancestor holding the state -- if they're on different routes and never co-exist in the tree, lifting to a shared ancestor that stays mounted across route changes (e.g., a layout route) still works, since React state persists in a fiber as long as that fiber (and the state hook's position in it) stays mounted, even if the fiber's rendered children change via routing. If the common ancestor itself unmounts between visits, the state needs to live outside the component tree's lifecycle entirely (URL state, localStorage, or a store) rather than in component state.

      Follow-up: Why does URL state (route params/query string) solve this particular case elegantly for shareable/bookmarkable state?
      Explain precisely why batched state updates inside one event handler don't each trigger a separate render.

      React groups all state updates triggered synchronously within a single event handler invocation (and, since React 18, within promises/timeouts/native event handlers too via automatic batching) into one render pass -- multiple `setX` calls in the same handler enqueue multiple updates against the fiber, but React only re-renders once after the handler finishes, applying all queued updates in order first. This is why `setCount(c=>c+1)` called twice in one handler increments by 2 in a single render, while two separate `setCount(count+1)` calls (reading the same stale `count` closure) only increment by 1.

      Follow-up: What's the exact difference in outcome between the updater-function form and the direct-value form when called twice in one handler?
      Is it ever architecturally correct to have the "same" logical state exist in two different components simultaneously?

      Yes, when one is a deliberate, intentionally-desynced local draft (e.g., an uncontrolled form field holding in-progress edits) that only syncs to the canonical state on an explicit commit action (submit/blur) -- this is a valid, common pattern, not a bug, as long as the "source of truth" moment is well-defined and both the UI and the team understand which copy is authoritative at any given time.

      Follow-up: How does this relate to the controlled-vs-uncontrolled forms distinction in Chapter 4?

      Practice Assignments

      Beginner (30-60 min)

      Fix a props-mutation bug

      Given a small provided component that mutates an array/object prop directly (e.g., pushing to a `items` prop array), rewrite it to never mutate props, deriving new arrays/objects instead and communicating changes via a callback prop to the parent.

      Acceptance criteria: No prop is ever mutated; React DevTools shows the parent's state updating correctly after the child's action.

      Hints

      Use spread syntax or array methods that return new arrays (`map`, `filter`, `[...arr, x]`) instead of in-place methods (`push`, `splice`).

      Bonus: Add a prop-types or TypeScript readonly annotation to make the mutation a compile-time error.

      Intermediate (2-4 hrs)

      Build a lifted-state favorites system

      Build a recipe list and a separate "favorites summary" sidebar as true siblings (not parent/child), sharing favorite-recipe state lifted to their common parent, with toggle buttons on each recipe card. Add a counter showing total favorites, computed as derived data (not stored state).

      Acceptance criteria: Toggling a favorite in the list instantly updates the sidebar count and list, with state living in exactly one place.

      Hints

      A `Set` of favorite IDs is often cleaner than an array for toggle/has-membership checks.

      Bonus: Persist the favorites to localStorage via a custom hook (preview of later chapters).

      Quick Revision Cheat Sheet

      • Props: read-only, flow parent → child only. Never mutate them.
      • State: private, triggers re-render on change, scoped to the component instance/fiber.
      • Calling a state setter doesn't synchronously update the variable in the current closure.
      • Events = callback props by convention (onX); child calls, parent decides.
      • Lifting state up = move shared state to the nearest common ancestor of the components that need it.
      • Derived data should be computed on render, not duplicated into its own state.
      • useState(initialArg) only uses initialArg on first mount, never again.
      • Multiple setState calls in one handler are batched into a single re-render.
      • A fully controlled child has no internal state for the controlled value — it's 100% owned by the parent.
