    React Basics: What React Actually Is, and JSX & Components Precisely

    ⏱ 1.5 hrs📍 Chapter 1 of 6

    One-line summary: React is a library for building UI as a tree of pure(-ish) functions that return a description of what should be on screen; JSX is sugar over React.createElement calls, and "component" means exactly one thing — a function that takes props and returns elements — everything else (hooks, state, context) is built on top of that one abstraction.

    On this page

      Why It Matters for a Senior Developer

      This is the chapter interviewers skip fastest and candidates get wrong most subtly. "React is a library, not a framework" sounds memorized until you can explain exactly what that implies (no built-in routing, no built-in data fetching, no opinion on file structure — all bolted on by the ecosystem, including the very topics in this site's advanced topic). Getting JSX-to-createElement compilation precisely right is also the foundation for every later explanation of reconciliation, keys, and fragments — if you're fuzzy here, every later answer gets fuzzy too.

      Prerequisites

      You should be comfortable with modern JS (ES2020+: destructuring, modules, arrow functions, template literals) and basic DOM/browser concepts — see Web Fundamentals if any of that feels shaky. This chapter is the on-ramp for the rest of this topic — Props, State & Events next — and the eventual on-ramp for React Internals: Fiber & Reconciliation, which assumes everything here is second nature.

      Core Concepts

      What React actually is (and isn't)

      React is a UI library whose one real job is: given a tree of "what should be on screen" described as plain JS objects (React elements), compute the minimal set of changes needed to make the real DOM match, and do it again every time that description changes. That's it. It deliberately does not ship routing, HTTP/data-fetching, global state, CSS handling, or a file structure convention — which is why "React vs. Next.js" is a category error (Next.js is a framework built on React, not a competitor to it) and why a fundamentals-level app doesn't need any of them to be correct.

      JSX is syntax sugar, not a template language

      JSX is not HTML and not interpolated at runtime like a template engine — it's compiled at build time (by Babel, esbuild, or SWC, depending on your toolchain) into function calls. This:

      const el = <Greeting name={name}>Hello</Greeting>;

      compiles (with the modern automatic JSX runtime used by Vite/CRA/Next by default since React 17) to:

      import { jsx as _jsx } from "react/jsx-runtime";
const el = _jsx(Greeting, { name: name, children: "Hello" });

      Older toolchains/the classic runtime instead emit React.createElement(Greeting, { name, children: "Hello" }). Either way, the result is a plain JS object — { type, props, key, ref } roughly — not a DOM node, not a string. Nothing is rendered yet; this object just describes intent. This is why you can store JSX in a variable, pass it as a prop (children is just a prop), return it conditionally, or map over an array to produce an array of elements.

      A component is a function from props to elements — nothing more

      A function component's entire contract: receive one argument (the props object), return something renderable (an element, a string/number, an array/fragment of elements, or null). It must be callable multiple times with the same props and return equivalent output (purity) — React calls it whenever it decides a re-render is needed, and it may call it more than once per commit in development (Strict Mode) specifically to catch impurity bugs.

      function Greeting({ name, children }) {
  return (
    <div className="greeting">
      <h2>{children}, {name}!</h2>
    </div>
  );
}

      Naming must start with an uppercase letter — this isn't a style preference, it's how JSX's compiler decides whether <Foo /> means "call the variable Foo as a component" vs. <foo /> meaning "create a host DOM element literally named foo."

      Composition is the only extension mechanism — there is no component inheritance

      React explicitly has no supported pattern for one component class extending another to share behavior. Instead, you compose: nest components as children, pass render-affecting data via props, and share cross-cutting logic via custom hooks (Chapter 3) rather than base classes. This single decision is why "container/presentational," "render props," "higher-order components," and eventually hooks all exist — they're successive answers to "how do I share behavior without inheritance."

      Fragments, keys, and why a component must return one thing

      A component must return a single value, so returning two sibling elements requires wrapping them — either in a real DOM element or a <>...</> fragment (sugar for <React.Fragment>), which produces no extra DOM node. When rendering a list via .map(), each resulting element needs a stable key prop so React can track identity across re-renders — covered in depth (and why it matters for the diff algorithm) in the Internals chapter; for now, the fundamentals-level rule is: use a stable, unique ID from your data, never the array index, unless the list is truly static.

      How It Works Under the Hood

      End-to-end for a simple render, at the fundamentals level (the full Fiber mechanics are in topic 03):

      1. Your JSX compiles to _jsx()/createElement() calls, producing a tree of plain element objects — no DOM involved yet.
      2. createRoot(domNode).render(<App />) hands that root element to React.
      3. React walks the element tree, calling each function component with its props, recursively resolving children until it reaches host elements (div, span, etc.).
      4. React creates real DOM nodes for the host elements and inserts them into the container — the actual browser paint happens after this JS work completes.
      5. On a later update, React re-runs this process for the parts of the tree that changed and patches only the differences into the existing DOM (instead of tearing everything down and rebuilding).

      Code Examples

      // BAD: component defined inside another component — a new function identity
// every render, which breaks memoization and causes unnecessary remounts.
function Parent() {
  function Child() { return <p>hi</p>; } // new reference every Parent render
  return <Child />;
}

// GOOD: components defined at module scope, stable identity across renders.
function Child() {
  return <p>hi</p>;
}
function Parent() {
  return <Child />;
}

// Fragments avoid an unnecessary wrapper div in the DOM output.
function RecipeMeta({ prepTime, servings }) {
  return (
    <>
      <span>⏱ {prepTime} min</span>
      <span>🍽 {servings} servings</span>
    </>
  );
}

// `children` is just a prop -- composition in action.
function Card({ children, title }) {
  return (
    <div className="card">
      <h3>{title}</h3>
      {children}
    </div>
  );
}
function App() {
  return (
    <Card title="Pasta">
      <RecipeMeta prepTime={20} servings={2} />
    </Card>
  );
}

      Real-World Production Scenario at Scale

      At scale

      A team's component library had every component defined as a nested function inside a parent "feature" component "for organization." As the app grew, this meant every parent re-render created brand new child function references, which silently defeated every memo() wrapper the team had added for performance — React saw a "new" component type each render and remounted instead of reusing. The bug was invisible in code review (it looks fine) and only surfaced as a profiler showing unexpected full remounts and lost focus/animation state on every keystroke in an unrelated sibling input. The fix was a lint rule (react/no-unstable-nested-components) plus moving all component definitions to module scope — a pure fundamentals-level fix for what looked like an "internals" bug.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Thinking JSX "is" HTML leads to real bugs: class is className, for is htmlFor, inline styles are objects with camelCase keys ({{ backgroundColor: 'red' }}), and self-closing tags are mandatory for void-like elements (<img />, not <img>). These aren't arbitrary — JSX attributes become JS object properties, and class/for are reserved words in JS.

      • Defining components inside other components (see production scenario above) — always hoist to module scope.
      • Forgetting that JSX expressions ({...}) can hold any JS expression but NOT statements — {if (x) {...}} is invalid; use a ternary, &&, or an early return instead.
      • Returning undefined from a component by accident (e.g. an arrow function with a body block and no explicit return) — React throws, since undefined isn't a valid render result (unlike null, which is explicitly "render nothing").

      Interview Questions

      Basic

      What is JSX and is it required to use React?

      JSX is syntax sugar that compiles to createElement/_jsx() calls producing plain JS objects. It's not required — you can call those functions directly — but virtually all real codebases use it for readability.

      Follow-up: What does JSX compile to under the automatic runtime vs. the classic runtime?
      What is a React component, precisely?

      A function that takes a props object and returns a renderable value (elements, string/number, array/fragment, or null). Function identity and naming (capitalized) matter to how JSX and React treat it.

      Follow-up: Why must component names be capitalized?
      Why `className` instead of `class` in JSX?

      JSX attributes compile to JS object properties, and `class` is a reserved word in JavaScript, so React uses the DOM property name `className` instead.

      Follow-up: What other HTML attributes get renamed in JSX, and why?
      What is React, and what is it explicitly NOT (i.e. what doesn't it ship with)?

      React is a UI-rendering library: elements, components, reconciliation. It ships with no router, no data fetching, no global state, no CSS solution, no file-structure convention -- all of those are separate libraries/frameworks layered on top.

      Follow-up: What does a framework like Next.js add on top of React?
      Can a component return multiple sibling elements directly?

      No -- a component must return a single value. Multiple siblings must be wrapped, typically in a Fragment (`<></>`) to avoid adding an extra DOM node, or in a real wrapper element.

      Follow-up: When would you choose a real element over a Fragment?
      What does `children` represent in props?

      Whatever was nested between a component's opening and closing JSX tags, passed automatically as the `children` prop -- it's not special syntax, just a regular prop with a reserved name.

      Follow-up: How would you type `children` in TypeScript?

      Medium

      Why does defining a component inside another component's function body cause bugs?

      Every time the parent re-renders, a brand-new function (new identity) is created for the nested component. React treats a changed component type/identity as "different component" at that position, so memoization breaks and the subtree can remount/lose state unnecessarily even though the code "looks" the same each render.

      Follow-up: What lint rule catches this, and what's its exact check?
      Explain exactly what a JSX expression `{...}` can and cannot contain.

      It can contain any JS expression (ternaries, function calls, logical `&&`/`||`, arithmetic, array literals) because it's evaluated and the result spliced into the element tree. It cannot contain statements (`if`, `for`, variable declarations) because those don't produce a value -- you must move that logic outside the JSX or use expression-based equivalents.

      Follow-up: How would you conditionally render three different branches inside JSX cleanly?
      Why is composition preferred over inheritance in React, concretely?

      React components don't share a class hierarchy mechanism designed for reuse -- there's no supported "extends" pattern for behavior sharing between components. Composition (nesting via children/props, and later custom hooks) keeps behavior sharing explicit and avoids the classic OOP pitfalls (fragile base classes, tight coupling) that inheritance-based UI frameworks ran into.

      Follow-up: Name three composition patterns used historically before hooks existed.
      What's the actual difference between `null` and `undefined` as a component's return value?

      `null` is a valid, explicit "render nothing" signal React understands. `undefined` is not a supported render return value and React throws an error -- it's almost always an accidental missing `return` statement, not an intentional choice.

      Follow-up: What's a common code pattern that accidentally returns undefined?
      Does the choice of key in a list affect anything if the list never reorders or filters?

      At a purely fundamentals level, no -- a static, never-mutated list's index-based keys behave identically to stable ID keys, since item identity-to-position never changes. The risk is purely about lists that can reorder/insert/delete, which is the common real-world case, so stable IDs are the universally-safe default.

      Follow-up: What's the actual mechanism that breaks when a filtered list uses index keys? (Covered in topic 03.)

      Advanced

      Why does React's automatic JSX runtime remove the need to `import React` in every file, and what changed at the language/tooling level to make that possible?

      Before React 17, JSX always compiled to `React.createElement(...)`, requiring `React` to be in scope in every file that used JSX. The automatic runtime instead has the compiler auto-import dedicated `jsx`/`jsxs` functions from `react/jsx-runtime` based on whether an element has a static vs. dynamic number of children, decoupling "using JSX" from "having the React object in scope" -- a build-tooling change (Babel/SWC plugin config), not a language change.

      Follow-up: What's the difference between the `jsx` and `jsxs` runtime functions?
      Is a React element object (the output of createElement) mutable, and why does that matter?

      React elements are treated as immutable snapshots -- you're not meant to mutate `element.props` after creation. This matters because React may reuse/compare these objects (and the objects derived from them during reconciliation) assuming they describe a fixed point in time; mutating one after passing it to React produces undefined behavior since React's diffing assumes referential snapshots it controls the lifecycle of.

      Follow-up: How does this immutability assumption relate to why you can't mutate props inside a component?
      Why must a function component be "pure" with respect to render, and what specifically is allowed vs. disallowed during the render call itself?

      Disallowed during render: mutating existing variables/objects created before render, DOM mutations, starting timers/subscriptions, making non-idempotent calls (e.g., random values or timestamps that should be stable per commit) without intentional memoization. Allowed: creating new local variables/objects, calling other pure functions, deriving values from props/state. The purity requirement exists because render can be called multiple times for the same eventual commit (Strict Mode double-invoke, interrupted/retried renders in concurrent features) -- side effects there would run redundantly or at the wrong time.

      Follow-up: Where do legitimate side effects belong instead, and why does that API exist?

      Practice Assignments

      Beginner (30-60 min)

      Decompile JSX by hand

      Take 5 JSX snippets of increasing complexity (plain element, element with props, element with children, a fragment, a conditional expression) and write out, by hand, the equivalent createElement calls. Then verify using the Babel REPL (babeljs.io/repl) with the React preset.

      Acceptance criteria: All 5 match the compiler output exactly, including prop ordering concerns and how children are passed.

      Hints

      Pay attention to how a fragment compiles — it uses a special `Fragment` symbol as the "type," not a string.

      Bonus: Compare the classic vs. automatic runtime output for the same snippet.

      Intermediate (2-4 hrs)

      Build a component library with pure composition

      Build 5 reusable, composable UI primitives (Card, Button, Modal, Tabs, Badge) with zero component nesting inside other component bodies, using only props and children for composition — no state yet (that's Chapter 2). Each must be usable standalone and composed together in at least one example screen.

      Acceptance criteria: ESLint with eslint-plugin-react's no-unstable-nested-components rule passes with zero violations.

      Hints

      Modal and Tabs are the components most tempted to be defined inline for "scoping" reasons — resist it.

      Bonus: Add TypeScript prop types for all 5 and ensure `children` is correctly typed per component.

      Quick Revision Cheat Sheet

      • React = a UI-rendering library only; no router/data-fetching/state/CSS opinion built in.
      • JSX compiles to createElement/_jsx() calls → plain JS objects, not DOM nodes.
      • A component = a function(props) → renderable value; must be capitalized; should be pure.
      • Never define a component inside another component's render — kills identity stability and memoization.
      • children is just a prop populated from nested JSX content.
      • JSX {...} holds expressions only, never statements.
      • Returning undefined throws; returning null means "render nothing" — know the difference.
      • Fragments group siblings without adding a DOM node.
      • Composition (props + children + hooks), not inheritance, is React's only extension mechanism.
