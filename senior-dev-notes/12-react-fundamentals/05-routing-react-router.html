    Routing with React Router: Routes, Params, Nesting & Guards

    ⏱ 2 hrs📍 Chapter 5 of 6

    One-line summary: React Router maps URL paths to component trees client-side, intercepting navigation so the browser never does a full page reload; nested routes let a layout persist across child route changes, and "protected routes" are just a conditional render wrapped around navigation — no magic, just composition applied to routing.

    On this page

      Why It Matters for a Senior Developer

      React itself has no routing opinion (Chapter 1), so every multi-page React app needs this layer, and React Router is the de facto standard for plain client-side-rendered apps (as opposed to framework-level routing like Next.js's file-based router, covered in React & Next.js Advanced). Interviewers test this to see if you understand client-side routing is a client-side illusion built on the History API — not a server concept — and whether you can reason about the classic "refresh on a deep route breaks" deployment gotcha.

      Prerequisites

      Requires Props, State & Events and Hooks Basics (route guards commonly use useEffect/state for auth checks). See Web Fundamentals for how the browser's History API and URL structure work underneath this. Feeds directly into the capstone's multi-page routing requirement, and contrasts with React & Next.js Advanced's server-centric routing model.

      Core Concepts

      Routes map URL paths to components

      Modern React Router (v6/v7, "data router" APIs) centers on createBrowserRouter + RouterProvider, or the simpler declarative <BrowserRouter> + <Routes>/<Route> form for straightforward apps:

      import { BrowserRouter, Routes, Route, Link } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/favorites">Favorites</Link>
      </nav>
      <Routes>
        <Route path="/" element={<RecipeList />} />
        <Route path="/recipes/:id" element={<RecipeDetail />} />
        <Route path="/favorites" element={<Favorites />} />
        <Route path="*" element={<NotFound />} />
      </Routes>
    </BrowserRouter>
  );
}

      Critically, <Link> (not a plain <a>) is what makes navigation client-side: it intercepts the click, calls the History API's pushState under the hood, and re-renders the matching route — no full-page network round trip, no lost React state outside the routed tree.

      Route params: reading dynamic URL segments

      :id in a path is a dynamic segment; useParams() reads its current value inside the matched component:

      import { useParams } from "react-router-dom";

function RecipeDetail() {
  const { id } = useParams(); // string, always -- even if your IDs are numeric
  // fetch/display recipe by id...
}

      useSearchParams() similarly reads/writes the query string (?sort=name) for filter/sort state that should be shareable/bookmarkable — often the better home for "search query" state than plain component state, since it survives a page refresh and is linkable.

      Nested routes: shared layout, swapped content

      A parent route can render a persistent layout (nav, sidebar, header) with an <Outlet /> marking where the matched child route renders — the layout itself does NOT re-mount when you navigate between its children, only the Outlet's content swaps:

      <Routes>
  <Route path="/" element={<AppLayout />}>
    <Route index element={<RecipeList />} />
    <Route path="recipes/:id" element={<RecipeDetail />} />
    <Route path="favorites" element={<Favorites />} />
  </Route>
</Routes>

function AppLayout() {
  return (
    <>
      <NavBar /> {/* never unmounts when switching between child routes */}
      <Outlet /> {/* matched child route renders here */}
    </>
  );
}

      Protected routes: composition, not a router feature

      React Router has no built-in "requireAuth" concept — you build it with a wrapper component that checks auth state and either renders its children/an Outlet or redirects via <Navigate>:

      import { Navigate, Outlet } from "react-router-dom";

function ProtectedRoute({ isAuthenticated }) {
  if (!isAuthenticated) return <Navigate to="/login" replace />;
  return <Outlet />;
}

// usage
<Route element={<ProtectedRoute isAuthenticated={isLoggedIn} />}>
  <Route path="recipes/new" element={<AddRecipeForm />} />
</Route>

      The replace prop on <Navigate> swaps the current history entry instead of pushing a new one — important so the back button doesn't bounce the user back into the page they were just redirected away from.

      How It Works Under the Hood

      Clicking a <Link>: the click handler calls event.preventDefault() to stop the browser's native navigation (which would hit the network and reload the page), then calls the History API's history.pushState() to change the URL without a network request, then notifies the router's internal state that the location changed. React Router re-evaluates which <Route> elements match the new path/params and re-renders just the parts of the tree whose matched route changed — a parent layout route with an unchanged match is never unmounted, which is exactly why nested routes preserve layout-level state (open modals, scroll position of a persistent sidebar, etc.) across child navigation.

      Code Examples

      // BAD: a plain <a> tag causes a full page reload, discarding all
// client-side React state (e.g., an in-progress multi-step form elsewhere).
function BadNav() {
  return <a href="/favorites">Favorites</a>;
}

// GOOD: <Link> (or useNavigate for programmatic navigation) stays client-side.
import { Link, useNavigate } from "react-router-dom";

function GoodNav() {
  const navigate = useNavigate();
  return (
    <>
      <Link to="/favorites">Favorites</Link>
      <button onClick={() => navigate(-1)}>Go back</button>
    </>
  );
}

// Reading and writing the query string for shareable filter state.
import { useSearchParams } from "react-router-dom";

function RecipeList() {
  const [searchParams, setSearchParams] = useSearchParams();
  const sort = searchParams.get("sort") ?? "name";

  return (
    <select value={sort} onChange={e => setSearchParams({ sort: e.target.value })}>
      <option value="name">Name</option>
      <option value="time">Prep time</option>
    </select>
  );
}

      Real-World Production Scenario at Scale

      At scale

      A team shipped a client-side-routed React app to a static file host (e.g., S3/CloudFront with no SPA fallback configured). Everything worked while navigating inside the app via <Link>, but any user who refreshed the page on a deep route (/recipes/42) or shared/bookmarked that URL got a 404 from the host, because the server had no actual file at that path — it only exists as a client-side route React Router creates after index.html loads and JS runs. The fix was configuring the static host to serve index.html for any unmatched path (a "SPA fallback" rewrite rule), letting the client-side router take over once the JS bundle loads. This is a deployment concern every React Router app has and a classic "works in dev, breaks in prod" interview scenario.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting that useParams() values are always strings, even for routes that are logically numeric IDs — comparing id === 42 (number) against useParams().id (string "42") silently fails with strict equality. Convert explicitly (Number(id)) before comparing or using as an array index/object key where type matters.

      • Using <a href> instead of <Link to> for in-app navigation — causes a full page reload, a flash of white, and destroys any client-side state outside the URL.
      • Forgetting the SPA fallback rewrite rule on deployment (see production scenario) — deep links and refreshes 404 in production even though everything worked in local dev (where the dev server already has this fallback built in).
      • Putting auth-gated routes behind a client-only check with no server-side enforcement for anything that actually matters securely — client-side route guards are a UX nicety (don't show the form), never a real security boundary; the API must independently enforce authorization.

      Interview Questions

      Basic

      Why use `<Link>` instead of a plain `<a>` tag?

      `<Link>` intercepts the click and performs client-side navigation via the History API, avoiding a full page reload and preserving any React state outside the routed component. A plain `<a>` triggers a real browser navigation/network request.

      Follow-up: What actually breaks if you accidentally use a plain `<a>` for in-app links?
      How do you read a dynamic URL segment like `:id` inside the matched component?

      `useParams()`, which returns an object of all dynamic segments as strings, e.g. `const { id } = useParams();`.

      Follow-up: What type is `id` -- string or number -- and why does that matter?
      What is a nested route and what's its main benefit?

      A route that renders a parent layout with an `<Outlet />` where matched child routes render. The benefit is the layout (nav, sidebar) stays mounted across child route changes instead of remounting on every navigation.

      Follow-up: What state would be lost if the layout DID remount on every child navigation?
      How would you build a "protected route" with React Router?

      A wrapper component that checks auth state and either renders an `<Outlet />`/children (if authenticated) or redirects via `<Navigate to="/login" />` (if not) -- it's a composition pattern, not a built-in router feature.

      Follow-up: Is a client-side protected route a real security boundary?

      Medium

      Why do deep links 404 in production on a static host but work fine in local development?

      The dev server (e.g. Vite's) is pre-configured to serve `index.html` for any unmatched path, letting client-side routing take over after JS loads. A plain static host (S3, basic nginx config) has no such fallback by default -- it looks for an actual file at that path, finds none, and returns a real 404, since the route only exists virtually, created by React Router after the JS bundle runs.

      Follow-up: What's the exact server config change needed to fix this on most static hosts?
      What's the difference between storing filter/sort state in the query string vs. plain component state, and when does it matter?

      Query string state is part of the URL -- it survives a page refresh, is bookmarkable, and is shareable via a link that reproduces the exact same filtered view for someone else. Plain component state resets on refresh and isn't linkable. It matters whenever a user would reasonably want to share, bookmark, or refresh-and-keep a particular filtered/sorted view.

      Follow-up: What's a downside of putting EVERY piece of UI state into the query string?
      Why does `useParams().id` compared with `===` against a number silently fail, and how would this actually manifest as a bug?

      `useParams()` always returns string values regardless of what the route segment logically represents. `"42" === 42` is `false` under strict equality, so code like `recipes.find(r => r.id === id)` where `r.id` is a number would never find a match, silently showing a "not found" state for every valid recipe ID -- a bug that's easy to miss in manual testing if your mock data happens to use string IDs too.

      Follow-up: What's the safest place to do the string-to-number conversion?

      Advanced

      Why doesn't React Router need a full page reload to update the URL displayed in the browser's address bar?

      The browser's History API (`pushState`/`replaceState`) lets JavaScript change the URL shown in the address bar and add/modify history entries WITHOUT triggering an actual navigation/network request -- this is a browser platform feature React Router builds on, not something React Router invents. React Router pairs this with its own internal "current location" state so its component tree re-renders to match, purely client-side.

      Follow-up: What does `popstate` have to do with the browser's back/forward buttons working correctly with this?
      How would you reason about whether a given piece of state belongs in the URL (path param, query string) vs. component/global state?

      Ask: should refreshing the page keep this state? Should a shared link reproduce it for someone else? Does the back/forward button logically relate to this changing? If yes to any, it belongs in the URL (path param for identity-like data such as a resource ID, query string for filter/sort/pagination-like data). If the state is purely ephemeral UI (a dropdown being open, an in-progress unsaved form draft), it belongs in component state, since forcing it into the URL adds complexity (serialization, history-entry noise) with no user-facing benefit.

      Follow-up: Where would you put the state of a multi-step form wizard's current step, and why?
      Why is a client-side-only auth guard never sufficient as a security boundary, mechanistically?

      The entire client-side bundle, including the guard's logic and whatever "auth state" it checks, is fully visible and modifiable by the user's browser -- a user can open DevTools and directly flip the in-memory auth flag, bypass the router entirely by calling the underlying API directly, or simply read the bundled source. The guard only controls what the UI RENDERS; it has zero enforcement power over what the backend API actually accepts, which is why every protected action/data access must be independently authorized server-side regardless of what the client-side route guard shows.

      Follow-up: Given that, what IS a legitimate reason to still implement client-side route guards?

      Practice Assignments

      Beginner (30-60 min)

      Build a 3-route app with nested layout

      Build Home / About / Contact routes sharing a persistent nav layout via <Outlet />. Add a visible "render count" in the layout (via a useRef counter incremented in a useEffect with no deps) to prove the layout doesn't remount when switching routes.

      Acceptance criteria: The layout's render count stays at 1 regardless of how many times you navigate between the three routes.

      Hints

      If the count increments on every navigation, something in your route tree is forcing the layout itself to remount — check you nested the routes correctly under one parent `<Route>`.

      Bonus: Add active-link styling using `<NavLink>`'s automatic active-state class.

      Intermediate (2-4 hrs)

      Build param-based detail routes + a protected route

      Build a list/detail pair (/items and /items/:id) backed by mock data, plus a protected /admin route that redirects to /login if a fake "isAuthenticated" state is false, with a working login form that sets it true and redirects back to where the user originally tried to go.

      Acceptance criteria: Visiting /admin unauthenticated redirects to login; logging in redirects back to /admin, not just to the home page.

      Hints

      `useLocation()` inside the protected route lets you capture where the user was trying to go, passed as `state` to the `<Navigate>` to `/login`.

      Bonus: Make the "logged in" state survive a page refresh via localStorage.

      Advanced (1-2 days)

      Wire full routing into the capstone

      Implement all required capstone routes: home/list, recipe detail with param, favorites, and a protected add-recipe route with a fake-login redirect flow. Verify a hard refresh on /recipes/7 works correctly in a production build (vite build + vite preview, which doesn't have dev-server SPA fallback automatically — you may need to configure it).

      Hints

      `vite preview` serves a production build locally — test the deep-refresh behavior there, not just in `vite dev`, since dev and preview/prod SPA-fallback behavior can differ.

      Quick Revision Cheat Sheet

      • Always use <Link>/useNavigate() for in-app navigation, never a plain <a>.
      • useParams() values are always strings — convert explicitly when comparing to numbers.
      • Nested routes + <Outlet /> keep a layout mounted while only child content swaps.
      • useSearchParams() is the right home for shareable/bookmarkable filter/sort state.
      • Protected routes are a composition pattern (check + redirect), not a built-in router feature.
      • Client-side route guards are UX only — never a real security boundary; the API must enforce auth independently.
      • Deploying an SPA to a static host needs a rewrite/fallback rule serving index.html for unmatched paths.
      • <Navigate replace /> avoids a broken back-button bounce after a redirect.
