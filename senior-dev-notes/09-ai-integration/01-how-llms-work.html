    How LLMs Work (Practical View for Developers)

    ⏱ ~2.5 hrs📍 Chapter 1 of 7

    One-line summary: An LLM is a next-token predictor trained on huge text corpora; everything you build on top of it — chat, RAG, agents, tool calling — is really just clever ways of constructing the input text so that "predict the next token well" produces useful behavior.

    On this page

      Why It Matters for a Senior Developer

      You don't need to train a model to be dangerous in an AI-feature interview — you need to not be fooled by the chat-bubble UI into thinking the model "understands" or "remembers" things the way a database does. Senior-level AI questions are rarely about math; they're about whether you know why an LLM hallucinates a fact, why it forgets something you said 40 messages ago, why longer prompts cost more and respond slower, and why two calls with the same prompt can give different answers. Every one of those questions has a precise, mechanical answer rooted in how tokenization, context windows, and autoregressive generation actually work — and being able to give that answer, instead of "it's AI, it's a black box," is exactly the signal that separates someone who has shipped LLM features from someone who has only called an API once.

      Why

      Nearly every "weird AI bug" a team hits in production — truncated context, inconsistent outputs, runaway cost, injected instructions working — traces back to one of: token limits, sampling randomness, or the model treating all input text (yours, the user's, a retrieved document's) as equally authoritative unless you structure it otherwise. Understanding generation mechanics is what lets you debug and prevent these instead of guessing.

      Prerequisites

      None specific to ML — basic familiarity with arrays/vectors and probability (what a probability distribution is) is enough. Related: Using LLM APIs, Embeddings & Vector Databases.

      Core Concepts

      Tokens, not words or characters

      An LLM never sees "words." Text is first split by a tokenizer into subword chunks called tokens, using an algorithm like Byte-Pair Encoding (BPE) or a variant of it. BPE starts from individual bytes/characters and iteratively merges the most frequent adjacent pair into a new token, built up over the training corpus, until it has a fixed vocabulary (commonly 50k–200k entries). The result: common words ("the", "is") are a single token, rare words ("tokenization" itself) get split into a few pieces ("token", "ization"), and anything unseen (random strings, most non-English scripts, emoji) gets split down toward individual bytes, costing far more tokens per visible character.

      This is why: a sentence with lots of rare jargon or non-English text costs more tokens (and money) than the same idea in plain English; a model can "spell" a word character by character only with effort because the word is normally one indivisible token to it; and token counts, not character counts, are what every context window and billing limit is measured in.

      The context window

      A model has a fixed maximum number of tokens it can attend to in one request — the context window (e.g. 200k tokens for Claude Sonnet/Opus class models, up to 1M+ for some Gemini models as of 2025). This window covers everything: system prompt, conversation history, retrieved documents, tool definitions, and the output being generated. There is no separate "memory" — a model that appears to "remember" your name from 10 turns ago is simply re-reading the entire conversation transcript you (or your chat framework) re-sent as part of this request's input tokens. Nothing persists between API calls unless you explicitly resend it, or the provider offers a separate, bolted-on memory/caching feature.

      Practical consequence: long conversations get expensive (you resend the whole history every turn) and eventually hit the window limit, at which point something has to be truncated, summarized, or dropped — and if you don't design that truncation deliberately, the model silently loses early context.

      Autoregressive generation: one token at a time

      Generation is autoregressive: the model takes the current sequence of tokens, computes a probability distribution over its entire vocabulary for "what token comes next," samples (or picks) one token, appends it to the sequence, and repeats — feeding its own previous output back in as input for the next step. This is why streaming works the way it does (each token really is produced one at a time, in sequence) and why generation gets linearly slower as output gets longer: token N+1 cannot be computed until token N exists, because it's part of the input to produce N+1.

      Attention, practically: how the model decides what matters

      Internally, a transformer processes the sequence of token embeddings through many stacked layers, each containing a self-attention block. Attention's job: for each token position, decide how much to "pull in" information from every other token position, and combine them into an updated representation. Mechanically, each token's embedding is projected into three vectors — Query (Q), Key (K), and Value (V). The attention score between token i and token j is the dot product of Qi and Kj (scaled and passed through softmax to become a weight between 0 and 1, summing to 1 across all j); the output for token i is the weighted sum of all Vj using those weights. Intuitively: Q is "what am I looking for," K is "what do I offer," and a high Q·K match means "this other token is relevant to me, pull in its Value." This happens in parallel across many "heads" (multi-head attention), each able to specialize in a different kind of relationship (e.g. one head tracks subject-verb agreement, another tracks which pronoun refers to which noun), and is stacked across dozens of layers so relationships can compose (a late layer can combine what earlier layers already resolved).

      Causal (decoder-only) models used for chat apply a mask so a token can only attend to itself and earlier tokens, never future ones — consistent with generating left-to-right. This is also why prompt structure matters: content placed earlier in the context can only be "looked back at" by later content, not the reverse, and attention has a real, measurable bias toward the beginning and end of a long context over the middle (the "lost in the middle" effect, directly relevant to RAG — see RAG).

      Sampling, temperature, and why output varies

      The final layer produces logits — a raw score per vocabulary token — turned into probabilities via softmax. If you always picked the single highest-probability token (greedy decoding), output would be fully deterministic but often bland and repetitive. Real APIs sample from the distribution, shaped by parameters you control:

      • temperature — divides logits before softmax; low (→0) sharpens the distribution toward the top choice (more deterministic, more repetitive); high (→1+) flattens it (more diverse, more likely to go off the rails).
      • top_p (nucleus sampling) — restricts sampling to the smallest set of tokens whose cumulative probability exceeds p, cutting off the unlikely long tail regardless of how many tokens that takes.
      • top_k — restricts sampling to the k highest-probability tokens outright.

      Even at temperature 0, outputs can differ slightly run-to-run on frontier APIs due to floating-point non-determinism from batched GPU execution — a real, frequently-asked-about fact: "deterministic" settings are "mostly deterministic," not bitwise reproducible.

      Why a model answers in a "helpful assistant" voice

      Base pretraining (next-token prediction over internet-scale text) alone produces a model that continues text plausibly — not one that reliably follows instructions or refuses harmful requests. Production chat models go through further stages: supervised fine-tuning (SFT) on curated instruction/response pairs, and preference-based alignment (RLHF or newer variants like DPO/Constitutional AI) that use human or AI-generated preference judgments to push the model toward responses people rate as more helpful/honest/harmless. This is why a raw base model and a "chat" model behave so differently from the same architecture, and why system prompts work at all — the model has been specifically trained to treat a designated "system" role as higher-priority instructions.

      Hallucination: the honest mechanical explanation

      A model has no built-in fact database and no notion of "I don't know this." It is always doing the same thing: producing the statistically most plausible continuation given its training and the current context. When it has strong training signal (a fact repeated often, in many sources), the plausible continuation is usually correct. When it doesn't — an obscure API, a recent event after its training cutoff, a very specific number — the plausible continuation is still generated, confidently, because "plausible-sounding text" is the only thing the mechanism ever produces. This is why grounding the model in retrieved, verified text (RAG) and asking it to cite sources is an architectural fix, not a prompting trick — you are changing what information is actually in context, not hoping the model "tries harder" to be truthful.

      How It Works Under the Hood

      End-to-end path for a single request, in order:

      1. Tokenization — input text (system prompt + history + user message) is converted to token IDs via the model's tokenizer.
      2. Embedding — each token ID is looked up in an embedding table, producing a vector; a positional signal is added/blended in (so the model knows token order, since attention alone is order-agnostic).
      3. Transformer stack — the sequence of vectors passes through N stacked blocks, each doing self-attention (mixing information across positions) followed by a position-wise feed-forward network (transforming each position's representation independently), with residual connections and normalization around each.
      4. Prefill — for the input portion, this entire stack runs once over all input tokens in parallel (this is why prompt processing is comparatively fast and heavily parallelizable on GPU — it's a one-shot matrix computation over the whole prompt).
      5. Unembedding / logits — the final layer's output vector for the last position is projected back to vocabulary size, producing one logit per possible next token.
      6. Sampling — temperature/top_p/top_k shape the distribution; a token is chosen.
      7. Decode loop — that token is appended, and the model computes one more position's worth of attention/FFN (reusing cached K/V vectors from all previous positions — the KV cache — rather than recomputing the whole sequence) to produce the logits for the next token. This is why decode (output generation) is comparatively slow and serial per token, while prefill (reading the prompt) is fast and parallel — a critical distinction for reasoning about latency in streaming API design.
      8. Stop condition — generation ends when a stop token/sequence is produced, a max-tokens limit is hit, or (for tool-calling models) the model emits a structured tool-call block instead of continuing free text.

      Code Examples

      You'll never implement attention yourself in a product job, but seeing the tokenizer and sampling parameters directly removes the mystery. Example: inspecting token counts and watching how sampling parameters change output determinism.

      // Rough token-count estimate without calling an API — useful for client-side cost guards.
// Real tokenizers (tiktoken for GPT, Claude's own) are more precise; this approximation
// (~4 chars per token for English) is good enough for a UI budget warning.
function estimateTokens(text: string): number {
  return Math.ceil(text.length / 4);
}

// Calling an LLM API with sampling controls — note how temperature 0 is "mostly" deterministic,
// not guaranteed bit-for-bit identical across calls (GPU batching non-determinism).
import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

async function askDeterministic(question: string) {
  const resp = await client.messages.create({
    model: "claude-sonnet-4-5",
    max_tokens: 500,
    temperature: 0,          // sharpest distribution: favors the single most likely token
    messages: [{ role: "user", content: question }],
  });
  return resp.content;
}

async function askCreative(question: string) {
  const resp = await client.messages.create({
    model: "claude-sonnet-4-5",
    max_tokens: 500,
    temperature: 0.9,        // flatter distribution: more diverse, more likely to drift off-topic
    messages: [{ role: "user", content: question }],
  });
  return resp.content;
}

// BAD: resending an ever-growing, unbounded conversation history every turn.
// This silently approaches the context window limit and gets linearly more expensive per turn.
function badBuildHistory(allMessages: { role: string; content: string }[]) {
  return allMessages; // every single message, forever
}

// GOOD: cap history explicitly and summarize what falls off, so cost/latency stay bounded
// and you control what gets dropped instead of hitting a hard API error mid-conversation.
function goodBuildHistory(
  allMessages: { role: string; content: string }[],
  runningSummary: string,
  maxRecentTurns = 10
) {
  const recent = allMessages.slice(-maxRecentTurns);
  const summaryMsg = runningSummary
    ? [{ role: "system", content: `Summary of earlier conversation: ${runningSummary}` }]
    : [];
  return [...summaryMsg, ...recent];
}

      Real-World Production Scenario at Scale

      At scale

      A support-chatbot team ships a feature where the bot "remembers" the whole conversation. In week one it works fine. By week three, power users with 200+ message threads start getting truncated/garbled answers and the per-request cost for those users is 10x the median. The cause: the team was resending the full transcript every turn with no cap, so cost grew linearly with conversation length and eventually some threads exceeded the context window, silently dropping the earliest (often most important — the original problem statement) messages via the SDK's own truncation behavior. The fix was exactly the "GOOD" pattern above: a rolling window of recent turns plus a maintained summary of everything older, recomputed incrementally, with a hard token budget enforced before each call so cost and latency are predictable regardless of conversation length.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Treating "the model said X confidently" as evidence X is true. Confidence of phrasing and correctness are generated by completely separate mechanisms — fluency is the model's core competence; factual accuracy is a side effect that only holds when the training data strongly and consistently supported the answer. Never ship an LLM answer as fact without either grounding it in retrieved/verified data or clearly labeling it as unverified.

      • Don't assume more context is always better — past a point, relevant information gets diluted and the "lost in the middle" effect can make a model miss something that's literally in the prompt.
      • Token costs are asymmetric: output tokens typically cost several times more than input tokens on most providers — a feature that generates long answers is far more expensive than one that reads long input.
      • Temperature 0 does not mean "safe to cache the result forever" — it reduces but does not eliminate variance, and model versions change over time (silently, on "latest" aliases) which changes output too.
      • Don't conflate "bigger context window" with "better recall at every position in it" — a 200k window doesn't mean the model uses all 200k tokens equally well.

      Interview Questions

      Basic

      What is a token, and why doesn't the model operate on words or characters directly?

      A token is a subword unit produced by a tokenizer (typically BPE): frequent words are single tokens, rare words split into pieces, and unseen text degrades toward individual bytes. This gives a fixed, manageable vocabulary size while still representing any possible input text, at the cost of tokens per word being variable and unintuitive (especially for non-English text or jargon).

      Follow-up: why would a prompt full of random IDs or hashes cost noticeably more tokens than the same length of plain English?
      What is a context window, and what counts against it?

      The maximum number of tokens a model can process in one request, covering system prompt, conversation history, retrieved documents, tool schemas, and the generated output combined. There's no separate memory — anything the model appears to "remember" is just text being resent inside this window.

      Follow-up: what happens when a conversation's accumulated history exceeds the window?
      What does "autoregressive" mean in the context of LLM generation?

      The model generates one token at a time, each new token conditioned on all previous tokens (including ones it just generated itself), feeding its own output back in as input for the next step. It cannot generate token N+1 before token N exists.

      Follow-up: why does this make output generation slower, token-by-token, than processing the input prompt?
      What does the temperature parameter actually do?

      It rescales the logits before the softmax that turns them into probabilities. Lower temperature sharpens the distribution toward the highest-probability token (more deterministic/repetitive); higher temperature flattens it (more diverse, higher chance of an unlikely, possibly wrong, token).

      Follow-up: does temperature 0 guarantee the exact same output every time you run the same prompt?
      Why does an LLM "hallucinate" facts instead of saying "I don't know"?

      The model only ever does one thing: produce the statistically most plausible next token given its training and context. It has no built-in fact-checking step or confidence gate — fluent, plausible-sounding text is generated the same way whether the underlying claim is well-supported by training data or not.

      Follow-up: what's the architectural (not prompting) fix for reducing hallucination on factual questions?
      What's the difference between a base (pretrained) model and a chat/instruction-tuned model?

      A base model only continues text plausibly from pretraining on raw text. A chat model goes through further supervised fine-tuning on instruction/response pairs plus preference-based alignment (RLHF/DPO-style), which is what makes it reliably follow instructions, adopt an assistant persona, and respect a system prompt's priority.

      Follow-up: why does this explain why system prompts are more effective at steering behavior than just asking nicely in the user message?
      Why are output tokens usually priced higher than input tokens on LLM APIs?

      Generating output is inherently serial (one token at a time, each requiring a forward pass) while processing input (prefill) is parallelized over the whole prompt at once — output generation is the more compute-expensive, latency-sensitive part per token, and pricing generally reflects that.

      Follow-up: what design choice in a chat feature would you make differently knowing this?

      Medium

      Explain self-attention mechanically — what are Q, K, and V and how do they interact?

      Each token's embedding is projected into a Query, Key, and Value vector. The attention weight between token i and j is softmax(Q_i · K_j / sqrt(d)) across all j; the updated representation for token i is the weighted sum of all V_j using those weights. Q represents "what this position is looking for," K represents "what each position offers," and a high dot product means high relevance, so that position's Value gets pulled in more strongly.

      Follow-up: why is attention computed with multiple heads in parallel rather than one big attention computation?
      What is the KV cache, and why does it matter for latency and memory in production LLM serving?

      During decoding, each new token only needs to attend to all previous tokens' Key/Value vectors — which don't change — so a correctly implemented decoder caches them instead of recomputing the full sequence's attention on every new token. This makes decode roughly linear in new tokens generated rather than quadratic, but the cache itself grows with sequence length and consumes significant GPU memory, which is a real constraint on how many concurrent long-context requests a server can serve.

      Follow-up: why does this make very long conversations or very long system prompts expensive to serve even before considering token pricing?
      What is the "lost in the middle" effect and why does it happen?

      Empirically, models are measurably better at using information placed near the start or end of a long context than information buried in the middle, even though attention in principle lets any token attend to any other. It's attributed to training data distribution and positional/attention biases that favor the edges of a sequence. Practical implication: in RAG, the most relevant retrieved chunk should usually be placed last (closest to the question) or structured prominently, not buried in the middle of ten other chunks.

      Follow-up: how would you validate whether this is actually hurting your RAG pipeline's answer quality?
      Why can the same prompt at temperature 0 still produce slightly different outputs across calls on a hosted API?

      Hosted inference batches many requests together on GPUs, and floating-point operations are not strictly associative — the exact numerical result of a matmul can vary slightly depending on batch composition and execution order, even with greedy decoding. Temperature 0 removes sampling randomness but not this low-level numerical non-determinism. Model aliases like "latest" can also silently point to a different underlying checkpoint over time.

      Follow-up: if you need true reproducibility for an eval harness, what would you pin or control?
      Why does prefill scale differently with hardware than decode, and what does that mean for a system that mixes short and long prompts?

      Prefill processes the whole input in one parallel pass across GPU cores — it's compute-bound and scales well with batching and parallel hardware. Decode is memory-bandwidth-bound and inherently serial per token per request, so throwing more GPUs at it helps much less per-request; it mainly helps by serving more concurrent requests. A product with very long prompts but short answers (e.g. document Q&A) has a very different latency/cost profile than one with short prompts and long answers (e.g. long-form generation).

      Follow-up: which of your product's endpoints would benefit most from prompt caching, and why?
      How would you explain, to a skeptical PM, why "just make the prompt longer and more detailed" doesn't reliably fix a quality problem?

      Longer prompts increase cost and latency, dilute attention over more tokens (worsening lost-in-the-middle for the genuinely important instructions), and if the added detail is redundant or contradictory, can actively confuse the model about which instruction takes priority. Quality problems rooted in missing facts need retrieval/grounding, not more prompt text; quality problems rooted in ambiguous instructions need sharper, shorter prompts, not longer ones.

      Follow-up: what's one concrete way to test whether a prompt change actually helped, rather than just feeling like it should?
      What role does positional encoding play, and why does attention need it at all?

      Raw self-attention is permutation-invariant — without positional information, "the cat sat on the mat" and "mat the on sat cat the" would produce identical attention patterns, since attention only sees a set of Q/K/V vectors, not an inherent order. Positional encodings (absolute, or more commonly in modern models relative schemes like RoPE) inject order information into the vectors so the model can distinguish sequence position and relative distance between tokens.

      Follow-up: why do some positional encoding schemes generalize better to longer sequences than others — why does this matter for context-window extension?

      Advanced

      Design a token-budget enforcement system for a multi-turn chat product serving millions of users with wildly varying conversation lengths. What do you measure and cap?

      Key points: track input tokens (system + history + retrieved context) and output tokens (max_tokens cap) separately since they're priced and latency-impact differently; enforce a hard per-request token ceiling before calling the API (truncate/summarize history proactively rather than reacting to an API error); maintain a rolling summary of dropped history so truncation doesn't silently lose critical early context; set per-user or per-conversation budgets/alerts since a small fraction of power users often drive a disproportionate share of cost; log actual token usage per request (most APIs return this) to catch prompts that balloon unexpectedly (e.g. a bug that duplicates history).

      Follow-up: how would you detect, in production, that your truncation strategy is degrading answer quality rather than just saving cost?
      A teammate claims "since attention lets every token see every other token, context position shouldn't matter." Where's the flaw, and how would you prove them wrong empirically?

      The flaw: attention's theoretical capacity to connect any two positions doesn't mean it does so with equal fidelity in practice — training data distribution (documents tend to put key info at the start/end), learned attention patterns, and interactions with positional encoding all introduce real, measurable positional bias. To prove it: construct a needle-in-a-haystack test — insert the same fact at varying depths (0%, 25%, 50%, 75%, 100%) through a long filler context of fixed length, ask a question that requires the fact, and measure accuracy by position. This is a standard, publishable benchmark methodology for exactly this reason.

      Follow-up: how would this experiment's results change your RAG chunk-ordering strategy?
      Explain why multi-head attention is used instead of a single, larger attention computation with the same total parameter count.

      Splitting into multiple smaller heads lets the model learn several distinct, specialized attention patterns in parallel (e.g. one head tracking syntactic dependencies, another tracking coreference, another tracking long-range topical relevance) within the same layer, rather than being forced to find one attention pattern that averages/compromises across all these needs. Empirically this gives richer representational capacity for the same parameter budget — a single head collapses these distinct relational signals into one weighted average, losing the ability to represent "this token is relevant for reason A AND unrelated for reason B" simultaneously.

      Follow-up: how does this relate to why some heads can be pruned post-training with minimal quality loss, and what does that imply about head redundancy?
      Why is inference latency for a single long request often dominated by decode rather than prefill, and how does this change your system design for a chat product versus a summarization product?

      Prefill is a single parallel pass over the whole prompt (compute-bound, fast per token). Decode is serial, one token per forward pass, memory-bandwidth-bound by repeatedly reading the growing KV cache — so a response of 1000 output tokens takes roughly 1000x the "per-step" latency regardless of how long the input was. A chat product (short prompts, short-to-medium answers) is comparatively cheap and fast; a long-form generation product (long documents, long outputs) is decode-dominated and benefits far more from techniques like speculative decoding, response length limits, or switching to a smaller/faster model for the bulk of the generation.

      Follow-up: what is speculative decoding, at a high level, and why does it help specifically with the decode bottleneck?
      How would you design an automated eval to detect that a provider has silently changed the model behind a "latest" alias in a way that degraded your product?

      Maintain a fixed, versioned eval set (golden input/expected-behavior pairs covering your product's critical paths — factual grounding, tool-call correctness, tone, refusal behavior) and run it on a schedule against whatever model alias production actually points to, diffing scores against a stored baseline; alert on score drops beyond a threshold. Separately, log the model version string returned by the API on every real request (most providers return the resolved model ID, not just the alias) so you can correlate quality incidents with an actual version change after the fact, even if you didn't initiate it.

      Follow-up: why might you deliberately pin to an exact model version in production despite missing out on "free" improvements from a moving alias?

      Practice Assignments

      Beginner (30-60 min)

      Token counting and cost estimator

      Write a small Node/TypeScript script that takes a block of text and a model's pricing (input $/1M tokens, output $/1M tokens), estimates the token count, and prints the estimated cost of sending it as a prompt plus a hypothetical 500-token response.

      • Use a real tokenizer library (e.g. tiktoken or @anthropic-ai/tokenizer) rather than a character-count approximation.
      • Support at least two different models/pricing tiers via a config object.
      • Print input tokens, output token estimate, and total estimated cost separately.

      Acceptance criteria: running the script on a known string gives a token count within a few tokens of what the provider's own playground/console reports for the same text.

      Hints

      Most tokenizer libraries expose an encode(text) function returning an array of token IDs — the array length is your token count. Keep pricing as a simple lookup table keyed by model name.

      Bonus: add a warning when estimated input tokens exceed 50% of the model's context window.

      Intermediate (2-4 hrs)

      Sliding-window chat history manager with summarization

      Build a small TypeScript module that manages chat history for a conversation: keeps the last N turns verbatim, and once older messages fall off the window, asks the LLM to fold them into a running summary instead of discarding them outright.

      • Expose addMessage(role, content) and buildContextForNextCall().
      • When total estimated tokens exceed a configurable budget, summarize the oldest chunk of messages (via one extra LLM call) into/merged with the existing running summary, then drop those raw messages.
      • The context sent to the model should always be: summary (if any) + recent verbatim turns, under the token budget.

      Acceptance criteria: simulate a 50-turn conversation with a small token budget and verify the module never exceeds the budget, and that a fact mentioned early (then summarized) is still recoverable from the summary text later in the conversation.

      Hints

      Keep the summarization prompt tight and explicit: "Here is the current summary and a block of older messages. Produce an updated summary that preserves all facts, names, decisions, and open questions, in under 150 words." Test it in isolation before wiring it into the sliding window.

      Bonus: add a metric that logs how many raw messages vs. summarized tokens are in each constructed context, over the life of the conversation.

      Advanced (1-2 days)

      Needle-in-a-haystack positional recall benchmark

      Build a small evaluation harness that empirically measures "lost in the middle" behavior for a model of your choice, producing a chart of recall accuracy vs. the depth (percentile position) at which a fact was inserted into a long context.

      • Generate filler text of a fixed large size (e.g. ~50k tokens) — unrelated factual/narrative text works well (concatenate public domain text).
      • Insert a unique, synthetic "needle" fact (e.g. "The secret code for the blue door is 7f3k9.") at multiple depths: 0%, 10%, 25%, 50%, 75%, 90%, 100%.
      • For each depth, ask the model a question that can only be answered from the needle, and score whether the answer is correct, across several repeated runs per depth to reduce sampling noise.
      • Plot or tabulate accuracy by depth.

      Acceptance criteria: a clear, reproducible table/chart showing accuracy by position, with enough repetitions per depth to distinguish a real effect from sampling noise; a short written conclusion on whether/where this model shows the effect.

      Hints

      Keep the question format identical across depths so the only variable is needle position. Watch out for the model "cheating" by guessing from stylistic cues in your filler text — use genuinely unrelated filler, and make the needle fact unguessable without finding it.

      Bonus: repeat the experiment with the needle fact explicitly repeated twice at different depths, and see whether redundancy recovers accuracy — directly relevant to how you'd design RAG chunk ordering in practice.

      Quick Revision Cheat Sheet

      • Tokens = subword units from BPE-style tokenization; not words, not characters — rare/non-English text costs more tokens.
      • Context window = everything (system + history + retrieved docs + tools + output); no persistent memory between calls.
      • Generation is autoregressive: one token at a time, each conditioned on everything before it, including its own prior output.
      • Attention = Q·K similarity determines how much of each other token's V gets mixed in; multi-head lets several relationship types coexist.
      • Prefill (reading the prompt) is parallel and fast; decode (generating output) is serial and comparatively slow — this drives pricing and latency asymmetry.
      • Temperature/top_p/top_k shape sampling randomness; temperature 0 ≈ deterministic but not bitwise guaranteed on hosted APIs.
      • SFT + RLHF/DPO on top of base pretraining is what produces "helpful assistant" behavior and system-prompt obedience.
      • Hallucination is not a bug to patch with better wording — it's the mechanism working as designed without grounding; fix with retrieval, not prompting alone.
      • "Lost in the middle": content near the start/end of a long context is used more reliably than content buried in the middle.
