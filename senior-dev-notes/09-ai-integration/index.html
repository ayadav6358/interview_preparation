    AI Integration

    📚 7 chapters⏱ ~17–20 hrs total

    AI integration has become a real line item in senior and tech-lead interviews even outside dedicated ML roles — interviewers want to know you can reason about LLM behavior, design a production RAG or agent pipeline, control cost and latency, and avoid the failure modes (hallucination, prompt injection, runaway tool loops) that non-ML-background engineers routinely miss. This track builds that from first principles: how transformers actually generate tokens, how streaming and function calling work over the wire, how vector search and chunking really behave, how agents loop and fail, and how to ship all of it safely and cheaply inside a normal React/Node stack.

    Learning Outcomes

    • Explain next-token generation, attention, and context windows well enough to reason about model behavior and limitations in a design discussion — without needing an ML background.
    • Build against modern LLM APIs (Claude, GPT) using streaming, structured output, and tool/function calling, and know the SSE/token mechanics underneath the SDK.
    • Choose and tune an embedding model, a chunking strategy, and a vector index (HNSW vs IVF vs brute-force) for a given dataset size and recall/latency budget.
    • Design, build, and evaluate a RAG pipeline end-to-end, including retrieval quality metrics and common failure modes (lost-in-the-middle, chunk fragmentation, stale indexes).
    • Design an agent loop (ReAct-style) with guardrails against infinite loops, tool hallucination, and prompt injection from untrusted content.
    • Run AI features in production: cost/latency budgets, caching, rate limiting, PII handling, and continuous evaluation — and wire all of it into a real React/Node application.

    🏆 Capstone Project: Build a RAG-Based Chatbot Over Your Own Docs

    Problem statement: Build a production-shaped RAG chatbot over a set of your own markdown documents (e.g. this course's own chapter files, or a project's internal docs) that answers questions with citations, streams its response token-by-token, and can take one real action via tool calling (e.g. "create a support ticket") — with cost and latency logged on every request and a small eval set to catch regressions.

    Required features:

    • Ingestion/chunking pipeline: parse markdown, chunk with heading-aware splitting + overlap, store chunk metadata (source file, heading path, token count).
    • Embeddings generated per chunk and stored in a vector DB (pgvector, Qdrant, or even a local HNSW index) with a re-embedding path for when docs change.
    • Retrieval + re-ranking: top-k vector search followed by a cheap re-rank step (cross-encoder or LLM-based) before the chunks go into the prompt.
    • Node backend exposing a streaming chat endpoint (SSE or chunked HTTP) and a React chat UI that renders tokens as they arrive, including interim "thinking/retrieving" states.
    • One real tool/function call (e.g. "create a ticket" that writes to a database or calls a mock API), gated so the model can only invoke it with validated arguments.
    • Cost and latency logging per request (tokens in/out, model, retrieval time, generation time) and a basic dashboard or log view.
    • A simple eval set (15–30 question/expected-answer or expected-citation pairs) run automatically to catch retrieval or prompt regressions.

    Tech stack suggestion: Node.js + TypeScript (Fastify/Express) for the API, React for the chat UI, Claude or GPT API for generation, an embeddings API (OpenAI, Voyage, or Cohere) plus pgvector or Qdrant for storage, SSE for streaming.

    Milestones:

    1. Write a short design doc: data flow diagram, chunking strategy, index choice, and why.
    2. Build the ingestion pipeline and populate the vector DB from a real set of markdown files.
    3. Build the retrieval + re-rank step and verify it returns relevant chunks for 10 hand-picked queries before touching generation.
    4. Wire up the streaming chat endpoint and React UI, including citations rendered next to the answer.
    5. Add the tool-calling action with argument validation and a confirmation step.
    6. Add cost/latency logging and the eval set; run the eval set before and after a prompt change to prove it catches a regression.

    Evaluation checklist:

    • ☐ Can explain exactly why each retrieved chunk was selected (embedding similarity + re-rank score).
    • ☐ Streaming works token-by-token with no visible buffering lag, and errors mid-stream are handled.
    • ☐ The tool call cannot be triggered by injected text inside a retrieved document (tested with an adversarial doc).
    • ☐ Cost per query is known and a budget/rate-limit guard exists.
    • ☐ Can defend the chunking size/overlap and index choice against at least one alternative.
