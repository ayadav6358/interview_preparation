    Cloud, AWS, Docker & K8s

    📚 7 chapters⏱ ~18–21 hrs total

    The infrastructure layer senior engineers are expected to own end-to-end: packaging an app correctly with Docker, running it locally with Compose, orchestrating it in production with Kubernetes, knowing the core AWS primitives well enough to design a VPC and reason about IAM, picking serverless where it actually wins, provisioning everything as code with Terraform, and shipping changes with CI/CD patterns that fail safely. Staff/Lead interviews probe the internals here — layer caching, the K8s control loop, IAM policy evaluation, Terraform state — not just tool familiarity.

    Learning Outcomes

    • Explain Docker's union filesystem, layer caching, and multi-stage builds well enough to cut image size and build time by 10x on a real pipeline.
    • Design a local dev environment with Docker Compose that mirrors prod topology (networks, volumes, healthchecks, dependency ordering).
    • Reason about Kubernetes as a reconciling control-loop system: pods, Deployments, Services, Ingress, ConfigMaps/Secrets, and what the scheduler and controllers actually do.
    • Design a VPC, pick the right IAM policy shape, and know when to reach for EC2 vs S3 vs RDS vs managed services.
    • Decide serverless vs containers with real cost/latency/ops tradeoffs, not dogma.
    • Provision infrastructure with Terraform and understand state, locking, drift, and plan/apply internals.
    • Run blue-green and canary rollouts with real traffic-shifting mechanics, automated rollback, and feature flags as a decoupling layer from deploys.

    🏆 Capstone Project: Containerize, Orchestrate & Ship a Multi-Service App

    Problem statement: Take a realistic multi-service app — a Node.js API, a React frontend, Postgres, and Redis — and productionize it: multi-stage Dockerfiles, local orchestration with Docker Compose, Kubernetes manifests for a real cluster, a Terraform module for the AWS resources it would need in production, and a CI/CD pipeline that ships with a canary-style rollout and automatic rollback.

    Required features:

    • Multi-stage Dockerfiles for the API and frontend: build stage with full toolchain, final stage on a minimal base image, non-root user, layer order optimized for cache hits.
    • Docker Compose file wiring API + frontend + Postgres + Redis with healthchecks, a dedicated bridge network, named volumes for Postgres data, and env files per service.
    • Kubernetes manifests: Deployment + Service for API and frontend, Ingress routing paths to each, ConfigMap for non-secret config, Secret for DB credentials, readiness/liveness probes, resource requests/limits, and an HPA on the API Deployment.
    • A Terraform module provisioning the production AWS footprint: a VPC with public/private subnets, an RDS Postgres instance in the private subnet, an S3 bucket for static frontend assets, and IAM roles scoped to least privilege for whatever needs to talk to them.
    • A CI/CD pipeline (GitHub Actions or equivalent) that builds images, pushes to a registry, applies Terraform with a plan-then-apply gate, and rolls out to Kubernetes using a canary step (10% → 50% → 100% traffic) with an automated rollback trigger on error-rate threshold.

    Tech stack suggestion: Node.js (Fastify/Express) API, React (Vite) frontend, Postgres 16, Redis 7, Docker, Docker Compose, Kubernetes (kind or EKS), Terraform (AWS provider), GitHub Actions, Argo Rollouts or a manual canary script for traffic shifting.

    Milestones:

    1. Write multi-stage Dockerfiles for both services; measure and document image size and build-time before/after multi-stage + cache optimization.
    2. Bring the full stack up locally with Docker Compose, including healthcheck-gated startup order.
    3. Write and apply the Kubernetes manifests against a local cluster (kind/minikube); verify rolling updates and probe behavior under a forced crash.
    4. Write the Terraform module; run plan, apply, then deliberately cause drift and run plan again to see it detected.
    5. Wire the CI/CD pipeline end-to-end, including the canary stage and a rollback drill where you inject a bad deploy and watch it auto-rollback.
    6. Write a one-page runbook: how to deploy, how to roll back, how to read the canary metrics.

    Evaluation checklist:

    • ☐ Can explain exactly which Docker layers get cache-busted by a given file change.
    • ☐ Can trace a request from Ingress → Service → Pod and explain what each hop does.
    • ☐ IAM roles in the Terraform module follow least privilege — can justify every permission.
    • ☐ Terraform state is stored remotely with locking; a concurrent apply is safely rejected.
    • ☐ The canary rollback actually triggers automatically on a bad deploy, not just in theory.
    • ☐ Can defend at least 2 alternative designs rejected (e.g., ECS vs EKS, Lambda vs containers).
