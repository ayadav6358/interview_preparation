    Docker Deep Dive

    ⏱ 3 hrs📍 Chapter 1 of 7

    One-line summary: Images are a stack of immutable, content-addressed layers over a union filesystem — every build, cache, and size optimization decision follows directly from that one fact.

    On this page

      Why It Matters for a Senior Developer

      You've written Dockerfiles for years. The gap at Staff/Lead level isn't "can you write one" — it's whether you can explain why a build is slow, why an image is 1.2GB when it should be 80MB, why a cache keeps busting on every CI run, and why a container that works on your laptop OOM-kills in prod. All of those trace back to layer mechanics, the union filesystem, and how the daemon actually executes a build. Interviewers at this level ask "walk me through what happens when you run docker build" and expect you to talk about layer hashing and cache invalidation, not just syntax.

      Why

      Image bloat and slow builds are one of the most common real-world production pain points senior engineers are asked to fix — and the fix is almost always "restructure the Dockerfile around how caching actually works," not "add more RAM to the build box."

      Prerequisites

      Basic Dockerfile syntax and having run docker build/docker run before. Related: Docker Compose, Kubernetes Core.

      Core Concepts

      Images as layer stacks

      An image is a manifest (JSON) referencing an ordered list of layers, each a tarball diff, each addressed by a SHA256 content hash. A running container adds one thin writable layer on top (the "container layer") via a copy-on-write (CoW) filesystem driver — overlay2 on modern Linux. Reading a file walks down through layers until found; writing a file that exists in a lower layer triggers a "copy-up" into the writable layer first. This is why a container that writes a lot to a file that exists deep in the image (e.g. a large log file baked into a base image) pays a one-time copy-up cost and why containers are not meant to hold mutable state.

      Layer caching mechanics

      Each Dockerfile instruction produces a layer. The builder caches layers keyed by: (1) the instruction text itself, (2) the hash of the parent layer, and for COPY/ADD, (3) a checksum of the file contents being copied (not file timestamps). The moment one instruction's cache misses, every subsequent instruction in the file also misses — cache validity is a chain, not independent per-line. This is the single most important fact for Dockerfile ordering: put the least-frequently-changing instructions first (OS packages, then dependency manifests + install, then app source last), because app source changes on every commit and would otherwise invalidate everything below it.

      Gotcha

      COPY package.json package-lock.json ./ followed by RUN npm ci before COPY . . is the classic trick — it means dependency install is cache-hit on every build where only app code changed, which is most builds. Copying everything first and installing after throws this away completely.

      Multi-stage builds and BuildKit internals

      A multi-stage Dockerfile has multiple FROM blocks; each is an independent build stage with its own layer cache, and later stages can COPY --from=<stage> specific artifacts out of earlier ones. The build toolchain (compilers, dev dependencies, source maps) lives only in the builder stage and never reaches the final image — this is how a Go binary ships in a 10MB scratch image despite a multi-GB build stage, and how a Node app ships without its devDependencies or TypeScript compiler.

      Modern Docker builds run on BuildKit, not the legacy builder. BuildKit builds a DAG of the Dockerfile instead of executing linearly, so independent stages (e.g. building the frontend and the backend in parallel stages) execute concurrently. It also supports cache mounts (RUN --mount=type=cache,target=/root/.npm) which persist a cache directory across builds without baking it into any layer — critical for package manager caches that would otherwise bloat every layer that touches them. And it supports secret mounts (RUN --mount=type=secret,id=npmrc) so a build-time credential never gets written into any layer, unlike a naive ARG or ENV secret which persists in image history forever and is extractable with docker history.

      Union filesystem and storage drivers

      overlay2 merges layers by stacking directories: lowerdir (read-only image layers, applied bottom-up), upperdir (the writable container layer), and a merged view the container actually sees. Deleting a file that exists in a lower layer doesn't remove it from disk — overlay2 creates a "whiteout" marker in the upper layer that hides it from the merged view. This means deleting a large file in a later Dockerfile instruction does not shrink the image; the bytes are still in the lower layer and still shipped. The fix is to never write the large file in the first place (multi-stage), or to delete it in the same instruction that created it so it never becomes its own layer.

      Gotcha

      RUN wget big.tar.gz && tar xf big.tar.gz && rm big.tar.gz as one RUN never persists the tarball as a layer. Splitting that into three separate RUN lines bakes the tarball into a layer permanently — the final rm only hides it from the merged view, image size stays bloated.

      How It Works Under the Hood

      End to end, docker build: the CLI sends the build context (everything not excluded by .dockerignore) to the daemon/BuildKit; BuildKit parses the Dockerfile into a DAG of LLB (low-level build) ops; for each op it computes a cache key from the op type + inputs + parent digest; it walks the content-addressable local cache (and optionally a remote cache via --cache-from) looking for a match; on a hit it reuses the existing layer blob with zero execution; on a miss it executes the step in an ephemeral container, snapshots the resulting filesystem diff as a new layer, and computes that layer's content hash for future cache lookups. The final image manifest is an ordered list of these layer digests plus config (entrypoint, env, exposed ports) — pushing an image to a registry only needs to push layers the registry doesn't already have, which is why registries dedupe shared base-image layers across many images.

      Diagrams

      graph TD A[Dockerfile instructions] --> B{Cache key match?} B -- hit --> C[Reuse existing layer blob] B -- miss --> D[Execute in ephemeral container] D --> E[Snapshot FS diff as new layer] E --> F[Hash layer -> content-addressed digest] C --> G[Next instruction] F --> G G --> H[Final image manifest: ordered layer digests + config]

      Code Examples

      ## BAD: cache-hostile ordering — every code change reinstalls all deps
FROM node:20-slim
WORKDIR /app
COPY . .
RUN npm ci --omit=dev
CMD ["node", "server.js"]

## GOOD: multi-stage, cache-friendly, non-root, minimal final image
# ---- deps stage: cached unless package*.json changes ----
FROM node:20-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

# ---- build stage: full toolchain, never shipped ----
FROM node:20-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci
COPY . .
RUN npm run build        # e.g. TypeScript -> dist/

# ---- final stage: only runtime deps + compiled output ----
FROM node:20-slim AS final
WORKDIR /app
ENV NODE_ENV=production
RUN addgroup --system app && adduser --system --ingroup app app
COPY --from=deps  /app/node_modules ./node_modules
COPY --from=build /app/dist         ./dist
USER app
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD node dist/healthcheck.js || exit 1
CMD ["node", "dist/server.js"]

      # Inspect the layer history of an image and see which layers are large
docker history --no-trunc myapp:latest

# See the actual layer digests and base-image sharing
docker inspect myapp:latest --format '{{json .RootFS.Layers}}'

# Build with a remote cache so CI runners share cache across machines
docker buildx build \
  --cache-from type=registry,ref=myrepo/myapp:buildcache \
  --cache-to   type=registry,ref=myrepo/myapp:buildcache,mode=max \
  -t myrepo/myapp:latest --push .

      Real-World Production Scenario at Scale

      At scale

      A CI pipeline building 40 microservice images per deploy was taking 18 minutes total, mostly in npm ci steps that ran from scratch every time because the self-hosted runners were ephemeral (fresh VM per job, no local Docker cache). The fix was two-layered: switch to BuildKit with --cache-from/--cache-to against a registry-backed cache (so cache survives across ephemeral runners), and restructure every Dockerfile to the deps/build/final split above. Build time dropped to under 3 minutes aggregate because only services with actual dependency changes paid the install cost; everything else hit registry cache. Image sizes also dropped ~70% on average because devDependencies and build tooling stopped shipping to production.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Using :latest in production manifests. It's not pinned, it's mutable, and a rollback that re-pulls :latest can silently pull a newer image than the one you rolled back from. Always deploy by immutable digest or a specific semantic/commit-sha tag.

      • Always add a .dockerignore — without it, node_modules, .git, and build artifacts get sent as build context, slowing every build even on a full cache hit.
      • Run as a non-root USER — a container compromise with root inside often means root on the host if there's a container-runtime escape; it's cheap defense-in-depth.
      • Prefer COPY over ADD — ADD's auto-extract and URL-fetch behavior are surprising and have been the source of supply-chain issues.
      • Pin base image digests (FROM node:20-slim@sha256:...) for anything security-sensitive — tags can be repointed upstream.
      • Use HEALTHCHECK in the image, or rely on orchestrator-level probes (Kubernetes) — don't assume "process is running" means "process is ready."

      Interview Questions

      Basic

      What is a Docker image layer and why are they cached?

      Each Dockerfile instruction produces an immutable, content-hashed filesystem diff (a layer). Layers are cached by content hash so unchanged instructions can reuse a previously built layer instead of re-executing, which is why Dockerfile instruction order matters.

      Follow-up: what breaks the cache for a COPY instruction specifically?
      What's the difference between CMD and ENTRYPOINT?

      ENTRYPOINT defines the fixed executable that always runs; CMD supplies default arguments to it (or the full command if ENTRYPOINT isn't set). docker run args after the image name override CMD but are appended to ENTRYPOINT.

      Follow-up: how would you make an image behave like a CLI tool with sane defaults?
      Why use multi-stage builds?

      To separate the build toolchain (compilers, dev deps) from the runtime image, so the final image only ships what's needed to run the app — smaller, fewer CVEs, no build secrets.

      Follow-up: how do you copy an artifact from one stage to another?
      What does .dockerignore do and why does it matter?

      Excludes files from the build context sent to the daemon. Without it, large/irrelevant directories (node_modules, .git) slow every build and can leak files into COPY . . unintentionally.

      Follow-up: what happens if .git is included and you COPY . . — what's the risk?
      What is the difference between docker run and docker exec?

      docker run creates and starts a new container from an image; docker exec runs an additional process inside an already-running container.

      Follow-up: how would you debug a running production container without restarting it?
      What's the purpose of EXPOSE in a Dockerfile?

      It's documentation/metadata declaring which ports the container listens on; it does not actually publish the port. Publishing requires -p/--publish at run time or a Service in Kubernetes.

      Follow-up: does removing EXPOSE break networking?
      Why should containers run as non-root?

      Defense in depth — if an attacker achieves code execution inside the container, root-in-container combined with certain runtime misconfigurations or escape vulnerabilities can mean root on the host.

      Follow-up: how do you handle a process that needs to bind to port 80 as non-root?

      Medium

      Walk through what happens, layer by layer, when docker build runs.

      BuildKit parses the Dockerfile into a DAG, computes a cache key per instruction from instruction text + parent digest + (for COPY) file content checksums, checks local/remote cache, executes misses in ephemeral containers, snapshots the FS diff as a new content-addressed layer, and assembles the final manifest as an ordered list of layer digests plus image config.

      Follow-up: why does a cache miss on one instruction invalidate everything after it?
      Why doesn't deleting a file in a later RUN instruction shrink the image?

      overlay2 is append-only across layers; a delete in a later layer is a whiteout marker hiding the file from the merged view, but the bytes remain in the lower layer and are still shipped/pulled. Only not creating the file in a persisted layer (or deleting it within the same RUN that created it) avoids shipping the bytes.

      Follow-up: how would you verify this empirically on an existing image?
      How do BuildKit cache mounts differ from a regular layer?

      A cache mount (--mount=type=cache) persists a directory (e.g. ~/.npm) across builds in a side cache outside the image's layer chain, so repeated package-manager downloads are avoided without that cache data ever being committed into a shipped layer.

      Follow-up: why would baking the same cache dir into a layer instead be a mistake?
      Why is COPY package.json + npm ci before COPY . . a critical pattern?

      It isolates the dependency-install layer so it's only cache-busted when package.json/lockfile changes, not on every source edit — since cache invalidation cascades downward, this ordering is what makes most CI builds cache-hit on the expensive step.

      Follow-up: what happens if you use npm install instead of npm ci here?
      How would you securely pass a build-time secret (e.g. private registry token) without it leaking into the image?

      Use BuildKit's --mount=type=secret, which makes the secret available to a RUN step's filesystem only for that step's execution and never writes it into any layer or image history, unlike ARG/ENV which persist permanently and are extractable via docker history.

      Follow-up: how would you detect if a secret was accidentally baked into an existing image?
      Why can two services in the same registry share storage even with different image names?

      Layers are content-addressed by hash; if two images share an identical base-image layer, the registry stores that blob once and both manifests reference the same digest — dedup happens naturally, not by name.

      Follow-up: does this affect pull speed for a fleet of services sharing a base image?
      What's the risk of ARG for secrets even though it's "build-time only"?

      ARG values get baked into intermediate layer metadata/history and are visible via docker history or by inspecting layer diffs, even if the final stage doesn't reference them directly in a multi-stage build — they're not truly ephemeral.

      Follow-up: how is this different in a single-stage vs multi-stage build?

      Advanced

      Design a Dockerfile + CI caching strategy for a monorepo with 40 services sharing a lockfile, running on ephemeral CI runners with no persistent local disk.

      Use BuildKit with a registry-backed remote cache (--cache-from/--cache-to type=registry) so cache survives across ephemeral runners regardless of which machine builds next. Structure Dockerfiles with a shared deps stage keyed only on the lockfile hash so unrelated service changes don't bust it. Consider a shared base image layer for common runtime deps, built and cached once, referenced by all 40 service images via FROM, so registry-level layer dedup also saves pull bandwidth.

      Follow-up: how does mode=max on --cache-to differ from the default and why does it matter here?
      A security scan flags a CVE in a transitive OS package inside your final image, but your Dockerfile never installs it directly. How do you find and fix it?

      Inspect docker history/manifest layers to find which base image or intermediate layer introduced it; it's likely inherited from the base image. Fix by bumping the base image tag/digest, or by adding a targeted apt upgrade/remove of that package in a layer, or switching to a distroless/minimal base that doesn't ship it. Also check whether it's a build-stage-only dependency that shouldn't even be in the final stage if multi-stage isn't being used correctly.

      Follow-up: how would you prevent this regressing silently on every future build?
      Explain copy-up cost in overlay2 and when it becomes a real production performance issue.

      Writing to a file that exists in a lower read-only layer forces overlay2 to copy the entire file up into the writable layer first, then apply the write. For a small config file this is negligible; for a large file (e.g. a multi-GB dataset baked into the image that the app then modifies) the first write incurs a large one-time I/O cost, which under high container-churn (e.g. autoscaling spinning up many short-lived containers) can show up as CPU/I/O spikes cluster-wide.

      Follow-up: what's the fix — mount it as a volume instead, or avoid baking it into the image?
      Why can two builds of the "same" Dockerfile on different days produce different layer digests even with no code changes?

      Non-determinism in the build: apt/npm resolving to newer transitive package versions if not fully lockfile-pinned, timestamps embedded by some package managers, or a FROM tag that moved to a new digest upstream. True reproducibility requires pinning the base image by digest, using lockfiles for all package managers, and avoiding any instruction that embeds wall-clock time.

      Follow-up: why does this matter for supply-chain security audits?
      How would you reduce a 1.2GB Node.js image to under 150MB, and what would you check first?

      First check docker history for the largest layers — usually devDependencies, build tooling, or OS packages installed but never removed in the same layer. Fix: multi-stage build separating install/build from runtime, --omit=dev in the final npm ci, switch base to node:slim or distroless/nodejs, ensure no large files are deleted in a later layer instead of never persisted, and use a cache mount for npm's cache dir so it never lands in a layer at all.

      Follow-up: how do you verify the size reduction didn't break anything at runtime?

      Practice Assignments

      Beginner (30-60 min)

      Audit and fix a wasteful Dockerfile

      You're given a single-stage Node.js Dockerfile that COPYs the whole repo before installing deps and results in a 900MB image.

      • Add a .dockerignore
      • Reorder COPY/RUN for cache efficiency
      • Convert to multi-stage with a slim final image

      Acceptance criteria: Final image under 200MB; a source-only code change rebuilds in under 5 seconds from cache.

      Hints

      Check what npm ci actually needs (package.json + lockfile) before touching source. Use docker history to measure before/after.

      Bonus: Pin the base image by digest and justify the choice of base (alpine vs slim) for this app.

      Intermediate (2-4 hrs)

      Set up registry-backed BuildKit caching in CI

      Configure a CI pipeline (GitHub Actions is fine locally simulated) that builds a multi-stage image using buildx with --cache-from/--cache-to against a registry, across two separate "runner" invocations (simulate ephemeral runners by clearing local Docker cache between builds).

      • First build: no cache, record time
      • Second build with only source changed: should hit cache for deps layer
      • Second build with lockfile changed: should miss deps layer but still be faster than a cold build

      Acceptance criteria: Measurable, documented time difference across the three scenarios with explanation of why each cache hit/miss occurred.

      Hints

      docker buildx create --use for a builder that supports cache export; mode=max on --cache-to to export all layers not just the final one.

      Bonus: Add a build-time secret mount for a fake npm registry token and prove via docker history that it never appears in any layer.

      Advanced (1-2 days)

      Build a reproducible, minimal, multi-arch base image for your org

      Design a shared base image (used as FROM by multiple service Dockerfiles) that is pinned by digest, built for both amd64 and arm64 via buildx, scanned for CVEs as part of the build, and republished on a schedule.

      • Multi-arch manifest list published to a registry
      • Automated CVE scan gate before publish
      • Documented upgrade/rollback process for consuming services

      Acceptance criteria: left as an exercise — think through reproducibility, consumer impact of base image updates, and a rollback story if a new base image breaks a downstream service.

      Hints

      docker buildx build --platform linux/amd64,linux/arm64; consider how you'd pin consumers to a specific base digest vs a floating tag, and the operational tradeoff between the two.

      Quick Revision Cheat Sheet

      • Layers are content-hashed, immutable FS diffs; containers add one writable layer on top (CoW).
      • Cache invalidation cascades: one missed instruction busts every instruction after it.
      • Order Dockerfile instructions from least- to most-frequently-changing.
      • COPY package*.json + install before COPY . . is the single highest-leverage caching trick.
      • Multi-stage builds keep build toolchain and secrets out of the final image entirely.
      • Deleting a file in a later layer doesn't shrink the image — it only hides it (whiteout).
      • Use --mount=type=cache for package manager caches, --mount=type=secret for build secrets.
      • Pin base images by digest for anything security-sensitive; never deploy :latest.
      • Always run as non-root; always add a .dockerignore.
