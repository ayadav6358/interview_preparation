    Docker Compose

    ⏱ 2 hrs📍 Chapter 2 of 7

    One-line summary: Compose is a thin declarative layer over the Docker Engine API that wires multiple containers into one named network with dependency ordering — it is not an orchestrator, and knowing exactly where that line sits saves you from reaching for it (or K8s) at the wrong time.

    On this page

      Why It Matters for a Senior Developer

      Every team has a docker-compose.yml, and most of them have at least one subtle bug: a service that starts before its dependency is actually ready (not just "started"), a volume that silently diverges between dev and prod, or a network misconfiguration that only breaks under a specific startup order. At senior level you're expected to design the local dev environment so it's a faithful enough model of production that bugs show up locally instead of in staging.

      Why

      Compose is also frequently used as a lightweight deployment tool for single-host production (small startups, side projects, internal tools) — understanding its restart policies, healthchecks, and networking model matters even outside "just local dev."

      Prerequisites

      Comfortable with the Docker CLI and Dockerfiles. Related: Docker Deep Dive, Kubernetes Core.

      Core Concepts

      Services, networks, volumes

      A Compose file declares services (each maps to one or more containers from an image/build context), networks (by default Compose creates one bridge network per project and attaches every service to it, giving each service DNS resolution by service name), and volumes (named volumes for persistent data, bind mounts for live-reloading source code into a container during dev).

      depends_on vs real readiness

      depends_on without a condition only waits for the dependency's container to start — not for Postgres to finish accepting connections, not for a migration to finish. This is the single most common Compose bug: an API container starts, tries to connect to Postgres, and crash-loops for the first few seconds until Postgres is actually ready, by which time a naive restart policy may have already given up. The fix is depends_on with condition: service_healthy, tied to a healthcheck block on the dependency — Compose then genuinely blocks startup of the dependent service until the healthcheck passes.

      Gotcha

      A healthcheck that just checks "is the process running" (e.g. pg_isready with no retries/interval tuning) can still race during slow disk I/O on CI runners. Tune interval, retries, and start_period deliberately — don't just copy a healthcheck snippet from docs without matching it to your actual startup time.

      Compose networking model

      Each project gets an isolated bridge network; services reach each other by service name via Compose's embedded DNS (backed by the Docker daemon's internal resolver, 127.0.0.11 inside each container). Ports exposed via ports: are published to the host; ports only listed in a service's own expose (or not listed at all) are reachable from other containers on the same network but not from the host — this is why your API container can reach postgres:5432 with no published port, but your laptop's psql client needs an explicit ports: ["5432:5432"] to do the same.

      Override files and environment parity

      Compose merges docker-compose.yml with docker-compose.override.yml (loaded automatically) or an explicit -f base.yml -f dev.yml chain, letting you keep one base definition and layer dev-only bind mounts / debug ports on top without duplicating the whole file. The discipline this buys you: the base file should look structurally like what you'd actually run in production (same image build, same env var names, same healthchecks), with only genuinely dev-specific concerns (hot reload mounts, exposed debug ports) in the override.

      How It Works Under the Hood

      Compose is a client of the Docker Engine API, not a separate orchestration daemon. docker compose up resolves the dependency graph from depends_on, topologically orders service creation, creates the project network and volumes if missing, then for each service: builds the image if a build: context is given (subject to the same layer caching as a plain docker build), creates the container with the declared config, and starts it — waiting on healthcheck conditions where declared. There is no scheduler, no rescheduling across hosts, no built-in load balancing across replicas beyond what docker compose up --scale gives you (multiple containers of one service sharing the project network, with no automatic load balancing — you'd still need an external proxy in front). This is exactly the ceiling that pushes real multi-host, self-healing production workloads to Kubernetes or ECS.

      Code Examples

      name: myapp

services:
  frontend:
    build:
      context: ./frontend
      target: dev
    ports: ["5173:5173"]
    environment:
      VITE_API_URL: http://localhost:3000
    depends_on:
      api:
        condition: service_started
    volumes:
      - ./frontend/src:/app/src   # bind mount for hot reload, dev only

  api:
    build:
      context: ./api
      target: dev
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:app@postgres:5432/app
      REDIS_URL: redis://redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    volumes:
      - ./api/src:/app/src

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 3s
      timeout: 3s
      retries: 10
      start_period: 5s

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      timeout: 2s
      retries: 10

volumes:
  pgdata:

      # Bring the stack up, rebuilding only services whose build context changed
docker compose up -d --build

# Tail logs across all services with service-name prefixes
docker compose logs -f

# Run a one-off migration against the running postgres service
docker compose run --rm api npm run migrate

# Scale the api service to 3 replicas (no built-in LB — pair with a proxy)
docker compose up -d --scale api=3

      Real-World Production Scenario at Scale

      At scale

      A team's CI integration tests were flaky roughly 1 in 20 runs — API tests failing with connection-refused against Postgres. Root cause: depends_on listed postgres with no condition, so Compose considered the dependency "ready" the instant the container process started, not when Postgres finished WAL recovery and began accepting connections (which varied with CI runner disk speed). Adding a proper healthcheck on Postgres with condition: service_healthy on the API's depends_on eliminated the flakiness entirely — zero app-level retry logic needed, because Compose now guarantees real readiness order.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Bind-mounting node_modules from the host into the container (or not excluding it from a bind mount) silently overwrites the container's Linux-built native modules with the host's (possibly macOS/Windows) build — classic "works outside Docker, breaks inside" or vice versa. Use an anonymous volume to "shadow" node_modules inside the container instead of letting the host bind mount cover it.

      • Never bake secrets into the Compose file committed to git — use an untracked .env file or Docker secrets, and commit a .env.example.
      • Give every stateful service a named volume, not an anonymous one, so docker compose down (without -v) doesn't silently orphan it.
      • Keep the base Compose file structurally close to production (same image, same healthchecks); push dev-only conveniences into an override file.
      • restart: unless-stopped is usually the right default for anything meant to stay up locally across a daemon restart.

      Interview Questions

      Basic

      What problem does Docker Compose solve that plain docker run doesn't?

      It declaratively defines multiple related containers, their shared network, volumes, and startup dependencies in one file, replacing a series of manual docker run/network/volume commands.

      Follow-up: is Compose an orchestrator like Kubernetes?
      How do services in the same Compose project reach each other?

      By service name, via Compose's embedded DNS on the shared project network — e.g. the api service connects to postgres:5432, not localhost:5432.

      Follow-up: why doesn't localhost work between two containers?
      What's the difference between ports and expose in a Compose service?

      ports publishes the port to the host machine; expose (or omitting both) only makes it reachable from other containers on the same network, not from the host.

      Follow-up: why would you intentionally not publish a database port to the host?
      What does depends_on actually guarantee by default?

      Only container start order, not application readiness — the dependency container has started, not that the service inside it is ready to accept connections.

      Follow-up: how do you make it wait for real readiness?
      Why use a named volume instead of a bind mount for a database?

      Named volumes are managed by Docker, persist independently of the host filesystem layout, and survive docker compose down without -v, giving more predictable lifecycle semantics than a bind mount tied to a host path.

      Follow-up: when would a bind mount actually be preferable?
      How do you view logs for all services in a Compose project at once?

      docker compose logs -f, which tails and prefixes output by service name across every running container in the project.

      Follow-up: how would you filter to just one service's logs?

      Medium

      Explain exactly how to make an API service wait for Postgres to be truly ready, not just started.

      Add a healthcheck block to the postgres service (e.g. pg_isready) with tuned interval/retries/start_period, then set the api service's depends_on to { postgres: { condition: service_healthy } }. Compose then blocks api's start until the healthcheck reports healthy.

      Follow-up: what happens if the healthcheck never passes — does Compose hang forever?
      Why might bind-mounting the entire project directory into a Node container break native dependencies?

      If node_modules (containing OS-specific compiled native modules) is included in the bind mount, the host's build of those modules overwrites the container's Linux build, causing ABI mismatches at runtime. Fix with an anonymous volume mounted at node_modules to shadow the bind mount for that specific subdirectory.

      Follow-up: does this issue exist for pure-JS dependencies too?
      How would you structure Compose files to keep dev and "prod-like" configs in sync without duplication?

      Keep a base docker-compose.yml that mirrors production shape (image build target, env var names, healthchecks), then layer a docker-compose.override.yml (auto-loaded) or explicit -f chain adding only dev-specific bind mounts, debug ports, and verbose logging — never duplicating the whole service definition.

      Follow-up: how do multiple -f files merge when the same key is set in both?
      What actually happens on the network when you run docker compose up --scale api=3 with no proxy in front?

      Three containers are created for the api service, all reachable via the same service-name DNS entry which round-robins at the DNS level across the replicas' IPs — but there's no health-aware load balancing, retry, or connection draining, so a crashed replica can still receive traffic briefly.

      Follow-up: how would you add real load balancing locally?
      Why is committing a .env file with real secrets to git in a Compose project dangerous even for "just local dev"?

      Local dev credentials are often reused or structurally similar to staging/prod ones, get picked up by secret scanners anyway, and git history retains them even after later removal/rotation — the fix is .env in .gitignore plus a committed .env.example with placeholder values.

      Follow-up: how would you rotate a secret that was already committed and pushed?

      Advanced

      Your team wants to run a small production workload on Compose on a single EC2 box rather than standing up Kubernetes. What do you need to add beyond the dev Compose file to make this defensible?

      restart: always/unless-stopped policies, resource limits (mem_limit/cpus) to prevent one service from starving others, log rotation (Compose logging driver config, since container logs grow unbounded by default), a reverse proxy (nginx/traefik/Caddy) for TLS termination and routing, externalized secrets (not in the committed file), a backup strategy for named volumes, and a plan for what happens on host reboot/Docker daemon restart. Also explicitly document the ceiling: no multi-host failover, no rolling zero-downtime deploys without extra tooling.

      Follow-up: at what point would you say "this should move to K8s/ECS now"?
      Design a Compose-based local environment for a monorepo with 6 services and 2 databases such that a fresh clone + one command gets a new engineer to a fully working, seeded environment in under 5 minutes.

      One docker-compose.yml with healthchecked dependency ordering, a one-off init/migrate/seed service (depends_on all datastores being healthy, runs once via profiles or a dedicated `docker compose run`), cached builds via BuildKit so repeat `up --build` is fast, and a Makefile/script wrapping `docker compose up -d && docker compose run --rm migrate && docker compose run --rm seed` into one command. Document expected first-run time vs cached-run time.

      Follow-up: how do you avoid the seed step accidentally re-running destructively on every up?
      Why can depends_on with service_healthy still not fully prevent a startup race in a service that does async initialization after its HTTP server starts listening?

      If the healthcheck only tests "process/port is up" but the app does further async init (e.g. warming a cache, running in-process migrations) after the server starts accepting connections, a dependent service can still hit it mid-initialization. The healthcheck endpoint itself needs to reflect true application readiness (e.g. a /health endpoint gated on init completion), not just process liveness — this is the same readiness-vs-liveness distinction that matters even more in Kubernetes.

      Follow-up: how does this map to Kubernetes' separate readiness and liveness probes?

      Practice Assignments

      Beginner (30-60 min)

      Fix a flaky Compose stack

      Given a Compose file where an API service depends_on postgres with no condition and intermittently crash-loops on startup, diagnose and fix it.

      • Add a correct healthcheck to postgres
      • Wire depends_on with condition: service_healthy
      • Verify with repeated `docker compose up` runs that the race is gone

      Acceptance criteria: 20 consecutive `docker compose up` runs with zero API crash-loop restarts.

      Hints

      pg_isready is the standard healthcheck test for Postgres; tune start_period to your actual cold-start time.

      Bonus: Add a similar healthcheck-gated dependency for Redis.

      Intermediate (2-4 hrs)

      Build a full local dev stack with hot reload

      Compose stack with a React frontend, Node API, Postgres, and Redis, with bind-mount hot reload for both frontend and API source, without breaking native node_modules.

      • Base file resembling prod shape; override file for dev-only mounts
      • Anonymous volume shadowing node_modules
      • One-command fresh-clone-to-running setup

      Acceptance criteria: Editing a source file on the host reflects in the running container within 2 seconds, with no native-module breakage.

      Hints

      volumes: [./api/src:/app/src, /app/node_modules] — the second entry is the anonymous-volume shadow trick.

      Bonus: Add a seed service that only runs once and is idempotent on repeat `up`.

      Advanced (1-2 days)

      Harden a Compose stack for small-scale single-host production

      Take the dev stack and produce a production variant: resource limits, log rotation, reverse proxy with TLS, externalized secrets, and a documented backup/restore procedure for the Postgres volume.

      • nginx or Caddy in front with TLS (self-signed is fine for the exercise)
      • mem/cpu limits on every service
      • Backup script for the named Postgres volume + restore drill

      Acceptance criteria: left as an exercise — think through what happens on host reboot, what happens if one container OOMs, and how you'd actually restore from a backup under time pressure.

      Hints

      docker run with --volumes-from or a tar of the volume's mountpoint is the simplest backup mechanism to start from.

      Quick Revision Cheat Sheet

      • Compose = declarative multi-container wiring over the Docker Engine API; not an orchestrator.
      • Services reach each other by name via embedded DNS on the shared project network.
      • ports publishes to host; expose (or nothing) is container-network-only.
      • depends_on alone = start order only. Add healthcheck + condition: service_healthy for real readiness.
      • Named volumes for persistent state; bind mounts for dev hot-reload only.
      • Shadow node_modules with an anonymous volume when bind-mounting source into a Node container.
      • Base file should mirror prod shape; push dev-only concerns into an override file.
      • --scale gives you N replicas with zero health-aware load balancing — pair with a proxy if you need that.
