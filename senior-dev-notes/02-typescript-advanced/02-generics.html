    Generics In Depth

    ⏱ ~2.5 hrs📍 Chapter 2 of 6

    One-line summary: Good generics are designed so types are inferred from real arguments at the call site, not supplied manually — this chapter covers constraints, variance, inference sites, and the design discipline that makes that happen.

    On this page

      Why It Matters for a Senior Developer

      Why

      Generic design is the clearest signal of TS seniority in a live coding interview. Junior code passes type parameters explicitly everywhere (fetchData<User>(url)); senior code designs the function signature so TS infers User from an argument automatically. Interviewers will hand you a vague, loosely-typed helper and ask you to "make it properly generic" — this is exactly that skill.

      Prerequisites

      Builds on Type System Deep Dive (inference, narrowing). Related: Utility Types.

      Core Concepts

      Basics: parameters, constraints, defaults

      // Unconstrained — T can be anything, so you can't access any members on it
function identity<T>(x: T): T { return x; }

// Constrained — T must have a `length` property
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

// Default type parameter — used when TS can't infer and caller doesn't supply one
function createMap<K = string, V = unknown>(): Map<K, V> { return new Map(); }
const m = createMap(); // Map<string, unknown>

// Multiple constrained params referencing each other
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const user = { id: 1, name: "Ana" };
pluck(user, "name"); // string, inferred; pluck(user, "nope") is a compile error

      The pluck pattern — <T, K extends keyof T> — is the single most common "write a type-safe getter" interview exercise. Internalize it.

      Inference sites: where TS actually infers from

      TypeScript infers generic type parameters from argument positions (and a few other spots: contextual typing from the expected return type, and from the type of a variable a generic function result is assigned to). Parameters that appear only in the return type, or inside positions TS can't observe a concrete value for, can't be inferred and will fall back to the constraint or unknown.

      // T is inferable — it appears in a parameter position
function wrap<T>(value: T): { value: T } { return { value }; }
wrap(42); // T = number, inferred from the argument

// T is NOT inferable from any argument — caller must specify it explicitly
function parse<T>(json: string): T { return JSON.parse(json); }
const user = parse<{ id: number }>('{"id":1}'); // must annotate; T can't be inferred

// Design fix: make it inferable by accepting a "shape hint" value instead
function parseAs<T>(json: string, _shape: T): T { return JSON.parse(json); }
// still contrived — better fix is a runtime validator (see ch.5), which both
// infers AND actually checks the shape at runtime.

      This is the core design lesson: a generic parameter that only appears in the return type is a design smell — it forces callers to annotate manually, which is exactly the ergonomics problem senior generic design avoids.

      Variance: covariance, contravariance, bivariance

      Variance describes how subtyping of a compound type (arrays, functions, generics) relates to subtyping of its type parameters.

      • Covariant: if Dog is a subtype of Animal, then Container<Dog> is a subtype of Container<Animal>. TS arrays and "output position" generics (return types) behave this way.
      • Contravariant: the relationship flips for function parameter positions — a function accepting Animal can be used where one accepting Dog is expected (it handles at least as much), not the other way around.
      • Bivariant: TS checks method-shorthand parameters in both directions (unsoundly) for legacy compatibility — see chapter 1.
      type Animal = { name: string };
type Dog = { name: string; breed: string };

// Covariant position — fine, narrower return is safely substitutable
type AnimalFactory = () => Animal;
const dogFactory: AnimalFactory = (): Dog => ({ name: "Rex", breed: "Lab" }); // OK

// Contravariant position — handler accepting the WIDER type is substitutable
type DogHandler = (d: Dog) => void;
const animalHandler: DogHandler = (a: Animal) => console.log(a.name); // OK — handles any Animal, Dog included

// This direction is unsafe and correctly rejected under strictFunctionTypes:
// const dogOnlyHandler: (a: Animal) => void = (d: Dog) => d.breed.toUpperCase(); // Error

      Generic + conditional types: inferring nested shapes

      Combining generics with conditional types lets you destructure types, not just values, at the type level — this is the gateway to chapter 4's territory but belongs here conceptually:

      // Extract the resolved type from a Promise
type Awaited2<T> = T extends Promise<infer U> ? U : T;
type A = Awaited2<Promise<string>>; // string
type B = Awaited2<number>;            // number (not a promise, falls through)

// Extract function return type (this is literally lib.d.ts's ReturnType)
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;

// Generic class with a constrained, defaulted parameter — a typed cache
class Cache<T, K extends string | number = string> {
  private store = new Map<K, T>();
  get(key: K): T | undefined { return this.store.get(key); }
  set(key: K, value: T): void { this.store.set(key, value); }
}
const userCache = new Cache<{ id: number; name: string }>(); // K defaults to string

      How It Works Under the Hood

      During a generic call, the checker collects "inference candidates" for each type parameter by structurally comparing each argument's type against the corresponding declared parameter type, recording what each type parameter would need to be for that position to type-check. After scanning all arguments, it reconciles the candidates per type parameter into a single inferred type — generally the best common supertype of covariant candidates, and the most specific (intersection-like) type for contravariant candidates (parameters of callback arguments). If no candidates were collected for a parameter, TS falls back to its constraint, or to unknown, or the parameter's default.

      Variance checking happens in a second pass: once two generic instantiations need to be compared for compatibility (e.g. assigning one callback type to another), TS recursively compares the structural positions, flipping the comparison direction every time it crosses into a parameter position of a function type — that flip is literally what contravariance means mechanically.

      flowchart LR A["Call site: pluck(user, 'name')"] --> B["Collect candidate for T from arg 1: typeof user"] A --> C["Collect candidate for K from arg 2: literal 'name'"] B --> D["T = { id: number; name: string }"] C --> E["K extends keyof T → check 'name' in keyof T → OK"] D --> F["Resolve return type T[K] → string"] E --> F

      Code Examples

      // BAD: generic parameter not inferable, forces manual annotation at every call site,
// and nothing stops a caller from lying about T.
function unsafeGet<T>(obj: Record<string, unknown>, key: string): T {
  return obj[key] as T; // unchecked cast — T is purely "trust me"
}
const x = unsafeGet<number>(data, "count"); // could actually be a string at runtime

// GOOD: T is inferred from the object + constrained key, fully type-safe, zero casts
function safeGet<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const data = { count: 42, label: "x" };
const n = safeGet(data, "count"); // number, inferred, no annotation needed

// Generic builder pattern — each call narrows the accumulated type
class QueryBuilder<T extends Record<string, unknown> = {}> {
  private filters: Partial<T> = {};
  where<K extends string, V>(key: K, value: V): QueryBuilder<T & Record<K, V>> {
    (this.filters as any)[key] = value;
    return this as unknown as QueryBuilder<T & Record<K, V>>;
  }
  build(): T { return this.filters as T; }
}
const q = new QueryBuilder().where("status", "active").where("age", 30).build();
// q: { status: string } & { age: number } — accumulated via chained generics

      Real-World Production Scenario at Scale

      At scale

      A shared internal HTTP client library originally required every call site to manually annotate the response type: client.get<User>("/users/1"). Across ~40 services this produced dozens of mismatches where the annotation drifted from the actual API response after backend changes, because nothing connected the annotation to anything real — it compiled regardless of correctness. Redesigning the client around a typed route map (generic inferred from a route key rather than supplied manually, the same idea as this topic's capstone) eliminated the annotation entirely: the response type became a structural consequence of the route definition, so an API contract change that wasn't reflected in the route map now fails to compile at every affected call site instead of silently drifting.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Generic parameters that appear in multiple unrelated argument positions (e.g. function merge<T>(a: T, b: T): T) infer the union/best-common-supertype of both arguments, which is often wider than intended — passing a Dog and a Cat infers T as something like { name: string } (their common shape) rather than erroring, silently discarding the more specific fields from both. If arguments should genuinely be independent types, give them independent type parameters.

      • Design generics so the type parameter is inferred from a real argument, never supplied manually at call sites.
      • A type parameter that appears only in the return position is a smell — look for a way to connect it to an input.
      • Use <T, K extends keyof T> for "typed property access" style helpers.
      • Give genuinely independent values independent type parameters instead of reusing one for both.
      • Use defaults (<T = Foo>) to keep simple call sites simple while still allowing overrides.

      Interview Questions

      Basic

      What does <T extends U> mean in a generic declaration?

      It constrains T to types assignable to U — T can be U or anything narrower/more specific, which lets you safely access U's members on a value of type T.

      Why can't a generic parameter be inferred if it only appears in the return type?

      Inference works by comparing argument types to parameter positions; if T never appears in a parameter, there's no argument value to derive it from, so the caller must supply it explicitly or it falls back to a default/constraint.

      Write a generic first<T>(arr: T[]): T | undefined and explain why it's "properly generic".

      function first<T>(arr: T[]) { return arr[0]; } — it's properly generic because T is inferred automatically from the array argument's element type at every call site; callers never annotate it.

      What's the difference between a default type parameter and a constraint?

      A constraint (extends) restricts what types are legal for the parameter. A default (= Foo) supplies a fallback type used only when inference can't determine one and the caller didn't specify one — it doesn't restrict what's allowed.

      What is the keyof operator and how is it typically combined with generics?

      keyof T produces a union of T's property name literal types. It's commonly paired as <T, K extends keyof T> to type-safely reference a dynamic property name on T.

      Can a generic function have more than one type parameter depend on another, e.g. <T, K extends keyof T, V extends T[K]>?

      Yes — type parameters can reference earlier ones in their constraints, letting you build up progressively more specific relationships between parameters.

      Medium

      Explain covariance vs contravariance with a concrete function-type example.

      Covariance: a function returning a more specific type can substitute for one returning a more general type (narrower outputs are fine). Contravariance: a function accepting a more general parameter type can substitute for one accepting a more specific type (handling "more" is fine, handling "less" isn't) — this is why (a: Animal) => void is assignable to a (d: Dog) => void-typed slot but not vice versa.

      Why does TypeScript check method-shorthand parameters bivariantly, and what unsafe pattern does it enable?

      For backward compatibility with common pre-strict-function-types patterns (especially array method overriding in class hierarchies before strict variance checking existed). It enables assigning a method with a narrower, more specific parameter type where a wider one is expected, which can let incompatible values reach the override at runtime.

      Given function merge<T>(a: T, b: T): T, what happens if you call it with two structurally different object types, and why might that be undesirable?

      TS infers T as the best common supertype of both arguments' types — typically their shared shape — rather than erroring. This silently discards type information unique to each argument and can mask a bug where the two arguments were never meant to be treated as the same type.

      How would you redesign a generic function so a caller can never pass a mismatched key/value pair, using two type parameters?

      Use <T, K extends keyof T> for the key so it's restricted to T's actual property names, then type the value parameter as T[K] rather than a separate unconstrained generic — this connects the value's required type directly to whichever key was passed, so an invalid pair fails to compile.

      What's the difference between inferring a generic from a parameter vs from a contextual return-type expectation (e.g. assigning to an explicitly typed variable)?

      Parameter-based inference derives T directly from argument value types. Contextual inference instead propagates an expected type backward into the call (e.g. from a variable's declared type or a surrounding function's expected return) — TypeScript's "contextual typing," used e.g. when inferring callback parameter types from the expected function type.

      Advanced

      Design a type-safe pipe() function that composes an arbitrary number of typed functions end-to-end, inferring each stage's input/output. What generic technique makes the variadic chain type-check?

      Use a variadic tuple type parameter with constrained overloads (or a recursive conditional type) that checks each adjacent pair's output/input compatibility — commonly implemented as a tuple of function types `Fns extends [(a: any) => any, ...any[]]` combined with a recursive helper type that walks the tuple pairwise verifying `Fns[i]`'s return is assignable to `Fns[i+1]`'s parameter, with the overall pipe's input/output derived from the first function's parameter and the last function's return.

      Explain precisely why TypeScript's variance checking for generic classes is "measured", not fully sound — what does the compiler actually verify?

      TS performs structural, member-by-member comparisons rather than true nominal variance annotations (no `in`/`out` enforcement by default, though TS 4.7+ lets you declare `in`/`out` markers for stricter checking). Without explicit variance annotations, the checker infers "measured" variance by analyzing how the type parameter is actually used in the class's members, which can be more permissive than a hand-verified sound variance rule, especially with mutable fields that use the type parameter in both read and write positions.

      Why might two independently-used generic type parameters still leak into each other's inferred type in certain overload resolutions, and how do you prevent it?

      If overload signatures aren't mutually exclusive, or if a single implementation signature's inference scans all arguments together rather than per-overload, TS can unify type parameters across what should be unrelated positions. Prevent it by keeping overloads genuinely disjoint (non-overlapping argument shapes) or restructuring to a single signature using conditional types keyed off a discriminant argument instead of overloads.

      How does TypeScript handle generic inference when an argument's type itself contains unresolved generic placeholders (higher-order generic inference), e.g. passing a generic function as an argument to another generic function?

      This is a known weak spot: TS 5.x added partial support for "higher order function type inference" allowing a generic function passed as an argument to have its own type parameters correctly instantiated based on the outer call's context, but this support is limited to specific shapes (e.g. a generic callback directly in parameter position) — deeply nested or indirect cases still often require the caller to specify type arguments explicitly or restructure the API to avoid needing it.

      You have a generic cache class whose `get` method's return type should narrow based on a runtime key registered via a separate typed `register()` call. How would you model this with generics, and what are the limits of what the type system can track across separate method calls?

      You'd typically model the whole registered-keys-to-types mapping as a single type parameter (a lookup object type) on the class itself, updated via the builder-chaining pattern (each `register()` call returns a new class instance typed with an intersected mapping), since TypeScript cannot mutate a class instance's own generic type parameter in place after construction — there's no way to have a single stateful instance's type parameter change across separate method calls without re-assigning to a new statically-retyped reference.

      Practice Assignments

      Beginner (30-60 min)

      Type-safe groupBy

      Implement function groupBy<T, K extends string | number>(items: T[], keyFn: (item: T) => K): Record<K, T[]>.

      • Both T and K must be inferred, never explicitly annotated at call sites.
      • No any.

      Acceptance criteria: calling it on an array of objects with a keyFn returning one of their literal-typed fields infers a precisely keyed record type.

      Hints

      The implementation body will need one `as` or a loosely-typed accumulator internally — that's fine, since the public signature stays fully safe. Internal implementation-detail casts are acceptable; public API casts are not.

      Bonus: add an overload that also accepts a plain key string instead of a function.

      Intermediate (2-4 hrs)

      Generic fluent QueryBuilder

      Extend the QueryBuilder from the code examples into a working mini library: .where(), .orderBy(), .limit(), .build() returning a fully-typed filter object accumulated across the chain, with no two .where() calls on the same key allowed to conflict in type.

      • Each chained call must narrow the builder's generic type parameter.
      • Calling .build() mid-chain returns the correctly accumulated type at that point.

      Acceptance criteria: a // @ts-expect-error test proves re-using a key with an incompatible value type fails to compile.

      Hints

      Use `Record<K, V>` intersections accumulated via `T & Record<K, V>` as the new generic parameter returned from each `.where()` call, same pattern as the chapter's code example.

      Bonus: make .orderBy() only accept keys that exist on the accumulated filter type so far.

      Advanced (1-2 days)

      Variadic type-safe pipe()

      Implement a pipe(...fns) function that composes 2-6 functions end to end with full type inference of intermediate stages, rejecting at compile time any pair of adjacent functions whose output/input types don't match.

      • Must work for at least 5 chained functions without manual type arguments.
      • A mismatched pair in the middle of the chain must produce a compile error pointing roughly at the right argument.

      Acceptance criteria: a handful of valid and invalid chains (via // @ts-expect-error) all behave as expected under tsc --strict.

      Hints

      Research "variadic tuple types" and recursive conditional types over tuples — you'll likely need an overload set for small fixed arities (2 through 6) rather than one fully generic recursive type, which is a legitimate, commonly-used real-world compromise.

      Quick Revision Cheat Sheet

      • Design generics so T is inferred from an argument — never require manual type arguments at call sites.
      • A type parameter appearing only in the return position is a design smell.
      • <T, K extends keyof T> is the standard pattern for type-safe property access.
      • Covariant: output/return positions. Contravariant: function parameter positions. Bivariant: method shorthand (unsound, legacy).
      • Two unrelated values sharing one type parameter infer their best common supertype, often wider than intended.
      • Builder/fluent patterns accumulate type info via chained generic returns, each call re-typing the next instance.
      • Higher-order generic inference (generic callback passed into a generic function) is improving in TS 5.x but still has real limits.
