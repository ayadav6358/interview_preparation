    tsconfig, Strict Mode, Declaration Files, Monorepos

    One-line summary: Knowing the type system is half the job; a senior/lead is also expected to own the compiler configuration that keeps a large codebase's type-checking correct, fast, and consistently enforced across every package in a monorepo.

      Why It Matters for a Senior Developer

      Why

      At staff/lead level you're expected to make and defend decisions like "should we enable noUncheckedIndexedAccess on a 5-year-old codebase", "why is tsc taking 4 minutes on every save", and "how do we share types between our frontend and backend packages without circular dependency hell." These are exactly the kinds of pragmatic, infrastructure-shaped questions that distinguish a senior interview from a mid-level one — type system trivia gets you in the door, but this chapter is what gets you trusted to own a repo's TS setup.

      Prerequisites

      Benefits from all prior chapters, especially Type System Deep Dive for the strict-flag discussion. Related: Cloud, AWS, Docker & K8s for CI/build pipeline context.

      Core Concepts

      Strict mode: what each flag actually does

      strict: true is a bundle of individually-togglable flags. Knowing what each one actually changes (not just "it makes things stricter") is a very common interview probe.

      FlagWhat it actually does
      strictNullChecksnull/undefined are not implicitly part of every type; you must explicitly include them in a union to allow them. The single highest-impact flag.
      noImplicitAnyAny value the compiler can't infer a type for and would otherwise default to any instead raises an error.
      strictFunctionTypesFunction parameters are checked contravariantly instead of bivariantly for function-typed values (not method shorthand — see ch.1/2).
      strictPropertyInitializationClass properties without a default or constructor assignment must be explicitly typed as possibly undefined or marked definitely-assigned (!).
      strictBindCallApply.bind()/.call()/.apply() are type-checked against the function's actual signature instead of returning any.
      noImplicitThisthis inside a function with no clear contextual type is an error instead of implicitly any.
      alwaysStrictEmits "use strict" and parses files in ECMAScript strict mode.
      useUnknownInCatchVariables(TS 4.4+) catch (e) types e as unknown instead of any, forcing you to narrow before use.

      Flags not included in strict but worth knowing: noUncheckedIndexedAccess (index/Record lookups return T | undefined), noPropertyAccessFromIndexSignature (forces bracket notation for index-signature-only properties, catching typos), and exactOptionalPropertyTypes (an optional property's declared type cannot be explicitly assigned undefined unless undefined is in the union — distinguishes "missing" from "present but undefined").

      Project references: the monorepo primitive

      TypeScript project references (composite: true + references: [...]) let you split a large codebase into independently-buildable packages, where tsc --build only rechecks packages whose dependencies actually changed, using cached .tsbuildinfo incremental state per package.

      // packages/shared-types/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}

// packages/api/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "references": [{ "path": "../shared-types" }],
  "include": ["src"]
}

// Root orchestrating tsconfig (not usually compiled directly, just for `tsc --build`)
{
  "files": [],
  "references": [
    { "path": "packages/shared-types" },
    { "path": "packages/api" },
    { "path": "packages/web" }
  ]
}

      Without composite/references, a monorepo typically either (a) has every package import every other package's raw .ts source, so the whole repo gets rechecked on every build with no incrementality boundary, or (b) relies entirely on each package pre-building to JS + .d.ts and consuming compiled output, which is correct but slow to iterate on locally (every tiny change needs a rebuild step). Project references give you real incremental, dependency-aware builds without giving up the "import source directly in dev" ergonomics most monorepo tooling (Turborepo, Nx) is built around.

      Declaration files: what .d.ts actually is and when you write one by hand

      // Auto-generated by `declaration: true` — don't hand-write these for your own TS code
// dist/user.d.ts
export interface User {
    id: string;
    name: string;
}
export declare function getUser(id: string): Promise<User>;

// Hand-written — for a plain-JS dependency with no types, or to extend a global
// types/legacy-lib.d.ts
declare module "legacy-lib" {
  export function doThing(x: number): string;
}

// Augmenting a global (e.g. extending Express's Request type with your auth middleware's field)
// types/express.d.ts
declare global {
  namespace Express {
    interface Request {
      user?: { id: string; roles: string[] };
    }
  }
}
export {}; // needed to make this file a module, not a global script,
            // while still allowing the `declare global` augmentation to apply

      That export {} at the bottom is a very common point of confusion: without at least one top-level import/export, a .d.ts file is treated as a global script (everything it declares pollutes the global scope directly) rather than a module — but once you add any import/export, declare global { ... } becomes necessary specifically to escape back out to global augmentation from within a module.

      Sharing types cleanly across monorepo packages

      The two dominant patterns: (1) a dedicated @myorg/types package other packages depend on normally (clean, but adds a build step/dependency edge for every type change), or (2) generating types from a single source of truth (an OpenAPI/GraphQL schema, or — matching this topic's capstone idea — a typed route definition file) so frontend and backend both consume generated types rather than hand-syncing two separate definitions. At scale, (2) is usually the senior-preferred answer for anything crossing a network boundary, because hand-synced types between frontend and backend silently drift the moment someone forgets to update one side.

      How It Works Under the Hood

      tsc --build with project references works by topologically ordering the reference graph, building each dependency project to its declared outDir (emitting both JS and .d.ts) before building anything that depends on it, and recording a content hash / timestamp fingerprint per project in its .tsbuildinfo file. On a subsequent build, it compares each project's current inputs against that fingerprint and skips re-checking/re-emitting any project whose inputs (and whose dependencies' outputs) are unchanged — this is why composite projects MUST emit declaration files: a downstream project type-checks against the upstream project's .d.ts output, not its .ts source, which is also what enables the incrementality (re-checking downstream only needs to re-read a declaration file, not re-typecheck the dependency's full implementation).

      Diagrams

      flowchart TD A["tsc --build (root tsconfig)"] --> B["Topologically sort references"] B --> C["Build shared-types first (composite, emits .d.ts)"] C --> D["Build api (references shared-types, type-checks against its .d.ts)"] C --> E["Build web (references shared-types, type-checks against its .d.ts)"] D --> F["Write api/.tsbuildinfo fingerprint"] E --> G["Write web/.tsbuildinfo fingerprint"] F --> H["Next build: unchanged inputs → skip rebuild entirely"] G --> H

      Code Examples

      // A realistic, defensible tsconfig.json base for a modern (2025-26) Node/React monorepo package
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",            // or "ESNext" + bundler moduleResolution for frontend packages
    "moduleResolution": "NodeNext",
    "lib": ["ES2022"],                 // add "DOM" for frontend packages
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noPropertyAccessFromIndexSignature": true,
    "exactOptionalPropertyTypes": true,
    "esModuleInterop": true,
    "skipLibCheck": true,              // don't re-check node_modules' own .d.ts files — big perf win
    "forceConsistentCasingInFileNames": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,            // lets "go to definition" jump to source, not just .d.ts
    "sourceMap": true,
    "incremental": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"],
  "exclude": ["node_modules", "dist"]
}

      Real-World Production Scenario at Scale

      At scale

      A 25-package monorepo's tsc --noEmit CI check grew to ~6 minutes as the codebase grew, because every package re-type-checked every other package's full source on every CI run with no incremental cache persisted between runs, and skipLibCheck was off, meaning every dependency's own .d.ts files (including deeply nested transitive ones) were re-verified every time too. Enabling project references with real package boundaries, turning on skipLibCheck, and persisting each package's .tsbuildinfo as a CI cache keyed on a lockfile hash brought full CI type-checking down to under 90 seconds on a typical PR touching 2-3 packages, because unaffected packages' builds were skipped entirely rather than re-verified from scratch.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Enabling strict (or any of its sub-flags) on a large existing codebase all at once typically produces hundreds or thousands of new errors overnight, which teams either panic-revert or — worse — silence wholesale with blanket // @ts-ignore. The standard mitigation is enabling strict flags per-sub-flag, often per-directory via a tsconfig override or a tool like ts-migrate, landing them incrementally with ownership assigned per area of the codebase, rather than attempting a single big-bang flip.

      • Always set skipLibCheck: true in application code — re-checking dependencies' own type definitions is rarely worth the cost.
      • Use project references for any monorepo package that's imported by more than one other package.
      • Prefer generating shared types from a single source of truth (schema/route definitions) over hand-synced packages for anything crossing a network boundary.
      • Enable noUncheckedIndexedAccess and exactOptionalPropertyTypes on new projects from day one — retrofitting them later is painful but usually still worth doing.
      • Never hand-write a .d.ts for your own TypeScript source — only for untyped JS dependencies or global augmentation.

      Interview Questions

      Basic

      What does strictNullChecks actually change?

      Without it, null and undefined are implicitly assignable to every type; with it, they must be explicitly included in a type's union for a value to legally be null/undefined.

      What's the difference between strict: true and individually enabling flags?

      strict: true is shorthand for enabling a whole bundle of related flags (strictNullChecks, noImplicitAny, etc) at once; you can still override individual ones afterward if needed.

      What is skipLibCheck and why is it almost always turned on?

      It skips type-checking of .d.ts files, including those in node_modules. It's turned on because re-verifying third-party declaration files (which are assumed already correct) on every build is usually wasted compile time with little benefit.

      What's the purpose of a .d.ts file?

      It declares types for JavaScript code without containing any implementation — used for untyped JS dependencies, or auto-generated as the public type surface of your own compiled TypeScript package.

      What does noUncheckedIndexedAccess do?

      Makes any indexed access (array index, or a Record/index-signature lookup) return T | undefined instead of just T, since nothing actually guarantees the key/index exists.

      Medium

      Explain what composite: true requires and why.

      It requires declaration: true (and implicitly sets some other constraints like disallowing certain unlisted includes) because composite projects are meant to be referenced by other projects, which type-check against their emitted .d.ts output rather than re-reading their raw source.

      How does tsc --build decide whether to skip rebuilding a referenced project?

      It compares the project's current source files and its dependencies' outputs against the fingerprint recorded in its .tsbuildinfo file from the last build; if nothing relevant changed, it skips both type-checking and re-emitting that project entirely.

      Why would you choose to generate shared types from an OpenAPI/GraphQL schema instead of hand-writing a shared types package for an API contract?

      Hand-synced types between two packages (e.g. frontend and backend) can silently drift whenever one side's types are updated without the other being updated to match, since nothing enforces the sync; generating both from one schema source of truth makes drift structurally impossible — a schema change regenerates both sides consistently or fails the generation step.

      What's the risk of rolling out strict mode flags all at once on a large legacy codebase, and what's a safer rollout strategy?

      It can produce an overwhelming number of new errors at once, leading teams to either revert strict mode entirely or mass-suppress errors with blanket ignores, defeating the purpose. A safer strategy enables flags incrementally (one sub-flag at a time, or scoped per-directory via tsconfig overrides), assigning ownership and fixing real issues gradually rather than suppressing them.

      Why does a .d.ts file need at least one import/export to be treated as a module rather than a global script, and why does that matter for declare global?

      TypeScript (matching JS module semantics) treats a file with no top-level import/export as a global script, where every declaration pollutes the global scope automatically — once you add any import/export, the file becomes a module with its own scope, and `declare global { ... }` is then required as the explicit escape hatch to still augment the global scope from within that module.

      Advanced

      Design a strategy for incrementally rolling out strict: true across a 200k-line legacy codebase with an existing CI pipeline that must stay green throughout.

      Enable strict flags one at a time, starting with the highest-value/lowest-noise ones (`noImplicitAny`, then `strictNullChecks` last since it's usually the biggest). For each flag, generate a baseline error count, suppress pre-existing errors with a tracked, dated `// @ts-expect-error` (or a per-file allowlist consumed by a custom lint rule) rather than blanket-ignoring, require all NEW code to be clean under the flag immediately, and track the suppressed-error count trending to zero over time as a team-visible metric, removing suppressions as files are touched for other reasons.

      Explain exactly why composite project references require emitting declaration files rather than letting downstream projects read upstream `.ts` source directly, and what incrementality property this buys you.

      If downstream projects read upstream raw source, type-checking downstream would require re-type-checking the entire upstream implementation transitively every time, defeating incrementality — there'd be no stable, cheap-to-read artifact representing "what upstream's public surface currently is." Requiring `.d.ts` emission gives a project-boundary-respecting contract: downstream only needs to read a (usually much smaller) declaration file and can skip re-verifying upstream's actual implementation logic, which is also why changing an upstream project's internal implementation without changing its public type signature doesn't force downstream rebuilds.

      You need to share a validation schema (and its inferred types) between a Node backend and a React frontend in a monorepo, where the frontend bundler can't handle certain backend-only dependencies the schema file might accidentally pull in. How do you architect the shared package to avoid this?

      Isolate the schema definitions (and only the schema definitions — no backend-specific logic like DB clients) into their own leaf package with zero backend-only dependencies, exporting both the schemas and their `Infer`-derived types; both frontend and backend depend on this leaf package, and any backend-only logic that uses those schemas lives in a separate package that the frontend never imports, keeping the dependency graph's "frontend-safe" boundary explicit and enforceable (optionally lint-enforced via import restrictions).

      What causes `tsc --build` to sometimes rebuild more than expected even when `.tsbuildinfo` is present and seemingly valid, and how would you debug it?

      Common causes: the `.tsbuildinfo` cache wasn't restored correctly in CI (wrong cache key, e.g. not including the TypeScript version or tsconfig hash), a referenced project's declaration output changed in a way that invalidates downstream fingerprints even if source didn't change meaningfully (e.g. formatting-only changes to emitted `.d.ts`), or `outDir`/`rootDir` misconfiguration causing paths to not match between builds. Debug with `tsc --build --verbose` (or `--explainFiles`), which reports exactly why each file was or wasn't rebuilt.

      How would you enforce, at the CI level, that no new code in a large repo introduces an `any` or a suppressed strict-mode error, while still allowing a long tail of pre-existing suppressions to be paid down gradually?

      Run a strict-mode-enabled `tsc --noEmit` pass and diff the resulting error list (or a tracked allowlist of known-pre-existing error locations, e.g. file+line) against a checked-in baseline file; CI fails only if the current error set contains anything NOT in the baseline, and passes (even celebrates) when the current set is a strict subset of the baseline as suppressions get fixed — this pattern (often implemented via a small custom script wrapping `tsc`'s JSON-ish diagnostic output) is the standard way to ratchet strictness without requiring a single all-at-once fix.

      Practice Assignments

      Beginner (30-60 min)

      Audit a tsconfig.json

      Given a 15-option tsconfig.json you write yourself (deliberately including some questionable choices — e.g. strict: false, missing skipLibCheck, no target set), write a short review listing which options you'd change and why, as if reviewing a teammate's PR.

      • Cover at least 5 specific options.
      • Justify each recommendation with a concrete reason, not just "best practice".

      Acceptance criteria: each recommendation names the actual behavioral change the option causes.

      Hints

      Use the strict-flags table in this chapter as your checklist.

      Intermediate (2-4 hrs)

      Set up a 3-package monorepo with project references

      Create packages/shared-types, packages/api, packages/web with real composite/references wiring, where api and web both depend on shared-types, and prove incremental builds actually skip unaffected packages.

      • Running tsc --build twice with no changes must report nothing to rebuild.
      • Changing only web's source must not trigger a rebuild of api.

      Acceptance criteria: demonstrate the above with tsc --build --verbose output showing the skip behavior.

      Hints

      Each package's own tsconfig needs `composite: true` AND `declaration: true`; the root orchestrating tsconfig just lists `references`, with `files: []` so it doesn't try to compile anything itself.

      Bonus: wire up a root-level `.tsbuildinfo`-aware CI cache config (even just describing the cache key strategy in comments if you don't have real CI to test against).

      Advanced (1-2 days)

      Incremental strict-mode rollout tool

      Write a small script that runs tsc --noEmit on a codebase, parses the diagnostic output, compares it against a checked-in baseline file of known pre-existing errors (by file + rough location), and exits non-zero only if NEW errors (not in the baseline) are introduced — implementing the "ratchet" pattern described in the advanced interview questions.

      • Must correctly distinguish a genuinely new error from a pre-existing one that merely shifted line numbers slightly.
      • Must support regenerating the baseline as a separate command once errors are intentionally fixed.

      Acceptance criteria: demonstrate it passing on a seeded "has pre-existing errors" sample project, then failing when you introduce one new deliberate error, then passing again after regenerating the baseline.

      Hints

      Match on file + rule/error code + a normalized version of the error message rather than exact line number, since line numbers shift constantly as unrelated code changes — exact line matching will produce constant false positives.

      Quick Revision Cheat Sheet

      • strict: true bundles several flags — know each one individually (null checks, implicit any, function type variance, property init, bind/call/apply, implicit this).
      • noUncheckedIndexedAccess, exactOptionalPropertyTypes, noPropertyAccessFromIndexSignature are NOT in strict but are high-value additions.
      • Always set skipLibCheck: true in app code for build performance.
      • Project references (composite + references) enable real incremental, dependency-aware monorepo builds.
      • Composite projects must emit declaration files — downstream type-checks against .d.ts, not source, which is what makes incrementality possible.
      • Hand-write .d.ts only for untyped JS deps or global augmentation — never for your own TS source.
      • A .d.ts needs an import/export to be a module; declare global is the escape hatch back to global scope from within one.
      • Prefer schema-generated shared types over hand-synced packages for anything crossing a real network boundary.
      • Roll out strict mode flags incrementally with a tracked baseline/ratchet, never as a single big-bang flip on a large legacy codebase.
