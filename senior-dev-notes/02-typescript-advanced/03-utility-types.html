    Utility Types

    ⏱ ~2.5 hrs📍 Chapter 3 of 6

    One-line summary: Built-in utility types like Partial, Pick, and Record are just mapped/conditional types defined in lib.es5.d.ts — once you can read and rebuild them yourself, you can design your own for any shape-transformation problem.

    On this page

      Why It Matters for a Senior Developer

      Why

      "Implement Partial/Pick/Omit from scratch" is one of the most common TS whiteboard exercises at senior level — not because anyone needs to reimplement them, but because it proves you understand mapped types well enough to write a new one when a built-in doesn't fit. Codebases accumulate domain-specific utility types (DeepPartial, NonNullableFields, PickByValue) and someone has to be able to write and debug them.

      Builds on Type System Deep Dive and Generics In Depth. Leads into Conditional/Mapped/Template Literal Types.

      Rebuilding them from scratch

      // Partial — mapped type with the `?` modifier added to every key
type MyPartial<T> = { [K in keyof T]?: T[K] };

// Required — the `-?` syntax REMOVES the optional modifier
type MyRequired<T> = { [K in keyof T]-?: T[K] };

// Readonly — adds the readonly modifier
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };

// Pick — mapped type iterating over a constrained subset of keys
type MyPick<T, K extends keyof T> = { [P in K]: T[P] };

// Omit — defined via Pick + Exclude, not a separate mapped type in lib.d.ts
type MyOmit<T, K extends keyof any> = MyPick<T, Exclude<keyof T, K>>;

// Record — mapped type over an arbitrary key union, every value is V
type MyRecord<K extends keyof any, V> = { [P in K]: V };

// Exclude — distributive conditional type (see ch.4) filtering out matches
type MyExclude<T, U> = T extends U ? never : T;

// Extract — the inverse filter
type MyExtract<T, U> = T extends U ? T : never;

// ReturnType — infer captures the return position of a function type
type MyReturnType<F extends (...args: any[]) => any> =
  F extends (...args: any[]) => infer R ? R : never;

// Parameters — infer captures the whole parameter tuple
type MyParameters<F extends (...args: any[]) => any> =
  F extends (...args: infer P) => any ? P : never;

      Building your own domain-specific utilities

      // DeepPartial — recursive, handles nested objects (NOT arrays/functions correctly
// without extra branches — a common follow-up question is "what does this miss?")
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

// DeepReadonly — same recursive shape, readonly instead of optional
type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends object
    ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
    : T;

// PickByValue — keep only keys whose value type matches a given type
type PickByValue<T, V> = Pick<T, { [K in keyof T]: T[K] extends V ? K : never }[keyof T]>;

interface Form { name: string; age: number; email: string; active: boolean; }
type StringFields = PickByValue<Form, string>; // { name: string; email: string }

// NonNullableFields — strip null/undefined from every property's value type
type NonNullableFields<T> = { [K in keyof T]: NonNullable<T[K]> };

// RequireAtLeastOne — at least one of a set of keys must be present
type RequireAtLeastOne<T, Keys extends keyof T = keyof T> =
  Pick<T, Exclude<keyof T, Keys>> &
  { [K in Keys]-?: Required<Pick<T, K>> & Partial<Pick<T, Exclude<Keys, K>>> }[Keys];

      That last one (RequireAtLeastOne) is a genuinely advanced pattern worth memorizing the shape of, not the exact characters — it's the standard trick for "at least one of these fields is required" forms and config objects, built entirely from utilities you already know.

      How It Works Under the Hood

      A mapped type like { [K in keyof T]: X } is resolved by the checker by first resolving keyof T to a concrete union of literal key types, then iterating that union, re-evaluating the value expression X (with K substituted) for each key, and reassembling the results into a fresh object type. Modifiers (?, readonly, and their --prefixed removal forms) are applied per-property during this reassembly. Homomorphic mapped types — ones of the exact shape { [K in keyof T]: ... } over a generic T — get special-cased by the checker to preserve the "shape" of T (optional/readonly modifiers of the source carry through consistently and arrays/tuples map over elements rather than being treated as plain index signatures), which is why Partial<T> maps over tuples element-wise instead of collapsing them to an array type.

      Diagrams

      flowchart TD A["Pick<User, 'id' | 'name'>"] --> B["Resolve K in 'id' | 'name'"] B --> C["For K='id': T['id'] → number"] B --> D["For K='name': T['name'] → string"] C --> E["Reassemble: { id: number; name: string }"] D --> E

      Code Examples

      // BAD: a hand-rolled "optional update" type that silently allows removing
// required fields because it just slaps Partial over the whole thing.
interface User { id: number; name: string; email: string; }
function updateUserBad(id: number, patch: Partial<User>) { /* id itself could be overwritten */ }

// GOOD: Omit the identity field from the patchable set, keep everything else optional
type UserPatch = Partial<Omit<User, "id">>;
function updateUserGood(id: number, patch: UserPatch) { /* ... */ }

// Combining multiple utilities for a real DTO transformation:
// API response has extra internal fields; the public DTO should hide them
// and make audit fields readonly.
interface UserRecord {
  id: number; name: string; email: string;
  passwordHash: string; internalNotes: string;
  createdAt: string; updatedAt: string;
}
type UserDTO = Readonly &
  Omit<UserRecord, "passwordHash" | "internalNotes" | "createdAt" | "updatedAt">;
// UserDTO: { id; name; email } + readonly { createdAt; updatedAt } — no secrets, no accidental mutation

      Real-World Production Scenario at Scale

      At scale

      A team's internal form library used raw Partial<FormValues> for "draft" state across ~30 forms. A production bug let users save a draft that cleared a legally-required field because Partial made literally everything optional including fields that should never be removable, only left blank temporarily during editing. The fix was a custom DraftOf<T, Required extends keyof T> utility combining Partial for most fields with a forced-present (but nullable) type for the protected subset — a five-line addition to the shared types package that closed an entire class of bug across every form that adopted it, which is the kind of leverage interviewers want to hear you reason about.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Record<string, T> looks like it means "an object with any string keys", but combined with noUncheckedIndexedAccess (a strict flag worth enabling — see ch.6) every lookup becomes T | undefined, which is actually correct (a Record<string,T> doesn't guarantee a key exists) but frequently causes confused bug reports when a team enables that flag mid-project and dozens of previously "safe" lookups suddenly need narrowing.

      • Prefer composing existing utility types (Pick/Omit/Partial) over hand-writing a new mapped type when possible.
      • Name domain-specific utilities clearly (UserPatch, not PartialOmitUser) — hide the mechanism behind an intention-revealing alias.
      • DeepPartial/DeepReadonly need explicit array/tuple branches or they'll behave oddly on nested arrays — always check this in review.
      • Don't blanket-apply Partial to update/patch DTOs without excluding identity/immutable fields first.

      Interview Questions

      Basic

      What's the difference between Pick and Omit?

      Pick<T,K> keeps only the listed keys; Omit<T,K> keeps everything except the listed keys. Omit is implemented internally via Pick + Exclude over keyof T.

      Implement Partial<T> from scratch.

      type MyPartial<T> = { [K in keyof T]?: T[K] } — a mapped type adding the optional modifier to every property.

      What does Record<K, V> produce?

      An object type with every key in the union/string type K mapped to value type V — e.g. Record<"a"|"b", number> is { a: number; b: number }.

      What's the difference between Exclude and Extract?

      Exclude<T,U> removes members of union T assignable to U; Extract<T,U> keeps only members of T assignable to U — they're mirror-image conditional types.

      What does ReturnType<typeof someFn> give you, and why do you need typeof?

      It extracts the return type of the function type. typeof is needed because someFn is a value/runtime identifier — you need the type-space operator typeof to refer to its type.

      Medium

      Why does a naive DeepPartial implementation behave oddly on arrays, and how do you fix it?

      Without a dedicated array branch, the generic object branch ({ [K in keyof T]?: ... }) would map over an array's numeric-like keys and methods incorrectly, often collapsing useful array typing. The fix adds an explicit T extends (infer U)[] ? Array<DeepPartial<U>> : ... branch checked before the general object branch.

      How is Omit actually defined in TypeScript's lib.d.ts, and why not as a standalone mapped type?

      As Pick<T, Exclude<keyof T, K>> — composed from two existing simpler utilities rather than duplicating mapped-type logic, which keeps the type system's built-in vocabulary small and composable, mirroring good userland type design.

      What is a "homomorphic" mapped type and why does it matter for how Partial<T> behaves on tuples?

      A mapped type of the exact shape { [K in keyof T]: ... } over a bare generic T is special-cased by the checker to preserve T's underlying structure (array/tuple-ness, existing modifiers) rather than collapsing to a generic indexed type — this is why Partial<[string, number]> yields a tuple of optional slots rather than losing the tuple shape.

      Design a PickByValue<T, V> utility that keeps only properties whose value type is assignable to V. Explain the two mapped-type passes involved.

      First pass: a mapped type producing, for each key, either that key (if its value extends V) or `never`. Second pass: index into that mapped type with `[keyof T]`, which collects the non-never results into a union of valid keys, then feed that union into `Pick`.

      What's the practical effect of enabling noUncheckedIndexedAccess on existing code using Record<string, T> heavily?

      Every indexed lookup (`record[key]`) becomes `T | undefined` instead of `T`, forcing explicit narrowing/guards at every access site — correct behavior, since nothing guarantees the key exists, but it's a large one-time migration cost on existing codebases.

      Advanced

      Implement RequireAtLeastOne<T, Keys> and explain, mechanically, how the mapped type over a union of keys produces a union of object shapes rather than one merged shape.

      The trick is that { [K in Keys]: ... }[Keys] maps each key in `Keys` to a full variant type requiring that specific key and making the rest optional, THEN indexes the resulting mapped type by `[Keys]` again, which — because the mapped type's keys union is `Keys` — produces a union of all those per-key variant shapes rather than a single intersected object, since indexing a mapped type by its own key union distributes over each member.

      Why can't you write a fully generic, sound DeepReadonly that correctly handles functions, Maps, Sets, and class instances with private fields, and what do real-world implementations do instead?

      Functions have no meaningful "readonly" transformation; Map/Set need bespoke readonly-interface substitutions (`ReadonlyMap`/`ReadonlySet`) rather than generic object mapping; class instances with private fields can't be mapped-typed at all since private members aren't visible to `keyof`. Real implementations special-case each of these (function/Map/Set passthrough or dedicated branches) and explicitly document that arbitrary class instances are out of scope, falling back to treating them as opaque leaves.

      Explain why `keyof any` is used in `Omit`'s constraint (`K extends keyof any`) instead of `K extends keyof T`.

      `keyof any` resolves to `string | number | symbol` — the universal key type — which deliberately allows passing a key that doesn't exist on T (so you can omit a key defensively even if a future refactor removes it from T, without causing a constraint error); constraining to `keyof T` directly would make `Omit` reject omitting a key that a later type change removes, which is the opposite of what a defensive utility should do.

      How would you design a `Merge<A, B>` utility where B's properties should override A's on key collision, as a real "shallow object merge" type (not a plain intersection)?

      type Merge<A, B> = Omit<A, keyof B> & B — remove from A any key that also exists on B, then intersect with B, so B's version wins outright rather than producing an unhelpful intersection of both types at the colliding key (which plain `A & B` would do, often resulting in a `never` at that key if the types conflict).

      What breaks if you try to write a recursive mapped/conditional type utility without a depth limit or base case over a genuinely circular type (e.g. a type that references itself through an optional parent pointer)?

      TypeScript detects unbounded recursive type instantiation and throws "type instantiation is excessively deep and possibly infinite" once it exceeds an internal depth threshold, rather than looping forever — the fix is adding an explicit depth-counter type parameter that stops recursing past a fixed limit, or special-casing the circular reference to resolve to a shallow/opaque type instead of recursing through it.

      Practice Assignments

      Beginner (30-60 min)

      Reimplement 5 built-ins from scratch

      Without looking at lib.d.ts, implement MyPartial, MyRequired, MyReadonly, MyPick, MyExclude. Verify each against the real built-in using the Equal<A,B> type-level-test pattern from the topic's capstone.

      • No peeking at lib.d.ts until you've attempted each one.
      • Each must match the built-in's behavior on at least 3 test cases.

      Acceptance criteria: all type-level equality tests pass under tsc --noEmit.

      Hints

      Start with the modifier syntax (`?`, `readonly`, and their `-` removal forms) before worrying about conditional logic — most of these five are pure mapped types with no conditional branch.

      Intermediate (2-4 hrs)

      Build a DTO-shaping utility library

      Build PickByValue, OmitByValue, NonNullableFields, and RequireAtLeastOne as a small reusable module, with doc comments explaining the mechanism of each.

      • Each utility needs at least 2 realistic usage examples in comments.
      • No any in any definition.

      Acceptance criteria: apply all four to a realistic 10-field "UserRecord" type and show the resulting shapes compile as expected.

      Hints

      `OmitByValue` is `PickByValue`'s mirror — swap `extends V ? K : never` for `extends V ? never : K`.

      Bonus: add a `DeepPartial` with a correct array branch and a unit-style type test proving it handles `T[]` correctly.

      Advanced (1-2 days)

      Design a `Merge<A, B, Depth>` with configurable recursion depth

      Build a deep-merge type utility (B overrides A on conflicting keys, recursively for nested objects) that takes a numeric literal type parameter capping recursion depth to avoid "excessively deep" errors on pathological inputs, defaulting to a sane depth.

      • Must correctly deep-merge at least 3 levels of nesting by default.
      • Must not throw the "excessively deep" compiler error on a deliberately deep (6+ level) test input.

      Acceptance criteria: a test type with 6 levels of nesting compiles cleanly with the depth cap in place, and fails obviously (documented, not silently) past the cap.

      Hints

      Depth-limiting recursive types typically thread a tuple like `[...]["length"]`-based counter or a literal-number decrement type through each recursive call, stopping when it hits 0.

      Quick Revision Cheat Sheet

      • All built-in utility types are just mapped/conditional types in lib.d.ts — none are compiler magic (except the string-case intrinsics).
      • Omit = Pick<T, Exclude<keyof T, K>> — composed, not separately defined.
      • Homomorphic mapped types ({ [K in keyof T]: ... } over bare T) preserve tuple/array shape and existing modifiers.
      • -? and -readonly remove modifiers in a mapped type; plain ?/readonly add them.
      • DeepPartial/DeepReadonly need explicit array branches, or nested arrays misbehave.
      • Name domain-specific utility types for intent (UserPatch), hide the mapped-type mechanism behind the alias.
      • noUncheckedIndexedAccess makes every Record/index lookup T | undefined — correct, but a big migration if enabled late.
