    Type-Safe Patterns for React & Node

    ⏱ ~2.5 hrs📍 Chapter 5 of 6

    One-line summary: This chapter applies everything from chapters 1-4 to the two domains you actually work in daily — discriminated unions and polymorphic components in React, branded types and schema-inferred types in Node APIs — plus the patterns that keep static types and runtime validation from drifting apart.

      Why It Matters for a Senior Developer

      Why

      Interviewers testing "real" TS seniority (as opposed to type-theory trivia) ask you to design a component prop API or an Express/Fastify route handler that's impossible to misuse at compile time. This is where generics, discriminated unions, and branded types earn their keep in code you'd actually ship — and it's the chapter most directly reusable in your day job tomorrow.

      Core Concepts

      React: discriminated union props and exhaustive variant rendering

      type ButtonProps =
  | { variant: "link"; href: string; onClick?: never }
  | { variant: "action"; onClick: () => void; href?: never };

function Button(props: ButtonProps) {
  if (props.variant === "link") {
    return <a href={props.href}>Click</a>; // props.onClick not accessible — correctly absent
  }
  return <button onClick={props.onClick}>Click</button>;
}
// <Button variant="link" onClick={fn} /> is now a compile error —
// the `onClick?: never` in the link branch rejects it even though it's "optional"

      The onClick?: never trick is the standard way to make mutually exclusive prop sets actually mutually exclusive — without it, TS's structural typing would happily accept extra unrelated props from the other union branch on a fresh object literal in some circumstances.

      React: polymorphic "as" components

      type PolymorphicProps<E extends React.ElementType> = {
  as?: E;
} & Omit<React.ComponentPropsWithoutRef<E>, "as">;

function Box<E extends React.ElementType = "div">({ as, ...rest }: PolymorphicProps<E>) {
  const Component = as || "div";
  return <Component {...rest} />;
}
// <Box as="a" href="/x" />  — href is correctly typed/required because E="a"
// <Box as="button" type="submit" /> — type is correctly the button's type, not a generic string

      This is the pattern behind most design systems' as prop (Chakra, Radix-adjacent libraries). The generic default E = "div" plus ComponentPropsWithoutRef<E> is what makes the prop set change correctly based on which tag/component is passed.

      React: generic hooks with correctly inferred return tuples

      function useToggle(initial = false): [boolean, () => void] {
  const [state, setState] = React.useState(initial);
  const toggle = React.useCallback(() => setState(s => !s), []);
  return [state, toggle]; // tuple return type, NOT (boolean | (() => void))[]
}
// Without an explicit return type annotation, TS would infer the WIDER array type
// (boolean | (() => void))[] by default, losing positional typing —
// always annotate tuple-returning hooks explicitly, or use `as const` on the return.

function useToggleConst(initial = false) {
  const [state, setState] = React.useState(initial);
  const toggle = React.useCallback(() => setState(s => !s), []);
  return [state, toggle] as const; // readonly tuple inferred, positions preserved
}

      Node/APIs: branded (nominal) types for IDs

      type Brand<T, B extends string> = T & { readonly __brand: B };
type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

function toUserId(raw: string): UserId { return raw as UserId; } // the ONE allowed cast
function toOrderId(raw: string): OrderId { return raw as OrderId; }

function getUser(id: UserId) { /* ... */ }

const uid = toUserId("u_123");
const oid = toOrderId("o_456");
getUser(uid);  // OK
// getUser(oid);  // Error — OrderId is not assignable to UserId, despite both being `string` at runtime
// getUser("u_123");  // Error — a raw string isn't a UserId either; must go through toUserId()

      Branded types cost nothing at runtime (the __brand property never actually exists on the object — it's purely a compile-time marker via intersection) but prevent an entire bug class: passing the wrong ID type to a function, which structurally-typed string params can never catch on their own.

      Node/APIs: schema-driven type inference (no drift between runtime and static types)

      // A minimal hand-rolled schema + inferred-type pattern (the same shape Zod/Valibot use)
type Schema<T> = { parse(input: unknown): T; readonly _type?: T };
type Infer<S> = S extends Schema<infer T> ? T : never;

function string(): Schema<string> {
  return { parse(input) { if (typeof input !== "string") throw new Error("expected string"); return input; } };
}
function object<Shape extends Record<string, Schema<any>>>(shape: Shape): Schema<{ [K in keyof Shape]: Infer<Shape[K]> }> {
  return {
    parse(input) {
      if (typeof input !== "object" || input === null) throw new Error("expected object");
      const result: any = {};
      for (const key in shape) result[key] = shape[key].parse((input as any)[key]);
      return result;
    }
  };
}

const UserSchema = object({ id: string(), name: string() });
type User = Infer<typeof UserSchema>; // { id: string; name: string } — derived, never hand-written

function handler(body: unknown) {
  const user = UserSchema.parse(body); // runtime-validated AND statically typed as User
  return user.name; // fully typed, and guaranteed to have actually been validated
}

      This is the exact mechanism libraries like Zod use: the static type is derived from the runtime validator definition via infer, so the two can never drift — there's only one source of truth. This is the core idea the capstone project's validation layer is built around.

      How It Works Under the Hood

      The branded type trick works because TS structural typing checks assignability by shape — intersecting with a property typed as a specific string literal ({ __brand: "UserId" }) makes that shape structurally incompatible with any type lacking a matching literal-typed __brand, even though the property is erased entirely at compile time (it's never actually assigned, only asserted via as). Schema-driven inference works because infer operating over a generic Schema<T> interface lets the checker read back whichever concrete T was threaded through at schema-construction time — the "phantom" _type?: T field (never actually populated at runtime) exists purely so T has somewhere to be recorded for infer to extract later; without it, T would never appear anywhere in the schema object's actual type and couldn't be recovered.

      Diagrams

      flowchart LR A["object({ id: string(), name: string() })"] --> B["Infer each field's Schema<T> via mapped type"] B --> C["{ id: Infer<Schema<string>>; name: Infer<Schema<string>> }"] C --> D["Resolves to { id: string; name: string }"] D --> E["type User = Infer<typeof UserSchema>"] E --> F["Static type always matches runtime validator — zero drift"]

      Code Examples

      // BAD: Express handler typed loosely, params/body are `any`, nothing stops a typo
app.post("/users/:id", (req, res) => {
  const id = req.params.id;          // any
  const name = req.body.name;         // any, could be anything at runtime
  res.json({ id, nmae: name });        // typo ships silently
});

// GOOD: typed request helper + schema validation, typo becomes a compile error
interface TypedRequest<Params = {}, Body = unknown> {
  params: Params;
  body: Body;
}
function postUser(req: TypedRequest<{ id: string }, { name: string }>, res: Response) {
  const { id } = req.params;  // string, typed
  const { name } = UserBodySchema.parse(req.body); // runtime-checked AND typed
  res.json({ id, name }); // typo here is now a compile error against the response DTO type
}

// Generic, reusable typed-route wrapper combining both ideas
function route<P, B>(
  schema: Schema<B>,
  handler: (req: TypedRequest<P, B>, res: Response) => void
) {
  return (req: Request, res: Response) => {
    const body = schema.parse(req.body); // throws (caught by error middleware) if invalid
    handler({ params: req.params as P, body }, res);
  };
}

      Real-World Production Scenario at Scale

      At scale

      A fintech API had a recurring class of incidents where a customerId was accidentally passed where a merchantId was expected — both were plain string, so TS never caught it, and three separate production incidents over a year traced back to exactly this swap in different services. Introducing branded types for every domain ID (CustomerId, MerchantId, TransactionId, ~12 total) across the shared types package, with a single conversion function per ID type at the data-access boundary, converted this entire bug class into compile errors. The migration took about a week across 40 services (mostly mechanical: add brand, fix resulting compile errors) and the team reported zero ID-confusion incidents in the following year — a strong, quantifiable story for "why would you add this complexity."

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Branded types are a compile-time-only guarantee — if a branded UserId gets serialized to JSON (e.g. in an API response) and deserialized on another service's boundary without going back through the brand's conversion function, nothing at runtime stops a caller from constructing a fake branded value via as. Brands prevent accidental misuse within type-checked code; they are not a security boundary and don't replace runtime validation at trust boundaries.

      • Use discriminated union props with ?: never on the excluded branch's fields for truly mutually-exclusive component APIs.
      • Annotate tuple-returning custom hooks explicitly, or use as const, or inference will widen to an array type.
      • Derive static types from runtime validators (Infer<typeof schema>), never hand-maintain both separately.
      • Brand IDs and other primitive-but-semantically-distinct values at the data layer boundary, convert once, pass branded values everywhere internally.
      • Keep the polymorphic as component pattern's generic default sensible (usually the most common tag) so simple usage doesn't require annotation.

      Tradeoffs

      Interview Questions

      Basic

      What problem do branded types solve that plain type aliases (type UserId = string) don't?

      A plain alias is still structurally just string — any string is assignable to it, so mixing up two ID types compiles fine. A branded type adds a compile-time-only marker that makes two otherwise-identical primitive types structurally incompatible with each other.

      Why does a custom hook returning [value, setter] sometimes get typed as an array instead of a tuple?

      Without an explicit tuple return type annotation or `as const`, TS infers array literal returns by taking the union of element types and producing a plain array type, losing positional/tuple information.

      How do you make two component prop variants truly mutually exclusive in a discriminated union?

      Add the other variant's unique props typed as `?: never` in each branch, so structurally providing a prop that belongs to the other branch becomes a type error instead of being silently accepted.

      What is schema-derived typing and name one library that uses this pattern?

      Deriving the static TypeScript type directly from a runtime validator definition via `infer`/a generic `Infer<typeof schema>` helper, so the static and runtime types can never drift apart. Zod is the most common example.

      Medium

      Walk through how the polymorphic as prop pattern correctly types `href` only when `as="a"` and `type` only when `as="button"`.

      The component is generic over `E extends React.ElementType`, and its props type is `{ as?: E } & Omit<ComponentPropsWithoutRef<E>, "as">`. Because `E` is inferred from the actual `as` value passed at the call site, `ComponentPropsWithoutRef<E>` resolves to that specific element/component's real prop type, so `href` only appears when E resolves to `"a"` and `type` only when E resolves to `"button"`.

      Why are branded types "free" at runtime, and what's the one place a cast to the branded type is acceptable?

      The `__brand` property is never actually assigned to any object — intersecting with `{ __brand: "X" }` only exists in the type system, erased completely on compile. The one acceptable cast is inside the dedicated conversion/constructor function (e.g. `toUserId`) at the trust boundary where the raw value has just been validated as genuinely a valid UserId; everywhere else should receive already-branded values.

      What happens if a Zod-style schema's inferred type and its actual parse() implementation diverge (e.g. the parse function forgets to validate a field declared in the shape)?

      The static type is trusted by the type checker regardless of what the runtime implementation actually does — if `parse()` has a bug and returns an object missing a declared field, TypeScript still believes the full inferred type is correct, since type inference only reads the *declared* schema shape, not the implementation's actual runtime behavior. This is why schema libraries need their own test suites validating `parse()` against the schema definition.

      Design a generic `TypedRequest<Params, Body, Query>` helper for Express/Fastify-style handlers and explain why `req.params`/`req.body` are typed `any` by default in these frameworks.

      Express types route params/body generically but defaults the generics to `any`/`ParamsDictionary` because the framework has no way to know your route's actual shape at the type level — it's runtime string-matched routing. A `TypedRequest<Params, Body, Query>` interface overrides those fields with your own generics, threaded through a typed `route()` wrapper function (as shown in the code examples) that both validates and casts.

      Advanced

      Design a fully type-safe `useReducer`-based state machine where dispatching an action with an invalid payload for the current state is a compile error, not just a runtime no-op.

      Model state and actions as parallel discriminated unions keyed by the same tag values. Instead of a single flat reducer type, type the reducer as a mapped type over each state's tag, where each entry's handler only accepts the subset of actions valid for that state (expressed via a lookup type like `ValidActions<StateTag>`). Enforcing this generally requires the dispatch function itself to be generic over the current state's tag (inferred from the current state value at the call site), with the action parameter's type conditionally narrowed based on that inferred tag, rather than a single flat `Action` union accepted unconditionally.

      Explain the actual runtime risk of branded types when a branded value crosses a serialization boundary (e.g. JSON over HTTP between two TypeScript services), and how you'd mitigate it.

      JSON serialization has no concept of TypeScript's type-level brand — a `UserId` becomes a plain string over the wire, and the receiving service's deserialization code typically re-brands it via the same unchecked `as` cast used at construction, meaning a malformed or wrong-domain string could be smuggled through as if freshly validated. Mitigate by pairing brands with actual runtime validation at every trust boundary (e.g. a schema's `parse()` that checks format, not just casts) rather than relying on the brand alone to imply validity.

      How would you type a generic `createSlice`-style Redux Toolkit-like API where action creators' payload types are inferred per-reducer-case, and reducers can "mutate" an Immer-drafted state?

      Each reducer case function's second parameter type (the action) is derived via a mapped type over the `reducers` object passed in, extracting each function's second parameter type (commonly via a `Parameters<F>[1]` pattern) to build a per-case action type; the returned `actions` object is itself a mapped type converting each reducer key into an action-creator function whose parameter matches that extracted payload type. Modeling "mutation" over an Immer draft requires typing the state parameter as `Draft<State>` (Immer's own branded/structural draft type) rather than plain `State`, so property mutation type-checks even though the actual reducer may return nothing (relying on in-place draft mutation).

      What's the fundamental limitation of schema-derived static types when the runtime validator includes logic TypeScript's type system can't express (e.g. "field B is required only if field A equals 'x'")?

      TypeScript's static type system can express conditional requiredness across fields using discriminated unions (modeling each valid combination as a separate union member), but a schema library's `infer` typically only reads the declared shape, not arbitrary custom refinement logic (e.g. a `.refine()` callback) — so cross-field conditional validation needs to be modeled as an explicit discriminated union in the schema's own type (if the library supports union schemas) for the static type to actually reflect the constraint, rather than relying on a generic refinement to "just work" at the type level.

      Design the type signature for a generic `withQuery` Next.js/React hook-like data-fetching wrapper that infers both the response type AND a typed error union from a single typed fetcher function, usable across dozens of different API calls.

      Type the fetcher as `() => Promise<Result<T, E>>` (a discriminated success/error union, as in chapter 1), and make the hook generic over the fetcher function itself: `function useQuery<F extends () => Promise<Result<any, any>>>(fetcher: F)`, then extract `T`/`E` via nested `infer` over the `Awaited<ReturnType<F>>` shape. This lets every call site's specific fetcher drive both the returned data's type and the specific error union, without the hook itself needing explicit type arguments at any call site.

      Practice Assignments

      Beginner (30-60 min)

      Mutually exclusive component props

      Build a Alert component with two variants: { variant: "dismissible"; onDismiss: () => void } and { variant: "persistent" }, using the ?: never trick so passing onDismiss on a persistent alert is a compile error.

      • Must use a discriminated union, not optional-everything props.
      • Verify the invalid combination actually fails via // @ts-expect-error.

      Acceptance criteria: both valid variants render correctly; the invalid combination is caught at compile time.

      Hints

      Add `onDismiss?: never` to the persistent branch, not just omitting the field — omitting alone doesn't block excess props on non-literal-assigned values in every case.

      Intermediate (2-4 hrs)

      Branded IDs across a mini Node service

      Build a tiny in-memory "users" and "orders" service with branded UserId/OrderId types, conversion functions, and at least 3 functions per entity that would be easy to misuse with raw strings (e.g. getOrdersForUser(userId), refundOrder(orderId)).

      • No function should accept a raw, unbranded string for an ID parameter.
      • Include at least 2 `// @ts-expect-error` tests proving ID confusion is caught.

      Acceptance criteria: swapping a UserId and OrderId at any call site fails to compile.

      Hints

      Keep the `Brand<T, B>` generic utility in a shared file and reuse it for every branded type, rather than redefining the branding mechanism per type.

      Bonus: add a lightweight runtime format check inside each conversion function (e.g. `UserId`s must start with `u_`).

      Advanced (1-2 days)

      Hand-rolled schema library with full type inference

      Extend the chapter's minimal Schema<T>/Infer<S> pattern into a small library supporting string(), number(), boolean(), object(), array(), and .optional(), with correct nested type inference throughout.

      • array(string()) must infer string[].
      • .optional() wrapping any schema must correctly make that field optional AND | undefined in the inferred type.
      • Nested object({ a: object({ b: string() }) }) must infer the correctly nested shape.

      Acceptance criteria: a battery of Equal-based type tests covering at least 8 schema combinations, plus runtime tests proving parse() actually validates.

      Hints

      `.optional()` is naturally implemented as a function that takes a `Schema<T>` and returns a `Schema<T | undefined>` wrapping the original's parse with an undefined-check short-circuit — no new generic machinery needed beyond what you already have.

      Quick Revision Cheat Sheet

      • Discriminated union props + ?: never on excluded branches = truly mutually exclusive component APIs.
      • Annotate tuple-returning hooks explicitly (or as const) or inference widens to a plain array.
      • Polymorphic as components: generic over E extends ElementType, props = { as?: E } & Omit<ComponentPropsWithoutRef<E>, "as">.
      • Branded types = T & { readonly __brand: "X" }, zero runtime cost, prevents primitive-type confusion.
      • Brands are compile-time only — they are not a substitute for runtime validation at trust boundaries.
      • Derive static types from runtime validators via infer (Infer<typeof schema>) to eliminate drift.
      • A "phantom" unused type field (_type?: T) on a schema interface exists purely so infer has somewhere to read T from.
