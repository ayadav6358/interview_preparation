    Conditional, Mapped & Template Literal Types

    ⏱ ~3 hrs📍 Chapter 4 of 6

    One-line summary: This is the "type-level programming" toolkit — distributive conditional types, infer, recursive mapped types, and template literal type parsing let you compute new types from existing ones, which is the engine behind almost every advanced utility type and the whole capstone project.

    On this page

      Why It Matters for a Senior Developer

      Why

      This is the chapter interviewers use to separate "comfortable with TS" from "can design a type-safe library." Distributive conditional types explain real bugs you'll hit in production (why Exclude<T, never> behaves differently than expected on certain unions); template literal types are exactly what makes typed routers, typed SQL-ish query builders, and typed CSS-in-JS APIs possible. If you can't explain why a distributive conditional type distributes, you'll struggle the moment an interview question goes one level deeper than a memorized utility type.

      Builds directly on Type System Deep Dive, Generics In Depth, and Utility Types.

      Core Concepts

      Conditional types: the basics

      type IsString<T> = T extends string ? true : false;
type A = IsString<"hi">;   // true
type B = IsString<42>;      // false

// Conditional types can nest to build a chain of checks
type TypeName<T> =
  T extends string ? "string" :
  T extends number ? "number" :
  T extends boolean ? "boolean" :
  T extends undefined ? "undefined" :
  T extends Function ? "function" :
  "object";

      Distributive conditional types — the single trickiest mechanic in TS

      When the checked type of a conditional type is a bare, unqualified type parameter, and you pass a union as that type parameter, TS doesn't evaluate the conditional once against the whole union — it distributes: it evaluates the conditional separately for each member of the union, then unions the results back together.

      type ToArray<T> = T extends any ? T[] : never;
type X = ToArray<string | number>;
// NOT (string | number)[] — distributes to: string[] | number[]

// This is EXACTLY how Exclude works:
type MyExclude<T, U> = T extends U ? never : T;
type Y = MyExclude<"a" | "b" | "c", "a">;
// distributes: ("a" extends "a" ? never : "a") | ("b" extends "a" ? never : "b") | ("c" extends "a" ? never : "c")
// = never | "b" | "c" = "b" | "c"

// Wrapping the checked type in a tuple SUPPRESSES distribution —
// this is the standard trick when you want ONE evaluation against the whole union:
type ToArrayNonDist<T> = [T] extends [any] ? T[] : never;
type Z = ToArrayNonDist<string | number>;
// (string | number)[] — evaluated once, not distributed

      The rule precisely: distribution only happens when the checked type position is a naked type parameter (just T, nothing wrapping it). T extends U ? X : Y distributes over a union passed as T; [T] extends [U] ? X : Y does not, because now the checked type is a tuple containing T, not T itself. This single fact explains a huge fraction of "why doesn't my conditional type do what I expected" bugs.

      The infer keyword

      infer introduces a new type variable inside the extends clause of a conditional type, letting you "capture" a piece of the matched structure instead of just testing it.

      type ElementType<T> = T extends (infer U)[] ? U : T;
type E1 = ElementType<string[]>; // string

type FirstArg<F> = F extends (first: infer A, ...rest: any[]) => any ? A : never;
type F1 = FirstArg<(a: string, b: number) => void>; // string

// infer with a constraint (TS 4.7+) — restricts what the inferred type can be
type ArrayElementStringOnly<T> = T extends (infer U extends string)[] ? U : never;

// Recursive infer — unwrap arbitrarily nested promises/arrays
type DeepAwaited<T> = T extends Promise<infer U> ? DeepAwaited<U> : T;
type D1 = DeepAwaited<Promise<Promise<Promise<string>>>>; // string

      When a conditional type has multiple matching candidates for the same inferred variable in covariant positions (e.g. multiple array branches), TS infers a union; in contravariant positions (multiple function parameter branches), it infers an intersection instead — same variance rule from chapter 2, now applied inside infer.

      Mapped types: key remapping with as (TS 4.1+)

      Beyond adding/removing modifiers, mapped types can rename keys entirely using an as clause, almost always combined with template literal types:

      type Getters<T> = {
  [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K]
};
interface Person { name: string; age: number; }
type PersonGetters = Getters<Person>;
// { getName: () => string; getAge: () => number }

// Filtering keys out entirely by mapping them to `never` in the `as` clause
type OmitByValue<T, V> = {
  [K in keyof T as T[K] extends V ? never : K]: T[K]
};

      Template literal types: parsing strings at the type level

      Template literal types aren't just string concatenation — combined with infer in a conditional type, they let you pattern-match and destructure string literal types, which is exactly how typed routers extract path params.

      // Extract a single :param segment
type ExtractParam<S extends string> =
  S extends `${string}:${infer Param}/${string}` ? Param :
  S extends `${string}:${infer Param}` ? Param :
  never;

// Extract ALL :param segments from a full route into a union
type ExtractParams<S extends string> =
  S extends `${infer _Start}:${infer Param}/${infer Rest}`
    ? Param | ExtractParams<`/${Rest}`>
    : S extends `${infer _Start}:${infer Param}`
      ? Param
      : never;

type Params1 = ExtractParams<"/users/:userId/posts/:postId">; // "userId" | "postId"

// Turn that union of param names into an actual typed object
type RouteParams<S extends string> = { [K in ExtractParams<S>]: string };
type P1 = RouteParams<"/users/:userId/posts/:postId">;
// { userId: string; postId: string }

      This exact pattern — parse a route string into a param union via recursive template literal matching, then map that union into an object type — is the backbone of this topic's capstone project and of real typed routing libraries.

      How It Works Under the Hood

      Template literal types are compiled down to a pattern the checker can match against actual string literal types, essentially treating `${infer A}:${infer B}` like a regex with capture groups over the literal's characters — matching is attempted structurally against known literal unions (e.g. when matched against string itself with no literal information, inference falls back to string for each captured group, which is why this machinery requires literal types to be useful). Distributive conditional type resolution is implemented by the checker literally iterating the union's constituents when it detects the checked type position is a bare, unsubstituted type parameter at the time of evaluation — "bare" is checked structurally on the conditional type's syntax, not on the runtime union value, which is exactly why wrapping in a tuple ([T]) defeats it: the syntactic position checked is no longer a bare type parameter.

      Code Examples

      // BAD: non-distributive conditional used where distribution was actually wanted,
// silently producing a much wider/less useful type than intended.
type Flatten<T> = [T] extends [Array<infer U>] ? U : T;
type Bad = Flatten<string[] | number[]>;
// [T] suppresses distribution, so T is the WHOLE union (string[] | number[]) at once,
// which doesn't match `Array` as a single literal pattern the way you'd hope;
// here it actually still partially works by luck of structural matching, but the
// INTENT (flatten each member separately) is obscured and breaks on mixed shapes.

// GOOD: bare type parameter distributes correctly per-union-member
type FlattenGood<T> = T extends Array<infer U> ? U : T;
type Good = FlattenGood<string[] | number[]>;
// string | number — each member flattened independently, then unioned. Correct.

// Type-level test utilities — the Equal/Expect pattern used throughout this topic
type Equal<A, B> =
  (<T>() => T extends A ? 1 : 2) extends (<T>() => T extends B ? 1 : 2) ? true : false;
type Expect<T extends true> = T;

type test1 = Expect<Equal<FlattenGood<string[] | number[]>, string | number>>; // compiles
// type test2 = Expect<Equal<FlattenGood<string[] | number[]>, (string | number)[]>>; // would fail

      That Equal type (comparing two generic function types rather than a naive A extends B ? B extends A ? true : false : false) is intentionally written this way because the naive version has known false positives around any and certain union edge cases — the "generic function comparison" trick is the community-standard, battle-tested version and is worth memorizing as-is.

      Real-World Production Scenario at Scale

      At scale

      A design-system team built a typed CSS-in-JS helper where sx({ color: "red", "&:hover": {...} }) needed to validate pseudo-selector keys and nested property names at compile time across ~200 components. The first version used a plain Record<string, unknown> for nested selectors, so any typo in a pseudo-selector silently did nothing at runtime (a classic, hard-to-notice CSS bug). Rewriting the nested key type as a template literal union of known selector patterns (` &:${PseudoState}` | `&> ${string}`) turned every typo'd selector into an immediate compile error across all 200 call sites, with zero runtime cost — a good concrete story for "when did a type-level trick actually prevent a real bug class."

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Recursive conditional types over unbounded string/array inputs can blow past the compiler's recursion depth limit ("Type instantiation is excessively deep and possibly infinite"), especially on route strings with many params or deeply nested template literal parsing. Production typed-router libraries almost always cap recursion depth or restructure the recursive branch to be tail-position (TS 4.5+ has better tail-recursion elimination for conditional types, which materially raised the practical depth limit, but it's not unlimited).

      • Remember: distribution only happens on a bare type parameter in the checked position — wrap in [T] to opt out.
      • Use the generic-function-comparison Equal pattern for type-level tests, not naive mutual-extends checks.
      • infer unions results from covariant positions, intersects from contravariant ones — know which you're in.
      • Template literal pattern matching needs literal types to be useful; matching against plain string degrades to string.
      • Cap recursion depth explicitly in recursive type utilities meant for arbitrary user input (route strings, deep objects).

      Interview Questions

      Basic

      What does infer do inside a conditional type?

      It declares a new type variable that captures a piece of the type being matched against, so you can use that captured piece in the "true" branch — e.g. capturing an array's element type or a promise's resolved type.

      What is a distributive conditional type, in one sentence?

      A conditional type whose checked type is a bare type parameter, which — when given a union — is evaluated separately per union member and the results are unioned back together, rather than evaluated once against the whole union.

      How do you extract the element type of an array type T?

      type ElementType<T> = T extends (infer U)[] ? U : never;

      What's the syntax for renaming keys in a mapped type?

      The as clause: { [K in keyof T as NewKeyExpression]: T[K] }, introduced in TS 4.1, usually combined with a template literal type to compute the new key name.

      Write a template literal type that extracts the file extension from a filename literal type.

      type Ext<S extends string> = S extends `${string}.${infer E}` ? E : never;

      Medium

      Explain exactly why Exclude<"a"|"b"|"c", "a"> works correctly but a naive "wrap it in a tuple" version wouldn't.

      `Exclude` is defined as `T extends U ? never : T` with T as a bare type parameter, so passing the union distributes the check across "a", "b", "c" individually and unions the non-excluded results. Wrapping as `[T] extends [U] ? never : T` would evaluate the whole union against U in one shot, which — since the whole union isn't assignable to "a" — would just return the entire original union unfiltered.

      How does TypeScript decide whether an inferred type from multiple `infer` matches in different branches becomes a union or an intersection?

      It follows the same covariance/contravariance rule as generic inference generally: candidates found in covariant (output/return-like) positions are combined via union; candidates found in contravariant (function parameter) positions are combined via intersection, because a value needing to satisfy "could be called with any of these parameter types" requires the intersection of them.

      Why does matching a template literal type against a non-literal `string` degrade to `string` for the inferred capture groups?

      Without concrete literal character data, the checker has no information to narrow the captured substring beyond "some string," so each `infer` group in the pattern falls back to the widest type consistent with that position, which is `string` itself.

      Design a recursive template literal type that converts `"hello_world_foo"` into `"helloWorldFoo"` (snake_case to camelCase) at the type level.

      Recursively match on the underscore: `type CamelCase<S> = S extends \`${infer Head}_${infer Tail}\` ? \`${Head}${Capitalize<CamelCase<Tail>>}\` : S;` — each recursive step strips one underscore and capitalizes everything after it, recursing until no underscore remains.

      What's the practical difference between checking equality of two types with `A extends B ? B extends A ? true : false : false` versus the generic-function-comparison `Equal` pattern?

      The naive mutual-extends check has known false positives, notably both directions being (vacuously) true when either type is `any`, and subtle mismatches around certain union/optional-property edge cases. The generic-function trick compares how a fresh, unconstrained type parameter would resolve against each type inside a conditional, which is sensitive to structural differences the naive check misses, making it the more reliable community-standard test.

      Advanced

      Walk through, mechanically, how `ExtractParams` on `"/users/:userId/posts/:postId"` resolves to `"userId" | "postId"`, including each recursive step's intermediate types.

      Step 1: the first branch matches with `_Start="/users/"`, `Param="userId"`, `Rest="posts/:postId"`, emitting `"userId" | ExtractParams<"/posts/:postId">`. Step 2: recursing on `"/posts/:postId"`, the first branch (requiring a trailing `/`) fails to match since there's no second `:param` after it, so it falls to the single-param branch, matching `_Start="/posts/"`, `Param="postId"`, emitting `"postId"`. The final union assembled bottom-up is `"userId" | "postId"`.

      Why does TS 4.5's tail-recursion optimization for conditional types matter for recursive utility types, and what shape must a conditional type have to benefit from it?

      Before TS 4.5, every recursive step in a conditional type added to a fixed internal recursion depth counter regardless of structure, hitting the "excessively deep" error relatively quickly on real inputs (e.g. long route strings or deep JSON). TS 4.5 recognizes when a conditional type's recursive reference is in "tail position" (the recursive call's result is returned directly, not wrapped in further type-level computation) and defers/iterates these differently, substantially raising the practical recursion ceiling for that specific shape — mis-structuring the recursive call (e.g. wrapping it, like `Param | Recurse<Rest>` instead of pure tail position) can lose this optimization.

      Design a type-safe SQL-like query builder where `.select("id", "name")` on a typed table narrows the eventual row type to just those columns, using template literal types to also validate dotted `table.column` references.

      Model the table as a plain object type for columns; `.select` takes a generic tuple of keys constrained to `keyof Table` and returns a builder re-typed with `Pick<Table, Tup[number]>` as its row type. For dotted references, use a template literal type like `` `${TableName}.${keyof Table & string}` `` as the allowed key shape, and a conditional/infer pattern to strip the table prefix back off when resolving the actual column before indexing into the row type.

      Explain a scenario where a distributive conditional type over a union containing `never` produces a surprising result, and why.

      Distributing over a union that includes `never` effectively removes `never` from the distributed result, because TypeScript's union normalization drops `never` members (union with `never` is itself) — so `Exclude<T, never>`-style patterns, or any distributive conditional applied to `T | never`, silently behave as if `never` was never part of the union at all, which can hide a bug where `never` was meant to represent "no match found" and be meaningfully present in a downstream check.

      How would you write a depth-limited recursive `DeepReadonly` that stops recursing after N levels, using a literal-number type parameter, and why can't you just use runtime-style decrementing (`N - 1`) directly?

      TypeScript's type system has no native arithmetic on number literal types; "decrementing" is simulated by indexing into a fixed tuple of literal numbers (a precomputed "digit" tuple) by length, e.g. using a `Prev` lookup type mapping each literal 0-20 to the previous one via a tuple's `length` property, then threading that `Prev<N>` through each recursive call and stopping when it hits 0 — true arbitrary arithmetic isn't supported, so these tricks only work up to a bounded range before hitting the same depth/instantiation limits.

      Practice Assignments

      Beginner (30-60 min)

      Distributive vs non-distributive conditional types

      Write both a distributive and a non-distributive version of a type that converts a type to its array form, apply both to a union of 3 types, and write a comment explaining the different results.

      • Must use the [T] extends [U] trick for the non-distributive version.
      • Include an Equal-based type test proving the two produce different results on a union.

      Acceptance criteria: the type test compiles and demonstrably shows the two are NOT equal for a 3-member union.

      Hints

      Start from the chapter's ToArray/ToArrayNonDist examples and adapt them.

      Intermediate (2-4 hrs)

      Typed route param extractor

      Build ExtractParams<S> and RouteParams<S> fully from scratch (don't copy the chapter's version verbatim — write your own recursive pattern), then build a small navigate(route: S, params: RouteParams<S>) function that's fully type-checked.

      • Must correctly handle routes with 0, 1, and 3+ params.
      • Must handle a route with no trailing segment after the last param.

      Acceptance criteria: calling navigate with a missing or extra param key is a compile error for at least 3 different route shapes.

      Hints

      Write the single-param base case first, get it working, then add the recursive multi-param case on top — don't try to write both branches at once.

      Bonus: support optional params with a `?` suffix syntax, e.g. `:id?`.

      Advanced (1-2 days)

      Type-level JSON path getter

      Build a Get<T, Path extends string> type that, given a dotted path string like "user.address.city", resolves to the actual nested value type on T (or never if the path is invalid), plus a runtime get(obj, path) function whose return type matches.

      • Must support at least 4 levels of nesting.
      • Must fail to compile (via the return type resolving to `never`, or an overload rejecting it) for a path that doesn't exist on T.

      Acceptance criteria: a battery of Equal-based type tests covering valid paths, invalid paths, and array-indexed segments if you attempt the bonus.

      Hints

      Split the path on `.` using a recursive template literal conditional, then recursively index into T using each segment, combining `infer` for the split with a standard indexed-access type for the lookup.

      Quick Revision Cheat Sheet

      • Distribution happens only when the checked type is a bare type parameter — [T] extends [U] opts out.
      • infer captures a piece of a matched type; multiple candidates union in covariant positions, intersect in contravariant ones.
      • Mapped type as clause (TS 4.1+) lets you rename/filter keys, often with template literals.
      • Template literal types pattern-match literal strings; matching against plain string degrades captures to string.
      • Use the generic-function-comparison Equal pattern for type-level tests, not naive mutual-extends.
      • Recursive conditional/template literal types can hit "excessively deep" — cap recursion depth for unbounded input.
      • TS 4.5+ tail-recursion optimization raises the practical depth limit for correctly tail-positioned recursive conditional types.
      • Exclude<T, never>-style distribution silently drops never from a union — union normalization removes it.
