    TypeScript Advanced

    📚 6 chapters⏱ ~15–17 hrs total

    TypeScript questions in senior/staff interviews rarely stop at "what's the difference between interface and type". You'll be asked to reason about how inference actually resolves, why a conditional type didn't distribute the way you expected, how to design a generic API that infers correctly at every call site, and how to keep a large monorepo's type-checking fast and sound. This topic goes under the hood of the compiler's type system and builds the pattern library you need to design type-safe libraries, not just consume them.

    Learning Outcomes

    • Explain how TypeScript's structural type system, control-flow narrowing, and inference algorithm actually work — not just "it just knows".
    • Design generic functions and types whose inference "falls out" naturally at call sites, without annotation gymnastics.
    • Read, build, and debug mapped, conditional, and template literal types, including distributive conditional types and recursive type-level computation.
    • Apply branded/nominal types, discriminated unions, and type-safe builder/factory patterns in real React and Node codebases.
    • Configure tsconfig.json strict mode flags with intent, author clean .d.ts output, and keep a multi-package monorepo's type-checking fast and correct with project references.
    • Defend design tradeoffs (type complexity vs readability, compile-time guarantees vs runtime cost) under interviewer pushback.

    🏆 Capstone Project: Build a Fully Type-Safe REST Client + Validation Layer

    Problem statement: Build a TypeScript library that lets a consumer define a small REST API's shape once (routes, params, request bodies, response bodies) and get a fully type-safe client where every call site's argument types and return type are inferred from that one definition — no manual generic annotations at call sites, no any, no response shape drift between client and server.

    Required features:

    • A route definition map (e.g. { "GET /users/:id": { params: {...}, response: User } }) typed with template literal types to extract path params automatically from the route string.
    • Generic request()/client.get()/client.post() functions whose parameter and return types are inferred from the route key passed in — using conditional and mapped types, not overload spam.
    • A runtime validation layer (hand-rolled or a thin wrapper) whose validator type and inferred static type are provably the same type (no "trust me" as casts) — i.e. Infer<typeof UserSchema> style.
    • Branded types for IDs (UserId, OrderId) so swapping them at a call site is a compile error, with zero runtime cost.
    • A mini type-level test suite using conditional types (an Expect<Equal<A, B>> pattern) that fails the build if an inferred type regresses — no test runner needed, just tsc --noEmit.
    • At least one deliberately tricky case handled correctly: optional vs required params inferred from the route string, and a distributive conditional type used to map a union of route keys to a union of response types.

    Tech stack suggestion: Plain TypeScript 5.x, no framework required for the client; optionally wire it to a small Express/Fastify mock server for an end-to-end demo. Vitest or tsc --noEmit for the type-level tests.

    Milestones:

    1. Design the route definition shape and write the template literal type that extracts :id-style params into a typed object.
    2. Build the generic request() core and prove inference works end-to-end for one GET and one POST route.
    3. Add the runtime validator + Infer<T> type-level extraction so static and runtime types can never drift silently.
    4. Add branded ID types and thread them through the route map.
    5. Write the type-level test suite (Equal/Expect utilities) covering at least 8 inference scenarios, including one that currently fails until you fix the type.
    6. Write a short README explaining the 3 hardest type-level tricks you used and why each exists.

    Evaluation checklist:

    • ☐ No any or unchecked as casts anywhere in the public API surface.
    • ☐ Changing a route's response shape in the definition map produces a compile error everywhere it's consumed incorrectly.
    • ☐ Can explain, from memory, why the conditional type you used for param extraction distributes the way it does.
    • ☐ Branded types prevent passing a UserId where an OrderId is expected, with a one-line proof.
    • ☐ Can defend at least one place you chose not to push the type system further, and why (readability/compile-time cost).
