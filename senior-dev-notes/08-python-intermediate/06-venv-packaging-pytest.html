    Virtual Envs, Packaging, Testing with pytest

    ⏱ ~3 hrs📍 Chapter 6 of 6

    One-line summary: Python's dependency story (venv + pip/pyproject.toml) solves the same "isolated, reproducible dependencies" problem node_modules+package.json solves, with one crucial difference you must internalize — isolation is per-interpreter-environment, not automatic per-project — and pytest gives you Jest-equivalent fixtures, parametrization, and mocking with a philosophy of plain functions over class-based test suites.

    On this page

      Why It Matters for a Senior Developer

      Every Python interview that goes past "write a function" eventually touches tooling: how you'd set up a reproducible dev environment, how you'd structure a test suite for a FastAPI service, how you'd mock an async dependency. These are exactly the questions that separate "wrote some Python scripts" from "can own a Python service in production" — and they map cleanly onto things you already know cold from Node, so the leverage here is high relative to the effort.

      Why

      Unlike npm, where node_modules is scoped to the project directory automatically, Python's default pip install targets whatever interpreter is currently active globally unless you've explicitly activated a virtual environment first. Forgetting this is the single most common "works on my machine" bug new Python developers (including experienced engineers new to Python) introduce, and it's a very fair interview probe for whether you actually understand the tooling or just copy-pasted commands that happened to work.

      Prerequisites

      Builds on Python for JS Developers (interpreter basics) and pairs with FastAPI (the service you'll actually be testing and packaging). No further Python-intermediate prerequisites — this is the capstone tooling chapter for the topic.

# Classic stdlib workflow
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install fastapi uvicorn pytest

uv init my-service
uv add fastapi uvicorn
uv add --dev pytest pytest-asyncio

      Where npm has dependencies/devDependencies as top-level keys, Python's convention is [project.optional-dependencies] groups (often named dev, test), installed with pip install -e ".[dev]" or uv sync --extra dev. def sample_user():
    return {"id": 1, "name": "Ada"}

def test_user_has_name(sample_user):
    assert sample_user["name"] == "Ada"

@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 1, 0),
])
def test_add(a, b, expected):
    assert a + b == expected

      How It Works Under the Hood: environment isolation vs node_modules resolution

      Node's module resolution walks up the directory tree looking for node_modules, and every project gets a fresh, isolated tree by default — isolation is a property of the filesystem layout, enforced per-project automatically. Python's import system instead resolves against sys.path, which is populated based on which interpreter binary you invoked — a venv works by giving you a separate interpreter (or a symlink to the system one) with its own site-packages directory baked into that interpreter's sys.path. Activating a venv just prepends that venv's bin/Scripts directory to your shell's PATH, so typing python or pip resolves to the venv's copies instead of the system ones — isolation is a property of which binary your shell finds first, not of the project directory itself. This is why running the wrong interpreter (forgetting to activate, or a misconfigured IDE) silently uses the wrong — often global — set of installed packages, with no error at all, unlike Node where a missing project-local package simply fails to resolve.

      Code Examples

      
# conftest.py -- shared fixtures, auto-discovered by pytest (no import needed in test files)
import pytest
import pytest_asyncio
from httpx import AsyncClient, ASGITransport
from main import app, get_db

class FakeDB:
    def __init__(self):
        self.orders = {}
        self._next_id = 1

    async def insert_order(self, product_id: int, quantity: int) -> dict:
        order = {"id": self._next_id, "product_id": product_id, "quantity": quantity, "total_cents": quantity * 500}
        self.orders[self._next_id] = order
        self._next_id += 1
        return order

@pytest.fixture
def fake_db():
    return FakeDB()

@pytest_asyncio.fixture
async def client(fake_db):
    async def override_get_db():
        yield fake_db
    app.dependency_overrides[get_db] = override_get_db
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()   # teardown: don't leak overrides into other tests

# test_orders.py
import pytest

@pytest.mark.asyncio
async def test_create_order_success(client):
    response = await client.post("/orders", json={"product_id": 1, "quantity": 3})
    assert response.status_code == 201
    body = response.json()
    assert body["quantity"] == 3
    assert body["total_cents"] == 1500

@pytest.mark.asyncio
async def test_create_order_validation_error(client):
    response = await client.post("/orders", json={"product_id": "not-a-number", "quantity": 3})
    assert response.status_code == 422

@pytest.mark.parametrize("quantity,expected_total", [
    (1, 500), (2, 1000), (10, 5000),
])
@pytest.mark.asyncio
async def test_create_order_pricing(client, quantity, expected_total):
    response = await client.post("/orders", json={"product_id": 1, "quantity": quantity})
    assert response.json()["total_cents"] == expected_total

# Mocking an external call with monkeypatch (vs jest.mock)
import httpx

async def fetch_exchange_rate() -> float:
    async with httpx.AsyncClient() as c:
        r = await c.get("https://api.example.com/rate")
        return r.json()["rate"]

@pytest.mark.asyncio
async def test_fetch_exchange_rate_uses_mocked_response(monkeypatch):
    class FakeResponse:
        def json(self):
            return {"rate": 1.23}

    class FakeClient:
        async def __aenter__(self): return self
        async def __aexit__(self, *a): pass
        async def get(self, url): return FakeResponse()

    monkeypatch.setattr(httpx, "AsyncClient", lambda *a, **kw: FakeClient())
    rate = await fetch_exchange_rate()
    assert rate == 1.23

      Real-World Production Scenario at Scale

      At scale

      A team's CI pipeline passes consistently, but a new engineer's local "it works on my machine" report doesn't match a bug reported in staging. Root cause, after investigation: the engineer's editor was configured to use the system Python interpreter directly (no venv activated), which happened to have an older pydantic version installed globally from a previous unrelated project — their local runs silently used that version's (different) validation behavior, while CI correctly used the pinned version from the project's lockfile inside a clean venv. The fix wasn't a code change at all: standardizing on uv (or any tool that creates and auto-activates a project-scoped venv transparently, erroring instead of silently falling back to a global interpreter) and adding a pre-commit check that fails if sys.prefix doesn't point into the project's .venv. This class of bug — silent interpreter/dependency mismatch — is Python's most common "works on my machine" failure mode, and it has no real Node equivalent because node_modules resolution makes the equivalent mistake nearly impossible to make by accident.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Running pip install without an active virtual environment installs into the global/system Python silently — no warning, no error. This is almost never what you want outside of throwaway scripts, and it's the single most common Python tooling mistake engineers new to the ecosystem make, since nothing in the default experience forces you to notice.

      Gotcha

      Writing async tests without pytest-asyncio installed and configured (or without the @pytest.mark.asyncio marker / asyncio_mode = "auto" in pyproject.toml) makes pytest silently treat an async def test_... function as passing without ever actually running its body — pytest just gets back a coroutine object, doesn't await it, and reports success. A test that can never fail is far more dangerous than one that's merely slow.

      • Forgetting to add app.dependency_overrides.clear() in fixture teardown lets overrides from one test leak into unrelated tests run later in the same session — a classic shared-mutable-state bug.
      • Committing a .venv directory to version control (instead of .gitignore-ing it and relying on pyproject.toml/lockfile for reproducibility) bloats the repo and bakes in platform-specific binaries that won't work on a different OS.
      • Relying on pip freeze > requirements.txt as a lockfile: it pins every installed package including transitive ones with no distinction between direct and transitive dependencies, and has no hash verification — reproducible but not auditable or minimal the way a real lockfile (uv.lock, poetry.lock) is.

      Tradeoffs

      ApproachUse whenAvoid whenAlternative

      monkeypatch/manual mocksMocking a specific function/attribute precisely, want explicit controlHeavy, repeated mocking needs across many tests where boilerplate adds uppytest-mock's mocker fixture (thin wrapper reducing boilerplate) or dependency-injection overrides at the framework level (FastAPI's dependency_overrides)

      Interview Questions

      Basic

      What problem does a virtual environment solve, and how is it different from `node_modules`?

      It isolates a project's installed packages from the system Python and from other projects' dependencies, avoiding version conflicts. Unlike `node_modules`, which is automatically project-scoped by directory structure, a venv requires you to explicitly create and activate it — if you forget, `pip install` silently installs into the global interpreter instead.

      Follow-up: how do you check, from the command line, whether a venv is currently active?
      What is `pyproject.toml` and what's its closest npm equivalent?

      It's the modern standardized file (PEP 621) for declaring a Python project's metadata, dependencies, and build configuration — the direct equivalent of `package.json`. It replaces the older, more fragmented combination of `setup.py` and separate `requirements.txt` files.

      Follow-up: where would you declare dev-only dependencies in pyproject.toml?
      What's a pytest fixture, and what's its closest Jest equivalent?

      A fixture is a function decorated with `@pytest.fixture` that provides setup (and optionally teardown, via `yield`) for tests that declare it as a parameter — pytest injects the fixture's return/yielded value automatically. It's conceptually similar to Jest's `beforeEach`/`afterEach`, but more composable since fixtures can depend on other fixtures and are requested explicitly per test rather than applying globally.

      Follow-up: how would a fixture with yield handle cleanup if the test raises an exception?
      What does `@pytest.mark.parametrize` do?

      It runs the same test function multiple times, once per set of parameters provided, reporting each as a separate test case — directly equivalent to Jest's `test.each`. It avoids copy-pasting near-identical test functions that only differ in input/expected-output values.

      Follow-up: can you stack multiple parametrize decorators on one test, and what does that produce?
      Why would `pip freeze > requirements.txt` be considered an incomplete substitute for a real lockfile?

      It lists every installed package with its exact version, including transitive dependencies, with no distinction between what you directly declared and what was pulled in indirectly, and no cryptographic hashes to verify package integrity on install. A real lockfile (uv.lock, poetry.lock, or pip-tools output) tracks the resolution graph and often includes hashes, making installs both reproducible and auditable.

      Follow-up: what problem specifically arises if you try to remove one no-longer-needed dependency from a pip-freeze-generated requirements.txt?
      How does pytest's plain `assert` statement give useful failure output without a special assertion API like Jest's `expect`?

      pytest rewrites assert statements at import/collection time (via its assertion rewriting hook) to capture the values of subexpressions, so a failed `assert x == y` can show you the actual values of `x` and `y` in the failure output, without you needing to call a special comparison function.

      Follow-up: does this assertion rewriting work on third-party library code too, or only your own test files by default?

      Medium

      Explain exactly why running `pip install` with the wrong (or no) venv active can produce a "works on my machine" bug that's hard to diagnose.

      Python resolves imports based on whichever interpreter binary is currently first on `PATH` — if no venv is active, that's the system Python, whose `site-packages` may already contain unrelated packages (at different versions) from previous work. Code then silently runs against whatever happens to be globally installed, with no error, producing behavior that differs from a clean environment (like CI) without any obvious signal that the wrong interpreter was used at all.

      Follow-up: what command would you run to print the exact interpreter path currently in use, to debug this?
      Why must you clear `app.dependency_overrides` in a FastAPI test fixture's teardown, and what class of bug does forgetting it cause?

      `dependency_overrides` is a mutable dict on the shared `app` instance — if one test overrides `get_db` and doesn't clear it afterward, that override persists into the next test that reuses the same `app` object, potentially making an unrelated test pass or fail incorrectly because it's silently using a fake dependency it never asked for. This is a shared-mutable-state bug, the same category as leaking global variables between Jest test files that don't reset module state between runs.

      Follow-up: how would you structure fixtures to make this cleanup automatic and impossible to forget?
      What specifically goes wrong if you write `async def test_foo(): ...` without pytest-asyncio configured, and why is it worse than a normal test failure?

      Without `pytest-asyncio` (or `asyncio_mode` configured), pytest calls the test function, gets back a coroutine object (since it's `async def`), and — because nothing awaits it — simply records the test as passed, since no exception was raised by merely creating the coroutine object. The test body, including every assertion inside it, never actually executes. It's worse than a normal failure because it reports false confidence — a test that can never catch a real bug, silently.

      Follow-up: how would you write a meta-test or CI check to catch this misconfiguration before it hides a real bug?
      Compare mocking strategy in pytest (`monkeypatch`) versus Jest's `jest.mock()` for replacing a module-level import.

      Jest's `jest.mock('./module')` can auto-mock an entire module's exports based on static analysis of the import graph, often with minimal setup. pytest's `monkeypatch.setattr(module, "name", replacement)` is more explicit and surgical — you patch one specific attribute/function on an already-imported module object, which means you need to know exactly where the thing is looked up from (the consuming module's namespace, not necessarily the defining module's), a common source of "my mock didn't take effect" bugs.

      Follow-up: why does patching `httpx.AsyncClient` at the httpx module level work in the example, but patching it on a module that did `from httpx import AsyncClient` would not?
      What's the practical benefit of `uv` over stdlib venv + pip for a team's CI pipeline, beyond raw install speed?

      `uv` produces a real lockfile (`uv.lock`) with a full resolved dependency graph and hashes, resolves dependencies deterministically, and can manage the Python interpreter version itself — collapsing what would otherwise be pyenv + venv + pip + pip-tools into one tool with one config source of truth (`pyproject.toml`). For CI specifically, `uv sync` reproduces an exact environment from the lockfile reliably and quickly, reducing both flakiness and pipeline duration compared to a fresh `pip install` resolving dependencies from scratch each run.

      Follow-up: how does uv's dependency resolution algorithm differ from pip's, and why did pip's historically cause more conflicts?

      Advanced

      Design a pytest fixture hierarchy for testing a FastAPI service with layered dependencies: a fake DB, an authenticated test user, and a per-test transaction rollback so tests don't leak state into each other.

      A session-scoped fixture creates the FastAPI app once; a function-scoped `fake_db` fixture provides a fresh in-memory (or SQLite-in-memory) database per test, with a transaction begun at test start and rolled back at teardown regardless of pass/fail (via `yield` inside a try/finally); a `client` fixture depends on `fake_db` and wires it into `app.dependency_overrides` for `get_db`, clearing overrides at teardown; an `authenticated_client` fixture builds on `client`, additionally overriding `get_current_user` to return a fixed test user. Scoping `fake_db` at function level (not session) is the key decision that guarantees test isolation — a session-scoped DB fixture would leak state across tests even with per-test transaction rollback if the rollback logic has any gap.

      Follow-up: how would you handle a test that specifically needs to verify behavior ACROSS a transaction commit, where rollback-per-test would defeat the test's purpose?
      Explain the tradeoff between pinning exact versions in `pyproject.toml` dependencies versus using compatible-release operators (`>=2.0,<3.0`), especially for a library versus an application.

      An application (deployed as a whole, with a lockfile pinning exact resolved versions for reproducibility) can afford loose version ranges in `pyproject.toml` itself since the lockfile is the actual source of truth for what gets installed — the ranges just express compatibility intent. A library published to others (who have their own dependency trees) should use loose ranges deliberately, since over-pinning a library's dependencies causes version conflicts for every consumer who also depends on that same package at a slightly different version — the Python equivalent of an npm package pinning an exact React version and breaking everyone who's on a different one.

      Follow-up: what's the specific mechanism (dependency resolution algorithm) that causes an over-pinned library dependency to produce an unresolvable conflict for a consumer?
      A test suite passes reliably in CI but is flaky locally for one team member, intermittently failing on async tests with "Event loop is closed" errors. Diagnose likely causes.

      This is a classic symptom of event-loop-scoped fixtures/resources being created in one test's event loop and reused in another after pytest-asyncio has torn down and created a new loop between tests (depending on the configured event loop scope — function vs session) — often caused by a fixture that caches an async resource (like an httpx client or DB connection) at session scope while pytest-asyncio's default loop scope is function-level, so the cached resource's loop reference goes stale between tests. The team member's local flakiness versus CI stability suggests a timing-dependent factor (test ordering via `pytest-xdist` parallelism, or a slower machine surfacing a race that CI's consistent ordering happens to avoid).

      Follow-up: how would you configure pytest-asyncio's event loop scope to fix this, and what's the tradeoff of a session-scoped loop?
      How would you structure packaging for a monorepo containing a shared internal library and multiple FastAPI services that depend on it, without publishing the library to PyPI?

      Give the shared library its own `pyproject.toml` and treat it as a local path dependency: each service's `pyproject.toml` references it via `{ path = "../shared-lib", editable = true }` (uv/Poetry syntax) or an editable pip install (`pip install -e ../shared-lib`), so changes to the shared library are immediately reflected in each service's environment without a publish/version-bump cycle during development. For CI/production builds, decide whether to vendor a pinned snapshot or keep the editable/path reference depending on whether services need independent release cadences from the shared library.

      Follow-up: what breaks if two services in the monorepo need genuinely different versions of the shared library simultaneously, and how would you resolve that?
      Explain how you'd design a test suite's mocking boundary for a service that calls an LLM API (e.g., for an AI feature) — what should be mocked versus tested against the real API, and why?

      Unit/integration tests for business logic (prompt construction, response parsing, error handling, retry/timeout behavior) should mock the LLM client entirely — real API calls are slow, costly, and non-deterministic, making them unsuitable for a fast CI feedback loop and for asserting exact behavior. A small, separate suite of "contract" or smoke tests, run less frequently (nightly, or pre-release, not on every commit) and clearly isolated, should hit the real API to catch breaking changes in the provider's response shape or behavior that a mock could silently drift away from. The mocking boundary should sit at your own client wrapper function, not deep inside a third-party SDK, so your tests assert against a stable interface you control.

      Follow-up: how would you structure the mock's fake responses to stay honest about real API response variability (e.g., token limits, partial failures) rather than only ever testing the happy path?

      Practice Assignments

      Beginner (30-60 min)

      Set up a project from scratch and write your first fixtures

      Create a new project using `uv init` (or stdlib venv + pip if you prefer), add `pytest` as a dev dependency, write a small module with 2-3 pure functions, and write tests using at least one fixture and one `@pytest.mark.parametrize` test covering at least 4 input cases.

      • Must include a `pyproject.toml` with dependencies correctly separated into main vs dev groups.

      Acceptance criteria: `pytest` (or `uv run pytest`) runs and passes from a clean clone of the project with no manually pre-installed global packages required.

      Hints

      Verify isolation actually works by running `which python` (or `where python` on Windows) before and after activating your venv — confirm the path changes.

      Intermediate (2-4 hrs)

      Test a small FastAPI service with dependency overrides and mocking

      Using the FastAPI orders service from chapter 5 (or a similar small service you build), write a test suite covering: a fake-DB-backed happy path via `dependency_overrides`, a validation-failure case, an authenticated-vs-unauthenticated case, and a mocked external HTTP call (using `monkeypatch` or `pytest-mock`) that simulates both a successful response and a timeout.

      • Must use `httpx.AsyncClient` with `ASGITransport` (not the deprecated sync `TestClient` pattern) for async route testing.
      • Must demonstrate fixture teardown correctly clearing `dependency_overrides` between tests.
      • Must achieve test isolation: running tests in random order (`pytest-randomly` or similar) still passes.

      Acceptance criteria: Full suite passes in any test order; coverage report (via `pytest-cov`) shows the critical paths (success, validation failure, auth failure, downstream timeout) are all exercised.

      Hints

      Run `pytest --random-order` (after installing `pytest-randomly`) specifically to catch hidden test-order dependencies — this is the fastest way to surface a forgotten teardown.

      Advanced (1-2 days)

      Build and package a reusable internal library, consumed by a separate test project

      Create two separate projects: a small internal library (e.g., a shared Pydantic schema package plus a couple of utility functions) packaged correctly with `pyproject.toml` for editable local installation, and a second "consumer" project (a tiny FastAPI service) that depends on it via a local path reference. Write a CI-style script (a shell script or Makefile target) that sets up both projects' environments from clean, runs the consumer's test suite against the library, then simulates a breaking change in the library (change a function's signature) and shows the consumer's tests catching it.

      • Must use editable/path-based local dependency resolution, not a copy-pasted or manually symlinked library.
      • Must include a lockfile-based reproducible setup (uv.lock, poetry.lock, or pip-compile output) for the consumer project.
      • Must demonstrate, with a real before/after test run, that the breaking change is caught by the test suite rather than silently passing.

      Acceptance criteria: Clean-environment setup script works end to end; the breaking-change demonstration shows a clear pass-then-fail transition in test output. No full reference solution — this is meant to force real engagement with Python's local/monorepo packaging story, which has no single standardized "right answer" the way basic pip install does.

      Quick Revision Cheat Sheet

      • Python isolation is interpreter-based (which `python`/`pip` binary is first on PATH), not directory-based like `node_modules` — you must create and activate a venv explicitly.
      • pyproject.toml ≈ `package.json`; modern standard replacing `setup.py`/bare `requirements.txt`.
      • uv is the fast, increasingly default 2025-26 tool combining venv creation, dependency resolution, lockfiles, and Python version management.
      • pip freeze > requirements.txt is a crude pin list, not a real lockfile — no hash verification, no direct/transitive distinction.
      • pytest fixtures (@pytest.fixture, optionally with yield for teardown) ≈ Jest's beforeEach/afterEach, but composable via explicit parameter declaration.
      • @pytest.mark.parametrize ≈ Jest's `test.each` — one test body, many input/expected cases.
      • Async tests silently "pass" without running if pytest-asyncio isn't configured — verify `asyncio_mode` or markers are set.
      • Always clear app.dependency_overrides (FastAPI) in fixture teardown to avoid leaking state between tests.
      • monkeypatch.setattr patches a specific attribute where it's looked up from — know the difference between patching a module attribute vs a name imported via `from x import y`.
