    OOP, Dataclasses, Type Hints

    ⏱ ~2.5 hrs📍 Chapter 3 of 6

    One-line summary: Python classes are closer to JS classes than you'd expect, but @dataclass and the descriptor protocol behind @property give you boilerplate-free value objects and computed-property mechanics that have no exact JS equivalent.

    On this page

      Why It Matters for a Senior Developer

      Every real Python codebase you'll touch in an AI/backend-adjacent role uses dataclasses or Pydantic models as its domain layer. Interviewers test whether you understand what a dataclass actually generates (not just "it's like an interface with less typing") and whether you know the descriptor protocol underneath @property — that's the mechanism that makes computed attributes, validators, and even ORMs' field access work, and it's a legitimate "do you actually understand Python objects" probe at senior level.

      Why

      Type hints plus dataclasses are how modern Python gets some of TypeScript's safety back — understanding exactly where that safety is real (static analysis) vs illusory (no runtime enforcement without a validation layer) is a recurring theme across this topic.

      Related: Python for JS Developers, FastAPI (Pydantic models build on these same ideas with runtime validation added).

      Dataclasses

      @dataclass is a class decorator that inspects your class's type-hinted attributes and auto-generates __init__, __repr__, and __eq__ for you — the exact boilerplate you'd otherwise hand-write for a value object. It's the closest thing Python has to a TypeScript interface + constructor combined, except it's a real runtime class, not erased.

      • @dataclass plain — mutable, auto __init__/__repr__/__eq__.
      • @dataclass(frozen=True) — immutable after construction (assignment raises FrozenInstanceError), and becomes hashable by default — this is your closest match to a JS Object.freeze()'d object, but enforced structurally, not just at the top level (nested mutable fields can still be mutated — freezing is shallow, same caveat as Object.freeze).
      • field(default_factory=list) — the dataclass-safe way to give a field a mutable default (solves the exact mutable-default-argument trap from chapter 1, but for class fields).
      • __post_init__ — runs right after the generated __init__, the natural place for validation/derived-field computation.

      The descriptor protocol (what's actually behind @property)

      This is the internals question that separates "I use @property" from "I understand Python's object model." A descriptor is any object implementing __get__, __set__, and/or __delete__, placed as a class attribute. When you access instance.attr, Python doesn't just look in instance.__dict__ — it checks whether the class-level attribute is a descriptor, and if so, calls its __get__ instead of returning it directly.

      @property is just a built-in descriptor class: @property above a method wraps it in a property object (which implements __get__) and binds it to the class attribute of that name. That's the entire mechanism — no special-casing in the interpreter beyond "check for a descriptor before falling back to instance __dict__." This same protocol is what powers @staticmethod, @classmethod, bound methods themselves (functions are descriptors too — that's literally how self gets bound), and ORM field access in libraries like SQLAlchemy and Django.

      Type hints, generics, and Protocol

      Beyond simple hints (x: int), Python's typing module gives you generics (list[int], dict[str, User] — built-in generic syntax since 3.9, no typing.List needed anymore), Optional[X] / X | None (3.10+ union syntax), and Protocol — structural typing, Python's actual equivalent of a TypeScript interface: any class with matching method signatures satisfies a Protocol without explicitly inheriting from it, exactly like TS's "if it has the shape, it fits."

      How It Works Under the Hood

      Every Python object has a __dict__ (unless it defines __slots__) storing its instance attributes — conceptually like a plain JS object's own properties. Attribute lookup on obj.x follows a defined order: first check the type's __mro__ for a data descriptor (has both __get__ and __set__ — these win even over instance __dict__), then check instance.__dict__, then fall back to a non-data descriptor or plain class attribute. This is why @property (a data descriptor) always "wins" even if something tried to stuff a same-named key into instance.__dict__ — the descriptor intercepts first.

      @dataclass does none of this magic at the attribute-access level — it operates purely at class-definition time, reading __annotations__ (the dict of name→type hints you wrote) and generating real Python source for __init__ etc., then exec-ing it into the class. There's no runtime overhead or interception on each attribute access the way descriptors add — a dataclass instance's fields are plain instance attributes once constructed.

      Code Examples

      
from dataclasses import dataclass, field
from typing import Protocol

# ---- BAD: hand-written value object, lots of boilerplate ----
class UserManual:
    def __init__(self, id: int, email: str, tags: list[str] | None = None):
        self.id = id
        self.email = email
        self.tags = tags if tags is not None else []

    def __repr__(self):
        return f"UserManual(id={self.id!r}, email={self.email!r}, tags={self.tags!r})"

    def __eq__(self, other):
        if not isinstance(other, UserManual):
            return NotImplemented
        return (self.id, self.email, self.tags) == (other.id, other.email, other.tags)

# ---- GOOD: dataclass generates all of the above ----
@dataclass(frozen=True)
class User:
    id: int
    email: str
    tags: list[str] = field(default_factory=list)  # safe mutable default

    def __post_init__(self):
        if "@" not in self.email:
            raise ValueError(f"invalid email: {self.email!r}")

u1 = User(id=1, email="a@x.com")
u2 = User(id=1, email="a@x.com")
print(u1 == u2)        # True -- generated __eq__ compares field values
# u1.email = "new@x.com"  # raises FrozenInstanceError

# ---- The descriptor protocol behind @property ----
class Celsius:
    def __init__(self, value: float = 0.0):
        self._value = value

    @property
    def fahrenheit(self) -> float:
        return self._value * 9 / 5 + 32

    @fahrenheit.setter
    def fahrenheit(self, f: float) -> None:
        self._value = (f - 32) * 5 / 9

c = Celsius(100)
print(c.fahrenheit)    # 212.0 -- looks like an attribute, calls __get__
c.fahrenheit = 32      # calls the setter's __set__, no parens, feels like assignment
print(c._value)        # 0.0

# A minimal hand-rolled descriptor -- this is ALL @property does for you
class TypedField:
    def __init__(self, expected_type):
        self.expected_type = expected_type

    def __set_name__(self, owner, name):
        self.name = "_" + name

    def __get__(self, instance, owner):
        return getattr(instance, self.name, None)

    def __set__(self, instance, value):
        if not isinstance(value, self.expected_type):
            raise TypeError(f"{value!r} is not {self.expected_type}")
        setattr(instance, self.name, value)

class Point:
    x = TypedField(int)
    y = TypedField(int)
    def __init__(self, x: int, y: int):
        self.x = x   # triggers TypedField.__set__
        self.y = y

p = Point(1, 2)
# p.x = "oops"       # raises TypeError via TypedField.__set__

# ---- Protocol: structural typing, Python's "interface" ----
class SupportsSave(Protocol):
    def save(self) -> None: ...

class FileLogger:
    def save(self) -> None:
        print("saved to file")

def persist(obj: SupportsSave) -> None:
    obj.save()

persist(FileLogger())   # works -- FileLogger never inherits SupportsSave, just matches shape

      Real-World Production Scenario at Scale

      At scale

      A team building an internal feature store represents each feature definition as a frozen dataclass (immutable, hashable, safe to use as a dict key and to cache). A later requirement needs computed/derived fields (e.g., a feature's "staleness" based on a timestamp field) without breaking immutability or the generated __eq__/hashing. The right tool is a @property (computed from existing frozen fields, not stored state) rather than adding a mutable field — this keeps the object's identity/equality semantics intact (equality still only compares the real stored fields) while giving callers a clean computed attribute, the same tradeoff as choosing a getter over a stored, potentially-stale cached field in a JS class.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      frozen=True only prevents reassigning the dataclass's own fields — it does not make nested mutable objects immutable. @dataclass(frozen=True) class Order: items: list still lets you call order.items.append(x), silently mutating "immutable" state. If you need deep immutability, use tuples instead of lists for the field type, or wrap mutation points behind methods that return new instances.

      • Don't forget field(default_factory=...) for mutable defaults on dataclasses — a bare tags: list[str] = [] raises ValueError at class definition time specifically to prevent the shared-mutable-default bug from chapter 1.
      • __eq__ is auto-generated from fields in declaration order as a tuple comparison — if you add a field that shouldn't participate in equality (e.g., an internal cache), mark it field(compare=False).
      • Multiple inheritance's MRO is powerful but can produce surprising method resolution — use ClassName.__mro__ to inspect it when debugging, don't guess.
      • Don't rely on __slots__ blindly for "performance" without measuring — it saves memory per instance and blocks dynamic attribute addition, but it complicates multiple inheritance and default values; use it deliberately for high-volume value objects, not everywhere.

      Interview Questions

      Basic

      What does `@dataclass` actually generate for you?

      By default, `__init__` (from the type-hinted class attributes), `__repr__`, and `__eq__`. With `frozen=True` it also blocks attribute reassignment and makes the instance hashable (by default, plain mutable dataclasses are unhashable).

      Follow-up: why are plain (non-frozen) dataclasses unhashable by default?
      What's the difference between `self` in Python and `this` in JS?

      `self` is an explicit first parameter you must name in every instance method — Python passes the instance to it automatically when called as `obj.method()`, but there's no implicit binding magic; a method pulled off an instance and called standalone loses that binding entirely (`unbound method` issues), somewhat like `this` losing its binding in JS when a method is detached from its object, but Python requires the explicit parameter everywhere.

      Follow-up: what happens if you call an instance method via the class, like `ClassName.method(instance)`?
      Does Python have true private fields like JS's `#field`?

      No. A single leading underscore (`_name`) is purely a convention signaling "internal, don't touch." A double leading underscore (`__name`) triggers name-mangling (`_ClassName__name`) which makes accidental access harder but is still accessible if you know the mangled name — not true privacy.

      Follow-up: why does name-mangling exist at all if it's not real privacy?
      What is a descriptor, in one sentence?

      Any object implementing `__get__` (and optionally `__set__`/`__delete__`) placed as a class attribute, which Python's attribute-lookup machinery calls instead of returning the object itself.

      Follow-up: name two other Python features besides @property that are built on descriptors.
      What's `Protocol` used for, and how is it different from inheriting an abstract base class?

      `Protocol` enables structural typing — a class satisfies a Protocol just by having matching method signatures, with no explicit inheritance needed (checked statically by type checkers). An ABC requires explicit inheritance and can enforce the interface at runtime (instantiating a subclass missing an abstract method raises `TypeError`).

      Follow-up: can a Protocol provide a default method implementation?

      Medium

      Why does `frozen=True` not give you deep immutability?

      `frozen=True` overrides `__setattr__`/`__delattr__` on the dataclass to raise on reassignment of its own fields — it has no effect on the mutability of the objects those fields point to. A list or dict field remains fully mutable in place; only rebinding the field itself (`obj.field = new_value`) is blocked. True deep immutability requires using immutable field types (tuples, frozensets, nested frozen dataclasses) throughout.

      Follow-up: how would you enforce deep immutability for a nested structure at construction time?
      Walk through Python's attribute lookup order when both a data descriptor and an instance `__dict__` entry exist for the same name.

      Data descriptors (implementing both `__get__` and `__set__`) take priority over instance `__dict__` — Python checks the type's MRO for a data descriptor first, and if found, calls its `__get__`, ignoring any same-named key that might exist in `instance.__dict__`. Only non-data descriptors (`__get__` only, like plain functions/methods) yield to instance `__dict__` first. This is why you can't "shadow" a `@property` by just setting `instance.__dict__['prop'] = x` directly.

      Follow-up: how would you actually bypass a property to set the underlying value directly, if needed?
      How does Python resolve method calls under multiple inheritance, and how is that different from JS?

      Python computes a Method Resolution Order (MRO) per class using C3 linearization — a deterministic order that respects each parent's own MRO and local precedence, resolvable via `ClassName.__mro__` or `.mro()`. `super()` walks this MRO, not just "the direct parent," which lets cooperative multiple inheritance chains work correctly. JS has no multiple inheritance at the class level at all — you'd simulate it with mixins (functions that return a class extending their argument) composed manually, with no language-level MRO resolution.

      Follow-up: what's the classic "diamond problem" and how does C3 linearization avoid it?
      When would you reach for `__slots__`, and what does it cost you?

      Use it for high-volume, fixed-shape value objects where per-instance memory matters (each instance normally carries a `__dict__`, which has real overhead multiplied across millions of instances). `__slots__` replaces that with fixed, fast attribute storage. The cost: no dynamic attribute addition at runtime, more friction combining with multiple inheritance (all non-empty-`__slots__` bases must cooperate), and it conflicts with default mutable field patterns dataclasses otherwise handle for you cleanly.

      Follow-up: can a `@dataclass` use `__slots__`? What changed in recent Python versions to make this easier?
      Why would you choose `@dataclass` for an internal domain model but Pydantic's `BaseModel` for the same shape of data at an API boundary?

      `@dataclass` trusts its inputs — it doesn't validate or coerce types at construction, just assigns whatever you pass (type hints are purely static-analysis documentation here, same "not enforced at runtime" point from chapter 1). At an API boundary you're receiving untrusted external data (JSON from a client), where you need real runtime validation, coercion, and structured error messages — exactly what Pydantic adds on top of the same type-hint syntax. Using dataclasses internally and Pydantic at the boundary cleanly separates "trusted internal representation" from "validated external contract."

      Follow-up: would you ever convert a Pydantic model into a dataclass internally, and why?

      Advanced

      Implement, conceptually, what `@property` does using the raw descriptor protocol, and explain why `fahrenheit.setter` needs to return a new property object.

      `property` is a class whose `__init__` stores a getter function; `.setter(fn)` doesn't mutate the existing property in place — it returns a brand-new `property` object built from the original getter plus the new setter function, which then gets rebound to the same class attribute name by the `@` decorator syntax reassigning it. This immutable-builder pattern is why you write `@fahrenheit.setter` referencing the already-decorated name — it's calling a method on the property object created by the first decoration, not modifying a method on the class directly.

      Follow-up: what would go wrong if `property` objects were mutable and `.setter()` mutated in place instead?
      A senior teammate claims "dataclasses have zero runtime attribute-access overhead compared to plain classes." Is this accurate, and how would you verify it?

      Accurate for the common case: a dataclass without `@property` fields stores its data as plain instance attributes in `__dict__` (or `__slots__`), with the same attribute-access path as any plain class — `@dataclass` only adds work at class-definition time (generating `__init__` etc.), not at attribute-access time. You'd verify with `timeit` comparing attribute gets on a dataclass instance vs an equivalent hand-written class instance — they should be statistically indistinguishable. This stops being true the moment you add `@property` fields or override `__getattribute__`, which do add per-access overhead regardless of whether the class is a dataclass.

      Follow-up: does `frozen=True` add any attribute-access overhead, or only write-path overhead?
      Design an immutable, versioned configuration object that supports "update one field, get a new object back" without re-validating every field on every update.

      Use a frozen dataclass with a `replace`-style method (or `dataclasses.replace(obj, field=new_value)` from the stdlib) that constructs a new instance by copying existing field values and overriding the changed one. To avoid re-validating unchanged fields, structure `__post_init__` validation to be field-local (each field's own invariant checked independently) so a targeted validation path can re-check only the changed field(s) if you build a custom `replace` wrapper, rather than relying on the stdlib's generic `dataclasses.replace` (which does re-run `__post_init__` on the whole new instance — worth knowing explicitly, since "no re-validation" isn't actually free with the stdlib helper unless you bypass `__post_init__` deliberately).

      Follow-up: what does `dataclasses.replace` actually do internally — does it call `__init__` or `__new__` + manual field copy?
      How would you statically enforce that a function only accepts objects that are both "comparable" and "serializable to dict," without using an ABC?

      Define two `Protocol`s — e.g. `class Comparable(Protocol): def __lt__(self, other) -> bool: ...` and `class DictSerializable(Protocol): def to_dict(self) -> dict: ...` — then intersect them with a function signature typed to accept an object satisfying both, using `Protocol` multiple inheritance: `class ComparableSerializable(Comparable, DictSerializable, Protocol): pass`, and type the parameter against that combined Protocol. Any class with matching methods satisfies it with zero explicit inheritance, verified by mypy/pyright at type-check time — genuinely closer to TypeScript's intersection types (`A & B`) than anything an ABC-based approach gives you.

      Follow-up: can you runtime-check (`isinstance`) against a Protocol? What's required for that (`@runtime_checkable`) and what are its limits?

      Practice Assignments

      Beginner (30-60 min)

      Convert a hand-written class to a dataclass

      Take a plain Python class with manually written __init__, __repr__, and __eq__ (at least 4 fields, one with a mutable default like a list) and convert it to @dataclass. Verify behavior is identical via assertions covering equality, repr output format, and the mutable-default trap being correctly avoided.

      • Must use `field(default_factory=...)` correctly for the mutable field.
      • Write one short comment explaining what `@dataclass` eliminated from your original code.

      Acceptance criteria: All assertions pass; the dataclass version is visibly shorter.

      Hints

      Compare `repr()` output strings directly in an assertion, not just by eye — the generated repr format is predictable and worth locking down.

      Intermediate (2-4 hrs)

      Build a validating descriptor library

      Implement a small set of reusable descriptor classes: `PositiveInt`, `NonEmptyString`, `OneOf(*choices)`, each raising a clear `ValueError`/`TypeError` on invalid assignment, using the raw descriptor protocol (`__get__`/`__set__`/`__set_name__`) — not `@property`. Use them as class attributes on at least two different domain classes.

      • Each descriptor must work correctly across multiple instances without state leaking between instances (a classic descriptor bug if you store the value on the descriptor itself instead of the instance).
      • Write a pytest suite covering valid assignment, invalid assignment (expecting the right exception type), and the no-cross-instance-leakage case explicitly.

      Acceptance criteria: pytest suite passes; a test specifically creates two instances, sets different valid values on each, and asserts they don't interfere.

      Hints

      Store each instance's value keyed by instance identity or inside the instance's own `__dict__` under a mangled name set via `__set_name__` — storing it as `self.value = value` directly on the descriptor object is the bug that causes cross-instance leakage.

      Advanced (1-2 days)

      Design an immutable event-sourced aggregate

      Model a simple domain aggregate (e.g., a bank account: deposit/withdraw/freeze) as a frozen dataclass representing current state, where every mutation is actually "apply an event, get a new frozen state back" — never mutating in place. Support replaying a list of events from an initial state to reconstruct current state, and reject invalid transitions (e.g., withdraw more than balance, or any mutation on a frozen account) with domain-specific exceptions.

      • State transitions must go through a single `apply(event)` method returning a new instance, never mutating.
      • Must support replaying an arbitrary list of historical events to reconstruct state from scratch.
      • Include a pytest suite with parametrized test cases covering valid sequences, invalid transitions, and full replay correctness.

      Acceptance criteria: No test or production code path ever mutates a constructed aggregate instance in place — verify this is actually true, don't just assume `frozen=True` handles it (remember the shallow-immutability gotcha). No full reference solution — the point is reasoning about immutable state transitions yourself.

      Quick Revision Cheat Sheet

      • @dataclass generates __init__/__repr__/__eq__ from type-hinted class attributes.
      • frozen=True blocks field reassignment and enables hashing — but immutability is shallow (nested mutables still mutate).
      • Use field(default_factory=...) for mutable field defaults, never a bare mutable literal.
      • A descriptor = object with __get__/__set__ as a class attribute; @property is just the built-in one.
      • Data descriptors (get+set) win over instance __dict__ in attribute lookup; non-data descriptors lose to it.
      • Python supports real multiple inheritance, resolved via MRO (C3 linearization) — JS doesn't have this at all.
      • Protocol = structural typing (duck typing checked statically); ABC = explicit inheritance + optional runtime enforcement.
      • No true private fields — single underscore is convention, double underscore name-mangles but isn't real privacy.
      • Dataclasses don't validate at runtime — use Pydantic at trust boundaries, dataclasses for trusted internal models.
