    Async Python (asyncio)

    ⏱ ~3 hrs📍 Chapter 4 of 6

    One-line summary: asyncio gives Python the same single-threaded, event-loop-driven concurrency model Node has always had by default — the syntax (async/await) is nearly identical, but Python makes you opt in explicitly and never implicitly awaits anything for you.

    On this page

      Why It Matters for a Senior Developer

      You already understand event loops, microtasks, and non-blocking I/O deeply from Node — this chapter is mostly about mapping that mental model onto asyncio's specific vocabulary (tasks, futures, the event loop API) and learning the handful of places where Python's explicitness bites you if you assume Node's implicit behavior. FastAPI (chapter 5) is built entirely on asyncio, so this chapter is the load-bearing prerequisite for writing production Python web services correctly rather than accidentally serializing every request.

      Why

      The single most common production bug in Python async code — a blocking call inside an async def stalling the entire event loop — is invisible in testing with light load and catastrophic in production under concurrency. Understanding exactly why it happens (not just "don't do that") is what separates someone who can debug it at 2am from someone who can't.

      Prerequisites

      Strongly build on Data Structures, Comprehensions, Generators (coroutines are generator-based under the hood) and Python for JS Developers (the GIL discussion). Related: FastAPI.

      Core Concepts

      Tasks, futures, and the event loop API

      • A coroutine object (what calling an async def function gives you) does nothing until it's awaited or scheduled — it's inert, like an unresolved Promise factory, not a running Promise.
      • asyncio.create_task(coro()) schedules the coroutine to run concurrently on the event loop right now, returning a Task you can await later or let run in the background — this is the actual Node-like "fire it and move on" primitive; a bare await coro() does not run concurrently with anything, it runs that one coroutine to completion before continuing.
      • A Future is the lower-level primitive a Task wraps — a placeholder for a result that will exist later, conceptually identical to a bare Promise before any .then is attached.
      • The event loop itself (asyncio.get_running_loop()) is Python's equivalent of Node's libuv loop — it schedules callbacks, polls I/O readiness (via select/epoll/kqueue depending on OS, same underlying OS mechanisms libuv uses), and resumes suspended coroutines when their awaited operation completes.

      Async generators, async context managers, async comprehensions

      Just as a generator suspends at yield, an async generator (async def containing yield) suspends at both yield and await — consumed with async for. async with handles setup/teardown that itself needs to await (e.g., acquiring a DB connection from an async pool) via __aenter__/__aexit__, the async counterparts of __enter__/__exit__. These have no close JS equivalent as language syntax (JS doesn't have async generators as commonly used for resource management, though async iterables exist) but the underlying need — "this cleanup must await something" — is the same problem Node solves with try/finally plus manual awaited cleanup.

      How It Works Under the Hood: asyncio's loop vs Node's libuv loop

      Both are single-threaded, cooperative-multitasking event loops — the core idea (don't block the one thread; suspend and resume logical tasks around I/O waits) is identical. The differences that matter for a senior discussion:

      AspectNode (libuv)Python (asyncio)
      Suspension mechanismCallback registration; async/await is syntactic sugar over Promises, which are themselves callback chains under the hoodNative coroutine frame suspension (the same generator-frame mechanism from chapter 2) — await literally suspends the Python call stack frame
      I/O pollinglibuv abstracts epoll/kqueue/IOCP across platforms, with a dedicated thread pool for things that can't be made non-blocking (DNS, some fs ops)asyncio's event loop uses selectors (epoll/kqueue/select depending on OS) directly for socket I/O; blocking calls need explicit offload via loop.run_in_executor
      Microtask/callback orderingWell-defined phases: timers, pending callbacks, poll, check, close callbacks, with microtasks (Promise callbacks) drained between phasesSimpler single ready-queue model: the loop repeatedly runs ready callbacks/tasks, checks I/O readiness, runs due timers — no distinct "microtask vs macrotask" phase split like Node's
      What blocks the loopAny synchronous CPU-bound JS code, or a blocking syscall not routed through libuvAny synchronous blocking call inside a running coroutine (e.g., requests.get(), time.sleep(), CPU-bound work) — identical failure mode, same fix (offload it)
      Concurrency primitive exposed to youPromises (then-chains) or async/await sugar over themCoroutines + Tasks, explicitly scheduled with create_task/gather — "fire and continue" isn't automatic, you must explicitly create a Task

      The most important practical divergence: in Node, calling an async function and not awaiting it still starts executing synchronously up to the first await, and continues in the background automatically once you move on. In Python, calling an async def function does not even start running it — you get back an inert coroutine object; nothing executes until you either await it or wrap it in asyncio.create_task(). This trips up almost everyone coming from JS at least once.

      Code Examples

      
import asyncio
import time

# ---- BAD: blocking call inside async def stalls the WHOLE event loop ----
async def bad_fetch_all(urls: list[str]):
    import requests   # synchronous, blocking HTTP library
    results = []
    for url in urls:
        results.append(requests.get(url))   # blocks the ENTIRE loop, not just this task
    return results
# while this runs, every other concurrent coroutine on the same loop is frozen --
# identical failure mode to a synchronous CPU-bound loop blocking Node's event loop

# ---- GOOD: async-native HTTP client, real concurrency ----
import httpx

async def good_fetch_all(urls: list[str]):
    async with httpx.AsyncClient() as client:
        tasks = [asyncio.create_task(client.get(url)) for url in urls]
        return await asyncio.gather(*tasks)

# ---- The classic "forgot to await/schedule it" bug ----
async def send_email(to: str) -> None:
    await asyncio.sleep(0.5)   # simulate I/O
    print(f"sent to {to}")

async def handler_bug():
    send_email("user@x.com")   # BUG: this does NOTHING -- returns an unawaited
                                 # coroutine object, Python even warns about this
    print("handled")            # prints immediately, email never sent

async def handler_fixed():
    asyncio.create_task(send_email("user@x.com"))  # fire-and-continue, like Node
    print("handled")             # runs immediately, email sends concurrently

# ---- Offloading a genuinely CPU-bound or blocking-library call ----
def cpu_heavy_sync(n: int) -> int:
    return sum(i * i for i in range(n))

async def offloaded():
    loop = asyncio.get_running_loop()
    # run_in_executor hands this to a thread pool (or process pool) so the
    # event loop keeps serving other coroutines while this runs
    result = await loop.run_in_executor(None, cpu_heavy_sync, 10_000_000)
    return result

# ---- Async context manager + async generator ----
class AsyncDBConnection:
    async def __aenter__(self):
        await asyncio.sleep(0.01)   # simulate async connect
        print("connected")
        return self

    async def __aexit__(self, exc_type, exc, tb):
        await asyncio.sleep(0.01)   # simulate async close
        print("closed")

    async def stream_rows(self):
        for i in range(3):
            await asyncio.sleep(0.01)
            yield {"id": i}

async def query_rows():
    async with AsyncDBConnection() as conn:
        async for row in conn.stream_rows():
            print(row)

asyncio.run(query_rows())

      Real-World Production Scenario at Scale

      At scale

      A FastAPI service handling a few hundred requests/sec starts showing p99 latency spikes to several seconds under load, despite each individual endpoint being fast when tested alone. Root cause: a single endpoint calls a third-party SDK that internally uses the blocking requests library, inside an async def route handler. Every request hitting that endpoint freezes the entire event loop — and therefore every other concurrent request on that worker process — for the duration of that blocking call, exactly like one synchronous CPU-bound handler starving every other connection in a single Node process. The fix mirrors the Node playbook: either swap the SDK for an async-native client, or wrap the blocking call in loop.run_in_executor so it runs on a thread pool instead of the event loop thread. This is consistently the top production asyncio bug reported by teams migrating from Node, because the failure is silent under light load and only shows up under real concurrency.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Calling an async def function without awaiting or scheduling it does not run its body at all — it silently returns an unawaited coroutine object (Python does emit a RuntimeWarning: coroutine was never awaited in many cases, but it's easy to miss in logs). This is the single most common "my async Python code doesn't do what I expected" bug for developers coming from JS, where calling an async function always starts executing it immediately.

      • Never use time.sleep() inside an async def — it blocks the whole thread/loop. Always await asyncio.sleep().
      • asyncio.gather() without return_exceptions=True cancels remaining tasks and raises on the first exception — decide deliberately whether partial failure should be tolerated, same design question as Promise.all vs Promise.allSettled.
      • Mixing sync and async DB drivers in the same codebase is a frequent source of "why is this endpoint slow" bugs — pick one async-native driver (asyncpg, aiomysql, motor) and use it consistently for request-path code.
      • Unhandled exceptions inside a "fire and forget" create_task() are swallowed silently unless you keep a reference and check/await it later, or add a done-callback that logs exceptions — easy to lose errors this way in production.

      Tradeoffs

      ApproachUse whenAvoid whenAlternative
      asyncio (single-threaded concurrency)I/O-bound work, many concurrent network/DB calls, want Node-like scalability per processCPU-bound work exists in the request pathrun_in_executor for the CPU-bound slice, or multiprocessing for heavier CPU work
      asyncio.gatherYou need all results and want to fail fast on the first error (or collect all with return_exceptions=True)You want the first result and don't care about the restasyncio.wait(..., return_when=FIRST_COMPLETED)

      Interview Questions

      Basic

      What happens when you call an `async def` function without `await`ing it?

      Nothing runs — you get back an inert coroutine object. The function body doesn't execute until that coroutine is awaited or scheduled via `asyncio.create_task()`. This differs from JS, where calling an async function always begins executing synchronously up to the first `await`.

      Follow-up: what warning (if any) does Python give you when this happens accidentally?
      What's the difference between `await some_coro()` and `asyncio.create_task(some_coro())`?

      `await some_coro()` runs that coroutine to completion before the current coroutine continues — no concurrency with anything else. `create_task()` schedules it to run concurrently on the event loop right away, returning a Task you can await later or let run in the background — this is the "fire and continue" pattern.

      Follow-up: what happens to a created Task if the program exits before it's awaited?
      Why does calling `time.sleep()` inside an `async def` function break concurrency?

      `time.sleep()` is a blocking call — it blocks the entire OS thread, including the event loop running on it, so every other coroutine scheduled on that loop is frozen for the sleep duration. `asyncio.sleep()` is a proper awaitable that yields control back to the loop, letting other coroutines run during the wait.

      Follow-up: is this analogous to anything in Node? What's the exact parallel?
      What's a Future, and how does a Task relate to it?

      A Future is a low-level placeholder object representing a result that will become available later — like an unresolved Promise. A Task is a Future subclass that specifically wraps and drives a coroutine's execution on the event loop; most application code works with Tasks, Futures being the lower-level primitive underneath.

      Follow-up: when would you create a bare Future directly instead of a Task?
      What's Python's equivalent of `Promise.all`?

      `asyncio.gather(*coroutines_or_tasks)` — runs them concurrently and returns a list of results in the same order, raising on the first exception by default unless `return_exceptions=True` is passed.

      Follow-up: what's the equivalent of `Promise.allSettled`?

      Medium

      Compare asyncio's event loop to Node's libuv loop in terms of how suspension/resumption actually works.

      Node's async/await is sugar over Promises, which are themselves callback-registration chains — the JS engine doesn't suspend "the call stack frame" in the same literal sense; it schedules a continuation callback. Python's `await` genuinely suspends the coroutine's actual stack frame (reusing the generator frame-suspension mechanism) and the event loop resumes execution at the exact bytecode instruction after `await` once the awaited thing is ready. Conceptually both achieve "don't block the thread, come back to this later," but Python's mechanism is closer to true coroutines while JS's is callback/continuation-based under a syntactic veneer.

      Follow-up: does this difference have any observable effect on stack traces or debugging experience?
      Why is "fire and forget" with `create_task()` dangerous for error handling in production?

      If you call `asyncio.create_task(coro())` and never keep a reference or await it, any exception raised inside that task is swallowed — it's only reported (as a warning in the event loop's exception handler, often just logged, not raised) when the task object is garbage collected, which can be much later or never observed. Production code should keep a reference to background tasks (e.g., in a set) and either await them at shutdown or attach a `done_callback` that explicitly logs/handles exceptions.

      Follow-up: how would you implement a "background task registry" pattern to avoid this?
      What's the practical effect of running CPU-bound work via `run_in_executor` with a `ThreadPoolExecutor` vs a `ProcessPoolExecutor`?

      A `ThreadPoolExecutor` still shares the GIL with the main interpreter — it frees the event loop thread to keep serving I/O-bound coroutines while the CPU-bound work runs on another thread, but that other thread still competes for the GIL with any other Python-level work, so it doesn't give you real multi-core parallelism for the CPU-bound task itself. A `ProcessPoolExecutor` runs the work in a separate process with its own GIL, giving genuine parallel CPU execution, at the cost of serialization (pickling) overhead to send arguments/results across the process boundary.

      Follow-up: when would the pickling overhead of ProcessPoolExecutor outweigh the parallelism benefit?
      Explain what `async with` buys you over a plain `try/finally` with manual awaited setup/teardown.

      `async with obj:` calls `await obj.__aenter__()` and guarantees `await obj.__aexit__(...)` runs even on exception, exactly like a sync context manager but for resources whose setup/teardown themselves need to await (e.g., an async DB pool acquiring/releasing a connection). You could hand-roll this with `try/finally` and manual awaits, but `async with` makes the contract explicit, reusable across many call sites, and composable with multiple context managers in one statement.

      Follow-up: how would you implement a custom async context manager using `contextlib.asynccontextmanager` instead of writing `__aenter__`/`__aexit__` by hand?
      How would you detect, in code review, that a third-party library call inside an async route handler is secretly blocking?

      Check whether the library's client is explicitly documented as async-native (uses `async def` methods, built on asyncio/httpx/aiohttp internally) vs a synchronous client called directly inside `async def` — any plain function call without `await` that does network/disk I/O is a red flag. In practice, also profile: if p99 latency under concurrent load is dramatically worse than single-request latency times expected concurrency, suspect a blocking call serializing requests on one event loop.

      Follow-up: what tooling (e.g., `asyncio` debug mode, `blockbuster`-style libraries) can detect blocking calls in async code automatically?

      Advanced

      Design the concurrency architecture for a FastAPI service that must call three downstream APIs per request (two independent, one depending on the first two's results) plus run a moderate CPU-bound scoring function on the combined result.

      Issue the two independent downstream calls as concurrently scheduled tasks via `asyncio.gather`, await both, then make the dependent third call with their combined result. For the CPU-bound scoring step, if it's light enough not to meaningfully stall the loop (measure this, don't guess), leave it inline; if it's heavy, offload via `run_in_executor` with a `ProcessPoolExecutor` sized to available cores, shared across requests (not spun up per-request, which adds process-start overhead on the hot path) — a process pool initialized once at app startup and reused.

      Follow-up: how would you apply a per-downstream-call timeout without one slow call stalling the whole gather?
      Explain exactly how `asyncio.CancelledError` propagates through nested awaits, and why cancellation in asyncio is sometimes called "cooperative."

      Calling `task.cancel()` schedules a `CancelledError` to be raised at the next suspension point inside that task's coroutine (the next `await`) — it doesn't interrupt mid-execution of non-async code. The exception propagates up through the chain of awaited coroutines like any other exception, and each level can catch it to do cleanup (though re-raising is expected convention, since swallowing it silently breaks cancellation semantics for callers awaiting that task). It's "cooperative" because a coroutine that never hits another `await` (e.g., stuck in a blocking call or a tight sync loop) cannot be cancelled until it does — cancellation is a request, not a forced interrupt, unlike OS-level thread termination.

      Follow-up: what's the correct pattern for a coroutine that must guarantee cleanup runs even on cancellation?
      A service runs fine under moderate load but under a traffic spike, p99 latency degrades non-linearly (not just proportionally) worse than CPU/memory metrics would suggest. You suspect the asyncio event loop itself is the bottleneck, not downstream services. How would you confirm or rule this out?

      Instrument event loop lag directly (schedule a cheap periodic callback via `loop.call_later` and measure actual vs expected delay, or use `asyncio`'s debug mode / a library like `aiomonitor`) to see if the loop itself is falling behind scheduling ready callbacks — a sign something is blocking it. Cross-check with per-request tracing to see if latency is uniformly spread (suggesting true loop contention from many legitimate concurrent tasks, possibly meaning you need more worker processes) vs concentrated on requests hitting a specific code path (suggesting one blocking call type is the culprit). Non-linear degradation specifically suggests a resource (loop capacity, a connection pool size limit, a blocking call whose frequency scales with load) hitting a hard ceiling rather than gradual resource exhaustion.

      Follow-up: how does the number of worker processes (e.g., Uvicorn workers) interact with this — does adding more always help?
      Compare Python's structured concurrency (`asyncio.TaskGroup`, 3.11+) to manually managed `gather`/`create_task`, and explain what problem it specifically fixes.

      `asyncio.TaskGroup` (via `async with asyncio.TaskGroup() as tg: tg.create_task(...)`) guarantees that if any child task raises, all sibling tasks in the group are cancelled and the group's `__aexit__` waits for all of them to actually finish (cancelled or completed) before propagating a combined exception (`ExceptionGroup`), eliminating the "orphaned task that outlives its logical scope and silently fails" problem that plain `create_task()` + manual bookkeeping is prone to. This mirrors the structured-concurrency principle from other ecosystems (and is conceptually similar to disciplined use of `Promise.all` plus explicit cleanup in JS, but enforced by the language construct rather than convention) — a task's lifetime is scoped to a block, not left dangling.

      Follow-up: how does an `ExceptionGroup` from a TaskGroup differ from a single exception raised by `gather`, and how do you handle multiple distinct exception types from it?

      Practice Assignments

      Beginner (30-60 min)

      Fix the "forgot to await" bugs

      Given 4 small async functions with deliberately introduced bugs (missing await, missing create_task where concurrency was intended, a blocking time.sleep inside async code, a gather that should have used return_exceptions=True), identify and fix each one, with a comment explaining the symptom you'd observe before the fix.

      • Each fix must be demonstrated with a runnable before/after comparison (timing or print-order output).

      Acceptance criteria: Running each fixed function produces the expected concurrent/non-blocking behavior, measurably (e.g., via timing) different from the buggy version.

      Hints

      Use `asyncio.sleep` calls of a known duration as stand-ins for I/O and measure total elapsed time with `time.perf_counter()` — concurrency bugs become obvious as "took N times longer than expected."

      Intermediate (2-4 hrs)

      Build a rate-limited concurrent fetcher

      Build an async function that fetches N URLs concurrently but respects a maximum concurrency limit (e.g., 5 at a time) using asyncio.Semaphore, with per-request timeout and retry-with-backoff on failure, collecting both successes and failures without one failure aborting the whole batch.

      • Must use a Semaphore to bound concurrency, not just gather everything at once.
      • Must implement timeout per request (`asyncio.wait_for` or `asyncio.timeout`) and exponential backoff retry.
      • Must return a structured result distinguishing successes from failures (not raise on partial failure).

      Acceptance criteria: Against a mock server/endpoint with injected failures and delays, your fetcher respects the concurrency cap (verify this by tracking max concurrent in-flight requests) and correctly separates successes/failures.

      Hints

      Use `httpbin.org`'s delay and status endpoints, or run a tiny local test server, to simulate real latency and failures rather than mocking at the function level — you want to actually exercise the concurrency behavior.

      Advanced (1-2 days)

      Build a tiny async task queue with graceful shutdown

      Implement an in-process async task queue: producers submit coroutine-producing jobs, a fixed pool of worker coroutines consumes from an `asyncio.Queue` and runs them, with graceful shutdown (SIGTERM handling) that stops accepting new jobs, lets in-flight jobs finish (with a maximum drain timeout), and reports any jobs that didn't complete in time.

      • Must use `asyncio.Queue` for job distribution across a configurable number of worker coroutines.
      • Must handle signal-based shutdown using `asyncio`'s signal handling integration, not a busy-poll flag.
      • Must guarantee no job is silently lost or silently swallows an exception.
      • Include a pytest-asyncio test suite covering normal operation, a worker raising an exception mid-job, and shutdown with in-flight jobs.

      Acceptance criteria: Shutdown under load completes within the configured drain timeout, reports incomplete jobs accurately, and the test suite demonstrates no swallowed exceptions. No full reference solution — this is meant to force real engagement with asyncio's cancellation and shutdown semantics.

      Quick Revision Cheat Sheet

      • Calling `async def` without awaiting/scheduling it does nothing — you get an inert coroutine object.
      • await coro() = sequential; create_task(coro()) = concurrent, fire-and-continue.
      • Never call blocking functions (`time.sleep`, sync HTTP/DB libs) inside `async def` — use async-native equivalents or `run_in_executor`.
      • asyncio.gather ≈ `Promise.all`; pass `return_exceptions=True` for `Promise.allSettled`-like behavior.
      • asyncio's loop uses real coroutine frame suspension at `await`; Node's async/await is sugar over Promise callback chains.
      • `ThreadPoolExecutor` offload still shares the GIL; use `ProcessPoolExecutor` for real CPU parallelism.
      • Unreferenced background tasks silently swallow exceptions — keep references or attach done-callbacks.
      • Cancellation is cooperative — a `CancelledError` only fires at the next `await` suspension point.
      • asyncio.TaskGroup (3.11+) gives structured concurrency: child failures cancel siblings and propagate together.
