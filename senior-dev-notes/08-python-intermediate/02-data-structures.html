    Data Structures, Comprehensions, Generators

    ⏱ ~2.5 hrs📍 Chapter 2 of 6

    One-line summary: Python's built-in collections map closely to JS's, but comprehensions, the iterator protocol, and generators give you a memory-efficient lazy-evaluation toolkit that JS only approximates with generator functions and iterables.

    On this page

      Why It Matters for a Senior Developer

      Comprehensions and generators are the single most distinctive "write it the Python way" skill — interviewers use them to separate someone translating JS line-by-line from someone who's actually fluent. Beyond style, generators are a real memory/performance tool: processing a 10GB file or an unbounded stream without loading it all into memory is a daily concern in data/ML-adjacent backend work, and it maps directly onto Node generator functions and streams, which you already understand.

      Why

      If you can explain why a generator doesn't hold the whole sequence in memory (what __next__ actually does, frame suspension), you can also explain backpressure and lazy evaluation in any language — this is transferable systems knowledge, not Python trivia.

      Related: Python for JS Developers, Async Python (async generators build directly on this).

      Comprehensions

      A list comprehension is Array.map/.filter fused into one expression, built into the syntax rather than a method call: [x * 2 for x in items if x > 0] is items.filter(x => x > 0).map(x => x * 2) — but evaluated in one pass, not two. Dict and set comprehensions follow the same shape: {k: v for k, v in pairs}, {x for x in items}.

      Prefer a comprehension over an equivalent for loop with .append() when the body is simple — it's idiomatic, often faster (no repeated method-call overhead per iteration), and clearer at a glance once you're fluent. Don't nest more than two levels or cram complex conditionals in — that's where it stops being readable and a plain loop wins.

      The iterator protocol (the actual mechanism)

      This is the part that doesn't map 1:1 from JS and is worth understanding precisely, because it's exactly what interviewers probe to check real understanding vs memorized syntax.

      • An iterable is any object with an __iter__ method that returns an iterator. An iterator is any object with a __next__ method that returns the next value or raises StopIteration when exhausted.
      • for x in obj: is syntactic sugar for: call iter(obj) (which calls obj.__iter__()), then repeatedly call next() on the result (which calls __next__()) until StopIteration is raised.
      • This is the direct analog of JS's iterable protocol (Symbol.iterator returning an object with a .next() method returning {value, done}) — the mechanics are almost identical, just Python uses a sentinel exception (StopIteration) instead of a {done: true} flag.
      • Lists, dicts, sets, strings are all iterable (have __iter__) but are not iterators themselves — calling iter() on a list creates a separate, stateful list_iterator object. This is why you can loop over the same list twice independently, but can't call next() twice and get two different starting points for the "same" iteration.

      Generator functions and generator expressions

      A function with a yield statement anywhere in its body becomes a generator function — calling it doesn't run the body, it returns a generator object (an iterator) that runs the body lazily, one step per __next__() call, suspending at each yield and resuming exactly there on the next call. This is identical in spirit to a JS function* generator — same suspend/resume mechanism, same "nothing executes until you ask for the next value."

      A generator expression — (x * 2 for x in items), note the parens instead of brackets — is a generator built inline without a def, for cases where you want laziness without a comprehension's eager materialization of the whole list in memory.

      How It Works Under the Hood

      A generator's magic is frame suspension: when CPython executes a generator function and hits yield, it doesn't discard the function's stack frame the way a normal return would — it freezes the frame (local variables, instruction pointer, the works) and hands control back to the caller. The next __next__() call resumes execution from exactly that frozen instruction pointer, with all local state intact. This is the same conceptual mechanism as a coroutine, and it's precisely what asyncio's async def functions build on (covered in depth in chapter 4) — an async def function is, under the hood, a specialized generator-like coroutine that suspends at await instead of yield.

      Memory-wise, this is the entire reason generators matter at scale: a list comprehension over a 10-million-row dataset materializes all 10 million results in memory before you can touch the first one. A generator expression over the same data holds only the current item (and whatever state the loop needs) at any instant — O(1) memory instead of O(n), the same tradeoff as streaming a file in Node with a Readable stream vs loading it entirely with fs.readFileSync.

      Code Examples

      
# ---- Comprehensions vs map/filter ----
nums = [1, -2, 3, -4, 5]

# BAD-ish: works, but verbose for simple transforms
doubled_positive = []
for n in nums:
    if n > 0:
        doubled_positive.append(n * 2)

# GOOD: idiomatic, single expression, same result
doubled_positive = [n * 2 for n in nums if n > 0]
# JS equivalent: nums.filter(n => n > 0).map(n => n * 2)

# dict comprehension
squares_by_n = {n: n ** 2 for n in nums if n > 0}

# defaultdict -- no "if key not in d" boilerplate
from collections import defaultdict
groups = defaultdict(list)
for word in ["cat", "car", "dog", "do"]:
    groups[word[:2]].append(word)
# groups == {'ca': ['cat', 'car'], 'do': ['dog', 'do']}

# ---- The iterator protocol, written out manually ----
class CountUpTo:
    """Mirrors a JS class implementing Symbol.iterator + next()."""
    def __init__(self, limit: int):
        self.limit = limit

    def __iter__(self):
        self.n = 0
        return self   # the object is its own iterator here

    def __next__(self):
        if self.n >= self.limit:
            raise StopIteration
        self.n += 1
        return self.n

for value in CountUpTo(3):
    print(value)   # 1 2 3

# ---- Generator function: same result, far less code, lazy ----
def count_up_to(limit: int):
    n = 1
    while n <= limit:
        yield n
        n += 1

for value in count_up_to(3):
    print(value)   # 1 2 3

# ---- Why laziness matters: memory at scale ----
def read_large_file_eager(path: str) -> list[str]:
    with open(path) as f:
        return [line.strip() for line in f]   # whole file in memory

def read_large_file_lazy(path: str):
    with open(path) as f:
        for line in f:                         # file object is ALREADY an iterator
            yield line.strip()                 # one line in memory at a time

# consuming a 10GB log file to count ERROR lines -- lazy version never
# holds more than one line + a counter in memory
error_count = sum(1 for line in read_large_file_lazy("huge.log") if "ERROR" in line)

      Real-World Production Scenario at Scale

      At scale

      An ETL job ingests a nightly 40GB CSV export and needs to transform and upsert rows into a warehouse. A junior implementation reads the whole file with pandas.read_csv into one DataFrame — it works in dev with a 10MB sample file, then OOMs the container in production. The fix is pandas.read_csv(path, chunksize=50_000) (itself a generator yielding DataFrame chunks) composed with a generator pipeline: read chunk → transform chunk → yield rows → batch-upsert — so memory usage stays flat regardless of file size. This is the same pattern as piping a large file through Node Transform streams instead of buffering it whole; the interview-relevant point is recognizing "this needs to be lazy" before the OOM, not after.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      A generator is exhausted after one full iteration — unlike a list, you can't loop over it twice. gen = (x for x in range(3)); list(gen); list(gen) gives you the values once, then an empty list the second time. If you need to iterate multiple times, either materialize it (list(gen)) once and reuse that, or write a function that returns a fresh generator each time it's called, not a generator object itself.

      • Don't build a huge list comprehension just to immediately iterate it once and discard it — use a generator expression instead (same syntax, swap [] for (), drop the memory cost).
      • dict keys must be hashable — using a list as a key raises TypeError: unhashable type; use a tuple instead, same way you'd use a stable string key in a JS Map rather than an object reference.
      • Mutating a list while iterating over it (for x in lst: lst.remove(x)) skips elements unpredictably — iterate over a copy (for x in lst[:]:) or build a new list instead.
      • Nested comprehensions beyond 2 levels hurt readability fast — refactor into a named helper function or plain loop.

      Interview Questions

      Basic

      What's the difference between a list comprehension and a generator expression?

      Syntax: brackets vs parens. Behavior: a list comprehension eagerly builds the entire list in memory immediately; a generator expression produces a lazy iterator that computes each value on demand and holds only one item's worth of state at a time.

      Follow-up: which one would you use processing a 50GB file line by line?
      What makes an object "iterable" in Python?

      Having an __iter__ method that returns an iterator (an object with __next__). The for loop calls iter() once, then next() repeatedly until StopIteration is raised.

      Follow-up: can an object be its own iterator? When would you do that vs return a separate iterator object?
      Can you iterate over the same generator twice?

      No — once a generator is exhausted (StopIteration raised), it stays exhausted. You'd need to call the generator function again to get a fresh generator object, or materialize the values into a list first.

      Follow-up: is the same true for a list? For a dict's .keys() view?
      What does collections.defaultdict do that a plain dict doesn't?

      It takes a factory function and auto-creates a default value (calling the factory) for any missing key accessed, instead of raising KeyError — removing the "if key not in d: d[key] = []" boilerplate.

      Follow-up: what's a surprising side effect of using defaultdict for a read that you expected to just check existence?
      Why can't you use a list as a dict key?

      Dict keys must be hashable, and lists are mutable — Python disallows hashing mutable types because the hash would need to stay constant for the object's lifetime for dict lookups to work, which mutation would violate. Tuples (immutable) are hashable and commonly used instead.

      Follow-up: why is a tuple containing a list still unhashable?
      What's the Python equivalent of JS array destructuring with a rest element?

      Tuple/list unpacking with a starred name: first, *rest = [1, 2, 3, 4] gives first = 1, rest = [2, 3, 4], mirroring const [first, ...rest] = arr.

      Follow-up: can the starred name be in the middle, like `a, *mid, b = [1,2,3,4,5]`?

      Medium

      Explain exactly what happens, mechanically, when CPython executes a `for` loop over a list.

      iter(lst) calls lst.__iter__(), which returns a new list_iterator object holding an internal index starting at 0. The loop then calls next(iterator) repeatedly; each call increments the internal index and returns lst[index], raising StopIteration once the index reaches the list's length. The list itself is never mutated by this process, and multiple independent iterators over the same list don't interfere.

      Follow-up: what happens if you mutate the list's length while a `for` loop is iterating it?
      How does frame suspension work for a generator, and how does it relate to `async def`?

      When a generator function hits `yield`, CPython doesn't tear down its stack frame as a normal return would — it freezes the frame object (local variables, bytecode instruction pointer) and returns control to the caller holding a reference to that frame via the generator object. The next call to `__next__()` resumes bytecode execution at the instruction right after that `yield`, with all locals intact. `async def` coroutines use the same frame-suspension machinery, suspending at `await` expressions instead of `yield` — which is why early Python async code was literally built on top of generators before `async`/`await` became first-class syntax.

      Follow-up: what's stored differently between a plain generator frame and a coroutine frame?
      You have a generator pipeline: `read_lines() -> parse() -> filter() -> write()`, each a generator. Walk through what actually executes when you call `write()`'s loop once.

      Nothing executes eagerly when the generators are created — only when `write()`'s `for` loop calls `next()` on `filter()`'s generator, which calls `next()` on `parse()`'s, which calls `next()` on `read_lines()`'s, which actually reads one line from disk, returns it up through parse and filter (each doing its transform/check), and only then does `write()` receive one fully-processed item. This "pull" model means at most one item is "in flight" through the whole pipeline at once — the same backpressure-by-construction you get composing Node Transform streams with `.pipe()`.

      Follow-up: what would change if `filter()` used a list comprehension instead of `yield`ing?
      When would a dict comprehension be the wrong tool, even though it's syntactically clean?

      When the data is large and you only need to look up a few keys, or when building the dict requires side effects/ordering guarantees that are easier to express with an explicit loop — comprehensions hide control flow, which is a cost when the logic isn't a pure one-to-one transform. Also when keys might collide and you need to decide how to handle the collision (comprehensions silently keep the last value written for a duplicate key, which can hide a bug).

      Follow-up: how would you detect duplicate keys being silently overwritten in a dict comprehension?
      What's the practical memory difference between `sum(x*x for x in range(10**8))` and `sum([x*x for x in range(10**8)])`?

      The generator version holds one squared value at a time — effectively O(1) memory overhead beyond the running sum. The list comprehension version first builds a 10^8-element list in memory (hundreds of MB to low GB depending on int sizes/overhead) before summing it — a huge, usually pointless, transient allocation for a reduction that never needed the whole list materialized.

      Follow-up: does `range()` itself behave lazily here, and why does that matter?

      Advanced

      Design a generator-based pipeline to process a continuous stream of JSON log lines from stdin, filtering and aggregating, without ever holding more than a bounded window in memory.

      Chain generators: a line-reading generator over `sys.stdin` (already lazy, line-buffered), a `json.loads`-per-line parsing generator (skip/log malformed lines rather than crash the pipeline), a filtering generator for the fields you care about, and a bounded aggregation step using a fixed-size structure (e.g., a `collections.deque(maxlen=N)` for a sliding window, or periodic flush of an accumulator) rather than an ever-growing dict. The key design point: every stage must be a generator (or operate on one item at a time) — introducing a single `list(...)` materialization anywhere in the chain reintroduces unbounded memory growth for an unbounded stream.

      Follow-up: how would you add graceful shutdown (flush partial aggregates) on SIGTERM to this pipeline?
      Explain `yield from` and what problem it solves versus manually delegating to a sub-generator with a loop.

      `yield from subgen` delegates iteration to `subgen`, yielding each of its values directly to the caller, and — critically — also forwards `.send()`, `.throw()`, and `.close()` calls through to the sub-generator, and its final return value becomes the value of the `yield from` expression itself. A manual `for x in subgen: yield x` only forwards the yielded values; it silently breaks two-way communication (send/throw) with the sub-generator and loses its return value. This matters anywhere generators are used as coroutines (pre-async/await style) or when composing generators that need bidirectional signaling.

      Follow-up: how is `yield from` related to how `await` works on a coroutine internally?
      A teammate wants to "parallelize" a CPU-heavy generator pipeline by running each stage in its own thread, passing items through queues. Evaluate this design given the GIL.

      If each stage's per-item work is CPU-bound Python code, threading buys nothing — the GIL still serializes execution of the actual transform logic across those threads; you've added queue and context-switch overhead without real parallelism. The queues do let you overlap I/O-bound stages (e.g., a stage reading from a socket) with CPU-bound stages in a different thread, which is a legitimate win, but any stage that's pure CPU-bound Python should go to a `multiprocessing`/`ProcessPoolExecutor` worker pool instead if parallel throughput is genuinely needed.

      Follow-up: what's the cost of moving generator items across a process boundary (pickling) that doesn't exist across threads?
      How would you make a custom object support both `for x in obj` and random access `obj[i]`, and what's the tradeoff of each?

      Implement `__iter__`/`__next__` (or just `__getitem__` with sequential integer indices — Python falls back to that for iteration if `__iter__` is absent) for iteration, and implement `__getitem__` with arbitrary index support plus `__len__` for random access and `len()`. The tradeoff: true random access generally requires the full data to be addressable (in memory or on fast storage), which conflicts with the lazy, single-pass nature that makes generators memory-efficient in the first place — you can't have O(1)-memory laziness and O(1) random access to arbitrary past elements simultaneously unless you buffer or recompute.

      Follow-up: how does Python's own `range` object manage to support both efficiently?

      Quick Revision Cheat Sheet

      • Iterable = has __iter__; Iterator = has __next__, raises StopIteration when done.
      • for x in obj = it = iter(obj) then repeated next(it) until StopIteration.
      • List/dict/set comprehensions are eager (build the whole thing now); generator expressions `()` are lazy.
      • A generator freezes its stack frame at `yield` and resumes exactly there — the same mechanism `async def` builds on.
      • Generators are single-use: exhausted once, exhausted forever. Materialize with `list()` to reuse.
      • `yield from` forwards values AND send/throw/return — a manual loop only forwards yielded values.
      • Use generators for large/unbounded data and pipeline composition; lists when you need length/random access/multiple passes.
      • dict keys must be hashable — use tuples, not lists, as composite keys.
      • defaultdict/Counter remove manual "check-then-init" boilerplate for grouping/counting.
