    FastAPI: Building Production APIs

    ⏱ ~3.5 hrs📍 Chapter 5 of 6

    One-line summary: FastAPI is Python's closest analogue to Express/NestJS for building async HTTP APIs — Pydantic replaces Zod/Joi for request validation, and its dependency-injection system replaces Express middleware chains with typed, composable, request-scoped functions resolved automatically from route signatures.

    On this page

      Why It Matters for a Senior Developer

      FastAPI is the dominant framework for Python web services in 2025-26, especially in AI/ML-adjacent backends (model-serving APIs, RAG pipelines, agent orchestration layers) — exactly the kind of system senior interviews increasingly probe for. It's built directly on the asyncio model from chapter 4 and on Pydantic for validation, so this chapter assumes both. Interviewers expect you to reason about request lifecycle, dependency injection, validation boundaries, and async correctness at the same depth you'd reason about an Express/Nest service — the vocabulary differs, the architectural concerns don't.

      Why

      Unlike Express, where "middleware" is a single generic concept stacked in a pipeline, FastAPI's dependencies are typed, composable functions that can themselves depend on other dependencies, get cached per-request, and integrate with OpenAPI docs generation automatically. Senior candidates who can only describe "it's like middleware" miss the parts interviewers actually probe: how dependency resolution order works, how to scope a dependency per-request vs per-app, and how validation errors propagate before your handler even runs.

      Prerequisites

      This chapter assumes Async Python (asyncio) (FastAPI route handlers are coroutines running on the event loop) and OOP, Dataclasses, Type Hints (Pydantic models extend this type-hint-driven mental model). Related: Virtual Envs, Packaging, Testing for testing FastAPI apps with pytest.

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UserIn(BaseModel):
    name: str
    email: str
    age: int | None = None

class UserOut(BaseModel):
    id: int
    name: str
    email: str
    # note: no "age" here -- response_model strips fields not declared,
    # similar to applying a Zod output schema on the way out

@app.post("/users", response_model=UserOut, status_code=201)
async def create_user(payload: UserIn):
    # payload is already validated -- this line only runs if validation passed
    return {"id": 1, "name": payload.name, "email": payload.email, "age": payload.age}

      Pydantic: request validation as the type system (vs Zod/Joi)

      Pydantic models are the Python equivalent of Zod schemas, but validation is driven by the same type hints you'd write anyway for readability — there's no separate schema DSL to maintain alongside your types. Validators run eagerly at model construction; FastAPI constructs the model from the incoming request body, so invalid input never reaches your handler at all (compare: Express middleware that calls schema.safeParse(req.body) and manually short-circuits on failure).

      
from pydantic import BaseModel, EmailStr, field_validator, Field

class SignupRequest(BaseModel):
    username: str = Field(min_length=3, max_length=30)
    email: EmailStr                      # built-in format validation, like Zod's .email()
    password: str = Field(min_length=8)

    @field_validator("username")
    @classmethod
    def no_spaces(cls, v: str) -> str:
        if " " in v:
            raise ValueError("username must not contain spaces")
        return v

      Dependency Injection (the real conceptual leap from Express middleware)

      • Depends(fn) declares that a route parameter's value comes from calling fn (itself possibly async) — FastAPI resolves the whole dependency graph before your handler runs, including dependencies that themselves use Depends(), recursively.
      • Unlike Express middleware, which runs unconditionally for every matched route in its mount path, a FastAPI dependency is declared explicitly per-route (or per-router via dependencies=[...]), making the "what runs before this handler" question answerable by reading the function signature alone.
      • Dependencies are cached per-request by default — if two different route parameters depend on the same underlying dependency function, it's called once per request, not twice (configurable via use_cache=False).
      • yield-based dependencies give you setup/teardown in one function (acquire a DB session, yield it, close it in a finally) — the dependency equivalent of the async context manager from chapter 4, scoped automatically to the request lifecycle.
      
from fastapi import Depends, HTTPException, Header

async def get_db():
    db = await create_connection()
    try:
        yield db          # handler runs here, db is available
    finally:
        await db.close()  # guaranteed cleanup, even on exception -- like Express's res.on('finish')
                           # but scoped per-request automatically, no manual wiring

async def get_current_user(authorization: str = Header(...), db = Depends(get_db)):
    token = authorization.removeprefix("Bearer ")
    user = await db.fetch_user_by_token(token)
    if user is None:
        raise HTTPException(status_code=401, detail="Invalid token")
    return user

@app.get("/me")
async def read_me(user = Depends(get_current_user)):
    # by the time we're here: token was validated, db session was opened,
    # and will be closed automatically after the response is sent
    return {"id": user.id, "name": user.name}

      How It Works Under the Hood: request lifecycle vs Node/Express

      FastAPI sits on Starlette (ASGI) the way Express sits on Node's raw http module. The request lifecycle: an ASGI server (Uvicorn) accepts the connection and hands off to the ASGI app; FastAPI matches the route, resolves the dependency tree (running each dependency's coroutine, respecting the per-request cache), validates path/query/body params into Pydantic models, calls your handler coroutine, then serializes the return value against response_model before sending bytes back. Critically, because route handlers are coroutines, a single Uvicorn worker process can hold many requests "in flight" concurrently exactly like a single Node process — the entire reason chapter 4's "don't block the loop" rule applies here with full force: a synchronous blocking call inside a FastAPI route handler stalls every other concurrent request on that worker.

      Code Examples

      
from fastapi import FastAPI, Depends, HTTPException, APIRouter
from pydantic import BaseModel
import asyncio

app = FastAPI(title="Orders API")
router = APIRouter(prefix="/orders", tags=["orders"])

class OrderIn(BaseModel):
    product_id: int
    quantity: int

class OrderOut(BaseModel):
    id: int
    product_id: int
    quantity: int
    total_cents: int

# ---- BAD: blocking DB driver call inside an async route stalls the whole worker ----
@router.post("/bad", response_model=OrderOut)
async def create_order_bad(payload: OrderIn):
    import psycopg2   # synchronous driver
    conn = psycopg2.connect("...")
    cur = conn.cursor()
    cur.execute("INSERT INTO orders ...")   # BLOCKS the event loop -- same bug as chapter 4
    conn.commit()
    return {"id": 1, **payload.model_dump(), "total_cents": 999}

# ---- GOOD: async-native driver, non-blocking end to end ----
async def get_pool():
    # created once at app startup in practice (lifespan event), shown inline here
    import asyncpg
    pool = await asyncpg.create_pool(dsn="postgresql://...")
    try:
        yield pool
    finally:
        await pool.close()

@router.post("", response_model=OrderOut, status_code=201)
async def create_order(payload: OrderIn, pool = Depends(get_pool)):
    async with pool.acquire() as conn:
        row = await conn.fetchrow(
            "INSERT INTO orders (product_id, quantity) VALUES ($1, $2) RETURNING id, total_cents",
            payload.product_id, payload.quantity,
        )
    return {"id": row["id"], **payload.model_dump(), "total_cents": row["total_cents"]}

# ---- Composable dependencies: rate limiting on top of auth ----
class RateLimitExceeded(HTTPException):
    def __init__(self):
        super().__init__(status_code=429, detail="Too many requests")

_request_counts: dict[str, int] = {}

async def rate_limiter(user = Depends(lambda: {"id": 1})):  # simplified; normally Depends(get_current_user)
    count = _request_counts.get(user["id"], 0)
    if count >= 100:
        raise RateLimitExceeded()
    _request_counts[user["id"]] = count + 1

@router.get("/{order_id}", response_model=OrderOut, dependencies=[Depends(rate_limiter)])
async def get_order(order_id: int, pool = Depends(get_pool)):
    async with pool.acquire() as conn:
        row = await conn.fetchrow("SELECT * FROM orders WHERE id = $1", order_id)
    if row is None:
        raise HTTPException(status_code=404, detail="Order not found")
    return dict(row)

app.include_router(router)

# ---- Lifespan events: startup/shutdown (replaces @app.on_event, deprecated) ----
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    print("startup: warm caches, open pools")
    yield
    print("shutdown: close pools gracefully")

app.router.lifespan_context = lifespan

      Real-World Production Scenario at Scale

      At scale

      A FastAPI service backing an internal ML feature store serves p50 latency under 20ms in staging but degrades sharply in production once traffic crosses roughly 200 req/sec per worker. Investigation shows the team wired Depends(get_db) to open a brand-new database connection per request (no pool) — functionally correct, but each connection's TCP handshake and TLS negotiation adds tens of milliseconds, and the DB server's max-connections limit gets hit under load, causing cascading timeouts. The fix: create the connection pool once at app startup via a lifespan context manager, and have get_db acquire/release from that shared pool per request instead of opening a fresh connection each time — directly analogous to the classic Node mistake of calling new Pool() inside a request handler instead of once at module load. This is the single most common FastAPI production misconfiguration reported by teams new to the framework.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Defining a route handler as a plain def (not async def) causes FastAPI to run it in a thread pool automatically — this is a deliberate feature for wrapping blocking libraries, not a free pass. Mixing def and async def handlers inconsistently across a codebase, without understanding which threading model each gets, is a common source of "why does this one endpoint behave differently under load" bugs.

      Gotcha

      response_model validates and filters the output too — if your handler returns extra sensitive fields (e.g., a password hash) and you forgot to declare a tight response_model, FastAPI will serialize whatever your handler returns using the model you declared, but if you return a raw dict and have no response_model at all, nothing strips sensitive fields. Always declare an explicit output model for anything touching user data — don't rely on remembering to manually exclude fields in each handler.

      • Creating a new DB connection pool (or any expensive resource) inside a dependency function called per-request, instead of once at startup via lifespan, defeats pooling entirely.
      • Forgetting that Pydantic's default BaseModel is strict about types but not about unexpected extra fields unless you set model_config = ConfigDict(extra="forbid") — silently accepting unknown fields can hide client bugs.
      • Using mutable default arguments or module-level mutable state (like the _request_counts dict above, shown simplified) across requests without considering multi-worker deployments — state like that must live in Redis/a shared store once you run more than one worker process, since each worker has its own memory.

      Interview Questions

      Basic

      How does FastAPI know how to validate an incoming request body?

      From the type hint on the route handler's parameter — if the parameter's type is a Pydantic BaseModel subclass, FastAPI parses the JSON body and constructs that model, running all its validators before the handler body ever executes. A validation failure returns a 422 automatically without your code running at all.

      Follow-up: what HTTP status code does a validation failure return by default, and what does the error body look like?
      What is `Depends()` and what's the closest Express equivalent?

      `Depends(fn)` tells FastAPI to call `fn` (resolving its own dependencies recursively) and inject the result as that parameter's value, before the route handler runs. The closest Express equivalent is middleware, but unlike middleware it's declared explicitly per-route/router, is typed, and can be swapped out in tests via dependency overrides.

      Follow-up: are dependencies resolved sequentially or can independent ones run concurrently?
      What does `response_model` do, and why would you always declare one on routes handling user data?

      It defines the shape FastAPI serializes the handler's return value into, stripping any fields not declared on that model. Without it, whatever dict/object your handler returns gets serialized as-is, which risks leaking fields like password hashes or internal IDs that happened to be present on the object you returned.

      Follow-up: does response_model also validate, or only filter?
      What's the practical difference between an `async def` and a plain `def` route handler in FastAPI?

      An `async def` handler runs directly on the event loop like any other coroutine. A plain `def` handler is automatically run in a thread pool by FastAPI/Starlette, so it won't block the event loop even if it does blocking work internally -- but it's bounded by the thread pool's size, and still shares the GIL, so it's not a substitute for genuinely async-native I/O under high concurrency.

      Follow-up: what's the default size of that thread pool, and how would you tune it?
      Where does FastAPI's automatic OpenAPI documentation (`/docs`) come from?

      It's generated from the type hints and Pydantic models on your route handlers -- path/query/body parameter types, response models, and status codes are all introspected to build the OpenAPI schema, which Swagger UI (`/docs`) and ReDoc (`/redoc`) render automatically with zero extra annotation work.

      Follow-up: how would you add a custom description or example to a field for the generated docs?
      What's `APIRouter` and why would you use it instead of registering every route directly on `app`?

      `APIRouter` lets you group related routes (e.g., all `/orders` endpoints) into their own module with a shared prefix, tags, and dependencies, then mount the whole group onto the main app with `app.include_router(router, prefix=...)` -- the direct equivalent of `express.Router()` for modularizing a large API.

      Follow-up: can you apply a dependency to every route in a router at once, without repeating `Depends()` on each?

      Medium

      Explain exactly what happens, step by step, between a client POST request arriving and your handler's code running, for a route with two nested dependencies.

      Uvicorn accepts the connection and hands the ASGI scope to FastAPI; FastAPI matches the route, then builds the dependency graph top-down: it calls the outermost dependency, which itself declares `Depends()` on an inner one, so the inner one is resolved first (and cached if reused elsewhere in the same request), then the outer one runs with that result. Only after the full graph resolves does FastAPI parse and validate the request body against the declared Pydantic model, and only after that does your handler coroutine actually get awaited.

      Follow-up: at what point in this sequence does a 422 get returned versus a 401 from an auth dependency?
      Why is creating a database connection pool inside a per-request `Depends()` function (instead of at app startup) a production problem, and what's the Node/Express parallel?

      It means every single request pays the cost of establishing a brand-new connection (TCP handshake, TLS, auth) instead of reusing one from a pre-warmed pool, adding latency and risking hitting the database's max-connections limit under concurrency. The exact parallel in Node is instantiating `new Pool()` (pg, mysql2) inside a request handler instead of once at module load -- both mistakes turn a cheap pooled operation into an expensive per-request setup cost.

      Follow-up: where specifically should the pool be created and torn down in a FastAPI app's lifecycle?
      How would you override a dependency in tests without changing production code?

      FastAPI's `app.dependency_overrides` dict lets you map a dependency function to a replacement for the duration of a test -- e.g., override `get_db` to return an in-memory/test database session, or override `get_current_user` to return a fixed test user, bypassing real auth entirely. This is cleaner than monkeypatching because it's scoped to the app instance and FastAPI's own resolution mechanism handles it.

      Follow-up: how would you scope an override to a single test function versus the whole test session using pytest fixtures?
      What's the risk of using a plain in-memory dict (like a request-count tracker) as shared state across requests in a FastAPI app deployed with multiple Uvicorn workers?

      Each worker process has its own separate memory space -- a dict in one worker's process is invisible to the others. A rate limiter or counter built this way will undercount under multi-worker deployment, since a client's requests get load-balanced across workers that each think they're seeing fewer requests than they actually are in aggregate. Shared state across workers needs an external store like Redis.

      Follow-up: how would you redesign the rate limiter example to be correct across multiple workers?
      Compare FastAPI's `response_model` filtering to how you'd achieve the same output-shaping in an Express/Zod stack.

      In Express, output shaping is manual: you'd typically call something like `OutputSchema.parse(data)` or hand-pick fields before calling `res.json()`, and nothing enforces that every handler does this consistently. FastAPI's `response_model` is declarative on the route decorator itself -- it's enforced automatically for every response from that route, and it's also what feeds the OpenAPI docs, so the documented response shape and the actual enforced shape can never drift apart.

      Follow-up: what happens if your handler returns a field that response_model doesn't declare but a required field is missing?

      Advanced

      Design a FastAPI service's dependency structure for an endpoint that needs: authenticated user, per-user rate limiting, and a database transaction that must roll back if the handler raises.

      Layer dependencies: `get_db` (yield-based, opens a connection), `get_current_user` depending on a decoded auth header, and a `get_db_transaction` dependency depending on `get_db` that begins a transaction, yields the connection, and commits on clean exit or rolls back if an exception propagates through it (via try/except around the yield). The route depends on `get_db_transaction` and `get_current_user`; because `get_db` is cached per-request, both the transaction dependency and anything else needing raw DB access share the same underlying connection without opening it twice.

      Follow-up: how would you handle a case where the rate limiter dependency must run and reject the request BEFORE the (potentially expensive) transaction dependency opens a connection?
      Explain how FastAPI's background tasks (`BackgroundTasks`) differ from `asyncio.create_task()`, and when you'd pick one over the other.

      `BackgroundTasks` (injected via a route parameter) schedules a function to run after the response has already been sent to the client, still within the same request's lifecycle and still on the same worker -- useful for "send a confirmation email after responding" without making the client wait. `asyncio.create_task()` schedules something to run concurrently immediately, not tied to response completion, and its lifecycle is detached from the request/response cycle entirely (with the exception-swallowing risk from chapter 4). For anything that must survive past a single request/response or needs retry guarantees, neither is really sufficient -- that's what a real task queue (Celery, arq, or a cloud queue) is for.

      Follow-up: what happens to a BackgroundTask if it raises an exception -- does the client ever find out?
      A FastAPI service needs to call three independent downstream APIs per request and combine results, while respecting a strict 2-second total SLA. Design the handler.

      Issue all three downstream calls as concurrently scheduled tasks (`asyncio.gather` or `TaskGroup`), each wrapped individually with `asyncio.wait_for`/`asyncio.timeout` sized so the slowest acceptable path still fits the 2-second budget, and decide explicitly whether a partial failure (one downstream timing out) should degrade gracefully (return partial data) or fail the whole request -- using `return_exceptions=True` with `gather` if partial degradation is acceptable. Wrap the whole dependency resolution + handler execution in an outer timeout as a backstop, and emit metrics on which downstream call is the actual bottleneck under load so the SLA risk is visible before it's breached in production.

      Follow-up: how would you differentiate, in your metrics, between "downstream is slow" and "our own event loop is the bottleneck"?
      How would you structure a large FastAPI codebase (50+ endpoints, multiple teams) to avoid a monolithic app.py, and what's the Express/Nest parallel?

      Split by domain into separate `APIRouter` modules (orders, users, payments), each with its own dependencies, Pydantic schemas, and service-layer functions, mounted onto the main app via `include_router` with distinct prefixes/tags -- directly analogous to Nest's module system or a well-organized Express app split into per-domain routers. Shared cross-cutting dependencies (auth, DB session, rate limiting) live in a common module imported by each domain router, and a `lifespan` context manager in the main app wires up app-wide resources (pools, caches) once at startup, injected down into domain-specific dependencies.

      Follow-up: how would you enforce that one domain's router never directly imports another domain's internal service functions?
      Explain the tradeoff between using FastAPI's built-in `response_model` validation on every response versus skipping it for performance on a very hot, high-throughput endpoint.

      `response_model` validation/serialization has real CPU cost -- Pydantic has to construct and validate a model instance from your return value on every single response, which is measurable overhead at very high request rates (tens of thousands of req/sec). For genuinely hot paths, FastAPI lets you set `response_model=None` or use `Response`/`ORJSONResponse` directly to bypass that step, trading the safety/consistency guarantee (and the OpenAPI doc accuracy) for raw throughput -- a decision that should be measured with profiling, not assumed, since Pydantic v2's Rust core made this overhead much smaller than it was in Pydantic v1.

      Follow-up: how would you benchmark whether response_model overhead is actually your bottleneck before deciding to remove it?

      Practice Assignments

      Beginner (30-60 min)

      Build a validated CRUD endpoint

      Build a single FastAPI route group for an in-memory "notes" resource (no real DB — a dict is fine): create, get-by-id, list, delete. Use separate Pydantic models for input and output, with at least one custom field validator (e.g., reject empty titles) and correct status codes (201 on create, 404 on missing, 204 on delete).

      • Must use distinct Pydantic input/output models, not the same model for both directions.

      Acceptance criteria: Hitting /docs shows correct request/response schemas; invalid input returns 422 with field-level errors; all four operations work via curl or the Swagger UI.

      Hints

      Start from `fastapi dev` (or `uvicorn main:app --reload`) and build incrementally, checking `/docs` after each route — it's the fastest feedback loop for catching schema mistakes.

      Intermediate (2-4 hrs)

      Layered dependency injection with auth and a fake DB pool

      Build a small API with a `get_db` yield-dependency wrapping a fake async connection pool (simulate with `asyncio.sleep` for "connect"/"query" delays), a `get_current_user` dependency that reads a bearer token from headers and raises 401 if invalid, and at least one route that depends on both plus a rate-limiter dependency layered on top of auth.

      • Must demonstrate dependency caching: prove via logging/print statements that `get_db` is called once per request even when two other dependencies both depend on it.
      • Must include a `lifespan` context manager that creates the fake pool once at startup.
      • Must write pytest tests using `app.dependency_overrides` to bypass real auth in tests.

      Acceptance criteria: Test suite passes with overridden dependencies; log output proves single resolution of shared dependencies per request.

      Hints

      Use `TestClient` (from `fastapi.testclient`, sync) or `httpx.AsyncClient` with `ASGITransport` for async tests — the pytest-asyncio chapter (06) covers the async test setup in depth.

      Advanced (1-2 days)

      Production-shaped service: real DB, graceful degradation, load test

      Build a FastAPI service backed by a real async-native database (SQLite via `aiosqlite` is fine for local dev) with a connection pool created at startup, at least two endpoints that fan out to two "downstream" calls concurrently (can be fake async HTTP calls to httpbin with simulated delay) with per-call timeouts and graceful partial-failure handling, structured logging of request latency per endpoint, and a basic load test (using `locust` or a simple asyncio-based script) demonstrating the service holds a target p99 latency under a defined concurrency level.

      • Must handle one downstream call timing out without failing the whole request (degrade gracefully).
      • Must include a pytest suite covering the happy path, a downstream timeout path, and a validation-failure path.
      • Must include a short write-up of what p99 latency you achieved under what concurrency, and what the bottleneck was.

      Acceptance criteria: Load test results and write-up included; test suite passes; no blocking calls present in any `async def` route (verify by code review, not just testing). No full reference solution — this is meant to force real engagement with FastAPI's production concerns.

      Quick Revision Cheat Sheet

      • FastAPI infers request validation from type hints on the handler signature — a Pydantic model param means automatic body validation, 422 on failure, before your code runs.
      • Depends(fn) ≈ typed, composable Express middleware — resolved per-route, cached per-request, recursively composable.
      • yield-based dependencies give setup/teardown (like async context managers) scoped automatically to the request lifecycle.
      • Always declare an explicit response_model for routes touching user data — it strips undeclared fields on the way out.
      • Create pools/expensive resources once in a lifespan context manager at startup, never per-request inside a dependency.
      • async def handlers run on the event loop; plain def handlers run in a bounded thread pool — know which one each route is and why.
      • In-memory shared state (dicts, counters) breaks across multiple Uvicorn workers — each worker has separate memory; use Redis/a shared store instead.
      • /docs (Swagger) and /redoc are generated automatically from your type hints and Pydantic models — no manual annotation needed.
      • Override dependencies in tests via app.dependency_overrides, not monkeypatching.
