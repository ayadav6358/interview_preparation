    Python Intermediate

    📚 6 chapters⏱ ~15–18 hrs total

    Python keeps showing up in senior/staff interviews now, not because teams are rewriting their Node backends in Python, but because every AI/ML-adjacent team (RAG pipelines, agent orchestration, data/ML platform work) is built on it, and interviewers expect a senior candidate to read and write it fluently, not just "know the syntax." You already have 10 years of JS/Node — this topic is not "learn programming again," it is a fast, honest bridge: what's the same, what's genuinely different (the GIL, the import system, duck typing without TypeScript's safety net), and where Python's answer to a problem you already solved in Node (concurrency, packaging, testing, building an API) actually works.

    Learning Outcomes

    • Read and write idiomatic Python without translating it mentally from JS line by line.
    • Explain the GIL, why CPython threads don't give you parallelism, and when multiprocessing/async actually help — and defend that against someone who thinks "Python is just slow."
    • Use comprehensions, iterators, and generators correctly, and explain the iterator protocol (__iter__/__next__) the way you'd explain JS iterables/generators.
    • Design clean domain models with dataclasses and type hints, and know what the descriptor protocol is actually doing under @property and dataclass fields.
    • Write and reason about asyncio code, and compare its single-threaded event loop to Node's libuv loop point by point — where they're the same idea and where they diverge.
    • Build a production-grade FastAPI service: routing, Pydantic validation, dependency injection, async DB access, middleware, background tasks.
    • Set up a real Python project the way a senior engineer would: venv, pyproject.toml, pinned deps, and a pytest suite with fixtures and parametrization.

    🏆 Capstone Project: Port a Node/Express "Users" API to FastAPI

    Problem statement: You have (or imagine) a small Express CRUD API for a users resource backed by Postgres — GET/POST/PATCH/DELETE /users, validation middleware, a service layer, and a Jest test suite. Port it to Python, end to end, using everything from this topic: FastAPI, async DB access, Pydantic validation, dataclasses for internal (non-wire) models, type hints throughout, pytest, and real packaging — not a single-file script.

    Required features:

    • POST /users, GET /users (paginated, filterable by query param), GET /users/{id}, PATCH /users/{id}, DELETE /users/{id}.
    • Pydantic models for request/response schemas (separate UserCreate, UserUpdate, UserOut — mirror how you'd separate DTOs in a typed Node API), and an internal @dataclass(frozen=True) domain model that the service layer works with.
    • Async Postgres access (via asyncpg or SQLAlchemy's async engine) — no blocking DB calls inside async route handlers.
    • Dependency-injected DB session/connection per request using FastAPI's Depends.
    • Proper HTTP error mapping (404 on missing user, 409 on duplicate email, 422 validation — FastAPI gives you most of this for free, but you should know why).
    • A pytest suite: unit tests for the dataclass/service logic, integration tests for the routes using httpx.AsyncClient + a test DB or transaction rollback fixture, parametrized edge cases (duplicate email, invalid payload, not-found).
    • Real packaging: pyproject.toml with pinned dependencies, a venv, a README with setup steps, ruff/mypy configured (even if you don't fix every warning).

    Tech stack suggestion: Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2.0 async (or asyncpg directly), Postgres (Docker Compose), pytest + pytest-asyncio + httpx, uv or pip-tools for dependency management.

    Milestones:

    1. Set up the project: venv, pyproject.toml, dependency groups (runtime vs dev/test), directory layout (app/routers, app/models, app/services, app/db, tests/).
    2. Define the Pydantic schemas and the frozen dataclass domain model; write unit tests for any validation/business logic that lives on the dataclass (e.g., an __post_init__ check).
    3. Wire up async DB access and a Depends-based session provider; write the service layer functions (pure async functions, no FastAPI imports — testable in isolation).
    4. Build the five routes on top of the service layer; add exception handlers that translate domain errors (e.g., UserNotFoundError) into HTTP responses.
    5. Write the pytest integration suite against a real (dockerized) Postgres or SQLite-for-tests, with fixtures for app/client/db session and a rollback-per-test strategy.
    6. Add ruff + mypy config, a Makefile or justfile for test/lint/run, and document how this differs from the Express version in a short README section ("what changed and why").

    Evaluation checklist:

    • ☐ No blocking I/O call sits inside an async def route or service function.
    • ☐ Can explain why the dataclass is frozen and what that buys you (vs a plain dict, vs a Pydantic model used for internal logic).
    • ☐ Tests pass in isolation and in any order — no shared mutable DB state leaking between tests.
    • ☐ Can explain FastAPI's dependency injection resolution order and request lifecycle from a cold request to response.
    • ☐ Can articulate, concretely, the single biggest mindset shift from Express to FastAPI (not "Python syntax is different" — something structural, e.g. Pydantic validation at the boundary vs hand-rolled middleware).
