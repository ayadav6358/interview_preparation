    Agent Frameworks, Memory & MCP

    ⏱ ~3 hrs📍 Chapter 12 of 14

    One-line summary: Agent frameworks differ mainly in how much control flow they take away from you (graph-based orchestration vs. simple loops vs. a thin SDK), agent memory is just "which parts of the context window do you persist, summarize, or retrieve, and from where" — and MCP is the thing that stops every team from writing a bespoke integration for every tool-times-model combination.

    On this page

      Why It Matters for a Senior Developer

      By the time you reach this chapter you already know (from chapter 11) that an "agent" is nothing more than an LLM call wrapped in a loop with tools and a stopping condition. The frameworks built on top of that loop are where most teams waste months — either over-adopting a heavyweight graph orchestration framework for a problem that's really just three sequential tool calls, or under-investing in memory architecture and shipping an agent that forgets what it was doing the moment the conversation gets long. Interviewers ask about this precisely because "should we use LangGraph or just write the loop ourselves" and "how do you give an agent persistent memory without blowing the context budget" are real decisions senior engineers make weekly in 2025-26 AI teams. MCP sits underneath all of this as the plumbing standard — not knowing what it actually standardizes (and why it exists) is an immediate signal that your agent experience is shallow.

      Why

      Every agent framework is solving the same underlying problem — "how do I manage state, control flow, and tool access around a model that only ever does next-token prediction" — with different opinions about how much of that should be implicit (a framework's graph engine) versus explicit (your own code). The "right" framework is a tradeoff between flexibility and the amount of machinery you don't have to build yourself, not a popularity contest.

      Core Concepts

      Three shapes of agent framework

      Strip away branding and nearly every agent framework in 2025-26 is one of three underlying shapes:

      • Graph/state-machine orchestration (LangGraph-style) — you define the agent as an explicit directed graph of nodes (each node is a function: call a model, call a tool, branch on a condition) and edges (including conditional edges and cycles). State is a typed object threaded through every node. This buys you: explicit, inspectable control flow; easy branching/looping/parallel sub-graphs; built-in checkpointing (persist state at any node, resume later, "time travel" to an earlier state). The cost: more upfront structure than many agents need, and a learning curve around the graph abstraction itself.
      • Simple loop-based frameworks — a `while` loop: call the model with the current message history and tool definitions, if it returns a tool call execute it and append the result, repeat until it returns a final answer or a stop condition fires. No graph, no nodes — just messages in, tool results appended, loop again. This is what chapter 11's from-scratch agent already is. Frameworks in this category add conveniences (tool-calling boilerplate, retry/error handling, streaming) without taking away your ability to see and modify the loop itself.
      • Thin SDK style (Anthropic Agent SDK style) — the framework gives you the primitives (a model client with native tool-use, a way to register tools, a way to manage a conversation/session) but deliberately does not impose a graph or an opinionated loop structure on top. You write the orchestration logic yourself using building blocks the SDK hands you — closest in spirit to "a really good standard library for building agents" rather than "a framework that owns your control flow."

      The real decision isn't "which framework is best" — it's "how much of my control flow do I want a framework to own." A graph framework is worth its complexity once you have genuine branching/parallel/cyclic workflows (e.g. a multi-agent pipeline with conditional routing and human-in-the-loop checkpoints). A simple loop is usually sufficient — and much easier to debug — for a single agent calling tools until done. A thin SDK is the right call when you need maximum control and are willing to write more of the orchestration yourself, often because your workflow doesn't map cleanly onto anyone else's graph abstraction.

      Memory architectures: short-term vs. long-term

      "Agent memory" is an overloaded term; it collapses into two genuinely different problems:

      • Short-term / working memory — the current conversation's message history, which lives directly in the context window. The problem it creates is purely a budget one: long-running agent sessions accumulate tool-call results, intermediate reasoning, and turns until they exceed the context window or degrade quality via lost-in-the-middle. Mitigations: sliding-window truncation (drop oldest turns), periodic summarization (collapse older turns into a compact summary, keep recent turns verbatim), or explicit "scratchpad" compaction where an agent is instructed to periodically condense its own state.
      • Long-term / persistent memory — information that should survive past the current session: user preferences, facts learned in a previous conversation, prior decisions. This cannot live in the context window by default (it's not there until something puts it there), so it needs an external store plus a retrieval mechanism to pull relevant memories back into context when needed.

      Vector-backed vs. structured long-term memory

      Two dominant patterns for the long-term store, often combined:

      • Vector-store-backed memory — each memory (a fact, an episode, a summarized interaction) is embedded and stored in a vector DB, exactly like RAG document chunks (see chapter 9). At the start of a new turn/session, the current query or context is embedded and used to retrieve the top-k most relevant past memories, which are injected into the prompt. This is good for fuzzy, semantic recall ("has this user ever mentioned a deadline preference") and scales to large memory stores, but inherits every RAG failure mode: retrieval miss, noise, no guarantee of exhaustive recall.
      • Structured memory — memory stored as explicit key-value facts or a small schema (e.g. a `user_profile` JSON object: `{timezone, preferred_language, past_purchases}`), updated via explicit writes (the agent, or a separate extraction step, decides "this is worth remembering" and writes a structured field) rather than dumping raw text into a vector store. This is good for information you need reliably and exhaustively (not "probably retrieved if semantically similar") — things like account settings or hard constraints — but requires upfront schema design and doesn't generalize to arbitrary unstructured facts the way embeddings do.

      Production agent memory systems typically run both: structured memory for a small set of must-always-be-present facts, vector memory for open-ended "might be relevant" recall, with an explicit write step (often an LLM call itself: "did anything in this conversation deserve to be remembered, and in which store") deciding what gets persisted at all — most of a conversation should not become a permanent memory.

      The Model Context Protocol (MCP)

      Before MCP, every team that wanted an LLM to use an external tool (a database, a SaaS API, a file system) wrote a bespoke integration: custom tool-definition JSON, custom request/response glue code, specific to that one model's tool-calling format. Multiply N tools by M different model providers/clients and you get N×M bespoke integrations — the exact problem USB solved for hardware peripherals and ODBC/JDBC solved for databases: a standard interface so tool builders and model/client builders don't each need bespoke knowledge of the other side.

      MCP standardizes three things: (1) how a tool/resource provider (an "MCP server") describes what it offers — tools (callable functions with typed schemas), resources (readable data, like files or query results), and prompts (reusable prompt templates); (2) how a client (an agent host — an IDE, a chat app, your own agent code) discovers and invokes those capabilities over a standard JSON-RPC-based wire protocol; (3) the session/transport layer connecting them (stdio for local processes, HTTP/SSE for remote servers). The result: write one MCP server for "our internal ticketing system" and every MCP-compatible agent host can use it immediately, with no per-host integration code — the N×M problem collapses to N + M.

      How It Works Under the Hood

      An MCP interaction, mechanically, end to end:

      1. Connection & initialization: the client (agent host) establishes a transport connection to the server (spawns a local stdio subprocess, or opens an HTTP/SSE connection to a remote server) and sends an `initialize` request declaring protocol version and client capabilities; the server responds with its own capabilities (which tools/resources/prompts it offers).
      2. Discovery: the client calls `tools/list` (and `resources/list`, `prompts/list`) to get the server's full catalog — each tool described with a name, description, and a JSON Schema for its input parameters, exactly analogous to a model's native tool-use schema.
      3. Exposure to the model: the client translates the MCP tool catalog into whatever tool-definition format the underlying LLM's API expects (e.g. Anthropic's `tools` parameter) and includes it in the model call — this is the layer that makes MCP model-agnostic: the server never needs to know which model is on the other end.
      4. Invocation: when the model emits a tool-call matching an MCP tool, the client sends a `tools/call` request to the MCP server with the tool name and arguments; the server executes (hits a real database, calls a real API, reads a real file) and returns a structured result (text, or a richer content type like an image or an embedded resource).
      5. Result round-trip: the client appends the tool result to the conversation and loops back into the model exactly as in the chapter 11 agent loop — MCP governs only the tool-discovery and tool-execution plumbing, not the agent's reasoning loop itself.

def get_ticket(ticket_id: str) -> dict:
    """Fetch a support ticket by ID, including status and last update."""
    # In production: real DB/API call. Kept trivial here for illustration.
    return {"id": ticket_id, "status": "open", "last_update": "2026-09-30"}

@mcp.tool()

# --- Structured + vector long-term memory, combined write-time decision ---
import json

class AgentMemory:
    def __init__(self, vector_store, llm_client):
        self.vector_store = vector_store      # semantic recall store
        self.structured = {}                  # must-always-be-present facts
        self.llm = llm_client

    def maybe_persist(self, conversation_turn: str, user_id: str):
        """Ask a cheap model call to classify what (if anything) is worth
        remembering, and route it to the right store. Most turns persist nothing."""
        decision = self.llm.classify_memory_worthiness(conversation_turn)
        if decision.kind == "structured_fact":
            # e.g. {"timezone": "IST"} -- exact, must always be present
            self.structured.setdefault(user_id, {}).update(decision.fields)
        elif decision.kind == "episodic":
            # fuzzy, semantically-searchable recall
            self.vector_store.upsert(
                text=decision.summary,
                metadata={"user_id": user_id, "ts": decision.timestamp},
            )
        # else: nothing worth persisting -- the common case

    def recall(self, query: str, user_id: str, k: int = 5) -> str:
        structured = self.structured.get(user_id, {})
        episodic = self.vector_store.search(query, filter={"user_id": user_id}, top_k=k)
        return f"Known facts: {json.dumps(structured)}\nRelevant past context: {episodic}"


# BAD: dumping the entire raw conversation history into a vector store every turn.
# Floods recall with noise, inflates storage, and makes "what does the agent actually
# know about this user" unanswerable without re-reading hundreds of raw snippets.
def bad_persist_everything(vector_store, full_transcript, user_id):
    vector_store.upsert(text=full_transcript, metadata={"user_id": user_id})

      Real-World Production Scenario at Scale

      At scale

      A team builds a customer-support agent that integrates 6 internal tools (ticketing, billing, user lookup, refund processing, knowledge base, escalation) directly against their chat product's own tool-calling API. Six months later, leadership wants the same tools usable from an internal Slack bot and a separate ops dashboard agent — meaning two more bespoke integrations against the same six tools, each with its own auth handling and schema translation bugs. The team migrates the six tools to MCP servers (one server per internal system, each exposing its existing tools unchanged) and both new surfaces become MCP clients — zero additional tool-integration code, only host-side wiring. The real payoff shows up a year later when a 7th tool (a fraud-detection lookup) is added once, as one more MCP server, and is immediately available to all three existing hosts plus a brand-new agent nobody had planned for yet.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Reaching for a graph-orchestration framework (LangGraph-style) on day one for an agent that's really just "call tools in a loop until done." The graph abstraction adds real value once you have genuine branching, parallel sub-agents, or need checkpoint/resume — but for a single linear agent it adds a learning curve and an extra layer of indirection between you and the actual message history, which is often exactly what you need to see clearly while debugging.

      Gotcha

      Treating vector-backed memory as exhaustive recall. "The agent should remember the user said X three weeks ago" is a reasonable expectation for structured memory (explicit, guaranteed) but an unreliable one for vector memory (probabilistic retrieval, subject to the exact same miss/noise failure modes as RAG). Teams that rely solely on embedding similarity for must-not-forget facts will intermittently "forget" them the moment phrasing drifts enough to drop below the retrieval threshold.

      • Persist memory selectively (an explicit write decision), not by default — most conversation turns contain nothing worth remembering long-term, and persisting everything degrades retrieval quality.
      • An MCP server should never assume which model is calling it — keep tool descriptions and schemas self-contained and model-agnostic, since the same server may serve Claude, GPT, or a local model.
      • Budget short-term memory (summarize/truncate) proactively on long-running agent sessions rather than discovering the context-window ceiling in production when a session finally fails.

      Interview Questions

      Basic

      What are the three broad "shapes" of agent framework, and what's the core axis they differ on?

      Graph/state-machine orchestration, simple loop-based frameworks, and thin SDKs. The core axis is how much control flow the framework takes away from you versus leaves in your own code — a graph framework owns the most, a thin SDK the least.

      Follow-up: which shape is closest to the from-scratch agent loop built in the previous chapter?
      What's the difference between short-term and long-term agent memory?

      Short-term/working memory is the current conversation's message history living directly in the context window, limited by context budget. Long-term/persistent memory is information meant to survive past the current session, which requires an external store plus a retrieval mechanism since it isn't automatically in context.

      Follow-up: name one mitigation for short-term memory running out of context budget.
      What problem does MCP solve, in one sentence?

      It standardizes how tools/data sources describe and expose themselves and how agent hosts discover and invoke them, collapsing the N tools times M models/clients bespoke-integration problem down to N + M.

      Follow-up: name the three kinds of capability an MCP server can expose.
      What are the two dominant patterns for long-term memory storage?

      Vector-store-backed memory (embed and semantically retrieve past facts/episodes, like RAG) and structured memory (explicit key-value facts in a defined schema, written and read exactly, not retrieved by similarity).

      Follow-up: which pattern would you use for "the user's timezone" versus "something the user mentioned once in passing"?
      In the MCP protocol flow, what's the purpose of the `tools/list` call?

      It lets the client discover the server's full tool catalog — names, descriptions, and JSON Schema input definitions — before translating that catalog into whatever tool-definition format the underlying model's API expects.

      Follow-up: why does the MCP server not need to know which specific LLM is on the other end of the connection?
      Why would a team choose a simple loop-based framework over a graph orchestration framework for a basic single-agent tool-use workflow?

      A simple loop is easier to read, debug, and reason about for linear tool-calling workflows — the graph abstraction's value (explicit branching, cycles, checkpoint/resume) isn't needed when there's no real branching, so adopting it just adds an extra layer of indirection with no payoff.

      Follow-up: at what point does that calculus flip in favor of a graph framework?

      Medium

      Explain mechanically what happens between a model emitting a tool-call and an MCP server returning a result.

      The client (agent host) receives the model's tool-call (name + arguments) and translates it into an MCP `tools/call` request sent to the appropriate MCP server over the established transport (stdio or HTTP/SSE). The server executes the real action (DB query, API call, file read) and returns a structured result back to the client, which appends it to the conversation and loops back into the model — MCP governs the discovery/invocation plumbing between client and server; the agent's own reasoning loop (chapter 11) is unchanged by MCP's presence.

      Follow-up: at what point in this flow does model-agnosticism actually happen?
      Why can't you rely solely on vector-backed memory for information an agent must never forget?

      Vector memory retrieval is probabilistic and similarity-based — it inherits RAG's exact failure modes (retrieval miss if phrasing drifts too far from how the fact was originally stored, noise from unrelated-but-similar memories). A fact the system is relying on being present 100% of the time needs a guaranteed-present mechanism: structured, explicitly-keyed storage read deterministically, not a "probably comes back if semantically close enough" lookup.

      Follow-up: how would you decide, for a new piece of information an agent learns, which store it belongs in?
      Why does checkpointing matter more for graph-based agent frameworks than for simple loop-based ones?

      A graph framework's explicit, typed state object threaded through named nodes gives you a natural unit to serialize and resume from — "resume from node X with this state." A simple loop's state is often just a flat message list, which can technically be checkpointed too, but graph frameworks build this in as a first-class feature because their structured state representation makes partial-resume, branching-resume, and "time travel" debugging tractable in a way an undifferentiated message list doesn't as cleanly support.

      Follow-up: what's a concrete scenario where resuming from a mid-graph checkpoint (rather than restarting the whole run) matters in production?
      What's the risk of writing every conversation turn into long-term memory by default, even when using a good vector store?

      It floods the memory store with low-signal content, which dilutes retrieval quality (more candidates to search through, more near-duplicate or irrelevant memories competing for top-k slots) and makes the system's effective "what does it actually know" unauditable without reading through a huge volume of raw snippets. An explicit write-time relevance decision keeps the memory store a curated signal rather than a transcript dump.

      Follow-up: who or what should make that write-time decision — the main agent itself, or a separate classification step? What are the tradeoffs?
      How does MCP's transport choice (stdio vs. HTTP/SSE) map to different deployment scenarios?

      stdio is used when the MCP server runs as a local subprocess alongside the client (e.g. a tool that reads local files or runs local commands) — the client spawns it directly and communicates over its stdin/stdout. HTTP/SSE is used for remote servers (a shared internal tool server, a SaaS-hosted MCP endpoint) that multiple clients across machines need to reach over a network, supporting the same discovery/invocation protocol over a network-appropriate transport.

      Follow-up: what security considerations change when moving from a local stdio server to a remote HTTP one?

      Advanced

      Design the memory architecture for a long-running personal-assistant agent that needs to recall both exact facts (user's preferred meeting times) and fuzzy context (general tone/preferences from past conversations), while keeping cost and latency bounded as memory grows over months.

      Split into structured memory for exact, bounded-size facts (meeting time preferences, hard constraints) read deterministically on every session with negligible cost, and vector-backed episodic memory for fuzzy context, retrieved only the top-k most relevant items per query rather than growing unboundedly in the prompt. Add a write-time classification step (cheap, fast model call) that decides per-turn whether anything is worth persisting and to which store, keeping the vector store's growth proportional to genuinely novel information rather than raw conversation volume. Periodically run a consolidation/summarization pass over episodic memory (collapsing many old similar entries into fewer summary entries) to bound both storage growth and retrieval latency as months of history accumulate, analogous to garbage collection for memory that's still occasionally useful but no longer needs full-fidelity storage.

      Follow-up: how would you test that consolidation isn't silently discarding information that later turns out to matter?
      A team wants to expose 10 internal tools to 4 different internal agent products. Walk through why MCP is the right call here versus bespoke integrations, and what the migration actually involves.

      Without MCP this is 10×4 = 40 potential bespoke integration paths (each product's tool-calling format against each tool's API), with auth, schema translation, and error handling duplicated and drifting independently across all 40. With MCP, each of the 10 tools becomes one MCP server (unchanged underlying logic, just wrapped with MCP's tool/resource exposure), and each of the 4 products becomes one MCP client implementation — reducing bespoke work to roughly 10 + 4 = 14 integration points, with any new 11th tool or 5th product adding only 1 more unit of work instead of 4 or 10. Migration mechanically involves: wrapping each tool's existing logic in an MCP server (`tools/list`-discoverable, `tools/call`-invokable), standing up transport (stdio for same-host, HTTP/SSE for shared/remote), and updating each product to be a generic MCP client rather than hardcoding tool-specific logic.

      Follow-up: what doesn't MCP solve here — i.e. what integration work remains even after the migration?
      When would you justify building a custom graph-orchestration layer in-house rather than adopting an existing framework like LangGraph, for a senior team with real engineering capacity?

      Justified when your control-flow needs are genuinely specific enough that an existing framework's abstraction fights you more than it helps — e.g. a workflow with domain-specific scheduling/priority semantics across sub-agents that doesn't map cleanly onto a generic node/edge graph, or hard requirements (specific checkpoint storage backend, specific observability integration, specific latency characteristics) that an off-the-shelf framework doesn't support without heavy forking. Not justified merely because "we want full control" in the abstract — that's a maintenance burden (reinventing checkpointing, state management, error handling) without a corresponding need the existing framework actually fails to meet. The honest test: can you point to a concrete scenario the existing framework's graph model cannot express, versus "we'd just prefer to own it"?

      Follow-up: what's a middle path between "adopt wholesale" and "build from scratch" that captures most of the benefit of each?
      How would you debug an agent whose long-term memory retrieval is returning technically-relevant-looking but ultimately unhelpful memories, degrading answer quality over time as the memory store grows?

      First separate it into the same retrieval-vs-generation decomposition used for RAG (chapter 9): is the memory store actually surfacing the right memories at all (measure recall against a labeled set of "this query should retrieve that memory" pairs), or is retrieval fine but the agent is using retrieved memories poorly in generation? If it's a retrieval problem, suspect memory store growth diluting relevance — stale, redundant, or overly granular memories crowding out signal — and investigate whether a consolidation/summarization pass or stricter write-time filtering (only persisting genuinely novel, high-value facts) would reduce noise. If retrieval is accurate but generation quality still degrades, check whether the agent is being handed too many memories per turn (its own lost-in-the-middle problem) rather than the most load-bearing few.

      Follow-up: how would you build a regression test that catches this kind of memory-quality degradation before it reaches users, analogous to a RAG eval harness?
      What are the security implications of an agent host connecting to a third-party MCP server it doesn't control, and how would you mitigate them?

      A third-party MCP server is effectively untrusted code/infrastructure the agent will call with real arguments and receive real results from — a malicious or compromised server could return crafted results designed to manipulate the agent's downstream reasoning (prompt-injection-via-tool-result), exfiltrate data passed as tool arguments, or simply misbehave. Mitigations: treat MCP tool results as untrusted input requiring the same scrutiny as any other external data the model consumes (don't blindly trust/execute follow-on instructions embedded in a tool result), scope what arguments/credentials are ever sent to third-party servers (least privilege, scoped tokens rather than broad API keys), and prefer vetted/first-party servers for anything touching sensitive data, treating unvetted third-party MCP servers similarly to an unvetted npm package in a supply chain.

      Follow-up: how is this risk similar to, and different from, the prompt-injection risk already present in RAG-retrieved documents?

      Practice Assignments

      Beginner (30-60 min)

      Loop vs. graph, on paper

      Take an agent workflow you've designed or used (even a hypothetical one — e.g. "research a topic, draft a summary, have a second pass fact-check it, revise if issues found") and sketch it twice: once as a simple linear loop (pseudocode), once as an explicit graph with nodes and conditional edges.

      • Identify at least one point in the workflow where the graph version's explicit branching/cycling genuinely simplifies something the loop version has to handle awkwardly with if/else and flags.

      Acceptance criteria: both sketches written out, plus a short written judgment on which you'd actually ship for this specific workflow and why.

      Hints

      The fact-check-and-revise loop is a good place to look — it's a cycle with a conditional exit, which is exactly where graph frameworks are designed to shine.

      Bonus: add a human-in-the-loop checkpoint to the graph version and describe what state would need to be persisted to support resuming after a human approves.

      Intermediate (2-4 hrs)

      Build a minimal MCP server and connect a client to it

      Using the official MCP SDK (Python or TypeScript), build an MCP server exposing 2-3 real tools (not toy stubs — e.g. read a local file, query a small local SQLite DB, call a public API). Connect it to an MCP-compatible client/host and run a real multi-step interaction through it.

      • Demonstrate the `tools/list` discovery step and show the translated tool schema the client builds for the underlying model.
      • Run at least one interaction where the model chains two of your tools (output of one informs the call to the next).

      Acceptance criteria: working server + client session transcript showing discovery, at least one multi-tool chain, and the raw `tools/call` request/response pairs.

      Hints

      Start from the official MCP SDK's quickstart example server and modify its tools rather than writing the protocol handling yourself — the protocol plumbing is the part not worth reinventing for this exercise.

      Bonus: add a resource (not just a tool) to your server and show the client reading it.

      Advanced (1-2 days)

      Hybrid memory system with write-time filtering

      Build an agent with a hybrid memory system: structured memory for a small fixed schema of must-always-be-present facts, vector-backed memory for open-ended episodic recall, and an explicit write-time classification step deciding what gets persisted where (or discarded) after each turn.

      • Run a 20+ turn synthetic conversation covering a mix of trivial small talk, exact facts worth remembering, and fuzzy preferences.
      • Measure: what fraction of turns got persisted at all, and to which store.
      • Build 10 recall queries and check whether structured facts come back deterministically (100%) and whether episodic recall's precision/recall is measurably reasonable (reuse your RAG eval approach from chapter 9).

      Acceptance criteria: working hybrid memory system, persistence-rate report, and a recall eval table comparing structured vs. episodic accuracy.

      Hints

      Keep the write-time classifier's prompt strict (ask for a JSON decision: discard / structured-field / episodic-summary) so you can measure persistence rate programmatically instead of eyeballing transcripts.

      Bonus: add a consolidation pass that runs after the 20 turns and collapses near-duplicate episodic memories, then re-run your recall eval and report whether precision improved.

      Quick Revision Cheat Sheet

      • Three framework shapes: graph orchestration (explicit control flow, checkpointing), simple loop (easiest to debug), thin SDK (max control, most DIY).
      • Pick graph frameworks for real branching/cycles/parallel sub-agents; a simple loop is usually enough otherwise.
      • Short-term memory = context window budget problem (truncate/summarize); long-term memory = needs an external store + retrieval.
      • Vector memory = fuzzy, probabilistic, scalable recall. Structured memory = exact, guaranteed, must be schema-designed.
      • Persist memory selectively via an explicit write-time decision — most turns deserve to be forgotten.
      • MCP standardizes tool/resource/prompt exposure + discovery + invocation, collapsing N tools × M models into N + M.
      • MCP flow: initialize → tools/list (discovery) → model call with translated schema → tools/call (invocation) → result appended, loop continues.
      • MCP servers are model-agnostic by design — never bake assumptions about which LLM is calling into the server.
      • Treat third-party MCP tool results as untrusted input — same prompt-injection discipline as RAG-retrieved documents.
