    HuggingFace Ecosystem

    ⏱ ~2.5 hrs📍 Chapter 7 of 14

    One-line summary: HuggingFace turned "download a pretrained transformer and run it" from a research-lab-only capability into a few lines of standard Python — but using it well still requires understanding tokenization deeply, because most of the "weird LLM behavior" developers run into traces directly back to how text gets converted into tokens in the first place.

    On this page

      Why It Matters for a Senior Developer

      Almost every production ML/NLP feature you'll touch as a senior engineer outside of a dedicated ML team — running a local embedding model, fine-tuning a small classifier, serving an open-weight LLM instead of a hosted API — goes through the HuggingFace ecosystem (transformers, datasets, the Hub). It's also where the theory from the last two chapters becomes runnable: AutoModel is quite literally loading the attention/transformer-block architecture from chapter 6 with pretrained weights. Separately, tokenization is one of those topics that looks like a minor preprocessing detail but actually explains several LLM behaviors that otherwise look like unexplainable bugs — bad arithmetic, inconsistent behavior on rare words, odd sensitivity to whitespace — all trace back to how the tokenizer segments text, and being able to explain that mechanism is a strong signal of real understanding.

      Why

      A model never sees raw text — it sees a sequence of integer token IDs, produced by a tokenizer trained separately from the model itself on a large text corpus to find a vocabulary of frequently-reused subword pieces. Every property of that tokenizer (what counts as one token, how numbers get split, whether whitespace is preserved) becomes a hard constraint on what the model can represent efficiently — the model's "intuitions" about language are downstream of the tokenizer's segmentation choices just as much as they're downstream of training data.

      Prerequisites

      Requires Attention & Transformers (this chapter is the practical, runnable counterpart to that architecture) and basic PyTorch & Tensors. For the applied, production-serving angle (prompting, cost, latency), see AI Integration: How LLMs Work.

      Core Concepts

      The transformers library: AutoModel, AutoTokenizer, pipelines

      The transformers library's core abstraction is the "Auto" class pattern: AutoTokenizer .from_pretrained("model-name") and AutoModel.from_pretrained("model-name") inspect the model's config on the Hub and automatically instantiate the correct tokenizer/model class (BERT, GPT-2, Llama, etc.) without you needing to know which specific class to import. Task-specific variants (AutoModelForSequenceClassification, AutoModelForCausalLM, AutoModelForQuestionAnswering) attach the right task-specific head on top of the base transformer body. For the fastest path to a working result, pipeline("task-name", model=...) wraps tokenization, model inference, and post-processing into one callable — the right tool for quick prototyping or simple production use cases, though production systems eventually drop down to the model/tokenizer level directly for control over batching, caching, and output format.

      The datasets library and the Hub

      The datasets library provides a standard, memory-efficient (via Apache Arrow and memory- mapping, so datasets far larger than RAM can be processed without loading everything into memory at once) interface for loading, transforming, and streaming datasets — both from the Hub and from local files. The Hub itself is the ecosystem's central registry: models (pretrained weights plus config/tokenizer files, versioned and tagged with task/license metadata), datasets (similarly versioned, with dataset cards describing provenance and intended use), and Spaces (hosted demo apps, usually Gradio or Streamlit, that let you try a model interactively before committing to integrating it). Treat the Hub the way you'd treat a package registry like npm: check the model card for license terms, intended use, and known limitations before pulling a model into a production system, not just the benchmark numbers on the leaderboard.

      Tokenization deep dive: BPE, WordPiece, special tokens, and why it causes weird behavior

      Modern tokenizers don't split on whitespace or use a fixed word-level vocabulary (which would explode in size and still fail on unseen words) — they use subword tokenization, built by an algorithm that finds a fixed-size vocabulary (e.g. 32k-100k+ entries) of frequently-recurring character sequences from a large training corpus:

      • BPE (Byte-Pair Encoding) — starts with individual characters/bytes, then iteratively merges the most frequent adjacent pair into a new single token, repeating until the target vocabulary size is reached. Common words end up as a single token; rare or unseen words get split into multiple smaller subword pieces (or, worst case, individual bytes), so the tokenizer never truly fails on out-of-vocabulary input — it just degrades gracefully into more, smaller tokens. GPT-family models use byte-level BPE specifically (operating on raw UTF-8 bytes, not characters), which guarantees any possible input string is representable.
      • WordPiece (BERT) — similar iterative-merge idea, but picks merges based on a likelihood criterion rather than raw frequency, and marks subword continuation pieces with a special prefix (##ing for a continuation that isn't a standalone word start).
      • Special tokens — reserved vocabulary entries with specific structural roles: [CLS]/<s> (sequence start, often used as the pooled representation for classification), [SEP]/</s> (sequence separator/end), [PAD] (padding shorter sequences to a uniform batch length — critically, paired with an attention mask so the model ignores padded positions), [UNK] (rare, used when a piece genuinely can't be represented, uncommon with byte-level BPE). Chat-tuned models add further special tokens marking turn boundaries and roles (e.g. <|im_start|>user) that the model was specifically trained to recognize as structural, not literal text.

      Why tokenization causes "weird" LLM behavior: the model never sees individual digits or characters the way a human reading the text does — it sees whatever chunks the tokenizer happened to split the input into, and those chunks are optimized for compression efficiency, not for arithmetic or spelling. A number like "48219" might be tokenized as a single opaque token, or split as "482"+"19", or "4"+"82"+"19" — inconsistently, depending on surrounding digits and what happened to be frequent in the training corpus — which is a major reason LLMs are unreliable at multi-digit arithmetic: the model isn't manipulating individual digit symbols the way a human (or a calculator) does, it's pattern-matching over whatever arbitrary digit-groupings its tokenizer produced, and the grouping for "482+19" may bear no clean relation to the grouping for "48219" elsewhere. Similarly, a model can struggle with letter-level tasks (e.g. "how many letters are in this word") because a whole word is often a single token with no exposed internal character structure — the model would have to have memorized the spelling as a side effect of training, not derive it compositionally the way it can for most semantic tasks.

      Loading and running a pretrained model locally

      Beyond calling pipeline(), running a model directly gives you control over tokenization details, batching, device placement, and output format — necessary for anything beyond a quick demo. Key practical details: move both model and input tensors to the same device explicitly (GPU mismatches are a common first error), use torch.no_grad() (or model.eval() plus no-grad) for inference to skip gradient tracking and cut memory usage, and pay attention to dtype (loading in float16/bfloat16 instead of the default float32 roughly halves memory for a modest, often negligible, accuracy cost — standard practice for any model beyond toy size).

      How It Works Under the Hood

      What actually happens when you call AutoModel.from_pretrained("bert-base-uncased"): the library resolves the model name to a Hub repository, downloads (and caches locally, usually under ~/.cache/huggingface) the config JSON (architecture hyperparameters: layer count, hidden size, number of heads, etc.), the tokenizer files (vocabulary, merge rules, special token definitions), and the model weights (typically safetensors format now, a safer and faster alternative to Python's pickle-based .bin format). It reads the config to determine which concrete model class to instantiate (resolving the "Auto" indirection), builds that architecture with randomly initialized weights, then loads the downloaded weights into it by matching parameter names. Tokenization at call time runs the loaded vocabulary/merge rules against your input string, producing token IDs plus an attention mask (and token type IDs, for models that need them), which are then fed as input tensors to the model's forward pass — the exact attention/transformer-block computation from the previous chapter, just with real pretrained weights instead of random initialization.

      Code Examples

      from transformers import AutoTokenizer, AutoModel, AutoModelForSequenceClassification, pipeline
import torch

# Quick prototyping path: pipeline wraps tokenize -> model -> post-process.
classifier = pipeline("sentiment-analysis", model="distilbert-base-uncased-finetuned-sst-2-english")
print(classifier("This architecture finally makes sense."))
# [{'label': 'POSITIVE', 'score': 0.999...}]

# Direct model/tokenizer path, for production control over batching and output.
model_name = "bert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModel.from_pretrained(model_name)
model.eval()

device = "cuda" if torch.cuda.is_available() else "cpu"
model.to(device)

texts = ["Attention computes relevance.", "Tokenizers segment text into subwords."]
inputs = tokenizer(texts, padding=True, truncation=True, return_tensors="pt").to(device)

with torch.no_grad():
    outputs = model(**inputs)

# outputs.last_hidden_state: (batch, seq_len, hidden_dim) — per-token contextual embeddings.
# A common pooling choice for a single sentence embedding: mean-pool over non-padded tokens.
mask = inputs["attention_mask"].unsqueeze(-1)
sentence_embeddings = (outputs.last_hidden_state * mask).sum(1) / mask.sum(1)
print(sentence_embeddings.shape)   # (2, 768)

# Demonstrating tokenization's inconsistent digit-splitting behavior directly.
for number in ["482", "48219", "482190000"]:
    ids = tokenizer.encode(number, add_special_tokens=False)
    print(number, "->", tokenizer.convert_ids_to_tokens(ids))
# Notice the split points are NOT a clean, consistent "one token per digit" or
# "one token per 3 digits" rule -- they're whatever the BPE/WordPiece training corpus
# happened to find frequent, which is exactly why multi-digit arithmetic is unreliable.

# BAD: forgetting the attention mask when pooling -- padded positions leak into the average.
bad_embeddings = outputs.last_hidden_state.mean(dim=1)   # includes padding tokens, biased toward shorter inputs' padding

# GOOD: mask-aware pooling, shown above as sentence_embeddings.

      Real-World Production Scenario at Scale

      At scale

      A fintech team builds an internal tool that extracts transaction amounts from free-text expense descriptions using a fine-tuned HuggingFace model, and QA flags that the model occasionally transposes or mis-groups digits in longer amounts (e.g. confusing "$482,190.00" with a similarly-tokenized but different number). Investigation traces it to tokenization: large numbers get split into inconsistent subword chunks depending on surrounding punctuation and digit count, so the model was never seeing a clean, consistent digit-by-digit representation to learn reliable arithmetic-adjacent behavior from — the model was pattern-matching over somewhat arbitrary token boundaries. The fix wasn't more training data; it was a pre-processing step that normalizes amounts into a consistent character- spaced format before tokenization (forcing a predictable split) for this specific numeric-extraction task, plus validating extracted numbers against a regex-based sanity check downstream rather than trusting the model's digit-level output unconditionally. This is a direct, production-grade illustration of why tokenization mechanics aren't just theoretical trivia — they determine what a model can and can't reliably do with certain input classes.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting padding=True plus relying on the attention mask when batching variable-length inputs — without it, shorter sequences get silently truncated or batching fails outright; and if you pool/average embeddings without masking out padded positions, the result is systematically biased by how much padding each example received.

      Gotcha

      Loading a model without checking whether it's an encoder, a decoder, or encoder-decoder, and then calling the wrong generation/inference API for its architecture — an encoder-only model like BERT has no generate() method and isn't built for open-ended text generation; using AutoModelForCausalLM versus AutoModel versus AutoModelForSequenceClassification matters and isn't interchangeable.

      • Always check the model card on the Hub for license terms before using a model in a commercial product — not all "open" models permit commercial use without restriction.
      • Prefer safetensors-format weights over legacy pickle-based .bin files where available — pickle deserialization can execute arbitrary code, a real supply-chain risk when loading third-party model weights.
      • Use float16/bfloat16 and device_map="auto" (via accelerate) for any model beyond toy size, rather than defaulting to full float32 on CPU and wondering why it's slow or won't fit in memory.
      • Pin exact model/tokenizer revisions (a commit hash or tag, not just the model name) in production — a model's default branch on the Hub can be updated by its maintainer, silently changing behavior under you if you don't pin a version.

      Interview Questions

      Basic

      What's the difference between AutoModel and AutoModelForSequenceClassification?

      AutoModel loads just the base transformer body (producing contextual hidden states); AutoModelForSequenceClassification loads the same base body plus a task-specific classification head on top, and expects/produces label-indexed logits rather than raw hidden states.

      Follow-up: what would you use if you wanted raw sentence embeddings instead of a classification?
      What does `pipeline()` do, and when would you choose it over calling the model directly?

      It bundles tokenization, model inference, and output post-processing into one callable for a given task. Good for quick prototyping or simple single-task production use; direct model/tokenizer calls are preferred when you need control over batching, device placement, or custom output handling.

      Follow-up: what's one downside of relying on pipeline() in a high-throughput production system?
      Why can't a tokenizer just split text on whitespace into a fixed word-level vocabulary?

      A word-level vocabulary would need to be enormous to cover all possible words and would still fail entirely on any word not seen during vocabulary construction (out-of-vocabulary). Subword tokenization (BPE, WordPiece) instead builds a smaller fixed vocabulary of frequent subword pieces, so any input can be represented by combining pieces, degrading gracefully rather than failing on unseen words.

      Follow-up: what happens to a genuinely rare or invented word under BPE?
      What is the attention mask for, in practical terms?

      It marks which positions in a padded, batched input are real tokens (1) versus padding added to make sequences a uniform length (0), so the model's attention computation ignores the padded positions rather than treating them as real content.

      Follow-up: what goes wrong if you pool/average embeddings without respecting the attention mask?
      What is the HuggingFace Hub, roughly?

      A central, versioned registry of pretrained models, datasets, and hosted demo apps (Spaces), each with metadata (license, task, model card) — functionally similar to a package registry like npm, but for ML artifacts.

      Follow-up: what should you check on a model's card before using it in a commercial product?
      Name one reason LLMs are often unreliable at multi-digit arithmetic that relates specifically to tokenization.

      Numbers aren't tokenized consistently digit-by-digit — a given number may be split into different, somewhat arbitrary subword chunks depending on its length and surrounding context, so the model is pattern-matching over inconsistent groupings rather than manipulating individual digit symbols the way a calculator or a human doing arithmetic would.

      Follow-up: would this issue be fixed by more training data alone? Why or why not?

      Medium

      Explain the core algorithmic idea behind Byte-Pair Encoding (BPE) tokenizer training.

      Starting from individual characters/bytes as the initial vocabulary, BPE repeatedly finds the most frequent adjacent pair of existing vocabulary units in the training corpus and merges them into one new unit, adding it to the vocabulary. This repeats until the target vocabulary size is reached. The result is a vocabulary where common words/subwords end up as single tokens (having been merged early and often) while rare sequences remain split into smaller, more primitive pieces.

      Follow-up: why does byte-level BPE (operating on raw bytes rather than characters) guarantee any input string is representable?
      Why must model and input tensors be on the same device, and what's the common failure mode when they aren't?

      PyTorch operations require all operand tensors to reside in the same memory space (CPU RAM or a specific GPU's memory) to execute the underlying kernel; mismatched devices raise a runtime error rather than silently working or auto-transferring. The common failure is loading a model with `.to("cuda")` but forgetting to move the tokenizer's output tensors to the same device, producing a device-mismatch error at the first forward pass.

      Follow-up: what utility (from the `accelerate` library) helps avoid manually managing this for large models split across multiple devices?
      Why is `float16`/`bfloat16` generally safe for inference but riskier for training, and why does bfloat16 differ from float16 in that respect?

      Inference doesn't accumulate gradients over many update steps, so reduced numerical precision has limited opportunity to compound into instability — a small per-step precision loss mostly just slightly perturbs the output. Training accumulates small numerical errors over many steps and relies on well-behaved gradient magnitudes; float16's narrow dynamic range makes gradient underflow/overflow more likely during training specifically, whereas bfloat16 keeps float32's exponent range (same number of exponent bits) with reduced mantissa precision, giving it much better numerical stability for training despite being lower precision than float32.

      Follow-up: why is float16 still commonly fine for inference despite this training-time instability risk?
      Why does pinning an exact model revision (commit hash) matter for a production system, beyond just reproducibility?

      A model repository's default branch/tag on the Hub can be updated by its maintainer (new weights, a bug fix, a different default config) without any action on your part; if your code loads by name without a pinned revision, a production system can silently start using different weights or behavior after a maintainer's update — a correctness and stability risk that's entirely outside your own deploy process's visibility.

      Follow-up: how would you detect, after the fact, that a silent model update had caused a production regression?
      Why is loading third-party pickle-based (.bin) model weights a supply-chain security concern, and how does safetensors address it?

      Python's pickle format can embed and execute arbitrary code during deserialization — loading an untrusted .bin checkpoint is functionally similar to running untrusted code, not just loading data. Safetensors is a format designed to store only raw tensor data with no executable payload, so loading a safetensors file cannot trigger arbitrary code execution regardless of what a malicious uploader embedded, making it the safer default for third-party Hub weights.

      Follow-up: would you still fully trust a safetensors file from an unknown, unverified Hub account? What else would you check?

      Advanced

      Design a preprocessing strategy for a numeric-extraction task (e.g. extracting dollar amounts from free text) that mitigates tokenization-driven digit-grouping inconsistency, without retraining the base model's tokenizer.

      Normalize numeric substrings into a consistent, tokenizer-friendly format before they reach the model — e.g. inserting consistent separators (spaces between digit groups, or between every digit) so the same BPE merge rules apply predictably regardless of the number's length or surrounding punctuation, effectively forcing a stable, learnable tokenization pattern for numbers specifically. Pair this with downstream validation (regex-based sanity checks, or a secondary deterministic parser) on the model's numeric output rather than trusting raw generated/extracted digits unconditionally, since no amount of input normalization makes a transformer a reliable calculator.

      Follow-up: why might retraining or extending the tokenizer's vocabulary specifically for digits be a more robust (but costlier) fix than input normalization alone?
      You need to fine-tune a HuggingFace model on a domain with significant vocabulary not well-represented in the base tokenizer (e.g. heavy chemical compound names). What are your options, and what are the tradeoffs?

      Option 1: use the existing tokenizer as-is — domain terms get split into many small subword pieces, which still works but is less token-efficient and may dilute the signal for distinctive domain terms across multiple arbitrary pieces. Option 2: extend the tokenizer's vocabulary with new domain-specific tokens (resizing the model's embedding matrix to match, with new embeddings initialized randomly or from an average of existing ones) before fine-tuning, giving the model single-token representations for important domain terms, at the cost of needing enough domain fine-tuning data for those new embeddings to be learned well (an undertrained new embedding can introduce noise rather than help). Option 3: train a fully new domain-specific tokenizer and model from scratch, which guarantees efficient domain coverage but discards all benefit of the base model's general pretraining — usually only justified at very large domain-data scale.

      Follow-up: how would you decide, practically, whether Option 2's new-token-embedding approach has actually been learned well versus just adding noise?
      Explain how you'd debug a production HuggingFace model deployment where inference latency spikes intermittently under load, walking through the likely causes in order of investigation.

      First check batching behavior — dynamic/naive batching under variable load can produce inconsistent batch sizes and padding amounts, and padding to the longest sequence in a batch means one unusually long request can inflate compute for an entire batch of otherwise-short requests; check whether a request-bucketing or length-based batching strategy is in place. Second, check for GPU memory fragmentation or contention from concurrent model instances/requests sharing a device without proper queuing. Third, check whether KV-cache memory growth (for generative models, from chapter 6) is causing memory pressure that triggers slower fallback paths or OOM-adjacent GC behavior under sustained load. Only after ruling these out would raw model size/compute be the suspect, since it would typically produce consistent, not intermittent, latency.

      Follow-up: what specific metric would you instrument to distinguish "padding-driven batch inflation" from "KV-cache memory pressure" as the root cause?
      Compare WordPiece and BPE's merge-selection criteria and explain a concrete scenario where this difference would produce different tokenizations for the same input.

      BPE merges the most frequent adjacent pair by raw co-occurrence count; WordPiece merges the pair that maximizes the likelihood of the training corpus under a language-model-like scoring criterion (effectively favoring merges that are more "informative" relative to their individual-piece frequencies, not just frequent as a pair). For a word where two subpieces are individually very common (each appearing in many other contexts) but their specific combination is only moderately frequent, BPE might merge them earlier (driven by raw pair frequency) than WordPiece would, since WordPiece's likelihood criterion can be less swayed by raw frequency if the combined piece doesn't add corpus-likelihood benefit over keeping them separate.

      Follow-up: in practice, does this difference in merge criteria have a large practical effect on downstream task performance, or is it mostly a minor historical implementation difference?
      You're serving a fine-tuned model via HuggingFace in production and need to support hot-swapping between several fine-tuned variants of the same base model with minimal memory overhead. What approach would you use, and why?

      Use parameter-efficient fine-tuning (e.g. LoRA — Low-Rank Adaptation) rather than full fine-tuning: LoRA trains small, low-rank adapter matrices on top of a frozen base model instead of updating all base weights, so each fine-tuned "variant" is just a small adapter (megabytes, not gigabytes) that can be loaded/swapped on top of one shared, resident base model in memory. This lets you serve many task- or customer-specific variants from one base model's memory footprint, swapping adapters per-request rather than keeping multiple full model copies resident, which would be the memory cost of naive full-fine-tuning-per-variant.

      Follow-up: what's the latency cost, if any, of swapping a LoRA adapter per request compared to a fully static single-model deployment?

      Practice Assignments

      Beginner (30-60 min)

      Explore tokenization behavior across several models

      Load tokenizers for 3 different models (e.g. bert-base-uncased, gpt2, and a modern model like meta-llama or mistralai's tokenizer) and tokenize the same set of 10 sentences, including some with numbers, rare words, and code snippets.

      • Print the resulting tokens (not just IDs) for each model side by side.
      • Identify at least 2 concrete cases where the three tokenizers split the same text differently.

      Acceptance criteria: a side-by-side comparison table/printout with at least 2 clearly annotated differences and a brief explanation of why each difference likely occurred (vocabulary size, BPE vs. WordPiece, byte-level vs. character-level).

      Hints

      Use tokenizer.tokenize(text) (not encode) to see the actual subword strings rather than just numeric IDs — much easier to compare visually.

      Bonus: include a sentence in a non-English language and compare how efficiently (fewest tokens) each tokenizer represents it.

      Intermediate (2-4 hrs)

      Build a local sentence-embedding + similarity search tool

      Load a pretrained encoder model locally, compute mean-pooled (attention-mask-aware) sentence embeddings for a small corpus of 50-100 short text snippets, and build a simple cosine-similarity search over them.

      • Correctly implement attention-mask-aware pooling (not naive mean over all positions).
      • Given a query string, return the top-5 most similar snippets by cosine similarity.
      • Demonstrate, with one deliberately constructed example, what goes wrong if pooling ignores the attention mask (compare masked vs. unmasked pooling results for a batch with mixed-length inputs).

      Acceptance criteria: working similarity search with correct masked pooling, plus a clear before/after demonstration of the masking bug.

      Hints

      Normalize embeddings to unit length before computing cosine similarity via a simple dot product — it's equivalent to true cosine similarity and slightly cheaper to compute in a batch.

      Bonus: compare your manually mean-pooled embeddings against a dedicated sentence-embedding model (e.g. a `sentence-transformers` model) on the same queries and discuss any quality difference.

      Advanced (1-2 days)

      Fine-tune a small classifier and measure the tokenizer-driven numeric extraction issue directly

      Fine-tune a small pretrained model (e.g. DistilBERT) on a synthetic numeric-extraction or arithmetic- reasoning task, and empirically measure accuracy degradation as number length grows, tying the result back to the tokenization issue discussed in this chapter.

      • Generate a synthetic dataset of short texts containing numbers of varying length (2-10 digits) with a labeled target (e.g. extract the number, or classify whether two numbers in the text are equal).
      • Fine-tune the model and evaluate accuracy bucketed by number length.
      • For each bucket, also report the actual tokenization (number of tokens the number was split into) to correlate split-count with accuracy.

      Acceptance criteria: a clear report showing accuracy degrading as number length (and token-split count) increases, with the correlation explicitly shown, not just asserted.

      Hints

      Keep the task itself simple (e.g. binary equality classification between two numbers in the text) so that any accuracy degradation can be more confidently attributed to tokenization/representation issues rather than general task difficulty.

      Bonus: repeat the experiment after applying the digit-normalization preprocessing strategy discussed in the advanced interview question, and show whether it measurably improves accuracy on longer numbers.

      Quick Revision Cheat Sheet

      • AutoModel/AutoTokenizer resolve a model name into the correct concrete class automatically; task-specific Auto* classes attach the right head.
      • pipeline() is great for prototyping; drop to direct model/tokenizer calls for production control over batching and output.
      • The Hub = models + datasets + Spaces, all versioned with metadata — check license and model card before production use.
      • BPE/WordPiece build a subword vocabulary from a training corpus; common text = fewer tokens, rare text = more, smaller tokens.
      • Tokenization inconsistency (especially for numbers) is a root cause of LLM arithmetic unreliability — not a training-data gap alone.
      • Always pass and respect the attention mask when batching variable-length inputs, especially when pooling.
      • Use float16/bfloat16 + safetensors + pinned revisions as production defaults, not float32 + unpinned + pickle.
      • LoRA and other parameter-efficient fine-tuning methods let you serve many fine-tuned variants cheaply on one base model.
