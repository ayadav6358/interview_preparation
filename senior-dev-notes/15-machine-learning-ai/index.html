    Machine Learning & AI

    📚 14 chapters⏱ ~40–46 hrs total

    Genuine ML/DL foundations, built from first principles, for engineers who are strong in software engineering but want to stop hand-waving "the model just learns it." Starts with the math and history that everything else rests on, builds neural networks and transformers from scratch so attention stops being magic, moves through the practical HuggingFace/PyTorch ecosystem, then spends the second half on what it actually takes to ship LLM-based systems in production: observability, RAG, context engineering, agents, agent frameworks and memory, fine-tuning and alignment, and finally how to evaluate all of it rigorously while surveying where the frontier (MoE, long context, reasoning models, multimodal) is heading. This is the deepest and most 2025-26-current topic in the entire site, and the one most likely to separate "has used an LLM API" from "actually understands what's happening underneath it" in a senior interview.

    Learning Outcomes

    • Explain backpropagation, gradient descent, and the attention mechanism precisely — not as "magic," but as mechanisms you could implement from scratch with tensors.
    • Build, train, and fine-tune real models using PyTorch and the HuggingFace ecosystem, including parameter-efficient fine-tuning (LoRA/QLoRA) and alignment techniques (RLHF/DPO).
    • Design production-grade RAG and agent systems, including retrieval strategies, context engineering, agent memory architectures, and MCP-based tool integration.
    • Instrument and evaluate LLM systems rigorously — observability/tracing, golden datasets, LLM-as-judge methodology, and regression testing for prompts and model versions.
    • Speak fluently about the 2025-26 frontier landscape (mixture-of-experts, long-context techniques, reasoning/test-time-compute models, multimodal architectures) and defend when each technique is and isn't the right lever to pull.

    🏆 Capstone Project: Fine-tune, Retrieve, Observe, Evaluate

    Problem statement: Build a genuinely comprehensive ML engineering pipeline for one specific target task of your choosing (e.g. support-ticket triage, structured data extraction from documents, or a domain-specific Q&A assistant): fine-tune a small open-source model with LoRA, build a minimal RAG pipeline over a personal document set, wire up basic LLM observability, and write an eval suite that compares the fine-tuned model, the base model alone, and the RAG-augmented base model head-to-head on your target task — then make and defend a recommendation for which approach you'd actually ship.

    Required components:

    • A small open-source base model (e.g. a 1-3B Llama or Qwen variant) runnable on commodity hardware.
    • A LoRA/QLoRA fine-tuning run on a curated SFT dataset (200+ examples) targeting your chosen task, using HuggingFace PEFT (chapters 4, 7, 13).
    • A minimal RAG pipeline over a personal document set (10+ real documents) with a vector DB, heading-aware or parent-child chunking, and at least basic hybrid retrieval (chapters 9, 10).
    • Basic LLM observability/tracing instrumented across all three variants being compared, capturing latency, token usage, and full request/response traces (chapter 8).
    • A golden dataset (25-30 examples, labeled where applicable) and an eval harness scoring all three variants — base model, fine-tuned model, RAG-augmented base model — on the same task, using deterministic checks where possible and LLM-as-judge for free-form outputs (chapter 14).

    Tech stack suggestion: Python, HuggingFace Transformers + PEFT + TRL, a local vector DB (Chroma or FAISS), a lightweight tracing setup (OpenTelemetry-based or a hosted LLM observability tool), and any capable model as your LLM-as-judge.

    Milestones:

    1. Pick a concrete target task and build the golden dataset first — before touching any model, define what "good" looks like and how you'll measure it.
    2. Build the RAG pipeline over your document set and get it answering reasonably on a few manual spot-checks.
    3. Curate the SFT dataset and run the LoRA fine-tune; verify trainable-parameter percentage and training loss curves look sane.
    4. Instrument all three variants (base, fine-tuned, RAG-augmented base) with the same tracing setup so you can compare latency/cost alongside quality.
    5. Run the full eval harness across all three variants on your golden dataset, broken down by category, not just one aggregate score.
    6. Write up a short recommendation: which variant would you actually ship for this task, and why — citing specific eval numbers and tradeoffs (cost, latency, accuracy, maintainability), not vibes.

    Evaluation checklist:

    • ☐ Can explain exactly what the LoRA fine-tune changed and why, down to the matrix math.
    • ☐ RAG pipeline's retrieval and generation quality were measured separately, not just end-to-end.
    • ☐ Eval harness produces per-category scores for all three variants, with a stored baseline for future regression checks.
    • ☐ Tracing data was actually used to compare cost/latency tradeoffs, not just collected and ignored.
    • ☐ Final recommendation is defensible under pushback — can justify why the chosen variant wins on the dimensions that matter most for this specific task.
