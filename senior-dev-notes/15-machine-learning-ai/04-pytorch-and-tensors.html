    PyTorch & Tensors

    ⏱ ~3 hrs📍 Chapter 4 of 14

    One-line summary: PyTorch's entire value proposition is that it automates exactly the backward pass you derived by hand in chapter 3, by silently recording every operation into a computation graph as you run the forward pass — once you see that graph explicitly, .backward() stops being magic and loss.backward() reads as "replay the chain rule through everything I just did."

    On this page

      Why It Matters for a Senior Developer

      PyTorch is the dominant framework for both research and a huge share of production deep learning in 2025-26, and senior ML interviews routinely probe whether you understand autograd's mechanics rather than just its API surface — "what does .backward() actually do," "why do I need zero_grad()," "why did my loss become NaN after an in-place operation" are all questions that separate someone who's internalized chapter 3's manual backprop from someone pattern-matching PyTorch tutorials. As a strong general-purpose engineer, you'll also map PyTorch's computation graph directly onto concepts you already know (a DAG, lazy evaluation of gradients, reference-counted memory for the graph) — this chapter leans on exactly that intuition.

      Why

      Every PyTorch training loop is the same four-line pattern repeated millions of times: forward, compute loss, loss.backward(), optimizer.step(). Understanding that this pattern is a direct automation of chapter 3's hand-derived forward/backward loop — not a different thing — is what lets you debug training failures (vanishing gradients, in-place-op errors, memory leaks from retained graphs) by reasoning about the underlying mechanism instead of guessing from Stack Overflow.

      Core Concepts

      What a tensor is

      A tensor is PyTorch's n-dimensional array — conceptually identical to a numpy array, but with two crucial additions: it can live on a GPU, and it can track the operations performed on it for automatic differentiation. A scalar is a 0-d tensor, a vector is 1-d, a matrix is 2-d, and a batch of images is typically a 4-d tensor ([batch, channels, height, width]). Every tensor has a .shape, a .dtype (float32 is the default for most training), and a .device (cpu or cuda) — operations between two tensors on different devices raise an error, a common early-career PyTorch mistake.

      Autograd: how .backward() actually works

      Set requires_grad=True on a tensor (or create it as a parameter of an nn.Module, which does this automatically), and PyTorch begins silently building a computation graph as you perform operations: every tensor operation (add, matmul, relu, ...) creates a graph node recording what inputs produced it and what operation was used, stored on the output tensor's .grad_fn attribute. This is exactly the "cache every intermediate value" step from chapter 3's manual backprop — PyTorch is doing it for you, automatically, for an arbitrarily complex sequence of operations, not just a fixed 2-layer network.

      Calling loss.backward() walks this graph backward from the loss (a scalar), applying the chain rule at each node exactly as derived in chapter 3, and accumulates the resulting gradient into each leaf tensor's .grad attribute. "Accumulates" is the key word: gradients are added to whatever is already in .grad, not overwritten — which is precisely why every training loop must call optimizer.zero_grad() before each .backward(), or gradients from previous batches silently pile up and corrupt training.

      nn.Module and the training loop

      nn.Module is PyTorch's base class for anything with learnable parameters — a single layer, or an entire network. Subclassing it, you define your layers in __init__ (e.g. nn.Linear, which is chapter 3's W @ x + b wrapped with automatic parameter registration and initialization) and the forward computation in forward(); calling the module like a function (model(x)) runs forward() and builds the computation graph as described above. A full training loop is the exact four-step loop from chapter 3's "under the hood" section, now automated: optimizer.zero_grad() → output = model(x) (forward) → loss = loss_fn(output, y) → loss.backward() (autograd walks the graph) → optimizer.step() (applies SGD/Adam's update rule using the now-populated .grad tensors).

      GPU vs CPU tensors, and common pitfalls

      Moving a model and its data to GPU (.to("cuda") or .cuda()) offloads the matrix-multiply-heavy forward/backward computation to the GPU's massively parallel cores (chapter 1's "matrix multiply is many dot products at once" point is exactly why this helps). Both the model's parameters and every tensor involved in a given forward pass must be on the same device, or PyTorch raises a device-mismatch error — a very common bug when, say, loading a batch from a CPU-based data pipeline and forgetting to move it to GPU before the forward pass.

      The single most common class of PyTorch bug is breaking autograd via an in-place operation (e.g. x += 1 or x[0] = 5 on a tensor that's part of the computation graph) — because autograd's backward pass for some operations needs the original (pre-operation) tensor value to compute the correct gradient, and an in-place modification destroys that value before backward can use it, producing either a cryptic runtime error ("a leaf Variable that requires grad is being used in an in-place operation" or "one of the variables needed for gradient computation has been modified by an inplace operation") or, worse, silently wrong gradients if PyTorch doesn't catch the specific case.

      How It Works Under the Hood

      Concretely, for y = relu(W @ x + b) with W, b, x all requiring gradients:

      1. Forward pass executes, and each operation (matmul, add, relu) creates a node in the computation graph, with y.grad_fn pointing to the last op (ReluBackward), which in turn references the AddBackward node that produced its input, which references the MatmulBackward node, forming a DAG back to the leaf tensors W, x, b.
      2. loss.backward() starts at the loss (implicitly treating it as having gradient 1 with respect to itself) and walks this DAG in reverse topological order, at each node calling that operation's specific backward function (e.g. ReluBackward multiplies the upstream gradient by a 0/1 mask, exactly chapter 3's relu_deriv) and passing the result further back.
      3. When the walk reaches a leaf tensor with requires_grad=True, the computed gradient is accumulated into that tensor's .grad attribute.
      4. After .backward() completes, the graph is by default freed (to save memory) — calling .backward() a second time on the same graph without retain_graph=True raises an error, since the intermediate values needed were already discarded.
      5. optimizer.step() then reads each parameter's .grad and applies the optimizer's update rule (SGD, Adam, ...) — this step does not touch the computation graph at all; it's a separate, simple loop over parameters.

      Code Examples

      import torch
import torch.nn as nn

# --- Tensors: shape, dtype, device ---
x = torch.tensor([[1.0, 2.0], [3.0, 4.0]])
print(x.shape, x.dtype, x.device)   # torch.Size([2, 2]) torch.float32 cpu

device = "cuda" if torch.cuda.is_available() else "cpu"
x_gpu = x.to(device)   # mismatched devices between tensors raise a RuntimeError

# --- Autograd: watch the graph build and .backward() walk it ---
w = torch.tensor([0.5, -0.3], requires_grad=True)
b = torch.tensor(0.1, requires_grad=True)
x = torch.tensor([2.0, 1.0])

z = (w * x).sum() + b          # z.grad_fn chains back through mul, sum, add
y = torch.relu(z)
loss = (y - 1.0) ** 2           # a tiny "network": relu(w·x+b), MSE loss vs target 1.0

loss.backward()                 # walks the graph backward, chain rule at every node
print("dw:", w.grad)            # populated — this is exactly chapter 3's dW, computed automatically
print("db:", b.grad)

# --- nn.Module: a real tiny network, defined declaratively ---
class TinyNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(2, 4)   # is literally W1 @ x + b1, auto-initialized
        self.fc2 = nn.Linear(4, 2)

    def forward(self, x):
        h = torch.relu(self.fc1(x))
        return self.fc2(h)           # raw logits — pair with CrossEntropyLoss, which applies softmax internally

model = TinyNet().to(device)
optimizer = torch.optim.Adam(model.parameters(), lr=0.01)
loss_fn = nn.CrossEntropyLoss()

X = torch.tensor([[0., 0.], [0., 1.], [1., 0.], [1., 1.]]).to(device)
Y = torch.tensor([0, 1, 1, 0]).to(device)   # XOR, class indices (not one-hot — CrossEntropyLoss expects this)

for epoch in range(500):
    optimizer.zero_grad()           # CRITICAL: without this, gradients accumulate across batches
    logits = model(X)                # forward pass, builds the graph
    loss = loss_fn(logits, Y)
    loss.backward()                  # backward pass, populates .grad on every parameter
    optimizer.step()                 # applies Adam's update rule using those .grad values
    if epoch % 100 == 0:
        print(f"epoch {epoch}  loss {loss.item():.4f}")

# --- BAD: in-place operation breaking autograd ---
a = torch.tensor([1.0, 2.0], requires_grad=True)
b = a * 2
# b += 1   # in-place op on a tensor needed for backward -> RuntimeError on .backward()
# Fix: use out-of-place ops when the tensor is part of an active computation graph
c = b + 1   # GOOD: creates a new tensor, doesn't destroy a value autograd needs

# --- GOOD: no_grad() for inference, where you don't want graph-building overhead ---
with torch.no_grad():
    preds = model(X)   # no graph built, no .backward() possible or needed, saves memory/compute
print("inference preds shape:", preds.shape)

      Real-World Production Scenario at Scale

      At scale

      A team's training job runs fine for a few hundred steps, then crashes with "CUDA out of memory," despite the model and batch size being well within the GPU's known capacity based on earlier successful runs. Investigation reveals a validation loop embedded inside the training loop that calls model(val_batch) for logging purposes without wrapping it in torch.no_grad() — every validation forward pass was building and retaining a full computation graph that was never used for a backward pass, silently accumulating unreleased GPU memory across training steps until it exhausted available memory. The fix (wrapping all non-training forward passes in torch.no_grad(), or equivalently using model.eval() plus no_grad() together) is a direct application of understanding what autograd's graph-building actually costs — it's not free bookkeeping, it's real retained memory, and skipping it for passes that don't need gradients is standard, necessary practice at any production training scale.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Forgetting optimizer.zero_grad() before loss.backward() — because PyTorch accumulates gradients into .grad rather than overwriting them, skipping this call causes gradients from every previous batch to silently sum together, producing training that appears to run without errors but converges incorrectly or diverges, with no obvious error message pointing at the cause.

      Gotcha

      Using an in-place operation (+=, indexed assignment, or an in-place method ending in _ like relu_()) on a tensor that's part of an active computation graph — this is the single most common "why is my training crashing with a cryptic autograd error" issue for PyTorch beginners, and the fix is almost always to use the out-of-place equivalent operation instead.

      • Always check tensor.device matches across model and data before a forward pass in a new environment — a device mismatch is an immediate, unambiguous error, but it's a very common first bug when moving code from CPU-only development to a GPU training environment.
      • Wrap any forward pass that doesn't need a backward pass afterward (validation, inference, logging) in torch.no_grad() to avoid needlessly building and retaining computation graphs that waste memory and compute.

      Interview Questions

      Basic

      What is a PyTorch tensor, and how does it differ from a numpy array?

      A tensor is an n-dimensional array like a numpy array, but it can additionally live on a GPU and can track the operations performed on it to support automatic differentiation (autograd), neither of which numpy arrays support.

      Follow-up: what attribute enables a tensor to track operations for autograd?
      What does loss.backward() actually do?

      It walks the computation graph built during the forward pass, starting from the loss, backward to every leaf tensor, applying the chain rule at each node to compute the gradient of the loss with respect to every parameter, and accumulates those gradients into each parameter's .grad attribute.

      Follow-up: why does it "accumulate" rather than overwrite .grad, and what does that imply for the training loop?
      Why must you call optimizer.zero_grad() before loss.backward() in every training iteration?

      Because PyTorch accumulates (adds) new gradients into .grad rather than replacing them, so without zeroing first, gradients from previous batches would pile up on top of the current batch's gradients, corrupting the training signal.

      Follow-up: what would the symptom of forgetting this look like in a loss curve?
      What is nn.Linear, in terms of what you learned in the from-scratch neural networks chapter?

      It's exactly W @ x + b (a single layer's weighted sum plus bias) wrapped with automatic parameter registration, initialization, and autograd tracking — the same operation implemented by hand in chapter 3, provided as a reusable building block.

      Follow-up: what does calling model.parameters() return, and why does the optimizer need it?
      Why does moving a model to GPU speed up training?

      The core operations in a forward/backward pass are matrix multiplications, which are many parallel dot products — GPUs have thousands of cores built specifically to execute this kind of parallel arithmetic far faster than a CPU can.

      Follow-up: what error occurs if the model is on GPU but the input data tensor is still on CPU?
      What is torch.no_grad() used for, and why does it matter for memory?

      It's a context manager that disables computation graph building for the operations inside it, typically used for inference/validation where no backward pass is needed — without it, every forward pass still builds and retains a full graph in memory even if .backward() is never called, wasting memory.

      Follow-up: what's the difference between model.eval() and torch.no_grad(), and why are they often used together?

      Medium

      Explain what grad_fn represents and how it relates to the computation graph.

      grad_fn is an attribute on any non-leaf tensor produced by an operation on a tensor requiring gradients; it points to the specific backward function (e.g. ReluBackward, AddBackward) that knows how to compute the local gradient for that operation, and it references the grad_fn of its own inputs, forming a chain (a directed acyclic graph) back to the leaf tensors — this chain is exactly what .backward() traverses.

      Follow-up: why do leaf tensors (like model parameters) not have a grad_fn?
      Why does an in-place operation on a tensor involved in the computation graph often cause an autograd error, rather than just silently computing something slightly wrong?

      Some backward functions need the original (pre-operation) value of a tensor to correctly compute their local gradient (e.g. ReLU's backward needs to know which entries of the original input were positive). An in-place modification overwrites that value before backward runs, so PyTorch's autograd engine detects (via a version counter it tracks per tensor) that the tensor has been modified since the forward pass and raises an explicit error, rather than silently computing a wrong gradient — this is a deliberate safety check, not an incidental side effect.

      Follow-up: can you think of an in-place operation that would NOT trigger this error, and why?
      Why is the graph freed by default after calling .backward(), and what happens if you call .backward() again without retain_graph=True?

      Retaining the graph after backward costs memory for no benefit in the typical single-backward-pass-per-forward-pass training loop, so PyTorch frees intermediate values by default to save memory. Calling .backward() again on the same graph without retain_graph=True raises an error, because the intermediate values needed to recompute the backward pass were already discarded.

      Follow-up: name a real scenario where you'd deliberately need retain_graph=True.
      What's the practical difference between model.parameters() in a training loop versus manually tracking individual weight tensors as in a from-scratch numpy implementation?

      model.parameters() returns an iterator over every registered learnable tensor in the module (and any submodules), letting the optimizer update an arbitrary, dynamically-structured set of weights generically, without the optimizer or training loop needing to know the specific architecture — in the from-scratch version, every weight tensor had to be named and updated individually and explicitly, which doesn't scale past toy examples.

      Follow-up: how does nn.Module know to automatically register a tensor as a parameter versus treating it as a regular attribute?
      Why does CrossEntropyLoss in PyTorch expect raw logits (not softmax probabilities) as input?

      PyTorch's CrossEntropyLoss internally combines log-softmax and negative log likelihood in a single numerically stable operation, which both avoids a separate, less numerically stable softmax step and directly produces the simplified y_hat - y gradient from chapter 3 during backward — passing already-softmaxed probabilities in would double-apply softmax and produce an incorrect loss and gradient.

      Follow-up: what's the numerical stability benefit of combining log-softmax and NLL into one operation instead of doing them as two separate steps?

      Advanced

      Explain how PyTorch's autograd engine determines the correct order to traverse the computation graph during .backward(), and why this matters for a graph with multiple paths converging on one tensor.

      Autograd performs a reverse topological sort of the DAG rooted at the loss, ensuring that when a node's backward function runs, all of its "downstream" consumers (nodes that depend on it) have already had their gradients computed and passed back to it, so gradients arriving at a node from multiple paths (e.g. a tensor used twice in the forward pass, feeding two different branches that later recombine) are correctly summed before that node's own backward function runs. Without this ordering guarantee, a node could run its backward computation using only a partial (incomplete) upstream gradient, producing an incorrect result for any tensor reused across multiple paths in the forward pass.

      Follow-up: give a concrete architectural example where a tensor is legitimately used along two different paths that later reconverge.
      Why does PyTorch build the computation graph dynamically (define-by-run) rather than statically (define-then-run, as early TensorFlow did), and what are the practical tradeoffs?

      Dynamic graph construction means the graph is built fresh on every forward pass call, following whatever Python control flow (loops, conditionals) actually executes that time — this makes debugging dramatically easier (you can set breakpoints and inspect intermediate tensors with ordinary Python tooling, since the "graph" is just the normal Python execution) and makes variable-length/data-dependent architectures (like RNNs over variable-length sequences, or conditionally-skipped layers) natural to express. The tradeoff is some performance overhead versus a static graph that can be compiled/optimized once ahead of time and reused unchanged across many forward passes — this is exactly the gap tools like torch.compile aim to close, by tracing the dynamic graph once and generating optimized, static-like execution for repeated use.

      Follow-up: how does torch.compile attempt to get static-graph-like performance while keeping the dynamic authoring experience?
      Walk through why a model.eval() call is necessary in addition to torch.no_grad() when running validation, and what would silently go wrong if you only used no_grad().

      torch.no_grad() only disables gradient/graph tracking; it has no effect on layers whose forward behavior itself differs between training and evaluation, like dropout (which randomly zeroes activations only during training, to regularize) and batch normalization (which uses batch statistics during training but running/stored statistics during evaluation). Without calling model.eval() to switch these layers' internal mode, a "no_grad-only" validation pass would still apply dropout's random zeroing and batchnorm's training-time batch statistics, producing noisy, non-reproducible, and systematically different validation metrics than what the model will actually do at real inference/serving time.

      Follow-up: why is batchnorm's behavior difference between train and eval mode specifically dependent on batch size during training but not during eval?
      Explain memory-wise why gradient accumulation (summing gradients over several small forward/backward passes before one optimizer.step()) is a valid and common technique for simulating a larger batch size than fits in GPU memory.

      Since .grad accumulates (sums) rather than overwrites, you can run several forward+backward passes on smaller sub-batches without calling zero_grad() or optimizer.step() between them — each sub-batch's gradient contribution adds into the same .grad tensors, and after N sub-batches you call optimizer.step() once, mathematically approximating (up to a scaling factor on the learning rate/averaging) the gradient you'd have gotten from one large batch forward/backward pass, while only ever holding one sub-batch's activations in memory at a time instead of the full large batch's.

      Follow-up: what scaling adjustment do you need to apply to the loss or learning rate to make gradient accumulation mathematically equivalent to true large-batch training?
      Why can repeatedly appending per-step loss values to a Python list for logging purposes (e.g. losses.append(loss)) cause a subtle GPU memory leak, and what's the fix?

      loss is a tensor still attached to its full computation graph; appending the tensor itself (rather than its plain scalar value) to a Python list keeps a live reference to that tensor, which in turn keeps the entire computation graph (and all its intermediate activations) alive and un-freed for as long as the list holds the reference — across thousands of training steps, this accumulates retained graphs for every single step and exhausts GPU memory. The fix is to call .item() (for a scalar) or .detach() (for a tensor you still want values from, without graph attachment) before storing it, which extracts the plain value/un-attached tensor without holding a reference into the computation graph.

      Follow-up: why does .item() specifically force a CPU-GPU synchronization, and what performance implication does that have if called too frequently inside a tight training loop?

      Quick Revision Cheat Sheet

      • A tensor = numpy array + GPU support + autograd tracking.
      • Autograd builds a computation graph during the forward pass; .backward() walks it backward applying the chain rule.
      • Gradients accumulate into .grad — always call optimizer.zero_grad() before each .backward().
      • nn.Linear is literally W @ x + b from chapter 3, with auto-init and parameter registration.
      • Standard loop: zero_grad() → forward → loss → backward() → optimizer.step().
      • In-place ops on graph-attached tensors are the #1 PyTorch autograd bug — use out-of-place equivalents.
      • torch.no_grad() skips graph-building for inference/validation — saves memory and compute.
      • model.eval() changes layer *behavior* (dropout, batchnorm); no_grad() only skips *gradient tracking* — you usually need both for validation.
      • CrossEntropyLoss expects raw logits, not softmax probabilities — it applies log-softmax internally for numerical stability.
      • Device mismatches (CPU tensor + GPU model) raise explicit errors — always confirm model and data share a device.
