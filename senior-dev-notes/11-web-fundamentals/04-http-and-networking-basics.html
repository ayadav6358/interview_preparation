    HTTP & Networking Basics: Requests, Status Codes, Headers, Cookies, CORS

    ⏱ 2 hrs📍 Chapter 4 of 6

    One-line summary: Every API call you've ever made is an HTTP request/response pair governed by precise rules around status codes, headers, cookies, and the same-origin policy — CORS in particular is one of the most-misunderstood "basic" topics and a reliable interview filter.

    On this page

      Why It Matters for a Senior Developer

      You've debugged a thousand failed `fetch()` calls. The senior-level bar isn't "I can call an API" — it's "I can read a raw response and immediately know whether this is a CORS problem, a cookie `SameSite` problem, a caching problem, or an actual server bug, from the headers alone." CORS especially is asked constantly because it's genuinely confusing (it's enforced by the browser, not the server, and the error message is deliberately vague for security reasons) and because getting it wrong in production causes real, embarrassing outages. This chapter is foundational to React/Next.js Advanced (data fetching, SSR cookies) and Node.js Advanced (building the server side of these same requests).

      Prerequisites

      Builds on Chapter 2 (Promises/async-await for fetch) and Chapter 3 (browser environment). Directly assumed by React/Next.js Advanced and Node.js Advanced for building/consuming APIs.

      Core Concepts

      Request/response anatomy

      An HTTP request has: a method (verb), a path, headers, and optionally a body. A response has: a status code, headers, and optionally a body. HTTP is stateless by design — the server retains no memory of previous requests from the same client unless state is explicitly carried (cookies, tokens, session IDs) in each request. Methods carry precise semantics senior devs are expected to know exactly: GET (safe — no side effects — and idempotent), POST (neither safe nor idempotent — calling it twice may create two resources), PUT (idempotent — replaces the whole resource; calling it N times has the same effect as once), PATCH (partial update, not guaranteed idempotent depending on the patch semantics), DELETE (idempotent — deleting an already-deleted resource is still "deleted"). "Idempotent" means repeating the same request produces the same server state, not that the response is identical.

      Status codes: the precise groupings

      1xx informational (rare in app code, e.g. `101 Switching Protocols` for WebSocket upgrade). 2xx success: `200 OK`, `201 Created` (should include a `Location` header pointing to the new resource), `204 No Content` (success, deliberately empty body — common for DELETE). 3xx redirection: `301` permanent (clients/caches should remember and reuse the new URL), `302`/`307` temporary (302 historically allowed method-changing redirects, 307 strictly preserves the original method — a subtle but real distinction that breaks POST redirects differently across the two). 4xx client error: `400` bad request (malformed), `401` unauthenticated (you are not who you say you are, or haven't said), `403` unauthorized/forbidden (you are known but not allowed), `404` not found, `409` conflict (e.g., version mismatch, duplicate unique key), `422` unprocessable entity (semantically invalid, e.g. failed validation despite well-formed JSON), `429` too many requests (rate limited, should include `Retry-After`). 5xx server error: `500` generic, `502` bad gateway (upstream server gave an invalid response), `503` service unavailable (temporarily down/overloaded, should include `Retry-After`), `504` gateway timeout. The 401 vs 403 distinction is one of the most commonly botched in real APIs and a frequent interview question.

      Headers and cookies, precisely

      Key request headers: `Authorization` (bearer tokens/basic auth), `Content-Type` (what the body actually is), `Accept` (what the client wants back), `If-None-Match`/`If-Modified-Since` (conditional requests for caching, paired with response `ETag`/`Last-Modified`). Key response headers: `Set-Cookie`, `Cache-Control` (`no-store` never cache, `no-cache` cache but revalidate every time, `max-age=N` cache for N seconds, `private` vs `public` for shared caches/CDNs), `Content-Encoding` (gzip/br compression).

      Cookie attributes senior devs must know exactly: `HttpOnly` (inaccessible to JS via `document.cookie` — the primary XSS mitigation for session cookies), `Secure` (only sent over HTTPS), `SameSite` — `Strict` (never sent cross-site, even on top-level navigation from another site), `Lax` (sent on top-level navigation like clicking a link, but not on cross-site subresource requests or most fetches — the modern browser default), `None` (sent on all cross-site requests, but requires `Secure`). `SameSite=Lax` as the default is precisely what killed most classic CSRF attacks without requiring any app-level CSRF token for simple cases — a senior-relevant detail many miss.

      CORS: enforced by the browser, not the server

      The Same-Origin Policy blocks a page from script-reading responses from a different origin (scheme+host+port) unless the server opts in via CORS headers. Critically: the request still reaches the server and the server still processes it — CORS only blocks the browser from letting your JS read the response. This is why "it works in Postman but not the browser" is the single most common CORS confusion: Postman isn't a browser and doesn't enforce same-origin policy at all.

      A simple request (GET/HEAD/POST with only a small whitelist of headers and content-types like `text/plain`/`form-urlencoded`/`multipart`) goes straight through, and the browser just checks the `Access-Control-Allow-Origin` response header before exposing the response to JS. Anything else (custom headers like a bearer `Authorization`, `Content-Type: application/json`, methods like `PUT`/`DELETE`/`PATCH`) triggers a preflight: the browser automatically sends an `OPTIONS` request first, asking "would you allow this actual request?" via `Access-Control-Request-Method`/`-Headers`; the server must respond with matching `Access-Control-Allow-Method`/`-Headers`/`-Origin` for the real request to even be attempted. `Access-Control-Allow-Credentials: true` (server) + `credentials: 'include'` (client fetch) are both required together to send cookies cross-origin — and critically, `Access-Control-Allow-Origin` cannot be the wildcard `*` when credentials are involved; it must echo back the specific requesting origin.

      How It Works Under the Hood

      A browser-initiated cross-origin request that needs a preflight flows as: (1) browser sees the JS wants to make a "non-simple" cross-origin request, (2) browser automatically fires an `OPTIONS` request with no body, carrying `Access-Control-Request-Method` and `-Headers`, (3) server inspects these and responds with its allowed origins/methods/headers as response headers (no actual business logic runs for this request), (4) browser checks the response against what the real request needs — if everything matches, (5) the browser fires the actual request and, on response, checks `Access-Control-Allow-Origin` again before handing the response body to your JS code; if it doesn't match, the browser throws a CORS error in the console and your `.catch()`/promise rejection fires, even though the server may have returned `200 OK` — the data was received over the wire but withheld from your JS.

      Code Examples

      // fetch with explicit error handling — fetch() does NOT reject on 4xx/5xx!
async function getUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) { // response.ok is false for status >= 400
    // fetch only rejects on network failure (DNS, offline, CORS block) — not HTTP error codes
    throw new Error(`Request failed: ${response.status} ${response.statusText}`);
  }
  return response.json();
}

// Sending cookies cross-origin requires BOTH sides to opt in
fetch('https://api.example.com/profile', {
  credentials: 'include', // client: actually send cookies cross-origin
});
// Server MUST respond with:
//   Access-Control-Allow-Credentials: true
//   Access-Control-Allow-Origin: https://app.example.com   (NOT '*' — wildcard is rejected with credentials)

      # Reading CORS/cache behavior directly from raw headers with curl -i
curl -i -X OPTIONS https://api.example.com/resource \
  -H "Origin: https://app.example.com" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: content-type"

# Expected preflight response headers (what to look for):
#   HTTP/1.1 204 No Content
#   Access-Control-Allow-Origin: https://app.example.com
#   Access-Control-Allow-Methods: GET, POST, PUT, DELETE
#   Access-Control-Allow-Headers: content-type
#   Access-Control-Max-Age: 86400   (cache the preflight result for a day)

      // Conditional caching: ETag round-trip
// 1st request
// Response: 200 OK, ETag: "abc123"
// 2nd request (browser automatically adds this if cached)
// Request:  If-None-Match: "abc123"
// Response: 304 Not Modified, empty body — browser reuses its cached copy

      Real-World Production Scenario at Scale

      At scale

      A team splits their frontend (`app.example.com`) and API (`api.example.com`) onto different subdomains for independent deployment. After launch, login works in every manual test via Postman/curl but silently fails in the real browser app — specifically, the session cookie never gets attached to subsequent requests, so every "authenticated" call 401s right after a successful login. The root cause is a stacked CORS + cookie misconfiguration: the API set `Access-Control-Allow-Origin: *` (convenient during early development) while the client used `credentials: 'include'` — browsers reject this combination outright since a wildcard origin cannot be paired with credentials, for the obvious security reason that `*` would let literally any site read a user's authenticated response. The fix requires three coordinated changes: the API must echo back the specific requesting origin instead of `*`, set `Access-Control-Allow-Credentials: true`, and the cookie itself must be set with `SameSite=None; Secure` since it's now genuinely cross-site between subdomains — missing any one of these three leaves the exact same symptom.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Assuming `fetch()` throws/rejects on a 404 or 500. It does not — `fetch()` only rejects on true network failures (DNS failure, offline, CORS block). A `404` or `500` is a "successful" fetch from the Promise's perspective; you must check `response.ok` or `response.status` yourself and throw explicitly if you want error-path handling.

      Gotcha

      Treating a CORS error as a server-side problem to "fix on the backend only," without realizing the request already succeeded server-side — the data was computed and sent, the browser just withheld it from JS. This matters for anything with side effects: a blocked POST may have still created the resource server-side even though the client sees only a CORS error and assumes it failed, leading to duplicate-submission bugs on retry.

      • Always check `response.ok`/`response.status` explicitly after `fetch()` — never assume a resolved promise means success.
      • Know the 401 vs 403 distinction cold: 401 = "I don't know who you are," 403 = "I know who you are and the answer is no."
      • For cross-site cookies, all three must align: `SameSite=None; Secure` on the cookie, a specific echoed origin (never `*`) plus `Access-Control-Allow-Credentials: true` on the server, and `credentials: 'include'` on the client.

      Interview Questions

      Basic

      What does "idempotent" mean for an HTTP method, and which common methods are idempotent?

      Repeating the same request produces the same end server state as doing it once. GET, PUT, and DELETE are idempotent; POST is not (calling it twice can create two resources); PATCH's idempotency depends on the specific patch semantics.

      What's the difference between 401 and 403?

      401 Unauthorized actually means "unauthenticated" — the server doesn't know who you are (missing/invalid credentials). 403 Forbidden means the server knows who you are but you don't have permission for this action/resource.

      Does `fetch()` reject its promise on a 404 response?

      No. `fetch()` only rejects on network-level failures. A 404 resolves successfully with `response.ok === false` — you must check status explicitly.

      What does the `HttpOnly` cookie attribute do?

      Prevents the cookie from being accessed via `document.cookie` in JavaScript, which mitigates session-cookie theft via XSS.

      What is a CORS preflight request?

      An automatic `OPTIONS` request the browser sends before a "non-simple" cross-origin request, asking the server whether the actual request (method/headers) will be allowed, before sending it.

      Is CORS enforced by the client or the server?

      Enforced by the browser (the client). The server opts in via response headers, but the actual blocking of the JS from reading the response happens in the browser — the request itself still reaches the server and is processed.

      Medium

      A request works fine in Postman/curl but fails with a CORS error only in the browser. Explain exactly why, and what that tells you about where the request actually got processed.

      CORS is a browser-enforced policy, not a server/network restriction — tools like curl/Postman don't implement the same-origin policy at all. The request reached the server and was processed normally; the browser simply withheld the response from the page's JS because the response didn't carry the required `Access-Control-Allow-Origin` header matching the page's origin.

      What three things must align correctly to send cookies on a cross-origin fetch request?

      The cookie itself must be set with `SameSite=None; Secure`; the server response must include a specific echoed `Access-Control-Allow-Origin` (not a wildcard) plus `Access-Control-Allow-Credentials: true`; and the client's fetch call must include `credentials: 'include'`. Missing any one silently breaks cookie delivery.

      Why can't `Access-Control-Allow-Origin: *` be combined with credentialed requests?

      If a wildcard origin were allowed alongside credentials, any arbitrary website could make a credentialed request (with the user's cookies) to the API and read the authenticated response — defeating the entire purpose of same-origin protection. The spec explicitly forbids this combination; browsers reject it even if a server mistakenly sends both.

      What's the practical difference between `Cache-Control: no-cache` and `no-store`?

      `no-cache` allows the response to be cached but requires revalidation (e.g., via ETag/If-None-Match) with the server before reuse. `no-store` forbids caching entirely — the response must be refetched fully every time, never stored anywhere.

      Why does `SameSite=Lax` as a default break fewer things than `Strict`, while still stopping most CSRF attacks?

      `Lax` still sends the cookie on top-level navigations (clicking a link to your site from elsewhere), preserving normal "click a link and you're still logged in" UX, while blocking it on cross-site subresource requests and most programmatic cross-site POSTs — which is exactly the vector classic CSRF attacks rely on. `Strict` would also block the cookie on simple top-level navigation, breaking legitimate flows like following an email link while logged in.

      Advanced

      Design the CORS and cookie configuration for a company splitting a monolith into `app.company.com` (frontend) and `api.company.com` (backend), while keeping session-based auth and protecting against CSRF.

      Cookie: `Set-Cookie: session=...; HttpOnly; Secure; SameSite=None` (required since it's now cross-subdomain, hence cross-site per browser rules) — but `SameSite=None` alone reopens CSRF risk that `Lax` used to mitigate for free, so add an explicit CSRF token (double-submit cookie or synchronizer token) validated server-side on state-changing requests. Server CORS: echo `Access-Control-Allow-Origin: https://app.company.com` exactly (never `*`), `Access-Control-Allow-Credentials: true`, and explicitly list allowed methods/headers for preflight. Client: `credentials: 'include'` on every request needing the session.

      Why does a blocked CORS POST request still potentially create a resource server-side, and what design pattern protects against the resulting duplicate-submission risk?

      CORS blocking happens entirely client-side after the response returns — the server received, processed, and responded to the request before the browser decided to withhold the response from JS. If the client then retries blindly (assuming failure), it may create duplicate resources. The protection is a client-supplied idempotency key sent as a header/field, which the server uses to detect and safely no-op a retried request for an operation it already completed, regardless of whether the client "saw" the original success.

      Explain `Access-Control-Max-Age` and its security/performance tradeoff.

      It tells the browser how long (in seconds) it may cache a preflight response and skip re-sending `OPTIONS` for matching subsequent requests — improving performance by avoiding a round trip per request. The tradeoff is that if the server's CORS policy changes (e.g., revoking an origin) before this cache expires, browsers that already cached the old preflight approval will continue allowing the now-revoked origin until the cache naturally expires, so overly long values create a window where a CORS policy change isn't actually enforced immediately for returning clients.

      A 307 redirect is used instead of 302 for a POST-heavy API gateway migration. Why would the team have made that specific choice?

      307 strictly guarantees the redirected request preserves the original method and body — critical for a POST that carries a payload, since some clients historically "helpfully" converted a redirected POST into a GET on a 302 (dropping the body), causing silent data loss. 307 removes that ambiguity entirely at the protocol level, which matters specifically because the migration involves re-pointing POST endpoints to a new host.

      How would you debug a production incident where users intermittently get logged out, and the suspected cause is cookie/CORS misconfiguration rather than an actual session expiry bug?

      Inspect the raw `Set-Cookie` response header for the exact `SameSite`/`Secure`/`Domain`/`Path` attributes actually sent (not just what the code intends to send — a misconfigured reverse proxy or CDN can strip/rewrite headers); check whether the affected users share a pattern (specific browser enforcing stricter third-party cookie policies, a specific subdomain, or an iframe/embedded context where third-party cookie blocking applies); and verify the preflight response's `Access-Control-Allow-Origin` exactly matches the request `Origin` byte-for-byte (including scheme and port) for every affected origin, since even a trailing slash or `www.` mismatch silently breaks the whole flow.

      Practice Assignments

      Beginner (30-60 min)

      Status code and header scavenger hunt

      Using your browser's Network tab, visit 5 different real websites and record: at least one 2xx, 3xx, 4xx response in the wild, the exact `Cache-Control` header on a static asset, and the `SameSite` attribute on at least 2 different cookies set by those sites.

      • Explain in one sentence why each status code you found makes sense for that request.
      • Note any cookie using `SameSite=None` and hypothesize why (likely a cross-site embedded widget/ad/analytics).

      Acceptance criteria: A table of findings with status code, header value, and a correct one-line explanation for each.

      Hints

      Open DevTools → Network tab → reload the page → click individual requests → check the Headers panel for both request and response headers.

      Bonus: Find a 304 Not Modified response and identify the `ETag`/`If-None-Match` pair that produced it.

      Intermediate (2-4 hrs)

      Build and break a CORS setup

      Stand up two tiny local servers on different ports (simulating different origins) — one serving a static HTML page with a `fetch()` call, one serving a JSON API. Deliberately misconfigure CORS first (missing header, wildcard + credentials), observe the exact browser console error, then fix it correctly including a credentialed cookie-based request.

      • Reproduce and screenshot/record at least 2 distinct CORS failure modes and their exact console error text.
      • Get a fully working credentialed cross-origin GET and POST, including correct preflight handling for the POST.

      Acceptance criteria: Working cross-origin fetch with cookies, plus a written explanation of each failure mode you deliberately caused and fixed.

      Hints

      Use any minimal HTTP server (even Node's built-in `http` module) on two different ports — different ports alone are a different origin, you don't need different hostnames.

      Bonus: Add a custom header to the request (e.g., `X-Request-Id`) and observe the preflight's `Access-Control-Request-Headers` picking it up automatically.

      Advanced (1-2 days)

      Design and document a full auth + CORS architecture for a split frontend/API

      Write a design document (no need to fully implement, but a working proof-of-concept is encouraged) for a system with `app.example.com` and `api.example.com`, covering: cookie attributes, CORS headers on every endpoint type (public vs authenticated), CSRF protection strategy, and how a mobile app (no cookies/CORS at all) would authenticate against the same API.

      • Explicitly justify SameSite choice and the accompanying CSRF mitigation.
      • Explain how the mobile client's auth strategy differs from the web client's and why CORS is irrelevant there.

      Acceptance criteria: A design doc that correctly distinguishes browser-enforced concerns (CORS, SameSite) from concerns that apply regardless of client (token validation, rate limiting), and a proof-of-concept demonstrating the web flow working end-to-end.

      Hints

      Mobile apps aren't browsers — there's no same-origin policy or CORS enforcement at all for a native HTTP client, so mobile auth is typically a bearer token in an `Authorization` header with no cookie/CORS concerns whatsoever.

      Bonus: Add rate limiting (429 + `Retry-After`) and show a client correctly backing off based on that header rather than retrying blindly.

      Quick Revision Cheat Sheet

      • Idempotent methods: GET, PUT, DELETE. Not idempotent: POST. PATCH depends on semantics.
      • 401 = unauthenticated ("who are you?"). 403 = unauthorized ("I know you, no.").
      • `fetch()` only rejects on network failure — always check `response.ok`/`status` yourself for HTTP errors.
      • CORS is browser-enforced; the request still reaches and is processed by the server regardless of whether the browser lets JS read the response.
      • Non-simple cross-origin requests trigger an automatic `OPTIONS` preflight checked against `Access-Control-Allow-*` response headers.
      • Credentialed cross-origin requires all three: `SameSite=None; Secure` cookie, server echoing a specific origin + `Allow-Credentials: true` (never `*` with credentials), and client `credentials: 'include'`.
      • `HttpOnly` blocks JS access to a cookie (XSS mitigation); `Secure` requires HTTPS; `SameSite=Lax` is the modern default CSRF mitigation.
      • `Cache-Control: no-store` never caches; `no-cache` caches but revalidates every time via ETag/Last-Modified.
      • 307/308 redirects strictly preserve method+body; 302 historically allowed a method change on redirect.
