    Bash & Terminal Basics: Navigation, Piping, Redirection, Environment Variables, Scripting

    ⏱ 2 hrs📍 Chapter 6 of 6

    One-line summary: The shell is a precise, composable programming environment built on pipes, exit codes, and text streams — knowing it cold means you debug a broken deploy or CI pipeline in two commands instead of googling the error message.

    On this page

      Why It Matters for a Senior Developer

      You SSH into servers, debug CI pipelines, and write one-off scripts constantly, and you've built muscle memory for the commands you use daily. The senior-level gap is usually around the parts used less often but that matter disproportionately when they come up: exact quoting rules, exit codes and `&&`/`||` chaining, what a pipe actually does under the hood (concurrent processes, not "run A then feed its output to B"), and why a script that works interactively fails in CI (non-interactive shells, different `PATH`, different working directory assumptions). Being fluent here is also what makes Node.js tooling, Docker, and CI/CD configuration (covered elsewhere on this site) legible instead of cargo-culted.

      Prerequisites

      No hard prerequisite within this topic, though it pairs naturally with Chapter 5 (Git) since Git is used from the shell daily. This is the final chapter of Web Fundamentals; from here the site continues into React Fundamentals.

      Core Concepts

      Navigation and the filesystem model

      Every process has a current working directory; `cd` changes it for the current shell only (not for a subprocess you spawn, since each process gets its own copy of this state at fork time). `.` is the current directory, `..` is the parent, `~` expands to `$HOME`, `-` after `cd` returns to the previous directory. Absolute paths start with `/`; relative paths are resolved against the current working directory — a huge source of CI bugs is a script assuming a working directory that differs between local runs and the CI runner's checkout location.

      Piping and redirection — what's actually happening

      A pipe (`|`) connects one process's `stdout` directly to another process's `stdin` via a kernel-managed buffer — critically, both processes run concurrently, not sequentially; the second process can start consuming output before the first has finished producing it (this is why `tail -f log | grep ERROR` works as a live stream, not a batch operation). Redirection (`>`, `>>`, `<`, `2>`, `&>`) operates on file descriptors: `1` is stdout, `2` is stderr, `0` is stdin. `command > file` truncates and writes stdout only (stderr still goes to the terminal); `command 2>&1` redirects stderr to wherever stdout is currently going (order matters: `> file 2>&1` sends both to the file, but `2>&1 > file` does not, because `2>&1` is evaluated first against the terminal, before stdout is redirected to the file).

      Exit codes and command chaining

      Every command returns an exit code: `0` means success, any nonzero means failure (the specific nonzero value is command-defined, e.g. `1` generic error, `127` command not found, `130` killed by Ctrl+C/SIGINT). `$?` holds the most recent command's exit code. `&&` runs the next command only if the previous succeeded (exit 0); `||` runs the next command only if the previous failed; `;` runs the next command unconditionally regardless of the previous result. This is the actual mechanism behind `set -e` in scripts (abort immediately on any nonzero exit) and why `cmd1 && cmd2 && cmd3` is a common "only proceed if every step succeeds" CI idiom.

      Environment variables and scope

      A variable set with `VAR=value` (no `export`) is a shell variable visible only to the current shell, not to any subprocess it spawns. `export VAR=value` promotes it to an environment variable, which is copied into the environment of every child process the shell spawns from that point on — but critically, a child can never modify its parent's environment back (environment inheritance is one-directional, copy-on-fork). This is precisely why `cd /some/path` inside a script run via `./script.sh` doesn't change your interactive shell's directory — the script runs in a child process/subshell with its own copy of the working directory state that's discarded when it exits; `source ./script.sh` (or `. ./script.sh`) instead runs the script's commands directly in your current shell, which is why `source` can change your actual shell's state while executing a script normally cannot.

      Basic scripting idioms

      A script begins with a shebang (`#!/usr/bin/env bash`) telling the OS which interpreter to use when executed directly. `set -euo pipefail` is the standard "fail fast" header for production scripts: `-e` exits immediately on any command's nonzero exit (with some well-known exceptions, e.g. inside `if` conditions), `-u` treats referencing an unset variable as an error instead of silently substituting empty string, `-o pipefail` makes a pipeline's exit code reflect the last command that actually failed rather than always just the final command's exit code (without it, `false | true` reports success, masking the real failure). Quoting matters precisely: `"$var"` preserves whitespace/prevents word-splitting and glob expansion of the variable's value; unquoted `$var` is split on whitespace and glob-expanded, which is the source of countless "works with simple filenames, breaks with a space in the path" bugs.

      How It Works Under the Hood

      When the shell runs `cmd1 | cmd2`, it forks two child processes, wires `cmd1`'s stdout file descriptor directly to `cmd2`'s stdin file descriptor via a pipe (a kernel ring buffer), and starts both roughly simultaneously — the OS scheduler interleaves them, with `cmd2` blocking on reads whenever the buffer is empty and `cmd1` blocking on writes whenever the buffer is full (backpressure), which is exactly why a pipe between a fast producer and a slow consumer doesn't buffer unboundedly in memory. Variable expansion, globbing, and word-splitting all happen in a specific order before the command actually runs — the shell first expands `$VAR`, then performs word-splitting on unquoted results, then glob-expands any remaining `*`/`?` patterns — which is precisely why quoting order/placement changes behavior and why `rm $file` with an unquoted variable containing a space silently tries to delete two separate paths instead of one.

      Code Examples

      # Exit codes and chaining
grep "ERROR" app.log && echo "found errors" || echo "no errors found"
echo $?   # exit code of the most recently run command

# BAD: pipeline failure is masked — reports success because `true` is the LAST command
false | true; echo $?     # => 0 (misleading!)

# GOOD: pipefail makes the pipeline's exit code reflect the real failure
set -o pipefail
false | true; echo $?     # => 1 (the actual failure from `false` is now visible)

      # Redirection order matters
command > file 2>&1    # both stdout AND stderr go to `file` (stderr redirected to wherever stdout NOW points)
command 2>&1 > file     # stderr goes to the terminal, ONLY stdout goes to `file`
                        # (2>&1 duplicates stderr to wherever stdout points AT THAT MOMENT — the terminal — BEFORE stdout is redirected)

# Quoting: the classic space-in-filename bug
file="my report.txt"
rm $file      # BAD: expands to `rm my report.txt` — tries to delete TWO files, "my" and "report.txt"
rm "$file"    # GOOD: expands to `rm "my report.txt"` — one correctly-quoted argument

      #!/usr/bin/env bash
set -euo pipefail   # fail fast: -e exit on error, -u error on unset var, -o pipefail catch pipe failures

# export makes a variable visible to child processes; plain assignment does not
DB_HOST="localhost"       # shell-local only — a spawned subprocess won't see this
export API_KEY="secret"   # child processes (e.g., `node server.js` run from here) WILL see this

deploy() {
  echo "Deploying with API_KEY=${API_KEY}..."
  ./run-migrations.sh && ./start-server.sh
}

      Real-World Production Scenario at Scale

      At scale

      A CI pipeline step runs `npm run build | tee build.log` to both display and save build output, followed by a deploy step gated on the previous step's success. For weeks, broken builds (npm exiting nonzero) still trigger deploys of stale/broken artifacts, because the pipeline checks the exit code of the overall line, which without `pipefail` reflects only `tee`'s exit code (`tee` almost always succeeds at writing a file, regardless of whether `npm run build` failed upstream in the same pipeline) — a direct real-world instance of the "masked pipeline failure" mechanism. The fix is a one-line `set -o pipefail` added to the CI script's shebang block, after which the pipeline correctly reports failure the moment `npm run build` fails, and the deploy step's `&&`-gated dependency correctly refuses to run. The postmortem's lasting takeaway, now in the team's CI style guide: every CI script must start with `set -euo pipefail`, no exceptions, because the cost of silently deploying a broken build vastly outweighs the rare cases where strict-fail behavior is inconvenient.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Leaving variable expansions unquoted (`rm $file`, `cp $src $dest`) — any value containing a space, glob character, or being empty/unset can cause word-splitting or glob-expansion into multiple unintended arguments, or (worse) deleting/copying the wrong thing entirely. Default to quoting every variable expansion (`"$file"`) unless you specifically need word-splitting/globbing.

      Gotcha

      Assuming a pipeline's exit code reflects the whole pipeline's success. By default it only reflects the last command — `set -o pipefail` is required to catch failures anywhere earlier in the chain, and it's missing from a huge fraction of real CI scripts until someone gets bitten by exactly this.

      • Start every non-trivial script with `#!/usr/bin/env bash` and `set -euo pipefail`.
      • Quote every variable expansion by default; only leave something unquoted when you deliberately want word-splitting/globbing.
      • Remember `export` is required for a child process to see a variable — plain assignment is shell-local only, and `cd`/variable changes inside a script run normally (not sourced) never affect your interactive shell.

      Interview Questions

      Basic

      What does `&&` do differently from `;` between two commands?

      `&&` only runs the second command if the first succeeded (exit code 0). `;` runs the second command unconditionally, regardless of the first's result.

      What file descriptor numbers correspond to stdin, stdout, and stderr?

      0 = stdin, 1 = stdout, 2 = stderr.

      What's the difference between `export VAR=value` and `VAR=value`?

      Plain assignment is a shell-local variable only; `export` additionally makes it part of the environment that gets copied into any child processes the shell spawns afterward.

      What does `$?` hold?

      The exit code of the most recently executed command.

      Why should you generally quote variable expansions, e.g. `"$file"` instead of `$file`?

      Unquoted expansions undergo word-splitting (on whitespace) and glob expansion, which can turn one intended argument into multiple, incorrect arguments — especially dangerous with filenames containing spaces.

      What does `cd -` do?

      Changes back to the previous working directory (the one you were in before the last `cd`).

      Medium

      Why doesn't `cd /some/path` inside a script change your interactive shell's working directory when you run the script normally?

      Running `./script.sh` executes it in a separate child process with its own copy of shell state (including working directory), inherited at fork time from the parent but never propagated back. Only `source ./script.sh` (or `. ./script.sh`) runs the script's commands directly within your current shell process, allowing changes like `cd` to persist.

      Explain why `false | true` reports exit code 0 by default, and how `set -o pipefail` changes that.

      A pipeline's default exit code is simply the last command's exit code — `true` always succeeds, so the pipeline reports success even though `false` (earlier in the pipe) failed. `pipefail` changes the pipeline's reported exit code to be the rightmost nonzero exit code among all commands in the pipe, or zero only if all of them succeeded.

      What's the practical difference between `command > file 2>&1` and `command 2>&1 > file`?

      Redirections are applied left to right. In the first, stdout is redirected to `file`, then `2>&1` duplicates stderr to wherever stdout currently points — which is now `file` — so both streams end up in the file. In the second, `2>&1` duplicates stderr to wherever stdout currently points — still the terminal at that point — and only afterward is stdout redirected to `file`, leaving stderr still going to the terminal.

      Why is a pipe not simply "run command A fully, then feed its complete output to command B"?

      Both processes in a pipe run concurrently, connected via a kernel buffer; the second process can begin consuming data as soon as any is available, and the first process blocks (backpressure) if it produces faster than the buffer can be drained. This is why something like `tail -f file | grep pattern` can stream matches live rather than waiting for `tail -f` (which never terminates) to "finish."

      What does `set -u` protect against, and give an example of a bug it would catch.

      It makes referencing an unset variable an immediate error instead of silently substituting an empty string. Example: a typo like `$DEPLOY_ENVIRONEMNT` (misspelled) would silently expand to empty string without `-u`, potentially causing a command like `rm -rf /app/$DEPLOY_ENVIRONEMNT/cache` to become `rm -rf /app//cache` — with `-u`, the script errors out immediately instead of executing a dangerously different command.

      Advanced

      Walk through, at the OS level, what happens when you run `cmd1 | cmd2 | cmd3` — process creation order, file descriptor wiring, and how the shell waits for completion.

      The shell parses the pipeline and creates pipe pairs (two file descriptors each: a read end and a write end) between each adjacent pair of commands, then forks a child process for each command, duping the appropriate pipe ends onto each child's stdin/stdout before exec'ing the actual program, and closing unused pipe ends in each child to avoid descriptor leaks and ensure EOF propagates correctly when a producer finishes. All three processes are started roughly together and run concurrently; the shell then waits on all of them, and the overall pipeline's reported exit status (absent `pipefail`) is the last command's exit status, since that's the one the shell is most directly "waiting on" as the pipeline's nominal result.

      Design a production deploy script's error-handling strategy: what should trigger immediate abort vs. what should be allowed to fail with manual follow-up?

      Use `set -euo pipefail` as the baseline so any unexpected failure aborts immediately rather than continuing into an inconsistent state. For steps that are expected to sometimes fail non-fatally (e.g., a best-effort cache warm), explicitly wrap them with `|| true` or an explicit `if ! command; then log_warning; fi` so a deliberate, documented exception exists rather than relying on globally disabling `-e`, which would silently hide genuinely unexpected failures everywhere else in the script.

      A script behaves correctly when run interactively but fails mysteriously in CI. What categories of differences between interactive and non-interactive/CI shells would you investigate first?

      PATH differences (CI runners often have a minimal PATH that doesn't include tools available in an interactive login shell's profile); working directory assumptions (CI checkouts may place the repo at a different path, or the step may run from a different directory than expected); environment variables that are normally set by an interactive shell's rc files (`.bashrc`/`.profile`) but never sourced in a non-interactive/non-login CI shell; and TTY-dependent behavior (some commands behave differently or prompt for input when there's no attached terminal, which can hang a CI job indefinitely instead of erroring immediately).

      Explain the exact order of shell expansions (brace, tilde, parameter/variable, command substitution, arithmetic, word-splitting, pathname/glob) and why getting this order wrong leads to subtly incorrect scripts.

      Bash performs expansions in a fixed order: brace expansion, tilde expansion, parameter/variable and command substitution and arithmetic expansion (these three left-to-right together), then word-splitting on the results of the previous step, then pathname (glob) expansion, and finally quote removal. Because word-splitting happens AFTER variable expansion but BEFORE globbing, a variable holding `*.txt` won't glob-expand from the variable's assignment — it only glob-expands if the `*` literally appears unquoted in the command line itself at the point globbing occurs, which is a frequent source of "why didn't my wildcard work when it's inside a variable" confusion.

      How would you make a Bash script safely idempotent for use in automated retries (e.g., a CI job that might be re-run after a transient failure)?

      Design every side-effecting step to check current state before acting rather than assuming a clean slate: use `mkdir -p` instead of `mkdir`, check for existing resources before creating them (or use upsert-style operations), make file writes atomic (write to a temp file then `mv` into place, since `mv` within the same filesystem is atomic) so a half-written file from an interrupted run is never mistaken for a complete one, and ensure any external API calls the script makes are themselves idempotent (e.g., via a client-supplied idempotency key) since the script itself re-running can't guarantee it wasn't partially successful on a prior attempt.

      Practice Assignments

      Beginner (30-60 min)

      Pipe and redirect scavenger hunt

      Using only shell built-ins and common utilities (`grep`, `wc`, `sort`, `uniq`, `head`), write 5 one-line pipelines against a real log file or `ls -la` output answering questions like "how many unique IP addresses appear" or "what are the 5 largest files in this directory."

      • At least one pipeline must redirect stderr separately from stdout into two different files.
      • At least one must demonstrate `set -o pipefail` catching a failure that would otherwise be masked.

      Acceptance criteria: All 5 pipelines produce correct answers, with the pipefail demonstration showing a before/after exit code difference.

      Hints

      `sort | uniq -c | sort -rn` is a classic "count and rank unique lines" idiom worth memorizing.

      Bonus: Chain a 6th pipeline that only proceeds to a second command if the first pipeline's grep found at least one match (using exit codes, not output content).

      Intermediate (2-4 hrs)

      Write a defensive deploy-simulation script

      Write a Bash script simulating a 4-step deploy (build, test, migrate, start) using functions, with `set -euo pipefail`, proper quoting throughout, and explicit handling for one step that's allowed to fail non-fatally (e.g., a cache warm-up).

      • Deliberately inject a failure into each of the 4 steps (one at a time, across 4 runs) and verify the script aborts at exactly the right point for 3 of them, and continues past the 4th (the non-fatal one) with a logged warning.
      • Use an exported environment variable to pass a value into a step that runs as a separate subprocess, and demonstrate it would NOT be visible if the variable weren't exported.

      Acceptance criteria: All 4 failure-injection scenarios behave exactly as designed, with clear log output distinguishing fatal aborts from the one tolerated failure.

      Hints

      Use `some_command || { echo "non-fatal failure, continuing"; }` for the one step allowed to fail, leaving `set -e`'s default fatal behavior intact for every other step.

      Bonus: Add a cleanup step using `trap ... EXIT` that always runs, even when the script aborts early due to `set -e`.

      Advanced (1-2 days)

      Build a small CI-style pipeline runner from scratch in Bash

      Write a script that reads a simple list of shell commands from a config file (one per line, or a tiny custom format) and runs them in sequence, logging each command's output to its own timestamped log file, aborting the whole run on the first failure (with pipefail-aware failure detection for any piped commands), and printing a final pass/fail summary table.

      • Must correctly detect failure inside a piped command within a step, not just a step's final command.
      • Must produce a clear, readable summary distinguishing which steps ran, which passed, which failed, and which were skipped due to an earlier abort.

      Acceptance criteria: Running against a config with a deliberately failing piped command correctly aborts remaining steps and reports them as skipped, not silently omitted.

      Hints

      Run each step as `bash -c "set -o pipefail; $step_command"` inside the runner so pipefail semantics apply per-step even though the runner script itself is doing the orchestration.

      Bonus: Add parallel execution for steps explicitly marked independent, using background jobs (`&`) and `wait`, while keeping sequential steps correctly ordered.

      Quick Revision Cheat Sheet

      • fd 0 = stdin, 1 = stdout, 2 = stderr. `2>&1` duplicates stderr to wherever stdout points AT THAT MOMENT — order of redirections matters.
      • A pipe runs both processes concurrently via a kernel buffer with backpressure, not sequentially.
      • `&&` = run next only on success; `||` = run next only on failure; `;` = run next unconditionally.
      • Plain `VAR=value` is shell-local; `export VAR=value` is inherited by child processes (one-directional, copy-on-fork).
      • Running `./script.sh` can't change your interactive shell's state (new process); `source ./script.sh` can.
      • Default pipeline exit code = last command's only; `set -o pipefail` makes it reflect any earlier failure too.
      • Always quote variable expansions (`"$var"`) to avoid word-splitting and glob-expansion surprises.
      • `set -euo pipefail` is the standard fail-fast header for production scripts.
      • Shell expansion order: brace → tilde → parameter/command/arithmetic → word-splitting → glob — this is why globs inside variables don't expand the way literal globs do.
