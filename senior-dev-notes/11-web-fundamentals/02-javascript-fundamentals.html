      Core Concepts

      Hoisting and the Temporal Dead Zone, precisely

      `var` declarations are hoisted to the top of their function (or global) scope and initialized to `undefined` immediately — you can reference a `var` before its declaration line and get `undefined`, not an error. `function` declarations are fully hoisted, including their body — you can call a hoisted function before its textual definition. `let`/`const` are hoisted too (binding exists from the start of the scope) but NOT initialized — accessing them before their declaration line throws a `ReferenceError`, because they sit in the Temporal Dead Zone (TDZ) from the start of the block until the declaration executes. This is why `typeof x` before a `let x` declaration throws, while `typeof y` before a `var y` declaration safely returns `"undefined"` — a frequently-asked precise distinction.

      Function expressions (`const f = function() {}`) are hoisted only as a `const`/`let`/`var` binding, not with their body — calling `f()` before that line throws (TDZ for `const`/`let`, or `TypeError: f is not a function` for `var`, since the binding exists as `undefined`).

      Scope chains and closures

      JS scoping is lexical: a function's scope is determined by where it's written, not where it's called. A closure is a function bundled with references to its surrounding lexical scope — critically, it captures variables by reference, not by value. The classic `var` loop bug: `for (var i = 0; i < 3; i++) { setTimeout(() => console.log(i), 0); }` logs `3, 3, 3` because all three closures share the single function-scoped `i`, which has finished the loop (value 3) by the time the callbacks run. Switching to `let` fixes it because `let` creates a new binding per iteration — each closure captures its own `i`. This single example tests hoisting, scope, and closures simultaneously, which is exactly why it's an interview staple.

      Type coercion: the actual rules, not "just use `===`"

      `==` performs type coercion before comparing; `===` never coerces. The precise coercion algorithm (Abstract Equality Comparison) matters: `null == undefined` is `true` (special-cased, they only equal each other and nothing else), but `null == 0` is `false` (null does NOT coerce to a number for `==`). `NaN === NaN` is `false` — `NaN` is the only value not equal to itself, which is why `Number.isNaN()` (precise) or `Object.is()` exists instead of relying on equality. `[] == false` is `true` (array → primitive via `toString()` → `""` → number `0`; `false` → number `0`; `0 == 0`). `"0" == false` is `true` for the same numeric-coercion reason. `[] == ![]` is `true` (`![]` is `false` since any object is truthy, then same path as above) — a classic "gotcha" trivia question, not something you'd ever write, but it tests whether you actually know the ToNumber/ToPrimitive algorithm versus memorizing "avoid `==`."

      Falsy values (exactly 8, memorize them precisely): `false, 0, -0, 0n, "", null, undefined, NaN`. Everything else, including `[]`, `{}`, and `"0"` (the string), is truthy — a very common trap since empty array/object "feel" like they should be falsy.

      Functions, `this` binding, and arrow functions

      `this` in a regular function is determined by how it's called (call-site binding), not where it's defined: implicit (`obj.method()` → `this` is `obj`), explicit (`.call`/`.apply`/`.bind`), `new` binding (new object), or default (`undefined` in strict mode, global object otherwise). Arrow functions have no own `this` — they lexically capture `this` from their enclosing scope at definition time, which is precisely why they fixed the old "`this` inside a callback is wrong" problem that used to require `.bind(this)` or `const self = this`.

      Four ways to invoke that change `this`, ranked by precedence: `new` binding > explicit binding (`call`/`apply`/`bind`) > implicit binding (method call) > default binding. `Function.prototype.bind` permanently locks `this` (and optionally partial arguments) and returns a new function — even a later `.call()` on the bound function cannot override the bound `this`.

      ES6+ features that actually changed how senior devs write JS

      Destructuring + defaults: `const { a, b = 5 } = obj;` — defaults only apply when the property is `undefined`, not for any other falsy value. Spread/rest: `{...obj}` does a shallow copy only — nested objects are still shared references, the classic "I thought I cloned it" bug. Optional chaining `?.` short-circuits to `undefined` the moment any link in the chain is nullish, without throwing. Nullish coalescing `??` only falls back on `null`/`undefined`, unlike `||` which falls back on any falsy value — `count ?? 0` correctly preserves a real `0`, while `count || 0` would incorrectly replace it. Promises/async-await are syntactic sugar over the microtask queue — `await` pauses the async function and yields to the event loop, but everything after it still runs as a microtask, which resolves before the next macrotask (setTimeout) even if scheduled earlier — a common "predict the console.log order" interview question.

      How It Works Under the Hood

      Before executing any code, the JS engine does a creation phase per execution context: it scans the scope for `var`/`function` declarations (hoisted, `var` → `undefined`, functions → fully defined) and `let`/`const` declarations (hoisted but left in the TDZ, uninitialized). Only then does the execution phase run top to bottom. This two-phase model is exactly why hoisting works the way it does, and it's the same reason a function declaration can be called "before" it appears in the file — by the time any code executes, the whole function already exists in memory.

      For the event loop: synchronous code runs first (the call stack), then all queued microtasks (Promise `.then`/`.catch`/`.finally`, `queueMicrotask`) drain completely before the engine picks up a single macrotask (`setTimeout`, `setInterval`, I/O callbacks). This is why `Promise.resolve().then(fn)` always logs before a `setTimeout(fn, 0)` scheduled earlier in the same tick — microtasks always fully drain between macrotasks, never interleaved partially.

      Code Examples

      // BAD: classic var-in-loop closure bug
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// logs: 3, 3, 3 — all closures share the same function-scoped `i`

// GOOD: let creates a fresh binding per iteration
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// logs: 0, 1, 2

      // Coercion precision — predict these without running them first
console.log(null == undefined);   // true  (special-cased to equal only each other)
console.log(null == 0);           // false (null does NOT coerce to a number for ==)
console.log(NaN === NaN);         // false (NaN is never equal to itself)
console.log(Number.isNaN(NaN));   // true  (precise check, no coercion)
console.log([] == false);         // true  ([] -> "" -> 0; false -> 0; 0 == 0)
console.log([1] == 1);            // true  ([1] -> "1" -> 1)

// ?? vs || — the bug that costs you a real zero
function getCount(count) { return count ?? 0; }  // preserves count === 0
function getCountBuggy(count) { return count || 0; } // WRONG: replaces 0 with 0 anyway but
// breaks for count = "" or count = false where you actually wanted to keep the falsy value
console.log(getCount(0));        // 0 (correct, unchanged)
console.log(getCountBuggy(0));   // 0 (looks the same here, bug shows up with "" or NaN inputs)

      // this binding precedence: new > explicit (call/apply/bind) > implicit > default
function whoAmI() { console.log(this?.name ?? 'default/undefined'); }
const obj = { name: 'obj', whoAmI };
obj.whoAmI();                        // "obj"            (implicit)
whoAmI.call({ name: 'explicit' });   // "explicit"       (explicit)
const bound = whoAmI.bind({ name: 'bound' });
bound.call({ name: 'tryOverride' }); // "bound"          (bind locks `this` permanently)

// Arrow functions capture `this` lexically — no own `this`
const timer = {
  seconds: 0,
  start() {
    setInterval(() => { this.seconds++; }, 1000); // `this` = timer, captured lexically
  }
};

      Real-World Production Scenario at Scale

      At scale

      A dashboard renders 500 rows, each with a "delete" button wired up in a loop using `var` inside an older codebase migrated from pre-ES6 JS. Every delete button ends up deleting the last row's ID because all closures share the single `var` loop variable — a bug that only manifests at scale (with 500 items, the probability a QA tester notices clicking row #3 deletes row #500 is high, but with 2 test rows it might go unnoticed). The fix is mechanical once you know the mechanism: switch `var` to `let` so each iteration gets its own binding, or explicitly capture the value in an IIFE/closure per iteration. This exact bug class — shared mutable loop variable captured by async callbacks — also shows up constantly in React (`useEffect` closures capturing stale state) and Node (async handlers in a `for` loop over `var`), making it one of the highest-value mental models in this entire chapter.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Assuming `{...obj}` or `[...arr]` deep-clones. Spread only shallow-copies the top level — nested objects/arrays are still shared by reference, so mutating `copy.nested.value` also mutates the original. Use `structuredClone(obj)` for a real deep clone when needed.

      Gotcha

      Using `||` for default values when `0`, `""`, or `false` are valid, intentional values — `||` treats all falsy values as "missing," while `??` correctly treats only `null`/`undefined` as missing.

      • Default to `const`, use `let` only when reassignment is truly needed, avoid `var` entirely in new code.
      • Memorize the 8 falsy values exactly — `[]` and `{}` are both truthy, a very common trap.
      • When in doubt about equality, use `===` and `Object.is`/`Number.isNaN` for the edge cases `===` doesn't cover (`NaN`, `-0` vs `0`).

      Interview Questions

      Basic

      What's the difference between `let`, `const`, and `var` in terms of scope?

      `var` is function-scoped (or global); `let`/`const` are block-scoped. `var` is hoisted and initialized to `undefined`; `let`/`const` are hoisted but left uninitialized in the TDZ until their declaration executes.

      What is the Temporal Dead Zone?

      The period between entering a scope and a `let`/`const` variable's declaration line executing, during which referencing that variable throws a ReferenceError rather than returning `undefined`.

      List the 8 falsy values in JavaScript.

      `false, 0, -0, 0n, "", null, undefined, NaN`. Everything else (including `[]` and `{}`) is truthy.

      What's the difference between `==` and `===`?

      `==` performs type coercion before comparing (Abstract Equality Comparison); `===` compares type and value with no coercion (Strict Equality Comparison).

      Does a closure capture a variable's value or a reference to it?

      A reference — the closure sees the variable's current value whenever it's accessed, not a frozen snapshot taken at closure-creation time.

      What does `?.` (optional chaining) do differently from just accessing a property directly?

      It short-circuits to `undefined` the moment any link in the chain is `null`/`undefined`, instead of throwing a TypeError trying to read a property off null/undefined.

      What's the difference between `??` and `||`?

      `??` falls back only when the left side is `null` or `undefined`. `||` falls back on any falsy value, incorrectly overriding intentional values like `0`, `""`, or `false`.

      Medium

      Predict the console output order: a `setTimeout(fn, 0)`, a `Promise.resolve().then(fn2)`, and a synchronous `console.log`, all triggered in the same tick.

      Synchronous log first, then the Promise's `.then` callback (microtask), then the setTimeout callback (macrotask) — microtasks always fully drain before the next macrotask runs, regardless of scheduling order.

      Why does `for (var i...) { setTimeout(() => console.log(i)) }` log the final value for every iteration, and how does switching to `let` fix it?

      `var` is function-scoped, so all iterations share one binding; by the time the timeouts fire, the loop has finished and `i` holds its final value. `let` creates a new binding scoped to each loop iteration, so each closure captures its own independent `i`.

      Explain why `[] == false` evaluates to `true` using the actual coercion steps.

      For `==` between an object and a boolean, the object is converted to a primitive first: `[].toString()` → `""`. Then `"" == false` coerces both to numbers: `Number("")` is `0`, `Number(false)` is `0`. `0 == 0` is `true`.

      What's wrong with `const clone = {...original}` if `original` has nested objects?

      Spread only copies top-level properties; any nested object/array value is copied by reference, so mutating `clone.nested.x` also mutates `original.nested.x`. Use `structuredClone()` or a deep-clone utility for full independence.

      Why do arrow functions make bad object methods when you need dynamic `this`?

      Arrow functions don't have their own `this` — they capture it lexically from the enclosing scope at definition time. As an object method, that's usually the outer scope (often the module or global), not the object itself, so `this.someProp` inside an arrow-function method won't refer to the object as expected.

      What does `Function.prototype.bind` return, and why can't a later `.call()` override its `this`?

      `bind` returns a brand-new function with `this` (and optionally leading arguments) permanently locked via an internal closure; calling `.call()`/`.apply()` on that bound function cannot change `this` because the bound function ignores the `this` it's invoked with and always substitutes the originally bound value.

      Advanced

      Explain the two-phase execution context model (creation + execution) and how it accounts for both hoisting and the TDZ in the same mechanism.

      In the creation phase, the engine scans the scope and allocates memory for every `var`/`function`/`let`/`const` binding before any code runs: `var` gets `undefined`, function declarations get their full body, and `let`/`const` get an uninitialized marker (TDZ). Execution then proceeds top to bottom; accessing a `let`/`const` binding while it's still marked uninitialized throws, which is exactly the TDZ, while `var`'s pre-initialization to `undefined` is why it never throws, only returns an unhelpful `undefined`.

      Why does `await` not block the thread, and what exactly happens to the rest of the async function after an `await`?

      `await` suspends the async function and returns control to the event loop immediately; the remainder of the function is scheduled to resume as a microtask once the awaited promise settles. The thread is never blocked — other synchronous code and queued microtasks/macrotasks can run while the await is pending, which is precisely why async/await is sugar over Promises and the microtask queue, not a new concurrency primitive.

      Design a memoization utility using closures that correctly handles both primitive and object arguments, and explain the WeakMap tradeoff.

      For primitive args, a closure over a plain `Map` keyed by a serialized argument string works and allows long-lived caching. For object arguments, serializing can be expensive/incorrect for cyclic structures; using a `WeakMap` keyed by the object reference itself avoids serialization and, critically, allows the cached entry to be garbage-collected once the object argument itself is no longer referenced elsewhere — a plain Map would leak memory by keeping every object argument alive forever.

      Why is `NaN === NaN` false, and what are the precise alternatives, including their difference from each other?

      IEEE 754 defines NaN as unordered with respect to everything including itself, so both `==` and `===` return false for any NaN comparison. `Number.isNaN(x)` checks strictly without coercion (recommended). The global `isNaN(x)` coerces its argument first, so `isNaN("hello")` incorrectly returns true. `Object.is(NaN, NaN)` returns true because `Object.is` uses SameValue semantics, which (unlike `===`) treats NaN as equal to itself and also distinguishes `+0` from `-0`, which `===` does not.

      A senior candidate says "I always use `===` so I never have coercion bugs." What's the gap in that claim?

      `===` eliminates cross-type coercion bugs but doesn't eliminate coercion elsewhere in the language — template literals, `+` concatenation, array `.toString()` in `join`/implicit conversions, truthy/falsy checks in `if`, and `??` vs `||` semantics are all coercion-adjacent behaviors `===` has no effect on. "Always use `===`" is necessary but not sufficient for coercion safety.

      Bonus: Add one snippet demonstrating TDZ inside a `switch` statement's single block scope — a commonly-missed edge case.

      Intermediate (2-4 hrs)

      Build a tiny Promise-based task queue from scratch

      Implement a `TaskQueue` class with an `add(fn)` method that queues async functions and runs at most `N` concurrently, resolving/rejecting each task's own promise appropriately, using only closures and native Promises (no libraries).

      • Must correctly handle a task that throws/rejects without breaking the queue for subsequent tasks.
      • Must demonstrate understanding of microtask ordering in at least one test case with mixed `setTimeout` and Promise-based tasks.

      Acceptance criteria: 10 tasks queued with concurrency limit 3 complete all successfully, with console output proving no more than 3 ever run simultaneously.

      Hints

      Keep an internal running counter and a pending array; when a task settles (via `.finally`), decrement the counter and pull the next pending task if under the concurrency limit.

      Bonus: Add a `pause()`/`resume()` method that stops pulling new tasks without cancelling in-flight ones.

      Advanced (1-2 days)

      Write a from-scratch deep-equal and deep-clone utility, handling the real edge cases

      Implement `deepEqual(a, b)` and `deepClone(a)` without using `JSON.stringify`/`structuredClone`, correctly handling: circular references, `Map`/`Set`, `Date`, `NaN` equality, and `-0` vs `0` distinction per `Object.is` semantics.

      • `deepEqual` must treat `NaN` as equal to `NaN` and `-0` as NOT equal to `0`, matching `Object.is` semantics, not `===`.
      • `deepClone` must correctly handle a circular reference without infinite recursion (e.g., using a `WeakMap` to track already-cloned objects).

      Acceptance criteria: A test suite covering at least 10 cases including circular refs, Map/Set, Date, NaN, and -0 all passes.

      Hints

      Use a `WeakMap<original, clone>` passed through recursive calls to detect and reuse already-cloned objects for cycles. For equality, special-case `Object.is` for primitives before recursing into object/array/Map/Set comparison.

      Quick Revision Cheat Sheet

      • `var` hoisted + initialized to `undefined`; `let`/`const` hoisted but TDZ (ReferenceError if accessed early); functions fully hoisted.
      • Closures capture variables by reference — the classic `var` loop bug happens because all iterations share one binding; `let` fixes it with per-iteration bindings.
      • 8 falsy values: `false, 0, -0, 0n, "", null, undefined, NaN`. `[]`/`{}` are truthy.
      • `==` coerces types before comparing; `===` never coerces. `null == undefined` is true; `null == 0` is false.
      • `NaN === NaN` is false; use `Number.isNaN()` or `Object.is()` for precise checks.
      • `??` falls back only on null/undefined; `||` falls back on any falsy value — don't use `||` for numeric defaults.
      • Spread/`{...obj}` is a shallow copy only — nested structures still share references.
      • `this` binding precedence: `new` > explicit (`call`/`apply`/`bind`) > implicit (method call) > default. Arrow functions have no own `this` (lexical capture).
      • Microtasks (Promises) fully drain before the next macrotask (`setTimeout`) runs — never partially interleaved.
