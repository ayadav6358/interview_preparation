    Code Reviews That Improve Teams

    ⏱ ~2 hrs📍 Chapter 2 of 7

    One-line summary: A code review's job is to catch real problems and raise the team's skill level over time — not to prove the reviewer is smart or to rubber-stamp everything to avoid conflict.

    On this page

      Why It Matters for a Senior Developer

      Junior and mid-level engineers review code to check it works. Senior engineers review code to prevent the next bug of this shape, teach a pattern that pays off for months, and protect the production system. How you review is also one of the most visible signals of your seniority — a thoughtful, specific, kind review builds trust and gets people requesting you as a reviewer; a nitpicky or harsh one makes people dread your name on their PR and quietly route around you.

      Why

      Code review is the highest-leverage, lowest-cost mentoring you'll ever do — it happens on real code, in the flow of actual work, dozens of times a month. Done well it scales your judgment across the whole team without you writing every line yourself.

      Prerequisites

      No hard technical prerequisite. Related: Mentoring Juniors (review feedback is often the seed of a longer mentoring conversation) and Technical Decision Making (for when a review comment turns into a real disagreement).

      Core Concepts

      What to actually look for

      In priority order — don't spend your first pass on formatting if there's a correctness bug three lines down:

      • Correctness — does it do what it claims? Edge cases, off-by-one, error handling, concurrency issues.
      • Safety — can this take production down? Missing rollback, unbounded resource use, a migration with no backward compatibility.
      • Design — is this the right shape, or does it bolt a special case onto something that should have been generalized / simplified instead?
      • Readability — will the next person (possibly you in 8 months) understand this without archaeology?
      • Style/nits — naming, formatting. Lowest priority; many teams automate this away with linters so humans don't have to spend review time on it.

      How to phrase feedback

      The content of a comment matters less than most people think; the framing determines whether it lands as useful or as an attack. Three concrete techniques:

      • Lead with the question, not the verdict when you're not 100% sure — "What happens if items is empty here?" invites a conversation; "This is broken" invites defensiveness, even when you're right.
      • Separate "must fix" from "consider" explicitly, in words, every time. A reviewer who doesn't label severity forces the author to guess whether a comment blocks merge — most authors will guess "yes" to everything and either over-fix or get frustrated.
      • Explain the "why," not just the "what." "Use a Map here" is a command. "Use a Map here — this is O(n) lookups inside a loop so it'll be O(n²) overall at the current list size" teaches something reusable.

      Calibrating review depth and being reviewed well

      Senior reviewers also know when not to dig deeper: a hotfix for an active incident gets a lighter review focused only on "will this make things worse," with a follow-up ticket for anything else noticed. A new architectural pattern that will be copy-pasted 50 times gets the deepest review you can give, because the cost of a mistake compounds.

      Being reviewed well is a skill too, and senior engineers model it: respond to every comment (even if just "done" or "good catch, fixed"), don't take "consider" comments as mandates to silently ignore either — engage with the reasoning, and if you disagree, say so with your own reasoning instead of just not addressing it. Silence on a comment reads as either ignoring the reviewer or secretly disagreeing without saying so — both erode trust.

      How It Works in Practice

      A healthy PR review loop: author opens PR with a clear description (what changed and why, not just what), reviewer does a first pass within a stated SLA (commonly same-day or next-morning for normal work, within the hour for incident fixes), comments are labeled by severity, author responds to every comment and pushes a fix or a counter-argument, reviewer re-reviews only the diff since last review (not the whole PR again), and the loop closes with an approval once no blocking comments remain. The whole thing should typically take 1-2 round trips for a normally-sized PR (under ~400 lines changed) — if it's taking 5+ rounds, the PR was probably too large or the design should have been discussed before code was written (see Chapter 1).

      Templates / Example Scripts

      # Bad vs good review comments

## Bad: verdict with no reasoning, reads as an attack
"This is wrong."

## Good: specific, explains why, suggests a fix
"This will throw if `user.address` is null (happens for guest checkouts —
 see CHECKOUT-88). Suggest: `user.address?.city ?? 'unknown'`."

---

## Bad: command with no context, no severity signal
"Use a Set instead."

## Good: explains the why, labels severity
"[consider] Switching `allowedIds` to a Set would make this O(1) lookup
 instead of O(n) — probably not urgent at current list size (~20 items)
 but worth it if this list grows. Not blocking."

---

## Bad: nitpick phrased as if it were a correctness issue
"This is terrible, nobody names things like this."

## Good: same nit, low-stakes framing, still gives a concrete alternative
"[nit] `d` is a bit terse for a variable that lives for 40 lines —
 maybe `daysSinceLastLogin`? Not blocking either way."

---

## Bad: question that's actually just a disguised demand
"Did you even test this?"

## Good: genuine, specific question that invites a real answer
"What happens here if the webhook arrives twice (provider retries on
 timeout)? Want to make sure this is idempotent — if it already is,
 a quick comment would help the next reader."

      Real-World Scenario at Scale (large team / org)

      At scale

      On a 50+ engineer org, inconsistent review rigor across teams becomes a real problem: team A blocks on style nits while team B rubber-stamps everything to hit velocity targets, and incidents start clustering in team B's code. The fix usually isn't "mandate stricter review" — it's making review norms explicit and shared (a short team-wide review guide: what's blocking vs not, SLA expectations, required reviewers for certain paths like auth or billing code via CODEOWNERS), and tracking a lagging signal like "incidents caused by code that was merged with zero review comments" to catch rubber stamping without having to police every individual review.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Re-reviewing a PR from scratch every time instead of just the new diff since your last pass. This re-raises comments the author already addressed, wastes everyone's time, and signals you didn't track what happened — the author starts dreading your re-reviews specifically.

      • Mistake: "drive-by" nitpicking on a PR that's already been through 3 rounds and is about to merge — adding a new low-priority comment at the last second resets the clock and frustrates everyone. If it's not blocking, file it as a follow-up ticket instead.
      • Mistake: approving with unaddressed "must fix" comments because you're worried about blocking someone's velocity. If it's actually a must-fix, block it — approving anyway teaches the team that "must fix" doesn't really mean fix.
      • Best practice: praise good decisions in the review, not just flag problems. "Nice catch wrapping this in a transaction" costs one sentence and reinforces the behavior you want repeated.
      • Best practice: if you've left the same category of comment on someone's last 5 PRs, stop leaving it in review and have a direct 1:1 conversation instead — review comments are a bad channel for a recurring pattern; it starts to feel like public correction.

      Interview Questions

      Basic

      What should a code reviewer prioritize first: correctness or style?

      Correctness and safety first (does it work, can it break production), then design, then readability, then style/nits last — many teams automate style away with linters so review time isn't spent on it.

      Follow-up: why automate style instead of reviewing it manually?
      What's the difference between a "must fix" and a "consider" comment, and why label it?

      "Must fix" blocks merge; "consider" is an opinion the author can take or leave. Labeling explicitly prevents the author from having to guess severity — unlabeled comments get either over-applied (wasting time) or ignored (missing real issues).

      Follow-up: what happens if you never label severity?
      Give an example of a bad review comment and rewrite it as a good one.

      Bad: "This is wrong." Good: "This will throw if the input is null (happens for guest users) — suggest a null check or default value." The good version is specific, explains why, and offers a path forward.

      Follow-up: why does explaining "why" matter more than just saying "what"?
      How should you respond to review comments on your own PR?

      Respond to every comment, even briefly ("done" or "good catch"). For "consider" comments you disagree with, explain your reasoning rather than silently ignoring them — silence reads as either not noticing or secretly disagreeing, both of which erode trust.

      Follow-up: what if you disagree with a "must fix" comment?
      Why is it bad practice to re-review a whole PR from scratch on every round?

      It re-raises already-addressed comments, wastes both people's time, and signals the reviewer didn't track prior feedback. Reviewers should review just the diff since their last pass.

      Follow-up: what tooling helps with this?
      When is it appropriate to do a lighter-than-normal code review?

      For an active-incident hotfix, where the priority is "will this make things worse" — deep design review can wait for a follow-up ticket once the fire is out.

      Follow-up: what's the risk of always reviewing lightly "to move fast"?
      Why should reviewers praise good decisions, not just flag problems?

      It reinforces behavior you want repeated at near-zero cost, and keeps reviews from feeling purely punitive, which improves how reviews are received over time.

      Follow-up: can over-praising cause its own problems?

      Medium

      A teammate keeps making the same mistake across several PRs. How do you handle it in review?

      Stop leaving it as a recurring review comment after the second or third occurrence — move it to a direct 1:1 conversation. Repeated public correction in review starts to feel punitive even when each individual comment is reasonable; a private conversation can address the root cause (missing context, a gap in understanding) more effectively.

      Follow-up: how do you raise it without sounding like you're scolding them?
      You approve a PR with several "consider" comments left unaddressed. Is that OK?

      Yes, if they're genuinely non-blocking — that's what "consider" means. The key is the label was honest: if you actually think it should block, it should be labeled "must fix" and not approved until resolved. Approving with unaddressed must-fix comments, on the other hand, undermines the severity system entirely.

      Follow-up: how do you avoid "consider" comments quietly becoming de facto requirements?
      How do you review code in a part of the codebase or language you're not an expert in?

      Focus comments on what you can genuinely assess (logic, naming, test coverage, whether it matches the stated intent) and ask genuine questions about the parts you're unsure of rather than either staying silent or bluffing confidence. Flag explicitly that a domain expert should also weigh in if the change touches something sensitive.

      Follow-up: should you still be a required approver on such PRs?
      A PR is 1,200 lines changed across 15 files. How do you review it effectively?

      If possible, ask the author to split it into smaller, independently reviewable PRs (e.g., refactor-only vs behavior-change). If it genuinely can't be split, review in passes by concern (correctness pass, then design pass) rather than file-by-file top to bottom, and consider a synchronous walkthrough for the parts that are hard to parse from the diff alone.

      Follow-up: what's the real cost of routinely allowing oversized PRs?
      How do you give critical feedback to someone more senior than you in a code review?

      Frame it as a genuine question when you're not certain ("What happens in case X?"), and when you are certain, state the issue plainly with your reasoning and let the seniority gap be irrelevant to the facts — a real bug is a real bug regardless of rank. Avoid either over-hedging to the point the issue gets missed, or being unnecessarily blunt in a way that reads as undermining.

      Follow-up: what if they push back and you're still not convinced?

      Advanced

      Tell me about a time you gave code review feedback that was poorly received. What happened and what would you do differently?

      (Scenario-based — strong answers name a specific comment, the actual reaction (defensiveness, a Slack escalation, silence), identify the real cause — usually missing severity labels, a verdict with no reasoning, or public criticism of a recurring pattern — and describe a concrete behavior change made afterward, e.g. moving recurring feedback to 1:1s or always leading with a question rather than a verdict.)

      Follow-up: how did you repair the relationship afterward?
      How would you design a code review policy for a team that's shipping lots of bugs despite "approved" reviews on every PR?

      First diagnose whether reviews are rubber-stamped (check for PRs with zero substantive comments that still had incidents), too style-focused (automate style away, redirect time to correctness/design), or structurally too fast (a same-day SLA being treated as "must approve same day" rather than "should get a first pass same day"). Add a required second reviewer or CODEOWNERS gate only for the highest-blast-radius paths, and track a lagging incident-correlation metric rather than just review-count metrics, which can be gamed.

      Follow-up: how do you avoid this turning into review theater — more process with the same rubber-stamping underneath?
      Describe a disagreement in code review that escalated beyond the PR itself. How was it resolved?

      (Scenario-based — strong answers describe recognizing when a review comment thread has gone back and forth twice with no convergence, pulling it into a synchronous conversation with the right people (sometimes including a tie-breaking senior/staff engineer), separating the technical disagreement from any personal friction, and reaching either a decision with documented reasoning or an agreement to disagree-and-commit.)

      Follow-up: how do you prevent the same disagreement from recurring on every future PR touching that code?
      How do you calibrate code review rigor differently for a startup moving fast versus a regulated enterprise environment?

      In a fast-moving startup, bias toward lighter review on low-blast-radius code and reserve deep review for genuinely risky paths (payments, auth, data integrity) — velocity matters and most mistakes are cheap to fix. In a regulated environment (healthcare, finance), mandate stricter review with audit trails, required multiple approvers, and explicit sign-off even on seemingly low-risk changes, because the cost of an undetected issue (compliance violation, data breach) is categorically higher and often not just a "ship a fix later" situation.

      Follow-up: how would you explain this difference to a junior engineer frustrated by "too much process" after joining from a startup?
      You're reviewing a PR from someone who consistently writes low-quality code, but they're under pressure from their manager to ship fast. How do you balance review rigor against not becoming the bottleneck everyone blames for missed deadlines?

      Separate must-fix (correctness/safety) from everything else ruthlessly in this case — block only on what would actually break something, and move quality-pattern feedback to a direct conversation (ideally with their manager looped in if it's a repeated, deadline-driven pattern) rather than blocking delivery on it. Make the tradeoff visible rather than silently absorbing it: if shipping now means taking on debt, say so explicitly and get it tracked, instead of either rubber-stamping or becoming an unaccountable blocker.

      Follow-up: how do you avoid becoming known as "the reviewer who always blocks," fairly or not?

      Practice Assignments

      Beginner (30-60 min)

      Rewrite bad review comments

      Below are 5 real-sounding bad review comments. Rewrite each as a good one using the framing techniques from this chapter (question vs verdict, severity label, explain the why).

      • "This is bad."
      • "Why would you do it this way?"
      • "lol no"
      • "Fix this."
      • "Did you even read the ticket?"

      Acceptance criteria: Every rewrite includes a severity signal and a reason, and none of them would make a teammate feel attacked reading it in a PR with 3 other people watching.

      Hints

      You'll need to invent plausible context (what the code does) for each one to write a specific comment — that's intentional; vague comments are vague partly because the reviewer didn't engage with specifics.

      Bonus: Rewrite one of them as a question instead of a statement, and explain when a question is the better choice.

      Intermediate (2-4 hrs)

      Review a real open-source PR

      Find an open, unreviewed or lightly-reviewed PR on a GitHub repo you use (ideally under 400 lines changed). Do a full review pass and leave real comments (or write them in a doc if you don't want to post publicly).

      • At least one correctness/safety-focused comment.
      • At least one design-level comment with reasoning.
      • Label severity on each comment.

      Acceptance criteria: You can explain, for each comment, why it's must-fix vs consider, and what you'd expect the author to do in response.

      Hints

      Pick a repo/language you actually know — reviewing something you don't understand will push you toward empty nitpicks.

      Bonus: If the PR gets a response, reflect on whether your framing landed the way you intended.

      Advanced (1-2 days)

      Write a team code review guide

      Write a one-to-two-page code review guide for a hypothetical 10-person team that currently has no shared norms — some reviewers block on nits, others rubber-stamp everything.

      • Define what's blocking vs non-blocking by category.
      • Define a review SLA (and what happens for incident hotfixes vs normal PRs).
      • Define when a second reviewer or CODEOWNERS gate is required.
      • Define how disagreements that stall in comments get escalated.
      Hints (no full solution)

      Think about what you'd actually want to measure 3 months later to know if the guide helped — not just "are people following it" but "did incident rates or review cycle time actually change."

      Quick Revision Cheat Sheet

      • Review priority: correctness → safety → design → readability → style.
      • Label severity explicitly: must-fix vs consider vs nit.
      • Explain the "why," not just the "what" — teaches something reusable.
      • Lead with a question when unsure; state plainly when certain.
      • Review the diff since last pass, not the whole PR from scratch each round.
      • Respond to every comment on your own PR — silence erodes trust.
      • Praise good decisions, not just flag problems.
      • Recurring pattern across PRs → move to a 1:1, not more review comments.
      • Scale rigor to blast radius — incident hotfix vs new shared pattern get different depth.
      • Automate style/formatting via linters; save human review time for substance.
