    Python Fundamentals

    📚 6 chapters⏱ ~10–12 hrs total

    You're a 10-year web developer who is fluent in JS/TS and has written "basic" Python before — enough to follow a tutorial but not enough to be fast or confident in an interview or a real codebase. This topic is the deliberate, slower-paced foundation layer: real Python syntax, control flow, data structures, files/modules, error handling, and a first taste of serving HTTP with Flask and FastAPI — each concept explicitly bridged from the JS/Node mental model you already have. It is the prerequisite for Python Intermediate, which assumes everything covered here is already second nature.

    Learning Outcomes

    • Write idiomatic Python (PEP 8, indentation-based blocks, naming conventions) without translating from JS syntax in your head.
    • Use Python's core data structures (list, tuple, dict, set) fluently, including comprehensions, and know exactly which JS structure each one replaces.
    • Read and write files safely with context managers, and structure code across multiple modules the way you'd split files in Node — without a bundler.
    • Handle errors the Python way (try/except/else/finally, custom exceptions) instead of writing try/catch-shaped Python that misses Python-specific idioms.
    • Stand up a minimal HTTP endpoint in both Flask and FastAPI and explain when you'd reach for which.
    • Debug Python code with print-debugging and pdb instead of reflexively reaching for console.log habits that don't map cleanly.

    🏆 Capstone Project: Build a CLI Expense Tracker (with an optional web face)

    Problem statement: Build a command-line expense tracker that stores expenses locally, supports basic reporting, is organized into real modules, handles errors without crashing on bad input, has a small automated test suite, and — optionally — exposes the same core logic through a tiny FastAPI (or Flask) HTTP endpoint so the exact same "business logic" is reachable from both a terminal and a browser/Postman request. This mirrors a very common real task: a script that later needs to grow a thin API layer without a rewrite.

    Required features:

    • Add an expense (amount, category, date, note) and persist it to a local JSON or CSV file.
    • List expenses with filters (by category, by date range) using list comprehensions, not manual loops where a comprehension reads better.
    • Summary report: total spend, spend by category (a dict built with a comprehension or collections.Counter/defaultdict).
    • Proper error handling: invalid amount, missing file on first run (auto-create it), malformed JSON — none of these should produce a raw traceback for the user; each should print a clear message.
    • Code organized into at least 3 modules (e.g. storage.py, reports.py, cli.py) with a single entry point, no business logic living directly in if __name__ == "__main__":.
    • A tests/ folder with pytest tests covering at least the storage layer and one report calculation, using a temp file fixture (not your real data file).

    Optional stretch: Wrap the same storage/reports modules with a FastAPI app exposing POST /expenses and GET /expenses/summary — no logic duplicated between the CLI and the API, both call the same functions.

    Tech stack suggestion: Plain Python 3.13 standard library (json, csv, argparse or click, pathlib), pytest for tests, FastAPI + uvicorn for the optional web layer.

    Milestones:

    1. Design the data model (what fields an expense has) and the on-disk JSON shape.
    2. Build storage.py: load/save with context managers, error handling for a missing/corrupt file.
    3. Build reports.py: filtering and aggregation using comprehensions and dict/set operations.
    4. Build cli.py: argument parsing, wiring storage + reports together, user-facing error messages.
    5. Write pytest tests for storage and reports against a temp file.
    6. (Optional) Add a FastAPI wrapper exposing the same two operations as HTTP endpoints.

    Evaluation checklist:

    • ☐ No bare except: anywhere — every except clause names a specific exception type.
    • ☐ No business logic duplicated between CLI and the optional API layer.
    • ☐ Running with a missing or corrupted data file degrades gracefully instead of crashing.
    • ☐ Tests pass against a temp file and don't touch your real expense data.
    • ☐ You can explain, out loud, why you chose with open(...) over manual open/close everywhere.
