    Data Types & Collections

    ⏱ ~2 hrs📍 Chapter 3 of 6

    One-line summary: Python gives you four core collection types — list, tuple, dict, set — where JS gives you two (array, object/Map/Set blurred together); the mutability rules, the comprehension syntax, and slicing are where most of the real learning (and interview questions) live.

    On this page

      Why It Matters for a Senior Developer

      Every real Python codebase you'll read leans heavily on comprehensions and the right collection type for the job — a senior Python engineer reaches for a set to deduplicate or test membership in O(1), a dict comprehension to reshape data, a tuple to signal "this is immutable and fixed-shape" the way you might reach for a readonly tuple type in TypeScript. If you only know "list for everything" the way you might lean on arrays for everything in quick JS scripts, you'll write correct but distinctly non-idiomatic, often slower code — and it reads as a tell in review and interviews alike.

      Why

      Comprehensions aren't just syntax sugar — they're how experienced Python developers think about transforming data, and interviewers use them as a quick signal of real fluency versus "ported from Python 101 tutorial." Mapping each one cleanly to the JS array method you already know (.map(), .filter()) is the fastest path to fluency here.

      Prerequisites

      Requires Python Syntax & Basics and Control Flow & Functions (comprehensions are loops in disguise). Continues into File I/O & Modules. Python Intermediate covers generators, which generalize the comprehension idea to lazy, memory-efficient iteration.

      Core Concepts

      Lists, tuples, dicts, sets — and mutability

      Python typeClosest JS equivalentMutable?Ordered?
      listArrayYesYes (insertion order)
      tupleNo direct equivalent — closest is a frozen/readonly array, or just a fixed-shape return valueNo — immutable once createdYes
      dictPlain object ({}) or MapYes (values; keys must be hashable/immutable)Yes — guaranteed insertion order since 3.7
      setSetYesNo — unordered, no guaranteed iteration order
      
nums = [1, 2, 3]            # list -- mutable, like a JS array
nums.append(4)                # same idea as .push()
point = (10, 20)              # tuple -- immutable, fixed shape
# point[0] = 99               # TypeError -- tuples don't support item assignment
user = {"name": "Alice", "age": 30}   # dict -- like a JS object, but keys can be any hashable type
tags = {"python", "backend", "senior"}  # set -- like JS's Set, unordered, deduplicated automatically

# JS equivalents:
# const nums = [1, 2, 3]; nums.push(4);
# const point = Object.freeze([10, 20]);   // closest JS gets to a real tuple
# const user = { name: "Alice", age: 30 };
# const tags = new Set(["python", "backend", "senior"]);

      Gotcha

      Dict keys must be hashable — meaning immutable. You can use a string, number, or tuple as a key, but never a list or another dict. JS object keys are always strings (or Symbols) regardless of what you pass, which silently coerces; Python raises a TypeError: unhashable type instead of coercing — this is Python being stricter, not more permissive.

      List, dict, and set comprehensions

      This is the single biggest syntax-level productivity unlock in this chapter. A comprehension is .map() + .filter() fused into one expression, read right-to-left in your head as "for each x in this iterable, (optionally if some condition), compute this expression."

      
nums = [1, 2, 3, 4, 5, 6]

squares = [n ** 2 for n in nums]                  # list comprehension
# JS: const squares = nums.map(n => n ** 2);

evens = [n for n in nums if n % 2 == 0]            # with a filter condition
# JS: const evens = nums.filter(n => n % 2 === 0);

even_squares = [n ** 2 for n in nums if n % 2 == 0]  # map + filter fused
# JS: const evenSquares = nums.filter(n => n % 2 === 0).map(n => n ** 2);

square_map = {n: n ** 2 for n in nums}              # dict comprehension
# JS: const squareMap = Object.fromEntries(nums.map(n => [n, n ** 2]));

unique_remainders = {n % 3 for n in nums}            # set comprehension -- dedupes automatically
# JS: const uniqueRemainders = new Set(nums.map(n => n % 3));

# Nested comprehension -- flatten a matrix (read the fors left to right, outer first)
matrix = [[1, 2], [3, 4], [5, 6]]
flat = [n for row in matrix for n in row]
# JS: const flat = matrix.flat();   -- or matrix.flatMap(row => row)

      Gotcha

      A comprehension that nests more than 2 levels deep, or mixes 3+ conditions, is a readability trap — at that point a regular for loop (or a named helper function) is more maintainable than a comprehension. "Can I write it as a comprehension" and "should I" are different questions; the same discipline applies to chaining .map().filter().reduce() too far in JS.

      Slicing and common collection methods

      Slicing (seq[start:stop:step]) works on lists, tuples, and strings uniformly and is more powerful than JS's .slice() because it supports a step and negative indices natively in the same syntax.

      
letters = ["a", "b", "c", "d", "e"]
print(letters[1:3])     # ['b', 'c']   -- like letters.slice(1, 3) in JS
print(letters[:2])       # ['a', 'b']   -- omit start = from the beginning
print(letters[2:])       # ['c', 'd', 'e'] -- omit stop = to the end
print(letters[-1])       # 'e'          -- negative index = from the end
print(letters[::-1])     # ['e','d','c','b','a'] -- step -1 = reversed, a very common idiom
print(letters[::2])      # ['a', 'c', 'e'] -- every 2nd element

# Common dict methods with no direct JS equivalent syntax
user = {"name": "Alice"}
print(user.get("age", 0))      # 0 -- default if key missing, like user.age ?? 0 but explicit
user.setdefault("tags", []).append("vip")   # get-or-create-then-mutate in one line

# Common set operations -- genuinely nicer than JS's Set, which lacks these operators
a = {1, 2, 3}
b = {2, 3, 4}
print(a & b)   # {2, 3} -- intersection
print(a | b)   # {1, 2, 3, 4} -- union
print(a - b)   # {1} -- difference

      How It Works Under the Hood

      Python's list is a dynamic array of pointers to objects (like a JS array under most engine implementations, conceptually), over-allocating capacity to amortize append cost — the same general strategy V8 uses for arrays. The real divergence is dict and set: both are hash tables, and since Python 3.7 a regular dict guarantees iteration in insertion order as a language-level guarantee (an implementation detail in 3.6 that became official in 3.7+) — this is different from a JS Map, which has always guaranteed insertion order, but similar in spirit. A Python tuple, unlike a list, is allocated as a fixed-size immutable structure — no resizing logic needed at all, which is part of why tuples have slightly less memory overhead and are hashable (usable as dict keys) when their contents are themselves hashable, while lists never are.

      Code Examples

      
# ---- BAD: using a list where a set is the right tool ----
seen = []
def is_duplicate_slow(item, seen=seen):
    if item in seen:          # O(n) membership check on a list
        return True
    seen.append(item)
    return False

# ---- GOOD: a set gives O(1) average membership checks ----
seen_set = set()
def is_duplicate_fast(item):
    if item in seen_set:       # O(1) average
        return True
    seen_set.add(item)
    return False

# ---- Tuple unpacking -- Python's answer to JS array destructuring ----
point = (3, 4)
x, y = point                    # JS: const [x, y] = point;
first, *rest = [1, 2, 3, 4]     # JS: const [first, ...rest] = [1, 2, 3, 4];
print(first, rest)                # 1 [2, 3, 4]

# ---- Dict comprehension to reshape a list of records (a very common real task) ----
users = [{"id": 1, "name": "Alice"}, {"id": 2, "name": "Bob"}]
by_id = {u["id"]: u["name"] for u in users}
# JS: const byId = Object.fromEntries(users.map(u => [u.id, u.name]));
print(by_id)   # {1: 'Alice', 2: 'Bob'}

      Real-World Production Scenario at Scale

      At scale

      A reporting service deduplicating millions of event IDs coming off a Kafka topic was originally written by a JS-background engineer as if event_id not in seen_list: seen_list.append(event_id), with seen_list as a plain Python list. Throughput degraded badly as the list grew, because membership testing on a list is O(n) — every single check scanned a growing list linearly. Switching seen_list to a set turned the membership check into an O(1) average-case hash lookup and restored throughput immediately, with a one-line change. The broader lesson for a senior engineer: picking list vs set vs dict isn't a style choice, it's an algorithmic complexity choice with direct production performance consequences.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Using a list for membership testing or deduplication out of JS habit (where arrays are the default go-to collection). Reach for a set whenever you need "have I seen this before" or "remove duplicates," and only use a list when order and duplicates both genuinely matter.

      Gotcha

      Trying to use a list or dict as a dict key ( cache[[1,2]] = "x") and hitting TypeError: unhashable type: 'list'. Convert to a tuple first if you need a composite, immutable key (cache[(1,2)] = "x") — this is a very common pattern for memoization keys.

      • Prefer dict.get(key, default) over a manual if key in d: ... else: ... when you just need a fallback value.
      • Use tuple unpacking (a, b = pair) instead of manual indexing (a = pair[0]; b = pair[1]) — it's the idiomatic equivalent of JS array destructuring.
      • Avoid comprehensions nested more than 2 levels or with 3+ conditions — fall back to a named loop for readability.

      Tradeoffs

      ApproachUse whenAvoid whenAlternative
      listOrdered, mutable sequence; duplicates allowed/expectedFrequent membership checks on large dataset (unordered) or keep a parallel set index
      tupleFixed-shape, immutable data (coordinates, a function's multi-return)Collection that needs to grow/shrinklist

      Interview Questions

      Basic

      What's the main difference between a list and a tuple?

      A list is mutable (can grow, shrink, have items reassigned); a tuple is immutable once created. Both are ordered.

      Follow-up: why does immutability make a tuple usable as a dict key while a list isn't?
      What's a Python list comprehension equivalent to in JS array methods?

      A fusion of .map() and .filter() — [x for x in items if cond] is items.filter(x => cond).map(x => x) shape, done in one pass, one expression.

      Follow-up: what's the closest JS equivalent of a dict comprehension?
      Can a Python set contain duplicate values?

      No — a set automatically deduplicates. Adding an already-present value is a silent no-op.

      Follow-up: what must be true about a value for it to be addable to a set at all?
      What does letters[::-1] do?

      Reverses the sequence — slicing with a step of -1 and default start/stop walks the whole sequence backward. This is an extremely common Python idiom for reversing a list or string.

      Follow-up: how would you reverse in place instead of creating a new reversed copy?
      Is dict iteration order guaranteed in Python?

      Yes, since Python 3.7 — dicts guarantee iteration in insertion order as an official language guarantee, not just an implementation detail.

      Follow-up: was this true in Python 3.6? What changed between 3.6 and 3.7 officially?
      How do you provide a default value when getting a possibly-missing dict key?

      d.get(key, default_value) — returns the default instead of raising KeyError if the key is absent.

      Follow-up: what's the difference between .get() and dict[key] when the key is missing?
      What are the three set algebra operators Python gives you that JS's Set lacks natively?

      & (intersection), | (union), - (difference) — and also ^ (symmetric difference). JS's Set has no operator or built-in method for any of these; you'd manually combine .has() checks with .filter().

      Follow-up: write the JS equivalent of Python's set intersection using only Set and array methods.

      Medium

      Why can't a list be used as a dictionary key, and what's the practical workaround?

      Dict keys must be hashable, and hashability requires immutability (a mutable object's hash could change after insertion, corrupting the hash table). Lists are mutable, so they're unhashable. The workaround is converting to a tuple first, which is immutable and hashable if its elements are.

      Follow-up: is a tuple containing a list still hashable? Why or why not?
      Why would you choose a set over a list for a deduplication task, beyond just "it's built in"?

      A set gives O(1) average-time membership checks and insertion via hashing, versus O(n) linear scans for list membership checks. For large or growing collections, this is the difference between a script finishing instantly and one that degrades quadratically as data grows.

      Follow-up: what's the Big-O of converting a list to a set, and does that cost ever outweigh the benefit?
      How would you deduplicate a list while preserving original order — why doesn't a plain set work for that?

      A plain set drops order entirely (not reliably sortable back to original order). The idiomatic order-preserving dedup is list(dict.fromkeys(items)) — dicts preserve insertion order since 3.7, and fromkeys naturally drops duplicate keys while keeping first-seen order.

      Follow-up: what's the time complexity of this dict.fromkeys() approach versus a naive nested-loop dedup?
      Explain what happens, step by step, when you write a nested list comprehension flattening a matrix: [n for row in matrix for n in row].

      The for clauses read left to right like nested loops written inline: the outer loop is for row in matrix, and for each row, the inner loop for n in row runs, yielding each n which gets appended to the result — equivalent to two nested for statements with the innermost expression appended each time.

      Follow-up: how would you flatten only rows where len(row) > 1, and where would that condition clause go?
      What's the actual memory/performance tradeoff between a tuple and a list of the same values?

      Tuples have slightly lower memory overhead (no over-allocated capacity for future growth, since they can't grow) and are faster to construct for fixed data, plus they're hashable if their contents are. Lists pay a small memory/time cost for mutability (resize logic, over-allocation) that's worth it only when you actually need to mutate.

      Follow-up: does Python ever reuse/cache small tuple objects the way it interns small integers?

      Advanced

      Explain how Python's dict achieves O(1) average lookup while also guaranteeing insertion order — aren't those two properties in tension?

      CPython's dict implementation (since 3.6 as an optimization, official since 3.7) separates the hash table (sparse array of indices into a dense array) from a dense array holding the actual key-value-hash entries in insertion order. Lookups still hash the key and probe the sparse table for O(1) average access; iteration walks the dense array, which happens to be insertion-ordered because entries are appended there as inserted. The two properties aren't actually in tension — they're served by two different underlying structures working together.

      Follow-up: what happens to the dense array's "order" when a key is deleted and a new one is added — does it reuse the slot?
      When does a Python list comprehension actually underperform a generator expression, and why would you choose one over the other for a large dataset?

      A list comprehension eagerly builds the entire result list in memory. A generator expression (same syntax, parentheses instead of brackets) produces values lazily, one at a time, with O(1) memory regardless of input size. For a large dataset you're only going to iterate once (e.g. summing, or feeding into another loop), a generator avoids materializing the whole intermediate list — this becomes critical at data sizes where the list comprehension would exhaust memory.

      Follow-up: can you use a generator expression result more than once? What happens if you try?
      Design a caching layer that needs composite keys (e.g. function name + sorted kwargs) — walk through the hashability constraints you'd need to satisfy.

      The key must be built from hashable, immutable pieces: convert the function name (string, already hashable) and the kwargs into a sorted tuple of (key, value) pairs — sorting first guarantees the same logical kwargs always produce the same tuple regardless of call-site ordering, and the tuple itself is hashable as long as every value inside it is also hashable (so you'd need to handle or reject unhashable argument values like lists/dicts being passed as kwargs).

      Follow-up: how does functools.lru_cache handle this exact problem internally?
      A teammate claims "Python sets and dicts have basically the same performance characteristics since a dict is just a set with values." Is that accurate, and what's actually shared vs different in CPython's implementation?

      Mostly accurate at a conceptual level — both are hash tables with nearly identical collision resolution (open addressing with perturbation) and both guarantee O(1) average membership/lookup. CPython's set and dict implementations are historically closely related (dict predates and the set implementation borrowed heavily from it). The real difference is just the payload: a set's table entries store only the hashed key, while a dict's entries store key+value+hash — a dict is conceptually "a set that also carries a value," which matches the teammate's claim reasonably well.

      Follow-up: given this similarity, why is there no dict-to-set O(1) "view" — why does converting between them cost O(n)?
      Explain why frozenset exists and when you'd reach for it over a regular set.

      frozenset is an immutable, hashable set — needed anywhere a set-like collection must itself be used as a dict key or stored inside another set (which requires hashability, which a mutable set lacks). It's the set-world equivalent of why tuple exists alongside list.

      Follow-up: can a frozenset contain a regular set as an element? Why or why not?

      Practice Assignments

      Beginner (30-60 min)

      Comprehension translation drill

      Take five JS array operations using chained .map()/.filter() and rewrite each as a single Python comprehension (list, dict, or set as appropriate), with a comment showing the original JS chain.

      • At least one must become a dict comprehension and one a set comprehension.
      • One must involve nested data (an array of arrays, or array of objects) requiring a nested comprehension or a comprehension over an attribute.

      Acceptance criteria: Each comprehension produces output identical to what the described JS chain would produce, verified by printing both the input and output.

      Hints

      For the dict comprehension from an array of objects, think of it as the Python equivalent of Object.fromEntries(arr.map(...)).

      Intermediate (2-4 hrs)

      Build a small in-memory "inventory" data processor

      Given a hardcoded list of product dicts (id, name, category, price, quantity), write functions using comprehensions and the right collection types to: get unique categories (set), build a category→total-value dict, find all products under a price threshold (list), and build an id→product lookup dict for O(1) access by id.

      • Every transform must use a comprehension, not a manual for-loop with .append().
      • Include a function that demonstrates the O(1) dict lookup vs. an O(n) linear search for the same lookup, timed with time.perf_counter() on a larger generated dataset.

      Acceptance criteria: All transform functions produce correct results against a small hand-verified dataset, and the timing comparison clearly shows the dict lookup winning on a larger (1000+ item) generated dataset.

      Hints

      Use random to generate the larger dataset for the timing test, and make sure both the dict-lookup and linear-search versions look up the same set of ids for a fair comparison.

      Advanced (1-2 days)

      Build a tiny immutable "record" type using tuples and compare it to a dataclass

      Implement a simple point/record type two ways: once as a plain tuple with manual index-based access, once using typing.NamedTuple (field-named tuples). Build a small suite of geometric functions (distance between two points, midpoint, is-collinear check for three points) that work against both representations, and write a short comparison of readability and safety.

      • Must demonstrate that both representations are still fundamentally immutable tuples under the hood.
      • Include pytest tests for each geometric function against known coordinate triples.
      • Written comparison (5+ sentences) on when you'd reach for NamedTuple vs a dataclass vs a plain tuple in real code.

      Acceptance criteria: All geometric functions produce mathematically correct results verified by the test suite, and work identically against both the plain-tuple and NamedTuple representations. No full solution here — this is meant to build real intuition about immutability tradeoffs.

      Quick Revision Cheat Sheet

      • list = mutable, ordered; tuple = immutable, ordered; dict = key-value, insertion-ordered since 3.7; set = unordered, unique, hashable items only.
      • List/dict/set comprehensions fuse .map() + .filter() into one expression.
      • Use a set for membership checks/dedup — O(1) average vs O(n) for a list.
      • Dict keys must be hashable (immutable) — convert composite keys to tuples.
      • Slicing seq[start:stop:step] supports negative indices and a step natively; [::-1] reverses.
      • Tuple unpacking (a, b = pair) is Python's array destructuring; *rest captures the remainder.
      • Set algebra operators: & intersection, | union, - difference, ^ symmetric difference.
      • dict.get(key, default) avoids manual existence checks; dict.fromkeys() dedupes a list while preserving order.
      • Avoid comprehensions nested more than 2 levels — fall back to a named loop for readability.
