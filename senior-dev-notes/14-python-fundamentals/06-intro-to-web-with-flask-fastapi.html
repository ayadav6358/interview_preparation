    Intro to Web with Flask/FastAPI

    ⏱ ~2 hrs📍 Chapter 6 of 6

    One-line summary: Flask is Python's Express — minimal, synchronous by default, decades of ecosystem maturity; FastAPI is Python's closer analog to a modern typed framework (think NestJS-with-Pydantic-validation) — async-native, type-hint-driven request validation, and automatic OpenAPI docs out of the box.

    On this page

      Why It Matters for a Senior Developer

      You already know how to build an HTTP endpoint — you've done it in Express or Fastify a hundred times. What you need here isn't "how does routing work" (you already have that instinct); it's the specific Python-world defaults and idioms: Flask's synchronous-by-default request handling, FastAPI's reliance on type hints as the actual request validation mechanism (not just documentation, unlike everywhere else you've seen Python type hints in this topic), and the dev-server/ASGI vs WSGI distinction that decides whether your framework can handle concurrent I/O-bound requests efficiently at all.

      Why

      Nearly every Python backend you'll read or extend in a real job — internal tools, ML model-serving endpoints, data platform APIs — is Flask or FastAPI. Knowing both, side by side, lets you correctly answer "which would you pick for this" in an interview instead of defaulting to whichever one you happened to see first in a tutorial.

      Prerequisites

      Requires every prior chapter in this topic, especially Control Flow & Functions (decorators) and Error Handling & Debugging (exceptions become HTTP error responses here).       Core Concepts

      A first endpoint in Flask

      Flask's decorator-based routing is the direct analog of an Express route handler — a function decorated with the path and method it serves.

      
# app_flask.py
from flask import Flask, request, jsonify

app = Flask(__name__)

@app.route("/hello/<name>", methods=["GET"])
def hello(name: str):
    return jsonify({"message": f"Hello, {name}!"})

@app.route("/users", methods=["POST"])
def create_user():
    data = request.get_json()           # parse JSON body -- like req.body in Express (with middleware)
    if not data or "name" not in data:
        return jsonify({"error": "name is required"}), 400   # (body, status_code) tuple
    return jsonify({"id": 1, "name": data["name"]}), 201

if __name__ == "__main__":
    app.run(debug=True, port=5000)        # dev server -- NOT for production

# JS/Express equivalent:
# app.get('/hello/:name', (req, res) => res.json({ message: `Hello, ${req.params.name}!` }));
# app.post('/users', (req, res) => {
#   if (!req.body?.name) return res.status(400).json({ error: 'name is required' });
#   res.status(201).json({ id: 1, name: req.body.name });
# });

      The same endpoint in FastAPI

      FastAPI uses the same decorator-routing idea, but request bodies are defined as typed Pydantic models — the type hints you learned in earlier chapters are not just documentation here, they're live runtime validation, which is the single biggest reason FastAPI feels different from everything else you've seen Python type hints do so far.

      
# app_fastapi.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class CreateUserRequest(BaseModel):     # Pydantic model -- the request body's shape AND validation
    name: str
    email: str | None = None             # optional field, Python 3.10+ union syntax

@app.get("/hello/{name}")
def hello(name: str):
    return {"message": f"Hello, {name}!"}

@app.post("/users", status_code=201)
def create_user(user: CreateUserRequest):   # FastAPI parses + validates the JSON body automatically
    if not user.name.strip():
        raise HTTPException(status_code=400, detail="name must not be blank")
    return {"id": 1, "name": user.name}

# run with: uvicorn app_fastapi:app --reload --port 8000
# OpenAPI docs are generated automatically at /docs -- zero extra config required

      Gotcha

      Unlike the type hints covered in earlier chapters (which Python ignores at runtime by default), FastAPI's Pydantic models DO validate at runtime — sending {"name": 123} where name: str is declared will raise a real 422 validation error automatically, before your function body even runs. This is the one place in mainstream Python web development where "the type hint is a real runtime contract," and it's specifically why FastAPI exists rather than people just adding manual validation to Flask.

      FastAPI handlers can be async def or plain def — if plain, FastAPI runs them in a thread pool automatically so they don't block the event loop, giving you Node-like concurrency for I/O-bound work without forcing every handler to be async. Flask historically has no native async request handling story (classic Flask is WSGI, synchronous-only); Flask 2.0+ added limited async def view support, but the underlying WSGI server still processes one request per worker — true concurrent I/O benefits still require an ASGI-based setup, which is part of why FastAPI (ASGI-native from day one) is the more common choice for I/O-heavy modern services.

      How It Works Under the Hood

      WSGI (Web Server Gateway Interface, what Flask is built on by default) defines a synchronous contract: a single callable that receives an environ dict and returns a response — one request occupies one worker (thread or process) for its entire duration, so concurrency comes from running multiple worker processes/threads (e.g. via Gunicorn), not from a single process handling many requests concurrently. ASGI (Asynchronous Server Gateway Interface, what FastAPI/Uvicorn is built on) defines an async contract compatible with asyncio's event loop, letting a single worker process handle many concurrent I/O-bound requests the way Node handles many concurrent connections on one event loop — a slow downstream call in one request doesn't block other requests from being served concurrently, as long as the handler actually awaits properly instead of doing blocking I/O inline. This WSGI-vs-ASGI distinction is the Python ecosystem's version of "sync server" vs "non-blocking event-loop server," and it's the real architectural reason FastAPI scales differently than classic Flask under I/O-bound load, independent of any type-hint/validation features.

      Code Examples

      
# ---- BAD: blocking I/O inside an async FastAPI handler defeats the whole point ----
import time
from fastapi import FastAPI

app = FastAPI()

@app.get("/slow-bad")
async def slow_bad():
    time.sleep(2)     # BLOCKING call inside an async function -- freezes the entire
    return {"status": "done"}   # event loop for 2s, stalling every other concurrent request

# ---- GOOD: use an async-native sleep/client, or run blocking work in a thread pool ----
import asyncio

@app.get("/slow-good")
async def slow_good():
    await asyncio.sleep(2)     # non-blocking -- other requests are served during this wait
    return {"status": "done"}

# For a genuinely blocking library you can't avoid (e.g. a sync DB driver),
# either use a plain `def` handler (FastAPI runs it in a thread pool automatically)
# or explicitly offload: await loop.run_in_executor(None, blocking_fn)

# ---- Error handling becomes HTTP responses -- direct line to Chapter 5's exceptions ----
from fastapi import HTTPException

class UserNotFoundError(Exception):
    pass

fake_db = {1: {"id": 1, "name": "Alice"}}

@app.get("/users/{user_id}")
def get_user(user_id: int):
    try:
        return fake_db[user_id]
    except KeyError:
        raise HTTPException(status_code=404, detail=f"User {user_id} not found")

      Real-World Production Scenario at Scale

      At scale

      A team ported an internal reporting tool from Flask to FastAPI expecting a free concurrency win, but latency under load barely improved — profiling revealed every handler was async def but called a synchronous ORM driver directly inside the handler body, which is a blocking call masquerading as async code. The event loop was being stalled exactly as badly as the WSGI version, just with extra async overhead layered on top for no benefit. The fix was either switching to the ORM's true async driver and properly await-ing calls, or — more pragmatically for a quick win — declaring the handlers as plain def so FastAPI's automatic thread-pool offloading handled the blocking calls correctly, which is exactly the lesson from the diagrams above: declaring a function async doesn't make blocking code non-blocking; you have to actually use non-blocking primitives throughout the call chain.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Calling a blocking function (time.sleep, a sync DB driver, requests.get) inside an async def FastAPI/asyncio handler. The async keyword doesn't make the code inside it non-blocking by magic — every blocking call inside still blocks the entire event loop, stalling every other concurrent request being served by that worker, which can be worse than a plain synchronous framework in surprising ways.

      Gotcha

      Running app.run(debug=True) (Flask) or Uvicorn's --reload dev server in production. Both are explicitly development-only servers — not hardened, not performant under real load, and debug mode can leak stack traces/source code to clients. Production needs a real WSGI server (Gunicorn) in front of Flask, or Uvicorn workers managed by something like Gunicorn's Uvicorn worker class for FastAPI, typically behind a reverse proxy.

      • Validate request bodies with Pydantic models (FastAPI) rather than manually checking request.get_json() keys (Flask) when you have the choice — it eliminates an entire class of manual validation bugs.
      • Return proper HTTP status codes explicitly — don't let every error default to a 200 with an error message buried in the JSON body.
      • Use FastAPI's automatically generated /docs during development to manually test endpoints instead of hand-writing curl commands for every change.

      Interview Questions

      Basic

      What's the Flask equivalent of an Express route handler?

      A function decorated with @app.route("/path", methods=["GET"]) (or FastAPI's @app.get("/path")) — the decorator registers the function as the handler for that path and HTTP method, the same role an Express app.get('/path', handler) call plays.

      Follow-up: how do you access a path parameter in Flask versus FastAPI?
      What's a Pydantic model, in one sentence?

      A class (inheriting from BaseModel) that declares typed fields and automatically validates/parses incoming data against those types at runtime, used by FastAPI to define and validate request bodies.

      Follow-up: what happens if a client sends data that doesn't match the Pydantic model's types?
      How do you run a Flask app in development versus how you'd run a FastAPI app?

      Flask: app.run(debug=True) or flask run. FastAPI: uvicorn app:app --reload (FastAPI itself doesn't include a built-in dev server runner the way Flask does — it needs an ASGI server like Uvicorn).

      Follow-up: why does FastAPI need a separate ASGI server while Flask ships its own dev server?
      Does FastAPI give you API documentation automatically?

      Yes — Swagger UI at /docs and ReDoc at /redoc are generated automatically from your route definitions and Pydantic models, with zero extra configuration.

      Follow-up: what underlying spec format powers this auto-generated documentation?
      What's WSGI, in plain terms?

      A synchronous interface standard between Python web servers and web applications — Flask is built on it by default. One worker handles one request fully before being free for the next.

      Follow-up: what's the ASGI equivalent, and what does it add?
      In Flask, how do you return a JSON response with a specific status code?

      Return a tuple: return jsonify({...}), 201 — Flask interprets a (body, status_code) tuple returned from a view function as the response with that status.

      Follow-up: how would you set a custom response header alongside this?

      Medium

      Why does declaring a FastAPI handler as async def not automatically make it non-blocking?

      async def only changes how the function is called (it must be awaited, and it can contain await expressions) — it doesn't transform blocking calls inside it into non-blocking ones. If the body calls a synchronous blocking function (time.sleep, a sync DB driver), that call still blocks the entire event loop for its duration, stalling every other request being served concurrently by that worker.

      Follow-up: what's the correct fix if you must call a genuinely blocking library from an async handler?
      Why might a plain `def` handler in FastAPI sometimes perform better under load than a poorly-written `async def` handler?

      FastAPI automatically runs plain (non-async) handlers in a thread pool, so a blocking call inside one only occupies a thread-pool thread, not the main event loop — other requests keep flowing through the event loop normally. A poorly-written async handler that blocks the event loop directly can stall ALL concurrent requests on that worker, which is strictly worse.

      Follow-up: is there a limit to how many concurrent plain-def handlers can run via the thread pool, and what happens when it's exhausted?
      Compare how Flask and FastAPI each handle an invalid request body (e.g. a required field missing).

      Flask does nothing automatically — you must manually check request.get_json() for required keys/types and return your own 400 response. FastAPI validates automatically against the Pydantic model's field types before your handler body even runs, returning a structured 422 response listing exactly which fields failed and why, with zero manual validation code.

      Follow-up: can you customize FastAPI's default 422 error response format, and why might you want to?
      Why is running a dev server (Flask debug mode, Uvicorn --reload) in production a security and reliability risk, specifically?

      Flask's debug mode can expose an interactive debugger in the browser on unhandled exceptions, potentially allowing arbitrary code execution if reachable by an attacker, and both dev servers are single-process/unoptimized for concurrent load and don't handle worker crashes/restarts gracefully the way a production process manager (Gunicorn with multiple workers, often behind a reverse proxy) does.

      Follow-up: what's the role of a reverse proxy (nginx) in front of either framework in a typical production deployment?
      How would you decide between Flask and FastAPI for a new internal service today?

      If the service is I/O-bound (calls other services/DBs frequently, needs to handle many concurrent requests efficiently) and the team can invest a bit in learning Pydantic/async patterns, FastAPI's ASGI foundation and built-in validation/docs pay off quickly. If it's a simple, low-concurrency internal tool, or the team has deep existing Flask/extension expertise and a tight timeline, Flask's simplicity and massive extension ecosystem can still be the pragmatic choice.

      Follow-up: are there scenarios where you'd actually run both side by side in the same organization, and why?

      Advanced

      Walk through exactly what happens, request by request, when 100 concurrent clients hit a FastAPI endpoint with a properly-awaited async DB call versus the same load against Flask with 4 Gunicorn workers.

      FastAPI/ASGI: a single worker's event loop accepts all 100 requests, issues the async DB call for each (non-blocking), and while each awaits its DB response, the loop services other requests' work — throughput is limited by how much actual CPU work each request needs between awaits, not by a fixed worker count. Flask/WSGI with 4 Gunicorn workers: only 4 requests can be "in flight" through a worker at once (each occupying a worker fully, blocking, until the DB responds); the remaining 96 requests queue until a worker frees up — throughput is bounded by worker count × (1 / blocking time per request), a fundamentally different scaling curve under I/O-bound load.

      Follow-up: at what point does adding more Gunicorn workers stop helping, and why?
      Explain how FastAPI's dependency injection system (Depends()) relates to, but differs from, a typical DI container in a framework like NestJS.

      FastAPI's Depends() declares a callable (sync or async) whose return value is injected into a route handler's parameter, resolved per-request, with support for nested dependencies and automatic caching within a single request if the same dependency is referenced multiple times. Unlike a full DI container (NestJS's, built on decorators + a module/provider graph resolved mostly at startup), FastAPI's version is request-scoped and function-based rather than class/module-graph based — closer to a request-scoped middleware chain with typed parameters than a true IoC container.

      Follow-up: how would you implement a dependency that needs cleanup after the request (like closing a DB session), analogous to a context manager?
      A team reports that their FastAPI service's latency degrades sharply under load despite low CPU usage and a correctly async DB driver. What would you investigate?

      Low CPU with degrading latency under concurrency, despite proper async DB usage, points toward something else blocking the event loop: a logging call doing synchronous file/network I/O, a third-party client library that looks async but calls a sync method internally, CPU-bound serialization (large Pydantic model validation/JSON encoding) running inline on the event loop instead of offloaded, or insufficient Uvicorn worker count relative to available cores (a single ASGI worker is still one process — you typically still run multiple Uvicorn/Gunicorn-managed workers for multi-core utilization, since asyncio concurrency within one process doesn't use multiple CPU cores).

      Follow-up: how would you profile an event loop to find exactly which call is blocking it, in a live service?
      Design the migration path for moving a mature Flask (WSGI) service to FastAPI (ASGI) incrementally, without a big-bang rewrite.

      A pragmatic path: mount new endpoints as FastAPI routes behind the same reverse proxy path prefix while leaving existing Flask routes untouched during a transition window (two services routed by path at the proxy layer), migrating endpoint-by-endpoint as each is touched for other reasons rather than rewriting everything at once; alternatively, some teams run Flask mounted inside an ASGI app via a WSGI-to-ASGI adapter as a stopgap, accepting that the Flask-mounted routes don't get ASGI's concurrency benefits until individually ported. The key senior-level judgment is recognizing this is an infrastructure/routing decision as much as a code-rewrite decision.

      Follow-up: what are the risks of running both frameworks side by side in production during a long transition period?
      Why does Pydantic's runtime validation make FastAPI's type hints fundamentally different in kind from the "documentation only" type hints discussed in earlier chapters of this topic — and where's the actual enforcement boundary?

      Pydantic generates real validators from the type hints at class-definition time and FastAPI invokes them specifically at the HTTP request boundary (parsing/validating the incoming JSON against the model) — so the enforcement is real but scoped: it validates external input crossing into your application, not arbitrary internal function calls elsewhere in your codebase, which still rely on mypy/pyright or manual checks exactly as covered earlier. This is the single most important "externally-facing boundary gets enforcement, internal code doesn't automatically" distinction to articulate clearly in a senior interview.

      Follow-up: would mypy catch a type error in internal code that calls a FastAPI-validated function with the wrong type, given that Pydantic already validates at the boundary?

      Practice Assignments

      Beginner (30-60 min)

      Build the same 3-route API in both Flask and FastAPI

      Build a tiny "notes" API (GET all notes, POST a new note, GET one note by id) twice — once in Flask, once in FastAPI — with in-memory storage (a plain list/dict, no real database needed).

      • FastAPI version must use a Pydantic model for the POST body.
      • Flask version must manually validate the POST body and return a 400 on missing fields.
      • Both must return proper status codes (200, 201, 404).

      Acceptance criteria: Both APIs behave identically from a client's perspective (same routes, same status codes, same JSON shapes) when tested with curl or the FastAPI /docs UI.

      Hints

      Keep the in-memory list as a module-level variable in both versions — don't worry about thread-safety or persistence for this exercise, just correctness of the routes.

      Intermediate (2-4 hrs)

      Demonstrate the blocking-call-in-async-handler bug yourself

      Build a FastAPI service with two endpoints: one that uses time.sleep() inside an async def handler (the bug), and one that uses await asyncio.sleep() correctly. Write a small concurrent client script (using httpx async client or multiple threads) that fires several requests at each endpoint simultaneously and measures total wall-clock time, proving the bad version serializes requests while the good version doesn't.

      • Must measure and print total wall-clock time for N concurrent requests against each endpoint.
      • Written conclusion (3-5 sentences) explaining the measured difference in your own words.

      Acceptance criteria: Your measured results clearly show the bad endpoint's total time scaling roughly linearly with request count, while the good endpoint's total time stays roughly flat (close to the single-request latency) regardless of concurrent request count.

      Hints

      Use asyncio.gather() with an async httpx client to fire requests truly concurrently from the client side — firing them sequentially from the client would hide the server-side behavior you're trying to demonstrate.

      Advanced (1-2 days)

      Wrap the Chapter capstone's expense tracker logic in a FastAPI layer

      Take the storage/reports modules from this topic's capstone project (or build a minimal equivalent if you haven't done the capstone yet) and expose them through a FastAPI app with POST /expenses (Pydantic-validated body) and GET /expenses/summary (returns category totals), without duplicating any business logic between the original CLI and the new API layer — both must call the exact same underlying functions.

      • The FastAPI layer must import and call the existing storage/reports functions directly — no copy-pasted logic.
      • Must return proper validation errors (422) for malformed POST bodies, and a sensible error for a corrupted/missing data file.
      • Include a pytest suite using FastAPI's TestClient covering at least the happy path and one validation-error path for each endpoint.

      Acceptance criteria: The API and the original CLI produce consistent results against the same underlying data file, and the pytest suite passes. No full solution here — the point is proving you can layer a web interface on existing logic without a rewrite.

      Quick Revision Cheat Sheet

      • Flask = Python's Express: minimal, WSGI (synchronous) by default, huge mature ecosystem.
      • FastAPI = async-native (ASGI), Pydantic-validated request bodies, automatic OpenAPI docs at /docs and /redoc.
      • FastAPI's type hints ARE enforced at runtime via Pydantic — unlike plain Python type hints elsewhere.
      • async def doesn't make blocking calls non-blocking — you must use genuinely non-blocking primitives (await) throughout.
      • Plain def FastAPI handlers run in a thread pool automatically — a safe default for blocking libraries.
      • WSGI (Flask): one worker per request for its full duration. ASGI (FastAPI/Uvicorn): one worker can serve many concurrent I/O-bound requests via the event loop.
      • Never run a dev server (debug=True, --reload) in production — use Gunicorn (Flask) or Gunicorn+Uvicorn workers (FastAPI).
      • Flask: manual JSON body validation. FastAPI: automatic 422 validation errors from Pydantic models.
      • Flask: jsonify(data), status_code tuple. FastAPI: just return the dict/model, set status via decorator argument.
