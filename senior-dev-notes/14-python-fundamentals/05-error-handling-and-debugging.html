    Error Handling & Debugging

    ⏱ ~1.5 hrs📍 Chapter 5 of 6

    One-line summary: Python's try/except/else/finally is a richer shape than JS's try/catch/finally, exceptions are the idiomatic control-flow tool for "this didn't work" (not an edge case to avoid), and pdb is Python's interactive debugger — the closest thing to Node's --inspect but terminal-native and always available.

    On this page

      Why It Matters for a Senior Developer

      Python's philosophy leans harder into "exceptions are normal control flow" than JS culture typically does — EAFP ("easier to ask forgiveness than permission") is the idiomatic default, versus the LBYL ("look before you leap") style more common in JS (checking if (x) before using x). Writing defensive if-checks everywhere instead of embracing try/except where appropriate is a visible tell of translated-from-JS code, and knowing when each style actually fits is a real senior-level judgment call, not just a stylistic preference.

      Why

      A bare except: (catching everything, including KeyboardInterrupt and SystemExit) is one of the most common and most dangerous Python anti-patterns in real codebases — it silently swallows bugs that should have crashed loudly. Interviewers watch for whether you reach for specific exception types or hide behind a catch-all, because it's a direct signal of production debugging maturity.

      Requires Control Flow & Functions and File I/O & Modules (context managers and exceptions interact constantly). Leads into Intro to Web with Flask/FastAPI, where exception handling becomes HTTP error responses. See Python Intermediate for logging and testing in depth.

      Core Concepts

      try/except/else/finally

      JS gives you try/catch/finally. Python adds a fourth clause, else, which runs only if the try block completed with no exception — genuinely useful for separating "the risky operation" from "what to do only on success," without nesting.

      
try:
    result = 10 / int(input("Enter a divisor: "))
except ValueError:
    print("That wasn't a valid number")
except ZeroDivisionError:
    print("Can't divide by zero")
else:
    print(f"Result: {result}")      # runs ONLY if no exception occurred
finally:
    print("Done processing")         # always runs, exception or not -- same as JS finally

# JS equivalent -- no `else` clause exists, success-only logic goes inline in `try`
# try {
#   const result = 10 / parseDivisor(input);
#   console.log(`Result: ${result}`);   // success logic mixed into the try block itself
# } catch (e) {
#   console.log("Something went wrong");   // JS often catches broadly by default
# } finally {
#   console.log("Done processing");
# }

      Gotcha

      JS's single catch clause catches everything by default, and you check e instanceof SomeError manually inside it if you need to differentiate. Python's multiple except clauses are matched top-to-bottom like a type switch — always catch the most specific exception types first, since Python stops at the first matching clause (a broader except Exception: placed first would shadow more specific clauses below it).

      Raising exceptions and custom exception classes

      Raising is raise ExceptionType("message") — the direct analog of JS's throw new Error("message"). Custom exceptions are just classes inheriting from Exception (or a more specific built-in), the same idea as extending Error in JS.

      
class InsufficientFundsError(Exception):
    """Raised when a withdrawal exceeds the available balance."""
    def __init__(self, balance: float, requested: float):
        self.balance = balance
        self.requested = requested
        super().__init__(f"Cannot withdraw {requested}, balance is only {balance}")

def withdraw(balance: float, amount: float) -> float:
    if amount > balance:
        raise InsufficientFundsError(balance, amount)
    return balance - amount

try:
    withdraw(100, 150)
except InsufficientFundsError as e:
    print(f"Failed: {e}")
    print(f"Shortfall: {e.requested - e.balance}")   # custom attributes are accessible on the exception object

# JS equivalent:
# class InsufficientFundsError extends Error {
#   constructor(balance, requested) {
#     super(`Cannot withdraw ${requested}, balance is only ${balance}`);
#     this.balance = balance;
#     this.requested = requested;
#   }
# }

      Re-raising while preserving context uses raise ... from ... — Python's explicit way to chain a new exception to the one that caused it, which shows up in tracebacks as "the above exception was the direct cause of the following exception," similar in spirit to setting error.cause in modern JS (Error's cause option, ES2022+).

      Print-debugging vs pdb

      Print-debugging in Python is identical in spirit to console.log debugging in JS — quick, universally understood, but noisy and requires editing code. pdb (Python DeBugger, built into the standard library, no install needed) gives you breakpoints, step-through execution, and live variable inspection — the terminal-native equivalent of Node's --inspect + Chrome DevTools, or VS Code's JS debugger.

      
def process(items):
    total = 0
    for item in items:
        breakpoint()      # built-in since Python 3.7 -- drops into pdb right here
        total += item["value"]
    return total

# At the breakpoint prompt (pdb), common commands:
#   n       -- next line (step over)
#   s       -- step into a function call
#   c       -- continue execution until the next breakpoint
#   p item  -- print the value of `item`
#   pp item -- pretty-print item (useful for dicts/lists)
#   l       -- list source code around the current line
#   q       -- quit the debugger

      breakpoint() is the modern, idiomatic entry point (3.7+) — it's a thin wrapper that by default calls pdb.set_trace(), but respects the PYTHONBREAKPOINT env var so it can be redirected to a richer debugger (like ipdb) without changing your code.

      How It Works Under the Hood

      When an exception is raised, CPython constructs an exception object and begins unwinding the call stack, looking for a matching except clause in each enclosing try block — this unwinding builds the traceback you see printed, which is literally a linked list of frame records (file, line, function) walked from the raise point outward. Python's except clause matching uses isinstance() checks against the exception's class hierarchy, which is exactly why exception class inheritance matters for catching: except Exception: catches any subclass of Exception, including your custom ones, because it's a real class hierarchy check, not string matching. pdb works by hooking Python's trace function (sys.settrace) — the same low-level hook that coverage tools and profilers use — to pause execution and give you an interactive prompt at a specific line, line-by-line stepping being implemented as toggling trace callbacks on/off per frame.

      Code Examples

      
# ---- BAD: bare except swallows everything, including bugs and Ctrl+C ----
def load_data_bad(path):
    try:
        with open(path) as f:
            return f.read()
    except:                      # catches EVERYTHING -- including KeyboardInterrupt, SystemExit, typos
        return None                # silent failure -- you'll never know why this returned None

# ---- GOOD: catch specific exceptions, let unexpected ones propagate loudly ----
def load_data_good(path):
    try:
        with open(path, encoding="utf-8") as f:
            return f.read()
    except FileNotFoundError:
        print(f"Config file not found: {path}, using defaults")
        return None
    except PermissionError:
        print(f"No permission to read: {path}")
        raise                      # re-raise -- this one shouldn't be silently handled

# ---- EAFP vs LBYL: the idiomatic Python style ----
data = {"name": "Alice"}

# LBYL (JS-habit style) -- check first, then act
if "age" in data:
    age = data["age"]
else:
    age = 0

# EAFP (idiomatic Python) -- try the operation, handle the failure
try:
    age = data["age"]
except KeyError:
    age = 0

# In practice, .get() is even more idiomatic than either for this specific case:
age = data.get("age", 0)

      Real-World Production Scenario at Scale

      At scale

      An API integration script wrapped every external call in a bare except: continue "to be safe" during a demo sprint, and that pattern shipped to production unchanged. Weeks later, a downstream API started returning malformed responses that triggered a real bug in the parsing code — but because the bare except silently swallowed it and moved on, the team had no idea data was being silently dropped for days, discovered only when a business stakeholder noticed missing records in a report. The fix: replace every bare except with specific exception types, log unexpected failures loudly with logging.exception() (which captures the full traceback), and let truly unexpected exceptions propagate and alert rather than vanish. This incident is the canonical argument for why "catch everything, just in case" is actively dangerous in production code.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Using a bare except: (or the nearly-as-bad except Exception: with no logging) to silence errors "temporarily." This hides real bugs, including ones that should crash the program loudly (a bare except even catches KeyboardInterrupt, meaning Ctrl+C might not stop your script). Always name the specific exception type(s) you expect, and log or re-raise anything else.

      Gotcha

      Writing heavily nested if-checks to avoid exceptions entirely (pure LBYL) out of a JS-flavored defensive-coding habit, when the idiomatic and often more correct Python style is EAFP — attempt the operation and handle the specific failure. This matters especially with dict/attribute access and concurrent code, where an LBYL check-then-act can have a race condition between the check and the act that EAFP's single atomic attempt avoids.

      • Prefer logging.exception("message") over print(e) in except blocks — it captures the full traceback automatically and integrates with real log aggregation.
      • Use raise ... from ... when re-raising a different exception type, to preserve the original cause in the traceback for debugging.
      • Reach for breakpoint() instead of sprinkling print() statements when you need to inspect multiple variables or step through logic — it's faster once you know the basic pdb commands.

      Interview Questions

      Basic

      What does the else clause on a try/except do, and when does it run?

      It runs only if the try block completes with no exception raised — it's for success-only logic that you want to keep separate from both the risky operation and any cleanup in finally.

      Follow-up: why not just put that code directly after the try/except block instead of in else?
      What's wrong with a bare except: clause?

      It catches every exception, including ones you almost never want to catch silently, like KeyboardInterrupt and SystemExit — and it hides the actual error type, making debugging much harder. Always name specific exception types.

      Follow-up: what's the difference between a bare except and except Exception?
      How do you raise an exception in Python, and how does it compare to JS?

      raise ExceptionType("message") — directly analogous to JS's throw new Error("message").

      Follow-up: what's the minimum you need to define a custom exception class?
      What is breakpoint() and when was it introduced?

      A built-in function (since Python 3.7) that drops into the pdb interactive debugger at the line it's called, without needing to import pdb manually.

      Follow-up: how would you redirect breakpoint() to use a different debugger like ipdb?
      What's the difference between EAFP and LBYL?

      EAFP ("easier to ask forgiveness than permission") attempts an operation and handles failure via except; LBYL ("look before you leap") checks a condition before acting. Python culture favors EAFP more than typical JS culture does.

      Follow-up: give an example where LBYL is clearly the better choice despite Python's EAFP preference.
      Does Python's finally run even if the try block has a return statement?

      Yes — finally always runs before the function actually returns, even if both the try and finally blocks contain return statements (in which case finally's return wins, which is a notorious gotcha in its own right).

      Follow-up: what happens if try returns a value and finally also returns a different value?

      Medium

      Why must more specific except clauses come before more general ones in the same try statement?

      Python checks except clauses top-to-bottom and uses the first one whose type matches (via isinstance) the raised exception. If a general clause like except Exception: is listed first, it will catch and handle exceptions that a more specific clause below it was meant to handle — the specific clause becomes unreachable dead code.

      Follow-up: does Python raise a warning or error if you order except clauses incorrectly like this?
      What does raise NewError("msg") from original_error actually do, and why use it over a plain raise inside an except block?

      It sets the new exception's __cause__ attribute to original_error, which the default traceback printer shows as "The above exception was the direct cause of the following exception" — preserving the full causal chain for debugging, versus a plain re-raise of a different exception type which would otherwise hide what originally triggered it (though Python does still attach it as __context__ automatically even without `from`, just with different wording in the traceback).

      Follow-up: what's the difference between __cause__ and __context__ specifically?
      Why is EAFP sometimes the only correct choice, not just a style preference, in concurrent code?

      An LBYL check-then-act (e.g. "if key in dict: then access it") has a window between the check and the action where another thread could change the state — a classic TOCTOU (time-of-check to time-of-use) race condition. EAFP's single atomic attempt-and-handle-failure avoids that window entirely for many built-in operations.

      Follow-up: give a concrete concurrent scenario where dict.get() (an LBYL-flavored EAFP hybrid) is still safe despite this concern.
      How does pdb's step ("s") differ from next ("n") when the current line is a function call?

      n (next) executes the current line as a whole and stops at the next line in the same frame, treating any function call on that line as a black box. s (step) steps into the function call itself if the current line calls one, pausing at its first line — the pdb equivalent of "step over" vs "step into" in a GUI debugger like Chrome DevTools or VS Code.

      Follow-up: what does "step out" / "finish" do in pdb, and when would you use it after stepping into a function you didn't mean to?
      Design a custom exception hierarchy for a payments module with at least 3 distinct failure categories, and explain how callers would use it.

      Define a base PaymentError(Exception), then subclasses like InsufficientFundsError(PaymentError), CardDeclinedError(PaymentError), and GatewayTimeoutError(PaymentError). Callers that only care about "something went wrong with payment" can catch the base PaymentError broadly; callers that need to react differently (retry on timeout, show a specific message on decline) catch the specific subclasses — the hierarchy gives both coarse and fine-grained catching for free, the same design principle as a custom Error subclass hierarchy in a well-structured JS/TS codebase.

      Follow-up: should GatewayTimeoutError inherit from a built-in exception type as well, via multiple inheritance? Why or why not?

      Advanced

      Explain exactly how CPython builds a traceback object during exception propagation, and what information it preserves at each frame.

      Each time an exception propagates out of a frame, CPython prepends a new traceback node recording that frame's code object (file name, function name, line number) to a linked list attached to the exception's __traceback__ attribute — so the final traceback, printed outermost frame first... actually innermost (raise point) last in the default printed order, reflects the exact call chain the exception unwound through, which is why you can read a traceback bottom-up to find the originating line.

      Follow-up: what happens to the traceback object's reference chain if you store a caught exception in a long-lived variable — any memory leak risk?
      Why does chaining exceptions with bare re-raise still show "During handling of the above exception, another exception occurred" even without an explicit `from` clause?

      Python automatically sets the new exception's __context__ to whatever exception was currently being handled at the point of the new raise — this is implicit context chaining, distinct from the explicit __cause__ set by raise X from Y. Both get surfaced in the printed traceback, with slightly different wording depending on which attribute is set, which is why the two chaining mechanisms exist side by side rather than one subsuming the other.

      Follow-up: how would you suppress the implicit context entirely if you intentionally want a "clean" new exception with no chain?
      How does sys.settrace (which pdb relies on) affect the performance of code it's attached to, and why is this relevant to production debugging decisions?

      Once a trace function is installed, CPython calls it on nearly every line executed (and every function call/return/exception event) across every frame in that thread, which adds meaningful per-line overhead — this is why running code under pdb or a profiler based on the same hook is measurably slower than normal execution, and why you'd never leave a trace function active in a production hot path; you'd use targeted logging or sampling profilers (py-spy) that don't rely on per-line tracing instead.

      Follow-up: how does py-spy avoid this overhead while still providing stack sampling in production?
      A teammate wants to use exceptions for ordinary control flow in a hot loop (e.g. StopIteration-style signaling for every iteration) — is this actually a performance concern in CPython, and how would you evaluate it?

      Exception raising/handling in CPython has real but historically shrinking overhead (3.11+ introduced "zero-cost" exception handling for the non-raising path specifically, so a try block that doesn't raise is nearly free; the raise path itself still costs more than a simple conditional). For a hot loop raising exceptions on every iteration as the normal case rather than the rare case, you'd benchmark with realistic data rather than assume — but idiomatically, exceptions should signal exceptional/rare conditions, and iterator protocols already use StopIteration internally in a way that's optimized at the C level, which is different from hand-rolled per-item exception signaling in pure Python code.

      Follow-up: what did Python 3.11's "zero-cost exceptions" change specifically about the non-exceptional path's bytecode?

      Quick Revision Cheat Sheet

      • try/except/else/finally — else runs only when no exception occurred; Python adds this clause beyond JS's try/catch/finally.
      • Never use a bare except: — always name specific exception types.
      • Order except clauses from most specific to most general — the first match wins.
      • Custom exceptions are just classes inheriting from Exception (or a more specific type).
      • Use raise ... from ... to explicitly chain a new exception to its cause.
      • EAFP (try/except) is often more idiomatic than LBYL (if-check first) in Python, especially under concurrency.
      • breakpoint() (3.7+) drops into pdb without importing it manually.
      • pdb commands: n next, s step into, c continue, p/pp print, l list source, q quit.
      • Use logging.exception() instead of print(e) to capture full tracebacks.
      • Never ship a breakpoint() call to production code.
