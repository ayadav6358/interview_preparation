    Python Syntax & Basics

    ⏱ ~1.5 hrs📍 Chapter 1 of 6

    One-line summary: Python trades braces and semicolons for significant whitespace, trades const/let/var for plain name binding, and runs as a script interpreted top-to-bottom — the syntax looks sparse compared to JS, but every omission is a deliberate design choice you need to internalize, not just memorize.

    On this page

      Why It Matters for a Senior Developer

      You will read far more Python than you write for the first few months in any Python-adjacent role — data pipelines, ML notebooks, internal tooling, infra scripts. If you're still mentally inserting semicolons or hunting for braces that don't exist, every code review and every pairing session is slower than it needs to be. The goal here isn't "learn Python syntax" in the abstract; it's to get the muscle memory fast enough that reading a 200-line Python file feels as automatic as reading a 200-line TypeScript file.

      Why

      Interviewers calibrate "how comfortable are you actually in Python" within the first two minutes, usually by watching whether you reach for the right idiom without thinking (f-strings, snake_case, no semicolons) or write JS-shaped Python with the serial numbers filed off. Getting the basics automatic is what buys you the mental bandwidth to focus on the actual problem being asked.

      Prerequisites

      None beyond having Python 3.13 installed and a terminal. This is the first chapter of Python Fundamentals; later chapters build directly on this one: Control Flow & Functions, Data Types & Collections. Once this whole topic is comfortable, continue to Python Intermediate.

      Core Concepts

      Indentation is the block syntax — there are no braces

      In JS, { } delimit a block and whitespace is cosmetic — you could write an entire Node app on one line (badly, but it would run). In Python, indentation is the block delimiter. The interpreter tracks indentation level as a real part of the grammar, not a linter preference.

      
# Python: indentation defines the block
if True:
    print("inside the if")   # 4 spaces — this line belongs to the if
    print("still inside")
print("outside the if")      # back to column 0 — outside the block

# JS equivalent — braces define the block, indentation is just style
# if (true) {
#   console.log("inside the if");
#   console.log("still inside");
# }
# console.log("outside the if");

      Gotcha

      Mixing tabs and spaces in the same file raises a TabError (or silently misbehaves in older Pythons). Configure your editor to insert 4 spaces per indent level — this is PEP 8 convention and effectively mandatory in any real codebase. VS Code's Python extension does this by default; just don't fight it by hand-typing tabs.

      Variables, dynamic typing, and the absence of declaration keywords

      There's no const, let, or var. Writing x = 5 creates a name binding in the current scope — full stop. Python is dynamically typed like JS (a name can be rebound to any type at any time), but unlike JS it has no undefined/null split — there is only None.

      ConceptJS/TSPython
      Declare a variablelet x = 5;x = 5 (no keyword)
      Constant-ish bindingconst x = 5; (binding is fixed, value may still mutate)No true constant — convention is ALL_CAPS name, enforced by nothing
      Absent / not-yet-set valueundefined vs nullJust None — one concept for both
      Block scopelet/const are block-scopedNo block scope — only function and module scope
      Type of a variableDynamic, checked with typeofDynamic, checked with type(x) or isinstance(x, T)
      
x = 5
x = "now a string"   # perfectly legal — same name, different type, just like JS `let x`
print(type(x))        # <class 'str'>

# No block scoping -- a variable assigned inside an `if` leaks to the enclosing function/module
if True:
    leaked = "I'm visible outside this if"
print(leaked)   # works -- would NOT work in JS with `let leaked` inside the if block

      Basic operators, print/input, and running a script

      Arithmetic and comparison operators are mostly the same shapes as JS with a few additions: ** for exponent (JS also has this since ES2016), // for floor division (no JS equivalent — you'd write Math.floor(a / b)), and and/or/not spelled as words instead of &&/||/!.

      
print(7 // 2)     # 3  -- floor division, like Math.floor(7/2) in JS
print(7 % 2)       # 1  -- modulo, same as JS
print(2 ** 10)      # 1024 -- exponent, same operator JS added in ES2016
print(True and False, True or False, not True)  # words, not && || !

name = input("What's your name? ")   # blocking read from stdin -- like a synchronous readline
print(f"Hello, {name}!")              # f-string -- Python's template literal equivalent

# JS equivalent of the f-string:
# console.log(`Hello, ${name}!`);

      Running a script is a single command, no build step: python script.py (or python3 depending on your system PATH setup). There's no transpilation step comparable to Babel/tsc — CPython compiles to bytecode internally and runs it immediately.

      Gotcha

      On many systems, python still points to Python 2 or doesn't exist at all, while python3 is the real Python 3.13 binary. Always verify with python3 --version before assuming which one a python command resolves to — this trips up almost every JS dev's first hour with Python.

      How It Works Under the Hood

      When you run python3 script.py, CPython parses the source into a syntax tree, compiles that tree into bytecode (the same intermediate form you'd get cached as a .pyc file inside __pycache__ for imported modules — your entry-point script itself isn't cached), and then a bytecode interpreter — a stack-based virtual machine — executes it instruction by instruction. This is conceptually similar to how V8 compiles your JS to bytecode (Ignition) before potentially JIT-ing hot paths, except mainstream CPython has historically had no JIT for your Python-level code — the speed of built-ins comes from their C implementation, not runtime optimization of your loops. The practical effect: there's no "warm-up" period and no build artifact to inspect — what you write is, line for line, what runs.

      Diagrams

      flowchart TD A["x = 5"] --> B{"Name 'x' bound\nin current scope"} B --> C["Module scope\n(top-level script)"] B --> D["Function scope\n(inside def)"] C -.->|no block scope| E["if/for/while bodies\nshare enclosing scope"] D -.->|no block scope| E

      Code Examples

      
# ---- BAD: JS habit of expecting block scope ----
# This "feels wrong" to a JS dev used to `let` in a for loop, but it's correct Python:
for i in range(3):
    pass
print(i)   # 2 -- `i` is still bound after the loop; no error, unlike `let i` in JS

# ---- GOOD: naming convention matters (PEP 8) ----
user_name = "alice"        # snake_case for variables/functions -- not camelCase
MAX_RETRIES = 3             # ALL_CAPS by convention for "constant-ish" module-level values
class HttpClient:           # PascalCase for classes -- same convention as JS/TS

    def __init__(self, base_url: str) -> None:
        self.base_url = base_url   # no `this`, use explicit `self` as first param

# ---- f-strings vs template literals ----
amount = 42.5
print(f"Total: ${amount:.2f}")   # :.2f -- format spec, 2 decimal places
# JS: `Total: $${amount.toFixed(2)}`

# ---- Multi-line values: no semicolons, line continuation is implicit inside brackets ----
total = (
    1 + 2
    + 3
)   # parentheses let the expression span lines -- no trailing `\` needed, unlike raw statements

      Real-World Production Scenario at Scale

      At scale

      A platform team's onboarding doc for new hires coming from a Node background used to take three days because new hires kept writing JS-shaped Python: semicolons (harmless but non-idiomatic), camelCase function names (breaks PEP 8 linting in CI and causes failed pre-commit hooks), and relying on block-scoped loop variables for logic that silently leaked past the loop. The fix wasn't more documentation — it was a strict ruff + black pre-commit setup that rejects non-idiomatic style before it ever reaches review, forcing the muscle memory to form in week one instead of being "corrected" piecemeal in code review for a month.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Writing camelCase function and variable names out of JS habit. Python's community convention (PEP 8) is snake_case for variables and functions, PascalCase for classes, and ALL_CAPS for constants. This isn't just style — linters (ruff, pylint) and most style guides in real codebases will flag it, and it marks your code as obviously non-native immediately.

      Gotcha

      Forgetting that there is no block scope, and being surprised when a variable defined inside an if or for is still accessible afterward. This is correct, intentional Python behavior — not a bug — but it means you must be deliberate about not accidentally relying on a loop variable that didn't get set because the loop body never ran.

      • Don't add semicolons at line ends — they're legal (Python tolerates them) but never idiomatic; only used rarely to put two statements on one line.
      • Use f-strings (f"{x}") over %-formatting or .format() — f-strings are the modern, fastest, and most readable choice since Python 3.6+.
      • Don't confuse python and python3 on your PATH — be explicit, especially when scripting CI.

      Tradeoffs

      Interview Questions

      Basic

      Why doesn't Python use braces for blocks?

      Python's design philosophy (PEP 20, "The Zen of Python") treats readability as a primary goal, and significant whitespace forces consistent, visually nested code since the interpreter enforces it as grammar rather than leaving indentation to style convention.

      Follow-up: what error do you get from inconsistent indentation, and how does Python detect it?
      What's the Python equivalent of let/const?

      There isn't a direct one — any assignment (x = 5) just binds a name, with no keyword and no built-in immutability. "Constants" are a naming convention (ALL_CAPS) only, not an enforced language feature.

      Follow-up: how would you actually enforce immutability for a value in Python?
      Does Python have block scope like JS's let inside an if?

      No. Python has only function scope and module scope. A name assigned inside an if/for/while block remains accessible after the block ends, within the same function or module.

      Follow-up: what problem can this cause if a conditional branch never executes?
      What's the difference between None and JS's undefined/null?

      Python collapses both concepts into a single None value. There's no distinction between "never assigned" and "explicitly set to nothing."

      Follow-up: how do you then tell "key was never set" apart from "key was set to None" in a dict?
      What does // do that / doesn't?

      / is true division and always returns a float in Python 3 (7 / 2 == 3.5). // is floor division, returning the floored quotient (7 // 2 == 3).

      Follow-up: what does // return for negative numbers, and does it round toward zero or toward negative infinity?
      How do you run a Python script from the terminal?

      python3 script.py on most systems (or just python if that resolves to Python 3). There's no build/transpile step — CPython compiles to bytecode internally and runs it in one invocation.

      Follow-up: what's the difference between running a file directly and running it with python -m?
      Is Python statically or dynamically typed?

      Dynamically typed — a variable name can be rebound to a value of any type at any time, and types are checked at runtime, not compile time. Type hints are optional annotations, not enforcement.

      Follow-up: how does this compare to TypeScript's compile-time structural typing?

      Medium

      Explain exactly what happens if you mix tabs and spaces in the same Python file.

      CPython's tokenizer raises a TabError (a subclass of IndentationError) when it detects indentation that's ambiguous between tab-width interpretations within the same block — this is a hard parse-time failure, not a style warning, which is why editors are configured to insert spaces only.

      Follow-up: why is this risk higher in files edited by multiple people with different editor configs?
      Why does for i in range(3): pass followed by print(i) print 2 rather than raising an error?

      Because Python has no block scope, the loop variable i is bound in the enclosing function/module scope and simply holds whatever value it had on the last iteration when the loop exits normally. This differs fundamentally from JS's let i in a for, which is genuinely out of scope after the loop.

      Follow-up: what happens to that variable if the iterable is empty — does the loop variable even exist afterward?
      What's the actual difference between f-strings and .format() under the hood?

      f-strings are evaluated and compiled at parse time into efficient bytecode that directly interpolates expressions — they're generally faster. .format() is a regular method call on a string object that parses the format spec at runtime on every call. For hot loops, f-strings have a real, measurable performance edge.

      Follow-up: can f-strings contain arbitrary expressions, including function calls? Any restrictions?
      A new hire writes idiomatic-looking code but every function and variable is camelCase. Why is this a real problem beyond aesthetics?

      It breaks linting conventions (ruff/pylint flag non-PEP-8 naming by default in most configured projects), signals unfamiliarity with the ecosystem to reviewers, and can clash with actual Python convention-driven behavior in some tooling/autocomplete heuristics that assume snake_case.

      Follow-up: are there any Python standard library APIs that intentionally use camelCase, and why (hint: threading module)?
      Explain the compile step a .py file goes through before anything executes, and why your main script file isn't cached as .pyc the way imported modules are.

      Source is tokenized, parsed to an AST, compiled to bytecode, then interpreted. Imported modules get their compiled bytecode cached in __pycache__ keyed by a hash/mtime of the source so repeated imports skip recompilation; the entry-point script run directly isn't cached this way because it's expected to run once per process invocation, not be re-imported.

      Follow-up: what invalidates the .pyc cache, and what happens if the source changes but the cache doesn't get invalidated correctly?

      Advanced

      Why did Python's designers choose significant whitespace over braces, and what's the actual tradeoff versus a brace-delimited language like JS?

      The stated design goal (Guido van Rossum, and later formalized in PEP 20) is that forcing visual structure to match logical structure eliminates an entire class of bugs and style disputes (brace placement wars, inconsistent indentation that doesn't match actual nesting). The tradeoff: copy-pasting code across differently-indented contexts is more fragile than in brace languages, and some code generation/templating scenarios are genuinely harder because you can't just insert braces — you must track and emit consistent indentation.

      Follow-up: how do templating tools that generate Python code (e.g. code generators) typically handle this?
      Walk through what the CPython tokenizer actually emits for INDENT/DEDENT, and how that interacts with implicit line joining inside brackets.

      The tokenizer emits explicit INDENT and DEDENT tokens when leading whitespace increases or decreases between logical lines, and these are what the grammar actually consumes to delimit blocks — it's not "whitespace as a byte count" but a structured token stream. Inside any open bracket ((), [], {}), the tokenizer suppresses NEWLINE tokens entirely, which is why an expression can span multiple physical lines without a continuation backslash as long as it's inside brackets.

      Follow-up: why does a backslash continuation outside of brackets feel fragile compared to bracket-based continuation, and which do style guides prefer?
      Is there any meaningful performance difference between an f-string, %-formatting, and .format() in a hot path, and how would you actually verify it rather than assume it?

      f-strings are generally fastest because they compile to direct BUILD_STRING-style bytecode rather than a runtime method dispatch, but the "assume" part is the problem: you'd verify with timeit on a representative snippet at realistic string/interpolation sizes, since the difference is often negligible outside genuinely hot loops and premature micro-optimization here rarely matters compared to I/O or algorithmic costs elsewhere.

      Follow-up: at what call frequency does this difference actually start to matter in a real service?
      Design an onboarding lint/pre-commit setup that would catch "JS-shaped Python" systematically rather than relying on code review.

      A senior-level answer: ruff (fast, covers PEP 8 naming, unused imports, many correctness checks) plus black (formatting, removes bikeshedding) as pre-commit hooks, wired into CI so a PR can't merge without passing. Add a naming-convention rule set specifically (N-series rules in ruff) to catch camelCase. This shifts the cost from repeated human review comments to a one-time automated gate, which is the same principle as ESLint + Prettier pre-commit hooks in a JS codebase — the pattern transfers directly, only the tool names change.

      Follow-up: how would you roll this out to an existing large codebase without breaking everyone's workflow on day one?

      Practice Assignments

      Beginner (30-60 min)

      Rewrite five JS snippets as idiomatic Python

      Take five small JS snippets (variable declarations, a template literal, a loop with a scoped variable, a constant, a function) and rewrite each as idiomatic Python, then write one sentence per snippet explaining the biggest syntactic or semantic difference.

      • Use f-strings, snake_case, and no semicolons throughout.
      • At least one snippet must demonstrate the "no block scope" difference explicitly.

      Acceptance criteria: All five run with python3 file.py with no errors, and each has a one-line comment explaining the key difference from the JS original.

      Hints

      For the loop-scope snippet, deliberately print the loop variable after the loop ends in both languages (mentally, for the JS one) to make the contrast concrete.

      Intermediate (2-4 hrs)

      Build a small "unit converter" REPL script

      Write a script that loops, reading a line of input like "10 km to miles", parses it, converts, and prints the result, until the user types "exit". Support at least 4 unit pairs (length, weight, temperature).

      • Use f-strings for all output formatting.
      • Handle malformed input (wrong format, unknown unit) without crashing — print a friendly message and re-prompt.
      • Follow PEP 8 naming throughout; run it through ruff or at least mentally check for camelCase.

      Acceptance criteria: The script never raises an unhandled exception for any text input, and correctly converts all 4 supported unit pairs.

      Hints

      Use input().split() to break the line into tokens, and a dict of conversion functions keyed by a (from_unit, to_unit) tuple to avoid a long if/elif chain.

      Advanced (1-2 days)

      Write your own mini indentation checker

      Build a small Python script that reads another .py file and reports any line that mixes tabs and spaces in its leading whitespace, plus any place where indentation increases by something other than a consistent multiple of spaces. Don't use the real tokenizer — parse the raw text yourself, line by line, to force yourself to think about what "indentation" actually means character by character.

      • CLI takes a file path argument.
      • Reports line numbers and a short description of each issue found.
      • Include a handful of test fixture files (some clean, some deliberately broken) and assert the right lines get flagged.

      Acceptance criteria: Running against your fixtures correctly flags every deliberately broken line and produces zero false positives on the clean fixtures. No full solution here — the point is building the muscle for reasoning about indentation as data.

      Quick Revision Cheat Sheet

      • Indentation (4 spaces, PEP 8) is the block delimiter — no braces, no semicolons needed.
      • No const/let/var — assignment just binds a name in the current scope.
      • No block scope — only function scope and module scope; loop/if-body variables leak to the enclosing scope.
      • None replaces both JS undefined and null.
      • Naming convention: snake_case functions/variables, PascalCase classes, ALL_CAPS "constants."
      • f-strings (f"{x}") are the idiomatic way to interpolate — prefer them over .format() or %.
      • // is floor division, / is true division (always float), ** is exponent.
      • and/or/not are words, not &&/||/!.
      • Run scripts with python3 file.py — no build/transpile step.
      • Always verify whether python on your system means Python 2 or 3 — use python3 explicitly.
