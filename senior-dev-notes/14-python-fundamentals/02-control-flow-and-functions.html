    Control Flow & Functions

    ⏱ ~2 hrs📍 Chapter 2 of 6

    One-line summary: Python's if/for/while do the same job as JS's, but functions carry real differences that bite JS developers specifically — default argument evaluation timing, *args/**kwargs instead of arguments/rest+spread, and scope rules that don't match closures the way you expect.

    On this page

      Why It Matters for a Senior Developer

      Control flow syntax is the easy 20% — you'll pick it up by pattern matching within an hour. The part that actually causes production bugs and interview stumbles is function semantics: mutable default arguments are a real, recurring source of bugs in production Python codebases (including ones written by experienced engineers who know better but typed it on autopilot), and *args/**kwargs show up constantly in any framework code (Flask, FastAPI, Django) you'll read. Getting this chapter solid is what lets you read decorator-heavy framework code without flinching.

      Why

      Nearly every "gotcha" Python interview question about functions exists because Python evaluates default arguments once, at definition time, not per call — this single fact explains a disproportionate number of real bugs and interview questions, so understanding why it works that way (not just memorizing "don't use mutable defaults") pays off repeatedly.

      Requires Python Syntax & Basics (indentation, variable binding, no block scope). Feeds directly into Data Types & Collections (comprehensions are a control-flow concept in disguise). See also Python Intermediate for generators and async functions, which build on everything here.

      Core Concepts

      if/elif/else and for/while loops

      Structurally identical to JS in spirit, syntactically different. There's no switch statement built in before 3.10 — match (structural pattern matching, added in 3.10) is the closest equivalent and is more powerful than a JS switch.

      
score = 85
if score >= 90:
    grade = "A"
elif score >= 80:          # elif, not "else if"
    grade = "B"
else:
    grade = "C"

# for loop iterates over an iterable directly -- there is no classic C-style for(;;)
for i in range(5):          # range(5) -- like [...Array(5).keys()] in JS, but lazy
    print(i)

fruits = ["apple", "banana", "cherry"]
for fruit in fruits:        # like `for (const fruit of fruits)` in JS
    print(fruit)

for index, fruit in enumerate(fruits):   # like `fruits.forEach((fruit, index) => ...)`
    print(index, fruit)

count = 0
while count < 3:
    print(count)
    count += 1               # no ++ operator in Python -- must write += 1

# match statement (3.10+) -- structural pattern matching, richer than JS switch
match grade:
    case "A" | "B":
        print("Good job")
    case "C":
        print("Needs improvement")
    case _:                  # `_` is the wildcard/default case
        print("Unknown grade")

      Gotcha

      There is no ++ or -- operator in Python at all — not even as an alternative spelling. Always write count += 1. Typing count++ is a silent no-op on some edge cases or a flat SyntaxError in most — either way it's not what you meant.

      Function definitions, default/keyword args, *args/**kwargs

      Python functions are defined with def, support default parameter values (like JS default params), and go further than JS with explicit keyword-only arguments and the *args/**kwargs convention for variadic parameters.

def greet(name, greeting="Hello"):     # default arg, same idea as JS default params
    return f"{greeting}, {name}!"

print(greet("Alice"))                   # "Hello, Alice!"
print(greet("Bob", greeting="Hi"))      # keyword arg -- order-independent, explicit

def sum_all(*args):                      # *args collects positional extras into a tuple
    return sum(args)

print(sum_all(1, 2, 3, 4))               # 10
# JS: function sumAll(...args) { return args.reduce((a,b) => a+b, 0); }

def make_request(url, **kwargs):         # **kwargs collects keyword extras into a dict
    print(f"GET {url} with options: {kwargs}")

make_request("/users", timeout=30, retries=3)
# JS-ish equivalent: makeRequest('/users', { timeout: 30, retries: 3 })

double = lambda x: x * 2                 # lambda -- single expression only, no statements
# JS: const double = x => x * 2;         -- JS arrows can have full bodies; lambdas cannot

      Scope basics: local, enclosing, global, built-in (LEGB)

      Python resolves names using the LEGB rule: Local → Enclosing → Global → Built-in. The critical JS-breaking detail: if you assign to a name anywhere inside a function body, Python treats that name as local for the entire function, even on lines before the assignment — unlike JS, where reading an outer-scope variable before reassigning it later in the function just works via the scope chain.

      
counter = 0

def increment_broken():
    counter += 1   # UnboundLocalError! Python sees the assignment and treats `counter`
                    # as local for the whole function -- so reading it here fails,
                    # it never falls back to the global one like JS would.
    return counter

def increment_fixed():
    global counter   # explicitly declare we mean the module-level name
    counter += 1
    return counter

# JS has no equivalent keyword needed:
# let counter = 0;
# function increment() { counter += 1; return counter; }  // just works

      How It Works Under the Hood

      CPython determines variable scope statically at compile time, not at runtime. When the bytecode compiler processes a function body, it scans every name for assignment — any name assigned anywhere in the function is marked as a local variable slot in that function's compiled code object, and the compiler emits LOAD_FAST/STORE_FAST bytecode for it instead of LOAD_GLOBAL. This is why UnboundLocalError happens: the bytecode was already compiled to treat the name as local before the function ever runs, so reading it before the local assignment executes finds an empty slot, not the outer value. JS engines, by contrast, resolve free variables through a live scope chain lookup at access time — there's no equivalent "this name is local for the whole function because it's assigned somewhere in it" compile-time rule.

      Code Examples

      
# ---- BAD: the classic mutable default argument trap ----
def add_item(item, basket=[]):     # basket=[] is created ONCE at def time
    basket.append(item)
    return basket

print(add_item("apple"))            # ['apple']
print(add_item("banana"))           # ['apple', 'banana'] -- SURPRISE, not a fresh list!

# ---- GOOD: use None as sentinel, create fresh default inside the function ----
def add_item_fixed(item, basket=None):
    if basket is None:
        basket = []
    basket.append(item)
    return basket

print(add_item_fixed("apple"))      # ['apple']
print(add_item_fixed("banana"))     # ['banana'] -- fresh list every call, as expected

# ---- *args and **kwargs together, matching a typical framework handler signature ----
def route_handler(request_path, *args, method="GET", **kwargs):
    print(f"{method} {request_path} args={args} kwargs={kwargs}")

route_handler("/users/42", "extra", method="POST", auth=True)

# ---- keyword-only arguments: the `*` forces everything after it to be keyword-only ----
def create_user(name, *, email, is_admin=False):
    return {"name": name, "email": email, "is_admin": is_admin}

create_user("Alice", email="a@example.com")       # OK
# create_user("Alice", "a@example.com")           # TypeError -- email must be passed by keyword

      Real-World Production Scenario at Scale

      At scale

      A team building an internal caching decorator wrote def cached(fn, _cache={}): intending _cache as a private per-decorated-function store. Because the default dict is created once at function-definition time and the decorator function itself is only defined once at import time, every single function decorated with @cached across the entire codebase ended up sharing the same dict — cache key collisions silently returned wrong cached results for unrelated functions whenever two functions happened to produce the same cache key shape. The fix mirrored the general rule: never rely on a mutable default for storage that should be fresh or scoped per use; the cache was moved to a functools.lru_cache-backed implementation (or a closure-created dict per decoration) instead.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Mutable default arguments (def f(x=[]) or def f(x={})) are evaluated exactly once, when the function is defined, and that same object is reused and mutated across every call that doesn't supply its own. Always default to None and create the real mutable value inside the function body.

      Gotcha

      Forgetting global or nonlocal when you intend to reassign (not just read) an outer-scope name inside a function. Reading an outer value without assigning to that name works fine without any keyword; the keyword is only required the moment you assign to that same name inside the function.

      • Prefer keyword-only arguments (def f(a, *, b)) for functions with many boolean/options params — it prevents positional mix-ups that are easy to make in both Python and JS.
      • Lambdas are expressions only — if you need more than one statement or a docstring, write a real def instead; don't fight the lambda syntax.
      • Use match/case (3.10+) over long if/elif chains when branching on the shape/value of one variable — it reads closer to a JS switch but supports pattern destructuring JS switch can't.

      Interview Questions

      Basic

      What's the Python equivalent of JS's ...args rest parameter?

      *args — it collects any extra positional arguments into a tuple inside the function.

      Follow-up: what collects extra keyword arguments, and into what data type?
      Why is def f(items=[]) considered a bug risk?

      The default list is created once, at function-definition time, and shared/mutated across every call that relies on the default — not recreated fresh per call like you'd expect from JS default parameters.

      Follow-up: does this apply to default arguments that are tuples? Why or why not?
      Does Python have a ++ increment operator?

      No. You must write x += 1. There is no ++ or -- in the language at all.

      Follow-up: why do you think Python's designers omitted it when C-family languages have it?
      What does * alone in a parameter list mean, as in def f(a, *, b):?

      It marks everything after it as keyword-only — callers must pass b as b=value, not positionally.

      Follow-up: what does a bare / in a parameter list mean (3.8+)?
      Can a Python lambda contain an if/else?

      Only as a conditional expression: lambda x: "even" if x % 2 == 0 else "odd". It cannot contain statements (assignments, loops, multiple lines) — it must be a single expression.

      Follow-up: when would you refactor a lambda into a regular function?
      What is the LEGB rule?

      The order Python searches for a name: Local, Enclosing (closures), Global (module), Built-in (len, print, etc.) — first match wins.

      Follow-up: where does a class body's namespace fit into LEGB?
      Is switch available in Python?

      Not as a switch keyword. Python 3.10+ added match/case, which is structurally similar but supports pattern matching/destructuring, not just value equality.

      Follow-up: what Python versions would you need to support to safely avoid match/case?

      Medium

      Why does counter += 1 inside a function raise UnboundLocalError instead of just reading the outer counter?

      Because Python's compiler statically scans the function body and marks any assigned name as local for the entire function — the assignment on that line means the compiler never emits a lookup of the outer counter at all; it compiled the function expecting a local slot that doesn't yet hold a value when read.

      Follow-up: what's the fix, and what are its downsides for testability?
      Explain exactly when the mutable-default-argument object gets created and how many times, across many calls.

      Exactly once — when the def statement itself executes (typically at module import time), not on each call. The same object reference is stored in the function's __defaults__ tuple and reused as the parameter's value on every call that doesn't override it.

      Follow-up: how would you inspect a function's current defaults from outside it, to debug this?
      Compare Python keyword-only arguments to a JS pattern that approximates the same safety.

      Python's def f(a, *, b, c) forces callers to name b and c explicitly, preventing accidental positional swaps. JS has no native equivalent for positional functions, so the idiomatic approximation is accepting a single destructured object parameter: function f(a, {b, c}) {}, called as f(a, {b: 1, c: 2}) — similar safety, different mechanism (one param object vs real multiple keyword args).

      Follow-up: can you mix positional-only, normal, and keyword-only parameters in one Python signature? What's the ordering rule?
      When would you reach for *args, **kwargs in a wrapper function, and what's the real cost of overusing it?

      It's the right tool for generic forwarding — decorators, middleware-style wrappers, adapters that don't know or care about the wrapped function's exact signature. Overusing it in regular business logic functions destroys readability and defeats static type checking/autocomplete, since callers and readers can no longer see what parameters actually exist without reading the implementation.

      Follow-up: how do type checkers like mypy handle *args/**kwargs typing, and what's lost compared to explicit params?
      What does match/case support that a JS switch fundamentally cannot?

      Structural pattern matching: destructuring into sub-patterns (matching a dict's keys, a list's length/elements, a class's attributes), guard clauses (case x if x > 0:), and OR-patterns (case "A" | "B":). JS switch only does value equality on a single expression per case.

      Follow-up: show a case pattern that destructures a dict with a specific key present.

      Advanced

      Explain the compiled bytecode difference between a name treated as local vs global in a CPython function, and why this matters for performance, not just correctness.

      Local variable access compiles to LOAD_FAST/STORE_FAST, which indexes directly into a fixed-size array on the frame — O(1), no dict lookup. Global access compiles to LOAD_GLOBAL, which does a dictionary lookup (with caching optimizations in 3.11+'s adaptive specializing interpreter, but still fundamentally different). This is part of why tight loops that reference a global repeatedly are measurably slower than the equivalent with a local alias — a known micro-optimization technique in performance-sensitive Python code.

      Follow-up: what did PEP 659 (specializing adaptive interpreter, 3.11+) change about global lookup cost?
      Design a decorator that needs genuinely private, per-decoration mutable state (like a counter per decorated function), and explain why a naive mutable default argument on the decorator itself is the wrong tool.

      The naive def decorator(fn, _state={}): shares one dict across every use of the decorator across the whole codebase — not per-decorated-function. The correct pattern creates the mutable state inside the decorator's closure, fresh per decoration: def decorator(fn): state = {}; def wrapper(*a, **kw): ...; return wrapper — each call to decorator creates a new closure cell, giving true per-function isolation, the same principle as a JS factory function creating isolated closures per call.

      Follow-up: how would functools.wraps interact with this, and why is it needed at all?
      Why can keyword-only and positional-only markers (* and /) both appear in the same signature, and what ordering rule governs them?

      A full signature can look like def f(a, b, /, c, d, *, e, f): — parameters before / are positional-only, between / and * are normal (positional-or-keyword), after * are keyword-only. This exists so library authors can lock down call-site API shape precisely (e.g. dict.get(key, default, /) style stdlib signatures use positional-only to reserve the right to rename parameters without breaking callers).

      Follow-up: why does the standard library itself use positional-only parameters in many built-in function signatures?
      A teammate argues "mutable default arguments are just a footgun Python should have fixed." Steelman why the current behavior is actually a deliberate, defensible design rather than an oversight.

      Default values are part of the function object itself (__defaults__), evaluated once at definition time — this is consistent with Python's broader model where def is itself a runtime statement that constructs a function object, and the defaults are just attributes computed then, same as any other expression evaluated at def time (e.g. a default of time.time() would also be "frozen" at def time, which is arguably correct behavior, not a bug). The real fix isn't changing the semantics — it's a well-known idiom (default to None) that's cheap to apply once understood; changing the language semantics would be a much larger breaking change for a learnable convention.

      Follow-up: can you think of a case where "evaluated once at def time" is actually exactly the behavior you want?
      How would you use match/case to parse a heterogeneous list of event dicts coming from a webhook, dispatching on event "type"?

      match event: case {"type": "created", "id": id}: ...; case {"type": "updated", **rest}: ...; case _: ... — destructuring directly on dict shape avoids a chain of if event["type"] == "..." checks with manual key extraction, and the wildcard case gives you an explicit, impossible-to-forget default branch, unlike a JS switch's often-forgotten default.

      Follow-up: what happens if the "type" key is missing entirely — does match raise, or fall through to the wildcard?

      Practice Assignments

      Beginner (30-60 min)

      Function signature translation drill

      Take five JS function signatures (default param, rest param, a destructured-object "options" param, an arrow function, a function calling another with spread) and write the idiomatic Python equivalent for each, with a one-line comment on the key syntactic difference.

      • At least one must use *args and one must use **kwargs.
      • The lambda translation must demonstrate the single-expression limitation (pick a JS arrow with a one-liner body).

      Acceptance criteria: All five run standalone and produce output demonstrating correct behavior with at least two different call shapes each.

      Hints

      For the destructured-object param, Python's closest idiom is often just named keyword arguments rather than literally passing a dict, unless the JS code specifically needs an arbitrary bag of options (then **kwargs is closer).

      Intermediate (2-4 hrs)

      Build a tiny "command dispatcher" using *args/**kwargs and match

      Build a CLI-style dispatcher: a dict mapping command names to handler functions, each handler accepting *args, **kwargs, plus a separate match-based dispatcher for a second set of commands that branch on a dict-shaped "action" payload (e.g. {"action": "move", "dx": 1, "dy": 0}).

      • At least 4 distinct commands across the two dispatchers.
      • Demonstrate and deliberately trigger the mutable-default-argument bug in one early draft, then fix it, keeping both versions with comments.
      • Write a short README-style docstring at the top of the file explaining when you'd pick dict-dispatch vs match/case in real code.

      Acceptance criteria: All commands execute correctly through both dispatch mechanisms; the buggy-vs-fixed mutable default comparison clearly shows the difference when run.

      Hints

      For the deliberate bug demo, call the buggy handler 3 times and print its "memory" each time before showing the fixed version staying clean.

      Advanced (1-2 days)

      Build a signature-inspecting decorator

      Build a decorator @log_calls that, when applied to any function, logs the function name, the actual argument values it was called with (matching them to parameter names using inspect.signature), and the return value — working correctly regardless of whether the wrapped function uses positional args, keyword args, defaults, or *args/**kwargs.

      • Must use functools.wraps so the wrapped function's name/docstring are preserved.
      • Must correctly bind and display argument names even when called positionally, using inspect.signature(fn).bind(*args, **kwargs).
      • Include a pytest suite testing it against at least 3 differently-shaped function signatures.

      Acceptance criteria: The decorator works transparently (wrapped functions behave identically, just with logging) across all 3+ signature shapes in your test suite. No full solution here.

      Quick Revision Cheat Sheet

      • No ++/-- — always x += 1 / x -= 1.
      • elif, not "else if"; match/case (3.10+) for structural branching.
      • *args collects extra positional args into a tuple; **kwargs collects extra keyword args into a dict.
      • Mutable default arguments are evaluated once at def time — default to None and build the real value inside the function.
      • Assigning to an outer-scope name inside a function requires global or nonlocal; just reading it doesn't.
      • lambda is a single expression only — no statements, no multi-line bodies.
      • * alone in a parameter list forces everything after it to be keyword-only.
      • LEGB scope resolution order: Local → Enclosing → Global → Built-in.
      • Local variable access (LOAD_FAST) is faster than global access (LOAD_GLOBAL) — matters in hot loops.
