    File I/O & Modules

    ⏱ ~1.5 hrs📍 Chapter 4 of 6

    One-line summary: Python file I/O is synchronous and blocking by default (no fs.readFile-style callbacks or promises baked in), context managers (with) replace manual try/finally cleanup, and modules resolve via the filesystem and sys.path instead of a bundler graph.

    On this page

      Why It Matters for a Senior Developer

      Every real Python script or service touches files or config at some point, and with is the single most "why does Python do it this way" construct a JS developer encounters early — there is genuinely no direct JS equivalent, because JS doesn't have a deterministic, synchronous "guaranteed cleanup on scope exit" primitive for arbitrary resources the way Python's context manager protocol provides. Understanding *why* context managers exist (not just the with syntax) is what separates "copies the pattern" from "understands resource management in Python."

      Why

      JS relies on garbage collection and, for truly scoped cleanup, either manual try/finally or newer explicit resource management (using, Stage 3 as of 2025). Python chose a different, older answer: any object can define __enter__/__exit__ and the with statement guarantees __exit__ runs even if an exception is thrown inside the block — this is why it's the idiomatic way to handle files, locks, DB connections, and any other resource that must be released deterministically.

      Prerequisites

      Requires Python Syntax & Basics and Control Flow & Functions. Continues into Error Handling & Debugging (exceptions and context managers interact constantly). See Python Intermediate for packaging, virtual environments, and async file I/O patterns.

      Core Concepts

      Opening, reading, and writing files

      Python's open() is synchronous and blocks the calling thread until the OS call returns — there is no non-blocking-by-default behavior the way fs.readFile's callback API implies in Node. If you want non-blocking file I/O in Python, you opt in explicitly (e.g. asyncio + aiofiles, or a thread pool) — it is never automatic.

      
# Reading an entire file
with open("notes.txt", "r", encoding="utf-8") as f:
    content = f.read()           # blocks until the whole file is read into memory

# Reading line by line (memory-efficient for large files)
with open("notes.txt", "r", encoding="utf-8") as f:
    for line in f:                 # file objects are iterable -- one line at a time
        print(line.strip())

# Writing (overwrites the file if it exists)
with open("output.txt", "w", encoding="utf-8") as f:
    f.write("Hello, file!\n")

# Appending
with open("output.txt", "a", encoding="utf-8") as f:
    f.write("Another line\n")

# JS/Node equivalent (callback or promise-based, never implicitly synchronous):
# const fs = require('fs');
# const content = fs.readFileSync('notes.txt', 'utf-8');       // sync version exists but is rarely default
# fs.readFile('notes.txt', 'utf-8', (err, data) => { ... });    // async is the Node convention

      Gotcha

      Always pass encoding="utf-8" explicitly. Without it, Python uses a platform-dependent default encoding (often UTF-8 on Linux/macOS but historically different on Windows), which means code that "works on your machine" can silently misbehave or raise UnicodeDecodeError on a teammate's machine or in CI.

      Context managers (with) — why they exist

      Without with, you'd need manual try/finally to guarantee a file handle closes even if an error occurs mid-read:

      
# What `with` replaces -- manual, error-prone resource cleanup
f = open("notes.txt", "r", encoding="utf-8")
try:
    content = f.read()
finally:
    f.close()        # MUST remember this, or the file handle leaks

# `with` does exactly this automatically:
with open("notes.txt", "r", encoding="utf-8") as f:
    content = f.read()
# f.close() is called automatically here, even if read() raised an exception

# Any object can be a context manager by implementing __enter__/__exit__
class Timer:
    def __enter__(self):
        import time
        self.start = time.perf_counter()
        return self
    def __exit__(self, exc_type, exc_value, traceback):
        import time
        print(f"Elapsed: {time.perf_counter() - self.start:.4f}s")
        return False   # False = don't suppress exceptions; True would swallow them

with Timer():
    sum(range(10_000_000))   # timer prints elapsed time when this block exits, success or error

      There's no clean JS equivalent for the general pattern — the closest conceptual cousins are try/finally (manual, every time) or the newer using declaration (TC39 Stage 3 as of 2025, requiring Symbol.dispose), which is new enough that most JS code you'll see still doesn't use it. Python's context manager protocol has been standard since Python 2.5 (2006) and is used pervasively — files, locks, DB transactions, mocking in tests, temporary directories, all use it.

      Creating and importing your own modules

      Any .py file is a module. A directory with an __init__.py (or, since Python 3.3+, even without one via "namespace packages") is a package. Imports resolve against sys.path and the filesystem — there's no bundler resolving a dependency graph at build time the way webpack/Vite does.

      
# ---- math_utils.py ----
def add(a, b):
    return a + b

PI = 3.14159

# ---- main.py, in the same directory ----
import math_utils
print(math_utils.add(2, 3))     # 5
print(math_utils.PI)

from math_utils import add       # named import, like `import { add } from './mathUtils'`
print(add(4, 5))                  # 9

import math_utils as mu           # aliased import, like `import * as mu from './mathUtils'`
print(mu.add(1, 1))

# JS/Node equivalent (ESM):
# import * as mathUtils from './mathUtils.js';
# import { add } from './mathUtils.js';
# import { add as addFn } from './mathUtils.js';

      The standard library at a glance — these are the modules you'll reach for constantly without installing anything: os/pathlib (filesystem paths), json (parsing/serializing), csv, datetime, collections (Counter, defaultdict, namedtuple), itertools, re (regex, same engine family concepts as JS regex but different syntax corners), argparse (CLI argument parsing), logging, and subprocess (spawning processes, similar role to Node's child_process).

      How It Works Under the Hood

      The with statement is syntax sugar over a fixed protocol: Python calls __enter__() on the context manager object, binds its return value to the as target if present, runs the block, and guarantees __exit__(exc_type, exc_value, traceback) is called on the way out — whether the block completed normally or raised. If __exit__ returns a truthy value, the exception (if any) is suppressed; otherwise it propagates after __exit__ runs. For imports, Python maintains sys.modules as a cache keyed by module name — the first import foo finds the file via sys.path, compiles it, executes the module body top-to-bottom exactly once, and caches the resulting module object; every subsequent import foo anywhere in the process just returns the cached object without re-executing the file. This is conceptually similar to CommonJS's require.cache, though ESM's module graph resolution and live bindings work somewhat differently.

      Code Examples

      
# ---- BAD: manual open/close, easy to forget cleanup on an error path ----
def read_config_bad(path):
    f = open(path, "r", encoding="utf-8")
    data = f.read()        # if this raises, f.close() below never runs -- file handle leaks
    f.close()
    return data

# ---- GOOD: with guarantees cleanup regardless of how the block exits ----
def read_config_good(path):
    with open(path, "r", encoding="utf-8") as f:
        return f.read()

# ---- Reading/writing JSON, the most common "config/data file" format ----
import json
from pathlib import Path

def load_settings(path: str) -> dict:
    p = Path(path)
    if not p.exists():
        return {}                     # sensible default instead of crashing
    with p.open("r", encoding="utf-8") as f:
        return json.load(f)

def save_settings(path: str, settings: dict) -> None:
    with open(path, "w", encoding="utf-8") as f:
        json.dump(settings, f, indent=2)

# ---- pathlib over manual string path building (idiomatic since 3.4+) ----
data_dir = Path("data") / "exports"      # `/` is overloaded as a path-join operator
data_dir.mkdir(parents=True, exist_ok=True)   # like `mkdir -p`
for file in data_dir.glob("*.json"):       # like fs.readdirSync + a glob filter
    print(file.name)

      Real-World Production Scenario at Scale

      At scale

      A batch ETL script processing thousands of daily report files was intermittently leaving file descriptors open under load, eventually hitting the OS's open-file limit and crashing mid-run. The root cause: a code path used manual open()/close() with the close call placed after a block that could raise (a malformed CSV row), so any parse error skipped the close entirely. Migrating every file-handling path to with blocks fixed the leak permanently — not by adding more error handling, but by making cleanup structurally guaranteed regardless of what exception path was taken. This is the single most common real-world payoff of context managers: they eliminate an entire category of "forgot to clean up on the error path" bugs.

      Common Mistakes, Gotchas and Best Practices

      Gotcha

      Opening a file without with "because it's just a quick script." Resource leaks compound in long-running processes (servers, workers) even if a one-off script "gets away with it" because the process exits soon after. Make with the default reflex, not an exception.

      Gotcha

      Forgetting encoding="utf-8" on open() calls, relying on the platform default. This is one of the most common "works on my machine, fails in CI/production" bugs for teams with mixed OS development environments.

      • Prefer pathlib.Path over manual string concatenation (dir + "/" + filename) for building file paths — it's cross-platform correct and more readable.
      • Check for circular imports early — Python allows them in some cases but the behavior (a partially-initialized module) is genuinely confusing; restructure to avoid them rather than debug around them.
      • Use json.load(f)/json.dump(f, obj) directly on the file object rather than reading to a string and calling json.loads() separately — it's both more idiomatic and slightly more memory-efficient for large files.

      Interview Questions

      Basic

      What does the with statement guarantee?

      That the context manager's __exit__ method runs when the block ends, whether it completed normally or raised an exception — guaranteeing cleanup (like closing a file) happens exactly once, reliably.

      Follow-up: what two special methods must an object implement to be used in a with statement?
      Is Python's default file reading synchronous or asynchronous?

      Synchronous and blocking — open() and its read/write methods block the calling thread until the OS call returns, unlike Node's convention of async-by-default for I/O.

      Follow-up: how would you make file I/O non-blocking in Python if you needed to?
      What's the Python equivalent of a JS import statement?

      import module_name, from module_name import thing, or import module_name as alias — resolved via sys.path and cached in sys.modules, not a bundler graph.

      Follow-up: what makes a directory a Python "package" rather than just a folder of scripts?
      Why should you pass encoding="utf-8" explicitly to open()?

      Without it, Python uses a platform-dependent default encoding, which can differ between your machine, a teammate's, and CI — causing inconsistent behavior or UnicodeDecodeError in some environments but not others.

      Follow-up: what's the default encoding behavior specifically on Windows versus Linux/macOS?
      What module would you use to read and write JSON files in Python?

      The standard library json module — json.load()/json.dump() work directly with file objects, and json.loads()/json.dumps() work with strings.

      Follow-up: what Python types does json.dump() fail to serialize by default, and how would you handle them?
      What happens if you open the same file twice with mode "w"?

      Each "w" open truncates the file immediately upon opening — the second open wipes out anything written by the first, which is a common source of "my data disappeared" bugs when a file is opened in write mode more than once in a flow.

      Follow-up: what mode would you use to append without truncating?

      Medium

      Why doesn't JavaScript have a direct equivalent to Python's context manager protocol?

      JS has historically relied on garbage collection plus manual try/finally for deterministic cleanup; there was no standardized "any object can declare enter/exit cleanup behavior enforced by the language" mechanism until the using declaration (TC39 Stage 3, requiring Symbol.dispose) which is new and not yet idiomatic in most existing JS code, unlike Python's with, standard since 2006.

      Follow-up: once `using` is widely adopted, how closely would it match Python's with/context manager semantics?
      Explain what __exit__'s return value controls, and why returning True is dangerous if misused.

      If __exit__ returns a truthy value, any exception raised inside the with block is suppressed — it does not propagate further. This is intentional for some use cases (e.g. a context manager designed to swallow a specific known exception type), but returning True unconditionally silently hides real bugs, since any exception — expected or not — disappears without a trace.

      Follow-up: how would you write __exit__ to suppress only one specific exception type and let others propagate?
      Walk through exactly what happens the second time a module is imported in the same process.

      Python checks sys.modules first; since the module name is already a key there from the first import, it returns the cached module object directly without re-reading, re-compiling, or re-executing the file's top-level code at all.

      Follow-up: what's a practical consequence of this for module-level code that has side effects, like opening a DB connection at import time?
      What's the risk of reading an entire large log file with .read() instead of iterating line by line?

      .read() loads the entire file content into memory as one string before you can process anything — for a multi-gigabyte file this can exhaust available memory or cause severe slowdowns from swapping. Iterating the file object directly (for line in f:) reads lazily, one line at a time, with roughly constant memory regardless of file size.

      Follow-up: how would this change if you needed random access to specific lines rather than sequential processing?
      How would you implement your own context manager without writing a class, using the standard library?

      contextlib.contextmanager — a decorator that turns a generator function into a context manager: code before yield is __enter__, the yielded value is the as target, and code after yield (in a try/finally) is __exit__. This is often more concise than writing a full class with __enter__/__exit__.

      Follow-up: how do you handle exceptions raised inside the with block when using @contextmanager — where do you catch them?

      Advanced

      Design a context manager that must manage two resources (e.g. a DB connection and a file) and roll back/clean up correctly even if acquiring the second resource fails after the first succeeded.

      The safest pattern nests two separate with statements (or uses contextlib.ExitStack for a dynamic number of resources) rather than acquiring both inside one custom __enter__ — if acquisition of the second resource fails partway through a single combined __enter__, you're responsible for manually unwinding the first resource's acquisition yourself, which is exactly the bug class with normally prevents. Composing standard context managers (nested or via ExitStack) gets this correctness for free.

      Follow-up: how does contextlib.ExitStack help when the number of resources isn't known until runtime?
      Explain the actual mechanics of a circular import in Python and why the failure mode is different from a CommonJS circular require.

      When module A imports module B, which imports module A back, Python finds A already present in sys.modules (inserted before A's body finished executing) and returns that partially-initialized module object — any names A hadn't defined yet by the point of the circular import simply don't exist on it yet, causing an AttributeError or ImportError depending on the exact import style used. CommonJS's require has very similar "partially-initialized module" behavior; ESM's circular imports behave somewhat better due to live bindings and hoisted declarations, which is a meaningful difference if you're comparing to modern JS specifically rather than CommonJS.

      Follow-up: what refactor reliably eliminates a circular import rather than working around it with lazy imports?
      You need to process a 50GB file that doesn't fit in memory, transforming each line and writing to a new file. Design the I/O approach and explain the memory profile.

      Open the input file in read mode and the output file in write mode simultaneously (two nested with statements), and iterate the input file object directly line by line, transforming and writing each line immediately rather than collecting results in a list first. Memory usage stays roughly O(1) relative to file size — only one line (plus any small buffers) is ever resident at once — versus the O(n) blow-up of reading the whole file, transforming a full list, then writing it all out.

      Follow-up: how would buffering (the `buffering` argument to open()) affect throughput here, and when would you tune it?
      Compare Python's module caching (sys.modules) to ESM's module graph in terms of what guarantees each gives about "the module body runs exactly once."

      Both guarantee single execution of a module's top-level code per unique module identity within a process/realm — Python keys this by module name/path in sys.modules; ESM keys it by resolved module specifier in the module graph, with live binding semantics (exported names are references that update if reassigned in the exporting module) that Python's import doesn't replicate — Python imports bind a name to whatever value existed in the module's namespace dict at import time, not a live reference to subsequent reassignments in the general case for `from x import y` style imports.

      Follow-up: demonstrate a case where `from module import value` in Python does NOT see a later reassignment of `value` in the source module, and how you'd restructure to see it.

      Practice Assignments

      Beginner (30-60 min)

      Config file reader with safe defaults

      Write a function that reads a JSON config file using with and pathlib, returning a hardcoded default dict if the file doesn't exist, without ever crashing on a missing file.

      • Must use with open(...), never manual open/close.
      • Must use pathlib.Path, not string concatenation, for the path.

      Acceptance criteria: Running against both an existing and a nonexistent config path produces correct output with no unhandled exceptions.

      Hints

      Check Path.exists() before opening, rather than relying on catching an exception for the missing-file case — both work, but the explicit check is clearer for this exercise.

      Intermediate (2-4 hrs)

      Split a project into modules and demonstrate the import cache

      Build a tiny multi-module project (3+ files: a utils module, a models module, a main script) where the utils module prints a message at import time (module-level side effect). Import the utils module from two different other modules in the project and demonstrate — with printed proof — that the import-time message only prints once across the whole run, regardless of how many places import it.

      • At least one module-level constant and one function per module.
      • A written explanation (3-5 sentences) of why the side-effect message only fires once.

      Acceptance criteria: Running the main script shows the side-effect message exactly once in the output, even though the module is imported from multiple places.

      Hints

      Put a plain print("utils loaded") at the top level of the utils module (not inside a function) to make the import-time execution visible.

      Advanced (1-2 days)

      Build a custom context manager for a "scratch directory"

      Write a class-based context manager ScratchDir that creates a temporary directory on __enter__, yields its path, and recursively deletes it on __exit__ — regardless of whether the block succeeded or raised. Then rewrite the same behavior using @contextlib.contextmanager and compare the two implementations.

      • Must correctly clean up even when the code inside the with block raises an exception.
      • Must not suppress exceptions raised inside the block (verify this explicitly in a test).
      • Include pytest tests verifying the directory exists during the block and is gone afterward, both on success and on a forced exception.

      Acceptance criteria: Both implementations pass the same test suite, and the directory is reliably cleaned up in all tested scenarios. No full solution here — this is meant to build real intuition about the protocol, not follow a recipe.

      Quick Revision Cheat Sheet

      • Python file I/O is synchronous/blocking by default — opt in explicitly for async or threaded I/O.
      • Always use with open(...) — guarantees cleanup via __exit__ even on exceptions.
      • Always pass encoding="utf-8" explicitly — platform defaults differ and cause "works on my machine" bugs.
      • Any object implementing __enter__/__exit__ can be used with with; @contextlib.contextmanager gives a generator-based shortcut.
      • Prefer pathlib.Path over manual string path concatenation.
      • json.load/json.dump work directly on file objects — no need to round-trip through a string.
      • Imports resolve via sys.path and cache in sys.modules — a module's body runs exactly once per process.
      • Mode "w" truncates immediately on open — use "a" to append without destroying existing content.
      • Iterate large files line by line instead of .read()-ing the whole thing into memory.
